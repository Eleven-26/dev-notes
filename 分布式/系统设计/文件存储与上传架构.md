# 文件存储与上传架构

> 文件服务器怎么选型（Ceph vs 对象存储），以及视频上传该直传还是中转——同一原则「业务节点只做计算、数据一律中心化」的两个侧面。

## Q1. 文件服务器如何选型？（Ceph vs 对象存储）

**来源**：`p=15` 百度 Go 前端一面 · 时长 13分36秒
**考察意图**：**这题考的是"选型方法"而不是"性能对比"**——
面试官想听你先问需求，而不是先比较参数。

### 选型第一原则（先答这个）

> **从需求出发，从熟悉程度出发，而不是从性能出发。**

原因：
- **成型的文件系统不会有太拉垮的性能**，性能差异通常在百分之几；
- 很多业务**根本到不了需要考虑那百分之几性能的量级**；
- 所以更该关注的是：**哪个方案能更好解决实际问题、团队更熟悉哪个**。

### 三类方案的适用场景

#### ① 分布式文件系统（Ceph 等）—— 需要共享

**场景**：K8s 环境。所有容器/Pod **部署在多台机器上**，机器之间需要**共享文件或磁盘**。

具体例子：
- 在 K8s 里搭建 **Docker 私有镜像仓库**，把镜像都存在一个位置，
  **所有集群节点共享同一个文件系统**（镜像存在这里）；
- **有状态应用**（etcd、Redis、MySQL）：每个 Pod 需要一块**独立的存储块设备**（RBD），
  这类也用 Ceph 提供。

**原理**：把设备以**类似网盘 / 共享文件夹**的形式**挂载到操作系统**的某个目录上。
对使用者来说，**操作它就是复制文件到目录、从目录取文件**，
与本地文件夹**几乎没有区别**。

**唯一区别**：**挂载动作需要权限校验**，之后的读写就不需要了。
好处是**隐藏了文件上传/下载的细节**——开发时就像操作本地目录。

#### ② 对象存储（COS / OSS 等）—— 不需要共享

**场景**：普通网站里的**图片、用户头像**等静态文件。

特征：
- **不需要在多个操作系统/节点之间共享**；
- 只需要**持久化保存**，以及**偶尔被用户查看**。

满足这两点，用对象存储就够了。

### 传输失败怎么办？（第二问）

取决于**上传方式**——如果是"业务服务器上传到文件服务器"，失败处理如下：

**① 断点续传 + 重试**

重试要做**退避策略**，不要无脑重试：

```
第 1 次失败 → 5 秒后重试
第 2 次失败 → 10 秒后重试
第 3 次失败 → 1 分钟后重试
第 4 次失败 → 5 分钟后重试
最多重试 5~10 次
```

**为什么要退避**：
- **正常的请求**（如网络抖动）重试一两次就会成功；
- **不正常的请求**（如资源不存在、权限错误）**重试多少次都不会成功**，
  只会白白消耗资源。

**② 监控告警**

- 用 **Prometheus** 监控文件服务器，或由业务服务器**上报失败指标**；
- 多次失败后通过**邮件 / 企业微信**通知开发人员，及时感知重试情况。

### 要不要经过业务服务器？（第三问，加分点）

**判断标准很简单**：

> **如果文件上传到业务服务器后"什么都不做"，只是原样转发给文件服务器，
> 那就没有理由经过业务服务器——直接绕过。**

**绕过的好处（前端直传对象存储）**：
- 文件从客户端 → 业务服务器 → 对象存储，**要走两次网络**
  （消耗两次带宽，也消耗两倍时间）；
- 直传只有**一次上传**，**减少一次上传时间，同时大幅降低业务服务器负载**。

**必须经过业务服务器的例外**：
- 文件**需要在业务侧处理**，例如报表文件需要**导入数据库**；
- 处理完之后，再把文件**备份到文件服务**。

### COS 直传的两步实现（以腾讯云 COS 为例）

| 步骤 | 谁做 | 内容 |
|---|---|---|
| **① 换临时密钥** | 后端 | 用**永久密钥换取临时密钥**，临时密钥有**有效期**（如 30 分钟 / 1 小时）——避免把永久密钥暴露给前端 |
| **② 生成预签名 URL** | 后端 | 根据文件名等信息**签名**，下发预签名上传地址和访问地址 |
| **③ 上传** | 前端 | 对预签名 URL 发 **PUT** 请求，**以二进制方式**传输文件内容 |

**验证方式**：上传返回 **HTTP 200** 即表示成功，可直接用返回的访问地址下载核对内容。

> **安全要点**：**前端永远拿不到永久密钥**，只拿到**有时效的临时凭证和预签名 URL**，
> 即使泄露也只在有效期内可用。

### 落地实现：直传凭证的最小可运行骨架（Go，已编译校验 + 已测）

> 正文给了三步（换临时密钥 / 生成预签名 URL / 前端 PUT），
> 但那句"**前端永远拿不到永久密钥**、即使泄露也只在有效期内可用"是**一句可以被测出来的话**。
> 这一节就把凭证写成能跑的实现，再用篡改测试逐条验证。
>
> **校验口径**：`go build` / `go vet` / `gofmt -l` 通过（go 1.26，纯标准库），
> 下面的表是 `go test` 的真实输出。
>
> ⚠️ 这里实现的是**通用 HMAC 预签名**（结构与 AWS SigV4 / 腾讯云 COS 一致，但字段名和算法不同）。
> **接真实对象存储时请直接用官方 SDK 的 PresignedUpload**，不要拿这套签名去对厂商的格式。

```go

package upload

import (
	"crypto/hmac"
	"crypto/sha256"
	"encoding/hex"
	"errors"
	"fmt"
	"net/http"
	"net/url"
	"strconv"
	"strings"
	"time"
)

// 直传的落地形态只有三件事：**后端签名、前端 PUT、后端只发凭证**。
// 正文那句"前端永远拿不到永久密钥"在这段代码里是可验证的：
// 前端拿到的是**一个带过期时间的签名串**，拿不到 secret 本身。
//
// ⚠️ 这里实现的是**通用 HMAC 预签名**（与 AWS SigV4 / 腾讯云 COS 的字段不同但结构一致），
// 用来把"签名 → 校验 → 过期"这条链路跑通并测出行为。
// **接真实对象存储时请直接用官方 SDK 的 PresignedUpload**，不要手改这套签名格式。

// Policy 是一次上传的授权范围。**签名必须把所有授权字段全签进去**：
// 只签 key 的话，前端把 size 上限或有效期改掉，签名照样通过 = 授权形同虚设。
//
// 注意这里**没有 secret 字段**——secret 只作为参数传给 Sign/Verify。
// 混进结构体就会被顺手 JSON 序列化下发出去，正文"前端永远拿不到永久密钥"那句就破功了。
type Policy struct {
	Key         string    // 对象键，通常带用户前缀：uid/2026/09/uuid.png
	MaxSize     int64     // 字节
	ExpireAt    time.Time // 过期时刻（UTC）
	ContentType string    // 允许的 Content-Type，空 = 不限
}

// canonical 是签名覆盖的原文。**签发和校验必须走同一个函数、同一套字段顺序**，
// 否则就会踩中"签名算法两边各写一遍、某天对不上"这个经典事故。
func canonical(method, key, max, ctype, exp string) string {
	return strings.Join([]string{method, key, max, ctype, exp}, "\x00")
}

func (p Policy) canonical() string {
	return canonical(http.MethodPut, p.Key, strconv.FormatInt(p.MaxSize, 10), p.ContentType,
		p.ExpireAt.UTC().Format(time.RFC3339))
}

// signWith 是**唯一的**签名实现：签发与校验必须共用同一个函数。
// 两边各写一遍是这类手工签名最常见的事故——某天字段顺序变了，
// 只有服务端发现，前端已经发出去的一批 URL 全在报 403。
func signWith(secret, canon string) string {
	mac := hmac.New(sha256.New, []byte(secret))
	mac.Write([]byte(canon))
	return hex.EncodeToString(mac.Sum(nil))
}

// Sign 对授权字段做 HMAC-SHA256。字段间用 \x00 分隔，
// 避免"字段里含分隔符"造成签名歧义（拼接式签名的经典坑）。
func (p Policy) Sign(secret string) string { return signWith(secret, p.canonical()) }

// PresignedURL 是给前端的完整地址：凭证全在 query 里，前端不需要任何密钥。
//
// ⚠️ 必须用 url.Values 编码，不能手拼字符串：对象键是用户可影响的输入，
// 里面出现 & 或 + 时手拼会把参数结构改掉（等价于参数注入）。
func (p Policy) PresignedURL(host, secret string) string {
	q := url.Values{}
	q.Set("key", p.Key)
	q.Set("max", strconv.FormatInt(p.MaxSize, 10))
	q.Set("ctype", p.ContentType)
	q.Set("exp", p.ExpireAt.UTC().Format(time.RFC3339))
	q.Set("sig", p.Sign(secret))
	return strings.TrimSuffix(host, "/") + "/upload?" + q.Encode()
}

// 下面每种拒绝原因都要**分开打点**：只报一个模糊的 403，线上就查不动"为什么传不上去"。
var (
	ErrNoSecret  = errors.New("upload: 服务端未配置 secret")
	ErrNoCred    = errors.New("upload: 凭证字段缺失")
	ErrBadSign   = errors.New("upload: 签名不匹配（被篡改或密钥不一致）")
	ErrBadFormat = errors.New("upload: 凭证字段格式非法（签发端与校验端不一致）")
	ErrExpired   = errors.New("upload: 凭证已过期")
	ErrTooLarge  = errors.New("upload: 超过授权大小")
	ErrBadType   = errors.New("upload: Content-Type 不在授权范围内")
	ErrBadMagic  = errors.New("upload: 文件头与允许类型不符（伪造扩展名）")
)

// Verify 是接收端（或网关）的校验。
//
// ★ 顺序就是这段代码的意义：**先验签，再信字段**。
// 如果先解析 max/exp 去判断大小和过期，攻击者只要改一个字段就能绕开限制——
// 未验签的输入一律当作不可信，格式错误也必须在验签之后才可能出现在"合法"凭证上。
func Verify(r *http.Request, secret string, now time.Time) error {
	if secret == "" {
		return ErrNoSecret
	}
	q := r.URL.Query()
	key, maxS, expS, ctype, sig :=
		q.Get("key"), q.Get("max"), q.Get("exp"), q.Get("ctype"), q.Get("sig")
	if key == "" || sig == "" || expS == "" {
		return ErrNoCred
	}
	// 1) 用**原始字符串**重算签名再比对（定时安全比较，不要用 ==）
	if !hmac.Equal([]byte(signWith(secret, canonical(http.MethodPut, key, maxS, ctype, expS))), []byte(sig)) {
		return ErrBadSign
	}
	// 2) 验签通过后字段就是自己签出去的，这里解析失败只可能是两端格式不一致
	max, err1 := strconv.ParseInt(maxS, 10, 64)
	exp, err2 := time.Parse(time.RFC3339, expS)
	if err1 != nil || err2 != nil {
		return ErrBadFormat
	}
	if !now.Before(exp) {
		return ErrExpired
	}
	if r.ContentLength > max {
		return ErrTooLarge
	}
	if ctype != "" && !strings.EqualFold(r.Header.Get("Content-Type"), ctype) {
		return ErrBadType
	}
	return nil
}

// magicOf 按文件头判断真实类型。**扩展名和 Content-Type 都是客户端说了算的**，
// 只要文件之后会被浏览器直接打开，就必须校验文件头：
// 别人传一个"后缀 .png 内容是 HTML"的片子，访问时被当网页执行 = 存储型 XSS。
// （这也是正文 Q2"文件别放业务服务器"的延伸：放在自己域名下时，这类漏洞算你头上。）
func magicOf(b []byte) (string, bool) {
	head := func(n int) string {
		if len(b) < n {
			return ""
		}
		return hex.EncodeToString(b[:n])
	}
	switch {
	case strings.HasPrefix(head(8), "89504e470d0a1a0a"):
		return "image/png", true
	case strings.HasPrefix(head(3), "ffd8ff"):
		return "image/jpeg", true
	case strings.HasPrefix(head(6), "474946383761"), strings.HasPrefix(head(6), "474946383961"):
		return "image/gif", true
	case len(b) >= 12 && string(b[4:8]) == "ftyp":
		return "video/mp4", true
	default:
		return "", false
	}
}

// CheckMagic 校验开头的若干字节：真实类型必须是 allow 里的一个。
func CheckMagic(head []byte, allow []string) error {
	got, ok := magicOf(head)
	if !ok {
		return fmt.Errorf("%w: 认不出文件头", ErrBadMagic)
	}
	for _, a := range allow {
		if a == got {
			return nil
		}
	}
	return fmt.Errorf("%w: 实际 %s 不在允许列表 %v", ErrBadMagic, got, allow)
}

```

#### 实测：把正文那句"安全要点"逐条攻击一遍

| 攻击 / 场景 | 结果 | 说明 |
|---|---|---|
| 正常凭证 PUT | **通过** | 下发的 URL 里只有 `sig=`，**不含 secret** |
| 把 `max` 改大到 1GB | 签名不匹配 | 大小上限**被签进了签名**，改不动 |
| 把有效期延到 10 年后 | 签名不匹配 | 同上——"只在有效期内可用"是这么保证的 |
| 换 `key` 写到别人目录（越权） | 签名不匹配 | 对象键也在签名里 |
| 把 `ctype` 清空以放开类型 | 签名不匹配 | 连"留空"这个动作都会改变签名 |
| 直接去掉 `sig` | 凭证字段缺失 | 与"签名不对"分开打点 |
| 用另一把服务端 secret 校验 | 签名不匹配 | 密钥轮换期间的双验要自己加，这里只演示单密钥 |
| 凭证过期 1 小时后使用（签名仍合法） | **凭证已过期** | 校验的是 `now`，**不是客户端时间** |
| `Content-Length` 超过 `max` | 超过授权大小 | 签名合法也拦得住实际大小 |
| 声明 `image/png` 实际发 HTML | 类型不符 / 文件头认不出 | **扩展名与 Content-Type 都不可信**，必须看文件头 |

#### 三条只有写出来才会注意到的点

1. **先验签、再信字段**：`Verify` 里判断大小和过期的 `max`/`exp` 都来自 query，
   如果解析在比对之前，攻击者改字段就能绕限制——**顺序本身就是安全属性**。
2. **签发与校验共用 `canonical` + `signWith`**：两处各写一遍签名逻辑，
   早晚会不一致（表现为"一部分前端拿的 URL 突然全 403"）。
   比对签名用 `hmac.Equal` 而不是 `==`。
3. **凭证里不能塞 secret 字段**、query 必须用 `url.Values` 编码：
   前者会被顺手 JSON 下发，后者在手拼时会被 `&`/`+` 改变参数结构。

> **面试时怎么把这段讲出来**：正文的三步是流程，
> 这段代码回答的是"**为什么这样就不会泄露密钥**"——
> 因为授权范围（键名、大小、类型、有效期）**全都在签名里，改任何一项签名就废**，
> 而且**过期判断用的是服务端时间**。能补上这一句，这题就从"背流程"变成"懂原理"。

## Q2. 视频文件上传：放业务服务器和放文件服务器有什么差异？

**来源**：`BV1xSRXBwEeM p=40` 百度 Go 实习二面 · 时长 6分55秒
**考察意图**：表面在问"文件放哪"，实际考的是**"无状态 vs 有状态"这条分布式设计的基本原则**——
文件放业务服务器，就把一个无状态服务变成了有状态服务。

### 一、先看部署结构

```
客户端 → 网关（负载均衡）→ [业务服务器1 | 业务服务器2 | 业务服务器3] → 文件服务器集群
```

### 二、核心结论：文件放业务服务器 = 把服务做成"有状态"

| 维度 | **文件放业务服务器（本地）** | **文件放文件服务器（中心化）** |
|---|---|---|
| **服务状态** | 每个节点存的内容都不一样（A 存 A 文件、B 存 B 文件）→ **变成有状态服务，跟数据库一样** | 业务节点**不存任何数据，只做计算** → **无状态** |
| **扩缩容** | 扩容的新节点**没有历史文件**；缩容**要撤掉的节点上还挂着文件** → **不敢缩** | 加机器 / 减机器只影响算力，**随时可扩可缩** |
| **路由复杂度** | 负载均衡过后"**到底该访问哪台服务器**"不知道 → 只能再维护一份"文件↔节点"映射 | 文件的定位由**文件系统自己解决**，业务侧不关心 |
| **本质** | 相当于**自己在开发一套文件系统**，而且和业务**深度耦合** | 业务只调**标准接口 / SDK**，背后怎么实现完全隐藏 |
| **带宽** | 客户端 → 业务服务器 → 文件系统，**走两次网络** | 直传只走一次（详见 Q1） |

### 三、为什么必须做无状态（最值钱的一句）

> **业务服务器要尽可能做到无状态——本地不保存任何数据，只做计算。**
>
> 这样：**流量激增 → 直接加机器加节点，处理能力立刻变强**；
> **流量回落 → 把多余资源撤下来**。整个过程**没有任何数据迁移问题**。

**换个角度理解**：这和"为什么要用中心化的 Redis 缓存、中心化的 DB"是**同一件事**——

> 把数据放到数据中心、缓存放到缓存中心、Session 放到 Session 中心、**文件放到文件中心**，
> 业务服务器只通过标准接口调用它们。
> **文件系统用 Ceph 也好、对象存储也好、自研也好，对业务服务器都是隐藏的，业务只关心调用结果。**

### 四、和 Q1 的关系（避免答串）

| | **Q1（追问：要不要经过业务服务器）** | **本题（Q2）** |
|---|---|---|
| 关注点 | **链路效率与安全**：能不能前端直传、临时密钥怎么签发 | **服务架构**：文件存在业务节点会把服务做成有状态 |
| 结论 | 中间"什么都不做"就直传，避免多一次网络与带宽消耗 | 文件**存**在业务节点本地 → 破坏无状态、扩缩容受阻 |

> 两题其实是**同一原则的两个侧面**：**业务节点只做计算，数据一律中心化。**

### 面试官会追问什么

- **文件放业务服务器，就一定要自己实现文件系统吗？** → 是的。
  因为请求轮询到哪台不确定，**你就得维护"文件在哪台节点"的映射**——
  这份映射加上定位逻辑，就是文件系统在做的事（相当于自己造一个）。
- **业务节点一点都不缓存文件吗？** → 可以缓存（如本地磁盘做 CDN 前置），
  但**缓存必须可重建、可淘汰**，不能是"唯一副本"，否则又变回有状态。
- **无状态服务的代价是什么？** → **每次都要走网络访问中心化存储**，
  延迟高于本地读写 → 用**缓存、CDN、就近接入**来补。
- **有状态服务就一定是错的吗？** → 不是。**数据库、缓存、消息队列本身就是有状态的**，
  关键是**把"状态"收敛到专门的有状态系统里**，而不是散落在业务节点上。
