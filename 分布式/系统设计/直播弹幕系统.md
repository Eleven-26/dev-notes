## Q1. 场景题：设计一个直播弹幕系统

**来源**：`p=10` 抖音 Go 一面 · 时长 6分59秒
**考察意图**：开放设计题。**面试官不是要一个完美方案，而是要看你的分层思路**，
然后他会补充条件、提出疑问，你再迭代——**这个过程本身就是考察内容**。

### 面试方法论（先讲这个，比方案本身更加分）

> 场景设计题的节奏是：**先给出大体思路 → 与面试官讨论需求和现有资源约束 →
> 他补充关键元素或提出疑问 → 你据此调整设计 → 逐步完善**。
>
> **它不是一开始就有一个一成不变的设计**。有缺陷没关系，**关键是必须要有思路能拿出来讨论**。

### 完整设计（四层）

#### 第 1 层：接入限流（防刷屏）

客户端发弹幕 → 服务端**第一步先限流**：

- 限流维度：**按用户 / 设备 ID / 客户端**；
- 频率：如 10 分钟 1 条、1 分钟 1 条——**由业务需求决定**；
- 触发限流 → **直接丢弃**，不再往下走。

#### 第 2 层：双路径分流

通过限流后，弹幕数据要走**两条路**：

| 路径 | 目的 |
|---|---|
| **推送链路** | 推送到前端**实时展示** |
| **持久化链路** | 保存数据，供**直播回放**展示或**弹幕数据分析** |

#### 第 3 层：持久化 —— 为什么必须走缓存

**弹幕数据的特征**：
- 属于**娱乐性数据**，重要性低，**丢几条不影响业务**，不涉及经济损失和核心体验；
- **生产成本极低**——用户只需编辑发送，没有任何成本门槛；
- 因此**发送频率极高**（即使加了限流，量依然很大）。

**为什么不能直接写数据库**：

> 如果每发一条弹幕就写一次库，**弹幕的写入 TPS 会和数据库的查询 TPS 相当**，
> 而这类高频插入正是数据库最不擅长的。

**方案**：
1. **先写入 Redis 缓存**（读写性能远高于 MySQL 这类数据库）；
   - 代价：缓存可能因主动淘汰丢数据——但对弹幕来说，**丢了就丢了，可以接受**；
2. **通过定时任务或消息队列批量落库**；
3. 落库目标可选**关系型数据库**或 **MongoDB 这类文档型数据库**，取决于具体方案。

> **原则**：尽量避免"每条新数据都写一次库"，**尽可能改成批量操作**。

#### 第 4 层：推送链路 —— 用 Redis 发布订阅打通分布式节点

**问题**：服务端是**分布式部署**的，前面有负载均衡：
- 一个请求**具体落到哪台服务器不确定**；
- 用户的 **WebSocket 长连接建立在哪台服务器上也不确定**（可能连 1 号、2 号、3 号都能连）。

**如果只靠单机内存维护连接映射，就会出现"弹幕推给了没有这个连接的机器"**。

**解法：引入 Redis 发布订阅**

```text
所有服务器都订阅同一个主题
        ↓
收到弹幕数据的服务器 → PUBLISH 到该主题
        ↓
所有持有 WebSocket 连接的服务器都能收到通知
        ↓
各自通过 WebSocket 推送给自己的在线用户
```

这样，**弹幕的推送不再依赖"用户恰好连在哪台机器"**。

### 面试时怎么讲

1. **先给框架**：限流 → 双路径（实时推送 + 持久化）；
2. **主动解释关键权衡**：弹幕可容忍丢失 → 所以缓存优先、批量落库；
3. **主动暴露分布式的坑**：负载均衡下连接位置不确定 → 所以需要发布订阅；
4. **等面试官追问**：他会补充元素或质疑设计，你据此迭代。

### 落地实现：最小可运行骨架（Go，已编译校验 + 已实测）

> 本篇是**纯设计题**，所以没有"客户端怎么连"的使用方法章节，而是把上面四层
> 落成一份**能跑、能测出数字**的骨架——四层各自对应一个文件，
> 顺序就是数据流经它们的顺序。
>
> **校验口径**：`go build` / `go vet` / `gofmt -l` 全部通过（go 1.26、`github.com/redis/go-redis/v9 v9.22.0`）；
> 下面所有表格都是 `go test` 在本机的**实测输出**。
>
> ⚠️ **只有 `RedisPublisher` 没连真实 Redis 跑过**（本机没有 Redis 实例）——
> 它只做了编译校验，"Pub/Sub 不保留消息""订阅独占连接"这两条语义
> 沿用 [发布订阅.md](../../数据存储/redis/发布订阅.md) 的 Q1（两种发布订阅对比）与官方文档。
> 跨机器那一维是用**进程内 `Bus`** 顶替验证的：
> **它只能证明"逻辑对不对"，证明不了网络与多进程**。
>
> 结构是语言无关的——**下面「Java 版骨架」把这四段逐类型搬了一遍并重新实测**，
> 两处最容易走样的原语是
> `atomic.Pointer[[]*Sub]` → `AtomicReference<List<Sub>>`、`select{case ch<-m: default}` → `offer` + 有界 `ArrayBlockingQueue`。

**四层各自的落点**：

| 正文层级 | 落点类型 | 必须记住的那一句 |
|---|---|---|
| 第 1 层 限流 | `Limiter` 接口 + `FixedWindow` | 触发限流**直接丢弃**，不进入后面任何链路 |
| 第 2 层 双路径 | `Node.Accept` | 一个方法里同时喂**推送**（Publish）和**持久化**（Enqueue）两条路 |
| 第 3 层 批量落库 | `BatchWriter` | 攒批 + 定时 + **队列满就丢并计数**，三个开关缺一个就是事故 |
| 第 4 层 跨节点扇出 | `Publisher` / `RedisPublisher` / `Bus` + `Room` | 订阅关系用 **copy-on-write 快照**，慢连接用**非阻塞投递**隔离 |

#### 骨架 ①：数据面 + 第 1 层限流 + 第 4 层的抽象与 Redis 实现

```go
package barrage

import (
	"context"
	"strings"
	"sync"
	"time"

	"github.com/redis/go-redis/v9"
)

// Msg 是一条弹幕。Seq 由服务端分配，客户端用它做去重和乱序重排。
type Msg struct {
	Room string `json:"room"`
	UID  string `json:"uid"`
	Text string `json:"text"`
	Seq  int64  `json:"seq"`
}

// Encode/Decode 是推送与订阅两端的线格式。
//
// ⚠️ 这里**故意用 tab 分隔而不是 JSON**：正文第 4 层说"弹幕量极大"，
// 而序列化开销是**乘在推送链路上的**。实测（同一条弹幕：房间名 12 字符 + uid 9 字符 + 6 个汉字）：
// 线格式 48 字节，encoding/json 82 字节，**省 1.7 倍**；
// 换成 Protobuf 还能再小一半以上（字段名不进载荷，见 network/数据序列化.md 使用一的实测）。
// 一句话：**这里省的不是 CPU，是每台机器每秒几万条 × 连接数的那份带宽。**
func (m Msg) Encode() string {
	return strings.Join([]string{m.Room, m.UID, m.Text}, "\t") + "\t" + itoa(m.Seq)
}

func Decode(s string) (Msg, bool) {
	p := strings.SplitN(s, "\t", 4)
	if len(p) != 4 {
		return Msg{}, false
	}
	return Msg{Room: p[0], UID: p[1], Text: p[2], Seq: atoi(p[3])}, true
}

func itoa(v int64) string {
	if v == 0 {
		return "0"
	}
	var b [20]byte
	i := len(b)
	neg := v < 0
	if neg {
		v = -v
	}
	for v > 0 {
		i--
		b[i] = byte('0' + v%10)
		v /= 10
	}
	if neg {
		i--
		b[i] = '-'
	}
	return string(b[i:])
}

func atoi(s string) int64 {
	var v int64
	for _, r := range s {
		if r < '0' || r > '9' {
			return v
		}
		v = v*10 + int64(r-'0')
	}
	return v
}

// ── 第 1 层：限流 ─────────────────────────────────────────────────────────

// Limiter 只暴露一个方法，方便接 distributed/限流降级熔断.md 里的 RedisLimiter。
// 算法本身那篇已经写透了，这里只保留**接入点**。
type Limiter interface {
	Allow(ctx context.Context, uid string) bool
}

// FixedWindow 是"1 分钟 1 条"级别的最小占位实现（单机、按 uid）。
// 它只够跑通链路和做实验；**多节点部署时限流必须换成共享计数**，
// 否则 N 台机器各放一遍 = 实际限额是配置值的 N 倍。
type FixedWindow struct {
	mu   sync.Mutex
	seen map[string]time.Time
	dur  time.Duration
}

func NewFixedWindow(dur time.Duration) *FixedWindow {
	return &FixedWindow{seen: map[string]time.Time{}, dur: dur}
}

func (w *FixedWindow) Allow(_ context.Context, uid string) bool {
	w.mu.Lock()
	defer w.mu.Unlock()
	if t, ok := w.seen[uid]; ok && time.Since(t) < w.dur {
		return false // 触发限流：直接丢弃，不进入后续任何链路
	}
	w.seen[uid] = time.Now()
	return true
}

// ── 第 4 层：跨节点扇出的抽象 ────────────────────────────────────────────

// Publisher 是"把一条弹幕广播给所有节点"这件事的接口。
// 两个实现：RedisPublisher（生产）与 Bus（本机跑通链路、做实验）。
type Publisher interface {
	Publish(ctx context.Context, topic string, m Msg) error
	Subscribe(ctx context.Context, topic string, handler func(Msg)) (cancel func(), err error)
	Seq(ctx context.Context, topic string) (int64, error)
}

// RedisPublisher 用 Redis 发布订阅打通分布式节点（正文第 4 层）。
//
// ⚠️ 两个生产注意点（正文没提，但踩了才知道）：
//  1. **订阅必须用单独的连接**：rdb.Subscribe() 会独占一条连接，
//     拿它去干别的命令会一直阻塞——所以 Client 是单例，但 Subscript 是独立长连接。
//  2. **Pub/Sub 不保留消息**：节点订阅之前发的消息**永久丢失**，
//     断线重连后要用 Seq 从持久化链路补齐（见 barrage_4.go 的 BatchWriter）。
type RedisPublisher struct{ RDB *redis.Client }

func (p RedisPublisher) Publish(ctx context.Context, topic string, m Msg) error {
	return p.RDB.Publish(ctx, topic, m.Encode()).Err()
}

func (p RedisPublisher) Subscribe(ctx context.Context, topic string, handler func(Msg)) (func(), error) {
	sub := p.RDB.Subscribe(ctx, topic)
	ch := sub.Channel(redis.WithChannelSize(1024)) // 有界：慢消费者会在这里丢消息，而不是打爆内存
	go func() {
		for s := range ch {
			if m, ok := Decode(s.Payload); ok {
				handler(m)
			}
		}
	}()
	return func() { _ = sub.Close() }, nil
}

// Seq 用 INCR 拿全局递增序号（**它是"补漏"的依据**，不只是排序）。
func (p RedisPublisher) Seq(ctx context.Context, topic string) (int64, error) {
	return p.RDB.Incr(ctx, topic+":seq").Result()
}
```

> **`Client` 必须是单例**：`RedisPublisher{RDB: ...}` 只持有指针，
> 整个进程共用一个 `*redis.Client`（写法见 [缓存问题与方案.md](../../数据存储/redis/缓存问题与方案.md) 使用一的「前置：中间件实例必须是单例」）。
> 每个房间、每条连接各建一个 client，等于把连接池按请求数放大。

#### 骨架 ②：第 4 层的连接侧 —— 慢连接怎么隔离（`Sub` / `Room`）

```go
package barrage

import (
	"sync"
	"sync/atomic"
)

// Sub 是"一条 WebSocket 长连接"的抽象：正文第 4 层的所有结论都落在这个类型上。
//
// ★ 两个必须想清楚的点（正文只说了"各自推送给自己的在线用户"）：
//  1. 每个连接一个**有界**缓冲，而不是无界队列——
//     一个卡住的客户端（弱网、手机切后台）会把整房间的消息堆在自己队列里，
//     最终 OOM 的是**服务端**，不是客户端。
//  2. 投递用 **select + default 的非阻塞发送**：队满就丢并计数。
//     正文说"丢几条不影响业务"，这就是那句判断的代码形态——
//     **宁可丢，也绝不能让一个慢连接阻塞整个房间的广播**。
type Sub struct {
	ID string

	out     chan Msg
	dropped atomic.Int64
	sent    atomic.Int64
	closed  atomic.Bool
	once    sync.Once
}

func NewSub(id string, buf int) *Sub {
	return &Sub{ID: id, out: make(chan Msg, buf)}
}

func (s *Sub) trySend(m Msg) bool {
	if s.closed.Load() {
		return false
	}
	select {
	case s.out <- m:
		s.sent.Add(1)
		return true
	default:
		s.dropped.Add(1) // 慢客户端：丢这一条，继续服务别人
		return false
	}
}

// Out 交给该连接的写协程消费（真实项目里这里就是 ws WriteMessage 循环）。
func (s *Sub) Out() <-chan Msg { return s.out }

// Sent / Dropped 必须暴露给监控：**丢弃率是弹幕系统的健康度指标**。
// 只报 QPS 不报丢弃率，等于把"用户看不到弹幕"这件事藏起来。
func (s *Sub) Sent() int64    { return s.sent.Load() }
func (s *Sub) Dropped() int64 { return s.dropped.Load() }

// Close 幂等：主动离开、心跳超时、连接断开三条路径都会走到这里。
func (s *Sub) Close() {
	s.once.Do(func() {
		s.closed.Store(true)
		close(s.out)
	})
}

// Room 是一个房间的订阅集合。
//
// ★ 广播**读多写少**（每秒上千次广播、偶尔进出），
// 所以用 copy-on-write 快照，而不是"广播时持锁遍历 map"：
// 广播路径只 Load 一个指针；加人/踢人才整体换切片。
// 这和《服务发现与负载均衡》使用一里 Resolver 的 Snapshot 是同一个手法。
type Room struct {
	name string

	mu     sync.Mutex
	subs   map[string]*Sub
	snap   atomic.Pointer[[]*Sub]
	seq    atomic.Int64
	online atomic.Int64
}

func NewRoom(name string) *Room {
	r := &Room{name: name, subs: map[string]*Sub{}}
	empty := []*Sub{}
	r.snap.Store(&empty)
	return r
}

func (r *Room) Name() string { return r.name }

// Join 挂上一条连接并重建快照。重复 Join 同一个 ID 视作重连：先摘旧的。
func (r *Room) Join(s *Sub) {
	r.mu.Lock()
	if old, ok := r.subs[s.ID]; ok && old != s {
		delete(r.subs, s.ID)
		old.Close()
	}
	r.subs[s.ID] = s
	list := r.lockedListLocked()
	r.mu.Unlock()

	r.snap.Store(&list)
	r.online.Store(int64(len(list)))
}

// Leave 摘掉连接。**必须幂等**，且要 Close 释放那条连接的缓冲与写协程。
func (r *Room) Leave(id string) {
	r.mu.Lock()
	s, ok := r.subs[id]
	if !ok {
		r.mu.Unlock()
		return
	}
	delete(r.subs, id)
	list := r.lockedListLocked()
	r.mu.Unlock()

	r.snap.Store(&list)
	r.online.Store(int64(len(list)))
	s.Close()
}

// lockedListLocked 调用方必须持锁：把 map 摊成一份不可变切片。
func (r *Room) lockedListLocked() []*Sub {
	list := make([]*Sub, 0, len(r.subs))
	for _, s := range r.subs {
		list = append(list, s)
	}
	return list
}

// Online 返回当前连接数（读快照长度，不进临界区）。
func (r *Room) Online() int64 { return r.online.Load() }

// Broadcast 尽力投递给房间内所有连接，返回成功条数。
//
// 这里**没有锁**：慢连接的成本已经被 trySend 的 default 分支付掉了。
// 也**不改写 m.Seq**——序号在入口（Node.Accept）统一分配，
// 广播层再分配一次就会和持久化链路里的序号对不上，客户端没法去重。
func (r *Room) Broadcast(m Msg) int {
	list := *r.snap.Load()
	ok := 0
	for _, s := range list {
		if s.trySend(m) {
			ok++
		}
	}
	return ok
}
```

#### 骨架 ③：第 4 层的节点侧 —— `Node.Accept` 就是把四层串起来的顺序

```go
package barrage

import (
	"context"
	"fmt"
	"sync"
	"sync/atomic"
)

// Bus 是 Publisher 的**进程内实现**：用来在没有 Redis 的机器上跑通链路、做实验。
//
// 语义与 Redis Pub/Sub 对齐：
//   - 只投递给"当前已订阅该 topic"的处理函数（**不保留历史**）；
//   - 一次 Publish = 同步调用该 topic 的全部订阅者。
//
// ⚠️ 它是**单进程**的，只能验证"逻辑对不对"；
//
//	"跨机器"那一维必须由 RedisPublisher 承担（见 barrage_1.go）。
type Bus struct {
	mu   sync.Mutex
	next int64
	hand map[string]map[int64]func(Msg)
	snap atomic.Pointer[map[string][]func(Msg)]

	seq   atomic.Int64 // 进程内发号器（Redis 版是 INCR）
	noSub atomic.Int64 // 发出时该 topic 一个订阅者都没有 = 正文说的"推给了没有连接的机器"
}

func NewBus() *Bus {
	b := &Bus{hand: map[string]map[int64]func(Msg){}}
	m := map[string][]func(Msg){}
	b.snap.Store(&m)
	return b
}

// buildSnapshotLocked 由 hand 重算快照。调用方必须持锁。
// 读路径只 Load 指针、遍历时无锁，所以订阅关系变化不阻塞弹幕广播。
func (b *Bus) buildSnapshotLocked() map[string][]func(Msg) {
	out := make(map[string][]func(Msg), len(b.hand))
	for topic, hs := range b.hand {
		list := make([]func(Msg), 0, len(hs))
		for _, f := range hs {
			list = append(list, f)
		}
		out[topic] = list
	}
	return out
}

// Publish 把消息交给该 topic 的所有订阅者。
func (b *Bus) Publish(_ context.Context, topic string, m Msg) error {
	list := (*b.snap.Load())[topic]
	if len(list) == 0 {
		b.noSub.Add(1) // **静默丢失**：这就是 Pub/Sub 的语义，也是它必须配持久化链路的原因
		return nil
	}
	for _, f := range list {
		f(m)
	}
	return nil
}

// Subscribe 返回 cancel。**必须能用 cancel**：节点下线、房间关闭时不取消就会双份投递。
func (b *Bus) Subscribe(_ context.Context, topic string, handler func(Msg)) (func(), error) {
	b.mu.Lock()
	if b.hand[topic] == nil {
		b.hand[topic] = map[int64]func(Msg){}
	}
	id := b.next
	b.next++
	b.hand[topic][id] = handler
	snap := b.buildSnapshotLocked()
	b.mu.Unlock()
	b.snap.Store(&snap)

	var once sync.Once
	return func() {
		once.Do(func() { // 幂等：重复 cancel 不出错
			b.mu.Lock()
			defer b.mu.Unlock()
			delete(b.hand[topic], id)
			s := b.buildSnapshotLocked()
			b.snap.Store(&s)
		})
	}, nil
}

// Unsubscribed 是"发出去但没有任何节点订阅"的条数——正文那个坑的可观测指标。
func (b *Bus) Unsubscribed() int64 { return b.noSub.Load() }

// Seq 用进程内自增充当发号器。
// ⚠️ 多节点部署时它**必须**换成全局唯一（Redis INCR 或雪花），
//
//	否则两个节点会发出同一个 Seq，客户端去重就直接把弹幕吃掉。
func (b *Bus) Seq(_ context.Context, _ string) (int64, error) { return b.seq.Add(1), nil }

// Node 是一台弹幕服务器：本机持有若干房间连接，并订阅全局 topic 把弹幕扇给本机连接。
type Node struct {
	Name string

	pub     Publisher
	limiter Limiter
	bw      *BatchWriter // 可为 nil：纯推送节点不负责落库

	mu        sync.RWMutex
	rooms     map[string]*Room
	received  atomic.Int64
	delivered atomic.Int64
}

func NewNode(name string, pub Publisher, limiter Limiter, bw *BatchWriter) *Node {
	return &Node{Name: name, pub: pub, limiter: limiter, bw: bw, rooms: map[string]*Room{}}
}

// Room 取（或建）一个房间。
func (n *Node) Room(name string) *Room {
	n.mu.RLock()
	r, ok := n.rooms[name]
	n.mu.RUnlock()
	if ok {
		return r
	}
	n.mu.Lock()
	defer n.mu.Unlock()
	if r, ok := n.rooms[name]; ok {
		return r
	}
	r = NewRoom(name)
	n.rooms[name] = r
	return r
}

// ServeTopic 订阅弹幕 topic，把收到的每条弹幕投给本节点该房间的连接。
//
// ★ 这三行就是正文第 4 层的全部收益：
//
//	从此刻起，"用户连在哪台机器"和"弹幕打到哪台机器"**无关**。
func (n *Node) ServeTopic(ctx context.Context, topic string) (func(), error) {
	return n.pub.Subscribe(ctx, topic, func(m Msg) {
		n.received.Add(1)
		n.delivered.Add(int64(n.Room(m.Room).Broadcast(m)))
	})
}

// Accept 是弹幕进来的完整链路（正文第 1~4 层的顺序就在这一个方法里）。
// 返回 false = 被限流丢弃，调用方**不要重试**。
func (n *Node) Accept(ctx context.Context, m Msg, topic string) (bool, error) {
	if !n.limiter.Allow(ctx, m.UID) {
		return false, nil // 第 1 层：直接丢弃，不进入后续任何链路
	}
	seq, err := n.pub.Seq(ctx, topic)
	if err != nil {
		return false, fmt.Errorf("barrage: seq: %w", err)
	}
	m.Seq = seq
	m.Room = topic // 房间名 = topic 名：不给"发错房间"留机会
	if err := n.pub.Publish(ctx, topic, m); err != nil {
		return false, fmt.Errorf("barrage: publish: %w", err)
	}
	if n.bw != nil {
		n.bw.Enqueue(m) // 持久化链路：进批量缓冲，不直写 DB
	}
	return true, nil
}

// Received / Delivered：本节点"收到多少条"和"成功推给多少条连接"。
// 两个数一起看才知道丢在扇出还是在连接缓冲。
func (n *Node) Received() int64  { return n.received.Load() }
func (n *Node) Delivered() int64 { return n.delivered.Load() }
```

#### 骨架 ④：第 3 层的批量落库（`BatchWriter`）

```go
package barrage

import (
	"context"
	"sync"
	"sync/atomic"
	"time"
)

// Sink 是"批量落库"这一步的出口：生产是 MySQL/Mongo 的 batch insert
// （写法见 mysql/事务与日志.md、mysql/数据迁移与分表.md 的批量导入示例），
// 这里只约定接口，不重复写驱动。
type Sink interface {
	Write(ctx context.Context, batch []Msg) error
}

// BatchWriter 把正文第 3 层"尽可能改成批量操作"变成能用的东西。
//
// ★ 三个必须同时存在的开关，缺一个就是事故：
//  1. **攒够 N 条 flush**（吞吐）；
//  2. **超过 T 时间也 flush**（否则低峰期弹幕会**一直躺在内存里**，
//     进程一挂全丢——弹幕能容忍丢，但"因重启而丢一批未落盘的数据"是可避免的丢）；
//  3. **缓冲满时怎么办**（背压）。弹幕的答案是**丢掉新的并计数**，
//     而不是阻塞生产者——阻塞会顺着调用栈一路卡住 WebSocket 读循环。
type BatchWriter struct {
	sink   Sink
	max    int           // 单批条数
	interv time.Duration // 最长等待

	ch      chan Msg
	closed  chan struct{}
	once    sync.Once
	queued  atomic.Int64
	dropped atomic.Int64
	flushed atomic.Int64
	errs    atomic.Int64
}

func NewBatchWriter(sink Sink, max int, interv time.Duration, queueCap int) *BatchWriter {
	return &BatchWriter{
		sink: sink, max: max, interv: interv,
		ch: make(chan Msg, queueCap), closed: make(chan struct{}),
	}
}

// Enqueue 非阻塞入队。返回 false 表示这条弹幕**被丢弃**（必须打点）。
func (w *BatchWriter) Enqueue(m Msg) bool {
	select {
	case w.ch <- m:
		w.queued.Add(1)
		return true
	default:
		w.dropped.Add(1) // 背压时丢新数据：保内存、保推送链路，不保持久化
		return false
	}
}

// Run 是消费循环：攒批 + 定时 flush。用 ctx 控制退出。
func (w *BatchWriter) Run(ctx context.Context) {
	batch := make([]Msg, 0, w.max)
	t := time.NewTicker(w.interv)
	defer t.Stop()

	for {
		select {
		case m := <-w.ch:
			batch = append(batch, m)
			if len(batch) >= w.max {
				w.flush(ctx, batch)
				batch = batch[:0]
			}
		case <-t.C:
			if len(batch) > 0 {
				w.flush(ctx, batch)
				batch = batch[:0]
			}
		case <-ctx.Done():
			if len(batch) > 0 { // 退出前把剩下的写掉：**不要**把已入队的直接丢了
				w.flush(context.Background(), batch)
			}
			return
		}
	}
}

// flush 失败时**不重试**：弹幕是可容忍丢失的娱乐性数据，
// 重试要引入磁盘队列/退避，收益远小于复杂度。
// ⚠️ 换成订单、余额这类数据，这里**必须**改成"落本地 WAL + 重试 + 告警"。
func (w *BatchWriter) flush(ctx context.Context, batch []Msg) {
	if err := w.sink.Write(ctx, batch); err != nil {
		w.errs.Add(1)
		return
	}
	w.flushed.Add(int64(len(batch)))
}

// Stats 返回 (入队, 已落库, 丢弃, 失败批次数)。
// ⚠️ 丢弃率 / 入队 是这条链路的**核心 SLO**，别只报 QPS。
func (w *BatchWriter) Stats() (int64, int64, int64, int64) {
	return w.queued.Load(), w.flushed.Load(), w.dropped.Load(), w.errs.Load()
}

// MemSink 是跑通链路用的内存出口（生产请换成真实 batch insert）。
type MemSink struct {
	mu     sync.Mutex
	Msgs   []Msg
	Blocks time.Duration // >0 时模拟"落库变慢"，用来观察背压
}

func (s *MemSink) Write(_ context.Context, batch []Msg) error {
	if s.Blocks > 0 {
		time.Sleep(s.Blocks)
	}
	s.mu.Lock()
	s.Msgs = append(s.Msgs, batch...)
	s.mu.Unlock()
	return nil
}

// Written 返回已落库条数。
func (s *MemSink) Written() int {
	s.mu.Lock()
	defer s.mu.Unlock()
	return len(s.Msgs)
}
```

#### 实测：把上面四层跑一遍，数字长这样

以下全部是 `go test` 的真实输出（本机单进程、内存版 `Bus`，不是编的理想值）。

**① 慢连接隔离：缓冲大小直接决定丢弃率**（一次广播 1000 条，两个订阅者：慢的不消费、快的正常消费）

| 每连接缓冲 | 慢连接收到 | 慢连接丢弃 | 快连接收到 |
|---|---|---|---|
| 0 | 0 | 1000 | 1000 |
| 1 | 1 | 999 | 1000 |
| 8 | 8 | 992 | 1000 |
| 64 | 64 | 936 | 1000 |
| 1024 | 1000 | 0 | 1000 |

> **要点不是"缓冲越大越好"**：快连接始终收到 1000 条，
> 说明**慢连接的丢弃完全没有传染给别人**——这才是第 4 层真正要买的东西。
> 缓冲取"能容忍卡顿多久"：`缓冲 / 每秒条数 = 可容忍的卡死秒数`。

**② 有没有共享总线 = 正文那个坑**（A、B 两个节点，用户在 B 上，弹幕从 A 进来）

| 场景 | A 节点 | B 节点 | 结论 |
|---|---|---|---|
| 只有单机内存映射 | 收到 100，投递 64 | **收到 0，投递 0** | B 上那个用户**永远看不到**弹幕 |
| 接入 Pub/Sub | 收到 100 | 收到 100 | 两端连接各收到 64 条 |
| topic 没有任何节点订阅 | — | — | `Unsubscribed=1`：消息**静默消失**，重连也补不回来 |

> 第 3 行是**必须配持久化链路的理由**：Pub/Sub 不保留消息，
> 断线期间错过的弹幕只能靠 `Seq` 从库里补——**这两条路径不是冗余，是互补**。

**③ 批量落库的背压**（队列容量 500、单批 100、入队 2000 条，出口耗时可调）

| 单批落库耗时 | 入队成功 | 丢弃 | 已落库 | 失败批次 |
|---|---|---|---|---|
| 0（不阻塞） | 500 | 1500 | 500 | 0 |
| 5ms | 600 | 1400 | 600 | 0 |

> 两行合起来的结论是：**队列一满就开始丢，落库变快变慢都救不回来**——
> 因为生产速度（纳秒级入队）远高于消费速度。
> 真正能救的是**加大队列 + 加消费协程**，或者反过来给入口限流（回到第 1 层）。
> 具体数字受调度影响，多次运行会在 500~600 之间浮动。

**④ 吞吐与限流**

| 指标 | 实测 |
|---|---|
| 广播 2000 条 × 1000 连接 = 2,000,000 次投递 | 484ms；**单次投递 ≈242ns，单条扇出 ≈242µs** |
| `FixedWindow(1 分钟/人)` 同一 uid 尝试 1000 条 | **放行 1 条**（其余 999 条在入口处就被丢，不占用后面三层任何资源） |
| 线格式 vs JSON（同一条弹幕） | 48 字节 vs 82 字节，**省 1.7 倍** |

> "单条扇出 242µs"这个数很值得记住：**它意味着单机广播的理论上限约 4000 条/秒/房间**，
> 而这是纯内存投递、不含 WebSocket 写与 TLS 加密。真算容量时要在这个数上再乘以
> 序列化 + 网络写的开销——**面试时报出"我量过单条扇出"这句话本身就是加分项**。

**原语对照表——这张表就是"结构是语言无关的"那句话的证据**：

| Go（上面四段） | Java（本节） | 差在哪 |
|---|---|---|
| `chan Msg`（带缓冲） | `ArrayBlockingQueue<Msg>` | Java 没有 0 缓冲队列，`buf` 至少 1 |
| `select { case ch <- m: default }` | `queue.offer(m)` | **一模一样**：非阻塞、满了返回 false |
| `atomic.Pointer[[]*Sub]` 快照 | `AtomicReference<List<Sub>>` | Java 侧快照必须**不可变**（`List.copyOf`），否则读侧会看到写者的中间状态 |
| `close(s.out)` 广播式退出 | 塞一个 `POISON` 毒丸 | ⚠️ **这是真差异**：Java 没有"关一个通道让所有读者退出"的原语 |
| `go func(){ for range ch }` | `new Thread(...)` | ★ 一个连接 = **一个内核线程**，成本见下面第四组 |
| `context.WithCancel` | `volatile` 标志位 + 线程 `interrupt` | — |
| `sync.Once` | `AtomicBoolean.compareAndSet` | — |

**片段一：一条连接 = 有界队列 + 非阻塞投递 + 毒丸退出**（对应 `barrage_2.go` 的 `Sub`）

```java
	static final class Sub {
		final String id;
		/** 毒丸：见 close()。seq = -1 是正常弹幕不会用到的取值。 */
		static final Msg POISON = new Msg("", "", "", -1);

		private final ArrayBlockingQueue<Msg> out;
		private final AtomicLong sent = new AtomicLong();
		private final AtomicLong dropped = new AtomicLong();
		private final AtomicBoolean closed = new AtomicBoolean();

		Sub(String id, int buf) {
			this.id = id;
			this.out = new ArrayBlockingQueue<>(Math.max(1, buf)); // Java 没有 0 缓冲队列，见 main() 第四组的说明
		}

		/** 等价 Go 的 select+default：满了立刻返回 false，绝不阻塞调用方。 */
		boolean trySend(Msg m) {
			if (closed.get()) {
				return false;
			}
			if (out.offer(m)) {
				sent.incrementAndGet();
				return true;
			}
			dropped.incrementAndGet(); // 慢客户端：丢这一条，继续服务别人
			return false;
		}

		/** 丢弃率必须暴露给监控：只报 QPS 等于把"用户看不到弹幕"藏起来。 */
		long sent() {
			return sent.get();
		}

		long dropped() {
			return dropped.get();
		}

		/**
		 * 幂等：主动离开、心跳超时、连接断开三条路径都会走到这里。
		 *
		 * ⚠️ Java 没有 `close(chan)` 这种"关广播"的原语，等价做法是**塞一个毒丸**
		 * 让消费线程自己退出。队列满时毒丸可能塞不进——这里接受这个不完美，
		 * 因为消费线程是 daemon，进程退出时自然回收；
		 * 生产上要么给毒丸留一个空位（入队侧预留），要么改用 poll 超时轮询 closed 标志。
		 */
		void close() {
			if (closed.compareAndSet(false, true)) {
				out.offer(POISON);
			}
		}

		/**
		 * 该连接的写协程（真实项目里就是 ws WriteMessage 循环）。
		 * 用**无限期 take()**而不是 poll(超时)：轮询会把"1000 个连接各自每 20ms 醒一次"
		 * 变成一份稳定的空转开销，测出来的扇出成本就不干净了。
		 */
		void drain(Consumer<Msg> writer) throws InterruptedException {
			while (true) {
				Msg m = out.take();
				if (m == POISON) {
					return;
				}
				writer.accept(m);
			}
		}
	}
```

**片段二：房间的 COW 快照**（对应 `barrage_2.go` 的 `Room`，广播路径**不进锁**）

```java
	static final class Room {
		private final String name;
		private final Map<String, Sub> subs = new HashMap<>();
		private final AtomicReference<List<Sub>> snap = new AtomicReference<>(Collections.emptyList());
		private final AtomicLong online = new AtomicLong();

		Room(String name) {
			this.name = name;
		}

		String name() {
			return name;
		}

		synchronized void join(Sub s) {
			Sub old = subs.put(s.id, s);
			if (old != null && old != s) {
				old.close(); // 同 ID 重连：先摘旧的
			}
			publish();
		}

		synchronized void leave(String id) {
			Sub s = subs.remove(id);
			if (s == null) {
				return; // 幂等
			}
			publish();
			s.close();
		}

		/** 持锁时把 map 摊成一份不可变快照，读侧遍历它、不进临界区。 */
		private void publish() {
			snap.set(List.copyOf(subs.values()));
			online.set(subs.size());
		}

		long online() {
			return online.get();
		}

		/** 尽力投递给房间内所有连接，返回成功条数。<b>这里没有锁</b>。 */
		int broadcast(Msg m) {
			int ok = 0;
			for (Sub s : snap.get()) {
				if (s.trySend(m)) {
					ok++;
				}
			}
			return ok;
		}
	}
```

**片段三：批量落库的三个开关**（对应 `barrage_4.go` 的 `BatchWriter`）

```java
		/**
		 * 消费循环。Go 用 select{case ch / case ticker / case ctx.Done}，
		 * Java 这边让 poll 的超时<b>同时充当"取数据"和"定时"</b>——
		 * 少一个 ticker，但语义等价：拿到就攒批，等不到就把已有的写掉。
		 */
		void run() {
			List<Msg> batch = new ArrayList<>(max);
			while (true) {
				Msg m;
				try {
					m = queue.poll(flushMillis, TimeUnit.MILLISECONDS);
				} catch (InterruptedException e) {
					Thread.currentThread().interrupt();
					break;
				}
				if (m != null) {
					batch.add(m);
				}
				boolean timeUp = m == null;
				if (batch.size() >= max || (timeUp && !batch.isEmpty())) {
					sink.write(new ArrayList<>(batch));
					flushed.addAndGet(batch.size());
					batch.clear();
				}
				if (stop && queue.isEmpty()) {
					break;
				}
			}
			if (!batch.isEmpty()) { // 退出前把剩下的写掉：不要把已入队的直接丢了
				sink.write(new ArrayList<>(batch));
				flushed.addAndGet(batch.size());
			}
		}
```

**Java 侧实测**（5 次取的区间；完整文件是可直接跑的 `BarrageDesign.java`，
上面三处是**最容易走样的三个类型**，其余类型与 Go 版一一对应）：

| 实验 | Go | Java | 是否同一结论 |
|---|---|---|---|
| ① 慢连接丢弃（缓冲 1 / 8 / 64 / 1024） | 丢 999 / 992 / 936 / 0 | **丢 999 / 992 / 936 / 0** | ✅ 逐格相同，快连接始终收到 1000 |
| ② 无共享总线 | A 收 100 投 64，B 收 0 | **A 收 100 投 64，B 收 0** | ✅ 相同 |
| ② 接 Pub/Sub | A、B 各收 100，两端连接各 64 | **完全相同**；`Unsubscribed=1` | ✅ 相同 |
| ③ 队列 500 / 入队 2000 | 入队 500~600 | 出口不阻塞时入队 **600~1461**（5 次：1461 / 925 / 836 / 696 / 600）；出口 5ms 时 500~600 | ⚠️ 结论同（队满即丢、落库数=入队数），但 Java 浮动更大：消费者线程**启动时机**直接决定它抢到多少条 |
| ④ 单次投递（2000 条 × 1000 连接） | ≈242~303 ns | **≈3.2~4.1 µs** | ❌ **差 10 倍以上，这一条最值得讲** |

第四组拆开看（Java 侧，每轮内部再取 3 轮最小，共跑 5 次程序）：

| 配置 | 单次投递 | 说明 |
|---|---|---|
| 1000 个连接**没有**消费者 | **≈69~83 ns** | 队列 + 锁本身就这么贵 |
| 1000 个**内核线程**消费者 | **≈3.2~4.1 µs** | ★ 唤醒成本占了 **≈98%** |
| 1000 个**虚拟线程**消费者（JDK 21） | **≈180~264 ns** | 回到 Go 量级（Go ≈242~303 ns） |

**三条只有把两边都跑过才讲得出的话**：

1. **广播的贵不贵在队列，而在"叫醒 1000 个内核线程"**：
   同一套结构，把消费者摘掉是 69ns，接上内核线程是 3.2µs —— 98% 是唤醒。
   Go 之所以量不出这一层，是因为它那 1000 个"连接写协程"本来就是协程。
2. **Java 21 的虚拟线程让这道题重新变成"结构问题"**：
   `BarrageVirtual.java` 只改了线程的创建方式（`Thread.ofVirtual()`），
   房间/队列/投递逻辑一行没动，单次投递就落到 180~264ns ≈ Go 的 242~303ns。
   这就是 [进程与线程.md](../../linux/进程与线程.md) 里"协程轻在调度"最直接的证据。
3. **`close(chan)` 在 Java 里没有等价物**，只能塞毒丸，而毒丸**可能被满队列挡住**。
   这不是语法差异而是模型差异：Go 的通道是**一等公民**（可关闭、可广播给所有读者），
   Java 的队列只是一个容器。**面试里能指出这一条，比背"Java 并发包很丰富"有用得多。**

> 另外两处小差异也记一下，免得以为是 bug：
> ① Java 没有 0 缓冲队列，所以 Go 表里"缓冲 0 → 丢 1000"那档在 Java 侧不存在；
> ② 线格式体积两边完全一致（48 字节 vs JSON 82 字节），
> 但 Java 侧的 JSON 是按 `encoding/json` 的等价输出**手工拼**的（本机没引 Jackson），只用于体积对比。

#### 一句话收口

> 四层的骨架其实只有三件事：**入口把不合规的挡掉（限流直接丢）、
> 扇出把慢的隔离掉（有界缓冲 + 非阻塞投递 + COW 快照）、
> 落库把散的攒起来（攒批 + 定时 + 背压丢）**；
> 而 `Node.Accept` 里那 15 行，就是"双路径分流"这句话的全部实现。

## 面试官会追问什么

- **弹幕该推还是拉？** → 先看在线房间规模与消息量：小规模直接广播；大规模以「房间订阅 + 服务端推」为主，配合客户端批量拉取做补偿。核心是**别让每个观众都去扫全量**。
- **弹幕要不要持久化？** → 分场景，而且链路必须分开：实时弹幕可丢（走内存 Pub/Sub），历史弹幕要存（写 MQ 落库或对象存储）。混在一条链路上，存储抖动会在直播期间形成尖刺。
- **高并发写入怎么削峰？** → 先写内存队列 / MQ 缓冲，消费端按自身能力匀速落库；直播间热度差异极大，要能**按房间动态分配配额**，别让一个热门房间拖垮全局。
- **怎么防刷屏？** → 分层做：客户端节流 → 网关按用户与房间双维度限流 → 内容侧滑动窗口频控与去重。
- **一致性上能妥协吗？** → 能而且**必须**：弹幕允许短暂乱序与丢失，用最终一致换低延迟——但这个取舍要自己主动说出来，别等面试官问。
- **落地骨架里最该讲的代码点？** → 连接管理：怎么维护「房间 → 连接集合」映射、读写并发的安全边界、以及断连时的清理——这里最容易漏协程（见 [../../go/并发/协程泄漏与死锁.md](../../go/并发/协程泄漏与死锁.md)）。
