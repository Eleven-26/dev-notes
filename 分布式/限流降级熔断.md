# 限流、降级与熔断
> 介绍限流 / 熔断 / 降级三件套在稳定性体系中的分工，给出算法横向对比、Go 与 Java 的落地代码和生产踩坑，并附高频面试追问。
>
> 内容整理自个人学习笔记，并参考《大型网站技术架构：核心原理与案例分析》（李智慧）。Go 单机令牌桶的实现细节见 [限流器.md](../go/并发/限流器.md)。
## 一、一句话定位与三件套的关系
> **三件套解决的是同一个问题的三个不同侧面：系统在过载或依赖故障时，如何"有策略地放弃"，而不是整体崩溃。**
| 手段 | 保护对象 | 触发条件 | 直接后果 | 本质 | 典型位置 |
| --- | --- | --- | --- | --- | --- |
| **限流** | **自己**（防系统过载） | 进入的流量超过容量 | 多余请求被拒绝 / 排队 / 等待 | **流量防护**：控制"进来多少" | 网关、接入层、接口入口 |
| **熔断** | **下游**（防雪崩扩散） | 依赖的错误率 / 慢调用比例超阈值 | 一段时间内所有对该依赖的调用直接快速失败 | **依赖防护**：控制"出去多少" | RPC Client、HTTP Client、DAO 层 |
| **降级** | **业务**（保住核心链路） | 人工开关 / 熔断触发 / 限流触发 | 非核心功能被关闭，返回兜底值 | **业务取舍**：决定"放弃什么" | 业务代码、配置中心 |
> ⭐ 三者在稳定性体系中的位置是一条链：流量防护（限流）→ 依赖防护（熔断）→ 业务取舍（降级）。关键区分：**限流是"我扛不住了，少来点"；熔断是"你（下游）不行了，我先不调你"；降级是"这个先不做了，把资源留给核心"。**
> 熔断和限流是**触发手段**，降级是**被触发后的业务表现**——熔断后必须要有降级逻辑（兜底），否则熔断只会把"慢"变成"错"。
| 容易混淆的点 | 澄清 |
| --- | --- |
| 熔断 vs 降级 | 熔断是**框架层**的自动保护（打开后直接抛异常）；降级是**业务层**的兜底方案（返回什么）。熔断常常**触发**降级，但降级也可由开关/限流独立触发 |
| 限流 vs 熔断 | 限流看**自身流量**（入口 QPS 超阈值）；熔断看**调用结果**（错误率/慢调用）。限流通常一直生效，熔断是故障期的临时状态 |
| 降级 vs 快速失败 | 快速失败只是降级策略之一；降级还包括返回默认值、兜底缓存、异步化等 |
## 二、限流
### 2.1 算法全景对比 ⭐
| 算法 | 实现复杂度 | 允许突发 | 临界突变问题 | 内存开销 | 分布式支持 | 典型框架 |
| --- | --- | --- | --- | --- | --- | --- |
| **固定窗口计数** | ⭐ 极低（一个计数器） | 不支持 | ⚠️ **严重**，窗口交界处可放行 2 倍阈值 | 极低（O(1)） | 容易（Redis INCR + EXPIRE） | Nginx `limit_req` 简化版、自研 |
| **滑动窗口计数** | 低（多个小格子） | 不支持 | 缓解，精度取决于格子数 | 低（O(格子数)） | 中（Redis Hash/ZSET） | Sentinel 默认统计、Kratos |
| **滑动日志** | 中 | 不支持 | ⭐ 无，最精确 | ⭐ **高**，每个请求一条记录 | 中（Redis ZSET） | 精确限流、Ratelimit-Services |
| **漏桶 Leaky Bucket** | 低（队列 + 匀速出水） | ⚠️ **不允许**，强制匀速 | 无 | 中（需缓存队列） | 中 | Nginx `limit_req`、流量整形 |
| **令牌桶 Token Bucket** | 低（计数 + 时间推算） | ⭐ **允许**（桶内令牌可一次用完） | 无 | 极低（O(1)，只存两个值） | 容易（Redis Hash + Lua） | `golang.org/x/time/rate`、Guava `RateLimiter`、Sentinel |
| **Redis 分布式限流** | 中（需 Lua 保证原子） | 取决于底层算法 | 取决于底层算法 | 取决于底层算法 | ⭐ **原生支持** | `redis-cell`、Spring Cloud Gateway `RequestRateLimiter` |
| **自适应限流** | ⭐ 高（需采集系统指标） | 动态允许 | 无（按实时负载调整） | 低 | 弱（通常单机生效） | BBR（TCP）、Sentinel 系统规则、Kratos `adaptive`、Envoy |
> ⭐ **选型一句话**：绝大多数业务用**令牌桶**（要突发、开销小）；要严格保护下游恒定速率用**漏桶**；要跨机总量控制用 **Redis + Lua**；不想人工调参、机器规格不一用**自适应**。
### 2.2 两个必须讲清的关键差异
#### 漏桶 vs 令牌桶（⭐ 面试高频）
| 维度 | 漏桶 | 令牌桶 |
| --- | --- | --- |
| 控制对象 | **流出速率恒定**（桶底匀速漏水） | **流入速率受限**（取到令牌才放行） |
| 突发流量 | ⚠️ 不允许，请求在桶里排队等待匀速处理 | ⭐ 允许，桶里攒的令牌可**一次性取完** |
| 超出后行为 | 排队等待（有延迟）或溢出丢弃 | 直接拒绝（也可以选择等待） |
| 语义 | **流量整形**（削峰填谷，保护下游） | **速率限制 + 允许突发**（保护自己） |
| 适用场景 | 下游处理能力固定、要求匀速（如写 DB、调第三方） | 互联网业务（流量本身有突发性） |
#### 固定窗口的临界突刺问题
```text
窗口 1s，阈值 100：第 0.9s 来 100 个，第 1.1s 又来 100 个
→ 每个窗口内都没超 100，全部放行；但 0.9s~1.1s 这 0.2s 内实际处理了 200 个（2 倍阈值）
```
**解决办法**：① 拆成更细的**滑动窗口**（窗口越小越精确，开销越大）；② 用**滑动日志**记录每个请求时间戳（精确到毫秒，代价是内存）；③ 改用**令牌桶**（天然无边界累积问题）。
### 2.3 分布式限流
#### Redis + Lua 令牌桶（完整脚本）
> ⭐ 为什么必须用 Lua：一次限流需要"读令牌数 → 计算补充 → 判断 → 扣减 → 写回"多步操作，**分步做会有竞态**（并发请求都读到同一个 tokens 值）。Lua 脚本在 Redis 中**单线程原子执行**。
```lua
-- KEYS[1]=key(如 rl:token:{uid}:{api})  ARGV[1]=burst  ARGV[2]=rate(个/秒)
-- ARGV[3]=now(秒，浮点，客户端传入)  ARGV[4]=cost(本次消耗，一般 1)；返回 1=放行，0=拒绝
local key, burst = KEYS[1], tonumber(ARGV[1])
local rate, now, cost = tonumber(ARGV[2]), tonumber(ARGV[3]), tonumber(ARGV[4])
local data   = redis.call('HMGET', key, 'tokens', 'ts')
local tokens = tonumber(data[1])
local ts     = tonumber(data[2])
if tokens == nil then tokens = burst; ts = now end      -- 首次访问：桶是满的
local delta  = math.max(0, now - ts)                    -- ⚠️ 防止时钟回拨导致 delta 为负
local filled = math.min(burst, tokens + delta * rate)   -- 平滑补充，最多补到 burst
local ttl    = math.ceil(burst / rate * 1000) + 1000    -- 空闲后自动清理，防 key 泄漏
if filled < cost then
  redis.call('HSET', key, 'tokens', filled, 'ts', now)
  redis.call('PEXPIRE', key, ttl)
  return 0
end
redis.call('HSET', key, 'tokens', filled - cost, 'ts', now)
redis.call('PEXPIRE', key, ttl)
return 1
```
#### Redis + Lua 滑动日志（ZSET 版，精度更高）
```lua
-- KEYS[1] = key；ARGV[1]=now(ms) ARGV[2]=window(ms) ARGV[3]=limit ARGV[4]=member(唯一ID)
local key, now, window, limit, member =
    KEYS[1], tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3]), ARGV[4]
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)   -- 清掉窗口外的记录
local cnt = redis.call('ZCARD', key)
if cnt < limit then
    redis.call('ZADD', key, now, member)
    redis.call('PEXPIRE', key, window)
    return 1
end
return 0
```
> ⚠️ 滑动日志内存开销 = 窗口内请求数 × 每条记录约 100B，大流量下不可用；生产更常用**令牌桶 Lua** 或**滑动窗口计数**。
#### 取巧方案与部署位置
| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 单机均分 | 集群限流总量 N，每台机器限 N/节点数 | 无网络开销、无中心依赖 | ⚠️ 节点数变化/流量倾斜时不准 |
| Redis 中心计数 | Lua 原子计数，全集群共享 | ⭐ 精确控制集群总量 | 每次请求一次 Redis RT；Redis 成新单点，需降级为单机限流 |
| 环形桶 / 多桶 | 把 1s 拆成多个子桶，按时间轮转取多个桶求和 | 近似滑动窗口，开销可控 | 实现复杂，仍有边界误差 |
| 分批取令牌 | 每台机器一次向 Redis 申请一批令牌，本地消费完再申请 | ⭐ 大幅降低 Redis 压力 | 突发期分配不均，需要预留余量 |
| 部署位置 | 适用场景 | 说明 |
| --- | --- | --- |
| **网关层限流** | 防外部流量打垮系统、按 IP/AppKey/租户限流 | 拦截早、代价小，但看不到业务语义（如商品 ID 热点） |
| **应用层限流** | 保护自身资源、按业务维度（接口/用户/热点参数）限流 | 粒度细、可动态调整，但请求已进入进程 |
| **客户端限流** | 防止自己的重试打垮下游 | 只能约束合作方，恶意流量无效 |
> ⚠️ **网关限流与应用限流的重复计数**：同一条链路配了两层限流，网关阈值 100、应用阈值 100，看起来一致，但网关后面有多台实例，实际放行可能远超预期。原则是**网关做粗粒度总量防护，应用做细粒度自我保护，两层阈值要按实例数折算并对齐**，且限流计数上报到同一个监控看板。
### 2.4 限流维度
| 维度 | 含义 | 适用场景 | 典型配置 |
| --- | --- | --- | --- |
| **QPS / TPS** | 单位时间请求数 | 绝大部分接口 | Sentinel `FLOW_GRADE_QPS` |
| **并发数（线程数）** | 同时处理的请求数（Sentinel `FLOW_GRADE_THREAD`） | ⭐ 耗时波动大的接口，QPS 限流保护不了（慢请求堆积会耗尽线程池） | 按线程池大小设置 |
| **热点参数** | 对同一参数值（如 `skuId`）单独限流 | ⭐ 秒杀热点商品、大 V 用户刷接口 | Sentinel `ParamFlowRule` |
| **集群总量** | 整个集群的总 QPS | 保护共享下游（DB、第三方 API） | Redis 计数 / Sentinel 集群流控 |
| **系统负载（自适应）** | 按 CPU、Load、总 RT、总 QPS 综合判断 | 不想人工压测调参 | Sentinel `SystemRule`、Kratos adaptive |
## 三、熔断 ⭐
### 3.1 三态模型与状态图
```text
                 错误率/慢调用比例 >= 阈值 且 请求数 >= 最小请求数
  ┌────────┐ ─────────────────────────────────────► ┌────────┐
  │ Closed │                                        │  Open  │ 全部快速失败
  │  正常  │ ◄───────── 试探请求成功 ────────────── │  熔断  │
  └────────┘                                        └────────┘
       ▲                                                  │
       │                              熔断时长(timeWindow)到期
       │                                                  ▼
       └─ 成功→Closed；失败→回Open ───────────────  ┌────────────┐
                                                   │ Half-Open  │ 只放行 N 个试探
                                                   └────────────┘
```
| 状态 | 请求行为 | 进入条件 | 退出条件 |
| --- | --- | --- | --- |
| **Closed**（正常） | 全部放行，持续统计成功/失败/耗时 | 初始状态；Half-Open 试探成功 | 统计窗口内错误率（或慢调用比例）≥ 阈值 **且** 请求数 ≥ 最小请求数 |
| **Open**（熔断） | ⭐ **直接快速失败**，不再发起真实调用（返回降级结果/异常） | 见上一行 | 熔断时长 `timeWindow` 到期 → 转 Half-Open |
| **Half-Open**（半开） | 只放行**有限个**试探请求，其余仍快速失败 | Open 状态超时 | 试探全部/大部分成功 → Closed；出现失败 → 回到 Open 并重置计时 |
**为什么需要 Half-Open**：Open 到期就直接全量放行是危险的——下游可能还没恢复，瞬间全量流量会**二次打垮**刚起来的服务。半开用少量请求"探针"验证恢复情况。
### 3.2 统计窗口与判定条件
| 要素 | 说明 |
| --- | --- |
| **统计窗口** | 滑动窗口（Sentinel 默认 1s 拆成若干 bucket，窗口长度 `statIntervalMs`，如 10s）或时间桶（Resilience4j 可按次数 `COUNT_BASED` 或时间 `TIME_BASED`） |
| **错误率阈值** | 一般 **50%**（如 Sentinel `count=0.5`）；过高不敏感，过低容易误熔断 |
| **慢调用比例** | RT 超 `maxAllowedRt` 的请求算"慢调用"，比例超阈值即熔断。⭐ 比错误率更早发现问题（很多故障先表现为"变慢"而不是"报错"） |
| **⚠️ 最小请求数** | 必须配（如 10 或 20）。**请求太少时错误率不可信**——总共 2 个请求失败 1 个就是 50%，会误熔断 |
| **熔断时长** | 一般 **5~30s**。太短频繁试探，太长恢复慢 |
### 3.3 熔断恢复（Half-Open 细节）
- **放行多少**：Resilience4j `permittedNumberOfCallsInHalfOpenState`（默认 10）；Sentinel 半开只允许**1 个**试探请求，成功即关闭断路器。
- **判定标准**：试探请求全部成功（或错误率低于阈值）→ 回到 Closed 并清空统计；任一失败 → 立即回 Open，重新开始计时。
- ⚠️ 试探请求要走**真实调用**，不能被缓存命中，否则会把"下游已恢复"误判成"已恢复"。
### 3.4 熔断与重试的相互作用 ⭐
> ⚠️ **熔断期间必须禁用重试。**
```text
下游故障 → 调用失败 → 重试 3 次 → 流量放大 3 倍 → 下游更慢 → 更多失败 → 更多重试 = 重试风暴
```
| 措施 | 说明 |
| --- | --- |
| **熔断优先于重试** | 重试应该包在熔断器**内部**（重试是熔断统计的一次调用），或熔断打开时直接短路重试逻辑 |
| **重试预算（retry budget）** | 限制重试请求占总请求的比例（如 ≤10%，Envoy/Google SRE 实践），超出即不再重试 |
| **指数退避 + 抖动** | 重试间隔指数增长并加随机抖动，避免同一时刻集中重试 |
| **只对幂等接口重试** | 非幂等写操作重试会造成重复扣款/重复下单，必须配合幂等键 |
| **熔断后返回降级** | 熔断抛出的异常要走 `fallback`，而不是冒泡给用户一个 500 |
## 四、降级
### 4.1 三种触发方式
| 触发方式 | 谁触发 | 时机 | 优点 | 缺点 |
| --- | --- | --- | --- | --- |
| **开关降级** | 人（配置中心 / 运维平台手动） | 大促前预防性降级、故障时应急 | ⭐ 最可控、可提前演练 | 依赖人的响应速度 |
| **熔断降级** | 熔断器自动（依赖故障） | 下游错误率/慢调用超阈值 | 全自动、反应快 | 只对"依赖调用"生效 |
| **限流降级** | 限流器自动（超阈值） | 入口 QPS 超容量 | 保护自身 | 被拒绝的请求需要友好处理 |
### 4.2 降级策略
| 策略 | 做法 | 适用 | 注意 |
| --- | --- | --- | --- |
| **返回默认值** | 直接返回空结果 / 默认配置 / 兜底文案 | 推荐位、评价数、个性化 | ⚠️ 默认值要"业务可接受"，不能是空指针 |
| **兜底缓存** | 返回上一次成功的缓存快照（可设计成短期 stale 缓存） | 商品详情、价格、配置 | 要有缓存更新与过期策略 |
| **异步化** | 同步改异步：请求入队，立即返回"处理中" | 非实时流程（发券、通知） | 需要结果查询入口 |
| **关闭非核心功能** | 直接停掉推荐、广告、埋点、排行榜 | ⭐ 大促最常用，资源让给交易链路 | 必须提前梳理"哪些能关" |
| **排队 / 友好提示** | 返回排队页、"稍后再试"、429 状态码 | 抢购、秒杀 | ⭐ 比白屏/500 体验好得多 |
### 4.3 读降级 vs 写降级
- **读降级**：代价低、可随时开关，直接返回兜底数据即可（最常见的降级）。
- **写降级**：⚠️ 必须配合**补偿机制**——请求落本地消息表 / MQ，降级期间异步补做，恢复后对账。典型如：下单时积分服务不可用 → 先落"待发放积分"记录，恢复后补发。
- 判断标准：**降级后是否产生了"本该发生但没发生"的副作用**——有副作用就要有补偿，没有就可以直接丢弃。
### 4.4 降级预案设计原则
1. **先识别核心链路**：画出"用户能完成主流程的最短路径"（如 加购 → 下单 → 支付），路径外的都是可降级项。
2. **开关粒度要分层 + 可动态下发**：全局 / 服务 / 接口 / 参数级开关（如"只降级 skuId=X 的推荐"），配置中心推送、秒级生效，不能靠发版。
3. **⭐ 定期演练**：预案没演练过等于没有。大促前做一次全链路降级演练 + 故障注入（chaos），验证开关真的生效、业务真的可用。
4. **降级要有监控和告警**：降级开关被打开、熔断状态变化必须告警，否则"静默降级"会掩盖真实故障。
## 五、使用一：Go ⭐
### 5.1 sentinel-golang
```go
package main

import (
	sentinel "github.com/alibaba/sentinel-golang/api"
	"github.com/alibaba/sentinel-golang/core/base"
	"github.com/alibaba/sentinel-golang/core/circuitbreaker"
	"github.com/alibaba/sentinel-golang/core/flow"
)

const res = "order:query"

func initRules() error {
	// 1) QPS 限流：单机 100 QPS，超出直接拒绝
	_, err := flow.LoadRules([]*flow.Rule{{
		Resource:               res,
		TokenCalculateStrategy: flow.Direct, // Direct=按 Threshold 计数；WarmUp=预热/冷启动
		ControlBehavior:        flow.Reject, // Reject=直接拒绝；Throttling=匀速排队（漏桶效果）
		Threshold:              100,         // QPS 阈值
		StatIntervalInMs:       1000,
	}})
	if err != nil {
		return err
	}
	// 2) 熔断：错误率 50% 触发，熔断 3s 后进入半开
	_, err = circuitbreaker.LoadRules([]*circuitbreaker.Rule{{
		Resource:         res,
		Strategy:         circuitbreaker.ErrorRatio, // ErrorRatio / SlowRequestRatio / ErrorCount
		Threshold:        0.5,                       // 错误率阈值（慢调用比例模式下为比例）
		MinRequestAmount: 20,                        // ⚠️ 最小请求数，太少不熔断
		StatIntervalMs:   10000,                     // 统计窗口 10s
		RetryTimeoutMs:   3000,                      // 熔断时长，到期转 Half-Open
	}})
	return err
}

func queryOrder(uid int64) (string, error) {
	entry, blockErr := sentinel.Entry(res, sentinel.WithTrafficType(base.Inbound), sentinel.WithArgs(uid))
	if blockErr != nil { // 被限流 或 被熔断：走降级
		return cachedOrder(uid), nil
	}
	defer entry.Exit()

	order, err := callOrderService(uid)
	if err != nil {
		sentinel.TraceError(entry, err) // ⭐ 必须上报，否则错误率统计永远是 0
		return "", err
	}
	return order, nil
}
```
> ⚠️ `sentinel.TraceError(entry, err)` 容易被漏掉：不主动上报，熔断器的错误率永远是 0，熔断规则形同虚设。慢调用同理，需要 `entry.Exit(base.WithError(err))` 或保证 RT 被统计。
### 5.2 sony/gobreaker（轻量熔断器）
```go
package main

import (
	"errors"
	"log"
	"time"

	"github.com/sony/gobreaker"
)

var cb = gobreaker.NewCircuitBreaker(gobreaker.Settings{
	Name:        "userService",
	MaxRequests: 3,                // ⭐ Half-Open 允许的最大并发试探请求数（0 = 仅 1 个）
	Interval:    60 * time.Second, // Closed 状态下计数清零周期（0 = 不清零）
	Timeout:     10 * time.Second, // Open 持续时长，到期转 Half-Open
	ReadyToTrip: func(counts gobreaker.Counts) bool {
		// ⚠️ 必须先判断请求数，否则低流量下 1 次失败就熔断
		return counts.Requests >= 10 &&
			float64(counts.TotalFailures)/float64(counts.Requests) >= 0.5
	},
	OnStateChange: func(name string, from, to gobreaker.State) {
		log.Printf("cb=%s %v -> %v", name, from, to) // ⭐ 这里接告警
	},
	IsSuccessful: func(err error) bool { // 自定义哪些错误算成功（如 404 不算失败）
		return err == nil || errors.Is(err, ErrNotFound)
	},
})

func GetUser(uid int64) (*User, error) {
	v, err := cb.Execute(func() (interface{}, error) { return callUserRPC(uid) })
	if err != nil {
		// ErrOpenState = 熔断中；ErrTooManyRequests = 半开试探已满
		if errors.Is(err, gobreaker.ErrOpenState) || errors.Is(err, gobreaker.ErrTooManyRequests) {
			return defaultUser(), nil // 降级兜底
		}
		return nil, err
	}
	return v.(*User), nil
}
```
| 字段 | 含义 |
| --- | --- |
| `MaxRequests` | Half-Open 时允许的并发试探请求数（超出返回 `ErrTooManyRequests`）；设为 0 时只允许 1 个 |
| `Interval` | Closed 状态下统计周期，周期性清零计数；设为 0 则累计不清零 |
| `Timeout` | Open 状态持续时间 |
| `ReadyToTrip` | ⭐ 是否跳变的判定函数（**必须自己做最小请求数保护**） |
### 5.3 Redis + Lua 分布式限流（完整可运行）
```go
package ratelimit

import (
	"context"
	"time"

	"github.com/redis/go-redis/v9"
)

const tokenBucketLua = `-- 完整脚本见 2.3 节（此处为同一份，可直接落地）
local key, burst = KEYS[1], tonumber(ARGV[1])
local rate, now, cost = tonumber(ARGV[2]), tonumber(ARGV[3]), tonumber(ARGV[4])
local data   = redis.call('HMGET', key, 'tokens', 'ts')
local tokens = tonumber(data[1])
local ts     = tonumber(data[2])
if tokens == nil then tokens = burst; ts = now end
local delta  = math.max(0, now - ts)
local filled = math.min(burst, tokens + delta * rate)
local ttl    = math.ceil(burst / rate * 1000) + 1000
if filled < cost then
  redis.call('HSET', key, 'tokens', filled, 'ts', now)
  redis.call('PEXPIRE', key, ttl)
  return 0
end
redis.call('HSET', key, 'tokens', filled - cost, 'ts', now)
redis.call('PEXPIRE', key, ttl)
return 1`

type RedisLimiter struct {
	rdb   *redis.Client
	rate  float64 // 每秒生成令牌数
	burst int     // 桶容量
}

func NewRedisLimiter(rdb *redis.Client, rate float64, burst int) *RedisLimiter {
	return &RedisLimiter{rdb: rdb, rate: rate, burst: burst}
}

// Allow 判断 key 维度的请求是否放行；cost 为本次消耗的令牌数（一般 1）
func (l *RedisLimiter) Allow(ctx context.Context, key string, cost int) (bool, error) {
	// ⭐ now 由客户端传入：避免依赖 Redis 机器时钟，也规避 Lua 中 TIME 命令的复制语义问题
	now := float64(time.Now().UnixNano()) / 1e9
	res, err := l.rdb.Eval(ctx, tokenBucketLua, []string{key}, l.burst, l.rate, now, cost).Int()
	if err != nil {
		// ⚠️ Redis 故障策略：fail-open 放行（保自身可用）/ fail-close 拒绝（保护共享下游）
		return true, err
	}
	return res == 1, nil
}

// 使用：limiter := NewRedisLimiter(rdb, 100, 200) // 100 QPS，允许 200 突发
// ok, err := limiter.Allow(ctx, fmt.Sprintf("rl:api:%d", uid), 1) // !ok → 返回 429 + Retry-After
```

## 七、生产实践与坑
| 主题 | 要点 |
| --- | --- |
| **⭐ 阈值怎么定** | ① **单机压测**拿到单机容量（QPS 拐点、P99 RT）；② 线上按**单机阈值 = 容量 × 安全系数（0.6~0.8）**配置；③ **渐进式**上线：先只监控不拦截（观察模式），再小流量放开，再全量；④ 集群阈值 = 单机阈值 × 实例数，但要考虑流量倾斜打折 |
| **⚠️ 分布式限流的时钟与一致性** | ① Lua 里的 `now` **由客户端传入**，不要依赖 Redis 服务器 `TIME`（主从/集群模式下时钟与复制语义有坑）；② 时钟回拨会让 `delta` 变负，必须 `math.max(0, now-ts)`；③ Redis 主从切换可能丢计数（异步复制），极端场景要容忍超发或用 Redlock（一般不值得）；④ Redis 挂了要有兜底策略（fail-open / 降级为单机限流） |
| **⚠️ 网关与应用限流重复计数** | 两层阈值要按实例数折算对齐；用一个看板同时看网关拒绝数和各应用拒绝数，避免"两层都限了但总量仍超标" |
| **限流后的用户体验** | 返回 **429 + `Retry-After`** 而不是 500；秒杀场景用**排队页 / 排队号**而不是直接拒绝；接口层面给明确的错误码和文案 |
| **熔断告警与演练** | 状态变化（Closed→Open）必须告警；配置 `OnStateChange` 回调打点；定期做**故障注入演练**（kill 下游、注入延迟）验证熔断真的打开、降级真的生效 |
| **⚠️ 重试风暴** | 熔断期间禁用重试；设重试预算（≤10%）；指数退避 + 抖动；只对幂等接口重试；客户端/网关/SDK 多层重试会**乘性放大**（3 层 ×3 次 = 27 倍） |
| **⚠️ 幂等** | 重试 + 补偿 + 消息重投都会产生重复请求，写接口必须有幂等键（订单号 / requestId + 唯一索引），否则降级补偿会造成重复扣款 |
| **粒度与 key 设计** | key 要包含维度（租户/用户/接口），避免全局一个 key；⚠️ 高基数 key（按 userId）会让 Redis key 数暴涨，要设 TTL 或改用局部限流 |
| **不要忽视并发数限流** | QPS 限流挡不住"慢请求堆积"——100 QPS 但每个请求 10s，会堆积 1000 个并发把线程池打满。耗时接口要配**并发数 / 信号量隔离** |
## 八、面试官会追问什么
1. **限流算法有哪些？各自优缺点？** → 固定窗口（简单但有 2 倍临界突刺）、滑动窗口（缓解、精度看格子数）、滑动日志（精确但内存高）、漏桶（匀速、不允许突发）、令牌桶（允许突发、O(1) 内存）、Redis 分布式、自适应（按 CPU/RT 动态）。
2. **令牌桶和漏桶的区别？** → 令牌桶**限制流入速率 + 允许突发**（积攒的令牌可一次用完）；漏桶**限制流出速率、强制匀速**（做流量整形）。互联网业务多为令牌桶。
3. **固定窗口的临界突刺怎么解决？** → 滑动窗口（细分格子）、滑动日志（记时间戳，精确但费内存）、或直接用令牌桶。
4. **分布式限流怎么做？Redis 挂了怎么办？** → Redis + Lua 原子脚本（令牌桶或 ZSET 滑动日志）；可选单机均分、分批取令牌。Redis 挂了按场景选 **fail-open**（保护自身可用性）或 **fail-close**（保护共享下游），并降级为单机限流。
5. **为什么限流要用 Lua 脚本？** → "读—算—判断—扣减—写回"多步操作，分开执行有竞态；Lua 在 Redis 中单线程原子执行，且减少网络往返。
6. **熔断三态怎么转换？** → Closed 统计错误率；达阈值且满足最小请求数 → Open（快速失败）；Open 持续 `timeWindow` → Half-Open；Half-Open 放行少量试探，成功 → Closed，失败 → 回 Open。
7. **半开状态放多少请求？** → 少量即可：Sentinel 只放 1 个，Resilience4j 配 `permittedNumberOfCallsInHalfOpenState`（默认 10）/ gobreaker `MaxRequests`。目的是**避免全量流量二次打垮刚恢复的下游**。
8. **熔断一定要配最小请求数吗？** → ⭐ 必须。请求太少时错误率统计不可信（2 个请求失败 1 个就是 50%），会误熔断。一般配 10~20，或按时间窗口内的样本量动态判断。
9. **熔断和降级的区别？** → 熔断是**框架层的自动保护机制**（打开后快速失败），降级是**业务层的兜底方案**（返回什么）。熔断通常触发降级，但降级还可由限流或人工开关触发。没有降级逻辑的熔断只是把"慢"变成"错"。
10. **为什么熔断期间要关掉重试？** → 重试会把流量放大 N 倍，下游故障未恢复时放大压力 → 更多失败 → 更多重试，形成**重试风暴**，把可恢复的故障拖成雪崩。做法：熔断优先于重试（熔断打开直接短路重试）、重试预算、指数退避 + 抖动、只对幂等接口重试。
11. **限流阈值怎么定？** → 压测拿单机容量拐点 → 乘安全系数 0.6~0.8 → 先观察模式（只统计不拦截）→ 小流量灰度 → 全量；集群阈值 = 单机 × 实例数（考虑倾斜打折）。
12. **限流了用户体验很差怎么办？** → 429 + `Retry-After`、排队页/排队号、友好文案、错峰引导；核心链路优先放行，非核心先降级。
