# 注册模式：一张"全局对象表"，以及在 PHP 里它为什么会串号

> 素材来源：博客系列 [PHP 设计模式(六)：注册模式](https://blog.csdn.net/weixin_43837229/article/details/102660328)。
> 本篇把它重写成能落地的版本，重点补三条原系列没讲透的现实问题：
> **①注册模式与单例、与服务容器的真实区别（注册表持有"一组"对象）；②用静态属性做注册表，在 php-fpm 下"跨请求不存活"、在 Swoole/RoadRunner 常驻下"跨请求串号"（有可复现实验）；③为什么现代 PHP 项目几乎都用容器取代 Registry——可测试性。**
>
> 单例见 [单例模式.md](单例模式.md)，容器 `singleton` 的写法也在其中第五节。

## 一、注册模式是什么：一张能按名字存取对象的全局表

注册模式（Registry）来自游戏开发（Phalcon 框架里最典型），本质是一个**进程内可见的键值对象表**：把对象以字符串 key 存进去，任何地方都能用 key 取回来。它由三部分构成：

| 结构角色 | 职责 | PHP 落地形态 |
| --- | --- | --- |
| 注册表容器 | 持有 `key => object` 的映射 | 静态属性 `array`，或一个 `ArrayObject`/`ArrayAccess` 实例 |
| 全局访问点 | 让任意模块拿到这张表 | `Registry::get('db')` 静态方法，或把表实例注入 |
| 生命周期管理 | 存/取/判存/删 | `set`/`get`/`has`/`remove` |

**它和单例的边界（最常被混淆）**：

| | 单例 | 注册表 |
| --- | --- | --- |
| 管几个对象 | **一个**（本类的唯一实例） | **一组**任意对象 |
| 谁存谁 | 类自己存自己 | 外部把各种对象塞进表 |
| 关心唯一性吗 | 是核心 | 不关心，只关心"按名字能找到、能找到的是同一个" |

可以理解为：**单例 = 只能装自己那一份的全局访问点；注册表 = 能装很多对象的全局访问点。** 二者都靠静态属性实现"全局"，也因此都继承了静态属性在 PHP 里的作用域问题（第四节）。

## 二、最小可用实现：静态数组注册表（本机 PHP 8.0.2 跑通）

```php
<?php

declare(strict_types=1);

final class Registry
{
    /** @var array<string, object> 全局对象表 */
    private static array $objects = [];

    public static function set(string $key, object $obj): void { self::$objects[$key] = $obj; }
    public static function get(string $key): object
    {
        if (!isset(self::$objects[$key])) {
            throw new RuntimeException("未注册: {$key}");
        }
        return self::$objects[$key];
    }
    public static function has(string $key): bool { return isset(self::$objects[$key]); }
    public static function remove(string $key): void { unset(self::$objects[$key]); }
}

final class Logger { public function __construct(public string $tag) {} }

Registry::set('log', new Logger('app'));
$a = Registry::get('log');
$b = Registry::get('log');
echo 'same_instance: ', var_export($a === $b, true), ' tag=', $a->tag, PHP_EOL;
// 注册表可放多个不同对象（区别于单例：单例只管自己那一个）
Registry::set('db', new Logger('db'));
echo 'count_keys: ', var_export(Registry::has('db') && Registry::has('log'), true), PHP_EOL;
try { Registry::get('missing'); } catch (RuntimeException $e) { echo 'err: ', $e->getMessage(), PHP_EOL; }
```

```text
same_instance: true tag=app
count_keys: true
err: 未注册: missing
```

`get` 里对未注册 key **抛异常**（而不是返回 `null`），调用点才能立刻暴露"忘了注册"的错误。`===` 为 `true` 说明注册表按 key 复用了同一实例——这是注册表最基础的收益：一次构造，全局共享。

## 三、更 PHP 的写法：实现 `ArrayAccess`，用起来像数组

Phalcon 里 `$di`、`$config` 常以"数组式"访问（`$registry['db']`）。给自己实现 `ArrayAccess` 即可，比 `get/set` 更顺手，也更容易后续换成真的 `ArrayObject`：

```php
<?php

declare(strict_types=1);

final class Registry implements ArrayAccess, Countable
{
    private array $data = [];
    public function offsetSet($k, $v): void { $this->data[$k] = $v; }
    public function offsetGet($k): mixed { return $this->data[$k] ?? throw new RuntimeException("未注册 {$k}"); }
    public function offsetExists($k): bool { return isset($this->data[$k]); }
    public function offsetUnset($k): void { unset($this->data[$k]); }
    public function count(): int { return count($this->data); }
}

$r = new Registry();
$r['logger'] = new stdClass();
$r['db'] = new stdClass();
echo 'isset_logger: ', var_export(isset($r['logger']), true), PHP_EOL;
echo 'count: ', count($r), PHP_EOL;
echo 'same_ref: ', var_export($r['logger'] === $r['logger'], true), PHP_EOL;
unset($r['db']);
echo 'after_unset_count: ', count($r), PHP_EOL;
```

```text
isset_logger: true
count: 2
same_ref: true
after_unset_count: 1
```

这里刻意把注册表做成**实例**（`$r = new Registry()`）而不是第二节的静态类——这是走向"可测试"的第一步，第五节解释。生产上更偷懶的做法是直接内建 `ArrayObject`（`$registry = new ArrayObject(); $registry['db'] = ...;`），省得自己实现 `ArrayAccess`。

## 四、静态属性做注册表的作用域：php-fpm 不存活、Swoole 会串号（可复现）

这是本篇相对教科书最重要的一节。用 `private static array $objects`（第二节那种）实现注册表时，**"这张表能活多久"完全由运行模型决定**，和 [单例模式.md](单例模式.md) 第四节同源：

| 运行模型 | 静态注册表生命周期 | 后果 |
| --- | --- | --- |
| php-fpm（传统） | **单个请求内**，请求结束随进程内存回收 | 跨请求不存活，`Registry::set` 下个请求全没了；不能当"跨请求缓存" |
| Swoole / RoadRunner / 常驻 | **整个进程生命周期** | 跨请求存活 → 一旦存了请求态数据（当前用户/租户）就**串号** |
| CLI | 单次运行 | 同常驻 |

php-fpm 下"不存活"是显性的（表现为"怎么每次都要重新注册"，容易发现）。真正的安全事故是常驻模型的**串号**：静态表在请求之间不重置，上一个请求写进去的用户身份被下一个请求读到。本机未装 Swoole，无法直接跑协程服务器，但**串号的根因是"静态状态在同一进程内跨调用存活"**——用一个 CLI 循环连续模拟两个请求即可复现同一机制：

```php
<?php

declare(strict_types=1);

final class CurrentUser
{
    public static ?string $name = null;   // 危险：把请求态存进静态属性（注册表同理）
}

// 模拟"常驻进程"里连续处理两个请求
function handle_request(?string $login): string
{
    if ($login !== null) {
        CurrentUser::$name = $login;
    }
    // 请求结束忘记重置：下一个请求进来时静态属性还留着上一个用户的值
    return 'seen=' . (CurrentUser::$name ?? 'null');
}

echo 'req1: ', handle_request('alice'), PHP_EOL;
echo 'req2(匿名,未登录): ', handle_request(null), PHP_EOL;

// 修复：每个"请求"结束显式清空静态状态
CurrentUser::$name = null;
echo 'req3(after_reset): ', handle_request(null), PHP_EOL;
```

```text
req1: seen=alice
req2(匿名,未登录): seen=alice
req3(after_reset): seen=null
```

`req2` 本该是匿名用户，却读到了 `req1` 留下的 `alice`——这就是常驻模型里注册表/静态属性存请求态数据的越权事故。结论：

- **注册表只放"无请求身份"的共享对象**（连接、配置、驱动句柄）。**绝不能放"当前用户 / 当前租户 / 当前 token"这类请求态数据**。
- php-fpm 下想"跨请求复用"，静态表帮不上忙，要靠连接持久化或代理层（见 [../PHP-FPM对接步骤.md](../../php/PHP-FPM对接步骤.md)）。
- 常驻 PHP 里如果确实要全局，需要框架的"每请求重置"机制（Laravel Octane 的 `Resettable`、Swoole 的协程 `Context` 隔离），本质都是把 `req3` 那行"显式清空"自动化。

## 五、为什么现代 PHP 项目用容器而不是 Registry：可测试性

注册表和 DI 容器功能高度重叠（都是"按标识取共享对象"）。差别在**取的方式**：Registry 是"对象自己伸手去全局表里捞依赖"（服务定位器 Service Locator，隐式依赖），容器是"装配时把依赖从构造函数塞进去"（DI，显式依赖）。可测试性上前者明显吃亏：

```php
<?php

declare(strict_types=1);

// 反例：静态注册表是"隐式全局单例"，被测代码偷偷依赖全局状态
final class StaticRegistry
{
    public static array $c = [];
}

final class Cache
{
    public function __construct(public string $backend) {}
}

// 正例：依赖从构造函数注入，测试时传假的进来，完全不碰全局
final class OrderService
{
    public function __construct(private Cache $cache) {}
    public function describe(): string { return 'cache=' . $this->cache->backend; }
}

$prod = new OrderService(new Cache('redis'));       // 生产：装配真实现
echo 'prod: ', $prod->describe(), PHP_EOL;

$test = new OrderService(new Cache('array-fake'));  // 测试：直接传假实现
echo 'test: ', $test->describe(), PHP_EOL;

// 对比：若用静态注册表，测试得先改全局、跑完还得还原，测试之间容易互相污染
StaticRegistry::$c['cache'] = new Cache('redis');
echo 'static_total: ', count(StaticRegistry::$c), PHP_EOL;
```

```text
prod: cache=redis
test: cache=array-fake
static_total: 1
```

为什么用容器不用 Registry：

| | Registry（服务定位器） | DI 容器（构造函数注入） |
| --- | --- | --- |
| 依赖可见性 | 藏在方法体 `Registry::get('x')` 里，看签名看不出来 | 全在构造函数签名上，一目了然 |
| 单测替换 | 要改全局静态、跑完还原，测试互相污染 | 直接 `new OrderService(new FakeCache())` |
| 缺依赖何时暴露 | 运行时某方法执行到才 `get` 报错 | 构造/装配时就报错 |
| 跨请求状态风险 | 静态表 → 第四节串号 | 实例由容器管，作用域可控 |

一句话：**Registry 把"依赖"变成了"全局查找"，牺牲了可测试性换便利；容器保留同样的集中管理，却让依赖显式、可替换。** 这也是 Laravel/Symfony 生态几乎不再自造 Registry、统一用容器的原因。今天再写 Registry，通常只剩两类正当场景：库级别的小型 DI（不想引入框架）、或明确是"进程内无身份共享表"。

## 六、Go / Java 对照（都已本机编译 + 运行）

Go（`go1.26.5`，`go vet` + `go run`）——Go 无静态属性，用包级 map + `sync.RWMutex` 做进程级注册表；注意它**天然常驻**，所以第四节串号风险在 Go 里同样存在，锁也不能省：

```go
package main

import (
	"errors"
	"fmt"
	"sync"
)

// 注册表：进程级 map，持有"一组"命名对象（区别于单例只管一个）
type Registry struct {
	mu sync.RWMutex
	m  map[string]interface{}
}

func NewRegistry() *Registry { return &Registry{m: map[string]interface{}{}} }

func (r *Registry) Set(k string, v interface{}) {
	r.mu.Lock()
	defer r.mu.Unlock()
	r.m[k] = v
}

func (r *Registry) Get(k string) (interface{}, error) {
	r.mu.RLock()
	defer r.mu.RUnlock()
	v, ok := r.m[k]
	if !ok {
		return nil, errors.New("未注册: " + k)
	}
	return v, nil
}

func main() {
	reg := NewRegistry()
	reg.Set("log", &struct{ Tag string }{Tag: "app"})
	a, _ := reg.Get("log")
	b, _ := reg.Get("log")
	fmt.Println("same_instance:", a == b, "count:", len(reg.m))
	if _, err := reg.Get("missing"); err != nil {
		fmt.Println("err:", err)
	}
}
```

```text
same_instance: true count: 1
err: 未注册: missing
```

Java（`javac 1.8.0_321` 编译 + `java` 运行）——用静态 `Map`，JVM 存活期间跨"请求"存在，作用域等价于 PHP 常驻模型（不是 php-fpm）：

```java
public class Registry {
    // 静态 Map = 进程级全局对象表；JVM 存活期间跨请求存在
    private static final java.util.Map<String, Object> OBJECTS =
            new java.util.HashMap<String, Object>();

    public static void set(String key, Object obj) { OBJECTS.put(key, obj); }

    public static Object get(String key) {
        if (!OBJECTS.containsKey(key)) {
            throw new IllegalStateException("未注册: " + key);
        }
        return OBJECTS.get(key);
    }

    public static boolean has(String key) { return OBJECTS.containsKey(key); }

    static void run() {
        set("log", "app-logger");
        Object a = get("log");
        Object b = get("log");
        System.out.println("same_instance=" + (a == b) + " value=" + a);
        System.out.println("has_db=" + has("db"));
    }
}

class RegistryDemo {
    public static void main(String[] args) {
        Registry.run();
    }
}
```

```text
same_instance=true value=app-logger
has_db=false
```

三者对照：

| | PHP | Go | Java |
| --- | --- | --- | --- |
| 注册表载体 | `private static array` | 包级 `map` + `Mutex` | `static Map` |
| 跨请求存活 | 否（php-fpm）/ 是（常驻） | 是（进程常驻） | 是（JVM 常驻） |
| 并发/串号 | 常驻下需每请求重置 | 需加锁 + 请求态隔离 | 需 `ConcurrentHashMap` + 请求态隔离 |
| 现代用法 | 被 DI 容器取代 | `fx`/手动装配 | Spring 容器 |

## 面试官会追问什么

- **注册模式和单例有什么区别？** → 单例只管"自己类的一个实例"，注册表管"一组任意对象"；两者都靠静态属性实现全局访问，因此共享同一套作用域问题。
- **注册模式和服务容器什么关系？** → 容器是"带依赖解析的注册表"。Registry 是服务定位器（对象自己去全局捞依赖），容器是 DI（装配时注入）；后者依赖显式、可测试，所以现代项目倾向容器。
- **php-fpm 下用静态属性做注册表能跨请求缓存吗？** → 不能。请求结束进程内存回收，静态表消失；要跨请求复用得靠常驻或代理层。
- **Swoole 下注册表最大的坑？** → 进程常驻 → 静态表跨请求存活，存了当前用户/租户就串号（越权）。要么只放无身份共享对象，要么每请求重置。
- **为什么 `get` 要抛异常而不是返回 `null`？** → 让"忘记注册"在取用点立刻暴露，避免 `null` 沿调用链传下去变成更难查的错误。
