# 单例模式：在 PHP 里它到底"单"了多大范围

> 素材来源：博客系列 [PHP 设计模式(一)：单例模式](https://blog.csdn.net/weixin_43837229/article/details/102607857)。
> 本篇把它重写成了可直接落地的版本，并补上原系列没展开的关键一点：**PHP 的请求模型决定了单例的生命周期**，
> 所以"全局唯一"在 php-fpm 下和 Java/Go 下完全不是一回事。
>
> 工厂/注册/原型等其它创建型模式见 [工厂模式.md](工厂模式.md)、[注册模式.md](注册模式.md)、[原型模式.md](原型模式.md)。

## 一、单例模式的三个约束，缺一不可

单例（Singleton）属于创建型模式，保证**一个类只有一个实例**，并提供一个全局访问点。它由三条约束组成，缺任何一条都不算单例：

| 约束 | 实现手段 | 不做的后果 |
| --- | --- | --- |
| 不许外部 `new` | `private function __construct()` | 谁都能 `new`，实例数不受控 |
| 有全局访问点 | `public static function getInstance()` | 实例无法在模块间共享 |
| 不许造出第二个 | 堵 `clone` 与反序列化 | 静态属性只挡得住 `new`，另两条路会绕过 |

第三条最容易被忽略，也是面试的区分点，见第三节实测。

## 二、最小可用实现（本机跑通）

```php
<?php

declare(strict_types=1);

final class Counter
{
    private static ?self $instance = null;
    private int $n = 0;

    private function __construct() {}

    public static function getInstance(): self
    {
        return self::$instance ??= new self();
    }

    public function inc(): int
    {
        return ++$this->n;
    }

    private function __clone() {}

    public function __wakeup(): void
    {
        throw new RuntimeException('单例不允许反序列化');
    }
}

$a = Counter::getInstance();
$b = Counter::getInstance();
echo 'identity_same_object: ', var_export($a === $b, true), PHP_EOL;
echo 'inc_twice: ', $a->inc(), ' then ', $b->inc(), PHP_EOL;
```

实测输出（`D:\phpstudy_pro\Extensions\php\php8.0.2nts\php.exe`）：

```text
identity_same_object: true
inc_twice: 1 then 2
```

两个细节值得记：

- `self::$instance ??= new self()` 等价于 `if (self::$instance === null) { ... }`，PHP 7.4+ 可用；写在标准 `getInstance()` 里比 `if` 少一层缩进，且**天然幂等**。
- `final` + `private __construct` 要一起用。少了 `final`，子类 `extends` 后 `new self()` 造出的仍是父类实例，是个隐蔽 bug；此时应改用 `new static()`（late static binding），但那样"一个静态属性管所有子类"的语义就不再是单例了，所以实践上直接 `final` 更干净。

## 三、clone 和 unserialize 是两条后门，实测能堵

```php
<?php

declare(strict_types=1);

// 接第二节代码
$c = clone Counter::getInstance();
```

```php
<?php

declare(strict_types=1);

// 接第二节代码
$d = unserialize(serialize(Counter::getInstance()));
```

实测输出：

```text
clone_blocked: Error / Call to private Counter::__clone() from global scope
unserialize_blocked: 单例不允许反序列化
```

结论与坑：

1. **`private __clone()` 抛的是 `Error`（致命），不是异常**，业务代码 `try {} catch (Exception)` 抓不到，只能用 `Throwable`。
2. **反序列化默认不经过构造函数**，只触发 `__wakeup()`，所以只写私有构造是挡不住它的。`__wakeup()` 里抛异常是标准堵法。这一条在真实项目里远不止"挡单例"——PHP 的反序列化 POP 链（unserialize → `__wakeup`/`__destruct` 魔术方法串联）就是靠这些入口打进去的，能把任意类实例化出来。
3. `__destruct` 不需要挡：单例销毁时机本来就不确定，主动 `unset` 反而会让后续 `getInstance()` 返回一个已被析构的对象。

## 四、PHP 的单例只"单"一次请求，这是和 Java/Go 最大的差别

这一节是本篇相对传统讲解要补的核心。

PHP 是 **shared-nothing** 模型：php-fpm 每个请求结束后，Zend 会回收用户态内存，静态属性随之消失。所以：

| 运行模型 | `getInstance()` 作用域 | 想跨请求复用怎么办 |
| --- | --- | --- |
| php-fpm（传统 PHP） | **单个请求内**唯一 | 静态属性无效；只能靠连接持久化（如 PDO 复用连接需 `php-fpm` 常驻 + 应用层池，或换模型） |
| Swoole / RoadRunner / FrankenPHP 常驻 | **整个进程生命周期**内唯一 | 天然复用，但**必须考虑协程隔离与多进程不共享** |
| CLI 脚本 | 单次进程运行 | 同常驻 |

实测证据：同一个脚本里连续三次 `getInstance()`，构造函数只跑了一次。

```php
<?php

declare(strict_types=1);

final class RequestScoped
{
    public static int $ctorCount = 0;

    private static ?self $instance = null;

    private function __construct()
    {
        self::$ctorCount++;
    }

    public static function getInstance(): self
    {
        return self::$instance ??= new self();
    }
}

RequestScoped::getInstance();
RequestScoped::getInstance();
RequestScoped::getInstance();
echo 'ctor_calls_for_3_getInstance: ', RequestScoped::$ctorCount, PHP_EOL;
```

```text
ctor_calls_for_3_getInstance: 1
```

由此推出两条实战判断：

- **php-fpm 下单例省的是"一次请求内的重复开销"**（同一请求里第 2、3 次拿连接/配置），省不了跨请求开销。所以说"单例用来减少数据库连接数"在 php-fpm 下是错的——连接数由 `php-fpm` 进程数（`pm.max_children`）决定，跟单例无关。
- **到了 Swoole/RoadRunner 下，单例反而变成风险源**：进程常驻使静态属性变成跨请求状态，一旦实例里存了用户态数据就是**串号（数据越权）**。这也是 Laravel Octane 要提供 `Table`/`Odan\Resettable` 这类"请求结束重置"机制的原因。写常驻 PHP 时应优先把"共享的东西"（连接、配置）和"请求态的东西"（当前用户）分开，前者可单例、后者必须每请求重建。

## 五、使用方法：三种写法怎么选，推荐把实例交给容器

单例的类自持 `getInstance()` 写法有个实际代价：**私有构造 + 静态访问点让依赖无法注入、无法在测试里替换**。所以下面三档按可测试性递增：

| 写法 | 代码形态 | 适用 | 问题 |
| --- | --- | --- | --- |
| 类自持 | `X::getInstance()` | 日志/配置这类真正全局的基础设施 | 隐式全局，单测要 `setUp` 里重置静态属性，容易漏 |
| 服务容器 | `$c->singleton(X::class, fn)` | 业务依赖（DB、HTTP client、缓存） | 需要容器 |
| 显式传参 | 构造时把依赖交进去 | 库代码 / 需要严格测试的模块 | 上层要写装配代码 |

容器版 `singleton`（实测可跑，就是 Laravel 容器 `singleton()` 的最小内核）：

```php
<?php

declare(strict_types=1);

final class Container
{
    /** @var array<string, array{factory: callable, resolved: ?object}> */
    private array $bindings = [];

    /** @param callable(self): object $factory */
    public function singleton(string $id, callable $factory): void
    {
        $this->bindings[$id] = ['factory' => $factory, 'resolved' => null];
    }

    public function make(string $id): object
    {
        $b = $this->bindings[$id];
        if ($b['resolved'] === null) {
            $this->bindings[$id]['resolved'] = ($b['factory'])($this);
        }
        return $this->bindings[$id]['resolved'];
    }
}

final class DbHandle
{
    public function __construct(public string $dsn) {}
}

$c = new Container();
$c->singleton('db', static fn (): DbHandle => new DbHandle('mysql:host=127.0.0.1'));
$x = $c->make('db');
$y = $c->make('db');
echo 'container_same: ', var_export($x === $y, true), ' dsn=', $x->dsn, PHP_EOL;
```

```text
container_same: true dsn=mysql:host=127.0.0.1
```

关键差别：**"只创建一个"这件事由容器负责，类本身保持普通构造函数**，于是测试时可以 `$c->singleton('db', fn () => new FakeDb())` 直接换掉实现。业务代码里应该几乎不写 `getInstance()`，只在框架装配处写 `singleton()`。

一句话选型：**基础设施类（日志、配置、驱动句柄）可以自持单例；业务依赖一律走容器 `singleton`。**

## 六、Go / Java 的对照实现（都已编译校验）

同一模式在常驻语言里才真正"全局唯一"，写法也更简单。

Go（本机 `go1.26.5`，`go build` + `go vet` 通过）：

```go
package main

import (
	"fmt"
	"sync"
)

type Config struct{ DSN string }

var config = sync.OnceValue(func() *Config {
	return &Config{DSN: "mysql:host=127.0.0.1"}
})

func main() {
	a, b := config(), config()
	fmt.Println("same:", a == b, "dsn:", a.DSN)
}
```

```text
same: true dsn: mysql:host=127.0.0.1
```

Java（本机 `javac 1.8.0_202` 编译通过；推荐写法是**枚举单例**，反射和序列化都挡得住）：

```java
public enum AppContext {
    INSTANCE;

    private String dsn = "mysql:host=127.0.0.1";

    public String dsn() {
        return dsn;
    }
}

class SingletonDemo {
    public static void main(String[] args) {
        AppContext a = AppContext.INSTANCE;
        AppContext b = AppContext.INSTANCE;
        System.out.println("same: " + (a == b) + " dsn: " + a.dsn());
    }
}
```

```text
same: true dsn: mysql:host=127.0.0.1
```

三者对照：

| | PHP | Go | Java |
| --- | --- | --- | --- |
| 生命周期 | 一次请求（php-fpm）/ 进程（常驻） | 进程 | JVM 生命周期 |
| 并发安全 | 不涉及（单请求单线程） | 需要（`sync.OnceValue`） | 需要（枚举由 JVM 保证） |
| 能否被反射/序列化绕过 | 能（`clone`/`unserialize`，见第三节） | 不能（未导出即不可见） | 枚举不能，普通类能 |
| 跨请求复用 | 要靠常驻或连接池 | 天然 | 天然 |

## 面试官会追问什么

- **为什么只写私有构造函数挡不住单例？** → `clone` 与 `unserialize` 是两条绕过 `__construct` 的路；前者靠私有 `__clone`，后者靠 `__wakeup` 抛异常。
- **PHP 里用单例做数据库连接池，合理吗？** → 不合理。php-fpm 每请求回收内存，静态属性跨不了请求，连接数实际由 `pm.max_children` 决定；要真复用得靠常驻模型或代理层（ProxySQL / pgbouncer 这类）。
- **单例和"全局变量"有什么区别？** → 本质都是全局状态，单例只是把它包成了受控入口；测试上仍然难替换，所以业务依赖优先容器注入。
- **Swoole 下静态属性有什么坑？** → 进程常驻 → 静态属性变成跨请求共享，存请求态数据会串号；协程下还需要 `Context` 做协程级隔离。
- **`new self()` 和 `new static()` 在单例里的区别？** → `self` 绑死定义处父类，子类继承 `getInstance()` 会拿到父类实例；`static` 走后期静态绑定，但那就不再是"一个类一个实例"了。
