## 一、什么是工厂模式

原文的定义：

> 工厂模式是一种类，可以理解为创建类实例的工厂，它具有创建对象的某些方法。
> 可以**使用工厂类创建对象，而不直接使用 `new`**。这样，如果想要更改所创建的对象类型，**只需更改该工厂即可**。
> 使用该工厂的所有代码会自动更改。

原文对三种形态的划分与取舍，是全系列里讲得最清楚的一段：

> 根据抽象程度不同，PHP 工厂模式分为：**简单工厂、工厂方法和抽象工厂**。
>
> 三种工厂的区别是，**抽象工厂有多条产品线，而工厂方法只有一条产品线**，是抽象工厂的简化。
> 而工厂方法和简单工厂相对，初看起来好像工厂方法增加了许多代码、但实现的功能和简单工厂一样。
> 但本质是，**简单工厂并未严格遵循设计模式的开闭原则**，当需要增加新产品时也需要修改工厂代码；
> 而工厂方法则严格遵守开闭原则，模式只负责抽象工厂接口，**具体工厂交给客户去扩展**。
> 在分工时，**核心工程师负责抽象工厂和抽象产品的定义，业务工程师负责具体工厂和具体产品的实现**。

整理成表：

| 形态 | 一句话 | 新增产品时改哪里 | 是否满足开闭 |
| --- | --- | --- | --- |
| 简单工厂 | 一个方法 + 分支，集中决定造哪个 | 改这个方法的 `match` | ❌ 要改工厂 |
| 工厂方法 | 每个产品配一个子工厂类，实现同一接口 | 加一个新工厂类，不动老代码 | ✅ |
| 抽象工厂 | 一个工厂负责造"一整族"相关产品 | 加一族工厂 | ✅ |

原文最后那句**"核心工程师定义抽象、业务工程师实现具体"**，说的其实是工厂方法的真正价值：它把"产品接口长什么样"和"这次要造哪一个"拆成了两个人的工作。

## 二、应用场景

| 场景 | 说明 |
| --- | --- |
| 运行时按输入决定造哪个 | 用户选格式（CSV/JSON）、按配置选驱动（local/s3）、按渠道选支付 |
| 造出来的对象初始化步骤相同、只是类型不同 | 各类 `Handler`、各类 `Exporter` |
| 想把"造哪个"这个决定收拢到一处 | 以后换实现只改一个地方 |

**反过来，下面这些情况不要工厂**：

- 写代码时就知道要 `new` 谁、且关系固定 → 直接 `new` 或走容器绑定，工厂是多余的一层；
- 只是想让 `new` 看起来"解耦" → 那需要的是**依赖注入**，不是工厂（见第五节）。

判据一句话：**"造哪个类"是写代码时就定死，还是运行时按输入决定？** 后者才需要工厂。

## 三、PHP 标准实现

场景统一为**报表导出**：同一批数据，按格式产出 CSV 或 JSON。

### 3.1 产品与简单工厂

```php
<?php

declare(strict_types=1);

interface Exporter
{
    public function export(array $rows): string;
}

final class CsvExporter implements Exporter
{
    public function export(array $rows): string
    {
        $lines = [];
        foreach ($rows as $row) {
            $lines[] = implode(',', array_map(static fn ($v): string => (string) $v, $row));
        }
        return implode("\n", $lines);
    }
}

final class JsonExporter implements Exporter
{
    public function export(array $rows): string
    {
        return (string) json_encode($rows, JSON_UNESCAPED_UNICODE);
    }
}

/** 简单工厂：一个方法集中决定造哪个 */
final class ExporterFactory
{
    public function create(string $format): Exporter
    {
        return match ($format) {
            'csv' => new CsvExporter(),
            'json' => new JsonExporter(),
            default => throw new InvalidArgumentException("不支持的导出格式：{$format}"),
        };
    }
}
```

### 3.2 工厂方法：把「造哪个」下推给子类

```php
abstract class ReportGenerator
{
    /** 子类决定用哪种导出器；父类只管流程 */
    abstract protected function createExporter(): Exporter;

    final public function generate(array $rows): string
    {
        return $this->createExporter()->export($rows);
    }
}

final class MonthlyReport extends ReportGenerator
{
    protected function createExporter(): Exporter
    {
        return new CsvExporter();
    }
}

final class ApiReport extends ReportGenerator
{
    protected function createExporter(): Exporter
    {
        return new JsonExporter();
    }
}
```

**使用示例**：

```php
// 简单工厂：调用方只依赖 Exporter 接口，换格式不改调用方
$factory = new ExporterFactory();
$rows = [['Ann', 'eng'], ['Bob', 'sales']];

$factory->create('csv')->export($rows);     // Ann,eng | Bob,sales
$factory->create('json')->export($rows);    // [{"name":"Ann","dept":"eng"},...]

// 未知格式当场抛异常，而不是返回 null
$factory->create('xml');                    // 抛 InvalidArgumentException

// 工厂方法：父类只管流程，子类决定造哪个
(new MonthlyReport())->generate($rows);     // Ann,eng | Bob,sales
(new ApiReport())->generate($rows);         // [{"name":"Ann","dept":"eng"},...]
```

实测（PHP 8.0.2 CLI）：

```text
1a_简单工厂 csv : Ann,eng | Bob,sales
1b_简单工厂 json: [{"name":"Ann","dept":"eng"},{"name":"Bob","dept":"sales"}]
2a_工厂方法 MonthlyReport : Ann,eng | Bob,sales
2b_工厂方法 ApiReport     : [{"name":"Ann","dept":"eng"},{"name":"Bob","dept":"sales"}]
4_非法格式当场失败 : 不支持的导出格式：xml
```

两者的差别不在输出，而在**扩展成本**：新增一种格式，简单工厂要改 `match`（违反开闭），工厂方法只需加一个 `XxxReport` 类（不动老代码）。

### 4 个让它算「标准写法」的细节

| # | 做法 | 为什么 |
| --- | --- | --- |
| 1 | 产品先有 `interface`，工厂返回**接口类型** | 调用方只依赖抽象，换实现不改调用方 |
| 2 | 简单工厂用 `match` 而不是 `switch` | `match` 是表达式、无贯穿、未覆盖分支会报 `UnhandledMatchError` |
| 3 | 未知类型**当场抛异常**，不返回 `null` | 返回 `null` 会把错误推到调用方，且 IDE 无法提示 |
| 4 | 工厂方法里 `createExporter()` 是 `abstract protected` | 只给子类用，不该暴露给外部；父类的 `generate()` 声明 `final` 防覆盖 |

## 四、`new self()` 与 `new static()`：工厂基类里的一个真坑

这是原文没提、但在"可继承的工厂基类"里必定会遇到的问题：

```php
class BaseFactory
{
    public static function makeWithSelf(): self
    {
        return new self();          // self 是「定义时」的类
    }

    public static function makeWithStatic(): static
    {
        return new static();        // static 是「调用时」的类（late static binding）
    }
}

class ChildFactory extends BaseFactory
{
}
```

实测输出：

```text
3a_new self()   造出来的类型 : BaseFactory
3b_new static() 造出来的类型 : ChildFactory
3c_是 ChildFactory 吗        : self=false static=true
```

**`ChildFactory::makeWithSelf()` 造出来的是 `BaseFactory` 实例** —— 这是 `self` 的编译期绑定语义（`self` 在定义处就被解析成 `BaseFactory`）。一旦工厂基类里有 `new self()`，子类"继承工厂"这个行为就是**坏的**：它返回父类对象，且**不报错**，直到某个只存在于子类的方法被调用时才炸。

**实践结论**：

- 工厂基类里要造"自己这个类"，用 `static`（或 `static::class`）；
- 但如果这个工厂压根不该被继承，**加 `final` 更省事** —— 那 `self` 与 `static` 的差别就不存在了。这也是为什么本目录的工厂一律 `final`。

## 五、什么时候不需要工厂（工厂 vs 容器）

这是比其他模式更常被过度使用的地方。三个判据：

| 情况 | 该用什么 |
| --- | --- |
| 依赖固定、写代码时就知道要谁 | **直接 `new`**（或用构造注入） |
| 依赖要按配置/环境切换（dev 用 file，prod 用 s3） | **容器绑定**（`$container->bind(...)` / `singleton()`） |
| 要按**运行时输入**（用户传参、数据库里的类型字段）决定造哪个 | **工厂** |

工厂与容器的分工是：**工厂负责"根据输入决定造哪个"，容器负责"装配与生命周期"**。二者常一起用 —— 工厂作为服务注册进容器，由容器保证它是单例（见 [单例模式.md](单例模式.md) 3.2 的 `Container::singleton()`）。

反过来说，**只是为了"看起来解耦"而把每个 `new` 都包进工厂，是把复杂度从一处摊到了各处**：多一个类、多一层跳转，而依赖关系并没变。

## 六、Java 实现

```java
public class FactoryStandard {
    interface Exporter {
        String export(List<String[]> rows);
    }

    static final class CsvExporter implements Exporter {
        public String export(List<String[]> rows) {
            StringBuilder sb = new StringBuilder();
            for (int i = 0; i < rows.size(); i++) {
                if (i > 0) {
                    sb.append("\n");
                }
                sb.append(String.join(",", rows.get(i)));
            }
            return sb.toString();
        }
    }

    static final class JsonExporter implements Exporter {
        public String export(List<String[]> rows) {
            StringBuilder sb = new StringBuilder("[");
            for (int i = 0; i < rows.size(); i++) {
                if (i > 0) {
                    sb.append(",");
                }
                sb.append("{\"name\":\"").append(rows.get(i)[0])
                  .append("\",\"dept\":\"").append(rows.get(i)[1]).append("\"}");
            }
            return sb.append("]").toString();
        }
    }

    /** 简单工厂：集中决定造哪个 */
    static final class ExporterFactory {
        Exporter create(String format) {
            if ("csv".equals(format)) {
                return new CsvExporter();
            }
            if ("json".equals(format)) {
                return new JsonExporter();
            }
            throw new IllegalArgumentException("不支持的导出格式：" + format);
        }
    }

    /** 工厂方法：子类决定造哪个，父类只管流程 */
    abstract static class ReportGenerator {
        protected abstract Exporter createExporter();

        final String generate(List<String[]> rows) {
            return createExporter().export(rows);
        }
    }
}
```

**使用示例**：

```java
// 简单工厂：调用方只依赖 Exporter 接口
ExporterFactory factory = new ExporterFactory();
List<String[]> rows = new ArrayList<String[]>();
rows.add(new String[] {"Ann", "eng"});
rows.add(new String[] {"Bob", "sales"});

factory.create("csv").export(rows);      // Ann,eng | Bob,sales
factory.create("json").export(rows);     // [{"name":"Ann","dept":"eng"},...]

// 未知格式当场抛异常
factory.create("xml");                   // 抛 IllegalArgumentException

// 工厂方法：子类实现 createExporter()，父类只管流程
ReportGenerator report = new ReportGenerator() {
    protected Exporter createExporter() { return new CsvExporter(); }
};
report.generate(rows);                   // Ann,eng | Bob,sales
```

JDK 1.8 实测输出与 PHP 版逐行一致：

```text
1a_简单工厂 csv : Ann,eng | Bob,sales
1b_简单工厂 json: [{"name":"Ann","dept":"eng"},{"name":"Bob","dept":"sales"}]
2a_工厂方法 MonthlyReport : Ann,eng | Bob,sales
2b_工厂方法 ApiReport     : [{"name":"Ann","dept":"eng"},{"name":"Bob","dept":"sales"}]
3_非法格式当场失败 : 不支持的导出格式：xml
```

Java 侧的两点差异：

- **没有 `new self()` 之争**：Java 的静态方法不参与继承语义，`Base.make()` 里的 `new Base()` 就是 `Base`，不存在 late static binding 这个概念，因此也没有这个坑；
- **JDK 8 没有 switch 表达式**，分支要用 `if` 或传统 `switch`（写 `default: throw`）。JDK 12+ 才有 `switch` 表达式，与 PHP 的 `match` 对应。

## 七、Go 实现

```go
// NewExporter 简单工厂：集中决定造哪个
// Go 的惯例是返回接口 + error，而不是抛异常
func NewExporter(format string) (Exporter, error) {
	switch format {
	case "csv":
		return CsvExporter{}, nil
	case "json":
		return JsonExporter{}, nil
	default:
		return nil, errors.New("不支持的导出格式：" + format)
	}
}

// ReportGenerator 工厂方法：子类决定造哪个，父类只管流程
type ReportGenerator interface {
	CreateExporter() Exporter
	Generate(rows [][2]string) (string, error)
}

type MonthlyReport struct{}

func (MonthlyReport) CreateExporter() Exporter { return CsvExporter{} }

func (m MonthlyReport) Generate(rows [][2]string) (string, error) {
	return m.CreateExporter().Export(rows)
}
```

**使用示例**：

```go
// 简单工厂：返回接口 + error，而不是抛异常
rows := [][2]string{{"Ann", "eng"}, {"Bob", "sales"}}

csv, err := NewExporter("csv")
if err != nil {
	panic(err)
}
out, _ := csv.Export(rows)              // Ann,eng | Bob,sales

js, _ := NewExporter("json")
out, _ = js.Export(rows)                // [{"name":"Ann","dept":"eng"},...]

// 未知格式返回 error，调用方必须处理
_, err = NewExporter("xml")             // err: 不支持的导出格式：xml

// 工厂方法：父类是接口，MonthlyReport 自己决定造 CsvExporter
var report ReportGenerator = MonthlyReport{}
report.Generate(rows)                   // Ann,eng | Bob,sales, nil
```

go1.26.5 实测输出（与 PHP/Java 一致）：

```text
1a_简单工厂 csv : Ann,eng | Bob,sales
1b_简单工厂 json: [{"name":"Ann","dept":"eng"},{"name":"Bob","dept":"sales"}]
2a_工厂方法 MonthlyReport : Ann,eng | Bob,sales
2b_工厂方法 ApiReport     : [{"name":"Ann","dept":"eng"},{"name":"Bob","dept":"sales"}]
3_非法格式当场失败 : 不支持的导出格式：xml
```

Go 的三点差异：

- **没有异常，错误是返回值**：`NewExporter` 返回 `(Exporter, error)`，调用方必须显式判断 —— 比 PHP/Java 的 `throw` 更啰嗦，但调用点永远不会漏掉错误分支；
- **没有继承，用接口 + 组合表达"工厂方法"**：`ReportGenerator` 是接口而非抽象类，`MonthlyReport` 只是实现了它。Go 里"子类决定父类行为"这件事靠**接口实现**而不是继承；
- **一个易踩的点**：`json.Marshal` 对 `map` 的键顺序是**无序的**，要保证输出稳定，必须用带 tag 的 struct（本实现就是这么做的）。

## 八、PHP / Java / Go 对照

| | PHP | Java | Go |
| --- | --- | --- | --- |
| 简单工厂的分支写法 | `match`（8.0+） | `if` / `switch`（JDK 12+ 才有表达式） | `switch` |
| 工厂方法 | `abstract class` + 子类继承 | `abstract class` 或接口默认方法 | **接口 + 实现**（无继承） |
| 未知类型 | `throw` | `throw` | **返回 `error`** |
| `new self()` 陷阱 | **有**（late static binding） | 无 | 无 |
| 与容器配合 | `$container->bind()` | Spring `@Bean` / `FactoryBean` | 手写装配或 wire |

三种语言里，**只有 PHP 需要操心 `self` 与 `static` 的差异**；而"错误怎么传"是三语言里最需要区分的：PHP/Java 抛异常，Go 返回 `error`。

## 九、面试官会追问什么

- **简单工厂、工厂方法、抽象工厂的区别？** → 简单工厂一个方法内部分支（违反开闭）；工厂方法每个产品配一个工厂类（满足开闭，一条产品线）；抽象工厂一个工厂造一族相关产品（多条产品线）。
- **`new self()` 和 `new static()` 有什么区别？** → `self` 编译期绑定（定义时的类），`static` 运行期绑定（调用时的类）。工厂基类里用 `self` 会让子类继承出**父类实例**，且不报错。不想被继承就加 `final`。
- **什么时候不该用工厂？** → 依赖固定、写代码时就知道 `new` 谁的时候。那种情况下需要的是依赖注入，不是工厂。
- **工厂和容器是什么关系？** → 工厂负责"按输入决定造哪个"，容器负责"装配 + 生命周期"。工厂常作为服务注册进容器。
- **工厂方法里的 `createExporter()` 为什么要 `protected`？** → 它是给子类实现的钩子，不属于对外接口；对外只暴露 `generate()`（通常还要 `final` 防覆盖流程）。
- **为什么简单工厂常被批评？** → 违反开闭原则：加一个产品就要改工厂的分支。但它的复杂度最低，**产品种类少且稳定时完全够用**，不必为"政治正确"上工厂方法。
