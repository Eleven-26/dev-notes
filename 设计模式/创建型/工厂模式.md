# 工厂模式：把"new 哪个类"这个决定收拢到一处

> 素材来源：博客系列 [PHP 设计模式(二)：工厂模式](https://blog.csdn.net/weixin_43837229/article/details/102619258)。
> 本篇把它重写成能直接抄进项目的版本，并补上原系列没讲清的三件事：
> **①简单工厂 / 工厂方法 / 抽象工厂在 PHP 里各自的真实形态；②`new static()` 与 `new self()` 在工厂基类里的致命差异（实测）；③工厂和服务容器（DI）的边界——什么时候工厂纯属多余。**
>
> 单例见 [单例模式.md](单例模式.md)，注册表见 [注册模式.md](注册模式.md)，克隆见 [原型模式.md](原型模式.md)。

## 一、工厂不是"一个"模式，是三个，先分清楚各解决什么

| 形态 | 一句话 | 新增产品时改哪里 | PHP 里常见吗 |
| --- | --- | --- | --- |
| 简单工厂 | 一个静态方法 + `switch`，集中决定造哪个 | 改这个方法的 `switch`（违反 OCP） | 最常见，就是普通静态方法 |
| 工厂方法 | 每个产品配一个子工厂类，实现同一接口 | 加一个新工厂类，不动老代码 | 常用 |
| 抽象工厂 | 一个工厂负责造"一整族"相关产品 | 加一族工厂 | 很少；PHP 缺泛型，价值有限 |

**结论先行：多数业务你要的是"简单工厂"，需要可插拔才升级到"工厂方法"，抽象工厂在 PHP 里几乎用不上**（动态类型 + 容器让它有更轻的替代，见第四节）。是否需要工厂只看一个问题：**"造哪个类"是写代码时就定死，还是运行时按输入决定？**

- 写代码时就知道、关系固定 → **不要工厂，直接 `new` 或走容器绑定**（第五节）。
- 运行时才知道（用户选支付、按配置选驱动）→ 简单工厂起步。
- 分支持续增长、且每支都要在测试里单独替换 → 工厂方法。

## 二、最小可用实现：简单工厂（本机 PHP 8.0.2 跑通）

```php
<?php

declare(strict_types=1);

interface Payment { public function pay(int $cents): string; }

final class Alipay implements Payment {
    public function pay(int $c): string { return "支付宝扣 {$c} 分"; }
}
final class WechatPay implements Payment {
    public function pay(int $c): string { return "微信扣 {$c} 分"; }
}

final class PaymentFactory
{
    // 简单工厂：一个静态方法 + match，新增渠道要回来改这里（这就是它的代价）
    public static function make(string $channel): Payment
    {
        return match ($channel) {
            'alipay' => new Alipay(),
            'wechat' => new WechatPay(),
            default => throw new InvalidArgumentException("未知渠道: {$channel}"),
        };
    }
}

echo PaymentFactory::make('alipay')->pay(100), PHP_EOL;
echo PaymentFactory::make('wechat')->pay(250), PHP_EOL;
try { PaymentFactory::make('paypal'); }
catch (InvalidArgumentException $e) { echo 'err: ', $e->getMessage(), PHP_EOL; }
```

```text
支付宝扣 100 分
微信扣 250 分
err: 未知渠道: paypal
```

要点：

- 返回值声明成**接口** `Payment` 而非具体类，调用方只依赖接口——这是工厂能"隐藏具体类"的前提。
- `match` 是 PHP 8.0 引入的，7.4 及以下要写回 `switch`。
- 未知输入**抛异常而不是返回 `null`**，把错误暴露在构造点，省掉调用方满屏 `if ($p === null)`。

## 三、工厂方法：把"造哪个"下推给子工厂，新增不改老代码

简单工厂的 `switch` 越长越脏。工厂方法把每个渠道拆成自己的工厂类，都实现同一个 `PaymentFactory` 接口：

```php
<?php

declare(strict_types=1);

interface Payment { public function pay(int $c): string; }
final class Alipay implements Payment { public function pay(int $c): string { return "支付宝 {$c}"; } }
final class Wechat implements Payment { public function pay(int $c): string { return "微信 {$c}"; } }

interface PaymentFactory { public function create(): Payment; }
final class AlipayFactory implements PaymentFactory {
    public function create(): Payment { return new Alipay(); }
}
final class WechatFactory implements PaymentFactory {
    public function create(): Payment { return new Wechat(); }
}

// 业务只依赖"工厂接口"，具体用哪个工厂由上层装配决定
function checkout(PaymentFactory $f, int $c): string {
    return $f->create()->pay($c);
}
echo checkout(new AlipayFactory(), 100), PHP_EOL;
echo checkout(new WechatFactory(), 250), PHP_EOL;
```

```text
支付宝 100
微信 250
```

新增"云闪付"时，只加一个 `UnionPayFactory` 类，`checkout()` 和已有工厂一行不动——**这才是工厂方法相对简单工厂唯一的实质收益：对扩展开放**。代价是类数量翻倍，所以只有当分支真的会持续增加时才值得。

## 四、"抽象工厂"在 PHP 里的真实形态：造一族，不混用

抽象工厂保证"同一族的产品一起造"，典型是跨平台 UI（Win 按钮配 Win 输入框）：

```php
<?php

declare(strict_types=1);

interface Button { public function render(): string; }
interface Input  { public function render(): string; }

final class WinButton implements Button { public function render(): string { return 'Win 按钮'; } }
final class WinInput  implements Input  { public function render(): string { return 'Win 输入框'; } }
final class MacButton implements Button { public function render(): string { return 'Mac 按钮'; } }
final class MacInput  implements Input  { public function render(): string { return 'Mac 输入框'; } }

// 一个工厂 = 一整个产品族，接口锁死"按钮+输入框"必须成对
interface UIFactory { public function button(): Button; public function input(): Input; }
final class WinFactory implements UIFactory {
    public function button(): Button { return new WinButton(); }
    public function input(): Input { return new WinInput(); }
}
final class MacFactory implements UIFactory {
    public function button(): Button { return new MacButton(); }
    public function input(): Input { return new MacInput(); }
}

function renderForm(UIFactory $f): string {
    return $f->button()->render() . ' + ' . $f->input()->render();
}
echo renderForm(new WinFactory()), PHP_EOL;
echo renderForm(new MacFactory()), PHP_EOL;
```

```text
Win 按钮 + Win 输入框
Mac 按钮 + Mac 输入框
```

**为什么说 PHP 里它很少用**：抽象工厂的价值在编译期"类型族"约束（Java 靠泛型 `Factory<AbstractProduct>` 表达）。PHP 是动态类型，这层约束表达不出来，于是"族"往往退化成一组普通工厂方法 + 数组配置，或交给容器按 tag 分组。真要"整套驱动切换"（MySQL/Postgres 各配一套连接+方言），PHP 项目更常用**一个 Driver/Repository 对象内部同时提供多种能力**，而不是教科书式的抽象工厂类族。

## 五、PHP 没有方法重载：命名构造函数 or `__callStatic`

Java/C# 的工厂常写成同名不同参的 `Point(x,y)` / `Point(r,a)`。PHP 不支持构造函数重载，标准解法是**私有构造 + 多个命名构造函数**；再配 `__callStatic` 兜住"调了不存在的构造入口"：

```php
<?php

declare(strict_types=1);

final class Point
{
    private function __construct(
        public float $x,
        public float $y,
        public string $kind,
    ) {}

    public static function fromPolar(float $r, float $a): self
    {
        return new self($r * cos($a), $r * sin($a), 'polar');
    }
    public static function fromCartesian(float $x, float $y): self
    {
        return new self($x, $y, 'cartesian');
    }

    // 调用未定义的静态方法时兜底：给出清晰错误，而不是致命 Error
    public static function __callStatic(string $name, array $args): void
    {
        throw new BadMethodCallException("Point::{$name} 不是合法构造入口");
    }

    public function label(): string { return sprintf('[%s] (%.2f,%.2f)', $this->kind, $this->x, $this->y); }
}

echo Point::fromCartesian(3, 4)->label(), PHP_EOL;
echo Point::fromPolar(5, 0)->label(), PHP_EOL;
try { Point::fromWhatever(1); } catch (BadMethodCallException $e) { echo 'err: ', $e->getMessage(), PHP_EOL; }
```

```text
[cartesian] (3.00,4.00)
[polar] (5.00,0.00)
err: Point::fromWhatever 不是合法构造入口
```

取舍：命名构造函数（`fromXxx`）是**首选**，可读、可静态分析、IDE 能补全。`__callStatic` 只做"拼写错误兜底 / 动态派发"，别用它去模拟重载分发业务逻辑——那会让调用点失去类型检查。这里 `__construct` 用了构造器属性提升（PHP 8.0+），7.3 及以下要手写属性声明和赋值。

## 六、`new static()` vs `new self()`：工厂基类里的一个致命 bug

如果工厂逻辑写在**会被继承的基类**里（常见于"父类提供一个 `make()` 造自己"），`self` 和 `static` 的结果完全不同：

```php
<?php

declare(strict_types=1);

class SelfBase
{
    // new self()：绑死"定义处"的类，永远造 SelfBase
    public static function makeSelf(): self { return new self(); }
    // new static()：走后期静态绑定(LSB)，谁调用造谁
    public static function makeStatic(): static { return new static(); }

    public function name(): string { return static::class; }
}

final class Child extends SelfBase {}

echo 'base_makeSelf: ', get_class(SelfBase::makeSelf()), PHP_EOL;
echo 'child_makeSelf: ', get_class(Child::makeSelf()), ' <- 子类调用仍是父类(陷阱)', PHP_EOL;
echo 'child_makeStatic: ', get_class(Child::makeStatic()), PHP_EOL;
echo 'name_via_static: ', Child::makeStatic()->name(), PHP_EOL;
```

```text
base_makeSelf: SelfBase
child_makeSelf: SelfBase <- 子类调用仍是父类(陷阱)
child_makeStatic: Child
name_via_static: Child
```

结论：

1. `new self()` 里的 `self` 在**编译期**就绑死为写这行代码的类（`SelfBase`），无论谁来调用都造 `SelfBase`。
2. `new static()` 的 `static` 在**运行期**按调用者解析（后期静态绑定），`Child::makeStatic()` 造出 `Child`。
3. 这条和 [单例模式.md](单例模式.md) 第二节是同一枚硬币：单例故意用 `new self()` + `final` 把子类堵死；工厂基类想"被子类继承后造子类"就必须 `new static()`。判断标准只有一句——**这个创建点希不希望被子类改写目标类型？希望用 `static`，不希望用 `self` 并配 `final`。**

## 七、工厂 vs 容器 DI：什么时候工厂纯属多余

工厂和容器做的是**同一件事**——把"决定 new 哪个"从业务代码里搬走。区别在"搬运方式"：

| 维度 | 工厂 | 服务容器（DI） |
| --- | --- | --- |
| 触发时机 | 运行时按**输入**分派（`make($channel)`） | 装配时按**类型**解析（`make(Payment::class)`） |
| 依赖图 | 只造一个对象，不管它的依赖 | 递归解析整棵依赖树 |
| 可测试性 | 要传"工厂"进去，测试传假工厂 | 测试传假实现或重绑绑定 |
| 何时多余 | **依赖固定、无运行时分派时**——工厂只是给 `new` 套了层壳 | — |

```php
<?php

declare(strict_types=1);

interface Mailer { public function send(string $to): string; }
final class SmtpMailer implements Mailer {
    public function __construct(private string $host) {}
    public function send(string $to): string { return "via {$this->host} -> {$to}"; }
}

// 依赖关系固定、没有按输入分派的分支：容器绑定即可，写个工厂类是多余的
$c = new class {
    private array $binds = [];
    public function bind(string $id, callable $f): void { $this->binds[$id] = $f; }
    public function make(string $id): object { return ($this->binds[$id])($this); }
};
$c->bind(Mailer::class, static fn (): Mailer => new SmtpMailer('smtp.example.com'));
echo $c->make(Mailer::class)->send('a@b.com'), PHP_EOL;
```

```text
via smtp.example.com -> a@b.com
```

- **需要工厂**的信号：`switch ($input)`、`if (config) ... else ...` 这类**运行时才知道造哪个**。
- **不要工厂**的信号：一个接口只对应一个实现、且关系固定 → 直接让容器把接口绑到实现，或干脆 `new`。给这种情况套一层 `XxxFactory` 是典型的过度设计（多一个要维护、要在测试里替换的间接层）。

**Laravel / Symfony 里谁在当工厂**：

- Laravel 的 **`Container`**（`App::make()`、`bind()`/`singleton()`）就是中央工厂：`Manager` 类（`DB`、`Cache`、`Queue`、`Auth`）是**按驱动名分派的工厂方法模式**——`CacheManager::driver('redis')` 内部的 `match`/`createRedisDriver()` 就是一个简单工厂；再往下具体实例的复用交给容器 `singleton`。
- Symfony 的 **`ContainerBuilder` + 服务定义（YAML/Attribute）** 在编译期把工厂生成成 PHP 代码（`*_Container.php`），`factory: ['@logger','create']` 这种配置就是"把工厂方法交给容器调"。
- 一句话：**框架的 Manager / Container 在替你当工厂；业务代码里应优先声明依赖让容器解析，而不是自己到处写 `Xxx::create()`。**

## 八、Go / Java 对照（都已本机编译 + 运行）

Go（`go1.26.5`，`go vet` + `go run` 通过）——Go 无静态方法，工厂就是一个返回接口的函数：

```go
package main

import "fmt"

type Payment interface{ Pay(int) string }

type alipay struct{}
func (alipay) Pay(c int) string { return fmt.Sprintf("支付宝 %d", c) }

type wechat struct{}
func (wechat) Pay(c int) string { return fmt.Sprintf("微信 %d", c) }

// Go 无静态方法：工厂就是一个返回接口的函数
func makePayment(channel string) (Payment, error) {
	switch channel {
	case "alipay":
		return alipay{}, nil
	case "wechat":
		return wechat{}, nil
	default:
		return nil, fmt.Errorf("未知渠道: %s", channel)
	}
}

func main() {
	p, _ := makePayment("alipay")
	fmt.Println(p.Pay(100))
	if _, err := makePayment("paypal"); err != nil {
		fmt.Println("err:", err)
	}
}
```

```text
支付宝 100
err: 未知渠道: paypal
```

Java（`javac 1.8.0_321` 编译，`java` 运行；工厂方法 = 每个产品配一个 `Creator`）：

```java
public class Factory {
    interface Payment { String pay(int cents); }

    static final class Alipay implements Payment {
        public String pay(int c) { return "支付宝 " + c; }
    }
    static final class Wechat implements Payment {
        public String pay(int c) { return "微信 " + c; }
    }

    // 工厂方法：每个产品有自己的 Creator，新增渠道不改老代码
    interface Creator { Payment create(); }
    static final class AlipayCreator implements Creator {
        public Payment create() { return new Alipay(); }
    }

    static String checkout(Creator c, int cents) {
        return c.create().pay(cents);
    }
}

class FactoryDemo {
    public static void main(String[] args) {
        System.out.println(Factory.checkout(new Factory.AlipayCreator(), 100));
        Factory.Payment p = new Factory.Wechat();
        System.out.println(p.pay(250));
    }
}
```

```text
支付宝 100
微信 250
```

三者对照：

| | PHP | Go | Java |
| --- | --- | --- | --- |
| "静态工厂方法" | `XxxFactory::make()` 原生支持 | 没有静态方法，退化成包级函数 | `static` 方法 |
| 无重载问题 | 命名构造函数 + `__callStatic` | 靠返回值/多参数区分 | 靠方法重载 `create(int)/create(String)` |
| 抽象工厂价值 | 低（动态类型表达不出类型族） | 低 | 高（泛型 `Factory<T>` 是它的用武之地） |
| 谁来当工厂 | 框架容器/Manager | `fx`/手动装配 | Spring 容器 |

## 面试官会追问什么

- **简单工厂和工厂方法到底怎么选？** → 分支稳定、就两三样 → 简单工厂（一个方法）；分支频繁增长且要在测试里逐个替换 → 工厂方法（一产品一工厂）。
- **为什么说抽象工厂在 PHP 里少见？** → 它的核心收益是编译期"类型族"约束，靠泛型表达；PHP 动态类型表达不出，且容器/数组配置能更轻地达到"整套驱动一起换"的效果。
- **`new self()` 和 `new static()` 的区别？** → `self` 编译期绑死定义处；`static` 运行期按调用者做后期静态绑定。工厂基类想被子类改目标类型用 `static`，否则用 `self`+`final`（第六节实测）。
- **有了容器还需要工厂吗？** → 依赖固定就交给容器解析；工厂只在"运行时按输入分派"时才有存在价值，否则是多余的间接层。
- **PHP 不支持构造函数重载，怎么提供多种构造入口？** → 私有构造 + `fromXxx` 命名构造函数；`__callStatic` 只做错误兜底，不用来模拟重载分发逻辑。
