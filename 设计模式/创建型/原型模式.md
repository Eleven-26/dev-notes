## 一、什么是原型模式

原文的定义：

> 原型模式是**先创建好一个原型对象，然后通过 clone 原型对象来创建新的对象**。
> 适用于**大对象**的创建，因为创建一个大对象需要很大的开销，如果每次 new 就会消耗很大，
> 原型模式**仅需内存拷贝**即可。

两个角色：

| 角色 | 职责 | PHP 对应 |
| --- | --- | --- |
| Prototype（抽象原型） | 声明一个克隆自身的接口 | `__clone()` 魔术方法 |
| Concrete Prototype（具体原型） | 实现克隆自身的操作 | 在 `__clone()` 里处理引用属性 |

在原系列的所有模式里，**原型是唯一一个 PHP 直接用语言关键字支持的**（`clone`），不需要额外的接口或框架。

## 二、浅拷贝与深拷贝

原文对这两者的论述相当完整，直接保留：

> **浅拷贝**：被拷贝对象的所有变量都含有与原对象相同的值，**而且对其他对象的引用仍然是指向原来的对象**。
> 即变量之间是地址传递的；对象之间同时指向一个地址，大家共享一个地址。
> 赋值时，引用赋值，相当于取了一个别名。**对其中一个修改，会影响另一个**。
>
> **深拷贝**：被拷贝对象的所有变量都含有与原来对象相同的值，**除了那些引用其他对象的变量**。
> 那些引用其他对象的变量将指向一个被拷贝的新对象，而不再是原有那些被引用对象。
> 即变量被复制了一份，值传递，深拷贝把要拷贝的对象所引用的对象也都拷贝了一次，
> 而这种对被引用到的对象拷贝叫做**间接拷贝**。

原文还特别点了深拷贝最大的隐患：

> 深拷贝要深入到多少层，是一个不确定的问题。…… 在深拷贝的过程中，**很可能会出现循环引用的问题**。

原文用"腌咸菜"比喻序列化也很形象：

> 把对象写到流里的过程是序列化（Serialization）…… 业界又将串行化这一过程形象地称为"**冷冻**"或"**腌咸菜**"；
> 而把对象从流中读出来的过程则叫做反序列化，也称为"**解冻**"或"**回鲜**"。

## 三、应用场景

原文的判据：**需要的对象已经创建过，可考虑复制、克隆对象，避免再次创建对象。**

展开成表：

| 场景 | 为什么用 clone 而不是 new |
| --- | --- |
| 构造昂贵（大量默认配置、预建索引/树结构） | 以现成对象为起点派生，省掉重复初始化 |
| 需要"基准配置"派生多份变体 | 复制一份再各改各的 |
| 快照 / 撤销 | 改之前留一份 |
| 不可变对象派生新版本 | 与 `withXxx()` 风格配合（见第七节） |

**不该用的场景**：对象几乎无状态、或构造本来就很便宜 —— 那时 `new` 更直观，`clone` 反而增加"到底共不共享"的心智负担。

## 四、PHP 标准实现

场景：**邮件模板**。模板里除了一批收件人（数组），还有一个签名对象（对象属性）—— 后两者在拷贝时的行为**完全不同**。

```php
<?php

declare(strict_types=1);

/** 会被引用的「子对象」—— 拷贝时最容易出问题的地方 */
final class Signature
{
    public function __construct(private string $text) {}

    public function text(): string
    {
        return $this->text;
    }

    public function setText(string $text): void
    {
        $this->text = $text;
    }
}

/** 模板基类：属性用 protected，好让子类在 __clone 里深拷 */
class MailTemplate
{
    /** @var list<string> */
    protected array $recipients = [];

    public function __construct(
        protected string $subject,
        protected Signature $signature
    ) {}

    public function addRecipient(string $email): void
    {
        $this->recipients[] = $email;
    }

    public function signatureText(): string
    {
        return $this->signature->text();
    }

    public function setSignatureText(string $text): void
    {
        $this->signature->setText($text);
    }

    /** @return list<string> */
    public function recipients(): array
    {
        return $this->recipients;
    }
}

/** 不实现 __clone：clone 就是浅拷贝，对象属性仍与原对象共享 */
final class ShallowTemplate extends MailTemplate
{
}

/** 实现 __clone：手动深拷「引用类型」属性 */
final class DeepTemplate extends MailTemplate
{
    public function __clone(): void
    {
        $this->signature = clone $this->signature;
    }
}
```

**使用示例**：

```php
// 浅拷贝：ShallowTemplate 没实现 __clone，对象属性仍是同一个
$shallow = new ShallowTemplate('欢迎', new Signature('-- 客户成功团队'));
$copy = clone $shallow;
$copy->setSignatureText('-- 被副本改掉了');
$shallow->signatureText();           // '-- 被副本改掉了'（原件被连累）

// 但数组属性是值拷贝：副本加收件人不影响原件
$copy->addRecipient('a@x.com');
count($shallow->recipients());       // 0

// 深拷贝：DeepTemplate::__clone 里把 Signature 也复制了一份
$deep = new DeepTemplate('欢迎', new Signature('-- 客户成功团队'));
$deepCopy = clone $deep;
$deepCopy->setSignatureText('x');    // 只改副本
$deep->signatureText();              // '-- 客户成功团队'（原件不受影响）
```

实测（PHP 8.0.2 CLI）：

```text
1a_浅拷贝·改副本的签名，原件变成 : -- 被副本改掉了
1b_浅拷贝·原件收件人数           : 1
1c_浅拷贝·副本收件人数           : 2
2_深拷贝·改副本的签名，原件仍为   : -- 客户成功团队
3_序列化深拷贝·原件仍为           : -- 客户成功团队
```

## 五、拷贝的不对称：对象属性 vs 数组属性

**1a 与 1b/1c 是同一个 `clone` 的两副面孔**，这是 PHP 里最容易埋雷的地方：

| 属性类型 | `clone` 后的行为 | 实测证据 |
| --- | --- | --- |
| **对象属性**（`Signature $signature`） | **共享同一个对象**（复制的是引用） | `1a`：改副本的签名，**原件也被改了** |
| **数组属性**（`list<string> $recipients`） | **值拷贝**，各自独立 | `1b`/`1c`：副本加了收件人，原件仍是 1 个 |

也就是说：

```php
$copy = clone $original;      // 数组属性已经独立了
$copy->addRecipient('b@x.com');  // 不影响 $original

$copy->setSignatureText('x');    // ⚠️ 会影响 $original —— 它们共享同一个 Signature
```

**为什么会这样**：PHP 的赋值/拷贝对"对象"采用的是**句柄语义**（变量里存的是对象标识），对"数组"采用的是**写时复制的值语义**。`clone` 用的是同一套规则，于是同一个对象里的两类属性出现了不对称。

这条不对称的实践含义是：**只写 `clone` 是不够的，必须逐个数一遍类里的引用类型属性，在 `__clone()` 里显式处理。** 漏一个，就是一个静默的数据污染源（1a 那种）。

## 六、三种深拷贝做法与代价

| 做法 | 写法 | 代价 |
| --- | --- | --- |
| **`__clone()` 里手动深拷**（推荐） | `$this->signature = clone $this->signature;` | 要维护：**新增引用属性时必须记得加一行**，否则漏拷 |
| **序列化往返** | `unserialize(serialize($obj))` | 实测可行（第 3 行），但慢；**要求所有属性可序列化**（含闭包、资源句柄的对象直接失败）；会触发 `__wakeup`，若类里有副作用会意外执行 |
| **拷贝构造器 / `withXxx()`** | `new self($this->subject, ...)` 或返回新实例 | 最显式、最易测，但要手写构造参数；不可变对象配合它最自然 |

实测第 3 行证明序列化方案确实能深拷，但它有两个隐藏成本：**性能**（序列化 + 反序列化整棵树）与**可序列化约束**（对象图里只要有一个 `Closure` 属性就直接报错）。所以它适合"偶尔拷一次、对象图简单"的场景，不适合高频路径。

> 原文的实现用 `cloned($isDeep)` 的参数来决定深浅。
> 标准做法不建议这样：**""这个类拷贝时是深还是浅"应该是类的固定语义，而不是调用方每次要记住的参数**。
> 把语义固定进 `__clone()`（如 `DeepTemplate`），调用方只需要 `clone`，不需要知道细节。

## 七、什么时候不该用 `clone`

| 情况 | 更好的选择 |
| --- | --- |
| 对象几乎是不可变的 | `withXxx()` 返回新实例（PHP 8.1+ 可用 `readonly`） |
| 构造很便宜 | 直接 `new`，别引入"共享不共享"的心智负担 |
| 对象图里有循环引用 | 手动 `__clone` 会无限递归；改用显式的 ID 引用或拷贝构造器 |
| 对象持有资源句柄（文件、连接） | 不能拷 —— 必须让新对象自己开资源 |

最后一条尤其重要：资源句柄（`fopen` 的句柄、PDO 连接）**拷贝后共享同一个底层资源**，两个对象各自关闭会造成另一方的"已关闭连接"错误。这类属性要么不拷，要么在新对象里重新建。

## 八、Java / Go 实现

### Java 实现

Java 的 `clone` 机制比 PHP 啰嗦：必须实现 `Cloneable` 标记接口，且 `Object.clone()` 默认也是浅拷贝。

```java
static final class Signature implements Cloneable {
    private String text;

    Signature(String text) { this.text = text; }

    String text() { return text; }

    void setText(String text) { this.text = text; }

    @Override
    public Signature clone() {
        try {
            return (Signature) super.clone();
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);
        }
    }
}

static final class MailTemplate implements Cloneable {
    private final String subject;
    private Signature signature;
    private List<String> recipients = new ArrayList<String>();

    /** 浅拷贝：super.clone() 只复制字段的引用 */
    MailTemplate shallowCopy() {
        try {
            return (MailTemplate) super.clone();
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);
        }
    }

    /** 深拷贝：手动处理每一个引用类型字段 */
    @Override
    public MailTemplate clone() {
        MailTemplate copy = shallowCopy();
        copy.signature = signature.clone();                        // 深拷引用对象
        copy.recipients = new ArrayList<String>(recipients);       // 集合也要新副本
        return copy;
    }
}
```

**使用示例**：

```java
// 原型：先造一个基准模板，再从它派生副本
MailTemplate base = new MailTemplate("欢迎", new Signature("-- 客户成功团队"));
base.addRecipient("a@x.com");

// 浅拷贝：super.clone() 只复制字段引用，Signature 仍是同一个
MailTemplate shallow = base.shallowCopy();
shallow.setSignatureText("-- 被浅拷贝改掉了");
base.signatureText();        // "-- 被浅拷贝改掉了"（原件被连累）

// 深拷贝：重写的 clone() 里复制了 Signature 与 recipients
MailTemplate deep = base.clone();
deep.setSignatureText("-- 被深拷贝改掉了");
base.signatureText();        // "-- 客户成功团队"（原件不受影响）
base.recipientCount();       // 1（集合各自独立）
```

JDK 1.8 实测输出：

```text
1_浅拷贝·原件签名被连累 : -- 被浅拷贝改掉了
2_深拷贝·原件签名不变   : -- 客户成功团队
3_深拷贝·原件收件人数   : 1
4_深拷贝·副本收件人数   : 2
```

Java 与 PHP 的对应关系：

| | PHP | Java |
| --- | --- | --- |
| 默认拷贝行为 | 浅拷贝 | 浅拷贝 |
| 深拷的钩子 | `__clone()` | 重写 `clone()` |
| 需要声明接口 | 不需要 | **必须 `implements Cloneable`** |
| 集合属性 | 数组天然值拷贝 | **必须 `new ArrayList<>(src)`**，否则共享同一个 List |
| 更推荐的替代 | `withXxx()` | **拷贝构造器**（`new MailTemplate(other)`） |

Java 社区其实**不推荐用 `Cloneable`**（《Effective Java》专门有一章讲它的设计缺陷）：它不包含 `clone()` 方法、`CloneNotSupportedException` 是受检异常、浅拷贝容易漏字段。推荐做法是**拷贝构造器**或静态工厂，语义比 `clone()` 清楚得多。

### Go 实现

Go 里**没有 clone 关键字，也没有 `__clone` 钩子**，深拷贝必须自己写：

```go
type Signature struct {
	Text string
}

type MailTemplate struct {
	Subject    string
	Signature  *Signature
	Recipients []string
}

// ShallowCopy 结构体值拷贝：指针字段仍然指向同一个 Signature
func (t MailTemplate) ShallowCopy() MailTemplate {
	return t
}

// Clone 手写深拷贝：所有引用类型都要复制一份
func (t MailTemplate) Clone() MailTemplate {
	recipients := make([]string, len(t.Recipients))
	copy(recipients, t.Recipients)

	return MailTemplate{
		Subject:    t.Subject,
		Signature:  &Signature{Text: t.Signature.Text},
		Recipients: recipients,
	}
}
```

**使用示例**：

```go
// 原型：先造一个基准模板，再从它派生副本
base := MailTemplate{
	Subject:    "欢迎",
	Signature:  &Signature{Text: "-- 客户成功团队"},
	Recipients: []string{"a@x.com"},
}

// 值拷贝：指针字段共享，改副本的 Signature 连累原件
shallow := base.ShallowCopy()
shallow.Signature.Text = "-- 被浅拷贝改掉了"
base.Signature.Text                  // "-- 被浅拷贝改掉了"

// 手写深拷贝：Clone() 里换了新的 Signature，也 copy 了 slice
deep := base.Clone()
deep.Signature.Text = "-- 被深拷贝改掉了"
base.Recipients                      // 仍只有 a@x.com 一条
```

go1.26.5 实测输出：

```text
1_浅拷贝·原件签名被连累 : -- 被浅拷贝改掉了
2_深拷贝·原件签名不变   : -- 客户成功团队
3_深拷贝·原件收件人数   : 1
4_深拷贝·副本收件人数   : 2
```

Go 的拷贝语义与 PHP 有两点不同：

- **赋值就是拷贝**（结构体是值类型），不需要 `clone` 关键字。但**指针、slice、map 字段依然是共享的**（第 1 行实测：改副本的 `Signature.Text` 连累了原件），所以"深拷贝"在 Go 里同样要手写；
- **slice 的共享更隐蔽**：`append` 是否影响原 slice 取决于**容量是否足够**（够则原地写，不够则重新分配）。这种"有时共享有时不共享"的行为，正是要写显式 `Clone()` 的理由 —— 把不确定性收进一个方法里。

## 九、三语言对照

| | PHP | Java | Go |
| --- | --- | --- | --- |
| 拷贝关键字 | `clone` | `clone()`（需 `Cloneable`） | 无（赋值即拷贝） |
| 深拷钩子 | `__clone()` | 重写 `clone()` | 手写 `Clone()` 方法 |
| 默认行为 | 浅拷贝 | 浅拷贝 | 值拷贝（引用字段仍共享） |
| 集合属性 | 数组天然值拷贝 | 必须新建集合 | slice 需 `copy` 显式复制 |
| 更推荐的替代 | `withXxx()` | **拷贝构造器**（优于 `Cloneable`） | 手写 `Clone()` / 不可变结构 |
| 循环引用风险 | 有（用手动 `__clone` 会递归） | 有 | 有（指针环） |

三语言共通的一条：**浅拷贝是默认，深拷贝要显式**。而且**深到哪一层没有统一答案** —— 原文那句"深拷贝要深入到多少层，是一个不确定的问题"说的就是这件事，它必须由业务决定，而不是由语言决定。

## 十、面试官会追问什么

- **浅拷贝和深拷贝的区别？** → 浅拷贝只复制顶层字段，对象属性仍然共享；深拷贝把被引用的对象也复制一份。PHP/Java 的 `clone` 默认都是浅拷贝。
- **PHP 的 `clone` 对对象属性和数组属性处理一样吗？** → **不一样**：对象属性共享（句柄语义），数组属性值拷贝（写时复制）。这个不对称是原型模式最大的坑（第四节实测）。
- **`__clone()` 里要写什么？** → 逐个数类里的**引用类型**属性（对象、资源句柄），该深拷的深拷、该重建的重建。集合属性是否要新建取决于语言：PHP 数组不用，Java 集合必须。
- **用 `serialize` 做深拷贝有什么问题？** → 慢；要求整个对象图可序列化（含闭包就失败）；会触发 `__wakeup`/`__destruct` 等魔术方法，可能产生意外副作用。
- **原型和工厂的区别？** → 工厂从**零**造对象（`new` + 初始化），原型从**现成实例**复制（`clone`）。构造昂贵、且大部分状态与现成对象相同时，原型更划算。
- **单例为什么反过来要堵 `clone`？** → 单例要求全局唯一，而 `clone` 是绕过私有构造造出第二个实例的后门（见 [单例模式.md](单例模式.md) 第四节），所以必须把 `__clone` 声明为 `private`。
- **Java 为什么有拷贝构造器还要 `clone`？** → 社区实践上反而推荐拷贝构造器：《Effective Java》指出 `Cloneable` 的设计有缺陷（不含 `clone()` 方法、受检异常、易漏字段）。
