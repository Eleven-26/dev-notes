# 观察者模式

> 素材来源：博客 [PHP 设计模式(三)：观察者模式](https://blog.csdn.net/weixin_43837229/article/details/102623997)（2019-10-22），
> 内容出自《深入PHP：面向对象、模式与实践（第三版）》的学习笔记。
>
> 本篇的**讲解脉络取自博客原文**（是什么、为什么要解耦、应用场景、`SplSubject`/`SplObserver` 都保留原话）；
> **代码按标准生产写法重写** —— 不可变事件对象 + 监听器接口 + 派发器，第三.三节给出与 PSR-14 的对应关系。
>
> 同属行为型的还有 [策略模式.md](策略模式.md)、[迭代器模式.md](迭代器模式.md)。

## 一、什么是观察者模式

原文的定义：

> 观察者模式，属于行为型模式。观察者模式有时也被称作**发布/订阅模式**，该模式用于为对象实现发布/订阅功能：
> **一旦主体对象状态发生改变，与之关联的观察者对象会收到通知，并进行相应操作。**

原文接着解释了它存在的理由，这段话值得原样留着：

> 将一个系统分割成一些相互协作的类有一个不好的副作用，那就是需要维护相关对象间的一致性。
> 我们不希望为了维持一致性而使各类紧密耦合，这样会给维护、扩展和重用都带来不便。**观察者就是解决这类的耦合关系的。**
> 消息队列系统、事件都使用了观察者模式。

原文还提到：**PHP 为观察者模式定义了两个接口 `SplSubject` 和 `SplObserver`**，主体实现 `SplSubject`、观察者实现 `SplObserver` 即可。

三个角色：

| 角色 | 职责 | 原文对应 |
| --- | --- | --- |
| 主体 / 事件源（Subject） | 维护观察者列表、状态变化时通知 | 实现 `SplSubject` |
| 观察者 / 监听器（Observer） | 收到通知后做自己的事 | 实现 `SplObserver` |
| 事件（Event） | 承载"发生了什么"的数据 | 原文挂在主体上（见 3.3，这是个坑） |

## 二、应用场景

原文的列举很接地气：

> 跟发布/订阅类似，某些场景的改变需要通知其相关的模块做出相应改变，
> 比如**订单下单成功需要通知库存模块减库存**、**通知信息通知模块发送验证码**、**日志的记录**等。

翻成判据：**一次状态变化要触发多个彼此独立的副作用，且这些副作用以后还会增加。** 加一个副作用不该改事件源 —— 这正是原文说的"解决耦合"。

## 三、PHP 标准实现

原文的示例用 `__set()` 魔术方法在属性赋值时触发通知。这在演示里很直观，但把它放进生产会有三个问题：**赋值副作用隐蔽**、**事件数据只能从主体上读**、**一个属性一次通知会连带触发全部监听器**。标准写法是显式派发。

### 3.1 三段式：事件 / 监听器 / 派发器

```php
<?php

declare(strict_types=1);

/** 事件：不可变数据对象，只装数据、不带行为 */
final class OrderPaid
{
    public function __construct(
        private int $orderId,
        private int $amountInCents
    ) {}

    public function orderId(): int
    {
        return $this->orderId;
    }

    public function amountInCents(): int
    {
        return $this->amountInCents;
    }
}

/** 监听器接口：一个监听器只负责一件事 */
interface OrderPaidListener
{
    public function handle(OrderPaid $event): void;
}

/** 派发器：数组注册表 + 快照遍历 + 逐个隔离异常 */
final class OrderEventDispatcher
{
    /** @var list<OrderPaidListener> */
    private array $listeners = [];

    public function subscribe(OrderPaidListener $listener): void
    {
        if (in_array($listener, $this->listeners, true)) {
            return;                                    // 按对象身份去重
        }
        $this->listeners[] = $listener;
    }

    public function unsubscribe(OrderPaidListener $listener): void
    {
        $this->listeners = array_values(array_filter(
            $this->listeners,
            static fn (OrderPaidListener $registered): bool => $registered !== $listener
        ));
    }

    public function dispatch(OrderPaid $event): void
    {
        $failures = [];
        foreach ($this->snapshot() as $listener) {
            try {
                $listener->handle($event);
            } catch (Throwable $e) {                   // Throwable 而非 Exception
                $failures[] = $listener::class . ': ' . $e->getMessage();
            }
        }
        if ($failures !== []) {
            // 同步事件里「有监听器失败」必须冒泡；要静默就改异步队列靠重试兜底
            throw new RuntimeException('部分监听器失败 -> ' . implode(' | ', $failures));
        }
    }

    /** 遍历快照：handle() 里增删注册表不影响本轮 */
    private function snapshot(): array
    {
        return $this->listeners;
    }
}
```

对应的监听器就是普通类，业务逻辑各自独立：

```php
final class AuditListener implements OrderPaidListener
{
    public function handle(OrderPaid $event): void
    {
        // 写审计日志
    }
}

final class StockListener implements OrderPaidListener
{
    public function handle(OrderPaid $event): void
    {
        // 扣库存
    }
}
```

**使用示例**：

```php
// 1) 事件对象：不可变，只带数据
$event = new OrderPaid(1001, 25900);        // 订单号 + 金额（分）

// 2) 派发器登记监听器（监听器只实现 handle()，彼此互不认识）
$dispatcher = new OrderEventDispatcher();
$audit = new AuditListener();
$dispatcher->subscribe($audit);
$dispatcher->subscribe(new StockListener());

// 3) 派发：逐个调用 handle()，单个监听器抛异常不影响其它（见 3.2 场景 2）
$dispatcher->dispatch($event);

// 4) 摘除：必须传之前 subscribe 的同一个实例，下一轮它就不再收到
$dispatcher->unsubscribe($audit);
```

**注意第 5 行那句"数组注册表天然有快照语义"** —— 这是 PHP 的一个语言特性，见 3.2 的场景 3。

### 3.2 三个必须知道的语义（本机 PHP 8.0.2 实测）

三个场景跑下来（用两个演示替身：一个记录通知顺序，一个模拟短信网关超时）：

```text
1a_第一轮（C 应仍收到，D 应缺席）: A > B > C
1b_第二轮（C 已摘，D 已生效）    : A > B > D
1c_重复挂载 D（应按身份去重）    : A > B > D
2a_不隔离 : 短信网关超时
    实际收到通知: Mailer
2b_隔离 : 部分监听器失败 -> SmsListener: 短信网关超时
    实际收到通知: Mailer > Points
3_数组遍历是快照: 依次访问 abc，遍历后原数组剩 ac
```

**语义一：遍历的是快照，本轮改动下一轮才生效（1a / 1b）。**

场景 1 里 `B` 在 `handle()` 中摘掉了 `C`、挂上了 `D`。实测：**第一轮 `C` 照样收到**（`A > B > C`），`D` 到第二轮才出现（`A > B > D`）。用"注销监听"做权限控制的代码要特别小心这条 —— 它挡不住正在进行的这一轮。

**语义二：一个监听器抛异常，不能让其余监听器收不到（2a / 2b）。**

不隔离时只打印了 `Mailer`，`Points` 直接消失，主流程也被一起带崩。隔离版三条要点：`catch (Throwable)` 而不是 `Exception`（否则监听器里抛 `TypeError` 照样漏）；失败者攒起来、通知完**统一抛一次**；日志里记 `$listener::class`，能直接定位出问题的那个监听器。

**语义三：注册表按对象身份去重（1c）。**

`D` 被 `subscribe` 两次，只通知一次。换成 `array` + 手动判重也行，但要自己保证判据是"身份"而不是"值相等"；用 `SplObjectStorage` 则天然按身份 —— 代价是它是**对象**，遍历的 `clone` 快照得自己写（见 3.3）。

**场景 3 是语义一的语言层原因**：PHP 的 `foreach` 遍历数组时用的是快照（写时复制语义），遍历中把 `b` 从原数组删掉，`b` 仍会被访问到，而遍历结束后原数组里确实只剩 `ac`。**所以用数组当注册表，快照是白送的**；这也是标准写法选数组而不是 `SplObjectStorage` 的原因之一。

### 3.3 从 `SplSubject` 到 PSR-14：事件为什么要当参数传

博客原文用的是 SPL 那对接口。它们能用（本机 8.0.2 实测 `interface_exists('SplSubject')` 为 `true`），但有个历史包袱：

```php
interface SplSubject
{
    public function attach(SplObserver $observer): void;
    public function detach(SplObserver $observer): void;
    public function notify(): void;      // ⚠️ 无参数
}
```

`notify()` **不能收参数**，于是"发生了什么事件"只能挂在主体身上（原文字例子里就是主体上的 `$data`）。这带来两个后果：

1. **重入会串数据**：`handle()` 里如果再触发一次通知、写入主体上的事件名，外层正在遍历的其它监听器读到的就是内层的事件名；
2. **一个主体只能表达一种事件**：多事件类型要建多个主体类。

现代 PHP 的做法就是把事件**作为参数传下去** —— PHP-FIG 的 **PSR-14** 正是这么定的：

```php
// PSR-14 的两个接口（psr/event-dispatcher 包定义）
interface EventDispatcherInterface
{
    public function dispatch(object $event): object;
}

interface ListenerProviderInterface
{
    /** @return iterable<callable> */
    public function getListenersForEvent(object $event): iterable;
}
```

按这个形状自己写一个派发器（本机实测通过）：

```php
final class SimpleEventDispatcher
{
    /** @var array<class-string, list<callable>> */
    private array $listeners = [];

    public function listen(string $eventClass, callable $listener): void
    {
        $this->listeners[$eventClass][] = $listener;
    }

    public function dispatch(object $event): object
    {
        foreach ($this->listeners[$event::class] ?? [] as $listener) {
            $listener($event);
        }
        return $event;                    // PSR-14 要求返回事件本身
    }
}
```

```text
audit: 1001
sms: 1001
dispatch 返回事件本身: OrderPaidEvent
按类名查表，无关事件的监听器不会被触发
```

两个设计点：**按 `$event::class` 查表**，无关事件的监听器连碰都不会被碰到；**`dispatch` 返回事件对象**，方便调用方继续传递或改写。

| | `SplSubject` + `SplObserver` | 事件对象 + PSR-14 |
| --- | --- | --- |
| 事件数据 | 挂在主体属性上 | 事件对象的构造参数 |
| 重入安全 | 会串事件名 | 安全（数据随参数走） |
| 多事件类型 | 每个事件一个主体类 | 一个派发器按类名分派 |
| 生态兼容 | 仅 PHP 内置 | 可对接 Laravel / Symfony 的事件系统 |

**结论**：学结构看 SPL 那对接口就够（博客原文的价值）；**要落地就用事件对象 + 类名分派**。

## 四、php-fpm 的边界：观察者表跨不了请求

这是 PHP 与 Java/Go 差别最大的一点：Java 的观察者挂在堆上，注册一次活到 JVM 结束；**PHP 每个请求结束，整个用户态内存（含注册表）就回收**。

不用框架也能跑出来 —— 脚本自己 spawn 一个子进程，等价于"下一个请求"：

```php
<?php

declare(strict_types=1);

/** 模拟框架的事件注册表：由框架在每次请求里重新装配 */
final class EventRegistry
{
    /** @var array<string, list<string>> */
    public static array $map = [];
}

$queueFile = sys_get_temp_dir() . '/dp-obs-queue.jsonl';

if (($argv[1] ?? '') === '--next') {                 // 下一个请求 = 又一个全新进程
    printf("2_新进程注册表 : %s\n", json_encode(EventRegistry::$map));
    printf("2_队列文件     : %s\n", trim((string) @file_get_contents($queueFile)));
    exit;
}

@unlink($queueFile);
EventRegistry::$map['OrderPaid'] = ['AuditListener', 'SmsListener'];   // 请求 1 装配
printf("1_本请求注册表 : %s\n", json_encode(EventRegistry::$map));

// 跨请求的副作用只能投递出去（这里用文件当队列替身，真实项目是 Redis / RabbitMQ / Kafka）
file_put_contents(
    $queueFile,
    json_encode(['event' => 'OrderPaid', 'orderId' => 1001], JSON_UNESCAPED_UNICODE) . PHP_EOL,
    FILE_APPEND | LOCK_EX
);

echo shell_exec(escapeshellarg(PHP_BINARY) . ' ' . escapeshellarg(__FILE__) . ' --next');
```

```text
1_本请求注册表 : {"OrderPaid":["AuditListener","SmsListener"]}
2_新进程注册表 : []
2_队列文件     : {"event":"OrderPaid","orderId":1001}
```

`2_新进程注册表 : []` 就是那堵墙 —— **新进程里监听表是空的，唯一跨过进程边界的，是被序列化出来的那行事件**。

由此推出实践结论：

| 副作用 | 该怎么放 |
| --- | --- |
| 要和本次请求（乃至同一事务）共进退（扣库存、写审计） | 同步监听器 |
| 可以延迟、允许重试（发短信、推送、写日志） | **事件序列化进队列** |

真实项目里（Laravel 公开用法，本机未装框架，**非实跑**）：事件类只装数据，监听器实现 `ShouldQueue` 就自动从同步变投递队列；注册动作发生在每次请求的 `EventServiceProvider::boot()` 或 Symfony 编译期的 `kernel.event_listener` tag —— 所以 PHP 的观察者代码长成"**存类名的表 + 派发那一刻才 new**"，而不是启动时挂好对象。

常驻模型（Swoole / RoadRunner）下注册表变成**跨请求共享状态**：注册只做一次，且监听器里绝不能存用户态数据（串号风险，与 [单例模式.md](../创建型/单例模式.md) 第四节的静态属性是同一件事）。

## 五、Java 实现

Java 里同一个模式要额外处理两个 PHP 根本不存在的问题：**通知期间改表**与**忘了反注册**。

```java
import java.util.ArrayList;
import java.util.List;

public class ObserverStandard {

    interface OrderPaidListener {
        void handle(int orderId);
    }

    /** 标准派发器：注册表 + 快照遍历 + 逐个隔离异常 */
    static final class OrderEventDispatcher {
        private final List<OrderPaidListener> listeners = new ArrayList<OrderPaidListener>();

        void subscribe(OrderPaidListener listener) {
            if (listeners.contains(listener)) {   // 对象身份去重（未重写 equals）
                return;
            }
            listeners.add(listener);
        }

        void unsubscribe(OrderPaidListener listener) {
            listeners.remove(listener);
        }

        int size() {
            return listeners.size();
        }

        void dispatch(int orderId) {
            List<String> failures = new ArrayList<String>();
            // 遍历副本：handle 里增删注册表不影响本轮
            for (OrderPaidListener listener : new ArrayList<OrderPaidListener>(listeners)) {
                try {
                    listener.handle(orderId);
                } catch (RuntimeException e) {
                    failures.add(listener.getClass().getSimpleName() + ": " + e.getMessage());
                }
            }
            if (!failures.isEmpty()) {
                throw new RuntimeException("部分监听器失败 -> " + failures);
            }
        }

        /** 反面：直接遍历原表，通知期间改表就抛异常 */
        void dispatchUnsafe(int orderId) {
            for (OrderPaidListener listener : listeners) {
                listener.handle(orderId);
            }
        }
    }
}
```

**使用示例**：

```java
// 派发器 + 监听器：接口是单方法，直接写 lambda 即可
OrderEventDispatcher dispatcher = new OrderEventDispatcher();
dispatcher.subscribe(orderId -> System.out.println("audit " + orderId));
dispatcher.subscribe(orderId -> { throw new RuntimeException("listener boom"); });
dispatcher.subscribe(orderId -> System.out.println("points " + orderId));

// 一个监听器抛错：其余照常收到，最后统一抛一次
try {
    dispatcher.dispatch(1001);                 // 抛 RuntimeException: 部分监听器失败 -> ...
} catch (RuntimeException e) {
    System.out.println(e.getMessage());
}
dispatcher.size();                             // 3（异常不影响注册表）
```

JDK 1.8 实测输出：

```text
===== 1. 异常隔离 =====
audit order=1001
audit order=1001
抛出: 部分监听器失败 -> [BoomListener: listener boom]
表长仍为 3（异常不影响注册表）
===== 2. 通知期间改表（不安全做法）=====
ConcurrentModificationException
===== 3. 常驻进程里的监听器累积 =====
leaky request=1 listeners=1
leaky request=2 listeners=2
leaky request=3 listeners=3
audit order=1
fixed request=1 listeners=0
audit order=2
fixed request=2 listeners=0
audit order=3
fixed request=3 listeners=0
```

三处要点：

- **`ConcurrentModificationException`**：直接遍历原 `ArrayList` 并在 `handle()` 里 `unsubscribe`，立刻抛这个异常。所以 Java 的"快照"不是可选项，是**必须写 `new ArrayList<>(listeners)`**。（PHP 的数组是快照，不用写；`SplObjectStorage` 是对象，必须 `clone`。）
- **`listeners.contains(listener)` 用的是 `equals`**，默认实现即身份比较 —— 与 PHP 数组的 `in_array(..., true)` 等价。
- **`leaky` 那一列是 Java 里最有名的内存泄漏来源之一**：监听器持有 Session / 请求上下文，事件源是长生命周期单例，于是这些对象全被拽住不释放。PHP 因为每请求重建而**根本没有这个问题**（同级风险在常驻模型下才出现）。

## 六、Go 实现

```go
package main

import "fmt"

// OrderPaidListener 监听器就是「接收事件的一个函数」，Go 里不必为它建接口
type OrderPaidListener func(orderID int)

// OrderEventDispatcher 标准派发器：注册表 + 快照遍历 + recover 隔离
type OrderEventDispatcher struct {
	listeners []OrderPaidListener
}

func NewOrderEventDispatcher() *OrderEventDispatcher {
	return &OrderEventDispatcher{}
}

// Subscribe 返回取消注册的函数。
// Go 的函数值不可比较，所以反注册不能像 PHP/Java 那样「把同一个对象传回来」，
// 惯用做法是把 cancel 交出去。
func (d *OrderEventDispatcher) Subscribe(l OrderPaidListener) (cancel func()) {
	index := len(d.listeners)
	d.listeners = append(d.listeners, l)
	return func() {
		if index < len(d.listeners) {
			d.listeners[index] = nil
		}
	}
}

func (d *OrderEventDispatcher) Size() int { return len(d.listeners) }

// Dispatch 遍历快照：通知期间新注册的不在本轮生效
func (d *OrderEventDispatcher) Dispatch(orderID int) error {
	snapshot := append([]OrderPaidListener(nil), d.listeners...)
	var failures []string
	for _, l := range snapshot {
		if l == nil {
			continue
		}
		if err := callSafely(l, orderID); err != nil {
			failures = append(failures, err.Error())
		}
	}
	d.compact()
	if len(failures) > 0 {
		return fmt.Errorf("部分监听器失败 -> %v", failures)
	}
	return nil
}

func (d *OrderEventDispatcher) compact() {
	kept := d.listeners[:0]
	for _, l := range d.listeners {
		if l != nil {
			kept = append(kept, l)
		}
	}
	d.listeners = kept
}

// callSafely 把 panic 收敛成 error：不隔离的话，后面的监听器一个都收不到
func callSafely(l OrderPaidListener, orderID int) (err error) {
	defer func() {
		if r := recover(); r != nil {
			err = fmt.Errorf("%v", r)
		}
	}()
	l(orderID)
	return nil
}
```

**使用示例**：

```go
// 监听器就是函数；Subscribe 返回 cancel，用来反注册
dispatcher := NewOrderEventDispatcher()
dispatcher.Subscribe(func(orderID int) { fmt.Println("audit order=", orderID) })
cancel := dispatcher.Subscribe(func(orderID int) { fmt.Println("points order=", orderID) })

// 一个监听器 panic：其余照常收到，最后统一返回 error
dispatcher.Subscribe(func(orderID int) { panic("sms boom") })
if err := dispatcher.Dispatch(1001); err != nil {
    fmt.Println("抛出:", err)                  // 部分监听器失败 -> [sms boom]
}
fmt.Println("表长仍为", dispatcher.Size())      // 3

// 反注册后不再收到，compact 顺带收敛注册表
cancel()
dispatcher.Dispatch(1002)
```

```text
抛出: 部分监听器失败 -> [sms boom]
表长仍为 3
===== 2. 快照语义 =====
first sees 1
first sees 2
second sees 2
两次 dispatch 之后表长: 3
===== 3. 反注册 =====
temp listener sees 1
反注册并 compact 后表长: 0
```

三点与 PHP/Java 的差异：

- **`recover` 对应 PHP 的 `catch (Throwable)`、Java 的 `try/catch`**：不写它，`panic` 会直接终止整个 goroutine，「后面的监听器静默收不到」在两门语言里表现完全一样（实测 `points order= 1001` 仍在，说明隔离生效）；
- **快照靠 `append` 复制 slice**（`append([]T(nil), src...)`），语义与 PHP 数组一致（场景 2 里第二轮才看到新注册的 `second`）；
- **函数值不可比较**，所以反注册用"返回 cancel 函数"的惯用法（标准库 `context.WithCancel`、`signal.Notify` 都是这个形状）。

## 七、PHP / Java / Go 对照

| | PHP（php-fpm） | Java | Go |
| --- | --- | --- | --- |
| 观察者形态 | 接口实现类 | 接口实现类 / lambda | 函数值 |
| 注册表生命周期 | **一次请求**，进程结束自动干净 | JVM，**必须显式注销** | 进程，**必须显式注销** |
| 快照 | 数组遍历天然快照 | 必须 `new ArrayList<>(src)` | 必须 `append(nil, src...)` |
| 通知期间改表 | 本轮不受影响 | 不复制就 `ConcurrentModificationException` | 不复制则本轮就看到新元素 |
| 一个观察者抛错 | `catch (Throwable)` 逐个隔离 | `try/catch` 逐个隔离 | `recover` 逐个隔离 |
| 忘反注册的后果 | 无（随请求销毁） | 内存泄漏 + 重复投递 | 泄漏 + 重复投递 |
| 跨请求副作用 | **只能序列化进队列** | 直接同步执行 | 直接同步执行 |

一句话总结三者的差别：**PHP 用「进程用完即弃」换掉了注册表管理，代价是跨请求只能靠队列；Java/Go 省掉了队列，代价是必须自己管反注册与并发。**

## 八、面试官会追问什么

- **观察者模式和发布/订阅是一回事吗？** → 结构上同源（博客原文也是这么说的）。严格讲，"发布/订阅"通常多一层 broker（事件总线/MQ），发布者与订阅者互不认识；经典观察者里主体持有观察者引用。
- **`SplSubject`/`SplObserver` 现在还能用吗？** → 本机 8.0.2 实测可用、无告警。但 `notify()` 无参数，事件数据只能挂主体上，**重入会串事件名**，多事件类型要建多个主体类。落地建议用事件对象 + 类名分派（PSR-14 形状）。
- **一个监听器抛异常会怎样？** → 不隔离的话后面的监听器一个都收不到（实测只打印了 `Mailer`）。标准做法：逐个 `catch (Throwable)`，失败攒起来统一抛；要静默就改异步队列。
- **通知过程中注销某个监听器，本轮还有效吗？** → 无效，本轮仍会被通知（遍历的是快照），下一轮才生效。Java 里直接遍历原表改表会抛 `ConcurrentModificationException`。
- **PHP 里观察者能替代 MQ 吗？** → 不能。监听表随请求销毁（实测 `2_新进程注册表 : []`），跨请求/跨服务的副作用必须把事件序列化进队列。
- **怎么保证通知幂等？** → 事件带唯一 ID，消费端记已处理集合去重。观察者本身不保证"只通知一次"，异步重试必然造成重复投递。
- **和注册模式、中介者的边界？** → 注册模式管"全局拿到实例"，观察者管"一对多通知"；事件之间互相依赖时用事件总线/中介者收口，别在 `handle()` 里同步级联。
