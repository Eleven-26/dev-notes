## 一、访问者解决什么问题

访问者（Visitor）属于行为型模式：**把"对一组对象的操作"从对象本身剥离出来**，使得新增操作时不必改动这些对象。

它要解决的是"**数据结构稳定、但操作会不断增加**"：

| 需求 | 没有访问者时 |
| --- | --- |
| 文档要导出 HTML / Markdown / 纯文本 | 每个元素类都长出 `toHtml()` / `toMarkdown()` / `toText()` |
| 再加一种导出格式 | **所有元素类都要改一遍** |
| 加一种统计（字数、引用数） | 同样每个元素都要加方法 |
| 元素类想保持"纯数据" | 做不到，业务/格式逻辑全糊在数据类上 |

**关键判断**：这个模式把"加操作"变容易了，代价是"**加元素**"变难。这是它与大多数模式相反的取舍 —— 见第三节。

四个角色：

| 角色 | 职责 | 本篇对应 |
| --- | --- | --- |
| Visitor | 声明"每种元素怎么处理"（**每种元素一个方法**） | `DocumentVisitor` |
| ConcreteVisitor | 一种具体操作（一种导出格式） | `HtmlVisitor` / `MarkdownVisitor` / `PlainTextVisitor` |
| Element | 提供 `accept(visitor)` 入口 | `Heading` / `Paragraph` / `Image` / `Table` |
| ObjectStructure | 持有元素集合，负责"逐个 accept" | `Document` |

**双分派（double dispatch）** 是这个模式的机制核心：

```php
// 第一次分派：运行时决定调用哪个元素的 accept()
$element->accept($visitor);
// 第二次分派：accept() 内部再决定调用 visitor 的哪个方法
return $visitor->visitHeading($this);      // 而 visitHeading 的参数类型又约束了元素
```

**两次分派合起来才能确定"哪个 visitor 处理哪个元素"** —— 单靠一次分派做不到（PHP / Java / Go 都没有多方法重载）。实测第 6 行确认 `accept()` 只做这一件事：

```text
6_双分派入口          : Heading::accept 只做一件事 —— 把自己交给 visitor（1 个参数）
```

## 二、PHP 标准实现

场景：**文档导出**（同一份文档 → HTML / Markdown / 纯文本）。

```php
<?php

declare(strict_types=1);

/** 元素接口：accept 是唯一需要元素配合的入口 */
interface DocumentElement
{
    public function accept(DocumentVisitor $visitor): string;
}

/**
 * 访问者接口：**每个元素种类都要在这里有一个方法**。
 * 这是这个模式耦合方向的体现 —— 元素种类一多，接口就要改，所有实现都要跟着改。
 */
interface DocumentVisitor
{
    public function visitHeading(Heading $element): string;

    public function visitParagraph(Paragraph $element): string;

    public function visitImage(Image $element): string;

    public function visitTable(Table $element): string;
}

// ---------------- 元素（结构） ----------------

final class Heading implements DocumentElement
{
    public function __construct(
        private string $text,
        private int $level = 1
    ) {}

    public function text(): string
    {
        return $this->text;
    }

    public function level(): int
    {
        return max(1, min(6, $this->level));
    }

    /** 双分派的第一跳：把"我是 Heading"这件事交给 visitor 去处理 */
    public function accept(DocumentVisitor $visitor): string
    {
        return $visitor->visitHeading($this);
    }
}

final class Paragraph implements DocumentElement
{
    public function __construct(private string $text) {}

    public function text(): string
    {
        return $this->text;
    }

    public function accept(DocumentVisitor $visitor): string
    {
        return $visitor->visitParagraph($this);
    }
}

final class Image implements DocumentElement
{
    public function __construct(
        private string $src,
        private string $alt
    ) {}

    public function src(): string
    {
        return $this->src;
    }

    public function alt(): string
    {
        return $this->alt;
    }

    public function accept(DocumentVisitor $visitor): string
    {
        return $visitor->visitImage($this);
    }
}

final class Table implements DocumentElement
{
    /** @param list<list<string>> $rows */
    public function __construct(private array $rows) {}

    /** @return list<list<string>> */
    public function rows(): array
    {
        return $this->rows;
    }

    public function accept(DocumentVisitor $visitor): string
    {
        return $visitor->visitTable($this);
    }
}

/** 文档：只负责持有元素与"逐个 accept"，不知道任何导出格式 */
final class Document
{
    /** @var list<DocumentElement> */
    private array $elements = [];

    public function add(DocumentElement $element): self
    {
        $this->elements[] = $element;

        return $this;
    }

    /** 块之间用空行连接：Markdown 需要空行才能正确分块，HTML 里多余的换行无影响 */
    public function export(DocumentVisitor $visitor): string
    {
        return implode("\n\n", array_map(
            static fn (DocumentElement $e): string => $e->accept($visitor),
            $this->elements
        ));
    }
}
```

三种导出格式 —— 每个都是一整个 `Visitor` 类：

```php
/** 导出为 HTML */
final class HtmlVisitor implements DocumentVisitor
{
    public function visitHeading(Heading $element): string
    {
        $tag = 'h' . $element->level();
        $text = htmlspecialchars($element->text(), ENT_QUOTES);

        return "<{$tag}>{$text}</{$tag}>";
    }

    public function visitParagraph(Paragraph $element): string
    {
        return '<p>' . htmlspecialchars($element->text(), ENT_QUOTES) . '</p>';
    }

    public function visitImage(Image $element): string
    {
        return sprintf(
            '<img src="%s" alt="%s">',
            htmlspecialchars($element->src(), ENT_QUOTES),
            htmlspecialchars($element->alt(), ENT_QUOTES)
        );
    }

    public function visitTable(Table $element): string
    {
        $out = ['<table>'];
        foreach ($element->rows() as $row) {
            $cells = array_map(
                static fn (string $c): string => '<td>' . htmlspecialchars($c, ENT_QUOTES) . '</td>',
                $row
            );
            $out[] = '<tr>' . implode('', $cells) . '</tr>';
        }
        $out[] = '</table>';

        return implode('', $out);
    }
}

/** 导出为 Markdown */
final class MarkdownVisitor implements DocumentVisitor
{
    public function visitHeading(Heading $element): string
    {
        return str_repeat('#', $element->level()) . ' ' . $element->text();
    }

    public function visitParagraph(Paragraph $element): string
    {
        return $element->text();
    }

    public function visitImage(Image $element): string
    {
        return sprintf('![%s](%s)', $element->alt(), $element->src());
    }

    public function visitTable(Table $element): string
    {
        $rows = $element->rows();
        if ($rows === []) {
            return '';
        }
        $out = [];
        $out[] = '| ' . implode(' | ', $rows[0]) . ' |';
        $out[] = '| ' . implode(' | ', array_fill(0, count($rows[0]), '---')) . ' |';
        foreach (array_slice($rows, 1) as $row) {
            $out[] = '| ' . implode(' | ', $row) . ' |';
        }

        return implode("\n", $out);
    }
}

/** 新增一个导出格式 = 只加一个类，不动任何元素（这就是访问者的价值） */
final class PlainTextVisitor implements DocumentVisitor
{
    public function visitHeading(Heading $element): string
    {
        return $element->text() . "\n" . str_repeat('=', mb_strlen($element->text()));
    }

    public function visitParagraph(Paragraph $element): string
    {
        return $element->text();
    }

    public function visitImage(Image $element): string
    {
        return sprintf('[图片：%s（%s）]', $element->alt(), $element->src());
    }

    public function visitTable(Table $element): string
    {
        return implode("\n", array_map(
            static fn (array $row): string => implode("\t", $row),
            $element->rows()
        ));
    }
}
```

**使用示例**：

```php
// 结构：Document 装元素，元素不知道任何导出格式
$doc = (new Document())
    ->add(new Heading('设计模式', 1))
    ->add(new Paragraph('一句话说明'))
    ->add(new Image('a.png', '示意图'));

// 换个 visitor 就换一种导出，元素一个都不用改
$doc->export(new HtmlVisitor());        // <h1>设计模式</h1>...
$doc->export(new MarkdownVisitor());    // # 设计模式...
$doc->export(new PlainTextVisitor());   // 设计模式\n====

// 也可以只让单个元素接受访问（双分派：accept → visitXxx）
(new Heading('标题', 2))->accept(new HtmlVisitor());   // <h2>标题</h2>
```

三个要点：

- **同一份文档、三种完全不同的结果** —— 元素类一行没改，只换了 Visitor；
- **第 3 组是"新增操作"的演示**：纯文本导出是新写的 Visitor，`Heading`/`Paragraph`/`Image`/`Table` **一个字都没动**。这就是访问者的全部价值；
- **表格那行最能体现差异**：HTML 变成 `<table><tr><td>…`，Markdown 变成 `| 元素 | … |` + 分隔行，纯文本变成制表符分隔。**同一个元素结构，三种完全不同的产出**。

### 让它算「标准写法」的 4 个细节

| # | 做法 | 为什么 |
| --- | --- | --- |
| 1 | `accept()` 里**只做一件事**：`$visitor->visitXxx($this)` | 双分派的第二跳放在这里，模式才成立 |
| 2 | 元素**只提供读方法**，不提供写方法 | 访问者是"只读遍历"，允许它改元素会让流程失控 |
| 3 | ObjectStructure（`Document`）**只负责遍历** | 它不该知道任何格式细节，否则又是一个上帝对象 |
| 4 | **块之间的空白由 Visitor 决定**（`implode("\n\n")`） | 格式规范是 Visitor 的职责 —— HTML 无所谓，Markdown 缺空行就不成块 |

## 三、耦合方向：这个模式的核心权衡

访问者把"操作"和"结构"解耦了，但**耦合并没有消失，只是换了个方向**：

| 变化 | 用访问者 | 不用访问者（元素自带方法） |
| --- | --- | --- |
| **加一种操作**（新导出格式） | ✅ 加一个 Visitor 类，**元素不动** | ❌ 每个元素都要加方法 |
| **加一种元素**（如 `CodeBlock`） | ❌ **所有 Visitor 都要加方法** | ✅ 只加一个元素类 |
| 元素与操作的组合数 | V × E 个方法（分散在 V 个类） | V × E 个方法（分散在 E 个类） |

实测第 4、5 行量化了这件事：

```text
4_Visitor 接口方法数  : 4（visitHeading, visitParagraph, visitImage, visitTable）
5_元素种类数          : 4（Heading, Paragraph, Image, Table）
```

**两者必须相等**：`DocumentVisitor` 的方法数 = 元素种类数。加一种元素，**四个 Visitor 全部要改**（本实现里有 3 个具体 Visitor × 1 个方法 = 3 处，加上接口是 4 处）。

所以选型判据非常清晰：

| 用访问者 | 不用访问者 |
| --- | --- |
| **元素种类稳定**（HTML 标签、语法树节点、图形图元） | 元素种类还在频繁增加 |
| **操作会不断增加**（导出格式、统计、校验、优化） | 操作也很少，或固定在少数几个 |
| 需要"在不改数据结构的前提下加分析" | 元素自带行为更自然（如 `Circle::draw()`） |

**编译器是访问者的经典场景**：AST 节点种类（变量、加法、调用……）几十年就那几种，而要对它做的事源源不断（类型检查、常量折叠、代码生成、优化）——**结构稳定、操作爆炸**，正是访问者的甜点区。

## 四、代价：封装被打破，双分派难懂

这个模式有两处常被诟病的代价，都值得明说：

**(1) 元素必须把内部数据暴露给访问者。** 实测第 7 行：

```text
7_Table 暴露给 Visitor : rows（访问者必须能读到内部数据 → 封装的代价）
```

`Table` 只能提供 `rows()` 这样的读方法。这与"迪米特法则"（只见直接朋友）是冲突的 —— **访问者的定位就是"受控的例外"**：元素主动为访问者开一扇门。

缓解手段：

| 手段 | 说明 |
| --- | --- |
| 只开读方法，不开写方法 | 访问者只读，元素不会被它改坏 |
| **把 Visitor 接口的可见性收紧** | PHP 用 `@internal`、Java 用包级可见、Go 用未导出方法 |
| 元素把数据"打包"给访问者 | 提供一个 `toArray()`，而不是散落一堆 getter |

**(2) 双分派不直观。** 读者要在 `accept()` 和 `visitXxx()` 之间来回跳才看懂调用链。这也是很多语言选择**内置支持**的原因：

| 场景 | 内置机制 |
| --- | --- |
| Java 17+ | **sealed interface + `switch` 模式匹配**（JDK 8 无此能力） |
| C# | `switch` 表达式 + 模式匹配 |
| Rust | `enum` + `match`（**最彻底**：变体即元素，`match` 即访问者） |
| PHP | **没有内置** —— 只能靠 `instanceof` / `match(true)` 手写 |

Java 17+ 的写法（本机 JDK 8 无法验证，仅作说明）：

```java
sealed interface DocumentElement permits Heading, Paragraph, Image, Table { }

String html = switch (element) {                       // 编译器会检查"是否遗漏了某个变体"
    case Heading h    -> "<h" + h.level() + ">" + h.text() + "</h" + h.level() + ">";
    case Paragraph p  -> "<p>" + p.text() + "</p>";
    case Image i      -> "<img src=\"" + i.src() + "\">";
    case Table t      -> "<table>…</table>";
};
```

**这比访问者更好**：`sealed` 让编译器**强制**你在新增元素时报错（而不像访问者那样"运行到才发现漏了"），而且没有双分派的心智负担。**这才是现代语言里的正解**。

## 五、边界：与几个近亲的区分

| | 访问者 | 策略 | 迭代器 | 组合 |
| --- | --- | --- | --- | --- |
| 对什么做操作 | **一组不同类型的对象** | 一个算法 | 一个聚合的遍历 | 一棵树 |
| 谁分派 | 双分派（元素 + 访问者） | 单分派（调用方选） | 聚合自管 | 递归 |
| 加新"操作" | ✅ 加 Visitor | ✅ 加 Strategy | — | — |
| 加新"类型" | ❌ 改所有 Visitor | ✅ 加 Strategy | — | ✅ 加节点类型 |
| 典型 | 编译器 AST、文档导出 | 折扣计算、支付渠道 | 分页游标 | 文件树、菜单 |

**访问者 vs 策略**：策略是"**一个**算法可替换"，访问者是"**一组**对象 × 多种操作"。策略的接口只有一个方法，访问者的接口有 N 个（N = 元素种类）。

**访问者 vs 迭代器**：迭代器只解决"怎么遍历"，访问者解决"遍历时对每种元素做什么"。两者常合用：访问者在遍历过程中分派。

## 六、Java / Go 实现

### Java 实现

```java
/** 元素接口：accept 是唯一需要元素配合的入口 */
interface DocumentElement {
    String accept(DocumentVisitor visitor);
}

/** 访问者接口：每个元素种类都要在这里有一个方法 */
interface DocumentVisitor {
    String visitHeading(Heading element);

    String visitParagraph(Paragraph element);

    String visitImage(Image element);

    String visitTable(Table element);
}

static final class Heading implements DocumentElement {
    final String text;
    final int level;

    Heading(String text, int level) {
        this.text = text;
        this.level = Math.max(1, Math.min(6, level));
    }

    /** 双分派的第一跳 */
    @Override
    public String accept(DocumentVisitor visitor) {
        return visitor.visitHeading(this);
    }
}
```

**使用示例**：

```java
// 结构：Document 装元素，元素不知道任何导出格式
Document doc = new Document()
        .add(new Heading("设计模式", 1))
        .add(new Paragraph("一句话说明"))
        .add(new Image("a.png", "示意图"));

// 换个 visitor 就换一种导出，元素一个都不用改
System.out.println(doc.export(new HtmlVisitor()));        // <h1>设计模式</h1>...
System.out.println(doc.export(new MarkdownVisitor()));    // # 设计模式...
System.out.println(doc.export(new PlainTextVisitor()));   // 设计模式\n====

// 也可以只让单个元素接受访问（双分派：accept → visitXxx）
new Heading("标题", 2).accept(new HtmlVisitor());         // <h2>标题</h2>
```

JDK 1.8 实测输出与 PHP 版逐行一致。Java 侧的三点差异：

- **`@Override` 能帮上忙**：实现 `DocumentVisitor` 时漏写一个方法，`javac` 直接报"未实现抽象方法" —— **编译期就发现**。（PHP 同样会报，因为接口方法未实现会 fatal error）；
- **JDK 17+ 该用 sealed + switch**（第四节），比访问者更安全；
- **`accept()` 返回 `String` 是简化**。真实项目里访问者常用 `void` + 内部累积结果（如 `b.append(...)`），或者返回一个泛型 `R`：
  ```java
  interface DocumentVisitor<R> { R visitHeading(Heading element); /* ... */ }
  ```
  这样同一个模式下，"导出字符串"和"做类型检查（返回 `Type`）"可以复用同一套元素。

### Go 实现

```go
// DocumentElement 元素接口：Accept 是唯一需要元素配合的入口
type DocumentElement interface {
	Accept(DocumentVisitor) string
}

// DocumentVisitor 访问者接口：每个元素种类都要在这里有一个方法
type DocumentVisitor interface {
	VisitHeading(Heading) string
	VisitParagraph(Paragraph) string
	VisitImage(Image) string
	VisitTable(Table) string
}

// Heading 标题
type Heading struct {
	Text  string
	Level int
}

// Accept 双分派的第一跳：把「我是 Heading」这件事交给 visitor 处理
func (h Heading) Accept(v DocumentVisitor) string { return v.VisitHeading(h) }
```

**使用示例**：

```go
// 结构：Document 装元素，元素不知道任何导出格式
doc := (&Document{}).
	Add(Heading{Text: "设计模式", Level: 1}).
	Add(Paragraph{Text: "一句话说明"}).
	Add(Image{Src: "a.png", Alt: "示意图"})

// 换个 visitor 就换一种导出，元素一个都不用改
doc.Export(HtmlVisitor{})        // <h1>设计模式</h1>...
doc.Export(MarkdownVisitor{})    // # 设计模式...
doc.Export(PlainTextVisitor{})   // 设计模式\n====

// 也可以只让单个元素接受访问（双分派：Accept → VisitXxx）
Heading{Text: "标题", Level: 2}.Accept(HtmlVisitor{})   // <h2>标题</h2>
```

go1.26.5 实测输出（与 PHP/Java 一致）。

Go 侧的差异化写法和取舍：

- **Go 更常用"类型 switch"而不是访问者接口**。因为 Go 的接口是隐式实现，"遍历时按类型分派"直接写更自然：
  ```go
  switch v := e.(type) {          // 每个元素一个分支
  case Heading:   return fmt.Sprintf("<h%d>%s</h%d>", v.Level, html.EscapeString(v.Text), v.Level)
  case Paragraph: return "<p>" + html.EscapeString(v.Text) + "</p>"
  // ...
  }
  ```
  实测里 `InstanceofExporter.ToHTML` 就是这个版本。**代价是新增格式要改这个类、新增元素也要改每个方法**；
- **`switch v := e.(type)` 没有"穷尽性检查"**：漏掉一个类型不会报错，只是静默跳过（`default` 为空时什么都不做）。这是 Go 里做访问者的最大风险 —— **建议加 `default: panic("未处理的元素类型: " + fmt.Sprintf("%T", e))`**；
- **元素的 "getter" 在 Go 里是导出字段**（`Heading.Text`）。Go 没有"只读属性"机制，所以"元素只读"这条约定**只能靠不写 setter 来维持**。

## 七、三语言对照

| | PHP | Java | Go |
| --- | --- | --- | --- |
| 访问者接口 | `interface`（4 个方法） | `interface`（4 个方法） | `interface`（4 个方法） |
| 双分派 | `$visitor->visitHeading($this)` | `visitor.visitHeading(this)` | `v.VisitHeading(h)` |
| 元素只读 | `private` + getter | `final` 字段 + getter | **导出字段（无只读机制）** |
| 漏实现方法 | fatal error（加载时） | **编译错误** | 类型 switch 无检查（**易静默漏掉**） |
| 现代替代 | 无（`match(true)` 手写） | JDK 17+ sealed + switch | 类型 switch |
| 生态代表 | PHP-Parser / nikic 的 AST 遍历、Doctrine 的 SQL 生成 | `javax.lang.model.element.ElementVisitor`（注解处理器）、ASM 的 `ClassVisitor` | `go/ast` 的 `ast.Walk` + `Visitor` 接口 |

⭐ **`go/ast` 就是 Go 官方的访问者实现**：`ast.Visitor` 接口只有一个 `Visit(node Node) (w Visitor)` 方法，`ast.Walk` 负责遍历。它比本篇的实现"简化"了一步 —— **只用一个 `Visit` 方法 + 内部类型 switch**，因为 Go 的 AST 节点种类有几十种，逐个写 `visitXxx` 会让接口大到没法维护。

## 八、面试官会追问什么

- **访问者模式和策略模式的区别？** → 策略是"**一个**算法可替换"，接口只有一个方法；访问者是"**一组对象** × 多种操作"，接口**方法数 = 元素种类数**。策略的调用方选一个；访问者是双分派自动选。
- **什么叫双分派？为什么需要它？** → 第一次分派由运行时按元素类型选到 `accept()`，第二次分派由 `accept()` 内部按访问者类型选到 `visitXxx()`。**合起来才能确定"哪个访问者处理哪个元素"** —— PHP/Java/Go 都只有单分派（重载在编译期静态解析），所以必须手写这一跳。
- **这个模式最大的代价是什么？** → 两条：**加元素要改所有 Visitor**（耦合换了方向，没消失）；**元素必须暴露内部数据**（破坏封装）。所以它只适合"**结构稳定、操作多变**"的场景。
- **什么场景最典型？** → **编译器 / 解释器**：AST 节点种类几十年不变，而类型检查、优化、代码生成等操作源源不断。其它还有文档导出、报表统计、序列化框架。
- **PHP 里有内置双分派吗？** → 没有。而且 PHP 不支持方法重载，所以只能手写 `accept()` + `visitXxx()`。替代方式是 `match(true) { $e instanceof X => ... }`，但**没有穷尽性检查**。
- **Java 17+ 还需要访问者吗？** → 很多场景不需要了。**sealed interface + switch 模式匹配**能做同样的事，而且：① 编译器强制穷尽（新增变体立刻报错）；② 没有双分派的心智负担。**访问者的价值在 Java 17+ 明显下降**。
- **Go 里怎么做？** → 常见两种：① 手写 `Accept` + `Visitor` 接口（与本篇同构）；② **类型 switch**（更 Go 风格）。注意②**没有穷尽性检查**，漏掉一个类型会静默跳过 —— 务必加 `default: panic(...)`。`go/ast` 用的是"单方法 Visitor + 内部 switch"的折中方案。
- **怎么判断该不该用？** → 问两个问题：**元素种类会不会经常加？**（会 → 别用）；**操作会不会不断加？**（不会 → 别用）。两个答案分别是"否"和"是"时，访问者最划算。
