# 策略模式

> 素材来源：博客 [PHP 设计模式(四)：策略模式](https://blog.csdn.net/weixin_43837229/article/details/102657353)（2019-10-22），
> 内容出自《深入PHP：面向对象、模式与实践（第三版）》的学习笔记。
> 本篇以博客原文为骨架：一至三节保留原文的定义、场景与 `RotateItem` 示例；
> 第四、五节是针对原文写法的**实测纠错**与优化，第六、七节补 Java / Go 实现。
>
> 同属行为型的还有 [观察者模式.md](观察者模式.md)、[迭代器模式.md](迭代器模式.md)；
> 策略与它的近邻（工厂、状态、责任链）的边界见第八节。

## 一、什么是策略模式

策略模式（Strategy），又叫算法簇模式，**定义了不同的算法族，并且之间可以互相替换，此模式让算法的变化独立于使用算法的客户**。

原文举的两个开端场景很典型：

- 对象筛选——可以按日期筛选，也可以按 ID 筛选；
- 单元测试——在文件存储和内存存储之间切换。

原文接着讲了「为什么非要有它」：实现一个功能有多种算法时，常见的两种做法都是硬编码。

| 硬编码写法 | 原文指出的问题 |
| --- | --- |
| 把这些算法写到一个类中，一个方法对应一个算法 | 类里堆满算法，代码复杂、维护困难 |
| 把算法封装在一个统一方法里，用 `if…else…` 或 `case` 选择 | 增一种算法要改源码，换算法要改客户端调用代码 |

如果把策略包含在客户端，问题更严重——客户端程序会变得庞大且难以维护，可选算法一多就失控。

原文的设问很直接：**如何让算法和对象分开来，使得算法可以独立于使用它的客户而变化？** 为此引入策略模式。

三个角色（原文的 `RotateItem` 示例正好一一对应）：

| 角色 | 职责 | 原文里的类 |
| --- | --- | --- |
| 抽象策略 | 声明算法族的统一接口 | `RotateItem` |
| 具体策略 | 每一种算法的具体实现 | `XItem` / `YItem` / `XYItem` |
| 上下文 Context | 持有策略，对外转发调用 | `ContextStrategy` |

## 二、应用场景

原文列举：**有多种策略可选择的场景** —— 算法选择，以及数据库类型、缓存类型、发送验证码方式、支付方式、日志保存类型、队列类型等。

按原文这段话，可以提炼成一句话判据：**同一件事有多个可替换的做法，而且以后还会加新的做法**。

反过来，下面这些情况原文没展开、但实践里更常踩：

| 场景 | 该不该上策略 |
| --- | --- |
| 只有两种分支，且长期稳定 | ❌ 一个 `if` 或 `match` 更直白，策略是过度设计 |
| 分支会持续增长、且分支内部逻辑较重 | ✅ 典型受益场景 |
| 分支差异只在参数，不在流程 | ❌ 传参数就够，不必建类族 |
| 需要运行时按配置切换（数据库/缓存驱动） | ✅ 与工厂或容器配合最自然 |

## 三、PHP 实现（博客原文）

### 3.1 原文代码

原文的结构是：一个接口、三个具体策略、一个用反射选策略的 Context。

```php
<?php

/**
 * 抽象策略角色
 * Interface RotateItem
 */
interface RotateItem
{
    function inertiaRotate();
    function unInertisRotate();
}

/**
 * 具体策略角色——X产品
 * Class XItem
 */
class XItem implements RotateItem
{
    function inertiaRotate()
    {
        echo "我是X产品，我惯性旋转了。<br/>";
    }

    function unInertisRotate()
    {
        echo "我是X产品，我非惯性旋转了。<br/>";
    }
}

/**
 * 具体策略角色——Y产品
 * Class YItem
 */
class YItem implements RotateItem
{
    function inertiaRotate()
    {
        echo "我是Y产品，我不能惯性旋转。<br/>";
    }

    function unInertisRotate()
    {
        echo "我是Y产品，我非惯性旋转了。<br/>";
    }
}

/**
 * 具体策略角色——XY产品
 * Class XYItem implements RotateItem
 */
class XYItem implements RotateItem
{
    function inertiaRotate()
    {
        echo "我是XY产品，我惯性旋转。<br/>";
    }

    function unInertisRotate()
    {
        echo "我是XY产品，我非惯性旋转了。<br/>";
    }
}

/**
 * 调用策略--有点像工厂
 * 从这里应该知道每种模式不是独立的，而是多种结合起来灵活使用
 * Class ContextStrategy
 */
class ContextStrategy
{
    private $item;

    function getItem($item_name)
    {
        try
        {
            $class=new ReflectionClass($item_name);
            $this->item=$class->newInstance();
        }
        catch(ReflectionException $e)
        {
            $this->item="";
        }
    }

    function inertiaRotate()
    {
        $this->item->inertiaRotate();
    }

    function unInertisRotate()
    {
        $this->item->unInertisRotate();
    }
}
```

原文的调用段与注释化的结果（含 `<hr>` 分隔线）：

```php
//=======================调用策略===============================

$strategy = new ContextStrategy();

echo "X产品<br/>";
$strategy->getItem('XItem');
$strategy->inertiaRotate();
$strategy->unInertisRotate();

echo '<hr>';//横线

echo "Y产品<br/>";
$strategy->getItem('YItem');
$strategy->inertiaRotate();
$strategy->unInertisRotate();
```

原文自己在这里给出一句很有价值的注解，值得原样留下：

> 调用策略——**有点像工厂**。从这里应该知道每种模式不是独立的，而是多种结合起来灵活使用。

这句话点到了后面第四节要讲的要害：这段 `getItem()` 干的其实是**工厂**的活，不是策略的活。

### 3.2 原文运行结果

原文是在浏览器里跑的，输出用 `<br/>` 换行。本机 CLI 复核时把每个 `echo "…<br/>"` 换成 `echo "…", PHP_EOL`（`<hr>` 是纯排版，删掉不影响逻辑），同一份代码的输出是：

```text
X产品
我是X产品，我惯性旋转了。
我是X产品，我非惯性旋转了。
Y产品
我是Y产品，我不能惯性旋转。
我是Y产品，我非惯性旋转了。
XY产品
我是XY产品，我惯性旋转。
我是XY产品，我非惯性旋转了。
```

（PHP 8.0.2 CLI 实测，与原文注释里的结果一致。）

## 四、原文写法在 PHP 8 下要修正的三处

### 4.1 兜底 `$this->item = ""` 会让下一次调用直接致命

原文 `catch` 里的容错是 `$this->item = "";`。本机实测，一旦传入了不存在的策略名，后续调用就是**致命错误**而不是可处理的异常：

```text
PHP Fatal error:  Uncaught Error: Call to a member function inertiaRotate() on string
```

原因是 Context 对外暴露的 `inertiaRotate()` 会无条件执行 `$this->item->inertiaRotate();`，而此时 `$this->item` 是字符串。**容错写成了"静默降级 + 延迟爆炸"**，比直接抛异常更难排查。

正确做法是在 `getItem()` 里就把失败暴露出来：

```php
if (!class_exists($item_name)) {
    throw new InvalidArgumentException("未知的策略：{$item_name}");
}
```

### 4.2 用 `ReflectionClass` + 类名串选策略，其实是「简单工厂」

这是原文自己都点破了的（"有点像工厂"）。两者职责要分清：

| | 谁选 | 谁做 |
| --- | --- | --- |
| 简单工厂 | 工厂按入参选 | 工厂造出来的对象做 |
| 策略模式 | **调用方（或容器）选** | Context 只负责转发 |

原文的 `ContextStrategy::getItem('XItem')` 把"选"和"做"塞进了同一个类——这是**简单工厂 + 策略**的混合体。它能用，但有两个代价：

1. 策略名是字符串，IDE 无法跳转、重构改名不会同步，`'XItem'` 拼错只在运行时才炸；
2. Context 与所有具体策略产生了隐式耦合，新增策略时这个类的"可知范围"在变大。

### 4.3 Context 不该自己 `new` 策略对象

原文的 Context 主动 `newInstance()` 造策略，等于**高层模块直接依赖具体实现**，违反依赖倒置（见 [../原则/六大原则.md](../原则/六大原则.md) 第五节）。

后果很具体：**Context 没法被单测替身替换**。想测"Context 在拿到某个策略时的转发是否正确"，只能真的传入一个字符串类名去构造真实对象；而如果策略构造函数里连了数据库，这个单测就跑不起来。

## 五、优化后的写法

### 5.1 接口 + 构造注入（推荐）

把"选"交出去，"做"留下来。策略由调用方或容器注入：

```php
<?php

declare(strict_types=1);

interface RotateItem
{
    public function inertiaRotate(): string;
    public function unInertisRotate(): string;
}

final class XItem implements RotateItem
{
    public function inertiaRotate(): string   { return '我是X产品，我惯性旋转了。'; }
    public function unInertisRotate(): string { return '我是X产品，我非惯性旋转了。'; }
}

final class YItem implements RotateItem
{
    public function inertiaRotate(): string   { return '我是Y产品，我不能惯性旋转。'; }
    public function unInertisRotate(): string { return '我是Y产品，我非惯性旋转了。'; }
}

final class ContextStrategy
{
    public function __construct(private RotateItem $item) {}

    public function inertiaRotate(): string   { return $this->item->inertiaRotate(); }
    public function unInertisRotate(): string { return $this->item->unInertisRotate(); }
}

foreach ([new XItem(), new YItem()] as $item) {
    $ctx = new ContextStrategy($item);
    echo $ctx->inertiaRotate(), PHP_EOL;
    echo $ctx->unInertisRotate(), PHP_EOL;
}
```

实测输出：

```text
我是X产品，我惯性旋转了。
我是X产品，我非惯性旋转了。
我是Y产品，我不能惯性旋转。
我是Y产品，我非惯性旋转了。
```

三处改动对应三个问题：**接口约束返回值**（不再靠 `echo` 副作用）、**构造注入**（依赖倒置、可替换测试替身）、**失败提前于调用**（不会延迟到转发时才炸）。

### 5.2 闭包策略：没有状态的策略不必建类

如果一个策略就是"一段算法"，用 `Closure` 比建一个类轻得多，PHP 里很常见：

```php
$rotations = [
    'inertia'   => fn (string $p): string => "{$p}惯性旋转",
    'unInertia' => fn (string $p): string => "{$p}非惯性旋转",
];

echo $rotations['inertia']('X产品'), PHP_EOL;
```

代价也说清楚：闭包策略**没有类型约束**（只能靠 `Closure` 兜底）、**无法被反射/依赖注入自动装配**、也不便于挂注解。所以判据是：

| 选型 | 适用 |
| --- | --- |
| 接口策略 | 策略有多个方法、需要被容器装配、需要类型安全 |
| 闭包策略 | 策略只有一个方法、无状态、就地用完 |
| `match` 分支 | 分支 ≤3 个且长期稳定，连策略对象都不必存在 |

### 5.3 什么时候连策略模式都不用

- **分支只有两三种，且一两年没变过**：`match` 一行解决，引入接口 + 类 + 注入只是增加跳转成本；
- **差异只是参数**：`(string $mode)` 传进同一个函数即可；
- **分支之间需要互相调用**：可能真正需要的是状态模式或责任链，见第八节。

## 六、Java 实现

Java 里策略模式的写法与 PHP 几乎一一对应，但有两个语言级差异：接口是**强类型**的（策略类型不可能退化成字符串），以及可以用**方法引用**替代只含一个方法的策略类。

```java
public class StrategyDemo {
    interface RotateItem {
        String inertiaRotate();
        String unInertisRotate();
    }

    static final class XItem implements RotateItem {
        public String inertiaRotate()   { return "我是X产品，我惯性旋转了。"; }
        public String unInertisRotate() { return "我是X产品，我非惯性旋转了。"; }
    }

    static final class YItem implements RotateItem {
        public String inertiaRotate()   { return "我是Y产品，我不能惯性旋转。"; }
        public String unInertisRotate() { return "我是Y产品，我非惯性旋转了。"; }
    }

    static final class ContextStrategy {
        private final RotateItem item;
        ContextStrategy(RotateItem item) { this.item = item; }
        String inertiaRotate()   { return item.inertiaRotate(); }
        String unInertisRotate() { return item.unInertisRotate(); }
    }

    public static void main(String[] args) {
        RotateItem[] items = { new XItem(), new YItem() };
        for (RotateItem item : items) {
            ContextStrategy ctx = new ContextStrategy(item);
            System.out.println(ctx.inertiaRotate());
            System.out.println(ctx.unInertisRotate());
        }
    }
}
```

JDK 1.8 实测输出与 PHP 修正版逐行一致：

```text
我是X产品，我惯性旋转了。
我是X产品，我非惯性旋转了。
我是Y产品，我不能惯性旋转。
我是Y产品，我非惯性旋转了。
```

Java 里更地道的两点：

- **单方法接口可用 `lambda`**：`RotateItem r = () -> "旋转了";`，策略甚至不必有类；
- **生产代码里策略常由 Spring 注入**：`Map<String, RotateItem> strategies` 能一次收齐同接口的所有实现，把 5.1 的"手动选"变成"按名字查表"，且**新增策略不需要改任何既有代码**（开闭原则）。

## 七、Go 实现

Go 的接口是**隐式实现**——类型不需要写 `implements`，只要方法集匹配就算实现了接口。这让策略模式在 Go 里比其他语言更轻：加一个策略既不改接口声明，也不改已有类型的声明。

```go
package main

import "fmt"

// RotateItem 是策略接口：Go 里接口是隐式实现，不需要 implements
type RotateItem interface {
	InertiaRotate() string
	UnInertisRotate() string
}

type XItem struct{}

func (XItem) InertiaRotate() string   { return "我是X产品，我惯性旋转了。" }
func (XItem) UnInertisRotate() string { return "我是X产品，我非惯性旋转了。" }

type YItem struct{}

func (YItem) InertiaRotate() string   { return "我是Y产品，我不能惯性旋转。" }
func (YItem) UnInertisRotate() string { return "我是Y产品，我非惯性旋转了。" }

// ContextStrategy 持有一个策略，同样走构造注入
type ContextStrategy struct {
	item RotateItem
}

func NewContextStrategy(item RotateItem) *ContextStrategy {
	return &ContextStrategy{item: item}
}

func (c *ContextStrategy) InertiaRotate() string   { return c.item.InertiaRotate() }
func (c *ContextStrategy) UnInertisRotate() string { return c.item.UnInertisRotate() }

func main() {
	for _, item := range []RotateItem{XItem{}, YItem{}} {
		ctx := NewContextStrategy(item)
		fmt.Println(ctx.InertiaRotate())
		fmt.Println(ctx.UnInertisRotate())
	}
}
```

go1.26.5 实测输出（与上两语言一致）：

```text
我是X产品，我惯性旋转了。
我是X产品，我非惯性旋转了。
我是Y产品，我不能惯性旋转。
我是Y产品，我非惯性旋转了。
```

Go 与之相关的两点值得记：

- **函数类型也是一等公民**：`type RotateFunc func(string) string` 可以直接当策略用，配合 5.2 的闭包思路一致；
- **接口越小越好**：Go 惯例是 1~2 个方法的窄接口（如标准库的 `io.Writer`）。上面把两个方法放进同一个接口，若二者不常被一起使用，拆成两个单方法接口更符合 Go 的习惯。

## 八、PHP / Java / Go 对照

| 维度 | PHP | Java | Go |
| --- | --- | --- | --- |
| 接口声明 | `interface` + `implements` | `interface` + `implements` | 隐式实现，无需声明 |
| 无类型约束的退化写法 | 类名字符串 + 反射（原文写法） | 几乎不会出现 | 不会出现 |
| 单方法策略 | 闭包 `Closure` | `@FunctionalInterface` + lambda | 函数类型 |
| 策略的装配方式 | 手写简单工厂 / 容器 `bind` | Spring 注入 `Map<String, T>` | 手写 map 或 wire 之类代码生成 |
| 生命周期 | **仅当前请求**（php-fpm） | 随容器/单例常驻 | 随进程常驻 |

最容易考的一条是最后一行：**PHP 的 Context 每次请求都要重建策略对象**，而 Java/Go 里策略通常是无状态单例、全程复用。这直接决定了一件事 —— **策略对象里不要存请求级状态**，否则在 Java/Go 下并发调用会互相串数据（PHP 因为每请求重建，反而掩盖了这个 bug）。

策略与几个近邻的边界：

| 问题 | 归属 |
| --- | --- |
| 用哪种算法？（策略由调用方选） | 策略 |
| 造哪个对象？（选的动作在工厂里） | 工厂 |
| 对象自己随条件改变行为并迁移到下一态 | 状态模式 |
| 请求沿链条传递，谁合适谁处理 | 责任链 |
| 按条件筛选一个集合 | 过滤器（见 [../结构型/过滤器模式.md](../结构型/过滤器模式.md)） |

## 九、面试官会追问什么

- **策略模式和简单工厂的区别？** → 策略回答"用哪种算法"（选在调用方，Context 只转发）；工厂回答"造哪个对象"（选在工厂内部）。
- **策略模式和状态模式的区别？** → 状态模式里**状态自己会迁移**（`$state->next()` 返回下一个状态），调用方不指定；策略模式的策略由外部指定且不自动切换。类图几乎一样，区别在"谁决定改变"。
- **`if/else` 和策略模式怎么选？** → 分支 ≤3 且稳定就用 `match`；分支会持续增长、或分支逻辑本身较重、或需要运行时按配置切换，才上策略。
- **策略对象可以有状态吗？** → 可以有，但要**每个 Context 一份**。若做成共享单例又存了状态，在 Java/Go 下会串数据；PHP 因为每请求重建而掩盖问题，换 Swoole 就会暴露。
- **策略怎么选出来的？** → 三种：调用方直接 `new`（最直白）、容器按名字绑定（推荐，便于配置化）、策略自注册到 map（如 Java 的 `Map<String, T>` 收集所有实现）。
- **为什么原文的写法在 PHP 8 下会致命？** → `catch` 里把 `$this->item` 降级成了字符串 `""`，而转发方法仍无条件调用其方法 → `Call to a member function ... on string`。容错必须"提前失败"而不是"静默降级"。
