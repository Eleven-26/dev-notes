## 一、什么是策略模式

原文的定义：

> 策略模式（Strategy），又叫算法簇模式，**定义了不同的算法族，并且之间可以互相替换，此模式让算法的变化独立于使用算法的客户**。

原文举的两个开端场景很典型：对象筛选（按日期筛、按 ID 筛），以及单元测试中在文件存储和内存存储之间切换。

接着原文讲了「为什么非要有它」——实现一个功能有多种算法时，常见的两种做法都是硬编码：

| 硬编码写法 | 原文指出的问题 |
| --- | --- |
| 把这些算法写到一个类中，一个方法对应一个算法 | 类里堆满算法，代码复杂、维护困难 |
| 把算法封装在一个统一方法里，用 `if…else…` 或 `case` 选择 | 增一种算法要改源码，换算法要改客户端调用代码 |

原文还点出更糟的情况：**把策略包含在客户端**，会让客户端程序变得庞大且难以维护，可选算法一多就失控。于是原文提出那个设问：

> **如何让算法和对象分开来，使得算法可以独立于使用它的客户而变化？**

答案就是三个角色分工：

| 角色 | 职责 | 关键约束 |
| --- | --- | --- |
| 抽象策略（Strategy） | 声明算法族的统一接口 | 只声明「算什么」，**不声明「怎么选」** |
| 具体策略（ConcreteStrategy） | 每一种算法的实现 | 无状态，可被安全复用 |
| 上下文（Context） | 持有策略并对外转发 | **不自己 new 策略、不认识具体类型** |

第三行的两处加粗是策略模式最容易被写错的地方，第四节会展开。

## 二、应用场景

原文列举：**有多种策略可选择的场景** —— 算法选择，以及数据库类型、缓存类型、发送验证码方式、支付方式、日志保存类型、队列类型等。

按原文这段话可以提炼成一句话判据：**同一件事有多个可替换的做法，而且以后还会加新的做法**。

反过来，下面这些情况原文没展开、但实践里更常踩：

| 场景 | 该不该上策略 |
| --- | --- |
| 只有两种分支，且长期稳定 | ❌ 一个 `if` 或 `match` 更直白 |
| 分支会持续增长、且分支内部逻辑较重 | ✅ 典型受益场景 |
| 分支差异只在参数，不在流程 | ❌ 传参数就够，不必建类族 |
| 需要运行时按配置切换（数据库/缓存驱动） | ✅ 与工厂或容器配合最自然 |

## 三、PHP 标准实现

场景换成真实一点的需求：**订单折扣计算**。金额一律用「分」的整数，不碰浮点。

```php
<?php

declare(strict_types=1);

/**
 * 策略接口：只声明「算什么」。
 * 注意它不提供「怎么选」——选择权在调用方或容器，这正是策略与工厂的分界。
 */
interface DiscountStrategy
{
    /** @return int 折扣金额（分） */
    public function discountFor(int $amountInCents): int;
}

/** 具体策略：不打折 */
final class NoDiscount implements DiscountStrategy
{
    public function discountFor(int $amountInCents): int
    {
        return 0;
    }
}

/** 具体策略：满 200 元减 30 元 */
final class FullReduction implements DiscountStrategy
{
    private const THRESHOLD_IN_CENTS = 20000;
    private const REDUCTION_IN_CENTS = 3000;

    public function discountFor(int $amountInCents): int
    {
        return $amountInCents >= self::THRESHOLD_IN_CENTS ? self::REDUCTION_IN_CENTS : 0;
    }
}

/** 具体策略：按比例打折（1000 个基点 = 10%） */
final class PercentageDiscount implements DiscountStrategy
{
    public function __construct(private int $rateInBasisPoints)
    {
        if ($rateInBasisPoints < 0 || $rateInBasisPoints > 10000) {
            throw new InvalidArgumentException('折扣率必须在 0~10000 个基点之间');
        }
    }

    public function discountFor(int $amountInCents): int
    {
        return intdiv($amountInCents * $this->rateInBasisPoints, 10000);
    }
}

/** 上下文：只做编排与转发，不 new 策略、不认识具体策略类型 */
final class PriceCalculator
{
    public function __construct(private DiscountStrategy $strategy) {}

    public function payable(int $amountInCents): int
    {
        if ($amountInCents < 0) {
            throw new InvalidArgumentException('金额不能为负');
        }
        return $amountInCents - $this->strategy->discountFor($amountInCents);
    }
}
```

**使用示例**：

```php
// 「用哪种策略」由调用方决定，PriceCalculator 不认识具体策略
$calculator = new PriceCalculator(new FullReduction());
$calculator->payable(25000);                  // 22000（满 200 元减 30 元）

// 换策略 = 重新注入，上下文类一行都不用改
$calculator = new PriceCalculator(new PercentageDiscount(1000));   // 9 折
$calculator->payable(25000);                  // 22500

// 非法折扣率在「构造策略」时就失败，不会拖到 payable 时
new PercentageDiscount(20000);                // 抛 InvalidArgumentException
```

调用与实测（PHP 8.0.2 CLI）：

```php
$amount = 25000; // 250.00 元

$strategies = [
    '不打折'    => new NoDiscount(),
    '满200减30' => new FullReduction(),
    '9折'       => new PercentageDiscount(1000),
];

foreach ($strategies as $name => $strategy) {
    $calculator = new PriceCalculator($strategy);
    printf("%-10s 原价 %5d 分 -> 应付 %5d 分\n", $name, $amount, $calculator->payable($amount));
}

$calculator = new PriceCalculator(new PercentageDiscount(500)); // 95 折
printf("%-10s 原价 %5d 分 -> 应付 %5d 分\n", '改95折', $amount, $calculator->payable($amount));

try {
    new PercentageDiscount(20000);
} catch (InvalidArgumentException $e) {
    echo '4_拒绝非法折扣率 : ', $e->getMessage(), PHP_EOL;
}
```

```text
不打折  原价 25000 分 -> 应付 25000 分
满200减30 原价 25000 分 -> 应付 22000 分
9折       原价 25000 分 -> 应付 22500 分
改95折   原价 25000 分 -> 应付 23750 分
4_拒绝非法折扣率 : 折扣率必须在 0~10000 个基点之间
```

### 5 个让它算「标准写法」的细节

| # | 做法 | 为什么 |
| --- | --- | --- |
| 1 | 接口只声明 `discountFor()`，不提供 `factory()` | 策略不管选择，选择交给调用方/容器（分工见第一节） |
| 2 | 金额用 `int` 的「分」，`intdiv` 取整 | 浮点算钱必然出现 `0.1 + 0.2` 那类误差 |
| 3 | 构造注入 + **构造里校验参数** | 非法折扣率在 `new` 时就炸，而不是等到算钱的那一刻 |
| 4 | 类一律 `final`、属性 `private` | 策略不期望被继承；`final` 也顺带省掉了 late static binding 带来的坑 |
| 5 | 上下文只做「编排 + 转发」 | Context 里出现 `if ($type === ...)` 就说明选择职责回流了 |

## 四、原文写法的三个问题（别这么写）

原文示例用 `ReflectionClass` + 类名串来选策略，并自己点破了一句很有价值的话：

> 调用策略——**有点像工厂**。从这里应该知道每种模式不是独立的，而是多种结合起来灵活使用。

这句话是对的，但三种做法放进生产会出问题。

### 4.1 兜底 `$this->item = ""` 会让下一次调用致命

原文 `catch` 里的容错是把策略降级成空字符串。本机实测，传入不存在的策略名后：

```text
PHP Fatal error:  Uncaught Error: Call to a member function inertiaRotate() on string
```

因为上下文对外的方法仍无条件执行 `$this->item->xxx()`。**这叫「静默降级 + 延迟爆炸」**，比直接抛异常更难排查。标准做法是在选择的那一刻就失败：

```php
if (!isset($this->strategies[$key])) {
    throw new InvalidArgumentException("未知的策略：{$key}");
}
```

### 4.2 用 `ReflectionClass` + 类名串选策略，其实是「简单工厂」

| | 谁选 | 谁做 |
| --- | --- | --- |
| 简单工厂 | 工厂按入参选 | 造出来的对象做 |
| 策略模式 | **调用方（或容器）选** | Context 只负责转发 |

把「选」和「做」塞进同一个类，代价是：策略名成了字符串，IDE 无法跳转、重构改名不会同步，拼错只在运行时才炸。

### 4.3 Context 自己 `new` 策略 → 依赖倒置被破坏，也测不了

上下文主动 `newInstance()`，等于高层模块直接依赖具体实现（见 [../原则/六大原则.md](../原则/六大原则.md) 第五节）。最直接的后果是**无法替换测试替身**：想验「上下文转发是否正确」，只能真的传类名去构造真实对象；而策略构造函数里一旦连了数据库，这个单测就跑不起来。

## 五、什么时候不必上策略

策略不是免费的：每个分支一个类 + 一次注入。三种更轻的替代：

```php
// ① 闭包策略：无状态、单方法，就地用完
$discounts = [
    'none' => fn (int $amount): int => 0,
    'vip'  => fn (int $amount): int => intdiv($amount, 10),
];
echo $discounts['vip'](25000), PHP_EOL;   // 2500

// ② match 分支：分支少且长期稳定
$discount = match ($level) {
    'vip'    => intdiv($amount, 10),
    'normal' => 0,
    default  => throw new InvalidArgumentException("未知等级：{$level}"),
};
```

选型判据：

| 写法 | 适用 |
| --- | --- |
| 接口策略 | 策略有多个方法、需要被容器装配、需要类型安全 |
| 闭包策略 | 单方法、无状态、就地用完（代价：无类型约束、不可被反射/容器自动装配） |
| `match` | 分支 ≤3 个且长期稳定 |

## 六、Java 实现

```java
public class StrategyStandard {
    interface DiscountStrategy {
        int discountFor(int amountInCents);
    }

    static final class NoDiscount implements DiscountStrategy {
        public int discountFor(int amountInCents) { return 0; }
    }

    static final class FullReduction implements DiscountStrategy {
        private static final int THRESHOLD_IN_CENTS = 20000;
        private static final int REDUCTION_IN_CENTS = 3000;

        public int discountFor(int amountInCents) {
            return amountInCents >= THRESHOLD_IN_CENTS ? REDUCTION_IN_CENTS : 0;
        }
    }

    static final class PercentageDiscount implements DiscountStrategy {
        private final int rateInBasisPoints;

        PercentageDiscount(int rateInBasisPoints) {
            if (rateInBasisPoints < 0 || rateInBasisPoints > 10000) {
                throw new IllegalArgumentException("折扣率必须在 0~10000 个基点之间");
            }
            this.rateInBasisPoints = rateInBasisPoints;
        }

        public int discountFor(int amountInCents) {
            return amountInCents * rateInBasisPoints / 10000;
        }
    }

    static final class PriceCalculator {
        private final DiscountStrategy strategy;

        PriceCalculator(DiscountStrategy strategy) {
            if (strategy == null) {
                throw new IllegalArgumentException("策略不能为空");
            }
            this.strategy = strategy;
        }

        int payable(int amountInCents) {
            if (amountInCents < 0) {
                throw new IllegalArgumentException("金额不能为负");
            }
            return amountInCents - strategy.discountFor(amountInCents);
        }
    }
}
```

**使用示例**：

```java
// 上下文只认接口：注入哪个策略由调用方决定
PriceCalculator calc = new PriceCalculator(new FullReduction());
calc.payable(25000);                                // 22000

// 单方法接口可以用 lambda，连类都不用建
DiscountStrategy half = amount -> amount / 2;
new PriceCalculator(half).payable(25000);           // 12500

// 换策略 = 重新注入，PriceCalculator 不用改
new PriceCalculator(new PercentageDiscount(1000)).payable(25000);   // 22500
new PercentageDiscount(20000);                      // 抛 IllegalArgumentException
```

JDK 1.8 实测输出与 PHP 版逐行一致：

```text
不打折  原价 25000 分 -> 应付 25000 分
满200减30 原价 25000 分 -> 应付 22000 分
9折       原价 25000 分 -> 应付 22500 分
改95折   原价 25000 分 -> 应付 23750 分
4_拒绝非法折扣率 : 折扣率必须在 0~10000 个基点之间
```

Java 里比 PHP 多出来的两点：

- **单方法接口可以用 lambda**：`DiscountStrategy s = amount -> 0;`，连类都不用建；
- **生产代码里用 Spring 收齐实现**：注入 `Map<String, DiscountStrategy>` 能一次拿到同接口的所有 Bean，于是「选」变成按名字查表，**新增策略不改任何既有代码**（开闭原则）。

## 七、Go 实现

```go
package main

import (
	"errors"
	"fmt"
)

// DiscountStrategy 策略接口：Go 里接口是隐式实现，越小越好
type DiscountStrategy interface {
	DiscountFor(amountInCents int) int
}

type NoDiscount struct{}

func (NoDiscount) DiscountFor(int) int { return 0 }

const (
	thresholdInCents = 20000
	reductionInCents = 3000
)

type FullReduction struct{}

func (FullReduction) DiscountFor(amountInCents int) int {
	if amountInCents >= thresholdInCents {
		return reductionInCents
	}
	return 0
}

type PercentageDiscount struct {
	RateInBasisPoints int
}

func NewPercentageDiscount(rateInBasisPoints int) (PercentageDiscount, error) {
	if rateInBasisPoints < 0 || rateInBasisPoints > 10000 {
		return PercentageDiscount{}, errors.New("折扣率必须在 0~10000 个基点之间")
	}
	return PercentageDiscount{RateInBasisPoints: rateInBasisPoints}, nil
}

func (p PercentageDiscount) DiscountFor(amountInCents int) int {
	return amountInCents * p.RateInBasisPoints / 10000
}

// PriceCalculator 上下文：只做编排与转发
type PriceCalculator struct {
	strategy DiscountStrategy
}

func NewPriceCalculator(strategy DiscountStrategy) (*PriceCalculator, error) {
	if strategy == nil {
		return nil, errors.New("策略不能为空")
	}
	return &PriceCalculator{strategy: strategy}, nil
}

func (c *PriceCalculator) Payable(amountInCents int) (int, error) {
	if amountInCents < 0 {
		return 0, errors.New("金额不能为负")
	}
	return amountInCents - c.strategy.DiscountFor(amountInCents), nil
}
```

**使用示例**：

```go
// 策略与上下文都可能返回 error；这里用 _ 简化演示
pct, _ := NewPercentageDiscount(1000)          // 9 折
calc, _ := NewPriceCalculator(pct)
payable, _ := calc.Payable(25000)              // 22500

// 换策略 = 换实现，上下文类型不变
calc, _ = NewPriceCalculator(FullReduction{})
payable, _ = calc.Payable(25000)
fmt.Println(payable)

// 非法折扣率在构造时就返回 error
_, err := NewPercentageDiscount(20000)         // 折扣率必须在 0~10000 个基点之间
fmt.Println(err)
```

go1.26.5 实测输出（与前两语言一致）：

```text
不打折        原价 25000 分 -> 应付 25000 分
满200减30    原价 25000 分 -> 应付 22000 分
9折         原价 25000 分 -> 应付 22500 分
改95折       原价 25000 分 -> 应付 23750 分
4_拒绝非法折扣率 : 折扣率必须在 0~10000 个基点之间
```

Go 的两点差异：

- **错误是返回值不是异常**：所以 `NewPercentageDiscount` / `Payable` 都返回 `error`，调用方显式判断——这与 Java 的 `throw`、PHP 的 `throw` 是同一件事的三种表达；
- **接口越小越好**：Go 惯例是 1~2 个方法的窄接口（标准库 `io.Writer` 就是样板）。若策略确实需要两个方法，再考虑合并。

## 八、PHP / Java / Go 对照

| 维度 | PHP | Java | Go |
| --- | --- | --- | --- |
| 接口声明 | `interface` + `implements` | `interface` + `implements` | 隐式实现，无需声明 |
| 单方法策略 | 闭包 `Closure` | lambda / `@FunctionalInterface` | 函数类型 |
| 参数校验失败 | `throw` | `throw` | 返回 `error` |
| 策略装配 | 手写工厂 / 容器 `bind` | Spring 注入 `Map<String, T>` | 手写 map 或 wire 之类代码生成 |
| 生命周期 | **仅当前请求**（php-fpm） | 随容器常驻 | 随进程常驻 |

最后一行最容易考：**PHP 每次请求都要重建策略对象**，而 Java/Go 里策略通常是无状态单例、全程复用。这决定了一件事 —— **策略对象里不要存请求级状态**：在 Java/Go 下并发调用会互相串数据，而 PHP 因为每请求重建反而掩盖了这个 bug（换 Swoole/RoadRunner 就暴露）。

与近邻模式的边界：

| 问题 | 归属 |
| --- | --- |
| 用哪种算法？（选择在调用方） | 策略 |
| 造哪个对象？（选择在工厂内部） | 工厂 |
| 对象自己随条件改变行为并迁移到下一态 | 状态模式 |
| 请求沿链条传递，谁合适谁处理 | 责任链 |
| 按条件筛选一个集合 | 过滤器（见 [../结构型/过滤器模式.md](../结构型/过滤器模式.md)） |

## 九、面试官会追问什么

- **策略模式和简单工厂的区别？** → 策略回答"用哪种算法"（选在调用方，Context 只转发）；工厂回答"造哪个对象"（选在工厂内部）。原文那句"有点像工厂"说的就是把两者混在一起写。
- **策略模式和状态模式的区别？** → 状态模式里**状态自己会迁移**，调用方不指定；策略模式的策略由外部指定且不自动切换。类图几乎一样，区别在"谁决定改变"。
- **`if/else` 和策略模式怎么选？** → 分支 ≤3 且稳定就用 `match`；分支会持续增长、分支逻辑本身较重、或需要按配置运行时切换，才上策略。
- **策略对象可以有状态吗？** → 可以有，但要**每个 Context 一份**。做成共享单例又存状态，在 Java/Go 下会串数据；PHP 因为每请求重建而掩盖问题。
- **策略怎么选出来的？** → 三种：调用方直接 `new`（最直白）、容器按名字绑定（推荐，便于配置化）、策略自注册进 map（如 Java 收集所有实现）。
- **为什么原文的写法在 PHP 8 下会致命？** → `catch` 里把策略降级成字符串 `""`，而转发方法仍无条件调用其方法 → `Call to a member function ... on string`。容错必须"提前失败"，不能"静默降级"。
