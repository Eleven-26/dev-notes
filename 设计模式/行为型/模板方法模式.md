## 一、模板方法解决什么问题

模板方法（Template Method）属于行为型模式：**在一个方法里定义算法的骨架，把其中若干步骤延迟到子类实现**。

它要解决的是"**流程相同、个别步骤不同**"这种最常见的重复：

| 需求 | 没有模板方法时 |
| --- | --- |
| 三种数据源、同一套导入流程 | 三个类各写一遍"打开 → 逐行读 → 判定 → 规整 → 落库 → 关闭"，改一处得改三处 |
| 顺序不能乱（必须先校验再落库） | 顺序只存在于文档和记忆里，谁先写错都不知道 |
| 想加一个"跳过条件" | 要么改所有实现，要么到处 `if` |

模板方法与其它模式的最大不同在于：**它控制的是顺序，而不只是代码复用**。复用可以用组合拿到，但"骨架不许被改写"只有模板方法能保证。

四个角色：

| 角色 | 职责 | 本篇对应 |
| --- | --- | --- |
| AbstractClass | 定义骨架（模板方法本身）与钩子 | `DataImporter::import()` |
| 抽象步骤 | 骨架里必须由子类填的部分 | `open()` / `readRow()` / `close()` |
| 钩子（Hook） | 有默认实现、子类可选覆写的部分 | `shouldImport()` / `normalize()` / `persist()` |
| ConcreteClass | 只实现变化点 | `CsvImporter` / `JsonImporter` |

**好莱坞原则（Don't call us, we'll call you）**：整个过程里，是**父类调用子类**，而不是子类调用父类。子类只提供零件，装配顺序由父类决定。

## 二、PHP 标准实现

场景：**数据导入**（CSV / JSON / API 三种来源，流程一致、解析方式不同）。

```php
<?php

declare(strict_types=1);

/** 导入汇总：骨架统一产出，与具体格式无关 */
final class ImportReport
{
    public int $total = 0;
    public int $imported = 0;
    public int $skipped = 0;

    public function describe(): string
    {
        return sprintf('共 %d 行，导入 %d 行，跳过 %d 行', $this->total, $this->imported, $this->skipped);
    }
}

/**
 * 模板方法：把「导入」的骨架固定下来（final），把变化点交给子类。
 * 骨架 = 打开 → 逐行读 → 判定 → 规整 → 落库 → 关闭。
 */
abstract class DataImporter
{
    /** 模板方法本身：子类不能改写骨架，只能填步骤 */
    final public function import(): ImportReport
    {
        $report = new ImportReport();
        $this->open();                                   // 抽象步骤
        while (($row = $this->readRow()) !== null) {      // 抽象步骤
            $report->total++;
            if (!$this->shouldImport($row)) {             // 钩子（有默认实现）
                $report->skipped++;
                continue;
            }
            $this->persist($this->normalize($row));       // 钩子 + 钩子
            $report->imported++;
        }
        $this->close();                                   // 抽象步骤

        return $report;
    }

    // ---------- 抽象步骤：子类必须实现 ----------
    abstract protected function open(): void;

    /** @return array<string,string>|null 返回 null 表示读完 */
    abstract protected function readRow(): ?array;

    abstract protected function close(): void;

    // ---------- 钩子：有默认实现，子类按需覆写 ----------
    /** 默认每一行都要 */
    protected function shouldImport(array $row): bool
    {
        return true;
    }

    /** 默认不做规整 */
    protected function normalize(array $row): array
    {
        return $row;
    }

    /** 落库位置：真实项目里换成 repository 调用 */
    protected function persist(array $row): void
    {
        echo '    落库 ', json_encode($row, JSON_UNESCAPED_UNICODE), PHP_EOL;
    }
}
```

两个子类只需填自己的那部分：

```php
/** 具体实现一：CSV 文本 */
final class CsvImporter extends DataImporter
{
    /** @var list<string> */
    private array $lines;
    private int $cursor = 0;

    public function __construct(string $csv)
    {
        $this->lines = array_values(array_filter(
            array_map('trim', explode("\n", trim($csv))),
            static fn (string $l): bool => $l !== ''
        ));
    }

    protected function open(): void
    {
        $this->cursor = 0;   // 骨架保证 open 一定先被调用，子类借此重置状态
    }

    protected function readRow(): ?array
    {
        if (!isset($this->lines[$this->cursor])) {
            return null;
        }
        $cells = explode(',', $this->lines[$this->cursor++]);

        return [
            'name' => trim($cells[0] ?? ''),
            'dept' => trim($cells[1] ?? ''),
            'email' => trim($cells[2] ?? ''),
        ];
    }

    protected function close(): void
    {
        $this->cursor = 0;
    }

    /** 覆写钩子：没有邮箱的行不导入 */
    protected function shouldImport(array $row): bool
    {
        return $row['email'] !== '';
    }
}

/** 具体实现二：JSON 数组（结构不同、规整规则也不同） */
final class JsonImporter extends DataImporter
{
    /** @var list<array<string,mixed>> */
    private array $rows;
    private int $cursor = 0;

    public function __construct(string $json)
    {
        /** @var list<array<string,mixed>> $decoded */
        $decoded = json_decode($json, true, 512, JSON_THROW_ON_ERROR);
        $this->rows = $decoded;
    }

    protected function open(): void
    {
        $this->cursor = 0;
    }

    protected function readRow(): ?array
    {
        if (!isset($this->rows[$this->cursor])) {
            return null;
        }
        $raw = $this->rows[$this->cursor++];

        return [
            'name' => (string) ($raw['name'] ?? ''),
            'dept' => (string) ($raw['dept'] ?? ''),
            'email' => (string) ($raw['email'] ?? ''),
        ];
    }

    protected function close(): void
    {
        $this->cursor = 0;
    }

    /** 覆写钩子：不同来源大小写约定不同，入库前统一小写 */
    protected function normalize(array $row): array
    {
        $row['email'] = strtolower($row['email']);

        return $row;
    }
}
```

**使用示例**：

```php
// 子类只填「怎么读」，顺序由父类的 final 骨架 import() 固定
$csv = "张三, 研发, Zhang@Example.com\n李四, 研发, li@example.com\n王五, 运营, ";
$report = (new CsvImporter($csv))->import();
$report->describe();   // 共 3 行，导入 2 行，跳过 1 行（王五没邮箱，被钩子跳过）
$report->total;        // 3
$report->skipped;      // 1

// 换来源 = 换子类，骨架一行不改
$json = '[{"name":"赵六","dept":"市场","email":"ZHAO@Example.com"}]';
(new JsonImporter($json))->import()->imported;   // 1（normalize 已把邮箱转小写）
```

实测（PHP 8.0.2 CLI）：

```text
1_CSV 导入       :     落库 {"name":"张三","dept":"研发","email":"Zhang@Example.com"}
    落库 {"name":"李四","dept":"研发","email":"li@example.com"}
共 3 行，导入 2 行，跳过 1 行

2_JSON 导入      :     落库 {"name":"赵六","dept":"市场","email":"zhao@example.com"}
    落库 {"name":"钱七","dept":"市场","email":"qian@example.com"}
共 2 行，导入 2 行，跳过 0 行

3_组合版导入     :     落库 {"name":"张三","dept":"研发","email":"Zhang@Example.com"}
    落库 {"name":"李四","dept":"研发","email":"li@example.com"}
共 3 行，导入 2 行，跳过 1 行

4_骨架是 final 吗 : true
5_钩子带默认实现  : shouldImport=true
```

要看的点：

- 第 1 行 **`Zhang@Example.com` 保持原样**（CSV 没覆写 `normalize`），第 2 行 **`ZHAO@Example.com` 被转成小写**（JSON 覆写了）—— 同一个骨架、不同的钩子，行为不同；
- 第 1 行的"跳过 1 行"来自 CSV 覆写的 `shouldImport`，JSON 没覆写所以"跳过 0 行"；
- 第 4、5 行是反射拿到的骨架属性：**`import()` 是 `final`**（子类不能改写顺序），**`shouldImport` 不是抽象的**（有默认实现，子类可选）。

### 让它算「标准写法」的 6 个细节

| # | 做法 | 为什么 |
| --- | --- | --- |
| 1 | 骨架方法标 `final` | 模板方法**唯一的不可替代价值就是"顺序不许改"**；不加 `final` 就退化成普通基类了 |
| 2 | 抽象方法只留给"没有合理默认值"的步骤 | 有了默认值就该是钩子，否则子类被迫写一堆空实现 |
| 3 | 钩子命名体现"可插拔"：`shouldXxx()` / `beforeXxx()` / `afterXxx()` | 读代码时一眼能分辨"必须实现"与"可以不管" |
| 4 | 骨架里用 `$this->step()` 调用步骤，不用 `self::step()` | ⚠️ PHP 特有陷阱，见第四节实测 |
| 5 | 抽象步骤不放在构造器里调用 | 构造期子类字段可能还没就位，见第四节实测 |
| 6 | 子类里的 `open()` 负责重置自己的游标状态 | 骨架保证 `open()` 是最先调用的，子类借此做"每次导入都从头开始" |

## 三、抽象步骤 vs 钩子：这条线怎么划

```text
没有合理默认值 → 抽象方法（abstract）→ 子类必须实现
有合理默认值   → 钩子（普通方法 + 默认实现）→ 子类按需覆写
```

判据只有一个：**"不做这件事能不能给出一个说得过去的行为"**。

| 步骤 | 有没有合理默认 | 归类 |
| --- | --- | --- |
| `readRow()` | 没有（读不出数据就什么都不用做了） | 抽象方法 |
| `open()` / `close()` | 没有（资源必须显式管理） | 抽象方法 |
| `shouldImport()` | 有（默认全都要） | 钩子 |
| `normalize()` | 有（默认不改） | 钩子 |
| `persist()` | 其实有（默认落库实现），但子类常换 | 钩子 |

**钩子给多了会变成"配置项堆砌"**：如果一个基类有 8 个钩子、子类每次要覆写 6 个，那这个骨架的抽象层级就选错了 —— 应该退回来看是不是该用组合（见第五节）。

## 四、三个真实陷阱（都有实测）

### 陷阱 1：骨架里用 `self::` 调用步骤 → 子类覆写被吞掉

PHP 里 `self::` 是**编译期静态绑定**，`$this->` 才是运行时绑定。骨架方法里一个不留神写下 `self::step()`，所有子类的覆写都会静默失效：

```text
1_self::step()  → base  （期望 sub，实际不是 → 覆写被吞掉）
2_$this->step() → sub  （期望 sub）
```

**不报错、不告警、测试也不一定发现**（因为它只是"行为不对"）。PHP 里还有 `static::`（后期静态绑定），三者关系：

| 写法 | 绑定时机 | 用到哪个实现 |
| --- | --- | --- |
| `self::step()` | 编译期 | 永远是**定义骨架的那个类**的方法 |
| `$this->step()` | 运行期 | 实际对象的类的方法（**模板方法要用这个**） |
| `static::step()` | 运行期 | 实际对象的类；用于静态方法场景 |

### 陷阱 2：父类构造器里调用可覆写方法

这是模板方法的"经典误用"—— 把 `$this->init()` 放进父类构造器，看起来很像模板方法，实际依赖"子类字段何时被赋值"：

```text
8_PHP（父类构造器先跑）  : 抛 Error：Typed property CtorChildFirst::$value must not be accessed before initialization
9_PHP（字段有默认值）    : 拿到 name=ready
```

Java 侧同样结构的表现：

```text
9_Java：父类构造器拿到的值 = null（value 字段此刻还是 null）
10_Java：子类构造完成后再取值 = ready（此时才是 ready）
```

| 语言 | 父类构造器里读子类字段 |
| --- | --- |
| PHP | typed property 未初始化就读取 → **抛 `Error`**（响亮地失败）；无类型属性则是 `null` |
| Java | 字段初始化在 `super()` **之后** → **静默 `null`**（更危险，可能到别处才 NPE） |
| Go | 无继承构造链，**问题不存在** |

两个结论：**构造器里不要调用可覆写方法**；这条在 Java 里比 PHP 更阴险（PHP 至少抛错）。

### 陷阱 3：忘记给骨架加 `final`

PHP 里子类可以覆写任何非 `final` 的 `public` / `protected` 方法。骨架不加 `final`，子类一句 `public function import()` 就能把顺序整体改掉 —— 而模板方法的全部意义就在顺序。Java 同理（`final` 是 Java 里更常见的写法，因为不带 `final` 的模板方法在《Effective Java》里被直接点名是设计缺陷）。

## 五、边界：模板方法 vs 策略

这是最常被混的一对，因为**两者都在解决"同一流程、不同实现"**：

| | 模板方法 | 策略 |
| --- | --- | --- |
| 复用手段 | **继承**（父类定骨架） | **组合**（持有接口，可替换） |
| 变化点个数 | 多个步骤 | 一个算法 |
| 何时确定 | 编译/加载时（由类决定） | **运行时**（由调用方决定） |
| 顺序控制 | 骨架强制 | 调用方自己保证 |
| 典型代价 | 继承耦合、类数爆炸（每种组合一个子类） | 需要调用方知道有哪些策略 |

**一句话判据**：要"**换算法**"用策略，要"**定顺序**"用模板方法。两者也常同时出现 —— 骨架的某个步骤本身就是一个策略：

```php
abstract class DataImporter
{
    public function __construct(private Formatter $formatter) {}   // 骨架 + 策略

    final public function import(): ImportReport { /* ... $this->formatter->format($row) ... */ }
}
```

**现代 PHP 更倾向组合**。同一个骨架用闭包数组也能实现（实测里第 3 行就是这个版本，输出与继承版逐行一致）：

```php
/** 组合版：不继承也能复用同一骨架（把步骤当参数传进来） */
final class PipelineImporter
{
    /**
     * @param array{
     *     open: Closure,
     *     readRow: Closure,
     *     close: Closure,
     *     shouldImport?: Closure,
     *     normalize?: Closure,
     *     persist?: Closure
     * } $steps
     */
    public function __construct(private array $steps) {}

    public function import(): ImportReport
    {
        $report = new ImportReport();
        ($this->steps['open'])();
        $read = $this->steps['readRow'];
        while (($row = $read()) !== null) {
            $report->total++;
            $shouldImport = $this->steps['shouldImport'] ?? static fn (array $r): bool => true;
            if (!$shouldImport($row)) {
                $report->skipped++;
                continue;
            }
            $normalize = $this->steps['normalize'] ?? static fn (array $r): array => $r;
            $persist = $this->steps['persist']
                ?? static function (array $r): void {
                    echo '    落库 ', json_encode($r, JSON_UNESCAPED_UNICODE), PHP_EOL;
                };
            $persist($normalize($row));
            $report->imported++;
        }
        ($this->steps['close'])();

        return $report;
    }
}
```

**那什么时候仍该用继承版？**

| 选继承版（模板方法） | 选组合版（闭包 / 策略） |
| --- | --- |
| 骨架很长、步骤多，且**有明确的领域概念**（"导入器"本身是个实体） | 骨架短，或步骤是临时拼的 |
| 希望子类**共享**基类提供的小工具方法 | 步骤之间无共享状态 |
| 需要 IDE 的类型提示与静态分析 | 爱用函数式风格 |
| 步骤组合固定、数量有限 | 组合会运行时变化 |

## 六、Java / Go 实现

### Java 实现

Java 是模板方法的"母语"：`abstract class` + `final` 方法原样对应。

```java
/** 抽象类：把「导入」的骨架固定下来，把变化点交给子类 */
abstract static class DataImporter {

    /** 模板方法本身：final 保证子类不能改写骨架 */
    final ImportReport importAll() {
        ImportReport report = new ImportReport();
        open();                                     // 抽象步骤
        Map<String, String> row;
        while ((row = readRow()) != null) {         // 抽象步骤
            report.total++;
            if (!shouldImport(row)) {                // 钩子（有默认实现）
                report.skipped++;
                continue;
            }
            persist(normalize(row));                 // 钩子 + 钩子
            report.imported++;
        }
        close();                                     // 抽象步骤

        return report;
    }

    protected abstract void open();

    /** @return null 表示读完 */
    protected abstract Map<String, String> readRow();

    protected abstract void close();

    protected boolean shouldImport(Map<String, String> row) { return true; }

    protected Map<String, String> normalize(Map<String, String> row) { return row; }

    protected void persist(Map<String, String> row) { /* 默认落库 */ }
}
```

**使用示例**：

```java
// 子类只实现抽象步骤，顺序由父类的 final 骨架 importAll() 固定
String csv = "张三, 研发, Zhang@Example.com\n李四, 研发, li@example.com\n王五, 运营, ";
ImportReport report = new CsvImporter(csv).importAll();
System.out.println(report.describe());   // 共 3 行，导入 2 行，跳过 1 行（王五没邮箱）
System.out.println(report.total);        // 3
System.out.println(report.skipped);      // 1

// 换来源 = 换子类，骨架一行不改
String json = "[{\"name\":\"赵六\",\"dept\":\"市场\",\"email\":\"ZHAO@Example.com\"}]";
new JsonImporter(json).importAll();      // JsonImporter 覆写了 normalize，邮箱转小写
```

JDK 1.8 实测输出与 PHP 版逐行一致：

```text
1_CSV 导入       : 共 3 行，导入 2 行，跳过 1 行
2_JSON 导入      : 共 2 行，导入 2 行，跳过 0 行
3_骨架是 final 吗 : true
4_钩子是抽象的吗  : false（false=有默认实现，子类可选覆写）
```

Java 里的教科书案例是 **`HttpServlet#service()`**：`service()` 先按 HTTP 方法分派到 `doGet` / `doPost`，那几个 `doXxx` 就是抽象步骤 —— 骨架固定"先分派再处理"，子类只填具体方法。同类的还有 `AbstractList`（子类实现 `get` / `size`，`iterator` / `indexOf` 全部由骨架提供）、`InputStream#read(byte[])`（默认循环调用抽象方法 `read()`）。

### Go 实现

Go 没有继承，**模板方法退化成"接收接口参数的普通函数"**：

```go
// Importer 抽象步骤：Go 没有继承，用接口表达「子类必须填什么」
type Importer interface {
	Open()
	ReadRow() (row map[string]string, ok bool)
	Close()
}

// 钩子用可选接口表达：实现了就被调用，没实现就用默认行为。
// 这是 Go 里做「可覆写钩子」的标准手法（如 http.Flusher、io.ReaderFrom）。
type skipper interface {
	ShouldImport(row map[string]string) bool
}

type normalizer interface {
	Normalize(row map[string]string) map[string]string
}

// Import 模板方法：骨架固定，步骤由 Importer 提供
func Import(src Importer) ImportReport {
	report := ImportReport{}
	src.Open()
	for {
		row, ok := src.ReadRow()
		if !ok {
			break
		}
		report.Total++
		if s, ok := src.(skipper); ok && !s.ShouldImport(row) { // 钩子：默认全要
			report.Skipped++
			continue
		}
		if n, ok := src.(normalizer); ok { // 钩子：默认不改
			row = n.Normalize(row)
		}
		persist(row)
		report.Imported++
	}
	src.Close()

	return report
}
```

**使用示例**：

```go
// 骨架是自由函数：传入实现了 Importer 的具体来源
csv := "张三, 研发, Zhang@Example.com\n李四, 研发, li@example.com\n王五, 运营, "
report := Import(NewCsvImporter(csv))
fmt.Println(report.Describe())   // 共 3 行，导入 2 行，跳过 1 行（王五没邮箱）
fmt.Println(report.Total)        // 3
fmt.Println(report.Skipped)      // 1

// 换来源 = 换实现：JsonImporter 覆写 Normalize 把邮箱转小写
Import(NewJsonImporter(`[{"name":"赵六","dept":"市场","email":"ZHAO@Example.com"}]`))
```

go1.26.5 实测输出（前两组与 PHP/Java 一致）：

```text
    落库 {"name":"张三","dept":"研发","email":"Zhang@Example.com"}
    落库 {"name":"李四","dept":"研发","email":"li@example.com"}
1_CSV 导入       : 共 3 行，导入 2 行，跳过 1 行

    落库 {"name":"赵六","dept":"市场","email":"zhao@example.com"}
    落库 {"name":"钱七","dept":"市场","email":"qian@example.com"}
2_JSON 导入      : 共 2 行，导入 2 行，跳过 0 行
```

Go 的三点差异：

- **骨架是自由函数，不是方法**。因为不能"父类调用子类"，只能"函数接收接口" —— 顺序照样固定，只是固定在一处而不是继承关系里；
- **抽象步骤 = 接口方法，钩子 = 可选接口**。`if s, ok := src.(skipper); ok` 这就是 Go 里的"可选覆写"，标准库里的 `http.Flusher` / `io.ReaderFrom` 都是这个套路；
- **`persist` 手写固定键序而不是 `json.Marshal(map)`**。Go 的 map 序列化键序无序，直接 Marshal 输出不稳定（这一点在 [../创建型/工厂模式.md](../创建型/工厂模式.md) 里也踩过）。

**结论**：Go 里"模板方法"不是模式，是**把算法骨架写成函数**的常规做法 —— 这反过来印证了一条：模板方法本质上是**继承语言缺少"把函数当参数"能力时的一种替代品**。

## 七、三语言对照

| | PHP | Java | Go |
| --- | --- | --- | --- |
| 骨架载体 | `abstract class` + `final` 方法 | `abstract class` + `final` 方法 | **自由函数** |
| 抽象步骤 | `abstract protected` | `protected abstract` | 接口方法 |
| 钩子 | 普通方法 + 默认实现 | 普通方法 + 默认实现 | **可选接口 + 类型断言** |
| 防改写 | 加 `final` | 加 `final` | 无需（函数不可覆写） |
| 调用步骤 | 必须用 `$this->`（`self::` 会吞掉覆写） | 普通虚方法调用 | 接口方法调用 |
| 构造器陷阱 | typed property 未初始化 → 抛 `Error` | 字段在 `super()` 后初始化 → **静默 null** | 无继承构造链，不存在 |
| 生态代表 | `ArrayIterator`、`Illuminate\Console\Command`、`Symfony AbstractController` | `HttpServlet#service`、`AbstractList`、`InputStream#read` | `database/sql` 驱动、`sort.Interface` 的排序函数 |

## 八、面试官会追问什么

- **模板方法的核心价值是什么？** → 不是"复用代码"，而是**固定顺序**。复用可以用组合拿到，但"骨架不许被改写"只有模板方法能保证 —— 这也是骨架必须加 `final` 的原因。
- **抽象方法和钩子怎么区分？** → 看有没有合理默认值。有默认 → 钩子（可选覆写）；没有 → 抽象方法。**钩子给太多说明抽象层级选错了**。
- **和策略模式的区别？** → 模板方法用继承、由类决定变化点、**强制顺序**；策略用组合、运行时替换、不控制顺序。实践中常组合使用：骨架的某个步骤注入一个策略。
- **PHP 里用 `self::` 调用步骤方法会怎样？** → **子类的覆写静默失效**（`self::` 编译期绑定到定义处）。必须用 `$this->`。这是 PHP 相对 Java 多出来的坑。
- **为什么不要在构造器里调用可覆写方法？** → 子类字段可能还没初始化。Java 里静默拿到 `null`（可能到别处才 NPE），PHP 的 typed property 会抛 `Error`（更早暴露）。
- **Go 里怎么实现模板方法？** → 不用实现——**把骨架写成接收接口的函数**即可。Go 没有继承，这反而更直白。这也说明模板方法是继承语言的"补偿机制"。
- **这个模式什么时候不该用？** → 步骤组合会运行时变化时（该用策略/管道），或子类要覆写的钩子超过一半时（继承层次搭错了）。**"香蕉带丛林"** 的经典批评就在这里。
- **PHP 框架里哪里有？** → `Illuminate\Console\Command`（骨架负责解析参数、调用 `handle()`）、Symfony 的 `AbstractController`、各类 `AbstractMigration` 的 `up()` / `down()`。
