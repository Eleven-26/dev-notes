## 一、解释器解决什么问题

解释器（Interpreter）属于行为型模式：**给定一个语言，定义它的文法表示，并定义一个解释器来解释其中的句子**。

说人话：**把"一串规则字符串"变成一棵对象树，然后对这棵树求值**。

它要解决的是"**规则需要由非程序员在运行时配置**"：

| 需求 | 没有解释器时 |
| --- | --- |
| 风控规则、促销条件由运营配置 | 只能做成表单字段（"金额大于 ___ 且 等级是 ___"），表达能力受限 |
| 规则要能组合（AND / OR / NOT / 括号） | 表单装不下，只能开发硬编码 |
| 规则要能改而不发版 | 代码写死的条件改不了 |
| 用 `eval()` 求值 | **绝对不要** —— 注入风险、无法审计、调试噩梦（见第四节） |

两个角色概念（先建立，再看代码就不会晕）：

| 概念 | 含义 | 本篇对应 |
| --- | --- | --- |
| **抽象表达式** | 所有节点共同的接口（`interpret()`） | `Expression` |
| **终结符表达式** | 文法的最末端，不再包含子表达式 | `Comparison`（`age > 18` 是一个整体，到头了） |
| **非终结符表达式** | 由子表达式组合而成 | `AndExpression` / `OrExpression` / `NotExpression` |
| **上下文（Context）** | 解释时用到的外部信息 | `Context`（变量表） |

⭐ **解释器模式本质上是一个"复合模式"**：它把 [组合模式](../结构型/组合模式.md)（树形结构）+ 每个节点一个小类（类似 [策略模式](策略模式.md)）拼在一起，用递归完成求值。

## 二、PHP 标准实现

场景：**迷你规则引擎**（风控条件、促销规则、查询过滤条件都由它求值）。

先约定文法（这一步是这个模式真正的"设计"）：

```text
expr    := or
or      := and ( "OR" and )*
and     := not ( "AND" not )*
not     := "NOT" not | primary
primary := "(" expr ")" | field op value
op      := "=" | "!=" | ">" | ">=" | "<" | "<="
value   := 数字 | true | false | "字符串"
```

**每一条产生式都会变成一个类** —— 这是理解这个模式的钥匙（第三节有完整对照表）。

```php
<?php

declare(strict_types=1);

/** 上下文：存放变量（解释时读它，而不是去查全局） */
final class Context
{
    /** @param array<string,mixed> $vars */
    public function __construct(private array $vars = []) {}

    public function get(string $name): mixed
    {
        if (!array_key_exists($name, $this->vars)) {
            throw new InvalidArgumentException("变量「{$name}」未定义");
        }

        return $this->vars[$name];
    }
}

/** 抽象表达式：所有节点都只回答一个问题 —— 在我这份上下文下成立吗 */
interface Expression
{
    public function interpret(Context $context): bool;

    /** 打印语法树（解释器模式本身不要求，这里为了演示结构） */
    public function describe(): string;
}

// ---------------- 非终结符表达式（有子节点） ----------------

final class AndExpression implements Expression
{
    public function __construct(
        private Expression $left,
        private Expression $right
    ) {}

    public function interpret(Context $context): bool
    {
        // PHP 的 && 天然短路：左边为 false 时右边不会被求值
        return $this->left->interpret($context) && $this->right->interpret($context);
    }

    public function describe(): string
    {
        return sprintf('(%s AND %s)', $this->left->describe(), $this->right->describe());
    }
}

final class OrExpression implements Expression
{
    public function __construct(
        private Expression $left,
        private Expression $right
    ) {}

    public function interpret(Context $context): bool
    {
        return $this->left->interpret($context) || $this->right->interpret($context);
    }

    public function describe(): string
    {
        return sprintf('(%s OR %s)', $this->left->describe(), $this->right->describe());
    }
}

final class NotExpression implements Expression
{
    public function __construct(private Expression $inner) {}

    public function interpret(Context $context): bool
    {
        return !$this->inner->interpret($context);
    }

    public function describe(): string
    {
        return sprintf('NOT %s', $this->inner->describe());
    }
}

// ---------------- 终结符表达式（文法的最末端） ----------------

final class Comparison implements Expression
{
    public function __construct(
        private string $field,
        private string $operator,
        private mixed $value
    ) {}

    public function interpret(Context $context): bool
    {
        $actual = $context->get($this->field);

        return match ($this->operator) {
            '=' => $actual == $this->value,
            '!=' => $actual != $this->value,
            '>' => $actual > $this->value,
            '>=' => $actual >= $this->value,
            '<' => $actual < $this->value,
            '<=' => $actual <= $this->value,
            default => throw new LogicException("未知操作符「{$this->operator}」"),
        };
    }

    public function describe(): string
    {
        return sprintf('%s %s %s', $this->field, $this->operator, json_encode($this->value));
    }
}
```

解析部分（**注意：解析器不属于解释器模式**，它是把字符串变成树的前置步骤）：

```php
final class Tokenizer
{
    /** @return list<string> */
    public static function tokenize(string $input): array
    {
        preg_match_all(
            '/\(|\)|>=|<=|!=|[=<>]|[A-Za-z_][A-Za-z0-9_]*|-?\d+(?:\.\d+)?|"[^"]*"/',
            $input,
            $matches
        );

        return $matches[0];
    }
}

/** 递归下降解析器：把字符串变成表达式树（解析器本身不属于解释器模式） */
final class Parser
{
    /** @var list<string> */
    private array $tokens;
    private int $pos = 0;

    public function __construct(string $input)
    {
        $this->tokens = Tokenizer::tokenize($input);
    }

    public function parse(): Expression
    {
        $expression = $this->parseOr();
        if ($this->peek() !== null) {
            throw new InvalidArgumentException('表达式末尾有多余内容：「' . $this->peek() . '」');
        }

        return $expression;
    }

    private function parseOr(): Expression
    {
        $left = $this->parseAnd();
        while ($this->accept('OR')) {
            $left = new OrExpression($left, $this->parseAnd());
        }

        return $left;
    }

    private function parseAnd(): Expression
    {
        $left = $this->parseNot();
        while ($this->accept('AND')) {
            $left = new AndExpression($left, $this->parseNot());
        }

        return $left;
    }

    private function parseNot(): Expression
    {
        if ($this->accept('NOT')) {
            return new NotExpression($this->parseNot());
        }

        return $this->parsePrimary();
    }

    private function parsePrimary(): Expression
    {
        if ($this->accept('(')) {
            $inner = $this->parseOr();
            if (!$this->accept(')')) {
                throw new InvalidArgumentException('缺少右括号');
            }

            return $inner;
        }

        $field = $this->next();
        $operator = $this->next();
        $value = $this->next();
        if ($field === null || $operator === null || $value === null) {
            throw new InvalidArgumentException('比较表达式不完整');
        }

        return new Comparison($field, $operator, self::literal($value));
    }

    private function peek(): ?string
    {
        return $this->tokens[$this->pos] ?? null;
    }

    private function next(): ?string
    {
        $token = $this->peek();
        if ($token !== null) {
            $this->pos++;
        }

        return $token;
    }

    private function accept(string $token): bool
    {
        if ($this->peek() === $token) {
            $this->pos++;

            return true;
        }

        return false;
    }

    private static function literal(string $token): mixed
    {
        if (preg_match('/^-?\d+$/', $token)) {
            return (int) $token;
        }
        if (preg_match('/^-?\d+\.\d+$/', $token)) {
            return (float) $token;
        }
        if ($token === 'true') {
            return true;
        }
        if ($token === 'false') {
            return false;
        }

        return trim($token, '"');    // 带引号的字符串
    }
}
```

**使用示例**：

```php
// 解析一次：字符串 → 表达式树（Parser 是前置步骤，不属于解释器模式）
$expression = (new Parser('age > 18 AND (vip = true OR amount > 1000)'))->parse();

// 树的形状：括号被吸收进结构里
$expression->describe();     // (age > 18 AND (vip = true OR amount > 1000))

// 求值多次：换一份 Context 就换一套变量，树不必重建
$expression->interpret(new Context(['age' => 25, 'vip' => true, 'amount' => 500]));   // true
$expression->interpret(new Context(['age' => 16, 'vip' => true, 'amount' => 500]));   // false

// 变量缺失会抛异常（Context::get 里检查）
$expression->interpret(new Context(['age' => 25]));   // 抛 InvalidArgumentException
```

实测（PHP 8.0.2 CLI）：

```text
1_规则            : age > 18 AND (vip = true OR amount > 1000)
2_语法树          : (age > 18 AND (vip = true OR amount > 1000))

3.1_{"age":25,"vip":false,"amount":500}        → 拒绝
3.2_{"age":25,"vip":true,"amount":500}         → 通过
3.3_{"age":16,"vip":true,"amount":500}         → 拒绝
3.4_{"age":30,"vip":false,"amount":2000}       → 通过

4_规则            : NOT status = "banned"
5_语法树          : NOT status = "banned"
6_正常用户        : 通过
7_被封禁用户      : 拒绝

8_短路验证        : 拒绝（右侧变量不存在，但左侧已为 false）

9_非法表达式      : age >          → 比较表达式不完整
9_非法表达式      : age > 18 AND   → 比较表达式不完整
9_非法表达式      : (age > 18      → 缺少右括号
```

五个要点：

- **第 2 行是"解释器模式"最直观的产出**：字符串变成了树。括号被"吸收"进结构里（`describe()` 无脑加括号，输出恰好还原了优先级），**求值时不再需要关心括号**；
- **第 3.1~3.4 行是同一个表达式在四份上下文下的结果**。规则只解析一次（第 2 行），求值四次 —— **解析成本与求值成本分离**，这是把它做成对象而不是每次 `eval()` 的关键收益；
- **第 8 行暴露一个真实风险**：`age > 18 AND undefined_field > 0` 在 `age = 16` 时**因为短路而没有报"变量未定义"**。短路是性能也是陷阱 —— **规则的错误可能被掩盖到某个数据出现时才炸**。生产环境应在解析后**做一次变量存在性校验**，而不是依赖运行时抛错；
- **第 9 行是解析器的价值**：非法规则在**加载时**就报错（"比较表达式不完整" / "缺少右括号"），而不是运行到一半才炸。**规则配置类系统必须在保存时就校验**；
- **整个实现里没有一个 `eval()`**。

### 让它算「标准写法」的 5 个细节

| # | 做法 | 为什么 |
| --- | --- | --- |
| 1 | **先写文法，再写类** | 文法里每一条产生式对应一个类；不先定文法，类会写得毫无章法 |
| 2 | 变量通过 `Context` 传入，**不读全局** | 同一个表达式要能在不同数据上求值；读全局就没法复用、没法测试 |
| 3 | **拒绝 `eval()`** | 注入风险 + 无法审计 + 无法静态分析。这是本模式存在的根本理由之一 |
| 4 | **解析与求值分层** | 解析一次、求值多次；规则可在"保存时"校验、"运行时"复用（第 2 行 vs 第 3 组） |
| 5 | 未定义变量**显式抛错**，不静默当 `false` | 静默 `false` 会让规则的错误无声无息（且会被短路掩盖） |

## 三、文法 → 类的对照关系

这是本模式最机械、也最有价值的一张表 —— **写完文法，类就定完了**：

| 文法产生式 | 类型 | 对应类 | 子节点数 |
| --- | --- | --- | --- |
| `expr := or` | 非终结符 | —（直接转发） | 1 |
| `or := and ( "OR" and )*` | 非终结符 | `OrExpression` | 2（左结合，多个 OR 会嵌套） |
| `and := not ( "AND" not )*` | 非终结符 | `AndExpression` | 2 |
| `not := "NOT" not \| primary` | 非终结符 | `NotExpression` | 1 |
| `primary := "(" expr ")"` | — | 括号**不产生类**，它只影响树的形状 | — |
| `field op value` | 终结符 | `Comparison` | 0 |

两条经验：

1. **括号不需要类**。它的作用是改变树的形状（把子表达式抬高一层），求值阶段完全感知不到它 —— 这也解释了为什么"解析器不属本模式"；
2. **优先级 = 文法的层数**。`or` 在最外层、`not` 在最内层，所以 `NOT` 绑定最紧、`OR` 最松。**改优先级就是调整产生式顺序**，不用改任何节点类。

## 四、实用边界：什么时候**别**写解释器

GoF 原书对这个模式的评价是**唯一带明确警告**的：它适用于"**文法简单**"的场景，文法一复杂，类的数量就会爆炸。

| 文法复杂度 | 建议 |
| --- | --- |
| 几个操作符 + 括号（如本篇） | ✅ 手写解释器（约 250 行搞定，还能顺便做出漂亮的错误提示） |
| 十几条产生式（表达式 + 函数调用 + 数组下标） | ⚠️ 手写开始吃力，考虑用现成的表达式库 |
| 有语法嵌套结构（JSON、SQL、模板语言、编程语言） | ❌ **别手写**。用解析器生成器（ANTLR / yacc / bison）或现成解析库 |

**判断标准是"类的数量"**：本模式的类数 ≈ 文法产生式数 × 2（终结符 + 非终结符）。当这个数字超过十几个，维护成本就开始高于"用解析器生成器"的学习成本。

三个现实建议：

| 场景 | 推荐做法 |
| --- | --- |
| 简单的条件表达式（风控、促销、查询过滤） | **用成熟库**：PHP 的 `symfony/expression-language`、Java 的 SpEL / Aviator、Go 的 `govaluate` |
| 只想"存一个条件" | **别发明语言**。用 JSON 结构化描述（`{"and":[{">":["age",18]}, ...]}`），连解析器都省了 |
| 真的需要自定义 DSL | 走**解析器生成器**路线，把"模式"交给工具的产物 |

**那这个模式还有用吗？有** —— 两个地方：

- **理解它的产物**：AST、编译器的前端、模板引擎、规则引擎，**全都在用它**。学会它，读这些框架的源码才有底气；
- **极小的文法**：正如本篇——250 行换来"规则可配置 + 错误提示友好 + 可复用"，比引入一个库更轻。**关键是知道自己停在哪一步**。

⚠️ **绝对不要用 `eval()` 替代**：

| | `eval()` | 解释器模式 |
| --- | --- | --- |
| 安全 | **任意代码执行**（配置被篡改 = 服务器沦陷） | 只能表达已定义的文法 |
| 校验 | 无法在保存时校验 | 解析阶段就能报错 |
| 调试 | 无从下手 | 树可以打印、可以单步 |
| 性能 | 每次都要编译 | **解析一次、求值多次** |

## 五、Java / Go 实现

### Java 实现

```java
/** 抽象表达式：所有节点都只回答一个问题 —— 在我这份上下文下成立吗 */
interface Expression {
    boolean interpret(Context context);

    String describe();
}

static final class AndExpression implements Expression {
    private final Expression left;
    private final Expression right;

    AndExpression(Expression left, Expression right) {
        this.left = left;
        this.right = right;
    }

    /** Java 的 && 天然短路：左边为 false 时右边不会被求值 */
    public boolean interpret(Context context) {
        return left.interpret(context) && right.interpret(context);
    }

    public String describe() {
        return String.format("(%s AND %s)", left.describe(), right.describe());
    }
}

static final class Comparison implements Expression {
    private final String field;
    private final String operator;
    private final Object value;

    public boolean interpret(Context context) {
        return compare(context.get(field), operator, value);
    }

    private static boolean compare(Object actual, String op, Object expected) {
        if (actual instanceof Number && expected instanceof Number) {
            double a = ((Number) actual).doubleValue();
            double b = ((Number) expected).doubleValue();
            switch (op) {
                case "=": return a == b;
                case ">": return a > b;
                // ...
                default: throw new IllegalStateException("未知操作符「" + op + "」");
            }
        }
        switch (op) {
            case "=": return String.valueOf(actual).equals(String.valueOf(expected));
            case "!=": return !String.valueOf(actual).equals(String.valueOf(expected));
            default: throw new IllegalStateException("非数值不支持操作符「" + op + "」");
        }
    }
}
```

**使用示例**：

```java
// 解析一次：字符串 → 表达式树（Parser 是前置步骤，不属于解释器模式）
Expression expression = new Parser("age > 18 AND (vip = true OR amount > 1000)").parse();
System.out.println(expression.describe());   // (age > 18 AND (vip = true OR amount > 1000))

// 求值多次：换一份 Context 就换一套变量，树不必重建
Map<String, Object> vars = new HashMap<String, Object>();
vars.put("age", 25); vars.put("vip", true); vars.put("amount", 500);
expression.interpret(new Context(vars));     // true

// 变量缺失会抛异常（Context::get 里检查）
expression.interpret(new Context(new HashMap<String, Object>()));   // 抛 IllegalArgumentException
```

JDK 1.8 实测输出与 PHP 版逐行一致。Java 侧的三点差异：

- **`Object` + `instanceof Number` 是 Java 里做动态比较的常规手段**。JDK 8 没有模式匹配，只能强转；**JDK 17+ 可用 `instanceof` 模式匹配**（`if (actual instanceof Number n)`）省掉强转；
- **生态里成熟库很多**：**SpEL**（Spring Expression Language）几乎就是这个模式的产品化版本 —— `ExpressionParser` + `EvaluationContext` 与本篇的 `Parser` + `Context` 一一对应；
- **Java 的注解处理器（APT）是另一个"解释器"**：它把源码解析成 AST，再遍历求值生成代码。

### Go 实现

```go
// Expression 抽象表达式：所有节点都只回答一个问题 —— 在我这份上下文下成立吗
type Expression interface {
	Interpret(*Context) (bool, error)

	Describe() string
}

// AndExpression 与
type AndExpression struct{ Left, Right Expression }

// Interpret 短路：左边为 false 时不求值右边
func (e AndExpression) Interpret(c *Context) (bool, error) {
	left, err := e.Left.Interpret(c)
	if err != nil {
		return false, err
	}
	if !left {
		return false, nil
	}

	return e.Right.Interpret(c)
}

// Describe 打印
func (e AndExpression) Describe() string {
	return fmt.Sprintf("(%s AND %s)", e.Left.Describe(), e.Right.Describe())
}
```

**使用示例**：

```go
// 解析一次：字符串 → 表达式树（Parser 是前置步骤，不属于解释器模式）
expression, err := NewParser("age > 18 AND (vip = true OR amount > 1000)").Parse()
if err != nil {
	panic(err) // 语法错误：比较表达式不完整 / 缺少右括号
}
expression.Describe() // (age > 18 AND (vip = true OR amount > 1000))

// 求值多次：换一份 Context 就换一套变量，树不必重建
expression.Interpret(NewContext(map[string]any{"age": 25, "vip": true, "amount": 500})) // true
expression.Interpret(NewContext(map[string]any{"age": 16, "vip": true, "amount": 500})) // false
```

go1.26.5 实测输出（与 PHP/Java 一致）。

Go 侧的两点差异，都源于"**Go 没有异常**"：

- **`interpret` 返回 `(bool, error)`，错误逐层向上传递**：
  ```go
  left, err := e.Left.Interpret(c)
  if err != nil {
      return false, err
  }
  ```
  好处是**错误不会跳过任何一层**（必须显式处理）；代价是每个节点都要写四行样板。PHP/Java 用异常则自动向上冒泡；
- **短路必须手写**。PHP/Java 的 `&&` 自带短路，而 Go 里"先说左边、false 就返回"是显式的控制流 —— **这反而更清楚**：短路是行为，不是运算符的附带效果。

另外：Go 的 `map` 遍历随机，所以**实测里打印变量时手写了固定键序**（`varsJSON`）—— 这一点在 [../创建型/工厂模式.md](../创建型/工厂模式.md) 里也踩过。

## 六、三语言对照

| | PHP | Java | Go |
| --- | --- | --- | --- |
| 抽象表达式 | `interface` | `interface` | `interface` |
| 求值失败 | 抛异常（自动冒泡） | 抛异常（自动冒泡） | **返回 `error`（逐层传递）** |
| 短路 | `&&` / `\|\|` 自带 | `&&` / `\|\|` 自带 | **手写控制流** |
| 动态比较 | `==`（松散比较） | `Object` + `instanceof Number` | `any` + 类型断言 + helper |
| 上下文 | 对象 `Context` | 对象 `Context` | 结构体 `*Context` |
| 解析器 | 手写递归下降 / `symfony/expression-language` | 手写 / **SpEL、Aviator** | 手写 / `govaluate` |
| 生态代表 | Symfony ExpressionLanguage、Doctrine DQL 的 AST | SpEL、ANTLR、注解处理器 | `go/parser` + `go/ast`（Go 自己的编译器前端） |

**三语言共通**：这个模式的**成本与文法大小成正比**，与语言无关。**先看文法复杂度，再决定手写还是用库** —— 这是它区别于其它模式的地方（其它模式基本"总是值得用"，这个不是）。

## 七、面试官会追问什么

- **解释器模式解决了什么问题？** → 让**非程序员在运行时配置规则**成为可能：把规则字符串解析成一棵对象树，求值时递归解释。**核心价值是"规则可配置 + 可校验 + 可复用"，而不是"能算表达式"**（算表达式直接写代码更快）。
- **它的结构本质是什么？** → **组合模式 + 每个节点一个小类**：树形结构用组合，每个节点用一小段 `interpret()` 表达"我在什么条件下为真"。所以它是"复合模式"的典型。
- **为什么要双分派…不对，为什么会有一大堆类？** → 因为**文法里每一条产生式都对应一个类**。这也是它最大的缺点：文法一复杂，类就爆炸。
- **什么时候不该用它？** → **文法超过十几条产生式时**。GoF 原书明确警告过这点。这时应该用解析器生成器（ANTLR / yacc），或者直接换现成表达式库（PHP 的 `symfony/expression-language`、Java 的 SpEL、Go 的 `govaluate`）。
- **为什么不用 `eval()`？** → 三条硬理由：① **安全**（配置被篡改等于任意代码执行）；② **无法在保存时校验**；③ **无法审计与调试**。而解释器模式的文法是你自己定义的，能表达的范围完全可控。
- **解析和求值能分开吗？** → **必须分开**，而且这是它的关键收益：**解析一次、求值多次**。本篇实测里规则只解析了一次（第 2 行），然后在四份上下文上求值（第 3.1~3.4 行）。规则类系统还应在**保存时**就解析+校验（第 9 行那三个错误提示）。
- **短路是好事还是坏事？** → 两者都是。它是性能优化，但会**掩盖错误**：实测第 8 行 `age > 18 AND undefined_field > 0` 在 `age = 16` 时没报"变量未定义"。**生产上应该在解析后做一次变量存在性校验**，别指望运行时抛错。
- **PHP 里哪里有它？** → Symfony 的 ExpressionLanguage（路由约束、安全表达式、依赖注入的条件配置都是它）、Doctrine DQL 的 AST、各类模板引擎（Twig 的表达式部分）。**它们全都不是手写的**，都是用成熟的解析器/库 —— 这也印证了第四节那条边界。
- **和访问者模式什么关系？** → 两者常配对：**解释器负责"求值"，访问者负责"对 AST 做别的操作"**（打印、优化、类型检查、代码生成）。把 `describe()` 抽出去变成一个 `Visitor` 就是标准做法。
