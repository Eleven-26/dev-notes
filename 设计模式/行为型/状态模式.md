## 一、状态模式解决什么问题

状态模式（State）属于行为型模式：**把"每种状态下允许什么操作、以及操作后转移到哪个状态"封装进状态类**，让对象的行为随内部状态改变而改变，而调用方的写法完全不变。

它要解决的是"**一个对象的行为被一堆状态判断淹没**"：

```php
// 没有状态模式：每个方法开头都是一段状态检查
public function pay(): void
{
    if ($this->status === '待支付') {
        $this->status = '已支付';
    } elseif ($this->status === '已支付') {
        throw new LogicException('已支付，不能重复支付');
    } elseif ($this->status === '已取消') {
        throw new LogicException('已取消，不能支付');
    }
    // ... 还有 ship() / cancel() / confirm()，每个都来一遍
}
```

三个毛病：**状态列表散落在每个方法里**（加一个状态要改所有方法）、**转移规则看不出来**（得把所有 `if` 读一遍才能画出状态图）、**每个状态自己的措辞/数据没地方放**。

状态模式把这张表竖过来切：**一个状态一个类，每个类只回答"在我这个状态下，各个操作该怎么办"**。

四个角色：

| 角色 | 职责 | 本篇对应 |
| --- | --- | --- |
| Context | 持有当前状态，把操作委托出去 | `Order` |
| State | 声明所有操作 | `OrderState` |
| ConcreteState | 每个状态下各操作的行为 + 转移到哪 | `PendingPayment` / `Paid` / `Shipped` / … |
| 转移 | 由**状态自己**触发 | `$order->transitionTo(new Paid())` |

**关键在最后一行**：状态的转移是**状态对象自己决定的**，不是 Context 决定的。这条正是状态模式与策略模式的分水岭（见第五节）。

## 二、PHP 标准实现

场景：**订单状态机**（待支付 → 已支付 → 已发货 → 已完成，任意前序状态可取消）。

```php
<?php

declare(strict_types=1);

/** 订单：持有当前状态，并把操作委托给它 */
final class Order
{
    private OrderState $state;

    public function __construct(
        private string $id,
        ?OrderState $state = null
    ) {
        $this->state = $state ?? new PendingPayment();
    }

    public function stateName(): string
    {
        return $this->state->name();
    }

    public function pay(): void
    {
        $this->state->pay($this);
    }

    public function ship(): void
    {
        $this->state->ship($this);
    }

    public function confirm(): void
    {
        $this->state->confirm($this);
    }

    public function cancel(): void
    {
        $this->state->cancel($this);
    }

    /** 供状态对象回调，完成转移（状态自己决定转移到哪，Order 只负责记录） */
    public function transitionTo(OrderState $next): void
    {
        printf("    %s: %s → %s\n", $this->id, $this->state->name(), $next->name());
        $this->state = $next;
    }
}

/**
 * 抽象状态：默认所有操作都非法，子类只覆写自己允许的那几个。
 * （这本身就是模板方法思路：基类给出统一骨架与默认行为）
 */
abstract class OrderState
{
    abstract public function name(): string;

    public function pay(Order $order): void
    {
        $this->reject('支付');
    }

    public function ship(Order $order): void
    {
        $this->reject('发货');
    }

    public function confirm(Order $order): void
    {
        $this->reject('签收');
    }

    public function cancel(Order $order): void
    {
        $this->reject('取消');
    }

    /** 拒绝的措辞由状态自己给出 —— 调用方不需要知道"为什么不行" */
    protected function reject(string $action): void
    {
        throw new LogicException(sprintf('当前状态「%s」不允许「%s」', $this->name(), $action));
    }

    /** 状态对象不带实例数据，因此可以安全共享（真实项目里状态要存库，不可能把对象序列化进去） */
    final public static function shared(string $class): self
    {
        /** @var array<class-string,self> $pool */
        static $pool = [];
        $pool[$class] ??= new $class();

        return $pool[$class];
    }
}
```

五个具体状态，每个只写自己允许的操作：

```php
final class PendingPayment extends OrderState
{
    public function name(): string
    {
        return '待支付';
    }

    public function pay(Order $order): void
    {
        $order->transitionTo(new Paid());
    }

    public function cancel(Order $order): void
    {
        $order->transitionTo(new Cancelled());
    }
}

final class Paid extends OrderState
{
    public function name(): string
    {
        return '已支付';
    }

    public function ship(Order $order): void
    {
        $order->transitionTo(new Shipped());
    }

    /** 已支付未发货 → 可以取消（退款） */
    public function cancel(Order $order): void
    {
        $order->transitionTo(new Cancelled());
    }
}

final class Shipped extends OrderState
{
    public function name(): string
    {
        return '已发货';
    }

    public function confirm(Order $order): void
    {
        $order->transitionTo(new Completed());
    }
}

/** 终态：什么都不能做，全部落到基类的 reject */
final class Completed extends OrderState
{
    public function name(): string
    {
        return '已完成';
    }
}

final class Cancelled extends OrderState
{
    public function name(): string
    {
        return '已取消';
    }
}
```

**使用示例**：

```php
// 调用方只调 Order 的方法，行为随当前状态改变
$order = new Order('SO-1001');
$order->stateName();          // 待支付

// 该状态不允许的操作由状态类抛异常
$order->ship();               // 抛 LogicException: 当前状态「待支付」不允许「发货」

// 允许的操作触发状态转移
$order->pay();                // SO-1001: 待支付 → 已支付
$order->ship();               // SO-1001: 已支付 → 已发货
$order->confirm();            // SO-1001: 已发货 → 已完成
```

实测（PHP 8.0.2 CLI）：

```text
1_初始状态        : 待支付
2_未支付就发货    : 拒绝：当前状态「待支付」不允许「发货」
3_支付            :
    SO-1001: 待支付 → 已支付
4_重复支付        : 拒绝：当前状态「已支付」不允许「支付」
5_发货            :
    SO-1001: 已支付 → 已发货
6_发货后取消      : 拒绝：当前状态「已发货」不允许「取消」
7_签收            :
    SO-1001: 已发货 → 已完成
8_终态再取消      : 拒绝：当前状态「已完成」不允许「取消」

9_共享同一状态对象  : true
10_但状态不存实例数据: 订单表里存的是状态名「待支付」
```

值得看的几点：

- **第 3、5、7 行后的 `→` 是状态转移**。注意它是在状态类里被触发的（`$order->transitionTo(new Paid())`），不是 `Order` 自己判断"支付成功后该变成什么"；
- **第 2、4、6、8 行的拒绝措辞各不相同**，但都由状态类自己给出 —— `Order` 一个字都不用改；
- **第 8 行**：`Completed` 与 `Cancelled` 是**终态**，它们没有覆写任何操作，全部落到基类的 `reject`。这就是"抽象基类给默认实现"的价值：终态类的代码是零。

### 让它算「标准写法」的 5 个细节

| # | 做法 | 为什么 |
| --- | --- | --- |
| 1 | 抽象状态给出「**全部拒绝**」的默认实现，子类只覆写允许的 | 状态里"能做什么"通常只占少数，这样每个状态类的代码量 = 它能做的事的数量 |
| 2 | 转移由**状态自己**触发（`transitionTo`） | 转移规则与状态行为写在同一处，状态图一目了然；Context 不掺和 |
| 3 | 拒绝用**异常**而非返回 `false` | 非法操作是**程序 bug 或攻击**，不是正常业务分支；让它响亮地失败 |
| 4 | 拒绝消息包含"当前状态 + 操作名" | 日志里一眼能定位。**不要笼统写"操作不允许"** |
| 5 | 状态类**不带实例数据** | 因为状态要持久化到数据库（存名字），对象本身不参与持久化。这条直接决定了它们可以共享（见第四节） |

## 三、状态类 vs 表驱动状态机

状态模式不是唯一选择。**转移规则只是一张表时，用表就够了**：

```php
/** @var array<string,array<string,string>> 状态 → 操作 → 新状态 */
const TRANSITIONS = [
    '待支付' => ['pay' => '已支付', 'cancel' => '已取消'],
    '已支付' => ['ship' => '已发货', 'cancel' => '已取消'],
    '已发货' => ['confirm' => '已完成'],
    '已完成' => [],
    '已取消' => [],
];
```

实测输出与状态类版完全一致：

```text
3_表驱动·初始      : 待支付
4_表驱动·pay       : 待支付 → 已支付
5_表驱动·重复 pay  : 拒绝：当前状态「已支付」不允许「pay」
6_表驱动·ship      : 已支付 → 已发货
7_表驱动·发货后取消: 拒绝：当前状态「已发货」不允许「cancel」
```

**40 行 vs 200 行**，而且表能直接喂给前端画状态图。所以选型判据是：

| 用**表驱动** | 用**状态类** |
| --- | --- |
| 转移只取决于「当前状态 + 操作」两个变量 | 转移还要看**别的条件**（金额、用户等级、库存） |
| 状态无自己的数据 | 状态要携带数据（如"部分发货，已发 2 件"） |
| 不需要副作用（发通知、写日志） | 每个状态转移时要**做不同的事** |
| 想要"一份数据驱动前后端与文档" | 想要强类型、IDE 可跳转 |

**混用是常态**：主流程用表驱动（规则集中、易审计），少数有逻辑的状态用类。反过来的坑是 —— 一旦某个状态冒出"自己的数据"，表就会退化成"表里塞 JSON"，那时就该搬回状态类。

⚠️ PHP 8.1 之前不能给 `const` 加类型、也不能用 `enum`，所以状态名的合法值只能靠约定或 `SplEnum` 之类扩展来约束。**PHP 8.1+ 的 `enum` 可以让状态名 + 数据一次性拿到强类型**（本仓库验证环境只到 8.0.2，故未采用）。

## 四、三个实践要点

### 1. 状态对象能不能共享？

**能** —— 前提就是第二节第 5 条"状态类不带实例数据"。实测第 9、10 行：

```text
9_共享同一状态对象  : true
10_但状态不存实例数据: 订单表里存的是状态名「待支付」
```

三语言的做法不同：

| | 共享手段 | 实测 |
| --- | --- | --- |
| PHP | `static` 池（`OrderState::shared()`） | `true` |
| Java | 把状态做成 `enum` 常量（天然单例）或 `static final` 字段 | 每次 `new` 则是 `false` |
| Go | **空结构体**（`pendingPayment{}` 大小为 0，可直接比较） | `true` |

**但如果状态带数据就不能共享**。例如"部分发货"要记住已发件数，共享实例会串号 —— 这也正是"状态该不该带数据"的判断依据。

### 2. 状态**不持久化对象**，只存名字

数据库里存的是 `status = '已支付'` 这样的名字（或更稳的整型编码），**不是序列化的状态对象**。所以：

- 状态必须有**从名字恢复**的入口（工厂或映射表）；
- 状态类改名要跟着改数据（用整型编码 + 映射表更稳）；
- **不要**在状态类里放"只在当前请求内有效"的缓存数据 —— 它不属于状态。

### 3. 非法操作是异常还是返回值？

两种都能用，但**别混**：

| 方式 | 适用 | 代价 |
| --- | --- | --- |
| **抛异常**（本篇） | 调用方不该出现这种调用（编程错误 / 越权） | 调用方要 `try/catch`，或用全局异常处理器 |
| 返回结果对象 | 非法操作是**正常业务分支**（前端按钮状态不同步） | 调用方必须逐个判断，容易漏 |

判据：**这件事在正常业务里会发生吗**。"用户连点两次支付"会发生 → 更该把它当作"幂等/去重"来处理；"已取消的订单调发货"不会正常发生 → 抛异常。

## 五、边界：状态 vs 策略

这两个模式**结构几乎一样**（Context 持有一个接口、把调用委托出去），差别全在语义：

| | 状态 | 策略 |
| --- | --- | --- |
| 谁决定切换 | **状态对象自己**（知道下一个状态） | **调用方**（外部指定） |
| 状态之间有关系吗 | 有：一张**状态图** | 无：相互独立的算法 |
| 切换频率 | 随业务流程自动发生 | 通常一次（构造时注入） |
| 典型问题 | "这个操作现在能不能做" | "用哪种算法算" |
| 类之间的耦合 | 状态类**互相认识**（`PendingPayment` 里 `new Paid()`） | 策略之间**互不认识** |

**一句话判据**：**状态之间有"下一步"，策略之间没有。** 状态类之间是知道彼此的（这是刻意的），策略类之间必须互不依赖（否则就不叫"可替换"了）。

## 六、Java / Go 实现

### Java 实现

```java
/** 订单：持有当前状态，并把操作委托给它 */
static final class Order {
    private final String id;
    private OrderState state;

    Order(String id) {
        this.id = id;
        this.state = new PendingPayment();
    }

    void pay() { state.pay(this); }

    void ship() { state.ship(this); }

    void confirm() { state.confirm(this); }

    void cancel() { state.cancel(this); }

    /** 由状态对象回调，完成转移：状态自己决定去哪，Order 只负责记录 */
    void transitionTo(OrderState next) {
        System.out.printf("    %s: %s → %s%n", id, state.name(), next.name());
        state = next;
    }
}

/** 抽象状态：默认所有操作都非法，子类只覆写自己允许的那几个 */
abstract static class OrderState {
    abstract String name();

    void pay(Order order) { reject("支付"); }

    void ship(Order order) { reject("发货"); }

    void confirm(Order order) { reject("签收"); }

    void cancel(Order order) { reject("取消"); }

    private void reject(String action) {
        throw new IllegalStateException(String.format("当前状态「%s」不允许「%s」", name(), action));
    }
}
```

**使用示例**：

```java
// 新建订单：默认进入「待支付」状态
Order order = new Order("SO-1001");

// 能不能做，由当前状态自己决定；转移到哪儿，也由状态对象回填
order.pay();       // 待支付 → 已支付
order.ship();      // 已支付 → 已发货
order.confirm();   // 已发货 → 已完成

// 非法操作由状态类抛出，理由明确（终态什么都不允许）
try {
    order.cancel();
} catch (IllegalStateException e) {
    System.out.println(e.getMessage());   // 当前状态「已完成」不允许「取消」
}
```

JDK 1.8 实测输出与 PHP 版逐行一致。Java 侧的两点差异：

- **`enum` 是更地道的写法**。`enum OrderState { PENDING_PAYMENT, PAID, ... }` 实现接口，天然单例、可 `switch`、可序列化 —— 但一旦某个状态要带字段，就得回到 `abstract class`。**本篇用 `abstract class` 是为了与另外两个语言保持同构**；
  ```java
  // 实测第 9 行：每次 new 就不共享
  System.out.println("9_状态对象可共享   : " + (a == b) + "（false = 每次 new；改成 enum 常量即可共享且天然单例）");
  ```
- **状态机库很成熟**：Spring StateMachine、`squirrel-foundation`。它们把"转移表 + 动作 + 守卫（guard）"做成了配置，本质是"表驱动 + 状态类"的混合体。

### Go 实现

```go
// State 状态接口：每个状态自己决定「允许哪些操作」以及「转移到哪个状态」
type State interface {
	Name() string
	Pay(*Order) error
	Ship(*Order) error
	Confirm(*Order) error
	Cancel(*Order) error
}

// baseState 给出「全部拒绝」的默认实现，具体状态只覆写自己允许的操作。
// Go 没有抽象类，用「内嵌 + 覆写」达到同样效果。
type baseState struct{}

func (baseState) Pay(o *Order) error     { return reject(o, "支付") }
func (baseState) Ship(o *Order) error    { return reject(o, "发货") }
func (baseState) Confirm(o *Order) error { return reject(o, "签收") }
func (baseState) Cancel(o *Order) error  { return reject(o, "取消") }

// reject 拒绝的措辞由状态自己给出 —— 调用方不需要知道「为什么不行」
func reject(o *Order, action string) error {
	return fmt.Errorf("当前状态「%s」不允许「%s」", o.Current().Name(), action)
}

type pendingPayment struct{ baseState }

func (pendingPayment) Name() string        { return "待支付" }
func (pendingPayment) Pay(o *Order) error  { o.transitionTo(paid{}); return nil }
func (pendingPayment) Cancel(o *Order) error {
	o.transitionTo(cancelled{})

	return nil
}
```

**使用示例**：

```go
// 调用方只调 Order 的方法；非法转移返回 error，允许的返回 nil
o := NewOrder("SO-1001")
fmt.Println(o.Current().Name())   // 待支付
o.Ship()                          // error: 当前状态「待支付」不允许「发货」
o.Pay()                           // nil → 已支付
o.Ship()                          // nil → 已发货
o.Cancel()                        // error: 当前状态「已发货」不允许「取消」
```

go1.26.5 实测输出（与 PHP/Java 一致）：

```text
1_初始状态        : 待支付
2_未支付就发货    : 拒绝：当前状态「待支付」不允许「发货」
3_支付            :
    SO-1001: 待支付 → 已支付
...
9_状态对象可共享   : true（空结构体，可比较且无状态）
10_但状态不存实例数据: 订单表里存的是状态名「待支付」
```

Go 的两点差异：

- **用「内嵌空结构体 + 覆写」模拟抽象基类**：`type paid struct{ baseState }`。内嵌让 `paid` 免费获得另外三个操作的默认拒绝，只覆写 `Ship` / `Cancel`；
- **失败是值（`error`），不是异常**。`Pay` 返回 `error` 后，调用方必须显式处理 —— 这与 PHP/Java 的异常语义不同：Go 里"忘了处理"至少会有"未使用的返回值"这种提醒（配合 `errcheck` 之类的静态检查）。**"非法状态转移"在 Go 里也常被设计成返回一个可判定的错误值，而不是 panic**。

## 七、三语言对照

| | PHP | Java | Go |
| --- | --- | --- | --- |
| 状态载体 | `abstract class` + 子类 | `abstract class` 或 `enum` | 接口 + 内嵌空结构体 |
| 默认拒绝 | 基类方法（子类覆写） | 基类方法（子类覆写） | `baseState` 内嵌（外层覆写） |
| 失败表达 | 异常 | 异常 | **返回 `error`** |
| 转移触发 | `$order->transitionTo(new Paid())` | `order.transitionTo(new Paid())` | `o.transitionTo(paid{})` |
| 状态对象共享 | `static` 池 | `enum` 常量 | **空结构体（天然可比较、零大小）** |
| 状态持久化 | 存名字 | 存 `enum` 的 `name()` 或 `ordinal()` ⚠️ | 存名字或自定义编码 |
| 生态代表 | 各类订单/审批状态机（Laravel 里多为表驱动） | Spring StateMachine、squirrel-foundation | 手写状态机居多，库生态较弱 |

⚠️ **Java 存 `enum.ordinal()` 是坑**：枚举值顺序一改，历史数据的含义就全变了。存 `name()` 或显式的 `code` 字段。

## 八、面试官会追问什么

- **状态模式和策略模式的区别？** → 结构相似、语义相反：状态之间**知道彼此**（状态自己决定下一个状态），策略之间**互不认识**（由调用方选）。判据：有没有"状态图"。
- **状态模式解决了什么痛点？** → 把"每个操作里的一堆状态判断"转成"每个状态类里的少数几个操作"，即**把条件分支竖过来切**。加一个状态从"改所有方法"变成"加一个类"。
- **一定要用状态类吗？** → 不一定。**转移只取决于「状态 + 操作」时，一张转移表更划算**（本篇实测：40 行 vs 200 行，输出完全一致）。一旦某个状态带数据或转移要看别的条件，再搬回状态类。
- **状态对象能共享吗？** → 能，前提是**不带实例数据**。理由很实际：状态要存库（存名字），对象本身不参与持久化，所以天然是无状态的。一旦某个状态要记"已发 2 件"，共享就会串号。
- **非法操作抛异常还是返回错误？** → 看它在正常业务里会不会发生：会不会 → 抛异常（或做幂等）；会 → 返回结果让调用方处理。**别混用**。
- **状态图怎么画？** → 本模式的一大隐性收益：**每个状态类里 `transitionTo(new Xxx())` 的调用点就是状态图的所有边**，`grep transitionTo` 就能画出全图。表驱动版则是表本身就是图。
- **PHP 里状态怎么持久化？** → 存**状态名或整型编码**，绝不存序列化对象（类名/方法会变）。同时提供"从名字恢复状态"的入口，并且**状态改名要配数据迁移**。
- **有没有更省事的做法？** → 有：**表驱动 + 守卫函数**。`TRANSITIONS[$state][$action]` 给基本规则，转移条件复杂时在 action 上挂一个 `callable` 做守卫。Spring StateMachine / squirrel-foundation 都是这个思路的工程化版本。
