## 一、责任链解决什么问题

责任链（Chain of Responsibility）属于行为型模式：**让请求沿一串处理者依次传递，直到某个处理者把它处理掉**。

它要解决的是"**发送者不该知道谁处理、以及有多少个处理者**"：

| 需求 | 没有责任链时 |
| --- | --- |
| 加一条规则 | 在某个大方法里插一段 `if`，越插越长 |
| 规则顺序要能调 | 顺序硬编码在代码里 |
| 规则要能按场景裁剪（测试环境关掉限流） | 只能加开关变量，代码里全是 `if ($enabled)` |
| 某条规则拦下后，后面的不该再跑 | 手写 `return`，很容易漏 |

三个毛病：**调用方认识所有规则**（依赖爆炸）、**顺序散落在控制流里**、**"谁处理了"无法审计**。

责任链把它转成：**每个规则是一个"环"，环之间只知道下一个**。

四个角色：

| 角色 | 职责 | 本篇对应 |
| --- | --- | --- |
| Handler | 声明处理接口 + 持有下一个处理者 | `RiskHandler` |
| ConcreteHandler | 只判断"我这一关过不过" | `BlacklistHandler` / `RateLimitHandler` / … |
| 骨架 | "先问自己，再交给下一个" | `RiskHandler::handle()`（`final`） |
| Client | 组装链、发起请求 | `buildChain()` |

**注意 `handle()` 是 `final` 的骨架** —— 各环只实现 `check()`。这是模板方法在责任链里的复用：**"问自己 → 交下一个"的流程固定，各环只填判定**。

## 二、PHP 标准实现

场景：**订单风控链**（黑名单 → 限流 → 金额阈值 → 审计）。

```php
<?php

declare(strict_types=1);

/** 风控请求 */
final class RiskRequest
{
    public function __construct(
        public string $userId,
        public int $amount,
        public bool $newUser = false
    ) {}
}

/** 风控结论：放行，或由某一环给出拒绝理由 */
final class Decision
{
    private function __construct(
        public bool $allowed,
        public string $reason = ''
    ) {}

    public static function allow(): self
    {
        return new self(true);
    }

    public static function deny(string $reason): self
    {
        return new self(false, $reason);
    }
}

/**
 * 处理者基类：持有下一个处理者，但不认识调用方。
 * handle() 是 final 的骨架 —— 各环只实现 check()。
 */
abstract class RiskHandler
{
    private ?RiskHandler $next = null;

    /** 返回下一个处理者，方便链式组装 */
    final public function setNext(RiskHandler $next): RiskHandler
    {
        $this->next = $next;

        return $next;
    }

    final public function handle(RiskRequest $request): Decision
    {
        $decision = $this->check($request);
        if ($decision !== null) {
            return $decision;      // 本环给出结论 → 链在此终止
        }
        if ($this->next === null) {
            return Decision::allow();   // 链走完没人拦 → 放行
        }

        return $this->next->handle($request);
    }

    /** 子类实现：返回 null 表示「我不管，交给下一个」 */
    abstract protected function check(RiskRequest $request): ?Decision;
}
```

四个环，每个只关心自己那一关：

```php
final class BlacklistHandler extends RiskHandler
{
    /** @param list<string> $blocked */
    public function __construct(private array $blocked) {}

    protected function check(RiskRequest $request): ?Decision
    {
        return in_array($request->userId, $this->blocked, true)
            ? Decision::deny('命中黑名单')
            : null;
    }
}

final class RateLimitHandler extends RiskHandler
{
    /** @var array<string,int> */
    private array $counter = [];

    public function __construct(private int $limitPerWindow = 2) {}

    protected function check(RiskRequest $request): ?Decision
    {
        $n = ($this->counter[$request->userId] ?? 0) + 1;
        $this->counter[$request->userId] = $n;

        return $n > $this->limitPerWindow
            ? Decision::deny(sprintf('窗口内第 %d 次，超过上限 %d', $n, $this->limitPerWindow))
            : null;
    }
}

final class AmountThresholdHandler extends RiskHandler
{
    public function __construct(private int $maxAmount) {}

    protected function check(RiskRequest $request): ?Decision
    {
        return $request->amount > $this->maxAmount
            ? Decision::deny(sprintf('金额 %d 超过阈值 %d，转人工审核', $request->amount, $this->maxAmount))
            : null;
    }
}

/** 新用户首单强制人工审核：插进链里就能生效，且不必改任何其它环 */
final class NewUserHandler extends RiskHandler
{
    protected function check(RiskRequest $request): ?Decision
    {
        return $request->newUser ? Decision::deny('新用户首单，转人工审核') : null;
    }
}

/** 链尾：只记录，不拦（用来证明「前面的环终止后，它就收不到请求」） */
final class AuditTrailHandler extends RiskHandler
{
    public int $calls = 0;

    /** @var list<string> */
    public array $seen = [];

    protected function check(RiskRequest $request): ?Decision
    {
        $this->calls++;
        $this->seen[] = $request->userId;

        return null;
    }
}
```

链的组装与实测：

```php
$blacklist = new BlacklistHandler(['u-blocked']);
$rateLimit = new RateLimitHandler(2);
$audit = new AuditTrailHandler();
$blacklist->setNext($rateLimit)
    ->setNext(new AmountThresholdHandler(100000))
    ->setNext($audit);
```

**使用示例**：

```php
// 组装：setNext() 返回下一环，可连成一串
$blacklist = new BlacklistHandler(['u-blocked']);
$audit = new AuditTrailHandler();
$blacklist->setNext(new RateLimitHandler(2))
    ->setNext(new AmountThresholdHandler(100000))
    ->setNext($audit);

// 入口只认链首；handle() 返回 Decision
$ok = $blacklist->handle(new RiskRequest('u-1', 500));
$ok->allowed;                        // true（走完全链没人拦）

// 命中黑名单：第 1 环就终止，链尾审计收不到
$deny = $blacklist->handle(new RiskRequest('u-blocked', 500));
$deny->reason;                       // 命中黑名单
$audit->calls;                       // 1（只记到上一条通过的请求）
```

实测（PHP 8.0.2 CLI）：

```text
构建链：黑名单 → 限流 → 金额阈值 → 审计
1_正常请求        : 放行
   审计被调用次数  : 1
2_黑名单         : 拒绝（命中黑名单）
   审计被调用次数  : 1（没变 → 链在第 1 环就终止了）
3_第 3 次请求     : 拒绝（窗口内第 3 次，超过上限 2）
4_大额请求        : 拒绝（金额 200000 超过阈值 100000，转人工审核）

重新组装：黑名单 → 新用户 → 限流 → 审计
5_新用户请求      : 拒绝（新用户首单，转人工审核）
6_老用户同金额    : 放行

7_把审计放链首     : 审计被调用 1 次（拒绝也记到了 → 顺序即语义）
```

三种行为都在里面：

- **第 1、2 行是一组对照**：正常请求后审计计数变成 1；黑名单请求后计数**仍是 1** —— 说明请求在第 1 环就被终止，**链尾根本没收到**。这是责任链与装饰器最关键的区别（见第四节）；
- **第 5、6 行是"动态插环"**：新用户这一环插在链里就生效，**四个 handler 一行都没改**；
- **第 7 行是"顺序即语义"**：同一个审计环，放在链首就能记录"被拒绝的请求"，放在链尾就只能记录"通过的请求"。**换位置就是换语义**。

### 让它算「标准写法」的 6 个细节

| # | 做法 | 为什么 |
| --- | --- | --- |
| 1 | `handle()` 是 `final` 骨架，各环只实现 `check()` | "问自己 → 交下一个"的流程固定，各环不会忘了转发或忘了终止 |
| 2 | `check()` 返回 `?Decision`，`null` = 我不管 | 比"返回 bool + 忘了 return false 就断链"安全得多 |
| 3 | 链尾必须**明确兜底**（`next === null` → 放行） | 否则请求可能"没人处理"，静默通过或静默丢弃 |
| 4 | `setNext()` 返回下一个处理者 | 让组装写成一行链式调用，链的形状一眼可见 |
| 5 | 拒绝理由由**具体环**给出，不层层包装 | 日志里能直接看到"是黑名单拦的"还是"额度拦的" |
| 6 | 有状态的环（限流计数器）必须整链唯一 | 每次请求都 `new` 一个链，计数器就永远归零（见下方注意事项） |

⚠️ **第 6 条是实践中最容易翻车的**：本篇的 `RateLimitHandler` 计数器存在**对象属性**里，所以它只在**同一个进程、同一条链实例**内有效。真实项目里计数必须外置（Redis / 本地缓存 + 时间窗），否则 php-fpm 多进程各自计数 = 限流形同虚设。这也是"责任链的状态放哪儿"的经典追问。

## 三、两种终止语义（先选对，再写代码）

责任链有两种截然不同的用法，**必须先明确要哪种**：

| | **一环比到底**（本篇） | **全部执行** |
| --- | --- | --- |
| 行为 | 某环给出结论即终止 | 每环都跑，谁都能否决 |
| `check()` 返回 | `Decision`（终止）或 `null`（放行） | 累计结果，或抛异常 |
| 典型场景 | 风控、审批、鉴权（**通过就够，不必都问**） | 数据校验（**所有错误要一次报全**）、中间件 |
| 优点 | 短路、快 | 一次拿到全部问题 |

**PHP 世界里最常见的责任链其实是第二种** —— PSR-15 中间件就是"每层都执行、每层都能提前返回响应"的混合体：它既沿链传递（责任链），又每层都执行并可以包装响应（[装饰器](../结构型/装饰器模式.md)）。这两个模式在中间件里是**同时成立**的，不必硬分。

## 四、边界：责任链 vs 装饰器

这是最容易混的一对，因为**结构完全相同**（都是"持有下一个、调用下一个"）：

| | 责任链 | 装饰器 |
| --- | --- | --- |
| 每层都执行吗 | **通常不**（一个处理者处理完即终止） | **一定都执行** |
| 返回值 | 处理结论（谁处理的） | 被包装后的**同一个接口的返回值** |
| 接口形状 | 处理者接口（常与调用方不同） | **与目标同接口**（可以替换目标） |
| 目的 | 找"谁来处理" | 加"额外行为" |
| 典型 | 风控、审批、鉴权 | 缓存、日志、压缩 |

**实测第 1、2 行就是判据**：黑名单请求后审计计数**没变** —— 说明后面几层**没执行**，这是责任链；如果是装饰器，计数一定 +1（每层都会执行到）。

一句话判据：**"某层拦下后，后面的还要跑吗？"** 要 → 装饰器；不要 → 责任链。

## 五、真实形态

| 场景 | 语言/框架 | 说明 |
| --- | --- | --- |
| HTTP 中间件 | PHP：PSR-15 / Laravel Pipeline | `MiddlewareInterface` + `RequestHandlerInterface`，责任链 + 装饰器的混合 |
| Servlet Filter | Java：`javax.servlet.Filter` | `doFilter(req, res, chain)`，`chain.doFilter()` 就是"交给下一个" |
| 拦截器/切面链 | Java：Spring `HandlerInterceptor` | `preHandle` 返回 `false` 即终止 |
| `http.Handler` 包装 | Go：`func(http.Handler) http.Handler` | 中间件即"接受 handler 返回 handler"的函数 —— 形状是装饰器，语义常是责任链 |
| 路由分组中间件 | Go：chi / gin 的 `Use()` | 本质是 `[]Middleware` 顺序执行，即本篇 Go 侧的"切片版" |

## 六、Java / Go 实现

### Java 实现

```java
/**
 * 处理者基类：持有下一个处理者，但不认识调用方。
 * handle() 是 final 的骨架 —— 各环只实现 check()。
 */
abstract static class RiskHandler {
    private RiskHandler next;

    /** 返回下一个处理者，方便链式组装 */
    final RiskHandler setNext(RiskHandler next) {
        this.next = next;

        return next;
    }

    final Decision handle(RiskRequest request) {
        Decision decision = check(request);
        if (decision != null) {
            return decision;          // 本环给出结论 → 链在此终止
        }
        if (next == null) {
            return Decision.allow();  // 链走完没人拦 → 放行
        }

        return next.handle(request);
    }

    /** 子类实现：返回 null 表示「我不管，交给下一个」 */
    abstract Decision check(RiskRequest request);
}
```

**使用示例**：

```java
// 组装：setNext() 返回下一环，可连成一串
BlacklistHandler blacklist = new BlacklistHandler("u-blocked");
AuditTrailHandler audit = new AuditTrailHandler();
blacklist.setNext(new RateLimitHandler(2))
        .setNext(new AmountThresholdHandler(100000))
        .setNext(audit);

// 入口只认链首；handle() 返回 Decision
Decision ok = blacklist.handle(new RiskRequest("u-1", 500));
ok.allowed;                                  // true（走完全链没人拦）

// 命中黑名单：第 1 环就终止，链尾审计收不到
Decision deny = blacklist.handle(new RiskRequest("u-blocked", 500));
deny.reason;                                 // 命中黑名单
audit.calls;                                 // 1（只记到上一条通过的请求）
```

JDK 1.8 实测输出与 PHP 版逐行一致：

```text
构建链：黑名单 → 限流 → 金额阈值 → 审计
1_正常请求        : 放行
   审计被调用次数  : 1
2_黑名单         : 拒绝（命中黑名单）
   审计被调用次数  : 1（没变 → 链在第 1 环就终止了）
...
7_把审计放链首     : 审计被调用 1 次（拒绝也记到了 → 顺序即语义）
```

Java 侧值得提的是 **Servlet Filter 的写法差异**：它不返回"结论"，而是通过 `chain.doFilter()` **显式**决定是否继续 —— 调用它 = 继续，不调用 = 终止。这种"把转发写成副作用"的写法更灵活（可以在 `doFilter()` 前后各做一段，像装饰器），但也更容易忘记调用而**静默断链**。本篇的 `?Decision` 返回值写法把这件事变成了显式返回值。

### Go 实现

Go 里两种写法都常见。**接口链**版（与 PHP/Java 同构）：

```go
// Handler 处理者：持有下一个处理者，但不认识调用方
type Handler interface {
	SetNext(Handler) Handler
	Handle(RiskRequest) Decision
}

// baseHandler 给出链的「骨架」：各环只实现自己那一关的判定
type baseHandler struct {
	next Handler
}

// SetNext 返回下一个处理者，方便链式组装
func (h *baseHandler) SetNext(n Handler) Handler {
	h.next = n

	return n
}

// dispatch 骨架：check 返回 stop=true 表示本环给出结论 → 链在此终止
func (h *baseHandler) dispatch(r RiskRequest, check func(RiskRequest) (Decision, bool)) Decision {
	if d, stop := check(r); stop {
		return d
	}
	if h.next == nil {
		return Allow() // 链走完没人拦 → 放行
	}

	return h.next.Handle(r)
}
```

**切片版**（Go 里更常见的形态）：

```go
// Middleware 切片版：Go 里更常见的写法 —— 一串处理函数顺序执行
type Middleware func(RiskRequest) (Decision, bool)

// RunChain 顺序执行，任一环 stop=true 即终止
func RunChain(handlers []Middleware, r RiskRequest) Decision {
	for _, h := range handlers {
		if d, stop := h(r); stop {
			return d
		}
	}

	return Allow()
}
```

**使用示例**：

```go
// 接口链版：SetNext() 返回下一环，可连成一串
blacklist := NewBlacklistHandler("u-blocked")
audit := &AuditTrailHandler{}
blacklist.SetNext(NewRateLimitHandler(2)).
	SetNext(&AmountThresholdHandler{maxAmount: 100000}).
	SetNext(audit)
blacklist.Handle(RiskRequest{UserID: "u-1", Amount: 500}) // Allowed = true
blacklist.Handle(RiskRequest{UserID: "u-blocked", Amount: 500})
audit.Calls // 1（黑名单在第 1 环被拦 → 链尾收不到）

// 切片版：一串 Middleware 顺序执行，任一环 stop=true 即终止
handlers := []Middleware{func(r RiskRequest) (Decision, bool) { return Deny("命中黑名单"), true }}
RunChain(handlers, RiskRequest{UserID: "u-blocked", Amount: 500}) // Reason = 命中黑名单
```

go1.26.5 实测（切片版与接口链版行为一致）：

```text
8_切片版·正常     : 放行
9_切片版·黑名单   : 拒绝（命中黑名单）
10_切片版审计次数  : 2（两笔都记到了）
```

Go 的三点差异：

- **`func` 类型就是最轻的处理者**。不需要接口、不需要 `next` 字段 —— 一个切片顺序遍历即可。**这是 Go 的默认选择**，只有需要"每环带自己的状态与配置"时才升级成接口链；
- **标准库的 `net/http` 中间件是"包装形状"**：`func(http.Handler) http.Handler`。它是装饰器/责任链的混合体，与本篇的 `Handler` 接口是两种不同风格；
- **`check` 用闭包传入 `dispatch`**（而不是像 PHP/Java 那样的抽象方法）。因为 Go 没有继承，把"变化点"作为参数传进去是最直接的做法。

## 七、三语言对照

| | PHP | Java | Go |
| --- | --- | --- | --- |
| 骨架 | `abstract class` + `final handle()` | `abstract class` + `final handle()` | 接口 + 内嵌 `baseHandler`（或直接切片） |
| 变化点 | `abstract check()` | `abstract check()` | **闭包参数** / `func` 类型 |
| 终止方式 | 返回 `Decision` | 返回 `Decision` | 返回 `(Decision, bool)` |
| 最常用形态 | PSR-15 中间件、Laravel Pipeline | Servlet Filter、`HandlerInterceptor` | `[]Middleware` 顺序遍历 |
| 链的形状 | 链式 `setNext()` | 链式 `setNext()` | **切片字面量**（更易读、易重排） |
| 组装自由度 | 运行时 `setNext` | 运行时 `setNext` | 切片可以直接 append / slice 裁剪 |
| 断链风险 | 低（骨架 `final`） | 低；Servlet Filter 有（忘了 `doFilter`） | 低（顺序遍历天然完整） |

**一个跨语言通用的注意点**：链尾一定要有兜底。本实现是"没人拦 → 放行"，**反过来（"没人处理 → 拒绝"）也是合法设计**，但必须选一个并写清楚 —— 否则请求会在"没人管"的状态下被静默放行，这在风控/鉴权场景里是安全事故。

## 八、面试官会追问什么

- **责任链和装饰器的区别？** → 结构一样（都持有并调用下一个），语义相反：装饰器**每层都执行**并包装返回值；责任链**一环拦下即终止**。判据一句话："某层拦下后，后面的还要跑吗？"
- **链的顺序重要吗？** → **顺序即语义**。实测里同一个审计环放在链首能记录"被拒绝的请求"、放在链尾只能记录"通过的请求"。另外黑名单必须在限流之前（否则黑名单请求会先消耗限流额度，还可能被限流的错误理由掩盖）。
- **链尾没人处理怎么办？** → 必须显式兜底：**放行**（风控场景）或**拒绝**（鉴权场景）。**"默认放行"是很多安全事故的根源**，选择哪个要在代码里写明。
- **中间件算责任链还是装饰器？** → **两个都算**。PSR-15 的 `RequestHandlerInterface` 是责任链（沿链传递、可提前返回响应），同时每层都执行并可包装响应 = 装饰器。**中间件是这两个模式的重叠区**，不必硬分。
- **责任链的状态放哪儿？** → 本篇的限流计数器放在环的属性里，因此**只在单进程单链实例内有效**。php-fpm 多进程各算各的 → 限流形同虚设。真实项目必须外置（Redis / 共享缓存）或用粘性路由。这是最容易翻车的地方。
- **怎么保证不断链？** → 把 `handle()` 做成 `final` 骨架、各环只实现 `check()`（本篇做法）。Servlet Filter 那种"靠调用 `doFilter()` 表示继续"的写法更灵活，但忘调就静默断链。
- **PHP 里哪里有？** → PSR-15 中间件、Laravel 的 `Pipeline`（`$this->send($request)->through($middleware)->then(...)`）、Symfony 的事件分发与 Middleware。
- **和状态模式的区别？** → 责任链是**多个对象依次尝试**（横向），状态模式是**一个对象在不同状态间转移**（纵向）。两者常一起出现：状态转移时经过一条责任链做校验。
