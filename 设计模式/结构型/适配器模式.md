## 一、什么是适配器模式

原文的定义：

> 将一个类的接口**转换成外部希望的另外一个接口**，使原本不兼容的而不能在一起工作的那些类可以在一起工作。
> 适配器就是一个**把拥有相似功能但是接口名不同的类封装成拥有同样接口名的类**，
> 这样只需要更改接口引入的类，但不需要改变类中的方法，就可以换成另一个相同功能不同类名和方法名。

三个角色：

| 角色 | 职责 | 谁提供的 |
| --- | --- | --- |
| Target（目标接口） | 我的调用方认识的形状 | **我**定义 |
| Adaptee（被适配者） | 已有的、形状不对的实现 | 第三方 / 遗留代码 |
| Adapter（适配器） | 把 Adaptee 翻译成 Target | **我**写 |

关键点：**改的是"接口形状"，不动任何一方**。被适配者一行不改（它是别人的代码），调用方也不改（它按 Target 写的）。

## 二、应用场景

原文列举：**数据库多种驱动的适配、缓存多种方案的适配、日志存储的适配等**。

原文还特别提醒了一句，很值得保留：

> **跟策略模式不要混淆**，这是不同的，**适配器模式是对每种不同策略的接口做统一，而策略模式是能随需求切换选择不同的策略。**

这句话点到了本目录里最容易被问倒的一组对比：

| | 适配器 | 策略 |
| --- | --- | --- |
| 解决的问题 | 接口**形状**不一致 | 算法**可替换** |
| 谁定义接口 | 调用方定义，适配器去迎合 | 接口由模式自己定义 |
| 对方配合吗 | 不配合（第三方/遗留代码） | 配合（自己写的多个实现） |
| 换一个实现 | 换适配器，调用方不动 | 换策略对象，调用方不动 |

**两者常一起出现**：策略需要一个统一接口，而各实现形状不一样时，中间就要加适配器。原文那句"对每种不同策略的接口做统一"说的正是这个组合。

## 三、PHP 标准实现

场景：**通知渠道适配**。业务代码只想调 `send($to, $message)`，但手里有两个第三方 SDK。

```php
<?php

declare(strict_types=1);

/** 目标接口：调用方只认这个形状 */
interface Notifier
{
    public function send(string $to, string $message): string;
}

/** 被适配者 1：第三方短信 SDK —— 方法名、参数顺序、返回值都不一样 */
final class LegacySmsClient
{
    /** @param array{phone:string,len:int,urgent:bool} */
    public function dispatchMessage(string $text, string $phone, bool $urgent = false): array
    {
        return ['phone' => $phone, 'len' => strlen($text), 'urgent' => $urgent];
    }
}

/** 被适配者 2：Slack Webhook */
final class SlackWebhook
{
    public function post(array $payload): string
    {
        return 'slack:' . ($payload['text'] ?? '');
    }
}

/**
 * 对象适配器：组合被适配者并翻译。
 * 为什么不用「类适配器」（继承被适配者）？PHP 是单继承，
 * 一继承就占掉唯一继承位，且无法同时适配多个来源。
 */
final class LegacySmsAdapter implements Notifier
{
    public function __construct(private LegacySmsClient $client) {}

    public function send(string $to, string $message): string
    {
        $result = $this->client->dispatchMessage($message, $to);
        return "sms:{$result['phone']}({$result['len']})";
    }
}

final class SlackAdapter implements Notifier
{
    public function __construct(private SlackWebhook $webhook) {}

    public function send(string $to, string $message): string
    {
        return $this->webhook->post(['text' => "{$to}: {$message}"]);
    }
}

/** 调用方只依赖 Notifier，换供应商不改它 */
function notifyAll(Notifier $notifier, array $recipients, string $message): void
{
    foreach ($recipients as $to) {
        echo '   -> ', $notifier->send($to, $message), PHP_EOL;
    }
}
```

**使用示例**：

```php
// 调用方只依赖 Notifier 接口，不关心背后是哪家 SDK
$notifier = new LegacySmsAdapter(new LegacySmsClient());    // 被适配者注入进来
$notifier->send('13800000000', '您的订单已发货');            // "sms:13800000000(21)"

// 换供应商：new 另一个适配器，调用方一个字不改
$notifier = new SlackAdapter(new SlackWebhook());
$notifier->send('13800000000', '您的订单已发货');            // "slack:13800000000: 您的订单已发货"

// 适配器不是必经关卡，被适配者可单独使用（参数顺序是本来的 text, phone）
$legacy = new LegacySmsClient();
$legacy->dispatchMessage('hi', '138');                      // ['phone'=>'138','len'=>2,'urgent'=>false]
```

实测（PHP 8.0.2 CLI）：

```text
1_短信通道：
   -> sms:13800000000(21)
   -> sms:ann@example.com(21)
2_换成 Slack，调用方一个字没改：
   -> slack:13800000000: 您的订单已发货
   -> slack:ann@example.com: 您的订单已发货
3_被适配者可单独使用 : {"phone":"138","len":2,"urgent":false}
```

三个观察点：

- **第 1 组与第 2 组的 `notifyAll` 是同一个函数**，只换了传进去的适配器；
- 参数顺序的翻译发生在适配器里（被适配者要 `(text, phone)`，目标接口是 `(to, message)`）—— **这正是"适配"二字的字面含义**；
- 第 3 行说明**适配器不是必经关卡**，被适配者仍可被单独使用。

### 4 个让它算「标准写法」的细节

| # | 做法 | 为什么 |
| --- | --- | --- |
| 1 | Target 用 `interface`，适配器 `implements` 它 | 调用方只依赖目标接口，做到"换供应商零改动" |
| 2 | 被适配者**注入**进来，不在适配器里 `new` | 便于替换与测试；也避免适配器绑定到某个具体构造方式 |
| 3 | 参数顺序、返回值都在适配器里翻译 | 这是适配器的唯一职责，别让它顺手做业务 |
| 4 | 适配器保持薄 | 一旦适配器里出现业务分支，那部分逻辑该独立出去，别混进翻译层 |

## 四、原文写法的三个问题

### 4.1 用字符串拼类名直接 `new`

原文的"数据库工厂"是：

```php
$this->db = new $type;          // $type 来自字符串拼接
```

问题与 [../创建型/工厂模式.md](../创建型/工厂模式.md) 第四节说的一样：**类名成了字符串**，IDE 无法跳转、重构改名不会同步、拼错只在运行时炸，而且**没有任何类型约束**（`$this->db` 是不是 `Target` 完全靠自觉）。

### 4.2 `MySQLiAdapter` 没有实现 `Target`

原文里 `interface Target` 定义了 `connect/query/close`，但 `MySQLiAdapter` **没有 `implements Target`** —— 接口声明了却没被用来约束实现。结果是：漏写一个方法，直到运行时调用才炸。

### 4.3 用 `mysql_*` 函数（PHP 7 已移除）

原文示例调用 `mysql_connect` / `mysql_query` / `mysql_close`。这套扩展在 **PHP 5.5 被废弃、PHP 7.0 被完全移除**，今天跑会直接 `Call to undefined function mysql_connect()`。

这也是"第三方接口会变"的活教材：**适配器隔离的正是这种变化** —— 如果有适配器，换驱动只改适配器；如果没有（像原文那样在业务类里散落调用），就得满地找。

## 五、边界：和代理、装饰器、外观的区别

这四个都"包一层"，判据是**包这一层改了什么**：

| 模式 | 接口 | 目的 |
| --- | --- | --- |
| **适配器** | **改成调用方要的形状** | 让不兼容的接口能用 |
| 代理 | 与被代理对象**完全相同** | 控制访问（延迟、缓存、权限） |
| 装饰器 | 与被装饰对象**完全相同** | 增加行为（可叠加多层） |
| 外观 | **简化/收敛**成新接口 | 把 N 个子系统收成一个入口 |

一句话记法：**适配器换形状，代理控访问，装饰器加行为，外观收入口**。

## 六、Java / Go 实现

### Java 实现

```java
/** 目标接口：调用方只认这个形状 */
interface Notifier {
    String send(String to, String message);
}

/** 被适配者 1：第三方短信 SDK —— 方法名与参数顺序都不同 */
static final class LegacySmsClient {
    Map<String, Object> dispatchMessage(String text, String phone) {
        Map<String, Object> result = new HashMap<String, Object>();
        result.put("phone", phone);
        result.put("len", text.length());
        return result;
    }
}

/** 对象适配器：组合被适配者并翻译 */
static final class LegacySmsAdapter implements Notifier {
    private final LegacySmsClient client;

    LegacySmsAdapter(LegacySmsClient client) { this.client = client; }

    public String send(String to, String message) {
        Map<String, Object> result = client.dispatchMessage(message, to);
        return "sms:" + result.get("phone") + "(" + result.get("len") + ")";
    }
}
```

**使用示例**：

```java
// 调用方只依赖 Notifier 接口，换供应商不改它
Notifier notifier = new LegacySmsAdapter(new LegacySmsClient());
notifier.send("13800000000", "您的订单已发货");   // sms:13800000000(7)

// 被适配者作为依赖注入，可先持有再复用
LegacySmsClient legacy = new LegacySmsClient();
notifier = new LegacySmsAdapter(legacy);          // 换个实例，接口不变

// 适配器不是必经关卡：被适配者保留自己的原参数顺序
legacy.dispatchMessage("hi", "138");              // {len=2, phone=138}
```

JDK 1.8 实测输出：

```text
1_短信通道：
   -> sms:13800000000(7)
   -> sms:ann@example.com(7)
2_换成 Slack，调用方一个字没改：
   -> slack:13800000000: 您的订单已发货
   -> slack:ann@example.com: 您的订单已发货
3_被适配者可单独使用 : {len=2, phone=138}
```

**注意第一组的 `(7)` 与 PHP/Go 版的 `(21)` 不一样** —— 这不是 bug，是两种语言对"字符串长度"的定义不同：

| 语言 | 方法 | `'您的订单已发货'` 的结果 | 含义 |
| --- | --- | --- | --- |
| PHP | `strlen` | **21** | UTF-8 **字节数** |
| Go | `len` | **21** | 字节数 |
| Java | `String.length()` | **7** | UTF-16 **代码单元数** |

三种都"对"，只是口径不同。要按字符数算，PHP 用 `mb_strlen`、Go 用 `utf8.RuneCountInString`、Java 用 `codePointCount`。**这是跨语言写适配器时最容易被忽略的一类差异** —— 适配器不只翻译参数顺序，有时还要翻译这类口径。

### Go 实现

```go
// Notifier 目标接口：调用方只认这个形状
type Notifier interface {
	Send(to, message string) (string, error)
}

// LegacySmsAdapter 对象适配器：组合被适配者并翻译
type LegacySmsAdapter struct {
	client LegacySmsClient
}

func (a LegacySmsAdapter) Send(to, message string) (string, error) {
	if to == "" {
		return "", errors.New("收件人不能为空")
	}
	result := a.client.DispatchMessage(message, to)
	return fmt.Sprintf("sms:%s(%d)", result["phone"], result["len"]), nil
}
```

**使用示例**：

```go
// 调用方只依赖 Notifier 接口，换供应商不改它
var n Notifier = LegacySmsAdapter{client: LegacySmsClient{}}
out, err := n.Send("13800000000", "您的订单已发货")
// out = "sms:13800000000(21)"，err = nil

// 空收件人：适配器内做校验，走 error 返回值
_, err = n.Send("", "x")     // err = "收件人不能为空"

// 被适配者可单独使用（参数顺序是本来的 text, phone）
legacy := LegacySmsClient{}
_ = legacy.DispatchMessage("hi", "138")   // map[len:2 phone:138]
```

go1.26.5 实测输出（与 PHP 一致，见上）：

```text
1_短信通道：
   -> sms:13800000000(21)
   -> sms:ann@example.com(21)
2_换成 Slack，调用方一个字没改：
   -> slack:13800000000: 您的订单已发货
   -> slack:ann@example.com: 您的订单已发货
3_被适配者可单独使用 : map[len:2 phone:138]
```

Go 的两点差异：

- **接口是隐式实现**，所以适配器不需要写 `implements Notifier` —— 只要有 `Send` 方法就自动满足。代价是"忘了实现某个方法"不会被编译器立刻发现，要等赋值给接口变量时才报错；
- **错误是返回值**，所以适配器里可以做参数校验并返回 `error`（本实现在收件人为空时返回错误），这在 PHP/Java 里对应抛异常。

## 七、三语言对照

| | PHP | Java | Go |
| --- | --- | --- | --- |
| 目标接口声明 | `interface` + `implements` | `interface` + `implements` | 隐式实现 |
| 类适配器可行性 | ❌ 单继承 | ✅（Java 可单继承 + 实现接口） | ❌ 无继承 |
| 适配器形态 | 对象适配器 | 对象适配器为主 | 对象适配器 |
| 字符串长度口径 | `strlen`=字节 | `length()`=字符 | `len`=字节 |
| 参数校验失败 | `throw` | `throw` | 返回 `error` |

## 八、面试官会追问什么

- **适配器和策略的区别？** → 策略答"用哪种算法"（自己定义接口，实现都配合）；适配器答"怎么让形状不兼容的东西能一起工作"（迎合别人的接口）。原文那句"适配器是对不同策略的接口做统一"说的就是两者的组合用法。
- **适配器和代理/装饰器的区别？** → 看接口：适配器**改形状**，代理和装饰器**接口完全相同**（前者控访问，后者加行为）。
- **为什么 PHP 里基本只用对象适配器？** → 单继承：类适配器要继承被适配者，一继承就占掉唯一继承位，也无法同时适配多个来源。
- **适配器该不该有业务逻辑？** → 不该。适配器的职责只有"翻译形状"，出现业务分支说明那部分逻辑该独立出去。
- **第三方接口升级了怎么办？** → 改适配器一处即可 —— 这正是适配器的价值（原文用已被移除的 `mysql_*` 例子，恰好演示了"接口会变"）。
- **跨语言写适配器最容易错什么？** → 参数顺序、返回值结构，以及**度量口径**（如字符串长度：PHP/Go 是字节、Java 是字符，实测 `21` vs `7`）。
