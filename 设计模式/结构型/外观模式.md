## 一、什么是外观模式

原文的定义：

> 外观模式（有时候也称门面模式）是指**提供一个统一的接口去访问多个子系统的多个不同的接口**，
> 它为子系统中的一组接口提供一个统一的高层接口。使用子系统更容易使用。

原文的角色分析（这里两个角色的边界划得很清楚，值得原样留着）：

> **门面（Facade）角色**：此角色封装一个高层接口，将客户端的请求代理给适当的子系统对象，是门面模式的核心接口。
>
> **子系统（Subsystem）角色**：实现子系统的具体功能，处理 Facade 对象指派的任务。
> **子系统没有 Facade 的任何信息，没有对 Facade 对象的引用。**

最后那句是判据：**依赖是单向的**（外观 → 子系统），子系统不认识外观。反过来若子系统必须回调外观，那已经不是外观模式（见第五节的中介者）。

外观的三条性质，缺一条就不是外观（对应了那些常见误用）：

| 性质 | 含义 | 违反后的形态 |
| --- | --- | --- |
| 降接口面 | N 个子系统类 → 1 个业务入口 | 调用方仍要自己攒依赖 |
| 不独占 | 子系统可绕过外观直接使用 | 变成必经的"上帝类" |
| 无业务决策 | 方法体只有转发 + 顺序编排 | 退化成 God Service（见第四节判据） |

## 二、应用场景

原文给的三条，覆盖了外观在项目里出现的三个阶段：

> - 在**设计初期阶段**，有意识地**将不同的两个层分离**；
> - 在**开发阶段**，子系统往往因为不断的重构演化而变得越来越复杂，给调用它们的用户带来了使用上的困难，
>   增加外观 Facade 可以提供一个简单的接口，减少它们之间的依赖；
> - 在**维护一个遗留的大型系统**时，可能这个系统已经非常难以维护和扩展，但又包含新的需求开发必须依赖的重要功能，
>   此时可以为新系统开发一个外观 Facade 类，来提供设计旧系统比较清晰的简单接口，
>   让新系统与 Facade 对象交互，Facade 与遗留代码交互所有复杂的工作。

第三条（遗留系统的防腐层）是最实用的：**它把"改造老系统"降级成"包一层新接口"**。

## 三、PHP 标准实现

博客原文用了 `SubSystemOne/Two/Three` 三个占位类。工程里的对应物就是**一个用例一个入口** —— 把 Controller→Service→Repository 的调用链收敛成一个方法（application service / command handler）：

```php
<?php

declare(strict_types=1);

// ---------------- 子系统 ----------------
final class InventoryService
{
    public function reserve(int $sku, int $qty): string
    {
        if ($qty <= 0) {
            throw new InvalidArgumentException('数量必须为正');
        }
        return "reserved {$sku}x{$qty}";
    }
}

final class PaymentGateway
{
    public function charge(int $amountInCents): string
    {
        if ($amountInCents <= 0) {
            throw new InvalidArgumentException('金额必须为正');
        }
        return 'txn_' . $amountInCents;
    }
}

final class NotificationService
{
    public function notifyPaid(int $orderId): string
    {
        return "notified {$orderId}";
    }
}

// ---------------- 外观：只转发 + 编排 ----------------
final class CheckoutFacade
{
    public function __construct(
        private InventoryService $inventory,
        private PaymentGateway $payments,
        private NotificationService $notifications
    ) {}

    public function place(int $orderId, int $sku, int $qty, int $amountInCents): string
    {
        $this->inventory->reserve($sku, $qty);
        $txn = $this->payments->charge($amountInCents);
        $this->notifications->notifyPaid($orderId);
        return $txn;
    }
}
```

**使用示例**：

```php
// 外观：调用方只调一个入口，不必知道要串几个子系统
$facade = new CheckoutFacade(
    new InventoryService(),
    new PaymentGateway(),
    new NotificationService()
);
$facade->place(1, 88, 1, 25000);   // "txn_25000"（内部 reserve → charge → notify）

// 子系统不被外观独占，仍可单独使用
$payments = new PaymentGateway();
$payments->charge(999);            // "txn_999"
```

实测（PHP 8.0.2 CLI）：

```text
1_外观调用       : txn_25000
2_子系统单独使用 : txn_999
3_子系统直接询问 : reserved 88x1
```

**第二、三行才是关键**：外观的存在不妨碍子系统被单独调用，也不妨碍排查问题时直接问某个子系统。一个类如果把所有人逼得只能经它干活，它已经不是可选的门面了。

### 4 个让它算「标准写法」的细节

| # | 做法 | 为什么 |
| --- | --- | --- |
| 1 | 方法体只有「转发 + 顺序编排」 | 出现 `if/match` 判断业务，说明领域规则住错了地方 |
| 2 | 依赖全部构造注入、全部 `private` | 外观自己 `new` 子系统会导致无法替换测试替身 |
| 3 | 一个用例一个类（`CheckoutFacade`，不是 `OrderService::handle($action)`） | 按动作拆，避免半年后长成"什么都管"的门面 |
| 4 | 返回业务上有意义的东西（`$txn`），不返回"操作成功" | 调用方只发一次意图，不必再回头查状态 |

## 四、外观不该变成「上帝服务」：三条可反射验证的判据

"先建个 Facade 方便"的项目，半年后门面试图替你决定一切。退化不靠感觉，可以用反射量出来：

```php
final class OrderGodService
{
    /** @var array<int,string> 自建缓存 = 内部可变状态 */
    private array $memo = [];

    public function __construct(
        private InventoryService $inventory,
        private PaymentGateway $payments
    ) {}

    public function handle(array $order): string
    {
        $qty = (int) ($order['qty'] ?? 1);
        if (($order['vip'] ?? false) === true && $qty > 10) {
            $qty = 10;                                  // 业务决策跑进来了
        }
        $fee = match ($order['channel'] ?? 'web') {     // 分支也跑进来了
            'app' => 100,
            default => 200,
        };
        $this->inventory->reserve((int) $order['sku'], $qty);
        $txn = $this->payments->charge((int) $order['amount'] + $fee);
        $this->memo[(int) $order['id']] = $txn;         // 还自己养了状态
        return $txn;
    }
}
```

用一个 `inspect()` 函数（`ReflectionClass` 取方法起止行 + `preg_match_all` 数分支关键字 + 比对构造注入属性）量出来：

```text
CheckoutFacade     place    body= 7 行, 分支=0
CheckoutFacade     摘要: 内部可变状态属性数=0

OrderGodService    handle   body=15 行, 分支=2
OrderGodService    摘要: 内部可变状态属性数=1
```

三条判据与实测一一对应：

1. **方法体短**：合格外观单方法 5~10 行（实测 7）；`handle` 15 行说明它已在替子系统做决定。
2. **无业务分支**：外观里出现依赖入参的 `if/switch/match`（实测 2 个）说明领域规则下沉得不够，该回到领域对象或 [策略模式.md](../行为型/策略模式.md)。
3. **无内部可变状态**：构造注入的依赖不算，自己养缓存/累加器才算（实测 0 vs 1）。外观一旦有状态，就从"入口"变成"真相源"，测试与并发都会变复杂。

补救不是把上帝类拆小继续当上帝，而是**按用例拆** —— `CheckoutFacade` 优于 `OrderService::handle($action)`。

## 五、边界：和中介者、适配器、代理各管什么

这是面试最爱问的一组。判据是**它回答的问题**，不是类图：

| | 外观（结构型） | 中介者（行为型） |
| --- | --- | --- |
| 为谁服务 | 外部调用方：少记几个类 | 子系统内部：同事对象互相引用成网 |
| 依赖方向 | 单向：外观 → 子系统，子系统不知道外观 | 双向：同事持有中介者并回调它 |
| 解决的问题 | "用这套系统的人太多" | "系统内部模块互相调" |
| 删掉之后 | 子系统依然完整可用 | 对象立刻退回互相直连的蛛网 |

再加两个容易混的：

- **适配器**：已有接口不合调用方期望，**改造形状**；外观是接口**太多**，设计一个简化的新口（见 [适配器模式.md](适配器模式.md)）。
- **代理**：与外观、适配器的接口**完全一致**，只为控制访问（延迟、缓存、权限、远程），见 [代理模式.md](代理模式.md)。

## 六、生态里的真实外观：别把三个 "Facade" 混为一谈

| 真实代码 | 外观在哪 | 辨析 |
| --- | --- | --- |
| `PDO` | 对 `pdo_mysql`/`pdo_pgsql`/`pdo_sqlite` 驱动 | 换驱动不改业务代码；`query()` 内部编排准备→执行→取回 |
| `League\Flysystem` | `Filesystem` 对 aws/s3、本地磁盘、FTP 各 adapter | 业务只调 `write()/read()`，不知道文件落在哪个云 |
| Laravel `Storage` | GoF 意义的外观是 Flysystem 这层 | `FilesystemManager` 按 config 造 Flysystem 实例 |

**高频面试坑：Laravel 的 `Illuminate\Support\Facades\Facade` 基类不是 GoF 外观**，它是**静态代理** —— `Storage::put()` 靠 `__callStatic` 从容器解析真实实例再转发，解决的是"静态调用语法 + 可测试替换"，与"降接口面"无关。名字撞车纯属历史原因。GoF 外观在 Laravel 里的对位物是**应用服务层**。

## 七、Java 实现

```java
public class FacadeStandard {
    static final class InventoryService {
        String reserve(int sku, int qty) {
            if (qty <= 0) {
                throw new IllegalArgumentException("数量必须为正");
            }
            return "reserved " + sku + "x" + qty;
        }
    }

    static final class PaymentGateway {
        String charge(int amountInCents) {
            if (amountInCents <= 0) {
                throw new IllegalArgumentException("金额必须为正");
            }
            return "txn_" + amountInCents;
        }
    }

    static final class NotificationService {
        String notifyPaid(int orderId) {
            return "notified " + orderId;
        }
    }

    /** 合格外观：只转发 + 编排，无业务分支、无内部可变状态 */
    static final class CheckoutFacade {
        private final InventoryService inventory;
        private final PaymentGateway payments;
        private final NotificationService notifications;

        CheckoutFacade(InventoryService inventory, PaymentGateway payments, NotificationService notifications) {
            this.inventory = inventory;
            this.payments = payments;
            this.notifications = notifications;
        }

        String place(int orderId, int sku, int qty, int amountInCents) {
            inventory.reserve(sku, qty);
            String txn = payments.charge(amountInCents);
            notifications.notifyPaid(orderId);
            return txn;
        }
    }
}
```

**使用示例**：

```java
// 外观：调用方只调一个入口，依赖从构造传入
CheckoutFacade facade = new CheckoutFacade(
        new InventoryService(),
        new PaymentGateway(),
        new NotificationService());
facade.place(1, 88, 1, 25000);       // "txn_25000"（内部依次编排三个子系统）

// 子系统不被外观独占，可单独使用
new PaymentGateway().charge(999);         // "txn_999"
new InventoryService().reserve(88, 1);    // "reserved 88x1"
```

JDK 1.8 实测输出与 PHP 版逐行一致：

```text
1_外观调用       : txn_25000
2_子系统单独使用 : txn_999
3_子系统直接询问 : reserved 88x1
```

Java 里的对应习惯：**子系统通常声明为接口并用 `@Autowired` 注入**（依赖倒置），外观在 Spring 里就是个 `@Service`；另外 `final` 字段 + 构造注入能让"外观不该有可变状态"这条由编译器替你守住。

## 八、Go 实现

```go
package main

// InventoryService 子系统 1
type InventoryService struct{}

func (InventoryService) Reserve(sku, qty int) (string, error) {
	if qty <= 0 {
		return "", errors.New("数量必须为正")
	}
	return fmt.Sprintf("reserved %dx%d", sku, qty), nil
}

// CheckoutFacade 外观：一个用例一个入口，只做转发与编排
type CheckoutFacade struct {
	inventory     InventoryService
	payments      PaymentGateway
	notifications NotificationService
}

func NewCheckoutFacade(
	inventory InventoryService,
	payments PaymentGateway,
	notifications NotificationService,
) *CheckoutFacade {
	return &CheckoutFacade{inventory: inventory, payments: payments, notifications: notifications}
}

func (f *CheckoutFacade) Place(orderID, sku, qty, amountInCents int) (string, error) {
	if _, err := f.inventory.Reserve(sku, qty); err != nil {
		return "", err
	}
	txn, err := f.payments.Charge(amountInCents)
	if err != nil {
		return "", err
	}
	f.notifications.NotifyPaid(orderID)
	return txn, nil
}
```

**使用示例**：

```go
// 外观：调用方只调一个入口，依赖收在 New 里
facade := NewCheckoutFacade(InventoryService{}, PaymentGateway{}, NotificationService{})
txn, err := facade.Place(1001, 88, 2, 25000)   // txn = "txn_25000"，err = nil

// 外观存在也不妨碍子系统被单独使用
alone, _ := PaymentGateway{}.Charge(999)       // "txn_999"

// 子系统直接询问：不走外观
InventoryService{}.Reserve(88, 1)              // ("reserved 88x1", nil)
```

go1.26.5 实测输出（与上两语言一致）：

```text
1_外观调用       : txn_25000
2_子系统单独使用 : txn_999
3_子系统直接询问 : reserved 88x1
```

Go 里两点值得注意：

- **错误要逐个向上传**：每个子系统方法返回 `error`，外观在编排时逐项判断 —— Go 没有异常，这层"编排 + 错误短路"的样板代码比 PHP/Java 明显更长，也因此更鼓励**只包一层，别包两层**；
- **依赖用接口而非具体类型**：把 `inventory InventoryService` 换成接口（如 `Reserver`），外观就能被独立测试，这一点与 Java/PHP 的依赖倒置是同一件事。

## 九、PHP / Java / Go 对照

| | PHP | Java | Go |
| --- | --- | --- | --- |
| 外观的典型形态 | `XxxUseCase` / application service | `@Service` 用例类 | `XxxUseCase` struct |
| 依赖注入 | 构造器属性提升 | 构造注入 + 容器 | `NewXxx` 里装配 |
| 错误传播 | 异常 | 异常 | **`error` 逐层返回** |
| 子系统可独立使用 | ✅ | ✅ | ✅ |
| 最容易退化成的形态 | 塞满分支的 `XxxService` | 上帝 `@Service` | 巨型 usecase 结构体 |

三语言共通的一条：**外观是"入口"，不是"真相源"**。判据回到第四节那三条 —— 方法短、无业务分支、无内部可变状态。

## 十、面试官会追问什么

- **外观和适配器怎么选？** → 适配器是"已有接口不合调用方期望，改造形状"；外观是"接口太多，设计一个简化新口"。
- **外观和中介者的区别？** → 判据是**删掉它之后子系统是否依然完整可用**：可用 → 可选的外观；立刻退回互相直连的蛛网 → 中介者。
- **外观是不是就是那个塞满方法的 `XxxService`？** → 大概率是反面教材，三条可反射判据见第四节。
- **Laravel Facade 是 GoF 外观吗？** → 不是，是静态代理 + 容器解析（第六节）。GoF 外观在 Laravel 里的对位物是应用服务层。
- **外观会让性能变差吗？** → 只多一次方法调用，可忽略；真正的问题在"过度收敛"：把所有用例塞进一个外观，会让它变成所有改动的冲突点。
- **子系统之间需要互相通信怎么办？** → 那属于子系统内部设计，别让外观兼做调度中心；对象间互相通知该用中介者或观察者（见 [../行为型/观察者模式.md](../行为型/观察者模式.md)）。
