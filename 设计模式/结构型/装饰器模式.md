## 一、什么是装饰器模式

原文的定义：

> 装饰器模式（Decorator Pattern）：**允许向一个已有的对象添加新的功能或部分内容，同时又不改变其结构**。
> 属于**结构型模式**，它是作为现有的类的一个包装。
>
> 这种模式创建了一个**装饰类，用来包装原有的类**，并在**保持类方法签名完整性**的前提下，提供了额外的功能。

原文给出的"为什么需要它"三条理由，讲得比多数教材都直白：

> 1. 我们要对一个已有的对象添加新功能，**又不想修改它原来的结构**。
> 2. 使用**子类继承**的方法去实现添加新功能，会不可避免地出现**子类过多、继承链很长**的情况。
>    而且不少书籍都规劝我们竭力保持一个对象的父与子关系不超过 3 个。
> 3. 装饰器模式，可以提供对对象内容**快速非侵入式**地修改。

原文那句总结是本章的题眼：

> **装饰器模式使用组合和委托，而不是使用继承来解决扩展问题。**

三个角色：

| 角色 | 职责 |
| --- | --- |
| Component（组件接口） | 被装饰对象与所有装饰器**共用**的接口 |
| ConcreteComponent（具体组件） | 真正干活的原始对象 |
| Decorator（装饰器） | 也实现 Component，内部**持有**一个 Component，转发并加工 |

## 二、PHP 标准实现

场景：**数据源的多层加工**（压缩、加密、计数），三层各自独立、可任意组合。

```php
<?php

declare(strict_types=1);

/** 组件接口：被装饰对象与所有装饰器都实现它 */
interface DataSource
{
    public function write(string $data): void;

    public function read(): string;
}

/** 具体组件：真正存数据的地方 */
final class PlainDataSource implements DataSource
{
    public string $stored = '';

    public function write(string $data): void
    {
        $this->stored = $data;
    }

    public function read(): string
    {
        return $this->stored;
    }
}

/** 装饰器基类：持有一个同类型的被装饰对象 —— 组合 + 委托，不是继承 */
abstract class DataSourceDecorator implements DataSource
{
    public function __construct(protected DataSource $wrapped) {}
}

final class CompressionDecorator extends DataSourceDecorator
{
    public function write(string $data): void
    {
        $this->wrapped->write("zlib({$data})");
    }

    public function read(): string
    {
        return (string) preg_replace('/\Azlib\((.*)\)\z/s', '$1', $this->wrapped->read());
    }
}

final class EncryptionDecorator extends DataSourceDecorator
{
    public function write(string $data): void
    {
        $this->wrapped->write('enc(' . strrev($data) . ')');
    }

    public function read(): string
    {
        return strrev((string) preg_replace('/\Aenc\((.*)\)\z/s', '$1', $this->wrapped->read()));
    }
}

/** 再叠一个：统计写入次数 —— 装饰器之间互不知情 */
final class CountingDecorator extends DataSourceDecorator
{
    public int $writes = 0;

    public function write(string $data): void
    {
        $this->writes++;
        $this->wrapped->write($data);
    }

    public function read(): string
    {
        return $this->wrapped->read();
    }
}
```

**使用示例**：

```php
// 具体组件：真正存数据的地方
$plain = new PlainDataSource();

// 叠压缩 → 叠加密：写时层层包裹，读时层层还原
$stack = new EncryptionDecorator(new CompressionDecorator($plain));
$stack->write('hello');
$plain->stored;        // "zlib(enc(olleh))"
$stack->read();        // "hello"

// 计数装饰器只加统计，其它装饰器毫不知情
$counting = new CountingDecorator($stack);
$counting->write('a');
$counting->writes;     // 1
```

实测（PHP 8.0.2 CLI）：

```text
1_压缩→加密 实际落盘 : zlib(enc(olleh))
2_加密→压缩 实际落盘 : enc()olleh(bilz)
3_两者读回来相同吗   : true
4_三层叠加·写入次数  : 2
5_三层叠加·读回原值  : b
```

### 4 个让它算「标准写法」的细节

| # | 做法 | 为什么 |
| --- | --- | --- |
| 1 | 装饰器**也实现 Component 接口** | 这是"可以再被装饰"的前提，也是与代理最容易搞混的一点 |
| 2 | 用抽象基类收拢 `$wrapped` | 每个装饰器都要存一个被装饰对象，抽到基类省样板 |
| 3 | 装饰器之间**互不知情** | `CountingDecorator` 不知道外面还有加密，它只按接口转发 |
| 4 | 被装饰对象从构造器传入，不在装饰器里 `new` | 否则无法任意排列组合，也测不了 |

## 三、顺序即语义

实测第 1、2 行的落盘内容**完全不同**：

| 叠加方式 | 落到最底层的字节 |
| --- | --- |
| `Encryption(Compression(plain))` | `zlib(enc(olleh))` |
| `Compression(Encryption(plain))` | `enc()olleh(bilz)` |

而第 3 行说明：**两者读回来是一样的**（`true`），因为每个装饰器的读路径与写路径是对称的。

**那顺序为什么还重要？** 因为这种对称只在自己这一栈内成立：

- 如果数据会被**别处**读取（另一个服务、另一个版本的代码、离线任务），它必须知道"先解哪个"；
- 一旦某一层的实现变了（比如压缩从 `zlib` 换成 `gzip`），**旧数据能不能读出来，取决于当初哪一层在最外面**；
- 排错时也一样：日志里是 `zlib(enc(...))`，你要能一眼看出包装层次。

所以结论是：**装饰顺序要作为契约固定下来**（如"加密永远在最外层"），并写进文档 —— 它不是审美问题。

## 四、原文实现的辨析：钩子列表 vs 包装

原文的结构是这样的：

- 定义一个 `Decorator` 接口，含 `beforeDo()` / `afterDo()`；
- 被装饰类 `User` **内部用一个数组收集装饰器**，在 `eat()` 里遍历调用它们的 `beforeDo` / `afterDo`。

这是**钩子列表**（更接近观察者 + 模板方法的混合），而不是标准装饰器。两者差别很实质：

| | 原文的钩子列表 | 标准装饰器（本篇实现） |
| --- | --- | --- |
| 装饰器与组件接口 | **不同**（一个 `beforeDo`，一个 `eat`） | **完全相同** |
| 能否嵌套同类 | 不能 | 能（压缩外面还能再包一层） |
| 被装饰者是否知情 | **知情**（它自己遍历数组） | 完全不知情 |
| 扩展点 | 固定两个钩子（`before` / `after`） | 任意方法 |
| 适合什么 | 固定的"前后各跑一段" | 可叠加的行为层 |

原文的实现本身**能用**，而且在"就想要前后两个扩展点"时比标准装饰器更省事 —— 框架里的 `beforeXxx/afterXxx`、事件钩子都是这个思路。但它的能力上限也明显：**做不了"中间"的加工**（比如把数据换一种编码再交给内层），因为它没有"转发 + 加工"这个环节，只有"前置通知"和"后置通知"。

一句话区分：**钩子列表改的是"什么时候被通知"，标准装饰器改的是"数据怎么流过层层包装"**。

## 五、边界：装饰器 vs 代理 vs 继承

| | 装饰器 | 代理 | 继承 |
| --- | --- | --- | --- |
| 接口 | 完全相同 | 完全相同 | 子类可扩展 |
| 意图 | **增加行为** | **控制访问** | 复用实现 |
| 多层叠加 | **天生支持**（顺序即语义） | 少见（叠两层缓存代理没意义） | 层数越多越脆 |
| 被包装对象来源 | **调用方传入** | 代理**自己决定** | 编译期固定 |
| 运行时组装 | ✅ | ✅ | ❌ |

最实用的判据：**能不能在运行时自由排列组合**。装饰器天生为此设计（`Encryption(Compression(Counting(plain)))`），继承做不到，代理也不做这个。

至于原文引用的"父与子关系不超过 3 个"—— 用装饰器替换继承带来的直接好处是**子类数量从指数级降到线性**：3 种加工能力用继承要 8 个组合子类，用装饰器只要 3 个装饰器类。

## 六、Java / Go 实现

### Java 实现

```java
/** 组件接口：被装饰对象与所有装饰器都实现它 */
interface DataSource {
    void write(String data);

    String read();
}

/** 装饰器基类：持有一个同类型的被装饰对象 —— 组合 + 委托，不是继承 */
abstract static class DataSourceDecorator implements DataSource {
    protected final DataSource wrapped;

    DataSourceDecorator(DataSource wrapped) { this.wrapped = wrapped; }
}

static final class CompressionDecorator extends DataSourceDecorator {
    CompressionDecorator(DataSource wrapped) { super(wrapped); }

    public void write(String data) { wrapped.write("zlib(" + data + ")"); }

    public String read() { return wrapped.read().replaceAll("^zlib\\((.*)\\)$", "$1"); }
}

static final class EncryptionDecorator extends DataSourceDecorator {
    EncryptionDecorator(DataSource wrapped) { super(wrapped); }

    public void write(String data) { wrapped.write("enc(" + reverse(data) + ")"); }

    public String read() { return reverse(wrapped.read().replaceAll("^enc\\((.*)\\)$", "$1")); }
}
```

**使用示例**：

```java
// 具体组件：真正存数据的地方
PlainDataSource plain = new PlainDataSource();

// 装饰器实现同一个 DataSource 接口，可透明替换
DataSource stack = new EncryptionDecorator(new CompressionDecorator(plain));
stack.write("hello");        // 落盘 "zlib(enc(olleh))"
stack.read();                // "hello"（读时逐层剥掉包装）

// 换个叠法：顺序不同则落盘不同，读回仍一致
PlainDataSource plain2 = new PlainDataSource();
DataSource stack2 = new CompressionDecorator(new EncryptionDecorator(plain2));
stack2.write("hello");       // 落盘 "enc()olleh(bilz)"
stack2.read();               // "hello"
```

JDK 1.8 实测输出与 PHP 版逐行一致：

```text
1_压缩→加密 实际落盘 : zlib(enc(olleh))
2_加密→压缩 实际落盘 : enc()olleh(bilz)
3_两者读回相同吗     : true
4_三层叠加·写入次数  : 2
5_三层叠加·读回原值  : b
```

Java 里装饰器最出名的落地是 **`java.io` 的流**：`new BufferedReader(new InputStreamReader(new FileInputStream(...)))` 就是标准的装饰器链 —— `FileInputStream` 是具体组件，其余都是装饰器，层层包装且接口（`InputStream` / `Reader`）保持一致。

### Go 实现

Go 里装饰器用"结构体 + 接口字段"，而不是继承一个基类：

```go
// DataSource 组件接口
type DataSource interface {
	Write(data string)
	Read() string
}

// CompressionDecorator 装饰器：组合 + 委托，不是继承
type CompressionDecorator struct {
	wrapped DataSource
}

func (d CompressionDecorator) Write(data string) { d.wrapped.Write("zlib(" + data + ")") }

func (d CompressionDecorator) Read() string {
	s := d.wrapped.Read()
	if len(s) > 6 && s[:5] == "zlib(" && s[len(s)-1] == ')' {
		return s[5 : len(s)-1]
	}
	return s
}
```

**使用示例**：

```go
// 具体组件：本身就是一个 DataSource
plain := &PlainDataSource{}

// 装饰器也实现 DataSource，所以能替换它、也能再被别人包
var src DataSource = CompressionDecorator{wrapped: plain}
src.Write("hello")
src.Read()          // "hello"（写时加 zlib()，读时自动剥掉）

// 装饰器不是必经关卡：被装饰者仍可单独使用
plain.Read()        // "zlib(hello)"
```

go1.26.5 实测输出（与 PHP/Java 一致）：

```text
1_压缩→加密 实际落盘 : zlib(enc(olleh))
2_加密→压缩 实际落盘 : enc()olleh(bilz)
3_两者读回相同吗     : true
4_三层叠加·写入次数  : 2
5_三层叠加·读回原值  : b
```

Go 的两点差异：

- **没有继承，用"接口字段 + 方法转发"实现同样效果**；要覆盖很多方法时，可以用**结构体嵌入接口**省掉转发样板（未覆盖的方法自动转发，见 [代理模式.md](代理模式.md) 第八节）；
- **Go 的惯用装饰器常是函数式**：`func(http.Handler) http.Handler` 这种"接收 handler 返回 handler"的中间件，本质上就是装饰器，比建类更轻。标准库与主流框架（`net/http` 中间件、gRPC interceptor）都采用这个形状。

## 七、三语言对照

| | PHP | Java | Go |
| --- | --- | --- | --- |
| 装饰器基类 | `abstract class` + 构造注入 | `abstract class` + 构造注入 | 结构体 + 接口字段 |
| 再被装饰的条件 | 装饰器实现组件接口 | 同 | 同 |
| 最典型落地 | PSR-7 / PSR-15 中间件栈 | `java.io` 流链 | `http.Handler` 中间件 |
| 函数式替代 | 闭包 `fn($next)` | `Function<T,T>` 组合 | **`func(next T) T`**（最主流） |
| 层数多了怎么查 | 逐层打日志 | 同 | 同 |

三语言共通：**装饰器的价值在"运行时自由叠加"，代价在"层数不透明"** —— 包装深了之后，读代码时不容易看清一次调用穿过几层，所以叠加层数要克制、顺序要固定。

## 八、面试官会追问什么

- **装饰器和继承怎么选？** → 扩展维度固定且只有一两个时继承更简单；**多个可叠加的扩展维度**用装饰器 —— 3 种能力用继承要 8 个组合子类，用装饰器只要 3 个类。
- **装饰器和代理的区别？** → 接口都相同，区别在意图：装饰器**增加行为**（被装饰对象由调用方传入，天生叠加）；代理**控制访问**（自己决定真实对象是谁、何时创建）。
- **装饰器和适配器的区别？** → 适配器**改接口形状**，装饰器**保持接口不变**。
- **装饰顺序重要吗？** → 重要。实测 `zlib(enc(olleh))` 与 `enc()olleh(bilz)` 落盘完全不同；对称的读路径让两者都能读回来，但**跨服务/跨版本读数据时，顺序就是契约**。
- **原文那种"beforeDo/afterDo 钩子"算装饰器吗？** → 严格说不算，那是钩子列表（更接近观察者 + 模板方法）。扩展点固定在"前后"，做不了"把数据加工后交给内层"；但框架里的 `beforeXxx/afterXxx` 确实是这个思路。
- **PHP 里装饰器用在哪？** → PSR-7 / PSR-15 中间件栈（`$handler->handle($request)` 层层转发）、各类 SDK 的重试/日志包装、缓存层。
