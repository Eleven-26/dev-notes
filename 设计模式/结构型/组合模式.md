## 一、什么是组合模式

原文的定义：

> 组合模式（Composite Pattern），又叫**部分整体模式**，是用于**把一组相似的对象当作一个单一的对象**。
> 组合模式**依据树形结构来组合对象**，用来表示部分以及整体层次。这种类型的设计模式属于结构型模式，
> 它**创建了对象组的树形结构**。

原文的应用场景两条也很到位：

> 1. 在树型结构的问题中，**模糊了简单元素和复杂元素的概念**，客户程序可以像处理简单元素一样来处理复杂元素，
>    从而使得客户程序与复杂元素的内部结构解耦。
> 2. 组合模式让你可以**优化处理递归或分级数据结构**。

三个角色：

| 角色 | 职责 | PHP 里的形态 |
| --- | --- | --- |
| Component（组件） | 叶子与容器的**共同接口** | `interface Node` |
| Leaf（叶子） | 没有子节点 | `FileNode` |
| Composite（容器） | **本身也是 Component**，可容纳任意多个 Component | `DirectoryNode` |

**"容器本身也是组件"是组合模式的唯一难点，也是它全部力量的来源** —— 因为容器也是 `Node`，容器就能装容器，树自然长出来，而调用方不需要区分。

## 二、PHP 标准实现

场景：**文件系统树**。文件返回自身字节数，目录返回所有子项之和，调用方对两者用同一个方法。

```php
<?php

declare(strict_types=1);

/** 组件接口：叶子和容器都实现它 —— 调用方不必区分 */
interface Node
{
    public function name(): string;

    /** 文件返回自身字节数；目录返回所有子项之和 */
    public function size(): int;
}

/** 叶子：没有子节点 */
final class FileNode implements Node
{
    public function __construct(
        private string $name,
        private int $bytes
    ) {}

    public function name(): string
    {
        return $this->name;
    }

    public function size(): int
    {
        return $this->bytes;
    }
}

/** 容器：本身也是 Node，所以可以嵌任意层 */
final class DirectoryNode implements Node
{
    /** @var list<Node> */
    private array $children = [];

    public function __construct(
        private string $name,
        private bool $allowCycle = false
    ) {}

    public function add(Node $node): void
    {
        // 防环的关键：要加进来的这个 node 的子树里，不能已经包含 $this
        if (!$this->allowCycle && ($node === $this || ($node instanceof self && $node->contains($this)))) {
            throw new RuntimeException("不允许成环：{$node->name()}");
        }
        $this->children[] = $node;
    }

    /** 判断 $target 是否在本子树里（含自身） */
    public function contains(Node $target): bool
    {
        if ($target === $this) {
            return true;
        }
        foreach ($this->children as $child) {
            if ($child instanceof self && $child->contains($target)) {
                return true;
            }
        }
        return false;
    }

    public function name(): string
    {
        return $this->name;
    }

    /** 递归求和 —— 组合模式里唯一需要"知道自己是谁"的地方 */
    public function size(): int
    {
        $total = 0;
        foreach ($this->children as $child) {
            $total += $child->size();
        }
        return $total;
    }
}

/** 调用方只依赖 Node，不需要知道是文件还是目录 */
function totalSize(Node $node): int
{
    return $node->size();
}
```

**使用示例**：

```php
// 叶子：文件直接构造，size() 返回自身字节数
$readme = new FileNode('README.md', 1200);

// 容器：add 接收 Node，文件、目录都能塞
$src = new DirectoryNode('src');
$src->add(new FileNode('index.php', 800));
$src->add($readme);
$src->size();                  // 2000（递归求和）

// 容器可再嵌套（目录里放目录），调用方只认 Node
$root = new DirectoryNode('project');
$root->add($src);              // 不必区分加进来的是文件还是目录

// 成环会被拦下，间接环（把祖先加进后代）也一样
$src->add($root);              // 抛 RuntimeException：不允许成环：project
```

实测（PHP 8.0.2 CLI）：

```text
1_叶子文件大小        : 1200
2_目录大小（递归求和）: 2300
3_根目录大小          : 3800
4_叶子与目录同一接口  : true
5_直接成环被拒        : 不允许成环：project
6_间接成环也被拒      : 不允许成环：project
```

**第 4 行是组合模式的全部意义**：`totalSize()` 的参数类型只有一个 `Node`，它既接受文件也接受目录 —— 而且是**递归地接受**（`root.size()` 内部会调 `src.size()`，再调每个文件的 `size()`）。

### 4 个让它算「标准写法」的细节

| # | 做法 | 为什么 |
| --- | --- | --- |
| 1 | 容器**也实现** Component 接口 | 否则容器不能装容器，树就只有两层 |
| 2 | 递归逻辑只写在**容器**里 | 叶子不需要知道树的存在，`size()` 直接返回字节数 |
| 3 | 调用方只依赖 Component | `totalSize(Node $node)` 一个参数走天下，调用方不含任何 `instanceof` |
| 4 | `add()` 做**防环校验** | 否则 `size()` 会无限递归 —— 这是组合模式最危险的失效方式（见第四节） |

## 三、透明性 vs 安全性

组合模式有一个绕不开的设计选择：**`add()` / `remove()` 该定义在哪里？**

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **透明型** | 把 `add/remove` 也放进 Component 接口 | 调用方完全一致，无需判断类型 | 叶子被迫实现 `add()`（空实现或抛异常），违反接口隔离 |
| **安全型**（本篇采用） | `add/remove` 只定义在容器上 | 接口干净，叶子不可能被误加子节点 | 组装树时调用方要知道"哪个是容器" |

本篇选了**安全型**：`FileNode` 上没有 `add()`，所以"给文件加子文件"这种错误**在静态分析阶段**就不成立 —— 只有 `DirectoryNode` 才能 `add()`。

原文的实现把 `addUnit/removeUnit` 放在 `CompositeUnit` 上（属于安全型思路），但它让 `Archer`、`Cavalry` 这些叶子**也继承了 `CompositeUnit`** —— 结果是"弓箭手能 `addUnit`"，这显然是荒谬的。**把叶子从容器继承链里摘出来**，是这类实现最容易犯的错。

选择建议：**树的组装通常在启动时一次完成，调用方本来就知道谁是容器 → 选安全型**；只有在"拿到一个 Node 就要往里塞东西"的动态场景下才需要透明型。

## 四、防环：间接环才是最危险的

实测第 5、6 行是两个不同的环：

- **直接环**：`root->add(root)` —— 自己装自己；
- **间接环**：`src->add(root)` —— 把**祖先**装进**后代**，形成 `root → src → root`。

后果相同：**任何递归操作（`size()`、遍历、序列化）都会无限递归**，最终栈溢出或内存耗尽。区别在于直接环一眼能看出来，间接环藏在多层结构里，往往等到运行时才暴露。

**检测的正确写法**（本篇实现的关键）：

```php
// 要加进来的这个 node 的子树里，不能已经包含 $this
if ($node === $this || ($node instanceof self && $node->contains($this))) {
    throw new RuntimeException(...);
}
```

注意判据的方向：**不是"$this 里有没有 $node"，而是"$node 里有没有 $this"**。前者只能挡住直接自引用 —— 我在第一版实现里就写反了，实测时发现 `src->add(root)` 没被拦住；后者才能挡住间接环，因为"把祖先塞进后代"的本质就是"这个要加进来的节点，祖先链里已经有我了"。

检查代价是 O(子树大小)，但**建树是低频操作、遍历是高频操作**，这个交换很划算。

## 五、组合 vs 装饰器

两者都靠"实现同一个接口"这一招，容易混：

| | 组合 | 装饰器 |
| --- | --- | --- |
| 结构 | **树**（一对多） | **链**（一对一） |
| 子节点数量 | 任意多个 | 恰好一个 |
| 目的 | 统一"部分"与"整体" | 在接口不变的前提下加行为 |
| 递归方向 | 父 → 所有子 | 外 → 内（层层转发） |
| 典型例子 | 文件系统、组织架构、菜单树 | PSR-15 中间件、`java.io` 流链 |

一句话：**组合是"一对多 + 递归"，装饰器是"一对一 + 转发"**。

## 六、Java / Go 实现

### Java 实现

```java
/** 组件接口：叶子和容器都实现它 */
interface Node {
    String name();

    int size();
}

/** 叶子 */
static final class FileNode implements Node {
    private final String name;
    private final int bytes;

    FileNode(String name, int bytes) {
        this.name = name;
        this.bytes = bytes;
    }

    public String name() { return name; }

    public int size() { return bytes; }
}

/** 容器：本身也是 Node，可以嵌任意层 */
static final class DirectoryNode implements Node {
    private final String name;
    private final List<Node> children = new ArrayList<Node>();

    void add(Node node) {
        // 防环的关键：要加进来的这个 node 的子树里，不能已经包含 this
        if (node == this
                || (node instanceof DirectoryNode && ((DirectoryNode) node).contains(this))) {
            throw new IllegalStateException("不允许成环：" + node.name());
        }
        children.add(node);
    }

    boolean contains(Node target) {
        if (target == this) {
            return true;
        }
        for (Node child : children) {
            if (child instanceof DirectoryNode && ((DirectoryNode) child).contains(target)) {
                return true;
            }
        }
        return false;
    }

    public String name() { return name; }

    public int size() {
        int total = 0;
        for (Node child : children) {
            total += child.size();
        }
        return total;
    }
}
```

**使用示例**：

```java
// 叶子：文件直接构造，size() 返回自身字节数
FileNode readme = new FileNode("README.md", 1200);

// 容器：add 接收 Node，文件、目录都能塞
DirectoryNode src = new DirectoryNode("src");
src.add(new FileNode("index.php", 800));
src.add(readme);
src.size();                   // 2000（递归求和）

// 容器可再嵌套，调用方只认 Node 一个接口
DirectoryNode root = new DirectoryNode("project");
root.add(src);                // 不必区分加进来的是文件还是目录

// 成环会被拦下，间接环（把祖先加进后代）也一样
src.add(root);                // 抛 IllegalStateException：不允许成环：project
```

JDK 1.8 实测输出与 PHP 版逐行一致：

```text
1_叶子文件大小        : 1200
2_目录大小（递归求和）: 2300
3_根目录大小          : 3800
4_叶子与目录同一接口  : true
5_直接成环被拒        : 不允许成环：project
6_间接成环也被拒      : 不允许成环：project
```

Java 里最容易想到的"组合"落地是 **`java.io.File`**：一个 `File` 既可能是文件也可能是目录，`listFiles()` 返回 `File[]`，天然递归 —— 只是它没把"文件"和"目录"拆成两个类，所以享受不到"统一接口"的好处。本目录的写法才是教科书形态。

### Go 实现

```go
// Node 组件接口：叶子和容器都实现它
type Node interface {
	Name() string
	Size() int
}

// DirectoryNode 容器：本身也是 Node
type DirectoryNode struct {
	DirName  string
	children []Node
}

func (d *DirectoryNode) Add(node Node) error {
	// 防环的关键：要加进来的这个 node 的子树里，不能已经包含 d
	if node == Node(d) {
		return errors.New("不允许成环：" + node.Name())
	}
	if dir, ok := node.(*DirectoryNode); ok && dir.Contains(d) {
		return errors.New("不允许成环：" + node.Name())
	}
	d.children = append(d.children, node)
	return nil
}

// Size 递归求和
func (d *DirectoryNode) Size() int {
	total := 0
	for _, child := range d.children {
		total += child.Size()
	}
	return total
}
```

**使用示例**：

```go
// 叶子：文件直接构造，Size() 返回自身字节数
readme := FileNode{FileName: "README.md", Bytes: 1200}

// 容器：Add 接收 Node，文件、目录都能塞
src := &DirectoryNode{DirName: "src"}
_ = src.Add(FileNode{FileName: "index.php", Bytes: 800})
_ = src.Add(readme)
src.Size()              // 2000（递归求和）

// 容器可再嵌套，调用方只认 Node 一个接口
root := &DirectoryNode{DirName: "project"}
_ = root.Add(src)

// 成环被拦下：Add 返回 error，间接环（祖先加进后代）也一样
_ = src.Add(root)       // error: 不允许成环：project
```

go1.26.5 实测输出（与 PHP/Java 一致）：

```text
1_叶子文件大小        : 1200
2_目录大小（递归求和）: 2300
3_根目录大小          : 3800
4_叶子与目录同一接口  : true
5_直接成环被拒        : 不允许成环：project
6_间接成环也被拒      : 不允许成环：project
```

Go 的两点差异：

- **接口是隐式实现**，所以"叶子与容器实现同一接口"**在编译期自动成立**（本实现里 `var asFile Node = readme` 一行就是证明），不需要 `implements` 关键字；
- **类型断言替代 `instanceof`**：防环检查要判断"这个 Node 是不是容器"，Go 用 `node.(*DirectoryNode)` 两步断言（值 + 布尔），比 PHP 的 `instanceof` 多一个返回值要处理，但不会抛异常。

## 七、三语言对照

| | PHP | Java | Go |
| --- | --- | --- | --- |
| 组件接口 | `interface` + `implements` | `interface` + `implements` | 隐式实现 |
| 容器判断 | `instanceof` | `instanceof` | **类型断言** `v, ok := x.(T)` |
| 子节点容器 | `array` | `List` | `slice` |
| 防环策略 | 子树包含检查 | 同 | 同 |
| 递归深度保护 | PHP 栈限制 / `xdebug` | JVM 栈 | goroutine 栈（更大） |

三语言共通的一条：**组合模式的风险几乎全在"树的形状"上** —— 成环、深度过大、共享子树被多次遍历。所以别把 `add()` 暴露得太自由，能在构造时就固定结构的，就别做成可变容器。

## 八、面试官会追问什么

- **组合模式的核心是什么？** → **容器本身也是组件**（实现同一接口），于是树可以任意嵌套，调用方不必区分叶子与容器。
- **透明型和安全性怎么选？** → 透明型把 `add/remove` 放接口里（叶子被迫空实现或抛异常，违反接口隔离）；安全型只放在容器上（组装时要区分类型）。树在启动时一次组装完 → 选安全型。
- **组合模式最常见的 bug 是什么？** → **成环导致无限递归**。直接环（自己加自己）容易发现，**间接环**（祖先被加进后代）才是重点；检测方向必须是"要加进来的节点里不能包含自己"（实测第 6 行）。
- **组合和装饰器怎么区分？** → 组合是"一对多 + 递归"（树），装饰器是"一对一 + 转发"（链）。
- **遍历顺序怎么控制？** → 树形遍历可以照搬迭代器模式（PHP 用 `RecursiveIterator`，Java 用递归 `Iterable`，Go 用回调或 `iter.Seq`），详见 [../行为型/迭代器模式.md](../行为型/迭代器模式.md)。
- **组合模式适合什么场景？** → 文件系统、组织架构、商品分类、菜单与权限树，任何"整体与部分要统一对待"的层级结构。
