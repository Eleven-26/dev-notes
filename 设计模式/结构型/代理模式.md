## 一、什么是代理模式

原文的定义与角色分析：

> 给某一个对象提供一个**代理**，并由代理对象**控制对原对象的引用**。代理模式的英文叫做 Proxy 或 Surrogate，
> 它是一种**对象结构型模式**。

> 1. **抽象主题角色（Subject）**：定义了 RealSubject 和 Proxy 公用接口，这样就在任何使用 RealSubject 的地方都可以使用 Proxy。
> 2. **真正主题角色（RealSubject）**：定义了 Proxy 所代表的真实实体。
> 3. **代理对象（Proxy）**：保存一个引用使得代理可以访问实体，并提供一个与 RealSubject 接口相同的接口，
>    这样代理可以用来代替实体。

原文的动机也说得很清楚：

> 在某些情况下，一个客户不想或者不能直接引用一个对象，此时可以通过一个称之为"代理"的第三者来实现**间接引用**。
> 代理对象可以在客户端和目标对象之间起到中介的作用，并且可以通过代理对象**去掉客户不能看到的内容和服务**或者**添加客户需要的额外服务**。

**"接口完全相同"是代理的立身之本** —— 三个角色里，抽象主题存在的唯一理由就是让 Proxy 能替换掉 RealSubject。这句话在第五、六节还要反复用到。

## 二、应用场景

原文一口气列了八种，这是全系列里最全的一份场景清单：

| 类型 | 原文描述 | 一句话用途 |
| --- | --- | --- |
| 远程（Remote）代理 | 为不同地址空间的对象提供本地代理，也叫大使（Ambassador） | 跨进程/跨网络的本地代表 |
| 虚拟（Virtual）代理 | 资源消耗大的对象，先造一个轻量替身，真实对象需要时才创建 | **延迟加载** |
| Copy-on-Write 代理 | 把克隆推迟到真正需要时 | 深拷贝很贵时的写时复制 |
| 保护（Protect/Access）代理 | 控制访问，给不同用户不同权限 | 权限校验 |
| 缓冲（Cache）代理 | 为目标操作的结果提供临时存储，多个客户端共享 | 结果缓存 |
| 防火墙（Firewall）代理 | 保护目标不让恶意用户接近 | 网络层的访问控制 |
| 同步化（Synchronization）代理 | 让几个用户能同时使用一个对象而不冲突 | 并发访问串行化 |
| 智能引用（Smart Reference）代理 | 对象被引用时提供额外操作，如记录被调用次数 | 引用计数、调用审计 |

名目虽多，但**都是在同一个位置上做同一件事：拦一次访问，加点东西**。本篇据此挑最常用的四类（虚拟、缓存、保护、远程）写成可跑代码。

三条判据，缺一条就不是代理：

1. 替身与目标**面向同一个接口**；
2. 目标（或其"构造配方"）从**外面进来**，不是替身在业务里自己造别的对象；
3. 加的那一层做的是**控制访问**（时机 / 次数 / 放行），不是新行为 —— 加日志、压缩、重试是 [装饰器模式.md](装饰器模式.md) 的活。

## 三、PHP 标准实现

### 3.1 抽象主题用接口，不用抽象类

原文用的是 `abstract class Subject`。**标准做法是 `interface`** —— 理由不是风格洁癖：PHP 是单继承，抽象类会占掉子类**唯一**的继承位。一旦 `RealSubject` 还需要继承别的基类（或 `Proxy` 需要复用一个通用转发 trait），继承体系立刻卡死。原文自己写的是"定义了 RealSubject 和 Proxy 公用**接口**"，用 `interface` 才名副其实。

```php
<?php

declare(strict_types=1);

/** 角色常量（PHP 8.0 没有 enum，用类常量） */
final class Role
{
    public const ADMIN = 'admin';
    public const GUEST = 'guest';
}

/** 抽象主题：真实主题与代理共用同一个接口 */
interface DocumentRepository
{
    public function find(int $id): string;
}

/** 真实主题：昂贵操作（真实项目里是查库 + 反序列化 + 渲染） */
final class DatabaseDocumentRepository implements DocumentRepository
{
    /** @var list<int> 记录真实被查过的 id —— 证明代理确实拦住了访问 */
    public static array $queries = [];

    public function find(int $id): string
    {
        self::$queries[] = $id;
        return "doc#{$id}";
    }
}
```

### 3.2 四类代理，各控制一种「访问」

```php
/** 虚拟代理：真实对象只在第一次访问时才创建 */
final class LazyDocumentRepository implements DocumentRepository
{
    private ?DocumentRepository $real = null;

    /** @param Closure(): DocumentRepository $factory */
    public function __construct(private Closure $factory) {}

    public function find(int $id): string
    {
        $this->real ??= ($this->factory)();
        return $this->real->find($id);
    }

    public function isRealCreated(): bool
    {
        return $this->real !== null;
    }
}

/** 缓存代理：为同一目标操作的结果提供临时存储，多个客户端共享 */
final class CachedDocumentRepository implements DocumentRepository
{
    /** @var array<int,string> */
    private array $cache = [];

    public function __construct(private DocumentRepository $inner) {}

    public function find(int $id): string
    {
        return $this->cache[$id] ??= $this->inner->find($id);
    }
}

/** 保护代理：按角色决定放行还是拒绝 */
final class GuardedDocumentRepository implements DocumentRepository
{
    public function __construct(
        private DocumentRepository $inner,
        private string $role
    ) {}

    public function find(int $id): string
    {
        if ($this->role !== Role::ADMIN) {
            throw new RuntimeException("角色 {$this->role} 无权访问文档 {$id}");
        }
        return $this->inner->find($id);
    }
}
```

**使用示例**：

```php
// 虚拟代理：注入工厂，真实对象第一次访问才构造
$lazy = new LazyDocumentRepository(static fn (): DocumentRepository => new DatabaseDocumentRepository());
$lazy->isRealCreated();      // false
$lazy->find(1);              // "doc#1"，此刻才创建真实对象

// 缓存代理：同一 id 第二次不再落到真实对象
$cached = new CachedDocumentRepository(new DatabaseDocumentRepository());
$cached->find(2);
$cached->find(2);            // 命中缓存，真实对象只被查一次

// 保护代理：角色不符直接拒绝
$guarded = new GuardedDocumentRepository(new DatabaseDocumentRepository(), Role::GUEST);
$guarded->find(4);           // 抛 RuntimeException：guest 无权访问
```

实测（PHP 8.0.2 CLI）：

```text
1a_访问前真实对象已创建 : false
1b_访问结果             : doc#1
1c_访问后已创建         : true
2_真实查询次数（应为 2）: 2 -> [2,3]
3_保护代理拒绝          : 角色 guest 无权访问文档 4
4a_叠加代理第一次       : doc#5
4b_叠加代理第二次       : doc#5
4c_真实查询次数（应为 1）: 1
```

读法：

- **1a/1c 是虚拟代理的全部价值**：没访问之前真实对象**根本不存在**（`false` → 访问 → `true`）。这就是原文说的"真实对象只在需要时才会被真正创建"。
- **第 2 行是缓存代理**：`find(2)` 调了两次、`find(3)` 一次，真实对象只被查了 2 次（`[2,3]`），第二次 `find(2)` 被缓存挡住。
- **第 3 行是保护代理**：拒绝发生在**代理层**，真实对象完全不知道有人来过。
- **第 4 组是代理可以叠加**：`保护 → 缓存 → 虚拟` 串成三层，调用方只认 `DocumentRepository` 一个接口，两次 `find(5)` 只落到真实对象一次。**能叠加，正是因为三者接口完全一致。**

### 4 个让它算「标准写法」的细节

| # | 做法 | 为什么 |
| --- | --- | --- |
| 1 | 抽象主题用 `interface` | PHP 单继承，抽象类会占掉唯一继承位 |
| 2 | 代理持有**接口类型**而不是 `RealSubject` | 才能代理同接口的任意实现（含另一个代理），第 4 组的叠加就靠这条 |
| 3 | 真实对象**注入进来，不在构造器里 `new`** | 虚拟代理因此能把"创建"推迟到第一次访问；原文构造器里直接 `new` 就把这个可能性堵死了 |
| 4 | 代理类自己 `final` | 代理不是给继承用的；要扩展行为应该再叠一层代理 |

## 四、原文写法的两个问题

### 4.1 构造函数里的「无参分支」是坏的（实测致命错误）

原文的代理构造器允许不传真实对象，此时自己造一个：

```php
public function __construct(RealSubject $realSubject = null)
{
    if (empty($realSubject)) {
        $this->realSubject = new RealSubject();   // ⚠️ 没有传参
    }
    ...
}
```

而 `RealSubject::__construct($name)` 的 `$name` **没有默认值**。本机实测 `new Proxy()`（走无参分支）：

```text
PHP Fatal error:  Uncaught ArgumentCountError: Too few arguments to function RealSubject::__construct(),
0 passed in ... and exactly 1 expected
```

这是"默默替调用方做决定"的代价 —— 那个分支从写下的那天起就没跑通过。标准做法是**要么必须传，要么注入工厂**（如 3.2 的 `Closure $factory`），把"怎么造"交给调用方表达。

### 4.2 类型声明写成具体类，代理能力被砍一半

原文代理里声明的是具体类。一旦类型是具体类，就意味着**这个代理只能代理它**，不能代理同接口的其它实现，也不能把两个代理叠起来。改成接口类型后，第 4 组的 `保护(缓存(虚拟))` 才成立。

## 五、PHP 没有 JDK 那种动态代理，只有两条路

Java 可以在运行时生成代理类（见第七节），PHP **没有**；想"不手写转发方法"只有两条路：

| 路线 | 做法 | 代价 |
| --- | --- | --- |
| 魔术方法 `__call` / `__callStatic` | 拦截未定义的方法，统一转发 | 只对"没声明的方法"生效。**代理若实现了接口，接口方法必须显式声明**，否则 `__call` 拦不到；且 IDE 无法跳转、参数不做类型检查 |
| 代码生成 | 用扩展或第三方库在编译期/首次运行时生成代理类 | 需要额外依赖与缓存目录；换来**类型完整、可静态分析** |

Laravel 的 `Facade` 基类走的是第一条路的静态版（`__callStatic` 从容器解析实例再转发），它解决的是"静态调用语法 + 可测试替换"，**与 GoF 代理的"控制访问"目的不同**（辨析见 [外观模式.md](外观模式.md) 第六节）。

实践结论：**PHP 里手写代理是常态** —— 一个接口的方法数通常有限，手写能保住类型与可跳转性；真到了"几十个方法都要转发"，才值得引入代码生成。

## 六、边界：代理 vs 装饰器 vs 适配器 vs 外观

这四个都"包一层"，面试最爱放在一起问。判据是**包这一层改了什么**：

| 模式 | 接口 | 目的 | 一句话区分 |
| --- | --- | --- | --- |
| **代理** | **完全相同** | 控制**访问**（延迟、缓存、权限、远程） | 还是那个东西，只是"要通过我" |
| **装饰器** | 完全相同 | **增加行为**（可叠加多层） | 还是那个东西，但"变得更强了" |
| **适配器** | **改成另一个** | 让不兼容的接口能用 | 换成"另一个东西" |
| **外观** | **简化/收敛** | 把 N 个子系统收成 1 个入口 | 把"一堆东西"变成"一个入口" |

代理与装饰器最难分，**看意图**：代理通常**自己决定**真实对象是谁、要不要创建（虚拟代理甚至改变"对象何时存在"）；装饰器必须由调用方把被装饰对象传进来。另一条直观判据：**代理一般不允许同类多层叠加**（叠两层缓存代理意义不大），装饰器天生为叠加而设计。

一个刻意的例外：**只读视图**（收窄到目标接口的子集）也常被归为保护代理 —— 它实现了接口的**一部分**，用"少实现几个方法"来表达"这条路根本不提供"。

## 七、Java 实现

Java 里代理有两种写法，第二种是 PHP 没有的：

```java
import java.lang.reflect.InvocationHandler;
import java.lang.reflect.Method;
import java.lang.reflect.Proxy;

public class ProxyStandard {

    /** 抽象主题 */
    interface DocumentRepository {
        String find(int id);
    }

    /** 真实主题 */
    static final class DatabaseDocumentRepository implements DocumentRepository {
        static final List<Integer> QUERIES = new ArrayList<Integer>();

        public String find(int id) {
            QUERIES.add(id);
            return "doc#" + id;
        }
    }

    /** JDK 动态代理：不用为每个接口手写代理类 */
    static final class LoggingHandler implements InvocationHandler {
        private final Object target;

        LoggingHandler(Object target) { this.target = target; }

        public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
            System.out.println("   before " + method.getName());
            Object result = method.invoke(target, args);
            System.out.println("   after  " + method.getName() + " -> " + result);
            return result;
        }

        @SuppressWarnings("unchecked")
        static <T> T wrap(T target, Class<T> iface) {
            return (T) Proxy.newProxyInstance(
                    iface.getClassLoader(),
                    new Class<?>[] { iface },
                    new LoggingHandler(target));
        }
    }
}
```

**使用示例**：

```java
// 真实主题
DatabaseDocumentRepository real = new DatabaseDocumentRepository();

// JDK 动态代理：wrap 返回接口类型，代理类运行时才生成
DocumentRepository proxy = LoggingHandler.wrap(real, DocumentRepository.class);
proxy.find(1);                // 打印 before/after，返回 "doc#1"
proxy.getClass().getName();   // "...$Proxy0"：源码里不存在的类

// 调用方只认 DocumentRepository，真实对象仍可单独使用
real.find(2);                 // "doc#2"（无日志）
```

JDK 1.8 实测输出：

```text
1_静态代理(手写)      : doc#1
   before find
   after  find -> doc#2
2_动态代理(JDK Proxy) : doc#2
3_动态代理是运行时生成的类 : $Proxy0
4_真实查询次数        : 2 -> [1, 2]
```

**`$Proxy0` 就是证据**：这个类在源码里不存在，是 `Proxy.newProxyInstance` 在运行时生成的。这是与 PHP 最大的差别 —— Java 的代理**可以完全不写转发方法**，只要实现一个 `InvocationHandler`。

两种写法对照：

| | 静态代理 | JDK 动态代理 |
| --- | --- | --- |
| 要写的代码 | 每个接口一个代理类 | 一个 `InvocationHandler` |
| 约束 | 无 | **只能代理接口**（代理类要继承 `Proxy`，类没有继承位） |
| 典型用途 | 转发逻辑简单、要类型完整 | AOP、事务、日志（Spring `@Transactional` 就是它） |

> "只能代理接口"这条限制，正是 Spring 对没有接口的类改用 CGLIB（生成子类）的原因 —— 与 PHP 那条"接口方法 `__call` 拦不到"的限制，性质相同。

## 八、Go 实现

Go 的接口是隐式实现，写代理比 PHP 还轻，并且多一个省样板的工具：**结构体嵌入**。

```go
// DocumentRepository 抽象主题
type DocumentRepository interface {
	Find(id int) string
}

// LoggingProxy 手写代理：实现同一接口 + 持有真实对象
type LoggingProxy struct {
	inner DocumentRepository
}

func (p *LoggingProxy) Find(id int) string {
	fmt.Println("   before Find")
	result := p.inner.Find(id)
	fmt.Println("   after  Find ->", result)
	return result
}

// EmbeddingProxy 用结构体嵌入省掉全部转发样板：
// 未覆盖的方法会自动转发给被嵌入的接口
type EmbeddingProxy struct {
	DocumentRepository // 嵌入接口，而不是具体类型
	Calls              int
}

func (p *EmbeddingProxy) Find(id int) string {
	p.Calls++
	return p.DocumentRepository.Find(id)
}
```

**使用示例**：

```go
// 真实主题：实现 DocumentRepository 接口
real := &DatabaseDocumentRepository{}

// 手写代理：实现同一接口并持有真实对象，调用方无感
var proxy DocumentRepository = &LoggingProxy{inner: real}
proxy.Find(1)          // 打印 before/after，返回 "doc#1"

// 嵌入代理：只覆盖 Find，其余方法零成本自动转发
embedding := &EmbeddingProxy{DocumentRepository: real}
embedding.Find(2)      // "doc#2"
embedding.Calls        // 1（只统计被覆盖的方法）
```

go1.26.5 实测输出：

```text
   before Find
   after  Find -> doc#1
1_手写代理            : doc#1
2_嵌入代理            : doc#2
3_只覆盖了 Find，其它方法零成本转发；调用计数 = 1
4_真实查询次数        : 2 -> [1 2]
```

**嵌入是 Go 独有的省事办法**：接口有 20 个方法、你只想改 1 个 —— 把接口嵌进结构体，另外 19 个自动转发，一行都不用写。代价是"未覆盖的方法原样透传"，等于默认放弃了对它们的控制，所以**用嵌入做代理时要想清楚哪些方法必须拦**。

## 九、PHP / Java / Go 对照

| | PHP | Java | Go |
| --- | --- | --- | --- |
| 抽象主题 | `interface` | `interface` | `interface`（隐式实现） |
| 手写代理 | 常规做法 | 可行（静态代理） | 常规做法 |
| 运行时生成代理 | ❌ 只能 `__call` 或代码生成 | ✅ `Proxy.newProxyInstance` | ❌ 无 |
| 省转发的工具 | 无（`__call` 有类型代价） | 动态代理 | **结构体嵌入** |
| 叠加多层代理 | ✅ | ✅ | ✅ |
| 最常用的一类 | 缓存 / 保护代理 | 事务 / AOP 动态代理 | 缓存 / 埋点代理 |

三语言共通的一条：**代理必须与被代理对象接口完全一致**。一旦为了让代理好写而改了接口，它就不再是代理 —— 改接口形状是 [适配器模式.md](适配器模式.md) 的活。

## 十、面试官会追问什么

- **代理和装饰器的区别？** → 接口都相同，区别在**意图**：代理控制访问（自己决定真实对象是谁、何时创建），装饰器增加行为（被装饰对象由调用方传入，天生支持多层叠加）。
- **代理和适配器的区别？** → 代理的接口与被代理对象**完全一致**；适配器**改变接口形状**。
- **PHP 有动态代理吗？** → 没有。要么手写，要么用 `__call`（接口方法必须显式声明，否则拦不到），要么引入代码生成库。
- **虚拟代理里的"延迟创建"怎么做才对？** → 注入工厂或可调用对象，把"怎么造"交给调用方；不能在代理构造器里 `new`（原文那个无参分支实测直接 `ArgumentCountError`）。
- **保护代理和权限中间件有什么区别？** → 保护代理在**对象访问层**（拿不到被保护对象就绕不过去），中间件在**请求链路层**。前者能被单元测试直接触发，后者依赖框架生命周期。
- **代理会不会有性能损耗？** → 多一次转发，可忽略；真正要小心的是**代理里的状态**：php-fpm 下缓存代理只活一次请求，Java/Go 常驻进程下它**跨请求共享**，会读到脏数据（与 [../创建型/单例模式.md](../创建型/单例模式.md) 第四节同一件事）。
- **多个代理叠加时顺序有讲究吗？** → 有。`保护(缓存(虚拟))` 与 `缓存(保护(虚拟))` 语义不同：前者"先鉴权再查缓存"，后者"缓存命中就绕过鉴权"。顺序即语义。
