# 六大原则

> 素材来源：博客 [设计模式六大原则——SOLID](https://blog.csdn.net/weixin_43837229/article/details/102970905)（2019-11-08），
> 内容出自《深入PHP：面向对象、模式与实践（第三版）》的学习笔记。
>
> 本篇的**讲解脉络取自博客原文**（每条原则的定义与"实践要求"都保留原话）；
> **代码按标准生产写法重写** —— 每条原则配一组"反例 → 正例"的可跑对照，并给出实测输出。
>
> 各模式与原则的对应关系见第三节；单篇模式文档见本目录 [README.md](../README.md)。

## 一、六条原则各自回答什么

原文逐条给了定义，照录如下（这六条是后文所有模式的判据来源）：

| # | 原则 | 原文定义（摘） |
| --- | --- | --- |
| 1 | **单一职责（SRP）** | 有且只有一个原因引起类的变更。就是说，不能有多个导致类变更的原因 |
| 2 | **开闭原则（OCP）** | 一个类或者模块和函数应该**对扩展来实现变化，对修改关闭** |
| 3 | **里氏替换（LSP）** | 所有引用基类的地方必须能**透明地使用其子类的对象** |
| 4 | **迪米特法则（LoD）** | 一个类应该对自己需要耦合或者调用的类**知道的最少** |
| 5 | **接口隔离（ISP）** | 客户端**不应该依赖它不需要的接口**；类间的依赖关系应该建立在最小的接口上 |
| 6 | **依赖倒置（DIP）** | 细节依赖抽象，抽象不应该依赖细节；**高层模块不应该依赖底层模块，两者应该依赖抽象** |

原文还单独列了第七条：

> **优先使用组合而不是继承原则** —— 这个虽然不算六大原则里面的，但是也一样重要。

（这条在本目录里被反复用到：装饰器、组合、代理都是它的产物。）

原文对里氏替换给出的"良好继承规范"四条值得留下：

> - 子类必须完成实现父类的方法；
> - 子类可以有自己的功能；
> - 子类覆盖或者实现父类的方法**可以使用比父类更加宽泛的参数类型**；
> - 子类覆盖或者实现父类的方法**可以定义返回类型的范围小于父类方法返回类型的范围**。

后两条就是"**前置条件不能收紧、后置条件不能放宽**"的白话版 —— 第三节的实测正是针对它。

## 二、逐条对照：反例 → 正例

### 2.1 单一职责：判据是"变更原因"，不是"方法个数"

```php
// 反例：一个方法里同时做校验、持久化、发信 —— 三个变更原因挤在一起
final class BadRegisterService
{
    public function register(string $email): string
    {
        if (!filter_var($email, FILTER_VALIDATE_EMAIL)) {
            throw new InvalidArgumentException('邮箱格式错误');
        }
        return 'saved:' . $email . ' | mailed:' . $email;
    }
}

// 正例：拆成三个各司其职的协作者，由一个用例类编排
final class EmailValidator
{
    public function validate(string $email): void
    {
        if (!filter_var($email, FILTER_VALIDATE_EMAIL)) {
            throw new InvalidArgumentException('邮箱格式错误');
        }
    }
}

final class UserRepository
{
    public function save(string $email): string
    {
        return 'saved:' . $email;
    }
}

final class WelcomeMailer
{
    public function send(string $email): string
    {
        return 'mailed:' . $email;
    }
}

final class RegisterUser
{
    public function __construct(
        private EmailValidator $validator,
        private UserRepository $repository,
        private WelcomeMailer $mailer
    ) {}

    public function handle(string $email): string
    {
        $this->validator->validate($email);
        return $this->repository->save($email) . ' | ' . $this->mailer->send($email);
    }
}
```

**判据是"谁会因为什么原因改这个类"**：邮箱规则变了只改 `EmailValidator`，存储方式变了只改 `UserRepository`。原文说的"代码的粒度降低了、可读性提高了、可维护性提高了"，落点就在这。

### 2.2 开闭原则：新增不进老代码

```php
// 反例：加一种折扣就要再加一个 if
final class BadDiscountCalculator
{
    public function calc(string $type, int $amountInCents): int
    {
        if ($type === 'vip') {
            return intdiv($amountInCents, 10);
        }
        if ($type === 'coupon') {
            return 3000;
        }
        return 0;
    }
}

// 正例：接口 + 实现，新增一种折扣不改老代码
interface DiscountPolicy
{
    public function discountFor(int $amountInCents): int;
}

final class VipDiscount implements DiscountPolicy
{
    public function discountFor(int $amountInCents): int
    {
        return intdiv($amountInCents, 10);
    }
}

final class CouponDiscount implements DiscountPolicy
{
    public function discountFor(int $amountInCents): int
    {
        return 3000;
    }
}
```

**使用示例**：

```php
// SRP：三个协作者各管一件事，RegisterUser 只做编排
$register = new RegisterUser(new EmailValidator(), new UserRepository(), new WelcomeMailer());
$register->handle('a@x.com');        // saved:a@x.com | mailed:a@x.com

// OCP：调用方只依赖 DiscountPolicy 抽象，新增折扣不改这里
$policies = ['vip' => new VipDiscount(), 'coupon' => new CouponDiscount()];
$policies['vip']->discountFor(25000);       // 2500
$policies['coupon']->discountFor(25000);    // 3000

// 反例结果一样，差别只在"加一种折扣要不要改老代码"
(new BadDiscountCalculator())->calc('vip', 25000);   // 2500
```

实测（PHP 8.0.2 CLI）：

```text
1_SRP 拆分后编排     : saved:a@x.com | mailed:a@x.com
2_OCP 多态替换       : 2500 / 3000
3a_LSP 父类处理 null : (no sql)
3b_LSP 子类崩了      : InvalidArgumentException - 不接受 null
4_ISP 拆分后         : robot=working human=working/eating
5_DIP 注入实现       : notified:a@x.com
6_LoD 推荐写法       : 杭州
6_LoD 链式写法(反面) : 杭州
```

**注意"开闭"不等于"用接口"**：定义一个接口但仍然在每个调用点 `if ($type === ...)` 选实现，等于没开闭。真正的开闭要求**选择逻辑也收在一个可扩展的地方**（工厂、容器、或策略注册表，见 [../行为型/策略模式.md](../行为型/策略模式.md)）。

### 2.3 里氏替换：子类不能收紧前置条件

```php
// 反例：子类加重了前置条件 —— 调用方按父类契约传 null，子类直接崩
class BadConnection
{
    public function query(?string $sql): string
    {
        return $sql === null ? '(no sql)' : "ran:{$sql}";
    }
}

final class BadStrictConnection extends BadConnection
{
    public function query(?string $sql): string
    {
        if ($sql === null) {
            throw new InvalidArgumentException('不接受 null');   // 收紧了前置条件
        }
        return "strict:{$sql}";
    }
}
```

实测第 3a/3b 行就是 LSP 被破坏的样子：**同一个 `null` 参数，父类能处理，子类抛异常**。调用方按父类契约写代码，换成子类就崩 —— 这就是"引用基类的地方不能透明地使用子类"。

正例是把契约写进抽象：

```php
interface Connection
{
    public function query(string $sql): string;    // 干脆不允许 null，契约更紧
}

final class PdoConnection implements Connection
{
    public function query(string $sql): string
    {
        return "pdo:{$sql}";
    }
}
```

**LSP 的实操判据**：拿子类替换父类后，原来能跑通的调用（含边界值）必须全部仍然能跑通。做不到，就说明继承关系错了 —— 这时候通常该改用**组合**（第七条原则）。

### 2.4 接口隔离：别让实现者"装死"

```php
// 反例：一个大接口，实现者被迫空实现
interface BadWorker
{
    public function work(): string;

    public function eat(): string;
}

final class BadRobot implements BadWorker
{
    public function work(): string { return 'working'; }

    public function eat(): string { return ''; }      // 机器人不吃饭，只能装死
}

// 正例：按能力拆接口
interface Workable
{
    public function work(): string;
}

interface Eatable
{
    public function eat(): string;
}

final class Robot implements Workable
{
    public function work(): string { return 'working'; }
}

final class Human implements Workable, Eatable
{
    public function work(): string { return 'working'; }

    public function eat(): string { return 'eating'; }
}
```

**判据**：接口里是否存在"某些实现只能空着或抛异常"的方法。有，就说明这个接口被多个不同角色共用了。

### 2.5 依赖倒置：高层不 new 低层

```php
// 反例：高层直接 new 低层，换实现要改高层，也没法替身测试
final class BadNotifier
{
    public function notify(string $to): string
    {
        return (new BadRegisterService())->register($to);   // 直接依赖具体类
    }
}

// 正例：依赖抽象
interface Notifier
{
    public function notify(string $to): string;
}

final class RealNotifier implements Notifier
{
    public function notify(string $to): string
    {
        return 'notified:' . $to;
    }
}

final class OrderService
{
    public function __construct(private Notifier $notifier) {}

    public function pay(string $to): string
    {
        return $this->notifier->notify($to);
    }
}
```

**DIP 最实际的收益是可测试性**：因为依赖的是 `Notifier` 接口，测试时可以注入一个假实现，不必真的发通知。这也是 [../创建型/注册模式.md](../创建型/注册模式.md) 里容器存在的理由 —— 容器就是"自动完成注入"的工具。

### 2.6 迪米特法则：只跟"直接朋友"说话

```php
final class Address
{
    public function __construct(public string $city) {}
}

final class Customer
{
    public function __construct(private Address $address) {}

    /** 推荐：直接给出结果，不把内部对象暴露出去 */
    public function city(): string
    {
        return $this->address->city;
    }

    /** 反面：暴露内部结构，调用方就会写出 $c->address()->city 这种链 */
    public function address(): Address
    {
        return $this->address;
    }
}
```

原文的定义是"一个类应该对自己需要耦合或者调用的类知道的最少"，实操上就是**别让调用方穿过你的对象去拿别人的对象**：`$c->address()->city` 让 `Customer` 的调用方同时耦合了 `Address`。

**这条与外观模式直接相关**：外观就是把"三跳变一跳"（见 [../结构型/外观模式.md](../结构型/外观模式.md)）。

## 三、六条原则是怎么落到模式上的

原目录里每个模式，本质上都是某条原则的具体解法：

| 原则 | 落到哪些模式 |
| --- | --- |
| 单一职责 | 几乎所有模式的共同前提（工厂只管造、观察者只管通知） |
| 开闭原则 | [策略](../行为型/策略模式.md)、[工厂方法](../创建型/工厂模式.md)、[过滤器](../结构型/过滤器模式.md) |
| 里氏替换 | [原型](../创建型/原型模式.md)（`clone` 的语义要一致）、[组合](../结构型/组合模式.md)（叶子与容器可互换） |
| 迪米特法则 | [外观](../结构型/外观模式.md)、[代理](../结构型/代理模式.md) |
| 接口隔离 | [适配器](../结构型/适配器模式.md)（目标接口只声明调用方真正需要的）、[迭代器](../行为型/迭代器模式.md) |
| 依赖倒置 | [工厂](../创建型/工厂模式.md)、[单例](../创建型/单例模式.md)（容器 `singleton`）、[观察者](../行为型/观察者模式.md) |
| 组合优于继承 | [装饰器](../结构型/装饰器模式.md)、[组合](../结构型/组合模式.md)、[代理](../结构型/代理模式.md) |

**六条原则的共同点**：都在做同一件事 —— **把"变化"关进一个可替换的单元里，让不变的部分不受影响**。区别只是"变化"在哪里：变的是职责（SRP）、是扩展点（OCP）、是实现（LSP/DIP）、是依赖面（LoD/ISP）。

## 四、原则不可证伪，反例才是判据

这是本篇与原文最大的差别。原文是"定义 + 优点 + 实践要求"的列表式陈述，读完记住的是名词；而**原则本身无法被证伪** —— 任何一个类你都能论证它"符合单一职责"，也都能论证它"违反了"，取决于你把职责切多细。

所以我给的是反例：**看代码在什么情况下会坏、坏得多难看**。

| 原则 | 违反后的具体症状 |
| --- | --- |
| SRP | 改邮箱规则要动注册逻辑，改注册要重测邮件发送 |
| OCP | 每加一种类型都要改同一个方法，且要重跑它的全部测试 |
| LSP | 换成子类后，原来能跑的边界值抛异常（实测 3b） |
| LoD | 内部结构调整（`Address` 改名）导致所有调用点编译失败 |
| ISP | 实现类里出现空方法或 `throw new NotSupportedException` |
| DIP | 无法为高层模块写单测（因为它 `new` 了低层） |

一句话：**判断原则有没有被遵守，不需要背定义，看改动会波及多少地方**。

## 五、Java / Go 对照

### Java 实现

```java
/** LSP 反例：子类收紧前置条件 */
static class BadConnection {
    String query(String sql) { return sql == null ? "(no sql)" : "ran:" + sql; }
}

static final class BadStrictConnection extends BadConnection {
    @Override
    String query(String sql) {
        if (sql == null) {
            throw new IllegalArgumentException("不接受 null");   // 收紧了前置条件
        }
        return "strict:" + sql;
    }
}

/** LSP 正例 + DIP：高层依赖接口，不依赖具体实现 */
interface Connection {
    String query(String sql);
}

static final class PdoConnection implements Connection {
    public String query(String sql) { return "pdo:" + sql; }
}

/** 测试替身：因为依赖的是接口，这里才能替换 */
static final class FakeConnection implements Connection {
    public String query(String sql) { return "fake:" + sql; }
}
```

**使用示例**：

```java
// LSP：引用基类的地方必须能透明地换成子类
BadConnection base = new BadConnection();
BadConnection child = new BadStrictConnection();   // 按父类契约调用

base.query(null);            // "(no sql)" —— 父类能处理
child.query(null);           // 抛 IllegalArgumentException —— 子类收紧了前置条件

// DIP：高层 OrderService 只依赖 Connection 接口，注入谁就用谁
new OrderService(new PdoConnection()).pay("select 1");    // "pdo:select 1"
new OrderService(new FakeConnection()).pay("select 1");   // "fake:select 1"（测试替身）

// ISP：实现类只需实现它真正会用的那个小接口
new Robot().work();          // "working"
```

JDK 1.8 实测输出：

```text
1a_LSP 父类处理 null : (no sql)
1b_LSP 子类崩了      : IllegalArgumentException - 不接受 null
2_DIP 真实实现       : pdo:select 1
3_DIP 测试替身       : fake:select 1
4_ISP 拆分后         : robot=working human=working/eating
```

第 2、3 行是 DIP 的直接收益：**同一个 `OrderService`，注入真实实现就干活，注入替身就能测**。

### Go 实现

```go
// OrderService 高层模块依赖抽象（DIP）
type OrderService struct{ conn Connection }

func (s OrderService) Pay(sql string) (string, error) { return s.conn.Query(sql) }

// ISP：Go 里接口要小，由隐式实现自动满足
type Workable interface{ Work() string }

type Eatable interface{ Eat() string }

type Robot struct{}

func (Robot) Work() string { return "working" }
```

**使用示例**：

```go
// DIP：OrderService 只依赖 Connection 接口，注入谁就调谁
svc := OrderService{conn: PdoConnection{}}
out, err := svc.Pay("select 1")
fmt.Println(out, err)                // pdo:select 1 <nil>

// 换个实现即可当测试替身，高层代码一行不改
fake := OrderService{conn: FakeConnection{}}
out, _ = fake.Pay("select 1")
fmt.Println(out)                     // fake:select 1

// ISP：接口小，Robot 只实现 Workable，不必被迫实现 Eat
var w Workable = Robot{}
fmt.Println(w.Work(), Human{}.Eat()) // working eating
```

go1.26.5 实测输出：

```text
1_DIP 真实实现 : pdo:select 1
2_DIP 测试替身 : fake:select 1
3_ISP 拆分后   : robot= working  human= working / eating
4_ISP 检查     : Robot 未被要求实现 Eat（编译期即成立）
```

**Go 把 ISP 变成了语言习惯**：接口是隐式实现，且社区惯例是"接口越小越好"（`io.Writer` 只有一个方法）。所以"某个实现被迫实现不需要的方法"这件事在 Go 里几乎不会发生 —— 你不需要声明自己实现了哪些接口，只要方法集匹配即可。

而 **DIP 在 Go 里要注意一点**：接口应该**由使用方定义**（而不是实现方）—— 这是 Go 社区的一条明确惯例（"accept interfaces, return structs"），与 DIP 说的"高层定义抽象"完全一致。

## 六、面试官会追问什么

- **六条原则哪条最重要？** → 开闭原则是目标，其余五条是手段：单一职责让类只为一个原因改，里氏替换保证多态能安全替换，依赖倒置让高层不绑死实现，接口隔离让接口别太胖，迪米特法则减少耦合面 —— 最终都是为了"加功能不改老代码"。
- **怎么判断违反了单一职责？** → 看**变更原因**：改一个需求要不要动这个类里不相干的方法。不是数方法个数、也不是看类有多大。
- **里氏替换为什么叫"替换"？** → 因为它的判据就是"替换"这个动作：把父类换成子类，原有调用必须全部照常工作（含边界值）。子类收紧前置条件（实测 3b）就是典型违反。
- **接口隔离和单一职责的区别？** → SRP 约束**类**（一个类只为一个原因改），ISP 约束**接口**（调用方不该看到用不到的方法）。ISP 可以理解为"接口维度的 SRP"。
- **依赖倒置的"倒置"倒的是什么？** → 传统依赖是"高层调用低层"（高层依赖具体实现），倒置后两边都依赖抽象，**依赖方向反过来了**：实现去迎合接口，而不是接口迁就实现。
- **迪米特法则和外观模式的关系？** → 外观就是迪米特的批量落地：把"三跳"收敛成"一跳"（见 [../结构型/外观模式.md](../结构型/外观模式.md)）。
- **"组合优于继承"为什么单列？** → 继承是编译期绑定、无法运行时替换、且层级一多就不堪重负；组合是运行期绑定、可替换、可叠加。装饰器/组合/代理全是这条原则的产物。
