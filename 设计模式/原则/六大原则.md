## 一、单一职责（SRP）：判据是"变更原因"，不是"方法个数"

定义：一个类有且只有一个引起它变化的原因。

最常见的误解是"一个类只做一件事，所以方法要少"。真正的判据是**有几个上游需求会来改它**：

```php
<?php

declare(strict_types=1);

// 反例：产品需求（字段校验）、DBA（表结构）、运营（邮件文案）三方都会来改这个类
final class UserBad
{
    public function save(): void
    {
        // 校验 + INSERT INTO users + 发欢迎邮件，三个变更原因挤在一起
    }
}

// 正例：按"谁来提变更"切分
final class UserValidator
{
    public function check(array $input): array
    {
        return [];
    }
}

final class UserMapper
{
    public function insert(array $user): int
    {
        return 1;
    }
}

final class WelcomeMailer
{
    public function send(string $email): void {}
}

foreach ([UserValidator::class, UserMapper::class, WelcomeMailer::class] as $c) {
    $r = new ReflectionClass($c);
    printf("%-16s public 方法数=%d\n", $r->getShortName(), count($r->getMethods(ReflectionMethod::IS_PUBLIC)));
}
```

```text
UserValidator    public 方法数=1
UserMapper       public 方法数=1
WelcomeMailer    public 方法数=1
```

三条实操判据，比背定义好用：

1. **给这个类写一句描述时出现了"和/以及"** → 大概率两个职责（"取数据**和**格式化输出"）。
2. **一个上游需求变化时，你需要改的文件数 > 1** → 切分不够或耦合过紧。
3. **拆多细？** → 拆到"一个类只被一类角色修改"为止，而不是拆到只剩一个方法。过度拆分导致跳转成本上升，是本原则最常见的反噬。

相关模式：外观模式（对外收敛）、代理模式（访问控制单独拿出来）、策略模式（把"怎么算"从"什么时候算"里拆走）。

## 二、开闭原则（OCP）：对扩展开放、对修改关闭

定义：新增行为应该靠**加代码**完成，而不是**改已有代码**。

```php
<?php

declare(strict_types=1);

interface Discount
{
    public function apply(float $price): float;
}

final class NoDiscount implements Discount
{
    public function apply(float $price): float
    {
        return $price;
    }
}

final class VipDiscount implements Discount
{
    public function apply(float $price): float
    {
        return $price * 0.8;
    }
}

// 新增：只加这个类，Checkout 与已有折扣类一行不动
final class NewCustomerDiscount implements Discount
{
    public function apply(float $price): float
    {
        return max(0.0, $price - 30.0);
    }
}

final class Checkout
{
    public function __construct(private Discount $discount) {}

    public function total(float $price): float
    {
        return $this->discount->apply($price);
    }
}

foreach ([new NoDiscount(), new VipDiscount(), new NewCustomerDiscount()] as $d) {
    printf("%-22s => %.2f\n", (new ReflectionClass($d))->getShortName(), (new Checkout($d))->total(100.0));
}
```

```text
NoDiscount             => 100.00
VipDiscount            => 80.00
NewCustomerDiscount    => 70.00
```

反面形态就是 `switch ($type)`：每加一种类型，都要回到 `Checkout` 里加分支，同时回归测试要覆盖全部旧分支。

一句话记住代价：**OCP 的本质是"用一次抽象换掉以后每次修改"**，所以抽象点选错就是纯亏。判据是"这个维度确实还会再加成员"——只有两种且长期不变的分支，写 `switch`（或 PHP 8 的 `match`）比建接口更好。

相关模式：策略、装饰器、观察者、责任链，全是 OCP 的具体化。

## 三、里氏替换（LSP）：子类必须能"不被察觉地"替换父类

定义：凡使用父类对象的地方，都能替换成子类对象，且程序行为不变。

教科书反例是正方形继承矩形，本机实测它坏在哪：

```php
<?php

declare(strict_types=1);

class Rectangle
{
    protected float $w = 0.0;
    protected float $h = 0.0;

    public function __construct(float $w, float $h)
    {
        $this->w = $w;
        $this->h = $h;
    }

    public function setWidth(float $w): void
    {
        $this->w = $w;
    }

    public function setHeight(float $h): void
    {
        $this->h = $h;
    }

    public function area(): float
    {
        return $this->w * $this->h;
    }

    public function size(): string
    {
        return sprintf('%.1fx%.1f', $this->w, $this->h);
    }
}

final class Square extends Rectangle
{
    public function setWidth(float $w): void
    {
        $this->w = $this->h = $w;
    }

    public function setHeight(float $h): void
    {
        $this->w = $this->h = $h;
    }
}

$sq = new Square(4.0, 4.0);
$sq->setWidth(4.0);
$sq->setHeight(5.0);
printf("期望 area=20.00，实得 area=%.2f，size=%s\n", $sq->area(), $sq->size());

$rect = new Rectangle(4.0, 4.0);
$rect->setWidth(4.0);
$rect->setHeight(5.0);
printf("Rectangle 同样调用得 area=%.2f\n", $rect->area());
```

```text
期望 area=20.00，实得 area=25.00，size=5.0x5.0
Rectangle 同样调用得 area=20.00
```

**同样的两次 setter 调用，父类得到 20、子类得到 25**——这就是"子类加强了后置条件"，凡是依赖"宽高互相独立"这段调用方契约的代码，换上 `Square` 就静默算错，没有任何异常抛出。

破坏 LSP 的四种常见写法（PHP 场景）：

| 写法 | 后果 |
| --- | --- |
| 子类覆写方法后**缩小入参范围**（加更严校验、抛类型错误） | 调用方按父类约定传值就炸 |
| 子类覆写后**放宽返回值**（父类声明非空，子类返回 `null`） | 下游 `->` 直接 fatal |
| 子类对某些方法抛 `BadMethodCallException`（"我不支持这个操作"） | 用 `instanceof` 打补丁，等于承认继承错了 |
| 子类重写后不改行为但**改了副作用**（父类不写日志、子类写） | 测试断言数量失败 |

修法几乎都是：**别继承，抽公共接口或改成组合**（见第七节）。

## 四、接口隔离（ISP）：别让实现者被迫"装死"

定义：客户端不该依赖它用不到的方法；接口要按调用方视角拆分。

```php
<?php

declare(strict_types=1);

interface WorkerBad
{
    public function code(): string;

    public function attendMeeting(): string;
}

final class RobotWorker implements WorkerBad
{
    public function code(): string
    {
        return '写代码';
    }

    public function attendMeeting(): string
    {
        throw new BadMethodCallException('Robot 不会开会，只能抛异常或返回空实现');
    }
}

interface Coder
{
    public function code(): string;
}

interface MeetingAttendee
{
    public function attendMeeting(): string;
}

final class RobotWorkerFixed implements Coder
{
    public function code(): string
    {
        return '写代码';
    }
}

try {
    (new RobotWorker())->attendMeeting();
} catch (Throwable $e) {
    echo 'bad: ', get_class($e), ' -> ', $e->getMessage(), "\n";
}
echo 'fixed: ', RobotWorkerFixed::class, ' 只实现 Coder，methods=', implode(',', get_class_methods(RobotWorkerFixed::class)), "\n";
```

```text
bad: BadMethodCallException -> Robot 不会开会，只能抛异常或返回空实现
fixed: RobotWorkerFixed 只实现 Coder，methods=code
```

**判据**：只要出现"实现某接口时有一个方法只能抛异常或返回空"，就是接口该拆了。PHP 里最典型的是实现了 `Countable`/`IteratorAggregate` 的胖基类，以及框架的 `ArrayAccess`——不需要写能力的只读集合被迫实现 `offsetSet`。

与 SRP 的区别：SRP 管**一个类内部**的职责，ISP 管**一个接口对外的暴露面**。同一个"太胖"的问题，一个从实现看，一个从调用方看。

## 五、依赖倒置（DIP）：高层不依赖低层，两边都依赖抽象

定义：抽象不依赖细节，细节依赖抽象；具体对象由外部注入。

```php
<?php

declare(strict_types=1);

interface Mailer
{
    public function send(string $to, string $body): string;
}

final class SmtpMailer implements Mailer
{
    public function send(string $to, string $body): string
    {
        return "SMTP->{$to}";
    }
}

final class ArrayMailer implements Mailer
{
    /** @var array<int, string> */
    public array $sent = [];

    public function send(string $to, string $body): string
    {
        $this->sent[] = $to;
        return "ARRAY->{$to}";
    }
}

final class OrderNotifier
{
    public function __construct(private Mailer $mailer) {}

    public function notifyPaid(string $to): string
    {
        return $this->mailer->send($to, 'paid');
    }
}

$fake = new ArrayMailer();
echo (new OrderNotifier(new SmtpMailer()))->notifyPaid('a@x.com'), "\n";
echo (new OrderNotifier($fake))->notifyPaid('b@x.com'), "\n";
echo '测试里可断言的收件人: ', json_encode($fake->sent), "\n";
```

```text
SMTP->a@x.com
ARRAY->b@x.com
测试里可断言的收件人: ["b@x.com"]
```

反例是 `OrderNotifier` 内部直接 `new SmtpMailer()`：那样单测必须真连 SMTP，或者上 runkit/Runkit7 这类 hack。

**DIP 与 DI 不是一回事**：DIP 是原则（依赖抽象），DI 是手段（从外部把实现塞进来），IoC 容器只是把 DI 的装配代码自动化了。仓库里 [单例模式.md](../创建型/单例模式.md) 第五节的容器版 `singleton()` 就是这条的最小实现。

## 六、迪米特法则与合成复用原则（原系列也常并称"第六、第七条"）

SOLID 是五条，中文语境说的"六大原则"通常再加**迪米特（LoD）**，有时再把**合成复用（CRP）**算进去。

迪米特：只跟"直接朋友"说话，别跨对象链取数据。

```php
<?php

declare(strict_types=1);

class Address
{
    public function __construct(private string $city) {}

    public function city(): string
    {
        return $this->city;
    }
}

class Company
{
    public function __construct(private Address $addr) {}

    public function address(): Address
    {
        return $this->addr;
    }
}

class User
{
    public function __construct(private Company $company) {}

    public function company(): Company
    {
        return $this->company;
    }
}

$u = new User(new Company(new Address('杭州')));
echo '三跳: ', $u->company()->address()->city(), "\n";

class User2
{
    public function __construct(private Company $company) {}

    public function city(): string
    {
        return $this->company->address()->city();
    }
}

echo '一跳: ', (new User2(new Company(new Address('杭州'))))->city(), "\n";
```

```text
三跳: 杭州
一跳: 杭州
```

两者结果相同，差别在**变更影响面**：`Address` 改名或换成多地址时，前者所有调用点都要改。`User2::city()` 把三跳收成一个方法，这就是外观模式和代理模式在做的事。

合成复用：尽量用组合/聚合（含 `trait`），少用继承，只在确实是"is-a 且行为可替换"时才继承。

```php
<?php

declare(strict_types=1);

trait CacheableTrait
{
    public function cacheKey(string $prefix): string
    {
        return $prefix . ':' . static::class;
    }
}

interface Cache
{
    public function get(string $key): ?string;
}

final class NullCache implements Cache
{
    public function get(string $key): ?string
    {
        return null;
    }
}

final class RedisLikeCache implements Cache
{
    public function get(string $key): ?string
    {
        return "hit:{$key}";
    }
}

final class QueryWithTrait
{
    use CacheableTrait;
}

final class Repo
{
    use CacheableTrait;

    public function __construct(private Cache $cache) {}

    public function find(int $id): string
    {
        $k = $this->cacheKey('user');
        return $this->cache->get($k) ?? 'miss';
    }
}

echo 'trait 复用: ', (new QueryWithTrait())->cacheKey('user'), "\n";
echo '组合 + 注入: ', (new Repo(new RedisLikeCache()))->find(1), ' / ', (new Repo(new NullCache()))->find(1), "\n";
```

```text
trait 复用: user:QueryWithTrait
组合 + 注入: hit:user:Repo / miss
```

注意 `trait` 的代价：它没有接口约束、同名方法冲突要靠 `insteadof` 手工解决、也不能被 mock。所以**复用优先"接口 + 注入"，`trait` 只用于纯粹的实现细节共享**（比如上面这个 key 拼接规则）。

## 七、原则 → 模式对照表

| 原则 | 落地它的模式 | 反面信号 |
| --- | --- | --- |
| SRP | 外观、代理、策略 | 类描述里有"和" |
| OCP | 策略、观察者、装饰器、责任链、工厂 | 每次加类型要改 `switch` |
| LSP | 模板方法（反向教材）、组合优于继承 | 子类抛"不支持"异常 |
| ISP | 适配器（按调用方切接口） | 实现者有空方法/抛异常 |
| DIP | 工厂、抽象工厂、注册、依赖注入容器 | 类内部 `new` 具体业务依赖 |
| LoD | 外观、中介者、代理 | 调用链超过两跳 |
| CRP | 装饰器、桥接、组合 | 继承层级 ≥ 3 层还打算继续加 |

## 八、Go / Java 对照（都已编译运行）

原则跨语言通用，但**Go 没有继承**，LSP/CRP 的表现形式不同：Go 里"替换"靠隐式接口，"复用"靠结构体嵌入。

Go（`go1.26.5`，`go vet` 通过并 `go run`）：

```go
package main

import "fmt"

// OCP / DIP：新增折扣只加类型，不改 Checkout
type Discount interface{ Apply(price float64) float64 }

type VIP struct{}

func (VIP) Apply(p float64) float64 { return p * 0.8 }

type NewCustomer struct{}

func (NewCustomer) Apply(p float64) float64 {
	if p > 30 {
		return p - 30
	}
	return 0
}

type Checkout struct{ d Discount }

func (c Checkout) Total(p float64) float64 { return c.d.Apply(p) }

// Go 无继承：LSP 表现为"同一接口下实现可替换"，复用靠嵌入而不是 extends
type Logger interface{ Log(s string) }

type FileLogger struct{}

func (FileLogger) Log(s string) { fmt.Println("file:", s) }

type WithRetry struct{ Logger }

func (w WithRetry) Log(s string) { w.Logger.Log(s + " (retry=1)") }

func main() {
	fmt.Println("VIP:", Checkout{VIP{}}.Total(100))
	fmt.Println("NewCustomer:", Checkout{NewCustomer{}}.Total(100))
	WithRetry{FileLogger{}}.Log("hello")
}
```

```text
VIP: 80
NewCustomer: 70
file: hello (retry=1)
```

Java（`jdk1.8.0_202`，`javac -encoding UTF-8` 通过并运行）：

```java
interface Discount {
    double apply(double price);
}

final class Vip implements Discount {
    public double apply(double p) { return p * 0.8; }
}

final class FreeShipping implements Discount {
    public double apply(double p) { return p - 10; }
}

// DIP + OCP：Checkout 只认识抽象，实现从构造参数进来
final class Checkout {
    private final Discount discount;

    Checkout(Discount discount) { this.discount = discount; }

    double total(double p) { return discount.apply(p); }
}

public class Solid {
    public static void main(String[] args) {
        System.out.println("Vip: " + new Checkout(new Vip()).total(100));
        System.out.println("FreeShipping: " + new Checkout(new FreeShipping()).total(100));
    }
}
```

```text
Vip: 80.0
FreeShipping: 90.0
```

三语言在这几条上唯一的真差别：**Java/C# 有 `abstract class`，LSP 违约成本最高（继承链一改动全炸）；Go 从语言层面就把 CRP 变成了默认答案**——你想违约也没有 `extends` 可用。

## 面试官会追问什么

- **六大原则里哪条最难落地？** → OCP。它要求提前判断"哪个维度还会扩展"，抽象点猜错就是纯成本；答"看变更频率决定要不要抽象"比答"永远面向接口"成熟。
- **LSP 违反和 ISP 违反怎么区分？** → LSP 是"实现替换后行为不对"（运行时静默错），ISP 是"接口暴露了用不到的方法"（编译期就得写空实现）。
- **DIP 是不是一定要有 IoC 容器？** → 不是。构造函数传接口就是 DIP，容器只是集中装配。小项目手写 factory 函数完全够，容器换来的是配置集中，代价是启动扫描与调试跳转。
- **PHP 有什么语言特性会破坏这些原则？** → `new` 到处写（DIP）、`array` 传参无契约（ISP/LSP 的隐性违约高发区）、`trait` 冲突静默（CRP 的伪复用）、魔术方法 `__call`（IDE 与静态分析看不见依赖）。
- **原则之间会冲突吗？** → 会。SRP 拆得越细，LoD 越容易被破（调用链变长），所以拆完通常要配一个外观或中介者收口。
