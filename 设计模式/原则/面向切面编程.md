## 一、AOP 要解决什么

原文对 AOP 与 OOP 关系的论述相当完整，照录要点：

> AOP（Aspect-Oriented Programming，面向方面编程），可以说是 **OOP 的补充和完善**。
> OOP 引入封装、继承和多态性等概念来建立一种对象层次结构，用以模拟公共行为的一个集合。
> **当我们需要为分散的对象引入公共行为的时候，OOP 则显得无能为力**。
> 也就是说，**OOP 允许你定义从上到下的关系，但并不适合定义从左到右的关系**。
> 例如日志功能。日志代码往往**水平地散布在所有对象层次中**，
> 而与它所散布到的对象的核心功能毫无关系。对于其他类型的代码，如安全性、异常处理和透明的持续性也是如此。
> 这种散布在各处的无关的代码被称为**横切（cross-cutting）代码**。

然后是核心结论：

> AOP 把软件系统分为两个部分：**核心关注点**和**横切关注点**。
> 业务处理的主要流程是核心关注点，与之关系不大的部分是横切关注点。
> 横切关注点的一个特点是，**它们经常发生在核心关注点的多处，而各处都基本相似**。
> 比如**权限认证、日志、事务处理**。

原文还引了一句很好的概括：

> AOP 的核心思想就是"**将应用程序中的商业逻辑同对其提供支持的通用服务进行分离**"。

原文提到实现 AOP 有两大类技术：**动态代理**（截取消息、装饰原有行为）与**静态织入**（引入特定语法，编译期织入）—— 这个区分是后文三语言对照的骨架。

## 二、五个核心概念

原文列全了 AOP 的术语，这几个词在看 Spring / 框架文档时会反复遇到：

| 概念 | 原文定义 | PHP 里的对应物 |
| --- | --- | --- |
| **join point**（连接点） | 程序执行中的一个精确执行点，例如类中的一个方法（抽象概念，不需要定义） | 被包装对象的方法 |
| **point cut**（切入点） | 本质上是一个**捕获连接点的结构**，用来捕获相关方法的调用 | 装饰器里那次转发调用 |
| **advice**（通知） | point cut 的执行代码，是执行"方面"的具体逻辑 | 转发前后的那几行 |
| **aspect**（方面） | point cut 和 advice 结合起来就是 aspect，类似 OOP 的一个类，但**代表对象间横向的关系** | 一个装饰器类 |
| **introduce**（引入） | 为对象引入附加的方法或属性，从而修改对象结构（有的工具叫 mixin） | PHP 里无原生支持 |

应用场景原文写得很直白：

> 类似于**钩子函数**，在需要做**权限控制、日志记录**的地方，可以考虑这种方法，
> 以**低耦合**的方式扩展功能，**避免硬编码**。

## 三、PHP 标准实现：两种切面

场景：给 `UserService::rename()` 加"耗时日志"这个横切关注点。

### 3.1 切面一：装饰器式（推荐）

```php
<?php

declare(strict_types=1);

interface UserService
{
    public function rename(int $id, string $name): string;
}

final class RealUserService implements UserService
{
    public function rename(int $id, string $name): string
    {
        return "user#{$id} -> {$name}";
    }
}

/**
 * 切面：装饰器式 —— 类型安全、IDE 可跳转、只拦声明过的方法。
 * 代价：每加一个方法都要在这里转发一次。
 */
final class LoggingAspect implements UserService
{
    /** @var list<string> */
    public array $log = [];

    public function __construct(private UserService $target) {}

    public function rename(int $id, string $name): string
    {
        $start = microtime(true);
        $result = $this->target->rename($id, $name);          // 业务本体
        $this->log[] = sprintf(
            'rename(%d) 耗时 %.3fms -> %s',
            $id,
            (microtime(true) - $start) * 1000,
            $result
        );
        return $result;
    }
}
```

### 3.2 切面二：`__call` 代理（原文写法）

```php
/**
 * 切面：__call 代理 —— 任意方法都能拦，不用写一行转发。
 * 代价：返回值退化成 mixed、IDE 不认、接口方法拦不到。
 */
final class CallAspect
{
    /** @var list<string> */
    public array $log = [];

    public function __construct(private object $target) {}

    public function __call(string $method, array $args): mixed
    {
        $this->log[] = "before {$method}";
        $result = $this->target->{$method}(...$args);          // 业务本体
        $this->log[] = "after {$method}";
        return $result;
    }
}
```

**使用示例**：

```php
// 装饰器式：包一层切面，调用方拿到的仍是 UserService
$aspect = new LoggingAspect(new RealUserService());
$aspect->rename(7, 'Ann');           // user#7 -> Ann
$aspect->log[0];                     // rename(7) 耗时 ... -> user#7 -> Ann

// __call 式：不用写转发就能拦任意方法（代价是返回值退化成 mixed）
$callAspect = new CallAspect(new RealUserService());
$callAspect->rename(8, 'Bob');       // user#8 -> Bob
$callAspect->log;                    // ['before rename', 'after rename']

// 实现了接口的类必须显式转发，否则 __call 拦不到
$withIface = new CallAspectWithInterface(new RealUserService());
$withIface->rename(9, 'Cara');       // user#9 -> Cara

// 两种切面可叠加：都实现 UserService，装饰器能包住 __call 代理
(new LoggingAspect($withIface))->rename(10, 'Dan');   // user#10 -> Dan
```

实测（PHP 8.0.2 CLI）：

```text
1_装饰器式切面返回值 : user#7 -> Ann
2_装饰器式切面日志   : rename(7) 耗时 0.012ms -> user#7 -> Ann
3a___call 式返回值   : user#8 -> Bob
3b___call 式日志     : before rename / after rename
4_带接口的 __call    : user#9 -> Cara
5_两种切面可叠加     : user#10 -> Dan
```

两种写法的取舍：

| | 装饰器式 | `__call` 代理式 |
| --- | --- | --- |
| 类型安全 | ✅ 完整 | ❌ 返回值退化成 `mixed` |
| IDE 跳转 | ✅ | ❌ |
| 加方法要不要改切面 | **要**（每个方法转发一次） | 不要 |
| 拦到接口方法 | ✅ | **❌ 必须显式转发**（见下） |
| 适合 | 方法少、要类型 | 方法多、动态性强 |

**第 4 行说明的那条坑很关键**：`__call` 只在调用"**未定义方法**"时触发。如果类实现了接口，接口里声明过的方法必须**显式转发**到 `__call`，否则魔术方法根本不会被调用：

```php
final class CallAspectWithInterface implements UserService
{
    /** @var list<string> */
    public array $log = [];

    public function __construct(private UserService $target) {}

    public function rename(int $id, string $name): string
    {
        return $this->__call('rename', [$id, $name]);   // 必须显式转发
    }

    public function __call(string $method, array $args): mixed
    {
        $this->log[] = "before {$method}";
        $result = $this->target->{$method}(...$args);
        $this->log[] = "after {$method}";
        return $result;
    }
}
```

第 5 行还说明**两种切面可以互相叠加**（`LoggingAspect` 包住 `CallAspectWithInterface`）—— 因为它们都实现了同一个接口，这正是装饰器模式的性质。

## 四、PHP 没有"织入"，只有代理 + 管道

原文提到的两类 AOP 技术，PHP 只能走第一类：

| 技术 | 机制 | PHP |
| --- | --- | --- |
| **动态代理** | 运行时生成代理对象，拦截方法调用 | ✅ 可以（手写代理，或代码生成库） |
| **静态织入** | 编译器在编译期把切面代码插进字节码 | ❌ **没有**（PHP 没有编译期织入的通用机制） |

所以 PHP 里说"切面"，实际指的是下面几种**手工把握**的形式：

| 形式 | 说明 |
| --- | --- |
| 装饰器 / 代理 | 类型安全、可控，本篇 3.1 |
| 闭包管道（中间件） | 框架最常用，洋葱式 `fn($next)` |
| `__call` 代理 | 动态性最强、类型最弱，本篇 3.2 |
| 属性 + 反射 | 最接近"注解驱动"，但要自己扫描与转发 |

**与 Java 的差距是明确的**：Java 的 Spring AOP 能在运行时为你生成代理并织入通知（见第五节），而 PHP 需要显式写出来（或依赖框架在启动时用代码生成补齐）。好处是**可读性**：PHP 里一次调用经过了哪些切面，读代码就能看出来。

## 五、Java 实现

Java 的 AOP 就是"动态代理"这条路的成熟形态：

```java
/**
 * 切面：InvocationHandler。
 * 这就是 Spring AOP 的底层机制 —— 运行时生成代理并织入通知。
 */
static final class LoggingAspect implements InvocationHandler {
    private final Object target;

    LoggingAspect(Object target) { this.target = target; }

    public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
        long start = System.nanoTime();
        Object result = method.invoke(target, args);              // 业务本体
        System.out.printf("   [aspect] %s 耗时 %.3fms%n",
                method.getName(), (System.nanoTime() - start) / 1_000_000.0);
        return result;
    }

    @SuppressWarnings("unchecked")
    static <T> T wrap(T target, Class<T> iface) {
        return (T) Proxy.newProxyInstance(
                iface.getClassLoader(),
                new Class<?>[] { iface },
                new LoggingAspect(target));
    }
}
```

**使用示例**：

```java
// 业务接口与实现（动态代理只能代理接口）
UserService real = new RealUserService();

// 包装：代理类是运行时生成的，业务实现一行未改
UserService proxy = LoggingAspect.wrap(real, UserService.class);
proxy.rename(7, "Ann");       // 先打印 [aspect] rename 耗时 ...，返回 user#7 -> Ann
proxy.getClass().getName();   // com.sun.proxy.$Proxy0

// 代理可再被代理：这就是多个 @Around 通知能叠加的机制
UserService stacked = LoggingAspect.wrap(proxy, UserService.class);
stacked.rename(8, "Bob");     // user#8 -> Bob（打印两次 [aspect]）
```

JDK 1.8 实测输出：

```text
   [aspect] rename 耗时 0.256ms
1_动态代理切面返回值 : user#7 -> Ann
2_代理类是运行时生成的 : $Proxy0
3_切面无需改业务代码   : RealUserService 一行未动
   [aspect] rename 耗时 0.008ms
   [aspect] rename 耗时 0.270ms
4_切面可叠加           : user#8 -> Bob
```

三点值得注意：

- **`$Proxy0` 是运行时生成的类**，源码里不存在 —— 这就是"动态代理"的字面含义，也是 PHP 做不到的部分；
- **业务类一行未改**，`RealUserService` 完全不知道有切面存在；
- 第 4 行：**代理可以再被代理**（两个 handler 串起来），所以 Spring 里多个 `@Around` 通知能叠加 —— 但这也带来经典的坑：**同一个类被多层代理包装后，调试时栈会很深**，且"同类内部方法调用不走代理"（`this.xxx()` 不会触发通知）。

## 六、Go 实现

Go 里的 AOP 就是**中间件**：用"接收处理器、返回处理器"的函数来表达切面。

```go
// HandlerFunc 业务处理器
type HandlerFunc func(input string) string

// Middleware 切面：接收处理器、返回包装后的处理器
type Middleware func(next HandlerFunc) HandlerFunc

// LoggingAspect 前置/后置通知
func LoggingAspect(log *[]string) Middleware {
	return func(next HandlerFunc) HandlerFunc {
		return func(input string) string {
			*log = append(*log, "before:"+input)
			result := next(input)          // 业务本体
			*log = append(*log, "after:"+input)
			return result
		}
	}
}

// Chain 把多个切面串成一个 —— 洋葱式：最外层最先执行、最后返回
func Chain(h HandlerFunc, middlewares ...Middleware) HandlerFunc {
	for i := len(middlewares) - 1; i >= 0; i-- {
		h = middlewares[i](h)
	}
	return h
}
```

**使用示例**：

```go
// 业务处理器：只关心自己的逻辑，不知道有切面存在
business := func(input string) string { return "handled:" + input }

// 切面用闭包收集日志与耗时；组装顺序就是执行顺序（洋葱式）
var log []string
var elapsed time.Duration
handler := Chain(business, TimingAspect(&elapsed), LoggingAspect(&log))

handler("order-1")   // "handled:order-1"
log                  // ["before:order-1", "after:order-1"]
elapsed >= 0         // true —— 切面记录到了耗时

// business 一行未改：切面与业务完全解耦
business("order-1")  // "handled:order-1"
```

go1.26.5 实测输出：

```text
1_切面后返回值 : handled:order-1
2_切面日志     : before:order-1 / after:order-1
3_切面耗时     : 已记录 true
4_business 未被修改，输出仍是 : handled:order-1
```

Go 的形态与 PHP/Java 都不同：

- **没有类，用函数类型表达切面**：`func(next T) T` 这个形状就是"装饰器"，而且比建类轻得多；
- **切面的组装是显式的**（`Chain(business, A, B)`），一眼能看出顺序 —— 顺序即语义（外层先执行、内层后返回，即"洋葱模型"）；
- **这是 Go 生态的事实标准**：`net/http` 中间件、gRPC interceptor、各类框架的 `Use()` 都是这个形状。

## 七、三语言对照

| | PHP | Java | Go |
| --- | --- | --- | --- |
| 主流切面形态 | 装饰器 / `__call` 代理 / 中间件 | **动态代理**（`InvocationHandler`） | **函数式中间件** |
| 静态织入 | ❌ 无 | 编译期 AOP（AspectJ） | ❌ 无 |
| 是否需要改业务代码 | 不需要 | 不需要 | 不需要 |
| 类型安全 | 装饰器式有、`__call` 式无 | ✅ | ✅ |
| 框架代表 | Laravel Middleware、Symfony EventDispatcher | Spring AOP（`@Transactional`） | `net/http` middleware、gRPC interceptor |
| 调试难度 | 层数少，直观 | **栈深、同类内部调用不走代理** | 层数少，直观 |

三语言共通：**AOP 的价值是"横切关注点不用在每个方法里抄一遍"，代价是"控制流变得不直观"**。所以能不能用、用多少，取决于团队对"隐式行为"的容忍度 —— 这也是第八节要说的。

## 八、什么时候不该用切面

| 情况 | 更好的选择 |
| --- | --- |
| 只有一个类需要这个行为 | 直接写在那一个方法里，别为它建切面 |
| 切面里需要读业务参数做判断 | 说明它其实是业务逻辑，该放进领域代码 |
| 顺序有严格要求且会变 | 显式写成管道/服务编排，切面顺序是"配置"而非"代码"，容易失控 |
| 新人需要读三遍才能看懂调用链 | 换成显式的装饰器链或直接调用 |

判据一句话：**切面适合"各处都基本相似、且与业务无关"的逻辑**（原文的说法）；一旦它开始依赖业务细节，就不再是横切关注点，而是**被藏起来的业务逻辑**。

## 九、面试官会追问什么

- **AOP 解决什么问题？** → 横切关注点（日志、鉴权、事务、计时）散落在各处、与业务无关却每处都要写。AOP 把它们抽成"方面"，以低耦合的方式织入。
- **AOP 和 OOP 什么关系？** → 补充关系。原文的说法是"OOP 允许定义从上到下的关系，但不适合定义从左到右的关系"——AOP 正好补横向这一维。
- **PHP 能做 AOP 吗？** → 能做"手工切面"（装饰器、中间件、`__call` 代理、属性+反射），但**没有编译期织入**，也没有运行时自动生成代理的通用机制（需依赖代码生成库）。
- **`__call` 做切面有什么代价？** → 返回值退化成 `mixed`、IDE 无法跳转、参数不做类型检查；而且**实现了接口的类，接口方法必须显式转发**，否则 `__call` 根本不被触发（实测第 4 行）。
- **Java 的 `@Transactional` 是怎么实现的？** → 动态代理（JDK `Proxy` 或 CGLIB）：Spring 为目标 bean 生成代理，在方法前后开启/提交事务。所以**同类内部方法调用不会开启新事务**（没走代理）。
- **Go 的中间件算 AOP 吗？** → 算，而且是 Go 里最主流的形态：`func(next HandlerFunc) HandlerFunc` 就是装饰器式切面；`Chain()` 组装顺序就是"切面顺序"。
- **切面和装饰器的关系？** → 装饰器是切面的一种实现形式（类型安全的那种）。见 [../结构型/装饰器模式.md](../结构型/装饰器模式.md)。
