## 一、goroutine 的 7 个典型案例

**本节要点**：会写 `go` 是一回事，知道"起之前要回答哪三个问题"是另一回事。
下面 7 个案例按「起 → 等 → 收 → 限 → 退」排列，从最基础排到最工程。

### 写 `go` 之前先回答三个问题

| 问题 | 不合格的答案 | 合格的答案 |
|---|---|---|
| **它什么时候结束？** | "跑完就结束了" | "ctx 取消 / channel 关闭 / 超时到点" |
| **结束时谁负责收尾？** | 没想过 | `defer` 里 close / Unlock / 放回池 |
| **它崩了会怎样？** | 不知道 | 自己 recover 兜底（否则**整个进程退出**，见案例 7） |

> 一句话判据：**能回答"它靠什么停下来"，才允许写这个 `go`**。答不出来，就是一次潜在的泄漏。

### 案例 1：最基础的生产者 —— `go` + 匿名函数

```go
go func() { doWork() }()
```

就这么一行，但要把它写对得同时满足三件事：

| 坑 | 现象 | 正确做法 |
|---|---|---|
| **循环变量** | Go 1.21 及以前打印 `3 3 3` | 传参 `go func(i int){…}(i)`；1.22 起每轮新变量（语义由 `go.mod` 的 `go` 指令决定） |
| **panic** | **整个进程退出**，`main` 的 `recover` 拦不住 | 后台任务自带 `recover`（案例 7） |
| **没人等它** | `main` 返回 = 进程退出，协程被半路掐掉 | 用 `WaitGroup`（案例 2），或明确接受"发出去就不管" |

⭐ 第三条最容易被忽略：**`main` 函数返回时进程直接退出，不会等任何 goroutine**。
所以在长驻服务里"发出去就不管"可行，在短命脚本里就是"这段代码根本没跑"。

### 案例 2：等一批协程结束 —— `sync.WaitGroup`

```go
var wg sync.WaitGroup
for _, id := range ids {
	wg.Add(1)
	go func(id string) {
		defer wg.Done()
		fetch(id)
	}(id)
}
wg.Wait()
```

| 细节 | 为什么 |
|---|---|
| **`Add(1)` 必须在 `go` 之前** | 写在协程里可能出现"`Wait` 先返回、协程后启动"→ 提前放行 |
| **用 `defer wg.Done()`** | 中途 `return` / panic 也能减计数，否则 `Wait` 永远不返回 |
| **传参而不是闭包捕获** | 语义更明确，且不依赖 `go.mod` 的版本声明 |

### 案例 3：并发取结果 —— 按下标写切片

```go
results := make([]Result, len(ids)) // 预分配：长度固定，不用 append
var wg sync.WaitGroup
for i, id := range ids {
	wg.Add(1)
	go func(i int, id string) {
		defer wg.Done()
		results[i] = fetchOne(id) // 各写各的下标 → 天然无竞争
	}(i, id)
}
wg.Wait()
```

⭐ **为什么这样写不需要加锁**：每个协程只写自己的 `results[i]`，
**没有任何两个协程碰同一个内存位置**。改成 `results = append(results, r)` 就立刻有数据竞争
（`-race` 会报），那时才需要加锁，或者换下面第二种收法。

| 收结果的两种方式 | 适用 |
|---|---|
| **按下标写切片**（本节） | 结果数量已知、需要按输入顺序排列 |
| **channel 汇总** | 结果数量不定 / 要先到先处理 —— 见 [channel实战模式.md](channel实战模式.md) 用法三 |

### 案例 4：一错全停 —— `errgroup.WithContext`

```go
g, ctx := errgroup.WithContext(ctx)
for _, id := range ids {
	g.Go(func() error { return fetch(ctx, id) }) // g.Go 内部自己 Add/Done
}
if err := g.Wait(); err != nil {
	return err // 返回第一个非 nil 的错误
}
```

实测（5 个任务，第 2 个在 200ms 失败）：

```text
  任务 1 完成（100ms）
  任务 4 被取消（context canceled，200ms）
  任务 5 被取消（context canceled，200ms）
  任务 3 被取消（context canceled，200ms）
g.Wait() 返回：任务 2 失败（总耗时 200ms）
```

⭐ 三个自带的便利：`Add`/`Done` 不用手写、**派生出的 `ctx` 失败即取消**、错误只收敛第一条。
用 `WaitGroup` + `cancel` + 错误聚合手写也能做，但很容易漏掉"取消"这一半。

### 案例 5：限并发（背压）—— 带缓冲 channel 当信号量

```go
sem := make(chan struct{}, 50) // 缓冲区大小 = 并发上限
var wg sync.WaitGroup
for _, id := range ids {
	sem <- struct{}{} // ★ 拿不到令牌就阻塞在这里 —— 背压发生在这一行
	wg.Add(1)
	go func(id string) {
		defer wg.Done()
		defer func() { <-sem }()
		fetchOne(id)
	}(id)
}
wg.Wait()
```

**令牌的位置决定一切**（实测：5000 个任务、每个约 0.4ms、上限 50）：

```text
② 令牌在 go 之前拿    耗时 59~65ms ｜ 峰值协程       52 ｜ 堆分配 0.7 MB
③ 令牌在协程里拿      耗时 59~64ms ｜ 峰值协程 2800~3900 ｜ 堆分配 2.0 MB
```

⭐ **耗时几乎一模一样，峰值差 60~70 倍**。因为 ③ 里的 for 循环**已经把 5000 个协程全创建完了**，
它们只是各自卡在 `sem <-` 上 —— 它限住了"同时在跑"，没限住"同时在飞"。
**背压必须作用在"创建"这一步上**，否则内存峰值照样爆。

再看限并发整体的收益（5000 任务、每个 20ms，只改有没有限并发）：

```text
① 无限制（来一个起一个）      峰值协程 3702 ｜ 总耗时     46ms
② 信号量限 50 并发            峰值协程   52 ｜ 总耗时   2.034s
```

⭐ **限并发是"用吞吐换可控性"**：② 慢 44 倍，但内存峰值与下游压力都可控 —— 它换的不是速度。

### 案例 6：常驻 worker —— `ctx` + `for select`

```go
for {
	select {
	case <-ctx.Done(): // ★ 退出路径写在循环里，最不容易漏
		return
	case job := <-jobs:
		handle(job)
	}
}
```

`for range jobs` 更简洁（`close(jobs)` 后自然结束），但**只有 `select` 能同时监听多个退出源**
（`ctx.Done()`、`stopCh`、超时）。生产代码里常见混用：任务用 `range jobs`、退出用 `ctx`。

### 案例 7：纯后台任务 —— 必须自带 `recover`

```go
go func() {
	defer func() { // ⚠️ 不写这段，一个 panic 会带走整个进程
		if r := recover(); r != nil {
			log.Printf("后台任务 panic: %v\n%s", r, debug.Stack())
		}
	}()
	doWork()
}()
```

实测：协程里 `panic`，**两个场景退出码都是 2**，且 **`main` 的 `defer recover()` 完全没拦住**。

⭐ 原因：**`recover` 只对同一个 goroutine 的 defer 链有效**。由此得到两个推论：

- 每个"可能 panic 的后台协程"都要自带 `recover`；
- 反过来，Web 框架能给每个请求兜 panic，正是因为**每个请求都在自己的 goroutine 里**。

### ⚠️ 关键点与注意事项

| 要点 | 说明 |
|---|---|
| **`main` 返回 ≠ 等所有协程** | 进程立即退出，没跑完的协程被掐掉 |
| **`Add` 在 `go` 之前** | 写在协程里可能让 `Wait` 提前返回 |
| **panic 不跨协程** | 一个协程 panic 终止的是**整个进程**；`recover` 只救自己那条 defer 链 |
| **限并发要限在创建上** | 令牌写在 `go` 里面，限的是"在跑"而不是"在飞" |
| **传参优先于闭包** | 不依赖 `go.mod` 版本声明，语义更直白 |
| **切片按下标写免锁** | 各写各的下标没有竞争；`append` 有 |
| **能回答"它靠什么停下来"** | 答不出来 = 一次潜在的泄漏 |

## 二、项目里的 4 种典型用法

**本节要点**：第一节的 7 个案例是"形态"，这一节是**工程落地** ——
每种用法回答的是"这个业务场景该用哪种形态、边界在哪里"。

### 总纲：只扣住一句话，场景自己长出来

> **goroutine 是用来"把等待重叠起来"的。** 凡是"能同时等"的事情（多个独立 IO、多个下游调用）
> 都值得并发；凡是"本质串行"的事情（写一个文件、写一条响应、写库）都不值得。

### 用法一：请求入口的并发扇出（多段独立查询）

**场景**：一个列表 / 详情接口要拼多个来源的数据 —— 汇总、流水、标签、权限。
它们互不依赖，串行跑就是"多次 RTT 相加"。

```go
g, gctx := errgroup.WithContext(ctx) // 从请求 ctx 派生 → 客户端断开就全停
g.Go(func() error { var err error; sum, err = repo.Summary(gctx, q); return err })
g.Go(func() error { var err error; list, err = repo.List(gctx, q); return err })
g.Go(func() error { var err error; tags, err = repo.Tags(gctx, q); return err })
if err := g.Wait(); err != nil {
	return err
}
```

| 边界 | 说明 |
|---|---|
| **只用 `errgroup`，别手写** | 它一次给全"等全部""一错全停""收敛错误"三件事 |
| **`gctx` 必须派生自请求 ctx** | 否则客户端已经断开、后端还在跑（见 [../../分布式/分布式与微服务.md](../../分布式/分布式与微服务.md)） |
| **各段耗时之和要明显大于最慢那段** | 三段各 10ms 的查询并发起来只会更慢（多三次调度 + 多占两个连接） |
| **给连接池留余量** | 3 段并发 × 并发请求数，不能超过 `MaxOpenConns` |

### 用法二：限并发保护下游

**场景**：批量任务要调外部依赖 —— 下载图片、传 OSS、调三方 API。

```go
sem := make(chan struct{}, 16) // 数量取决于"对方能扛多少"，不是"我能起多少"
```

| 相关的三个东西 | 各自管什么 |
|---|---|
| **信号量**（本节） | 应用层：**同时在飞的任务数**上限 |
| **连接池**（`MaxOpenConns`） | 驱动层：**同时占用的连接数**上限 |
| **限流器**（[限流器.md](限流器.md)） | 入口层：**单位时间的请求数**上限 |

⭐ 三者不互相替代。实测过一个反例：2 万行数据"一行一个 goroutine、各自提交"，
连接池（16）确实挡住了 DB（**数据库没事**），但**应用侧堆了 1.9 万个协程**、
2 万个请求累计等连接 **7 小时** —— 连接池是天然闸门，但它不保证你的服务还健康。

### 用法三：常驻 worker（启动即起，退出靠 `close` + `WaitGroup`）

**场景**：消费型任务 —— 日志落盘、埋点上报、内部任务队列。

```go
jobs := make(chan Job, 1024)
var wg sync.WaitGroup
for i := 0; i < runtime.GOMAXPROCS(0); i++ {
	wg.Add(1)
	go func() {
		defer wg.Done()
		for job := range jobs { // close(jobs) 后自然退出
			job.Run()
		}
	}()
}
// 生产端：投完就关，由"唯一的生产者"负责 close，再等收尾
defer func() { close(jobs); wg.Wait() }()
```

⭐ **池不是用来提速的，是用来限流与复用资源的** —— 这一点第四节的实测会量化：
微 IO 场景下"每任务一协程"比 8 个 worker 的池**快约 100 倍**，
但池把并发上限焊死在 8，而这对"保护下游"恰恰是优点。

### 用法四：后台任务与优雅退出

```go
ctx, cancel := context.WithCancel(context.Background())
var wg sync.WaitGroup
wg.Add(1)
go func() {
	defer wg.Done()
	serve(ctx) // 内部是 for select { case <-ctx.Done(): return … }
}()

// 收到 SIGTERM / 关服信号时：
cancel()                            // ① 先把信号发出去
waitWithTimeout(&wg, 5*time.Second) // ② 再等收尾，但别无限等
```

| 顺序 | 为什么 |
|---|---|
| **先 `cancel()` 再 `Wait()`** | 反了就是死等（见 [../工程实践/context.md](../工程实践/context.md)） |
| **`Wait` 要带超时** | 有的任务卡在 IO 上，收不回来也得退 |
| **后台协程自带 `recover`** | 见案例 7：一个 panic 崩的是整个进程 |

### 延伸追问

- **`errgroup` 和 `WaitGroup` 怎么选？** → 需要"**一错全停**"用 `errgroup.WithContext`；
  只要结果、不要取消语义就用 `WaitGroup` + 按下标写切片。
- **限并发该用信号量、连接池还是限流器？** → 三者管的是不同层：**在飞任务数 / 占用连接数** /
  **单位时间请求数**。调外部依赖时通常三个都要有。
- **协程池该起多少个 worker？** → 任务**阻塞型**（等 IO）可以远多于核数，因为它不占 CPU；
  任务**计算型**就取 `GOMAXPROCS`。⚠️ 别靠猜：看下游能承受多少并发。
- **优雅退出为什么不能只 `cancel()`？** → `cancel` 只是**发信号**，不代表已经收尾；
  必须配 `WaitGroup` 等收尾，并给一个超时兜底。

## 三、端到端实例：导出对账 CSV，哪些环节能上 goroutine？

**本节要点**：检验"并发判据能不能落到真实接口上" —— 面对"这个导出接口能不能加并发"，
正确答案是**逐环节看**，而不是一句"能"或"不能"。

**分析对象**：`photography-server` 的 `FinanceExport`（导出对账 CSV；权限点独立于"查看"——
可见不等于可带走）。它由几个环节组成，每一环的答案都不一样：

```go
// internal/service/finance.go（现状：三段查询串行 + 内存拼 CSV + 返回 []byte）
sum, err := s.FinanceRepo.GetSummary(ctx, op.CompanyID, start, end)        // 四口径汇总
pays, err := s.FinanceRepo.ExportPayments(ctx, op.CompanyID, start, end)   // 收款流水
refunds, err := s.FinanceRepo.ExportRefunds(ctx, op.CompanyID, start, end) // 退款单据
var buf bytes.Buffer                     // ⚠️ 整份文件在内存里拼
w := csv.NewWriter(&buf)
// … w.Write(每一行) …
w.Flush()
return "财务对账-" + month + ".csv", buf.Bytes(), nil // ⚠️ 全部生成完才返回
```

| 环节 | 能不能并发 | 为什么 |
|---|---|---|
| **多个独立查询** | ✅ 能 | 三段互不依赖，`errgroup` 一把收 |
| **单个大查询** | ⚠️ 有条件 | 只能按区间 / 分页切片并发，且**必须保序**（否则导出文件行序错乱） |
| **写 CSV / 写响应** | ❌ 不能 | `csv.Writer` 与 HTTP 响应都是**单一有序流** → 只能**并发取数、串行写出** |
| **一次 `Find(&list)` 全量加载** | ❌ 不要 | 内存 O(行数)，且首字节要等全部查完 |

### 3.1 三段独立查询：能并发，但收益有限（实测 1.4~1.6x）

```go
var (
	sum     *Summary
	pays    []OrderPayment
	refunds []OrderRefund
)
g, gctx := errgroup.WithContext(ctx)
g.Go(func() error {
	var err error
	sum, err = s.FinanceRepo.GetSummary(gctx, op.CompanyID, start, end)
	return err
})
g.Go(func() error {
	var err error
	pays, err = s.FinanceRepo.ExportPayments(gctx, op.CompanyID, start, end)
	return err
})
g.Go(func() error {
	var err error
	refunds, err = s.FinanceRepo.ExportRefunds(gctx, op.CompanyID, start, end)
	return err
})
if err := g.Wait(); err != nil {
	return err // 任一段失败，其余请求随 gctx 一起被取消
}
```

实测（本地 SQLite 三表 5 万 / 3 万行，各跑 5 次）：

```text
① 串行三段查询    ~305ms
② 三段并发        ~205ms     加速比 1.41~1.56x
```

⭐ **收益为什么只有 1.5 倍**：三段查询在本地争同一块磁盘与 CPU，没有网络往返可重叠。
真实 MySQL 上每段各自有网络往返与执行时间，收益更接近"**最慢的那一段**"——
但如果三段都很快（比如都 < 50 ms），并发反而因为多占连接而不划算。

> 判据：**只有当「各段耗时之和」明显大于「最慢那一段」时，并发才有意义。**
> 三段各 10ms 的查询并发起来只会更慢（多三次调度 + 多占两个连接）。

### 3.2 真正的大头：「内存拼接」换成「流式写出」（实测 40 MB → 0 MB）

20 万行 CSV（18.5 MB），只改写出方式：

```text
① 内存拼接后一次性返回   耗时 ~110ms ｜ 内容 19419963 字节（18.5 MB）｜ 堆峰值增量 40.0 MB
② 流式写出（io.Writer）  耗时  ~80ms ｜ 写出 19419963 字节（18.5 MB）｜ 堆峰值增量  0.0 MB
```

（耗时是单次读数、重复跑在 ±40% 内波动；**两个堆峰值是稳定值** —— 40.0 MB 与 0.0 MB 每次都能复现。）

⭐ **内存差 40 MB，耗时还略快**（省掉了 `bytes.Buffer` 反复扩容搬数据）。

问题在**函数签名**：`FinanceExport(...) (string, []byte, error)` 这个 `[]byte` 决定了**没法流式** ——
必须整份生成完才能返回。要流式就得改成：

```go
// 把写入目标变成参数：生产环境传 http.ResponseWriter，测试传 bytes.Buffer
func (s *Service) FinanceExport(ctx context.Context, op Operator, month string, w io.Writer) (string, error)
```

代价是要重新安排"出错怎么办"：**响应头一旦发出就不能再改状态码**，所以要么先做一段能失败的准备
（查汇总 / 流水），要么约定"中途失败就把错误写进 CSV 的最后一行"（对账文件里这是可接受的）。

> ⭐ **导出场景的优化优先级**：① 流式写出 > ② 单查询拆并行 / 加索引 > ③ 三段小查询并发。
> 顺序搞反了会在小收益上花大力气。

### 3.3 导入：并发写不会更快，「批量 + 事务」才是关键

| 写法 | 20 万行耗时 | 说明 |
|---|---|---|
| 逐行插入（每行一次提交） | **13~14.3s** | 提交代价 × 行数 |
| 每 1000 行一个事务（单协程） | **1.8~1.9s** | 提交次数降到 1/1000 → **7~8 倍** |
| 每 1000 行一个事务 + 8 并发 | **2.9~3.0s** | ⚠️ **比单协程更慢**：写本身就是串行的，并发只是多花在抢锁上 |

（绝对耗时两次实测在 13.0~14.3s 之间波动；**"批量 ≫ 逐行、并发 < 单协程"这两条关系稳定**。）

同样 **2 万行**、改成"每次提交都真的 fsync"（贴近 MySQL 的 autocommit 语义）：

```text
④ 逐行插入（每次 fsync）  11.4~12.9s
⑤ 每 1000 行一个事务       0.19~0.30s     → 50~60 倍
```

⭐ 结论：**导入的银弹是「批量 + 事务」，不是 goroutine。**
写密集场景里，先问"一次事务能装多少行"，再谈并发——**并发度对写几乎无用**。

### 3.4 导入：无脑起协程的后果 —— 不会打挂 DB，但会堆在连接池上

"一行一个 goroutine、各自提交"（2 万行）：

```text
⑥ 一行一个 goroutine      耗时 2.531s ｜ 峰值协程 19098
连接池：MaxOpen=16 ｜ WaitCount=19984 ｜ WaitDuration=7h1m12s
```

⭐ **2 万个请求累计在"等连接"上花了 7 小时**。连接池（`MaxOpenConns=16`）挡住了对 DB 的直接冲击，
所以**数据库没事**；但**应用侧堆了 1.9 万个协程**，谁先拿到连接是随机的，延迟完全不可控。

> ⚠️ `WaitDuration` 是**累计值、随行数与等待分布波动**（两次实测 7h1m 与 5h22m），
> 要记的是它的**量级**：2 万个请求为了抢 16 个连接，累计等了好几个小时。
>
> 这是"**连接池是天然闸门，但不能替代应用层限并发**"的量化证据：
> 池只保证不打死 DB，不保证你的服务还健康。要限并发请用信号量（见案例 5）。

### 3.5 判据表：哪些环节该上 goroutine

| 场景 | 结论 | 做法 |
|---|---|---|
| 导出：多个独立查询 | ✅ 用 | `errgroup`；收益 ≈ 最慢那一段的耗时 |
| 导出：单个大查询 | ⚠️ 谨慎 | 按区间切片 + **保序**输出；通常不如先把索引 / 分页做好 |
| 导出：写 CSV / 写响应 | ❌ 不用 | **并发取数、串行写出**，并改成流式（`io.Writer`） |
| 导出：一次 `Find(&list)` 全量加载 | ❌ 不要 | 游标 / 分页 + 边查边写，内存与 TTLB 都受益 |
| 导入：解析与校验（纯 CPU） | ✅ 用 | fan-out 到 `GOMAXPROCS`；注意带行号以保持错误定位 |
| 导入：写库 | ❌ 不用 | **批量 + 事务**（1000 行/批），单协程足够 |
| 导入：调外部依赖（下载图片、传 OSS） | ✅ 用，必须限并发 | 信号量限 8~16，别把三方打挂 |
| 导入：进度反馈 | ⚠️ 别并发写 | 原子计数 + 定时上报，不要每个协程各写一次进度 |
| 导出 / 导入：超大文件 | ❌ 别放在 HTTP 请求里 | 落成异步任务（`xxl-job` / MQ）+ 轮询进度，见 [../../分布式/系统设计/数据导入导出设计.md](../../分布式/系统设计/数据导入导出设计.md) |

> ⭐ 一句话：**并发点要选在「纯计算」和「独立 I/O」上，绝不要选在「写库」和「写响应」上。**

## 四、这几种起法到底差多少？（实测对照）

**本节要点**：把第一节的形态放在同一把尺子上量 ——
"每任务一协程"和"固定 worker 池"到底谁快、峰值差多少、串行是不是真的更差。
**结论和直觉不一样**，这里是真跑出来的。

三个场景共用同一套骨架（20 万个任务；worker 池大小 8；`GOMAXPROCS=8`），
耗时取多次运行的区间，**峰值协程与分配量是稳定量**。

### 场景 A：纯计算（每个任务只有十几 ns）

| 写法 | 耗时 | 峰值协程 | 堆分配 |
|---|---|---|---|
| ① 每任务一协程 | 88~121ms | 53~1905 | 9.4 MB |
| ② 固定 worker 池（8） | 35~52ms | 10 | 0.0 MB |
| ③ **串行基线** | **3~7ms** | 2 | 0.0 MB |

⭐ **串行最快**，而且是快一个数量级。因为任务本身只有十几 ns，
而"起一个协程"要几百 ns、"过一次 channel"要一两百 ns ——
**并发有固定成本，任务粒度太细时它是负收益**。

### 场景 B：微 IO（每个任务等一次约 0.4ms）

| 写法 | 耗时 | 峰值协程 | 堆分配 |
|---|---|---|---|
| ① **每任务一协程** | **102~110ms** | 1637~1905 | ≈28 MB |
| ② 固定 worker 池（8） | 11.1~11.6s | 10 | 0.0 MB |
| ③ 串行基线 | 97.7~100.9s | 2 | 0.0 MB |

⭐ 这一场景反转了：**① 比池快约 100 倍**。因为每个任务都在"等"，
20 万个等待能**同时重叠**；而池只有 8 个在飞，等于把并发上限焊死在 8。

⭐ 所以：**池不是用来提速的，是用来限流的** —— 它把"慢"变成了"可控的慢"。

> ⚠️ 校准：程序里标称 `time.Sleep(10µs)`，实测平均睡 **390~500µs**（本机定时器粒度）。
> 不先量这一下，场景 B 会被误读成"10µs 的 IO"，结论就全错了。

### 场景 C：限并发的令牌，拿在 `go` 之前还是里面

（5000 个任务、每个约 0.4ms、上限 50）

| 令牌位置 | 耗时 | 峰值协程 | 堆分配 |
|---|---|---|---|
| ② 在 `go` 之前拿 | 59~65ms | **52** | 0.7 MB |
| ③ 在协程里拿 | 59~64ms | **2800~3900** | 2.0 MB |

⭐ **耗时一样，峰值差 60~70 倍**。两种写法都"限制住了同时执行 50 个"，
但 ③ 的循环已经把 5000 个协程**全创建完了**，它们只是卡在 `sem <-` 上 ——
**限住了"在跑"、没限住"在飞"**。背压要作用在"创建"这一步上才有效。

### 一点补充：峰值协程不是"任务总数"

场景 A 的峰值在多次运行里从 53 到 1905 都出现过，场景 B 稳定在 1600~1900。
差别在任务时长：**峰值 ≈ 创建速率 × 任务时长**。
所以"起 20 万个协程"并不等于"同时有 20 万个活着"——
但**上游一突发**（创建快、任务慢），这个数字就会立刻冲上去。

实验台：`.workbuddy/tmp/golab/workerpool/`（`go run ./workerpool`，现场跑三个场景并打印校准值）。

## 延伸追问

- **什么时候必须限并发？** → 只要调用了**容量有限的外部资源**（DB、三方 API、连接池）就必须限。
  实测：5000 个任务，无限制峰值协程 3702、耗时 46ms；限 50 后峰值 52、耗时 2.034s ——
  限并发是**用吞吐换可控性**，不是"更快"。
- **限并发的令牌写在 `go` 里行不行？** → 不行（或者说只做对了一半）。实测 5000 任务：
  令牌在 `go` 之前峰值 52，写在协程里峰值 3200~3900，**而耗时几乎相同** ——
  它限住了"在跑"，没限住"在飞"，内存峰值照样爆。
- **每任务起一个协程和 worker 池，谁快？** → **取决于任务在干什么**。实测 20 万任务：
  纯计算（十几 ns/个）时**串行最快**（3~7ms），池 35~52ms、每任务一协程 88~121ms；
  微 IO（每个等 0.4ms）时反转，**每任务一协程最快**（102~110ms），池要 11s+。
  池的价值在**限流**，不在提速。
- **为什么"起 20 万个协程"没有把内存撑爆？** → 因为**峰值 ≈ 创建速率 × 任务时长**：
  任务跑得快，峰值就只有几十到一两千个活着。但**上游一突发**，这个数字会立刻冲上去 ——
  所以判断内存风险要看任务时长的分布，不是任务总数。
- **`errgroup` 和 `WaitGroup` 怎么选？** → 需要"**一错全停**"用 `errgroup.WithContext`
  （实测任务 2 在 200ms 失败后，其余任务立刻被 ctx 取消，总耗时 200ms）；
  只要结果、不要取消语义就用 `WaitGroup` + 按下标写切片。
- **导入导出能用 goroutine 吗？** → **要逐环节看**：多段**独立查询**能并发（实测 1.4~1.6x）；
  **写 CSV / 写响应**绝不能并发（`csv.Writer` 与响应都是单一有序流）→
  只能"并发取数、串行写出"；**写库**不要并发（实测"每 1000 行一个事务 + 8 并发"
  比单协程**更慢**）。并发点要选在**纯计算**和**独立 I/O**上。
- **导入 20 万行，怎么最快？** → 不是加协程，而是**批量 + 事务**：实测逐行插入
  14.3s → 每 1000 行一个事务 1.77s（8.1 倍）；在"每次提交都 fsync"（贴近 MySQL 的 autocommit）下
  2 万行是 11.4s → 0.19s（**60 倍**）。先问"一次事务能装多少行"，再谈并发。
- **导出为什么要流式？** → 项目现状是 `bytes.Buffer` + 最后 `buf.Bytes()`，
  整份文件在内存里拼完才返回：实测 20 万行 18.5MB 的堆峰值增量 **40MB**，
  而流式写 `io.Writer` 是 **0MB**、耗时还略快。根因在函数签名 `(string, []byte, error)` ——
  要流式就得改成 `w io.Writer`。
- **无脑"一行一个 goroutine"写库会怎样？** → **不会打挂 DB，但会堆在连接池上**：
  实测 2 万行起 2 万个协程，峰值协程 19098、`WaitCount=19984`、`WaitDuration=7h1m12s`。
  连接池（`MaxOpenConns=16`）是天然闸门，但它只保证不打死 DB，不保证你的服务还健康。
