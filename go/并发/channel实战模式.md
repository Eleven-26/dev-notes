## Q1. 用 channel 通信的 6 个典型案例

**来源**：`p=6` 滴滴 Go 后端一面 · 时长 7分52秒
**考察意图**：channel 的用法是否能覆盖真实工程场景，而不是只会 `ch <- x` / `<-ch`。

### 案例 1：基本数据传递（生产者 → 消费者）

```go
ch := make(chan int) // 1. 创建无缓冲 channel

go func() { // 2. 启动生产者 goroutine
for i := 0; i < 10; i++ {
ch <- i // 3. 发送 0~9
}
close(ch) // 4. 发送完毕，关闭 channel
}()

for v := range ch { // 5. 消费者：循环接收
fmt.Println(v) // 6. 打印 0~9
} // 7. close 且数据取完后，range 自动结束
```
时序图（简化）
```text
生产者 goroutine                 main goroutine
      |                               |
      |--- ch <- 0 ------------------>| 收到 0，打印
      |--- ch <- 1 ------------------>| 收到 1，打印
      |--- ...                       |
      |--- ch <- 9 ------------------>| 收到 9，打印
      |                               |
      |--- close(ch)                  |
      |                               | range 再次接收，发现已关闭且无数据
      |                               | 循环结束
      |                               | main 返回，程序退出
```
### ⚠️ 关键点与注意事项
| 要点 | 说明 |
| --- | --- |
| 谁关闭 channel | 只有发送方应该关闭 channel，接收方关闭会 panic。 |
| 关闭后不能发送 | 向已关闭的 channel 发送数据会 panic。 |
| 关闭后仍可接收 | 接收方可以继续取完缓冲区中剩余数据，取完后返回零值。 |
| range 自动结束 | 当 channel 关闭且数据取完，`range`<br/> 自动退出，不需要手动判断。 |
| 无缓冲 vs 有缓冲 | 无缓冲强制同步；有缓冲时发送方在缓冲区满之前不会阻塞。 |
| 不关闭的后果 | 如果生产者不 `close`<br/>，`range`<br/> 会永远阻塞，导致死锁。 |

### 案例 2：信号传递 + 同步等待

场景：启动 3 个协程执行任务，需要等待全部完成。
做法：主协程从 channel 中**读取 3 次信号**，收到 3 个才算全部完成。
这是"同步等待"同时也是"信号传递"——`sync.WaitGroup` 的等价手写实现。

### 案例 3：生产者-消费者模式（双 channel）

需要**两个 channel**：
1. `dataCh`：传递生产的数据；
2. `doneCh`（关闭信号）：通知主协程进入下一步。

要点：消费者**没有天然的退出机制**，必须等生产者生产完毕、`dataCh` 被 `close` 之后
（`range dataCh` 结束）才能退出消费循环。

### 案例 4：用信号量限制并发数

用一个**缓冲区为 N 的 channel** 做信号量：容量 2 表示最多允许 2 个任务同时执行。
- 写入 = **获取**一个许可（缓冲满则阻塞）；
- 读出 = **释放**一个许可。

```go
sem := make(chan struct{}, 2) // 并发上限 2
sem <- struct{}{}             // 获取
defer func() { <-sem }()      // 释放
```

启动 5 个协程时，会有 3 个阻塞在写入上，直到前面的任务释放。

### 案例 5：用 channel 控制超时

```go
select {
case res := <-workCh:
    fmt.Println("完成:", res)
case <-time.After(2 * time.Second):
    fmt.Println("超时")     // 2 秒未完成走超时逻辑
}
```

`time.After` 返回的 channel 在指定时间后变得可读，与业务 channel 一起放进 `select` 即可实现超时。

### 案例 6：用 `close` 广播通知多个协程

**核心机制**：channel **关闭后**，所有阻塞在读取上的协程**都会立刻解除阻塞**（读到零值 + `ok=false`），
从而实现"一对多广播"，而不需要发 N 次信号。

```go
stopCh := make(chan struct{})
for i := 0; i < 5; i++ {
    go func(id int) {
        select {
        case <-stopCh:
            return          // 收到广播，直接退出
        case <-doSomething():
        }
    }(i)
}
close(stopCh)   // 5 秒后广播中止信号，5 个协程同时感知
```

**这是 `close` 与"发送 N 次"的本质区别**，也是 `context` 取消传播的底层机制。

## Q2. 项目里 channel 的 4 种典型用法

**来源**：`BV12qjA6aErF p=54` B站 Go 面试真题 · 时长 12分03秒
**考察意图**：Q1 的 6 个案例偏"语法演示"，本题偏**工程落地**——
尤其是**协程池**的写法与**单向 channel 的传参约定**。

### 总纲：只扣住一句话，场景自己长出来

> **channel 是用于协程间通信的。** 凡是"协程之间要传数据 / 传信号"的场景都可以用它组织；
> 不符合的（单纯互斥保护共享变量）就别硬套。

### 用法一：应用内部的生产者-消费者（典型：日志聚合）

**场景**：多个协程都会产生日志，如果各自写磁盘，会有锁竞争和随机写放大。

```
N 个业务协程  →（写入 chan）→  1 个日志协程  →  顺序落盘
```

- **谁生产谁关闭**：生产者写完 `close(ch)`，消费者用 `for range` 感知结束并退出；
- `for range` 在 channel 为空时会**阻塞等待**，不会空转（"不用担心没数据时一直读"）；
- **通道本身就是解耦点**：系统规模变大后，把"进程内的 channel"换成
  **Kafka / RabbitMQ** 这类中间件即可，上下游代码结构几乎不用改。

**⭐ 顺带一个工程细节：用单向 channel 表达"职责"**

```go
func producer(ch chan<- int)   // 只写：生产者只能发
func consumer(ch <-chan int)   // 只读：消费者只能收
```

| 写法 | 含义 |
|---|---|
| `chan<- T` | **只能发送**（生产者） |
| `<-chan T` | **只能接收**（消费者） |
| `chan T` | 双向（**双向可以隐式转成单向，反之不行**） |

**价值**：把"这个函数会不会往里写"写进**函数签名**，编译期就能拦住误用。

### 用法二：信号量控制最大并发数

**场景**：一批任务要并发跑，但不加限制可能瞬间起几十万个协程，把内存和后端打垮。

```go
sem := make(chan struct{}, 3)   // 缓冲区大小 = 最大并发数
for _, task := range tasks {
    sem <- struct{}{}           // 获取令牌：满了就阻塞在这里
    go func(t Task) {
        defer func() { <-sem }() // 释放令牌
        t.Do()
    }(task)
}
```

**机制**：**缓冲区的容量就是"许可总数"**——写入 = 拿许可（写不进去说明已到上限，阻塞），
读出 = 还许可。

**与"协程池"的区别**：

- **信号量**：协程**照创建照销毁**，只是同一时刻最多 N 个在跑；
- **协程池**：协程**数量固定**、长期存活，避免频繁创建 / 销毁的开销。

### 用法三：协程池（jobs / results 双 channel）

**场景**：任务量大、创建销毁协程的开销不可忽略时，用固定数量的 worker **常驻**等待任务。

```go
jobs    := make(chan Job)
results := make(chan Result)

for i := 0; i < 3; i++ {          // 固定 3 个 worker
    go func() {
        for job := range jobs {   // 从 jobs 取任务；jobs 被 close 后循环自然结束
            results <- job.Do()
        }
    }()
}
```

| 关键细节 | 说明 |
|---|---|
| **两个 channel** | 一个**下发任务**、一个**回收结果**，职责分开 |
| **多个 worker 读同一个 channel** | **安全且不重不漏**——channel 线程安全，每个元素只会被一个 worker 取到 |
| **worker 数量固定** | 没有新任务时 worker 阻塞在 `range` 上**不销毁**，有新任务立刻接上 |
| **退出机制** | 投递完 `close(jobs)`，worker 的 `for range` 自然结束（对应 [channel使用陷阱.md](channel使用陷阱.md)"关闭后仍可读"） |

> 这就是"协程池"最朴素的实现：**不需要自己写调度器——channel 就是队列，
> `for range` 就是 worker 的主循环**。

### 用法四：事件通知 / 优雅退出

```go
func serve(stopCh <-chan struct{}) {
    for {
        select {
        case <-stopCh:   // ★ 收到关闭广播，退出
            return
        default:
            doWork()
        }
    }
}
```

**底子就是 [channel使用陷阱.md](channel使用陷阱.md) 讲的"`close` 广播"**：`close(stopCh)` 会让所有等待在这个 channel 上的协程
**同时**被唤醒。

**更优雅的写法：`context`**

```go
select {
case <-ctx.Done():   // 与 close(ch) 是同一套底层机制
    return
}
```

> `ctx.Done()` 返回的就是一个 channel，`cancel()` 的语义等价于关掉它——
> 所以"看懂 `close` 广播，就理解了 `context` 的取消传播"，
> 只是 `context` 额外帮你挂上了**超时、父子传播、值传递**。

### 面试官会追问什么

- **怎么选"信号量"还是"协程池"？** → 任务**短促、量大**且能容忍频繁启停 → 信号量；
  任务**持续到达**、希望控制常驻协程数 → 协程池。
- **多生产者怎么安全关闭 channel？** → 发送方用 `sync.WaitGroup` 等到所有生产者退出，
  再由**一个**协程 `close`；接收方只负责 `for range` 读空。
- **协程池怎么保证"正在跑的任务不丢"？** → 收到停止信号后**不再投递新任务**，
  再 `close(jobs)` 让 worker 把队列里剩下的任务做完后自然退出；
  必要时用 `WaitGroup` 等它们全部结束。
- **`context` 取消和 `close(ch)` 有区别吗？** → 底层都是"关闭 channel 触发广播"，
  `context` 多了**层级传播**（子随父取消）、**超时 / 截止时间**和**值传递**。

## Q3. 多生产者 + 单消费者：两个同步点怎么落

**来源**：`BV1EL4y1P7hh p=2` 马哥教育 Go 面试精讲 · 时长 56分33秒
**考察意图**：Q1 的案例、Q2 的用法都停在片段。本题是一个**完整可运行**的例子——
考的是"生产者何时算全部结束""主协程何时能退出"这两个同步点怎么落地。

### 场景：并发合并多个小文件

IO 慢，所以每个文件各开一个协程并发读，读出的内容统一写进一个**公共管道**，
再由一个消费者协程顺序写进最终文件：`N 个读取协程 →（公共管道 content）→ 1 个合并协程 → 输出文件`。

### 同步点一：怎么知道"生产者都干完了"——别用 sleep

最初的写法通常是 `time.Sleep(time.Second)` 等协程结束，**这不可靠**：
文件多大不知道、机器快慢不知道，**sleep 多久都是猜**。

可靠的信号应该是"**全部生产者结束**"这个**事件**：**每个生产者结束时交回一个信号，收满 N 个就说明全部干完**——这就是**手写版 `sync.WaitGroup`**。

```go
package main

import "fmt"

func produce(name string, content chan<- string, done chan<- struct{}) {
	for i := 1; i <= 2; i++ {
		content <- fmt.Sprintf("%s-%d", name, i)
	}
	done <- struct{}{} // ① 我干完了，交回一个信号
}

func main() {
	content := make(chan string)   // 公共管道：多生产者 → 单消费者
	done := make(chan struct{}, 3) // 容量 = 生产者个数
	for _, f := range []string{"a", "b", "c"} {
		go produce(f, content, done)
	}
	go func() { // 守望者：收满 3 个信号 = 所有生产者都已结束
		for i := 0; i < 3; i++ {
			<-done
		}
		close(content) // ★ 只在这里关，且只关一次
	}()
	for line := range content { // ② 消费者：读空 + 已关闭 才退出
		fmt.Println("merge:", line)
	}
	fmt.Println("merge done")
}
```

**结论**：`close(content)` 是生产者与消费者之间唯一的"收工"约定，由**确认所有生产者已退出**的那个协程执行（呼应 [channel使用陷阱.md](channel使用陷阱.md) 判据 3），消费者只负责把管道读空。

### 同步点二：消费者怎么通知 `main`

同一套路再用一次：用一个**无缓冲或容量 1** 的 channel 传"结束信号"，`main` 阻塞读取。

```go
exitCh := make(chan struct{})
go func() { defer close(exitCh); /* ...消费逻辑 */ }()
<-exitCh // main 在这里等，消费者干完才放行（同样等价于 WaitGroup）
```

**把两个同步点串起来看**：`done`（生产者 → 守望者）、`content`（生产者 → 消费者）、
`exitCh`（消费者 → `main`）——流水线上每个交接点都是 channel。

### 一个必须知道的副作用：顺序不可控

多个生产者往**同一个**管道里写，聚合顺序**完全由并发调度决定**，每次运行都可能不同
（原视频里 a/b/c 三个文件合并出来是 `a-1,b-1,c-1,a-2,...` 这类交错）。
**内容不丢，但顺序不保**——需要严格顺序就得给数据带序号，在消费端排序 / 缓冲。

### 面试官会追问什么

- **为什么不能用 `time.Sleep` 等协程结束？** → 等待时间无法预知，
  **等短了逻辑出错、等长了白等**；应该用 `sync.WaitGroup` 或"收满 N 个信号"这种**事件驱动**的等待。
- **消费者发现管道暂时空了，能直接退出吗？** → 不能。可能只是**消费者跑得比生产者快**，
  空一下不代表没有新数据；**唯一可靠的退出条件仍是"管道已空 + 已 `close`"**。
- **等协程结束该用 `sync.WaitGroup` 还是 channel 信号？** → 只"等一批协程结束"用 `WaitGroup` 最简洁；
  若这个**结束信号本身还要参与 `select` 多路复用**，channel 更灵活，两者也可以混用。
