## Q1. 使用协程过程中会遇到哪些问题？需要注意什么？

**来源**：`p=70` 腾讯云智后台开发一面 · 时长 10分43秒
**考察意图**：这题**很难靠背答案**，因为面试官会追问"你实际遇到过什么"。
**协程泄漏的四类成因**是这题最有价值的部分。

### 一、问题无非两大类

```
① 协程泄漏
② 协程间协调 / 协程间通信的问题
```

**⚠️ 一个面试技巧（原视频说的很直接）**：

> 如果被问"你遇到过什么问题"而你**完全没遇到过**，
> 那**侧面说明你协程用得很少**——
> 因为**刚上手用协程不出问题基本是不可能的**。
>
> **如果确实没遇到过，就去搜"别人踩过哪些坑"**，把别人的经验变成自己的回答。

### 二、常见的四类具体问题

| 问题 | 说明 |
|---|---|
| **① 协程泄漏** | 见下方专题 |
| **② 死锁** | 多个协程**相互等待**，或都在**等一个共享资源**，导致某些协程永远拿不到数据 |
| **③ channel 使用不当** | 可能造成 **panic** 或**协程死锁** |
| **④ 数据竞态** | 多个协程访问**共享变量**，最终结果**不符合预期** |

### 三、⭐ 协程泄漏的四类成因（本题核心）

#### 类型 1：一直在运行的协程

> **没有中止条件**，所以它**一直在执行**，永远不会退出。

#### 类型 2：一直在阻塞的协程

> 一直**拿不到资源** → 永远挂起、不会退出。
>
> ⚠️ **这类最阴险**：**它不会报错、不会 panic**，
> 只是默默挂在那里占着资源。

#### 类型 3：海量协程

**场景**：把一个大任务**拆成多个小任务并行执行**，全部完成后再继续大任务。

> **并发量不大时没问题，这个方案本身就是对的。**
>
> **但问题出在流量上**：当**大量流量涌进来**，
> 协程**来不及处理**（每个协程都要占资源和时间），
> **服务器资源被耗尽** → 表现为协程泄漏。

**解法：用协程池限流**

> 例如固定最多 1000 个协程，**超过 1000 就等待**，
> 而不是无限制地为每个请求创建新协程。
> **从根上避免"海量协程"这种泄漏。**

#### 类型 4：一直未被回收的连接对象（原视频的真实生产案例）⭐

**场景**：用 **`sync.Pool`** 做一个 **gRPC 客户端连接对象池**。

```
Pool 容量设为 4
    ↓
流量小的时候：Pool 里对象数 ≈ 4，正常
    ↓
流量大的时候：最多获取 4 个，不够就新创建
            用完丢回 Pool → Pool 里可能有 10 / 20 / 40 个对象
    ↓
流量降下来后：Pool 里看起来恢复到了 ≤ 4 个
             ❗ 但多出来的那些连接对象并没有被销毁
```

**为什么没被销毁（这是关键）**：

> **gRPC 客户端与服务端之间有「心跳」**，
> 所以这些连接对象**即使不在 `sync.Pool` 里，也仍然存活在内存中**。
>
> 结果：**GC 无法回收它们**（还有存活的引用），
> **而自己的代码又拿不到它们**（已经不在池子里了）——
> **彻底"失控"了。**

**后果（两个叠加）**：

| 后果 | 说明 |
|---|---|
| **① 内存泄漏** | 对象越来越多、又回收不了 → 内存持续增长 |
| **② 协程泄漏** | **每启动一个 gRPC 连接对象会产生 3~4 个协程** →<br>**一台 4 核机器上出现了约 1200 个协程** |

**根因**：**连接池的实现问题**——没有正确地关闭/复用超出的连接对象。

### 四、怎么排查协程泄漏：pprof

**做法**：
```
① 在后台服务中引入 pprof，启动 web 服务
② 访问 /debug/pprof/ 查看协程相关信息
```

**判断标准（原视频给的经验）**：

> - 协程数**没什么动静**，或**浮动很小** → **正常**；
> - **明显超出平常的活动范围**，而且**降不下来** → **一定有问题**。

**实例**：刷新一次从 8 个变 12 个 → 再调一次接口，**协程数暴增且不下降** → 就是泄漏了。

**定位**：
> 点进 pprof 的协程详情，**看这些协程是在什么地方启动的**（地址、代码路径），
> 找到大概位置后去分析代码逻辑。

### 五、使用协程需要注意什么（对应上面逐条）

| 要检查的点 | 具体问题 |
|---|---|
| **① 有没有泄漏** | 协程**有没有关闭条件**？**会不会一直阻塞**？**会不会死锁**？ |
| **② 会不会海量协程** | 能否用**协程池**把并发数限制住？ |
| **③ 有没有数据竞态** | 只要有多个协程访问**共享变量**，就要考虑会不会导致结果不符预期 |

> **一句话总结**：
> **每写一个 `go` 关键字，就要问自己三个问题——
> 它什么时候退出？会不会无限增长？它碰了哪些共享数据？**

### 面试官会追问什么

- **协程泄漏了怎么修复？** → ① 给协程加明确的退出条件（`ctx.Done()`）；
  ② 所有阻塞点都要能被打断（`select` + `ctx.Done()`）；
  ③ 连接池/资源池必须实现真正的**关闭与回收**（`defer conn.Close()`）；
  ④ 加**协程数监控与告警**（pprof / Prometheus 指标）。
- **怎么预防而不是事后排查？** → 统一用 `errgroup.WithContext` 管理协程组，
  **确保父 context 取消时所有子协程都能退出**；配合 `-race` 做竞态检测。
- **`sync.Pool` 适合放什么？** → 放**可丢弃、可重建、无外部句柄**的临时对象
  （如 buffer、序列化中间对象）。
  **不适合放长连接**——因为它可能在 GC 时被清空，
  而清理逻辑不一定能正确关闭底层连接，**正是上面那个案例的坑**。

## Q2. 协程泄漏的常见最小复现（channel / 锁 / context）

**来源**：`BV12qjA6aErF p=32` B站 Go 面试真题 · 时长 12分28秒
**考察意图**：Q1 讲"泄漏分几类"，这一题考的是**能不能把每一类还原成几行能跑的代码**——
面试官听到你说得出"最小复现"，就知道你是真踩过而不是背的。
> **判断口径**：**"永远出不去"就是泄漏**——在等一个**永远收不到的数据**、
> 一把**永远不会释放的锁**，或者**压根没有退出条件**。

### ① 无缓冲 channel：只有发送方，没有接收方

```go
ch := make(chan int)    // 无缓冲
go func() { ch <- 1 }() // ← 此刻没有接收者，永久阻塞在 send 上
```

### ② 接收方在等一个永远不会 close 的 channel

```go
ch := make(chan int, 10)
go func() { for range ch { /* ... */ } }()  // range 只在 close 之后才结束
// 生产者用完不 close(ch) → 协程永远停在 range 上
```

> **约定：谁写入、谁关闭**——由生产者 `close(ch)`，接收方的 `range` 才能退出。

### ③ `select` 里没有 `default`，也没有退出分支

```go
go func() {
    select {
    case v := <-ch:
        _ = v
        // ← 只监听这一个业务 channel；上游不再发数据 → 永远不被唤醒
    }
}()
```

> 修法：**每个长期运行的 `select` 都要留一条退出出口**，即补上
> `case <-ctx.Done(): return`（写法见 ④ 的正确版本）。

### ④ context 没把超时/取消传下去

```go
go func() { <-context.Background().Done() }()   // ✗ 永远不会触发
go func() { <-ctx.Done() }()                    // ✓ 跟着父级一起退出
```

> `context` 的取消是**向下传播**的。一旦链路上换成 `context.Background()` / `TODO()`，
> **父子关系就断了**——上层再怎么 `cancel()` 也管不到这个协程。
> 这是"阻塞型泄漏"最常见的生产来源。

### ⑤ 锁没释放

```go
mu.Lock()
// ← 中间某个 return / panic 分支忘了 Unlock → 后面所有等锁协程永久阻塞
```

> 兜底只有两种写法：**`defer mu.Unlock()`**（推荐），或**成对出现且覆盖所有分支**。

### 面试官会追问什么

- **怎么在测试里抓泄漏？** → `go.uber.org/goleak` 在用例结束时比对协程数，
  或自己用 `runtime.NumGoroutine()` 前后对比（配合 Q1 的 pprof 思路）。
- **channel 忘了 close 会 panic 吗？** → **不会**——正因为不 panic 才隐蔽；
  反过来**重复 close**、**向已关闭的 channel 发送**才会 panic。

## Q3. 什么情况下会产生死锁？

**来源**：`BV1xSRXBwEeM p=75` 虾皮 Go 后端开发面试 · 时长 8分21秒
**考察意图**：面试官想看**你能不能把课本上的"死锁"还原到 Go 的锁 / channel / WaitGroup 上**——
因为实际开发里绝大多数死锁**不报错、不 panic，只是永远卡住**。

### 一、底层逻辑与判断原则

> **一个或多个协程竞争同一批资源，导致谁都无法推进、永久阻塞在等待上——这就是死锁。**
>
> **判断原则**：**只要出现"一个或多个协程永久等待"，就一定是死锁**——不管它有没有报错。

| | **运行时会报的** | **运行时报不了的** |
|---|---|---|
| **表现** | `fatal error: all goroutines are asleep - deadlock!` | 没有任何输出，程序就是卡住 |
| **原因** | 所有协程都阻塞，且**没有任何能打破僵局的外部事件** | 只有**部分**协程互相等待，其他协程还在跑 |
| **定位** | 看 panic 栈即可定位到行 | **只能靠经验目视代码**找互相等待的那几处 |

**那个 `fatal error` 的触发条件**（很多人讲不清）：**所有用户协程都阻塞，
且不存在能打破僵局的事件**——没有活跃 timer（无超时的 `time.After`）、没有 netpoll；
运行时判定"再也动不了了"就主动 throw。

> ⚠️ **只要还有任何一个协程在跑**（一个 `for {}` 忙等、一个没超时的网络调用），
> 这个 fatal error **永远不会出现**——死锁就变成"静默卡死"。

### 二、五种典型死锁

**case 1 · 两个协程互持对方要的锁（经典循环等待）**

```go
var mu1, mu2 sync.Mutex
go func() { mu1.Lock(); mu2.Lock() }()   // A：先 1 后 2
go func() { mu2.Lock(); mu1.Lock() }()   // B：先 2 后 1 → 互相等
```

> 和数据库死锁一模一样：A 拿着 mu1 等 mu2，B 拿着 mu2 等 mu1。
> **解法：全局统一加锁顺序**（都按"先 1 后 2"申请），配合 `TryLock` + 超时回退。

**case 2 · 同一协程重复加锁（不可重入锁把自己锁死）**

```go
func f() {
    mu.Lock()
    defer mu.Unlock()   // defer 在 return 之后才执行
    mu.Lock()           // ← 锁已被自己持有 → 永久阻塞，自己等自己
}
```

**case 3 · channel 收发不匹配**

```go
ch := make(chan int)   // 无缓冲
ch <- 1                // ← 前面没有接收者，这里就阻死了；<-ch 永远执行不到
```

> **无缓冲 channel 的"发送"要求"此刻就有接收方"**。
> 视频里就是"接收写在了发送之后"——顺序反了。解法：调换顺序或改用带缓冲 channel。

**case 4 · `WaitGroup` 计数不匹配**

```go
wg.Add(1)
go func() { /* 忘了 wg.Done() */ }()
wg.Wait()   // ← 计数永远归不了零 → 永久等待
```

> `Wait()` 等的是**计数归零**，所以 **Add / Done 必须一一配对**。

**case 5 · `WaitGroup.Wait()` 与 `channel close` 互相等待** ⭐

```go
wg.Add(1)
go func() { defer wg.Done(); for { select { case <-ch: case <-done: return } } }()

wg.Wait()     // ← 先等协程退出
close(done)   // ← 但协程要等这里 close 之后才退出
```

> **"顺序反了"造成的循环等待**：`Wait()` 等协程退出，协程退出等 `done` 被 close，
> 而 `close` 又写在 `Wait()` 后面。
> ⚠️ **实测现象**：程序只打印启动信息就卡住，**连 `Ctrl+C` 都退不掉**——
> 主协程阻塞在 `Wait()` 上，接收中断信号的代码**根本没机会执行到**，只能杀进程。

### 三、死锁的四个必要条件（课本 → Go）

| 必要条件 | 含义 | 在 Go 里的对应 | 破解手段 |
|---|---|---|---|
| **互斥** | 资源同一时刻只能被一个持有者占用 | `Mutex` 的临界区、channel 中的数据 | 能用无锁就用 `atomic` / 分片 |
| **请求与保持** | 已持有资源，又去申请新资源 | A 持 mu1 再去 `mu2.Lock()` | **一次性申请全部资源**；统一加锁顺序 |
| **不可剥夺** | 资源不能被强行夺走，只能持有者主动释放 | 锁只能由持有者 `Unlock` | `TryLock` + 超时后放弃并释放 |
| **循环等待** | 存在"我等你、你等他、他等我"的环 | case 1、case 5 都是 | **打破环路：全局排序 + 统一顺序** |

> **面试点**：四个条件**只要破坏任意一个**，死锁就不可能发生。
> 工程上最容易做到的是**破坏"循环等待"**（统一加锁顺序）
> 和**破坏"请求与保持"**（一次性申请）。

### 四、怎么检测 / 定位

| 手段 | 能做什么 |
|---|---|
| **pprof `/debug/pprof/goroutine?debug=2`** | 打印**所有**协程的调用栈——直接看谁卡在同一把锁 / 同一个 channel 上 |
| **`runtime.Stack(buf, true)`** | 代码里主动 dump 全量协程栈，可周期性落盘 |
| **`GOTRACEBACK=all` + `SIGQUIT`** | 进程卡住时抓一份"现场快照"，不用重启就能看 |
| **`go vet`** | 静态检查 `Mutex` 的**值拷贝**、`WaitGroup` 误用等低级错误 |
| **`go run -race` / `go test -race`** | 抓的是**数据竞争**而非死锁，但能提前暴露很多死锁的根源竞态 |
| **超时兜底（最实用）** | 所有等待都带 `context.WithTimeout`——**卡住时至少返回错误，而不是永久挂起** |

> **优先级建议**：**"超时兜底"是第一道防线**——它把"死锁"**降级成"超时错误"**，
> 前者只能靠重启恢复，后者业务上还能兜住。

### 面试官会追问什么

- **死锁、活锁、饿死有什么区别？** → 死锁是**都不动**；
  活锁是**都在动但谁也推进不了**（互相让路）；
  饿死是**某个协程一直抢不到资源**（Mutex 的饥饿模式就是为解决它，见 [并发同步原语.md](并发同步原语.md) 的 Q4）。
- **单协程也会死锁吗？** → **会**。重复加锁、`ch <- 1` 无接收者、
  计数不为零时 `Wait()`，**一个协程就能把自己锁死**——
  此时运行时**通常能报** `all goroutines are asleep`。
- **为什么 Mutex 不可重入？`select` 能避免死锁吗？** → 前者：可重入要记录持有者与重入次数，
  **开销和复杂度都上去了**，Go 的取向是**别在临界区里再调可能加锁的函数**；
  后者：`select` 只是**多给一条退出路径**，**不自动解决循环等待**——根因还是得改代码。
