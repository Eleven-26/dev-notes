## Q1. 能不能先判断 channel 是否阻塞，再写入数据？

**来源**：`p=46` 深信服 Go 面试 · 时长 7分00秒
**考察意图**：这是一道**边界细节题**，能答出"只有 select + default 这一个点可以"就很强。

### 结论先行

> **在编程层面，我们无法"先判断它是否阻塞，再写入"。**
>
> 但 **channel 底层实现里确实提供了类似的判断逻辑**——
> **只存在于一个地方：多路复用（`select`）且带 `default` 子句时**（即**非阻塞模式**）。

### 一、常规写入：没有事前判断

```go

ch <- data   // 要么成功，要么阻塞，要么 panic（已关闭）
```

**普通 channel 读写只能"事后看结果"，没有事前判断**：
- 写成功 ✅
- 写不成功 → **要么阻塞**（等接收方），**要么 channel 已关闭**（panic）

> 我**不能**先问一句"现在能写吗？"，**不存在这种写法，也不存在这种返回值**。

### 二、唯一的例外：`select` + `default`

```go

select {
case ch1 <- v:          // 能写就写
    // 写成功了
case ch2 <- v:
    // 写成功了
default:
    // ★ 前面都写不进去 —— 尝试过但没写成功，于是不写了
}
```

**注意措辞的准确性**：这不是"**先判断**能不能写"，
而是"**尝试写，写不进去就走 default**"——
**本质是尝试后失败，而不是事前询问**。

⚠️ **反例：如果 `select` 没有 `default` 子句**

```go

select {
case ch1 <- v:   // 若 ch1 写不进去
case ch2 <- v:   // 若 ch2 也写不进去
}
// 没有 default → 两个都写不进去就永久阻塞
```

原视频演示：放入 10 次，但 channel 空间有限且**没有读取的协程**
→ 填满之后直接**死锁**（`fatal error: all goroutines are asleep`）。

### 三、从底层 `chansend` 看"能写成功"的四个快路径

`runtime` 包的 `chansend` 返回一个 **bool 值**表示**本次发送是否成功**。
只有 **`block == false`（非阻塞模式，即 `select` + `default`）** 才会返回 `false`，
阻塞模式下则直接挂起。

**非阻塞模式下的四条"能立刻成功"的快路径**：

| # | 判断条件 | 结果 |
|---|---|---|
| **①** | **`recvq` 非空**（有协程在等我发数据） | 直接把数据交给它 → **成功**。<br>注意：接收队列非空说明**缓冲区必然为空**——因为如果有数据，接收协程早就取走了 |
| **②** | **`qcount < dataqsiz`**（缓冲区没满） | 直接写入缓冲区 → **成功**（一定能写入，所以也算非阻塞） |
| **③** | **channel 未初始化（nil）** | 非阻塞模式 → **返回 `false`**；阻塞模式 → **阻塞** |
| **④** | **channel 已关闭** | 非阻塞模式 → **返回 `false`**；阻塞模式 → **抛异常（panic）** |

**①② 都不满足，且不是 ③④ 的情况（缓冲区满、也没有等待的接收方）**：
- **非阻塞模式** → **返回 `false`**，于是命中 `select` 的 `default` 分支；
- **阻塞模式** → 把当前协程**包装成一个 `sudog`，加入 `sendq`（发送等待队列）并挂起**。
  代码就停在这里，**只有接收流程来激活它才会继续往下走**。

### 四、一句话总结

> **`channel` 只有"写成功 / 写失败"两种结果，没有"事前判断是否阻塞"的 API。**
> **唯一的擦边球是 `select` + `default`**——它是"**尝试写入，写不进去就走 default**"的
> **非阻塞模式**，靠的是底层 `chansend` 在 `block=false` 时**返回 bool** 这个机制。
> **除此之外任何情况都做不到"先判断再写"。**

### 面试官会追问什么

- **为什么 `select` + `default` 能"不阻塞"？** → 因为编译器会把它编译成
  `chansend(c, v, false, ...)`，**`block=false` 表示"能写就写，不能写就返回 false"**。
- **`select` 多个 case 同时就绪会怎样？** → **随机选一个**执行，
  这是 Go 刻意设计的，避免某些 channel 被"饿死"。
- **怎么优雅地做"带超时的写入"？** →
  `select { case ch <- v: case <-time.After(d): }`——
  注意 `time.After` 会创建定时器，高频场景建议用 `time.NewTimer` 并复用/停止。

## Q2. 用 channel 时最容易踩的 4 个点

**来源**：`BV12qjA6aErF p=5` B站 Go 面试真题 · 时长 9分37秒
**考察意图**：[channel原理与底层实现.md](channel原理与底层实现.md) 讲的是"结构怎么工作"，本题站在**使用者**角度——
channel 的语义边界在哪里、哪些操作**合法但反直觉**。

### 先定住用途：channel 只干一件事

> **channel 是用于协程间通信的。**（"用通信来共享内存"）

判断一个场景该不该用 channel，只需问一句：
**"这里是不是两个（或更多）协程之间要传数据 / 传信号？"**
是 → 可以用；只是单纯保护一块共享数据 → 用 `sync.Mutex` / `atomic` 更合适。

### 注意点一：收发必须成对，否则一定死锁

> **一个 channel 要有发送方、也要有接收方**；只发不收，发送协程会**永久阻塞**。

```go

ch := make(chan int)
ch <- 1   // ❌ 无缓冲 + 没有其他协程在收 → fatal error: all goroutines are asleep - deadlock!
```

**两条出路**：
1. 把接收方放到**另一个协程**里（`go func() { <-ch }()`）；
2. 用**缓冲区**兜底（`make(chan int, 1)`），让发送**不必等接收方同步就绪**。

### 注意点二：`close` 是"广播"，不是"发一个值"

**关闭一个 channel 时，它会向所有在该 channel 上等待的协程发送一个广播通知**，
而不是只唤醒其中一个：

```
close(ch)  →  所有阻塞在 <-ch 的协程同时被唤醒  →  每个都读到零值 + ok = false
```

| 元素类型 | 被广播时"收到"什么 |
|---|---|
| `chan int` | `0` |
| `chan string` | `""` |
| `chan struct{}` | `struct{}{}` |

**这正是"一对多通知"的最佳手段**：不用发 N 次信号，一次 `close` 让所有等待者同时感知——
`context` 的取消传播就是这么实现的（对应 [channel实战模式.md](channel实战模式.md) 案例 6）。

### 注意点三：channel 关闭之后，**仍然可以读取**

> **"我写完了就 `close`，读的那一方会不会读不到数据？"——不会。**

| 情况 | 关闭后读取的行为 |
|---|---|
| **有缓冲且缓冲区还有数据** | 按 FIFO **把剩余数据读完**，不丢数据、不报错 |
| **有缓冲但已读空** | 返回**零值**，`ok = false` |
| **无缓冲** | 立即返回**零值**，`ok = false`（**不会 panic**） |

**所以 `close` 的正确含义是"不会再有新数据了"，而不是"数据没了"。**

### 注意点四：会不会阻塞，取决于"有没有缓冲 + 有没有对手方"

| 操作 | 无缓冲 | 有缓冲 |
|---|---|---|
| 发送 | 必须有接收方**同步就绪**，否则阻塞 | 缓冲区**没满**就立即返回 |
| 接收 | 必须有发送方**同步就绪**，否则阻塞 | 缓冲区**有数据**就立即返回 |
| 读已关闭的 channel | 立刻拿到零值 | 先读完剩余数据，再拿零值 |

**一句话**：缓冲区的存在，把"同步交接"变成了"**发送方可以先走**"的异步语义。

### 面试官会追问什么

- **`close` 一个已关闭的 channel 会怎样？** → panic（`close of closed channel`）。
  **关闭的责任只归发送方**，且只 `close` 一次。
- **接收方能 `close` 吗？** → 如果有多个发送方，接收方 `close` 之后它们再发送就会 panic
  （`send on closed channel`）。正确做法是**发送方用 `sync.WaitGroup` 收敛后，
  由单一协程 `close`**。
- **关闭后一直不读会怎样？** → 有缓冲时剩余数据**留在缓冲区**（不是被清空），
  `len(ch)` 能看出还剩几个；这个 channel 最终会被 GC 回收。
- **`chan struct{}` 为什么是通知的首选？** → 元素**零内存**，只表达"信号"、不承载数据，语义最干净。

## Q3. channel 的死锁到底什么时候报？——四条判据

**来源**：`BV1EL4y1P7hh p=2` 马哥教育 Go 面试精讲 · 时长 56分33秒
**考察意图**：Q2 只说了"收发不成对会死锁"。本题补的是**判定链路**：
阻塞之后协程在等谁、谁有能力来解救它、Go 凭什么在某一刻断定"没救了"。

### 四条判据

1. **管道满了再写 → 阻塞；管道空了再读 → 阻塞。**（最好理解的一条）
2. **阻塞的协程会交出 CPU 使用权**，让 CPU 去执行其他协程。
   它不是"躺平"，而是有个小心思：**希望别的协程来解救自己**——
   写阻塞（缓冲满）→ 希望有人来**取走**；读阻塞（缓冲空）→ 希望有人**放**进来。
3. **阻塞的是 `main`，且此时除 `main` 外已无任何其他协程** → 没人能来解救它，
   "这个希望永远等不来"于是不再等：抛 `fatal error: all goroutines are asleep - deadlock!` 终止进程。
4. **阻塞发生在普通协程里 → 不报死锁**：只要 `main` 还在，就永远"有可能"有新协程来解救它，
   于是它会**一直等下去**。

> **判定死锁的标准不是"有没有阻塞"，而是"所有协程（含 `main`）是否都被永久阻塞、还有没有人能来解救"。**

### 判据 4 的验证：普通协程阻塞，程序静默退出（不报错）

```go

func main() {
	ch := make(chan int, 1)
	ch <- 1 // 缓冲区已满
	go func() {
		ch <- 2 // 没人接收 → 该协程永久阻塞
		fmt.Println("永远不会打印")
	}()
	time.Sleep(100 * time.Millisecond)
	fmt.Println("main 正常结束") // ← 会打印，且没有任何 deadlock 报错
}
```

**结论**：阻塞在普通协程里**不会有任何提示**，比 panic 更隐蔽——线上"协程泄漏"多半就是这么来的。

### 判据 3 的验证：`for range` 忘了 `close`，`main` 直接死锁

```go

func main() {
	ch := make(chan int, 3)
	for i := 1; i <= 3; i++ {
		ch <- i
	}
	// close(ch) ← 漏了这一行
	for v := range ch {
		fmt.Println(v) // 打印出 1 2 3
	}
}
// 读空后 range 继续等数据 → main 阻塞且无人解救
// fatal error: all goroutines are asleep - deadlock!
```

**结论**：**`for range` 的退出条件是"管道已空且已 `close`"**——
只空不关就会一直等。这正是"谁生产谁关闭"必须成为纪律的原因。

### 面试官会追问什么

- **为什么普通协程阻塞不报死锁？** → 因为 `main` 还活着，runtime 认为"还有希望"；
  只有所有协程都睡死、没有任何协程能推动局面时，才会判定死锁并中止进程。
- **阻塞的协程占 CPU 吗？** → 不占。阻塞即**交出 CPU 使用权**（挂起，让给其他协程执行），
  所以 channel 远比"忙等 + 轮询"高效。
- **`for range` 遍历管道什么时候退出？** → 见判据 3 结论：**管道已空且已关闭**两个条件同时满足；
  只空不关是**阻塞等待**，既不是退出，也不是空转。
- **实际怎么排查死锁？** → 看 `fatal error: all goroutines are asleep - deadlock!` 之后打印的
  **协程栈**，找到停在 `chan send` / `chan receive` 上的那个协程，顺着看它等的对手方是谁。
