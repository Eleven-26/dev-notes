# Go 零拷贝（zero-copy）

> 零拷贝省掉了哪几次拷贝、五种实现路径的取舍，以及 Go 标准库里它"自动生效"与"静默失效"的分界线
>
> 内容整理自大厂 Go 后端面试真题视频，参考资料与原始素材见 [素材清单](../../面试/素材清单.md)。

## Q1. 什么是零拷贝？它到底要解决什么问题？

**来源**：`BV1xSRXBwEeM p=73` 虾皮 Go 后端开发面试 · 时长 6分03秒
**考察意图**："零拷贝"是个容易被说烂的词。面试官只想确认两点：**你知道它省的是哪几次拷贝**，
以及**你知道它并不真的是"零次"**。

### 一句话定义

零拷贝是一种**减少数据在内核态缓冲区与用户态缓冲区之间来回搬运**的 I/O 优化技术，
目标是把 CPU 从"纯粹搬数据"里解放出来，**把省下的算力和内存带宽还给业务逻辑**。

### 它解决的是什么问题

一次再普通不过的"把文件读出来发到网络"，传统实现是这样的：

```
        read(2)                          write(2)
磁盘 ──DMA──▶ 内核页缓存 ──CPU──▶ 用户缓冲区 ──CPU──▶ socket 缓冲区 ──DMA──▶ 网卡
```

| 开销 | 说明 |
|---|---|
| **CPU 拷贝 2 次** | 页缓存 → 用户缓冲区、用户缓冲区 → socket 缓冲区；都要 CPU 逐字节参与，**大文件传输能吃掉 30%+ 的 CPU 周期** |
| **系统调用 2 次** | `read` + `write`，每次都是一次 `用户态 → 内核态 → 用户态` 的上下文切换 |
| **内存带宽浪费** | 同一份数据在内存里搬了 4 次，page cache 副本还容易被反复换出换入 |
| **用户态纯属"过路"** | 应用既不改也不看数据（如文件下载），却硬要把它读进自己的地址空间 |

### 关键澄清：零拷贝 ≠ 零次拷贝

这是最容易被追问的一点：

> **"零拷贝"消除的是"不必要的用户态拷贝"，DMA 拷贝依然存在。**
> 数据从磁盘到网卡，物理上必经 page cache 和 socket 缓冲区；
> 哪怕 `MSG_ZEROCOPY`，数据也还得由网卡 DMA 读走。
> 更严谨的说法是 **"zero CPU copy"** —— **CPU 不再搬数据，只发指令**。

### 它不是为了"更快"，而是为了"同样的 CPU 做更多事"

- **收益巨大**：静态文件服务、对象存储下载 —— CPU 只发 `sendfile` 指令，吞吐受网卡/磁盘而非 CPU 限制；
- **收益明显**：反向代理 / TCP 转发、日志流式转发 —— 数据不落用户态，延迟与 CPU 双降；
- **收益几乎为零**：JSON 编解码、下单、风控 —— 瓶颈在业务逻辑，优化 I/O 等于没优化。

> **这就是"什么时候不需要零拷贝"的标准答案**：先 profile，确认瓶颈在数据搬运本身，再谈零拷贝。
> 在业务逻辑密集的服务里追零拷贝，是典型的过早优化。

### 面试官会追问什么

- **零拷贝是操作系统层面的还是语言层面的？** → **内核提供能力，语言负责暴露**。
  `sendfile` / `splice` / `mmap` / `MSG_ZEROCOPY` 都是 Linux 系统调用；
  Go 的价值在于**在 `io.Copy` 这类接口里替你做了自动分发**。
- **为什么说它天生适合"大文件 + 轻逻辑 + I/O 密集型"？** → 收益**正比于数据体积**、
  **反比于单位数据的业务处理量**。
- **一次拷贝到底算几"次"？** → **口径要说清**：算 DMA 是 4 次，只算 CPU 参与的是 2 次。
  先说"**传统 read+write 是 4 次拷贝、2 次系统调用、2 次 CPU 拷贝**"，再按面试官口径补充。

## Q2. 为什么传统 read + write 是"四次拷贝、两次系统调用"？

**来源**：`BV1xSRXBwEeM p=73` 虾皮 Go 后端开发面试 · 时长 6分03秒
**考察意图**：这是 Q3 所有方案的**基准线**。基准线画不出来，后面所有对比都是背的。

```go
buf := make([]byte, 32*1024)
for {
    n, err := f.Read(buf)   // ① 系统调用：磁盘 → 用户缓冲区
    if n > 0 {
        conn.Write(buf[:n]) // ② 系统调用：用户缓冲区 → socket 缓冲区
    }
    if err != nil {
        break
    }
}
```

| 序号 | 拷贝 | 参与者 | 说明 |
|---|---|---|---|
| **1** | 磁盘 → 内核页缓存（page cache） | **DMA** | 不占 CPU，但数据先进内核 |
| **2** | 内核页缓存 → 用户缓冲区 | **CPU** | `read()` 返回前必须完成 |
| **3** | 用户缓冲区 → socket 发送缓冲区 | **CPU** | `write()` 的核心开销 |
| **4** | socket 缓冲区 → 网卡 | **DMA** | 不占 CPU |

**系统调用 2 次**（`read`、`write`）；**上下文切换 4 次**（每次系统调用一进一出）；**CPU 拷贝 2 次**。

### 为什么会这样设计，以及优化方向

`read` / `write` 的**接口契约就是"数据必须经过用户态"**：应用拿到的是自己地址空间里的 `[]byte`，
内核不能假设"这个应用只是转发、不会改数据"。只要用这套 API，**拷贝就是接口语义的一部分，绕不开**。

既然根源是"数据非要经过用户态"，优化方向就两个：

1. **让用户态与内核态共享同一块内存** → `mmap` + `write`（少一次 CPU 拷贝，但用户态仍在链路里）；
2. **干脆让数据不经过用户态** → `sendfile` / `splice`（用户态只发指令，不碰数据）。

### 面试官会追问什么

- **DMA 拷贝为什么不占 CPU？** → DMA 控制器直接在内设与内存之间搬数据，CPU 只下发描述符；
  所以"拷贝次数"和"CPU 开销"不是一回事。
- **`read` 会触发磁盘 IO 吗？** → 不一定。**页缓存命中时是纯内存操作**，
  这也是冷读/热读性能差异巨大的原因（零拷贝的加速比在热读时更明显）。
- **小文件用零拷贝有意义吗？** → 收益很小。`sendfile` 省的开销**正比于数据量**，
  KB 级响应里系统调用的固定成本占比更高。

## Q3. 零拷贝有哪些实现路径？各自的代价是什么？

**来源**：`BV1xSRXBwEeM p=73` 虾皮 Go 后端开发面试 · 时长 6分03秒
**考察意图**：把"零拷贝"当成一个点的人会被这题筛掉，它能考出**你对 Linux I/O 栈的层次感**。

### 总览对比表

| 方案 | 经过用户态 | **CPU 拷贝** | **系统调用** | **上下文切换** | 典型限制 |
|---|---|---|---|---|---|
| `read` + `write`（基准） | 是 | **2 次** | 2 | 4 | — |
| `mmap` + `write` | 是（共享映射） | **1 次** | 2 | 4 | 文件被截断/变更可能触发 `SIGBUS` |
| **`sendfile`** | **否** | **1 次** | 1 | **2** | 只能"文件 fd → socket fd"，中间无法加工数据 |
| **`sendfile` + DMA gather** | 否 | **0 次** | 1 | 2 | 需要网卡支持 **SG-DMA**（scatter-gather） |
| **`splice`** | 否 | **0 次** | 2 | 2 | 两个 fd 中**至少一个是 pipe**；仅 Linux |
| **`MSG_ZEROCOPY`** | 否（发送时） | 0 次 | 1 + 完成通知 | 2 | Linux 4.14+；发送期间不得改动用户缓冲区 |

> 表里的拷贝次数只统计 **CPU 参与的数据拷贝**，这样对比才有区分度；加上 DMA 每种再多 1~2 次。

### ① `mmap` + `write`：让用户态与内核态共享页缓存

```
磁盘 ──DMA──▶ 内核页缓存 ══(共享映射)══ 用户地址空间 ──CPU──▶ socket 缓冲区 ──DMA──▶ 网卡
```

- **省掉"页缓存 → 用户缓冲区"那一次 CPU 拷贝**，因为用户态读的就是页缓存本身；
- 但数据仍要由 CPU 从用户可见内存搬进 socket 缓冲区，**所以不是真零拷贝**，上下文切换仍是 4 次；
- 副作用：**用户态写入会直接改页缓存**，映射期间文件被其他进程截断会收到 `SIGBUS`。

### ② `sendfile`：数据彻底不进用户态

```c
ssize_t sendfile(int out_fd, int in_fd, off_t *offset, size_t count);
// in_fd 必须是支持 mmap 的文件，out_fd 必须是 socket
```

- **用户态只发起一次系统调用、全程不接触数据**，上下文切换从 4 次降到 2 次；
- 代价是**数据对应用不可见**：不能加密、压缩、改内容、算摘要；
- 这就是"过 TLS 或 gzip 之后零拷贝必然失效"的原因——**数据必须回用户态加工**。

### ③ `sendfile` + DMA gather：真正意义上的零 CPU 拷贝

```
磁盘 ──DMA──▶ 内核页缓存 ──DMA(gather)──▶ 网卡
```

- 网卡支持 SG-DMA 后，内核**不再把数据搬进 socket 缓冲区**，
  只把**描述符**（内存地址 + 长度）写进去，**CPU 一次数据拷贝都不做**；
- 需要硬件支持（Linux 2.4+ 内核 + SG-DMA 网卡），是"零拷贝"一词最本源的实现；
- 仍然**只能用于文件 → socket**。

### ④ `splice`：用内核管道做"数据搬运中转站"

```c
splice(fd_in, NULL, pipefd[1], NULL, len, SPLICE_F_MOVE);   // 文件 → 管道
splice(pipefd[0], NULL, fd_out, NULL, len, SPLICE_F_MOVE);  // 管道 → socket
```

- 中间通过**内核 pipe buffer 传递的是页引用而非数据副本**，**不经过用户态**；
- 因此是 **socket → socket 转发**（反向代理、隧道）的首选；
- 代价：**两端 fd 至少有一个必须是 pipe**，所以需要两次 `splice` 配对；Linux 特有。

### ⑤ `MSG_ZEROCOPY`：发送时借用用户态缓冲区

- Linux 4.14+ 给 `sendmsg` 加了该标志：内核**不再把用户缓冲区内容拷进 socket 缓冲区**，
  而是把它"钉住"直接交给网卡 DMA；
- 拷贝降到 0，但省的是"**进内核**"这一步（数据本来就是用户态产生的，如序列化结果）；
- 内核通过 **socket 的 error queue** 异步回传"内存用完了"的通知，
  **应用在收到通知前不得改写/释放该缓冲区**——这是它最大的使用成本；
- 大块发送（几十 KB 以上）才划算，小包因通知开销反而更慢；
- **Go 标准库没有暴露它**，要用得走 `x/sys/unix` 手写 `sendmsg` + 收通知。

### 选型口诀

| 需求 | 选它 |
|---|---|
| 文件下载 / 静态资源 | `sendfile` + SG-DMA |
| 纯 TCP 转发、代理 | `splice` |
| 只读大文件、随机访问 | `mmap` |
| 应用自己生成的大块数据往外发 | `MSG_ZEROCOPY` |
| 要加密 / 压缩 / 计算摘要 | **老老实实走用户态**，零拷贝帮不了你 |

### 面试官会追问什么

- **`sendfile` 和 `splice` 怎么选？** → 一端是**文件**用 `sendfile`（一条系统调用，最简单）；
  一端是 **socket**（转发场景）用 `splice`。
- **为什么 `mmap` 不算真零拷贝？** → 它**仍保留一次 CPU 参与的数据搬运**
  （共享映射 → socket 缓冲区），只是砍掉了另一份用户态副本。
- **零拷贝的"不可用边界"？** → **只要数据需要被应用看到或改写**（加密、压缩、改内容、校验），
  就必须经过用户态，零拷贝立刻失效。

## Q4. Go 里哪些地方用到了零拷贝？

**来源**：`BV1xSRXBwEeM p=73` 虾皮 Go 后端开发面试 · 时长 6分03秒
**考察意图**：这是落地题。面试官想知道你写的 `io.Copy` 会不会走到内核快路径，
以及**你知道哪些写法会让它悄悄失效**。

### ① `io.Copy`：Go 的零拷贝自动分发器

`io.Copy` 看起来是"循环读写"，实际先做**能力探测**：

```go
// io.copyBuffer（简化）
if wt, ok := src.(io.WriterTo); ok {
    return wt.WriteTo(dst)          // 优先问源
}
if rt, ok := dst.(io.ReaderFrom); ok {
    return rt.ReadFrom(src)         // 再问目标
}
// 都不行 → 分配 32 KiB 缓冲区，纯用户态循环拷贝
```

关键路径 `io.Copy(conn, f)`（`conn` 是 `*net.TCPConn`，`f` 是 `*os.File`）：

```go
// net/tcpsock.go + net/splice_linux.go + net/sendfile_linux.go（简化）
func (c *TCPConn) readFrom(r io.Reader) (int64, error) {
    if n, err, handled := splice(c.fd, r); handled {   // ① 源也是 socket → splice(2)
        return n, err
    }
    if n, err, handled := sendFile(c.fd, r); handled { // ② 源是文件 → sendfile(2)
        return n, err
    }
    return genericReadFrom(c, r)                       // ③ 都不行 → 退回用户态拷贝
}
```

而 `sendFile` 的类型识别**只认两种情况**：

```go
lr, ok := r.(*io.LimitedReader)     // io.LimitReader / io.CopyN 包过的会被解开
if ok {
    remain, r = lr.N, lr.R
}
f, ok := r.(*os.File)               // 必须是 *os.File，否则 handled = false
```

**三条实战结论**：

| 写法 | 零拷贝? | 原因 |
|---|---|---|
| `io.Copy(conn, f)` | **是** | `*os.File` 被识别 → `sendfile(2)` |
| `io.Copy(conn, io.LimitReader(f, n))` | **是** | `*io.LimitedReader` 被特判解开 |
| `io.Copy(conn, io.TeeReader(f, hasher))` | 否 | 类型不匹配；且本来就要读数据 |
| `io.Copy(conn, countingReader{f})` | **否** | **任何自定义包装器都会打断快路径** |

> **最容易踩的坑**：一个"只做埋点计数"的 `io.Reader` 包装器，
> 就能把几千次 `sendfile` 变成十几万次 `read`+`write`，CPU 翻倍、吞吐腰斩。
> **凡是可能包住 `*os.File` 的中间件，都应该实现 `WriteTo`/`ReadFrom` 透传下去。**
> 线上验证：`strace -c -e trace=read,write,sendfile,splice ./server`，
> 看 `sendfile` 计数是否上去了、`read`/`write` 是否贴近 0。

### ② 文件 → 文件：`copy_file_range`

两端都是常规文件时不需要走网络，Linux 4.5+ 提供 `copy_file_range(2)`：

```go
io.Copy(dstFile, srcFile)   // 两个都是 *os.File
```

`(*os.File).ReadFrom`（Go 1.15+）与 `(*os.File).WriteTo`（Go 1.22+）
会在 Linux 上尝试内核快路径（`copy_file_range` / `sendfile`），
**全程在内核页缓存之间搬运、不产生用户态副本**，失败自动退化为带缓冲的循环拷贝。
适用场景：**大文件归档、日志滚动、对象存储落盘**。

### ③ `net/http`：静态文件服务天然零拷贝

`http.FileServer` / `http.ServeFile` 的调用链是：

```
serveFile → serveContent → io.CopyN(w, content, size) → (*http.response).ReadFrom → sendFile → sendfile(2)
```

也就是说，**只要把 `*os.File` 交给 `http.ResponseWriter`，Go 就会自动启用 `sendfile`**。
但它的快路径同样脆弱，**以下情况会静默退化**：

| 破坏因素 | 原因 |
|---|---|
| 中间件包装了 `http.ResponseWriter` | 类型断言失败，拿不到底层 `ReadFrom` |
| 启用了 gzip 压缩 | 数据必须回用户态压缩 |
| 走 TLS（未开 kTLS） | 数据必须回用户态加密 |
| 自己 `make([]byte, 32*1024)` 循环读写 | 绕过了 `io.Copy` 的分发 |

```go
// ❌ 自己造缓冲区循环 → 强制用户态拷贝，性能还不如标准库
buf := make([]byte, 32*1024)
for {
    n, err := f.Read(buf)
    if n > 0 { w.Write(buf[:n]) }
    if err != nil { return }
}

// ✅ 一行交给标准库走 sendfile，还顺带处理好 Range / If-Modified-Since
http.ServeFile(w, r, "big.zip")
```

> 顺带一个高频面试点：**反向代理别自己写 buffer 转发**。
> `io.Copy(dst, src)` 在两端都是 `*net.TCPConn` 时会走 `splice`；
> 自己写 `for { src.Read(buf); dst.Write(buf) }` 则是**纯用户态搬运**。

### ④ `syscall.Sendfile`：需要精确控制时的手工通道

```go
// outFd 目标 socket，inFd 源文件，offset 传 nil 表示从当前偏移继续，count 传 0 表示发到 EOF
n, err := syscall.Sendfile(int(connFD), int(fileFD), nil, 0)
```

什么时候需要它：标准库自动分发**够不到**的场景（响应体被自定义 Reader 包装、
只想发文件的一部分）、要**显式控制 offset/count**（Range 分段下载、断点续传）、
或需要**确定性而非依赖类型断言的隐式行为**。代价也直接：**Linux 独占**、
fd 生命周期要自己管、`EAGAIN` 要配合非阻塞 fd 自行处理，
通常用 `golang.org/x/sys/unix` 版本更稳。

### ⑤ `unsafe` 类型双关：语言层面的"零拷贝"

视频里演示了一类**不依赖系统调用**的零拷贝——`string` 与 `[]byte` 之间不复制数据。
Go 的 `string` 与 `[]byte` 底层都是 `{数据指针, 长度}`，**只是类型标记不同**：

```go
func stringToBytes(s string) []byte {
    return *(*[]byte)(unsafe.Pointer(&s))   // 改写类型标签，不复制数据
}

// 现代 Go 更推荐正规 API（Go 1.20+）
func stringToBytes2(s string) []byte { return unsafe.Slice(unsafe.StringData(s), len(s)) }
func bytesToString(b []byte) string  { return unsafe.String(unsafe.SliceData(b), len(b)) }
```

**代价与红线**：类型必须**底层布局兼容**（如 `string` ↔ `[]byte`），转成结构体等其他类型就是未定义行为；
转出来的 `[]byte` **绝对不能 append 或修改**（`cap` 无效、底层 string 常在只读段）；
绕过类型系统的指针若被错误持有，会让 GC 误判存活对象；且 `unsafe` 不受兼容性承诺保护，
**升级 Go 版本要重新验证**。

同类的语言层零拷贝还有：**切片共享底层数组**（`s[2:5]` 不复制）、
**`strings.NewReader(s)`**（直接持有原字符串，只读、不复制）。
注意 **`bytes.NewBufferString(s)` 是会复制的**——两者在"是否零拷贝"上并不等价。

### 面试官会追问什么

- **`io.Copy` 永远零拷贝吗？** → **不是**。只有"目标实现 `ReadFrom` 或源实现 `WriteTo`"
  且**类型精确匹配**（`*os.File`、`*net.TCPConn`、`*io.LimitedReader`）时才走快路径。
- **`io.CopyBuffer` 能提升性能吗？** → 它和 `Copy` 一样**先做能力探测**，
  只有真的退化时才用你给的缓冲区——作用是**复用缓冲区、省掉每次 32 KiB 的分配**，
  并不会关闭内核快路径（真零拷贝时那个缓冲区根本用不上）。
- **`sendfile` 支持下游是 TLS 吗？** → 标准 Go 不支持。加密必须在用户态完成，
  除非启用内核 kTLS，那不是 Go 的默认行为。

## Q5. 面试答题模板

**来源**：`BV1xSRXBwEeM p=73` 虾皮 Go 后端开发面试 · 时长 6分03秒
**考察意图**：这题几乎必考"你复述一遍"，**有结构的 90 秒回答胜过零散的两分钟**。

```
① 定义与目的（20s）：零拷贝 = 减少内核态/用户态之间不必要的 CPU 拷贝；
   本质是 zero CPU copy，DMA 拷贝依然存在。

② 基准线（20s）：传统 read+write = 4 次拷贝（2 DMA + 2 CPU）、2 次系统调用、4 次上下文切换；
   根源是接口语义强制数据经过用户态。

③ 实现路径（30s，挑 3 个）：mmap+write 砍一次 CPU 拷贝、但用户态仍在链路里；
   sendfile 数据不进用户态、1 次系统调用，+SG-DMA 后 CPU 拷贝降为 0；
   splice 用于 socket→socket 转发，两端至少一端是 pipe。
   共性代价：数据对应用不可见 —— 要加密/压缩/校验就必须回用户态。

④ 落到 Go（20s）：io.Copy 自动分发（dst 实现 ReaderFrom / src 实现 WriterTo）；
   io.Copy(tcpConn, file) → sendfile，双 socket → splice；http.ServeFile 天然零拷贝；
   任何自定义 io.Reader 包装器都会静默打断快路径 —— 线上最常见的退化原因。
```

### 一句话收尾（加分项）

> "零拷贝的前提是**瓶颈确实在数据搬运**。如果 profile 显示热点在 JSON 编解码或 RPC 上，
> 那把系统调用从 2 次压到 1 次，业务也不会快一毫秒。"

### 面试官会追问什么

- **`io.Copy` / `io.CopyBuffer` / `io.CopyN` 的区别？** →
  `Copy` 走能力探测；`CopyN` 内部是 `Copy(dst, LimitReader(src, n))`，
  **`*io.LimitedReader` 会被 `sendfile` 路径特判解开，所以 `CopyN` 仍是零拷贝**；
  `CopyBuffer` 只在退化路径上使用你给的缓冲区。
- **零拷贝能解决"磁盘到磁盘"的拷贝吗？** → 能。`copy_file_range(2)` 让两次文件 IO
  在同一内核路径完成，`(*os.File).ReadFrom` 走的就是这条路。
- **`splice` 为什么要求一端是 pipe？** → pipe 是内核里**存放"页引用"的容器**，
  数据以页为单位在各环节之间**传递所有权**；没有 pipe 作中转，
  就无法在两个任意 fd 之间保证"不落地到用户态"。
