## 一、Go 的内存逃逸是什么？什么情况会逃逸？

**来源**：`p=42` 深信服 Go 面试 · 时长 13分20秒
**考察意图**：五个递进问题——**是什么 / 为什么要逃逸 / 怎么分析 / 哪些情况逃逸 / 为什么要避免**。

### 一、什么是逃逸

> **逃逸 = 编译器编译代码时，把「原本应该分配在栈上」的变量，分配到了「堆」上。**

### 二、为什么要逃逸

> **因为函数结束了，但这个变量还在被使用**——
> 如果不逃逸（还在栈上被回收掉），**其他地方引用它的代码就会出错**。

**与 C/C++ 的对比（很好的加分点）**：

| | C/C++ | Go |
|---|---|---|
| 谁负责分析 | **开发者自己分析**（用了局部变量就得自己声明成全局之类） | **编译器自动分析并处理** |
| 效果 | 手动管理，容易出错 | **自动"纠错"**——发现变量被别处引用就自动逃逸到堆 |

### 三、怎么分析逃逸

```bash
go build -gcflags="-m" main.go
```

> **加 `-gcflags="-m"` 就能看到编译器的逃逸分析结果**——
> 哪些变量"moved to heap"一目了然。

### 四、哪些情况会逃逸

**可以归纳为两大类**：

```text
① 生命周期超出了函数的生命周期
② 变量的「不确定性」——大小不确定 或 类型不确定
```

**五种具体场景**：

| # | 场景 | 属于哪一类 |
|---|---|---|
| **①** | **返回指针 / 切片 / map** | 指针类型返回后**地址何时还被使用未知**；<br>切片和 map **底层都含数组指针**，同样是"超出函数生命周期"；<br>而且它们的**大小是不确定的**（可动态扩容）→ **同时命中两类** |
| **②** | **向 channel 发送指针**（或含指针的类型） | 返回的地址**不知何时被引用** |
| **③** | **闭包**（非直接的函数调用） | 如 `i` 在 `f3` 内未被引用，却在 `f3` **返回的函数**里被引用 →<br>**生命周期超出 `f3`** |
| **④** | **切片 / map 中存储指针** | 虽然没返回，但**其他函数或协程可能引用其中元素** →<br>元素可能超出本函数生命周期 |
| **⑤** | **动态类型（interface 多态）** | 见下方对比 |

**⑤ 的动态类型两种情况（实测对比）**：

```go
// 情况 A：没有逃逸 —— 声明时就确定了是具体类型（如 animal）
var a animal = dog{}     // 类型明确

// 情况 B：逃逸 —— 先声明接口类型，再赋值，类型不确定
var a Animal             // 此时 a 到底是什么类型"不知道"
a = dog{}                // → 动态类型问题 → 逃逸
```

### 五、实测结果（`-gcflags="-m"` 的输出）

| 函数 | 结果 |
|---|---|
| `f1` | `i`、**slice、map 全部逃逸**到堆 |
| `f2` | `i` 逃逸 |
| `f3` | **函数逃逸**；参数没逃逸（传的是**副本**），但 `i` 逃逸 |
| `f4` | **传入的指针 `i` 逃逸，而切片本身没逃逸** |
| 多态 | 情况 A（具体类型）**没逃逸**；情况 B（动态类型）**逃逸** |

### 六、为什么要避免逃逸（注意用词）

> ⚠️ **是"避免"而不是"杜绝"**——
> **有些场景必须逃逸**：比如用 **interface 解决多态**，
> 几乎是 **100% 逃逸**的，这种就没法避免，**要合理利用**。

**避免的核心原因是性能**：

| 分配位置 | 回收方式 | 效率 |
|---|---|---|
| **栈上** | **函数执行完立即回收**（类似"实时回收"） | **高** |
| **堆上** | 依赖 **GC 周期性回收** | 较低，且**可能回收不及时** |

> **大量逃逸 → 内存回收全部压在 GC 上** → 而 GC 是**周期性触发**的 →
> **内存占用会在一段时间内堆积**。所以减少不必要的逃逸能直接改善应用性能。

### 面试答题结构

```text
① 定义：本该在栈上的变量被分配到堆上
② 原因：函数结束但变量还在被引用
③ 分析工具：go build -gcflags="-m"
④ 五种场景：返回指针类 / channel 传指针 / 闭包 / 容器存指针 / 动态类型
   （归纳为「生命周期超出」+「大小或类型不确定」）
⑤ ★ 避免而非杜绝：核心是性能（栈是即时回收，堆要等 GC 周期）
```

## 二、逃逸分析的判定规则是什么？它有什么优点和代价？

**来源**：`BV12qjA6aErF p=2` B站 Go 面试真题 · 时长 9分00秒
**考察意图**：第一节讲"什么是逃逸、哪些场景逃逸"，这一题**再往前推一层**——
问编译器是**按什么规则**下这个结论的，以及**"全自动内存管理"的代价是什么**。

### 一、先纠正一个说法

> **是"逃逸分析"（escape analysis），不是"内存溢出"（out of memory）。**

它的定义是：**编译器在编译期做静态分析，判断一个变量该分配到栈上还是堆上。**

**默认假设是"变量本该在栈上"**——
逃逸分析真正做的事，是**找出"哪些变量没办法，只能上堆"**。

### 二、三条判定规则

| # | 规则 | 具体表现 |
|---|---|---|
| **① 是否被函数外部引用** | 变量的**生命周期会超出当前函数** | 返回指针、地址被存进全局变量、被闭包或其他协程捕获 |
| **② 是不是太大（栈放不下）** | **栈空间不够**时只能上堆 | 局部定义大数组 / 大 struct，超过栈的可用空间 |
| **③ 编译期能否确定大小或类型** | **编译时确定不下来** | 通过接口（多态）赋值——具体类型和大小要到运行时才知道 |

> 第 ① 条的细节：局部变量理论上函数结束即回收，
> 但**一旦把地址返回出去，外部函数就可能引用这个地址**，
> 提前回收就会出问题 → **必须逃逸**。

### 三、两条"内存分配基本原则"（这才是底层约束）

```text
原则 1：指向栈上对象的指针，不能被存到堆中 → 对象和指向它的指针必须在"同一侧"
原则 2：指向栈上对象的指针，生命周期不能超过该栈对象本身 → 指针活得更久，就一起搬到堆上
```

> 这两条其实就是**逃逸分析存在的理由**：栈是"函数返回就被整体回收"的，
> 一旦有指针逃出去引用它，回收后就会变成**悬空指针**。
> 编译器宁可让变量上堆，也不能让程序崩。

### 四、`-gcflags="-m"` 的输出怎么读

```bash
go build -gcflags="-m" main.go      # 一级信息
go build -gcflags="-m -m" main.go   # 二级：连"为什么"一起打印
```

输出里只看三类关键词：`escapes to heap`（逃逸了）、`moved to heap`（被搬到堆上）、
`does not escape`（**没逃逸，留在栈上，这是好事**）。

> **读法**：直接搜 `escape`，凡带 `escapes to heap` / `moved to heap` 的就是逃逸点。
> 加 `-m -m` 还能看到**原因**——`moved to heap: x` 后面会跟上是哪一行逼它上堆。
>
> ⚠️ 它是**编译期**工具，必须配合 `go build` / `go run` 使用，**不是运行时工具**。

### 五、⭐ 优点与代价（"避免而非杜绝"的完整理由）

> 先记住**两极都不能走**：**全放栈 → 提前回收 → 空指针 / 程序崩溃；
> 全放堆 → GC 压力骤增 → 性能大幅下降。**
> 逃逸分析要做的，就是在两者之间**找出正确的分配点**。
> （栈 vs 堆的回收代价对比见第一节第六节。）

**优点**：

| 优点 | 说明 |
|---|---|
| **自动内存管理** | 开发者**不用手动决定**内存分配位置，编译器代劳 |
| **简化编程** | 可以**随手返回指针、随手用闭包**——编译器会把该上堆的变量自动挪上堆，<br>**不会因为悬空指针导致程序随便崩溃** |

**代价**：

| 代价 | 说明 |
|---|---|
| **编译期开销** | 每次编译都要跑这一套静态分析 |
| **完全依赖编译器** | 分配位置**不由你决定**，取决于编译器"答得对不对"；<br>编译器版本或优化力度一变，逃逸结论可能就变 |
| **潜在的性能问题** | 如果**编程模式本身**就决定了大量对象只能上堆<br>（到处返回大对象的指针、接口满天飞），<br>**GC 压力反而被放大，性能不升反降** |

> **结论**：逃逸分析让"写法"变自由了，但**自由是有代价的**——
> 代价最终落在 **GC** 上。
> 所以结论还是第一节那句话：**能规避的规避（预分配、少返回指针、慎用不必要的接口），
> 该用的（多态、闭包）合理用——"避免"而不是"杜绝"。**

### 面试官会追问什么

- **逃逸一定变慢吗？** → **不一定**。逃逸本身只是一次堆分配，
  真正贵的是**随之而来的 GC 扫描与回收压力**；小对象偶尔上个堆，影响可以忽略。
- **为什么 `interface` 几乎必然逃逸？** → 接口值内部是 `(类型, 数据指针)`，
  具体类型和大小**编译期定不下来**，命中第 ③ 条规则。
- **"栈空间不够"和"goroutine 栈扩容"是一回事吗？** → **不是**。
  前者是**编译期**判定"这个变量放不进栈"→ 上堆（逃逸）；
  后者是**运行时**按需扩缩 goroutine 栈（2KB 起步、最大 1GB），两者别混。
- **怎么证明自己改的代码真的减少了逃逸？** → 改前改后**各跑一次 `-gcflags="-m"` 对比**；
  更硬的办法是跑 benchmark 看 **`allocs/op`**（每次操作的分配次数/字节数）是否下降。
