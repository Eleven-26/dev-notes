# Go 程序启动流程

> 从汇编入口 `_rt0_amd64` 走到 `main.main`：命令行参数与 auxv 的获取、栈初始化、内存分配器初始化、调度器初始化、运行时检查、操作系统信息初始化，以及 main goroutine 的创建与调度启动。
>
> 内容整理自大厂 Go 后端面试真题视频，参考资料与原始素材见 [素材清单](../../素材清单.md)。

## 一、Go 程序启动流程是怎样的？

**来源**：`BV12qjA6aErF p=21` B站 Go 面试真题 · 时长 12分38秒
**考察意图**：考你**知不知道真正的程序入口在哪**——很多人张口就是"`main` 函数"，而面试官想确认的是：你是否清楚在 `main` 之前，运行时已经用汇编和 Go 代码把 G/M/P、TLS、CGO、兼容性、调度器全部铺好了。这是一道典型的"底层意识"题。

### 一、真正的入口：`_rt0_amd64`

我们平常说的"程序入口是 `main` 函数"，**只对"我们写的业务代码"成立**——业务代码确实从 `main` 开始执行，但**整个程序的入口并不是它**。在 `runtime` 包里按文件名定位（`asm_amd64.s`），可以看到：

```text
_rt0_amd64              // 汇编层面的真正入口，位于 asm_amd64.s
   └── runtime·rt0_go   // 同一文件内，约 200 多行，一直到 370 行左右
```

`_rt0_amd64` 是**平台相关的通用入口**（不同架构有各自的 `_rt0_386`、`_rt0_arm64` 等）；它会调用 `runtime·rt0_go`，**这个函数才是启动流程的主干**。搜索技巧是在仓库里"按文件名查找"，会找到不止一处。

### 二、`runtime·rt0_go` 的前半程（汇编阶段）

| 步骤 | 做的事 |
|---|---|
| **① 栈与参数准备** | 调整栈空间并做对齐，**规范化地传递命令行参数**（把 argc/argv 入栈），这是整个函数的第一部分 |
| **② 初始化 g0** | 初始化 Go 运行时中**第一个特殊的 goroutine（g0）**的结构 |
| **③ 检测 CPU 型号** | 探测 CPU 厂商/型号信息（如是否 Intel），保存版本信息 |
| **④ 检测并初始化 CGO** | 整理 CGO 参数、真正执行初始化，并按操作系统做特定处理 |
| **⑤ 更新栈保护** | **CGO 会影响栈的布局**，所以初始化完 CGO 后必须重新调整 g 栈的保护机制（guard） |
| **⑥ 线程本地存储 TLS** | 初始化 TLS；非 Windows 直接跳转到 `ok` 继续；Windows 走 `runtime·wintls` 这条差异较大的专门路径 |
| **⑦ 绑定 m0 的 TLS 区域** | 把 TLS 绑定到 **m0**——m0 是启动时创建的第一个线程，是**整个程序初始化的执行载体**；程序总要交给某个 CPU 去跑，那就是 m0 |
| **⑧ 验证 TLS** | 校验 TLS 功能是否可用，随后**初始化 TLS 中当前 goroutine 的指针** |
| **⑨ g0 与 m0 双向绑定** | `m0` ↔ `g0` 建立一对一绑定 |
| **⑩ 兼容性校验** | 做硬件与操作系统的兼容性校验；不兼容则跳转到 `bad CPU` 分支做报错处理 |

### 三、GMP 概念（讲解 g0 时顺带给出）

**G = goroutine（协程）、M = 内核线程、P = 逻辑处理器**。关键在于 **g0 的用途与用户协程完全不同**：

- **g0 的栈属于"工作协程"之外的特殊栈**，主要负责**运行时调度逻辑**：比如当前 M 上的 goroutine 执行完毕、或因某些原因要切换下一个协程，**这个切换动作是 g0 去完成的**——所以 g0 类似"系统级别的线程"，**不是用户线程**；
- 再比如**垃圾回收的标记、清扫**，也都属于 g0 的操作范畴，不是用户协程去做的；**每一个 M 都会对应一个特殊的 g0（一对一绑定）**，而 **m0** 则是**启动这个应用程序的那个线程**。

### 四、后半程：进入 Go 代码的五个阶段

| 序号 | 阶段 | 说明 |
|---|---|---|
| **①** | **基础校验** | 验证程序启动前的关键状态（即 `runtime.check`，见第六节） |
| **②** | **解析命令行参数** | 提取命令行参数与 auxv 等关键信息（见第二节） |
| **③** | **初始化操作系统信息** | 获取 CPU 数量、透明大页大小、CGO 退出信号等（见第七节） |
| **④** | **初始化调度器** | 初始化核心锁、模块数据、算法、P 的数量与状态等（见第五节） |
| **⑤** | **创建应用程序启动入口** | **这个启动入口就是我们的 `main` 函数** |

第 ⑤ 步在源码里对应 `newproc`：**创建一个 goroutine 去执行 `main` 函数**，然后**启动调度器，让 m0 开始执行这个 goroutine**（`mstart`）。最后还有一处 `bad CPU`——**硬件不兼容的错误处理**兜底。

> **一句话收口**：`main` 是我们业务代码的起点，`_rt0_amd64` / `runtime·rt0_go` 才是整个程序的起点；程序启动就是"**把 G/M/P、TLS、CGO、栈、调度器全部准备好，再 newproc 出一个 goroutine 去跑 main**"。

### 面试官会追问什么

- **"`main` 之前运行时到底准备了什么？"** → 按第一节~第七节讲：g0/m0 与 TLS → auxv → 栈 → 内存分配器 → 调度器 → 运行时检查 → 操作系统信息。
- **"g0 和普通 goroutine 有什么区别？"** → g0 的栈是运行时的调度/GC 专用栈，每个 M 一对一绑定一个 g0，协程切换与 GC 标记清扫都跑在 g0 上。
- **"m0 是什么？"** → 启动应用程序的第一个内核线程，是初始化的执行载体；它同样一对一绑定一个 g0。
- **"为什么 CGO 初始化之后要重新调整栈？不同架构入口一样吗？"** → CGO 会影响栈的布局，所以要重新设置 g 栈的保护机制；入口不一样，`_rt0_386`/`_rt0_amd64`/`_rt0_arm64` 各自独立，`runtime·rt0_go` 才是共同的逻辑主干。

## 二、启动过程中除了获取命令行参数，还获取了哪些关键信息？

**来源**：`BV12qjA6aErF p=33` B站 Go 面试真题 · 时长 16分12秒
**考察意图**：考你对 **auxv（辅助向量）** 的认知深度。多数人只知道"启动时拿到了 argc/argv"，面试官问的是**"只有这些吗"**——真正想听的是 `AT_RANDOM`、`AT_PAGESZ`、`AT_SECURE`、`AT_HWCAP`、`AT_SYSINFO_EHDR(VDSO)` 这几个标签，以及**拿不到 auxv 时的兜底路径**。

### 一、入口函数：`runtime.args`

按文件名查找 `runtime1.go`，可以看到这个函数（视频里读作 "Runtime Ax / Runtime Args"）：**第一步**从命令行提取命令行参数**写入栈**，随后把 **c（参数个数）** 和 **v（参数列表）** 两个参数**复制到全局变量** `argc` / `argv`；**第二步**调用 `sysargs`，去解析更丰富的**内核信息**。

```go
func args(c int32, v **byte) {
    argc = c     // 参数个数 → 全局变量
    argv = v     // 参数列表 → 全局变量
    sysargs(c, v)
}
```

> 对照：用户代码里用到的 `os.Args`，正是由 runtime 启动阶段落库的 `argc` / `argv` 派生而来。

### 二、`sysargs` 为什么要分平台

`sysargs` 在源码里看起来"只是个摆设"——它本身是个**占位方法**（业务代码里调用不到它），但**它不是空方法**：Go 是跨平台语言，同一个方法在不同平台有不同实现，**编译时会按编译目标平台选用不同实现**。仍用"按文件名查找"，能找到 Linux、Windows、darwin 等各平台各自的版本；以 Linux 为例看它在做什么。

### 三、内核到底往进程栈上放了什么

内核在应用程序启动时，会**按固定顺序**向进程栈上传递数据：

```text
[ argc ][ argv[0] ... argv[argc-1] ][ NULL ]   ← 参数列表
[ envp[0] ... envp[n-1] ][ NULL ]             ← 环境变量列表
[ auxv[0] ][ auxv[1] ] ... [ AT_NULL ]        ← 辅助向量列表
```

argv 与环境变量列表**各自以一个 NULL 结尾**，两者之间还有一个 NULL 作为分隔；三段数据**连续排布**，所以只要**跳过 argv、再跳过 envp**，就能直接落到 auxv 的起始地址。`sysargs` 的指针游走逻辑：

| 动作 | 说明 |
|---|---|
| `argv + argc + 1` | argv 的最大索引是 `argc - 1`，再加上末尾 NULL，`+1` 后就指向**环境变量列表的头部** |
| `while *v != nil { v++ }` | 一路自增，跳过整个 envp，直到遇到 NULL |
| `v++` | 再**跳过一个 NULL 分隔符** |
| 得到 auxv 地址 | 此时位置就落在**辅助向量列表的起始地址**上 |

**辅助向量（auxv）** 就是内核传递给程序的额外系统信息，比如程序入口地址、CPU 类型、页大小、系统调用/信号相关元信息等；它是一个 **tag + value 的键值对结构**，以 `AT_NULL` 结尾。

### 四、auxv 里必须关注的五个标签

解析 auxv 时，**先取 Go 程序最核心、必须拿到（必查）的三个标签**：

| Tag | 含义 | 用途 |
|---|---|---|
| **`AT_RANDOM`** | 内核启动的**随机种子** | 作为运行时随机数的基础（`startupRandomData`） |
| **`AT_PAGESZ`** | **系统物理页大小** | 直接决定 `physPageSize` |
| **`AT_SECURE`** | **进程安全模式**标志 | 判断是否处于 secure-execution（如 setuid）场景 |

除此之外还有两个"有则更好"的标签：

| Tag | 含义 | 用途 |
|---|---|---|
| **`AT_HWCAP`** | **CPU 硬件能力标志** | 为后续**加速相关的优化**提供依据：CPU 打了哪些能力标签，运行时据此选择怎样的优化实现 |
| **`AT_SYSINFO_EHDR`** | **VDSO** | 为 Go 程序提供**高效的系统调用能力**，同时加载调试信息、有助于调试 |

> 视频里画流程图时把 `AT_HWCAP` 和 `VDSO` 的顺序画反了，两者都通过"按文件名查找"在各平台实现中定位。

### 五、拿不到 auxv 怎么办：两级兜底

解析完成后判断 `auxv` 是否 **不等于 0**。不等于 0 说明**确实从内核传参里拿到了辅助向量**；但也**有可能拿不到**，于是有两条兜底路径。**兜底一是读 `/proc/self/auxv`**（进程启动之后，`/proc/self/` 下确实会有这个文件，里面记录了辅助向量相关内容）：

```text
auxv == 0 → open("/proc/self/auxv") → 得到 fd
   ├── fd < 0 → 文件（路径）不存在 → 走兜底二
   └── fd > 0 → 确实存在 → 读取文件内容
          ├── 没读到 → 直接返回
          └── 读到   → 用同一套逻辑解析 auxv → 返回
```

**兜底二是 `mmap` 探测物理页大小**——如果栈上没有、proc 文件也没有，就只能**靠分配内存来探测物理页大小**：

```text
① size := 256 << 10                  // 申请 256KB
② p := mmap(nil, size, ...)           // p 已按物理页大小对齐，即一定是页大小的整数倍
③ n := 4096                           // 默认 4KB（4 << 10）
④ for n <= size:
     判断「p + n」之后剩余的空间是否仍是物理页大小的整数倍
       ├── 不是整数倍 → 报错（这个 n 不是页大小）
       └── 是整数倍   → 说明 n 就是物理页大小，跳出循环
     不满足则 n <<= 1（每次翻倍：4096 → 8192 → 16384 ...）
⑤ 整个循环都没能得到有效页大小 → 兜底把 physPageSize 设为 256KB
⑥ munmap(p, size)                     // 释放探测用的空间
```

核心套路是**"地址 + N 之后是否仍对齐"**：`mmap` 返回的地址天然是页对齐的，所以从 4KB 起不断翻倍测试，**第一个让偏移后依然满足页对齐的 n，就是物理页大小**；最后兜底设成 **256KB**：虽然**可能浪费一些内存**，但**至少保证应用程序能正常启动**；探测完成后**释放这块 mmap 空间**。

### 面试官会追问什么

- **"`AT_RANDOM` 是干什么的？"** → 内核给的随机种子，运行时的随机数从这里起头，避免早期随机性不足。
- **"为什么要从内核拿页大小，而不是写死 4KB？"** → 页大小是内核/架构相关的（4KB、16KB、64KB 都存在），写死会算错内存管理的基本单位。
- **"auxv 拿不到会怎样？"** → 先读 `/proc/self/auxv`，再不行用 `mmap` 对齐探测反推页大小，最后兜底 256KB。
- **"`sysargs` 是个空方法还能工作？auxv 的终止标志是什么？"** → 它是占位声明，编译期按目标平台选择具体实现（汇编或平台专属 Go 文件）；auxv 以 `AT_NULL` 结尾。

## 三、启动流程中栈初始化（`stackinit`）干了什么？

**来源**：`BV12qjA6aErF p=35` B站 Go 面试真题 · 时长 16分10秒
**考察意图**：考**栈缓存的两级结构**（`stackpool` / `stackLarge`）和**为什么要有它**——本质是"栈分配也要避免直接和操作系统交互"。追问点几乎必然落在 `_NumStackOrders` 怎么算、为什么按 64 字节对齐、大栈 `free` 数组为什么是 35 个元素。

### 一、`stackinit` 表面很简单

在 `schedinit` 一路找到 `stackinit`，代码只是把一批双向链表的 `first` / `last` 置空：

```go
stackpoolinit(&stackpool)        // 双向链表 first/last 置 nil
stackpoolinit(&stackLarge.free)  // 大栈 free 数组每个元素也置空
```

看起来什么都没做，但真正需要理解的是里面出现的 `stackpool`、`stackLarge`、`_NumStackOrders`（以及 `stackCacheSize`）。

### 二、两个池：小栈缓存与大栈缓存

| 结构 | 名称 | 作用 |
|---|---|---|
| **`stackpool`** | **小栈全（局）缓存** | 按**栈等级分组的数组**，每个元素对应一个栈等级缓存的链表 |
| **`stackLarge`** | **大栈缓存** | 缓存超过阈值的栈段 |

> 设计目的：**小栈缓存配合 P 的本地缓存，实现小栈的共享与复用，同时通过"缓存对齐"避免伪共享（false sharing）。**

### 三、`_NumStackOrders`：让最大缓存栈容量统一为 16KB

不同操作系统的**固定栈大小不一样**，`_NumStackOrders` 就是**按操作系统算出来的等级数量**，目标是：**不论底层固定栈大小是多少，都要保证"栈缓存能覆盖的最大栈容量"统一为 16KB。** 推导过程（栈等级 = 固定栈 × 2^i，i 从 0 开始）：

| 固定栈大小 | 等级数 `_NumStackOrders` | 各等级 |
|---|---|---|
| **2KB** | **4**（i = 0..3） | 2K、4K、8K、**16K** |
| **4KB**（如 Windows 32 位） | **3**（i = 0..2） | 4K、8K、**16K** |
| **8KB**（如 Windows 64 位） | **2**（i = 0..1） | 8K、**16K** |

三种情况下最大等级都正好是 16KB——这就是"用等级数量去保证统一"的含义。

### 四、`stackpoolItem` 为什么按 64 字节对齐

每个 `stackpoolItem` 会换成对应大小的栈块，但它的结构体大小**不可能刚好是 64 的整数倍**，所以要**按 64 对齐**：

```text
size % 64 = 16   →  补 64 - 16 = 48   →  对齐后再 % 64 仍为 48（无害）
size % 64 = 0    →  64 - 0 = 64      →  必须再 % 64 一次，得到 0
```

**为什么是 64？** 因为**主流 CPU 的缓存行（cache line）大小就是 64 字节**；CPU 的一级/二级/三级高速缓存**不是按字节往外写，而是以缓存行为最小操作单元**，所以内存对齐也按 64 来。**第二次取模是为了处理"大小恰好是 64 的整数倍"的特殊情况**：如果不再取模一次，就会**白白多消耗一个缓存行**的空间。

### 五、`stackCacheSize`：每个 P 每个等级的缓存上限

`stackCacheSize` 是**栈缓存大小的限制**：定义处对页大小做了**校验/取整**（与最大页大小相关），**如果不是页大小的整数倍就直接抛异常**；它的值是 **`32 << 10` = 32KB**。但它**不是**说 `stackpool` 总共只有 32KB，含义是：**每一个 P 的、每一个栈等级的栈段缓存上限为 32KB**。

```text
单个 P 的栈缓存总量上限 = stackCacheSize × _NumStackOrders
                        = 32KB × 4（64 位平台 4 个等级）
                        = 128KB
```

**为什么要做这个限制？** 因为**不允许无限缓存**——否则会过度消耗内存。缓存是为了快，但必须有界。

### 六、`stackLarge`：大栈缓存

`stackpool` 管的是**小于等于 16KB 的小栈**；遇到 **16KB 都装不下的栈**，就要走**大栈缓存 `stackLarge`**：**分配**时先去大栈缓存里找，有就直接拿；**用完/缩容**之后，再**归还到大栈缓存**里。其 `free` 数组的索引设计：

| 常量 | 值 | 说明 |
|---|---|---|
| `heapAddrBits` | **48** | 堆地址位数：64 位平台**并非真的 64 位有效**，Go 结合硬件与操作系统把有效长度定为 48 位（多数平台如此，个别平台还不到 48） |
| `pageShift` | **13** | 64 位平台页大小为 **8KB = 2¹³** |
| `len(free)` | **48 - 13 = 35** | 数组下标 **0 ~ 34**，第 i 个链表缓存 **2^i 个页**的栈 |

**不存在"3 个页"的链表**：这类缓存的页数**必须是 2 的幂次**；所以如果实际需要 3 个页，**因为对齐的关系不会拆成 3 个页，而是归到 4 个页**，走索引 2 的链表。

### 七、共同目的：缓存而不与操作系统直接交互

```text
需要栈 → 先看 P 本地缓存 / stackpool / stackLarge → 命中即拿走
       → 都不命中才去内存分配器/操作系统要 → 用完归还到缓存
```

如果不是缓存，那么**每次要用栈就去操作系统申请、用完再还给操作系统**，开销会明显变慢；同时**必须做缓存上限**，尽量避免无限缓存导致内存被过度占用。

### 面试官会追问什么

- **"`stackpool` 和 `stackLarge` 各自管什么？"** → 分界线 16KB：`stackpool` 缓存 ≤16KB 的小栈，`stackLarge` 缓存更大的栈，且大栈按"2^i 个页"分级。
- **"`_NumStackOrders` 是怎么来的？"** → 按操作系统固定栈大小反推等级数，保证最大缓存栈容量统一为 16KB（2KB→4 级，4KB→3 级，8KB→2 级）。
- **"为什么按 64 字节对齐？"** → CPU 缓存行是 64 字节且是缓存操作的最小单元；两次取模是为了防止大小恰好整倍时多占一个缓存行。
- **"`stackCacheSize = 32KB` 是全局总量吗？大栈 `free` 为什么是 35？"** → 不是，是**每个 P、每个栈等级**的上限，单 P 总量是 `32KB × _NumStackOrders`；35 来自 `heapAddrBits(48) - pageShift(13)`，下标 i 对应 2^i 个页（3 个页会归并到 4 个页）。

## 四、内存分配器初始化（`mallocinit`）做了哪些事情？

**来源**：`BV12qjA6aErF p=34` B站 Go 面试真题 · 时长 14分45秒
**考察意图**：考你**对内存分配器参数的"数感"**——`tinySizeClass`/`tinySize` 为什么是 2 和 16、堆位图为什么按"字"标记、`physPageSize` 与透明大页为什么必须是 2 的幂、128 个 arena 提示地址是干嘛的。这题答得好，说明你真读过 `malloc.go`，而不只是背过三级缓存。

### 一、主干只有五步

| 步骤 | 内容 |
|---|---|
| **①** | 检查微小分配器（tiny allocator）的定义 |
| **②** | 检查堆内存块位图字数为 2 的幂次 |
| **③** | 检查物理页大小、透明大页、span 扫描页数 |
| **④** | 初始化内存分配相关的核心锁 |
| **⑤** | 按指针宽度（4/8 字节）分支，生成 128 个地址提示（arena hints） |

### 二、第一步：tiny allocator 的两项校验

```text
_TinySizeClass = 2 ；_TinySize = 16
检查 class_to_size[_TinySizeClass] == _TinySize   // class_to_size[2] 应为 16
```

**为什么 Go 要有微小分配器？** 核心是**避免小对象对齐造成的惊人浪费**：

| 场景 | 无 tiny allocator | 浪费率 |
|---|---|---|
| 申请 1 字节 | 出于对齐需要分配 8 字节 | **7/8 ≈ 87%**（最大浪费率） |
| 申请 2 字节 | 同样需要对齐 | 浪费 6 字节 |

而现实中的数据分布是：**绝大多数对象都很小**——超过 80% 的对象小于 32KB，而这其中又有超过 80% 是**小于 1KB** 的；换言之，**小于 16B 的极小对象在数量上占比极大**。所以 Go 引入微小分配器：**把 `class 2` 的 span 切成极小的内存块，多个小对象可以"拼"进同一个块里**（一个 16 字节的块：申请 1 字节给整块剩 15 → 再申请 2 字节剩 13 → 再申请 10 字节剩 3，最后剩的 3 字节还能继续容纳 1/2/3 字节的小对象）。

> 微小分配器的核心逻辑就是**尽可能复用这一个 16 字节的块**——这就是这里必须先做 `class_to_size` 校验的原因。

### 三、第二步：堆内存块位图的字数必须是 2 的幂

| 常量 | 值/关系 | 说明 |
|---|---|---|
| `logHeapArenaBytes` | **26** | 与平台相关算出的 2 为底的对数，即 arena = 2²⁶ = 64MB |
| `heapArenaWords` | `heapArenaBytes / 指针大小` | 堆内存块的总字数 |
| `heapArenaBitmapWords` | `heapArenaWords / (8 × 指针大小)` | 位图以"字"为单位，**校验它是否为 2 的幂次** |

**为什么位图按"字"检查，而不是按字节？** 判断"内存有没有被分配"**不是一个字节一个字节去查**，而是**一个字（= 操作系统指针宽度）一次**：64 位系统上指针宽度 = **8 字节 = 64 bit**；一个标记字（8 字节）的每一位对应一个堆内存块单位（已分配标 1、未分配标 0），**因此一个字能标记 8 × 8 = 64 个堆内存块单位**。位图自身用多大数组来标记，就由 `heapArenaBitmapWords` 决定，并且**必须是 2 的幂次**。

### 四、第三步：页相关的三重检查

| 检查项 | 规则 |
|---|---|
| **物理页大小** | `physPageSize` **必须是 2 的幂次** |
| **透明大页** | 必须是 2 的幂次；**大于最大值（4GB）则置 0，即禁用透明大页** |
| **span 扫描页数** | 页数必须是 `pagesPerSpanRoot` 的整数倍（**能否被它整除**） |

其中 `pagesPerSpanRoot` 表示**跨度内用于扫描内存的页数**，**默认 512 页**——也就是**每次回收 512 个页**。

### 五、第四步与第五步

**第四步**：对内存分配器**需要用到的一批核心锁做初始化**。**第五步**：**根据指针宽度（8 字节还是 4 字节）分流**，代码看着很长，其实主要是**位运算**——64 位系统上会**生成 128 个地址提示（arenaHints）**，含义是**主动给应用程序预留/提示一批地址**：这些地址**容易识别、且不容易和其他层面的地址冲突**（既不和内核底层地址冲突，也不和用户层地址冲突）；**运行时需要分配地址时会优先从这 128 个提示地址里找可用的空间**，找到了就优先用，找不到再去尝试其他地址。目的就是**避免不必要的冲突，并让地址易于识别**。

### 面试官会追问什么

- **"tiny allocator 到底解决什么问题？"** → 小于 16B 的小对象对齐浪费太大（最高 87%），用一个 16B 块复用多个小对象。
- **"`_TinySizeClass` 和 `_TinySize` 是多少？"** → 2 和 16，并校验 `class_to_size[2] == 16`。
- **"堆位图为什么要按字算？"** → 分配标记以指针宽度为单位（64 位 = 8 字节 = 64 bit），一个字标 64 个单位，位图字数因此是 `heapArenaWords / (8 × 指针大小)`。
- **"为什么这些值都要求是 2 的幂？透明大页大于 4GB 会怎样？128 个地址提示干什么用？"** → 位运算/对齐是分配器的基础操作，非 2 的幂会让取整与索引变得昂贵甚至出错；透明大页大于 4GB 就把值置 0 禁用；地址提示用于预置一批易识别、低冲突的地址供优先分配。

## 五、调度器初始化（`schedinit`）过程是怎样的？

**来源**：`BV12qjA6aErF p=36` B站 Go 面试真题 · 时长 12分33秒
**考察意图**：考**流程的完整度与顺序感**。`schedinit` 一百来行却有二十多个环节，面试官想听的是：走过这个阶段之后**应用程序才具备资源调度能力**。重点要能把**锁 → 竞态检测 → 模块数据校验 → 各类初始化 → P 的数量与状态 → world start** 这条主线讲顺。

### 一、定位与总览

在 `proc.go` 里找到具体实现（约一百多行）。**字面意思就是"调度器初始化"——经过这个阶段之后，应用程序就具备了资源调度的能力。** 流程本身不复杂，但**环节很长（二十多个）**，按顺序如下。

### 二、前半段：锁、竞态检测与全局状态

| # | 环节 | 做什么 |
|---|---|---|
| **1** | **核心锁初始化** | 对运行时的核心锁做初始化，给这些锁**设置对应的优先级/锁顺序** |
| **2** | **数据竞态检测** | 编译时加了 `-race` 标志，会顺便帮我们初始化**数据竞态检测模块** |
| **3** | **设置最大内核线程数** | 限制 M 的数量上限 |
| **4** | **world stop** | 这里**事实上是个空函数，里面什么都没有**，作用是**语义标记** |
| **5** | **模块数据校验** | `moduledataverify`（详见下一小节） |

**关于第 1 步的锁顺序**：`lockInit` 默认实现（`lockRankOff`）**无非是把锁的顺序/优先级保存到锁对象里**，加锁解锁时会**沿着这个顺序去做检查**（例如检查加锁顺序是否合法）。这套**静态锁排序**是通过**编译期选项**启用的（实践中相当于加 `lockranking` 这类构建标签），目标用户是**Go 运行时的开发者、底层系统开发者**：在开发或测试阶段**验证锁使用顺序的正确性、提前暴露死锁风险**——**不是给业务开发者用的**。

**关于第 4 步 world stop**：

> 它是一个**语义标记**：从这一行开始，**要求应用程序处于 world stop 状态**——所有用户线程都会挂起，只保留系统级线程做全局操作。而当前正处于**应用程序初始化的阶段**，此时**本来就没有用户级别的协程**，所以默认就已经是这个状态，**不需要做任何操作**。补充：**GC 做内存回收/内存标记时也会涉及 stop the world**，目的是**避免用户协程并发导致标记不准确（多标、漏标）**。

### 三、中段：模块、类型、接口、算法、CPU

| # | 环节 | 做什么 |
|---|---|---|
| **5** | **`moduledataverify`（模块数据校验）** | 校验程序的模块信息，**包含函数符号表、PC 地址表、模块哈希等**；启动之初先校验这些数据**是否符合运行时的预期**，**避免元数据损坏/非法**导致**调度、栈回溯、函数查找等核心功能异常** |
| **6** | **页相关初始化** | 页面大小等信息初始化 |
| **7** | **`cpuinit`（CPU 特性初始化）** | 根据 CPU 特性初始化相应标志 |
| **8** | **算法初始化** | 根据 **CPU 硬件特性**选择并初始化**最优的加密与哈希实现**；同时包含 **M 的 ID 分配、随机函数/生成器、绑定关键的引用等内容** |
| **9** | **`modulesinit`（模块初始化）** | **整理所有已加载模块**（主程序 + 插件 plugin）的 `moduledata` 指针，**调整模块顺序以满足依赖**，最终**生成全局可用的活动模块列表**，为类型链接等核心功能提供统一的模块数据支持 |
| **10** | **`typelinksinit`（类型链接初始化）** | **扫描所有已加载模块**（主程序 + 插件）的**类型信息**，通过**哈希与类型对比**构建模块专属映射，实现**跨模块的类型去重**——**确保相同语义类型在运行时只有一个唯一实例** |
| **11** | **`itabsinit`（接口表初始化）** | **收集所有活动模块的预编译接口表并注册到全局**，为接口的**类型断言、方法调用**提供快速查找 |
| **12** | **栈对象管理初始化** | 提供**栈上特殊对象的指针标记信息**，确保能正确标识栈上对象的指针字段，**避免 GC 漏扫** |
| **13** | **信号掩码保存** | 保存信号掩码（`sigsave`） |

### 四、后段：参数、GC 与 P

| # | 环节 | 做什么 |
|---|---|---|
| **14** | **参数/命令行参数、环境变量、安全策略初始化** | `goargs` 一类的初始化 |
| **15** | **调试变量解析** | 解析 `debug.*` 相关变量 |
| **16** | **`GCinit`** | **垃圾回收器初始化**：初始化相关核心数据结构，以及状态、配置等（含调度器相关配置） |
| **17** | **内存分析状态设置** | 与内存分析相关，**在这里只是一个状态的设置** |
| **18** | **初始化 P 的数量与状态** | GMP 中的 **P**：根据 `GOMAXPROCS` 等确定 **P 的数量与状态** |
| **19** | **world start** | 前面有 stop，这里就必须有 start。**同样是空函数，同样是语义标记** |
| **20** | **CGO 检查与写屏障相关初始化** | 启动收尾阶段为后续并发运行做准备 |
| **21** | **构建版本信息** | 保留构建版本的模块信息；**如果版本信息为空，很可能被编译器优化掉，所以这里给一个 `unknown` 作为初始值/默认值兜底** |

**关于第 19 步 world start 的语义**：

> **在 world stop 到 world start 之间的这一段，必须要求应用程序处于停止状态、没有用户协程。** 对于启动过程而言，它**一直处于这个状态**，所以两个函数都是空的——它们标记的是**区间不变量**，不是动作。

### 面试官会追问什么

- **"`schedinit` 之后程序有什么能力？"** → 具备资源调度能力（P 已就绪、模块/类型/接口表已备好、GC 已初始化）。
- **"为什么 `worldstop` / `worldstart` 是空函数？"** → 它们是语义标记，保证 stop→start 区间内应用处于无用户协程的停止状态；启动阶段天然满足。
- **"`moduledataverify` 校验什么、防什么？"** → 函数符号表、PC 地址表、模块哈希；防止元数据损坏导致调度、栈回溯、函数查找异常。
- **"`typelinksinit` 和 `itabsinit` 的区别？栈对象管理初始化、版本信息兜底分别为了什么？"** → 前者做跨模块类型去重（保证语义类型唯一实例），后者注册预编译接口表服务类型断言与方法调用；栈对象管理给栈上特殊对象提供指针标记信息、避免 GC 漏扫，版本信息兜底防止空值被编译器优化掉。

## 六、启动过程中运行时做了哪些检查（`runtime.check`）？

**来源**：`BV12qjA6aErF p=37` B站 Go 面试真题 · 时长 12分00秒
**考察意图**：考你**知不知道 Go 为什么要"自检"**——这些检查校验的是**编译器、汇编器与运行时之间的隐含约定**（类型大小、结构体布局、原子操作、NaN 语义、固定栈大小）。面试官想听到的是"检查目的是提前暴露不兼容/编译错误"，而不是背九个条目。

### 一、定位

在 `runtime1.go` 里按文件名查找，就能搜到 `runtime.check` 的定义。流程图环节看似简单，但每一条都在**验证程序启动前的关键状态**。

### 二、九个检查项

**① 基本类型长度检查**：先定义一批类型与变量（`int`/`int8`/`int16`/`int32`/`int64`、若干浮点类型、指针类型、`byte` 切片，以及两个结构体和对应变量），然后**逐个比对基本类型的大小**——`int8` 1 字节、`uint8` 1 字节、`int16` 2 字节……直到 `float64` 8 字节。

**② 指针类型长度检查**：校验对象是**指针类型**（如 `unsafe.Pointer` 与无符号整型指针）。规则是**不管指向什么类型的指针，长度都应该一样**——指针存的是地址，长度固定；但**这个长度随 CPU 架构变化**：**32 位平台 4 字节，64 位平台 8 字节**。

**③ 结构体内存布局检查**：定义了嵌套结构体，按布局推算——内层结构体 1 字节；外层结构体内层 x 在偏移 0、字段 y 在偏移 1、整体 2 字节；**偏移量/大小不等于预期值就报错**（bad StructLayout）。若结构体里**没有字段**，就是**空结构体**，启动时同样会做相应校验（视频此处一带而过）。

**④ 时间转换函数（`timediv`）检查**：

```text
timediv(12345 * 1000000000 + 54321, 1000000000, &q, &r)
期望：q == 12345 且 r == 54321
```

这是**先乘、再加、再除**的组合运算，用来验证编译器的**除法/取模代码生成**是否正确——**结果不一致就说明有问题**。

**⑤ 原子操作检查：比较交换（CAS）**：定义变量后做 **compare and swap**，检验**比较并交换的原子操作**是否按预期工作（含失败场景的验证）。

**⑥ 原子操作检查：按位运算**：对**按位或（`|`）、按位与（`&`）、按位异或（`^`）** 等操作，与内存中对应位置的值做计算后逐项判断。

**⑦ NaN 特性检查**：Go 里常见 `a != a`、`a == a` 这类判断，本质是 **NaN 与自身不相等**的语义——用 `uint64(1<<64 - 1)` 取反得到全 1 位模式，**写到 `float64` 变量 j 所在地址**使其变成 NaN，**再校验 `j != j`**；同样还包含 `float32`（`uint32` 位模式）的检查。

**⑧ 64 位无符号整数的原子操作检查**：针对 `uint64` 做原子操作校验，包括 **Store、Load、Add、Swap** 等一整套。

**⑨ 固定栈大小必须是 2 的幂**：`if round2(fixedStack) != fixedStack → 有问题`。`fixedStack` 由栈的守护值算法导出：

| 量 | 说明 |
|---|---|
| 最小值 | **2048** |
| 加上 `stackSystem` | 由操作系统 + 栈守护倍数 × 指针宽度组成；**例如 Windows 上 512 × 8 字节 = 4096** |
| `fixedStack0` | `2048 + stackSystem`（如 2048 + 4096 = 6144 这条路径的起点） |
| `fixedStack` | 再往下逐级计算得到的最终值 |

**⑩ 汇编语言运行时的检查**：因为运行时里**会涉及大量汇编函数的调用**，所以还需要**校验汇编语言的运行时**——在 `runtime` 包里查找（例如 amd64 对应的汇编文件）可以看到这个汇编函数，`check` 会调用它，**校验不通过就报错**。

### 面试官会追问什么

- **"这些检查什么时机跑、失败会怎样？"** → 在进入业务代码前跑（`check` 阶段），失败直接 `throw` 终止，属于启动期的快速失败。
- **"为什么要检查指针类型长度一致？"** → 指针是固定长度的地址，长度只随架构（4/8 字节）变化，不一致说明编译器或 ABI 有问题。
- **"`timediv` 检查为什么用 12345 和 54321？"** → 用一组确定的商和余数验证"乘-加-除"代码生成路径的正确性。
- **"NaN 检查的核心是什么？为什么校验 `fixedStack` 是 2 的幂？为什么还要检查汇编运行时？"** → 构造 NaN 后验证 `j != j`，确保浮点比较语义符合 IEEE 预期；栈大小对齐依赖 2 的幂，`round2` 后必须等于自身；运行时大量依赖汇编函数，必须有独立的汇编侧自检。

## 七、操作系统信息初始化（`osinit`）做了什么？

**来源**：`BV12qjA6aErF p=38` B站 Go 面试真题 · 时长 16分47秒
**考察意图**：考你**知不知道运行时怎么"向操作系统问话"**——CPU 可用数量（亲和性）、透明大页大小、CGO 退出信号。追问点通常是 `sched_getaffinity` 为什么传 0 和缓冲区大小、禁用逃逸分析为什么在这里出现、`osArchInit` 为什么是空方法。

### 一、定位与总览

当前文件里**搜不到 `osinit`**（字面意思是"操作系统（信息）初始化"），仍然用**按文件名查找**的方式通过编译期检索：会看到很多个 `osinit`——**我们要找方法定义，而不是调用**。Go 是跨平台语言，不同平台实现有区别，会看到 `os_linux`、`os_windows`、`os_darwin` 等等。以 Linux 为例，`osinit` 的主干其实很简单，四件事：

| # | 环节 | 做什么 |
|---|---|---|
| **1** | **获取当前进程可用的 CPU 数量** | 通过 CPU 亲和性拿到进程能跑在哪些 CPU 上 |
| **2** | **获取透明大页（THP）/ 物理巨页的大小** | 读系统配置，得到大页尺寸 |
| **3** | **判定是否启用 CGO** | 若启用，则**从退出信号集中删除指定退出信号** |
| **4** | **操作系统架构初始化** | `osArchInit`（两个子流程就是上面的 1 和 2） |

### 二、获取 CPU 数量：为什么要问，怎么问

**为什么要获取 CPU 数量？** 因为应用程序运行时**并不能使用计算器上所有的 CPU**——启动进程时可以决定这个进程**能使用哪些 CPU**（亲和性限制）。

```text
① 定义 _CPU_SETSIZE（CPU 集合的最大数量）= 65536 = 64 × 1024
② 定义一个数组 buf，用来存 65536 个 CPU 的状态
   —— 每个 CPU 只用 1 个 bit 记录"能否使用"，65536 bit = 8KB，数组大小就是 8KB
③ 调用 sched_getaffinity 获取当前进程与 CPU 的亲和性：能用的 CPU 标 1，不能用的标 0
④ 得到结果 n，返回 n 即为可用 CPU 数量
```

**为什么范围要开这么大？** 常见的服务器只是几个核、几十核、上百核，多一点到 1024 核左右，再往上就是超级高性能服务器，用得比较少——**65536 个 CPU 的上限覆盖面非常大**，所以位图也只需要 8KB。调用细节：

| 参数 | 传什么 | 为什么 |
|---|---|---|
| pid | **0** | 表示**当前进程** |
| size | **buf 的大小** | 防止内核不知道缓冲区大小而**导致内存越界** |
| 缓冲区 | **buf 的地址** | 数组内容的地址就作为参数传入 |

**这个函数本身也是"占位"**：按文件名查找可以看到**不同架构有不同实现**，底层最终**触发系统调用**（`syscall.Syscall`），也就是**从用户态转入内核态**；取到结果后再**遍历计算出一个 n 并返回**——比如传入 65536 的数组，实际得到的可能是 1024，那么只需判断 1024 个 CPU 的状态。

### 三、获取透明大页大小：为什么需要大页

**背景（Linux 的 THP，Transparent Huge Page）**：传统内存页尺寸是 **4KB**，相对较小；而现在个人 PC/服务器的内存动辄 16G、32G 起步，内存容量上去了，就需要匹配更大的页：

| 收益 | 说明 |
|---|---|
| **① 减少页表条目** | 大页尺寸是 **2MB 或更大**，可**大幅减少页表条目数量**，从而**降低 CPU 进行地址转换的开销** |
| **② 提高 TLB 命中率** | 更大的页能让 **TLB（页表缓存）覆盖更多内存地址空间**，**命中率越高，等待内存的时间越少**，整体内存访问效率提升 |
| **③ 应用无感知** | 透明大页的优化**对应用程序完全无感知**——应用层不需要做任何修改或特殊配置，**操作系统在后台自动完成大页的分配、管理与回收** |

所以运行时这里只需要做一件事：**把大页的大小读出来**。

```text
① 打开 /sys/.../transparent_hugepage 下的配置地址（hugepagesize 一类文件）
     —— 操作系统配置的多大就读出多大；想改更大的页直接改文件即可，
        应用程序不需要做任何配置，会自动读这个文件
② 禁用内存逃逸分析（//go:uintptrescapes 一类的标注）
③ 分配 longBuf，把数据填充到这块地址上
④ 读取 fd，把数据填充进来 → 关闭 fd / 关闭文件
⑤ 对读到的数据做 Atoi（字符串转数字）→ 返回该数字的地址（无符号整型）
```

**为什么要禁用内存逃逸分析？**

> 这里涉及**地址传递**：通常把变量地址传给其他函数调用时，变量倾向于**逃逸到堆上**，而堆分配相对而言性能更好、也是这里的预期行为。逃逸的逻辑是：如果变量只在本方法里正常使用，方法结束它就释放（在栈上回收）；**但一旦把地址传出去，本方法可能结束了，其他方法还持有这个地址的引用**，变量就**没法随方法栈回收**，只能**逃逸到堆上由 GC 回收，而不是靠栈自动回收**。所以这里**主动禁用逃逸分析**，避免不必要的内存逃逸（否则会**让效率变低**）。

### 四、判定是否启用 CGO

```text
if isCGO {   // 应用程序里有没有嵌入 C 的代码；嵌入了默认就会启用 CGO
    // glibc / musl 这类 C 运行时的代码里会保留一些退出信号，
    // 而这些退出信号在 Go 里使用时并不希望被触发，
    // 所以把这些特定的信号量从退出信号集中移除，避免冲突/死锁
}
```

### 五、`osArchInit`：一个扩展位

最后是 **`osArchInit`（操作系统架构初始化）**。这个函数**没有实现——都是空方法**：它相当于**预留的接口/扩展位置**，**不同的硬件架构未来可能会对它做不同实现**；按文件名查找可确认它没有任何实现。

### 面试官会追问什么

- **"为什么 `sched_getaffinity` 传 pid = 0？为什么还要把 buf 的大小传进去？"** → 0 表示当前进程；传长度是让内核知道缓冲区大小，否则可能越界写。
- **"为什么 `_CPU_SETSIZE` 是 65536，却只占 8KB？"** → 每个 CPU 用 1 bit 记录可用状态，65536 bit = 8KB。
- **"Go 为什么要读大页大小？"** → 减少页表条目、降低地址转换开销、提高 TLB 命中率，且应用层无需改动。
- **"读大页配置时为什么禁用逃逸分析？CGO 为什么要动退出信号？`osArchInit` 为什么是空的？"** → 涉及地址传递会被判为逃逸并走堆分配，此处正是要堆分配、避免不必要的逃逸开销；glibc/musl 保留了若干退出信号，Go 不希望它们被触发，需要从退出信号集中移除；`osArchInit` 是留给不同硬件架构未来实现的扩展位。

## 启动流程全景图

下面按**面试背诵顺序**把整条时间线串起来（集号顺序 ≠ 流程顺序，本表已按流程重新排列）：

### 一、有序阶段

| # | 阶段 | 关键函数/入口 | 一句话记忆点 | 对应 Q |
|---|---|---|---|---|
| **1** | **汇编入口** | `_rt0_amd64` → `runtime·rt0_go` | 真正的程序入口，业务代码的 `main` 只是它的下游 | 第一节 |
| **2** | **g0 / m0 / TLS** | 初始化 g0、绑定 m0 的 TLS、g0↔m0 双向绑定 | g0 跑调度与 GC，M 与 g0 一对一 | 第一节 |
| **3** | **CPU 型号与 CGO** | 探测 CPU 厂商、`cgo` 初始化、**更新栈保护** | CGO 影响栈布局，必须重设栈保护 | 第一节 |
| **4** | **兼容性校验** | 硬件/OS 兼容性 → `bad CPU` | 不兼容就跳到 `bad CPU` 报错 | 第一节 |
| **5** | **运行时检查** | `runtime.check` | 九类自检：类型大小/布局/原子/NaN/固定栈/汇编 | 第六节 |
| **6** | **命令行参数与 auxv** | `runtime.args` → `sysargs` | 全局 `argc`/`argv` + auxv 五个关键 tag | 第二节 |
| **7** | **操作系统信息** | `osinit` | 可用 CPU 数、大页大小、CGO 退出信号 | 第七节 |
| **8** | **栈初始化** | `stackinit` | `stackpool`(≤16KB) / `stackLarge`(>16KB)，单 P 上限 128KB | 第三节 |
| **9** | **内存分配器初始化** | `mallocinit` | tiny 校验 → 位图 → 页检查 → 锁 → 128 个地址提示 | 第四节 |
| **10** | **调度器初始化** | `schedinit` | 锁顺序 → 模块校验 → 模块/类型/接口/算法 → GC → P → world start | 第五节 |
| **11** | **创建 main goroutine** | `newproc` | 创建一个 goroutine 去执行 `main` | 第一节 |
| **12** | **启动调度器** | `mstart` | 让 **m0 开始执行**这个 goroutine → 进入 `main.main` | 第一节 |

### 二、按顺序背诵版

```text
_rt0_amd64
  └─ runtime·rt0_go
       ├─ 调栈对齐 + 规范化传参（argc/argv 入栈）
       ├─ 初始化 g0；初始化 m0 的 TLS；g0 ↔ m0 双向绑定
       ├─ 探测 CPU 型号；初始化 CGO；更新 g 栈保护
       ├─ 硬件/OS 兼容性校验（失败 → bad CPU）
       ├─ runtime.check        运行时自检
       ├─ runtime.args         解析命令行参数 + auxv（含两级兜底）
       ├─ osinit               可用 CPU 数 / 大页大小 / CGO 退出信号
       ├─ schedinit
       │    ├─ stackinit       stackpool / stackLarge
       │    ├─ mallocinit      tiny / 位图 / 页 / 锁 / arenaHints
       │    ├─ moduledataverify、cpuinit、alginit
       │    ├─ modulesinit、typelinksinit、itabsinit、stkobjinit、sigsave
       │    ├─ goargs、parsedebugvars、gcinit
       │    ├─ procresize(P 的数量与状态)
       │    └─ worldstart
       ├─ newproc(main)        创建 main goroutine
       └─ mstart               启动调度器，m0 开始执行 → main.main
```

> **说明**：上面两个版本按"一个知识点一块"的粒度展开，便于逐段背诵。严格按源码执行次序是 `check()` → `args()` → `osinit()` → `schedinit()`，而 **`stackinit()` 与 `mallocinit()` 是 `schedinit()` 内部的子步骤**（视频也正是分集逐个展开讲的）。

### 三、三条速记线索

1. **G/M/P 何时就位**：g0/m0 与 TLS 在最前面的汇编阶段（第 2 步）就绪 → **P 在 `schedinit` 收尾的 `procresize` 才就绪** → 之后才 `newproc` + `mstart`。
2. **"兜底"集中出现的地方**：auxv 拿不到时的两级兜底（`/proc/self/auxv` → `mmap` 探测 → 256KB 兜底）；构建版本信息为空时的 `unknown` 兜底；透明大页超过 4GB 时置 0 禁用。
3. **"空函数/语义标记"一共有三类**：`worldstop` / `worldstart`（区间不变量）、`sysargs` 等跨平台占位方法（编译期选实现）、`osArchInit`（架构扩展预留位）。
