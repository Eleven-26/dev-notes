## 一、调用一个函数的具体过程是怎样的？

**来源**：`p=67` 腾讯 Go 后台开发面试 · 时长 2分53秒

**考察意图**：⚠️ **这是一道"态度题"而不是"能力题"**——原视频讲得很直白，值得单独记下这个判断。

### 一、先看这类题的性质

> **重点是「面试官问了、你答上来了」，而不是答案有多精准。**
>
> 因为**函数的调用过程是一成不变的、几乎不会变化**——
> 它是这么调就这么调，整个流程固定。
>
> **它不具备扩展性**，我们也**不会基于"函数调用过程"去优化代码**。

### 二、所以怎么应对

| 做法 | 说明 |
|---|---|
| **直接背下来** | 通过搜索引擎或 AIGC 查询"函数调用过程"，<br>拿到的答案基本**大差不差**，背下来即可 |
| **不必纠结精度** | 不需要去看源码，也不需要考证每个细节是否绝对准确 |
| **要能接住** | 面试时**答上边**就行 |

### 三、这题到底在考什么（理解了就不慌）

> **它考的是：你有没有开始关注底层逻辑，
> 而不是停留在"我会用"的应用层。**
>
> 很多面试官问这个问题时，**自己未必能完整答上来**——
> 他要的是一个信号：**你愿意往下看一层**。

### 面试建议

> **面这类"死知识"题，不要试图现场推导**——
> 直接把标准流程背熟、流利地讲出来，**比支支吾吾地"思考"效果好得多**。

## 二、栈里面除了局部变量、函数参数、返回值，还有什么？

**来源**：`p=68` 腾讯 Go 后台开发面试 · 时长 2分58秒

**考察意图**：这类题的共同点是——**考你有没有了解底层**，答案**能答出几个就行**。

### 六个部分（大概记住这六类即可）

| # | 内容 |
|---|---|
| **①** | **函数调用的相关信息**（如返回地址、栈帧指针等） |
| **②** | **函数参数、返回值、局部变量** |
| **③** | **寄存器状态**（需要保存/恢复的寄存器值） |
| **④** | **协程的相关信息** |
| **⑤** | **异常处理的相关信息**（`panic` / `recover` 相关） |
| **⑥** | **Go 特有的 `defer` 延迟调用信息** |

> **答题标准（原视频的建议）**：
> **能答出几个就够，不必答得多么精准漂亮**——
> 因为面试官自己也**未必能精确描述**栈里到底有什么。

### 面试官会追问什么

- **Go 的栈和线程栈有什么区别？** → **goroutine 栈是可增长的**：
  初始仅 **2KB**，不够时**自动扩缩容**（这也是 goroutine 比线程轻的关键）。
- **栈扩容时旧栈上的指针怎么办？** → 运行时**会扫描并调整所有指向旧栈的指针**
  （这也是 Go 需要精确 GC 类型信息的原因）。
- **逃逸和栈的关系？** → **逃逸就是"本该在栈上的变量被放到了堆上"**（见 [内存逃逸.md](内存逃逸.md)）。

## 三、⚠️ 但「背下来就行」有个版本陷阱：Go 1.17 起参数不再走栈

**来源**：本节为补充内容 —— 按《Go 语言核心编程》（李文塔）2.7.1 函数调用规约 整理，配套本机实测。

**考察意图**：考的是「**你背的那个版本对不对**」—— 调用约定在 Go 1.17 换过一次，只会复述老答案的人在这里露馅；能主动提「版本 + 怎么看汇编求证」就赢了。

> 前两节是原视频的定性（态度题、能答几个算几个）。**结论同意一半** ——
> 「不必纠结精度」没问题，但**要背的那个流程本身有版本**：
> 书 2.7.1 讲「函数调用规约」时（2018 年成书），描述的是**参数与返回值全部走栈**；
> **Go 1.17 起 amd64 的调用约定改成了寄存器传参**。所以搜索引擎上的答案**一半是过时的**——
> 面试官如果知道这个变更，你背老答案反而暴露了"只是搜来的"。

### 一、实测：参数和返回值都在寄存器里

```bash
go build -gcflags="-S" main.go        # 输出到 stderr
```

```text
main.add STEXT ... args=0x10 locals=0x0
	TEXT	main.add(SB), NOSPLIT|NOFRAME|ABIInternal, $0-16
	...

main.swap STEXT ... args=0x10 locals=0x0
	TEXT	main.swap(SB), NOSPLIT|NOFRAME|ABIInternal, $0-16
	...
	MOVQ	AX, CX          ← 暂存 a
	MOVQ	BX, AX          ← b 挪到 AX（第一个返回值）
	MOVQ	CX, BX          ← a 挪到 BX（第二个返回值）
	RET
```

| 记号 | 含义 |
|---|---|
| **`ABIInternal`** | ⭐ **寄存器调用约定**的标记（老版本的函数头**没有**这个标记） |
| **`$0-16`** | 本函数栈帧 **0** 字节、入参 16 字节 —— add/swap **全程没碰栈** |
| `MOVQ AX, CX` 等 | 参数**从 AX、BX 进来**，返回值也**从 AX、BX 出去** |

### 二、寄存器不够时照样溢出到栈

`sumBig(a,...,j int)`（10 个 int 参数）实测：

```text
main.sumBig STEXT ... args=0x50 locals=0x0
	TEXT	main.sumBig(SB), NOSPLIT|NOFRAME|ABIInternal, $0-80
	LEAQ	(BX)(AX*1), DX      ← a + b
	ADDQ	DX, CX              ← + c
	ADDQ	DI, CX              ← + d
	ADDQ	SI, CX              ← + e
	ADDQ	R8, CX              ← + f
	ADDQ	R9, CX              ← + g
	ADDQ	R10, CX             ← + h
	ADDQ	R11, CX             ← + i
	MOVQ	main.j+8(SP), DX    ← ⭐ 第 10 个参数：从栈上取
```

> ⭐ amd64 上**整数/指针参数寄存器共 9 个**（AX、BX、CX、DI、SI、R8、R9、R10、R11），
> 所以第 10 个参数 `j` 就溢出了 —— 汇编里直接写作 `main.j+8(SP)`，落在**调用者准备的入参栈区**上。
> 也就是说：**「寄存器传参」不是绝对的，参数一多自动退回栈**。回答时说清这一点，比背「走寄存器」更完整。

### 三、这个变更的收益，以及能不能关掉

- **收益**：省掉每次调用在栈上写一遍参数、再读回来的往返，官方给出的整体性能提升**约 5%**。
- **能否复现旧行为**：早期可以用 `GOEXPERIMENT=noregabi` 关闭该特性；
  **本机 go1.26.5 实测这个开关已被移除**（传了无效，汇编里仍是 `ABIInternal`）。
  → 「全栈传递」已经无法在新工具链上跑出来，只能作为**历史知识**记住它存在过。

## 四、顺手学会看 `-S` 输出：伪寄存器与栈帧记号

**来源**：本节为补充内容 —— 按《Go 语言核心编程》（李文塔）2.7.2 汇编基础 整理，配套本机实测。

**考察意图**：会看汇编不是加分项，而是**能自己求证的硬能力** —— 本章所有关于调用约定的结论，都能用这一步在自己机器上复核。

### 一、四个伪寄存器

| 伪寄存器 | 含义 |
|---|---|
| **SB** | Static Base，全局符号基址 —— `main.add(SB)` 表示「main.add 这个符号」 |
| **FP** | Frame Pointer，**入参 / 返回值区**，写作 `a+16(FP)` 这种「名字+偏移」的形式 |
| **SP** | 当前函数的**栈顶**（局部变量区），注意它不是硬件的 SP 寄存器 |
| **PC** | 程序计数器，跳转目标 |

### 二、函数头部那行怎么读

```text
main.main STEXT ... args=0x0 locals=0x58
	TEXT	main.main(SB), ABIInternal, $88-0
	CMPQ	SP, 16(R14)      ← ① 栈空间检查
	JLS	125              ← ② 不够就跳去扩栈
	PUSHQ	BP
	MOVQ	SP, BP           ← ③ 建立栈帧
	SUBQ	$24, SP          ← ④ 给局部变量下移栈顶
```

| 片段 | 含义 |
|---|---|
| `$88-0` | 本函数栈帧 **88 字节**（与 `locals=0x58`=88 对上）、入参 **0** 字节（main 无参数） |
| `CMPQ SP, 16(R14)` + `JLS` | ⭐ **栈增长检查**：`R14` 是 g 寄存器，`16(R14)` 即 `g.stackguard0` |
| `PUSHQ BP` / `MOVQ SP, BP` / `SUBQ $24, SP` | 保存旧帧指针 → 设立新帧 → 下移栈顶 |

> ⭐ 第 2 行是 **「Go 的栈为什么能自动增长」的直接证据** —— 每个普通函数的开头就插了这个检查，
> 栈不够就跳去 `morestack` 申请更大的栈、把旧栈搬过去（这也是第二节追问里「栈扩容时旧指针怎么办」的落地位置）。

## 五、多值返回与闭包，在汇编里长什么样

**来源**：本节为补充内容 —— 按《Go 语言核心编程》（李文塔）2.7.3 多值返回分析、2.7.4 闭包底层实现 整理，配套本机实测。

**考察意图**：多值返回与闭包是最容易被追问「**底层怎么实现的**」的两处；能指着汇编说出 `struct { F uintptr; X0 *int }` 是 funcval，比背结论有说服力得多。

### 一、多值返回：多给几只寄存器

就是第三节 `swap` 那几行 —— 两个 int 返回值分别放在 **AX / BX**，不需要堆、也不需要额外栈空间。
返回值多到寄存器放不下时，同样溢出到栈（调用者预留在 `FP` 区）。书里 2.7.3「多值返回分析」讲的就是这条规则。

### 二、闭包：一个叫 `funcval` 的堆上结构

`counter()` 返回一个闭包，实测汇编：

```text
main.counter STEXT ... args=0x0 locals=0x20
	TEXT	main.counter(SB), ABIInternal, $32-0
	LEAQ	type:int(SB), AX
	CALL	runtime.newobject(SB)                              ← ① n 被分到堆
	MOVQ	AX, main.&n+16(SP)
	LEAQ	type:noalg.struct { F uintptr; X0 *int }(SB), AX    ← ② 闭包对象的结构
	CALL	runtime.newobject(SB)                              ← ③ 闭包本身也在堆上
	LEAQ	main.counter.func1(SB), CX                         ← ④ 闭包的代码地址
	MOVQ	CX, (AX)                                           ← ⑤ 写进结构第一个字段
	CMPL	runtime.writeBarrier(SB), $0                       ← ⑥ 写屏障
```

| 观察 | 含义 |
|---|---|
| ② `struct { F uintptr; X0 *int }` | ⭐ **闭包 = `funcval` 结构**：`F` 是函数指针，`X0` 是**捕获的变量**（这里捕获的是 `*int`，因为 `counter.func1` 要改 `n`） |
| ① `runtime.newobject` | 被捕获的 `n` 被**分配到堆**（`&n` 被闭包引用 → 逃逸），见 [内存逃逸.md](内存逃逸.md) |
| ③ `newobject` + ⑤ | 闭包**本身也是一个堆对象**，每次创建都要分配 |
| ⑥ 写屏障 | 往堆对象里写指针，GC 需要记录这一处引用 |

> ⭐ 这三条回答了「**闭包为什么会慢 / 为什么会让变量逃逸**」：
> 闭包**不是**一个"指向函数的指针"，而是**堆上分配的结构体**（函数指针 + 捕获变量表）；
> 每次创建闭包要 `newobject`，被捕获的变量也必须搬到堆上，闭包才能长期访问它。
> 书 2.7.4「闭包底层实现」讲的就是这个 `struct { F uintptr; ... }`。

### 面试官会追问什么

- **为什么不能只用寄存器？** → 寄存器数量固定（amd64 上整数参数寄存器 9 个），且**调用者的寄存器在调用中不保证保留**，参数超了就溢出到栈。
- **怎么看某个函数到底有没有用寄存器？** → `go build -gcflags="-S"` 看函数头有没有 `ABIInternal`，再看指令里有没有 `(SP)` 形式的参数读取。
- **想看更准确的指令（而不是 -S 的伪汇编）？** → `go tool objdump -s 'main\.add' ./可执行文件`。
