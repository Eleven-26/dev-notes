## Q1. Map 为什么会有哈希冲突？Go 是怎么解决的？

**来源**：`p=14` 百度 Go 后端一面 · 时长 9分24秒
**考察意图**：从"为什么需要哈希"推演到"冲突不可避免"，再讲到 Go 的具体实现——考的是**推理链条**。

### 先回答"为什么会冲突"

假设我们要存 key-value：

- **用数组存**：靠"索引 + 地址偏移量"直接定位，**不可能有冲突**，但前提是**按下标访问**；
- **用"key 数组"存**：必须**循环遍历逐个比对 key** 才能找到目标——这是效率最差的做法。

map 存在的意义，就是让 **key 起到"索引"的作用**，快速定位 value。做法是：

> 用 **哈希函数把 key 映射到一个固定的区域**，直接跳到那个区域去找，跳过遍历。

**冲突正是这个优化的代价**：哈希值空间远大于桶的数量，必然出现"不同的 key 落到同一个位置"。
**如果不做任何优化（老老实实遍历比对），是不会有哈希冲突的——因为 key 本身是唯一的。**

### Go map 的底层结构（`hmap`）

需要关注的字段：

| 字段 | 含义 |
|---|---|
| `count` | map 中键值对的数量 |
| `B` | **以 2 为底的对数**，表示桶（bucket）的数量：`2^B` |
| `hash0` | **哈希因子**，参与哈希计算。它的作用是让**相同的 key 在不同 map 实例中得到不同的哈希值** |
| `buckets` | 存储 key-value 数据的桶数组，长度 `2^B` |

**容量关系**：`B=0` → 1 个桶；`B=1` → 2 个桶；`B=2` → 4 个桶。

**每个桶（bucket）可以存 8 个元素**，桶内布局为：`tophash[8]` + `keys[8]` + `values[8]`（+ 溢出指针）。

### 定位过程（结合结构说明）

1. 用 `key + hash0` 算出哈希值；
2. **哈希值对桶数量取模**（实际是取低位），定位到某个基础桶 —— 注意**不包含溢出桶**，只在 `2^B` 个基础桶里定位；
3. 取哈希值的**高 8 位**作为 `tophash`，在桶内**逐个比对 `tophash`** 做初步筛选；
4. `tophash` 命中后，再用 **key 做精确比对**（`tophash` 相同不代表 key 相同）；
5. key 匹配成功，按相同下标从 `values` 中取出 value。

### 冲突解决：开放寻址 + 溢出桶链

> **每个桶可存 8 个元素。发生冲突时，从桶内第 1 个位置开始往后找空位；
> 桶内 8 个位置都满了，就挂一个"溢出桶"继续找，直到找到空位。**

查找时同理：先算桶定位 → 比 `tophash` 初筛 → 比 key 精确匹配 →
不匹配就顺着溢出桶链继续找。

**关键点**：`tophash` 相同时 **key 不一定相同**，所以必须再做一次 key 比对才能确认命中。

### 面试官会追问什么

- **tophash 的作用是什么？** → 用 1 字节的哈希高位做**快速初筛**，避免对每个槽位都做完整的 key 比较（尤其是 key 是长字符串时）。
- **什么是渐进式扩容？** → 当负载因子过高（或溢出桶过多）时扩容为 2 倍，且**不是一次性搬运**：
  每次读写操作顺带搬迁一到两个桶，避免大 map 扩容时卡顿。
- **map 是线程安全的吗？** → 不是，见分册 02 相关题目。
- **map 的 key 有什么类型限制？** → **必须是可比较类型**（支持 `==`）：
  可以 bool/数值/字符串/指针/接口/包含上述字段的 struct、数组；
  **不可以是 slice、map、func**（它们只能和 `nil` 比较，不可比较）。

## Q2. map 什么时候触发扩容？两种扩容方式有什么区别？

**来源**：`p=12` 百度 Go 后端一面 · 时长 9分20秒
**考察意图**：三个递进问题——**为什么要扩容、什么时候扩容、扩容方式**。能答出"等量扩容"就超过大部分人。

### 先回答"为什么要扩容"

扩容的本质是为了**保证 map 的查找效率**。看反例：

> 如果桶内 8 个位置全满，数据都堆在溢出桶里，查找就变成
> "遍历 8 个 → 顺着链表找下一个溢出桶 → 再遍历 8 个 → 再 8 个……"
> 这和**顺序遍历所有 key** 的效率差不多，**快速定位的意义就没了**。

所以一旦结构"不紧凑"，就必须整理/扩容。

### 触发扩容的两个条件

前置条件：**当前 map 不处于正在扩容的过程中**（扩容是**渐进式**的，不是一瞬间完成，
所以要检查是否已在扩容中）。

在非扩容状态下，满足**任一**条件就触发：

#### 条件一：负载因子超标

```
负载因子 = count / 2^B >= 6.5
```

- 每个桶最多存 8 个元素；
- 如果**平均每个桶的元素个数 ≥ 6.5**，说明空间快用完了，需要更多空间。

**举例验证**：

| count | B | 桶数 `2^B` | 负载因子 | 是否扩容 |
|---|---|---|---|---|
| 20 | 2 | 4 | 20/4 = 5.0 | 否 |
| 24 | 2 | 4 | 24/4 = 6.0 | 否 |
| 26 | 2 | 4 | 26/4 = **6.5** | ✅ **触发** |

**扩容方式：双倍扩容**。因为扩容操作的是 `B`（`B = B + 1`），桶数 = `2^B`，
所以每次扩容桶数**翻倍**。

#### 条件二：溢出桶过多

判断规则分两段（`B` 是桶数的对数）：

| `B` 的取值 | 判断条件 |
|---|---|
| `B <= 15` | 溢出桶数量 **≈ 基本桶数量**（`2^B`） |
| `B > 15` | 溢出桶数量 `>= 2^15` |

**为什么"溢出桶过多"时负载因子反而没超标？**

这其实是**频繁删除造成的结构碎片化**：

> 正常情况下，只有基本桶放满了（8 个）才会往溢出桶写数据。
> 4 个基本桶 × 8 = 32 个元素，负载因子早就超过 6.5 了。
> **所以溢出桶过多却负载没超标，只有一个解释：这些位置上的 key-value 被大量删除了。**

后果：查找/找空位时会**大量遍历到已删除的无效位置**，并频繁跑到溢出桶里去找，效率急剧下降。

**扩容方式：等量扩容（`B` 不变）**。
本质是**内存整理**——把溢出桶里的数据**挪到基本桶中被删除的空位上**，
让整个结构重新紧凑起来。理论上所有数据都放得回基本桶，查找时就能基本只走基本桶。

### 两种扩容方式对比

| | 双倍扩容 | 等量扩容 |
|---|---|---|
| **触发条件** | 负载因子 ≥ 6.5 | 溢出桶过多（结构碎片化） |
| **`B` 的变化** | `B += 1`，桶数翻倍 | `B` 不变，桶数不变 |
| **目的** | 增加空间 | 整理碎片 |
| **典型场景** | 大量插入 | 大量删除后又插入 |

### 面试官会追问什么

- **负载因子为什么是 6.5 而不是 8？** → 留出余量。取 8 会导致大量写入直接落到溢出桶，
  6.5 是在"空间利用率"和"溢出桶概率"之间的经验平衡。
- **扩容是原子的吗？** → 不是，**渐进式扩容**：每次读写操作顺带搬迁 1~2 个桶，
  避免大 map 扩容时长时间卡顿（STW）。
- **扩容期间读写怎么定位数据？** → 同时保留新旧两个桶数组，写操作只写新数组，
  读操作先查新、再查旧。
