## Q1. Channel 的底层结构与数据收发流程

**来源**：`p=13` 百度 Go 后端一面 · 时长 7分20秒
**考察意图**：很多人只会用 channel，答不上 `sendq` / `recvq` / `sudog`——这题专治"只会用不懂原理"。

### 底层结构（`hchan` 关键字段）

channel 按是否有缓冲区分为**有缓冲**和**无缓冲**两类，主要字段如下：

| 字段 | 含义 | 是否只服务于有缓冲 |
|---|---|---|
| `qcount` | 缓冲区中**当前已缓冲的数据个数** | ✓ |
| `dataqsiz` | 缓冲区**容量**（`make(chan T, n)` 中的 `n`） | ✓ |
| `buf` | 缓冲区数组，**指向存储数据的数组** | ✓ |
| `sendx` | **下一次发送**要写入的下标位置 | ✓ |
| `recvx` | **下一次接收**要读取的下标位置 | ✓ |
| `recvq` | **接收等待队列**（阻塞的接收协程） | 通用 |
| `sendq` | **发送等待队列**（阻塞的发送协程） | 通用 |

### ⚠️ 一个常见误解：`buf` 是数组，不是环形链表

很多资料把 channel 的 `buf` 说成"环形队列"，容易让人以为是**首尾相接的链表**。

**实际上 `buf` 就是一个普通数组**，只是在**逻辑使用上**呈环状：

> 遍历到最后一个元素后，下一个元素**放回数组最前面**，从而构成"环"。

### `sendx` / `recvx` 如何构成环

- **`sendx`**：下一个数据发送到哪个位置。channel 为空时发送，`sendx` 指向 `0`；
  发送完成后 `sendx++`；到达末尾后回到 `0`。
- **`recvx`**：接收侧的对应索引，逻辑相同。

### 阻塞协程去了哪里：`sendq` / `recvq` + `sudog`

**什么时候阻塞**：
- **发送**时若缓冲区没空间，且没有等待中的接收协程 → 发送协程阻塞；
- **接收**时若没有正在发送的协程，且缓冲区没数据 → 接收协程阻塞。

**阻塞后怎么处理**：

```
阻塞的协程 → 被封装成 sudog → 放入对应队列
  发送阻塞 → sendq
  接收阻塞 → recvq
```

`sendq` / `recvq` 内部是**链表结构**：`first` 指向队列头元素，`last` 指向队尾。
当条件就绪时，会根据队列里的 `sudog` 去**激活**对应协程。

### 数据收发流程（先忽略缓冲区，最清晰）

**情况 A：发送时，`recvq` 里有等待的接收协程**

```
1. 从 recvq 取出一个 sudog
2. 直接把当前要发送的数据复制给它（数据不经缓冲区）
3. 双方协程都可以继续往下执行
```

**情况 B：发送时，`recvq` 为空**

```
1. 当前协程被封装成 sudog，放入 sendq 等待
2. 后续有接收协程来接收时：
   - 先检查自己的 recvq（为空）
   - 于是从 sendq 中取出一个等待发送的 sudog
   - 把 sudog 里的数据与当前接收协程做交换
   - 接收协程拿到数据立即继续执行
   - 被取出的发送协程也随即被激活
```

**核心思路**：**优先"直接配对交接"，其次才走缓冲区**。
这也是 Go "用通信共享内存"语义在实现层面的体现——
**发送方和接收方直接对接，数据不落地**，效率最高。

### 面试官会追问什么

- **有缓冲和无缓冲的区别？** → 无缓冲（`dataqsiz = 0`）要求收发**同时就绪**才能完成，
  即**同步交接**；有缓冲则允许发送方先写入缓冲就返回，是**异步**的。
- **关闭 channel 后再发送会怎样？** → panic（`send on closed channel`）；
  接收方则会立刻读到零值且 `ok = false`。
- **"向已关闭的 channel 发送"和"重复关闭"分别什么后果？** → 都是 panic。
- **怎么优雅地关闭多个生产者共享的 channel？** → 生产方统一用 `sync.WaitGroup` 收敛后由**单一协程**关闭，
  消费方只负责 `range` 读空。（对应分册 02 的 channel 通信六案例）

## Q2. （补充）channel 的并发安全靠什么？缓冲区怎么"总是新鲜的"？

**来源**：`p=64` 字节跳动一面 · 时长 6分15秒
**说明**：Q3（`p=13`）讲的是 channel 的**字段与收发流程**，本题补充两个更贴近"实现机制"的点——
**并发安全性的来源**与**缓冲区被及时填补的机制**。

### 一、channel 为什么是并发安全的：就靠那把锁

`hchan` 结构里有一个关键字段 —— **`lock`（互斥锁）**。

> **channel 虽然可以被多个协程并发访问，但同一时刻只有一个协程是"活动"的**——
> 不管它是读还是写。其他协程**都无法操作**。
>
> **这就是 channel 并发安全的根本原因。**

**顺带一个对照**：这也解释了为什么 channel 和 `sync.Mutex` 一样"内部都有锁"，
而 `atomic` 是**无锁化**的——对应分册 02 的"协程间通信五法"。

### 二、`sendx` / `recvx` 与 buf 的关系（再次强调那个误解）

| 字段 | 含义 |
|---|---|
| **`buf`** | **缓冲区数组**，大小由 **`dataqsiz`** 指定（`make(chan T, n)` 里的 `n`） |
| **`qcount`** | 缓冲区里**已填充元素的个数** |
| **`sendx`** | **下一次数据插入的位置** |
| **`recvx`** | **下一次读取的位置** |

**类比理解**：
> 缓冲区当前填满了、下一个位置是 `1` → 那 `sendx` 就是 `1`；
> 接收方刚接收完、下一个要读的位置是 `0` → 那 `recvx` 就是 `0`。

**⚠️ 再次澄清那个常见误解**：

> **`sendx` / `recvx` 只对有缓冲的 channel 有意义。**
> 而且 —— **`buf` 本身是数组，不是链表，结构上也不是环形**；
> 之所以叫"环形队列"，是因为**通过这两个索引的取模回绕，在使用上构造出了一个环**。
>
> **它并不是"结构是环形的"，而是"用起来像环"。**

### 三、无缓冲时的收发逻辑（双方直接对接）

**发送方要发数据**：

```
① 检查 recvq（接收等待队列）里有没有协程正在等接收
   ├─ 有 → 直接从 recvq 取出一个 sudog，把数据交给它 → 双方都完成 ✅
   └─ 无 → 当前协程被封装成 sudog，推送到 sendq，并阻塞
            （★ 阻塞后不占用 CPU 资源）
```

**接收方要收数据**：

```
① 检查 sendq（发送等待队列）里有没有正在等待发送的协程
   ├─ 有 → 从链表里取出一个 sudog，把数据接收过来 → 并激活那个被阻塞的发送协程 ✅
   └─ 无 → 把自己封装成 sudog 放入 recvq，阻塞等待
```

**核心思路**：**优先"直接从对方的等待队列里取出、当场配对交接"**，
**数据不落地**——这是最高效的路径。

### 四、有缓冲时：为什么缓冲区"总是新鲜的"

**读写顺序**：**优先使用缓冲区**（发送先看缓冲区有没有空位，接收先看缓冲区有没有数据）；
**只有缓冲区满/空时**，才退回到上面那套"阻塞 + 排队"的逻辑。

**⭐ 一个值得单独记的机制 —— 缓冲区会被及时填补**：

```
接收方从缓冲区取走一个 → 缓冲区空出一个位置
        ↓
立刻从 sendq（或 recvq）里取出一个协程，
把这个位置填补上
```

> **效果：缓冲区里的数据不会"一直不动"**——
> 只要有等待的协程，**空出来的位置马上就会被新数据填上**。
>
> 这保证了 **FIFO 语义**：先到的数据先被取走，后到的补位，
> **不会出现"老数据一直占着位置而新数据进不来"的情况**。

### 面试官会追问什么

- **channel 是"无锁"的吗？** → 不是，`hchan` 里有 `lock` 互斥锁；
  只是在无竞争时开销很低。
- **nil channel 读写会怎样？** → **永久阻塞**（且不会 panic）——
  这也是 `select` 里禁用某个分支的常用技巧（把对应 channel 置为 nil）。
- **为什么 `close` 之后还能读出缓冲区剩余数据？** →
  关闭只是禁止再写入并唤醒等待者，**`qcount` 里已有的数据仍会被正常读出**，
  读完后 `recvx == sendx` 才返回零值 + `ok=false`。

## Q3. 用 channel 通信的 6 个典型案例

**来源**：`p=6` 滴滴 Go 后端一面 · 时长 7分52秒
**考察意图**：channel 的用法是否能覆盖真实工程场景，而不是只会 `ch <- x` / `<-ch`。

### 案例 1：基本数据传递（生产者 → 消费者）

```go
ch := make(chan int)
go func() { for i := 0; i < 10; i++ { ch <- i }; close(ch) }()
for v := range ch { fmt.Println(v) }   // close 后 range 自动结束
```
要点：**生产完关闭 channel**，主协程通过 `range` 感知关闭状态并退出循环。

### 案例 2：信号传递 + 同步等待

场景：启动 3 个协程执行任务，需要等待全部完成。
做法：主协程从 channel 中**读取 3 次信号**，收到 3 个才算全部完成。
这是"同步等待"同时也是"信号传递"——`sync.WaitGroup` 的等价手写实现。

### 案例 3：生产者-消费者模式（双 channel）

需要**两个 channel**：
1. `dataCh`：传递生产的数据；
2. `doneCh`（关闭信号）：通知主协程进入下一步。

要点：消费者**没有天然的退出机制**，必须等生产者生产完毕、`dataCh` 被 `close` 之后
（`range dataCh` 结束）才能退出消费循环。

### 案例 4：用信号量限制并发数

用一个**缓冲区为 N 的 channel** 做信号量：容量 2 表示最多允许 2 个任务同时执行。
- 写入 = **获取**一个许可（缓冲满则阻塞）；
- 读出 = **释放**一个许可。

```go
sem := make(chan struct{}, 2) // 并发上限 2
sem <- struct{}{}             // 获取
defer func() { <-sem }()      // 释放
```

启动 5 个协程时，会有 3 个阻塞在写入上，直到前面的任务释放。

### 案例 5：用 channel 控制超时

```go
select {
case res := <-workCh:
    fmt.Println("完成:", res)
case <-time.After(2 * time.Second):
    fmt.Println("超时")     // 2 秒未完成走超时逻辑
}
```

`time.After` 返回的 channel 在指定时间后变得可读，与业务 channel 一起放进 `select` 即可实现超时。

### 案例 6：用 `close` 广播通知多个协程

**核心机制**：channel **关闭后**，所有阻塞在读取上的协程**都会立刻解除阻塞**（读到零值 + `ok=false`），
从而实现"一对多广播"，而不需要发 N 次信号。

```go
stopCh := make(chan struct{})
for i := 0; i < 5; i++ {
    go func(id int) {
        select {
        case <-stopCh:
            return          // 收到广播，直接退出
        case <-doSomething():
        }
    }(i)
}
close(stopCh)   // 5 秒后广播中止信号，5 个协程同时感知
```

**这是 `close` 与"发送 N 次"的本质区别**，也是 `context` 取消传播的底层机制。

## Q4. 能不能先判断 channel 是否阻塞，再写入数据？

**来源**：`p=46` 深信服 Go 面试 · 时长 7分00秒
**考察意图**：这是一道**边界细节题**，能答出"只有 select + default 这一个点可以"就很强。

### 结论先行

> **在编程层面，我们无法"先判断它是否阻塞，再写入"。**
>
> 但 **channel 底层实现里确实提供了类似的判断逻辑**——
> **只存在于一个地方：多路复用（`select`）且带 `default` 子句时**（即**非阻塞模式**）。

### 一、常规写入：没有事前判断

```go
ch <- data   // 要么成功，要么阻塞，要么 panic（已关闭）
```

**普通 channel 读写只能"事后看结果"，没有事前判断**：
- 写成功 ✅
- 写不成功 → **要么阻塞**（等接收方），**要么 channel 已关闭**（panic）

> 我**不能**先问一句"现在能写吗？"，**不存在这种写法，也不存在这种返回值**。

### 二、唯一的例外：`select` + `default`

```go
select {
case ch1 <- v:          // 能写就写
    // 写成功了
case ch2 <- v:
    // 写成功了
default:
    // ★ 前面都写不进去 —— 尝试过但没写成功，于是不写了
}
```

**注意措辞的准确性**：这不是"**先判断**能不能写"，
而是"**尝试写，写不进去就走 default**"——
**本质是尝试后失败，而不是事前询问**。

⚠️ **反例：如果 `select` 没有 `default` 子句**

```go
select {
case ch1 <- v:   // 若 ch1 写不进去
case ch2 <- v:   // 若 ch2 也写不进去
}
// 没有 default → 两个都写不进去就永久阻塞
```

原视频演示：放入 10 次，但 channel 空间有限且**没有读取的协程**
→ 填满之后直接**死锁**（`fatal error: all goroutines are asleep`）。

### 三、从底层 `chansend` 看"能写成功"的四个快路径

`runtime` 包的 `chansend` 返回一个 **bool 值**表示**本次发送是否成功**。
只有 **`block == false`（非阻塞模式，即 `select` + `default`）** 才会返回 `false`，
阻塞模式下则直接挂起。

**非阻塞模式下的四条"能立刻成功"的快路径**：

| # | 判断条件 | 结果 |
|---|---|---|
| **①** | **`recvq` 非空**（有协程在等我发数据） | 直接把数据交给它 → **成功**。<br>注意：接收队列非空说明**缓冲区必然为空**——因为如果有数据，接收协程早就取走了 |
| **②** | **`qcount < dataqsiz`**（缓冲区没满） | 直接写入缓冲区 → **成功**（一定能写入，所以也算非阻塞） |
| **③** | **channel 未初始化（nil）** | 非阻塞模式 → **返回 `false`**；阻塞模式 → **阻塞** |
| **④** | **channel 已关闭** | 非阻塞模式 → **返回 `false`**；阻塞模式 → **抛异常（panic）** |

**①② 都不满足，且不是 ③④ 的情况（缓冲区满、也没有等待的接收方）**：
- **非阻塞模式** → **返回 `false`**，于是命中 `select` 的 `default` 分支；
- **阻塞模式** → 把当前协程**包装成一个 `sudog`，加入 `sendq`（发送等待队列）并挂起**。
  代码就停在这里，**只有接收流程来激活它才会继续往下走**。

### 四、一句话总结

> **`channel` 只有"写成功 / 写失败"两种结果，没有"事前判断是否阻塞"的 API。**
> **唯一的擦边球是 `select` + `default`**——它是"**尝试写入，写不进去就走 default**"的
> **非阻塞模式**，靠的是底层 `chansend` 在 `block=false` 时**返回 bool** 这个机制。
> **除此之外任何情况都做不到"先判断再写"。**

### 面试官会追问什么

- **为什么 `select` + `default` 能"不阻塞"？** → 因为编译器会把它编译成
  `chansend(c, v, false, ...)`，**`block=false` 表示"能写就写，不能写就返回 false"**。
- **`select` 多个 case 同时就绪会怎样？** → **随机选一个**执行，
  这是 Go 刻意设计的，避免某些 channel 被"饿死"。
- **怎么优雅地做"带超时的写入"？** →
  `select { case ch <- v: case <-time.After(d): }`——
  注意 `time.After` 会创建定时器，高频场景建议用 `time.NewTimer` 并复用/停止。
