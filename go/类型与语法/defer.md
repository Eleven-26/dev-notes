## Q1. defer 有哪些特性？多个 defer 的执行顺序是什么？

**来源**：`p=38` 百度 Go 后端开发二面 · 时长 10分14秒
**考察意图**：**从特性推应用场景**——特性记住了，场景自然就能举例。

### 一、三个特性（先记这个）

| # | 特性 | 说明 |
|---|---|---|
| **①** | **标记函数延迟调用** | `defer` 用来**标记一个函数**，表示它**要被延迟调用** |
| **②** | **在 `return` 之后执行** | 例：打开文件后用 `defer` 标记关闭函数 → 它会在函数 `return` 之后执行 |
| **③** | **不会被 `panic` 打断** ⭐ | 即使主流程发生 panic、应用程序要中断，<br>**也会先把 `defer` 标记的函数执行完，再中断应用程序** |

### 二、两个好处

1. **资源打开与关闭成对出现**——文件打开/关闭、互斥锁加锁/解锁，
   **编码时就不会忘记释放资源**，代码更健壮；
2. **保证某些逻辑一定会被执行**——无论报错还是不报错（因为 panic 不会打断 defer）。

### 三、三个典型应用场景（都由特性衍生）

| 场景 | 说明 |
|---|---|
| **① 异常捕获与处理** | `defer` + `recover`——**因为 defer 不会被打断**，所以可以在 defer 里 recover，<br>拿到 panic 抛出的错误信息，完成异常捕获与处理 |
| **② 资源释放** | 文件关闭、互斥锁/读写锁解锁 |
| **③ 业务/流程相关** | • `defer wg.Done()` 配合 WaitGroup 递减计数<br>• **记录函数执行耗时**：进入时记 `startTime`，退出时在 defer 里算耗时 |

### 四、多个 defer 的执行顺序：LIFO（后进先出）

**从源码看**（`runtime/panic.go`）：

**第一步：`deferproc` —— 把 defer 挂到协程的 defer 链表上**

```
编译期：编译器根据代码里的 defer 标记，挨个创建对应的 defer 结构体
        ↓
运行时：得到 defer 结构对象 d
        ↓
把「当前协程已有的 defer 链表」挂到 d.link 后面
        ↓
把 d 放到链表的最前端
```

> **每来一个新的 defer，都放到链表最前面。**

**第二步：`deferreturn` —— 触发 defer 调用**

```
编译期：凡函数里含 defer 关键字，编译器都会在函数结尾（return 处）
        插入对 deferreturn 的调用
        ↓
运行时：deferreturn 从前往后遍历 defer 链表并逐个调用
```

**结论**：

> **`defer` 看似是栈结构，实际上是一条链表**——
> 因为**后加入的会被放到链表最前面**，所以执行顺序是
> **后进先出（LIFO）**：**最后注册的 defer 最先执行**。

**⚠️ 顺带提醒**：`defer` 的参数在**注册时**就求值（不是执行时），
所以 `defer f(x)` 里的 `x` 是当时的值——这是很常见的坑。
