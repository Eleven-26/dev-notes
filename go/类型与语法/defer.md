## 一、defer 有哪些特性？多个 defer 的执行顺序是什么？

**来源**：`p=38` 百度 Go 后端开发二面 · 时长 10分14秒

**考察意图**：**从特性推应用场景**——特性记住了，场景自然就能举例。

### 一、三个特性（先记这个）

| # | 特性 | 说明 |
|---|---|---|
| **①** | **标记函数延迟调用** | `defer` 用来**标记一个函数**，表示它**要被延迟调用** |
| **②** | **在 `return` 之后执行** | 例：打开文件后用 `defer` 标记关闭函数 → 它会在函数 `return` 之后执行 |
| **③** | **不会被 `panic` 打断** ⭐ | 即使主流程发生 panic、应用程序要中断，<br>**也会先把 `defer` 标记的函数执行完，再中断应用程序** |

### 二、两个好处

1. **资源打开与关闭成对出现**——文件打开/关闭、互斥锁加锁/解锁，
   **编码时就不会忘记释放资源**，代码更健壮；
2. **保证某些逻辑一定会被执行**——无论报错还是不报错（因为 panic 不会打断 defer）。

### 三、三个典型应用场景（都由特性衍生）

| 场景 | 说明 |
|---|---|
| **① 异常捕获与处理** | `defer` + `recover`——**因为 defer 不会被打断**，所以可以在 defer 里 recover，<br>拿到 panic 抛出的错误信息，完成异常捕获与处理 |
| **② 资源释放** | 文件关闭、互斥锁/读写锁解锁 |
| **③ 业务/流程相关** | • `defer wg.Done()` 配合 WaitGroup 递减计数<br>• **记录函数执行耗时**：进入时记 `startTime`，退出时在 defer 里算耗时 |

### 四、多个 defer 的执行顺序：LIFO（后进先出）

**从源码看**（`runtime/panic.go`）：

**第一步：`deferproc` —— 把 defer 挂到协程的 defer 链表上**

```text
编译期：编译器根据代码里的 defer 标记，挨个创建对应的 defer 结构体
        ↓
运行时：得到 defer 结构对象 d
        ↓
把「当前协程已有的 defer 链表」挂到 d.link 后面
        ↓
把 d 放到链表的最前端
```

> **每来一个新的 defer，都放到链表最前面。**

**第二步：`deferreturn` —— 触发 defer 调用**

```text
编译期：凡函数里含 defer 关键字，编译器都会在函数结尾（return 处）
        插入对 deferreturn 的调用
        ↓
运行时：deferreturn 从前往后遍历 defer 链表并逐个调用
```

**结论**：

> **`defer` 看似是栈结构，实际上是一条链表**——
> 因为**后加入的会被放到链表最前面**，所以执行顺序是
> **后进先出（LIFO）**：**最后注册的 defer 最先执行**。

## 二、书里点名的四个 defer 陷阱（实测）

**来源**：本节为补充内容 —— 按《Go 语言核心编程》（李文塔）2.3 defer、7.3 defer 陷阱 整理，配套本机实测。

**考察意图**：defer 的**第二层**。上一节是「特性与顺序」，这一节是「**它在哪里反直觉**」。四个陷阱都能说出**为什么**（而不是「记得别这么写」）才算过关 —— 它们全部由上一节第三条推出来：**`return` 不是原子操作、defer 参数在注册时求值、defer 只认函数返回（不认进程退出）**。

### 一、陷阱 ①：参数在「注册时」求值，不是执行时

```go
x := 1
defer fmt.Println("参数在注册时求值 : 打印", x)   // 此刻就把 x 的当前值拷进去了
x = 2
```

```text
   注册后 x 改成 2，但上面那行仍打印 1
1_参数在注册时求值   : 打印 1 (注册时 x=1)
```

> ⚠️ 想拿到**最终值**，必须用闭包（闭包捕获的是变量，不是当时的值）：
> `defer func() { fmt.Println(x) }()` —— 这样才打印 2。
> 参数求值时机和闭包捕获变量，是 defer 最容易被混为一谈的两个点。

### 二、陷阱 ②：想改返回值，必须用「命名返回值」

三种写法对照（同一份逻辑，只改签名）：

```go
func anonReturn() int {          // 匿名返回值
    r := 0
    defer func() { r = 100 }()
    return r                     // defer 改的是局部变量 r，返回槽里已经拷进了 0
}

func namedReturn() (r int) {     // 命名返回值
    defer func() { r = 100 }()
    return r                     // 返回槽就是 r 本身，defer 改的正是它
}

func namedReturnLiteral() (r int) {
    defer func() { r = 100 }()
    return 5                     // ⭐ 先把 5 写进 r，再跑 defer 改成 100
}
```

```text
2a_匿名返回值        : 0 (defer 改的是局部副本，返回仍是 0)
2b_命名返回值 return r: 100 (返回槽被 defer 改成 100)
2c_命名返回值 return 5: 100 ⭐ 不是 5——先赋值给返回槽，再被 defer 覆盖
```

> ⭐ **2c 是这组的重点**：`return 5` 不是「直接返回 5」，而是三步 ——
> **①把 5 写进命名返回值 `r` → ②执行 defer（改成 100）→ ③返回 `r`**。
> 记住这三步，同时解释了 2a、2b、2c 三行结果。也是「`defer` 能改返回值」这条结论的**唯一正确解释**。

### 三、陷阱 ③：循环里的 defer 全部堆到「函数返回」才跑

```go
order := []int{}
for i := 0; i < 3; i++ {
    defer func() { order = append(order, i) }()   // 每轮都注册，但一轮都不执行
}
fmt.Println("循环结束时的顺序数组:", order)          // 此刻 3 个 defer 都没跑
```

```text
3a_循环结束时的顺序数组: [] (3 个 defer 一个都还没跑)
3b_内层循环跑完了        : 但两个 defer 都还没执行
3d_循环里注册的 defer   : i = 1 (堆到内层返回才跑，LIFO)
3d_循环里注册的 defer   : i = 0 (堆到内层返回才跑，LIFO)
3c_内层函数返回时才执行  : inner 结束
```

> ⚠️ 读法：3a 是**外层函数**、3b～3d 是另一个**内层函数** —— 两个层次都在证明同一件事：
> **循环结束时代码已经跑完了，defer 却一个都还没执行**；它们全部堆到**函数返回**那一刻，再按 **LIFO** 依次跑。
>
> 真实危害不是"顺序不对"，而是**资源不释放**：循环里 `defer f.Close()` 处理 10000 个文件 → 10000 个句柄要等到函数返回才关，
> 中途就 `too many open files` 了。这也是它成为最高频误用的原因，改法见文末「使用」节。

### 四、陷阱 ④：`os.Exit` / `log.Fatal` 不执行 defer

```go
defer fmt.Println("这一行永远不会执行")
os.Exit(0)
```

```text
4_准备 os.Exit(0)，defer 会被跳过（本行之后的输出不该出现）
```

> 原因：`os.Exit` **直接终止进程，不经过栈展开**，`runtime` 根本没机会跑 `deferreturn`。
> 所以 `main` 里用 `defer` 做收尾（关闭日志、flush 缓冲、上报指标）**在异常退出路径上一定会丢**。
> 需要保证执行就得走 `return` 回到调用方，或显式调用清理函数。

### 五、附送两个坑：recover 的作用域、defer 里再 panic

```text
5_recover 取到什么      : 嵌套调用取到 <nil> / 直接调用取到 boom
6_最终被捕获到的是     : 第二个 panic ⭐ 原 panic 被顶掉了
```

| 现象 | 原因 |
|---|---|
| 包一层匿名函数再 `recover()` → 取到 `<nil>` | `recover` **只在被 defer 的函数「直接调用」时有效**，隔了一层就失效 |
| defer 里再 `panic` → 捕获到的是**新** panic | 新 panic **覆盖**原 panic 的值，原现场丢失 → 清理逻辑要么自己 recover，要么把 error 合并进返回值 |

> 这两条和第 ④ 条合起来说明同一件事：**`defer` 只保证「函数返回时执行」，不保证「进程退出时执行」，也不保证「不改变出错现场」**。

## 面试官会追问什么

- **defer 有性能开销吗？** → 有，但 Go 1.14 起的 **open-coded defer** 把常见场景（非循环、函数体不大）降到几乎零成本；用 `-N -l` 关优化会退回堆分配版本（见 [../工程实践/编译与gcflags.md](../工程实践/编译与gcflags.md)）。
- **在循环里写 defer 会怎样？** → 不是在每轮结束时执行，而是**全部堆到函数返回**才依次执行——循环里既慢又可能撑爆内存，这是最高频的误用。
- **defer 能改返回值吗？** → 能，但只在**命名返回值**上生效：`return` 先把值写入返回变量槽 → 执行 defer → 再真正返回，所以 defer 里改的是那个槽。
- **defer 里再 panic 会怎样？** → 会顶掉原来的 panic（recover 也救不了）；另外 `recover` 只在**当前 goroutine 的 defer 中**有效，跨协程无效。
- **为什么 `os.Exit` / `log.Fatal` 不执行 defer？** → 它们直接终止进程，不经过栈展开；需要清理逻辑时要用 `return err` 回到调用方。

## 使用：三个高频误用与改法

| 误用写法 | 现象 | 改法 |
|---|---|---|
| 在 `for` 循环里 `defer f.Close()` | 文件/连接全部堆到**函数返回**才关 → fd 耗尽、内存上涨 | 把循环体抽成**独立函数**，让 defer 在每轮返回时执行；或用 `closure` + 显式 `Close()` |
| 认为 `defer` 里改返回值一定生效 | 只有**命名返回值**能被改；匿名返回值下 defer 改的是局部副本，返回的仍是旧值 | 需要 defer 修正返回值时，把返回值**命名**；否则改用显式赋值 |
| `defer` 里执行可能 panic 的清理逻辑 | 新 panic **覆盖**原 panic，现场丢失，排障难度翻倍 | 清理逻辑自己 `recover` 并把错误转成日志/合并到返回错误里 |

**执行顺序速记**：同一函数内多个 `defer` 按**后进先出**（LIFO）执行；与 `return` 的三步关系是「**先给返回值赋值 → 再跑 defer → 最后跳回调用者**」，这也是「命名返回值能被 defer 改」的由来。

**性能判断**：

- Go 1.14+ 对「非循环、函数体不大」的 defer 做 **open-coded** 优化，开销几乎可以忽略；
- 用 `-N -l` 关掉优化（调试场景）时会退回堆分配版本，此时**不要拿调试版本的性能去推断线上**（见 [../工程实践/编译与gcflags.md](../工程实践/编译与gcflags.md)）。
