## 一、Map 为什么会有哈希冲突？Go 是怎么解决的？

**来源**：`p=14` 百度 Go 后端一面 · 时长 9分24秒
**考察意图**：从"为什么需要哈希"推演到"冲突不可避免"，再讲到 Go 的具体实现——考的是**推理链条**。

### 先回答"为什么会冲突"

假设我们要存 key-value：

- **用数组存**：靠"索引 + 地址偏移量"直接定位，**不可能有冲突**，但前提是**按下标访问**；
- **用"key 数组"存**：必须**循环遍历逐个比对 key** 才能找到目标——这是效率最差的做法。

map 存在的意义，就是让 **key 起到"索引"的作用**，快速定位 value。做法是：

> 用 **哈希函数把 key 映射到一个固定的区域**，直接跳到那个区域去找，跳过遍历。

**冲突正是这个优化的代价**：哈希值空间远大于桶的数量，必然出现"不同的 key 落到同一个位置"。
**如果不做任何优化（老老实实遍历比对），是不会有哈希冲突的——因为 key 本身是唯一的。**

### Go map 的底层结构（`hmap`）

需要关注的字段：

| 字段 | 含义 |
|---|---|
| `count` | map 中键值对的数量 |
| `B` | **以 2 为底的对数**，表示桶（bucket）的数量：`2^B` |
| `hash0` | **哈希因子**，参与哈希计算。它的作用是让**相同的 key 在不同 map 实例中得到不同的哈希值** |
| `buckets` | 存储 key-value 数据的桶数组，长度 `2^B` |

**容量关系**：`B=0` → 1 个桶；`B=1` → 2 个桶；`B=2` → 4 个桶。

**每个桶（bucket）可以存 8 个元素**，桶内布局为：`tophash[8]` + `keys[8]` + `values[8]`（+ 溢出指针）。

### 定位过程（结合结构说明）

1. 用 `key + hash0` 算出哈希值；
2. **哈希值对桶数量取模**（实际是取低位），定位到某个基础桶 —— 注意**不包含溢出桶**，只在 `2^B` 个基础桶里定位；
3. 取哈希值的**高 8 位**作为 `tophash`，在桶内**逐个比对 `tophash`** 做初步筛选；
4. `tophash` 命中后，再用 **key 做精确比对**（`tophash` 相同不代表 key 相同）；
5. key 匹配成功，按相同下标从 `values` 中取出 value。

### 冲突解决：开放寻址 + 溢出桶链

> **每个桶可存 8 个元素。发生冲突时，从桶内第 1 个位置开始往后找空位；
> 桶内 8 个位置都满了，就挂一个"溢出桶"继续找，直到找到空位。**

查找时同理：先算桶定位 → 比 `tophash` 初筛 → 比 key 精确匹配 →
不匹配就顺着溢出桶链继续找。

**关键点**：`tophash` 相同时 **key 不一定相同**，所以必须再做一次 key 比对才能确认命中。

### 面试官会追问什么

- **tophash 的作用是什么？** → 用 1 字节的哈希高位做**快速初筛**，避免对每个槽位都做完整的 key 比较（尤其是 key 是长字符串时）。
- **什么是渐进式扩容？** → 当负载因子过高（或溢出桶过多）时扩容为 2 倍，且**不是一次性搬运**：
  每次读写操作顺带搬迁一到两个桶，避免大 map 扩容时卡顿。
- **map 是线程安全的吗？** → 不是，见分册 02 相关题目。
- **map 的 key 有什么类型限制？** → **必须是可比较类型**（支持 `==`）：
  可以 bool/数值/字符串/指针/接口/包含上述字段的 struct、数组；
  **不可以是 slice、map、func**（它们只能和 `nil` 比较，不可比较）。

## 二、map 什么时候触发扩容？两种扩容方式有什么区别？

**来源**：`p=12` 百度 Go 后端一面 · 时长 9分20秒
**考察意图**：三个递进问题——**为什么要扩容、什么时候扩容、扩容方式**。能答出"等量扩容"就超过大部分人。

### 先回答"为什么要扩容"

扩容的本质是为了**保证 map 的查找效率**。看反例：

> 如果桶内 8 个位置全满，数据都堆在溢出桶里，查找就变成
> "遍历 8 个 → 顺着链表找下一个溢出桶 → 再遍历 8 个 → 再 8 个……"
> 这和**顺序遍历所有 key** 的效率差不多，**快速定位的意义就没了**。

所以一旦结构"不紧凑"，就必须整理/扩容。

### 触发扩容的两个条件

前置条件：**当前 map 不处于正在扩容的过程中**（扩容是**渐进式**的，不是一瞬间完成，
所以要检查是否已在扩容中）。

在非扩容状态下，满足**任一**条件就触发：

#### 条件一：负载因子超标

```text
负载因子 = count / 2^B >= 6.5
```

- 每个桶最多存 8 个元素；
- 如果**平均每个桶的元素个数 ≥ 6.5**，说明空间快用完了，需要更多空间。

**举例验证**：

| count | B | 桶数 `2^B` | 负载因子 | 是否扩容 |
|---|---|---|---|---|
| 20 | 2 | 4 | 20/4 = 5.0 | 否 |
| 24 | 2 | 4 | 24/4 = 6.0 | 否 |
| 26 | 2 | 4 | 26/4 = **6.5** | ✅ **触发** |

**扩容方式：双倍扩容**。因为扩容操作的是 `B`（`B = B + 1`），桶数 = `2^B`，
所以每次扩容桶数**翻倍**。

#### 条件二：溢出桶过多

判断规则分两段（`B` 是桶数的对数）：

| `B` 的取值 | 判断条件 |
|---|---|
| `B <= 15` | 溢出桶数量 **≈ 基本桶数量**（`2^B`） |
| `B > 15` | 溢出桶数量 `>= 2^15` |

**为什么"溢出桶过多"时负载因子反而没超标？**

这其实是**频繁删除造成的结构碎片化**：

> 正常情况下，只有基本桶放满了（8 个）才会往溢出桶写数据。
> 4 个基本桶 × 8 = 32 个元素，负载因子早就超过 6.5 了。
> **所以溢出桶过多却负载没超标，只有一个解释：这些位置上的 key-value 被大量删除了。**

后果：查找/找空位时会**大量遍历到已删除的无效位置**，并频繁跑到溢出桶里去找，效率急剧下降。

**扩容方式：等量扩容（`B` 不变）**。
本质是**内存整理**——把溢出桶里的数据**挪到基本桶中被删除的空位上**，
让整个结构重新紧凑起来。理论上所有数据都放得回基本桶，查找时就能基本只走基本桶。

### 两种扩容方式对比

| | 双倍扩容 | 等量扩容 |
|---|---|---|
| **触发条件** | 负载因子 ≥ 6.5 | 溢出桶过多（结构碎片化） |
| **`B` 的变化** | `B += 1`，桶数翻倍 | `B` 不变，桶数不变 |
| **目的** | 增加空间 | 整理碎片 |
| **典型场景** | 大量插入 | 大量删除后又插入 |

### 面试官会追问什么

- **负载因子为什么是 6.5 而不是 8？** → 留出余量。取 8 会导致大量写入直接落到溢出桶，
  6.5 是在"空间利用率"和"溢出桶概率"之间的经验平衡。
- **扩容是原子的吗？** → 不是，**渐进式扩容**：每次读写操作顺带搬迁 1~2 个桶，
  避免大 map 扩容时长时间卡顿（STW）。
- **扩容期间读写怎么定位数据？** → 同时保留新旧两个桶数组，写操作只写新数组，
  读操作先查新、再查旧。

## 三、map 是怎么创建出来的？`B` 是怎么算出来的？

**来源**：`BV12qjA6aErF p=28` B站 Go 面试真题 · 时长 10分51秒
**考察意图**：第一节 / 第二节讲的是"结构长什么样、什么时候扩"；本题聚焦**源码级流程**——
`makemap` 每一步做了什么，尤其是 **`B` 的推导**与**预估容量对 `B` 的影响**。

### 入口：`makemap(t, hint, h)`（4 步）

| 步骤 | 做什么 | 为什么 |
|---|---|---|
| ① 校验 `hint` | 溢出或超过 `maxAlloc` → **置 0** | 防止预分配把内存撑爆 |
| ② 取哈希种子 | `h.hash0 = fastrand()` | 让不同 map 实例对同一 key 得到**不同哈希值** |
| ③ 推导 `B` | `overLoadFactor(hint, B)` 为真就 `B++` | 初始桶数"装得下 hint 且负载不超 6.5" |
| ④ 分配桶 | `B != 0` → `makeBucketArray`；否则**不分配** | 只存几个元素时不必真去 malloc |

### `B` 的推导：用负载因子反推桶数

```go
B := uint8(0)
for overLoadFactor(hint, B) { B++ }   // count > 8 && count > 6.5 × 2^B
```

| `hint` | 推导过程 | 最终 `B` | 初始桶数 |
|---|---|---|---|
| 0 ~ 8 | `hint > 8` 就为假 | 0 | 1（不分配桶数组） |
| 9 ~ 13 | `> 6.5` → B=1；再判 `> 13` 为假 | 1 | 2 |
| 14 | `> 6.5` → B=1；`> 13` → B=2；`> 26` 为假 | 2 | 4 |
| 100 | 推到 `> 52` → B=4；`> 104` 为假 | 4 | 16 |

### `makeBucketArray`：真正分配桶数组

1. **基础桶数** `2^B`；`B >= 4` 时再多分配约 `1/16` 个桶作**溢出桶预留区**
   （串在 `h.extra.nextOverflow` 上，需要新溢出桶时优先取用，避免频繁 `newobject`）；
2. **内存对齐**：字节数按 size class **向上对齐到 2 的幂**，实际分配可能比"桶数 × 桶大小"更大；
3. **标记末尾**：把**最后桶的 `overflow` 指向桶数组首地址**（必然非空的哨兵值）——
   遍历时**只要发现 `overflow` 指回首地址就知道走到头了**，不必额外记录长度。

### `h.extra`：可选的溢出桶"账本"

`overflow` / `oldoverflow` 只在 **key/value 都不含指针**时使用：此时桶类型被标记为"不含指针"，
GC 扫描会**整块跳过桶内部**（性能好），但也因此**找不到这些桶对象**，必须用切片把指针**显式持有**住
——白送的好处是**迭代可以直接遍历数组**。

### 面试官会追问什么

- **`make(map[int]int, 100)` 和不带 hint 有什么区别？** → 前者把 `B` 推到 4（16 个桶），
  一开始就有空间、少扩几次容；后者 `B = 0`，**一个桶都不分配**，第一次写入时才创建。
  ⚠️ `hint` 只是"预估"，**不会**创建出 `hint` 个槽位，**传太大只会浪费内存**。
- **`hash0` 有什么用？** → 每个 map 实例一个随机种子，同一 key 在不同 map 里哈希值不同，
  攻击者**无法刻意构造"全撞进同一个桶"的 key** 打垮服务。

## 四、`hmap` 到底有哪些字段？桶（`bmap`）在内存里长什么样？

**来源**：`BV12qjA6aErF p=29` B站 Go 面试真题 · 时长 13分23秒
**来源（补充）**：`BV12qjA6aErF p=6` B站 Go 面试真题 · 时长 4分30秒
**考察意图**：本篇聚焦**字段级全景**。第一节只讲了 `count` / `B` / `hash0` / `buckets`，
这里把 `flags` / `noverflow` / `oldbuckets` / `nevacuate` / `extra` 补齐。

### `hmap` 全字段

| 字段 | 含义 |
|---|---|
| `count` | key-value 的**个数**（`len(m)` 返回的就是它） |
| `flags` | **标志位**（位图），关键位是 `hashWriting` |
| `B` | 桶数的对数，基础桶数 = `2^B`（**不含**溢出桶） |
| `noverflow` | 溢出桶数量，**只是近似值**，只服务于扩容判断 |
| `hash0` | 哈希种子 |
| `buckets` | 指向桶数组，长度 `2^B` |
| `oldbuckets` | **扩容前的旧桶数组**，只在扩容期间非 nil |
| `nevacuate` | **疏散进度计数器** |
| `extra` | 可选扩展字段 `*mapextra` |

**`flags` 里的 `hashWriting` 就是那句著名报错的来源**：写流程开始前先检查这一位，发现已置起 →
`fatal error: concurrent map writes`（读写并发则是 `concurrent map read and map write`）。
⚠️ 它是**检测**而非**保护**：runtime 只是"逮到就崩"，**并不会加锁**。

**`oldbuckets` / `nevacuate`**：扩容渐进式，新旧两套桶并存。`oldbuckets` 指向旧数组
（双倍扩容时长度只有新数组的**一半**，即 `2^(B-1)`）；`nevacuate` **只保证"索引小于它的桶已搬迁"**
——搬迁由访问驱动、顺序是乱的，**索引大于它的桶也可能早就搬完了**（详见第六节）。

### `bmap`：为什么结构体里只看到一个 `tophash`？

源码里 `bmap` **只定义了 `tophash [8]uint8` 一个字段**，内存里实际是四段：
`tophash[8]` → `keys[8]` → `elems[8]`（value）→ `overflow` 指针。

> `keys` / `elems` / `overflow` 是**编译期动态追加**的——key / value 的类型和大小由**具体 map 决定**，
> 写不进结构体定义，runtime 靠**固定的地址偏移**访问它们。
> 这解释了"为什么源码里 `bmap` 找不到 value 和溢出指针"。

**顺带回答：map 为什么天生不是线程安全的？**

> **`hmap` 里没有任何和锁相关的字段。**

桶数组本质上是**数组**：**并发写同一个数组的不同元素**会让各协程的写入**互相覆盖**
（错乱但不报错）。所以要并发用只能加 `sync.RWMutex`、用 `sync.Map`（读多写少）、
或**用 channel 收敛写入**。

### 面试官会追问什么

- **`len(m)` 为什么是 O(1)？** → 直接读 `h.count`，不需要遍历。
- **`noverflow` 是精确值吗？** → 不是，它是近似值（`uint16`，超过阈值后只做估算）。
- **无指针的 map 为什么更快？** → 桶类型标记为"不含指针"，GC 扫描**可以整块跳过**，
  溢出桶指针又集中放在 `extra.overflow` 里，扫描成本更低。
- **map 是并发安全的吗？** → 不是。`hmap` 里没有任何锁字段，
  并发写会导致数据被互相覆盖，运气不好被 runtime 检测到就直接 `fatal`。

## 五、`m[k]` 的读和 `m[k] = v` 的写，在底层分别做了什么？

**来源**：`BV12qjA6aErF p=30` B站 Go 面试真题 · 时长 13分11秒
**考察意图**：本篇聚焦**源码级流程**：`mapaccess1/2` 与 `mapassign` 的完整路径，
尤其是**扩容中的双桶查找**与 **`emptyRest` 提前终止扫描**这两个优化。

### 编译产物：读走 `mapaccess`，写走 `mapassign`

`v := m[k]` → `mapaccess1`、`v, ok := m[k]` → `mapaccess2`、`m[k] = v` → `mapassign`、
`delete(m, k)` → `mapdelete`。其中**读写都返回 value 的指针**——
所以 `m[k] = v` 的语义是"找到 value 的**槽位地址**，把 `v` 拷进去"。

### 共同的前置检查

```text
① h == nil？ 读 → 返回零值（读 nil map 合法）；写 → fatal("assignment to entry in nil map")
② h.flags & hashWriting != 0？ 写 → fatal("concurrent map writes")
                              读 → fatal("concurrent map read and map write")
③ hash = t.Hasher(key, h.hash0)   ⚠️ 必须在"置起 hashWriting 标记"之前算——
                                  哈希计算本身可能 panic，标记一旦置起就永远留在那里
④ h.buckets == nil → 说明 B == 0，第一次写入时才创建首个桶
```

### 定位：低位定桶，高 8 位定槽

`桶索引 = hash & (2^B - 1)`（相当于 `hash % 2^B`，取**低位**）、
`tophash = hash >> (64 - 8)`（取**高 8 位**）。

### ⭐ 扩容中的"双桶查找"（读路径独有）

```go
b := 新桶[hash & (2^B - 1)]
if h.oldbuckets != nil {
    m := 2^B 对应的掩码
    if !h.sameSizeGrow() { m >>= 1 }        // ★ 双倍扩容：旧数组只有一半，掩码降一位
    oldb := 旧桶[hash & m]
    if !evacuated(oldb) { b = oldb }        // ★ 旧桶还没搬走 → 数据还在旧的里面
}
```

- 双倍扩容时旧数组长度是 `2^(B-1)`，掩码要**右移一位**（等价于忽略哈希的最高位）；
- **旧桶没打上 `evacuated*` 标记，就查旧桶**——搬迁是渐进的，key 可能还在里面；
- **写路径不这么做**：`mapassign` 先 `growWork` 把当前桶搬完，然后一律写新桶。

### 桶内扫描：两层循环 + `emptyRest` 提前终止

```text
外层：沿溢出桶链逐桶（b = b.overflow）
  内层：桶内 8 个槽位 i = 0..7
    ① 取 b.tophash[i]：与本 key 的 tophash 相等 → 用 key 做**精确比较**
         ├─ key 相等 → 命中 ✅
         └─ key 不等 → 继续（★ tophash 相同 ≠ key 相同）
    ② 遇到空槽 → 记下"第一个可用空位"（供写入时落位）
    ③ 遇到 emptyRest → ★ 立刻跳出整个双层循环
```

> **`emptyRest`** 表示"本槽位及其之后的所有槽位、以及后续所有溢出桶**都是空的**"，
> 往后怎么找都不会有数据——这是 map 查找"平均很快"的关键优化之一。
> （对照：被 `delete` 清空的槽位标记的是 **`emptyOne`**，只代表"这一格空"，**扫描必须继续**。）

### 写路径：找不到就落位，落不下就扩容

```text
① 遍历中记录第一个可用槽位（inserti / insertk / elem）
② 桶和溢出桶都满了 → 申请新溢出桶（优先取 extra.nextOverflow，否则 newobject）
③ 写入前判断：!h.growing() && ( overLoadFactor(h.count+1, h.B)
                            || tooManyOverflowBuckets(h.noverflow, h.B) )
     → hashGrow(t, h)，然后 ★ 回到"定位"步骤重新算一遍
       （双倍扩容后 B 变了，桶索引也变了）
④ 写入 key / value，h.count++，清掉 hashWriting 标记，返回 value 指针
```

### 面试官会追问什么

- **为什么 `mapassign` 要返回指针？** → 编译器要拿到 value 的**地址**直接写入，
  避免"取出 → 改 → 写回"的两次拷贝。
- **读 map 会置起 `hashWriting` 吗？** → 不会。读路径只**检查**这一位（用于发现读写并发），
  **写路径才置起 / 清除**。
- **`emptyRest` 和 `emptyOne` 的区别？** → 前者表示"从这里往后全空"、可直接终止扫描；
  后者只表示"这一格空"，必须继续往下找。

## 六、扩容是怎么"一边跑一边搬"的？`growWork` 与 `evacuate` 的疏散流程

**来源**：`BV12qjA6aErF p=31` B站 Go 面试真题 · 时长 21分04秒
**考察意图**：第二节讲的是"**什么时候**扩、扩成什么样"，本篇聚焦**源码级流程**：
`hashGrow` 起了什么头、`growWork` 怎么触发搬迁、`evacuate` 具体怎么搬、
以及**怎么判断一个旧桶搬完没有**。

### 调用链：`hashGrow` → `growWork` → `evacuate`

**`hashGrow` 一个桶都不搬**——它只做"准备"（分配新数组、旧数组挂到 `oldbuckets`、设标记），
真正的搬运由 `growWork` → `evacuate` 摊到后续**每一次读写**里，这就是"渐进式扩容"的字面含义。

### `hashGrow`：判断类型 + 铺好新旧两套桶

```text
① 判断类型：overLoadFactor(h.count+1, h.B) → 双倍扩容（B+1）；否则 → 等量扩容（B 不变）
② 保存旧桶：oldbuckets = buckets
③ 分配新桶：双倍扩容 → h.B++，h.buckets = 新的 2^(B+1) 个桶
            等量扩容 → h.buckets = 新的 2^B 个桶（数量不变，纯换一块干净的地）
④ h.nevacuate = 0、h.noverflow = 0；并把旧桶的溢出桶挂到 extra.oldoverflow、
   新桶预分配的溢出桶挂到 extra.nextOverflow
```

**为什么"等量扩容"也要换一个新数组？** 因为要的**不是更多空间，而是一块紧凑的地**——
把旧数据重新按哈希分布到干净的桶数组里，之前被大量删除留下的"空洞"自然就消失了。

### 搬迁时怎么决定去 X 还是 Y

```text
等量扩容（B 不变）：只有 x，元素仍落在同一个桶号位置 → 本质是"整理"
双倍扩容（B+1）  ：旧桶 i 的元素只会去两个地方：x = i、y = i + 2^B（旧桶数量）
                  ← 取决于新哈希值**多出来的那一位**是 0 还是 1
```

判定方式就是**重算哈希、看新增的那一位**：`if !h.sameSizeGrow() && hash&newbit != 0 { useY = 1 }`
（`newbit = 1 << 旧B`）。

> 这也顺手解释了"为什么双倍扩容的元素只会去 `i` 或 `i + 2^B`"：
> 旧的 `hash & (2^B - 1)` 没变，**多出来的那一位**决定进前半还是后半。

### ⭐ 怎么知道一个旧桶搬完没有：拿 `tophash` 当标记

| 标记 | 含义 |
|---|---|
| **`evacuatedX`** | 该槽位的元素被搬到了 **x 桶**（原位置） |
| **`evacuatedY`** | 该槽位的元素被搬到了 **y 桶**（后半段） |
| **`evacuatedEmpty`** | 该槽位原本就是空的，没有东西要搬 |

> 判断"一个旧桶是否搬完"**不需要额外的位图**——看它第一个槽位的 tophash 是不是
> `evacuated*` 系列即可。这是把"搬迁状态"**复用 tophash 这一个字节**的经典技巧。
> **查找时也用得上**：读到 `evacuatedX` 就去 x 桶找，读到 `evacuatedY` 就去 y 桶找。

### `growWork`：每次最多搬两个桶

```go
evacuate(t, h, bucket & h.oldbucketmask())        // ① 先搬"当前要访问的桶"对应的旧桶
if h.growing() { evacuate(t, h, h.nevacuate) }    // ② 再顺手搬 nevacuate 指向的那个旧桶
```

- **第 ① 步必须搬"当前桶"**：这次读写马上要用它的**新位置**，不先搬完新旧数据就对不上；
- **第 ② 步是"顺带还债"**：每次读写额外搬一个，
  保证即使某些桶再没被访问过，**扩容最终也能收敛完成**。

### `evacuate` 内部：一个桶是怎么被搬空的

```text
① 定位旧桶，先检查是否已疏散（第一个槽位是 evacuated* → 直接 return）
② 按 useY 决定目标桶 x/y；目标桶第一个可写位置记为 ins.i
③ 遍历旧桶 8 个槽位：空的 → 标记 evacuatedEmpty 并 continue；正常值 → 取出 key
④ 搬迁中若发现"目标桶 i == 8"（满了）→ 申请新桶挂到溢出链上，i 归零
⑤ 拷贝 key / value 并写 tophash，旧桶该槽位改标 evacuatedX / Y；溢出桶用同样逻辑搬
```

**⚠️ 必须知道的特例：`NaN` 作为 key**

> key **不等于自己**时（`!t.ReflexiveKey() && !t.Key.Equal(k2, k2)`），
> 重算哈希会得到完全不同的值，没法用"看第 B 位"判断去向；
> runtime 改用 `useY = top & 1`（tophash 的最低位）来决定它进 x 还是 y——
> 目的是让这种 key **经过多轮扩容后能比较均匀地散到整个桶数组里**。

### 收尾：清零旧桶 + 推进计数器

旧桶搬空后，如果**没有迭代器在遍历旧桶**（`h.flags&oldIterator == 0`）且**桶内含指针**
（`t.Bucket.PtrBytes != 0`），就把旧桶"**除 tophash 段之外**"的区域整块清零——
清掉指针引用 GC 才能回收对象，而 tophash 段必须保留，因为后面还要靠 `evacuated*` 标记判断"搬没搬"。

**推进 `nevacuate`**：只有"本次搬的旧桶索引 == `nevacuate`"时才推进
（向后找已搬完的桶 → `nevacuate++`，带 `stop` 上限防止无限循环）；
当 `nevacuate == 旧桶总数` → 扩容结束：`oldbuckets = nil`、清 `sameSizeGrow` 标记、
清 `extra.oldoverflow`。

> **这就是"`nevacuate` 只是下界"的原因**：计数器只在**恰好轮到它**时才前进，
> 而搬迁是访问驱动的，可能先从桶 5 搬起——此时 `nevacuate` 还停在 0。

### 面试官会追问什么

- **扩容期间新写入的数据会落到旧桶吗？** → 不会。写路径先 `growWork` 搬完相关旧桶，
  之后一律写新桶，旧桶从此只读。
- **为什么一次只搬 1~2 个桶？** → 避免大 map 扩容时的**长时间停顿**，把成本均摊到每次读写上；
  另外只要还有**任何**读写，`growWork` 就会顺手搬一个桶，扩容最终一定能收敛完成。

## 七、map 的 key 有什么类型限制？为什么 `NaN` 存得进去却取不出来？

**来源**：`BV1xSRXBwEeM p=79` 小米云原生一面 · 时长 5分11秒
**考察意图**：第一节的追问里点过一句"必须是可比较类型"，本题把它讲到底——
**为什么必须可比较、哪些类型不可比较、以及 `NaN` 这个反直觉的运行时陷阱**。

### 结论：必须是"可比较类型"（编译期强制）

```go
m := make(map[[]int]int)   // ❌ 编译错误：invalid map key type []int
```

| 可作 key | 不可作 key |
|---|---|
| bool、数值、字符串、指针、channel | **slice**（`[]T`） |
| 数组（元素可比较时）、struct（字段都可比较时） | **map** |
| interface（动态类型可比较时） | **func** |

**共同特征**：语言层面**支持 `==` / `!=`**，而 slice / map / func 只能与 `nil` 比较。
**为什么必须可比较**：查找靠"算哈希定位到桶，再拿 key 逐个比对"，
如果 `key == key` 这种比较本身不成立，就**没法判断"存进去的 key"和"要找的 key"是不是同一个**。
反过来更直观：**不可比较 → 存进去就再也取不出来**。

### ⚠️ 反直觉案例：`NaN` 是"可比较类型"，但它是陷阱

```go
nan := math.NaN()
m := map[float64]string{nan: "hello"}

fmt.Println(m[nan])      // 空字符串 —— 找不到！
fmt.Println(nan == nan)  // false        ← 根源在这里
```

| 现象 | 原因 |
|---|---|
| `NaN` 能塞进去 | `float64` 是**合法的可比较类型**，编译期通过 |
| 查找时找不到 | `NaN == NaN` **恒为假**（它不等于自己），key 比对永远失败 |
| 连哈希值都不可靠 | `NaN` 参与哈希的结果**不保证可复现**，可能连落在哪个桶都对不上 |
| `delete` 也删不掉 | `delete` 同样依赖 key 比对 → 这个 key **永远泄漏在 map 里** |

**运行时怎么描述它**：`maptype` 的 `t.Key.Equal` 为 nil 就代表"不可比较类型"
（会在运行时 `panic: hash of unhashable type`）；`t.ReflexiveKey()` 表示 key 是否满足
**`k == k` 恒为真**，**`NaN` 是唯一不满足的"可比较类型"**——这也是第六节里 `evacuate` 对它特判的原因。

### 面试官会追问什么

- **struct 一定能当 key 吗？** → 只有**所有字段都可比较**时才行；
  字段里含 slice / map / func 就整体不可比较。
- **为什么 `[]byte` 不能当 key，`string` 可以？** → 切片不可比较，`string` 支持 `==`；
  所以 `map[string]T` 配 `string(b)` 转换是常见替代方案。
- **接口类型当 key 有什么坑？** → 比较的是**动态类型 + 动态值**：
  动态值本身不可比较会 panic；`nil` interface 作 key 是合法的。

## 八、nil map 能读不能写？map 是引用语义吗？遍历顺序为什么不固定？

**来源**：本节为补充内容 —— 按《Go 语言核心编程》（李文塔）1.6.4 map 整理，配套本机实测。
**考察意图**：前面七节都是源码层面的"深水区"。这一节回到**三个基础认知** —— 它们几乎每场面试都会被顺口问到，而且**都属于"看起来会、一写就错"的类型**：nil map 的边界、map 的引用语义、遍历顺序的随机性。

### 一、nil map：读 / delete / range 都安全，唯独写会 panic

```go
var nilMap map[string]int
len(nilMap)                 // 0
nilMap["x"]                 // 零值 0，不 panic
_, ok := nilMap["x"]        // false
delete(nilMap, "x")         // no-op，不 panic
for range nilMap { ... }    // 0 次，安全
nilMap["k"] = 1             // ✗ panic
```

实测这条 panic 的真实文案：

```text
写入 nil map 之前，len = 0
写入 nil map 的 panic : assignment to entry in nil map
```

| 操作 | nil map | 说明 |
|---|---|---|
| `len()` | 0 | 安全 |
| 读 `m[k]` | 返回零值 | 安全（区分"值是零值"要用 comma-ok） |
| `delete(m, k)` | no-op | 安全 |
| `range` | 迭代 0 次 | 安全 |
| **写 `m[k] = v`** | **panic** | `assignment to entry in nil map` |

> ⭐ **`var m map[string]int` 是一个"只读的空集合"**：能查、能遍历、能删，就是不能写。
> 要写必须 `make(...)` 或字面量 `map[string]int{}` 初始化。
> 这也是「map 声明了就要马上初始化」这条经验的由来 —— 它不是风格问题，是会 panic 的。

### 二、map 是引用语义：函数内写，调用方看得见

```go
func fill(m map[string]int) { m["from-func"] = 1 }

m := map[string]int{"origin": 0}
fill(m)
```

```text
3a_函数内写入后调用方可见: map[from-func:1 origin:0] （map 头是值拷贝，但指向同一张哈希表）
```

> ⭐ 措辞要准：**map 头是值传递**（拷贝的是一个指针字段），但**它指向同一张哈希表**，所以函数内的写入外面可见。
> 与切片是同一套逻辑 —— 「值是拷贝的，但拷贝出来的指针指向同一份底层数据」，所以**增删元素生效，而要让调用方拿到新 map 得用返回值**。

### 三、遍历顺序：Go 刻意随机化，别依赖

```text
4a_200 次遍历的首元素分布: map[a:154 b:24 c:22] （每个键都可能当第一 → 顺序不固定）
5a_连续 5 次的首个键     : [b c a d b] （不保证一致）
```

> ⭐ 同一个 map **连续遍历两次，顺序都可能不同**（第 5a 行）—— 因为 Go 在每次 `range` 时**随机挑选起始桶和一个桶内偏移**。
> 这是**故意设计**：如果让顺序稳定，就会有代码依赖它，之后想改实现（比如换哈希算法、加并发）就不敢动。
> 面试里被问"顺序为什么是随机的"，答"**防止依赖顺序**"比答"因为哈希"更准确。

### 四、附：并发写 map 是 `fatal error`，`recover` 都拦不住

和上面的 nil map **不是一类问题**，量级更严重：

```text
fatal error: concurrent map writes

goroutine 160 [running]:
internal/runtime/maps.fatal({0x7ff6a1a3f752?, 0x7ff6a1a26b40?})
	D:/go1.26.5.windows-amd64/go/src/runtime/panic.go:1181 +0x18
```

| 错误 | 类型 | 能否 `recover` |
|---|---|---|
| `assignment to entry in nil map` | 普通 panic | ✅ 能 |
| **`fatal error: concurrent map writes`** | **fatal error** | ❌ **不能**，进程直接退出 |

> ⚠️ 生产上"偶发整个进程挂掉、日志里只有 `fatal error: concurrent map writes`"就是这一条 ——
> 它不是普通 panic，**`defer + recover` 救不了**。完整机制与替代方案见 [../并发/线程安全.md](../并发/线程安全.md)。

### 面试官会追问什么

- **为什么 `&m[k]` 编译不过？** → map 元素**不可寻址**：元素位置会随扩容搬迁而改变，允许取址会留下悬空指针。
  需要"改元素"时要么整体重写 `m[k] = v`，要么把 value 换成指针/结构体指针（见 [for-range.md](for-range.md)）。
- **`delete` 不存在的键会怎样？** → 静默 no-op，不报错也不 panic（连 nil map 上都安全）。
- **map 能取 `cap` 吗？** → 不能，`cap` 只对数组/切片/channel 有效。map 只有 `len`。
