## 一、for range 中赋值的变量，是临时变量还是真实地址？

**来源**：`p=41` 深信服 Go 面试 · 时长 7分58秒

**考察意图**：一道**极高频的陷阱题**，考你踩没踩过 range 变量捕获的坑。核心是「range 赋给的是**逐次复制的临时变量**，不是原元素地址」；能顺势说出 Go 1.22 前后语义的变化就是加分点。

### 一、结论：指向的是「临时变量」

**证据 1（语法层面）**：

```go
for i, v := range s { ... }
//   ↑ 这里用的是 := —— 海象运算符是「定义新变量」的语法
//     如果 v 已经是原始元素，就没必要"定义"它
//     → 所以必然存在一次复制
```

**证据 2（运行时）**：打印 `i`、`v` 和 `&v` 的**地址**会发现
**每次迭代地址都不一样**——说明**每次都定义了一个新的变量**。

> ⚠️ **Go 1.22 的重要变更**：循环变量改为**每次迭代新建**，
> 因此 `for` 里启动 goroutine / 闭包捕获变量**不再有"都捕获到最后一个值"的问题**。
> 但"**range 的值变量是临时变量**"这个结论**没有变**。

### 二、⚠️ 想通过指针修改原始数据：只有切片可以

| 类型 | 能否改原始数据 | 原因 |
|---|---|---|
| **切片** | ✅ **可以** | 切片元素**可以取地址**——用索引 `&s[i]` 拿到原始元素地址 |
| **map** | ❌ **不行** | **map 的元素不可寻址**——语法上就取不到地址 |
| **channel** | ❌ **不行** | channel 是**跨协程的数据传递**，**根本不存在"原始数据"**——<br>原始数据可能在**另一个协程**的某个变量里 |

**正确写法（改切片原始数据）**：

```go
// ✗ 错：改的是临时变量的地址，切片内容不变
for _, v := range s {
    modify(&v)
}

// ✓ 对：用索引取元素的原始地址
for i := range s {
    modify(&s[i])
}
```

### 三、为什么 map 不可寻址（顺带解释）

> **map 的底层是哈希表（buckets + 溢出桶）**，
> 元素在桶里的位置**会随扩容、搬迁而改变**——
> 如果允许取地址，**扩容后这个地址就失效了**，
> 会变成一个**悬空指针**。所以 Go **从语言层面禁止**取 map 元素的地址。

### 面试官会追问什么

- **`for range` 遍历 map 的顺序是固定的吗？** → **不固定**，
  Go 刻意**随机化起始位置**，防止开发者依赖遍历顺序。
- **`for range` 遍历字符串呢？** → 按 **rune（Unicode 码点）** 迭代，
  索引是**字节偏移**（所以中文等变长字符的索引会跳着走）。
- **怎么避免大元素复制开销？** → 遍历 `[]struct{}` 这类大元素时，
  用 `for i := range s` 配合 `&s[i]`，**避免每轮复制一份**。

## 二、range 复用临时变量：书里点名的三类误用

**来源**：本节为补充内容 —— 按《Go 语言核心编程》（李文塔）7.2 range 复用临时变量 整理，配套本机实测。

**考察意图**：上一节回答「`v` 是什么」，这一节回答「**它会在哪里坑到你**」。三类误用是同一个根因（**老语义下所有迭代共用同一个变量**）的三种表现形式，能说出「根因相同、表现不同」比背三个结论更值钱。

### 一、根因：老语义下一次循环，一个变量

`for _, v := range s` 里的 `v` 在 **Go ≤ 1.21 的语义**下是**整个循环创建一次、每轮被覆盖**。所以：

- 任何**捕获** `v` 的东西（闭包、goroutine）拿到的都是**同一个变量的引用**；
- 循环结束时它停在**最后一个值**上，于是前面捕获的全都被"重写"了。

### 二、三类误用（同一个根因，三种表现）

| # | 误用写法 | 老语义下的现象 | 本质 |
|---|---|---|---|
| **①** | `fn = append(fn, func(){ use(v) })` | 所有闭包**都输出最后一个值** | 闭包捕获的是变量，不是值 |
| **②** | `ptrs = append(ptrs, &v)` | 所有指针**指向同一个地址**，解引用全是最后一个值 | 取的是变量的地址 |
| **③** | `go func(){ use(v) }()` | 所有 goroutine **都读到最后的值**（且结果还取决于调度时机） | 同上，只是换到了另一个协程 |

> ⚠️ 三类都会**静默出错**：不 panic、不报错，只是结果不对。这是它被书里单列一节的原因。

### 三、实测：同一份代码，两种语义，两种结果

```go
s := []int{1, 2, 3}

// ① 闭包捕获
fns := []func(){}
for _, v := range s {
    fns = append(fns, func() { fmt.Print(v, " ") })
}

// ② 存 &v，看是不是同一个地址
ptrs := []*int{}
for _, v := range s {
    ptrs = append(ptrs, &v)
}

// ③ goroutine 捕获
for _, v := range s {
    go func() { got = append(got, v) }()
}

// ④ 修正写法：循环体内显式遮蔽
for _, v := range s {
    v := v
    fns = append(fns, func() { fmt.Print(v, " ") })
}
```

**实测输出（`go.mod` 声明 `go 1.21`，旧语义）：**

```text
1_闭包捕获到的值        : 3 3 3
2_&v 是否同一个地址      : true；解引用得到 3 3 3
3_goroutine 拿到的值     : [3 3 3]
4_加 v := v 之后         : 1 2 3
5_range 字符串           : [i=0,r=中] [i=3,r=文] [i=6,r=a] [i=7,r=b]
```

**实测输出（同一份代码，`go.mod` 声明 `go 1.22`，新语义）：**

```text
1_闭包捕获到的值        : 1 2 3
2_&v 是否同一个地址      : false；解引用得到 1 2 3
3_goroutine 拿到的值     : [1 3 2]
4_加 v := v 之后         : 1 2 3
5_range 字符串           : [i=0,r=中] [i=3,r=文] [i=6,r=a] [i=7,r=b]
```

> ⭐ **对比读法**：第 1、2 行是**同一份源码**，只改了 `go.mod` 里的一行版本号，结果就完全不同 —— 第 2 行的 `&v` 在老语义下**是同一个地址**（所以三个指针解引用都是 3），在新语义下是**三个不同地址**。
> 第 4 行说明 `v := v` 这个老写法在两种语义下**都输出 `1 2 3`**，是最省心的跨版本写法。
> 第 5 行与版本无关：range 字符串**按 rune 迭代，但索引是字节偏移**（`中` 占 3 字节，所以下一个索引直接跳到 3）。

## 三、语义开关跟着谁走？三个实测结论

**来源**：本节为补充内容 —— 按《Go 语言核心编程》（李文塔）7.2 range 复用临时变量（版本语义部分为本机实测） 整理，配套本机实测。

**考察意图**：真正的考点不是「哪个版本改的」，而是 **「你知道语义开关在哪、怎么自己验证吗」** —— 能说出「跟 `go.mod` 的 `go` 指令走，不是编译器版本」并接上「用 `-d=loopvar=2` 可以自己看」，比背版本号有说服力得多。
这题最容易答错的地方是"哪个版本开始变"，实测下来有三个反直觉的点。

### 一、门槛在 `go.mod` 的 `go` 指令上，不是编译器版本

同一份源码、同一个 go1.26.5 编译器，只改 `go.mod` 的版本号：

```text
go 1.20  go run .  →  1_闭包捕获到的值 : 3 3 3   （旧语义）
go 1.21  go run .  →  1_闭包捕获到的值 : 3 3 3   （旧语义）
go 1.22  go run .  →  1_闭包捕获到的值 : 1 2 3   （新语义）
go 1.23  go run .  →  1_闭包捕获到的值 : 1 2 3   （新语义）
```

**门槛确实是 `go 1.22`** —— 语言变更只对 `go.mod` 里 go 指令 ≥ 1.22 的模块生效，这是 Go 兼容性承诺的一部分。

### 二、⚠️ `go run main.go` 不读 `go.mod`，会给你错误结论

这是验证语义时最容易踩的坑 —— **同一次实测里，运行方式不同，结果就不一样**：

```text
go 1.21  +  go run main.go  →  1 2 3   ⚠️ 新语义（单文件模式，按最新语言版本）
go 1.21  +  go run .        →  3 3 3   ✅ 旧语义（包模式，按 go.mod 声明）
go 1.22  +  go run main.go  →  1 2 3
go 1.22  +  go run .        →  1 2 3
```

> ⚠️ **写这种验证代码时，一定要 `go run .`（或 `go build` 后运行），不要用 `go run main.go`** ——
> 后者以「单文件」的形式编译，**不套用模块的语言版本**，于是永远给你新语义。
> 如果只用 `go run main.go` 验证，会得出「门槛不是 1.22」的错误结论。

### 三、别猜，让编译器告诉你：`-d=loopvar=2`

官方提供了一个诊断开关，直接打印**哪些循环变量被改成了每次迭代一个新变量**：

```bash
go build -gcflags=all=-d=loopvar=2 -o /dev/null .
```

```text
./main.go:13:9: loop variable v now per-iteration, stack-allocated
./main.go:24:9: loop variable v now per-iteration, heap-allocated
./main.go:39:9: loop variable v now per-iteration, stack-allocated
```

| 输出片段 | 含义 |
|---|---|
| `now per-iteration` | 该循环变量已改为**每次迭代新建** |
| `stack-allocated` | 新变量分配在**栈**上（开销可忽略） |
| `heap-allocated` | 新变量**逃逸到堆**（因为被 `&v` 取址或跨协程引用） |

> ⭐ 第三列还顺便回答了「改成每次迭代新建，会不会变慢」：**绝大多数是栈分配**，只有被取址/跨协程捕获的才落堆，
> 所以这个语言变更是**零成本**的（实测也只有 `&v` 那一处是 heap-allocated）。

## 使用：跨版本安全写法与升级检查

**避坑写法（两支，按需求选）**：

```go
// ① 闭包/协程要各自持有一份副本 → 循环体内显式遮蔽
for _, v := range s {
    v := v
    go func() { use(v) }()
}

// ② 要的是"当前元素的指针" → 取元素地址，而不是循环变量的地址
for i := range s {
    ptrs = append(ptrs, &s[i])   // ✅ 想清楚要的是 s[i] 的地址
}
```

> ⚠️ **② 是 `&v` 的正确替代**：第二节实测里 `&v` 三个指针指向同一地址（老语义），
> 因为要的本来就不是"元素地址"而是"循环变量地址"。别用 `&v` 拿元素指针，也别用 `v := v` 去救它 —— 直接 `&s[i]`。
> （要求元素可取址，所以这招对切片/数组有效，对 map 元素不成立，见 [map.md](map.md)）

**行为对照（本主题最容易答错的地方）**：

| 写法 | Go ≤ 1.21 | Go ≥ 1.22 |
|---|---|---|
| `for i, v := range s { go func(){ use(i, v) }() }` | `i`/`v` 是**整个循环共用一份** → 都打印最后的值 | 每轮迭代**新建变量** → 各自打印本轮的 i/v |
| `for _, v := range s { fn = append(fn, func(){ use(v) }) }` | 所有闭包共享同一个 `v` | 各闭包捕获各自的 `v` |
| `for _, v := range s { v.Field = 1 }` | 改的是**副本**，原切片不变（这一条 1.22 也一样） | 同左 —— 语义变化只涉及**变量身份**，不涉及「v 是不是元素本身」 |

**升级前必查的三件事**：

1. `go.mod` 的 `go` 指令是否 ≥ 1.22 —— 语义开关跟着它走，不是编译器版本；
2. 是否存在「靠共享变量做副作用的循环」（以前误打误撞能跑，升级后行为变了）；
3. 老代码里为规避该问题写的 `v := v` 是否已成为冗余（保留也无害，可渐进清理）。

> ⭐ 回答要点：**Go 1.22 把「循环变量每轮新建」写进了语言规范**（`go.mod` 里的 go 版本决定语义），修的是「闭包捕获共享变量」这个长期坑；但它**没有改变**「`v` 是元素副本」这一条——想改原元素仍要靠**下标**或**元素是指针/引用类型**。
