## 一、为什么需要依赖注入？不用 DI 会怎样？

**来源**：`BV12qjA6aErF p=26` B站 Go 面试真题 · 时长 6分14秒
**考察意图**：考对 DI 本质的理解——**DI 不是某个库，而是"依赖在使用方定义、由外部装配"这一种写法**。面试官想听的是解耦、可测试、生命周期三件事，而不是背 wire 的 API。

### 一、一个典型的三层应用：`controller → biz → data`

不用任何 DI 组件时，通常在 `main` 里手写装配：

```go
func main() {
	data := NewData()          // data 层
	biz := NewBiz(data)        // 业务层依赖 data
	ctrl := NewController(biz) // 控制层依赖业务层
	api := NewAPI(ctrl)        // 最后才拿到可工作的 API
	api.Handle()
}
```

这段代码本身没问题，问题出在规模上去之后：

| 问题 | 具体表现 |
|---|---|
| 装配逻辑爆炸 | 几十个组件、多层嵌套，`main` 变成一大坨 new；加一个中间层要顺着改一串 |
| 依赖"具体实现" | `NewBiz(data *Data)` 把 biz 焊死在 data 上，换实现、加缓存、写单测都要动源码 |
| 生命周期没人管 | DB、gRPC、Redis 客户端何时创建、何时关闭、关闭顺序如何，全靠自觉 |
| 测试成本高 | 想测 biz 就必须真造 data（连库），单测退化成集成测试 |

### 二、DI 带来的三个收益

| 收益 | 做法 | 效果 |
|---|---|---|
| **解耦** | 依赖倒置：接口定义在**使用方**（biz），实现放在 data | biz 不认识 data，只认识 `UserRepo` 接口 |
| **可测试** | 构造函数收接口，测试时传 fake / mock | biz 单测不连库，毫秒级跑完 |
| **生命周期管理** | 装配集中在一处，创建与释放成对出现 | 单例只建一次；关闭顺序可控（wire 的 `cleanup`、fx 的 `OnStop`） |

> 一句话：**DI = 把"我要什么"和"谁来给我"分开**——使用方只声明依赖的**契约**，由外层（main / 生成代码 / 容器）把**具体实现**递进来。

### 面试官会追问什么

- **DI 和"依赖倒置原则(DIP)"是一回事吗？** → 不是。DIP 是"高层不依赖低层、都依赖抽象"的设计原则；DI 是实现 DIP 的一种**手段**（把抽象从外部传进来）。
- **DI 会不会让代码更难读？** → 手写装配确实有样板代码；wire 把它压到 `wire.go` 一处声明 + 生成代码，读生成结果比读散落各处的 new 更直观。
- **Go 为什么没有 Spring 那种注解式 DI？** → Go 没有注解和运行时元编程，社区因此分成"代码生成"（wire）和"反射容器"（dig/fx）两条路。

## 二、不用框架，手动构造函数注入怎么写？

**来源**：`BV12qjA6aErF p=26` B站 Go 面试真题 · 时长 6分14秒
**考察意图**：考基本功。能徒手写出"接口在使用方定义、构造函数只收接口"的装配链路，说明理解 DI 的机制；只会框架 API 的人通常写不出来。

### 一、依赖倒置：接口定义在 biz，实现在 data

```go
// internal/biz/user.go —— 使用方定义接口
type UserRepo interface{ GetUser(ctx context.Context, id int64) (*User, error) }

type UserBiz struct{ repo UserRepo } // 只持有接口

func NewUserBiz(repo UserRepo) *UserBiz { return &UserBiz{repo: repo} } // 收接口，不收 *data.Data
func (b *UserBiz) GetUser(ctx context.Context, id int64) (*User, error) { return b.repo.GetUser(ctx, id) }
```

```go
// internal/data/user.go —— 实现方实现接口
type userRepo struct{ data *Data }

func NewUserRepo(d *Data) *userRepo { return &userRepo{data: d} }

func (r *userRepo) GetUser(ctx context.Context, id int64) (*biz.User, error) { /* 查库 */ }
```

```go
// cmd/app/main.go —— 最外层装配
func main() {
	d := data.NewData()
	repo := data.NewUserRepo(d) // 把具体实现"喂"给接口
	uc := biz.NewUserBiz(repo)
	ctrl := controller.NewUserController(uc)
	api := controller.NewAPI(ctrl)
	api.Handle()
}
```

### 二、测试时换个装配点，就变成单测

```go
type fakeRepo struct{}

func (fakeRepo) GetUser(ctx context.Context, id int64) (*biz.User, error) { return &biz.User{ID: id}, nil }

func TestUserBiz_GetUser(t *testing.T) {
	uc := biz.NewUserBiz(fakeRepo{}) // 不连库、不起容器
	if got, err := uc.GetUser(context.Background(), 1); err != nil || got.ID != 1 {
		t.Fatalf("unexpected: %v %v", got, err)
	}
}
```

### 三、优缺点（这就是 wire 存在的理由）

| 优点 | 缺点 |
|---|---|
| 零依赖、零运行时开销 | 样板代码量随组件数线性增长 |
| 依赖关系一眼可见，编译期就能查错 | 改一个构造函数签名，所有装配点都要改 |
| 断点可一路单步，最好调试 | 装配顺序、单例、释放逻辑全要人手维护 |

### 面试官会追问什么

- **接口为什么定义在使用方而不是实现方？** → 依赖倒置的要求：谁使用谁定义契约；Go 的隐式接口正好让 data 不必 import biz 的接口声明也能实现它。
- **构造函数返回指针还是接口？** → 一般返回具体类型（更灵活、便于 wire 绑定）；需要只对外暴露接口时再返回接口类型或用 `wire.Bind`。
- **`main` 里一堆 `if err != nil` 怎么办？** → 这正是 wire 支持的 `(T, func(), error)` 形态要解决的：生成代码把所有错误和清理函数串起来。

## 三、google/wire 的代码生成方案怎么用？（`wire.Build` 与 `wire_gen.go`）

**来源**：`BV12qjA6aErF p=26` B站 Go 面试真题 · 时长 6分14秒
**考察意图**：考有没有真跑通 wire 的两段式文件——**`wire.go` 只写声明（带 `wireinject` tag，永不参与真实编译），`wire_gen.go` 是生成物**；同时要知道 `wire.Bind` 为什么必需。

### 一、装工具、加依赖，每层导出自己的 ProviderSet

```bash
go install github.com/google/wire/cmd/wire@latest   # 装到 $(go env GOPATH)/bin
go get github.com/google/wire                       # 项目依赖
```

wire 把"制造某个类型"的函数叫 **provider**，用 `wire.NewSet` 打成一个集合；各层只导出自己的集合，**互相不必 import**：

```go
// internal/data/data.go
var ProviderSet = wire.NewSet(NewData, NewUserRepo, wire.Bind(new(biz.UserRepo), new(*userRepo)))

// internal/biz/biz.go —— 只提供自己，不关心 data 的实现
var ProviderSet = wire.NewSet(NewUserBiz)

// internal/controller/controller.go
var ProviderSet = wire.NewSet(NewUserController, NewAPI)
```

> **`wire.Bind` 是必需的**：`NewUserRepo` 返回 `*userRepo`，而 `NewUserBiz` 要的是 `biz.UserRepo` 接口；wire **不会隐式**把具体类型当接口用，必须显式 `wire.Bind(new(接口), new(实现))`，或者直接让 provider 函数的返回类型写成接口。

### 二、`wire.go`：只声明依赖图

```go
//go:build wireinject

package main

import "github.com/google/wire"

// InitApp 只是"模板"：函数体永远 panic，真正的实现由 wire 生成
func InitApp() (*controller.API, error) {
	panic(wire.Build(
		data.ProviderSet,    // 把各层 provider 组合到一起
		biz.ProviderSet,     // wire 在这些集合里找"谁能造出我需要的类型"
		controller.ProviderSet,
	))
}
```

`//go:build wireinject` 是关键：**带 tag 时 `wire.go` 参与编译，真实构建时不带 tag，所以 `panic` 永远不会被执行**。

### 三、执行生成

执行 `wire ./...`（也可在包目录下直接 `wire`，或写 `//go:generate wire` 后 `go generate ./...`），生成 `wire_gen.go`（**不要手改**）：

```go
// Code generated by Wire. DO NOT EDIT.

package main

func InitApp() (*controller.API, error) {
	d := data.NewData()          // 构造顺序、依赖关系全部由 wire 算好
	repo := data.NewUserRepo(d)
	uc := biz.NewUserBiz(repo)   // 把 data 的实现交给 biz 的接口参数
	api := controller.NewUserController(uc)
	return api, nil
}
```

对照第一节的 `main` 可以看出：**手写的那串 `data → biz → controller → api` 装配代码，只是被搬进了生成文件**，`main` 退化成一行 `InitApp()`。

### 四、常用的 wire 指令

| 指令 | 用途 |
|---|---|
| `wire.Build(set...)` / `wire.NewSet(...)` | 声明依赖图 / 把 provider 打成可复用集合 |
| `wire.Bind(new(I), new(*T))` | 把具体类型绑定到接口 |
| `wire.Struct(new(Foo), "*")` / `wire.FieldsOf(new(Conf), "Db")` | 自动填结构体字段 / 把某字段当作 provider |

### 面试官会追问什么

- **为什么 `wire.go` 里函数体要 panic？** → 它只是给 wire 看的"依赖声明 + 返回类型签名"；`wireinject` tag 保证它不进入真实构建，panic 是防止有人误调用。
- **provider 的错误和清理函数怎么处理？** → provider 签名写成 `(T, error)` 或 `(T, func(), error)` 即可，wire 会把错误层层上抛、把 `cleanup` 聚合成一个 `func()` 返回给调用方。
- **生成代码能改吗？** → 不能，重新 `wire` 会覆盖。

## 四、反射方案 dig / fx 怎么用？三种方案怎么选？

**来源**：`BV12qjA6aErF p=26` B站 Go 面试真题 · 时长 6分14秒（对比与选型为延伸内容）
**考察意图**：考技术视野与取舍能力。能说清"代码生成 vs 反射容器"的本质区别（错误暴露时机、可调试性、动态能力），比背 API 更有价值。

### 一、`uber/dig`：最小可用的反射容器

```go
import "go.uber.org/dig"

func main() {
	c := dig.New()
	for _, p := range []interface{}{NewData, NewUserRepo, NewUserBiz, NewUserController, NewAPI} {
		if err := c.Provide(p); err != nil { // 注册 provider，参数靠反射解析
			log.Fatal(err)
		}
	}
	// 声明"我要一个 *API"，dig 自己按类型把整条依赖链拉起来
	if err := c.Invoke(func(api *controller.API) { api.Handle() }); err != nil {
		log.Fatal(err)
	}
}
```

依赖靠**类型**匹配，同类型多实例用 `dig.Name`、`dig.Group` 消歧，或把参数写进 `dig.In` 结构体。坑是缺 provider 时报的是**运行时**错误（`missing type: ...`），一个字段写错可能到启动才炸。

### 二、`uber/fx`：dig + 生命周期 + 模块化

```go
func main() {
	fx.New(
		fx.Provide(NewData, NewUserRepo, NewUserBiz, NewUserController, NewAPI),
		fx.Invoke(RegisterRoutes), // 只为触发副作用，不关心返回值
	).Run()                        // 内部完成 Start → 阻塞 → Stop
}
```

fx 的价值主要是**生命周期钩子**：把资源的启动/关闭写在 provider 里，框架按依赖顺序正序启动、倒序关闭。

```go
func NewHTTPServer(lc fx.Lifecycle, cfg *Config) *http.Server {
	srv := &http.Server{Addr: cfg.Addr}
	lc.Append(fx.Hook{
		OnStart: func(ctx context.Context) error { go srv.ListenAndServe(); return nil },
		OnStop:  func(ctx context.Context) error { return srv.Shutdown(ctx) }, // 优雅退出
	})
	return srv
}
```

一个 provider 同时需要 `*Server` 和 `*Data` 时不用改签名——**只要类型能被提供出来，容器自己组装**；代价是依赖关系不再显式，`fx.Provide` 列表成了唯一的"接线图"。

### 三、三种方案对比

| 维度 | 手动构造函数注入 | google/wire（代码生成） | dig / fx（反射容器） |
|---|---|---|---|
| 运行时开销 | 无 | 无（产物就是普通 Go 代码） | 有反射与容器开销（集中在启动期） |
| 错误暴露时机 | 编译期 | 生成期报错 + 编译期 | **运行时**（启动才 panic） |
| 依赖关系可见性 | 完全显式 | 显式（`wire.go` 一处汇总） | 隐式（靠类型匹配） |
| 可调试性 | 最好 | 好（`wire_gen.go` 可打断点、可单步） | 差（调用栈在容器内部） |
| 动态/条件装配 | 手写 | 弱（生成期固定） | 强（按环境/模块条件注册） |
| 生命周期管理 | 自己写 | provider 返回 `cleanup func()` | 内置 `fx.Lifecycle` 钩子 |
| 典型场景 | 小项目、基础库 | 中大型服务，要确定性与性能 | 大型常驻服务、插件化/多环境装配 |

> 选型口诀：**小项目手写；要确定性和性能用 wire；要动态装配和生命周期编排用 fx**。

### 面试官会追问什么

- **wire 和 fx 能一起用吗？** → 可以（一套管装配、一套管生命周期），但没必要为同一批对象上两套容器。
- **反射开销大吗？** → 只在容器构建/解析时发生，属于启动期一次性成本，不在请求热路径上；真正的代价是**错误推迟到运行时**和难以调试。
- **fx 的 `fx.Invoke` 不接收返回值，为什么要它？** → 它只用来"触发副作用"（注册路由、启动定时任务），并保证依赖在 `Run()` 之前完成构建。

## 五、Kratos 项目里 wire 是怎么用的？

**来源**：`BV12qjA6aErF p=26` B站 Go 面试真题 · 时长 6分14秒（延伸自 `p=3` Kratos 集成 ent 中的 wire 用法）
**考察意图**：考工程落地。Kratos 官方骨架就是 wire，能说清"哪一层导出 ProviderSet、`wireApp` 在哪、参数从哪来、忘了加 provider 报什么错"，说明真的建过项目。

### 一、目录与职责，以及那个 `wireApp`

```text
cmd/app/     main.go（调 wireApp() 再 app.Run()）、wire.go（wireinject 声明）、wire_gen.go（生成物）
internal/    conf/（配置结构体）、data/、biz/、service/、server/ 各自导出 ProviderSet
```

```go
// cmd/app/wire.go
//go:build wireinject

package main

import "github.com/google/wire"

// 函数入参就是"种子依赖"：wire 把 *conf.Server、*conf.Data、log.Logger
// 当成已经能提供的类型，供下面的 provider 使用
func wireApp(*conf.Server, *conf.Data, log.Logger) (*kratos.App, func(), error) {
	panic(wire.Build(server.ProviderSet, data.ProviderSet, biz.ProviderSet, service.ProviderSet, newApp))
}
```

```go
// cmd/app/main.go —— 装配只剩一次调用
app, cleanup, err := wireApp(bc.Server, bc.Data, logger) // bc 来自 flags/env 解析
if err != nil {
	panic(err)
}
defer cleanup() // 释放 DB / Redis / gRPC 连接
app.Run()
```

### 二、各层 ProviderSet 怎么写

```go
var ProviderSet = wire.NewSet(NewHTTPServer, RegisterHTTPServer)   // internal/server/http.go
var ProviderSet = wire.NewSet(NewUserService)                      // internal/service/user.go
var ProviderSet = wire.NewSet(NewUserBiz)                          // internal/biz/user.go
var ProviderSet = wire.NewSet(NewData, NewDB, NewUserRepo,         // internal/data/data.go
	wire.Bind(new(biz.UserRepo), new(*userRepo)))
```

Kratos 生成的 `server.ProviderSet` 里还包含 `khttp.NewServer()` 等框架级 provider；`newApp` 负责把 server 列表、logger 组装成 `*kratos.App`。

### 三、生成与常见报错

```bash
go generate ./...     # 或 kratos 骨架里的 make generate / make init
wire ./...
```

| 报错 | 原因 |
|---|---|
| `wire: no provider found for biz.UserRepo` | 忘了把 `NewUserRepo` 加进 `data.ProviderSet`，或没写 `wire.Bind` |
| `wire: multiple bindings for ...` | 同类型被两个 provider 提供，需要 `wire.Bind` 拆开或改名 |
| `wire: circular dependency` | A 依赖 B、B 又依赖 A，通常是接口/实现的分层画错了 |

### 面试官会追问什么

- **`*conf.Server` 没有 provider，wire 为什么不报错？** → 它是 `wireApp` 的入参，wire 把它当作**外部注入的种子依赖**，无需 provider。
- **新增一个 repo 要改几处？** → 两处：`data` 层构造函数 + `data.ProviderSet`；`wire.go` 只维护集合粒度，通常不用动。
- **为什么不用 fx 替换 Kratos 的 wire？** → Kratos 追求依赖显式、启动确定性、零反射，wire 的生成代码更契合；fx 的动态能力在这里用不上，反而牺牲可调试性。

## 六、书里讲的 inject 库：反射注入的「早期形态」

**来源**：本节为补充内容 —— 按《Go 语言核心编程》（李文塔）6.3 inject 库与依赖注入 整理，配套本机实测。
**考察意图**：前五节讲的是今天在用的方案。这一节补**源头** —— 书 6.3 用 martini 框架的 `inject` 库讲 DI 的实现原理。
它已经不再维护，但**它的问题正是后来 wire 出现的原因** —— 能讲清这条演化链，说明你理解的是"为什么"而不只是"用哪个"。

### 一、它怎么工作：反射分析函数签名，自动填参数

```go
// martini 时代（2013）的写法：注册好类型，之后调用时参数自动注入
injector.Map(newLogger)        // ① 把一个构造函数/实例登记进去
injector.Invoke(func(l Logger, s Store) {   // ② 参数由 inject 自己找出来
	// 这里不用自己 new，也不用自己传
})
```

原理三步（书 6.3.4 讲的就是这个）：

| 步骤 | 做法 |
|---|---|
| ① 收集依赖 | 遍历已 `Map` 进来的构造函数/实例，建立"类型 → 提供者"的表 |
| ② 分析签名 | `reflect.TypeOf(fn).In(i)` 取出每个参数的类型 |
| ③ 反射调用 | 按类型从表里取实例，`reflect.Value.Call(...)` 调起来 —— **参数是"类型匹配"出来的，不是显式传的** |

### 二、⚠️ 三个绕不过去的问题

| 问题 | 表现 |
|---|---|
| **报错太晚** | 某个类型忘了注册 → **运行期 panic**（编译期完全查不出来） |
| **依赖不可见** | 看 `Invoke(func(l Logger, s Store))` 只能知道这两个参数，**看不出 `Logger` 又是谁造的、它还依赖谁** |
| **性能开销** | 反射调用比直接调用慢（书 6.4「反射的缺点」专门讲过）—— 服务启动期可以忍，请求路径上不能忍 |

> ⭐ 这三条可以一句话概括：**「依赖关系藏在运行期的类型表里，编译器和人都看不见」。**

### 三、演化链：从「运行期反射」退回「编译期生成」

| 代际 | 方案 | 谁 | 报错时机 | 依赖关系可见性 |
|---|---|---|---|---|
| 第一代 | **`inject`（martini）** | 2013 | ❌ 运行期 panic | 藏在类型表里 |
| 第二代 | `dig` / `fx` | Uber | ❌ 运行期（但提供**启动期校验**，可提前暴露） | 靠 `Provide/Invoke` 显式登记 |
| 第三代 | **`wire`** | 2018+ | ✅ **编译期**（生成代码时就能发现缺依赖） | **生成出来的 `wire_gen.go` 里全是显式调用** |
| 第零代 | **手动构造函数注入** | 一直可用 | ✅ 编译期 | 一眼看全 |

（第二、三代的具体写法见本文第四节、第三节。）

> ⭐ **这条演化链最有意思的地方**：它看起来是"**倒退**" —— 从"自动的反射注入"退回到"写代码生成代码"。
> 但换来的正是 inject 缺的东西：**错误提前到编译期、依赖关系显式可见、没有反射开销**。
> 所以在 Go 生态里，「**能编译期确定的就不要留到运行期**」是一条反复出现的取向
> （同一取向的另一面，就是第三节 `wire.go` 用 `//go:build wireinject` 让声明不进入真实构建）。

### 面试官会追问什么

- **为什么 martini 这类"自动注入"框架在 Go 里没流行起来？** → Go 社区偏好**显式**：自动注入把控制流藏进反射，调试点、IDE 跳转、编译期检查全部失效 —— 与「代码要能一眼读懂」的取向冲突。
- **`fx` 是反射方案，为什么它比 `inject` 活得久？** → 它把"登记"变成了**显式的 `fx.Provide`**，并提供**启动期校验**（依赖缺失/循环依赖能在启动时一次性报出来），补上了 inject 最致命的"报错太晚"。
- **DI 框架是非用不可吗？** → 不是。**依赖在十几个以内时，手动构造函数注入（第二节）是最优解** —— 编译期检查、零依赖、零学习成本；容器化的收益要到"依赖图很大、需要按环境替换实现"时才体现。
