## Q1. 切片 append 时如何分配内存？扩容规则是什么？

**来源**：`p=39` 百度 Go 开发二面 · 时长 22分43秒
**考察意图**：既要讲清**扩容规则**，也要落到**"所以我该怎么写代码"**——
后半段才是加分项。

### 一、底层结构：三个字段

| 字段 | 含义 |
|---|---|
| **`array`** | **指向底层数组的指针**（数组是**定长、连续**的地址空间） |
| **`len`** | 从 `array` 这个地址开始**引用了多少个元素** |
| **`cap`** | 底层数组从该起始地址**还有多少可用空间** |

**举例**：一个大数组索引 0~9，切片从索引 2 开始、引用 6 个元素：

```
array → 指向索引 2 的位置
len   = 6                     （引用 2~7 这 6 个元素）
cap   = 8                     （从索引 2 到 9，共 8 个位置）

→ 所谓"切片的底层数组"，是这个大数组从索引 2 开始的子数组
```

### 二、什么时候会扩容

> **当底层数组被填满（`len == cap`）之后，再继续 `append` 就会扩容。**

**为什么必须换新数组**：**数组类型是定长的**——
想改变长度，就**只能创建一个新数组**，把老数据**拷贝过去**，
再让切片的 `array` 指向新数组。

### 三、扩容规则（Go 1.18+）

```
老 cap < 256            → 双倍扩容（×2）
老 cap >= 256           → 从双倍平滑过渡到 1.25 倍
申请空间 > 2 × 老 cap    → 直接用「老 len + 新增元素数」
```

**为什么不是每次 +1？**（两个原因）

| 原因 | 说明 |
|---|---|
| **① 内存对齐需求** | 对齐之后 **CPU 寻址更快** |
| **② 减少系统资源消耗** | 频繁创建新数组开销大 → 用翻倍策略**尽可能减少底层数组的初始化次数** |

> ⚠️ **`newcap` 不是随便取的**——它是**经过计算、比较有规律**的数字，
> 这也是"从小切片的 2 倍**平稳过渡**到大切片的 1.25 倍"这个设计的用意。

### 四、⭐ 落地点：有意识地避免扩容

既然扩容要"新建 + 拷贝"，那**能预知大小就提前分配好 cap**：

```go
// 场景：分页每次读 100 条，装进切片
// ✗ 不预分配：中途会多次扩容、多次拷贝
var list []Item
for i := 0; i < 100; i++ { list = append(list, it) }

// ✓ 预分配 cap=100：append 100 次完全不触发扩容
list := make([]Item, 0, 100)
for i := 0; i < 100; i++ { list = append(list, it) }
```

**另一个技巧**：如果确定就是 100 条，可以 `make([]Item, 100)`，
然后**按索引直接赋值**（`list[i] = ...`）——此时 `cap` 刚好是 100，也不会扩容。

### 五、扩容的三个步骤（源码层面）

#### 第 1 步：计算 `newcap`（新数组长度）

```
newLen = 老 len + append 的元素数量
newCap = 扩容前数组的 capacity

① 若 newLen > 2 × oldCap  → newcap 直接取 newLen
② 否则按 256 分界：
     oldCap <  256 → newcap = 2 × oldCap          （小切片：双倍）
     oldCap >= 256 → 逐步过渡到 1.25 × oldCap      （大切片）
③ 溢出检查：若 newcap <= 0 说明溢出 → newcap = newLen
```

#### 第 2 步：计算「实际分配」的内存大小

```
理论大小 = newcap × elemsize
```

**⚠️ 但实际分配不是简单的乘法**——还要经过 **Go 内存分配器的 size class 对齐**：

> 例如算出 1000 字节，**实际可能分配 1024、1224 等**。
>
> 因为涉及**内存对齐**，也涉及 Go 底层的**对象分级**：
> 按元素大小分情况（`elemsize == 1` / 等于指针大小 / 其他），
> 再按**大对象/小对象**走**不同的 size class**，
> 每个 class 有固定的对象大小、span 大小、可分配对象数。
>
> **所以"分配的空间"和 `newcap × elemsize` 有关系，但不一定相等。**

#### 第 3 步：分配内存并拷贝

**分两种情况**：

| 元素类型 | 做法 |
|---|---|
| **不含指针** | 分配 `cap` 大小的内存，**只需要清空后半段**——<br>因为**前半段在 copy 老数据时会被覆盖**，没必要重复清零 |
| **含指针** | 需要分配并清空内存；<br>若老 `len > 0` 且**启用了写屏障**，还要**用三色标记法对即将被回收的老数据做着色处理**（配合 GC 回收） |

**最后**：把老切片的数据拷贝到新切片，返回新切片。

### 面试官会追问什么

- **为什么要用写屏障？** → 扩容时要保证 GC 能正确识别"这些指针被复制到了新数组"，
  避免**老对象被提前回收**或**新对象被漏标**。
- **`append` 一定扩容吗？** → 不一定。`len < cap` 时直接在原数组上追加，
  **多个切片可能共享同一底层数组**（这是常见 bug 来源）。
- **大切片为什么用 1.25 倍而不是 2 倍？** → 切片越大，**2 倍造成的内存浪费越严重**；
  1.25 倍在"扩容次数"与"内存浪费"之间取平衡（2 倍扩容会造成大量闲置空间）。

## Q2. 切片的底层结构是什么？为什么"修改有时生效、有时不生效"？

**来源**：`BV1xSRXBwEeM p=77` 虾皮 Go 后端开发面试 · 时长 3分39秒
**考察意图**：Q1 问的是"扩容规则"，这一题问的是**把切片当普通数组用会踩哪些坑**——
核心结论：切片是**值类型的外壳 + 引用语义的内核**。

### 一、底层就是一个三字段结构体

```go
type SliceHeader struct {
    Data uintptr   // 指向底层数组的指针
    Len  int       // 从 Data 开始，切片"看得到"多少个元素
    Cap  int       // 从 Data 开始，到底层数组末尾还剩多少可用空间
}
```

| 字段 | 含义 | 一句话记法 |
|---|---|---|
| **`Data`（array）** | 指向底层数组的**起始地址** | "**从哪儿开始看**" |
| **`Len`** | 从 `Data` 起**引用了多少个元素** | "**能看多长**" |
| **`Cap`** | 从 `Data` 起**底层数组还剩多少位置** | "**最多能长到哪**" |

> **切片本身并不存数据**——它只是"**一段底层数组的视图**"。
> 所谓"切片的底层数组"，就是从 `Data` 开始的那一段子数组。

### 二、关键认知："切片是引用类型"这个说法只对了一半

> **传参时，`SliceHeader` 这个结构体是「值传递」（会拷一份），
> 但它内部的 `Data` 指针指向的还是同一个底层数组。**

所以行为要分三种情况看：

| 操作 | 影响原切片吗 | 为什么 |
|---|---|---|
| **修改已有元素**（`s[i] = x`，`i < len`） | ✅ **生效** | 新旧切片**指向同一个底层数组**，改的确实是数组里的数据 |
| **在 `len` 和 `cap` 之间追加** | ❌ **外部看不到** | `append` 改的是**副本的 `len`**；<br>值传递 → **原切片的 `len` 没变**，根本看不见新增元素 |
| **触发扩容后再追加** | ❌ **完全不影响** | 扩容后 `Data`（新数组地址）、`Len`、`Cap` **三个字段全变了**；<br>副本的三要素变了，**原切片还指向老数组的老三要素** |

**用代码看更清楚**：

```go
func grow(s []int) []int {
    s = append(s, 99)   // 假设这里触发了扩容 → s 指向了新数组
    return s
}

func main() {
    a := make([]int, 2, 4)          // len=2, cap=4
    b := grow(a)
    fmt.Println(a, len(a), cap(a))  // [0 0] 2 4      ← 原切片一动不动
    fmt.Println(b, len(b), cap(b))  // [0 0 99] 3 4   ← 只有返回的副本变了
}
```

> ⚠️ **这就是"切片传进函数改了、外面却没变"的根因**：
> 改的是**副本的 `Len` / `Cap` / `Data`**，不是原切片那三个字段。

### 三、扩容后"指向新数组"意味着什么

```
扩容前：s.Data ─→ [数组 A][A][A][A]
扩容后：s.Data ─→ [数组 B][B][B][B][B][B][B][B]   ← 新数组，老数据已拷过去
                  ↑ 原切片（没接返回值时）依然指向数组 A
```

> **两条铁律**：
> 1. **`append` 的返回值必须接住**（`s = append(s, x)`）——
>    新的 `SliceHeader` 只在返回值里，不接就等于**把新数组丢了**；
> 2. **传切片进函数、又希望 `len` 的变化生效 → 必须把返回的新切片带出来**
>    （或者干脆传 `*[]T`）。

### 四、顺带一个易踩的坑：多个切片共享同一底层数组

```go
a := []int{1, 2, 3, 4, 5}
b := a[1:3]        // len=2, cap=4，和 a 共用底层数组
b = append(b, 99)  // cap 够用 → 没扩容，直接写在原数组上
fmt.Println(a)     // [1 2 3 99 5]   ← a 的索引 3 被"隔空改写"了
```

> 想彻底隔离，用 `slices.Clone`，或用三参数切片 `a[1:3:3]`（**把 cap 卡死**，
> 强制下一次 `append` 必然扩容）。

### 面试官会追问什么

- **`len` 和 `cap` 谁决定"能不能直接赋值"？** →
  只能访问 `[0, len)`。**`len ~ cap` 之间的位置必须靠 `append` 才能写**进去。
- **切片到底是不是引用类型？** → 严格说 **Go 里切片是值类型**（`SliceHeader` 会被拷贝），
  只是**内部含一个指向数组的指针**，表现得"像引用"。面试时把这层说清是加分项。
- **`make([]T, 0, n)` 和 `make([]T, n)` 有什么区别？** →
  前者 `len=0, cap=n`（**要用 `append`**）；后者 `len=n, cap=n`（**可直接按索引赋值**）。
  预知大小时后者更省事，也**完全不会触发扩容**。
- **扩容后老数组会立刻被回收吗？** → **不一定**——只要还有别的切片指向它就不会。
  这正是"共享底层数组"能产生隐蔽 bug 的原因。
