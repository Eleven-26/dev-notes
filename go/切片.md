## Q1. 切片 append 时如何分配内存？扩容规则是什么？

**来源**：`p=39` 百度 Go 开发二面 · 时长 22分43秒
**考察意图**：既要讲清**扩容规则**，也要落到**"所以我该怎么写代码"**——
后半段才是加分项。

### 一、底层结构：三个字段

| 字段 | 含义 |
|---|---|
| **`array`** | **指向底层数组的指针**（数组是**定长、连续**的地址空间） |
| **`len`** | 从 `array` 这个地址开始**引用了多少个元素** |
| **`cap`** | 底层数组从该起始地址**还有多少可用空间** |

**举例**：一个大数组索引 0~9，切片从索引 2 开始、引用 6 个元素：

```
array → 指向索引 2 的位置
len   = 6                     （引用 2~7 这 6 个元素）
cap   = 8                     （从索引 2 到 9，共 8 个位置）

→ 所谓"切片的底层数组"，是这个大数组从索引 2 开始的子数组
```

### 二、什么时候会扩容

> **当底层数组被填满（`len == cap`）之后，再继续 `append` 就会扩容。**

**为什么必须换新数组**：**数组类型是定长的**——
想改变长度，就**只能创建一个新数组**，把老数据**拷贝过去**，
再让切片的 `array` 指向新数组。

### 三、扩容规则（Go 1.18+）

```
老 cap < 256            → 双倍扩容（×2）
老 cap >= 256           → 从双倍平滑过渡到 1.25 倍
申请空间 > 2 × 老 cap    → 直接用「老 len + 新增元素数」
```

**为什么不是每次 +1？**（两个原因）

| 原因 | 说明 |
|---|---|
| **① 内存对齐需求** | 对齐之后 **CPU 寻址更快** |
| **② 减少系统资源消耗** | 频繁创建新数组开销大 → 用翻倍策略**尽可能减少底层数组的初始化次数** |

> ⚠️ **`newcap` 不是随便取的**——它是**经过计算、比较有规律**的数字，
> 这也是"从小切片的 2 倍**平稳过渡**到大切片的 1.25 倍"这个设计的用意。

### 四、⭐ 落地点：有意识地避免扩容

既然扩容要"新建 + 拷贝"，那**能预知大小就提前分配好 cap**：

```go

// 场景：分页每次读 100 条，装进切片
// ✗ 不预分配：中途会多次扩容、多次拷贝
var list []Item
for i := 0; i < 100; i++ { list = append(list, it) }

// ✓ 预分配 cap=100：append 100 次完全不触发扩容
list := make([]Item, 0, 100)
for i := 0; i < 100; i++ { list = append(list, it) }
```

**另一个技巧**：如果确定就是 100 条，可以 `make([]Item, 100)`，
然后**按索引直接赋值**（`list[i] = ...`）——此时 `cap` 刚好是 100，也不会扩容。

### 五、扩容的三个步骤（源码层面）

#### 第 1 步：计算 `newcap`（新数组长度）

```
newLen = 老 len + append 的元素数量
newCap = 扩容前数组的 capacity

① 若 newLen > 2 × oldCap  → newcap 直接取 newLen
② 否则按 256 分界：
     oldCap <  256 → newcap = 2 × oldCap          （小切片：双倍）
     oldCap >= 256 → 逐步过渡到 1.25 × oldCap      （大切片）
③ 溢出检查：若 newcap <= 0 说明溢出 → newcap = newLen
```

#### 第 2 步：计算「实际分配」的内存大小

```
理论大小 = newcap × elemsize
```

**⚠️ 但实际分配不是简单的乘法**——还要经过 **Go 内存分配器的 size class 对齐**：

> 例如算出 1000 字节，**实际可能分配 1024、1224 等**。
>
> 因为涉及**内存对齐**，也涉及 Go 底层的**对象分级**：
> 按元素大小分情况（`elemsize == 1` / 等于指针大小 / 其他），
> 再按**大对象/小对象**走**不同的 size class**，
> 每个 class 有固定的对象大小、span 大小、可分配对象数。
>
> **所以"分配的空间"和 `newcap × elemsize` 有关系，但不一定相等。**

#### 第 3 步：分配内存并拷贝

**分两种情况**：

| 元素类型 | 做法 |
|---|---|
| **不含指针** | 分配 `cap` 大小的内存，**只需要清空后半段**——<br>因为**前半段在 copy 老数据时会被覆盖**，没必要重复清零 |
| **含指针** | 需要分配并清空内存；<br>若老 `len > 0` 且**启用了写屏障**，还要**用三色标记法对即将被回收的老数据做着色处理**（配合 GC 回收） |

**最后**：把老切片的数据拷贝到新切片，返回新切片。

### 面试官会追问什么

- **为什么要用写屏障？** → 扩容时要保证 GC 能正确识别"这些指针被复制到了新数组"，
  避免**老对象被提前回收**或**新对象被漏标**。
- **`append` 一定扩容吗？** → 不一定。`len < cap` 时直接在原数组上追加，
  **多个切片可能共享同一底层数组**（这是常见 bug 来源）。
- **大切片为什么用 1.25 倍而不是 2 倍？** → 切片越大，**2 倍造成的内存浪费越严重**；
  1.25 倍在"扩容次数"与"内存浪费"之间取平衡（2 倍扩容会造成大量闲置空间）。

## Q2. 切片的底层结构是什么？为什么"修改有时生效、有时不生效"？

**来源**：`BV1xSRXBwEeM p=77` 虾皮 Go 后端开发面试 · 时长 3分39秒
**考察意图**：Q1 问的是"扩容规则"，这一题问的是**把切片当普通数组用会踩哪些坑**——
核心结论：切片是**值类型的外壳 + 引用语义的内核**。

### 一、底层就是一个三字段结构体

```go

type SliceHeader struct {
    Data uintptr   // 指向底层数组的指针
    Len  int       // 从 Data 开始，切片"看得到"多少个元素
    Cap  int       // 从 Data 开始，到底层数组末尾还剩多少可用空间
}
```

| 字段 | 含义 | 一句话记法 |
|---|---|---|
| **`Data`（array）** | 指向底层数组的**起始地址** | "**从哪儿开始看**" |
| **`Len`** | 从 `Data` 起**引用了多少个元素** | "**能看多长**" |
| **`Cap`** | 从 `Data` 起**底层数组还剩多少位置** | "**最多能长到哪**" |

> **切片本身并不存数据**——它只是"**一段底层数组的视图**"。
> 所谓"切片的底层数组"，就是从 `Data` 开始的那一段子数组。

### 二、关键认知："切片是引用类型"这个说法只对了一半

> **传参时，`SliceHeader` 这个结构体是「值传递」（会拷一份），
> 但它内部的 `Data` 指针指向的还是同一个底层数组。**

所以行为要分三种情况看：

| 操作 | 影响原切片吗 | 为什么 |
|---|---|---|
| **修改已有元素**（`s[i] = x`，`i < len`） | ✅ **生效** | 新旧切片**指向同一个底层数组**，改的确实是数组里的数据 |
| **在 `len` 和 `cap` 之间追加** | ❌ **外部看不到** | `append` 改的是**副本的 `len`**；<br>值传递 → **原切片的 `len` 没变**，根本看不见新增元素 |
| **触发扩容后再追加** | ❌ **完全不影响** | 扩容后 `Data`（新数组地址）、`Len`、`Cap` **三个字段全变了**；<br>副本的三要素变了，**原切片还指向老数组的老三要素** |

**用代码看更清楚**：

```go

func grow(s []int) []int {
    s = append(s, 99)   // 假设这里触发了扩容 → s 指向了新数组
    return s
}

func main() {
    a := make([]int, 2, 4)          // len=2, cap=4
    b := grow(a)
    fmt.Println(a, len(a), cap(a))  // [0 0] 2 4      ← 原切片一动不动
    fmt.Println(b, len(b), cap(b))  // [0 0 99] 3 4   ← 只有返回的副本变了
}
```

> ⚠️ **这就是"切片传进函数改了、外面却没变"的根因**：
> 改的是**副本的 `Len` / `Cap` / `Data`**，不是原切片那三个字段。

### 三、扩容后"指向新数组"意味着什么

```
扩容前：s.Data ─→ [数组 A][A][A][A]
扩容后：s.Data ─→ [数组 B][B][B][B][B][B][B][B]   ← 新数组，老数据已拷过去
                  ↑ 原切片（没接返回值时）依然指向数组 A
```

> **两条铁律**：
> 1. **`append` 的返回值必须接住**（`s = append(s, x)`）——
>    新的 `SliceHeader` 只在返回值里，不接就等于**把新数组丢了**；
> 2. **传切片进函数、又希望 `len` 的变化生效 → 必须把返回的新切片带出来**
>    （或者干脆传 `*[]T`）。

### 四、顺带一个易踩的坑：多个切片共享同一底层数组

```go

a := []int{1, 2, 3, 4, 5}
b := a[1:3]        // len=2, cap=4，和 a 共用底层数组
b = append(b, 99)  // cap 够用 → 没扩容，直接写在原数组上
fmt.Println(a)     // [1 2 3 99 5]   ← a 的索引 3 被"隔空改写"了
```

> 想彻底隔离，用 `slices.Clone`，或用三参数切片 `a[1:3:3]`（**把 cap 卡死**，
> 强制下一次 `append` 必然扩容）。

### 面试官会追问什么

- **`len` 和 `cap` 谁决定"能不能直接赋值"？** →
  只能访问 `[0, len)`。**`len ~ cap` 之间的位置必须靠 `append` 才能写**进去。
- **切片到底是不是引用类型？** → 严格说 **Go 里切片是值类型**（`SliceHeader` 会被拷贝），
  只是**内部含一个指向数组的指针**，表现得"像引用"。面试时把这层说清是加分项。
- **`make([]T, 0, n)` 和 `make([]T, n)` 有什么区别？** →
  前者 `len=0, cap=n`（**要用 `append`**）；后者 `len=n, cap=n`（**可直接按索引赋值**）。
  预知大小时后者更省事，也**完全不会触发扩容**。
- **扩容后老数组会立刻被回收吗？** → **不一定**——只要还有别的切片指向它就不会。
  这正是"共享底层数组"能产生隐蔽 bug 的原因。

## Q3. 母子切片什么时候共享内存、什么时候"断链"？

**来源**：`BV1EL4y1P7hh p=5` 马哥教育 Go 面试精讲 · 时长 62分25秒
**考察意图**：Q2 已经演示过"共享底层数组会互相污染"，这一题把**从切出子切片 → 共享 → 扩容断链的完整生命周期**跑一遍；
真正的加分点是那条**打印地址自证**的验证手法，以及"数据写进去了母切片却看不见"这个反直觉现象。

### 一、子切片的三个字段怎么算

```go

s := make([]int, 3, 5)
sub := s[1:3]
```

| 字段 | 母切片 `s` | 子切片 `s[1:3]` |
|---|---|---|
| **Data** | 数组首地址 | 数组首地址 **+ 1 × elemsize** |
| **Len** | 3 | **3 - 1 = 2** |
| **Cap** | 5 | **5 - 1 = 4** |

> **记法**：`s[i:j]` 的 `len = j - i`，`cap = cap(s) - i`。
> **注意 `cap` 跟 `j` 无关**——它只数"从起点到数组末尾还剩多少"。
> （这正是 Q2 里三参数切片 `s[i:j:k]` 能把 cap 卡死的原因：第三个参数默认值就是 `cap(s)`。）

### 二、完整生命周期：共享 → "看不见" → 断链

```go

package main

import "fmt"

func main() {
	s := make([]int, 3, 5)
	for i := 0; i < 3; i++ {
		s[i] = i + 1 // s = [1 2 3]
	}

	sub := s[1:3]                   // 与 s 共享底层数组
	fmt.Println(len(sub), cap(sub)) // 2 4
	fmt.Println(&s[1] == &sub[0])   // true：同一个地址

	sub[0] = 8     // 改子切片 = 改母切片
	fmt.Println(s) // [1 8 3]

	sub = append(sub, 6, 7) // len 2→4，cap=4 刚好填满 → 不扩容
	fmt.Println(s, sub)     // [1 8 3] [8 3 6 7]：6、7 已写进 s 的底层数组，但 s 的 len 还是 3

	sub = append(sub, 9) // len==cap==4 → 触发扩容，sub 换到新数组
	sub[0] = 100         // 此后改 sub 影响不到 s
	fmt.Println(s, sub)
	fmt.Println(&s[1] == &sub[0]) // false：地址已分离
}
```

**真实输出**：

```
2 4
true
[1 8 3]
[1 8 3] [8 3 6 7]
[1 8 3] [100 3 6 7 9]
false
```

> **三个结论**：
> 1. **共享期**：`sub[0]` 与 `s[1]` 是同一块内存，改一个另一个跟着变（打印地址可自证）；
> 2. **"看不见"不等于"没写入"**：未扩容时 `append` 的数据确实写进了母切片的底层数组，
>    但**母切片的 `len` 没变，它无权读**——`cap` 管"物理上能写到哪"，`len` 管"逻辑上能读多远"；
> 3. **断链期**：一旦 `len == cap` 再追加就扩容，`sub.Data` 指向新数组。
>    **扩容就是"共享 / 分离"的分水岭**，之前同呼吸，之后井水不犯河水。

### 面试官会追问什么

- **`s[1:3]` 的 `cap` 为什么是 4 而不是 2？** → `cap` 是"从起点到数组末尾"的剩余空间，
  起点偏移了 1，所以 `5 - 1 = 4`；**它由底层数组决定，和你截到哪里无关**。
- **怎么在代码里"证伪"共享底层数组？** → 打印 `&s[i]` 和 `&sub[j]`，
  **地址相同 → 共享；扩容后地址不同 → 已分离**。这比背结论可靠。
- **子切片 append 之后为什么母切片读不到新元素？** → **母切片的 `len` 没有变**。
  值传递 + 没接返回值，`len` 的增长只发生在子切片自己的 `SliceHeader` 上。

## Q4. 返回子切片会导致内存泄漏吗？`copy` 和预分配能解决什么？

**来源**：`BV1EL4y1P7hh p=5` 马哥教育 Go 面试精讲 · 时长 62分25秒
**考察意图**：Q2 末尾说过"扩容后老数组不一定被回收"，这一题把它落成一个**会真实发生的内存泄漏场景**，
并给出标准修复方式 `copy`——这是 Go 里"小切片拖住大数组"的经典事故。

### 一、泄漏是怎么产生的，又怎么修

```go

const total = 1 << 20 // 100 万个 int，约 8 MB

// ✗ 只返回 5 个元素，却把 8 MB 的底层数组一起拖了一辈子
func leaky() []int {
	parent := make([]int, total)
	return parent[2:7]
}

// ✓ 需要多少申请多少，把元素复制进一块新内存
func fixed() []int {
	parent := make([]int, total)
	dst := make([]int, 5)
	copy(dst, parent[2:7])
	return dst
}
```

```go

s1 := leaky()
fmt.Println(len(s1), cap(s1)) // 5 1048574

s2 := fixed()
fmt.Println(len(s2), cap(s2)) // 5 5
```

`parent` 这个变量虽然出了作用域，但**返回的子切片 `Data` 仍指向那块 8 MB 数组的中间**。
GC 回收的粒度是**整个底层数组对象**，只要还有**任何一个指针**落在它上面，它就不能被释放。

> **`len` 小得人畜无害，`cap` 大得触目惊心**（`cap = total - 2`）——
> 这是"小切片长期持有大数组"的典型信号，函数被高频调用时内存会一直涨、一直不还。
> 而 `fixed` 的返回值 `len == cap == 5`，与那块大数组再无关系 → **底层数组可被立即回收**。
> 标准库等价写法：`slices.Clone(parent[2:7])`（内部就是 `make` + `copy`）。

**`copy` 的三个行为要点**：拷贝 `min(len(dst), len(src))` 个元素（**与 `cap` 无关**）；
返回值是**实际拷贝的元素个数**；它**不会帮你扩容 `dst`**，多出来的元素被静默丢弃。

### 二、顺带把"预分配"的收益量化一下

同样往切片里 `append` 一百万次，只是初始化方式不同（素材中的实测对比）：

| 写法 | `append` 一百万次的耗时 |
|---|---|
| `var s []int`（len=cap=0，一路扩容 + 拷贝） | **约 18 ms** |
| `s := make([]int, 0, 1_000_000)`（cap 一次到位） | **约 3 ms** |

> **差好几倍**，而且切片越大差距越明显。原因是扩容要**把已有元素整体重拷一遍**，
> 100 万次 append 累计拷过的元素数量级是 n——所以"能预估规模就 `make([]T, 0, n)`"
> 不是玄学：Q1 第四节讲的是**规则**，这里补的是**代价量级**。

### 面试官会追问什么

- **怎么一眼看出可能有切片泄漏？** → 看 `cap`：**`len` 很小但 `cap` 大得离谱**，
  说明它背后还挂着一块用不完的大数组。
- **为什么 `len` 用得少也没用，还是泄漏？** → 是否被回收取决于**有没有指针指向那块内存**，
  `cap` 描述的正是"这块底层数组还伸出去多远"，`len` 只管读得到多远。
- **`copy` 和 `append` 怎么选？** → `append` 是"往后追加"（可能扩容、可能共享原数组）；
  `copy` 是"把元素写进一块**我自己申请的**目标内存"，天然隔离、不会牵连别人。

## Q5. 切片作为函数参数，要传 `*[]T` 吗？遍历时怎么改元素才生效？

**来源**：`BV1EL4y1P7hh p=5` 马哥教育 Go 面试精讲 · 时长 62分25秒
**考察意图**：Q2 回答了"为什么改了不生效"，这一题给出**两种传法的可运行对照**，
并把"边遍历边修改"的 `range` 坑一并收掉——核心是**盯住三要素每一行怎么变**。

### 一、传指针 vs 不传指针：同一段逻辑，两种结果

```go

package main

import "fmt"

func modify(arr *[]int) { // 传的是切片的指针
	*arr = append(*arr, 9) // ①
	*arr = (*arr)[1:2]     // ②
	(*arr)[0] = 9          // ③
}

func modifyNoPtr(a []int) { // 传的是 SliceHeader 的副本
	a = append(a, 9)
	a = a[1:2]
	a[0] = 9
}

func main() {
	s := []int{1, 2, 3}
	modify(&s)
	fmt.Println(s, len(s), cap(s)) // [9] 1 5

	t := []int{1, 2, 3}
	modifyNoPtr(t)
	fmt.Println(t, len(t), cap(t)) // [1 2 3] 3 3
}
```

**真实输出**：

```
[9] 1 5
[1 2 3] 3 3
```

### 二、逐行推演 `*arr` 的三个字段

| 步骤 | Data 指向 | Len | Cap |
|---|---|---|---|
| 初始 `[1 2 3]` | 数组 A | 3 | 3 |
| ① `append(9)`：`len == cap` → **扩容** | **数组 B（新）** | 4 | **6** |
| ② 截取 `[1:2]` | 数组 B + 1×elemsize | **1** | `6 - 1 =` **5** |
| ③ `(*arr)[0] = 9` | 不变 | 不变 | 不变 |

> **记法**：**`append` 动 `len`**（扩容时连 `Data`、`cap` 一起动）；
> **切片表达式动 `Data` 和 `cap`**（`len` 一并重算）；
> **按下标赋值只动底层数组的内容，三要素一个都不动**。
> 每写完一行切片操作就问自己"这三个字段各是多少"，切片就没有绕不清的。

不传指针那版**三行全部白干**：第①步就触发扩容，`a` 已经换到新数组，
后两步改的都是**外面根本看不到**的新内存。

| 你想做的事 | 传 `[]T` | 传 `*[]T` |
|---|---|---|
| 改已有元素（`s[i] = x`，且**未扩容**） | ✅ 生效 | ✅ 生效 |
| 改 `len` / `cap`（`append`、截取、整体重新赋值） | ❌ 副本上改，外面看不到 | ✅ 生效 |
| `append` 触发扩容后再改元素 | ❌ 改的是新数组 | ✅ 生效 |

> **判断标准只有一条：函数里会不会改变切片的 `len` / `cap`。**
> 会 → 传 `*[]T`；只读或只改元素 → 传 `[]T` 就够（也更符合 Go 的习惯用法）。
> 更常见的替代方案是**接住返回值**：`s = modify(s)`（Q2 第三节的两条铁律）。

### 三、边遍历边修改：`for range` 拿到的是元素的拷贝

```go

s := []int{1, 2, 3}

for _, v := range s {
	v++        // ✗ v 是元素的副本，改它跟切片无关 → s 仍是 [1 2 3]
}
fmt.Println(s) // [1 2 3]

for i := range s {
	s[i]++     // ✓ 通过下标写回底层数组
}
fmt.Println(s) // [2 3 4]
```

> `v` 是把元素**拷贝出来的一个独立变量**，`v++` 只改了那份拷贝，底层数组纹丝不动。
> 想真正落地，必须**用下标写回** `s[i]`。
> （`range` 变量"是不是真实地址"的完整机制见 [for-range.md](./for-range.md)。）

### 面试官会追问什么

- **`append` 之后 `cap` 为什么是 6 而不是 4？** → `oldCap = 3 < 256` → 双倍得 6，
  且 `6 ≥ newLen(4)`，所以 `newcap = 6`（Q1 第五步的规则）。
- **不传指针时 `a[0] = 9` 到底能不能影响外面？** → **取决于有没有扩容**：
  没扩容时 `a` 还指向原数组，外面能看到；一旦扩容，`a` 已换数组，就完全无关了。
  本例恰好第一步就扩容，所以三行全废。
- **为什么写 `(*arr)[0] = 9`，不能写 `*arr[0] = 9`？** → **运算符优先级**：
  `*arr[0]` 会被解析成 `*(arr[0])`。先括号解引用拿到切片，再取下标。
