## 一、一句话定位：HQL 不是解释执行，是「编译成作业」

**本节要点**：HQL 与 Spark SQL 都会先出计划，分水岭在计划之后交给谁——Spark 交给自己进程里的执行引擎，Hive 交给外部作业调度器（MR / Tez / 或 `spark`）。所以「Hive 慢」的第一层原因不是算得慢，而是**编译 + 作业启动**这两段固定开销与小查询无关地发生。

| 环节 | Spark SQL | HQL |
| --- | --- | --- |
| 解析与规划在哪 | driver 进程内 | HiveServer2 进程内 |
| 计划的产物 | 物理计划 → task | 作业配置 → 交给执行引擎 |
| 谁来执行 | 自己的 executor | MR / Tez；`hive.execution.engine=spark` 时交给 Spark |
| 成本结构 | 一个 job 的 task 调度 | 每次提交一次作业，分钟级起步（文档口径，未实测） |

⭐ 判据：**HQL 的成本 = 固定开销 + 扫描量**。固定开销不随数据量缩小，所以它适合批量入仓，不适合交互式探索；判断一条 HQL 慢在哪，第一步永远是分清「编译慢」还是「作业慢」。

⚠️ 一个常见误判：把「装了 Hive 容器」当成「在用 HQL 引擎」。容器里的 HS2 起来、`CREATE TABLE` 能跑，不代表有人真在用它跑 MR 作业——很多环境只是拿它当 HMS 的载体（见 [HiveMetastore.md](../../Catalog/HiveMetastore.md)）。

## 二、六步：一条 HQL 变成作业

**本节要点**：六步里只有第二步出 HS2 去查 HMS，第四步决定分区裁剪，第六步才产生作业开销。排查「为什么扫了全表」要定位到第二、四步；排查「为什么慢」要先分清前五步与第六步。

![一条 HQL 从解析到 MR 作业的六步编译链路：Parser 出 AST，Semantic Analyzer 查 HMS 拿 schema 与分区，Optimizer 决定谓词下推与分区裁剪，Physical Plan 落到 MR 或 Tez](images/HQL到MR的执行链路.svg)

图上从左到右是六步，中间那条支线是第二步对 HMS 的访问：schema、分区列表、SerDe 三样一次性读回来，第四步的裁剪用的就是这份列表。最后一步落到 MR 或 Tez，作业启动开销在这里产生。

| 步骤 | 做什么 | 出问题时看什么 |
| --- | --- | --- |
| 1 解析（Parse） | SQL → AST | 语法错，`ParseException` 在这一步 |
| 2 语义分析（Semantic Analyze） | 查 HMS 拿 schema、分区列表、SerDe；解析列引用 | 表 / 列不存在；分区列有没有被识别 |
| 3 逻辑计划（Logical Plan） | 关系代数树 | `EXPLAIN` 的前半段 |
| 4 优化（Optimize） | 谓词下推、分区裁剪、join 重排 | ⭐ 裁剪是否生效看这里 |
| 5 物理计划（Physical Plan） | 切 MR / Tez 作业、定算子 | `EXPLAIN` 的 `Map Operator Tree` |
| 6 执行（Execute） | 提交作业、拉结果 | 作业耗时、容器资源 |

### 2.1 第二步：一次访问拿回三样东西

HQL 进程自己不留表结构，所以第二步必须出 HS2 去问 HMS。拿回的是三样，各自服务后面的不同环节：

| 拿回什么 | 用在哪 | 细节在哪 |
| --- | --- | --- |
| schema 与列定义 | 类型检查、谓词下推 | 本篇 |
| 分区列表 | ⭐ 第四步的裁剪 | [分区分桶与SerDe.md](分区分桶与SerDe.md) 第二节 |
| SerDe 描述 | 第五步决定「文件怎么读成行」 | [分区分桶与SerDe.md](分区分桶与SerDe.md) 第六节 |

⭐ 这三样是**元数据，不是数据**。所以第二步不读文件，HMS 响应慢会直接拖慢每次查询的起步时间——但它与扫描量无关。

### 2.2 第四步：裁剪在这里就定了

分区列表是编译期就能拿到的东西，`WHERE dt='2026-10-25'` 也是常量，两者求交不需要碰数据。所以 Hive 在**不执行**的前提下就能算出「这次要读几个目录」，这也是 `EXPLAIN` 能当裁剪验证工具的原因。

⚠️ 反过来：只要分区列没被识别成分区（比如用 Spark 的写法建表，`dt` 变成了普通列），这一步就退化成「全部分区」，而且不报错——实测见 [分区分桶与SerDe.md](分区分桶与SerDe.md) 第四节。

### 2.3 第六步：开销在这里产生

MR 的固定成本（申请容器、分发 jar、调度）与小查询的扫描量无关，一条只扫 3 个文件的 HQL 同样要付这笔钱。Tez 把多个 MR 作业合成一个 DAG、复用容器，理论上把这笔钱摊薄——但**这是文档口径，本册没有 Tez 的作业实测**，只验证到「开关能设」。

## 三、执行引擎三档：mr / tez / spark

**本节要点**：`hive.execution.engine` 决定第六步把计划交给谁。三档的代价不同，但**都不改变前五步的语义**——分区裁剪、分桶、SerDe 照旧。

| 取值 | 计划交给谁 | 代价 | 现状 |
| --- | --- | --- | --- |
| `mr`（默认） | MapReduce | 每个 stage 一次作业，启动开销叠加 | 最稳、最慢，存量环境的默认 |
| `tez` | Tez 的 DAG | 多 stage 合一、容器复用 | ⚠️ 未实测（容器池配置没跑） |
| `spark` | Spark | 复用 Spark 的 DAG 与内存 | 等价于「用 Spark 跑 HQL」，新项目通常直接写 Spark |

```bash
# 只在当前会话生效；写进 hive-site.xml 才是全局
beeline -e "set hive.execution.engine=tez;"
```

⭐ 判据：**换执行引擎是换「作业怎么跑」，不是换「表怎么组织」**。表层面的问题——分区列没被识别、分桶没落、SerDe 对不上——换任何执行引擎都不解决，见 [分区分桶与SerDe.md](分区分桶与SerDe.md)。

⚠️ 本册的三档复现只到「设置成功、`set` 读回来是新值」。真实作业耗时、Tez 会话复用率、Spark 模式下与 `spark-submit` 的行为差异都没有读数。

## 四、EXPLAIN 怎么读

**本节要点**：`EXPLAIN` 只编译不执行，是验证「裁剪有没有生效」最便宜的手段——不用等作业，也不用扫数据。

```sql
EXPLAIN SELECT * FROM orders WHERE dt='2026-10-25';
```

输出按六步切开，读法如下：

| 段 | 来自第几步 | 看什么 |
| --- | --- | --- |
| `AST` | 1 | 语法是否按预期解析 |
| 逻辑计划 | 3~4 | 谓词有没有被推到扫描旁边 |
| `Map Operator Tree` / `Stage` | 5 | 扫描算子、分区过滤、作业切分 |
| `Partition` | 4 | ⭐ 列出的分区数 = 运行时真读的目录数 |

⭐ 一句话判据：**看 `Partition` 段的分区数**。它等于全部分区数时，裁剪已经失效；等于 1 时，与实测的输入文件数对得上（3 → 1 的读数见 [分区分桶与SerDe.md](分区分桶与SerDe.md) 第四节）。

## 五、编译期的三类失败

**本节要点**：编译阶段的失败都在第六步之前发生，不产生作业。只有三类，按步骤分正好一条一条对。

| 症状 | 属于哪一步 | 先查 |
| --- | --- | --- |
| `ParseException` | 1 解析 | SQL 语法、保留字、引号配对 |
| 表 / 列不存在 | 2 语义分析 | 当前库、HMS 连接、名字大小写 |
| `EXPLAIN` 里分区数等于全部分区数 | 4 优化 | 分区列是否真被识别成分区 |

⚠️ 第三种压根不报错：它不在「失败」里，而在「成功但慢」里。这也是本册要把分区、分桶、SerDe 单独拆成一篇的原因——**它们的问题全部表现为「能跑，只是不对」**。

## 延伸追问

- **为什么说 HQL 是「编译成作业」而不是「解释执行」？** → 因为第六步交出去的是作业配置，不是逐行求值的执行器。前五步全部在 HS2 进程内完成，第六步才离开；所以 `EXPLAIN` 能完全离线跑，而作业启动开销与小查询无关地发生。
- **既然编译期就能裁剪，为什么还会扫全表？** → 裁剪的前提是「分区列在元数据里被标记为分区」。表建错（`dt` 成了普通列）时，第四步拿到的分区列表是空的，条件退化成普通过滤，只能扫完再丢——不报错，只是慢。
- **换 tez 能快多少？** → 本册没有读数，只能给机制：Tez 把多个 MR 作业合成一张 DAG、复用容器，省的是「每 stage 一次作业启动」。数据量越大，这笔固定开销占比越小，所以它能改善的幅度取决于作业里有几个 stage。
- **`EXPLAIN` 为什么不用跑数据？** → 因为它停在第五步。分区裁剪、谓词下推、join 重排都在第四步完成，全部只依赖元数据与常量条件，不需要读一行数据。
