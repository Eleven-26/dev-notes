## 一、一句话定位与「为什么快」

Redis 是 **C 语言写的单进程内存 KV 数据库**，数据全在内存、命令用单线程处理，因此能把读写压到 **10 万级 QPS**（对比 MySQL 单连接约 500~2000 QPS，见 [缓存选型与容量.md](../../缓存/缓存选型与容量.md) 的第一节/第二节）。

| 快的原因 | 说明 |
|---|---|
| **纯内存操作** | 读写不进磁盘，没有磁盘 IO 与寻道开销 |
| **单线程处理命令** | 无锁、无上下文切换、无并发竞争；命令都是纳秒级纯内存操作，CPU 不是瓶颈 |
| **IO 多路复用** | `epoll` 单线程监听海量连接，事件就绪才处理，不阻塞在某个连接上 |
| **高效数据结构** | SDS、跳表、listpack、intset 按场景选型，空间与时间都做过优化（见 [底层结构.md](底层结构.md)） |
| **自定义 RESP 协议** | 文本协议极简、解析成本低，配合 Pipeline 大幅减少 RTT |

「单线程」指的是**命令处理是单线程**。瓶颈若在 CPU 上，多线程才有意义；Redis 的瓶颈在**内存带宽与网络 IO**，单线程反而省掉了锁与竞争开销。

> ⚠️ 单线程的代价：**一个慢命令会阻塞所有请求**。`keys *`、`hgetall` 大 hash、`flushall` 这类 O(N) 命令是线上事故重灾区（见 [部署与运维.md](部署与运维.md) 第二节）。

**6.0 的多线程改了什么**：只把**网络 IO**（读 socket、解析协议、写回结果）交给 IO 线程池，`io-threads 4` 解决的是「网络读写跟不上」，**命令执行与 Lua 仍是单线程**，所以 `keys *` 该阻塞还是阻塞。

## 三、持久化：RDB 与 AOF（速览）

**RDB 是「某一刻的内存快照」（二进制、文件小、恢复快、丢得多）；AOF 是「重建数据的命令日志」（丢得少、文件大、恢复慢）。** 7.0 起 AOF 默认带**混合持久化**：重写时前半段写成 RDB、后半段追加增量命令。

```conf
save 900 1 300 10 60 10000   # RDB：三个条件任一满足即触发；save "" 彻底关闭
appendonly yes               # AOF 开关
appendfsync everysec         # ⭐ 生产默认：最多丢 1 秒；always 不丢但慢一个数量级
aof-use-rdb-preamble yes     # 混合持久化（7.0 起默认）
```

**生产结论：两个都开** —— RDB 负责定时备份与主从全量同步，AOF 负责把丢失窗口压到 1 秒内。只做纯缓存、丢了能回源时，可只留 RDB 或全关。

⭐ **三档 `appendfsync` 的实测延迟**（本机 2000 条 SET，连跑 3 轮）：`always` 2508~2762 µs/条、`everysec` 215~245 µs/条、`no` 299~534 µs/条 —— **`always` 比 `everysec` 慢约一个数量级**，差的就是「每条命令后面多等一次磁盘同步」。

⚠️ **`BGSAVE` 与 `BGREWRITEAOF` 都要 `fork`**：实测 20 万 key 的实例 fork 只要 1.6ms，但**快照期间有写压力时 COW 会把内存峰值推高 54%**（29M → 44.68M）—— 大实例规划内存要按峰值算，不是按稳态数据量。

> 📖 **原理、实测与选型全部拆到 [持久化.md](持久化.md)**：`fork + COW` 的量化、三种 fsync 的崩溃恢复对照（RDB 全丢 vs AOF 一个不差）、AOF 重写的压缩比（10 万次 INCR → 一行 SET，25001:1）、混合持久化的文件头（`52 45 44 49 53` = `REDIS` 魔数）、7.0 的 MP-AOF 与 8.10 的 `BACKUP`。

## 四、高可用与集群（速览）

三个层次解决的是**不同问题**，不要混着选：

| 方案 | 解决什么 | 一句话机制 |
|---|---|---|
| **主从复制** | 读扩展 + 备份 | 从节点 `replicaof`；全量同步传 RDB，断线后靠 `repl-backlog` 增量补发 |
| **哨兵（Sentinel）** | 自动故障转移 | ≥3 个哨兵监控；先判主观/客观下线，再按 **优先级 → `repl_offset` 最大 → `runid` 最小** 选新主 |
| **Cluster** | 容量与写能力 | **16384 个槽**分片，`slot = CRC16(key) mod 16384`，每主可带一从 |

⭐ **复制是异步的**：主库写完就返回客户端，宕机会丢掉「还没同步过去」的那一段（本机实测大写入压力下最多落后 0.4MB 量级）。要「写进去就不丢」，得显式用 `WAIT` 或 `min-replicas-to-write` —— 用可用性换一致性。

⚠️ **两个最容易踩的点**：

1. **`sync_full` / `sync_partial_ok` / `sync_partial_err` 在 `INFO stats` 里，不在 `INFO replication`** —— 找错地方会一直读到空值；
2. **客户端必须通过哨兵地址取当前主节点**（`SENTINEL get-master-addr-by-name`），写死 IP 的话切换后就打到旧主了（旧主已变从节点，写入直接报 `READONLY`）。

⚠️ **Cluster 下多 key 操作必须同槽**，用 **hash tag**：`user:{1001}:name` 与 `user:{1001}:age` 只对花括号里的 `1001` 算槽位，所以天然同槽。

> 📖 **原理、故障转移全时间线与 Cluster 重定向拆到 [高可用.md](高可用.md)**：`repl-diskless-sync-delay` 默认让全量同步白等 5 秒（实测 173ms vs 5.86s）、backlog 溢出如何退化成全量（已复现：`sync_full:1`）、哨兵一次真实转移的完整时间线（sdown 5.27s → switch-master，旧主恢复后被自动降级）、MOVED 与 ASK 的逐步演示。

## 五、过期与内存淘汰

```bash
EXPIRE key 60 ; PEXPIRE key 60000 ; EXPIREAT key 1735689600   # 秒 / 毫秒 / 秒级时间戳
TTL key                  # 剩余秒数（-1 永久、-2 不存在）
```

| 删除策略 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **惰性删除** | 访问 key 时才检查是否过期 | 不浪费 CPU | 不被访问的 key 永不释放 |
| **定期删除** | 后台每秒 10 次**抽样**扫描过期字典并删除 | 兜住惰性删除的漏网之鱼 | 抽样而非全扫，可能有残留 |

**为什么不用定时器**：给每个 key 挂一个定时器，百万级 key 就要维护百万个定时任务，**内存与 CPU 开销不可接受**；抽样扫描是「用可控成本把过期 key 控制在低水位」的折中。

内存达到 `maxmemory` 且**新写入需要更多空间**时触发淘汰：

| 策略 | 淘汰范围 | 规则 |
|---|---|---|
| `noeviction` | — | 不淘汰，**写命令直接报错**（`DEL`/`GET` 仍可用） |
| `allkeys-lru` / `allkeys-lfu` / `allkeys-random` | 全库 | 分别淘汰最久未使用 / 访问频率最低 / 随机 |
| `volatile-lru` / `volatile-lfu` / `volatile-random` | 仅设了 TTL 的 key | 同上三种规则，但范围收窄 |
| `volatile-ttl` | 仅设了 TTL 的 key | 淘汰剩余存活时间最短的 |

**选型**：纯缓存、数据都可丢 → `allkeys-lru`；有冷热分层且要抗「批量扫描污染」→ `allkeys-lfu`；把 Redis 当存储用、数据不能丢 → `noeviction` + 扩容。策略细节与踩坑见 [淘汰策略.md](淘汰策略.md) 的第一节，以及 [缓存选型与容量.md](../../缓存/缓存选型与容量.md) 的第四节、[缓存问题与方案.md](../../缓存/缓存问题与方案.md) 的第三节。

## 延伸追问

- **单线程为什么还这么快？为什么不直接用多线程？** → 瓶颈在内存与网络 IO 而非 CPU，单线程省掉锁与上下文切换；多线程要引入锁，性能未必提升却大幅增加复杂度。6.0 的多线程**只加在网络 IO 上**。
- **缓存与数据库一致性怎么做？** → Cache Aside（先更新库、再删缓存）+ 延迟双删 / binlog 订阅（Canal）异步补偿 + TTL 兜底，见 [缓存问题与方案.md](../../缓存/缓存问题与方案.md) 的第一节与 [缓存选型与容量.md](../../缓存/缓存选型与容量.md) 的第一节。
- **底层结构、持久化细节、高可用机制分别在哪？** → 分别见 [底层结构.md](底层结构.md)、[持久化.md](持久化.md)、[高可用.md](高可用.md)。
- **`expire` 到期后 key 会立刻消失吗？** → 不会立刻，靠**惰性删除**（访问时才删）+ **定期删除**（抽样扫描）配合；可能读到尚未删除的过期 key，但 Redis 会按已过期处理并返回 `nil`。
