## 一、一句话定位与「为什么快」

Redis 是 **C 语言写的单进程内存 KV 数据库**，数据全在内存、命令用单线程处理，因此能把读写压到 **10 万级 QPS**（对比 MySQL 单连接约 500~2000 QPS，见 [缓存选型与容量.md](../../缓存/缓存选型与容量.md) 的第一节/第二节）。

| 快的原因 | 说明 |
|---|---|
| **纯内存操作** | 读写不进磁盘，没有磁盘 IO 与寻道开销 |
| **单线程处理命令** | 无锁、无上下文切换、无并发竞争；命令都是纳秒级纯内存操作，CPU 不是瓶颈 |
| **IO 多路复用** | `epoll` 单线程监听海量连接，事件就绪才处理，不阻塞在某个连接上 |
| **高效数据结构** | SDS、跳表、listpack、intset 按场景选型，空间与时间都做过优化（见第二节） |
| **自定义 RESP 协议** | 文本协议极简、解析成本低，配合 Pipeline 大幅减少 RTT |

「单线程」指的是**命令处理是单线程**。瓶颈若在 CPU 上，多线程才有意义；Redis 的瓶颈在**内存带宽与网络 IO**，单线程反而省掉了锁与竞争开销。

> ⚠️ 单线程的代价：**一个慢命令会阻塞所有请求**。`keys *`、`hgetall` 大 hash、`flushall` 这类 O(N) 命令是线上事故重灾区（见第九节）。

**6.0 的多线程改了什么**：只把**网络 IO**（读 socket、解析协议、写回结果）交给 IO 线程池，`io-threads 4` 解决的是「网络读写跟不上」，**命令执行与 Lua 仍是单线程**，所以 `keys *` 该阻塞还是阻塞。

## 二、五大数据结构与应用场景 ⭐

| 结构 | 底层实现 | 常用命令 | 典型场景 |
|---|---|---|---|
| **String** | SDS（简单动态字符串） | `SET` `GET` `INCR` `SETNX` `SETEX` `MSET` | 计数器、分布式锁、Session、缓存对象（序列化后存） |
| **Hash** | listpack（小）/ 哈希表（大） | `HSET` `HGET` `HGETALL` `HINCRBY` | 对象属性存储（用户资料、商品字段，可单字段读写） |
| **List** | quicklist（双向链表 + listpack） | `LPUSH` `RPUSH` `LPOP` `BRPOP` `LRANGE` `LTRIM` | 消息队列、最新 N 条列表、时间线 |
| **Set** | intset（全整数小集合）/ 哈希表 | `SADD` `SREM` `SMEMBERS` `SINTER` `SISMEMBER` | 去重、共同好友、标签 |
| **ZSet** | listpack（小）/ 跳表 + 哈希表（大） | `ZADD` `ZRANGE` `ZREVRANGE` `ZSCORE` `ZRANGEBYSCORE` | 排行榜、延迟队列、按分数范围查询 |

```bash
# String：value 最大 512MB；存对象建议 JSON/Protobuf 整体存取，要字段级更新则用 Hash
SET user:1:name "tom" EX 600
INCR article:1:views                # 原子自增，天然适合计数
SETNX lock:order:1001 uuid-abc      # 不存在才写入 → 分布式锁基础
HSET user:1 name tom age 18         # Hash：字段少时底层是 listpack（连续内存、省空间）
HGET user:1 name                    # 只取单字段；HGETALL 字段多时慎用，会阻塞
LPUSH queue:mail "m1" "m2"          # List：RPOPLPUSH/LMOVE 可做可靠队列
BRPOP queue:mail 5                  # 阻塞式出队，FIFO；高可靠场景改用 Stream
SADD user:1:tags go redis docker    # Set：判断存在 O(1)，集合运算在服务端完成
SINTER user:1:friends user:2:friends   # 共同好友
ZADD rank:day 95 tom 88 jerry       # ZSet：跳表让插入与范围查询都是 O(logN)
ZREVRANGE rank:day 0 9 WITHSCORES   # 取 Top 10
ZRANGEBYSCORE delay:queue 0 1700000000   # 延迟队列：score = 执行时间戳
```

**补充结构的用途**：

| 结构 | 用途                                                                                                                 |
|---|--------------------------------------------------------------------------------------------------------------------|
| **Bitmap** | 位操作，签到打卡、活跃用户统计（`SETBIT` / `BITCOUNT`），1 亿用户仅约 12MB，详见 [位图与布隆过滤器.md](../../../../02-计算机基础/数据结构/高级数据结构/位图与布隆过滤器.md) |
| **HyperLogLog** | 基数估算，UV 统计，**12KB 估算上亿基数、误差约 0.81%**，不能取回元素                                                                        |
| **GEO** | 地理坐标，附近的人 / 门店（底层是 ZSet，score 为 geohash）                                                                           |
| **Stream** | 可持久化消息队列，自带消费者组与 ACK，定位接近 Kafka（详见 [发布订阅.md](发布订阅.md) 的第一节）                                                        |

## 三、持久化：RDB 与 AOF（速览）

**RDB 是「某一刻的内存快照」（二进制、文件小、恢复快、丢得多）；AOF 是「重建数据的命令日志」（丢得少、文件大、恢复慢）。** 7.0 起 AOF 默认带**混合持久化**：重写时前半段写成 RDB、后半段追加增量命令。

```conf
save 900 1 300 10 60 10000   # RDB：三个条件任一满足即触发；save "" 彻底关闭
appendonly yes               # AOF 开关
appendfsync everysec         # ⭐ 生产默认：最多丢 1 秒；always 不丢但慢一个数量级
aof-use-rdb-preamble yes     # 混合持久化（7.0 起默认）
```

**生产结论：两个都开** —— RDB 负责定时备份与主从全量同步，AOF 负责把丢失窗口压到 1 秒内。只做纯缓存、丢了能回源时，可只留 RDB 或全关。

⭐ **三档 `appendfsync` 的实测延迟**（本机 2000 条 SET，连跑 3 轮）：`always` 2508~2762 µs/条、`everysec` 215~245 µs/条、`no` 299~534 µs/条 —— **`always` 比 `everysec` 慢约一个数量级**，差的就是「每条命令后面多等一次磁盘同步」。

⚠️ **`BGSAVE` 与 `BGREWRITEAOF` 都要 `fork`**：实测 20 万 key 的实例 fork 只要 1.6ms，但**快照期间有写压力时 COW 会把内存峰值推高 54%**（29M → 44.68M）—— 大实例规划内存要按峰值算，不是按稳态数据量。

> 📖 **原理、实测与选型全部拆到 [持久化.md](持久化.md)**：`fork + COW` 的量化、三种 fsync 的崩溃恢复对照（RDB 全丢 vs AOF 一个不差）、AOF 重写的压缩比（10 万次 INCR → 一行 SET，25001:1）、混合持久化的文件头（`52 45 44 49 53` = `REDIS` 魔数）、7.0 的 MP-AOF 与 8.10 的 `BACKUP`。

## 四、高可用与集群（速览）

三个层次解决的是**不同问题**，不要混着选：

| 方案 | 解决什么 | 一句话机制 |
|---|---|---|
| **主从复制** | 读扩展 + 备份 | 从节点 `replicaof`；全量同步传 RDB，断线后靠 `repl-backlog` 增量补发 |
| **哨兵（Sentinel）** | 自动故障转移 | ≥3 个哨兵监控；先判主观/客观下线，再按 **优先级 → `repl_offset` 最大 → `runid` 最小** 选新主 |
| **Cluster** | 容量与写能力 | **16384 个槽**分片，`slot = CRC16(key) mod 16384`，每主可带一从 |

⭐ **复制是异步的**：主库写完就返回客户端，宕机会丢掉「还没同步过去」的那一段（本机实测大写入压力下最多落后 0.4MB 量级）。要「写进去就不丢」，得显式用 `WAIT` 或 `min-replicas-to-write` —— 用可用性换一致性。

⚠️ **两个最容易踩的点**：

1. **`sync_full` / `sync_partial_ok` / `sync_partial_err` 在 `INFO stats` 里，不在 `INFO replication`** —— 找错地方会一直读到空值；
2. **客户端必须通过哨兵地址取当前主节点**（`SENTINEL get-master-addr-by-name`），写死 IP 的话切换后就打到旧主了（旧主已变从节点，写入直接报 `READONLY`）。

⚠️ **Cluster 下多 key 操作必须同槽**，用 **hash tag**：`user:{1001}:name` 与 `user:{1001}:age` 只对花括号里的 `1001` 算槽位，所以天然同槽。

> 📖 **原理、故障转移全时间线与 Cluster 重定向拆到 [高可用.md](高可用.md)**：`repl-diskless-sync-delay` 默认让全量同步白等 5 秒（实测 173ms vs 5.86s）、backlog 溢出如何退化成全量（已复现：`sync_full:1`）、哨兵一次真实转移的完整时间线（sdown 5.27s → switch-master，旧主恢复后被自动降级）、MOVED 与 ASK 的逐步演示。

## 五、过期与内存淘汰

```bash
EXPIRE key 60 ; PEXPIRE key 60000 ; EXPIREAT key 1735689600   # 秒 / 毫秒 / 秒级时间戳
TTL key                  # 剩余秒数（-1 永久、-2 不存在）
```

| 删除策略 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **惰性删除** | 访问 key 时才检查是否过期 | 不浪费 CPU | 不被访问的 key 永不释放 |
| **定期删除** | 后台每秒 10 次**抽样**扫描过期字典并删除 | 兜住惰性删除的漏网之鱼 | 抽样而非全扫，可能有残留 |

**为什么不用定时器**：给每个 key 挂一个定时器，百万级 key 就要维护百万个定时任务，**内存与 CPU 开销不可接受**；抽样扫描是「用可控成本把过期 key 控制在低水位」的折中。

内存达到 `maxmemory` 且**新写入需要更多空间**时触发淘汰：

| 策略 | 淘汰范围 | 规则 |
|---|---|---|
| `noeviction` | — | 不淘汰，**写命令直接报错**（`DEL`/`GET` 仍可用） |
| `allkeys-lru` / `allkeys-lfu` / `allkeys-random` | 全库 | 分别淘汰最久未使用 / 访问频率最低 / 随机 |
| `volatile-lru` / `volatile-lfu` / `volatile-random` | 仅设了 TTL 的 key | 同上三种规则，但范围收窄 |
| `volatile-ttl` | 仅设了 TTL 的 key | 淘汰剩余存活时间最短的 |

**选型**：纯缓存、数据都可丢 → `allkeys-lru`；有冷热分层且要抗「批量扫描污染」→ `allkeys-lfu`；把 Redis 当存储用、数据不能丢 → `noeviction` + 扩容。策略细节与踩坑见 [淘汰策略.md](淘汰策略.md) 的第一节，以及 [缓存选型与容量.md](../../缓存/缓存选型与容量.md) 的第四节、[缓存问题与方案.md](../../缓存/缓存问题与方案.md) 的第三节。

## 六、部署

```yaml
services:
  redis:
    image: redis:7.4-alpine
    restart: always
    ports:
      - "127.0.0.1:6379:6379"      # ⚠️ 只绑本机，切勿 0.0.0.0 暴露公网
    # 生产务必改强密码；maxmemory 必须设置，否则会吃光宿主机内存
    command: >
      redis-server --requirepass your-strong-password
      --appendonly yes --appendfsync everysec
      --maxmemory 2gb --maxmemory-policy allkeys-lru
    volumes:
      - ./data:/data               # RDB / AOF 落盘，随容器重建保留
```

```bash
docker compose up -d
docker exec -it redis redis-cli -a your-strong-password ping   # → PONG
```

| 配置 | 说明 |
|---|---|
| `bind 127.0.0.1` | 监听地址，默认只本机；对外需谨慎并配合防火墙 |
| `protected-mode yes` | 未设密码且非本机访问时拒绝连接，**保持开启** |
| `requirepass` / `masterauth` | 访问密码；主从/哨兵场景两者要一致 |
| `maxmemory` / `maxmemory-policy` | 内存上限与淘汰策略，**不设上限等于埋雷**（触发宿主 OOM Kill） |
| `appendonly` / `appendfsync` | AOF 开关与落盘频率，见第三节 |
| `timeout` / `tcp-keepalive` | 空闲连接超时（秒）；keepalive 推荐 300，及时清理死连接 |
| `slowlog-log-slower-than` | 慢查询阈值（微秒），默认 10000 |

**生产必须注意**：

- **绝不暴露公网**：Redis 未授权访问是最常见入侵入口。`bind` 内网 IP + 安全组白名单 + `requirepass` 三者叠加。
- **禁用危险命令**：`KEYS`、`FLUSHALL`、`FLUSHDB`、`CONFIG` 重命名或屏蔽：

```conf
rename-command KEYS "" ; rename-command FLUSHALL "" ; rename-command CONFIG CONFIG_b9f2c1
```

- **必须设 `maxmemory`**，且容器内存上限要比它大（给 fork / COW / 缓冲区留余量，通常取容器上限的 60%~70%）。
- **开启持久化并异地备份 RDB**；容器化时要挂数据卷，否则重建容器数据即丢。

## 七、使用一：Go（go-redis v9）⭐

依赖：`github.com/redis/go-redis/v9`。

### 连接、连接池与超时

```go
rdb := redis.NewClient(&redis.Options{
	Addr:         "127.0.0.1:6379",
	Password:     "your-strong-password",
	DB:           0,
	PoolSize:     100,               // ⭐ 池上限，约「QPS × 平均RT」量级，几十~几百
	MinIdleConns: 10,                // 常备空闲连接，避免临时建连
	PoolTimeout:  2 * time.Second,   // 池满时等待连接的最长时间
	DialTimeout:  2 * time.Second,
	ReadTimeout:  1 * time.Second,
	WriteTimeout: 1 * time.Second,
	MaxRetries:   2,
})

// 启动自检：ctx 带超时，失败即暴露，别让服务「带病启动」
ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
defer cancel()
if err := rdb.Ping(ctx).Err(); err != nil { panic(err) }
```

### ⚠️ context 超时：必须传，否则请求堆积

go-redis 的**每个操作都接收 `ctx`**。若直接传 `context.Background()`，Redis 变慢或网络抖动时该 goroutine 会**无限等下去**，连接池被占满 → 后续请求拿不到连接 → **整条调用链雪崩**。

```go
func getWithTimeout(key string) (string, error) {
	ctx, cancel := context.WithTimeout(context.Background(), 300*time.Millisecond)
	defer cancel()
	return rdb.Get(ctx, key).Result()
}
```

> 更好的做法：复用上游 HTTP / RPC 请求传入的 ctx（天然带 deadline），而不是每层新造。

### 五种数据结构的常用操作

```go
func crud(ctx context.Context) {
	// String：缓存 / 计数
	rdb.Set(ctx, "user:1:name", "tom", 10*time.Minute)
	rdb.Incr(ctx, "article:1:views")
	// Hash：对象属性，可字段级读写
	rdb.HSet(ctx, "user:1", "name", "tom", "age", 18)
	age, _ := rdb.HGet(ctx, "user:1", "age").Int()
	// List：队列 / 最新列表
	rdb.LPush(ctx, "queue:mail", "m1", "m2")
	item, _ := rdb.BRPop(ctx, 5*time.Second, "queue:mail").Result() // 阻塞式出队
	rdb.LTrim(ctx, "feed:1", 0, 99)
	// Set：去重 / 集合运算
	rdb.SAdd(ctx, "user:1:tags", "go", "redis")
	common, _ := rdb.SInter(ctx, "user:1:friends", "user:2:friends").Result()
	// ZSet：排行榜 / 延迟队列（score = 执行时间戳）
	rdb.ZAdd(ctx, "rank:day", redis.Z{Score: 95, Member: "tom"})
	top, _ := rdb.ZRevRangeWithScores(ctx, "rank:day", 0, 9).Result()
	due, _ := rdb.ZRangeByScore(ctx, "delay:queue", &redis.ZRangeBy{
		Min: "0", Max: fmt.Sprint(time.Now().Unix()),
	}).Result()
	// ⭐ MGET 替代循环 GET：一次 RTT 取多个 key
	vals, _ := rdb.MGet(ctx, "user:1:name", "user:2:name").Result()
	_, _, _, _, _, _ = age, item, common, top, due, vals
}
```

### Pipeline：批量命令减少 RTT

```go
pipe := rdb.Pipeline()
incr := pipe.Incr(ctx, "counter")
pipe.Expire(ctx, "counter", time.Hour)
if _, err := pipe.Exec(ctx); err == nil { fmt.Println(incr.Val()) } // Exec 一次网络往返
```

> ⭐ Pipeline 只减少网络 RTT，**不保证原子性**（中间可能穿插其他客户端的命令）；需要原子性用 `TxPipeline`（底层 `MULTI/EXEC`）或 Lua。

### Lua 脚本：原子逻辑

```lua
-- rate_limit.lua：固定窗口限流，返回 1 放行、0 拒绝
local key, limit = KEYS[1], tonumber(ARGV[1])
local current = tonumber(redis.call('get', key) or "0")
if current + 1 > limit then return 0 end
redis.call('incr', key)
if current == 0 then redis.call('expire', key, tonumber(ARGV[2])) end
return 1
```

```go
import _ "embed"

//go:embed rate_limit.lua
var rateLimitScript string

// 脚本在 Redis 端单线程原子执行；KEYS 与 ARGV 分开传
res, err := rdb.Eval(ctx, rateLimitScript, []string{"limit:ip:" + ip}, 10, 60).Int()
```

> ⚠️ Lua 里**只能用 `KEYS[i]` 访问 key**，不要在脚本内动态拼接 key 名（Cluster 下无法正确路由，7.0 前非 `KEYS` 声明的 key 还会直接报错）。

### 分布式锁：SetNX + Lua 原子释放

```go
var unlockScript = redis.NewScript(`
if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) end
return 0
`)

func doWithLock(ctx context.Context) error {
	token := fmt.Sprintf("%d-%d", time.Now().UnixNano(), rand.Int63()) // 唯一标识

	// 加锁：SET NX，value 是只有自己知道的 token
	ok, err := rdb.SetNX(ctx, "lock:order:1001", token, 10*time.Second).Result()
	if err != nil || !ok {
		return fmt.Errorf("抢锁失败")
	}
	// 解锁：必须 defer；Lua 保证「校验 token + 删除」原子，防止误删别人的锁
	defer unlockScript.Run(ctx, rdb, []string{"lock:order:1001"}, token)

	return businessLogic(ctx)
}
```

> ⭐ 这只是**最小可用版**：TTL 到期而业务未完成、续期（watchdog）、主从切换丢锁等问题见 [分布式锁.md](分布式锁.md) 的第一节。

### Scan 代替 Keys

```go
// ❌ rdb.Keys(ctx, "user:*") —— O(N) 且阻塞单线程，生产禁用
var cursor uint64
for {
	batch, next, err := rdb.Scan(ctx, cursor, "user:*", 100).Result() // 游标分批返回
	if err != nil { break }
	handle(batch)
	if cursor = next; cursor == 0 { break }   // 游标回到 0 表示遍历完成
}
```

> `Scan` 的**增量保证**：遍历期间新增的 key 可能返回也可能不返回，已删除的不会返回；**重复返回是可能的**，业务侧要能容忍（做去重）。

## 八、使用二：Java

### Jedis vs Lettuce

| 维度 | Jedis | Lettuce |
|---|---|---|
| 模型 | **同步阻塞**，直连 Redis | **Netty 异步 / 响应式**，基于 NIO |
| 线程安全 | ❌ `Jedis` 实例**不线程安全**，必须用 `JedisPool` 每次取还 | ✅ `StatefulRedisConnection` **线程安全**，可多线程共用 |
| 连接管理 | 每次操作从池里取一个连接 | 一个连接即可支撑高并发（多路复用） |
| 集群/哨兵 | `JedisCluster` / `JedisSentinelPool` | `RedisClusterClient` / `RedisSentinelClient` |
| 适用 | 简单场景、老项目、命令式写法 | 高并发、需要异步/响应式、Spring Boot 项目（**2.x 起默认**） |

### Jedis：连接池 + 五结构 + Pipeline + Lua

```java
JedisPoolConfig config = new JedisPoolConfig();
config.setMaxTotal(100);                    // 最大连接数
config.setMaxIdle(20);
config.setMinIdle(10);
config.setMaxWait(Duration.ofSeconds(2));   // 池耗尽时的最大等待
config.setTestOnBorrow(true);               // 借出前 ping，剔除死连接
JedisPool pool = new JedisPool(config, "127.0.0.1", 6379, 2000, "your-strong-password");

try (Jedis jedis = pool.getResource()) {    // try-with-resources 自动归还
    jedis.setex("user:1:name", 600, "tom");                   // String
    jedis.incr("article:1:views");
    jedis.hset("user:1", Map.of("name", "tom", "age", "18"));  // Hash
    jedis.lpush("queue:mail", "m1");                           // List
    jedis.sadd("user:1:tags", "go", "redis");                  // Set
    jedis.zadd("rank:day", 95, "tom");                         // ZSet
    List<String> top = jedis.zrevrange("rank:day", 0, 9);

    // Pipeline：批量命令，一次 RTT
    Pipeline p = jedis.pipelined();
    Response<Long> incr = p.incr("counter");
    p.expire("counter", 3600);
    p.sync();                                                  // 真正发出并等待全部返回

    // 分布式锁：SET NX 加锁 + Lua 原子释放
    jedis.set("lock:order:1001", token, SetParams.setParams().nx().ex(10));
    jedis.eval("if redis.call('get', KEYS[1]) == ARGV[1] then " +
               "  return redis.call('del', KEYS[1]) end return 0",
               Collections.singletonList("lock:order:1001"),
               Collections.singletonList(token));
}
```

### Lettuce：线程安全 + 异步

```java
RedisClient client = RedisClient.create("redis://:your-strong-password@127.0.0.1:6379/0");
StatefulRedisConnection<String, String> conn = client.connect();   // ⭐ 可多线程复用

RedisCommands<String, String> sync = conn.sync();
sync.setex("user:1:name", 600, "tom");
sync.hset("user:1", "name", "tom");
sync.zadd("rank:day", 95, "tom");

// 异步：不阻塞调用线程，用 CompletableFuture 组合
conn.async().set("k1", "v1").thenCompose(v -> conn.async().get("k1"))
    .thenAccept(System.out::println);

conn.close(); client.shutdown();
```

### Spring Data Redis：RedisTemplate 与序列化器 ⚠️

**默认 `RedisTemplate` 用 JDK 序列化**，写进去的是带类名的二进制，`redis-cli` 里全是乱码、跨语言不可读、体积也大，必须显式换成 String + JSON。

```java
@Bean
public RedisTemplate<String, Object> redisTemplate(RedisConnectionFactory factory) {
    RedisTemplate<String, Object> tpl = new RedisTemplate<>();
    tpl.setConnectionFactory(factory);

    StringRedisSerializer keySer = new StringRedisSerializer();   // key：字符串，可读
    // ⚠️ 默认 JDK 序列化不可读；value 统一换成 JSON 序列化器
    GenericJackson2JsonRedisSerializer valSer = new GenericJackson2JsonRedisSerializer();

    tpl.setKeySerializer(keySer);
    tpl.setHashKeySerializer(keySer);
    tpl.setValueSerializer(valSer);
    tpl.setHashValueSerializer(valSer);
    tpl.afterPropertiesSet();
    return tpl;
}
```

| 序列化器 | 特点 | 建议 |
|---|---|---|
| `JdkSerializationRedisSerializer` | 默认；二进制、体积大、不可读 | ❌ 不要用 |
| **`StringRedisSerializer`** | 纯字符串，可读、跨语言 | ✅ **key / hashKey 必选** |
| **`GenericJackson2JsonRedisSerializer`** | JSON、带类型信息、反序列化自动还原类型 | ✅ value 首选 |
| `Jackson2JsonRedisSerializer<T>` | JSON，但**必须指定固定类型**，否则易反序列化成 `LinkedHashMap` | 类型固定时可用 |

> **`StringRedisTemplate`** 是开箱即用版本，key/value 均为 `StringRedisSerializer`，纯字符串场景（计数器、token）直接用，无需自配 Bean。

```java
redisTemplate.opsForValue().set("user:1:name", "tom", Duration.ofMinutes(10)); // String
redisTemplate.opsForValue().increment("article:1:views");
redisTemplate.opsForHash().put("user:1", "age", 18);                           // Hash
redisTemplate.opsForList().leftPush("queue:mail", "m1");                       // List
redisTemplate.opsForSet().add("user:1:tags", "go", "redis");                   // Set
redisTemplate.opsForZSet().add("rank:day", "tom", 95);                         // ZSet

// 分布式锁：Lua 原子释放
Long r = redisTemplate.execute(new DefaultRedisScript<>(
        "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) end return 0",
        Long.class), Collections.singletonList(key), token);
```

## 九、生产实践与坑

| 坑 | 后果 | 处理 |
|---|---|---|
| **大 key**（value 几 MB、hash 上百万字段） | 单次操作阻塞主线程、网络打满、删除也阻塞 | 拆成多个小 key；用 `HSCAN`/`SSCAN` 分批处理；删除用 `UNLINK` 替代 `DEL`；巡检用 `--bigkeys` |
| **热 key** | 单节点被打满、集群倾斜 | 多副本打散 + 本地缓存兜底，细节见 [缓存问题与方案.md](../../缓存/缓存问题与方案.md) 的第二节 |
| **`keys *`** | O(N) 全库扫描，**直接阻塞单线程** | 一律用 `SCAN` 游标遍历；配置层 `rename-command KEYS ""` 彻底禁掉 |
| **Pipeline 误当事务** | 以为有原子性，实际中间可能穿插其他命令 | 需原子用 `MULTI/EXEC`（`TxPipeline`）或 Lua；⚠️ Redis 事务**不支持回滚**，只能打包顺序执行 |
| **Lua 脚本过长** | 执行期间**阻塞所有命令**（超 `busy-reply-threshold` 会记日志） | 脚本保持短小、逻辑简单；避免 O(N) 遍历；绝不写死循环 |
| **主从切换丢数据** | 异步复制下主节点宕机，未同步的写丢失 | `min-replicas-to-write 1` + `min-replicas-max-lag 10`：**健康从节点不足则拒绝写入**，用可用性换一致性 |
| **内存碎片 / 连接数暴涨** | 碎片率长期 > 1.5 则实际占用远大于数据量；连接未复用或未设超时则池被打爆 | 碎片开 `activedefrag yes` 或低峰期重建；连接复用客户端单例并设 `PoolSize` 上限、`PoolTimeout`、`timeout` |
| **慢查询未监控** | 线上卡顿无法定位到具体命令 | 常查 `SLOWLOG GET 10`；`slowlog-log-slower-than` 线上常见设为 10000μs |

```bash
redis-cli -a pwd slowlog get 10                                   # 慢查询
redis-cli -a pwd info memory | grep -E "used_memory_human|mem_fragmentation_ratio"
redis-cli -a pwd --bigkeys        # 大 key 巡检，⚠️ 线上低峰执行
redis-cli -a pwd monitor          # ⚠️ 略有性能损耗，短时使用
```

> ⚠️ **`min-replicas-to-write` 的取舍**：从节点掉线时会**拒绝写入**，用「宁可写不进去」换「写进去就不会丢」。账务等强一致场景值得，纯缓存场景则不必。

## 十、延伸追问

- **单线程为什么还这么快？为什么不直接用多线程？** → 瓶颈在内存与网络 IO 而非 CPU，单线程省掉锁与上下文切换；多线程要引入锁，性能未必提升却大幅增加复杂度。6.0 的多线程**只加在网络 IO 上**。
- **缓存与数据库一致性怎么做？** → Cache Aside（先更新库、再删缓存）+ 延迟双删 / binlog 订阅（Canal）异步补偿 + TTL 兜底，见 [缓存问题与方案.md](../../缓存/缓存问题与方案.md) 的第一节与 [缓存选型与容量.md](../../缓存/缓存选型与容量.md) 的第一节。
- **底层结构、持久化细节、高可用机制分别在哪？** → 分别见 [数据结构.md](数据结构.md)、[持久化.md](持久化.md)、[高可用.md](高可用.md)。
- **`expire` 到期后 key 会立刻消失吗？** → 不会立刻，靠**惰性删除**（访问时才删）+ **定期删除**（抽样扫描）配合；可能读到尚未删除的过期 key，但 Redis 会按已过期处理并返回 `nil`。
- **Lua 和 MULTI/EXEC 该用哪个？** → 需要**读-改-写**的原子逻辑（限流、原子解锁）用 **Lua**；只是打包一批命令、无需条件判断，用 **Pipeline / MULTI** 更省事。二者都**不支持回滚**。
