# Redis 多核利用与部署方案

> Redis 的命令处理是单线程，一个实例最多只能吃满一个核 —— 那多核机器怎么办？本文把「单机多实例」与「Redis Cluster」两条路的**实现方式、优缺点、适用场景**讲清，并把「单实例到底能吃几个核」「多实例能不能线性叠加」「io-threads 能不能突破单核」全部在本机容器里量出来。
>
> 内容整理自个人学习笔记，并参考《Redis 设计与实现》（黄健宏）的第 12 章「事件」与第 17 章「集群」。原书以 Redis 3.0 为准，文中标 ⚠️ 处为 3.0 之后的变化（尤其 6.0 的多线程 IO）。相关篇章：[数据结构.md](数据结构.md)、[持久化.md](持久化.md)、[高可用.md](高可用.md)；容量视角的扩容见 [缓存选型与容量.md](../../缓存/缓存选型与容量.md)。

## 一、前提：单线程卡在哪，为什么多核帮不上忙

「Redis 单线程」指的是**命令的执行**由一个主线程串行完成：从 `epoll` 拿到就绪的连接、解析 RESP、查字典、改数据结构、回写结果，全部在一条线程上跑。这么做的好处是没有锁、没有上下文切换、没有并发竞争（见 [命令与使用.md](命令与使用.md) 第一节）。

代价同样明确：**这条线程的执行速度就是整个实例的吞吐上限**。多核机器给了 8 个、16 个核，Redis 一个实例也只会用其中一个 —— 剩下的核在空转。

### 1.1 实测：单实例能用几个核

起一个**不做任何 CPU 限制**的实例（宿主 Docker Desktop 分配了 4 核），用 `redis-benchmark -t set` 从外部容器压满，取加载稳定后的 CPU 斜率（Redis 进程 `INFO cpu` 的 `used_cpu_sys + used_cpu_user`）：

| 负载 | 稳态 CPU | 聚合 SET rps |
|---|---|---|
| 2 客户端 · pipeline 32 | **0.96 核** | 281673 |
| 6 客户端 · pipeline 32 | **0.76 核** | 276900 |
| 2 客户端 · pipeline 32（跑更久） | **0.87 核** | 380511 |
| 客户端放进容器内走 loopback | **0.66 核** | 348614 |

```text
多次采样的区间：0.66 ~ 0.96 核
```

⭐ **两条判据**：

1. **封顶在 1 核附近**，宿主有 4 核也上不去 —— 这就是单线程模型的天花板。
2. ⚠️ **客户端从 2 个加到 6 个，rps 不涨反而略降**（281673 → 276900）。说明瓶颈已经从「客户端压不动」转移到了「服务端执行不完」，再加压没有意义。

> ⚠️ **口径说明**：0.66~0.96 是个区间，不是精确值。同一配置连跑会波动（容器 CPU 配额、宿主调度、客户端与被测实例抢核都会影响）。**要记住的不是某个数，而是「封顶约 1 核」这个量级。**

### 1.2 顺带排掉一个误解：`io-threads` 不是「多核版 Redis」

6.0 引入的 `io-threads` 常被误读成「Redis 支持多线程了」。它只把**网络读写**（读 socket、解析协议、回写结果）交给 IO 线程池，**命令执行仍然单线程**。本机实测它在本场景下反而是负收益：

| 配置 | 稳态 CPU | rps |
|---|---|---|
| `io-threads 1` · 50 客户端 · pipeline 32 | 0.87 核 | 380511 |
| `io-threads 4` · 50 客户端 · pipeline 32 | **2.60 核** | **157394** |
| `io-threads 1` · 500 客户端 · 无 pipeline | 0.91 核 | 32795 |
| `io-threads 4` · 500 客户端 · 无 pipeline | **1.85 核** | **18313** |

两组负载下 `io-threads 4` 都**多烧了 0.9~1.7 个核，吞吐却掉了 40%~44%**。

⭐ **判据**：`io-threads` 的收益前提是「Redis 自己的网络读写是瓶颈」。本机瓶颈其实落在 Docker Desktop 的网络代理层（容器间往返延迟很高，见 2.2），此时额外的 IO 线程只增加线程间同步与切换开销。**在网络不是瓶颈的场景里，把 `io-threads` 调大是纯粹的浪费。**

> ⚠️ `io-threads` / `io-threads-do-reads` 都是**不可运行时修改**的配置（`CONFIG SET` 报 `can't set immutable config`），只能写进配置文件或命令行重启。

结论：**要真正用上多核，只能让「多个 Redis 进程」同时跑** —— 要么在一台机器上起多个实例，要么用 Cluster 把实例摊到多台机器。

## 二、方案一：单机多实例（垂直扩展）

### 2.1 实现方式

同一台机器上起 N 个 `redis-server`，各自：

- **独立端口**（6379 / 6380 / …）或独立的 unix socket；
- **独立配置文件与数据目录**（`dir`、`dbfilename`、`appendonlydir` 必须分开，否则互相覆盖）；
- ⚠️ **各自设置 `maxmemory`**。这是最容易漏的一条：N 个实例**共享同一份物理内存**，如果每台都按「整机内存」去配，写满时会被 OS OOM Killer 直接杀掉。**N 个实例的 `maxmemory` 之和必须留出余量**（还要算上每个实例的 `fork` 时 COW 开销，见 [持久化.md](持久化.md)）；
- **绑定到指定 CPU 核**（Linux 下 `taskset -c`，容器下 `--cpuset-cpus`），避免多个实例在核之间来回漂移、互相抢；

客户端侧通常再配一层代理（`twemproxy` / `codis` / 自研路由）或用一致性哈希 SDK，把请求分到不同实例。

```bash
# 同一台机器起 4 个实例，每个绑一个核
for i in 0 1 2 3; do
  taskset -c $i redis-server /etc/redis/redis-$i.conf \
    --port 637$i --dir /data/redis-$i --maxmemory 4gb
done
```

### 2.2 实测：多实例能不能叠加

同样在 4 核宿主上，把实例分别限到 1 核，用外部客户端同时压：

| 实例数 | 各实例稳态 CPU | **合计 CPU** | 聚合 SET rps |
|---|---|---|---|
| 1 | 0.96 | 0.96 | 281673 |
| 2 | 0.85 + 0.72 | **1.57** | 326633 |
| 4 | 0.40 × 4 | **1.72** | 307654 |

把客户端放进各实例容器内走 loopback（绕开容器网络）再测：

| 实例数 | **合计 CPU** | 聚合 SET rps |
|---|---|---|
| 1 | 0.66 | 348614 |
| 2 | **1.44** | 381436 |
| 4 | **≈ 1.50** | 642142 |

⭐ **能读出什么、不能读出什么**：

- ✅ **合计 CPU 确实随实例数上升**（0.96 → 1.57 → 1.72 核）—— 多实例确实把活分给了多个线程/核。
- ⚠️ **但本机看不到「4 实例 = 4 核」的线性叠加**。原因有两个，都很实在：
  1. **宿主只有 4 核**，而 N 个实例之外还要养 N 个压测客户端，客户端和目标实例在同一批核里互相抢；
  2. **Docker Desktop 的容器网络有个 ~40 万 rps 的总量天花板**，压测路径上的聚合吞吐根本到不了单实例的 N 倍（`-P 32` 单实例就能到 38 万，2 实例合计只有 32~38 万）。

> ⭐ **这正是「多实例方案的上限由宿主核数决定」的直接体现**：一台 8 核机器上起 4 个实例，如果还跑着客户端、监控、其他服务，实际能给 Redis 的核远小于 8。**规划时不是「起几个实例」，而是「这台机器能给 Redis 留几个核」。**

### 2.3 优缺点

| | 说明 |
|---|---|
| ✅ **不改客户端** | 客户端看到的还是一个个独立的单机 Redis，不需要处理 MOVED/ASK 重定向，多 key 操作（`MGET`、Lua、`MULTI`）也不受槽约束 |
| ✅ **部署简单** | 不用组网、不用建槽、不用理解集群协议 |
| ✅ **单机可控** | 一个实例出问题不影响其他实例（记得配好各自的 `maxmemory`） |
| ⚠️ **容量不叠加** | N 个实例是 N 份独立数据，**不是一份数据摊开**；要靠客户端自己分片（一致性哈希），扩容时数据迁移得自己做 |
| ⚠️ **故障域不隔离** | 全在同一台机器上：这台挂了，N 个实例一起挂。**它解决的是 CPU，不是可用性**（可用性归 [高可用.md](高可用.md)） |
| ⚠️ **运维面变 N 倍** | N 份配置、N 份监控、N 份持久化文件、N 份内存账 |
| ⚠️ **不能无限加** | 受限于单机核数与内存；实例太多时 `fork`、上下文切换的开销也开始显现 |

### 2.4 适用场景

- **单机性能压榨**：一台大内存机器，想把 CPU 也用满（典型是「内存足够、瓶颈在 QPS」的场景）；
- **读写分离之外的补充**：主从解决读扩展，多实例再解决单实例写与吞吐上限；
- **不想引入集群复杂度**，且业务能接受客户端侧做分片（或有现成代理层）；
- **多租户/多业务共机**：不同业务线各用一个实例，互相隔离（但记得各自 `maxmemory`）。

## 三、方案二：Redis Cluster（水平扩展）

### 3.1 实现方式

Cluster 把**数据按 key 分片**到多个主节点，每个主节点仍是**一个独立的单线程 Redis 实例**：

- **16384 个槽**（slot），每个键经 `CRC16(key) mod 16384` 落到某个槽，每个槽归属一个主节点；
- **客户端路由**：客户端算槽 → 直连对应节点；发错节点时收到 `MOVED`（槽已永久变更，更新本地映射）或 `ASK`（槽正在迁移，仅本次转发）；
- **多 key 必须同槽**：`MGET`、Lua 等涉及多个 key 的操作，要么同槽、要么用 **hash tag**（`user:{1001}:name` 里的 `{1001}` 决定槽）把它们约束到一起，否则报 `CROSSSLOT`；
- **故障转移**：每个主节点挂若干从节点，主挂了由集群内部选举提升从节点（不需要哨兵）。

> 槽、`MOVED`/`ASK`、hash tag、以及一次真实的槽迁移，在 [高可用.md](高可用.md) 第四节已经逐条实测过，这里不重复。**本节只讲它与「多核利用」相关的部分。**

### 3.2 实测：负载真的被摊开了吗

起 3 主 3 从（`cluster_state:ok`，16384 槽全覆盖），用一个会做集群路由的客户端持续写入：

```text
集群分片数（主节点数）= 3
redis-c1 DBSIZE = 192271
redis-c2 DBSIZE = 185542
redis-c3 DBSIZE = 174827
```

⭐ **三个主节点的 key 数偏差小于 9%** —— 负载确实被均摊到了 3 个独立实例上。因为每个主节点都是一个独立进程，**3 个主节点在 CPU 上就等价于「单机 3 实例」**：各自单线程、各自最多吃 1 核，合计上限 ≈ 3 核（跨机部署时就是 3 台机器各 1 核）。

### 3.3 ⚠️ 实测踩到的一个部署坑：节点宣告了过期 IP

容器重启后，集群**一度不可用**：客户端连上种子节点拿到拓扑后，却对 `172.25.0.16` / `172.25.0.17` 疯狂重试：

```text
redis: connection pool: failed to dial after 5 attempts:
  dial tcp 172.25.0.16:6379: connect: no route to host
```

查下来，`redis-c2` 认为自己是 `172.25.0.16`、`redis-c3` 认为自己是 `172.25.0.17` —— 都是**容器上一轮运行时的旧 IP**。用三个主节点各自的 `CLUSTER SHARDS` 一比对就暴露了：

```text
redis-c1 视图: 172.25.0.2 172.25.0.3 172.25.0.4 172.25.0.5 172.25.0.6 172.25.0.7   ← 正确
redis-c2 视图: 172.25.0.16 172.25.0.2 172.25.0.4 ...                              ← 自己那项是旧 IP
redis-c3 视图: 172.25.0.17 172.25.0.2 172.25.0.3 ...                              ← 同上
```

**修法**：显式告诉每个节点自己该宣告哪个地址（该参数支持运行时修改）：

```bash
redis-cli CONFIG SET cluster-announce-ip <本节点当前 IP>
# 收敛后三节点视图一致
```

⭐⭐ **这是一条必须记住的生产判据**：**容器 / K8s 里 Pod 的 IP 是会变的，而 Redis Cluster 节点的「自我宣告地址」默认由它自己探测，重启后可能仍报旧值**。任何「Redis Cluster 跑在容器里」的部署都要显式配 `cluster-announce-ip`（K8s 下配合 Service/Headless Service 用固定 DNS 名更稳），否则表现就是**集群自身 `cluster_state:ok`、但客户端连不上** —— 非常难查。

### 3.4 优缺点

| | 说明 |
|---|---|
| ✅ **容量与吞吐都能横向扩** | 数据摊到 N 主节点，内存与 CPU 一起加（[缓存选型与容量.md](../../缓存/缓存选型与容量.md) 第 4.4 节的容量视角） |
| ✅ **内建故障转移** | 不需要哨兵；主挂了集群自己选新主 |
| ✅ **能跨机** | 真正突破单机上限，多实例做不到的它做到了 |
| ⚠️ **客户端复杂** | 必须处理 `MOVED`/`ASK` 重定向、维护槽映射；`SELECT` 不可用（只有 db 0）、`KEYS`/`SCAN` 语义变了 |
| ⚠️ **多 key 受槽约束** | 跨槽的 `MGET`、Lua、事务不可用，要设计 hash tag；⚠️ tag 选不好会把流量压到单个槽 |
| ⚠️ **槽迁移有代价** | 扩容/缩容时搬槽，期间有 `ASK` 重定向、`MIGRATE` 阻塞 |
| ⚠️ **运维最重** | 组网、槽分配、扩缩容、节点地址管理，都要专门的工具与流程 |

### 3.5 适用场景

- **单机内存放不下** 或 **单主写 QPS 扛不住**，必须跨机；
- 数据量/并发会持续增长，需要**能水平扩**的架构；
- 团队有能力维护集群客户端与运维流程（否则维护成本会反噬）。

## 四、三条路怎么选

| 维度 | 单机多实例 | Redis Cluster |
|---|---|---|
| **解决什么** | 单机 CPU/吞吐 | 单机 CPU + **容量 + 可用性** |
| **数据是否分片** | 不分（N 份独立数据，靠客户端分） | **分（16384 槽）** |
| **能否跨机** | ❌ 只能吃一台机器的核 | ✅ |
| **客户端复杂度** | 低（或用代理） | 高（重定向 + 槽映射） |
| **多 key 操作** | 自由 | ⚠️ 必须同槽 |
| **故障转移** | ❌（要另配主从+哨兵） | ✅ 内建 |
| **运维成本** | 低 | 高 |
| **典型场景** | 单机内存够、只想把核用满 | 数据/并发要持续扩、要跨机 |

**选型判据（按顺序问自己）**：

1. **单机放得下吗？**
   - 放得下，且只是 CPU/QPS 压不上去 → **单机多实例**（再配主从+哨兵保可用）。
   - 放不下，或单主写 QPS 到顶 → **上 Cluster**。
2. **业务能做客户端分片吗？** 不能、又不想上代理 → 优先多实例 + 代理，或直接 Cluster（用成熟的集群 SDK）。
3. **要不要跨机容灾？** 要 → Cluster（或「多实例 + 主从 + 哨兵」的组合，但复杂度未必更低）。

> ⚠️ **别忘了留核**：无论哪条路，Redis 之外还有客户端、监控、持久化 `fork`、其他服务。**规划的是「能给 Redis 几个核」，不是「机器有几个核」。**

## 使用：部署要点速查

```bash
# ---- 单机多实例：各自独立的配置要点 ----
port 6380                      # 每个实例不同端口
dir /data/redis-6380           # ⚠️ 数据目录必须分开
dbfilename dump-6380.rdb       # ⚠️ RDB 文件名必须分开
appendonlydir /data/redis-6380/aof
maxmemory 4gb                  # ⚠️ 每个实例单独设！N 个实例共享物理内存
maxmemory-policy allkeys-lru
save ""                        # 纯缓存场景可关掉 RDB

# 绑核启动（Linux）
taskset -c 2 redis-server /etc/redis/redis-6380.conf

# 看某个实例用了多少核（累计 CPU 秒 ÷ 墙钟秒）
redis-cli -p 6380 INFO cpu | grep -E '^used_cpu_(sys|user):'

# ---- Cluster：节点地址（容器/K8s 必配）----
cluster-enabled yes
cluster-config-file nodes.conf
cluster-node-timeout 5000
cluster-announce-ip 10.0.0.11     # ⚠️ 容器里必须显式指定，否则重启后可能宣告旧 IP
cluster-announce-port 6379
cluster-announce-bus-port 16379

# 运行时修正（已上线的集群）
redis-cli CONFIG SET cluster-announce-ip <当前 IP>

# ---- 集群体检 ----
redis-cli CLUSTER INFO | grep -E 'cluster_state|cluster_size'
redis-cli CLUSTER SHARDS            # 对比各节点视图里的 IP 是否一致（查 3.3 那个坑）
redis-cli CLUSTER KEYSLOT mykey     # 算某个 key 落哪个槽
redis-cli --cluster check host:port # 槽覆盖与一致性

# ---- io-threads（只在网络确实是瓶颈时才开，且不可运行时改）----
io-threads 4
io-threads-do-reads yes
```

## 延伸追问

- **单线程为什么还能做到 10 万级 QPS？为什么不多线程？** → 瓶颈在内存带宽与网络 IO，不在 CPU；单线程省掉了锁与上下文切换，多线程反而要引入锁且未必更快。6.0 的多线程**只加在网络 IO 上**，命令执行仍是单线程（第一节实测 `io-threads 4` 在本机反而更慢）。
- **一台 8 核机器上，Redis 应该起几个实例？** → 不是「8 个」。要扣掉客户端、监控、`fork` 时的 COW、其他服务的开销，**按「能给 Redis 留几个核」来定**；还要按 `maxmemory` 分摊总内存（N 个实例共享物理内存，任一实例写满不能拖垮全局）。
- **单机多实例能不能替代 Cluster？** → CPU 上能，**容量和可用性上不能**。N 个实例是 N 份独立数据，不是一份摊开；且全在一台机器上，故障域不隔离。
- **`io-threads` 该开吗？** → 判据是「Redis 自身网络读写是不是瓶颈」。用 `INFO cpu` 看 `used_cpu_sys` 占比、或在大 value / 高连接数 / 万兆网卡场景下测。本机实测（容器网络反而是瓶颈）开了是**纯亏**。
- **Cluster 的主节点挂了，多久恢复？** → 由 `cluster-node-timeout` 与从节点选举决定，机制与哨兵类似（[高可用.md](高可用.md) 第 3.2 节有一次完整的哨兵转移时间线可对照）。
- **为什么容器里的 Cluster 老是「状态正常但连不上」？** → 大概率就是 3.3 那个坑：节点宣告了过期 IP。用 `CLUSTER SHARDS` 逐个节点比对 IP，不一致就 `CONFIG SET cluster-announce-ip`。
