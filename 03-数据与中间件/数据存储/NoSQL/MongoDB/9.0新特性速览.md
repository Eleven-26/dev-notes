# MongoDB 9.0 新特性速览

> MongoDB 9.0（9.0.0 于 **2026-09-28** 发布）在加密、查询与聚合、校验与运维四类上的变化，
> 以及升级前必须回归的兼容性变更；末尾附一节「网上流传但不在 Release Notes 里」的说法核对。
>
> 内容整理自个人学习笔记，事实取自 MongoDB 官方 9.0 Release Notes（本机 `mongo:7.0` 无法运行 9.0 特性，
> 因此**本篇无本机实测读数**，均为官方原文口径）。

---

## 一、9.0 在加密上有什么变化？

**本节要点**：加密字符串字段的**前缀 / 后缀 / 子串查询正式 GA**；`mongocryptd` 被弃用，改走 Automatic Encryption Shared Library。

- ⭐ **QE 前缀 / 后缀 / 子串查询 GA**：可在加密字符串字段上做子串类查询；用 `mongosh` 时需单独下载 **Automatic Encryption Shared Library 9.0+** 并指定路径。
- ⚠️ **`mongocryptd` 弃用（9.0 起）**：改用 Automatic Encryption Shared Library，不再需要单独启动进程。
- 新增 `useInternalAuthzForX509` 参数：X.509 认证的客户端即便配了 LDAP 授权也走内部授权。
- `usersInfo` 新增 `authenticatedMechanism` 字段，用于指定查授权信息时用哪个认证后端。
- 审计日志新增 `directRemote`（`mongo` schema）与 `direct_endpoint`（OCSF schema）字段，记录会话的真实 TCP 对端，不受 PROXY protocol 头影响。

## 二、9.0 在查询与聚合上有什么变化？

**本节要点**：核心是**给单次操作加内存上限**、**默认开启 `$queryStats` 采样**，以及一批按「查询形状」生效的新设置。

### 2.1 ⭐ 单次操作内存上限

- 9.0 起限制**单个查询操作**可用的总内存：默认取 **1 GB 或服务端进程可用内存的 20%（取大者）**。
- 超限报 `ExceededMemoryLimit` 或 `QueryExceededMemoryLimitNoDiskUseAllowed`。
- 单个 stage 的 100 MB 上限与溢盘（spill to disk）行为**不变**——新增的是**整条操作**的全局上限。
- 影响：以前「靠大内存硬跑」的排序 / 聚合可能开始失败，升级前要回归这类查询（必要时 `allowDiskUse`）。

### 2.2 `$queryStats` 默认开启

- 9.0 起对读写操作**默认采样**收集统计：读写采样率参数默认均为 `0.01`（即 1%）。
- 输出结构改组：`metrics.cursor` / `metrics.queryExec` / `metrics.queryPlanner` / `metrics.writes`。
- 统计范围扩展到 `update` / `insert` / `delete` 命令。
- ⚠️ 因为它只报**被采样到**的操作，其输出是全部操作的一个子集，别当成全量账本。

### 2.3 按「查询形状」生效的新设置

| 能力 | 说明 |
| --- | --- |
| `querySettings` 作为命令字段 | 可直接传给 `find` / `distinct` / `aggregate`，**只对这次执行生效**，不落库、不影响同形状的其他查询；与集群级设置冲突时以集群级为准 |
| `queryKnobs` | 针对**单个查询形状**覆盖内部服务端参数，需要 FCV 9.0+ |
| 每形状 `maxTimeMS` | 用 `setQuerySettings` 给单个查询形状设超时，需要 FCV 9.0+ |

### 2.4 点号路径与 `null` 的比较语义变了

9.0 起，**点号路径未解析到非 null 值即视作 `null`**（例如路径中字段是空数组、标量数组或含嵌套数组）；
`$eq` / `$ne` / `$in` / `$nin` / `$gte` / `$lte` 与 `$lookup` 的等值匹配都遵循新语义 → 相关查询升级后结果可能不同。

## 三、9.0 在校验、运维与复制上有什么变化？

**本节要点**：schema 校验新增 `constraint` 级别、并发多文档事务有了上限、服务端 JS 以 WASM 引擎回归；

分片与复制的可观测性都补齐了进度类指标。

### 3.1 校验

- ⭐ **新增 `constraint` 校验级别**：校验规则作用于**所有插入与更新**，并保证集合内**每个文档**都满足规则（比 `strict` 更强）。
- BSON 校验默认开启：`net.wireObjectCheck` 配置项及 `--objcheck` / `--noobjcheck` 被弃用，服务端默认校验所有摄入的 BSON，非法数据直接报错。

### 3.2 运维与并发

- ⚠️ **并发多文档事务上限**：默认 `maxConcurrentMultiDocumentTransactions = 10000`，超出返回 `TooManyOpenTransactions`。高并发写事务的业务要评估。
- ⭐ **服务端 JavaScript 恢复**：`$accumulator` / `$function` / `$where` 不再弃用，改用 **WASM** 引擎执行，沙箱隔离更强（此前 8.0 已弃用）。注意 `ppc64le` 架构不支持。
- 新增 `sessionCatalogPartitions` 参数（9.0.1）：分区化 session 目录，降低大量会话下的锁争用。
- 时序集合：底层改为**单命名空间**存储（不再是可写的非物化视图），支持 `renameCollection`；⚠️ 单库超 5000 个时序集合时升级会更慢。

### 3.3 分片与复制的可观测性

- 分片：新增 `sh.shardDrainingStatus()`、`sh.getTransitionToDedicatedConfigServerStatus()`；`checkMetadataConsistency` 增加不一致类型与 `performStrictChunkChecksIfBelowThreshold`（大集合走轻量比对）。
- 复制：逻辑初始同步期间，`replSetGetStatus.initialSyncStatus` 暴露 `phase` / `totalAttempts` / `bytesPerSecond`，每次尝试还带 `phaseDurations`。
- 诊断：`2dsphere` 索引键提取失败改为具名错误码 `510`（`GeoKeyExtractionFailed`）与 `511`；失败插入 / 建索引会带 `writeErrors[].errInfo` 明细。
- 换流：新增一批 `metrics.changeStreams.cursor.*` 指标与 `currentOp.cursor.changeStreams.optime`（换流游标在 oplog 中的位置）。

### 3.4 被重命名的指标

- `metrics.changeStreams.showExpandedEvents` → `metrics.changeStreams.option.showExpandedEvents`；
- `shardingStatistics.databaseVersionUpdateCounters`（8.3 引入）→ `shardingStatistics.databaseShardingMetadataStatistics`，且字段集整体更换。
- ⚠️ 按名字采集指标的监控要同步改名，否则会「采集成功但值为空」。

## 四、升级前要回归哪些兼容性变更？

**本节要点**：四类高风险变更——点号路径对 `null` 的比较、单次操作内存上限、并发事务上限、指标改名。

| 变更 | 影响面 | 升级前动作 |
| --- | --- | --- |
| 点号路径与 `null` 的比较语义 | 所有「拿点号路径与 `null` 比较」的查询与 `$lookup` 等值匹配 | 扫一遍相关查询形状，用旧 / 新语义各跑一遍对比结果集 |
| 单次操作内存上限（默认 1 GB 或 20%） | 大排序、大聚合、无 `limit` 的全量扫描 | 找出历史上内存峰值高的操作，评估是否需要 `allowDiskUse` 或先收窄输入 |
| 并发多文档事务上限（默认 10000） | 高并发写事务的业务 | 压测观察并发事务峰值与是否触发 `TooManyOpenTransactions` |
| 指标重命名 / 时序存储模型变化 | 监控采集脚本、依赖 `system.buckets` 内部结构或对时序集合做 `rename` 的工具 | 同步监控名称；确认对时序集合内部结构的依赖已去掉 |

⚠️ 大版本升级要按官方版本路径**逐跳**，且 `feature compatibility version` 不能提前抬高——这条与 [副本集与选举.md](副本集与选举.md) 第五节「滚动维护」是同一套纪律。

## 五、哪些流传的说法不在 Release Notes 里？

**本节要点**：几组常被当作「9.0 新特性」的数字与能力，核对官方 Release Notes 后并不成立；引用前请自行溯源。

| 流传说法 | 核对结果 |
| --- | --- |
| 「9.0 的 find-one 提升 35%、update-one 吞吐提升 30%」 | ⚠️ **不在 9.0 Release Notes**。这组数字更接近一次 8.3 版本的宣传口径；9.0 官方的性能表述是「最高约 2 倍吞吐」。 |
| 「9.0 原生集成 OpenTelemetry」 | ⚠️ 9.0（以及 8.3）Release Notes 正文里**没有**这一项。服务端侧的 OTel 更多是通过监控栈对接，而非服务端内建导出。 |
| 「9.0 有 IWM 智能工作负载管理、自动排队」 | ⚠️ 9.0 Release Notes 未出现该术语。方向接近的是 8.3 引入的执行队列优先级 / 降级指标（`queues.execution.*`），但那是 8.3 而非 9.0。 |

⭐ 写方案时的稳妥做法：性能数字一律标注**来源与版本**，并说明「厂商口径 vs 自测」；
拿不到 Release Notes 原文时，宁可不写具体百分比。

## 使用：在 9.0 上观察这些变化

⚠️ **本机未实测**：本仓库容器只到 `mongo:7.0`，下列命令需要 9.0 实例，按官方文档整理为验证清单。

```javascript
// ① 单次操作内存上限：看配置值与失败计数
db.serverStatus().metrics.query.configuredMaxMemoryUsageBytesPerOperation
db.serverStatus().metrics.query.operationsFailedDueToMemoryLimit
db.serverStatus().metrics.query.peakMemoryUsageOperation

// ② 并发多文档事务：看上限与当前的冲突 / 等待
db.adminCommand({ getParameter: 1, maxConcurrentMultiDocumentTransactions: 1 })
db.serverStatus().metrics.operation.writeConflictRetryLimitHit

// ③ 按查询形状设超时（需要 FCV 9.0+）
db.adminCommand({ setQuerySettings: { find: "orders", filter: { status: "PAID" } },
                  settings: { maxTimeMS: 200 } })

// ④ 分片排空进度（9.0+）
sh.shardDrainingStatus()
```

三条判据：**① 内存上限看 `operationsFailedDueToMemoryLimit` 是否抬头**（抬头说明有查询撞上了新上限）；
**② 事务看 `TooManyOpenTransactions` 出现频率**；**③ 设置类改动只作用于指定形状**，改完记得用 `$queryStats` 或 `explain` 复核实际计划。

## 延伸追问

- **9.0 最可能「升级后就出问题」的是哪一条？**
  → 点号路径与 `null` 的比较语义。它改变的是**查询结果集**而不是报错，静默改变最危险——升级前必须把「点号路径比较 `null`」的查询与 `$lookup` 等值匹配逐条回归。
- **为什么 9.0 要给单次操作加内存上限？**
  → 因为此前一条查询可以无限吃内存，一个失控的排序 / 聚合能把实例拖垮（与 [运维与监控.md](运维与监控.md) 里 OOM 成因排序中的「大 sort/group」同源）。加上限是把它变成**可控失败**，代价是历史上靠「大内存硬跑」的查询要改为 `allowDiskUse` 或先收窄输入。
- **`$queryStats` 默认开启会不会有开销？**
  → 是**按采样**收集（读写默认各 1%），且它的输出只覆盖被采样到的操作——既要注意那点采样开销，也不要把它当成全量账本。
- **服务端 JS 用 WASM 重开是什么意思？**
  → `$accumulator` / `$function` / `$where` 在 8.0 被弃用，9.0 用 WASM 引擎重新启用，靠更强的沙箱隔离来换取安全性；功能回来了，但 `ppc64le` 架构不可用。
