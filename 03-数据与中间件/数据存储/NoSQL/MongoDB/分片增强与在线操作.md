# MongoDB 分片增强与在线操作

> 5.0 的在线重分片（`reshardCollection`）、7.0 的 `moveCollection` / `abortMoveCollection`、
> 8.0 的重分片提速与均衡优化、9.0 的分片元数据与一致性检查增强，
> 以及「不重建集合改片键」的完整操作顺序、检查点与跨分片事务的性能边界。
>
> 内容整理自个人学习笔记，版本事实取自 MongoDB 官方 Release Notes（5.0 / 7.0 / 8.0 / 8.3 / 9.0）。
> ⚠️ 本篇的 `mongosh` 命令**本机未实测**（分片集群起不来），按官方文档整理为操作清单；基础机制见 [分片基础.md](分片基础.md)。

## 一、基础回顾：为什么「改片键」这么贵？

**本节要点**：片键决定 chunk 边界、路由表与索引前缀；改它意味着把整片数据按新边界重排，并同步重写路由元数据。

回顾三条（细节见 [分片基础.md](分片基础.md)）：

- chunk 是片键上的**左闭右开区间**，路由表记录「区间 → 分片」的映射；
- 数据分布在物理上就是按片键区间组织的，换键就要重新落盘；
- 唯一索引必须包含完整片键，换键等于换索引定义。

所以「换片键」在 5.0 之前基本等于「换集合」。

## 二、5.0 起：在线重分片怎么做、限制在哪？

**本节要点**：`reshardCollection` 在不停机的前提下把集合迁到新片键——机制是「双写 + 拉取 + 追赶 + 切换」；

新片键索引由系统**自动**创建，不需要你预先建好。

### 2.1 机制（定性）

1. 在目标分片上按新片键建立新集合（含新索引）；
2. 源集合上的写入**同时**记录到新集合的变更流；
3. 后台按新片键区间拉取历史数据、追赶增量；
4. 追平后短暂切换路由（ownership 交接），随后清理旧集合。

⚠️ 全程需要**额外磁盘**（源 + 目标并存）与额外写入带宽，耗时随数据量增长；
它把「停机窗口」换成了「更长的资源占用窗口」，不是免费的。

### 2.2 两个常见误解

- ❌「必须先手工给新片键建索引」——官方文档说明重分片会**自动创建**新片键索引，不需要预先建。
- ❌「可以原地改成相同的片键」——不能重分片到**完全相同**的片键；8.0 起支持「同键重分片」是为了**重新分布数据**，用途是打散倾斜，不是改键。

### 2.3 限制（引用前以官方文档为准）

- 不能在已有重分片进行中再发起一次；
- 对唯一索引、`metaField`、某些索引类型有约束；
- 期间对写入有持续压力，且会抬高从节点 lag（与 [副本集与选举.md](副本集与选举.md) 的 oplog 窗口连锁反应同源）。

### 2.4 可以中止

`abortReshardCollection` 可中止正在进行/尚未完成的重分片；中止后集合回到源结构，但已投入的 IO 不会退还。

## 三、7.0 起：moveCollection 解决什么？

**本节要点**：`moveCollection` 针对的是**非分片集合**在分片集群上的位置问题（落在哪个分片），而不是片键问题；

它可配合 `abortMoveCollection` 中止。

| 命令 | 作用对象 | 解决的问题 |
| --- | --- | --- |
| `moveCollection` | **非分片**集合 | 把某个未分片集合从当前所在分片搬到另一个分片（7.0 引入），避免为它单独迁库或重建 |
| `abortMoveCollection` | 同上 | 中止进行中的搬迁（7.0 引入） |
| `movePrimary` | 库的 primary shard | 改变**库**的主分片归属，连带搬走该库里所有非分片集合；粒度更粗 |
| `sh.moveChunk` | 单个 chunk | 手工搬一块 chunk，微调倾斜 |

⚠️ 容易混：`moveCollection` 只管**未分片集合**的落点；已分片集合要改分布，走 `reshardCollection`（第 2 节）。
非分片集合落在哪个分片由「库的 primary shard」决定，因此多集合时用 `movePrimary` 更划算。

## 四、8.0 / 9.0 在分片与元数据上优化了什么？

**本节要点**：8.0 的重点是「重分片与均衡更快」，9.0 的重点是「分片元数据的一致性与可观测性」。

⚠️ 网上流传的「均衡速度提升 50 倍 / 单分片成本降 50%」是官方**博客**口径，不在 Release Notes 正文，引用时要标来源。

| 版本 | 与分片相关的官方口径 |
| --- | --- |
| 8.0 | 重分片**大幅提速**（官方称显著缩短了运行时间）；支持同键重分片以重新分布集合（比替代的范围迁移快得多）；`bulkWrite` 相对 7.0 最多快 56%，典型 Web 应用整体性能最多提升 32% |
| 8.3 | 分片元数据缓存重构，暴露了一批 `shardingStatistics` 下的数据库 / 集合元数据缓存指标（如缓存清理、版本不匹配等待、磁盘恢复耗时） |
| 9.0 | 新增 `sh.shardDrainingStatus()` 与 `sh.getTransitionToDedicatedConfigServerStatus()`；`checkMetadataConsistency` 新增不一致类型（如 `IncompatibleUniqueIndexOnShardedCollection`、`LegacyShardCacheCollectionsPresent`）并支持 `performStrictChunkChecksIfBelowThreshold` 做「大集合轻量比对」 |

⭐ 9.0 的 `shardDrainingStatus()` 是针对「排空分片」（把某个分片的数据迁走再下线）的可观测性补充——
这类操作过去只能靠日志判断进度。

## 使用：在线改片键的操作顺序与检查点

⚠️ **本机未实测**：分片集群需要「配置服务器副本集 + 至少两个分片副本集 + `mongos`」，本仓库的容器实测口径只覆盖单实例。
下列命令按官方文档整理，**没有跑过**，仅作为现场操作的清单与检查点。

```javascript
// ① 现状盘点：分片列表、chunk 分布、当前是否有重分片在跑
db.adminCommand({ listShards: 1 })
db.orders.getShardDistribution()
db.adminCommand({ balancerStatus: 1 })
db.adminCommand({ $currentOp: { allUsers: true, localOps: true } })  // 看有没有 resharding / migration

// ② 在线重分片：改成新片键（{ tenantId: 1, createdAt: 1 } → { tenantId: "hashed" }）
db.adminCommand({
  reshardCollection: "shop.orders",
  key: { tenantId: "hashed" },
  numInitialChunks: 64            // 预铺 chunk，避免切完立刻再均衡
})

// ③ 中止（可选）
db.adminCommand({ abortReshardCollection: "shop.orders" })

// ④ 搬迁未分片集合到指定分片（7.0+）
db.adminCommand({ moveCollection: "shop.archive", toShard: "shard02" })
db.adminCommand({ abortMoveCollection: "shop.archive" })

// ⑤ 元数据一致性自检（9.0+ 支持大集合轻量比对）
db.adminCommand({ checkMetadataConsistency: 1, performStrictChunkChecksIfBelowThreshold: 1000 })

// ⑥ 排空分片进度（9.0+）
sh.shardDrainingStatus()
```

看结果的三条判据：**① 资源先看够不够**（源 + 目标并存，磁盘与写入带宽要留一倍余量）；
**② 进度看 lag 与 `$currentOp`**（重分片期间从节点 lag 抬头、`currentOp` 里能看到 resharding 子阶段，lag 逼近 oplog 窗口就要评估是否中止）；
**③ 切完先看分布再看查询**（`getShardDistribution()` 的 chunk 数是否均衡，再 `explain` 确认常用查询是否定向）。

## 五、跨分片事务的性能边界

**本节要点**：跨分片事务比单分片多一轮协调，延迟与冲突率都更高；9.0 还给并发多文档事务加了默认上限。

- 事务要提交到涉及的所有分片，多一轮两阶段协调（2PC 语义），**延迟随参与分片数上升**。
- 冲突概率更高：不同分片上的文档都要持锁到提交，热点文档跨分片时冲突率显著上升。
- 分片集合的片键选择要尽量让事务落在**单分片**（例如把同一聚合根的文档放在一个片键区间里）。
- ⚠️ 9.0 起服务端对**并发打开的多文档事务数**加了上限：默认 10000（`maxConcurrentMultiDocumentTransactions`），超出返回 `TooManyOpenTransactions`。

替代手段与取舍见 [事务与一致性.md](事务与一致性.md)：本库内的强一致优先靠单文档原子与条件更新，而不是跨分片事务。

## 延伸追问

- **在线重分片能不建索引就换片键吗？**
  → 新片键的索引由重分片过程**自动创建**，不需要预先建（官方文档口径）。需要注意的反而是资源：源与目标集合并存，磁盘与写入带宽要留余量，且期间 lag 会抬头。
- **`reshardCollection` 和 `moveCollection` 到底管什么？**
  → 前者管**已分片集合**的片键与数据分布；后者管**非分片集合**落在哪个分片上（7.0）。已分片集合想「换个地方放」，得改片键（重分片）；非分片集合想搬家，用 `moveCollection` 或直接 `movePrimary`。
- **「均衡速度提升 50 倍」能直接写进方案吗？**
  → 慎用。这组数字出自官方 8.0 博客而非 Release Notes 正文；Release Notes 的表述是「重分片运行时间显著缩短」。写方案时标清来源，并把期望值绑到自己的数据量与集群规模上。
- **重分片中途顶不住想停怎么办？**
  → `abortReshardCollection` 可中止，集合回到源结构；但已消耗的 IO 与写入放大不会退还，且中止本身也要时间。更稳的做法是提前用「双写 + 回填 + 切读」的应用层路径（见 [分片基础.md](分片基础.md) 第六节）做灰度。
