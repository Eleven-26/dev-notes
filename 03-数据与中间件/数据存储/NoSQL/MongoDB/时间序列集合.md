# MongoDB 时间序列集合

> 时间序列集合（time series collection）为什么存在、桶文档与列式压缩省在哪、
> `timeField` / `metaField` / `granularity` / `expireAfterSeconds` 怎么配、索引该建在哪、
> 查询与聚合怎么利用桶元数据剪枝，以及什么场景**不该**用它。
>
> 内容整理自个人学习笔记，机制与版本事实取自 MongoDB 官方文档。
> ✅ 本机读数用 `docker` 里的 `mongo:7.0` 容器实测（见「使用」一节）；5.0 / 5.2 / 6.0 / 6.3 / 7.0 / 8.0 / 9.0 的版本差异以官方文档为准。

---

## 一、为什么需要时间序列集合？

**本节要点**：普通集合存高频点位会同时吃三份亏——文档头开销、每个文档的索引条目、频繁小写入。

时间序列集合把「时间 + 元数据 + 测量值」按时间窗压进**桶文档**，用列式压缩一次性解决三者。

### 1.1 普通集合的三个浪费

- **文档头与字段名重复**：1 分钟一个点 → 每天 86400 个文档，每个文档都要存 `_id`、字段名与类型信息。
- **索引膨胀**：给普通集合建 `{ sensorId: 1, ts: 1 }`，索引条目数 = 文档数；测量越多索引越大。
- **写入放大**：小文档高频插入，每次都要维护数据页与全部索引。

### 1.2 桶文档：把 N 条测量装进 1 个文档

时间序列集合对用户暴露的仍是「一条测量一个文档」，但底层按 `metaField` + 时间窗把多条测量装进一个桶。
本机实测取出的真实桶文档（`mongo:7.0`，1440 个点被压成 24 个桶，单个桶装 60 条）：

```javascript
{
  _id: ObjectId("..."),
  control: {
    version: 2,
    min: { ts: ISODate("2026-01-01T00:00:00Z"), v: 0,  _id: ObjectId("...") },
    max: { ts: ISODate("2026-01-01T00:59:00Z"), v: 59, _id: ObjectId("...") },
    count: 60                       // 桶内测量条数
  },
  meta: { sid: 7 },                  // 分桶维度
  data: {                            // ⭐ 列式：每列是一个压缩后的二进制块
    ts: Binary.createFromBase64("CQAAqNp2mwEAAIMMTB0AAAAAAAIAAAAAAAAAAwAAAAAAAAAJAAAAAAAAAAA=", 7),
    v:  Binary.createFromBase64("EAAAAAAAg6KqqqqqqqqqI0mSJEmSJEkHAoFAIBAIBC4AAAAAAAAAAA==", 7),
    _id: Binary.createFromBase64("BwBqwmU0o0NJCmbGTraDIgAAAAAAAAADAAAAAAAAAAcAAAAAAAAADgAAAAAAAAAA", 7)
  }
}
```

⭐ 两个要点：`data` 是**列式**存放（同一字段的值连续、且已压缩成二进制块），因此同类型、变化平缓的数值压缩比很高；
`control.min` / `control.max` 缓存了桶内各字段的极值与 `_id` 边界，是查询剪枝的依据。

### 1.3 这条线在版本上演进过什么

| 版本 | 变化 |
| --- | --- |
| 5.0 | 引入时间序列集合（桶文档）；二级索引仅限 `timeField` / `metaField`（`metaField` 为文档时可索引其子字段） |
| 5.2 | ⭐ 列式压缩（Delta / Delta-of-Delta / RLE，含对象压缩） |
| 6.0 | 二级索引放宽到 `timeField` / `metaField` / 测量字段的**复合**形式，并支持 partial 索引与 `metaField` 上的 `2dsphere` |
| 6.3 | ⭐ 新建集合**自动**在 `metaField + timeField` 上建复合索引 |
| 7.0 | 支持带 `partialFilterExpression`（仅依赖 `metaField`）的 TTL 索引 |
| 8.0 | 查询可走**块式处理**（block processing），官方称 `$group` 与分析查询吞吐可提升逾 200% |
| 9.0 | ⭐ 底层改为**单命名空间**存储（不再是「可写的非物化视图」）；支持 `renameCollection` |

⚠️ 9.0 升级提醒（官方原文）：单个库里超过 5000 个时间序列集合的集群，升级会更慢并出现额外的写入延迟毛刺 → 升级前先清理无用集合。

## 二、怎么建、参数怎么配？

**本节要点**：`timeField` 必填、`metaField` 强烈建议填（它就是分桶维度与剪枝依据）、`granularity` 决定桶的时间跨度、

`expireAfterSeconds` 决定数据自动老去的时间。

```javascript
db.createCollection("weather", {
  timeseries: {
    timeField: "ts",         // 必填：值必须是 BSON Date
    metaField: "meta",       // 建议：设备 / 租户等「分组维度」，几乎不变
    granularity: "minutes"   // seconds | minutes | hours
  },
  expireAfterSeconds: 86400  // 到点自动删除
})
```

| 参数 | 作用 | 取值与影响 |
| --- | --- | --- |
| `timeField` | 时间字段名 | 必填；值必须是 BSON Date（或 Date 数组） |
| `metaField` | 元数据字段名 | 建议填；分桶按它分组，也几乎决定查询能否剪枝 |
| `granularity` | 桶时间跨度 | `seconds` / `minutes` / `hours`；选得越细桶越多 |
| `expireAfterSeconds` | 数据保留期 | 支持；语义同 TTL 索引 |

⚠️ `bucketMaxSpanSeconds` / `bucketRoundingSeconds` 在官方文档里是合法的创建选项，
但**本机 `mongo:7.0` 里通过 `mongosh` 的 `createCollection` 传它会报 `IDLUnknownField`**（实测）
——真要手工控制桶边界，以实际发行版对命令的支持为准。

- 直接往不存在的时序集合写数据会**隐式创建**（此时可省略 `metaField`）。
- 除 `timeField` / `metaField` 之外的字段都算**测量值（measurement）**。
- 支持 `insert` / `find` / `aggregate` / `update` / `delete`，但它的写模型是「追加时间点」，不适合把某条历史测量反复原地改写。
- ⚠️ `metaField` 一旦选定就**不宜改**：它是分桶与剪枝的维度，语义变了等价于重建集合。

## 三、索引策略：什么时候要建、建在哪？

**本节要点**：时间范围查询靠**桶元数据**自动剪枝，不用你建索引；要建的索引是给 `metaField` 之外的过滤 / 排序维度用的。

- ⭐ 6.3 起新建集合自带 `{ metaField: 1, timeField: 1 }` 复合索引。本机 `mongo:7.0` 实测：`getIndexes()` 返回 `[{"meta":1,"ts":1}]`，无需手工创建。
- 二级索引**按桶建**而不是按测量建，索引条目数约等于「桶数」而非「测量数」——这是它索引不膨胀的根本原因。
- 值得建索引的是 `metaField` 子字段之外的常用过滤 / 排序维度（例如挂在 `meta` 里的 `city`、`deviceType`）。
- ⚠️ 不要对测量字段乱建索引：数值型高频测量建索引会重新引入膨胀，而且它天然不是等值检索的对象。
- 官方另有一份「时序集合不支持哪些索引类型」的限制清单，建索引前以官方 Limitations 页为准。

## 使用：建集合、灌数据、验证剪枝（容器实测）

实测环境：`docker run -d --name mongo-idx-lab -p 27018:27017 mongo:7.0`，`mongosh` 在容器内执行。

```javascript
// ① 建集合：granularity 选 seconds → 桶跨度约 1 小时
db.createCollection("m", {
  timeseries: { timeField: "ts", metaField: "m", granularity: "seconds" }
})

// ② 灌 1440 个点（1 分钟 1 个，覆盖 24 小时）
const base = new Date("2026-01-01T00:00:00Z")
const bulk = []
for (let i = 0; i < 1440; i++) {
  bulk.push({ ts: new Date(base.getTime() + i * 60000), m: { sid: 7 }, v: i })
}
db.m.insertMany(bulk)

// ③ 看底层桶：1440 条「测量」被装进 24 个桶文档
db.m.countDocuments({})                                   // 1440
db.getCollection("system.buckets.m").countDocuments({})   // 24
```

查询窗口 ↔ 实际扫描量（同一次运行，`explain("executionStats")` 的 `stages[0].$cursor.executionStats`）：

| 查询窗口 | `nReturned` | `docsExamined`（= 扫的桶数） |
| --- | --- | --- |
| 1 小时 | 1 | 4 |
| 6 小时 | 6 | 9 |
| 24 小时 | 24 | 24 |

⭐ 扫的**桶数**随窗口单调增长，而测量与桶是 60:1 的关系——这就是剪枝的实际收益。
⚠️ 扫的桶数会略多于命中的桶数（1 小时窗口扫了 4 个桶），因为元数据剪枝是**区间相交**判断，桶边界与查询窗口只是重叠关系。

## 四、查询与聚合怎么优化？

**本节要点**：查询**必须带时间范围**才能吃到桶元数据剪枝；补齐缺失时间点用 `$densify` / `$fill`（5.1+）。

### 4.1 explain 的形状与普通集合不同

对时序集合 `explain()` 返回的顶层是 `stages: [ { $cursor: ... } ]`（而不是普通集合的 `queryPlanner`），命名空间指向 `system.buckets.<集合名>`；
解析后的条件会**展开成对桶元数据的判断**（实测）：`control.min.ts` / `control.max.ts` 与 `_id` 边界，计划阶段是 `CLUSTERED_IXSCAN`。

### 4.2 ⭐ 不带时间范围会退化成 COLLSCAN

同一批数据的三组对照（实测）：

| 查询 | 计划 | 说明 |
| --- | --- | --- |
| `meta` 等值 + 时间范围 | `CLUSTERED_IXSCAN` | 元数据剪枝 + 时间剪枝都生效 |
| 只给时间范围 | `CLUSTERED_IXSCAN` | 时间剪枝生效 |
| ⚠️ 只给 `metaField` 等值 | **`COLLSCAN`** | 没有时间条件 → 桶元数据剪枝用不上 |

所以「用时序集合做设备维度的全量统计」是反模式：只按 `metaField` 查会退化成全表扫。

### 4.3 补齐缺失时间点

```javascript
db.m.aggregate([
  { $match: { "m.sid": 7 } },
  { $densify: { field: "ts", range: { step: 60000, unit: "millisecond", bounds: "full" } } },
  { $fill: { sortBy: { ts: 1 }, output: { v: { value: 0 } } } }
])
```

`$densify` / `$fill` 于 5.1 引入，用来把「缺失的时间点」补出来再做插值或默认值，省的正是应用层自己维护日历表。

### 4.4 8.0 的块式处理

8.0 起，部分时序查询可走**块式处理**：按桶的整列数据一次处理，而不是逐文档，官方称 `$group` 与分析查询吞吐可提升逾 200%。
优化方向与普通聚合一致——让更少的桶进入下游 stage。

## 五、什么时候不该用它？

**本节要点**：需要频繁原地更新单条测量、查询不带时间范围、或需要强事务与复杂关联时，普通集合更合适。

- ⚠️ **频繁原地更新单条测量**（例如设备回填某时刻的最终值）：时序集合的强项是「追加时间点」，不是原地改写。
- ⚠️ **查询不带时间范围、只按维度等值或全量聚合**：会退化成 `COLLSCAN`（见第 4.2 节）。
- ⚠️ **需要跨维度的复杂关联与强事务**：那是普通集合 + 索引 + [事务与一致性.md](事务与一致性.md) 的场景。
- ⚠️ 保留期很短、写入量也不大时，普通集合 + TTL 索引更简单，不必为了「新特性」上时序集合。

## 延伸追问

- **时间序列集合到底省在哪？**
  → 三处：① 字段名在桶里只写一次（列式，不再逐文档重复）；② 同类数值列式存放并压缩成二进制块，压缩比高；③ 二级索引按桶建，条目数约等于桶数而不是测量数，写入维护成本同步下降。
- **为什么查询必须带时间范围？**
  → 桶元数据 `control.min.ts` / `control.max.ts` 只对**时间**做区间相交判断；没有时间条件就没有可剪枝的元数据维度，只能全表扫（本机实测退化为 `COLLSCAN`）。
- **`granularity` 选错会怎样？**
  → 它是「精度 ↔ 桶数量」的旋钮：选得太细 → 桶数暴增、元数据与索引变大；选得太粗 → 单桶装太多点、剪枝粒度变粗、块式处理的可并行度下降。
- **`metaField` 能不能事后改？**
  → 不能等价改。它决定分桶与剪枝维度，改语义等于换集合：新集合 + 双写 + 回填 + 切读，代价与「换片键」同类（见 [分片增强与在线操作.md](分片增强与在线操作.md)）。
