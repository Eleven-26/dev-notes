## 一、图模式设计有哪些原则？

**本节要点**：图建模的核心问题只有一个 —— **"这个东西该是节点，还是该是属性？"**
判据是"它会不会被别人引用 / 需要独立被查"。关系方向、标签、关系类型的粒度都围绕这个判据展开。

### 1.1 属性还是节点？

| 判据 | 当**属性** | 当**节点** |
|---|---|---|
| 会不会被别人引用？（作为关系的一端） | 不会 → 属性 | 会 → 节点 |
| 需不需要**独立作为查询起点**？ | 不需要 → 属性 | 需要 → 节点 |
| 有没有自己的属性 / 关系？ | 没有 → 属性 | 有 → 节点 |
| 数量与复用度 | 值域小、随主体走 | 会被大量共享、需要单独维护 |

⭐ 例子：`(订单)-[:下单]->(用户)` 时，"所在城市"只是用户的一个属性（`u.city='北京'`）；
但一旦要**做"同城用户"的推荐、要查城市本身的经济数据**，"城市"就该升格为节点 `(:City)`，
用户用 `-[:LIVES_IN]->` 连过去。**判据始终是"要不要以它为起点 / 被引用"，不是"它看起来像不像实体"。**

⚠️ **过度节点化的代价**：每个升格都是多一次遍历 / 多一个索引。把"性别"这种只有两三个取值的东西做成节点，
除了让查询多一跳，没有任何好处。

### 1.2 关系方向怎么定？

Neo4j 的关系**有向**，但查询时可以**忽略方向**（`(a)-[:FOLLOWS]-(b)`）。所以方向设计的规矩是：

- **按语义定，不按查询定**：`(a)-[:FOLLOWS]->(b)` 就表示 a 关注 b，方向是业务事实；
- **不要为了"两个方向都快"而存两条反向边**：需要反向查询时用无向模式匹配，或按
  [架构与存储引擎.md](架构与存储引擎.md) 的邻接链理解"反向遍历靠关系记录里的双向指针"；
- ⚠️ **无向匹配更贵**：`-[:X]-` 要两个方向都试，能确定方向就写方向。

### 1.3 标签怎么设计？

| 做法 | 语义 | 何时用 |
|---|---|---|
| **单标签** | 这类实体 | 默认，绝大多数情况 |
| **多标签** | **交集（AND）** —— 同时属于多个类 | 需要"既是 A 又是 B"的复合查询，如 `(:User:Vip)` |

⚠️ **不要用多标签代替属性**：把"等级"拆成 `:Lv1`/`:Lv2`/`:Lv3` 十几个标签，
会让标签爆炸、索引数量翻倍、查询要枚举所有标签。**等级是属性，不是标签。**

### 1.4 关系类型的粒度

| 太细 | 太粗 |
|---|---|
| 每个动作一个类型（`LIKE_CLICK`/`LIKE_VIEW`/…） | 全叫 `RELATED` |
| 类型爆炸、查询要并列一堆类型 | 丢失语义、无法按类型过滤 |
| 判据：**这个区分会被查询用到吗**？ | 用到才拆 |

⭐ 折中：**按查询需求拆**。如果"点赞"和"收藏"永远一起查，就合并；如果经常要单独过滤，就分开。

## 二、常见建模模式长什么样？

**本节要点**：四类高频场景各有惯用模式 —— 社交看**方向与多跳**，知识图谱看**实体-关系-实体**，
权限看**用户-角色-资源**，时序看**"关系带时间属性"**。

```text
社交网络                知识图谱                权限模型                时序关系
(u1)-[:FOLLOWS]->(u2)  (实体A)-[:关系]->(实体B)  (用户)-[:拥有]->(角色)   (a)-[:CALLED {at: ts}]->(b)
 方向 = 业务事实          多类型 + 属性            (角色)-[:可访问]->(资源)  时间放在关系属性上
 多跳 = 三度人脉          多跳 = 推理链路          多跳 = "他能不能访问它"   按时间过滤 / 排序
```

| 模式 | 关键设计点 | 常见坑 |
|---|---|---|
| **社交网络** | 关注**有向**；"共同关注"靠多跳 | 把互关存成一条无向边 → 方向语义丢失 |
| **知识图谱** | 实体/关系/属性三层；多类型关系 | 关系类型随手起名 → 后期无法复用 |
| **权限模型** | 角色做中间节点（用户→角色→资源） | 把权限位塞进用户属性 → 无法复用与审计 |
| **时序关系** | **时间放在关系属性上**（`{at: datetime}`） | 用"每天建一个新节点" → 节点数爆炸 |

⭐ **"时间放关系属性"是时序建模的关键**：`(a)-[:TRANSFER {at: datetime('2026-01-01'), amount: 100}]->(b)`
既能按时间过滤（`WHERE r.at > …`），又能保留多重边（同一对节点间可有多条不同时刻的转账）。
⚠️ 与文档型建模的一个明确差异：图库**不擅长"以时间为主键的聚合"**（那是时序库的活，见
[存储选型.md](../../存储选型.md)）。

## 三、LOAD CSV 怎么把文件导进来？

**本节要点**：`LOAD CSV` 是内核自带的**逐行读取 → 执行 Cypher** 机制，
文件放在数据库的 `import/` 目录下（容器里就是挂载进去的那个目录），用 `file:///` 引用。**类型要显式转换。**

### 3.1 最小写法

```cypher
// 先看一眼文件长什么样（真实 CSV：表头 id,name,age；数据 0,cu0,20）
LOAD CSV WITH HEADERS FROM 'file:///csv_users.csv' AS row
RETURN row LIMIT 3;
```

```cypher
// 建节点
LOAD CSV WITH HEADERS FROM 'file:///csv_users.csv' AS row
CREATE (:CsvUser {id: toInteger(row.id), name: row.name, age: toInteger(row.age)});
```

⭐ `WITH HEADERS` 让 `row` 变成**按列名取值的 map**（`row.id`）；不加它只能用 `row[0]` 按下标取，
可读性差且一改列序就错。**永远用 `WITH HEADERS`。**

### 3.2 类型转换

`LOAD CSV` 读进来**全是字符串**，必须显式转换，否则数字会变成字符串、比较与索引用不上：

| 目标类型 | 函数 | 例 |
|---|---|---|
| 整数 | `toInteger(row.id)` | 主键、数量 |
| 浮点 | `toFloat(row.score)` | 分数、金额 |
| 时间 | `datetime(row.ts)` | ISO8601 字符串 → datetime |
| 布尔 | `toBoolean(row.flag)` | `'true'`/`'false'` |

⚠️ **类型不匹配是"索引失效"的头号原因**（见 [索引设计与查询优化.md](索引设计与查询优化.md)）：
如果导入时把 `id` 存成字符串，之后 `WHERE u.id = 50000`（整数）就**用不上索引**，
退化成全标签扫描 —— 这个账在导入时就得算清。

### 3.3 分批提交

大文件一把梭会形成超大事务（内存 + 锁都吃不消，见 [事务与并发控制.md](事务与并发控制.md)）。
用子查询分批：

```cypher
LOAD CSV WITH HEADERS FROM 'file:///csv_follows.csv' AS row
CALL {
  WITH row
  MATCH (a:CsvUser {id: toInteger(row.from)}), (b:CsvUser {id: toInteger(row.to)})
  CREATE (a)-[:CF]->(b)
} IN TRANSACTIONS OF 5000 ROWS;
```

⚠️ 两个语法坑（本仓实测踩过）：**`IN TRANSACTIONS` 是写在 `CALL { … }` 的"外面"**；
**`OF 5000` 后面必须跟 `ROWS`**（不写 `ROWS` 会报 `expected an expression, 'ROW' or 'ROWS'`）。
另见第六节的代价说明：**分批不等于更快**。

### 3.4 实测读数（本仓 5.26 社区版）

| 场景 | 读数（热），单位 ms | 冷启动首次 |
|---|---|---|
| 导入 20000 用户（纯 `CREATE`，无约束） | **425 ~ 876** | 5425 |
| 导入 20000 用户（`MERGE` + 唯一约束） | **1496 ~ 2266** | 7942 |
| 导入 60000 关系（**有**唯一约束 / 索引） | **3299 ~ 7163** | — |
| 导入 **1** 条关系（**有**约束） | **521** | — |
| 导入 **1** 条关系（**无**约束） | **1679** | — |

⭐ 三条直接结论：**①`MERGE` 比 `CREATE` 慢**（要查重，约 2~3 倍）；
**②"先建约束/索引再导关系"是数量级的差别** —— 见下面的计划对照；
**③无索引时每行要 1.7 s**，2000 行就是**一小时级**，等于不可行。

### 3.5 为什么无索引会慢到不可行？看计划

同一个 `LOAD CSV` + 双 `MATCH`，只差一个唯一约束，执行计划完全不同（`EXPLAIN` 实测）：

```text
无约束（退化成笛卡尔积，每行 20000 × 20000 次节点访问）
  LoadCSV → CartesianProduct
              ├── Filter b.id = toInteger(row.to)   ← NodeByLabelScan b:CsvUser (20000)
              └── Filter a.id = toInteger(row.from) ← NodeByLabelScan a:CsvUser (20000)
            → Create (a)-[:CF]->(b)

有唯一约束（两个端点各一次索引定位）
  LoadCSV → CartesianProduct
              ├── NodeUniqueIndexSeek(Locking) b:CsvUser(id)
              └── NodeUniqueIndexSeek(Locking) a:CsvUser(id)
            → Create (a)-[:CF]->(b)
```

⚠️ **关键看 `NodeByLabelScan` vs `NodeUniqueIndexSeek`**：没有约束时两个 `MATCH` 被规划成
**两个独立的全标签扫描再做笛卡尔积**（`20000 × 20000 = 4 亿` 次节点访问**换 1 条关系**）；
有了唯一约束，两端各一次**索引定位**（本仓单行从 `1679 ms` 降到 `521 ms`）。
**这就是"先建约束再导"的全部理由** —— 不是玄学，是计划里 `Scan` 变成了 `Seek`。

## 四、APOC 补了 LOAD CSV 哪些短板？

**本节要点**：`LOAD CSV` 够用但有边界（只认本地文件、格式固定、无内建分批控制）。
**APOC（Awesome Procedures On Cypher）**是官方支持的过程库，补上**多种源、批量事务、动态结构**三块。

| 需求 | LOAD CSV | APOC |
|---|---|---|
| 读 CSV | ✅ 内置 | `apoc.load.csv`（可分页、可跳过表头） |
| 读 **JSON** | ❌ | `apoc.load.json` |
| 读远程 URL | ❌（只认 `import/`） | ✅ 支持 http |
| **批量事务** | 手写 `CALL {} IN TRANSACTIONS` | `apoc.periodic.iterate`（一行搞定，可并行） |
| **动态关系类型** | ❌（类型必须写死） | `apoc.merge.relationship` |
| 导出 | ❌ | `apoc.export.csv/json/graphml` |

```cypher
// apoc.periodic.iterate：把「读」与「写」两段 Cypher 分开，按 batchSize 分批提交
CALL apoc.periodic.iterate(
  "LOAD CSV WITH HEADERS FROM 'file:///csv_users.csv' AS row RETURN row",
  "CREATE (:ApocUser {id: toInteger(row.id), name: row.name})",
  {batchSize: 5000, parallel: false}
) YIELD batches, total, timeTaken, committedOperations
RETURN batches, total, timeTaken, committedOperations;
```

⭐ **`apoc.periodic.iterate` 的价值是"把两段 Cypher 拆开"**：第一段只负责**产出**记录（读），
第二段对每条记录执行**写**。它自动按 `batchSize` 分批提交，还支持 `parallel: true`。
⚠️ `parallel: true` 只在**各批次之间不冲突**时才安全（否则会死锁 / 写冲突，见
[事务与并发控制.md](事务与并发控制.md)）—— 有唯一约束的并发 `MERGE` 尤其危险。

⚠️ **APOC 和 GDS 不是一回事**：APOC 是**通用过程库**（导入导出、结构操作、字符串/集合工具），
GDS 是**图算法引擎**（[GDS图算法实战.md](GDS图算法实战.md)）。两者都是插件，但解决的问题完全不同。

## 五、导入性能怎么优化？

**本节要点**：导入慢的本质是**"每行都要去找节点"**。所以优化的第一优先级永远是
**"让每一行的定位走索引"**；其次是批量与缓存；最后才是并行。

| 手段 | 为什么有效 | 本仓证据 |
|---|---|---|
| ⭐ **先建约束 / 索引，再导关系** | 每行的 `MATCH` 从全标签扫描（笛卡尔积）变成索引定位 | 有索引 60000 行 `3.3~7.2 s`；无索引**单行**就要 `1679 ms`（计划退化成 `20000 × 20000` 笛卡尔积） |
| **导入顺序：先节点后关系** | 关系两端必须先存在 | — |
| **`CREATE` 优先于 `MERGE`** | `MERGE` 要查重 | `MERGE` 约为 `CREATE` 的 2~3 倍 |
| **控制批量大小** | 单事务过大 → 内存 + 锁压力 | 单事务 60000 关系 `1981 ms`；`IN TRANSACTIONS OF 5000` `8042 ms` |
| **避免 `Eager` 算子** | 阻塞算子要先物化全部中间结果 | 见 [Cypher查询与执行计划.md](Cypher查询与执行计划.md) |
| **预热页缓存** | 首次读盘 vs 命中内存 | 冷 `5.4 s` → 热 `0.9 s`（≈6 倍） |
| **并行导入** | 多线程摊开 | 只在批次互不冲突时安全 |

⚠️ **两条最容易被误解的点**：

- **"分批一定更快"是错的**。本仓实测单事务一次写 60000 条关系 `1981 ms`，
  改成分批 `IN TRANSACTIONS OF 5000` 反而 `8042 ms`（**慢约 4 倍**）。
  分批换来的**不是速度，是"有界的内存与锁"** —— 这是吞吐与可控性的交易。
- **最大的初始导入不该用 Cypher**。**冷库全量初始化**用 **`neo4j-admin database import`**
  （离线、绕过事务与约束校验、最快）；`LOAD CSV` / APOC 适合**增量**与**在线补数据**。

## 六、导出与迁移怎么做？

**本节要点**：社区版**只能离线备份**（停库 → dump → 启库）；企业版才有在线备份。
跨版本迁移**一律先 dump**，因为存储格式会变（见 [架构与存储引擎.md](架构与存储引擎.md) 第四节）。

| 方式 | 命令 / 过程 | 版本 | 特点 |
|---|---|---|---|
| **离线备份** | `neo4j-admin database dump neo4j` | 社区版 ✅ | **要停库**；产物是逻辑备份 |
| **离线恢复** | `neo4j-admin database load neo4j --from-path=… --overwrite-destination=true` | 社区版 ✅ | 全量覆盖目标库 |
| **在线备份** | `neo4j-admin database backup` | **仅企业版** | 不停机 |
| **导出为 CSV** | `apoc.export.csv.all('out.csv', {})` | 有 APOC 即可 | 便于喂给别的系统 |
| **导出为 GraphML/JSON** | `apoc.export.graphml.all(...)` | 有 APOC 即可 | 可视化 / 迁移 |

本仓实测（5.26 社区版离线 dump → load）：**101000 节点 / 300000 关系 / 7 个索引**完整恢复。

⚠️ **迁移三条纪律**：

1. **跨大版本必须走 dump/load，不要直接拷贝 `data/` 目录** —— 5.x 的存储格式演进（见
   [架构与存储引擎.md](架构与存储引擎.md) 第四节）会让旧文件在新版本上不可直接读；
2. **恢复目标库是"覆盖"**：`--overwrite-destination=true` 会清掉目标库现有数据，执行前确认是空库或已备份；
3. **每次迁移后跑一次一致性验证**：节点 / 关系 / 索引计数对得上，再放行（本仓的验证就是那三个数字）。

## 使用：从 CSV 到图库的完整导入

**本节要点**：一条可复现的链路 —— **建约束 → 导节点 → 导关系 → 校验计数**。
本机读数附在每一步后面。

```bash
# ① 文件放进容器的 import 目录（容器里 file:/// 指的就是它）
#    本仓：-v <宿主目录>:/var/lib/neo4j/import
```

```cypher
// ② 先建唯一约束 —— 这一步决定了后面导关系的速度（数量级差别）
CREATE CONSTRAINT csvuser_id IF NOT EXISTS FOR (u:CsvUser) REQUIRE u.id IS UNIQUE;

// ③ 导节点（表头 id,name,age；类型显式转换）
LOAD CSV WITH HEADERS FROM 'file:///csv_users.csv' AS row
CREATE (:CsvUser {id: toInteger(row.id), name: row.name, age: toInteger(row.age)});

// ④ 导关系（两端靠唯一索引定位）
LOAD CSV WITH HEADERS FROM 'file:///csv_follows.csv' AS row
MATCH (a:CsvUser {id: toInteger(row.from)}), (b:CsvUser {id: toInteger(row.to)})
CREATE (a)-[:CF]->(b);

// ⑤ 校验计数：三处对得上才算导入成功
MATCH (u:CsvUser) RETURN count(u) AS users;
MATCH (:CsvUser)-[r:CF]->(:CsvUser) RETURN count(r) AS rels;
SHOW CONSTRAINTS YIELD name RETURN name;
```

实测读数（内核 5.26.31，容器 `import/` 挂载，热缓存）：

```text
20000 用户 纯 CREATE      : 425 ~ 876 ms      （冷启动首次 5425 ms）
20000 用户 MERGE+唯一约束 : 1496 ~ 2266 ms    （冷启动首次 7942 ms）
60000 关系 有唯一索引      : 3299 ~ 7163 ms
单行关系 有约束            : 521 ms
单行关系 无约束(全扫)      : 1679 ms           （计划退化成 20000 × 20000 笛卡尔积）
```

⭐ **判据表**：

| 观察 | 判 |
|---|---|
| 导关系和导节点耗时**同量级** | 索引用上了（每行是索引定位） |
| 导关系**远慢于**导节点（差几十倍） | 关系两端的 `MATCH` 没走索引 —— 先补约束/索引 |
| `MERGE` 明显慢于 `CREATE` | 正常（查重开销）；能用 `CREATE` 就别用 `MERGE` |
| 冷启动比热慢 5~10 倍 | 页缓存未命中，属正常；别把冷启动读数当稳定性能 |
| 计数与源文件行数一致 | 导入完整（本仓 20000 / 60000 对得上） |

⚠️ **关于计时口径**（本节读数怎么来的）：单条语句的耗时取自 **cypher-shell 的 `ready to start consuming query after N ms`**（数据库侧计时，**不含** shell 启动开销；
本机 cypher-shell 每次启动本身要 **7~8.6 s**，直接用 `time` 测会把这段算进去）。
含随机性 / 缓存效应的读数**只给区间与趋势**，不给单一"精确值"。

## 延伸追问

- **什么时候该把属性变成节点？**
  → 当这个值**需要被独立引用 / 作为查询起点 / 需要承载自己的属性或关系**时。
  反判据同样重要：**不要为了"看起来更图"而过度节点化** —— 取值很少、从不被单独查询的东西
  （性别、状态码）做成节点只会让每条查询多一跳。
- **`LOAD CSV` 大数据量怎么分片？**
  → ①大文件拆成多个小文件，**多个客户端并行**导入不同分片；②单文件用
  `CALL { … } IN TRANSACTIONS OF N ROWS` 或 `apoc.periodic.iterate` 控制批量；
  ③⚠️ **真正的冷库全量初始化不要用 LOAD CSV** —— 用 `neo4j-admin database import` 离线导入，
  它绕过事务与逐行约束校验，是数量级的差距。`LOAD CSV` 的位置是**在线增量**。
- **APOC 和 GDS 是一回事吗？**
  → 不是。**APOC 是通用过程库**（导入导出、结构操作、工具函数），**GDS 是图算法引擎**
  （PageRank / Louvain / 最短路等）。两者都是插件，解决的是完全不同的问题；
  导入选 APOC，算图选 GDS（见 [GDS图算法实战.md](GDS图算法实战.md)）。
- **导关系为什么比导节点慢这么多？**
  → 因为**导节点只写记录，导关系还要"先找到两端节点"**。找到的方式决定一切：
  靠唯一索引是"按号取记录"（O(1)），没索引就得把该标签的所有节点扫一遍（O(n)）。
  本仓的对比（有索引 60000 行 3.3~7.2 s vs 无索引**单行**就要 1679 ms）就是这个道理的极端体现 ——
  无索引时计划退化成 `20000 × 20000` 的笛卡尔积，规模一大等于不可行。
- **导入时用 `MERGE` 还是 `CREATE`？**
  → 需要**幂等**（同一份文件可重复跑、已存在的更新而不是重复创建）→ `MERGE`（慢，要查重）；
  一次性干净的初始导入 → `CREATE`（快）。⚠️ 用 `MERGE` 时**务必有对应的唯一约束**，
  否则 `MERGE` 在并发下可能创建重复节点（约束是它"查重"能走上索引的前提）。
- **导入后为什么查询还是慢？**
  → 常见三因：①**类型存错了**（`id` 存成字符串，`= 50000` 用不上索引）；②**约束/索引建晚了**
  （数据先到、索引后建，要等索引 ONLINE 才生效）；③**统计信息没更新**（`CALL db.stats.retrieve` / 重规划）。
  排查手法见 [索引设计与查询优化.md](索引设计与查询优化.md) 与
  [Cypher查询与执行计划.md](Cypher查询与执行计划.md)。
