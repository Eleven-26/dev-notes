## 一、内存怎么分：Heap 还是页缓存？

**本节要点**：Neo4j 的内存是**两笔独立预算** —— **Heap**（JVM 堆：查询执行、事务状态、GDS 投影）
与 **页缓存 Page Cache**（缓存存储文件页，避免每次读盘）。两者**不是此消彼长，而是各管一摊**：
页缓存小了就反复读盘，堆小了就 OOM 或频繁 GC。

```text
        机器物理内存
┌──────────────────────────────────────────────┐
│  Page Cache          │   Heap (JVM)  │  OS / 其他 │
│  缓存 neostore.* 页    │  查询/事务/GDS  │  留白      │
└──────────────────────────────────────────────┘
       ↑ 越大越好               ↑ 按并发与算法留
   理想：≥ 存储文件总体积      经验：数据量不大时 1~4G 起步
```

| 维度 | Heap（JVM 堆） | Page Cache（页缓存） |
|---|---|---|
| 装什么 | 查询执行状态、事务中间结果、**GDS 投影**、对象缓存 | `neostore.*` 存储文件的**页** |
| 小了会怎样 | GC 频繁 / OOM；大事务、GDS 跑不动 | 反复读盘，遍历变慢（但不报错） |
| 大了会怎样 | GC 停顿变长 | 挤占 OS 内存，可能触发换页 |
| 本仓实测值 | `max 1.00 GiB`，实际用 **≈276 MiB** | `512 MiB`（存储文件仅 **27 MB** → 全量可缓存） |
| 定大小的判据 | 并发查询数 + 最大事务 + GDS 投影（本篇第三节） | **尽量装下存储文件总体积** |

⭐ **两条经验值**：

- **页缓存优先给足**：如果存储文件能全装进页缓存，**绝大多数访问都在内存里**，性能跃升。
  本仓存储 27 MB 对上 512 MiB 页缓存 → 全命中。⚠️ **这是为什么"数据量不大时 Neo4j 很快"** ——
  页缓存装得下就几乎没有磁盘 IO。
- **堆不用给太大**：堆主要用于**查询与事务**，不是装数据（数据在页缓存里）。堆给太大反而拉长 GC 停顿。

⚠️ **页缓存效果实测**（`PROFILE MATCH (u:User) RETURN count(u.id)`，读 10 万节点的属性）：

```text
冷页缓存（重启后首次）：1370 ms   ← 要真读盘
热页缓存（同一查询再跑）：186 ms   ← 全内存
                         ≈ 7 倍
```

这就是"页缓存命中率"为什么是**第一个要看的监控指标**（见第五节）。

## 二、关键参数怎么配？（5.x 改名是坑）

**本节要点**：`neo4j.conf` 在 **5.x 做了一次改名**，老教程照抄会**直接起不来或静默不生效**。
⚠️ 而且改名是**部分的**：`heap` / `pagecache` 搬到了 `server.memory.*`，但**事务内存没搬**。

```properties
# /var/lib/neo4j/conf/neo4j.conf（本仓容器实际配置，节选）
server.memory.heap.initial_size=            # 未设 → 交给 JVM 自适应
server.memory.heap.max_size=1G
server.memory.pagecache.size=512m
```

本机实测（`CALL dbms.listConfig()`，内核 5.26.31）：

| 参数名 | 实测值 | 说明 |
|---|---|---|
| `server.memory.heap.max_size` | `1.00GiB` | ⭐ 旧名 `dbms.memory.heap.max_size` **已改名** |
| `server.memory.heap.initial_size` | `NULL`（未设） | 不设则 JVM 自适应 |
| `server.memory.pagecache.size` | `512.00MiB` | ⭐ 旧名 `dbms.memory.pagecache.size` **已改名** |
| `server.memory.off_heap.transaction_max_size` | `2.00GiB` | 事务的**堆外**上限 |
| `dbms.memory.transaction.total.max` | `716.80MiB` | 事务内存总量上限（**名字没搬**） |
| `db.memory.transaction.total.max` | `0B` | 同族新名（本仓为 0，未触及） |
| `db.transaction.timeout` | `0s`（= 不限） | ⭐ 旧名 `dbms.transaction.timeout` |
| `db.lock.acquisition.timeout` | `0s`（= 不限） | 锁获取超时 |
| `db.transaction.concurrent.maximum` | `1000` | 并发事务上限 |
| `db.checkpoint.interval.time` | `15m` | 检查点间隔（时间） |
| `db.checkpoint.interval.tx` | `100000` | 检查点间隔（事务数） |
| `db.logs.query.enabled` | `INFO` | ⚠️ **枚举**：`OFF` / `INFO` / `VERBOSE` |
| `db.logs.query.threshold` | `0s` | 慢查询阈值 |
| `server.bolt.thread_pool_min_size` | `5` | Bolt 线程池下限 |
| `server.bolt.thread_pool_max_size` | `400` | Bolt 线程池上限 |

⚠️ **三个必须记住的坑**：

1. **`db.logs.query.enabled` 不是布尔值**。写 `=true` **启动直接失败**，必须写
   `OFF` / `INFO` / `VERBOSE` 三选一（本仓实测踩过，服务起不来）。
2. **改名是部分的，别"一刀切"替换**。实测仍保留旧前缀的有：
   `dbms.memory.tracking.enable`、`dbms.memory.transaction.total.max`、`dbms.logs.http.enabled`，
   以及 `db.memory.transaction.*` / `db.memory.pagecache.warmup.*` 这一族。
   ⚠️ 正确姿势是**改完用 `CALL dbms.listConfig()` 核对生效值**，不要靠记忆替换。
3. **动态 ≠ 全部**。部分参数可在线改（`CALL dbms.setConfigValue(...)`，企业版能力更全），
   但 `server.memory.heap.*` 这类**必须重启**才生效。改内存参数一律按"要重启"来安排窗口。

## 三、慢查询怎么定位？

**本节要点**：三条路 —— **①`PROFILE` 看计划**（最直接）、**②`SHOW TRANSACTIONS` 看正在跑的**、
**③慢查询日志**（本仓实测**未能落盘**，见下方负结果）。诊断顺序建议：先看计划、再看运行中事务、最后才依赖日志。

### 3.1 PROFILE 看计划（首选）

```cypher
PROFILE MATCH (u:User {id: 0})-[:FOLLOWS*1..3]->(x) RETURN count(DISTINCT x);
```

看**算子类型**（`NodeByLabelScan` / `CartesianProduct` 是坏信号）与 **`dbHits`**。
完整读法见 [Cypher查询与执行计划.md](Cypher查询与执行计划.md) 与
[索引设计与查询优化.md](索引设计与查询优化.md)。

### 3.2 SHOW TRANSACTIONS 看正在跑的（取代旧过程）

```cypher
SHOW TRANSACTIONS
YIELD transactionId, username, status, elapsedTime, activeLockCount, currentQuery
RETURN transactionId, username, status, elapsedTime, activeLockCount, currentQuery;
```

⚠️ **5.x 用 `SHOW TRANSACTIONS` 取代了 `dbms.listTransactions()`**。
本仓实测它能看到 `status`（如 `Running` / `Blocked`）、`elapsedTime`（如 `PT5M1.255S`）、
`activeLockCount`（如 `2`）、以及**正在执行的语句文本** —— 定位"谁在锁着谁"就靠它
（用法见 [事务与并发控制.md](事务与并发控制.md) 的使用一节）。

### 3.3 慢查询日志 —— 本仓实测的**负结果**

按官方文档配好了，但**日志始终是空的**：

```text
db.logs.query.enabled   = INFO        （也试过 VERBOSE）
db.logs.query.threshold = 0s
db.logs.query.parameter_logging_enabled = true
user-logs.xml 里补了 QueryLog appender
→ /logs/query.log 仍是 0 字节（跑过多条 >100ms 的慢查询）
```

```text
$ docker exec neo4j-lab sh -c "wc -c /logs/query.log"
0 /logs/query.log
```

⭐ **如实报告**：在**本仓这个 5.26.31 社区版容器 + 该 `user-logs.xml` 组合**下，
`query.log` **未落盘**。可能原因（未逐一验证）：该镜像的 `user-logs.xml` 覆盖了默认 appender 配置、
或 `db.logs.query.*` 与 `dbms.logs.query.*` 的 appender 名映射不一致。
⚠️ **实践建议**：慢查询先用 **`PROFILE` + `SHOW TRANSACTIONS`** 定位；
若确需查询日志，**先在前置环境验证它真的写盘**再依赖它 —— 别把"配了"当成"生效了"。

### 3.4 常见慢查询模式速查

| 症状（计划里看到） | 病因 | 处方 |
|---|---|---|
| `NodeByLabelScan` 打头 | 起点没索引 | 建索引；或改写成有索引的起点 |
| `CartesianProduct` | 两个 `MATCH` 没连起来 | 用关系把模式连成一条路径 |
| `Eager` 出现在中间 | 阻塞算子提前物化全部结果 | 拆分查询；避免"先删后写"的混合操作 |
| `AllNodesScan` | 连标签都没指定 | 加标签 + 索引起点 |
| `dbHits` 远大于结果数 | 扫描后过滤 | 把过滤条件做进索引（复合索引） |

## 四、备份与恢复怎么做？

**本节要点**：**社区版只有离线备份**（停库 → `dump` → 启库）；**在线备份是企业版专属**。
跨版本恢复**必须走 dump/load**，别直接拷 `data/` 目录。

| 方式 | 命令 / 过程 | 可用版本 | 停机 |
|---|---|---|---|
| **离线备份** | `neo4j-admin database dump neo4j` | 社区版 ✅ | **要停库** |
| **离线恢复** | `neo4j-admin database load neo4j --from-path=… --overwrite-destination=true` | 社区版 ✅ | 要停库 |
| **在线备份** | `neo4j-admin database backup` | **企业版** | 不停机 |
| **一致性检查** | `neo4j-admin database check` | 社区版 ✅ | 建议停库 |
| **Aura 自动备份 / PITR** | 托管服务内置 | Aura | 不停机 |

本仓实测（5.26 社区版，离线 dump → load）：**101000 节点 / 300000 关系 / 7 个索引**完整恢复。

```bash
# 离线备份（社区版）——顺序不能反：停库 → dump → 启库
docker exec neo4j-lab neo4j-admin database dump neo4j --to-path=/backups
# 离线恢复
docker exec neo4j-lab neo4j-admin database load neo4j \
  --from-path=/backups --overwrite-destination=true
```

⚠️ **备份三条纪律**：

1. **备份要"停库"就别硬上**：社区版的 dump 要求数据库**不可写**。生产用社区版的话，
   备份窗口要有停写预案（或用挂载快照兜底）。
2. **恢复是"覆盖"**：`--overwrite-destination=true` 会清掉目标库现有数据 —— 执行前确认目标。
3. **备份没演练过等于没有**：定期做**恢复演练**，验收标准就是那三个数字
   （节点 / 关系 / 索引计数对得上）。本仓的验收方式就是查这三个计数。

## 五、监控哪些指标？

**本节要点**：社区版下 **Neo4j 自身的 JMX Bean（`org.neo4j:*`）未暴露** ——
本仓实测 `dbms.queryJmx('*:*')` 只返回 **27 个 JVM 级 Bean**（`java.lang:*` / `com.sun.management:*`）。
所以社区版监控主要靠 **JVM 指标 + Cypher 过程**；企业版才有 `org.neo4j:*` 那套细指标。

```cypher
// ① JVM 堆用量（本仓实测）
CALL dbms.queryJmx('java.lang:type=Memory') YIELD attributes
RETURN attributes.HeapMemoryUsage AS heap, attributes.NonHeapMemoryUsage AS nonheap;
```

```text
heap    : used 289256168 B (≈276 MiB) / max 1073741824 B (1 GiB)
nonheap : used 474854704 B (≈453 MiB) / max -1（无上限）
```

```cypher
// ② 图规模与索引体量（社区版可用）
CALL db.stats.retrieve('GRAPH COUNTS') YIELD section, data RETURN section, data;
```

实测输出（节选，本仓）：节点总计 **121000**；关系总计 **300001**（其中 `FOLLOWS` 300000）；
索引含 `RANGE`（`user_id` size 100000）、`VECTOR`、`TEXT`、`LOOKUP` 等。

⭐ **要盯的指标清单**：

| 指标 | 从哪来 | 看什么 |
|---|---|---|
| **Heap 使用率** | `dbms.queryJmx('java.lang:type=Memory')` | 长期 >90% → 加堆或查泄漏；频繁 GC → 堆过大或分配不合理 |
| **Page Cache 命中率** | 官方指标（需 `org.neo4j:*`，本仓未暴露） | 低 → 页缓存不够 / 存储文件太大（第一节那 7 倍差距就是它） |
| **查询延迟 P50 / P99** | 应用侧埋点（或慢查询日志，⚠️ 本仓未落盘） | P99 劣化往往先于平均延迟 |
| **事务吞吐 / 回滚率** | 应用侧 + `SHOW TRANSACTIONS` | 回滚率高 → 死锁 / 约束冲突（见 [事务与并发控制.md](事务与并发控制.md)） |
| **活跃锁与阻塞** | `SHOW TRANSACTIONS` 的 `activeLockCount` / `status` | 出现 `Blocked` 且时间增长 → 有长事务持锁 |
| **连接数 / Bolt 线程池** | `server.bolt.thread_pool_*` + 连接监控 | 线程池打满 → 拒绝新连接 |
| **磁盘与存储增长** | 宿主 / 容器磁盘 | 见 [架构与存储引擎.md](架构与存储引擎.md) 3.3「删除不缩文件」→ 空间只增不减 |
| **Raft / 集群状态** | **企业版**（`SHOW SERVERS` 等） | 社区版无此能力（见 [因果集群与高可用.md](因果集群与高可用.md)） |

⚠️ **一个社区版的现实**：本仓实测 `dbms.queryJmx('org.neo4j:*')` 返回**空**、`db.stats.retrieve`
只有 `GRAPH COUNTS` / `TOKENS` / `QUERIES` 三个 section（**没有 "PAGE CACHE"**）——
所以"页缓存命中率"这类指标在社区版要靠**操作系统层的磁盘 IO 观测**间接判断，
别指望有个现成过程能查出来。

## 六、怎么把运维自动化？

**本节要点**：容器化部署是当前最省事的方式；编排（K8s Operator）与健康检查是上生产的两块拼图。

| 环节 | 做法 | 注意 |
|---|---|---|
| **容器化** | 官方镜像 `neo4j:5.26-community`；`/data` 用 **volume** 持久化 | ⚠️ **不要在无 volume 的容器里存数据** —— 容器一删数据全没 |
| **配置注入** | 挂载 `neo4j.conf` 或设环境变量 `NEO4J_server_memory_heap_max__size` 等 | ⚠️ 环境变量写法是 **下划线转义**（`.`→`_`、`_`→`__`），易写错；改完核对 `dbms.listConfig()` |
| **健康检查** | Bolt 探活（`RETURN 1`）或 HTTP `:7474` 端口探测 | 别用"端口开着"当健康 —— 端口开但库在恢复中也会回拒绝 |
| **备份自动化** | 定时任务：停写 → dump → 启写 → 校验计数 | 见第四节；**恢复演练**要一起排进计划 |
| **K8s 编排** | 官方 **Neo4j Helm Chart / Operator** | 有状态集 + PVC；集群形态需企业版 |
| **日志与指标采集** | 挂 `/logs` 卷 + 采集 JVM 指标 | ⚠️ 本仓 `query.log` 未落盘（第三节），采集前先验证有内容 |

```bash
# 健康检查的最小实现：能跑通一条语句才算健康
docker exec neo4j-lab cypher-shell -u neo4j -p "$NEO4J_PASS" "RETURN 1;" >/dev/null 2>&1 \
  && echo healthy || echo unhealthy
```

⚠️ **编排前先想清楚"要不要集群"**：社区版**不支持集群**（实测 `SHOW SERVERS` 报
`Unsupported administration command`）。要 Core / Read Replica 就得**企业版或 Aura**，
这在选型阶段就要定（见 [选型与落地案例.md](选型与落地案例.md)）。

## 使用：核对参数并观察堆

**本节要点**：一条"改配置 → 核对生效 → 看资源"的闭环，全部用内置过程完成，不需要额外的监控组件。

```cypher
// ① 核对关键参数是否按预期生效（改完 conf 一定要做这一步）
CALL dbms.listConfig() YIELD name, value
WHERE name IN [
  'server.memory.heap.max_size', 'server.memory.pagecache.size',
  'db.transaction.timeout', 'db.logs.query.enabled'
]
RETURN name, value ORDER BY name;

// ② 看 JVM 堆用量（社区版拿不到 org.neo4j:* 指标，但 JVM 指标是有的）
CALL dbms.queryJmx('java.lang:type=Memory') YIELD attributes
RETURN attributes.HeapMemoryUsage AS heap;

// ③ 看正在跑的事务与锁（慢查询 / 阻塞的第一现场）
SHOW TRANSACTIONS
YIELD transactionId, status, elapsedTime, activeLockCount, currentQuery
RETURN transactionId, status, elapsedTime, activeLockCount, currentQuery;

// ④ 看图规模与索引体量
CALL db.stats.retrieve('GRAPH COUNTS') YIELD section, data RETURN section, data;
```

实测输出（内核 5.26.31）：

```text
① server.memory.heap.max_size     = "1.00GiB"
   server.memory.pagecache.size   = "512.00MiB"
   db.transaction.timeout         = "0s"
   db.logs.query.enabled          = "INFO"

② heap used ≈ 276 MiB / max 1 GiB

③ SHOW TRANSACTIONS 可见 status / elapsedTime(PT…S) / activeLockCount / currentQuery

④ GRAPH COUNTS：nodes 121000；relationships 300001（FOLLOWS 300000）
```

⭐ **判据表**：

| 观察 | 判 |
|---|---|
| `dbms.listConfig()` 里查不到你写的旧参数名 | 参数**改名了**（第一节第二节的坑），改成新名再看 |
| 堆使用率长期贴着 `max` | 加 `server.memory.heap.max_size`，或查是否有大事务 / GDS 投影没释放 |
| 存储文件（`du -sh data/databases`）远小于页缓存设置 | 页缓存够用，遍历基本全内存（本仓 27 MB vs 512 MiB） |
| `SHOW TRANSACTIONS` 有 `Blocked` 且 `elapsedTime` 一直涨 | 有长事务持锁，按 [事务与并发控制.md](事务与并发控制.md) 处理 |
| `query.log` 一直是 0 字节 | 别依赖它；用 PROFILE + SHOW TRANSACTIONS（第三节负结果） |

## 延伸追问

- **Heap 和页缓存怎么分配？**
  → 记住**数据在页缓存、计算在堆**：页缓存**尽量装下存储文件总体积**（本仓 27 MB ≪ 512 MiB，全命中）；
  堆按"并发查询数 + 最大事务 + GDS 投影"留（本仓实际用 276 MiB，1 GiB 的上限很宽裕）。
  ⚠️ 别把数据想成装在堆里 —— 那是 JVM 缓存型数据库的思路，Neo4j 的数据在**页缓存 + 存储文件**。
  两者之和要给 OS 留余地，不能吃满物理内存。
- **页缓存命中率低怎么办？**
  → 三条路：**①加页缓存**（最直接，只要物理内存允许）；**②减数据**（归档冷数据、清理不再需要的
  中间标签 —— 本仓就踩过"探针数据把图撑到 80 万节点"的坑）；**③优化访问模式**（让查询集中在热数据上，
  别做全库扫描）。⚠️ 社区版**没有现成的页缓存命中率指标**（本仓实测无 `PAGE CACHE` section），
  要靠操作系统的磁盘 IO 观测间接判断。
- **社区版和企业版运维差异？**
  → 社区版：**无集群**（`SHOW SERVERS` 不可用）、**无在线备份**（只能离线 dump）、
  **无 `org.neo4j:*` JMX 细指标**、无多数据库。企业版补齐这四块（还有在线备份 / 热备份 / RBAC / 集群）。
  ⚠️ 所以"运维方案"在选型阶段就分叉：小规模单机社区版够用，要 HA 或在线备份就必须企业版 / Aura。
- **慢查询日志为什么不落盘，怎么排查？**
  → 本仓实测：`db.logs.query.enabled=INFO` + `threshold=0s` + 补了 QueryLog appender，
  `query.log` 仍 0 字节。⚠️ **这类"配了不生效"最需要的是"验证生效"而不是继续加配置** ——
  先在**干净镜像**上确认默认行为，再逐步加自定义 `user-logs.xml`，用二分定位是哪一层覆盖了它。
  在此之前，**用 `PROFILE` + `SHOW TRANSACTIONS` 顶上**。
- **为什么要给存储文件留意的"只增不减"？**
  → 见 [架构与存储引擎.md](架构与存储引擎.md) 3.3：Neo4j **删除数据不缩小文件**（记录槽复用，
  `.id` 文件记高水位）。所以**磁盘规划按"峰值历史规模"而非"当前规模"**，
  想回收空间只能重建库（导出 → 重建 → 导入）。这是容量规划里最容易踩空的一条。
