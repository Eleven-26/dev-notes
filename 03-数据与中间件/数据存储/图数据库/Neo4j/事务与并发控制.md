## 一、ACID 各自靠什么实现？

**本节要点**：四个字母在图库里各有明确的落点 —— **原子性与持久性靠事务日志，一致性靠约束 + 应用，隔离性靠锁**（默认 READ COMMITTED，不是快照隔离）。

| 性质 | 实现 | 说明 |
|---|---|---|
| **A** 原子性 | 事务日志（`neostore.transaction.db.*`） | 事务内的所有修改先进日志；失败 / 回滚时按日志撤销 |
| **C** 一致性 | 唯一约束 + 应用层校验 | 图库只保证"声明过的约束"与结构一致性，跨实体的业务一致性仍归应用 |
| **I** 隔离性 | **行级锁**（节点 / 关系上的共享锁、排他锁） | 默认 **READ COMMITTED**；不加锁的读可能看到别的事务刚提交的值 |
| **D** 持久性 | 事务日志 + checkpoint | 提交先落日志；`checkpoint` 把内存里的记录刷进 store 文件（默认 15 min 或 10 万事务触发一次） |

⭐ 一个和"页缓存"有关的推论：**已提交的数据在崩溃后不会丢**（日志保证了），
但**磁盘上的 `neostore.*.db` 不会立刻更新** —— 这也是为什么"刚写完就把库停掉再起，数据还在，
但文件大小可能没变"。本仓实测：`db.checkpoint.interval.time = 15m`、`db.checkpoint.interval.tx = 100000`。

## 二、默认隔离级别到底是什么？

**本节要点**：Neo4j 的默认隔离级别是 **READ COMMITTED**（读已提交）—— 一个事务**不会看到别的事务未提交的修改**，但**能看到别人已提交的修改**。它不是"可重复读"，更不是快照隔离。

### 2.1 实测：同一事务内两次读，中间被别的事务改了会怎样

构造：事务 T1 显式开启 → 读 `User{id:0}.age` → **用 APOC 睡 9 秒做屏障** → 期间并发事务把 `age` 从 25 改成 31 并提交 → T1 再读一次。

```text
t1_first_read    25     ← 第一次读（此时库里是 25）
（并发写事务 SET age = 31 并提交）
t1_second_read   31     ← 第二次读，读到了别人刚提交的值
```

⭐ 结论：**同一事务内两次读到的值不同** → 确认是 **READ COMMITTED**，而**不是可重复读**（RR 会保持 25）。

⚠️ 一个必须说明的**测量陷阱**：我们最早一次做这个实验时，输出是 `25 → 25`，
差点被误判成"Neo4j 是可重复读"。查下来是**没有屏障**：读事务还没来得及读第二次，
并发写就已提交 / 或读事务根本没和写事务重叠。加同步屏障（用 `apoc.util.sleep` 把读事务撑开、
再轮询 `SHOW TRANSACTIONS` 确认它真的在运行）之后，两种客户端（`cypher-shell` 显式事务
与 Go 驱动显式事务）都稳定得到 **25 → 31**。
⭐ 教训：**并发实验没有屏障，读数就是噪声。**

### 2.2 它还支持别的隔离级别吗

```cypher
-- Neo4j 不提供 SET TRANSACTION ISOLATION LEVEL 这类语法
```

⚠️ 结论：**没有可切换的隔离级别**。需要"读一致快照"的场景，
惯用做法是**把读放在一个短事务里一次读完**，或由应用层做版本判断（乐观并发）。

## 三、锁机制：谁被锁、锁多久？

**本节要点**：Neo4j 在**节点**和**关系**两级加锁。**写**会拿**排他锁**，**读**在事务内也会拿**共享锁**；锁**持有到事务结束**（提交或回滚）。所以"事务开得越久，锁握得越久"。

### 3.1 实测：写锁互斥，后到者阻塞

构造：事务 A 先 `SET` 节点 `id:0`，持锁睡 6 秒；事务 B 在 A 持锁期间对**同一个节点**发写。

```text
基线（无争用，含 cypher-shell 启动开销）：3696 ms
[11:35:19.179] 持有者启动：u0 写锁 + sleep 6s
[11:35:21.293] 等待者发出对同一节点的写
[11:35:28.747] 等待者返回，用时 7459 ms（含 cypher-shell 启动；持锁窗口剩余约 4s）
```

⭐ 读法：`7459 − 3696 ≈ 3.7 s`，正是"等待者从 21.293 开始等、等到持有者约 25 秒释放锁"的时长
（持锁窗口 6 s 减去先到的 2 s）。**结论：同一节点上的写是互斥的，后到者排队**。

### 3.2 显式悲观锁：用在"检查后再写"的地方

```cypher
// 读并锁住节点（应用层保证唯一性的常用手法）
MATCH (u:User {id: $uid})
SET u._lock = true          // 写一下即拿到排他锁
WITH u
MERGE (g:Group {name: $gname})   // 再去做"检查后创建"
...
```

⭐ 惯例：**要对一组节点做"先读后写"的唯一性判断时，先用一次无副作用的写把锁拿到**，
否则两个并发事务可能都读到"不存在"，然后都去创建 —— 这正是 `MERGE` 在并发下会撞锁的原因（见 3.3）。

### 3.3 `MERGE` 的锁顺序问题

`MERGE` 是"匹配到了就用，匹配不到就建"。并发下两个事务同时 `MERGE` 同一个模式时，
**双方都可能先读到"不存在"，再一起尝试创建** —— 这时一个会拿到锁、另一个等待，
等待者拿到锁后发现**数据已经被对方建出来了**，于是重新匹配（Neo4j 会在这时抛唯一约束冲突）。
⚠️ 所以：**`MERGE` 的目标属性上一定要有唯一约束**，否则会出现重复节点。

## 四、死锁怎么发生、谁被回滚？

**本节要点**：两个事务**以不同顺序**持有并申请同一组锁，就会成环。Neo4j 有**主动的死锁检测**（`ForsetiClient`），检测到环后**挑一个事务当牺牲者回滚并抛错**，让另一个继续跑。

### 4.1 实测

构造：A 先锁 `id:0` 再要 `id:1`；B 先锁 `id:1` 再要 `id:0`（经典 AB-BA）。

```text
[11:35:37.078] 争用中的事务视图：
transactionId, status, elapsedTime, activeLockCount, currentQuery
"neo4j-transaction-136", "Running", PT2.527S, 2, "CALL apoc.util.sleep(3000)"
"neo4j-transaction-133", "Blocked by: [neo4j-transaction-136]", PT4.903S, 2,
                          "MATCH (u:User {id:1}) SET u.dl = 1 RETURN u.id AS a_locked_1"
```

最终结果：**A 正常提交**（输出了两个节点的写结果）；**B 被回滚**，报错：

```text
An error occurred while in an open transaction. The transaction will be rolled back and terminated.
Error: ForsetiClient[transactionId=136, clientId=1] can't acquire ExclusiveLock{owner=ForsetiClient[transactionId=133, clientId=2]} on NODE(1) because holders of that lock are waiting for ForsetiClient[transactionId=136, clientId=1].
 Wait list:ExclusiveLock[Client[133] waits for [ForsetiClient[transactionId=136, clientId=1]]]
```

⭐ 三点可直接用：

1. **死锁不会挂起，会被检测并解决**（代价是回滚一个事务）；
2. **牺牲者是哪一个由引擎决定**，应用不能假设 —— 所以**必须能安全重试**；
3. 报错信息里带 `ForsetiClient` 与 `Waits for` 链，是排查"谁锁了谁"的第一手材料。

### 4.2 重试与预防

```text
重试三原则：
① 有限次数（如 3 次）+ 指数退避 + 抖动，别无限重试；
② 只在"可重试错误"上重试（死锁 / 锁超时 / 瞬时不可用），事务里有副作用时别盲目重试；
③ 把整个事务包在重试里，不要只重试失败的那一条语句。
```

⭐ **预防比重试更划算**：**统一访问顺序**（比如永远按 `id` 升序去改）能让 AB-BA 环根本形不成。

## 五、大事务与长事务怎么处理？

**本节要点**：事务越长，**锁持有越久、内存占用越大、失败重做的代价越高**。图库的"大事务"最典型就是**批量导入**。

| 风险 | 后果 |
|---|---|
| 锁持有时间 | 别人排队（3.1 实测后到者等了约 3.7 s） |
| 事务状态内存 | 每一条修改都要在内存里记着，大事务会把堆吃光 |
| 失败重做 | 事务回滚，前面全白做 |

### 5.1 批量写入：切子事务是"用吞吐换可控性"

```cypher
// 每 5000 行为一个子事务，边跑边提交
MATCH (n:User)
CALL {
  WITH n
  SET n.touched = true
} IN TRANSACTIONS OF 5000 ROWS;
```

⭐ 实测（导入 6 万条关系，Go 驱动计时，不含进程启动开销）：

| 写法 | 耗时 | 代价 |
|---|---|---|
| 单事务一次写完 | **1981 ms** | 中间状态全在内存 / 日志里，事务期间锁与内存随数据量线性增长 |
| `CALL { … } IN TRANSACTIONS OF 5000` | **8042 ms** | 慢约 **4 倍**（12 次独立提交的开销），换来**每批只占一个子事务的内存与锁** |

⚠️ **这是个反直觉但重要的结论**：`IN TRANSACTIONS` **不是提速手段**，
它的价值是**把不可控的大事务切成可控的小事务** —— 数据量一次吃得下、也能接受长事务时，
一条语句写完反而更快；数据量大到内存 / 锁扛不住时，才值得付这 4 倍的代价。

⚠️ **语法坑**：`IN TRANSACTIONS OF 5000` 后面**必须跟 `ROWS`**（写成 `OF 5000` 会报
`Invalid input '': expected an expression, 'ROW' or 'ROWS'` —— 实测踩过）。

### 5.2 两条硬规矩

1. **事务里不做 IO** —— 不要在事务中间发 HTTP / 调外部服务 / 等文件。
   事务一开锁就握住了，等外部服务的每一毫秒都是别人在排队。
2. **超时要显式设** —— 本仓实测默认值是 `db.transaction.timeout = 0s`（**不超时**），
   `db.lock.acquisition.timeout = 0s`（**等锁不超时**），`db.transaction.concurrent.maximum = 1000`。
   ⚠️ 生产上应给业务事务设一个上限，否则一个卡住的事务能把连接池拖干。

## 六、集群里的因果一致性怎么落到事务上？

**本节要点**：单机上"写完再读自己写的数据"是免费的；**因果集群**里读可能被路由到 Read Replica，
这时就要靠 **bookmark（因果令牌）** 保证"读到自己已经写过的那个事务之后的状态"。

```go
// Go 驱动：session 级 bookmark —— 同一 session 内的写后读自动带上因果链
s := d.NewSession(ctx, neo4j.SessionConfig{})
// ExecuteWrite 完成后，驱动把 bookmarks 记在 session 上
// 之后同一 session 的 ExecuteRead 会带上它，服务端据此路由到"已经追上"的副本
```

⭐ 关键区别（一句话）：

- **bookmark 保证的是"读到自己写过之后的状态"（因果一致 / read-your-own-writes）**，
  不是"读到全局最新" —— 别人的写你仍可能看不到；
- ⚠️ **community 版没有集群**：本仓实测 `SHOW SERVERS` 与 `CREATE DATABASE` 都返回
  `Unsupported administration command`，所以这一节的因果一致性是在**单机语义**上理解的，
  真集群行为（Core / Read Replica 的路由）**未实测**，见
  [因果集群与高可用.md](因果集群与高可用.md)。

## 使用：用 SHOW TRANSACTIONS 现场观察锁与阻塞

**本节要点**：线上"看起来卡住"时，第一步不是看代码，而是**看现在有哪些事务、谁在等谁**。

```cypher
// ① 当前所有事务：状态 / 已运行时长 / 持锁数 / 正在跑的语句
SHOW TRANSACTIONS
YIELD transactionId, status, elapsedTime, activeLockCount, currentQuery;

// ② 看谁被谁挡着（status 会是 "Blocked by: [neo4j-transaction-133]"）
SHOW TRANSACTIONS YIELD transactionId, status, elapsedTime, currentQuery
WHERE status STARTS WITH 'Blocked';

// ③ 万不得已时，终止一个卡死的事务
TERMINATE TRANSACTIONS 'neo4j-transaction-133';
```

⭐ 判据：

| 现象 | 判 |
|---|---|
| `status = "Blocked by: [...]"` 且 `elapsedTime` 一直涨 | 锁等待，顺着 `Blocked by` 找到持有者 |
| 某事务 `activeLockCount` 大且 `elapsedTime` 很长 | 长事务 / 大事务，考虑拆分 |
| 一堆事务都在等同一个 id | 热点节点（超级节点），写模型要改 |

⚠️ **5.x 改名提醒**：`dbms.listTransactions()` 在 5.x 已被 **`SHOW TRANSACTIONS`** 取代
（旧过程名直接不可用，实测），`dbms.listQueries()` 同理让位给 `SHOW TRANSACTIONS` / `SHOW QUERIES`。
老博客里的写法照抄会报"未注册的过程"。

## 延伸追问

- **Neo4j 支持 MVCC 吗？**
  → 不支持多版本并发控制（没有版本链、没有快照读）。它用**锁 + READ COMMITTED** 实现隔离：
  写之间靠排他锁互斥，读不加 MVCC 快照，所以同一事务内两次读之间若有别人提交，
  第二次会读到**新值**（本文第 2.1 节实测 25 → 31）。
  ⚠️ 需要"一致性快照"的场景，要靠"把读收进一个短事务"或应用层版本号，而不是指望数据库给快照。
- **死锁了谁被回滚？**
  → **由引擎（`ForsetiClient`）挑一个牺牲者**，应用无法指定。实测就是"一个提交、一个被回滚并抛
  `can't acquire ExclusiveLock ... Wait list: ...`"。所以正确姿势是**把整个事务做成幂等 + 可重试**，
  而不是猜谁会被牺牲。
- **事务里能做 HTTP 调用吗？**
  → 技术上能（如果有 APOC 的 `apoc.load.json` 之类），**但绝对不要**。事务一开锁就握住了，
  外部调用的延迟会直接变成别人的锁等待；调用失败还会把整个事务拖成回滚。
  正确做法：**先在事务外把需要的数据取好，再开事务只做读写**。
- **为什么默认不设事务超时？**
  → 实测 `db.transaction.timeout = 0s`（不超时）、`db.lock.acquisition.timeout = 0s`（等锁不超时），
  这是"不打断长查询"的保守默认。真正的线上要自己设：给业务事务一个上限，
  否则一个卡住的写事务会把后续请求全部堵在锁上、连接池被拖干。
- **`MERGE` 在并发下为什么会撞唯一约束？**
  → 因为 `MERGE` 是"先查后建"两步，两个并发事务可能**同时查到"不存在"**，然后一起创建；
  引擎在第二个提交时会因唯一约束冲突而回滚它。所以 **`MERGE` 依赖的属性上必须有唯一约束**
  （约束不只是"防脏数据"，也是让并发 `MERGE` 有确定性行为的必要条件）。
