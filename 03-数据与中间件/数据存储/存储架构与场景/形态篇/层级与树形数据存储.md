# 层级与树形数据存储

> 覆盖：组织架构、商品类目、评论楼中楼、文件目录——这类「**父子层级**」的数据怎么存：
> 邻接表 / 路径枚举 / 嵌套集 / 闭包表四种模型各自的读写代价、深递归与环的坑，
> 以及什么时候它其实是一张图而不是一棵树。
>
> 不覆盖：本篇讲这类数据的**存储形态与查询路径**（不碰某个库的具体语法细节）；
> 具体到某个库怎么写递归查询，见 `数据存储/关系型/` 族目录。
>
> 内容整理自个人学习笔记，素材见 [素材清单](../../../../素材清单.md)。
>
> 📎 本篇是**跨场景的归纳篇**：不引入新的实测读数，所引读数来自关联篇目的本机实测；列出的都是**相对代价与适用面**。

## 一、层级数据是「关系的一个特例」，但访问模式很特别

**本节要点**：层级就是**有向、无环、每个节点至多一个父**的边集合。「每条路径唯一」这个约束，是用更省的存储换来的——但前提是它真的成立。

- 三个高频动作：**查子孙 / 查祖先 / 查直接子节点**；
- 和一般图数据的区别：树**没有环**、**每条路径唯一**，所以不必为「任意两点是否可达」付费；
- 和 [关系数据存储.md](关系数据存储.md) 的分工：那边讲「**边**怎么落库」（有向 / 无向、分片键、推拉），这边讲「**层级**这种边怎么高效地上下走」。

---

## 二、四种模型，差在「把路径信息冗余在哪」

**本节要点**：四种模型的核心差异只有一条——**把「路径」这件事冗余在哪**。冗余越多，查子孙越快、写越贵。

| 模型 | 怎么存 | 查子孙 | 查祖先 | 移动子树 | 适合 |
|---|---|---|---|---|---|
| **邻接表** | 每行只记 `parent_id` | 递归（或递归 CTE），**深度受限** | 沿父链上溯，便宜 | 改一行，最便宜 | 写多、层级浅、读少 |
| **路径枚举** | 每行存从根到自己的路径串（`/1/12/123/`） | 前缀匹配，快 | 拆路径串，便宜 | 改**所有子孙**的路径串（写放大） | 读多写少、层级浅 |
| **嵌套集** | 每行存 `left` / `right` 左右值 | 范围查，很快 | 便宜 | **改半个表**（极贵） | 几乎只读（静态类目） |
| **闭包表** | 另存一张「(祖先, 后代, 距离)」表 | 一次索引查，**任意深度都快** | 同样快 | 增删 O(深度²) 行 | 读多、层级深、要按距离查 |

⭐ 判据：**「读多还是写多」是第一分水岭**——只读选嵌套集 / 路径枚举；读多写少选闭包表；写多且层级浅选邻接表。

![四种层级模型在查子孙 / 查祖先 / 移动子树上的相对代价，以及读多写少的分水岭](images/四种层级模型的读写代价.svg)

图怎么读：四个模块自上而下各是一个模型——邻接表（改一行最便宜，但递归深度受限、且本身不保证无环）、路径枚举（前缀扫描快，但移动子树要重写所有子孙）、嵌套集（范围查很快，但增删要挪半个表）、闭包表（一次索引查、任意深度都快，但行数 ≈ 节点数 × 平均深度）。底部判据块才是选型的落点：**先看读多还是写多，再看层级深不深**；有环 / 多父 / 边带属性时它就不是树，退回邻接表或图模型。

### 2.1 同一棵树，四种模型存的是同一份路径的不同切面

以 `1 → 12 → 123` 这条链为例，节点 123 在四种模型里的「那一行」分别是：

- **邻接表**：`123 | parent_id = 12`——路径一份都不存，靠递归一层层拼；
- **路径枚举**：`123 | path = /1/12/123/`——存一份完整路径，前缀扫就是查子孙；
- **嵌套集**：`123 | left = 3 · right = 4`，而 `1 = (1,6)`、`12 = (2,5)`、`123 = (3,4)`——用区间包含表达祖先关系；
- **闭包表**：为 123 存三行 `(1,123,2)`、`(12,123,1)`、`(123,123,0)`——每条祖先-后代关系各一行（距离 = 边数）。

所以「冗余越多、查子孙越快、写越贵」不是一句口号，而是同一件事的四种刻度：**邻接表 0 份、路径枚举 1 份整串、嵌套集 1 对区间、闭包表 N 份关系**。图里把它们并排摆在同一棵树下。

![同一棵树在四种模型里的行布局：邻接表 0 份路径、路径枚举 1 份整串、嵌套集 1 对左右值、闭包表 N 份祖先-后代关系](images/四种模型把路径冗余在哪.svg)

图怎么读：左上是同一棵 `1 → 12 → 123` 的树；右侧四块是节点 123 在四种模型里实际落下的那一行（闭包表是三行）。看每一块只要问两件事：**这一行里路径占几份、查子孙要不要递归**。底部判据把「冗余量」和「哪一头贵」对上——写最便宜的是 0 份的邻接表，查最深也最快的是 N 份的闭包表；嵌套集与路径枚举卡在两个极端之间。

## 三、邻接表：最自然，但深递归是坑

**本节要点**：邻接表是「照着数据本来的样子存」，代价全在**递归查询**上。

- **递归深度 = 树高**，而树高不可控——用户（或脏数据）能构造出很深的链；
- 关系库里递归 CTE 是**逐层查**：每层一次索引访问，深度 d 就是 d 次（这与 [关系数据存储.md](关系数据存储.md) 里「多跳迅速变慢」是同一条判据）；
- ⚠️ **环**：邻接表**本身不保证无环**（写错了就成环，递归直接死循环）→ 必须有「不能指向自己的祖先」这类约束兜底；
- 适合的场合：**层级浅、写多读少**（写只改一行，是所有模型里最便宜的）。

---

## 四、闭包表：拿空间买查询

**本节要点**：闭包表把「所有祖先 - 后代关系」**预先算好存成一张表**，于是任意深度的查询都变成一次索引查。

- **行数不是 O(n)**，而是 **O(n × 平均深度)**——层级越深、冗余越大；
- 换来的是：查子孙 / 查祖先**都是一次索引查**，不随深度退化（这正是邻接表的痛点）；
- 移动子树 = 删掉受影响的边 + 重建，代价 **O(深度²)** → 所以要**限制移动频率**；
- ⭐ 判据：**闭包表是「拿空间买查询」**，只有当「读远多于写」且「层级深」时才划算。

---

## 五、路径枚举与嵌套集：两个极端

**本节要点**：这两个模型都把「路径」冗余到极致，所以一个偏「读」、一个偏「只读」。

| 模型 | 为什么快 | 为什么慢 |
|---|---|---|
| **路径枚举** | 查子孙就是字符串前缀匹配，一次索引范围扫 | 移动子树要**重写所有子孙**的路径串（写放大随子树大小） |
| **嵌套集** | 查子孙是 `left` / `right` 范围查 | 增删一个节点要**挪动半个表的左右值**（几乎等于全表更新） |

⭐ 两者共同的适用面：**几乎只读**的场景（静态类目树、省市区划）。一旦增删频繁，嵌套集会迅速变糟。

## 六、什么时候它其实是一张图

**本节要点**：树模型的一切优化都建立在「**每个节点只有一个父、且无环**」这个前提上。前提不成立，就该换模型，而不是硬套。

| 现象 | 说明 | 该用什么 |
|---|---|---|
| **有环** | A 是 B 的上司、B 也是 A 的 | 树模型失效 → 图，或邻接表 + 环检测 |
| **多父** | 一个标签挂多个类目、一条边属于多个组 | 不是树 → 邻接表或 [图数据库](../../图数据库/图数据库选型对比.md) |
| **边上带属性** | 权限继承链有生效范围、路径有权重 | 边不再是纯结构 → 图模型，或邻接表 + 属性列 |

⭐ 判据：**先确认「单一父 + 无环」是否成立**——成立才谈四种树模型的取舍；不成立，直接按 [关系数据存储.md](关系数据存储.md) 的邻接表 / 图那套走。

---

## 七、缓存与分片

**本节要点**：层级是**高频读、低频写**的典型，所以缓存和分片都要围绕「以子树为单位」来做。

- **整棵树 / 子树缓存**：树小就整棵序列化成嵌套结构放进缓存，读取一次成型；
- **失效粒度是子树**：改动一个节点，要失效**它的祖先链**（以及它自己）上的缓存——不是只失效一个 key；
- **分片按子树切**：同一棵子树放同一个分片，查子孙就不跨片；代价是**移动子树要跨片搬数据**（与 [关系数据存储.md](关系数据存储.md) 的「按同一个维度存的两行会一起搬」同一思路）。

## 八、应用场景

**本节要点**：层级数据在真实系统里落在哪儿——按**谁在维护这棵树**分几层看：平台维护分类与组织，业务维护内容与目录，基础设施维护文件系统与权限，判据都是第一节那几条（单一父 + 无环、读写比、缓存粒度）。

| 场景 | 树的形态 | 用谁 |
|---|---|---|
| **组织架构 / 部门树** | 单一父、无环，以「某部门及其全部下级」为单位读写 | 邻接表；批量授权 / 逐层统计要按区间做时见 [树链剖分.md](../../../../02-计算机基础/算法/高级技巧/树链剖分.md) |
| **商品类目 / 标签体系** | 类目静态为主、读多写少；标签可能是多父 | 类目树用嵌套集 / 路径枚举；多父退化为图，见第六节与 [图数据库选型对比.md](../../图数据库/图数据库选型对比.md) |
| **评论楼中楼** | 深度有限但写多、要按楼层分页 | 邻接表（逐层查），深递归的坑见第三节 |
| **文件目录 / 菜单与权限树** | 树是「整体与部分」统一的典型，常与组合模式同构 | 见 [组合模式.md](../../../../05-设计模式/结构型/组合模式.md)、[树的形态与选型.md](../../../../02-计算机基础/数据结构/树/树的形态与选型.md) |
| **省市区划 / 静态类目** | 几乎只读，多年不变 | 嵌套集 / 路径枚举；冷热处置见 [冷热数据分层.md](../横切篇/冷热数据分层.md) |
| **什么时候它其实是图** | 有环 / 多父 / 边带属性 | 判据见第六节与 [树与图的边界.md](../../../../02-计算机基础/数据结构/树/树与图的边界.md) |

⭐ **三条把上表读薄的工程判据**：

1. **先确认「单一父 + 无环」**：成立才谈四种树模型的取舍；一旦有环或多父，别硬套树模型，退回邻接表或图（第六节）。
2. **读写比决定模型**：写多层级浅走邻接表，读多层级深走闭包表，几乎只读才上嵌套集 / 路径枚举——嵌套集与闭包表是两个方向的极端（第二、四、五节）。
3. **缓存与分片的粒度是「子树」**：改一个节点要失效它的祖先链，分片按子树切；按单个节点做失效会漏（第七节）。

## 九、具体使用

**本节要点**：先量「读多还是写多」，再量「层级深不深」，四选一就定了。下面按「先选模型（9.1）→ 再落三种最小可抄的查询写法（9.2~9.4）」组织。

### 9.1 按读写比选模型

| 你的情况 | 模型 | 第一判据 |
|---|---|---|
| 写多、层级浅 | 邻接表 | 递归深度可控吗 |
| 读多写少、层级浅 | 路径枚举 | 移动子树频繁吗 |
| 几乎只读（静态类目） | 嵌套集 | 会不会增删节点 |
| 读多、层级深、还要按距离查 | 闭包表 | 写（尤其移动）能接受 O(深度²) 吗 |
| 有环 / 多父 / 边带属性 | 邻接表或图 | 「单一父 + 无环」还成立吗 |

⭐ 三条横向判据：**① 先确认「单一父 + 无环」，不成立就不是树问题**；**② 读写比决定模型，嵌套集与闭包表是两个方向的极端**；**③ 缓存的失效粒度是子树，不是单个节点**。

### 9.2 邻接表：递归 CTE 查子孙

> ⚠️ 落地写法骨架，未单独编译、未执行；写法属于通用递归 CTE，判据来自本篇第三节。

```sql
-- 邻接表：递归 CTE 查某节点的全部子孙（通用写法，MySQL 8.0+ / PostgreSQL 都支持）
WITH RECURSIVE subtree AS (
  SELECT id, parent_id, name FROM category WHERE id = :root
  UNION ALL
  SELECT c.id, c.parent_id, c.name
  FROM category c JOIN subtree s ON c.parent_id = s.id   -- 每层一次索引访问
)
SELECT * FROM subtree;
```

⭐ 写侧要配一条约束：**`parent_id` 不能指向自己或自己的祖先**——邻接表本身不保证无环，写错了递归会死循环（第三节）。

### 9.3 闭包表：建表与查子孙 / 查祖先

> ⚠️ 落地写法骨架，未单独编译、未执行；行数与代价口径来自本篇第四节。

```sql
-- 闭包表：另存 (祖先, 后代, 距离)，任意深度都是一次索引查
CREATE TABLE category_path (
  ancestor   BIGINT UNSIGNED NOT NULL,
  descendant BIGINT UNSIGNED NOT NULL,
  depth      INT NOT NULL,                 -- 0 表示自己到自己
  PRIMARY KEY (ancestor, descendant),
  KEY idx_desc (descendant)                -- 反向索引：查祖先走它
) ENGINE=InnoDB;

-- 查某节点的全部子孙（含按距离排序）
SELECT c.* FROM category_path p JOIN category c ON c.id = p.descendant
WHERE p.ancestor = :root ORDER BY p.depth;

-- 查某节点的全部祖先
SELECT c.* FROM category_path p JOIN category c ON c.id = p.ancestor
WHERE p.descendant = :node ORDER BY p.depth DESC;
```

⭐ 行数 ≈ 节点数 × 平均深度，移动子树要按受影响范围增删行（代价 O(深度²)）——所以它只在「读远多于写 + 层级深」时才划算（第四节）。

### 9.4 路径枚举：前缀匹配查子孙

> ⚠️ 落地写法骨架，未单独编译、未执行；写法与写放大口径来自本篇第五节。

```sql
-- 路径枚举：每行存「从根到自己的路径串」，查子孙退化成一次前缀范围扫
CREATE TABLE category (
  id   BIGINT UNSIGNED NOT NULL PRIMARY KEY,
  path VARCHAR(255) NOT NULL,             -- 形如 /1/12/123/
  KEY idx_path (path)
) ENGINE=InnoDB;

SELECT * FROM category WHERE path LIKE '/1/12/%';   -- 前缀匹配，一次索引范围扫
```

⭐ 代价在写侧：**移动子树要重写所有子孙的路径串**（写放大随子树大小）；嵌套集更极端，增删要挪半个表的左右值——两者都只适合几乎只读的场景（第五节）。

## 延伸追问

- **为什么不用「深度」字段直接查子孙？** → 深度只告诉你「在哪一层」，不告诉你「属于哪一支」；查某节点的子孙要靠路径，不是靠层号。
- **闭包表的行数会不会爆？** → 会，行数 ≈ 节点数 × 平均深度。所以它只适合「读远多于写」；增删频繁的场景，维护成本会盖过查询收益。
- **邻接表能不能靠「冗余一列路径」混合？** → 可以。很多实现是「邻接表 + 冗余路径串」：写时更新路径、读时用路径前缀——本质是把路径枚举嫁接到邻接表上。
- **层级数据该不该整棵塞进内存？** → 树小、读极热时可以；树的规模一大，就要按子树分片 + 逐层加载，而不是整棵常驻。
- **它和「图数据」的边界在哪？** → 判据是「**每条边是否只有唯一的一条到达路径**」。有唯一路径 → 树，能用树模型的廉价方案；没有 → 图。
