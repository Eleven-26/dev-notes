## 一、它们都是「为某类查询重建的物理组织」

**本节要点**：检索副本与分析副本，本质都是**把同一份数据按另一种查询方式重排一遍**——它们不是「更好的数据库」，而是「为某一类查询定制的物化视图」。

| | 检索副本（倒排） | 分析副本（列式） |
|---|---|---|
| 优化什么查询 | 「按词 / 条件找文档」 | 「按列扫全量做聚合」 |
| 物理组织 | 词 → 文档列表（倒排表） | 同一列的数据连续存放 |
| 关键取舍 | 分词 / 相关度 / 近似匹配 | 压缩比 / 扫描吞吐 / 预聚合 |
| 在存储组合里的角色 | [存储选型与组合.md](../存储选型与组合.md) 的「检索副本」 | 同上的「分析副本」 |

⭐ 关系库做这两件事的代价：`LIKE '%x%'` 用不上索引（要全扫）；`COUNT` / `SUM` 全表聚合会拖垮在线事务。这不是「关系库弱」，而是**同一份物理组织服务不了两种相反的访问形状**。

---

## 二、倒排索引：为什么「找」这么快

**本节要点**：倒排把「文档 → 词」翻过来，建成「**词 → 文档 ID 列表**」，于是「找一个词」变成「取一个列表」。

- 查询 = 若干词列表**求交 / 并**（短语、布尔条件都是列表运算）；
- **代价一：写入放大**——一个文档的每个词都要去更新对应列表。所以实现上用**不可变的段 + 后台合并**（与 LSM 树同一思路，见 [LSM树.md](../../../../02-计算机基础/数据结构/树/LSM树.md)）；
- **代价二：索引常比原文还大**——除了词和文档，还要存位置信息（为了短语查询）；
- ⚠️ **分词一旦定下就难改**：改分词器 = 语义变了 = 要整体重索引。

---

## 三、列式存储：为什么「算」这么快

**本节要点**：列式把「同一列的数据放在一起」，于是「算一列」变成「顺序读一段」。

- 同一列**数据类型相同** → **压缩比高**（字典编码、行程编码），IO 量成倍降；
- 扫描只读**涉及的那几列** → 行存要整行读，列存少读一大截；
- ⚠️ 代价：**随机点查慢**（一行要拼回很多列）、**更新难**（偏好批量追加）→ 所以它天然是「只追加的分析副本」；
- 行存与列存的取舍见 [列式数据库选型对比.md](../../列式数据库/列式数据库选型对比.md)。

## 四、为什么它们「必然不一致」

**本节要点**：两者都从权威源**派生**，所以「延迟」是设计的一部分，不是 bug。

- 副本由权威源同步而来，同步有延迟（三条路线的取舍见 [数据同步方式选型对比.md](../../数据同步/数据同步方式选型对比.md)）；
- ⚠️ 本质：**「为查询重建的副本」与「权威源」永远是两个时刻的快照**——所以「刚写完的搜不到 / 统计不到」是正常现象；
- ⭐ 判据：**要求「写后立即可搜」** → 只能同步写副本（贵、脆、双写易错），否则产品上必须接受延迟（很多场景用「乐观 UI + 稍后刷新」把它掩盖掉）。

## 五、聚合的三种口径：精确、近似、预计算

**本节要点**：聚合不是「一种做法」，先问容忍度再选口径。

| 口径 | 做法 | 代价 |
|---|---|---|
| **精确** | 列存全量扫（列存的强项） | 高基数分组会吃满内存，甚至打爆查询 |
| **近似** | 基数用基数估计算法、分位用可合并的近似结构 | 有误差，但可控、可标注 |
| **预计算** | 提前按常用维度聚合好（物化视图 / 宽表 / 预聚合表） | 维度组合爆炸；上游一改要重算 |

⭐ 判据：**先问「要看哪几个维度、能不能容忍误差」**——能容忍就上近似 / 预计算，不能容忍就只查明细的窄窗口。

## 六、合流：关键词 + 向量

**本节要点**：生产上常见「两路召回 + 融合排序」，因为两种检索各有所短。

- **关键词召回**：精确词、编号、短查询强；语义相近弱；
- **向量召回**：语义相近强；精确词弱（见 [向量数据存储.md](向量数据存储.md)）；
- ⚠️ 复杂点不在两路本身，而在**融合与去重**——和 [时序数据存储.md](时序数据存储.md) 的「多路归并去重」是同一类手法；
- 落地形态见 [Elasticsearch/向量与AI搜索.md](../../搜索与分析/Elasticsearch/向量与AI搜索.md)。

![倒排与列式的两种物理组织：词到文档列表的倒排为「找」付写代价，同列连续存放的列存为「算」付更新代价，外加派生副本的必然不一致与聚合三种口径](images/倒排与列式两种物理组织.svg)

图怎么读：A 面板是第二节的倒排——词翻成文档 ID 列表、查询变成交并运算，为「找」付的是写入放大（不可变段 + 后台合并，LSM 同一思路）和「索引常比原文大」，红字标注分词一改就要整体重索引；B 面板是第三节的列式——同列连续存放带来高压缩比与扫描吞吐，代价反过来落在随机点查和更新上，所以它天然是只追加的分析副本；C 面板对应第四节：副本由权威源派生，「刚写完的搜不到」是设计使然而非 bug；D 面板摆出第五节聚合的精确 / 近似 / 预计算三种口径。底部三条判据即上文。

### 2.1 一条写入怎么变成「可搜」：内存缓冲 → 不可变段 → 后台合并

倒排的「写」不是改旧的列表，而是一路追加：

- **先追加 translog，再改内存缓冲**：崩溃后靠 translog 重放，不靠内存；
- **refresh 生成一个不可变段**：这一刻起新内容才能被搜到——所以「刚写完搜不到」不是 bug（第四节）；
- **查询要合并多个段的结果**：段越多，查询要碰的列表越多；
- **后台合并把小段并成大段**：合并时顺带把删除标记真正清掉，段变少、查询变快。

⭐ 判据：**这套「追加 + 合并」用写放大换随机更新**——一个文档的每个词都要去更新对应列表，所以更新越频繁，后台合并的压力越大（与 [LSM树.md](../../../../02-计算机基础/数据结构/树/LSM树.md) 同一思路）。

![倒排副本的写入流转：translog 追加、内存缓冲、refresh 生成不可变段、多段查询、后台合并成大段](images/一条写入从内存到可搜的流转.svg)

图怎么读：上排是写入到可搜的先后——请求先进内存缓冲，refresh 之后才生成可搜的不可变段；下排是段的生命周期——refresh 吐出多个小段，后台合并再把它们并成大段，删除标记在合并时才真正生效。左侧标的是代价：写入放大、索引常比原文还大、分词器一改就要整体重索引。

## 七、应用场景

**本节要点**：这两种「为某类查询重建的物理组织」在真实系统里落在哪儿——按**谁在问它**分几层看：用户在搜、运营在看数、系统在做统计，判据都是第一节那条分界（它优化的是「找」还是「算」）。

| 场景 | 副本 | 用谁 |
|---|---|---|
| **站内搜索 / 商品筛选** | 检索副本（倒排） | 分词 + 相关度 + 条件筛选，见 [Elasticsearch/搜索流程与DSL.md](../../搜索与分析/Elasticsearch/搜索流程与DSL.md)、[搜索与分析选型对比.md](../../搜索与分析/搜索与分析选型对比.md) |
| **日志 / 指标检索** | 检索副本（倒排 + 按时间滤） | 「按词找 + 按时间筛」，与 [时序数据存储.md](时序数据存储.md) 的按时间读合流 |
| **报表 / 统计页 / 大盘** | 分析副本（列式） | 预先聚合的结果表，见 [统计页提速.md](../../../../04-架构与系统/系统设计/统计页提速.md)、[ClickHouse/定位与适用场景.md](../../列式数据库/ClickHouse/定位与适用场景.md) |
| **用户行为分析 / 漏斗** | 分析副本（列式，明细 + 聚合） | 高基数分组走近似 / 预计算，见第五节 |
| **自建多条件筛选** | 值 → 集合的倒排 | 「值倒排 + 求交」不只用于文本，见 [倒排索引.md](../../../../02-计算机基础/数据结构/高级数据结构/倒排索引.md) |
| **语义检索** | 向量 + 关键词合流 | 两路召回 + 融合排序，见第六节与 [向量数据存储.md](向量数据存储.md) |

⭐ **三条把上表读薄的工程判据**：

1. **它们都是派生副本，不是权威源**：「刚写完的搜不到 / 统计不到」是设计的一部分，产品要么接受延迟、要么用「乐观 UI + 稍后刷新」把它掩盖掉（第四节）。
2. **别指望一个副本两头讨好**：倒排擅长「找」、列式擅长「算」，合成一个两头不讨好——要么两个副本，要么明确放弃其中一类查询（第一节与延伸追问）。
3. **聚合先问「能不能容忍误差」**：能容忍就上近似 / 预计算，不能容忍才只查明细的窄窗口——先定口径，再选实现（第五节）。

## 八、具体使用

**本节要点**：先看查询长什么样，再选副本；这张表是起点，具体按数据规模与延迟要求裁剪。下面按「先选副本（8.1）→ 再落倒排、列式与同步骨架（8.2~8.4）」组织。

### 8.1 按查询形态选副本

| 你要的查询 | 副本 | 第一判据 |
|---|---|---|
| 按词 / 相关度找文档 | 检索副本（倒排） | 要不要分词与相关度排序 |
| 条件筛选 + 排序 | 检索副本 | 条件组合会不会爆炸（filter 能不能缓存） |
| 按列扫全量做聚合 | 分析副本（列式） | 是不是扫描型、能不能接受只追加 |
| 高基数分组的统计 | 分析副本 + 近似 / 预计算 | 能不能容忍误差 |
| 语义相近的检索 | 向量 + 关键词合流 | 精确词与语义各占多少 |

⭐ 三条横向判据：**① 它们都是「为某类查询重建的物化视图」**；**② 派生副本必然有延迟，产品要接受**；**③ 聚合先问「能不能容忍误差」，再决定精确 / 近似 / 预计算**。

### 8.2 倒排：查询骨架

> ⚠️ 落地写法骨架，未单独编译、未执行；以倒排的通用查询语义示意，判据来自本篇第二节。

```text
检索请求（语义骨架，非某产品的最终语法）：
  must   : 按词找      → 走倒排，词列表求交
  filter : 条件筛选    → 不打分、可缓存，与打分过程分离
  sort   : 相关度 + 唯一键 → 打平时用唯一键兜底，翻页才稳定
  注意：分词器一旦定下就难改，改 = 语义变了 = 要整体重索引
```

### 8.3 列式：聚合骨架

> ⚠️ 落地写法骨架，未单独编译、未执行；口径来自本篇第五节的「精确 / 近似 / 预计算」。

```sql
-- 分析副本：先问维度与容忍度，再选精确 / 近似 / 预计算
SELECT category, count() AS pv, uniqCombined(user_id) AS uv   -- 近似基数：省内存、有误差
FROM events
WHERE day >= :from AND day < :to
GROUP BY category
ORDER BY pv DESC
LIMIT 100;

-- 维度组合固定、容忍最终一致时，改为查「提前聚合好的结果表」
SELECT category, pv, uv FROM stat_daily WHERE day = :day ORDER BY pv DESC LIMIT 100;
```

⭐ 高基数分组会吃满内存（精确口径），所以能容忍误差就别硬算精确值（第五节）。

### 8.4 派生副本的同步

> ⚠️ 落地写法骨架，未单独编译；顺序与一致性口径来自本篇第四节与 [数据同步方式选型对比.md](../../数据同步/数据同步方式选型对比.md)。

```text
写路径：权威源提交 → 变更日志（CDC / outbox）→ 按主键顺序应用到副本
顺序  ：同一行的变更必须按权威源顺序应用，否则副本会算出错误状态
一致性：要求「写后立即可搜」只能同步写副本（贵、脆、双写易错），否则接受延迟
重建  ：副本是可重建的派生数据——留好「从权威源全量 + 增量重放」的路径
```

## 延伸追问

- **为什么不能只留一个副本，检索和分析合一？** → 两者的索引结构相反：倒排擅长「找」、列式擅长「算」，合成一个两头不讨好（这是 [存储选型与组合.md](../存储选型与组合.md) 延伸追问里的同一问）。
- **倒排索引为什么用「段 + 合并」而不是原地更新？** → 原地更新要改大量列表、并发与崩溃一致性都难；不可变段让写入变成「追加 + 后台合并」，与 LSM 树是同一套思路。
- **列存的更新为什么难？** → 列是按列连续存的，改一行要碰很多列文件；所以列存更愿意「把更新也当追加」，靠后台合并消解。
- **聚合为什么会吃满内存？** → 分组数（基数）一高，每个分组都要在内存里维护中间状态；基数估计算法就是为了「不精确地」把内存压住。
- **多副本之间要不要保持顺序？** → 要。同一份数据的变更要按权威源顺序应用，否则副本会算出错误状态（CDC 天然带顺序，双写要额外处理）。
