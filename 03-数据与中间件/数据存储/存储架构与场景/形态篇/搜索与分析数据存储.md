# 搜索与分析数据存储

> 「按词找」和「按列算」这两类查询，关系库为什么做不好：倒排索引与列式存储的物理组织、

## 一、它们都是「为某类查询重建的物理组织」

**本节要点**：检索副本与分析副本，本质都是**把同一份数据按另一种查询方式重排一遍**——它们不是「更好的数据库」，而是「为某一类查询定制的物化视图」。

| | 检索副本（倒排） | 分析副本（列式） |
|---|---|---|
| 优化什么查询 | 「按词 / 条件找文档」 | 「按列扫全量做聚合」 |
| 物理组织 | 词 → 文档列表（倒排表） | 同一列的数据连续存放 |
| 关键取舍 | 分词 / 相关度 / 近似匹配 | 压缩比 / 扫描吞吐 / 预聚合 |
| 在存储组合里的角色 | [存储选型与组合.md](../存储选型与组合.md) 的「检索副本」 | 同上的「分析副本」 |

⭐ 关系库做这两件事的代价：`LIKE '%x%'` 用不上索引（要全扫）；`COUNT` / `SUM` 全表聚合会拖垮在线事务。这不是「关系库弱」，而是**同一份物理组织服务不了两种相反的访问形状**。

---

## 二、倒排索引：为什么「找」这么快

**本节要点**：倒排把「文档 → 词」翻过来，建成「**词 → 文档 ID 列表**」，于是「找一个词」变成「取一个列表」。

- 查询 = 若干词列表**求交 / 并**（短语、布尔条件都是列表运算）；
- **代价一：写入放大**——一个文档的每个词都要去更新对应列表。所以实现上用**不可变的段 + 后台合并**（与 LSM 树同一思路，见 [LSM树.md](../../../../02-计算机基础/数据结构/树/LSM树.md)）；
- **代价二：索引常比原文还大**——除了词和文档，还要存位置信息（为了短语查询）；
- ⚠️ **分词一旦定下就难改**：改分词器 = 语义变了 = 要整体重索引。

---

## 三、列式存储：为什么「算」这么快

**本节要点**：列式把「同一列的数据放在一起」，于是「算一列」变成「顺序读一段」。

- 同一列**数据类型相同** → **压缩比高**（字典编码、行程编码），IO 量成倍降；
- 扫描只读**涉及的那几列** → 行存要整行读，列存少读一大截；
- ⚠️ 代价：**随机点查慢**（一行要拼回很多列）、**更新难**（偏好批量追加）→ 所以它天然是「只追加的分析副本」；
- 行存与列存的取舍见 [列式数据库选型对比.md](../../列式数据库/列式数据库选型对比.md)。

## 四、为什么它们「必然不一致」

**本节要点**：两者都从权威源**派生**，所以「延迟」是设计的一部分，不是 bug。

- 副本由权威源同步而来，同步有延迟（三条路线的取舍见 [数据同步方式选型对比.md](../../数据同步/数据同步方式选型对比.md)）；
- ⚠️ 本质：**「为查询重建的副本」与「权威源」永远是两个时刻的快照**——所以「刚写完的搜不到 / 统计不到」是正常现象；
- ⭐ 判据：**要求「写后立即可搜」** → 只能同步写副本（贵、脆、双写易错），否则产品上必须接受延迟（很多场景用「乐观 UI + 稍后刷新」把它掩盖掉）。

## 五、聚合的三种口径：精确、近似、预计算

**本节要点**：聚合不是「一种做法」，先问容忍度再选口径。

| 口径 | 做法 | 代价 |
|---|---|---|
| **精确** | 列存全量扫（列存的强项） | 高基数分组会吃满内存，甚至打爆查询 |
| **近似** | 基数用基数估计算法、分位用可合并的近似结构 | 有误差，但可控、可标注 |
| **预计算** | 提前按常用维度聚合好（物化视图 / 宽表 / 预聚合表） | 维度组合爆炸；上游一改要重算 |

⭐ 判据：**先问「要看哪几个维度、能不能容忍误差」**——能容忍就上近似 / 预计算，不能容忍就只查明细的窄窗口。

---

## 六、合流：关键词 + 向量

**本节要点**：生产上常见「两路召回 + 融合排序」，因为两种检索各有所短。

- **关键词召回**：精确词、编号、短查询强；语义相近弱；
- **向量召回**：语义相近强；精确词弱（见 [向量数据存储.md](向量数据存储.md)）；
- ⚠️ 复杂点不在两路本身，而在**融合与去重**——和 [时序数据存储.md](时序数据存储.md) 的「多路归并去重」是同一类手法；
- 落地形态见 [Elasticsearch/向量与AI搜索.md](../../搜索与分析/Elasticsearch/向量与AI搜索.md)。

## 使用：按查询形态选副本

**本节要点**：先看查询长什么样，再选副本；这张表是起点，具体按数据规模与延迟要求裁剪。

| 你要的查询 | 副本 | 第一判据 |
|---|---|---|
| 按词 / 相关度找文档 | 检索副本（倒排） | 要不要分词与相关度排序 |
| 条件筛选 + 排序 | 检索副本 | 条件组合会不会爆炸（filter 能不能缓存） |
| 按列扫全量做聚合 | 分析副本（列式） | 是不是扫描型、能不能接受只追加 |
| 高基数分组的统计 | 分析副本 + 近似 / 预计算 | 能不能容忍误差 |
| 语义相近的检索 | 向量 + 关键词合流 | 精确词与语义各占多少 |

⭐ 三条横向判据：**① 它们都是「为某类查询重建的物化视图」**；**② 派生副本必然有延迟，产品要接受**；**③ 聚合先问「能不能容忍误差」，再决定精确 / 近似 / 预计算**。

![倒排与列式的两种物理组织：词到文档列表的倒排为「找」付写代价，同列连续存放的列存为「算」付更新代价，外加派生副本的必然不一致与聚合三种口径](images/倒排与列式两种物理组织.svg)

图怎么读：A 面板是第二节的倒排——词翻成文档 ID 列表、查询变成交并运算，为「找」付的是写入放大（不可变段 + 后台合并，LSM 同一思路）和「索引常比原文大」，红字标注分词一改就要整体重索引；B 面板是第三节的列式——同列连续存放带来高压缩比与扫描吞吐，代价反过来落在随机点查和更新上，所以它天然是只追加的分析副本；C 面板对应第四节：副本由权威源派生，「刚写完的搜不到」是设计使然而非 bug；D 面板摆出第五节聚合的精确 / 近似 / 预计算三种口径。底部三条判据即上文。

## 延伸追问

- **为什么不能只留一个副本，检索和分析合一？** → 两者的索引结构相反：倒排擅长「找」、列式擅长「算」，合成一个两头不讨好（这是 [存储选型与组合.md](../存储选型与组合.md) 延伸追问里的同一问）。
- **倒排索引为什么用「段 + 合并」而不是原地更新？** → 原地更新要改大量列表、并发与崩溃一致性都难；不可变段让写入变成「追加 + 后台合并」，与 LSM 树是同一套思路。
- **列存的更新为什么难？** → 列是按列连续存的，改一行要碰很多列文件；所以列存更愿意「把更新也当追加」，靠后台合并消解。
- **聚合为什么会吃满内存？** → 分组数（基数）一高，每个分组都要在内存里维护中间状态；基数估计算法就是为了「不精确地」把内存压住。
- **多副本之间要不要保持顺序？** → 要。同一份数据的变更要按权威源顺序应用，否则副本会算出错误状态（CDC 天然带顺序，双写要额外处理）。
