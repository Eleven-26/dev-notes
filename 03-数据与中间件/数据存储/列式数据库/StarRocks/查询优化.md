## 一、查询慢，先看哪里

**本节要点**：慢查询分两类——**扫多了**（扫描量大于必要）与**算慢了**（扫描量合理但执行慢）。这两类的解法完全不重叠，先分类再动手。

### 1.1 两类问题，两条路

| 症状 | 该看什么 | 常见原因 |
|---|---|---|
| **扫多了** | Profile 里 scan 节点的**扫描行数 / 字节数** vs 结果行数 | 过滤条件没吃到前缀索引、分区键没写进 `WHERE`、分桶键没吃到裁剪、统计信息过期导致选错 join 顺序 |
| **算慢了** | Profile 里各节点的**耗时占比**、是否落盘（spill） | join 顺序差、聚合基数估错、内存不足触发落盘、数据倾斜导致个别实例拖尾 |

⭐ 判断顺序：**先看扫描量，再看耗时分布**。扫描量正常但慢，才去查执行；扫描量本身就不对，
调什么参数都是白费——这是最容易搞反的地方。

### 1.2 Profile 里先抓四个东西

| 抓什么 | 在哪 | 说明什么 |
|---|---|---|
| **扫描行数 / 扫描字节** | scan 节点 | 裁剪有没有生效。这是最该先看的数字 |
| **`ShortKeyFilterRows`** | scan 节点 | ⭐ 前缀索引过滤掉的行数。为 0 说明前缀索引没吃上 |
| **各节点耗时** | 整棵树 | 找那个占比最高的节点，而不是平均值 |
| **峰值内存 / 是否 spill** | 节点级指标 | 有 spill 说明内存不够，先调内存或改 SQL 形态，别调并行度 |

`ShortKeyFilterRows` 这个指标值得单独记：**它把「前缀索引到底生效没有」从推测变成了可读的数字**。
很多人调了半天排序键，其实查询条件根本没落在前缀上。

## 二、前缀索引：三个数字决定一切

**本节要点**：前缀索引是**排序键上的一层稀疏索引**，规则只有三条——**每 1024 行一条、每项最多 36 字节、前缀字段最多 3 个**。记住这三条就不需要背别的东西。

### 2.1 它是怎么建起来的

写入时数据先按排序键（sort key）排序，然后**每 1024 行构成一个逻辑数据块（Data Block）**，
在这一块的第一行上取排序列的前缀，作为前缀索引的一条索引项。

```
排序键 (uid, name)，写入 100 万行
├─ Data Block 0：行 0~1023      → 索引项 = (uid_0, name_0 的前缀)
├─ Data Block 1：行 1024~2047   → 索引项 = (uid_1024, name_1024 的前缀)
└─ ...
索引项数量 ≈ 100万 / 1024 ≈ 977 条
```

⭐ 因为它比数据小**至少 1024 倍**，所以可以全量常驻内存。查询时二分查找索引项，跳到对应的 Data Block 再细扫——
这就是「稀疏索引」的全部原理，和 ClickHouse 的 granule 索引是同一个思路（那边是 8192 行一个 granule）。

### 2.2 三个硬限制

| 限制 | 数值 | 后果 |
|---|---|---|
| **索引项长度** | **36 字节**，超出即截断 | 长字符串列只能贡献前几十字节 |
| **前缀字段数** | **不超过 3 个** | 排序列排到第 4 个就不进索引了 |
| **字符串列的位置** | `CHAR` / `VARCHAR` / `STRING` **只能出现一次，且必须在末尾** | 字符串列在前 → 前缀**到此为止**，后面的列全不进索引 |

第三条最容易踩。文档给的例子：排序列是 `name(varchar 20), uid, last_access`，
虽然总长只有 20 多字节、远没到 36，但因为**第一个排序列就是字符串**，前缀索引就只有 `name` 一个字段，
后面的 `uid` / `last_access` 完全不参与索引。

```sql
-- 好：整型在前，字符串在末尾
ORDER BY (uid, name)          -- 前缀 = uid(4B) + name(前 32B)

-- 差：字符串在前，后面的列白排
ORDER BY (name, uid, dt)      -- 前缀 = name（到字符串就截断）
```

### 2.3 排序键怎么设计

文档给的两条优先级可以直接照用：

1. **先按「谁最常出现在 `WHERE` 里」排，最常过滤的放最前面**。
   查询条件包含**完整前缀**时效果最好；只包含前缀的一部分也能用，但前缀越短效果越弱。
2. **过滤频率差不多时看基数，再看压缩**：基数高的列过滤效果好；如果高低基数谁前谁后对性能影响不大，
   **把低基数放前面**——排序后低基数列的压缩率会明显更高。

⚠️ 排序列不是越多越好，文档建议**一般 3 个、不超过 4 个**：多了会增加导入时的排序开销，收益却很小。

### 2.4 排序键可以事后改

这条推翻了「建表定终身」的印象：

- **v3.0 起**：主键表支持用 `ORDER BY` 定义排序键，且可以 `ALTER TABLE ... ORDER BY` 修改；
- **v3.3 起**：明细表、聚合表、更新表也支持。

聚合表与更新表的 `ORDER BY` 必须**包含全部 key 列**（顺序可不同），明细表与主键表则可以是任意列组合。
⚠️ 例外：用 v4.1 的**范围分桶**建的表不能改排序键（tablet 边界由排序键决定，改了边界就失效）。

## 三、内置索引不止前缀一层

**本节要点**：前缀索引解决「跳到哪一块」，**Ordinal 索引**解决「块里的某一列在哪」，**ZoneMap** 解决「这块要不要读」。三层配合才是一次完整裁剪。

| 索引 | 粒度 | 存什么 | 解决什么 |
|---|---|---|---|
| **前缀索引** | 每 1024 行 | 该块首行的排序键前缀 | 二分定位到 Data Block |
| **Ordinal 索引** | 每个列 Data Page | Data Page 的起始行号、物理地址 | ⭐ **按行号找列页**——所有其它索引最终都要经它落地 |
| **ZoneMap** | 每块数据 | 该块的 `MIN` / `MAX` / `HasNull` / `HasNotNull` | 用统计信息判断「这一块能不能整块跳过」 |

三者是**链式**的：前缀索引给出「大致在第几块」，ZoneMap 判断「这块的取值区间对不对得上」，
Ordinal 索引最后把「第几行」翻译成「哪一列页的哪个物理偏移」。

⭐ ZoneMap 的价值在没有索引的列上：**它对所有列自动生效**，不需要建。所以即使一列不在排序键上，
只要数据按相关列聚簇（例如按时间分区），ZoneMap 依然能跳掉大量数据块。

关于 Data Page 的粒度：文档给的 `data_page_size` 默认是 **64 × 1024 字节（64 KB）**，
每个列 Data Page 对应一条 Ordinal 索引项。

## 四、四种手动索引，各管一段

**本节要点**：手动索引是**给不在排序键上的列补课**。四种各有明确的适用面，选错不但不加速，还会增加写入与存储成本。

| 索引 | 适合的列 | 典型查询 | 代价与限制 |
|---|---|---|---|
| **Bitmap** | 中高基数、**过滤性极强**（官方口径：至少能滤掉 999/1000 的行）；多个低基数列组合 | 等值、`IN`、组合条件 | 对低选择性列收益低；占存储 |
| **Bloom filter** | **高基数**列（如 ID） | 等值 | 有误判率（假阳性），不会漏 |
| **N-Gram Bloom filter** | 文本列 | `LIKE`、`ngram_search` | 专为子串匹配设计 |
| **全文倒排索引** | 文本列 | 关键词检索、`MATCH` | 存算一体 v3.3+ / 存算分离 v4.1+ |
| **向量索引** | 向量列 | 近似最近邻（ANNS） | 存算一体 v3.4+；**存算分离待支持** |

⭐ 选择顺序可以简化成一句：**等值且高基数 → Bloom；等值且强过滤或组合条件 → Bitmap；**
**文本子串 → N-Gram；全文检索 → 倒排；向量召回 → 向量索引。**

⚠️ 一个反直觉的边界：Bitmap 索引官方说的是「**至少能过滤掉 999/1000 的数据**」时才值得建。
也就是说它是为**极强选择性**设计的，给一个「过滤掉一半」的列建 Bitmap，收益抵不过它的写入与存储成本。

## 五、Runtime Filter：MPP join 的关键一手

**本节要点**：join 的痛点永远是「探测端（大表）白扫了」。Runtime Filter 的思路是——**先用构建端（小表）算出一个过滤条件，再把它下推给探测端，让大表一开始就少扫**。

### 5.1 它解决什么问题

```
SELECT ... FROM 大表 A JOIN 小表 B ON A.k = B.k WHERE B.city = '杭州'
```

传统做法：两边各扫一遍，再在内存里做 hash join。大表 A 扫完全部数据，最后发现只有 B 里那几千个 key 有用。

Runtime Filter：先扫 B（构建端），把 `B.k` 的取值集合做成过滤器，**下推给 A 的 scan 节点**——
A 只把 hash 命中的行读出来。大表少扫多少，取决于 B 的选择性。

### 5.2 三种过滤器形态（按构建端产出的信息量）

| 形态 | 构建端给什么 | 适用 |
|---|---|---|
| **MinMax** | 最小 / 最大值的区间 | 构建端数据有序或值域集中时最省 |
| **Bloom filter** | 一个布隆过滤器 | 通用，有一定误判 |
| **IN** | 明确的取值列表 | 构建端基数很小（如 TopN 结果）时最精确 |

三种是**按信息量递进**的：MinMax 最便宜但最粗，IN 最精确但只在小基数时可用。优化器会按构建端的统计信息选。

### 5.3 为什么它有个「等待时间」

Runtime Filter 有个天然的代价：**探测端必须先等构建端算完**。
构建端慢，探测端就要空等——这时候全表先扫反而更快。所以它配了等待上限，
超时就不再等、直接扫，并在 Profile 里能看出来过滤是否真的生效了。

⭐ 这就是 MPP 里一个反复出现的权衡：**过滤器越精确 → 越依赖构建端先完成 → 空等风险越大**。
调优时不要只看「过滤器生效了吗」，也要看「为了等它，浪费了多少时间」。

## 六、CBO 与统计信息：join 顺序从哪来

**本节要点**：多表 join 的执行顺序由 **CBO（基于代价的优化器）** 决定，而 CBO 的输入是**统计信息**。统计信息过期，优化器就会选错顺序——表现是「SQL 没改、数据涨了、突然变慢」。

| 要素 | 说明 |
|---|---|
| **统计信息** | 表的行数、列的 NDV（不重复值数）、直方图等；由 `ANALYZE TABLE` 采集（可自动触发） |
| **代价模型** | 按扫描量、网络传输量、join 方式估算每种计划的代价，选最低的 |
| **join 顺序** | 小表在前还是大表在前、哪些表先 join，都由代价估算定 |
| **join 方式** | Broadcast / Shuffle / Colocate，取决于表的大小与分桶方式 |

⭐ 两个实操判断：

- **数据量突变后 SQL 变慢，第一反应应该是「重新收集统计信息」**，而不是改 SQL。优化器拿着旧的行数估算，
  会把「其实很大」的表当成小表去 broadcast，直接把内存打爆。
- **Colocate Join** 的收益来自「同分桶键的表，同 key 的数据本来就在同一个 BE 上」→ 省掉一次 shuffle。
  它要求参与 join 的表**分桶键一致、分桶数一致**，且在同一 Colocate Group 里。
  ⚠️ 随机分桶的表不支持 Colocate Group，所以「图省事不写 `DISTRIBUTED BY`」的代价在这里。

## 七、两刀裁剪：分区与分桶

**本节要点**：裁剪是**用元数据省 I/O**，比任何索引都便宜。两刀能不能落下，取决于 `WHERE` 里有没有那两个键。

### 7.1 第一刀：分区裁剪

`WHERE` 里带分区列 → FE 直接排除不相关的分区，**连 tablet 都不调度**。

```sql
-- 能吃分区裁剪
SELECT sum(pv) FROM site_access WHERE event_day >= '2026-11-01';

-- 吃不到：分区列套了函数，FE 算不出区间（除非是表达式分区且函数一致）
SELECT sum(pv) FROM site_access WHERE date_format(event_day,'%Y-%m') = '2026-11';
```

⚠️ 表达式分区有个额外好处：分区规则本身就是表达式，**同样的表达式写进 `WHERE` 时仍可能被识别**。
但这是「可能」——具体是否命中，本册未确认，以实际 `EXPLAIN` 为准。

### 7.2 第二刀：分桶裁剪

`WHERE` 里带**分桶键**的等值条件 → 只扫命中的那几个 bucket。

文档的例子很直观：每分区 10 个桶，`WHERE site_id = 54321` → 裁掉 9 个，只读 1/10。

三个前提缺一不可：

1. 这张表用的是**哈希分桶**（随机分桶没法按值定位）；
2. 条件列**就是分桶键**（或分桶键的前缀部分）；
3. 条件是**等值**（`IN` 也可以拆成多个等值）。

⭐ 所以「分桶键选谁」这个决定，实际是在选「**哪一类查询能享受 1/N 的扫描量**」。
选 `site_id` 就对 `site_id` 的查询有利，选 `(site_id, city_code)` 就更均匀但单列过滤的裁剪变弱——
这和 [架构与表模型.md](架构与表模型.md) 3.2 的倾斜问题是同一个取舍的两面。

### 7.3 三刀的顺序与量级

```
SQL
 ├─ 第 1 刀：分区裁剪      → 排除整个分区（省的是「整段数据」）
 ├─ 第 2 刀：分桶裁剪      → 排除桶（省的是「1/N 的数据」）
 ├─ 第 3 刀：前缀索引      → 跳到 Data Block（省的是「块内的行」）
 └─ 第 4 刀：ZoneMap / Bitmap / Bloom → 块内再筛
```

⭐ 越靠前的刀越便宜、省得越多。**一个查询慢，先看第 1、2 刀有没有落下**——
这两刀没落下，后面调索引的收益都有限。

![四刀裁剪的顺序与省下的量](images/四刀裁剪.svg)

条带宽度只是示意、不是实测比例，要记的是顺序与代价：前两刀靠元数据排除，几乎免费；第三刀靠前缀索引跳块；
最后一刀才真的把数据读进来再过滤。所以「查询慢」先查前两刀落没落下，而不是先去加索引。

## 八、这一篇的结论收口

- **先分「扫多了」还是「算慢了」**：看 scan 节点的扫描量与结果行数之比，再谈执行。
- **前缀索引三条硬限制**：1024 行一条、索引项 **36 字节**、前缀字段 **≤3 个**、**字符串列只能在末尾**。
- **`ShortKeyFilterRows` 是「索引到底生效没有」的唯一实锤**——为 0 就别再猜了。
- **三层内置索引是链式的**：前缀定位块 → ZoneMap 判断块要不要读 → Ordinal 找到列页。
- **手动索引是给非排序列补课**：Bloom 管高基数等值、Bitmap 管强选择性组合、N-Gram 管子串、倒排管全文。
- **Runtime Filter 的代价是「等构建端」**，不是免费的加速。
- **统计信息过期会让 CBO 选错 join 顺序**——数据量突变后先 `ANALYZE` 再改 SQL。
- **裁剪顺序：分区 → 分桶 → 前缀索引 → 块内索引**，前两刀不落，后面收益有限。
