# 物化视图与湖上分析

> 覆盖：同步物化视图（Rollup）与异步物化视图的分工、异步 MV 的两种刷新策略与分区级刷新、
> 透明改写的成立条件、External Catalog 与 Data Cache。
>
> ⚠️ 本篇**没有本仓实测读数**，全部为官方文档（`Latest-4.1`）口径。按机制推导的结论标「推演」；
> 文档未明说的写「未确认」。口径边界见 [README.md](README.md) 第四节。

---

## 一、两种物化视图，是两个东西

**本节要点**：名字像，机制完全不同——**同步 MV 是索引，异步 MV 是表**。判据只有一条：**刷新由谁触发**。

| | **同步物化视图**（Rollup） | **异步物化视图**（ASYNC MV） |
|---|---|---|
| 本质 | 基表的**附属索引** | 一张**独立的物理表** |
| 引入 | v2.3 及更早 | **v2.4 起**（查询改写 **v2.5 起**） |
| 基表 | **Default Catalog 中的单个表** | 多表：Default Catalog、External Catalog（v2.5+）、已有异步 MV（v2.5+）、已有视图（v3.1+） |
| 多表 join | ❌ | ✅ |
| 聚合函数 | **选择有限**（只有部分算子能改写） | 更丰富 |
| 刷新 | **导入基表时同步刷新**，无需命令 | **ASYNC**（定时 / 基表变更触发）或 **MANUAL**（手动） |
| 数据新鲜度 | 与基表强一致（导入即刷新） | 取决于刷新策略，**存在滞后** |
| 查询改写 | ✅（部分聚合算子） | ✅（**仅 SPJG 类型计划**） |

⭐ 一句话判据：**要「导入即可见、单表聚合」→ 同步 MV；要「多表 join、可接受分钟级滞后」→ 异步 MV。**

代价的对比也很清楚：同步 MV 不滞后，但它把刷新成本**摊进了每一次导入**（导入变慢）；
异步 MV 把刷新从导入链路上摘出去了，换来的是**数据有滞后**，以及一套「谁触发刷新、失败怎么办」的运维负担。

## 二、异步 MV：刷新是最需要想清楚的部分

**本节要点**：异步 MV 建完只反映**建表那一刻**的基表状态；之后的所有新鲜度都靠刷新。刷新策略选错，MV 会变成一份「看起来很新其实很旧」的表。

### 2.1 两种刷新策略

| 策略 | 何时刷新 | 适合 |
|---|---|---|
| **ASYNC** | 基表数据变更时自动触发，或按指定间隔定期触发 | 绝大多数场景 |
| **MANUAL** | **只能手动触发**，不会自动刷 | 刷新代价极高、能接受按业务节奏刷（如每天一次） |

⚠️ 注意 `ASYNC` 不是「实时」：它是「**变了就安排一次刷新**」，刷新本身是异步作业，中间有延迟。
把异步 MV 当强一致视图用，是这类组件最常见的事故来源。

### 2.2 分区级刷新

异步 MV 支持**只刷新变化的分区**，而不是整表重算——这是它能把刷新成本压下来的关键。
（机制上要求 MV 与基表的分区能对齐；具体对齐规则本册未逐条核，使用时以 `REFRESH` 语法与分区定义为准。）

⭐ 这一条决定了「要不要按天分区建 MV」：**不分区 = 每次刷新都是全量**；
分区了才有「只刷昨天那一格」的可能。数据量一大，这个差别是数量级的。

### 2.3 刷新不是免费的

| 成本项 | 说明 |
|---|---|
| **计算** | 刷新本身是一次查询，要占资源；多个 MV 同时刷新会互相挤 |
| **存储** | MV 是物理表，占存储（存算一体下还占本地盘） |
| **调度** | 定时刷新的任务堆积、失败重试，要有人管 |
| **一致性窗口** | 刷新之间，MV 与基表不一致，业务要能接受 |

## 三、透明改写：条件比想象中严

**本节要点**：改写是「优化器自动发现你的查询可以走 MV」，不是「有 MV 就一定走」。**条件不满足时它静默不生效**——这是最需要验证的一环。

### 3.1 成立条件

| 条件 | 具体要求 |
|---|---|
| **MV 的计划类型** | 必须是 **SPJG 类型**：计划里只包含 `Scan` / `Filter` / `Project` / `Aggregate` 四类算子 |
| **版本** | v2.5 起才支持自动透明改写（v2.4 的异步 MV 不支持改写） |
| **基表来源** | ⚠️ 建在 **JDBC catalog** 或 **Hudi catalog** 基表上的异步 MV **不支持改写** |
| **查询形态** | 查询要能被判定为「可复用 MV 的预计算结果」，涉及聚合函数匹配、谓词覆盖等 |

⭐ 第一条最容易被忽略：**SPJG 之外还有 join 的 MV，改写能不能成立？**
文档的表述是「支持基于 SPJG 类型异步 MV 的自动透明改写」——也就是**改写能力的边界由计划算子决定**。
至于带 join 的 MV 在什么条件下命中改写，本册未逐条核，**以实际 `EXPLAIN` 为准，不要按「建了就该改写」去假设**。

### 3.2 怎么验证改写生效

没有实测支撑，只能给方法：对同一条查询取**改写前 / 改写后**的执行计划，比对扫描的是基表还是 MV。
如果计划里仍然扫基表，说明条件没满足——此时该做的是回头核对上表，而不是调参数。

⚠️ 这是本篇最需要实测的一处，也是 README 4.2 里列的「缺的读数」之外应该补的第六项。

### 3.3 与 ClickHouse 的物化视图，思路完全相反

| | StarRocks 异步 MV | ClickHouse 物化视图 |
|---|---|---|
| 触发方式 | 独立作业（定时 / 变更） | **写入时由导入链路触发**（insert trigger） |
| 与查询的关系 | 优化器**主动**找匹配的 MV 改写 | 默认不参与查询改写；要么显式查 MV，要么手工改 SQL |
| 状态列 | 无（存的是最终结果） | `AggregatingMergeTree` + `AggregateFunction` 状态列，读时 `-Merge` |
| 回填历史 | 建完刷新即可（按 MV 的查询算） | ⚠️ **建 MV 不回填历史**（见 [物化视图与实时聚合.md](../ClickHouse/物化视图与实时聚合.md)） |

⭐ 最关键的一条差别：**ClickHouse 的 MV 是「写入侧的派生」，StarRocks 的异步 MV 是「查询侧的可复用结果」**。
前者新鲜度天然好但无法改写查询，后者能改查询但要管刷新。选型时这个差别比语法差别重要得多。

## 四、External Catalog：不改数据，直接读湖

**本节要点**：External Catalog 让 StarRocks 把 Hive / Iceberg / Hudi / Paimon / JDBC / Elasticsearch 里的表**当自己的表查**，数据不动。它的代价从「导入」换成了「远端读」。

### 4.1 能接哪些源

| 类型 | 典型 | 说明 |
|---|---|---|
| **Hive** | Hive Metastore | 最成熟的湖上接入 |
| **Iceberg / Hudi / Paimon** | 表格式 | 读快照，取决于表格式的元数据 |
| **JDBC** | MySQL、PostgreSQL 等 | ⚠️ 建在这类基表上的异步 MV **不支持改写** |
| **Elasticsearch** | — | 检索侧接入 |
| **Default Catalog** | StarRocks 自己的库 | 内部表默认就在这里 |

### 4.2 两条路线的取舍

| | **导入进来**（Broker Load / Routine Load） | **不导，直接读**（External Catalog） |
|---|---|---|
| 数据位置 | StarRocks 本地 / 对象存储 | 原地不动 |
| 查询延迟 | 低（本地列存 + 索引） | 取决于远端格式与缓存 |
| 数据新鲜度 | 取决于导入频率 | **读到的是快照当时的状态** |
| 存储成本 | 要额外一份 | 无额外副本 |
| 适合 | 高频查询的 serving 层 | 低频、临时、探索性查询；数据多方复用 |

⭐ 判断很简单：**同一份数据被高频查 → 导；偶尔查 / 多方共享 → 直接读**。
这也是「湖仓」里 MPP 数据库的位置——它既是 serving 层（导入的那部分），也是湖的查询入口（External Catalog 的那部分）。

## 五、Data Cache：存算分离下的性能命门

**本节要点**：存算分离把数据放到远端，**缓存命中率就成了性能的主变量**。这不是「加了缓存」，而是「把本地性做成了可调的策略」。

### 5.1 三层缓存

```
CN 内存
  ↓ 未命中
CN 本地磁盘（Data Cache）
  ↓ 未命中
对象存储 / HDFS（远端）
```

查询时的顺序是：**先扫缓存，再扫本地盘，最后才去远端拉**。冷数据拉回来后会写进本地缓存，加速后续查询。

- 建表时可以启用缓存：启用后数据**同时写本地磁盘和对象存储**；
- 查询时 CN 先从本地盘读，没有再回远端拿，并把结果缓存到本地；
- 文档还提到**数据预取策略**，用来缓解冷数据的首次访问延迟。

### 5.2 缓存带来的新问题

| 问题 | 说明 |
|---|---|
| **首次访问慢** | 缓存冷的时候，所有查询都退化成「远端读」 |
| **缓存容量** | 本地盘有限，装不下全部热数据时会有淘汰，命中率下降 |
| **多 CN 节点各自缓存** | 同一个 tablet 在不同 CN 上各缓存一份；v3.5.1+ 才有**跨节点 Data Cache 共享** |
| **弹性伸缩的冷启动** | 新加的 CN 缓存是空的，刚扩完容的那段时间性能会差 |

⭐ 所以「存算分离能不能替代存算一体」这个问题，实质是「**你的查询模式能不能让缓存命中率高到抵消远端读**」。
全量扫描型负载（每次都要读很大范围）命中率天然低；点查与热区查询则受益明显。

## 六、这一篇的结论收口

- **同步 MV 是索引、异步 MV 是表**：前者导入即刷新（成本摊在导入上），后者靠刷新（成本是滞后 + 运维）。
- **异步 MV 建完只反映建表那一刻**，之后全靠刷新；`ASYNC` 不等于实时。
- **分区级刷新是异步 MV 的成本命门**：不分区就是每次全量刷。
- **透明改写的边界是 SPJG 计划**（`Scan` / `Filter` / `Project` / `Aggregate`），且 **JDBC / Hudi 基表的 MV 不参与改写**。
  验证方法只有一个：看执行计划扫的是基表还是 MV。
- **External Catalog 把「导入」换成「远端读」**，适合低频与多方复用的数据，不适合高频 serving。
- **存算分离的性能命门是缓存命中率**，首次访问与扩容冷启动是两个必须预案的场景。
