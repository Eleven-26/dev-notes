所以收敛成一篇，把四个主题按「节点 → 表 → 分布 → 部署形态」串成一条线。

## 二、StarRocks 的数据分几层？

**本节要点**：它的层次比 ClickHouse 多一层「桶」，而这一层正是**扩容与裁剪的单位**——ClickHouse 靠 part 自己长，StarRocks 靠 tablet 被安排。

### 2.1 纵向：一份数据被切成了什么

```
表 (table)
 └─ 分区 (partition)          ← 按时间或枚举值切，是「管理单位」：可以单独设副本数、冷热介质、TTL
     └─ 分桶 (bucket)          ← 按哈希或随机切，是「并行与裁剪单位」
         └─ tablet             ← 分桶在一个副本上的实例，是「复制与调度单位」
             └─ segment 文件    ← 列存落盘单位，文件内部再切成 page
```

四个概念各管一件事，混起来就会问出「分桶数能不能改」这种没有统一答案的问题：

| 层 | 谁决定 | 能不能事后改 | 决定什么 |
|---|---|---|---|
| 分区 | 分区键 + 分区方式 | 能（加 / 删分区） | 数据生命周期、冷热、裁剪的第一刀 |
| 分桶 | 分桶键 + 分桶数 | 能（v3.2 起可 `ALTER`，v3.3.3 起可在线） | 并行度、按分桶键过滤时的裁剪比例 |
| tablet | 由分桶与副本数派生 | 随分区 / 分桶变化 | 复制、迁移、修复的最小单位 |
| segment | 写入时生成 | 随 compaction 变化 | 列存文件与索引的实际布局 |

### 2.2 横向：同一张表凭什么分布在多台机器上

一个分区被分成 N 个桶，每个桶在 M 个副本上各有一份 tablet —— 于是这个分区的 tablet 数是 `N × M`。
FE 负责把这些 tablet 摊到各 BE 上，BE 只认自己本地的那批。

⭐ **这一层的直接后果**：副本数是**分区级**属性（可以按月热、按年冷设不同副本数），
而分桶数是**分区内并行度**——两个旋钮管的是完全不同的事，却常被当成一个「副本与分片」笼统对待。

![两个旋钮：分区管生命周期，分桶管并行](images/两个旋钮.svg)

左边那个旋钮决定「数据保留多久、放什么介质、留几份副本」，右边那个决定「按某个键过滤能省几分之一的扫描量」。
两个一乘才是这张表的 tablet 总数，也是 FE 要长期记住的那份元数据量。

## 三、版本坐标速查

⭐ 本目录写于 **2026-11**，对应官方文档 `Latest-4.1`。**核不实的条目不列**：

| 项 | 现状 | 备注 |
|---|---|---|
| 当前主线 | **4.1.7**（2026-10-26） | 4.1 线，文档口径以此为基准 |
| 上一稳定线 | **3.5.21**（2026-07-23） | 3.5 线仍在维护 |
| 4.0 线 | **4.0.14**（2026-08-11） | ⚠️ 官方明示：升到 4.0 后**不可直接降级到 3.5.0 / 3.5.1**（元数据不兼容，会导致 FE crash），必须降到 3.5.2+；4.0.2 ↔ 4.0.1 之间降级前需先 `SET GLOBAL enable_rewrite_simple_agg_to_meta_scan=false` |
| 存算分离 | 3.0 起支持，4.x 是主推形态之一 | BE 被 CN 取代，数据落对象存储 / HDFS |

| 随机分桶 | v3.1 起 | 不指定 `DISTRIBUTED BY` 时的默认行为 |
| 自动设置分桶数 | v2.5.7 起 | 不写 `BUCKETS` 时的默认行为 |
| 基于范围的分桶 | **v4.1 起**，默认关闭 | 需开 FE 配置 `enable_range_distribution` |
| 主键表用 `ORDER BY` 定义排序键 | v3.0 起 | 明细 / 聚合 / 更新表要到 **v3.3** 才支持 |
| 倒排索引 | 存算一体 v3.3+ / 存算分离 v4.1+ | — |
| 向量索引 | 存算一体 v3.4+ | 存算分离**待支持** |

### 3.1 三条使用纪律

- **读法**：凡是「某功能从哪个版本开始」的判断，以这张表为准；表里没有的，本目录写「未确认」。
  网上的资料常把 2.x 的行为写成通例（例如「分桶数建完不能改」——v3.2 起就能改），照抄会误导。
- **版本差异不是小事**：上面那张表里「存算一体 / 存算分离」两列的差异（尤其是主键表的条件更新、
  部分更新、倒排索引），是**同一版本里两种部署形态**的差异，不是新旧版本差异。选型时问清部署形态再谈功能。
- **升级前先看降级路径**：4.0 的降级禁忌是踩过的坑（元数据不兼容 → FE crash），不是理论风险。

## 四、口径声明与本仓的实测边界

### 4.1 为什么没有实测

本仓对每个数据库册的要求是「读数必须来自本机容器」。这一册没做到，原因是**镜像拿不到**：

- `starrocks/allin1-ubuntu:4.1.7` 在 Docker Hub 上，本机直连 Docker Hub 不可达（`registry-1.docker.io` 超时）；
- 配置的三个国内 mirror（daocloud / nju / 163）对该镜像**缓存未命中**，daocloud 回源直接返回 HTTP 500；
- 试过的其它 mirror（1panel、hlmirror、tbedu、dockerpull 等）要么要登录、要么同样回源失败；
- 官方 tar 包（`StarRocks-4.1.4-ubuntu-amd64.tar.gz`，**1.79 GB**）可下，但实测单连接约 **268 KB/s**、
  12 线程分段合计约 **0.9 MB/s**，完整下载约半小时以上，且后续还要自建镜像补 JDK 与系统库。

结论：**在当前网络下无法在合理时间内建立起可复跑的实验环境**，故本册只写机制。

### 4.2 缺的是哪几组读数（补的条件明确）

按价值排序，这五组是补上之后最该改写的：

| # | 缺的读数 | 为什么重要 |
|---|---|---|
| 1 | 四种表模型对同一批重复行的实际结果 | 这是全册最核心的一张表，现在只能按语义推演 |
| 2 | 同一 label 重复提交的返回原文 | 证明 At-Most-Once 不是文档话术 |
| 3 | 主键表 `merge-on-write` 与更新表 `merge-on-read` 的更新代价对照 | 决定「更新频繁的表该建哪种」 |
| 4 | 分区裁剪与分桶裁剪在 `EXPLAIN` 里的实际表现（扫了几个 tablet） | 分桶键选错的代价，只有这个能说清 |
| 5 | Runtime Filter 开 / 关的 scan 行数差 | MPP join 的关键优化，现在只有机制 |

### 4.3 本册不写的东西

- **不写任何性能数字**。没有「比 X 快 N 倍」「延迟多少毫秒」这类句子——因为没有一组是本机跑出来的。
- **不引用第三方跑分**。TPC-H / SSB 的公开结果一律不搬（口径不同、硬件不同、版本不同，搬过来就是误导）。
- **不写未确认的默认值**。凡是「参数默认值」类断言，只写文档明确给出且本册核过的（如分桶自动设置在 2.5.7 引入）。

## 延伸追问

- **StarRocks 和 Doris 是什么关系？** → 同源。StarRocks 源自 Apache Doris（更早叫 Palo）的分支，此后各自演进：
  Doris 沿 Apache 基金会路线，StarRocks 独立发展并在执行引擎（Pipeline）、存算分离、物化视图上走出不同路径。
  两者的 SQL 方言与建表语法有相似处但**不通用**，运维命令与配置项也不同名。⚠️ 本仓没有 Doris 篇目，上面这句只到「同源与分叉」的层面。
- **为什么本册没有「性能调优」篇？** → 调优篇的价值九成在**对照读数**（改一个参数前后差多少），
  没有实测的调优篇只能写「建议调大 X」，那是文档搬运。等能实测了再补，不先占位。
- **存算分离是不是未来的默认？** → 官方在推，但不是所有功能都对等（见 [架构与表模型.md](架构与表模型.md) 第四节那张功能差异表）。
  倒排索引、向量索引、备份恢复、跨集群迁移在存算分离上要么版本更晚、要么**不支持**。
