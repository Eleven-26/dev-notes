## 一、FE 要几个节点

**本节要点**：高可用的门槛不是「有没有备份」，而是**过半 Follower 存活**。这条规则直接决定了 2 个节点比 1 个节点更危险。

### 1.1 判据：过半，而不是「有几个」

Leader 由 Follower 选举产生，**要选出 Leader，必须有过半的 Follower 存活**：

| Follower 数 | 容忍挂几个 | 说明 |
|---|---|---|
| **1** | **0** | 挂了就没有 Leader，集群只读不可写（甚至不可查） |
| **2** | **0** | ⚠️ 挂 1 个只剩 1，不过半 → 选不出 Leader。**2 个比 1 个更没意义** |
| **3** | **1** | 生产的最小可用配置 |
| **5** | **2** | 更高的容灾，但写元数据的 RTT 成本上升 |

⭐ 这张表解释了运维里一个反直觉的建议：**要么 1 个、要么 3 个，不要 2 个**。
2 个 Follower 的可用性与 1 个完全相同（都是 0 容错），却多了一份同步开销。

### 1.2 Observer：加并发不加选举压力

Observer 从 Leader 同步并重放日志，能提供**读元数据与查询并发**，但：

- ⚠️ **不参与选主** → 加多少 Observer 都不影响「过半 Follower」这条约束；
- 因此它适合**读多写少**的场景：报表、看板、临时查询集中打到 Observer 上，把 Leader / Follower 留给写入与 DDL。

这是 FE 部署里性价比最高的一招：**用 Observer 扩查询并发，不改变容灾等级**。

### 1.3 FE 的元数据是内存里的全量副本

每个 FE 都在内存里放一份**完整元数据**（BDB JE）。所以：

| 元数据量增长源 | 直接后果 |
|---|---|
| 表多 | FE 堆占用上升 |
| **分区多** | ⭐ 主要增长源；分区数从十万级往上要盯 FE 的 GC |
| tablet 多（分桶数 × 副本数 × 分区数） | 同上，且影响调度扫描的开销 |

⭐ 运维结论：**「分区粒度别切太碎」不只是查询性能问题，更是 FE 的稳定性问题**。
一个按小时分区、保留两年的表 = 17520 个分区；如果每个分区 10 桶 3 副本，就是 52 万个 tablet。

## 二、副本与修复

**本节要点**：修复以 **tablet** 为单位，不是以表或分区为单位。BE 掉线后触发的是「它上面那批 tablet 的副本补齐」。

### 2.1 三件事分开看

| 概念 | 是什么 | 谁管 |
|---|---|---|
| **副本数** | 一个 tablet 存几份 | **分区级属性**（`replication_num`），可以按月热 3 份、按年冷 1 份 |
| **`write_quorum`** | 几份写成功算这次导入成功 | 表属性，可用 `ALTER TABLE` 改 |
| **副本修复** | 副本数低于期望时，从健康副本克隆补齐 | FE 调度，以 tablet 为单位并发进行 |

⚠️ **把 `write_quorum` 当性能参数是错的**。它调的是「可用性与一致性的天平」：
调低 → 少数副本写成功就算成功，写入更快但故障时可能丢刚写的数据；调高 → 更安全但更容易因单副本抖动导致导入失败。

### 2.2 修复的两个典型场景

| 场景 | 表现 | 处理 |
|---|---|---|
| **单 BE 重启** | 它上面的 tablet 副本短暂不可用；恢复后可能触发一波补齐 | 通常自愈；关注补齐期间的整体 I/O |
| **BE 长时间离线 / 磁盘损坏** | 副本数持续低于期望，FE 反复尝试克隆 | 先修好节点或扩机器，让恢复目标可达；否则会一直重试 |

⭐ 一个容易被忽略的连锁：**补齐副本要和正常查询抢 I/O**。所以「加机器扩容」之后的那段时间，
查询可能反而变慢——新节点在拉数据。这个窗口要有预期，别当成「扩容没效果」。

### 2.3 单副本表

测试环境常写 `replication_num = 1` 省资源。要知道它的含义：**BE 一挂，数据直接不可用**，
没有修复的余地（源副本没了）。生产环境不要用单副本，除非这份数据可以从湖表 / 上游完全重建。

## 三、资源组与查询队列

**本节要点**：多租户场景下，「谁能用多少 CPU / 内存」和「排队还是拒绝」是两套机制，不要混为一谈。

### 3.1 资源组（Resource Group）

按**分类器**（如用户、查询类型、SQL 里的标记）把查询分到不同组，每个组有独立的 CPU / 内存配额与并发上限。

这个能力是 MPP 数据库相对单机列存库的一个实际优势：**同一个集群里，报表查询和临时探索查询可以互不干扰**。
ClickHouse 侧对应的能力是 `settings` 里的查询级限制（见 [OLAP查询服务.md](../../../../04-架构与系统/系统设计/大数据平台/OLAP查询服务.md) 4.3 节的对照）。

### 3.2 查询队列

超过并发的查询**排队等待**而不是直接失败。两套机制配合的典型配置：

```
资源组：限制「这个组最多用多少资源」
   +
查询队列：资源用满时，「新的查询排队等，还是直接报错」
```

⚠️ 这里有个必须想清楚的问题：**排队会把延迟变成不可预测**。前端接口后面挂一个会排队 30 秒的查询，
超时设置不匹配就会变成「接口超时但查询还在跑」——白烧资源。所以排队要有**队列超时**，且要和上游的超时对齐。

### 3.3 隔离做到什么程度

| 层面 | 手段 | 边界 |
|---|---|---|
| 资源 | 资源组（CPU / 内存 / 并发） | 组内仍会互相影响 |
| 数据 | 分库 / 分表 / 分集群 | 物理隔离，成本最高 |
| 故障 | BE 黑名单（v3.3+）/ CN 黑名单（v4.0+） | 把坏节点摘出去，不让它拖慢查询 |

## 四、监控：先看四个面

**本节要点**：StarRocks 的监控不是「指标越多越好」，四类指标覆盖了绝大多数故障。

| 面 | 看什么 | 异常意味着 |
|---|---|---|
| **FE 存活与角色** | 谁是 Leader、Follower / Observer 数量、日志重放进度 | 选主异常、Observer 落后 → 元数据不一致风险 |
| **FE 资源** | 堆占用、GC 时间、元数据量（库 / 表 / 分区 / tablet 数） | 堆涨 → 分区或 tablet 过多；GC 频繁 → 查询抖动 |
| **BE / CN 资源** | CPU、内存、磁盘使用率、**compaction 积压** | compaction 跟不上 → 读放大、查询变慢 |
| **查询** | 慢查询数、排队长度、失败率、Profile 里的扫描量 | 排队涨 → 资源不足或统计信息过期导致计划变差 |

⭐ 两个最该盯的「隐性指标」：

- **compaction 积压**。写入很猛但 compaction 跟不上时，读要扫的版本变多，表现是「数据量没涨多少但查询变慢」。
  ClickHouse 的 `Too many parts` 是同一类问题的另一种表现（见 [写入与数据导入.md](../ClickHouse/写入与数据导入.md)）。
- **FE 的元数据对象数**。它不是性能指标，但它决定了 FE 什么时候会突然 OOM。

## 五、起不来时的排查顺序

**本节要点**：按「进程 → 端口 → 元数据 → 副本」四层往下走，不要一上来就翻配置。

### 5.1 FE 起不来

```
1. 进程在不在           → 不在，看 fe.log / fe.warn.log 的最后一段
2. 端口有没有被占       → 9030（MySQL 协议）、8030（HTTP）、9010（EDIT_LOG_PORT）、9020（RPC）
3. 元数据能不能加载     → BDB JE 的日志；元数据损坏时 FE 会直接退出
4. 是不是选不出 Leader  → 检查 Follower 数量与存活数是否过半
```

### 5.2 BE 起不来

```
1. 进程在不在           → 看 be.out / be.WARNING
2. 存储目录权限与空间   → 数据目录不可写、磁盘满，是最常见的两个原因
3. 能不能连上 FE        → BE 要注册到 FE；网络不通会一直重试
4. 版本是否匹配         → FE 与 BE 大版本不一致会拒绝注册
```

### 5.3 集群起来了但查不到数据

| 现象 | 先查 |
|---|---|
| 表在、`SELECT` 返回空 | 数据真的进去了吗（导入作业是否 `FINISHED`、过滤行数多少） |
| 查询报副本不足 | `SHOW PARTITIONS` 看副本状态，是否有 tablet 在补齐 |
| 建表报错 | 副本数是否大于可用 BE 数（3 副本但只有 2 个 BE，建表直接失败） |

⭐ 最后一条是新手最常撞的：**`replication_num` 不能超过 BE 数量**。单机测试环境一律写 `1`。

## 七、这一篇的结论收口

- **FE 高可用看「过半 Follower」**：1 个和 2 个都是 0 容错，**生产最小 3 个**。
- **Observer 扩并发不加选举压力**，是读多写少场景里性价比最高的一招。
- **FE 的元数据在内存里**：分区数与 tablet 数是它的两个主要增长源，也是 OOM 的两个主因。
- **副本数、`write_quorum`、副本修复是三件事**：前者管存几份，中者管写成功门槛，后者管补齐。
- **扩容后的那段时间查询可能变慢**——新节点在拉数据，和查询抢 I/O。
- **compaction 积压是隐性杀手**：数据量没涨、查询却变慢，先看它。
- **`replication_num` 不能超过 BE 数量**，单机测试一律写 1。
