## 一、列式数据库是什么？它和行式存储的根本差别在哪

**本节要点**：差别不在「数据库」而在**同一张表在磁盘上的摆放方向** —— 行存把一行写在一起，列存把一列写在一起；这一个方向选择同时决定了压缩率、扫描效率与适用负载。

| 维度 | 行式存储（MySQL / PostgreSQL 的表） | 列式存储（ClickHouse / 数仓） |
|---|---|---|
| 落盘方向 | 一行内所有列**连续**存放 | 一列内所有行**连续**存放 |
| 压缩率 | 行内字段类型混杂，压缩率有限 | 同列同类型、相似度高，**压缩率高一个数量级** |
| 点查（按主键取一行） | **快**（一次顺序读拿到整行） | 慢（要拼多列，且列存无行级索引） |
| 聚合（`SUM` / `COUNT` / `GROUP BY`） | 慢（要把整行都读进来） | **快**（只读参与聚合的列，其余列一个字节不碰） |
| 更新 / 删除 | 原地更新，代价低 | 追加写入、后台合并，**更新删除代价高** |
| 典型负载 | OLTP：事务、高并发点查 | OLAP：大批量写入、宽表聚合、分析报表 |

⭐ **一句话判据**：**「按行取一条」选行存，「按列扫一片」选列存**。这不是谁更先进，而是同一份数据被读的方式不同。

## 二、这一类由谁代表？为什么本目录先收 ClickHouse

**本节要点**：列式存储一族至少分成四类落地形态；本目录先收**开源自建单机列存**这一类的代表 ClickHouse，因为它是**唯一能在本机跑起来、逐条实测**的形态。

| 形态 | 代表 | 说明 |
|---|---|---|
| **开源自建列存** | **ClickHouse**、Doris、StarRocks | 可自建、可本机实测；本目录当前收录 ClickHouse |
| 云数据仓库 | Snowflake、BigQuery、Redshift | 托管、按量计费，无法在本机复现读数 |
| 湖上分析格式 | Parquet / ORC / Iceberg / Hudi / Paimon | 是**文件格式**而非数据库，分析引擎读它；见 [数据湖/](../数据湖/README.md) |
| 时序 / 检索引擎里的列存 | GreptimeDB、Elasticsearch（doc_values） | 同为列式组织，但语义聚焦在时序 / 检索；分别见 [时序数据库/](../时序数据库/GreptimeDB/README.md) 与 [搜索与分析/](../搜索与分析/Elasticsearch/README.md) |

选 ClickHouse 作为本目录第一个组件的理由：**开源、单机可跑、列存特征齐全**（见下一节的收录清单），
且书（2020，19.17）与本机容器（26.3）能形成一组**跨版本对照**，把「书里写的」和「今天跑的」逐处比出来。

⭐ 本表按**落地形态**分四类；如果按「**数据与元数据归谁**」分，这一族只有三条实现路线（库内列存引擎 / 湖上开放格式 + 外部引擎 / 托管云数仓），
那条轴上的族内对照、四个分水岭与契合语言维度都在 [列式数据库选型对比.md](列式数据库选型对比.md) —— ⚠️ 两张表切的轴不同，不要混读。
