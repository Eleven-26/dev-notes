# GreptimeDB 目录导读

> 覆盖 GreptimeDB 的统一可观测数据模型、Mito 存储引擎与 region / SST 组织、写入路径、
> 三级剪枝与索引设计、SQL 与 PromQL 双查询、写入协议与可观测性集成、Flow 流计算、
> 部署与集群运维、性能调优，以及选型对比与落地案例。
>
> **基础框架**参考 Greptime 官方博客《GreptimeDB 存储引擎设计内幕》（2022-12-20），
> 以及 GreptimeDB 官方文档与 Release Notes。该博客写于 2022-12，早于之后的多个版本；
> 凡与最新官方文档不一致处，本目录以最新官方文档为准，并逐处标注「博客口径 vs 当前文档口径」。
>
> ⚠️ **本目录本轮未做容器实测**：正文均整理自 GreptimeDB 官方文档与官方博客，
> 不包含任何本机运行的读数或日志；涉及版本时间点的结论均注明官方出处，核不实的条目不写。
> 参考资料与原始素材见 [素材清单](../../../../素材清单.md)。

### 2.1 三条使用纪律

- **来源优先级**：官方 Release Notes > 官方技术文档 > 官方博客。本目录凡涉及具体版本号，
  都按这个优先级核对；三者冲突时以 Release Notes 为准，并在文中如实写出「博客口径 vs 当前文档口径」。
- ⚠️ **v1.0 的两项 breaking change**（据官方 Release Notes v1.0.0）：新建表默认 `flat` SST 格式
  （旧 `primary_key` 格式仍可读，可显式切回）；HTTP Arrow IPC 输出由 file 改为 stream 格式。
  升级前需确认读取端支持后者。
- **与 2022-12 博客的差异**：博客描述存储引擎时用的是当年的口径；当前官方文档已补充
  `flat` / `primary_key` 两种 SST 格式、三类索引（倒排 / 跳数 / 全文）、WAL 三模式（Local / Remote / Noop）等。
  本目录在 [架构与存储引擎.md](架构与存储引擎.md) 与 [索引设计与查询优化.md](索引设计与查询优化.md) 中会逐处点明差异。

术语约定（本目录统一）：

| 术语 | 含义 |
|---|---|
| Mito | GreptimeDB 的默认存储引擎，基于 LSM-tree，面向时序负载 |
| region | 表数据的物理分片，是引擎中的逻辑隔离存储单元，含自己的元数据 / memtable / SST / manifest |
| SST | 有序字符串表（Sorted String Table），在 GreptimeDB 里是 Parquet 格式的不可变文件 |
| manifest | 记录 region 变更（新增 / 移除文件）的元数据日志 |
| Puffin | 存放索引数据的辅助文件格式，索引以 Blob 形式与 SST 元数据放在一起管理 |
| TWCS | Time Window Compaction Strategy，按时间窗口分组候选文件的压缩策略 |

### 2.2 部署形态与接入协议速览

下面两条与版本无关，但决定了「怎么跑、怎么接」，各篇会反复引用：

| 维度 | 选项 | 出处 |
|---|---|---|
| 部署形态 | standalone（单进程）/ distributed（Metasrv + Frontend + Datanode，可选 Flownode） | 官方文档《架构》 |
| 持久化位置 | 本地文件系统 / 对象存储（S3 及兼容、GCS、Azure Blob、阿里云 OSS） | 官方文档《存储位置》 |
| WAL 模式 | Local（raft-engine）/ Remote（Kafka）/ Noop（应急，不存数据） | 官方文档《WAL 概述》 |
| 查询语言 | 所有信号可用 SQL；指标另可用 PromQL；链路另可用 Jaeger 兼容接口 | 官方文档《为什么选择 GreptimeDB》 |
| 写入协议 | Prometheus Remote Write、OTLP/HTTP、Loki Push API、Elasticsearch Bulk API、InfluxDB Line Protocol、MySQL、PostgreSQL、gRPC、HTTP | 官方文档《为什么选择 GreptimeDB》 |

⚠️ **「集成」不等于「完整兼容」**：官方文档明确指出，Loki 写入不含 LogQL，开源版 Elasticsearch 集成支持 Bulk API
但不等于完整支持 Query DSL。规划迁移前需核对各协议页面列出的边界。

### 3.1 两条线怎么走

> ⭐ **原理线**（②→③→④）回答「数据怎么存、查询为什么快」；
> **落地线**（①→⑦→⑧→⑩）回答「怎么把数据接进来、怎么把它跑稳」。

- **原理线**：② 建立存储布局的心智模型 → ③ 理解建表与写入语义 → ④ 掌握查询剪枝与调优。
  这条线读完，你能解释「为什么按时间范围查比按字段过滤快」，也能判断一张表该怎么建主键。
- **落地线**：① 先判断需求是否落在能力半径内 → ⑦ 选接入协议 → ⑧ 对接可视化与追踪生态 → ⑩ 把集群跑稳。
  这条线读完，你能把一套采集链路完整落到 GreptimeDB 上。
- **收口**：⑤⑥ 是**查询面**（两种查询语言），⑨ 是**计算面**（把聚合预先算好），⑪⑫ 是收口。
