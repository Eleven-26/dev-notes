## 一、Mito 扫描一次查询要经过几道剪枝？

**本节要点**：答案不是「一道」，而是**三道从粗到细、组合使用**的剪枝。
Mito 的核心设计思想就是「避免不必要的工作」——每一道都在回答「这批数据能不能直接跳过」。

### 1.1 三级剪枝的顺序

据博客《GreptimeDB 存储引擎设计内幕》，一次扫描从**查询可见的数据**开始：当前的 memtable 和相关的 SST 文件；
它同时知道查询的**谓词和时间范围**，并用这些信息减少需要打开、解码和过滤的数据量。博客强调：

> 关键在于 Mito 并不依赖单一的剪枝机制，而是把**时间范围、row group 统计信息和索引**结合起来使用。

当前文档《存储引擎》把它总结为「从粗到细」的三步：

| 顺序 | 剪枝手段 | 剪掉的对象 | 代价 |
|---|---|---|---|
| ① | **时间范围裁剪** | 时间范围与查询不相交的**文件 / memtable** | 最低（无需打开 reader） |
| ② | **Row group min-max 统计** | 统计能证明无行匹配谓词的**整个 row group** | 低（读元数据即可） |
| ③ | **索引**（倒排 / 跳数 / 全文） | 统计无法处理的谓词所命中的 row group 或行 | 较高（要读 Puffin 里的索引数据） |

### 1.2 为什么是「组合使用」

因为三道剪枝各自解决不同粒度的问题，互补而非替代：

- 时间范围解决**粗粒度**：整个文件要不要打开；
- row group 统计解决**中粒度**：一个文件里哪几块要解码；
- 索引解决**选择性**：统计区分不了的谓词（例如「某列等于某个具体值」）交给索引。

⭐ 博客的收尾句很好地概括了这套设计——**时间范围跳过整个文件，min-max 统计信息跳过 row group，索引剪除具有选择性的谓词**。

![三道剪枝按代价从低到高依次收窄候选数据的过程](images/三级剪枝流程.svg)

图从上到下依次是查询可见数据、时间范围裁剪、row group min-max 与索引三道闸：每往下一道，候选集都更小，
但单次判断的代价更高，所以顺序不能颠倒——便宜的剪枝先做，能剪掉的数据就不必再交给更贵的机制处理。

## 二、时间范围剪枝为什么最廉价也最重要？

**本节要点**：因为它是唯一「**在打开 reader 之前**就能做」的剪枝，且正好命中时序查询最普遍的过滤条件——
时间。

博客的口径：

> Mito 首先从时间索引上的谓词中提取时间范围。那些**存储时间范围与查询范围不相交的文件和 memtable，在打开 reader 之前就可以被跳过**。对于时序数据来说，这通常是最廉价、也最重要的剪枝步骤。

当前文档《存储引擎》把它列为第 1 步，并同样强调：**如果文件和 memtable 的时间范围与查询时间范围不相交，就会在打开 reader 之前被跳过**；对于时间序列查询，这通常是成本最低且最有效的步骤。

⭐ 两条实用推论：

1. **查询一定要带上时间范围**。省略时间范围等于放弃最便宜的那道剪枝，
   扫描会退化到「把所有候选文件都当相关」。
2. **按时间分区 / 分窗口的收益是双份的**：写入侧 TWCS 按时间窗口组织文件，
   读取侧时间范围剪枝正好按时间窗口跳过文件——两者共用同一套「时间是主轴」的设计。

## 三、row group 的 min-max 统计能剪掉什么？

**本节要点**：它剪掉的是「统计上不可能匹配」的整块数据。代价很低，效果依赖数据的局部性。

博客给出的机制与例子：

> 接下来，Mito 使用 min-max 统计信息。如果某个 row group 的统计信息能够证明其中没有任何行可能匹配谓词，
> 那么这个 row group 就会被跳过。例如，**一个 `cpu` 最大值为 `0.6` 的 row group 不可能匹配 `cpu > 0.7`**。
> row group 统计信息比较粗粒度，但代价低廉，在数据具有局部性时效果很好。

这些统计来自哪里？官方文档《数据持久化与索引》说明：**Parquet 在每个 column chunk 的元数据中保存 row group 级列统计信息，例如最小值、最大值和 null 数量**；Page 元数据和可选的 column index 可以提供粒度更细的统计信息。

⭐ 为什么说「粗粒度但代价低廉」：

- **便宜**：只需读元数据即可判断，不必解码整块数据；
- **粗**：它只能回答「这块数据有没有可能匹配」，不能精确定位到行——所以还需要第三道索引；
- **依赖局部性**：如果数据在 row group 内分布很散（例如同一列里既有 0.1 也有 0.9），
  min-max 区间就会很宽，剪不掉任何东西。

⚠️ 这也解释了「建表时列怎么排、主键怎么选」为什么会影响查询：良好的局部性让 min-max 区间更窄、更可剪。

## 四、索引为什么放在 Puffin 文件里？

**本节要点**：因为要「跟着数据文件走」。把索引与 SST 元数据绑在一起管理，
才能在对象存储场景下实现「一起管理、一起缓存、一起跳过」。

博客的原文口径：

> 当统计信息还不够时，索引可以提供更具选择性的剪枝。索引是为一列或多列构建的辅助数据，
> 使得扫描在解码数据列之前就能排除更多的行或 row group。Mito 把索引数据存储在 **Puffin 文件**中。
> Puffin 是一种辅助文件格式，用于把索引数据放在 **SST 元数据旁边**，而不必塞进主 Parquet 数据文件内部。

当前文档《数据持久化与索引》进一步明确：

- **只有当某个 SST 存在「已配置且适用的索引输出」时**，GreptimeDB 才把这些索引写入**与该 SST 关联的 Puffin 文件**；
  **没有适用索引的 SST 不需要生成 Puffin 文件**；
- Puffin 是**索引 Blob 及其元数据的容器**，使不同索引结构可以**共用一个文件**。

⭐ 博客点出了它与对象存储的契合关系（这一段值得原文记住）：

> 这种设计非常契合对象存储：**数据文件和索引文件可以一起管理、在有用时一起缓存，并在元数据证明它们与某次查询无关时一起被跳过。**

也就是说，索引不是「另一个独立的系统」——它和 SST 是同一份 region 状态的一部分，
生命周期与 SST 对齐（SST 被 compaction 移除时，相关索引元数据也会被更新）。

⭐ 本机可以把「跟着数据文件走」这句话量出来：`information_schema.ssts_index_meta` 在这个库里有 4 行索引登记（跨两张表），
每一行的 `index_file_path` 都以 `.puffin` 结尾、`file_id` 与数据文件同名，`index_type` 登记为 `bloom_filter` 与 `fulltext_bloom`：

```sql
SELECT index_type, target_type, index_file_path, index_file_size
FROM information_schema.ssts_index_meta
WHERE table_dir LIKE '%<库名>%';
```

实测关键读数（同一张表、同一个数据文件）：`bloom_filter` 与 `fulltext_bloom` 两条登记的 `index_file_path` **指向同一个 `.puffin` 文件**，
`index_file_size` 都是 651；而执行计划里该文件的 `index_size` 也是 651、`size` 是 6877。三条读数对上，就同时证实了两件事：
**一个 Puffin 文件容纳多种索引结构**（两类索引共用一个文件，不是各写一个文件），以及**索引体积与数据体积分开记账**。

## 五、GreptimeDB 支持哪些索引类型？

**本节要点**：当前文档给出的索引家族是**倒排索引、跳数索引、全文索引**三类，
它们都以 Blob 形式存进 Puffin 文件。⚠️ 博客只给出了「索引」这一抽象层，具体类型以最新官方文档为准。

### 5.1 倒排索引（Inverted Index）

官方文档明确：**在 v0.7 版本中，GreptimeDB 引入了倒排索引来加速查询**。它的原理借自全文搜索：

- 概念映射：**「单词」**在 GreptimeDB 中指**时间线的列值**；**「文档」**指**包含多个时间线的数据段**；
- 作用：让 GreptimeDB **跳过不符合查询条件的数据段**，从而提高扫描效率；
- 结构：按列构建，每个列索引包含一个 **null bitmap、多个 posting bitmap 和一个 FST**；
  Blob footer 记录定位与解码各列索引所需的 offset、size 和元数据；
- **FST（Finite State Transducer）** 以紧凑格式存储「列值 → Bitmap 位置」的映射，并支持正则等复杂搜索；
  Bitmap 维护数据段 ID 列表，每个位表示一个数据段；
- 分段：一个 SST 被分割成多个索引数据段，每段行数由 `index.inverted_index.segment_row_count` 控制，
  **默认 `1024`**；值越小索引越精确、查询往往更好，但索引存储成本更高。

### 5.2 跳数索引与全文索引

- **跳数索引（skipping index）**：官方文档说明其**基于 bloom filter**；在建表中通过列选项
  `SKIPPING INDEX` 声明，用于加速对**稀疏数据**的查询。
- **全文索引（fulltext index）**：通过列选项 `FULLTEXT INDEX` 声明，仅适用于**字符串类型列**，
  用于加速全文搜索。从 **v0.14（2025-04）** 起官方持续增强全文检索能力。

⭐ 一句话区分：**倒排索引面向「稠密」的等值 / 正则类过滤，跳数索引面向「稀疏」数据，全文索引面向文本检索。**

### 5.3 索引与元数据的关系

- 博客：当 Mito 写出 SST 文件时，它可以同时为那些**能从选择性剪枝中获益的列**构建索引文件；
  **SST 元数据会记录存在哪些索引、各自覆盖哪些列**；
- 当前文档：在**扫描规划阶段**，Mito 会检查**查询谓词是否能够利用可用的索引**；
  索引的结果会与经过时间范围和 min-max 剪枝后**存活下来的 row group 相结合**。

⚠️ **查询规划依赖元数据**：如果某个谓词在写入时没有对应索引，规划阶段就用不上它——
这也意味着「事后补索引」通常要等数据被重新写出才生效。索引的配置语法与边界以最新官方文档为准。

### 5.4 索引怎么写进建表语句（实测语法与回填的默认参数）

**本节要点**：`SKIPPING INDEX` / `FULLTEXT INDEX` 是**列选项**——跟在列类型后面写，不是表级子句；
建完表 `SHOW CREATE TABLE` 会把没显式写的参数按默认值补齐，这些默认值就是调优入口。

建表时这样写（本机建表成功，返回 `affectedrows: 0`）：

```sql
CREATE TABLE w7g3.ix_demo (
  ts TIMESTAMP TIME INDEX,
  host STRING,
  cpu DOUBLE SKIPPING INDEX WITH (TYPE = 'BLOOM'),
  msg STRING FULLTEXT INDEX,
  PRIMARY KEY (host)
) ENGINE=mito
```

`SHOW CREATE TABLE` 回填出的列定义原文（含本机未写、由引擎补齐的默认参数）：

```sql
  "cpu" DOUBLE NULL SKIPPING INDEX WITH(false_positive_rate = '0.01', granularity = '10240', type = 'BLOOM'),
  "msg" STRING NULL FULLTEXT INDEX WITH(analyzer = 'English', backend = 'bloom', case_sensitive = 'false', false_positive_rate = '0.01', granularity = '10240'),
```

| 回填参数 | 实测默认值 | 读法与调优方向 |
|---|---|---|
| `type` | `BLOOM` | 跳数索引的实现方式，呼应上一小节「跳数索引基于 bloom filter」 |
| `granularity` | `10240` | 一个索引块覆盖多少行；块越小剪得越细，但索引越大 |
| `false_positive_rate` | `0.01` | bloom filter 误判率；调小更准、索引更大 |
| `analyzer` / `backend` / `case_sensitive` | `English` / `bloom` / `false` | 全文索引的分词器、后端与大小写；**默认后端就是 bloom** |

- ⚠️ 回填出来的 `granularity`（跳数 / 全文索引的分块行数）与 5.1 的 `index.inverted_index.segment_row_count`（倒排索引的分段行数）是**两个独立旋钮**，别把其中一个的默认值当成另一个的；
- ⚠️ **表级子句写法在本机不被接受**：`FULLTEXT INDEX ON (host)` 报 `Invalid SQL syntax: sql parser error: Cannot use keyword 'FULLTEXT' as column name.`；`SKIPPING INDEX ON (cpu)` 报 `Expected ',' or ')' after column definition, found: ON`。看到这两条原文就是写法问题，不是索引功能没装；
- ⚠️ `region`、`zone` 这类保留字不能直接当列名，报 `Cannot use keyword 'region' as column name`——本文示例查询里恰好用了 `region` 作标签列名，落地时要换名或加引号。

## 六、查询优化有哪些实践？EXPLAIN 怎么读？

**本节要点**：优化实践的本质是「让三道剪枝都能用上」；`EXPLAIN` 则是把「哪道剪枝生效了」量化出来的工具。

### 6.1 四条优化实践

| 实践 | 为什么有效 | 对应剪枝 |
|---|---|---|
| **谓词下推** | 把过滤条件下推到扫描器，才能驱动 row group 剪枝、索引应用与精确过滤 | ②③ |
| **时间范围裁剪** | 查询带上时间范围，最便宜的剪枝才有对象可剪 | ① |
| **只读需要的列** | 列式存储只读被投影的列，避免解码整行 | 减少 I/O |
| **主键（tag）等值过滤优先** | 主键决定排序与局部性，等值过滤最贴合「按时间线扫描」 | ①③ |

- 当前文档在 `EXPLAIN` 的 verbose 输出里明确把下推的谓词称为 **`filters`：下推到扫描器的静态物理谓词表达式**，
  并注明「这些谓词可能驱动 row group 剪枝、索引应用和精确过滤」；
- **`projection`：投影剪枝后的输出列名**则对应「只读需要的列」。

### 6.2 EXPLAIN / EXPLAIN ANALYZE 的读法

语法（官方 `EXPLAIN` 文档）：

```sql
EXPLAIN [ANALYZE] [VERBOSE] SELECT ...
```

- `EXPLAIN`：只看**执行计划**，`plan_type` 区分 `logical_plan` / `physical_plan`；
  `MergeScan` 负责合并多个 region 的查询结果，物理计划 `MergeScanExec` 的 `peers` 数组包含将要扫描的 region ID；
- `EXPLAIN ANALYZE`：**真正执行语句**，并测量每个计划节点耗时与输出行数等；
- `EXPLAIN ANALYZE VERBOSE`：提供更详细的信息，包含**扫描器指标**。

⭐ 诊断查询「剪得好不好」，看 verbose 里的**剪枝计数**（字段名以官方文档为准，下列为官方示例中的字段）：

| 指标 | 含义 |
|---|---|
| `rg_total` | 剪枝前考虑的 row group 数量 |
| `rg_minmax_filtered` | 被 min-max 剪枝过滤的 row group 数 |
| `rg_inverted_filtered` | 被倒排索引过滤的 row group 数 |
| `rg_bloom_filtered` | 被 bloom filter（跳数索引）过滤的 row group 数 |
| `rg_fulltext_filtered` | 被全文索引过滤的 row group 数 |
| `rows_before_filter` | 行级过滤前候选 row group 中的行数 |
| `pruner_cache_hit` / `pruner_cache_miss` | 构建文件范围时 pruner builder 缓存的命中 / 未命中 |

⚠️ 官方文档明确提醒：**verbose 模式下的扫描器指标是诊断文本，不是稳定的公开 API**，
可选的零值字段通常会被省略。因此不要把字段名写进自动化断言。

⚠️ 版本差异在字段名上是实打实的：本机 **1.2.1** 的 verbose 输出里**没有** `rg_inverted_filtered` / `rg_bloom_filtered` /
`rg_fulltext_filtered` 这三个字段，能读到的是 `num_sst_rows`、`prefilter_filtered_rows`、`rg_total`，
以及索引真正被读过时才出现的 `inverted_index_apply_metrics`、`fulltext_index_apply_metrics`、
`inverted_index_cache_hit/miss`、`fulltext_index_cache_hit/miss`、`rows_fulltext_filtered`。
第 7 节全部按本机实际字段名记录；跨版本对照前先跑一条 `EXPLAIN ANALYZE VERBOSE` 看字段还在不在。

### 6.3 实测：同一条谓词带不带时间范围，计数差多少

**本节要点**：造 3 个数据文件、每个 3000 行，同一条 `cpu > 0.7` 跑两次——带上时间范围只打开 1 个文件、
只留 1 个 row group、候选行 3000；不带就 3 个文件全开、候选行 9000。差多少全部打印在计划里，不用猜。

观测前有两个坑（都是本机报错原文）：

- 数据还留在 memtable 时 `files=0`、`rg_total=0`，三道剪枝没有对象可剪，读不出任何差异；
- HTTP SQL 接口不接受 `FLUSH`：`FLUSH TABLE w7g3.pq_demo` 与 `FLUSH TABLES w7g3.pq_demo` 都报
  `SQL statement is not supported, keyword: FLUSH`；本机改用管理函数把 memtable 落盘成 SST：

```sql
SELECT flush_table('w7g3.pq_demo');
```

落盘后这张表有 3 个数据文件（每次插入 3000 行后各落一次），`rows` 均为 3000、`size` 分别为 6813 / 6813 / 6814、
时间范围分别是 1780048800000–1780051799000、1780052400000–1780055399000、1780056000000–1780058999000，`index_size` 均为 0。

三条查询的读数（同一张表、同一个 region）：

| 计划里的读数 | A：时间范围 + `cpu > 0.7` | B：只有 `cpu > 0.7` | C：只有时间范围 |
|---|---|---|---|
| `files` / `file_ranges` | 1 / 1 | 3 / 3 | 1 / 1 |
| `rg_total` | 1 | 3 | 1 |
| `rows_before_filter` | 3000 | 9000 | 3000 |
| `prefilter_filtered_rows` | 2373 | 7119 | 字段未出现（0 值被省略） |
| `num_sst_rows`（= 输出行） | 627 | 1881 | 3000 |

- A 连跑 3 次、B 连跑 3 次，上表计数逐次一致（627 / 2373 / 3000 与 1881 / 7119 / 9000），只有耗时抖动；
- 换算是本机自洽的：A 侧 3000 - 2373 = 627；B 侧 9000 - 7119 = 1881，且 1881 = 627 + 627 + 627——
  时间范围这道剪枝省掉的正是另外 2 个文件的 6000 候选行（3000 × 2）；
- 谓词下推与列裁剪的原文（A 的输出）：`"filters": ["ts >= TimestampMillisecond(1780048800000, None)", "ts < TimestampMillisecond(1780052400000, None)", "cpu > Float64(0.7)"]`、`"projection": ["host", "cpu"]`——
  表里有 4 列，投影只剩被选中的 2 列，这就是上一节表里「只读需要的列」那一行的实证；
- ⚠️ 本机每个文件只有 1 个 row group（`rg_total` 等于文件数），min-max 统计没有第二块可剪，
  所以 `rg_minmax_filtered`、`rg_inverted_filtered`、`rg_bloom_filtered`、`rg_fulltext_filtered`、`pruner_cache_hit`
  这几个字段在全部 7 次输出里都没出现过——**按「零值字段被省略」解读，不能反推引擎没实现它们**；
- 统计缓存有实测痕迹：同一条查询第 1 次输出 `minmax_cache_miss=1`、`pruner_cache_miss=1`，第 2、3 次变成 `minmax_cache_hit=1`，而候选行计数不变；
- 索引那档子的代价可以称重：没声明索引的表 `size=6813`、`index_size=0`；对同样 3000 行、声明了跳数 + 全文索引的另一张表（region 1422）是 `size=6877`、`index_size=651`——多出的 64 字节数据与 651 字节索引就是「辅助数据跟着数据文件走」的体积形态，且数据文件与索引文件在同一目录里成对出现。

**图注**：上半是这张表落盘后的 3 个数据文件（`rows` 均 3000，`size` 为 6813 / 6813 / 6814，时间范围与上表逐一对应，`index_size` 全为 0），

## 七、两条记录落盘后：原始数据和索引各在哪？

**本节要点**：Mito 每次落盘写出**两个文件加一条 manifest 记录**——Parquet 放原始数据，Puffin 放索引，
manifest 用同一个 `file_id` 把两者登记成一对。查询时先看 manifest 里的时间范围与主键范围挑文件，
再用 row group 统计与 Puffin 索引决定「这一段要不要读」。

建表时 `id`、`name` 都是保留字，必须加双引号（本机不加时报 `Cannot use keyword 'id' as column name`）：

```sql
CREATE TABLE user_demo3 (
  ts TIMESTAMP TIME INDEX,
  "id" UInt32,
  "name" STRING,
  age UInt8,
  phone STRING INVERTED INDEX,
  addr STRING,
  hobby STRING INVERTED INDEX,
  remark STRING FULLTEXT INDEX,
  PRIMARY KEY ("id")
)
```

样本仍是本文约定的两条：主键 `id`，`phone` / `hobby` 建倒排索引，`remark` 建全文索引，`age`、`name`、`addr` 不建索引。
插入后必须落盘，否则数据还在 memtable，磁盘上既没有 Parquet 也没有 Puffin：

```sql
INSERT INTO user_demo3 (ts, "id", "name", age, phone, addr, hobby, remark) VALUES
('2026-11-05 10:00:00', 1, '张三', 18, '13700000000', '广东省深圳', '打游戏，爬山', '这是张三备注'),
('2026-11-05 10:00:01', 2, '李四', 19, '13800000000', '广东省深圳', '唱、跳、rap、打蓝球', '这是李四备注');

SELECT flush_table('public.user_demo3');
```

### 7.1 建表与落盘：一次 flush 写出几个文件

这张表落在 region `1029`，一次 flush 之后的目录原文（`ls -l`，省略 manifest 目录）：

```text
1029_0000000000/fafced4d-b927-4411-b8f6-11e66bd731b8.parquet        6933
1029_0000000000/index/fafced4d-b927-4411-b8f6-11e66bd731b8.puffin    856
```

| 落盘产物 | 大小 | 存什么 |
|---|---|---|
| `<file_id>.parquet` | **6933 B** | 2 行 × 8 列的原始数据，1 个 row group |
| `index/<file_id>.puffin` | **856 B** | 2 个倒排索引 + 1 个全文 bloom |
| `manifest/000…01.json` | — | 把上面两个文件按同一个 `file_id` 成对登记，并记下时间范围与主键范围 |

manifest 里这条 `Edit.files_to_add` 的原文读数：

| 字段 | 原文值 | 读法 |
|---|---|---|
| `file_id` | `fafced4d-…` | 数据文件与索引文件**同名**，这就是两者的第一层绑定 |
| `time_range` | `1793872800000` – `1793872801000` | 即 `10:00:00`–`10:00:01`，供①时间范围剪枝 |
| `primary_key_min` / `max` | `AQAAAAE=` / `AQAAAAI=` | base64 解出 1 与 2，即主键区间 |
| `num_rows` / `num_row_groups` | `2` / `1` | 2 行只切了 1 个 row group |
| `available_indexes` | `["InvertedIndex","FulltextIndex"]` | 这个 SST 上有哪几类索引 |
| `indexes` | 列 `4` 倒排、列 `6` 倒排、列 `7` 全文 | 每个索引挂在哪一列 |
| `index_file_size` | `856` | 与上面 `ls` 的 Puffin 大小逐字节对上 |

⭐ 一次 flush 的产物是「**1 个数据文件 + 1 个索引文件 + 1 条 manifest 记录**」，
不是「数据文件里夹着索引」，也不是「索引单独一个库」。

### 7.2 原始数据：一个 SST 就是一份 8 列的 Parquet

列号不是猜的，建表 manifest 的 `column_metadatas` 与 `primary_key: [1]` 给出了完整映射：

| column_id | 列 | 角色 | 索引 |
|---|---|---|---|
| 0 | `ts` | Time Index | 无（时间范围走文件级元数据） |
| 1 | `id` | 主键（Tag） | 无 |
| 2 | `name` | Field | 无 |
| 3 | `age` | Field | 无 |
| 4 | `phone` | Field | 倒排 |
| 5 | `addr` | Field | 无 |
| 6 | `hobby` | Field | 倒排 |
| 7 | `remark` | Field | 全文 |

一个 6933 B 的文件里装的是「2 行 × 8 列 = 16 个值」，按列切开成 8 个 column chunk；
manifest 里 `max_row_group_uncompressed_size` 为 **610 B**，也就是这 2 行的列数据本体只有 610 B，
其余约 6.3 KB 是列块头、page 元数据与文件 footer。⚠️ 小文件里**元数据占大头**，
这个比例会随行数增长而降下去，别拿单条记录的文件大小去推算存储成本。

⚠️ **行在磁盘上同样不存在**：一条记录只是 8 个列块里同一个行号上的 8 个值。
但 Parquet 的每个 column chunk 自带 **min / max / null count** 统计，这就是②row group min-max 剪枝的数据来源。

### 7.3 索引数据：一个 Puffin 装下两种索引、三个列索引

先看 Puffin 文件的 footer（文件尾部的 JSON 原文，按偏移截取）：

| Blob 类型 | `offset` | `length` | 附加属性 |
|---|---|---|---|
| `greptime-inverted-index-v1` | 4 | **426** | 无 |
| `greptime-fulltext-index-bloom-7` | 430 | **86** | `fulltext_config: {"analyzer":"English","case_sensitive":false}` |

两类索引共用一个文件、首尾相接：倒排占 `[4, 430)`，全文 bloom 占 `[430, 516)`，剩下的 340 B 是 Puffin 头尾与对齐。
再看 `information_schema.ssts_index_meta` 里同一个 `file_id` 的三行登记：

| `index_type` | 列 | `blob_size` | `meta_json` 关键读数 |
|---|---|---|---|
| `inverted` | `phone`（4） | **107** | `base_offset: 0`、`bitmap_type: Roaring`、`fst_size: 63`、`null_bitmap_size: 8`、`segment_row_count: 1024`、`total_row_count: 2` |
| `inverted` | `hobby`（6） | **183** | `base_offset: 107`、`fst_size: 139`、`null_bitmap_size: 8`、`segment_row_count: 1024` |
| `fulltext_bloom` | `remark`（7） | **86** | `bloom_filter_size: 64`、`rows_per_segment: 10240`、`segment_count: 1`、`analyzer: English` |

⭐ 三个索引本体 107 + 183 + 86 = 376 B，加上倒排的头部与两个 8 B 的空位图，正好对上 footer 里 426 + 86 这两段；
**同一份数据文件的两个列索引不是两个文件，而是同一个 Puffin 里的两个 blob**。
⭐ 两个粒度旋钮在原文里都能看到：倒排按 `segment_row_count = 1024` 行切段，全文 bloom 按 `rows_per_segment = 10240` 行切段——
2 行数据在两边都只够 1 段，这正是小数据上索引剪不细的原因（见 7.7）。

### 7.4 两者靠什么连：同一个 `file_id` 加上 `(主键, 时间)` 这组行身份

和 MySQL「二级索引叶子存主键、再回表」不同，Mito 里**没有「索引项 → 行号」这种指针**。两层连接是：

- **文件级**：manifest 的一条 `files_to_add` 同时写 `file_id`、`time_range`、`primary_key_min/max`、`indexes`、`index_file_size`，
  查询规划据此知道「这个 SST 有没有索引、索引用在哪列、文件覆盖哪段时间与哪段主键」；
- **行级**：行身份是 `(PRIMARY KEY, TIME INDEX)`，即这里的 `(id, ts)`。倒排 / bloom 回答的是「这个 SST 里**哪些行可能匹配**」，
  命中后仍要按列解压、再用精确谓词逐行判断；同一 `(id, ts)` 出现多份时，按 **sequence** 取最新的一份。

扫描计划里的 `files` 数组把两个文件并排摆出来，是这条绑定最直接的证据：

```text
"files": [{"file_id":"…/fafced4d…","time_range_start":"1793872800000::Millisecond",
           "time_range_end":"1793872801000::Millisecond","rows":2,"size":6933,"index_size":856}]
```

`size` 与 `index_size` 分开记账：**一个文件是多少原始数据、它旁边挂着多少索引**，在计划里就能核。

![两条记录在 Mito 里的落点：Parquet 按列存值、Puffin 按 blob 存索引、manifest 用同一个 file_id 成对登记](images/两条记录在Mito的Parquet与Puffin.svg)

图里左栏是 6933 B 的 Parquet：2 行 × 8 列切成 8 个列块，每个列块自带 min/max 统计；中栏是 856 B 的 Puffin：
倒排 blob 426 B 里装着 `phone` 107 B 与 `hobby` 183 B，全文 bloom 86 B 按 10240 行一段；右栏列出三条查询在计划里的读数，
`index_size` 与 `size` 始终分开记账。底部的 manifest 条说明两者靠同一个 `file_id` 绑定，而不是靠目录约定。

### 7.5 三次查询各走哪条路（外加五条对照）

同样是这张 2 行、1 个 SST 的表，`EXPLAIN ANALYZE VERBOSE` 的读数如下（`rows_before_filter` 是索引前候选行，
`num_sst_rows` 是真正从 SST 读出的行，输出列是去重后的最终行数）：

| 查询 | `files` / `rg_total` | `rows_before_filter` | `num_sst_rows` | 输出 | 计划里的索引证据 |
|---|---|---|---|---|---|
| `phone = '13700000000'` | 1 / 1 | 2 | **1** | 1 | `inverted_index_cache_miss 1`；`apply 2.196786ms`、`blob_read_bytes 426`、`total_bytes 1278`、`total_ranges 3` |
| `hobby = '打游戏，爬山'` | 1 / 1 | 2 | **1** | 1 | `inverted_index_cache_miss 1`；`apply 74.906µs`、`blob_read_bytes 426`、`total_bytes 852`、`total_ranges 2` |
| `matches_term(remark, '这是张三备注')` | 1 / 1 | 2 | 2 | 1 | `fulltext_index_cache_hit 1`（整串命中，bloom 放行后逐行过滤） |
| `matches_term(remark, '张三')` | 1 / 1 | 2 | **0** | **0** | `rows_fulltext_filtered 2`；`apply 1.346614ms`、bloom `86 B`、`total_ranges 1` |
| `remark LIKE '%张三%'` | 1 / 1 | 2 | 2 | 1 | **无**（逐行过滤，索引没参与） |
| `remark = '这是张三备注'` | 1 / 1 | 2 | 1 | 1 | **无**（等值不走全文索引） |
| `phone LIKE '137%'` | 1 / 1 | 2 | 2 | 1 | **无**（前缀 LIKE 不剪枝） |
| `age = 18` | 1 / 1 | 2 | 1 | 1 | **无**：没有索引也能把 `num_sst_rows` 压到 1 |
| `"id" = 1` | 1 / 1 | 2 | 1 | 1 | **无**：主键靠合并去重，不是索引 |

（`remark =` 与 `phone LIKE` 两行在与 `user_demo3` 同构、同样 2 行 1 个 SST 的 `user_demo4` 上复测，读数逐项一致。）

⭐ 这张表要读出四件事：

1. **只有 `=` 加倒排索引时，计划里才出现 `inverted_index_apply_metrics`**。`LIKE` 无论是前缀还是中间子串都不出现——
   倒排索引给的是「这个值在不在」，不是「这个串包不包含」；
2. **`num_sst_rows` 不能当「索引生效」的证据**：`age = 18` 没建索引也压到 1，那是 page 级统计 `prefilter_filtered_rows` 干的；
   判断索引有没有参与，只看 `inverted_index_*` / `fulltext_index_*` 这组字段；
3. **全文索引是「分词后的 token 命中」，不是子串检索**。默认 `analyzer = English` 把整句中文当成一个 token，
   所以整串 `这是张三备注` 能命中，而 `张三` 这个词不在 token 表里，bloom 直接回「这一段肯定没有」，
   输出 0 行——可 `LIKE '%张三%'` 却能返回 1 行。同一列、同一份数据，两个谓词给出相反结论；
4. **2 行数据只切 1 个 row group、两边索引都只有 1 段**，三道剪枝里②③的「选多少」还体现不出来，
   它们的价值要等文件与分段变多才看得见（7.6 与第 6.3 节）。

### 7.6 写一条新记录：追加文件，同主键同时刻靠序列覆盖

先追加第三条 `id=3`、时间 `10:00:02` 的记录再 flush，目录里多出一对文件：

```text
97720d83-b991-489e-9fed-afe2f61722aa.parquet         6803   manifest sequence 3, num_rows 1
index/97720d83-b991-489e-9fed-afe2f61722aa.puffin     744
```

此时查 `phone = '13900000000'`（只有新文件里那一行命中），索引第一次剪掉了**整个文件**：

| 读数 | 值 | 读法 |
|---|---|---|
| `files` / `rg_total` | 2 / 2 | 打开 2 个文件、2 个 row group |
| `rows_before_filter` | 3 | 2 + 1，候选行 |
| `num_file_ranges` | **1** | 2 个文件范围里只有 1 个活下来 |
| `num_sst_rows` | **1** | 被剪掉的那个文件一行都没解压 |
| 输出 | 1 | 命中的新记录 |
| `apply` | **2.870856ms** | 冷启动读 Puffin：`blob_read_bytes 314`、`total_bytes 942`、`total_ranges 3` |

再把 `id=1`、`ts=10:00:00` 用新手机号重写一遍（同主键、同时间），落盘后是第三个 SST：

```sql
INSERT INTO user_demo3 (ts, "id", "name", age, phone, addr, hobby, remark) VALUES
('2026-11-05 10:00:00', 1, '张三', 18, '13600000000', '广东省深圳', '打游戏，爬山', '这是张三备注');
```

`phone = '13700000000'`（旧值）返回 **0 行**，`phone = '13600000000'`（新值）返回 **1 行**，
而 `"id" = 1` 仍只返回 **1 行**。三条读数背后的物理事实：

- 磁盘上有 **3 个 Parquet + 3 个 Puffin**，物理行数合计 4 行（2 + 1 + 1），一个文件都没删；
- 旧值仍躺在第一个 SST 里。查旧手机号时计划读到 `dedup_metrics.num_unselected_rows: 1`，
  FilterExec 的 `output_rows: 0`——**是去重把旧版本筛掉，不是删除**；
- 去重键就是 `(id, ts)`，胜负由 `sequence` 决定：manifest 里三次 flush 的 `sequence` 分别是 `2`、`3`、`4`；
- 时间范围剪枝同样只在文件级起效：`ts >= '2026-11-05 10:00:02'` 只打开 **1** 个文件（`rg_total 1`、候选 1 行），
  而 `ts >= '2026-11-05 10:00:00'` 打开 **3** 个文件（`rg_total 3`、候选 4 行）——①的收益是整文件级别的。

⚠️ 所以「改一条」在 Mito 里等于「**追加一个文件**」：旧版本要等 compaction 把多个 SST 合并时才会真正消失。
按时间窗组织 compaction（TWCS）既是为了合并小文件，也是旧版本被回收的时机。

### 7.7 本产品做不到什么

- **倒排索引只服务等值**：前缀 `LIKE '137%'` 与子串 `LIKE '%爬山%'` 都不带 `inverted_index_*` 指标，
  计划里 `num_sst_rows` 等于全部行——想按前缀 / 子串查，索引帮不上忙；
- **全文索引不是子串搜索**：`matches_term` / `@@` 走的是分词后的 token 与 bloom，中文默认 `English` 分词器不切词，
  短关键词会被 bloom 判成「肯定没有」而直接返回 0 行；整串查询能命中，`LIKE` 也能命中但全扫。
  ⚠️ 同一个短关键词在另一张同 DDL 但分成 3 个 SST 的表上返回过 1 行——bloom 的文件级误判会让结果随文件划分而变，
  这条谓词不能当作稳定的子串检索；
- **索引粒度受段大小限制**：倒排 `segment_row_count = 1024`、全文 `rows_per_segment = 10240`，
  数据少时只有 1 段，只能回答「整段可能有没有」，剪不到行；
- **索引在写入时构建**：没在 `CREATE TABLE` 里声明的列，查询规划阶段就没有可用索引，
  事后补索引通常要等数据重写（对应 5.3 的元数据依赖）；建表时写错的写法请回到 5.4 对照报错原文；
- **更新与删除都靠追加**：同一 `(id, ts)` 的新版本以新文件落盘，旧版本驻留到 compaction；没有原地改写的路径；
- **没有「覆盖索引」这个概念**：列式存储本来就只读投影列，索引解决的是「跳过哪些段」，不是「不回表」。

## 使用：用一个例子走一遍三级剪枝

取博客里的那条查询：

```sql
SELECT ts, cpu
FROM host_metrics
WHERE host = 'host-a'
  AND region = 'us-east'
  AND ts >= '2026-05-29 10:00:00'
  AND ts < '2026-05-29 11:00:00'
  AND cpu > 0.7;
```

逐级走一遍（这一步的每一跳都对应一个已存在的结构，不是假想流程）：

| 步骤 | 用到什么 | 剪掉什么 | 依据 |
|---|---|---|---|
| ① 时间范围 | `ts >= …` 与 `ts < …` 两个时间索引谓词 | 时间范围与 `[10:00, 11:00)` 不相交的**文件与 memtable** | 文件级元数据里的**时间范围** |
| ② min-max | `cpu > 0.7` 与主键等值过滤 | **`cpu` 最大值 ≤ 0.7 的 row group**（如最大值为 `0.6` 的块） | row group 的**列统计** |
| ③ 索引 | `host` / `region` 等值 + `cpu` 谓词 | 统计区分不了的 row group / 行 | **Puffin** 中的倒排 / 跳数 / 全文索引 |
| ④ 精确过滤 | 剩余数据 | 逐行应用精确谓词 | 扫描器在解码后执行精确过滤 |

⭐ 读这段要走出的三个结论：

1. **顺序有意义**：① 最便宜、先做；能靠 ① 解决的绝不留给 ③；
2. **时间范围是「入场券」**：没有它，②③ 的候选集就是「全部文件」，代价成倍；
3. **`cpu > 0.7` 这类范围谓词**在 ② 有效的前提是 `cpu` 在 row group 内**有局部性**；
   如果是低选择性或分布很散的列，就要靠 ③ 的索引。

## 延伸追问

- **三级剪枝一定会全跑一遍吗？** → 不会。它们是「按代价递增依次尝试」的关系：
  ① 能剪掉就不必开 reader；② 能证明不匹配就不必读索引；③ 只在统计不够时才用。
- **min-max 统计和索引有什么区别？** → 统计是 Parquet 自带的 row group 级元数据（min / max / null 数），
  便宜但粗；索引是为**有选择性**的谓词额外构建的辅助数据，存在 Puffin 里，更细但更贵。
- **为什么索引要放 Puffin 而不是塞进 Parquet？** → 为了「跟着 SST 走」：数据文件与索引文件可以
  一起管理、一起缓存、一起跳过，契合对象存储场景。
- **倒排索引里的「数据段」是什么粒度？** → 把一个 SST 分割成多个**等行数**的数据段，
  行数由 `index.inverted_index.segment_row_count` 控制，**默认 `1024`**；调小更精确但索引更大。
- **append-only 表在扫描时有什么不同？** → 博客说明：对可能含更新 / 删除的表，Mito 会按序列信息与
  操作类型合并去重；对 append-only 表，当查询不要求输出有序时间线时，**扫描可以省去较多的排序工作**。
- **`EXPLAIN` 输出里哪些信号说明「剪枝没生效」？** → 关注 row group 相关计数：
  若 `rg_total` 很大而各 `rg_*_filtered` 接近 0、`rows_before_filter` 很高，
  说明谓词可能没能利用统计或索引；具体字段以官方文档为准。
- **索引类型会随版本变化吗？** → 会。倒排索引自 v0.7 引入，全文检索在 **v0.14（2025-04）** 起持续增强，
  向量索引等仍在演进中。⚠️ 博客（2022-12）只给出「索引」这一抽象层，
  具体类型与配置以最新官方文档为准。
- **本机为什么读不出 min-max 剪掉的块数？** → 落盘后每个数据文件只有 1 个 row group，`rg_total` 恰好等于被打开的文件数，
  第二块不存在，就没有「这块被统计剪掉」可观测；要把这道剪枝拉开，得让单文件行数超过 row group 的大小（读数见第 6.3 节）。
- **引擎回填的索引默认值可信吗？** → `SHOW CREATE TABLE` 回填的是当前表定义原文，本文实测到 `granularity = '10240'`、
  `false_positive_rate = '0.01'`、全文后端 `backend = 'bloom'`；但不同版本默认值可能调整，跨版本引用前重新跑一次 `SHOW CREATE TABLE`。
- **想让查询用上索引，还得做什么？** → 先把数据落盘成 SST：memtable 阶段 `files=0`，索引没有载体，
  本文用 `SELECT flush_table('<库>.<表>')` 落盘；`FLUSH TABLE` 语句在该接口下不被支持。
