## 一、一个库文件里到底有什么？

**本节要点**：只有一个文件（可选加 `-wal`、`-shm`），里面是**等长的页**。
页长在库创建时定下，之后不可改——要改只能重建库。理解这一点，才能理解为什么
「删数据不缩文件」「改页大小要 VACUUM」这些现象。

### 1.1 文件的整体构成

![100字节头与B树页的布局](images/100字节头与B树页的布局.svg)

六段从上往下是文件里真实存在的顺序：头 100 字节、第 1 页的特殊身份、表页、索引页、溢出页、空闲页。看中间两段的「cell 指针数组从页尾往前长」——这就是页内空间耗尽时页分裂的直接原因。

| 部分 | 内容 | 可变性 |
|---|---|---|
| 文件头 | 100 字节，magic + 页大小 + 页数 + schema cookie + 版本号 | 随写入更新 |
| 页 1 | 头部之后的剩余部分：`sqlite_schema` 的根页 | 建表/改表时变 |
| 表 B 树页 | 页类型 5（内部）/ 13（叶子），cell 里装整行 | 随数据变 |
| 索引 B 树页 | 页类型 2（内部）/ 10（叶子），cell 里装键 + 页号 | 随索引变 |
| 溢出页 | 装不进一页的行的后半段 | 随长字段变 |
| freelist | 已释放、可复用的页 | 随删除/分裂变 |

### 1.2 页大小为什么建库后改不了

页大小写进文件头（偏移 16，2 字节；值 1 表示 65536），同时决定了：

- 每一页的边界在哪里（所有页号都是「第 n 个 4 KiB」）
- 溢出阈值怎么算（见第四节）
- B 树每个节点能放多少个 cell（也就是树的高度）

所以改页大小 = 把所有页重新排一遍 = 重建库。SQLite 的做法是：`PRAGMA page_size`
只对**尚未写入过**的新库生效，已有库要配合 `VACUUM`（`VACUUM INTO` 则生成新库，
可以用新页大小）。

| 场景 | 页大小怎么变 |
|---|---|
| 新建库 | `PRAGMA page_size=8192` 之后建表，立即生效 |
| 已有库 | 改 `page_size` 后 `VACUUM`；或 `VACUUM INTO 'new.db'` 换页大小 |
| WAL 模式 | 改页大小前要先切回 rollback journal，否则报错 |

## 二、100 字节的文件头每一段是什么？

**本节要点**：这个头不是「元数据摆设」，它保存了**恢复时必须先读到的信息**：
页大小、页数、schema 版本、以及「这份文件是不是被完整写过」。逐字段读一遍，
后面看 `dbstat`、看损坏、看迁移都会用到。

| 偏移 | 长度 | 内容 | 用途 |
|---|---|---|---|
| 0 | 16 | `SQLite format 3\0` | 认文件；不对就是 `SQLITE_NOTADB` |
| 16 | 2 | 页大小（1 表示 65536） | 所有页号的换算基准 |
| 18 | 1 | 写版本（1 = journal，2 = WAL） | 决定能否被老版本打开 |
| 19 | 1 | 读版本 | 同上 |
| 20 | 1 | 每页保留字节数 | 加密/扩展用，通常 0 |
| 21 | 1 | 负载分数（最大） | 页内 payload 上限的比例 |
| 22 | 1 | 负载分数（最小） | 同上 |
| 23 | 1 | 叶子负载分数 | 同上 |
| 24 | 4 | 文件变更计数器 | 每次事务提交 +1，用于检测热 journal |
| 28 | 4 | 数据库页数 | 与文件长度交叉校验 |
| 32 | 4 | 第一个 freelist trunk 页号 | 空闲链入口 |
| 36 | 4 | freelist 页总数 | 与 `freelist_count` 对应 |
| 40 | 4 | schema cookie | schema 变了就 +1，用来让缓存的计划失效 |
| 44 | 4 | schema 格式号 | 1~4，4 表示支持降序索引等 |
| 48 | 4 | 默认页缓存大小 | 建库时的提示值 |
| 52 | 4 | 最大 payload 分数 | 64 |
| 56 | 4 | 最小 payload 分数 | 32 |
| 60 | 4 | 叶子 payload 分数 | 32 |
| 64 | 4 | 文件变更计数器（in-header） | 与 24 配合 |
| 92 | 4 | version-valid-for | 校验 24/92 一致性 |
| 96 | 4 | 写入此库的 SQLite 版本号 | 迁移与诊断用 |

⭐ 两个最实用的字段：

- **偏移 24（文件变更计数器）**：它在每次提交时 +1。崩溃恢复用它判断
  「这份 journal 是不是属于当前这个文件版本」，对不上就不能直接回滚。
- **偏移 96（写入版本号）**：比如 3054001 对应 3.54.1。查「这个库是哪个版本写的」
  不用连库，读 4 个字节即可。

## 三、B 树页的布局：cell 指针数组为什么从页尾往前长？

**本节要点**：一页里同时有两种生长方向——**cell 内容从头往后长，cell 指针数组从尾往前长**。
两者相遇时页就满了，需要分裂。这个设计让「按 key 有序插入」只改指针数组，不用搬内容。

### 3.1 页内布局

| 位置 | 内容 |
|---|---|
| 页头（叶子 8 字节 / 内部 12 字节） | 页类型、第一个空闲块、cell 数、cell 内容起始偏移、碎片字节数、（内部页）最右子页号 |
| cell 指针数组 | 每 cell 2 字节偏移，**从页尾向页头方向增长** |
| 空闲区 | 指针数组与 cell 内容之间的空地 |
| cell 内容区 | 从页头之后向页尾方向增长 |
| 空闲块链 | 页内碎片（被删 cell 留下的洞），按偏移串成链 |

### 3.2 cell 里装什么

| 页类型 | cell 结构 |
|---|---|
| 13（表叶子） | 负载长度（varint）+ rowid（varint）+ 负载 + 溢出页号（可选） |
| 5（表内部） | 子页号（4 字节）+ 最大 rowid（varint） |
| 10（索引叶子） | 负载长度 + 负载（键 + rowid）+ 溢出页号（可选） |
| 2（索引内部） | 子页号 + 负载（键） |

⭐ 注意表内部页装的是「最大 rowid」而不是整行：内部页只负责导航，
所以即使行很大，内部页也能装很多子页——这是 B 树高度能压到 3~4 层的原因。

### 3.3 本机实测的页数

| 项 | 读数 |
|---|---|
| 插入 10 万行，每行约 88 字节负载 | 2159 页 / 8 843 264 字节 |
| 平均每页承载 | 约 46 行 |
| `dbstat` 汇总 | 2159 页 / 8 843 264 字节（与上一致，说明没有溢出页） |

⚠️ 「平均每页 46 行」远低于理论值（4 KiB / 88 ≈ 46）——说明这一批数据几乎把页填满了，
没有明显碎片。若看到平均每页只有十几行，就该怀疑页内碎片或行长差异过大。

## 四、一行太大时会发生什么？

**本节要点**：超过阈值后，行的一部分被移到**溢出页链**上。代价不是「大字段慢」，
而是「**跨页了才慢**」——每多一页就多一次 I/O，而这次 I/O 往往不在同一个页缓存槽里。

### 4.1 阈值怎么算

![溢出页与负载阈值](images/溢出页与负载阈值.svg)

五个格子从左到右是一条计算链：先算可用空间，再减去固定开销得到表叶子的阈值，然后分「装得下」与「装不下」两条路。最后那个代价格子是重点：溢出不是错误，只是多一次页访问。

表叶子页的局部负载上限（简化形式）：

```text
usable = page_size − reserved_bytes        -- 本机 4096 − 0 = 4096
X      = usable − 35                       -- 表叶子页的阈值
若 payload ≤ X：全部留在页内
否则：页内留 M 字节，其余进溢出页链（M 由 4.3 节的公式按 usable 算出）
```

索引页的阈值不同（用 `usable − 12` 一类），因为索引 cell 有额外头部。

### 4.2 怎么在库里看到溢出页

```sql
-- 每页的归属：表/索引名、页类型、占用字节
SELECT name, pagetype, count(*) AS pages, sum(pgsize) AS bytes
FROM dbstat
GROUP BY name, pagetype
ORDER BY bytes DESC;
```

`dbstat` 的 `pagetype` 会直接标出 `overflow`，所以「有多少页是被长字段吃掉的」
是一个可以直接查的整数，不需要猜。

### 4.3 三个可操作的结论

1. **长 TEXT / BLOB 尽量别和热字段放同一张表**。一行变长，同行其他列也一起被推到溢出页，
   热查询会连带读冷数据。
2. **别用 `SELECT *`**。溢出页是按需读的，但 `SELECT *` 一定会触发它。
3. **阈值随页大小变**。把页从 4 KiB 改到 8 KiB，阈值也翻倍，同样一行可能不再溢出——
   这是换页大小唯一确定的收益。

## 五、删除了为什么不缩文件？

**本节要点**：删除只把页标成「可复用」，文件长度不变。这是有意的设计：
复用比归还便宜得多，而且归还意味着要移动页、改所有指向它的父页指针。

### 5.1 本机实测的三步

![删除与VACUUM的空间账](images/删除与VACUUM的空间账.svg)

三行是同一次实验的三个时点：插入、删一半、VACUUM。第二行是重点——页数和文件大小一个字节都没变，只有 freelist 动了。第三行才是真正把空间还回去的样子。

| 时点 | page_count | freelist_count | 文件大小 |
|---|---|---|---|
| 插入 10 万行 | 2159 | 0 | 8 843 264 |
| 删掉奇数 id（5 万行） | 2159 | 1 | 8 843 264 |
| `VACUUM` 后 | 1113 | 0 | 4 558 848 |

⚠️ 注意 `freelist_count` 只涨了 1：删掉一半**行**并不等于释放一半**页**，
因为被删的行还留在页里，页里还有别的行。只有当一页上的行全被删掉，
这一页才进 freelist。要真正回收，得让页整体空出来或 VACUUM。

### 5.2 freelist 的结构

- trunk 页：页头之后第一个 4 字节是「下一个 trunk 页号」，其余是叶子页号列表
- 叶子页：整页可自由使用，不进链
- 文件头偏移 32/36 记录入口与总数

所以 `freelist_count` 是**可直接查询的空闲页数**，不是估算值：

```sql
PRAGMA freelist_count;   -- 空闲页数
PRAGMA page_count;       -- 总页数
-- 碎片比例 ≈ freelist_count / page_count
```

### 5.3 什么时候该 VACUUM

| 条件 | 该不该 VACUUM |
|---|---|
| `freelist_count / page_count` > 10% | 该 |
| 刚删了大量历史数据（超过一半） | 该 |
| 频繁小删小插 | 不必，freelist 会被复用 |
| 库在 WAL 模式且正被读 | 会等锁，安排在低峰 |
| 设备剩余空间 < 库大小 | 不能直接 `VACUUM`（要临时空间），用 `VACUUM INTO` 到外部 |

## 六、VACUUM 做了什么？

**本节要点**：`VACUUM` 不是「整理碎片」，是**把整个库读出来、按紧凑顺序写进一个新库、
然后替换**。所以它需要一份等大的临时空间，且全程持有写锁。

### 6.1 三个动作

1. 建一个临时库（页大小可用当前设置）
2. 按 B 树顺序把每张表、每个索引重建进临时库（页填满，无碎片，freelist 为空）
3. 用临时库替换原文件，并把文件变更计数器推进

### 6.2 本机读数与代价

| 项 | 读数 |
|---|---|
| 10 万行库 VACUUM（原地） | 199.9 ms |
| 页数 | 2159 → 1113 |
| 文件 | 8 843 264 → 4 558 848 字节 |
| 需要临时空间 | 约等于最终库大小 |

⭐ `VACUUM INTO` 是同一套逻辑，但产物写到指定路径（103.4 ms，比原地 VACUUM 快一半，
因为不用替换文件）。它同时是**在线备份**的首选，见 [备份恢复与迁移.md](备份恢复与迁移.md)。

### 6.3 三个容易踩的点

- **VACUUM 会改 rowid 顺序吗？** 不会改 rowid 值，但会改物理顺序（页内聚簇更紧）。
- **VACUUM 会重建索引吗？** 会，全部重建，所以索引很多的库 VACUUM 更慢。
- **VACUUM 能做「改页大小」吗？** 能，这是改页大小的唯一途径；`VACUUM INTO` 更安全。

## 使用：五条命令把空间账算清

**本节要点**：空间问题不要凭感觉。下面五条命令能回答「库多大、空多少、谁占的、
有没有溢出、要不要重建」，且都能在只读连接上跑（除最后一条）。

### 使用一：SQL 侧的五个查询

```sql
-- 1. 库有多大（页数与字节）
PRAGMA page_count;
PRAGMA page_size;
SELECT (SELECT * FROM pragma_page_count()) * (SELECT * FROM pragma_page_size()) AS bytes;

-- 2. 空了多少（碎片比例）
PRAGMA freelist_count;

-- 3. 谁占的（按表/索引聚合）
SELECT name, sum(pgsize) AS bytes, count(*) AS pages
FROM dbstat GROUP BY name ORDER BY bytes DESC LIMIT 20;

-- 4. 有没有溢出页
SELECT name, count(*) FROM dbstat WHERE pagetype = 'overflow' GROUP BY name;

-- 5. 顺带确认没有损坏（顺手，但比 integrity_check 快得多）
PRAGMA quick_check;
```

### 使用二：CLI 侧（装了 `sqlite3` 的环境或容器）

```bash
sqlite3 app.db ".dbinfo"                 # 页大小、页数、freelist、schema 版本
sqlite3 app.db "SELECT * FROM dbstat LIMIT 5;"
sqlite3 app.db "VACUUM INTO '/tmp/copy.db';"   # 紧凑副本，顺便当备份
```

本机没有 `sqlite3` CLI（实测 `which sqlite3` 为空），上面两条走容器或装了 CLI 的环境；
等价查询已在上面的 SQL 侧给出。

### 使用三：Go 里读这几个数

```go
func spaceReport(db *sql.DB) (map[string]int64, error) {
    out := map[string]int64{}
    for _, p := range []string{"page_size", "page_count", "freelist_count"} {
        var v int64
        if err := db.QueryRow("PRAGMA " + p).Scan(&v); err != nil {
            return nil, err
        }
        out[p] = v
    }
    out["bytes"] = out["page_size"] * out["page_count"]
    return out, nil
}
```

### 判读表

| 读数 | 正常 | 要处理 |
|---|---|---|
| `freelist_count / page_count` | < 10% | > 10% → 计划 VACUUM |
| 平均每页行数 | 与行长匹配 | 只填了 1/3 → 页内碎片或行长差异大 |
| `pagetype='overflow'` 页数 | 0 或占比很小 | 占比 > 20% → 长字段拖累，考虑拆表 |
| 文件大小 vs `page_count × page_size` | 相等 | 不等 → 有 `-wal` 未 checkpoint，或读到旧文件长度 |

⚠️ 最后一行的现象值得单独记：WAL 模式下主库文件可能长期只有 4096 字节，
数据全在 `-wal` 里（本机实测：10 万行后主库仍 4096 字节，`-wal` 2.36 MB）。
看到这个不要以为数据丢了，见 [WAL模式与检查点.md](WAL模式与检查点.md) 第三节。

## 延伸追问

**Q：为什么 SQLite 的 B 树不是「B+ 树」？**
严格说，表用的是 B 树变体：**内部页不存行，只存最大 rowid**，行只存在叶子页上——
这一点像 B+ 树；但**索引的内部页存键**（不只存 rowid），且叶子间没有兄弟指针，
范围扫描靠 B 树回溯而不是叶子链。所以文档说「B 树」。与 MySQL 的 InnoDB（聚簇索引 + 叶子链表）
对照读更清楚，见 [B树与B+树.md](../../../../02-计算机基础/数据结构/树/磁盘存储树/B树与B+树.md)。

**Q：页大小设 8 KiB 还是 4 KiB 好？**
取决于行宽与 I/O 模式。行大、批量顺序扫描多 → 大页（溢出少、I/O 次数少）；
随机点查多、写并发高 → 小页（每次读写的数据少、页内锁竞争小）。本机默认 4096，
`MAX_DEFAULT_PAGE_SIZE=8192`，所以上限受编译选项约束。

**Q：能不能直接改文件头里的「页数」来扩容？**
不能。页数必须与文件实际长度匹配，否则打开时校验失败（`SQLITE_CORRUPT`）。
扩容是通过写新页实现的，文件头只是结果。这也是为什么「拿十六进制编辑器修库」
几乎总是把库修坏。

**Q：库文件损坏了怎么办？**
先 `PRAGMA integrity_check`（能定位到具体页），再试 `.recover`（CLI 提供的恢复命令）或
`VACUUM INTO`（能成功就是大部分页可读）。恢复路径与备份策略见
[备份恢复与迁移.md](备份恢复与迁移.md) 第五节。
