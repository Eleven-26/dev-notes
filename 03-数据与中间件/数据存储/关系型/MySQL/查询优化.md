## 一、先想清楚：优化到底在优化什么

书里把这件事归结成一句话：**减少访问的行数，减少返回的列数**。

| 方向 | 手段 | 收益来源 |
| --- | --- | --- |
| **少访问行** | 加/改索引、改查询写法（让条件能走索引） | 少一次磁盘 IO |
| **少返回列** | 只 `SELECT` 需要的列（覆盖索引） | 少一次**回表**（随机 IO） |
| **少查几次** | 缓存、预计算、冗余字段 | 根本不产生这次查询 |
| **少读数据** | 分页、延迟关联、异步化 | 分摊到多次小查询 |

⭐ **"最快的查询是不查"**：一条 SQL 优化到极致，也不如"结果已经在缓存里"。
所以排查性能问题时，**先问"这个查询是不是必须每次都算"**，再动手改索引。

两个常见的思维误区：

| 误区 | 纠正 |
| --- | --- |
| "把 SQL 写短一点会更快" | **优化器不看你写了几个字符**，它按执行计划走。改名、换大小写、拆行都不影响 |
| "加索引就能解决" | 索引解决"访问行数"，解决不了"要返回 10 万行给前端"——那是分页或异步的问题 |

## 二、优化器怎么选执行计划

### 2.1 基于成本，不是基于规则

MySQL 的优化器是**基于成本的**（cost-based）：它会枚举可行的执行计划，**估算每个计划的成本**，选最低的。

| 成本类型 | 估算依据 |
| --- | --- |
| **IO 成本** | 需要读多少个页（数据页 + 索引页） |
| **CPU 成本** | 需要比较多少行、排序多大结果集 |

**查看当前查询的估算成本**（单位是"页"）：

```sql
SHOW STATUS LIKE 'Last_query_cost';
```

这个值**只是估算**：它反映"优化器以为要花多少"，而不是真实开销。

实测一条走 `idx_city_age(city, age)` 的 `SELECT age FROM users WHERE city='BJ' ORDER BY age`：
`Last_query_cost = 0.553630`，也就是"半页"；同一会话紧接着跑 `SELECT ... FROM users GROUP BY city`
再查就是另一个值 —— **这个状态变量是"上一条被优化的语句"的，不是全局平均值**，
所以必须紧跟目标语句读，中间别插别的查询。

### 2.2 为什么会选错索引

| 原因 | 说明 |
| --- | --- |
| **统计信息不准确** | `Cardinality` 是采样估算（见 [索引设计与EXPLAIN.md](索引设计与EXPLAIN.md) 第三节），分布倾斜时误差很大 |
| **估算模型简化** | 优化器假设"每个值均匀分布"、索引页都在内存里，与真实情况不符 |
| **条件之间有相关性** | 它假设 `WHERE city=? AND age=?` 两个条件相互独立，实际常常相关 |
| **没考虑 ORDER BY / LIMIT 的收益** | 走索引顺带排序可能更划算，但成本模型未必反映出来 |
| **多表 JOIN 时组合爆炸** | 表一多，优化器会放弃穷举，改用启发式（可能错过更优计划） |

**对策**：

| 手段 | 说明 |
| --- | --- |
| `ANALYZE TABLE t;` | 刷新统计信息（注意**它会隐式提交事务**） |
| 改写 SQL 引导优化器 | 比如把 `IN` 换成 `EXISTS`、加冗余条件让某个索引更"便宜" |
| `FORCE INDEX` / `USE INDEX` | **兜底手段**，会锁死计划，后续数据变化可能反而变差 |
| 上 `8.0` 的直方图 | `ANALYZE TABLE ... UPDATE HISTOGRAM ON col` —— 对有倾斜的列比采样更准 |

实测直方图确实建得出来，也确实存得住：

```text
mysql> ANALYZE TABLE orders UPDATE HISTOGRAM ON status WITH 8 BUCKETS;
Table            Op         Msg_type  Msg_text
docverify.orders histogram  status    Histogram statistics created for column 'status'.

-- 存到 information_schema.COLUMN_STATISTICS（4 列：SCHEMA_NAME/TABLE_NAME/COLUMN_NAME/HISTOGRAM）
HISTOGRAM = {"buckets": [[0, 0.25], [1, 0.5], [2, 0.75], [3, 1.0]], "data-type": "int", ...}
```

⚠️ 两处容易踩的：① 直方图**不在 `mysql.innodb_index_stats` 那两张表里**，别去那儿找；
② `mysql.column_stats` 在 8.0 **不存在**（实测 `ERROR 1146 (42S02): Table 'mysql.column_stats' doesn't exist`），
网上不少 8.0 的直方图文章第一句就查这张表。

### 2.3 "全表扫描"不一定是错的

优化器选择 `type=ALL` 时，先看 `rows`：

| 情形 | 是否合理 |
| --- | --- |
| `rows` 只有几十 / 几百，表也小 | ✅ 合理 —— 随机 IO 的开销可能大于顺序全扫 |
| 查询要返回表中**大部分行**（如 `WHERE status != 'x'` 命中 90%） | ✅ 合理 —— 走索引反而要回表 90% 的行 |
| `rows` 很大、且只用到少量行 | ❌ 有问题 —— 缺索引或索引没用上 |

⭐ **判据**：**"要读的行占总行数的比例"**。经验上超过 20%~30% 时，全表扫描可能比走二级索引更快（因为二级索引要走两次：索引 + 回表）。

## 三、查询重写：10 个能直接落地的套路

| # | 反例 | 改法 | 为什么 |
| --- | --- | --- | --- |
| 1 | `WHERE YEAR(created_at) = 2026` | `WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01'` | **函数包住列 → 索引失效**，改成范围条件即可用索引 |
| 2 | `WHERE phone = 13800000000`（`phone` 是 varchar） | `WHERE phone = '13800000000'` | **隐式类型转换**等价于对列做函数运算 → 索引失效 |
| 3 | `WHERE a = 1 OR b = 2`（a、b 各有索引） | 拆成两条 + `UNION ALL` | 索引合并（index merge）多数情况不如两条 `ref` 查询；**注意用 `UNION ALL` 而不是 `UNION`**（后者要额外去重） |
| 4 | `SELECT * FROM t WHERE ...` | 只列需要的列 | 争取**覆盖索引**，直接省掉回表 |
| 5 | `LIMIT 1000000, 20` | 游标分页 / 延迟关联 | 深分页要丢弃前 100 万行；做法见 [深分页与索引变更.md](深分页与索引变更.md) |
| 6 | `WHERE id NOT IN (SELECT ...)` | 改 `LEFT JOIN ... WHERE x IS NULL` 或 `NOT EXISTS` | `NOT IN` 遇 NULL 语义诡异，且常无法用索引 |
| 7 | 主表小、子表大时用 `IN (SELECT ...)` | 改 `EXISTS` | 存在性判断提前短路（反之：子表小则用 `IN`） |
| 8 | 超大 `IN (1,2,...,5000)` | 分批（每批几百个） | 单条 SQL 解析+执行成本高，且可能撑爆 `max_allowed_packet` |
| 9 | 在 `WHERE` 里做运算 `WHERE amount + 100 > 500` | 移到右侧 `WHERE amount > 400` | 同上：列上不套运算 |
| 10 | `GROUP BY x ORDER BY NULL`（旧写法） | 8.0 里直接去掉 `ORDER BY NULL` | **8.0 起 `GROUP BY` 不再隐式排序**，这个"优化技巧"已过时 |

⚠️ 第 3 条的补充：**`OR` 不一定要拆**。如果同一列上的多个值（`WHERE a = 1 OR a = 2`），
直接用 `IN (1,2)` 即可（等价的索引范围扫描）；只有**不同列**上的 `OR` 才考虑拆或依赖索引合并。

### 3.1 这几条改写实测下来，两条要修正

实测（`conv.phone` 是 `VARCHAR(20)` + `KEY idx_phone`；`t_or` 的 `a`、`b` 各有索引）：

```text
-- 第 2 条：隐式转换（数字对 varchar 列）
WHERE phone = 13800000000   ->  type: index  key: idx_phone  rows: 3  filtered: 33.33  Extra: Using where; Using index
WHERE phone = '13800000000' ->  type: ref    key: idx_phone  rows: 1  filtered: 100.00 Extra: Using index

-- 第 3 条：不同列的 OR
WHERE a = 1 OR b = 2        ->  type: index_merge  key: idx_a,idx_b  Extra: Using union(idx_a,idx_b); Using where
WHERE a = 1 OR a = 2        ->  type: range        key: idx_a        Extra: Using index condition

-- 第 6 条：NOT IN 子查询 与 LEFT JOIN ... IS NULL
NOT IN (SELECT o.customer_id FROM orders o)          ->  Extra: Using where; Not exists; Using index
LEFT JOIN orders o ON ... WHERE o.customer_id IS NULL ->  Extra: Using where; Not exists; Using index   （逐列相同）
```

两条修正：

- **第 2 条的表现比"索引失效"更微妙**：它没有回表全扫，而是把索引当覆盖索引**整棵扫一遍**
  （`type: index` + `filtered: 33.33`）。小表看不出差别，大表上这就是"扫完整个索引再逐行过滤"；
- **第 6 条在 8.0 里改写没有任何执行计划收益**：两种写法得到**完全相同**的计划，
  （优化器把 `NOT IN` 直接做成了反连接 `Not exists`）。**改它的理由是 NULL 语义，不是性能** ——
  `NOT IN` 的子查询一旦可能返回 NULL，结果集直接变空，这才是必须改的地方；
- 顺带一条实测：`WHERE created_at >= '2026-01-01'` 走的是 `type: range` +
  `Extra: Using index for skip scan`（索引是 `(status, created_at)`，范围条件不在最左列上）。
  **8.0 的 Skip Scan 会救回一部分"不符合最左前缀"的范围查询**，
  别再用 5.7 的直觉断定"第二列上的范围一定不走索引"。

## 四、`COUNT` 的优化

### 4.1 先说清语义差别

| 写法 | 语义 | 说明 |
| --- | --- | --- |
| `COUNT(*)` | 数**行数** | 不忽略任何行，`NULL` 行也算 |
| `COUNT(1)` | 数**行数** | 与 `COUNT(*)` 等价（**8.0 里执行计划完全相同**） |
| `COUNT(col)` | 数该列**非 NULL** 的个数 | **会漏掉 NULL**，语义完全不同 |

⚠️ **"`COUNT(1)` 比 `COUNT(*)` 快"是错误的**：优化器会把 `COUNT(*)` 转成数行操作，
且会**挑最小的那棵二级索引树**来扫（不读聚簇索引，省 IO）。所以两者没有性能差别，**别为了性能改写法，改了反而可能改错语义**。

实测这三条的执行计划（`orders` 2500 行，索引有 `idx_customer(customer_id)`、`idx_desc(status, created_at)` 等）：

```text
COUNT(*)       type: index  key: idx_customer  rows: 2500  Extra: Using index
COUNT(1)       type: index  key: idx_customer  rows: 2500  Extra: Using index        （与上一条逐列相同）
COUNT(status)  type: index  key: idx_desc      rows: 2500  Extra: Using index
```

`COUNT(*)` / `COUNT(1)` 的计划**一模一样**，都挑了最窄的 `idx_customer`；
而 `COUNT(status)` 必须真的读 `status` 列来判断 NULL，于是优化器改挑**覆盖这一列**的 `idx_desc`。
这就是"**列名会影响选哪棵树**"的直接证据 —— 三种写法的行数一样，成本却未必一样。

### 4.2 InnoDB 的 `COUNT(*)` 为什么慢

MyISAM 把"总行数"存在表头，`SELECT COUNT(*)` 直接读一个数字（所以 MyISAM 的 `COUNT(*)` 极快，**但带 `WHERE` 就一样慢**）。

InnoDB **做不到**，因为 MVCC 下"有多少行可见"取决于**当前事务的快照** —— 同一条 `COUNT(*)`，不同事务看到的行数可能不同。**所以它必须逐行判断可见性。**

### 4.3 四个优化方向

| 方案 | 适用 | 代价 |
| --- | --- | --- |
| **维护计数表 / 计数列** | 需要精确值、更新不频繁 | 要保证与主表一致（同一事务内 `+1/-1`，或用触发器/异步补偿） |
| **Redis 计数** | 高并发、可容忍短时不准 | 与数据库的一致性要靠业务兜底 |
| **近似值** | "大概多少"够用时 | `EXPLAIN` 的 `rows` 是估算值，够快也够糙；`SHOW TABLE STATUS` 的 `Rows` 同理 |
| **只判断"是否超过 N"** | 分页只要展示"还有下一页" | `SELECT COUNT(*) FROM (SELECT 1 FROM t WHERE ... LIMIT 1001) x` —— **扫够 1001 行就停**，比全量数快得多 |

⭐ **第 4 条最实用**：前端"共 N 条"里的 N 本身就不可靠（翻到第 3 页数据可能已经变了）。
很多系统真正需要的只是"有没有下一页"，用一个带 `LIMIT` 的子查询就能把成本从"全表"降到"扫 1001 行"。

实测 `SELECT COUNT(*) FROM (SELECT 1 FROM orders LIMIT 1001) x` 的计划是两行：
外层 `table: <derived2>  type: ALL  rows: 1001`，内层 `type: index  key: idx_customer`。
⚠️ 读法要点：**`rows: 1001` 是外层派生表的行数上限**，内层那行的 `rows` 仍是优化器对整个表的估算 ——
所以别拿 `EXPLAIN` 的 `rows` 判断"有没有真的提前停"，要提前停就得看 `EXPLAIN ANALYZE` 的 `actual rows`。

## 五、排序优化

### 5.1 `filesort` 的两种算法

`Extra` 里出现 `Using filesort` 时，MySQL 会在内存（或磁盘临时文件）里排序。它有两种策略：

| 算法 | 做法 | 内存占用 | 代价 |
| --- | --- | --- | --- |
| **全字段排序** | 把 `SELECT` 需要的**所有列**放进排序缓冲区，排完直接返回 | 大 | 无额外回表 |
| **rowid 排序** | 只放**排序键 + 主键**，排完再按主键**回表**取其余列 | 小 | 多一次随机 IO |

**选择依据**：单行长度是否超过 `max_length_for_sort_data`。
超过了就用 rowid 排序（省内存、多回表）。

⚠️ 默认值别照老文章抄：实测 8.0.46 里 `max_length_for_sort_data = 4096`（不是常见的 1024），
而且这一族"两种排序算法自动切换"的行为在新 8.0 已经改版（排序缓冲由 `sort_buffer_size` 决定，
见 [参数调优.md](参数调优.md) 第 4.1 节）。**结论方向不变**（行越宽越容易转成 rowid 排序），
但"超过 1024 就切换"这个具体数字在当前版本要按实例实测。

⚠️ **由此可推出一个优化点**：如果一个查询既 `filesort` 又 `SELECT *`，
**它会走 rowid 排序并大量回表** —— 改成只 `SELECT` 少数字段，可能让它变成全字段排序，减少回表。

### 5.2 什么时候能用索引排序（避免 filesort）

三个条件同时满足：

1. `ORDER BY` 的列顺序与某个索引的列顺序**一致**；
2. 每一列的排序方向**一致**（都是 `ASC` 或都是 `DESC`；8.0 之前不支持混合方向，8.0 可用降序索引）；
3. `WHERE` 条件是该索引的**最左前缀等值条件**（一旦出现范围条件，后面的列就不再有序）。

```sql
-- 索引 (city, age)
SELECT age FROM users WHERE city = 'BJ' ORDER BY age;        -- ✅ 用索引排序
SELECT age FROM users WHERE city > 'A'  ORDER BY age;        -- ⚠️ city 是范围 → age 不再有序
SELECT age FROM users WHERE city = 'BJ' ORDER BY name;       -- ❌ 排序键不在索引里
```

实测后两条（`users` 只有 4 行、`idx_city_age(city, age)`）：

```text
ORDER BY age   type: ref   key: idx_city_age  key_len: 67  ref: const  rows: 3  Extra: Using index
ORDER BY name  type: ALL   key: NULL          possible_keys: idx_city_age  rows: 4  filtered: 75.00
               Extra: Using where; Using filesort
```

TREE 格式把差别摊得更开：`ORDER BY name` 是 `-> Sort: users.name (cost=1.4 rows=4)` 套在
`-> Table scan on users` 外面，而 `ORDER BY age` 连 `Sort` 节点都没有。

⭐ `optimizer_trace` 里有一个专门回答"索引能不能提供顺序"的节点，比猜 `Extra` 直接得多：

```text
"reconsidering_access_paths_for_index_ordering": {
  "clause": "ORDER BY",
  "index_order_summary": {
    "index": "idx_city_age", "table": "`users`",
    "index_provides_order": true, "plan_changed": false, "order_direction": "asc"
  }
}
```

`index_provides_order: true` 就是"三个条件都满足"的官方判定；查不到这个节点或它是 `false`，
说明优化器已经放弃了索引排序。

### 5.3 `ORDER BY` + `LIMIT` 的细节

- 有 `LIMIT` 时 MySQL 会用**优先队列**（堆）而不是完整排序，只保留前 N 行 —— 这是 `ORDER BY ... LIMIT 10` 通常不慢的原因；
- 但**深分页**（`LIMIT 1000000, 10`）依然要**丢弃**前 100 万行，堆排序省不了这一步 → 用游标分页；
- **排序列有 NULL 时**，索引里 NULL 排在前面，可能打乱预期的顺序。

## 六、`GROUP BY` 与 `DISTINCT`

`GROUP BY` 通常隐含着"需要按分组键有序"或"需要临时表"：

| 执行方式 | 触发条件 | 表现 |
| --- | --- | --- |
| **松散索引扫描**（loose index scan） | 分组键是索引最左前缀，且不需要扫描全部行 | 最快，`Extra` 显示 `Using index for group-by` |
| **紧凑索引扫描**（tight index scan） | 分组键是索引前缀，但需要读全部匹配行 | 较快，无临时表 |
| **临时表 + 排序** | 分组键没有可用索引 | ❌ `Using temporary; Using filesort`（最慢） |

```sql
-- 索引 (city, age)
SELECT city, COUNT(*) FROM users GROUP BY city;              -- ✅ 松散索引扫描
SELECT city, COUNT(*) FROM users GROUP BY age;               -- ❌ 非最左前缀 → 临时表
SELECT city, COUNT(*) FROM users WHERE city = 'BJ' GROUP BY age;  -- ⚠️ 常量条件可跳过，看优化器判断
```

⚠️ **8.0 的一处行为变化**：8.0 之前 `GROUP BY` **隐式排序**（所以老代码里到处是 `GROUP BY x ORDER BY NULL` 来关掉排序）；
**8.0 移除了隐式排序**，需要排序就显式写 `ORDER BY` —— 老文章里的"`ORDER BY NULL` 优化"已经过时。

### 6.1 松散索引扫描没那么容易撞上（实测）

上面那张表把"分组键是索引最左前缀"当成松散扫描的充分条件，实测**不是**：

```text
SELECT city, COUNT(*)       FROM users GROUP BY city   ->  type: index  Extra: Using index
SELECT city                 FROM users GROUP BY city   ->  type: index  Extra: Using index
SELECT city, MAX(age)       FROM users GROUP BY city   ->  type: index  Extra: Using index
SELECT city, COUNT(DISTINCT age) FROM users GROUP BY city ->  type: range  Extra: Using index for group-by (scanning)
```

四条里只有最后一条出现了 `Using index for group-by`。trace 给的原因是
`group_index_range: { chosen: false, cause: "not_applicable_aggregate_function" }` ——
**`COUNT(*)` 这类聚合把松散扫描直接排除**（要数全部行，跳着读就没有意义），
能触发的是 `COUNT(DISTINCT col)` / `MIN` / `MAX` 这一族。
再加上本机表只有 4 行，成本模型本来也更倾向覆盖索引全扫，所以**别把"看到 Using index for group-by"当成必达目标**。

另外一条实测硬约束：默认 `sql_mode` 含 `ONLY_FULL_GROUP_BY`，上表第三行的写法
（`SELECT city ... GROUP BY age`）实测直接报错，**照抄会失败而不是"看优化器判断"**：

```text
ERROR 1055 (42000): Expression #1 of SELECT list is not in GROUP BY clause and contains
nonaggregated column 'docverify.users.city' which is not functionally dependent on columns
in GROUP BY clause; this is incompatible with sql_mode=only_full_group_by
```

`DISTINCT` 的实现与 `GROUP BY` 类似（都可以用索引或临时表），**能用索引消重就不要用临时表**。

## 七、JOIN 优化

### 7.1 表连接的三个要点

| # | 要点 | 说明 |
| --- | --- | --- |
| 1 | **小表驱动大表** | 驱动表的每一行都要去被驱动表查一次；驱动表小，外层循环次数少 |
| 2 | **被驱动表的连接列必须有索引** | 没有索引就会退化成块嵌套循环（`Using join buffer`），复杂度从 `N × log M` 变成 `N × M` |
| 3 | **关联字段的类型必须一致** | 字符集或类型不一致会导致**隐式转换** → 被驱动表的索引失效（这是"JOIN 突然变慢"的常见原因） |

### 7.2 四种 JOIN 算法

| 算法 | 出现条件 | 复杂度 |
| --- | --- | --- |
| **NLJ**（嵌套循环） | 被驱动表连接列有索引 | `N × log M` ✅ |
| **BNL**（块嵌套循环） | 被驱动表连接列**无索引** | `N × M` ❌（`Extra` 会显示 `Using join buffer (Block Nested Loop)`） |
| **BKA**（批量键访问） | NLJ + MRR，把多行的键批量传给引擎一次读 | 比 NLJ 少一些随机 IO |
| **Hash Join**（8.0.18+） | 等值连接且无可用索引时**自动启用**，替代 BNL | 显著快于 BNL ✅ |

⭐ **看到 `Using join buffer (Block Nested Loop)` 就该警觉**：优先给被驱动表的连接列加索引；
实在加不了（或 8.0.18+ 已自动用 Hash Join），再评估是否需要改写查询。

实测（`t_x` 2500 行、`t_y` 500 行，连接列 `k` 上**都没有索引**）：

```text
-- 传统格式
|  1 | SIMPLE | b | ALL | NULL | NULL | NULL | NULL |  500 | 100.00 | NULL                                       |
|  1 | SIMPLE | a | ALL | NULL | NULL | NULL | NULL | 2500 |  10.00 | Using where; Using join buffer (hash join)  |

-- TREE 格式
-> Inner hash join (a.k = b.k)  (cost=125051 rows=125000)
    -> Table scan on a  (cost=0.0505 rows=2500)
    -> Hash
        -> Table scan on b  (cost=50.2 rows=500)

-- EXPLAIN ANALYZE 实测行
-> Inner hash join (a.k = b.k)  (actual time=0.507..3.44 rows=12891 loops=1)
    -> Table scan on a          (actual time=0.0124..1.67 rows=2500 loops=1)
    -> Hash -> Table scan on b  (actual time=0.0258..0.382 rows=500 loops=1)
```

三条读法：

- `Extra` 里是 **`hash join`** 而不是 `Block Nested Loop` —— 8.0.46 上无索引等值连接**已经是哈希连接**，
  老文章里的 `BNL` 字样在这个版本看不到（想复现得用 `/*+ NO_BNL */` 之类的开关，且不同小版本行为不同）；
- TREE 里被驱动的那一侧挂在 `-> Hash` 节点下，**建哈希的正是小表 `b`（500 行）**，
  这就是"小表驱动大表"在哈希连接里的真实形态：不是循环顺序，而是"谁进哈希表"；
- `actual rows=12891` 对 `cost=... rows=125000`：**估算高了一个数量级**，
  这类"多对多放大"的估算偏差只能用 `EXPLAIN ANALYZE` 发现（正文 9.4）。

### 7.3 两条实践建议

- **不要盲目 `STRAIGHT_JOIN`**：它强制驱动顺序，锁死了优化器的选择。只在"确认优化器选错、且数据分布稳定"时用；
- **JOIN 表数别太多**：MySQL 对 JOIN 的优化是"从左到右"的（不是全排列），表越多越容易选错驱动顺序 —— 单条 SQL 关联 5 张以上就该考虑拆查询或用应用层组装（这也正是互联网架构"少用 JOIN"的原因之一，见 [数据建模.md](数据建模.md)）。

## 八、优化的流程：别凭感觉改

```text
① 定位：慢查询日志  →  ② 排序：按总耗时排序，先改最值钱的  →  ③ 分析：EXPLAIN
→  ④ 判断层次：索引问题 / SQL 问题 / 架构问题  →  ⑤ 改一处，复测，再改下一处
```

**第 ④ 步的"三个层次"是核心判断**：

| 层次 | 症状 | 手段 |
| --- | --- | --- |
| **索引问题** | `key = NULL`、`type = ALL`、`Using filesort` | 加/改索引，改写 SQL 让条件能用索引 |
| **SQL 问题** | 索引没问题，但逻辑本身要求大量数据（深分页、全表 COUNT、大结果集） | 改写法（游标分页、延迟关联、只判断"是否超过 N"） |
| **架构问题** | 单条 SQL 已经最优，但量级上不去了（热点行、超大表、强一致读） | 加缓存、读写分离、分表、异步化、预计算 |

⚠️ **用架构手段解索引问题，或用索引手段解架构问题，都是白费力气**。
一条 SQL 的瓶颈在"每次都要扫描上万行"时，加机器也没用；反过来，量级到亿级之后，
再精妙的索引也救不回"每次都要随机读很多页"。

另外两条纪律：**一次只改一处**（否则不知道是谁起的作用）、**用数据说话**（改前改后都要 EXPLAIN + 计时）。

## 九、怎么知道优化器「为什么这么选」？

**来源**：《高性能 MySQL》（第 4 版）第 8 章「查询执行的基础设施」「优化器」相关小节，加上 8.0 的可观测手段。

**本节要点**：第 2 节讲的是"优化器基于成本"，本节讲"怎么把它的成本账摊开看"。
三件工具按侵入性从低到高：`EXPLAIN` 的多种格式 → hint → `optimizer_trace`。

### 9.1 `EXPLAIN` 不只有一种输出

```text
EXPLAIN SELECT ...                    传统表格式：type / key / key_len / rows / Extra
EXPLAIN FORMAT=JSON SELECT ...        带每层 cost 与子查询结构，脚本解析用它
EXPLAIN FORMAT=TREE  SELECT ...       迭代器树，人读最舒服（8.0.18+）
EXPLAIN ANALYZE     SELECT ...        真的执行，附 actual time / rows / loops（8.0.18+，只有 TREE 格式）
```

- `rows`（估算）与 `rows=`（实际）差距大 → 统计信息或参数化偏移问题，见 9.4；
- `loops` 是这一层被外层驱动了多少次，**乘上 `actual time` 才是真实代价** ——
  单独看一个节点的耗时最容易误判；
- ⚠️ `EXPLAIN ANALYZE` 会**执行语句**：对 `UPDATE` / `DELETE` 别在生产随手加，
  要验证写语句就改成等价 `SELECT` 或先在从库/测试库跑。

实测最后一条不是建议而是硬限制：`EXPLAIN ANALYZE FORMAT=JSON` 直接报
`ERROR 1235 (42000): This version of MySQL doesn't yet support 'EXPLAIN ANALYZE with JSON format'`。
**要 JSON 就回到普通 `EXPLAIN FORMAT=JSON`（只有估算，没有 actual）**，两者不能同时要。

示例与迭代器读法见 [数据建模.md](数据建模.md) 第 2.1 节，本篇不重复。

### 9.2 `optimizer_trace`：把候选计划与成本打出来

```sql
SET optimizer_trace = "enabled=on";
SET optimizer_trace_max_mem_size = 100000;   -- 上限太小会截断，查不到内容先怀疑这里

SELECT ... ;                                 -- 目标语句，紧接着读 trace

SELECT TRACE FROM information_schema.OPTIMIZER_TRACE;
SET optimizer_trace = "enabled=off";
```

看两处就够：`considered_execution_plans`（每个候选计划的成本与 `chosen`）和
`rows_estimation[].range_analysis`（范围扫描的备选成本）。第 2.2 节「为什么会选错索引」的成因
在这里能直接看到：**是估算错了，还是正确的计划成本确实更低**。

实测 8.0.46 的 trace 顶层是 `steps` 数组，三段依次是 `join_preparation` → `join_optimization` → `join_execution`；
`join_optimization.steps` 里值得看的节点（单表查询的真实键名）：

```text
"rows_estimation": [ { "range_analysis": {
    "table_scan":  { "rows": 4, "cost": 3.5 },
    "potential_range_indexes": [ {"index":"idx_city_age","usable":true,"key_parts":["city","age","id"]} ],
    "analyzing_range_alternatives": { "range_scan_alternatives": [
        {"index":"idx_city_age","rows":3,"cost":0.56463,"chosen":true,
         "in_memory":1,"index_only":true,"using_mrr":false,"rowid_ordered":false} ] },
    "chosen_range_access_summary": { "chosen": true, "cost_for_plan": 0.56463, "rows_for_plan": 3 } } } ],
"considered_execution_plans": [ {
    "best_access_path": { "considered_access_paths": [
      {"access_type":"ref","index":"idx_city_age","rows":3,"cost":0.55463,"chosen":true},
      {"access_type":"range","cause":"heuristic_index_cheaper","chosen":false} ] },
    "cost_for_plan": 0.55463, "rows_for_plan": 3, "chosen": true } ],
```

三条实测口径：

- ⚠️ **`cost_for_query_block` 这个键在 8.0.46 的 trace 里没有**，照旧文章取它会拿到 NULL ——
  现在每层的成本字段叫 **`cost_for_plan`**，候选项里叫 `cost`；
- **`cause` 是免费的结论**：`heuristic_index_cheaper`、`not_applicable_aggregate_function`、
  `too_few_roworder_scans` 这类字符串直接说"为什么放弃"，比读成本快；
- 截断判断要读 `information_schema.OPTIMIZER_TRACE` 的另外两列（这张表实测固定 4 列：
  `QUERY`、`TRACE`、`MISSING_BYTES_BEYOND_MAX_MEM_SIZE`、`INSUFFICIENT_PRIVILEGES`）：
  `MISSING_BYTES_BEYOND_MAX_MEM_SIZE > 0` 就是被 `optimizer_trace_max_mem_size` 截断了，
  **而不是"trace 没内容"**。实测默认值是 `optimizer_trace = enabled=off,one_line=off`、
  `optimizer_trace_max_mem_size = 1048576`、`optimizer_trace_limit = 1` ——
  `limit=1` 意味着**只留最近一条**，正好印证下面的写法。

trace 只保留会话内最近执行的语句，缓冲写满会淘汰旧条目 —— 所以**跑一条读一条**，
别批量执行后再回头翻。

### 9.3 hint：只改这一条语句，别改全局

```sql
SELECT /*+ JOIN_ORDER(t2, t1) NO_ICP(t1) MAX_EXECUTION_TIME(1000) */ ...
    FROM t1 JOIN t2 ON ...;

EXPLAIN SELECT /*+ JOIN_ORDER(t2, t1) */ ...;   -- 再跟上 SHOW WARNINGS
SHOW WARNINGS;                                  -- 看 hint 是否被采纳；被忽略的不会显示
```

四条口径：

- `/*+ ... */` 语法 5.7 引入，8.0 扩充了大量 hint；
  `HASH_JOIN` / `NO_HASH_JOIN` 只在 8.0.18 有效，之后统一由 `BNL` / `NO_BNL` 管；
- `MAX_EXECUTION_TIME(N)` **只对只读 `SELECT` 生效**（单位毫秒），不要指望它限制写语句；
  实测：给一条三表笛卡尔的 `SELECT` 加 `/*+ MAX_EXECUTION_TIME(1) */`，
  报 `ERROR 1317 (70100) at line 3: Query execution was interrupted`（超时是被中断，不是 3024）；
  同样的 hint 写在 `UPDATE` 上**不报错也不生效**（语句正常执行完）——
  **"hint 没报错"绝不等于"hint 被采纳"**，要验证只能用会不会超时这类可观测后果去试。
- 全局开关是 `optimizer_switch`（可以会话级改，例如临时关掉 `index_merge` 复现问题），
  **hint 的作用域只在这一条语句** —— 生产上优先用 hint，把全局开关留在复现环境里；
- hint 是"绕过优化器"，不是"修好优化器"。用了 hint 就等于承认 schema 或统计信息有问题，
  该建索引仍然要建（第 7 节的清单）。

### 9.4 估算偏差从哪来

- InnoDB 的 `rows` / `Cardinality` 都是**采样估算**，机制见 [索引设计与EXPLAIN.md](索引设计与EXPLAIN.md) 第 3.2 节；
- 统计信息持久化在 `mysql.innodb_index_stats` 与 `mysql.innodb_table_stats`，
  `ANALYZE TABLE` 重采样，`innodb_stats_auto_recalc` 负责自动重算（参数见 [参数调优.md](参数调优.md)）；
- 数据分布倾斜（某个值占九成）时，估算总体正确仍可能在这一条语句上选错 ——
  这时先用 9.2 确认成本账，再用 9.3 的 hint 或改写（第 3 节）兜住，
  而不是"加索引试试"。

## 十、慢查询怎么定位与优化

**本节要点**：遇到"库变慢了"，先分清是**没用上索引**还是**用上了但还不够快** ——
两类原因的修法完全不同。

**本节要点**：要讲清楚的是**一套可执行的排查流程**，而不是零散的优化技巧。

### 第一步：定位 —— 用工具找出"真正值得优化"的慢查询

不要凭感觉挑。用 `mysqldumpslow` 等工具分析慢查询日志，但**默认的"按平均查询时长排序"往往选错目标**：

> 一个平均耗时最长的 SQL，可能一天只出现 5 次，而且都发生在非高峰的深夜——
> 优化它收益极小。

应该换排序维度：
- **按总耗时排序**（平均时长 × 次数）→ 找出真正消耗数据库总资源的 SQL；
- **按出现次数排序** → 找出高频但单次不慢的 SQL（积少成多）。

### 第二步：分析 —— 用 `EXPLAIN` 看查询计划

拿到目标 SQL 后，用 `EXPLAIN` 看优化器打算怎么执行，重点看三件事：

| 关注点 | 判断标准 |
|---|---|
| **有没有用到索引** | `type` 是否出现 `ALL`（全表扫描） |
| **扫描行数** | `rows` 越小越好；**即使走了索引，扫描行数太多也快不了** |
| **是否用到子查询** | 子查询往往无法有效利用索引，考虑改写成 JOIN |

### 第三步：优化 —— 两大类原因

#### 类型 B：用上了索引但还不够快

**B1. 使用覆盖索引，避免回表** ← 性价比最高的一招

如果查询需要的字段**全部都在索引里**，就不用再去主键索引（聚簇索引）取数据，少一步"回表"。
类比查字典：**已经直接在目录页看到了需要的信息，就不用翻到正文那一页**。

```sql
-- 假设有联合索引 idx_name_age(name, age)
-- ✗ 需要回表：select 的 address 不在索引里
SELECT name, age, address FROM users WHERE name = 'zhang';

-- ✓ 覆盖索引：所需字段都在索引中，无需回表
SELECT name, age FROM users WHERE name = 'zhang';
```

实测（`docidx.users2`，5 万行，`idx_name_age(name, age)`，`name='u1'` 命中 500 行）：

```text
# 回表版
| type: ref | key: idx_name_age | key_len: 202 | ref: const | rows: 500 | Extra: NULL
-> Index lookup on users2 using idx_name_age (name='u1')  (cost=175 rows=500)
   (actual time=0.166..1.3 rows=500 loops=1)
# 覆盖版
| type: ref | key: idx_name_age | key_len: 202 | ref: const | rows: 500 | Extra: Using index
-> Covering index lookup on users2 using idx_name_age (name='u1')  (cost=53.4 rows=500)
   (actual time=0.0322..0.154 rows=500 loops=1)
# 服务端耗时（各两轮）
0.00236275 / 0.00200900 秒   SELECT name, age, address FROM users2 WHERE name='u1'
0.00049875 / 0.00047425 秒   SELECT name, age          FROM users2 WHERE name='u1'
```

三件事只有跑过才看得清：

- **回表版的 `Extra` 是 `NULL`，不是 `Using index condition`**。`Using index condition` 属于
  **ICP（index condition pushdown）**：范围条件里"索引能判但需要回表才能确认"的那部分被下推到引擎，
  实测只在 `WHERE name='u1' AND age > 25`（`type=range`、非覆盖列）时出现；
  同一句把 `address` 去掉变覆盖索引就成了 `Using where; Using index`，
  而 `SET optimizer_switch='index_condition_pushdown=off'` 之后它退回 `Using where`。
  也就是说**覆盖索引和 ICP 是两件事**，`Extra` 从 `Using index condition` 变成 `Using index`
  这种"改 select 列导致的"说法不成立 —— 改列只让 `NULL` 变成 `Using index`。
- **`rows` 一样（都是 500），差别全在代价上**：`cost` 175 → 53.4，实际耗时 2.0~2.4 ms → 0.47~0.50 ms，
  **约 4~5 倍**。所以"少回表"这件事在计划上看不出行数差异，只能看 cost 与实测。
- **小夹具会把结论伪装成反例**：同一句在 6 行的 `users` 上，`SELECT *` 版直接
  `type=ALL, key=NULL`（优化器认为扫 6 行比走索引便宜），覆盖版则显示 `const table`。
  **别拿几行的演示表去解释回表代价**，本篇的实测块一律用 5 万行的表。

**B2. 表连接优化：用小表驱动大表**

原则：**行数少的表放左边**（驱动表），行数多的放右边。
用 `INNER JOIN` 时，执行方式是"拿小表的结果集去匹配大表"，小表越大范围越小的效果越好。

**B3. 先缩小范围，再做连接**

举例：要查 10 万行表与 50 万行表的连接结果，但最终只需要 1000 条：

```sql
-- 思路：先用条件把 10 万条数据过滤成 1000 条，再用这 1000 条去连接 50 万条的大表
-- 结果集非常小，比"10 万条直接连 50 万条"快得多
```

进一步可以把过滤后的结果集做成**临时表**，再做连接，减少中间数据量。

## 十一、`mysqldumpslow` 实操：按总时间排序

**本节要点**：前面讲的是"优化思路"，这一节讲的是**手上的具体动作**——
**怎么把慢查询日志开起来、怎么用它挑出该优化的 SQL**。
排查完之后紧接着就是"怎么优化"，所以这两节要连着看。

### 11.1 排查分两步

```text
① 启用 MySQL 慢查询日志
② 用工具分析慢查询日志文件，挑出最该优化的那几条
```

### 11.2 第 1 步：启用慢查询日志（两种方式）

| 方式 | 做法 | 适用 |
|---|---|---|
| **临时开启** ⭐ | 在**运行中的 MySQL 上直接设置变量** | **生产环境推荐**——可以周期性开关，减少性能开销 |
| **永久开启** | 修改**配置文件（my.cnf）并重启 MySQL 服务** | 新建服务时可用；<br>⚠️ **正在稳定运行的生产服务不要这么做**（不要为了开个日志去重启） |

```sql
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;       -- 超过 1 秒算慢查询
SHOW VARIABLES LIKE 'slow_query_log_file';   -- ★ 拿到日志位置（分析要用）
```

**三个必须确认的信息**：
1. **`long_query_time`** —— 多久算慢；
2. **开启状态**；
3. **慢日志文件的位置** —— 后面分析必须用到。

**容器化场景的两个坑**：

> 1. 用 `docker inspect` 看 **Mounts**，确认数据目录和配置文件都挂到宿主机了
>    （否则容器一删，数据就没了）；
> 2. **慢日志未必挂载出来** → 那就需要**从容器里 `docker cp` 出来**再分析。

### 11.3 第 2 步：用 `mysqldumpslow` 分析

**工具来源**：`mysqldumpslow` **默认和 MySQL 安装包打包在一起**——
Windows/Linux 装 MySQL 都会有。

**⚠️ 容器化运行 MySQL 的坑**：

> 容器镜像遵循**最小原则**构建，**无关紧要的内容不打进镜像**（为了减小体积）——
> 所以进容器后会发现 **`mysqldumpslow` 不存在**，甚至 **`mysql` 客户端也没有**。
>
> **解法**：在**宿主机本地安装**即可。
> 因为 **`mysqldumpslow` 只是分析日志文件，不需要连接 MySQL 服务器**。

**常用参数**（重点记 `-s` / `-t` / `-a` / `-g`）：

| 参数 | 作用 |
|---|---|
| **`-s`** | **排序规则**：`-s t` 按**总时间**、`-s at` 按**平均查询时间**、`-s c` 按**出现次数** |
| **`-r`** | **反转排序结果**（默认从高到低，反转后从低到高） |
| **`-t`** | 显示**前 N 条** |
| **`-a`** | **不做抽象化**（默认数字→`N`、字符串→`S`）。<br>见下方"抽象化"说明 |
| **`-n`** | 抽象化名称中**至少包含数字**（如 `-n 3` 会把 `id=3` 抽象成 `id=N`） |
| **`-g`** | **过滤**（正则）：只看包含某模式的查询 |
| **`-h`** | 指定**主机名/实例名**（慢日志里有多个主机时筛选） |
| **`-l`** | **不从总时间中减去锁等待时间**（默认保留原始总时间） |

**什么是"抽象化"（默认行为）**：

> 默认会把**数字替换成 `N`、字符串替换成 `S`**。
>
> 所以 `WHERE id=10` 和 `WHERE id=20` 会被**归为同一条语句**（这是好事，
> 因为它们本质是同一类查询，只是参数不同）。
>
> **加 `-a` 则显示原始值**，于是"同一条语句"会被**按不同参数拆成多条记录**
> **分别呈现**——条数会明显变多。

### 11.4 ⭐ 核心洞察：按「总时间」排序，而不是「平均时间」

**反例（一定要讲这个）**：

```text
A 语句：一天出现 100 次，每次 1.5 秒
B 语句：一天出现 1 次，  每次 2.0 秒
```

**按平均查询时间排序** → 先优化 **B**（因为 2.0 > 1.5）。
**但 B 一天才访问一次，优化它收益极低。**

**按总时间排序（`-s t`）**：
- A 总耗时 = 100 × 1.5 = **150 秒**
- B 总耗时 = 1 × 2.0 = **2 秒**

→ **A 的"影响"远大于 B**，应该**优先优化 A**。

> **结论**：**总时间反映的是"这条 SQL 对系统的实际影响"**——
> 而平均时间只反映"单次有多慢"。**优化总时长最大的，通常收益最高。**

**优化的迭代逻辑**：

```text
找出总耗时最大的 SQL → 优化它
      ↓
优化完，第二名变成第一名 → 继续优化
      ↓
如此迭代，逐步把性能问题清掉
```

> **所以只需要关注前 5 条 / 前 10 条**，不需要全看。

**日志文件里有什么**（分析时能筛的字段）：
时间、用户、主机、**查询时间**、**锁定时间**、**返回行数**、**扫描行数**。

### 11.5 下一步：优化阶段的套路与反例

**用 `EXPLAIN` 看查询计划**——它会返回一条或多条记录，告诉我们**这条 SQL 慢在哪里**。

**常见优化策略**：如**把子查询改写成 JOIN**（因为子查询可能全表扫描）。

**⚠️ 但策略未必好使（这段很实用）**：

> **两个大表直接 JOIN 会非常慢。**
>
> 但可以换个顺序：
> ```
> ① 先用 B 表的条件把数据范围缩到几十 / 100 条以内
> ② 把这个小结果集做成临时表（temp）
> ③ 再让 A 表去 JOIN 这个 temp
> ```
> **即使 temp 是全表扫描、即使它占内存，也比"大表直接 JOIN 大表"快得多。**
>
> **结论：先缩小数据范围，再做 JOIN。**

> **提示**：优化策略都是"可参考"的，**必须结合实际业务和实际情况判断哪种更优**，
> 不存在放之四海皆准的套路。

### 排查步骤小结

```text
① 先说排查两步：启用慢日志（临时/永久，生产用临时）→ 用工具分析
② 讲 mysqldumpslow 的关键参数：-s（排序）/ -t（前N条）/ -a（是否抽象化）
③ ★ 重点讲：要按「总时间」而不是「平均时间」排序（附 A/B 语句反例）
④ 讲后续优化：EXPLAIN 定位 → 大表 JOIN 先缩小范围做临时表再 JOIN
```

## 使用：一条慢 SQL 的改写与前后对比骨架

改写的前提是「先量化再动手」：先看优化器估算的成本，再对改写前后各做一次 `EXPLAIN`，一次只改一处。

```sql
-- ① 基准：先看优化器为当前 SQL 估算的成本（单位「页」，只是它的判断，正文 2.1）
SHOW STATUS LIKE 'Last_query_cost';

-- ② 改写前：排序键 name 不在索引 (city, age) 里 → 索引排序的三个条件不满足（正文 5.2）
EXPLAIN SELECT age FROM users WHERE city = 'BJ' ORDER BY name;

-- ③ 改写后：只把 ORDER BY 对齐索引顺序，其余一个字不动
EXPLAIN SELECT age FROM users WHERE city = 'BJ' ORDER BY age;

-- ④ 复测纪律：改前改后都要 EXPLAIN + 计时，别凭感觉宣布优化成功（正文第八节）
```

实测输出（`users` 4 行、`idx_city_age(city, age)`，MySQL 8.0.46）：

```text
-- ① 紧跟在 ③ 之后执行
Last_query_cost   0.553630

-- ② 改写前
type: ALL   possible_keys: idx_city_age   key: NULL   rows: 4   filtered: 75.00
Extra: Using where; Using filesort

-- ③ 改写后
type: ref   key: idx_city_age   key_len: 67   ref: const   rows: 3   filtered: 100.00
Extra: Using index
```

⚠️ 两条和直觉不一样的地方，正好是这套骨架的价值所在：

- **② 不是 `type: ref` 而是 `type: ALL`**：优化器为了排序直接放弃索引改走全表扫，
  `possible_keys` 里明明有 `idx_city_age` 却 `key: NULL` ——
  所以"过滤条件能走索引"不代表"这条语句会走索引"，**排序键也要一起算进成本**；
- `filtered: 75.00`（②）说明优化器估计全表扫之后还要丢掉四分之一行，
  而 ③ 的 `filtered: 100.00` 是"索引已经把范围收窄了"。
  改前改后各看一次这两个数，比只看 `Extra` 更能说明"真的变便宜了"。

## 延伸追问

- **`EXPLAIN` 和 `EXPLAIN ANALYZE` 该用哪个？** → 前者只看计划、不执行；后者真执行并给出 `actual time` / `rows` / `loops`，用来判断"估得准不准"。写语句别用后者在生产验证，它会真的跑一遍。
- **怎么确认优化器为什么没走某个索引？** → 开 `optimizer_trace` 看 `considered_execution_plans` 里那个计划的成本；临时验证用 hint（`/*+ */`）而不是改全局 `optimizer_switch`。
- **优化的总思路是什么？** → 两句话：**减少访问的行数、减少返回的列数**；再加一句"**最快的查询是不查**"（能缓存/预计算就别每次算）。
- **优化器为什么会选错索引？** → 统计信息是**采样估算**（可能失真）、成本模型假设值均匀分布、条件之间实际相关、JOIN 表多时放弃穷举。对策：`ANALYZE TABLE`、8.0 直方图、改写 SQL，`FORCE INDEX` 只作兜底。
- **优化器选全表扫描一定是问题吗？** → 不一定。判据是"**要读的行占总行数的比例**"，超过 20%~30% 时全扫可能更快（走二级索引要索引 + 回表两次）。先看 `rows`。
- **`COUNT(*)` 和 `COUNT(1)`、`COUNT(col)` 有什么区别？** → 前两者**完全等价**（8.0 执行计划相同）；`COUNT(col)` **会漏掉 NULL**，语义不同。**"`COUNT(1)` 更快"是错的**。
- **为什么 InnoDB 的 `COUNT(*)` 慢，MyISAM 的快？** → MyISAM 存了总行数（但带 `WHERE` 一样慢）；InnoDB 因为 MVCC，**"可见行数"取决于事务快照**，必须逐行判断。
- **`COUNT(*)` 怎么优化？** → 维护计数表/Redis（要接受一致性成本）、用近似值（`EXPLAIN` 的 `rows`）、或者**只判断"是否超过 N"**（`LIMIT 1001` 子查询，最实用）。
- **`filesort` 是怎么排的？** → 两种：**全字段排序**（把 `SELECT` 列都放进排序缓冲区）和 **rowid 排序**（只放排序键 + 主键，排完回表）。分界是单行长度与 `max_length_for_sort_data`（默认 1024 字节）。**`SELECT *` + `filesort` 会退化成 rowid 排序并大量回表**。
- **怎么让 `ORDER BY` 用上索引？** → 三个条件：列顺序与索引一致、排序方向一致、`WHERE` 是该索引的最左前缀**等值**条件（有范围条件后面的列就不有序了）。
- **`GROUP BY` 为什么慢？** → 没有合适的索引时会用**临时表 + filesort**（`Using temporary`）。分组键是索引最左前缀时能走松散/紧凑索引扫描。**8.0 起 `GROUP BY` 不再隐式排序**，老文章里的 `ORDER BY NULL` 技巧已过时。
- **JOIN 的核心优化点？** → 三条：**小表驱动大表**、**被驱动表的连接列必须有索引**（否则退化成 BNL）、**关联字段类型/字符集一致**（否则隐式转换让索引失效）。8.0.18+ 无索引时会自动用 Hash Join。
- **`Using temporary` 一定不好吗？** → 它是"需要临时表"的信号，通常要消除；但别看到就改 —— **小结果集用临时表代价很低**，为它多建一个索引往往更亏。
- **加索引能解决所有慢查询吗？** → 不能。分三个层次判断：**索引问题 / SQL 问题 / 架构问题**。用错层次的手段都是白费力气（比如用加索引去解决"深分页"或"每次要返回 10 万行"）。

- **游标分页的缺点？** → **不能随机跳页**（不能直接跳到第 500 页），
  只能"上一页/下一页"；适合 **feed 流、无限滚动**，不适合后台管理的页码跳转。
- **后台管理必须跳页怎么办？** → 如果表数据量大且必须支持跳页，
  考虑**限制最大页数**、**改用搜索条件收敛数据**、或用 **ES** 承接复杂分页。
- **`LIMIT 1000000, 10` 还能怎么优化？** → 先 `WHERE id > X` 缩小范围再 `LIMIT 10`；
  或**先只查主键**（`SELECT id ... LIMIT 1000000, 10`）**再回表关联**——
  这样回表只发生 10 次，而不是 100 万次。**这个技巧很实用。**

⚠️ 最后这条"先只查主键再回表"本机实测过，**收益比文案里听起来的小**：同一张 5 万行宽表上
`SELECT * ... OFFSET 40000` 是 15.8~17.1 ms，延迟关联是 **8.6~10.0 ms（约 1.6~2.0 倍）**，
而游标分页是 0.38~0.40 ms（约 40 倍）。原因是 **`OFFSET` 那 4 万条索引项照样要扫**，
延迟关联省掉的只是"把 4 万行宽数据交回服务端"这一段 —— 表越宽收益越大，但**它不治扫描**。
