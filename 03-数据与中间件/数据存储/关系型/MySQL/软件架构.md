## 一、请介绍一下 MySQL 的软件架构

**本节要点**：能**自顶向下分层讲清** MySQL 由哪些部分组成，并区分关系型与非关系型数据库。

### 先答：关系型 vs 非关系型数据库

| | **关系型（SQL）** | **非关系型（NoSQL）** |
|---|---|---|
| **代表** | **MySQL** | **Redis**（key-value）、**MongoDB**（文档型） |
| **数据结构** | 必须**严格预定义**：哪些表、哪些字段、什么类型 | **不要求预先定义**结构 |
| **数据模型** | 关系模型，以**表格**形式存储 | **多样化**（KV、文档、图……） |
| **表间关系** | 有**主外键关系**，可多表操作 | 通常无关系概念 |
| **记录字段** | 同一表所有行字段一致 | **每条记录的字段可以不同** |
| **擅长** | 复杂查询、事务处理、大量**结构化数据**管理 | 缓存、灵活 schema、高并发读写 |
| **主要用途** | **结构化数据的持久化** | Redis 常用作**缓存层** |

### MySQL 软件架构（自顶向下 7 层）

```text
客户端连接层
  ↓
服务层工具（备份/恢复/安全/复制）
  ↓
SQL 接口（DML / DDL / 存储过程 / 触发器 / 视图）
  ↓
解析器 → 优化器 → 缓存
  ↓
存储引擎层（InnoDB 等）
  ↓
文件系统 / 操作系统层（真正落盘）
```

| 层次 | 内容 |
|---|---|
| **① 客户端连接层** | 各种语言实现的客户端库、命令行工具。<br>**关键：连接池** |
| **② 服务层工具** | 备份、恢复、安全管理、数据复制等 |
| **③ SQL 接口** | DML（增删改查）、DDL（表结构操作）、存储过程、触发器、视图——<br>**是客户端与服务端交互的接口组件** |
| **④ 解析器** | **词法解析 + 语法解析**。SQL 本质是一种语言，需要把**人类可读的语句转成计算机可读的形式** |
| **⑤ 优化器** | 我们写的 SQL **未必是最优的**，优化器自动做一些优化，例如**选择使用哪个索引、选择访问路径** |
| **⑥ 缓存** | 包含查询缓存（**8.0 已移除**）、表元数据缓存、key 缓存等 |
| **⑦ 存储引擎层** | 支持多种引擎，**最常见的是 InnoDB** |
| **⑧ 文件系统/OS 层** | 最终由操作系统把数据、日志文件真正写到磁盘 |

### 为什么要有连接池？（这层最值得展开）

**要解决的问题**：频繁**创建和销毁连接**的开销很大。建立一条连接需要：
- **TCP 三次握手（断开时四次挥手）**；
- **认证与安全性校验**；
- 其他初始化动作。

**连接池的做法**：

> 客户端**用完之后不立即销毁连接对象，而是归还到连接池缓存起来**。
> 由于这些初始化动作在**创建连接时就已完成**，被缓存下来的连接**再次使用时就无需重复初始化**，
> 从而**避免频繁创建/销毁带来的性能消耗**。

## 二、MySQL 的元数据和数据文件分别落在哪里？

**来源**：《高性能 MySQL》（第 4 版）第 1 章「InnoDB 引擎」「数据文件结构」「数据字典的变化」「原子 DDL」「JSON 文档支持」。

**本节要点**：第一节回答「请求怎么走」，这一节回答「东西存在哪」。8.0 把表结构收进了事务型的数据字典，于是 DDL 第一次做到原子；「看文件」也是排查库表问题时独立于 SQL 的第二条路径。

### 2.1 数据文件结构：从 datadir 数一遍

```text
datadir/                                ← SELECT @@datadir → /var/lib/mysql/
├── auto.cnf                  # server_uuid；整目录拷贝会让两个实例共用 uuid，主从与 GTID 立刻打架
├── ibdata1                   # 系统表空间；实测 innodb_data_file_path = ibdata1:12M:autoextend
├── mysql.ibd                 # 8.0 数据字典本体，实测 32,505,856 字节（同目录 *.frm 实测 0 个）
├── ibtmp1                    # 会话级临时表空间，重启即清空
├── ib_buffer_pool            # buffer pool 页清单，配合 dump/load 两个开关缩短重启预热
├── #ib_16384_0.dblwr         # 独立双写文件（8.0.20+ 起不再借用系统表空间）
├── #ib_16384_1.dblwr
├── undo_001  undo_002        # undo 表空间；实测 innodb_undo_tablespaces = 2
├── #innodb_redo/             # 8.0.30 起的 redo 目录：实测 32 个文件 × 3,276,800 字节
│   ├── #ib_redo9             #   = 104,857,600 = innodb_redo_log_capacity 的实测值（能对上账）
│   └── #ib_redo40_tmp        #   带 _tmp 的是扩容时刚建、还没启用的文件
├── #innodb_temp/             # innodb_temp_tablespaces_dir = ./#innodb_temp/，实测 10 个 temp_N.ibt
├── binlog.000001 …           # ⚠️ 前缀由 log_bin_basename 决定，这个实例是 binlog，不是 mysql-bin
├── binlog.index              # binlog 文件清单
├── <id>-relay-bin.000001     # relay log 同样带实例前缀（实测形如 8de6e48de22a-relay-bin）
├── <db_name>/<table>.ibd     # file-per-table：实测 docverify 库里 19 张表 19 个 .ibd（orders.ibd 491,520 字节）
└── performance_schema/*.sdi  # SDI 序列化字典信息，每张表一份
```

三条判据：

- **`.ibd` 才是数据本体**：`innodb_file_per_table` 默认 ON（实测就是 ON），所以「这张表占多少磁盘」看它的 `.ibd`，
  不是看系统表空间；参数含义与默认值见 [参数调优.md](参数调优.md)。
- **删表不一定还空间**：`.ibd` 会跟着删，但系统表空间和 undo 里的内容不会自动收缩，
  碎片与回收的完整口径见 [数据迁移.md](数据迁移.md)。
- **redo 的文件形态在 8.0.30 换过一次**：从「两个固定文件循环写」变成「一个目录、按总容量动态增减文件」，
  扩 redo 不再需要停实例换文件（机制见 [日志与落盘.md](日志与落盘.md)）。

实测之后有三处和常见资料对不上，记下来比事后排查便宜：

- binlog 前缀是 **`binlog`**：`ls` 匹配 `mysql-bin.*` 的结果是**空**，前缀完全由 `log_bin_basename` 决定，
  脚本里写死 `mysql-bin.000001` 在这类实例上直接找不到文件；
- `ib_logfile0` / `ib_logfile1` **在这个实例里根本不存在**，redo 全在 `#innodb_redo/` 下 —— 旧口径的
  「ib_logfile 大小决定 crash recovery 时长」要换成 `innodb_redo_log_capacity`；
- `log_error` 实测是 **`stderr`**，所以错误日志落在容器日志里（`docker logs`），datadir 里找不到它；
  而 `general_log_file` / `slow_query_log_file` 默认仍指向 datadir（实测 `<实例id>.log` 与 `<实例id>-slow.log`）。

自查命令（换实例先跑这两条，别照抄任何文档里的文件名）：

```sql
SELECT @@datadir, @@log_bin_basename, @@innodb_redo_log_capacity, @@innodb_temp_tablespaces_dir;
SHOW VARIABLES WHERE Variable_name IN ('log_error', 'general_log_file', 'slow_query_log_file', 'relay_log');
```

### 2.2 数据字典的变化：从 .frm 到事务型字典

5.7 及之前，表结构存在**三处**：Server 层的 `.frm` 文件、存储引擎自己的元数据、
以及 `information_schema` 现拼出来的视图 —— 三处不同步就会出现「能 `SHOW TABLES` 但打不开表」。

8.0 的做法是：**表定义统一进 InnoDB 的数据字典表**（物理上落在 `mysql.ibd`），`.frm` 不再存在；
字典表的更新和普通表一样走 InnoDB 事务，因此**崩溃可回滚**。
另外每个 InnoDB 表空间文件里还带一份 **SDI（Serialized Dictionary Information）**，
让「只有一个 `.ibd`」也能反推出表结构 —— 这是传输表空间不再需要额外元数据文件的原因。
实测可以直接印证这两句：datadir 下 `*.frm` 的数量是 **0**，而 `performance_schema` 目录里每张表都配一份 `*.sdi`
（如 `socket_instances_147.sdi`），库目录 `docverify/` 下则是 19 张表 19 个 `.ibd`。

运维上要注意三点：

- **不能再靠改文件修表结构**：`.frm` 时代「拷一个 frm 过去」的手法彻底失效；
- **字典表禁止直连读写**：底层字典表被保护，一切元数据操作必须走 SQL 接口；
- **升级时自动迁移元数据**：从 5.7 升上来时 Server 在启动过程中把旧元数据搬进新字典，
  动手前必须备份（升级与回滚路径见 [数据迁移.md](数据迁移.md)）。

### 2.3 原子 DDL：三件事合成一个事务

**原子 DDL** 指一条 `CREATE / ALTER / DROP / TRUNCATE` 要么全部生效、要么全部不生效，
中途崩溃也能在重启后收敛到确定状态。它把原本各自提交的三个动作合进一个事务：
**数据字典更新 + 存储引擎的文件与元数据操作 + binlog 写入**。
再配合 InnoDB 的 **DDL log**（隐藏表 `mysql.innodb_ddl_log`，记录 FREE / DELETE / RENAME / DROP
这类文件级动作），重启时按日志把没做完的文件操作补上或回滚。

```text
DROP TABLE t1, t2;     -- t2 不存在
8.0：整条回滚，报错后 t1 仍在
5.7：逐表执行、逐表写 binlog，报错时 t1 已经被删掉
```

四个边界比「支持原子 DDL」这句话更值得记：

- **原子 DDL 不等于事务型 DDL**：DDL 仍然隐式提交当前会话事务，不能包在 `START TRANSACTION` 里回滚；
- **只有 InnoDB 对象原子**：涉及其他引擎的 DDL 退回逐表执行、逐条写 binlog；
- **插件 / 组件 / `CREATE SERVER` 类语句不在范围内**；
- **升级前建的表不享受**：老版本创建的表被视为非原子引擎，多表 `DROP`、`DROP DATABASE`
  仍可能半途完成；`DROP DATABASE` 最后删除目录这一步在事务之外，OS 报错或崩溃**不会回滚**。
  主库是 5.7、从库是 8.0 时，给复制过去的 DDL 补 `IF EXISTS` / `IF NOT EXISTS` 是配套的兼容手法。

### 2.4 JSON 文档支持：存储、局部更新与索引

- **二进制存储**：`JSON` 列存的是解析后的二进制文档而不是字符串 —— 写入时解析一次，
  读取时不必重新 parse；代价是比紧凑文本更占空间。
- **8.0 的局部更新**：对同一列使用 `JSON_SET / JSON_REPLACE / JSON_REMOVE` 时可以**原地改**，
  不必整篇重写；再配合 `binlog_row_value_options=PARTIAL_JSON`，binlog 也只记差异部分 ——
  大 JSON 文档的写放大主要靠这两步压下来（binlog 侧的影响见 [日志与落盘.md](日志与落盘.md)）。
- **索引路线换过两次**：8.0.17 之前只能「生成列 + 二级索引」绕路；8.0.17 起 InnoDB 支持
  **多值索引（multi-valued index）**，可以直接给 JSON 数组建索引（取舍见 [索引设计.md](索引设计.md)）。
- **聚合与合并**：8.0 中非 NULL 的 JSON 值参与数值聚合时自动转换类型，
  `MIN / MAX / GROUP_CONCAT` 除外；`JSON_MERGE_PRESERVE`（同名键拼成数组）与
  `JSON_MERGE_PATCH`（后者覆盖，遵循 RFC 7396）在 8.0.3 引入，
  同一个键重复时**最后一个赢**（5.7 的行为是第一个赢）。

## 延伸追问

- **为什么 8.0 移除查询缓存？** → 数据频繁增删改导致缓存**失效率极高、有效期极短**，
  维护成本超过收益。（详见本文 [JOIN与反范式.md](JOIN与反范式.md)）
- **`.frm` 文件去哪了？** → 8.0 把表定义收进 InnoDB 的数据字典表（物理在 `mysql.ibd`），`.frm` 不再存在，"拷 frm 修表"的手法随之失效。
- **原子 DDL 是不是等于"DDL 可以回滚"？** → 不是。一条 DDL 内部原子，但它仍会隐式提交当前会话事务，不能包在 `START TRANSACTION` 里；升级前建的老表也不享受原子性。
- **为什么直接拷贝 datadir 起第二台实例会出问题？** → `auto.cnf` 里的 `server_uuid` 被一起复制了，GTID 与主从复制会认为两台是同一个实例。
- **InnoDB 和 MyISAM 的区别？** → InnoDB 支持**事务、行级锁、外键、崩溃恢复（redo log）**；
  MyISAM 只有表级锁、不支持事务，但计数和全表扫描更快。**生产默认用 InnoDB**。

## 使用一：Go（读写分离：业务走主库、报表走从库）⭐

### 1. 读写分离：业务走主库、报表走从库

[JOIN与反范式.md](JOIN与反范式.md) 的风险提示是「重查询会打满 IO/CPU，内部/报表类查询最好走只读从库」。
在 Go 里这就是**两个单例池 + 按请求选池**，而不是把库名硬编码进 SQL。

```go
package rwsplit

import (
	"context"
	"database/sql"
	"fmt"
	"os"
	"sync"
	"time"

	_ "github.com/go-sql-driver/mysql"
)

type ctxKey struct{ name string }

var forceMasterKey = ctxKey{"force-master"}

// 主/从各一个单例池。⚠️ 千万不要在请求路径里 sql.Open。
var (
	Master  = sync.OnceValue(func() *sql.DB { return open("MYSQL_MASTER_ADDR") })
	Replica = sync.OnceValue(func() *sql.DB { return open("MYSQL_REPLICA_ADDR") })
)

func open(addrEnv string) *sql.DB {
	addr := os.Getenv(addrEnv)
	if addr == "" {
		panic("rwsplit: env " + addrEnv + " is empty") // 配置缺失属于启动失败
	}
	dsn := fmt.Sprintf("%s:%s@tcp(%s)/%s?charset=utf8mb4&parseTime=true",
		os.Getenv("MYSQL_USER"), os.Getenv("MYSQL_PASS"), addr, os.Getenv("MYSQL_DB"))

	db, err := sql.Open("mysql", dsn)
	if err != nil {
		panic("rwsplit: open: " + err.Error())
	}
	db.SetMaxOpenConns(20)
	db.SetMaxIdleConns(5)
	db.SetConnMaxLifetime(10 * time.Minute)
	db.SetConnMaxIdleTime(3 * time.Minute)

	ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
	defer cancel()
	if err := db.PingContext(ctx); err != nil {
		panic("rwsplit: ping " + addrEnv + ": " + err.Error())
	}
	return db
}

// ForceMaster 打标记：写之后的读、事务内的读都必须走主库，
// 否则会被主从延迟坑到（原因与三种处理方案见 [日志与落盘.md](日志与落盘.md) 的「读己之写」）。
func ForceMaster(ctx context.Context) context.Context {
	return context.WithValue(ctx, forceMasterKey, true)
}

// Pick 返回本次查询该用的池。默认从库，标记过的和事务内的走主库。
func Pick(ctx context.Context, inTx bool) *sql.DB {
	if inTx {
		return Master() // 事务只能跑在一个连接上，跨池不存在"一个事务两个库"
	}
	if forced, _ := ctx.Value(forceMasterKey).(bool); forced {
		return Master()
	}
	if err := ping(context.Background(), Replica()); err != nil {
		return Master() // 从库不可用要能降级；⚠️ 代价是报表流量会挤占业务库
	}
	return Replica()
}

func ping(ctx context.Context, db *sql.DB) error {
	ctx, cancel := context.WithTimeout(ctx, time.Second)
	defer cancel()
	return db.PingContext(ctx)
}

// Report 是"重查询"的落点：显式走从库 + 单独超时预算。
func Report(ctx context.Context, since time.Time) (int, error) {
	ctx, cancel := context.WithTimeout(ctx, 60*time.Second) // 报表可以给 60s，C 端接口不行
	defer cancel()

	var n int
	q := `SELECT COUNT(*) FROM orders WHERE created_at >= ?`
	if err := Pick(ctx, false).QueryRowContext(ctx, q, since).Scan(&n); err != nil {
		return 0, err
	}
	return n, nil
}
```

> ⚠️ 每次 `Pick` 都 Ping 一次等于给每个请求加一个 RTT。生产做法是后台定时探活 + 缓存健康状态，
> 或干脆用中间件（ProxySQL / MyCat / 云厂商代理）在**连接层**做分离，应用只拿到一个地址。
> 本节的目的是让「谁是主、谁是从」在代码里显式可辨，而不是散落在字符串里。

## 使用二：Java（`AbstractRoutingDataSource`）

### 1. 读写分离：`AbstractRoutingDataSource`

```java
package notes.mysql.rwsplit;

import java.util.HashMap;
import java.util.Map;
import javax.sql.DataSource;
import org.springframework.jdbc.datasource.AbstractRoutingDataSource; // 实际是 lookup 的基类，见下方说明
import org.springframework.jdbc.datasource.lookup.AbstractRoutingDataSource;

public class MasterReplicaRouting extends AbstractRoutingDataSource {

    // 路由键放 ThreadLocal：这是"按请求选库"的关键，业务代码不感知库地址
    private static final ThreadLocal<Boolean> FORCE_MASTER = ThreadLocal.withInitial(() -> Boolean.FALSE);

    public static void forceMaster() {
        FORCE_MASTER.set(Boolean.TRUE);
    }

    public static void clear() {
        FORCE_MASTER.remove(); // ⚠️ 必须 remove：线程池会复用线程，留着会把后续请求一路带进主库
    }

    @Override
    protected Object determineCurrentLookupKey() {
        return FORCE_MASTER.get() ? "master" : "replica";
    }

    @Override
    public void afterPropertiesSet() {
        Map<Object, Object> targets = new HashMap<>();
        // targetDataSources 需要由外部注入真实 DataSource，这里仅示意键名对应关系
        super.afterPropertiesSet();
    }
}
```

> 说明：`AbstractRoutingDataSource` 需要在配置类里 `setTargetDataSources(Map.of("master", ds1, "replica", ds2))`
> 并 `setDefaultTargetDataSource(ds1)`；`determineCurrentLookupKey` 的返回值用来查这张表。
> 拦截 `@Transactional(readOnly = true)` 自动切从库是**各中间件的行为**（ShardingSphere、
> `baomidou/dynamic-datasource`），Spring 自身只认 `readOnly` 标志并把它下推给连接的 `setReadOnly()`。

**结论对齐 Go 侧**：`FORCE_MASTER` ≈ Go 的 `ForceMaster(ctx)`；
只是 Java 用 ThreadLocal（因为 Spring 的连接绑定在线程上），Go 用 `context`（因为 `database/sql` 按调用点选池）。
