## 一、MySQL 的整体架构是怎样的？

**本节要点**：能**自顶向下分层讲清** MySQL 由哪些部分组成，并先分清关系型与非关系型的定位差异。

### 1.1 先分清定位：关系型 vs 非关系型

|          | **关系型（SQL）**              | **非关系型（NoSQL）**                       |
| -------- | ------------------------- | ------------------------------------- |
| **代表**   | **MySQL**                 | **Redis**（key-value）、**MongoDB**（文档型） |
| **数据结构** | 必须**严格预定义**：哪些表、哪些字段、什么类型 | **不要求预先定义**结构                         |
| **数据模型** | 关系模型，以**表格**形式存储          | **多样化**（KV、文档、图……）                    |
| **表间关系** | 有**主外键关系**，可多表操作          | 通常无关系概念                               |
| **记录字段** | 同一表所有行字段一致                | **每条记录的字段可以不同**                       |
| **擅长**   | 复杂查询、事务处理、大量**结构化数据**管理   | 缓存、灵活 schema、高并发读写                    |
| **主要用途** | **结构化数据的持久化**             | Redis 常用作**缓存层**                      |

### 1.2 自顶向下 7 层

```text
客户端连接层
  ↓
服务层工具（备份/恢复/安全/复制）
  ↓
SQL 接口（DML / DDL / 存储过程 / 触发器 / 视图）
  ↓
解析器 → 优化器 → 缓存
  ↓
存储引擎层（InnoDB 等）
  ↓
文件系统 / 操作系统层（真正落盘）
```

| 层次              | 内容                                                          |
| --------------- | ----------------------------------------------------------- |
| **① 客户端连接层**    | 各种语言实现的客户端库、命令行工具。<br />**关键：连接池**                          |
| **② 服务层工具**     | 备份、恢复、安全管理、数据复制等                                            |
| **③ SQL 接口**    | DML（增删改查）、DDL（表结构操作）、存储过程、触发器、视图——<br />**是客户端与服务端交互的接口组件** |
| **④ 解析器**       | **词法解析 + 语法解析**。SQL 本质是一种语言，需要把**人类可读的语句转成计算机可读的形式**        |
| **⑤ 优化器**       | 我们写的 SQL **未必是最优的**，优化器自动做一些优化，例如**选择使用哪个索引、选择访问路径**        |
| **⑥ 缓存**        | 包含查询缓存（**8.0 已移除**）、表元数据缓存、key 缓存等                          |
| **⑦ 存储引擎层**     | 支持多种引擎，**最常见的是 InnoDB**                                     |
| **⑧ 文件系统/OS 层** | 最终由操作系统把数据、日志文件真正写到磁盘                                       |

## 二、一条 SQL 从连接到返回经历了哪些环节？

**本节要点**：要能**按顺序说出整条链路**，并指出 8.0 之后被移除的是哪一环。

### 2.1 完整链路（7 步）

```text
客户端 → ① 查询缓存 → ② 解析器 → ③ 预处理器 → ④ 查询优化器
      → ⑤ 执行引擎 → ⑥ 存储引擎 → ⑦ 返回结果
```

| 步骤           | 做什么                                                                 |
| ------------ | ------------------------------------------------------------------- |
| **① 查询缓存**   | 根据 SQL 语句**直接找缓存的结果集**，命中就直接返回。<br />⚠️ **MySQL 8.0 已移除**（8.0 之前存在） |
| **② 解析器**    | **词法解析 + 语法解析**，检查 SQL 是否符合语法规则                                     |
| **③ 预处理器**   | 验证**对象是否存在**、**权限校验**、**处理默认值**等，形成新的解析树                            |
| **④ 查询优化器**  | 生成**执行计划**，选择最优访问路径。<br />执行计划**通常不缓存**，除非使用**预编译语句**               |
| **⑤ 查询执行引擎** | 按执行计划，通过 **API 接口**调用存储引擎                                           |
| **⑥ 存储引擎**   | 从 Buffer Pool / 磁盘取数据（InnoDB）                                       |
| **⑦ 返回结果**   | 结果集返回给客户端                                                           |

### 2.2 为什么 8.0 要移除查询缓存？

> MySQL 主要是**增删改查混合**的负载。一旦表上有任何写操作，**该表相关的查询缓存会全部失效**。  
> 结果就是：**缓存的有效期极短、命中率极低**，维护缓存的成本反而超过收益。
>
> 所以 8.0 干脆**移除了查询缓存**——这也解释了为什么现在主流做法是**在应用层用 Redis 做缓存**。

## 三、连接层与连接池省了什么？

**本节要点**：连接的**建立开销**在哪、连接池复用了什么又没复用掉什么，  
四个池参数分别管什么、多个实例一起部署时连接位怎么分。

### 3.1 建一条连接要付哪些开销

**要解决的问题**：频繁**创建和销毁连接**的开销很大。建立一条连接需要：

- **TCP 三次握手（断开时四次挥手）**；
- **认证与安全性校验**；
- 其他初始化动作。

**连接池的做法**：

> 客户端**用完之后不立即销毁连接对象，而是归还到连接池缓存起来**。  
> 由于这些初始化动作在**创建连接时就已完成**，被缓存下来的连接**再次使用时就无需重复初始化**，  
> 从而**避免频繁创建/销毁带来的性能消耗**。

### 3.2 池参数的四个关键值

连接池有两处：**客户端**（Go 的 `database/sql`、Java 的 HikariCP）和**中间件**（ProxySQL / MySQL Router）。  
参数名不同，语义一一对应：

| Go `*sql.DB` 方法      | HikariCP          | 管什么                      | 配错的典型症状                                                |
| -------------------- | ----------------- | ------------------------ | ------------------------------------------------------ |
| `SetMaxOpenConns`    | `maximumPoolSize` | 池里**最多几条活着的连接**（在用 + 空闲） | 太小 → 请求排队等连接；太大 → 打爆服务端 `max_connections`              |
| `SetMaxIdleConns`    | `minimumIdle`     | 最多**保留几条空闲连接**           | 默认只有 **2**；`MaxOpen` 调到 100 而它不跟着调，就退化成"用一条建一条、还一条关一条" |
| `SetConnMaxLifetime` | `maxLifetime`     | 一条连接**最长活多久**            | 不设（默认永不过期）→ 连接被 LB / 中间件在背后掐断，客户端下次用时报错                |
| `SetConnMaxIdleTime` | `idleTimeout`     | **空闲**多久后关闭              | 不设 → 空闲连接长期占着服务端线程；设太短又退化成不复用                          |

⭐ Go 标准库的默认值恰好是最容易踩的一组（`database/sql/sql.go:960`  
`const defaultMaxIdleConns = 2`；`sql.go:530` 注释 `zero means defaultMaxIdleConns`）：  
**`MaxOpen` 无限、`MaxIdle` 只有 2、两个超时都是 0（永不过期）**。  
名字叫"池"，但默认配置下并发一上来，空闲连接会被压回 2 条，超出部分**用完就关** ——  
复用被悄悄退化成了"按峰值反复建销"。所以这四个参数生产上**必须显式设**，且 `MaxIdle` 要跟 `MaxOpen` 一起调。

⚠️ 还有一条常被忽略的账：**连接池复用不掉的，是每条连接占的服务端内存**。  
握手、认证、线程初始化可以复用，但连接本身在服务端持有的会话级缓冲区  
（`read_buffer_size` / `sort_buffer_size` / `join_buffer_size` …）是**每连接一份** ——  
这部分账在 [参数调优.md](参数调优.md) 的"内存账"一节。

### 3.3 多实例部署时的连接预算

服务端的闸门是 `max_connections` —— 实测 8.0.46 默认 **151**：

```text
+------------------------------+-----------+
| Variable_name                | Value     |
+------------------------------+-----------+
| max_connections              | 151       |
| back_log                     | 151       |
| thread_cache_size            | 9         |
+------------------------------+-----------+
```

它约束的是**服务端同时接受的连接数**，而池配在**客户端** —— 两边分开配，于是最常见的翻车方式是：  
每个服务实例都按"独占"的思路配池，实例数一多就把服务端的连接位吃光。

预算按最坏情况算：

```text
Σ(每个应用实例的 MaxOpenConns) + 运维/备份/监控预留 ≤ max_connections
```

`max_connections = 151` 时，预留 20 条给运维与监控，剩 131 条分给业务：  
服务有 8 个实例，单实例的池**最多 16** —— 而不是拍脑袋写 100。

⚠️ 两条容易搞反的：

1. **连接池大小 ≠ 并发能力**。它只是"同时在跑的 SQL 条数"；真正决定吞吐的是服务端  
   **CPU 核数**（见 [参数调优.md](参数调优.md) 的"配置 MySQL 并发"一节）。  
   池配得远大于核数，只是把请求从客户端排队挪到服务端排队。
2. **`Threads_created` 是"池有没有真的复用"的裁判**。它**只增不减**；涨得比应用实例数快，  
   就说明连接在反复建销（池没配好、或 `MaxLifetime` 短于中间件的空闲回收）。  
   本机实例刚起时的基线是 `Threads_created = 1` / `Threads_cached = 0` / `Threads_connected = 1`  
   —— 只有一条连接时缓存还没生效，这是正常的，别拿它当"池没工作"的证据。

## 四、预编译与执行计划

**本节要点**：预编译在**服务端**到底做了什么、执行计划缓存在哪一层。

### 4.1 服务端 Prepared Statement 的工作机制

> 如果 SQL 使用**预编译（占位符 `?`）**，执行计划会被**提前申请并缓存**，  
> 真正查询时只需把参数替换进去，**省掉了每次重新解析和生成执行计划的开销**。  
> 这也是 Go 里 `database/sql` 的 `Prepare` 和各类 ORM 的**预编译逻辑**的收益来源，  
> 同时它还**天然防 SQL 注入**（参数与语句分离）。

> ⭐ `PREPARE` 的完整生命周期（`Com_stmt_prepare` / `Com_stmt_execute` 计数怎么读、  
> `Prepared_stmt_count` 为什么不是"每连接一份"）在本文「使用一：Go」里逐条实测过；  
> **文本拼接 / 占位符 / 显式 `Prepare` 三种写法的网络往返、计划缓存与安全对照，也在那里**，此处不重复。

## 五、InnoDB 与 MyISAM 的架构差异

**本节要点**：一张能力表说清两者差在哪，以及为什么新建表**没有理由**再选 MyISAM。

### 5.1 五个维度的对照

`information_schema.ENGINES` 直接给出各引擎的**能力声明**（实测 8.0.46，按 `SUPPORT` 排序、节选）：

```text
+--------------------+---------+--------------+------+------------+
| ENGINE             | SUPPORT | TRANSACTIONS | XA   | SAVEPOINTS |
+--------------------+---------+--------------+------+------------+
| InnoDB             | DEFAULT | YES          | YES  | YES        |
| MyISAM             | YES     | NO           | NO   | NO         |
| MEMORY             | YES     | NO           | NO   | NO         |
| ARCHIVE            | YES     | NO           | NO   | NO         |
| BLACKHOLE          | YES     | NO           | NO   | NO         |
+--------------------+---------+--------------+------+------------+
```

`TRANSACTIONS` 这一列就是分水岭 —— **只有 InnoDB 是 YES**，而它带来的一整条链是连着的：

| 维度       | InnoDB                | MyISAM                         |
| -------- | --------------------- | ------------------------------ |
| **事务**   | 支持（ACID）              | ❌ 不支持                          |
| **锁粒度**  | **行级锁**（默认），只锁相关行     | **表级锁**，一写全表阻塞                 |
| **崩溃恢复** | redo log 前滚 + undo 回滚 | ❌ 没有；崩溃后表可能损坏，要 `REPAIR TABLE` |
| **外键**   | 支持                    | ❌ 不支持（解析后忽略）                   |
| **索引结构** | 聚簇索引：数据就是主键索引的叶子      | 非聚簇：索引与数据分离，`SELECT *` 一律回表    |
| **行数**   | `COUNT(*)` 要扫索引       | 有计数器，**不带 `WHERE`** 时直接返回      |
| **数据文件** | 表空间 `.ibd`（可独立、可传输）   | `.MYD` + `.MYI` 两件套            |
| **空间占用** | 通常更大（MVCC 版本、页填充）     | 更小                             |

⚠️ 「MyISAM 的 `COUNT(*)` 更快」这条**只在没有 `WHERE` 时成立** —— 它读的是元数据里的计数器；  
一旦带上条件，两者都要扫。

### 5.2 为什么生产默认 InnoDB

三条理由，按重要性排：

1. **事务是业务的地基**。没有事务，就没有"要么全成功、要么全回滚"，也没有 MVCC 提供的快照读；  
   并发控制、崩溃恢复、主从复制的一致性语义全都建立在它上面（见  
   [事务与隔离级别.md](事务与隔离级别.md)、[日志与持久化.md](日志与持久化.md)）。
2. **行级锁决定了并发上限**。MyISAM 的表级锁意味着"两个人改同一张表的不同行"也要排队 ——  
   写入稍多就互相阻塞，这在互联网业务里不可接受。
3. **崩溃后能自愈**。InnoDB 靠 redo log 前滚已提交事务、undo 回滚未提交事务，断电重启就能恢复到一致状态；  
   MyISAM 崩溃后需要人工 `REPAIR TABLE`，数据还可能丢。

那 MyISAM 现在还有用吗 —— **只在两种窄场景**：① 历史遗留的只读表（换引擎要重建，收益不划算）；  
② 纯归档、写一次读多次、且能接受崩溃后重建的表。**新建表没有理由选它**。

## 六、文件与数据字典落在哪里？

**本节要点**：`datadir` 里到底有哪几类文件、8.0 的**数据字典**从 `.frm` 换成了什么、  
原子 DDL 把哪三件事合进了一个事务。

### 6.1 数据文件结构：从 datadir 数一遍

```text
datadir/                                ← SELECT @@datadir → /var/lib/mysql/
├── auto.cnf                  # server_uuid；整目录拷贝会让两个实例共用 uuid，主从与 GTID 立刻打架
├── ibdata1                   # 系统表空间；实测 innodb_data_file_path = ibdata1:12M:autoextend
├── mysql.ibd                 # 8.0 数据字典本体，实测 32,505,856 字节（同目录 *.frm 实测 0 个）
├── ibtmp1                    # 会话级临时表空间，重启即清空
├── ib_buffer_pool            # buffer pool 页清单，配合 dump/load 两个开关缩短重启预热
├── #ib_16384_0.dblwr         # 独立双写文件（8.0.20+ 起不再借用系统表空间）
├── #ib_16384_1.dblwr
├── undo_001  undo_002        # undo 表空间；实测 innodb_undo_tablespaces = 2
├── #innodb_redo/             # 8.0.30 起的 redo 目录：实测 32 个文件 × 3,276,800 字节
│   ├── #ib_redo9             #   = 104,857,600 = innodb_redo_log_capacity 的实测值（能对上账）
│   └── #ib_redo40_tmp        #   带 _tmp 的是扩容时刚建、还没启用的文件
├── #innodb_temp/             # innodb_temp_tablespaces_dir = ./#innodb_temp/，实测 10 个 temp_N.ibt
├── binlog.000001 …           # ⚠️ 前缀由 log_bin_basename 决定，这个实例是 binlog，不是 mysql-bin
├── binlog.index              # binlog 文件清单
├── <id>-relay-bin.000001     # relay log 同样带实例前缀（实测形如 8de6e48de22a-relay-bin）
├── <db_name>/<table>.ibd     # file-per-table：实测 docverify 库里 19 张表 19 个 .ibd（orders.ibd 491,520 字节）
└── performance_schema/*.sdi  # SDI 序列化字典信息，每张表一份
```

三条判据：

- **`.ibd` 才是数据本体**：`innodb_file_per_table` 默认 ON（实测就是 ON），所以「这张表占多少磁盘」看它的 `.ibd`，  
  不是看系统表空间；参数含义与默认值见 [参数调优.md](参数调优.md)。
- **删表不一定还空间**：`.ibd` 会跟着删，但系统表空间和 undo 里的内容不会自动收缩，  
  碎片与回收的完整口径见 [数据迁移与备份恢复.md](数据迁移与备份恢复.md)。
- **redo 的文件形态在 8.0.30 换过一次**：从「两个固定文件循环写」变成「一个目录、按总容量动态增减文件」，  
  扩 redo 不再需要停实例换文件（机制见 [日志与持久化.md](日志与持久化.md)）。

实测之后有三处和常见资料对不上，记下来比事后排查便宜：

- binlog 前缀是 **`binlog`**：`ls` 匹配 `mysql-bin.*` 的结果是**空**，前缀完全由 `log_bin_basename` 决定，  
  脚本里写死 `mysql-bin.000001` 在这类实例上直接找不到文件；
- `ib_logfile0` / `ib_logfile1` **在这个实例里根本不存在**，redo 全在 `#innodb_redo/` 下 —— 旧口径的  
  「ib_logfile 大小决定 crash recovery 时长」要换成 `innodb_redo_log_capacity`；
- `log_error` 实测是 **`stderr`**，所以错误日志落在容器日志里（`docker logs`），datadir 里找不到它；  
  而 `general_log_file` / `slow_query_log_file` 默认仍指向 datadir（实测 `<实例id>.log` 与 `<实例id>-slow.log`）。

自查命令（换实例先跑这两条，别照抄任何文档里的文件名）：

```sql
SELECT @@datadir, @@log_bin_basename, @@innodb_redo_log_capacity, @@innodb_temp_tablespaces_dir;
SHOW VARIABLES WHERE Variable_name IN ('log_error', 'general_log_file', 'slow_query_log_file', 'relay_log');
```

### 6.2 数据字典的变化：从 .frm 到事务型字典

5.7 及之前，表结构存在**三处**：Server 层的 `.frm` 文件、存储引擎自己的元数据、  
以及 `information_schema` 现拼出来的视图 —— 三处不同步就会出现「能 `SHOW TABLES` 但打不开表」。

8.0 的做法是：**表定义统一进 InnoDB 的数据字典表**（物理上落在 `mysql.ibd`），`.frm` 不再存在；  
字典表的更新和普通表一样走 InnoDB 事务，因此**崩溃可回滚**。  
另外每个 InnoDB 表空间文件里还带一份 **SDI（Serialized Dictionary Information）**，  
让「只有一个 `.ibd`」也能反推出表结构 —— 这是传输表空间不再需要额外元数据文件的原因。  
实测可以直接印证这两句：datadir 下 `*.frm` 的数量是 **0**，而 `performance_schema` 目录里每张表都配一份 `*.sdi`  
（如 `socket_instances_147.sdi`），库目录 `docverify/` 下则是 19 张表 19 个 `.ibd`。

运维上要注意三点：

- **不能再靠改文件修表结构**：`.frm` 时代「拷一个 frm 过去」的手法彻底失效；
- **字典表禁止直连读写**：底层字典表被保护，一切元数据操作必须走 SQL 接口；
- **升级时自动迁移元数据**：从 5.7 升上来时 Server 在启动过程中把旧元数据搬进新字典，  
  动手前必须备份（升级与回滚路径见 [数据迁移与备份恢复.md](数据迁移与备份恢复.md)）。


### 6.3 原子 DDL：三件事合成一个事务

**原子 DDL** 指一条 `CREATE / ALTER / DROP / TRUNCATE` 要么全部生效、要么全部不生效，
中途崩溃也能在重启后收敛到确定状态。它把原本各自提交的三个动作合进一个事务：
**数据字典更新 + 存储引擎的文件与元数据操作 + binlog 写入**。
再配合 InnoDB 的 **DDL log**（隐藏表 `mysql.innodb_ddl_log`，记录 FREE / DELETE / RENAME / DROP
这类文件级动作），重启时按日志把没做完的文件操作补上或回滚。

```text
DROP TABLE t1, t2;     -- t2 不存在
8.0：整条回滚，报错后 t1 仍在
5.7：逐表执行、逐表写 binlog，报错时 t1 已经被删掉
```

四个边界比「支持原子 DDL」这句话更值得记：

- **原子 DDL 不等于事务型 DDL**：DDL 仍然隐式提交当前会话事务，不能包在 `START TRANSACTION` 里回滚；
- **只有 InnoDB 对象原子**：涉及其他引擎的 DDL 退回逐表执行、逐条写 binlog；
- **插件 / 组件 / `CREATE SERVER` 类语句不在范围内**；
- **升级前建的表不享受**：老版本创建的表被视为非原子引擎，多表 `DROP`、`DROP DATABASE`
  仍可能半途完成；`DROP DATABASE` 最后删除目录这一步在事务之外，OS 报错或崩溃**不会回滚**。
  主库是 5.7、从库是 8.0 时，给复制过去的 DDL 补 `IF EXISTS` / `IF NOT EXISTS` 是配套的兼容手法。

### 6.4 JSON 文档支持：存储、局部更新与索引

- **二进制存储**：`JSON` 列存的是解析后的二进制文档而不是字符串 —— 写入时解析一次，
  读取时不必重新 parse；代价是比紧凑文本更占空间。
- **8.0 的局部更新**：对同一列使用 `JSON_SET / JSON_REPLACE / JSON_REMOVE` 时可以**原地改**，
  不必整篇重写；再配合 `binlog_row_value_options=PARTIAL_JSON`，binlog 也只记差异部分 ——
  大 JSON 文档的写放大主要靠这两步压下来（binlog 侧的影响见 [日志与持久化.md](日志与持久化.md)）。
- **索引路线换过两次**：8.0.17 之前只能「生成列 + 二级索引」绕路；8.0.17 起 InnoDB 支持
  **多值索引（multi-valued index）**，可以直接给 JSON 数组建索引（取舍见 [索引设计与EXPLAIN.md](索引设计与EXPLAIN.md)）。
- **聚合与合并**：8.0 中非 NULL 的 JSON 值参与数值聚合时自动转换类型，
  `MIN / MAX / GROUP_CONCAT` 除外；`JSON_MERGE_PRESERVE`（同名键拼成数组）与
  `JSON_MERGE_PATCH`（后者覆盖，遵循 RFC 7396）在 8.0.3 引入，
  同一个键重复时**最后一个赢**（5.7 的行为是第一个赢）。

## 使用一：Go（预编译 + 读写分离）⭐

### 1. 预编译：什么时候真的省了开销

第一节说的「预编译能缓存执行计划」，在 Go 里要拆成三种情况，否则容易配反 DSN：

| 情况 | 网络往返 | 执行计划 | 说明 |
|---|---|---|---|
| `db.Query(sql, args...)` + **未开** `interpolateParams` | 首次 `PREPARE`+`EXECUTE`，之后只 `EXECUTE` | **服务端缓存** | 驱动按**连接**缓存 prepared statement（LRU，上限 1000 条）。同一条 SQL 文本命中同一连接即省掉解析 |
| `db.Query(sql, args...)` + **开了** `interpolateParams=true` | 一次 `COM_QUERY` | 每次都要重新解析 | 驱动在客户端把参数转义后拼进去。**转义由驱动完成，仍然防注入**，但拿不到计划缓存 |
| 字符串拼 SQL | 一次 `COM_QUERY` | 每次都要重新解析 | ❌ **唯一真正危险的写法**：值里一个引号就能改写语义 |

**选型结论**：核心高频链路（SQL 文本固定、QPS 高）关掉 `interpolateParams`，让计划缓存生效；
低频、极在意一次往返的场景可以开着它换 RTT。两种模式下**都禁止手写拼接**。

```go
package prepstmt

import (
	"context"
	"database/sql"
	"strings"
)

// ✗ 反例：拼字符串。author 传 "x' OR '1'='1" 就把 WHERE 条件整个改写了。
func badListByAuthor(ctx context.Context, db *sql.DB, author string) (string, error) {
	q := "SELECT id FROM article WHERE author = '" + author + "'"
	var id int64
	err := db.QueryRowContext(ctx, q).Scan(&id)
	return q, err // 返回 q 只是为了让这一行不被编译器判为无用，业务里应直接删掉
}

// Placeholders 生成 "?, ?, ?"，这是唯一安全的"动态拼 SQL"方式：
// 拼进去的只有占位符，值永远走参数，不参与 SQL 语法解析。
func Placeholders(n int) string {
	return strings.TrimSuffix(strings.Repeat("?, ", n), ", ")
}

// ListByIDs 演示 IN 列表的正确写法。
// 注意 SQL 文本随 len(ids) 变化，计划缓存按文本分桶，
// 所以生产上通常把 n 分档（1/5/10/50…）或固定批大小，否则每个批长度都是一条新语句。
func ListByIDs(ctx context.Context, db *sql.DB, ids []int64) ([]Article, error) {
	if len(ids) == 0 {
		return nil, nil // 空集合必须提前返回：拼出 "IN ()" 是语法错误
	}
	args := make([]any, len(ids))
	for i, id := range ids {
		args[i] = id
	}
	q := `SELECT id, title, author FROM article WHERE id IN (` + Placeholders(len(ids)) + `)`

	rows, err := db.QueryContext(ctx, q, args...)
	if err != nil {
		return nil, err
	}
	defer rows.Close() // 必须 defer：Scan 报错提前 return 时也要关，否则连接不归还池

	var out []Article
	for rows.Next() {
		var a Article
		if err := rows.Scan(&a.ID, &a.Title, &a.Author); err != nil {
			return nil, err
		}
		out = append(out, a)
	}
	return out, rows.Err() // 迭代器本身可能因网络中断失败，漏掉这行会静默拿到半截结果
}

type Article struct {
	ID     int64
	Title  string
	Author sql.NullString // 列可为 NULL 时必须用 NullXxx / 指针，否则 Scan 直接报 converting NULL
}

// CountByAuthorPrepared 显式 Prepare 一次、执行多次：
// 适合批量导数、定时任务里同一条语句跑上万次的场景。
func CountByAuthorPrepared(ctx context.Context, db *sql.DB, authors []string) (map[string]int, error) {
	stmt, err := db.PrepareContext(ctx, `SELECT COUNT(*) FROM article WHERE author = ?`)
	if err != nil {
		return nil, err
	}
	defer stmt.Close()

	out := make(map[string]int, len(authors))
	for _, a := range authors {
		if err := ctx.Err(); err != nil { // 长循环一定要看点是否被取消
			return nil, err
		}
		var n int
		if err := stmt.QueryRowContext(ctx, a).Scan(&n); err != nil {
			return nil, err
		}
		out[a] = n
	}
	return out, nil
}
```

> ⚠️ `*sql.Stmt` 也**并发安全**，但它跟着 `DB` 走：连接池里每条连接各自准备一份，所以高并发下会看到
> `Com_prepare` 计数涨得比调用次数快——这不是泄漏，是驱动的每连接语句缓存。

### 2. 读写分离：业务走主库、报表走从库

[数据建模.md](数据建模.md) 的风险提示是「重查询会打满 IO/CPU，内部/报表类查询最好走只读从库」。
在 Go 里这就是**两个单例池 + 按请求选池**，而不是把库名硬编码进 SQL。

```go
package rwsplit

import (
	"context"
	"database/sql"
	"fmt"
	"os"
	"sync"
	"time"

	_ "github.com/go-sql-driver/mysql"
)

type ctxKey struct{ name string }

var forceMasterKey = ctxKey{"force-master"}

// 主/从各一个单例池。⚠️ 千万不要在请求路径里 sql.Open。
var (
	Master  = sync.OnceValue(func() *sql.DB { return open("MYSQL_MASTER_ADDR") })
	Replica = sync.OnceValue(func() *sql.DB { return open("MYSQL_REPLICA_ADDR") })
)

func open(addrEnv string) *sql.DB {
	addr := os.Getenv(addrEnv)
	if addr == "" {
		panic("rwsplit: env " + addrEnv + " is empty") // 配置缺失属于启动失败
	}
	dsn := fmt.Sprintf("%s:%s@tcp(%s)/%s?charset=utf8mb4&parseTime=true",
		os.Getenv("MYSQL_USER"), os.Getenv("MYSQL_PASS"), addr, os.Getenv("MYSQL_DB"))

	db, err := sql.Open("mysql", dsn)
	if err != nil {
		panic("rwsplit: open: " + err.Error())
	}
	db.SetMaxOpenConns(20)
	db.SetMaxIdleConns(5)
	db.SetConnMaxLifetime(10 * time.Minute)
	db.SetConnMaxIdleTime(3 * time.Minute)

	ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
	defer cancel()
	if err := db.PingContext(ctx); err != nil {
		panic("rwsplit: ping " + addrEnv + ": " + err.Error())
	}
	return db
}

// ForceMaster 打标记：写之后的读、事务内的读都必须走主库，
// 否则会被主从延迟坑到（原因与三种处理方案见 [日志与持久化.md](日志与持久化.md) 的「读己之写」）。
func ForceMaster(ctx context.Context) context.Context {
	return context.WithValue(ctx, forceMasterKey, true)
}

// Pick 返回本次查询该用的池。默认从库，标记过的和事务内的走主库。
func Pick(ctx context.Context, inTx bool) *sql.DB {
	if inTx {
		return Master() // 事务只能跑在一个连接上，跨池不存在"一个事务两个库"
	}
	if forced, _ := ctx.Value(forceMasterKey).(bool); forced {
		return Master()
	}
	if err := ping(context.Background(), Replica()); err != nil {
		return Master() // 从库不可用要能降级；⚠️ 代价是报表流量会挤占业务库
	}
	return Replica()
}

func ping(ctx context.Context, db *sql.DB) error {
	ctx, cancel := context.WithTimeout(ctx, time.Second)
	defer cancel()
	return db.PingContext(ctx)
}

// Report 是"重查询"的落点：显式走从库 + 单独超时预算。
func Report(ctx context.Context, since time.Time) (int, error) {
	ctx, cancel := context.WithTimeout(ctx, 60*time.Second) // 报表可以给 60s，C 端接口不行
	defer cancel()

	var n int
	q := `SELECT COUNT(*) FROM orders WHERE created_at >= ?`
	if err := Pick(ctx, false).QueryRowContext(ctx, q, since).Scan(&n); err != nil {
		return 0, err
	}
	return n, nil
}
```

> ⚠️ 每次 `Pick` 都 Ping 一次等于给每个请求加一个 RTT。生产做法是后台定时探活 + 缓存健康状态，
> 或干脆用中间件（ProxySQL / MyCat / 云厂商代理）在**连接层**做分离，应用只拿到一个地址。
> 本节的目的是让「谁是主、谁是从」在代码里显式可辨，而不是散落在字符串里。

## 使用二：Java（参数化 + 读写分离）

### 1. 参数化：`?` 与命名参数，永远不用字符串拼

```java
package notes.mysql.prepstmt;

import java.util.List;
import java.util.Map;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.core.RowMapper;
import org.springframework.jdbc.core.namedparam.MapSqlParameterSource;
import org.springframework.jdbc.core.namedparam.NamedParameterJdbcTemplate;

public class ArticleDao {

    private final JdbcTemplate jdbc;
    private final NamedParameterJdbcTemplate named;

    public ArticleDao(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
        this.named = new NamedParameterJdbcTemplate(jdbc);
    }

    // ✓ 占位符：JdbcTemplate 内部走 PreparedStatement，参数不参与语法解析
    public List<String> titlesByAuthor(String author) {
        RowMapper<String> mapper = (rs, i) -> rs.getString("title");
        return jdbc.query("SELECT title FROM article WHERE author = ?", mapper, author);
    }

    // ✓ IN 列表：命名参数自动展开占位符，不要自己拼 "?" 也不要拼值
    public List<Long> idsIn(List<Long> ids) {
        if (ids.isEmpty()) {
            return List.of();
        }
        return named.queryForList(
                "SELECT id FROM article WHERE id IN (:ids)",
                new MapSqlParameterSource("ids", ids),
                Long.class);
    }

    // ✗ 反例（写出来只为了说明它为什么错）：值直接进入 SQL 文本
    // jdbc.queryForList("SELECT id FROM article WHERE author = '" + author + "'", Long.class);

    // ✗ 另一个坑：MyBatis 里 ${} 是字面替换，等同于拼字符串；#{} 才是占位符
    //   <select id="q">SELECT id FROM article WHERE author = '${author}'</select>

    // ⚠️ ORDER BY / 表名这类"结构位"没法参数化（? 只能代表值），
    // 只能靠白名单映射，不要拼前端传进来的字符串。
    public List<Map<String, Object>> sorted(String sortBy) {
        String column = Map.of("id", "id", "time", "created_at", "views", "views")
                .getOrDefault(sortBy, "id");
        return jdbc.queryForList("SELECT id, title FROM article ORDER BY " + column + " DESC LIMIT 50");
    }
}
```

### 2. 读写分离：`AbstractRoutingDataSource`

```java
package notes.mysql.rwsplit;

import java.util.HashMap;
import java.util.Map;
import javax.sql.DataSource;
import org.springframework.jdbc.datasource.AbstractRoutingDataSource; // 实际是 lookup 的基类，见下方说明
import org.springframework.jdbc.datasource.lookup.AbstractRoutingDataSource;

public class MasterReplicaRouting extends AbstractRoutingDataSource {

    // 路由键放 ThreadLocal：这是"按请求选库"的关键，业务代码不感知库地址
    private static final ThreadLocal<Boolean> FORCE_MASTER = ThreadLocal.withInitial(() -> Boolean.FALSE);

    public static void forceMaster() {
        FORCE_MASTER.set(Boolean.TRUE);
    }

    public static void clear() {
        FORCE_MASTER.remove(); // ⚠️ 必须 remove：线程池会复用线程，留着会把后续请求一路带进主库
    }

    @Override
    protected Object determineCurrentLookupKey() {
        return FORCE_MASTER.get() ? "master" : "replica";
    }

    @Override
    public void afterPropertiesSet() {
        Map<Object, Object> targets = new HashMap<>();
        // targetDataSources 需要由外部注入真实 DataSource，这里仅示意键名对应关系
        super.afterPropertiesSet();
    }
}
```

> 说明：`AbstractRoutingDataSource` 需要在配置类里 `setTargetDataSources(Map.of("master", ds1, "replica", ds2))`
> 并 `setDefaultTargetDataSource(ds1)`；`determineCurrentLookupKey` 的返回值用来查这张表。
> 拦截 `@Transactional(readOnly = true)` 自动切从库是**各中间件的行为**（ShardingSphere、
> `baomidou/dynamic-datasource`），Spring 自身只认 `readOnly` 标志并把它下推给连接的 `setReadOnly()`。

**结论对齐 Go 侧**：`FORCE_MASTER` ≈ Go 的 `ForceMaster(ctx)`；
只是 Java 用 ThreadLocal（因为 Spring 的连接绑定在线程上），Go 用 `context`（因为 `database/sql` 按调用点选池）。

## 延伸追问

- **加索引一定能提速吗？** → 不一定：区分度低（如性别）、表本身很小、或查询要返回大部分行时，走索引反而不如全表扫。
- **预编译真的省开销吗？** → 看驱动与参数：Go 的 `database/sql` 在每条新连接上都要 prepare 一次，`interpolateParams` 更会退化成文本拼接；只有「连接复用 + 真正多次执行」才省（见本文「使用一」）。
- **为什么 `explain` 的估算和实际耗时差很远？** → `explain` 给的是基于统计信息的**估算**；要看 `explain analyze`（8.0.18+）拿真实行数与耗时。
- **读写分离之后为什么还会慢？** → 可能是主库写压力、也可能是从库并行复制跟不上导致查询排队；**先确认打到了哪台从库、它的延迟是多少**，再谈优化。
- **一条 SQL 从连接到返回经过哪些层？** → 连接层（认证、线程复用）→ SQL 层（解析、优化、执行）→ 引擎层（索引、锁、事务）；按这个顺序排查比记名词有用得多。

- **`.frm` 文件去哪了？** → 8.0 把表定义收进 InnoDB 的数据字典表（物理在 `mysql.ibd`），`.frm` 不再存在，"拷 frm 修表"的手法随之失效。
- **原子 DDL 是不是等于"DDL 可以回滚"？** → 不是。一条 DDL 内部原子，但它仍会隐式提交当前会话事务，不能包在 `START TRANSACTION` 里；升级前建的老表也不享受原子性。
- **为什么直接拷贝 datadir 起第二台实例会出问题？** → `auto.cnf` 里的 `server_uuid` 被一起复制了，GTID 与主从复制会认为两台是同一个实例。
- **InnoDB 和 MyISAM 的区别？** → InnoDB 支持**事务、行级锁、外键、崩溃恢复（redo log）**；
  MyISAM 只有表级锁、不支持事务，但计数和全表扫描更快。**生产默认用 InnoDB**。

- **连接池开大一点是不是就一定更快？** → 不是。池只是"同时在跑的 SQL 条数"，
  服务端的并发上限由 CPU 核数决定；池超过核数只是把排队从客户端挪到服务端（见本文第 3.3 节）。
