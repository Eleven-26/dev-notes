## 一、监控和"救火"差在哪？

**来源**：《高性能 MySQL》（第 4 版）第 2 章「可靠性工程对 DBA 团队的影响」「定义服务水平目标」「怎样才能让客户满意」「用什么来度量」。

### 1.1 SLI、SLO、错误预算：先有三个词，再有一堆指标

**本节要点**：这三个词决定"该采什么"，没定义它们之前上的监控，最后都会变成没人看的仪表盘。

```text
SLI  实测指标（Indicator）    —— 一次真实请求的测量值：这条查询延迟了多少毫秒
SLO  目标（Objective）        —— 对 SLI 的承诺：窗口内 99% 的查询在 100 ms 内返回
预算 允许失败的额度            —— (1 - 99%) × 窗口内总请求数 = 这个月可以慢多少次
```

（上面的 99% / 100 ms 只是示例形态，不是实测值。）

三者的关系是**单向约束**：先有 SLI 的定义口径，SLO 才有意义，预算才能被消耗；
"报警阈值"应当从 SLO 推导（比如预算烧掉 40% 就告警），而不是拍一个"CPU > 80%"。

### 1.2 可靠性工程对 DBA 团队的实际影响

传统 DBA 值班口径是"数据库没挂就行"，可靠性工程把它换成三件具体的事：

- **延迟预算归零时停止功能上线**，先还账——这把"要不要优化"从个人判断变成流程约束；
- **每次事故要落到 SLO 是否被违反**，而不是"有没有报错"；
- **监控面板按用户感知组织**（接口延迟、错误率），而不是按 mysqld 内部指标组织。

### 1.3 怎样才能让客户满意：为什么不能用平均值

平均值会把长尾完全抹平：99% 的请求 5 ms、1% 请求 2 s，平均仍不到 30 ms，
但那 1% 的用户体验是彻底失败的。第 2 章的判据是**看分布与分位点**，
并且要区分"慢的类别"：

- 均匀的慢（整体资源不足）→ 扩容或加索引；
- 周期性的慢（刷脏、统计信息重算、备份、GC）→ 是参数与调度问题，不是容量问题；
- 偶发的极慢（锁等待、执行计划翻车、`ALTER` 撞车）→ 才是"诊断"的主战场。

### 1.4 用什么来度量：三类核心指标

**来源**：第 2 章「监控可用性」「监控查询延迟」「监控报错」。

| 类别 | 采什么 | 常见误区 |
|---|---|---|
| 可用性 | 连接能否建立 + 一条探测查询是否返回（不是进程存活） | 只看 `mysqld` 进程在不在；实例"活着但不可用"（磁盘满、连接打满）最常见 |
| 查询延迟 | 按 digest 聚合的 P95/P99，而不是全局平均 | 只采慢日志阈值以上的语句，分位数就失真了 |
| 报错 | 连接失败、超时、死锁、复制中断的计数与趋势 | 只看有没有 error log 新增行；`Aborted_connects`、死锁计数是更早期信号 |

## 二、把 SLO 落到 MySQL 上：怎么采、怎么报？

**来源**：第 2 章「主动监控」「度量长期性能」「了解业务节奏」「有效地跟踪指标」「使用监控工具检查性能」「使用 SLO 来指导整体架构」。

### 2.1 主动监控：不要等用户来告诉你

主动监控 = **由监控系统周期性发起真实请求**，而不是被动读取服务器自报的数字。
MySQL 侧的最小形态：一条极轻的读探测（`SELECT 1` 或一行缓存表）+ 一条写探测
（对临时表或专用心跳表做一次 upsert，注意它会进 binlog、会占 GTID）。

写探测的价值在于：它能发现"只读可用、写入不可用"的中间态，例如半同步降级、
磁盘满导致提交失败、复制的 `read_only` 状态异常。

### 2.2 延迟要按"语句指纹"分桶

全局 P99 只能告警，不能定位。工程上要按**语句指纹（digest）**分桶统计：
同一类 SQL 参数化后归成一个指纹，每个指纹各自算 P95/P99 与总耗时。

这就决定了采集点的选择：`performance_schema` 的
`events_statements_summary_by_digest` 天生就是这个口径（见 3.2 与 5.1），
而慢查询日志只有超过阈值的语句，做不了分位统计。

### 2.3 长期性能与业务节奏

单点阈值报警必然误报。可操作的做法是：

- 用**同比**（昨天同一时刻 / 上周同一天）而不是固定阈值来判断"这个延迟是不是异常"；
- 识别业务节奏：整点任务、秒杀活动、报表跑批会造成周期性尖峰，
  这些尖峰如果是**已知节奏**，就该被 SLO 排除，而不是天天报警；
- 保留长期基线：容量规划要看的是"这个月比上个月慢了多少"，而不是"这台机器现在忙不忙"。

### 2.4 有效跟踪指标的代价：基数

指标的**时间序列数量 = 标签组合数**。给每条 SQL 的指纹、每个表、每个用户、每个来源 IP 都建一条曲线，
会让监控系统自身的开销爆炸（第 2 章「有效地跟踪指标」讲的就是这件事）。

MySQL 监控的常见控制手段：只保留 Top N 指纹的曲线（其余汇总成一条）、
按 digest 而不是按 SQL 全文建标签、库表级指标只采热点表。

### 2.5 用 SLO 反过来指导架构

第 2 章这一节是把数据库拉回架构讨论：**接口的 SLO 才是数据库 SLO 的来源**。

- 接口承诺 200 ms / P99 → 留给单次 DB 访问的预算要按调用次数倒推；
- 预算不够时，可选的是缓存层（见 [缓存问题与方案.md](../../缓存/缓存问题与方案.md)）、
  读写分离（见 [软件架构.md](软件架构.md)）、异步化与降级（见 [稳定性三件套.md](../../../../04-架构与系统/分布式/服务治理/稳定性三件套.md)）；
- 反过来，"给数据库加索引把 P99 压下来"往往比"给接口加超时兜底"更符合预算分配——
  这两个动作谁先做，正是 SLO 与错误预算给出的答案，而不是经验直觉。

## 三、Performance Schema 的结构：插桩 → 收集 → 消费者表

**来源**：《高性能 MySQL》（第 4 版）第 3 章「Performance Schema 介绍」「插桩元件」「消费者表的组织」「资源消耗」「局限性」「sys Schema」「理解线程」。

### 3.1 它是什么，以及不是什么

`performance_schema` 是**引擎内部埋点**的聚合系统：SQL 语句、文件 I/O、互斥量、等待、
阶段、事务、内存分配都会经过它预先分配的内存表累加。它解决的是"慢日志只能告诉你结果"的问题——
**它告诉你这条语句的时间花在了哪一层**（解析？排序？等锁？读盘？）。

三件事要先说清：

- 它**不是慢查询日志的替代品**：慢日志记录真实执行过的语句文本，PS 记录的是聚合事件；
- 它**默认不保存 SQL 全文**，只保存指纹（digest），文本按长度截断；
- 它是**内存驻留的表**，不是磁盘表：实例一重启，所有计数与指纹就清零，无法回溯历史。
  实测这条不是修辞——容器重启后 `events_statements_summary_by_digest` 只剩 **6 行**，
  而重启前跑过的那批建表与查询语句的指纹已经不在了。

### 3.2 插桩元件（instrument）：三类命名决定粒度

插桩点按命名前缀分类，最常见的几族：

| 前缀 | 采集内容 | 典型用途 |
|---|---|---|
| `wait/io/file/...` | 文件读写等待 | 定位磁盘瓶颈在哪个文件（ibdata、redo、临时表、慢日志） |
| `wait/lock/...` | 锁与互斥量等待 | 表锁、元数据锁、InnoDB 内部互斥量争用 |
| `statement/...` | SQL 语句执行 | 按语句/指纹统计耗时与调用次数 |
| `stage/...` | 语句内部阶段 | 看到"正在排序 / 正在拷贝到临时表"这类进度 |
| `idle/...`、`transaction/...` | 空闲与事务边界 | 长事务、连接空闲时间的来源 |

`file_summary_by_event_name` 里那串 `wait/io/file/innodb/innodb_data_file` 就是这个命名体系的直接产物。

### 3.3 消费者表（consumer）：current / history / summary 三层

同一个事件可以被写进不同"细度"的表，这就是消费者表：

- **current**：此刻正在发生（如 `events_statements_current`、`events_waits_current`）；
- **history**：最近的若干条历史（`events_statements_history`、`events_stages_history`）；
- **summary**：按维度聚合的累计值（按线程、按 digest、按事件名、按对象，
  如 `events_statements_summary_by_digest`、`events_waits_summary_global_by_event_name`）。

`setup_consumers` 是这些细度的总闸：父级关掉，子级无论怎么开都没数据。
排查"为什么这张表是空的"，第一站就是它。

实测这张表**只有两列**（`NAME varchar(64)` + `ENABLED enum('YES','NO')`）——
父子依赖关系并不体现在表结构里，只能靠命名和文档判断（8.0 里 `TIMED` 只在 `setup_instruments` 有）。
默认 16 个消费者里只开了 7 个：

```text
-- SELECT NAME, ENABLED FROM performance_schema.setup_consumers ORDER BY NAME;
events_stages_current            NO      events_stages_history       NO
events_stages_history_long       NO      events_statements_cpu       NO
events_statements_current        YES     events_statements_history   YES
events_statements_history_long   NO      events_transactions_current YES
events_transactions_history      YES     events_transactions_history_long  NO
events_waits_current             NO      events_waits_history        NO
events_waits_history_long        NO      global_instrumentation      YES
statements_digest                YES     thread_instrumentation      YES
```

⭐ 这张名单直接解释了"为什么 `events_waits_current` 常是空的"：**它默认就是 NO**，
不是没发生等待。而 `stage` 一族三个消费者全关，所以想看"正在排序 / 正在拷贝到临时表"必须自己开。

### 3.4 资源消耗与局限（决定你能开多细）

**来源**：第 3 章「资源消耗」「局限性」「调整 Performance Schema 的内存大小」「默认值」。

- 所有表都在内存里，容量由一组 `performance_schema_*_size` 参数决定。实测默认值分两类：
  **`-1`（按规模自动推导）** 的是账号/主机/用户/对象这几项，
  **固定数字** 的是每线程历史与 digest 表：

```text
performance_schema_accounts_size                        -1
performance_schema_users_size                           -1
performance_schema_hosts_size                           -1
performance_schema_setup_objects_size                   -1
performance_schema_digests_size                     10000
performance_schema_error_size                       5330
performance_schema_session_connect_attrs_size      512
performance_schema_events_statements_history_size    10   -- 每线程保留最近 10 条
performance_schema_events_statements_history_long_size 10000
performance_schema_events_waits_history_size         10
performance_schema_events_transactions_history_size  10
```

  ⚠️ 自动推导的结果是**表可能很小**：digest 表满了会合并/淘汰，
  这时你以为"没有这条 SQL 的记录"，实际是"被挤掉了"（填满后的自查写法见 5.5）。
- 开销来源是插桩数量 × 事件频率，不是数据量：`wait/synch` 一族在最热路径上，
  全开时开销显著，这也是发行版默认只开一部分的原因。
- 局限还有一条常被忽略：**它按线程/连接维度采样，聚合口径不能任意下钻**——
  例如某些维度只在 summary 表里存在，无法回溯到具体某一次执行。

### 3.5 sys schema：视图封装，不是新数据源

`sys` 库把常用的 PS + I_S 查询封装成视图（`statement_analysis`、`io_global_by_file_by_bytes`、
`innodb_lock_waits`、`memory_global_total`、`schema_unused_indexes` 等）。
它的意义是**降低查询书写成本**，不引入额外采集开销——数据仍然来自 `performance_schema` 与 `information_schema`。
所以生产上"没装 sys"时，完全可以直查 PS 表，只是语句长一些。

### 3.6 理解线程：两张表的分工

| 视图 | 看到什么 | 差异 |
|---|---|---|
| `SHOW PROCESSLIST` / `sys.session` | 客户端连接（过滤掉后台线程） | 值班时看"谁在跑什么" |
| `performance_schema.threads` | **全部线程**，含 InnoDB 后台、复制、page cleaner | 排查内部线程与内存/等待的归属 |

两表通过 `PROCESSLIST_ID` / `THREAD_ID` 关联，
再和 `events_statements_current`、`memory_summary_by_thread_by_event_name` 串起来，
就能回答"这个内存是哪个连接吃的""这个等待是哪条语句引起的"。

实测差距很直观：一个刚重启、只有 1 个客户端连接的容器里，
`SELECT COUNT(*) FROM performance_schema.threads` 是 **38 行**，按 `TYPE` 分组是
**BACKGROUND 35 / FOREGROUND 3** —— `SHOW PROCESSLIST` 一个后台线程都不会给你看。
更要注意的是 `threads` 里连后台线程也带 `PROCESSLIST_ID`（实测 `event_scheduler` 两行 
`PROCESSLIST_ID` = 5 与 7，`STATE` 分别是 `Waiting on empty queue` 与 `Suspending`），
所以按 `PROCESSLIST_ID IS NOT NULL` 过滤**不等于**"只看客户端连接"，要再加 `TYPE = 'FOREGROUND'`。

## 四、怎么开、开多大：配置的四个层次

**来源**：第 3 章「配置」「启用或禁用 Performance Schema」「启用或禁用插桩」「启用或禁用消费者表」「优化特定对象的监控」「优化线程的监控」。

### 4.1 总开关

8.0 起 `performance_schema` **默认开启（ON）**，它是启动期变量：
关掉它要改配置并重启。启动参数还能细粒度控制：

```bash
performance-schema-instrument='wait/io/file/%=ON'      # 按前缀批量开关
performance-schema-consumer='events_%_by_thread=OFF'    # 按消费者批量开关
```

### 4.2 开关插桩与消费者表（运行时可调）

```sql
-- 看当前开关
SELECT NAME, ENABLED, TIMED FROM performance_schema.setup_instruments
WHERE NAME LIKE 'wait/io/file/%' LIMIT 20;

SELECT NAME, ENABLED FROM performance_schema.setup_consumers;

-- 打开某一族的计时（TIMED 决定是否采集耗时，ENABLED 决定采不采事件）
UPDATE performance_schema.setup_instruments
SET ENABLED = 'YES', TIMED = 'YES'
WHERE NAME LIKE 'wait/io/file/innodb/%';

UPDATE performance_schema.setup_consumers
SET ENABLED = 'YES' WHERE NAME = 'events_waits_current';
```

实测这张表的规模：`setup_instruments` 共 **1254 行**，其中 `ENABLED='YES'` **777** 行、
`TIMED='YES'` **273** 行 —— **"开着采"和"开着计时"是两回事**，差出来的 504 个插桩
只记次数不记耗时，所以它们的 `SUM_TIMER_WAIT` 永远是 0，别拿这类表去做延迟统计。

⚠️ 顺序很重要：`setup_consumers` 里没有 `events_waits` 这一项，真正的总闸是
`global_instrumentation` 与 `thread_instrumentation`（实测两者默认 `YES`）；
`events_waits_current` 默认 `NO`，所以要**先把对应插桩打开，再把消费者打开**，只开一边照样是空表。

### 4.3 按对象收敛粒度：`setup_objects`

默认的 `@.%` 意思是"所有库所有表都采"。表很多时，把采集范围收到真正的热点表，
是**在不减信息量的前提下降开销**的主要手段：

```sql
SELECT OBJECT_TYPE, OBJECT_SCHEMA, OBJECT_NAME, ENABLED, TIMED
FROM performance_schema.setup_objects;
```

实测这张表默认 **20 行**，列是 `OBJECT_TYPE / OBJECT_SCHEMA / OBJECT_NAME / ENABLED / TIMED`
（⚠️ 没有 `DISABLED` 这一列，照旧文章写 `WHERE DISABLED = ...` 会报 1054）。
默认名单已经把三个系统库整体排除：

```text
EVENT      mysql                %   NO   NO
EVENT      performance_schema   %   NO   NO
EVENT      information_schema   %   NO   NO
EVENT      %                    %   YES  YES
FUNCTION / PROCEDURE / TABLE / TRIGGER 同上四行
```

（第 3 章「优化特定对象的监控」「优化线程的监控」两个小节对应的就是 `setup_objects` 与 `setup_threads`。）

### 4.4 先估开销再上线

判断"打开某项会不会太贵"，实操口径是**同一负载下对比开关前后的两组数**：
QPS、P99、`mysqld` 常驻内存，以及 PS 自身的内存占用（见 5.4）。
不要只看文档说的"开销很小"——它取决于插桩落在多热的路径上。

## 五、五类问题分别查哪张表？

**来源**：第 3 章「使用 Performance Schema」下的「检查 SQL 语句」「检查读写性能」「检查元数据锁」
「检查内存使用情况」「检查变量」「检查最常见的错误」「检查 Performance Schema 自身」。

### 5.1 检查 SQL 语句：digest 表是主战场

```sql
-- 按总耗时排序的 Top 指纹：平均慢 vs 累计慢，两个都要看
SELECT SCHEMA_NAME, DIGEST_TEXT,
       COUNT_STAR                       AS executions,
       SUM_TIMER_WAIT/1e12              AS total_sec,
       AVG_TIMER_WAIT/1e12              AS avg_sec,
       SUM_ROWS_SENT, SUM_ROWS_EXAMINED,
       SUM_CREATED_TMP_DISK_TABLES, SUM_SORT_MERGE_PASSES,
       FIRST_SEEN, LAST_SEEN
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 10;
```

三个判据：

- `SUM_ROWS_EXAMINED / SUM_ROWS_SENT` 比值大 → 扫描多、返回少，缺索引或条件太宽；
- `SUM_CREATED_TMP_DISK_TABLES`、`SUM_SORT_MERGE_PASSES` 非零 → 内存类参数与语句写法一起查
  （对应 [参数调优.md](参数调优.md) 第四节）；
- **按 `SUM_TIMER_WAIT` 排序而不是按 `AVG_TIMER_WAIT` 排序**——这与
  [索引与优化.md](索引与优化.md) 第四节「按总时间排序而不是平均时间」是同一条经验。

`sys.statement_analysis` 就是这张表的封装视图。

实测输出（刚跑完几条查询、按 `SUM_TIMER_WAIT DESC`）：

```text
SCHEMA_NAME | DIGEST_TEXT                                        | executions | total_sec | avg_sec | ROWS_SENT | ROWS_EXAMINED | TMP_DISK | SORT_MERGE
docverify   | SELECT COUNT ( * ) FROM `orders` WHERE `customer_id` = ?        | 1 | 0.0105 | 0.0105 | 1 | 0    | 0 | 0
docverify   | SELECT ... FROM `sys` . `schema_unused_indexes` ORDER BY ...    | 1 | 0.0057 | 0.0057 | 4 | 3314 | 0 | 0
docverify   | SELECT SUM ( `amount` ) FROM `orders` WHERE STATUS = ? AND ...  | 1 | 0.0035 | 0.0035 | 1 | 2500 | 0 | 0
docverify   | SELECT * FROM `customers` WHERE `JSON_CONTAINS` ( ... )         | 1 | 0.0033 | 0.0033 | 0 | 3    | 0 | 0
docverify   | SELECT `id` FROM `orders` ORDER BY `amount` DESC LIMIT ?        | 1 | 0.0025 | 0.0025 | 5 | 2505 | 0 | 0
```

两条实测才看得见的口径：

- 后两条就是"扫描多、返回少"的指纹（2500 / 2505 行 examined 对 1 / 5 行 sent），
  而第一条走覆盖索引的 `COUNT(*)` 报的是 **`SUM_ROWS_EXAMINED = 0`** ——
  走覆盖索引时这个计数器不涨，**别拿"examined=0"当成"没执行"**；
- `DIGEST_TEXT` 把标识符加了反引号、把常量换成 `?`，还会把像关键字的列名大写
  （实测 `status` 列被写成 `WHERE STATUS = ?`）。**按指纹文本做正则匹配前先看清这个归一化形态。**

### 5.2 检查读写性能：文件层与表索引层

```sql
-- 哪一类文件在消耗时间（数据文件 / redo / 临时表 / binlog）
SELECT EVENT_NAME, COUNT_STAR, SUM_TIMER_WAIT/1e12 AS total_sec,
       SUM_NUMBER_OF_BYTES_READ, SUM_NUMBER_OF_BYTES_WRITE
FROM performance_schema.file_summary_by_event_name
ORDER BY SUM_TIMER_WAIT DESC LIMIT 10;

-- 哪个索引从没被用过：删索引前的证据
SELECT object_schema, object_name, index_name
FROM sys.schema_unused_indexes
LIMIT 20;
```

`table_io_waits_summary_by_index_usage` 则给出"每个索引各被走了多少次"，
和 [索引设计.md](索引设计.md) 的冗余索引判断连用：先确认没人走，再谈删除。

实测（默认配置容器，`events_waits` 消费者全关的情况下这两张表**仍有数据**——
它们走的是 `file_%` / `table_%` 摘要链，不依赖 `events_waits_current`）：

```text
-- file_summary_by_event_name Top（total_sec = SUM_TIMER_WAIT/1e12）
wait/io/file/innodb/innodb_log_file    224   0.3250   R 68096      W 107008
wait/io/file/innodb/innodb_data_file  1458   0.1194   R 17072128   W 16007168
wait/io/file/innodb/innodb_dblwr_file   50   0.0691   R 9043968    W 1277952
wait/io/file/innodb/innodb_temp_file    60   0.0436   R 0          W 327680
wait/io/file/sql/binlog_index           31   0.0061   R 576        W 0

-- schema_unused_indexes（docverify 库里 4 个候选）
customers.zips  customers.idx_tags  orders.idx_status_created  orders.idx_desc

-- table_io_waits_summary_by_index_usage WHERE object_name = 'orders'
index_name=NULL(全表扫)  COUNT_STAR 5000   0.00466 s
index_name=idx_customer  COUNT_STAR 4      0.00024 s
index_name=PRIMARY / idx_status_created / idx_desc   COUNT_STAR 0
```

⭐ `index_name` 为 **NULL** 那一行代表"没走任何索引的访问"，它的 `COUNT_STAR` 5000 远大于
走索引的 4 —— 这就是"该表仍以全表扫为主"的直接证据。⚠️ 但 `schema_unused_indexes` 给出的
4 个"没用过"的索引里，`idx_status_created` 是本篇实验时**故意设成 INVISIBLE** 的，
另两个是 JSON 多值索引：**视图只告诉你"没计数"，不告诉你原因**，删之前要人工核一遍。

### 5.3 检查元数据锁与行锁

**元数据锁（MDL）**：DDL 卡在"Waiting for table metadata lock"时，
不要只看 `SHOW PROCESSLIST`，要从 `metadata_locks` 找出持有者与它自己的父请求：

```sql
SELECT OBJECT_SCHEMA, OBJECT_NAME, LOCK_TYPE, LOCK_STATUS, OWNER_THREAD_ID
FROM performance_schema.metadata_locks
WHERE OBJECT_TYPE = 'TABLE' AND OBJECT_SCHEMA NOT IN
      ('mysql','information_schema','performance_schema','sys');
```

实测两个要点：

- **8.0.46 默认就是开的**：在 `setup_instruments` 里筛 `NAME LIKE 'wait/lock/metadata%'`，
  只有一行 `wait/lock/metadata/sql/mdl`，实测 `ENABLED=YES`、`TIMED=YES`。
  旧文章里"MDL 插桩默认关、要自己开"的说法在 8.0 上已经不成立；
- 这张表**只记当前持有和当前等待**，锁一释放行就消失：实测空载实例里稳定有 13 行
  （后台线程与字典占的），而 DDL 一旦被放行，那行 `EXCLUSIVE PENDING` 立刻不见。
  所以它是**现场取证工具，不是历史记录**，等用户报障后再查大概率什么都剩不下。

实测现场（一个连接持事务不放，另一个连接 `ALTER TABLE orders ADD COLUMN`）：

```text
OBJECT_TYPE | OBJECT_SCHEMA | OBJECT_NAME | LOCK_TYPE         | LOCK_STATUS | OWNER_THREAD_ID
TABLE       | docverify     | orders      | SHARED_READ_ONLY  | GRANTED     | 153   -- 挡住 DDL 的那个查询
TABLE       | docverify     | orders      | SHARED_UPGRADABLE | GRANTED     | 154   -- DDL 自己先拿的升级锁
TABLE       | docverify     | orders      | EXCLUSIVE         | PENDING     | 154   -- 它正在等的独占锁
```

三行一起看才是完整因果：`SHARED_UPGRADABLE` + `EXCLUSIVE PENDING` 同属一个线程（154），
阻塞方是另一个线程（153）。手写这个 JOIN 麻烦，`sys.schema_table_lock_waits` 已经把
"谁挡谁 + `KILL` 语句"拼好了（实测输出里有 `waiting_query` = 那条 ALTER、
`blocking_lock_type` = `SHARED_READ_ONLY`、`sql_kill_blocking_query` = `KILL QUERY 94`）。

**行锁与死锁**：8.0 用 `data_locks` / `data_lock_waits`。
⚠️ 旧的 `information_schema.innodb_lock_waits` 不是"不推荐"而是**已经不存在**，实测：

```text
mysql> SELECT COUNT(*) FROM information_schema.innodb_lock_waits;
ERROR 1109 (42S02) at line 1: Unknown table 'INNODB_LOCK_WAITS' in information_schema
```

照抄 5.7 时代的排查脚本会在第一行就失败。
`sys.innodb_lock_waits` 直接把"谁在等谁、阻塞方正在跑哪条 SQL"拼成一行，
是排查"更新语句卡住"最快的入口。死锁的完整机制见 [并发控制与MVCC.md](并发控制与MVCC.md)。

### 5.4 检查内存使用情况

```sql
SELECT EVENT_NAME, COUNT_ALLOC,
       SUM_NUMBER_OF_BYTES_ALLOC/1024/1024 AS alloc_mb,
       CURRENT_NUMBER_OF_BYTES_USED/1024/1024 AS used_mb
FROM performance_schema.memory_summary_global_by_event_name
ORDER BY CURRENT_NUMBER_OF_BYTES_USED DESC LIMIT 15;

SELECT * FROM sys.memory_global_total;   -- 当前 PS 记账的总内存
```

用途有两层：**排查内存上涨的来源**（buffer pool 之外的那些项），
以及**衡量 PS 自身的开销**（`memory_summary_global_by_event_name` 里 EVENT_NAME 以
`memory/performance_schema/` 开头的行就是它自己吃了多少）。

实测（默认配置、单连接空载，单位 MiB 由 `CURRENT_NUMBER_OF_BYTES_USED/1048576` 得到）：

```text
memory/innodb/buf_buf_pool                                     130.88  (137236480 B)
memory/performance_schema/events_statements_summary_by_digest   40.28  (42240000 B)
memory/innodb/ut0link_buf                                       24.00
memory/innodb/log_buffer_memory                                 16.00
memory/performance_schema/events_statements_history_long         14.42
memory/performance_schema/events_errors_summary_by_thread...     12.83
memory/mysys/KEY_CACHE                                           8.00
-----------
memory/performance_schema/* 合计                               218.76  (229383592 B)
sys.memory_global_total  total_allocated                       436.83 MiB
```

⭐ 空载小库里 **PS 自己的常驻（218.76 MiB）比 128 MiB 的 buffer pool 还大**，
而单是 digest 表就 40 MiB（当时表里只有 6 行）。这条数字直接决定了 4.4 的做法：
小实例上开插桩前先问"内存够不够"，而不是问"开销大不大"。

⚠️ 口径：这些是**启动时按容量参数预分配**的常驻内存，不随负载线性增长，但**会随重启后的活动涨落**——
`sys.memory_global_total` 与逐项 `CURRENT_NUMBER_OF_BYTES_USED` 要同一时刻采。

### 5.5 检查变量、错误与 PS 自身

```sql
-- 谁在什么时候改过哪个变量（改完参数出问题时第一步）
SELECT VARIABLE_NAME, VARIABLE_SOURCE, SET_USER, SET_TIME
FROM performance_schema.variables_info
WHERE VARIABLE_SOURCE <> 'COMPILED';

-- 错误计数：连接失败、语法错误各自的次数
-- ⚠️ 列名是 SQL_STATE，不是 SQLSTATE（后者实测报 1054）
SELECT ERROR_NUMBER, ERROR_NAME, SQL_STATE,
       SUM_ERROR_RAISED, SUM_ERROR_HANDLED, FIRST_SEEN, LAST_SEEN
FROM performance_schema.events_errors_summary_global_by_error
WHERE SUM_ERROR_RAISED > 0
ORDER BY SUM_ERROR_RAISED DESC LIMIT 15;

-- digest 表是否已经被填满（填满后新指纹会合并进已有行、不再新增行）
SELECT
  (SELECT COUNT(*) FROM performance_schema.events_statements_summary_by_digest) AS digest_rows,
  (SELECT @@performance_schema_digests_size)                               AS digest_max_rows;
```

两处口径要注意：

- **列名要实测**：`variables_info` 固定 8 列：`VARIABLE_NAME`、`VARIABLE_SOURCE`、`VARIABLE_PATH`、
  `MIN_VALUE`、`MAX_VALUE`、`SET_TIME`、`SET_USER`、`SET_HOST`；
  **这张表既没有 `DEFAULT_VALUE`，也没有 `VARIABLE_VALUE`**，照旧文章写 `SELECT DEFAULT_VALUE ...`
  会直接报 `ERROR 1054 (42S22)`；当前值要回去问 `SHOW VARIABLES`。
- `events_errors_summary_*` 与 `memory_summary_*` 两类表**只有计数、没有计时**——实测在
  `memory_summary_global_by_event_name` 里筛 `LIKE '%TIMER_WAIT%'` 的列数是 **0**，
  所以别照语句表的写法去 `ORDER BY SUM_TIMER_WAIT`。

最后一条查询把「digest 表当前行数」和它的容量上限 `performance_schema_digests_size`（实测 10000）
放在一起比：两者相等且长期不动，说明新指纹已经在合并进老行，
此时 digest 里的 `FIRST_SEEN` 会比语句真正首次出现的时间**更晚**，不能当成"这条 SQL 刚上线"的证据。

实测的 Top 错误行（一个做过不少失败的建库/查询实验的实例）：

```text
ERROR_NUMBER | ERROR_NAME                             | SQL_STATE | RAISED | HANDLED
3554         | ER_NO_SYSTEM_TABLE_ACCESS              | HY000     | 111    | 0
3778         | ER_WARN_DEPRECATED_UTF8MB3_COLLATION   | HY000     | 73     | 0
1287         | ER_WARN_DEPRECATED_SYNTAX              | HY000     | 34     | 0
NULL         | NULL                                   | NULL      | 12     | 0
1051         | ER_BAD_TABLE_ERROR                     | 42S02     | 5      | 0
1054         | ER_BAD_FIELD_ERROR                     | 42S22     | 5      | 0
```

⭐ 有一行 `ERROR_NUMBER IS NULL`：**未映射到错误名的告警会归到 NULL 桶**，
看这张表时不要 `WHERE ERROR_NUMBER IS NOT NULL` 把它滤掉——它往往是"废弃语法警告"的总量。
前 3554/3778 两条正是本篇实验时误查 `information_schema.innodb_lock_waits`、
用 `utf8mb3` 排序规则留下的痕迹：**错误计数是"谁在乱改"的旁证**，不只是错误率的分子。

## 六、版本或权限受限时怎么兜底？

### 6.1 慢日志 + 离线聚合

慢查询日志是唯一"保留真实语句文本"的来源，实操（含 `mysqldumpslow` 的用法与两个必配参数）
在 [索引与优化.md](索引与优化.md) 第四节已经完整写过，本篇不重复。
它与 PS 的分工是：**PS 看全量分布，慢日志看具体语句**。

### 6.2 `SHOW PROCESSLIST` 的 `State` 列仍然有用

没开 PS 或只有只读权限时，`State` + `Time` 是最快的现场快照：
`Sending data`、`Copying to tmp table`、`Waiting for table metadata lock`、
`Updating` 各自指向不同层。⚠️ 它是**瞬时值**，抓不住已经过去的等待，
所以只能作为"现场取证"，不能作为趋势依据。

（更细的 `SHOW PROFILE` 一类逐阶段剖析在新版本已废弃，改用
`events_stages_history` / `events_stages_current`。）

### 6.3 状态计数器成对采样

最粗糙但任何版本都能用的口径：`SHOW GLOBAL STATUS` 两次采样取差（写法见
[参数调优.md](参数调优.md) 的 3.5 与使用一节）。它的优点是**不依赖任何采集开关**，
缺点是只有全局聚合、无法下钻到单条语句。

## 使用：值班现场的四条查询

✅ 以下 4 段都在 Docker Desktop 的 `mysql:8.0`（8.0.46）容器里逐条跑过，输出抄自本机；
列名以 8.0.46 为准 —— 5.7 的 `performance_schema` 列结构不同，先 `DESC` 再抄。

### 1. 现在谁在跑、跑了多久

```sql
SELECT t.PROCESSLIST_ID, t.PROCESSLIST_USER, t.PROCESSLIST_DB,
       LEFT(t.PROCESSLIST_INFO, 120) AS sql_head,
       t.PROCESSLIST_TIME, t.PROCESSLIST_STATE
FROM performance_schema.threads t
WHERE t.PROCESSLIST_ID IS NOT NULL
  AND t.PROCESSLIST_COMMAND <> 'Sleep'
ORDER BY t.PROCESSLIST_TIME DESC
LIMIT 20;
```

实测（一个只有我自己这条连接的容器）返回 3 行：

```text
PROCESSLIST_ID | USER            | DB        | sql_head | TIME | STATE
5              | event_scheduler | NULL      | NULL     | 805  | Waiting on empty queue
7              | NULL            | NULL      | NULL     | 805  | Suspending
16             | root            | NULL      | SELECT … | 0    | executing
```

⚠️ 前两行是后台线程，**它俩也带 `PROCESSLIST_ID`** → 只看客户端连接要再加一条
`AND t.TYPE = 'FOREGROUND'`（实测同一实例 `TYPE` 分布是 BACKGROUND 35 / FOREGROUND 3）。

### 2. 最耗时的语句指纹（先定位，再优化）

见 5.1 的 digest 查询；值班时把 `ORDER BY` 换成 `SUM_ROWS_EXAMINED DESC`
可以再问一遍"是不是有人在扫全表"。

### 3. 谁在等锁、被谁挡住

```sql
SELECT wait_started, wait_age_secs,
       waiting_pid, waiting_query,
       blocking_pid, blocking_query,
       sql_kill_blocking_query, sql_kill_blocking_connection
FROM sys.innodb_lock_waits
LIMIT 20;
```

实测 `DESC sys.innodb_lock_waits` 在 8.0.46 是 **30 列**，上面选的 8 列都存在，
真实输出（一个被 `SELECT SLEEP(20)` 挡住的 `UPDATE`）节选：

```text
wait_started:  2026-10-03 17:47:45        wait_age_secs: 4
locked_table:  `docverify`.`orders`       locked_index:  PRIMARY
locked_type:   RECORD
waiting_pid:   88   waiting_query:      UPDATE orders SET note='blocked-by-B' WHERE id=1
waiting_lock_mode:      X,REC_NOT_GAP
blocking_pid:  87   blocking_query:     SELECT SLEEP(20)
blocking_lock_mode:     X,REC_NOT_GAP    blocking_trx_rows_modified: 1
sql_kill_blocking_query:      KILL QUERY 87
sql_kill_blocking_connection: KILL 87
```

⭐ 值班时只要看最后两行：`KILL QUERY 87` 停掉阻塞方的语句，`KILL 87` 直接断连接。
先跑 `sql_kill_blocking_query`，别一上来就断连接——阻塞方是个事务，
断连等于回滚它已经改过的行（实测 `blocking_trx_rows_modified: 1`）。

### 4. 内存去了哪里

```sql
SELECT EVENT_NAME, CURRENT_NUMBER_OF_BYTES_USED/1024/1024 AS cur_mb
FROM performance_schema.memory_summary_global_by_event_name
ORDER BY CURRENT_NUMBER_OF_BYTES_USED DESC
LIMIT 10;
```

## 延伸追问

- **SLI 和 SLO 有什么区别，为什么要提错误预算？** → SLI 是测出来的值，SLO 是承诺的目标，
  错误预算是"允许失败多少"的量化额度。预算的作用不是数学，而是**给"要不要停功能、先还账"提供流程依据**。
- **为什么 P99 比平均值有用？** → 平均值会被长尾抹平；用户感知的是最差的那部分请求。
  监控上还要看"慢的形态"：均匀慢是容量、周期慢是调度与刷脏、偶发慢才是锁与计划翻车。
- **`performance_schema` 会不会拖慢 MySQL？** → 会有开销，来源是插桩数量 × 事件频率，
  默认配置已经把最贵的族关掉一部分。判断方法是同一负载下对比开关前后的 QPS、P99 与内存占用，
  并且用 `memory_summary_global_by_event_name` 里 `performance_schema/` 开头的行看它自己吃多少。
- **digest 表里查不到某条 SQL，是不是它没执行过？** → 不一定。digest 表有容量上限，
  满了会合并/淘汰；高频但耗时短的语句、或系统运行太久都可能把它挤掉。
  这时用两个间接口径判断：`SELECT COUNT(*) FROM events_statements_summary_by_digest` 是否长期贴住 `@@performance_schema_digests_size`，以及表里的 `MIN(FIRST_SEEN)` 是否随时间前移（说明老行已被合并掉）。
- **`metadata_locks` 查出来是空的？** → 8.0 上多半不是开关问题：实测
  `wait/lock/metadata/sql/mdl` 默认 `ENABLED=YES、TIMED=YES`。更常见的是**时机**——
  这张表只记当前持有与当前等待，锁一释放行就没了；DDL 被放行之后再查就是空的。
  值班口径是：先 `SELECT * FROM metadata_locks WHERE OBJECT_NAME='<卡住的表>'`，
  再顺手把 `sys.schema_table_lock_waits` 存一份，因为它连 `KILL` 语句都拼好了。
- **`sys` schema 和 `performance_schema` 什么关系？** → `sys` 只是把常用查询封装成视图，
  数据仍来自 PS 与 `information_schema`，不额外采集；没有 `sys` 时直查底层表即可。
- **为什么不能只用慢查询日志做监控？** → 它只记录超过阈值的语句，做不了分位统计，
  也无法回答"这条语句的时间花在哪一层"。两者分工：PS 看分布与内部耗时，慢日志留语句原文。
- **PS 的数据能持久化吗？** → 不能，内存表随实例重启清空。要长期趋势就把 summary 表
  周期性导出到监控系统（注意指标基数，见 2.4），别指望重启后还能回看昨天的曲线。
