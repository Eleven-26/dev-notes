## 一、时间类型：`timestamp` 和 `datetime` 该怎么选？

**本节要点**：这一节的重点只有一个词 —— **时区**。关键在能说出
"同一份数据在不同时区读出来不一样"这类真实线上事故，而不是只列长度和范围。

### 1.1 最本质的区别：一个存"绝对时刻"，一个存"字面值"

- **`TIMESTAMP`**：内部存的是 **UTC 纪元秒（绝对时刻）**，读出来时按**当前会话的 `time_zone`**
  换算成"年-月-日 时:分:秒"。所以**同一个值，换个时区显示就变了**。
- **`DATETIME`**：存的就是写进去的那串字面值，**写什么读什么，不随时区换算**。

有个演示非常直观：同一个 `TIMESTAMP` 字段，把会话时区**改成东八区之后，查出来的时间跟着变了**；
而 `DATETIME` 字段改完时区还是原来的值，纹丝不动。

```sql
SELECT @@time_zone;          -- 当前会话时区
SET time_zone = '+08:00';    -- 切成东八区，TIMESTAMP 字段会跟着变，DATETIME 不变
```

### 1.2 逐项对比

| 维度 | **TIMESTAMP** | **DATETIME** |
|---|---|---|
| **存的是什么** | 绝对时刻（内部按 UTC 存） | 字面值（写什么存什么） |
| **时区敏感** | ✅ 敏感，显示值随会话时区变化 | ❌ 不敏感 |
| **取值范围** | 1970-01-01 00:00:01 UTC ~ **2038-01-19 03:14:07 UTC**（有 2038 问题） | 1000-01-01 00:00:00 ~ 9999-12-31 23:59:59 |
| **存储空间** | 4 字节 | 5 字节 |
| **自动更新** | 支持 `DEFAULT CURRENT_TIMESTAMP` / `ON UPDATE CURRENT_TIMESTAMP` | 同样支持 |
| **跨时区场景** | 更安全：存一次，各地按本地时区正确展示 | 有风险：全链路时区必须统一，否则值"看起来是错的" |

### 1.3 结论与补充

**结论**：

> 强烈建议用 `TIMESTAMP`；如果不能用 `TIMESTAMP`，退一步**用整型（`BIGINT`）存时间戳**，
> 没有必要再用 `DATETIME`——因为 `DATETIME` 写进去就是一个固定字符串，
> **多时区或时区设错时，这个值没法自己纠正**，最终存下来的内容就是不准确的。

**补充**：

- `DATETIME` 并不是"错误类型"：它**没有 2038 上限**、范围更大。
  只要**全链路时区统一**（服务端、DB、客户端都锁死 UTC），它同样可信。
- `TIMESTAMP` 的"自动换算"是双刃剑：**服务器时区被改掉时，历史数据的展示值会整体漂移**，
  排查问题时容易被误导。
- 工程上比较稳的组合：**库里存 UTC 的 `TIMESTAMP`（或 `BIGINT` 毫秒时间戳**），
  **时区转换全部放到应用层 / 展示层去做**。

## 二、数值类型怎么选？

**本节要点**：数值是建表时最容易「随手写」的一类 —— 显示宽度被当成长度限制、`UNSIGNED` 在减法与跨语言映射上咬人、金额用浮点必然出错、自增主键选错宽度会提前用完。下面挑真正会出事的几个点。

### 2.1 `int(11)` 的 11 是显示宽度，不是长度限制

| 类型 | 存储 | 取值范围（有符号） | 常见误解 |
| --- | --- | --- | --- |
| `TINYINT` | 1 字节 | -128 ~ 127 | 常用来做状态 / 布尔 |
| `SMALLINT` | 2 字节 | -32768 ~ 32767 | |
| `MEDIUMINT` | 3 字节 | ±838 万 | |
| `INT` / `INT(11)` | **4 字节** | ±21 亿 | ⚠️ `(11)` 只是**显示宽度**，配合 `ZEROFILL` 才有意义，**既不改变范围也不限制写入** |
| `BIGINT` | 8 字节 | ±9.2×10¹⁸ | 自增主键的默认选择 |

⭐ **MySQL 8.0.17 起 `int(11)` 这类显示宽度已被弃用**：实测建表时报 **Warning 1681「Integer display width is deprecated and will be removed in a future release」**，且 `SHOW CREATE TABLE` 里**宽度不落进表定义**（写成 `int(11)`，回显是 `int DEFAULT NULL`）—— 它从来没有约束过取值范围，现在连留痕都不留。

### 2.2 `UNSIGNED` 的两个坑

- **隐式转换导致索引失效**：`INT UNSIGNED` 的范围是 0 ~ 42 亿，看似「更划算」；但 ⚠️ 它与**有符号列比较或关联时会发生隐式类型转换**，可能让索引失效（`WHERE unsigned_col = -1` 这类最典型）。
- **不是所有数据库都有**：PostgreSQL 没有 `UNSIGNED`，迁库时要改用 `NUMERIC` + CHECK 约束或 `BIGINT`；同时注意 MySQL 的 `INT UNSIGNED` 上限（42 亿）远小于 `BIGINT`。

### 2.3 金额绝对不能用 `FLOAT` / `DOUBLE`

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| `FLOAT` / `DOUBLE` | 快、省空间 | ⚠️ **二进制浮点无法精确表示 0.1**，累加会漂移，且比较不能用 `=` | ❌ 不要用于金额 |
| `DECIMAL(M,D)` | 精确十进制，可在 SQL 内直接算 | 占用随位数增长、运算比整数慢；⚠️ 除法 / 乘法的 scale 变化要留意 | 需要在库内做金额运算时用 |
| **`BIGINT` 存最小单位（分）** | ⭐ 整数运算最快、无精度问题 | 应用层负责单位换算与展示 | ✅ **交易 / 订单 / 账户的推荐做法** |

> ⭐ 工程结论：**金额统一用「整数 + 最小货币单位」**（`BIGINT` 存「分」）。确需在库内做分摊 / 汇率计算时用 `DECIMAL(20,6)` 这类足够宽的类型，**永远别用浮点**。

### 2.4 自增主键用 `BIGINT UNSIGNED`，不要用 `INT` 或 UUID

- `INT` 上限 21 亿，有日志 / 流水类业务几年就可能打满，**用满后插入直接失败**；
- ⚠️ **不要用 UUID 做主键**：随机分布会造成 B+Tree **频繁页分裂与索引膨胀**，写入性能与空间双双变差（见 [索引设计与EXPLAIN.md](索引设计与EXPLAIN.md)）；
- 需要「对外不可猜测的 ID」时，用「内部自增 + 外部 ID 映射」，或用雪花算法生成**有序** ID（见 [分布式ID.md](../../../../04-架构与系统/分布式/理论/分布式ID.md)）。

## 三、字符串类型怎么选？

**本节要点**：`CHAR` 与 `VARCHAR` 的差别不只在"定长 / 变长"，还在**长度语义是字符数**（`utf8mb4` 下 1 字符最多 4 字节）—— 这两点直接决定了索引键长度上限会不会被撑爆，以及 `TEXT` / `BLOB` 该不该出现在索引里。

### 3.1 `CHAR` 与 `VARCHAR`

| 维度 | `CHAR(n)` | `VARCHAR(n)` |
| --- | --- | --- |
| 存储 | **定长**，不足补空格（取出时去掉尾随空格） | **变长**，额外 1~2 字节存实际长度 |
| 长度语义 | `n` 是**字符数**（不是字节数） | 同左 |
| 适用 | 长度固定的值：MD5（32）、手机号、国家码、固定格式编码 | 绝大多数业务字段 |
| 坑 | ⚠️ 尾随空格被去掉，**不保存「末尾有空格」这一信息** | 长度前缀：实际长度 ≤255 用 1 字节，>255 用 2 字节 |

⚠️ **`VARCHAR(n)` 的 n 是字符数，实际占用字节数取决于字符集**：`utf8mb4` 下每字符最多 4 字节，因此 `VARCHAR(255)` 最坏占 **1020 字节**——这正是下一节「建索引失败」的根源。

### 3.2 索引键长度上限（varchar 的真坑）

- 上限是**字节**，且**随行格式变**（8.0.46 / `innodb_page_size=16384` 实测）：

```text
默认行格式  @@innodb_default_row_format = dynamic    @@innodb_strict_mode = 1
utf8mb4 字符集上限  SHOW CHARACTER SET → utf8mb3 Maxlen 3 / utf8mb4 Maxlen 4 / latin1 Maxlen 1

DYNAMIC   ：VARCHAR(255) 建索引 通过（1020 字节）  VARCHAR(768) 通过（3072 字节，刚好到上限）
            VARCHAR(769) → ERROR 1071 Specified key was too long; max key length is 3072 bytes
COMPACT   ：VARCHAR(192) → ERROR 1071 ... max key length is 767 bytes
REDUNDANT ：VARCHAR(200) → ERROR 1071 ... max key length is 767 bytes
```

- ⚠️ 5.7 时代那对开关 `innodb_large_prefix` / `innodb_file_format` 在 8.0 已经没有了 ——
  实测 `SELECT @@innodb_file_format` 报 `ERROR 1193 Unknown system variable`，别再照旧文档去查它；
- 三种解法：① 用 DYNAMIC 行格式（8.0 默认）② **前缀索引** `KEY idx_name (name(20))` ③ 缩短列长度；
- ⚠️ 前缀索引的代价：**不能用于覆盖索引**（索引里没有完整值，无法只靠索引返回），且区分度受前缀长度影响
  （怎么选前缀长度见 [索引设计与EXPLAIN.md](索引设计与EXPLAIN.md) 第六节）。

### 3.3 `TEXT` / `BLOB` 的边界

| 限制 | 说明 |
| --- | --- |
| **不能有默认值** | 严格模式下 `TEXT NOT NULL DEFAULT ''` 直接报错 |
| **不能整列建索引** | 只能前缀索引（`KEY (col(10))`） |
| **行溢出** | DYNAMIC 行格式下大字段存到 off-page，读它要多一次 IO，拖慢整行查询 |
| **临时表代价** | 含 TEXT 的查询更容易落磁盘临时表 |
| ⭐ 建议 | 大文本 / 文件**不要放在主业务表**：拆到附表，或存对象存储只留 URL（见 [文件存储与上传架构.md](../../../../04-架构与系统/系统设计/文件存储与上传架构.md)） |

### 3.4 `ENUM`、`SET` 与 `JSON` 的取舍

| 类型 | 优点 | 缺点 | 建议 |
| --- | --- | --- | --- |
| `ENUM` | 省空间、取值可读 | ⚠️ 增删枚举值要 **DDL**（大表变更代价高）；不同 ORM / DAL 兼容性差；序号与字符串双语义易错 | 状态字段用 `TINYINT` + 应用层枚举更稳 |
| `SET` | 一个字段存多选 | 位运算查询不直观、扩展要 DDL | 用关联表或 JSON |
| `JSON` | 稀疏 / 结构不固定的字段免 DDL | ⚠️ 直接查询与索引能力弱（需要**生成列 + 索引**）；体积与解析有开销 | 适合配置 / 扩展字段；核心查询字段必须提炼成独立列 |

> ⭐ 一句话：**长度固定用 `CHAR`、一般用 `VARCHAR`（先算清字符集下的字节数）、大文本走附表或对象存储、状态用 `TINYINT` 而不是 `ENUM`。**

### 3.5 字符集与排序规则：比长度更早该定的一件事

**来源**：《高性能 MySQL》（第 4 版）第 6 章「选择存储引擎和数据类型」相关的字符集讨论。

| 问题 | 结论 |
| --- | --- |
| `utf8` 是什么？ | 它是 **`utf8mb3` 的别名**，只能存 3 字节编码的字符，**存不了 emoji 和部分生僻字**；8.0 里它没被禁止，但每次使用都报 **Warning 3719**：现在是 `utf8mb3`、将来会变成 `utf8mb4` |
| 应该用什么？ | `utf8mb4`，新建库表显式写明，别依赖默认值 |
| 排序规则怎么选？ | 8.0 引入 `0900` 系列（基于 UCA 9.0.0），默认是 `utf8mb4_0900_ai_ci`；`_ai` 表示**重音不敏感**（实测 é 与 e 判等为 1），`_as` 表示重音敏感，`_bin` 按字节比（实测为 0）；`_ci` 未标 `_ai`/`_as` 时默认按 `_ai` 处理。`utf8mb4_general_ci` 仍然可用（ID 45），为兼容旧库而保留 |
| 为什么它是 schema 问题而不是显示问题？ | 排序规则决定**索引的排序方式与等值判断**：两列 collation 不同时，实测 join 直接 `ERROR 1267`，用 `COLLATE` 强转则索引失效（见 4.3 与下面的实测块） |

```sql
-- ① 服务器与当前库的默认字符集 / 排序规则
SELECT @@character_set_server, @@collation_server,
       @@character_set_database, @@collation_database;
SHOW CREATE DATABASE docverify;

-- ② `utf8` 这个别名实际落到哪
CREATE TABLE t_alias (s VARCHAR(10)) CHARACTER SET utf8;
SHOW WARNINGS;
SHOW CREATE TABLE t_alias;

-- ③ 3 字节上界：中文进得去，emoji 进不去
INSERT INTO t_alias VALUES ('中文');
INSERT INTO t_alias VALUES ('😀');

-- ④ 排序规则决定"相等"的含义
SELECT 'é' COLLATE utf8mb4_0900_ai_ci = 'e' COLLATE utf8mb4_0900_ai_ci;
SELECT 'é' COLLATE utf8mb4_bin        = 'e' COLLATE utf8mb4_bin;

-- ⑤ 排序规则不一致的两条出路（t_c1 是 0900_ai_ci，t_c2 是 general_ci）
SELECT a.s FROM t_c1 a JOIN t_c2 b ON a.s = b.s;
SELECT s FROM t_ci WHERE s = 'abc' COLLATE utf8mb4_general_ci;   -- t_ci.s 带索引 idx_s
```

实测输出（本机 Docker Desktop 的 `mysql:8.0`，**8.0.46**，库 `docverify`；③ 的 emoji 与 ⑤ 的 join 都是**报错**，
一批里报错后续语句默认不执行，靠 `--force` 才跑完整批）：

```text

utf8mb4   utf8mb4_0900_ai_ci  utf8mb4   utf8mb4_0900_ai_ci

CREATE DATABASE `docverify` /*!40100 DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci */ /*!80016 DEFAULT ENCRYPTION='N' */

Charset    Description           Default collation     Maxlen
latin1     cp1252 West European  latin1_swedish_ci          1
utf8mb3    UTF-8 Unicode          utf8mb3_general_ci         3
utf8mb4    UTF-8 Unicode          utf8mb4_0900_ai_ci         4

Warning  3719  'utf8' is currently an alias for the character set UTF8MB3, but will be
                an alias for UTF8MB4 in a future release.
CREATE TABLE `t_alias` ( `s` varchar(10) DEFAULT NULL ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb3

ERROR 1366 (HY000): Incorrect string value: '\xF0\x9F\x98\x80' for column 's' at row 1
s       chars  bytes
中文        2      6

ai_equal  bin_equal
       1         0

ERROR 1267 (HY000): Illegal mix of collations (utf8mb4_0900_ai_ci,IMPLICIT) and
                (utf8mb4_general_ci,IMPLICIT) for operation '='
```

另两条补测（同一实例，SQL 见随篇留档的 `Z2_charset2`、`Z3_collate` 两组）：

```text
-- 非严格模式（SET SESSION sql_mode = ''）往 utf8mb3 列塞 emoji
Warning  1366  Incorrect string value: '\xF0\x9F\x98\x80'  for column 's' at row 1
Warning  1366  Incorrect string value: '\xF0\x9F\x98\x80b' for column 's' at row 2
s      chars  bytes  hex
?          1      1  3F
a?b        3      3  613F62

-- COLLATE 强转的代价：t_ci.s 是 varchar(20) NOT NULL（utf8mb4_0900_ai_ci），带 idx_s
WHERE s = 'abc'                             → type: ref    key: idx_s  key_len: 82  ref: const  rows: 2
WHERE s = 'abc' COLLATE utf8mb4_general_ci  → type: index  key: idx_s  key_len: 82  ref: NULL   rows: 3  filtered: 33.33
WHERE s COLLATE utf8mb4_general_ci = 'abc'  → type: index（同样退化）
```

四条只有实测才给得准的结论：

1. **8.0 的默认确实已是 `utf8mb4` + `utf8mb4_0900_ai_ci`**（服务器与当前库两边一致），但这是**实例级**默认值，
   `my.cnf` 一改全实例跟着变 —— 建表规范里显式写 `CHARACTER SET utf8mb4 COLLATE ...` 才是可移植的做法。
2. **`utf8` 现在解析成 `utf8mb3`**，而且 `SHOW CREATE TABLE` 里落下来的就是 `CHARSET=utf8mb3`。
   也就是说存量库里写 `utf8` 的表**实际已经是 3 字节字符集**；等别名改指 `utf8mb4`，同一份 DDL 的语义又会变 ——
   这是"不要写 `utf8`"的真正理由，而不是"它已被废弃"（8.0 并没有禁止它）。
3. **emoji 的报错是 `ERROR 1366`，非严格模式则变成"内容被改写"**：实测把放不下的字符替换成 `?`（0x3F），
   整串长度按替换后重新算（`a😀b` → `a?b`）。这比报错危险得多，因为应用层看不出异常。
4. **排序规则不一致时先报错、强转再退化**：join 直接 `1267`；`COLLATE` 强转后 `EXPLAIN` 从 `ref` 变 `index`，
   连 `key_len` 都没变（索引还是那棵），**变的是"能不能用它定位"**。

## 四、schema 设计陷阱

**来源**：《高性能 MySQL》（第 4 版）第 6 章「Schema 设计与管理」的读后整理，按主题归纳而非逐字摘录。

**本节要点**：前三节讲的是"单个列选什么类型"，这一节讲"一张表 / 一组表怎么搭"。
本书列的五个陷阱的共同代价都落在**索引能不能用**和**一次 IO 能带走多少有用数据**上。

### 4.1 列太多、行太宽：读一列也要搬一页

InnoDB 以**页**为单位进出 buffer pool，读一行里的一个字段，代价是整行所在页都要进内存。
列越多、越大，同样大小的 buffer pool 能装的有效行数就越少 —— 命中率下降最终表现为**同一句 SQL 时快时慢**。

- 判据：慢日志里 `Rows_read` 远大于 `Rows_sent`，或 digest 表的
  `SUM_ROWS_EXAMINED / SUM_ROWS_SENT` 比值偏大（口径见 [观测与诊断.md](观测与诊断.md) 第 5.1 节）；
- 做法：**很少用到又很宽**的列垂直拆到附表；结构不固定的扩展属性用 `JSON` 列
  （存储与索引代价见 [架构与执行链路.md](架构与执行链路.md) 的 6.4）；核心查询字段必须提炼成独立列。

### 4.2 表拆得太碎：规范化过头就是 join 税

范式减少冗余、让更新更便宜，但每次读都要用 join 把数据拼回来：每多一张表，
优化器多一次索引查找，执行计划出错的机会也多一处。判据很简单 ——
**冗余字段只在"读远多于写"的路径上加**，写放大与一致性代价要一起算（详细取舍见
[数据建模.md](数据建模.md)）。

### 4.3 join 列的类型与字符集必须一致

这是本章最"便宜"的一条性能经验：**join 的两列类型不一致时会做隐式转换，而转换后的列用不上索引**。
常见踩法有三种：

```text
int       JOIN bigint unsigned   -- 符号或宽度不同
utf8mb3   JOIN utf8mb4           -- 字符集不同，需转换
utf8mb4_general_ci JOIN utf8mb4_0900_ai_ci  -- 字符集相同但 collation 不同
```

实测这两条路各有结局（8.0.46，见 3.5 的实测块）：

- **排序规则不同 + 不写 `COLLATE`** → 根本不给执行计划，`ERROR 1267 Illegal mix of collations`；
- **写 `COLLATE` 强转**（常量侧或列侧都一样） → 能跑，但 `EXPLAIN` 从 `type: ref / ref: const / rows: 2`
  退化成 `type: index / ref: NULL / rows: 3`，也就是**放弃索引定位、改成扫完整棵索引**。

建表规范里把「关联列类型 + 字符集 + 排序规则三件一致」写成硬约束，
比事后 `EXPLAIN` 再改表便宜得多（隐式转换的完整口径见 [索引设计与EXPLAIN.md](索引设计与EXPLAIN.md)）。
比事后 `EXPLAIN` 再改表便宜得多（隐式转换的完整口径见 [索引设计与EXPLAIN.md](索引设计与EXPLAIN.md)）。

### 4.4 分区表不是分片

分区把一张表按规则切成多个物理片段，**仍然是同一个表名、同一个实例**，
适合"按时间淘汰旧数据"和"查询能带上分区键从而只扫部分分区"；
它解决不了单实例的写入瓶颈与容量上限。分库分表的判据见
[分表与路由.md](分表与路由.md)，本节只补一句：**先确认查询条件里带分区键**，
否则分区只是把一次全表扫描摊到更多文件上。

### 4.5 改表结构：慢的 ALTER 仍然是风险项

8.0.12 起 `ALTER TABLE` 有了 `INSTANT`（只改字典元数据，不动行），
不写 `ALGORITHM` 时按 `INSTANT → INPLACE → COPY` 依次尝试；
`COPY` 会锁写并整表重灌。显式写 `ALGORITHM=INPLACE, LOCK=NONE`、
以及超大表走影子表工具的做法，见 [深分页与索引变更.md](深分页与索引变更.md) 与 [数据迁移与备份恢复.md](数据迁移与备份恢复.md) ——
**这两处已经写透了，本篇不重复**。

## 五、JOIN 怎么用？在什么场景下才该用？

**本节要点**：**结论偏向"少用 JOIN"**，
能讲出"互联网为什么不推荐 JOIN"才是关键。

### 5.1 JOIN 是什么

最常用的是**内连接（`INNER JOIN`）**：

```sql
SELECT o.id, o.amount, u.name
FROM orders o
INNER JOIN users u ON o.user_id = u.id;
```

> **两张表里都有、且能相互匹配的数据才会被查出来**——
> 相当于**把两张表的数据拼到一起，再查出所需字段**。

### 5.2 ⚠️ 关键认知：JOIN 不一定更快

> **`INNER JOIN` 只是"能一次性把数据查出来"，它并不是"性能最优"的选择。**

**传统企业 vs 互联网企业的思路差异**：

| | 思路 |
|---|---|
| **传统企业** | **想尽一切办法一次性把所需数据都查出来**（更看重"一次拿到完整结果"） |
| **互联网企业** | **想尽办法加快单次请求的过程**（更看重延迟） |

**核心判断**：

> **数据量大之后，一次 JOIN 的查询效率往往比不过两次单表查询。**

### 5.3 互联网的常见替代做法：拆成单表查询 + 应用层拼接

```text
① 先查 table1
② 再查 table2
③ 在应用程序的内存里把两次结果拼接起来，得到最终数据
```

**为什么这样更快**：

| 原因 | 说明 |
|---|---|
| **避免大表 JOIN 的中间结果集** | JOIN 会产生笛卡尔积式的中间结果，数据量大时内存/临时表压力剧增 |
| **两次查询都能走索引** | 单表按主键/索引精确查询，**每次都是 O(log n) 级别的定位** |
| **可并行** | 两次查询甚至可以用 `errgroup` 并发执行，**总耗时取较慢的那个** |
| **易缓存** | 两张表的结果可以分别进 Redis，**命中率比 JOIN 结果高得多** |
| **便于分库分表** | 拆表后天然支持分片；JOIN 在分片后几乎无法使用 |

上表这五条"为什么拆成单表更快"，在本机 10 万用户 / 100 万订单的夹具上量过（细节见「使用三」）：
**小结果集时两种写法打平（各 12~14 ms），拆单表在"快"这一项上换不到东西**。
真正能落地的是"避免中间结果集"那一条 —— 连接列没索引时，优化器对联接输出行数的估算
会**放大约 250 倍**（估 250 万行、实际 1 万行，实测见第 2.1 节）。
这就是"中间结果集"在执行计划里的真实样子：它不一定让这条 SQL 当场更慢，
但会让**优化器失去判断力**，后面的联接顺序、索引选择、半联接改写全跟着翻车。

**Go 中的做法示例**：

```go
// 用 errgroup 并发两次单表查询，再在内存拼接
g, ctx := errgroup.WithContext(ctx)
var users map[int64]*User
var orders []*Order

g.Go(func() error { users, err = userRepo.BatchGet(ctx, ids); return err })
g.Go(func() error { orders, err = orderRepo.ListByUserIDs(ctx, ids); return err })
if err := g.Wait(); err != nil { return err }
// 内存里按 user_id 归并
```

### 5.4 什么场景下才适合用 JOIN

**两类典型场景**：

| 场景 | 说明 |
|---|---|
| **企业管理内部系统** | 数据量不大、开发效率优先，JOIN 很方便 |
| **报表统计 / 跑定时任务** | 例如**凌晨跑任务统计、抓取数据**——不在业务高峰，性能压力小 |

**⚠️ 一个重要的风险提示**：

> 当表里的数据特别大时，如果**同一个数据库既给前端业务用、又给企业后端用**，
> 那么**用 JOIN 可能会影响前端系统**（一次重查询会占满 IO/CPU）。
>
> 所以内部/报表类查询**最好走只读从库**，与线上业务隔离。

### 5.5 结论

> **能用单表查询就用单表查询，尽可能避免连接查询。**
>
> **需要 JOIN 的场景，基本是企业管理系统和离线报表/定时任务**；
> 而**面向 C 端的高并发链路**，应当**拆成多次单表查询 + 应用层拼接 + 缓存**。

## 六、MySQL 到底怎么执行一个 JOIN？

**来源**：《高性能 MySQL》（第 4 版）第 6 章「太多的联接」、第 8 章「执行计划」相关的联接执行方式。

**本节要点**：1.2 已经给出「JOIN 不一定更快」的结论，这一节补它的原因 ——
MySQL 的联接算法本质都是**嵌套循环**，内层能不能走索引决定了代价是 `M×N` 还是 `M×logN`。

### 6.1 三种执行方式：NLJ、Index NLJ、Hash Join

```text
① Simple Nested Loop（无索引）
   for 外层每一行:  for 内层全表扫描:  比较
   代价 ≈ M × N            ← 这就是"join 列没索引"的真实成本

② Index Nested Loop（内层有可用索引，EXPLAIN 里内层 type=ref）
   for 外层每一行:  走内层索引点查
   代价 ≈ M × logN         ← 唯一真正有效的优化方向

③ 内层没索引时怎么少扫几遍
   8.0.18 之前： Block Nested Loop —— 把外层若干行攒进 join_buffer，再扫一遍内层批量比较
   8.0.18 起：  无索引的等值联接改用 Hash Join（小的一侧建哈希，另一侧探测）
   8.0.20 起：  原先走 BNL 的场景**全部**改走 Hash Join，BNL 不再被使用
```

读执行计划时的三条判据：

- 内层 `type=ALL` 且 `Extra` 里出现 `Using join buffer` → **缺索引**，
  先给联接列建索引，再谈其他（`EXPLAIN` 各列含义见 [架构与执行链路.md](架构与执行链路.md)）；
- 8.0.18+ 看到 `Inner hash join` / `Left hash join` 说明优化器已经在用哈希兜底 ——
  它比 BNL 快，但**两侧都要扫一遍**，仍然不如索引点查；
- `EXPLAIN ANALYZE`（8.0.18 起）会**真的执行**语句，并给出每个迭代器的
  `actual time` / `rows` / `loops`，用来核对"优化器估的行数"和"实际行数"差多少 ——
  估偏了才轮到统计信息与写法，估准了才是纯粹的索引问题。

本机 8.0.46 上这三条判据都能直接量出来（两张 5000 行、连接列都没有索引的表）：

```text
# 判据 ①②：FORMAT=TREE 里就是迭代器名
-> Aggregate: count(0)  (cost=2.75e+6 rows=1)
    -> Inner hash join (b.k = a.k)  (cost=2.5e+6 rows=2.5e+6)
        -> Table scan on b  (cost=0.0101 rows=5000)
        -> Hash
            -> Table scan on a  (cost=500 rows=4993)

# 判据 ③：EXPLAIN ANALYZE 会真的执行，估算与实际的差距一眼可见
    -> Inner hash join (b.k = a.k)  (cost=2.5e+6 rows=2.5e+6)
                                  (actual time=3.51..5.41 rows=10000 loops=1)
```

- **估算 vs 实际**：无索引时优化器估 `rows=2.5e+6`，实际只有 **10000 行**，偏了约 **250 倍**；
  给 `b.k` 补上索引之后估 `rows=9986`、实际 `rows=10000` —— 几乎正中。
  "估偏了才轮到统计信息与写法背锅"这条判据在这台实例上能复现。
- ⚠️ **"内层走索引一定更快"在小数据量上不成立**。同一份夹具的两种计划实测：
  Hash Join 是 `actual time=3.51..5.41 rows=10000 loops=1`；
  索引版 `Nested loop inner join` 是 `actual time=0.18..13 rows=10000 loops=1`，
  里面那行 `Covering index lookup on b using idx_k` 标着 `loops=5000` —— **慢了一倍多**，
  因为它把内层点查重复做了 5000 次。索引换来的是**结果集变大时的可扩展性**，不是无条件的快。
- 顺手记录一个估算细节：同一份数据在 `ANALYZE TABLE` 之前估 `rows=4993`、之后估 `rows=5000`
  （实际 5000）—— 统计信息对这种小表的影响只有 0.1%，**别指望 ANALYZE 能救回翻车的计划**。

### 6.2 `join_buffer_size` 治的是哪种慢

`join_buffer_size` 决定 BNL 一轮能攒多少组外层行，攒得越多、内层被重复扫描的次数越少；
反过来它**按连接分配**，调大等于给每个连接多要一块内存（每连接内存的算法见
[参数调优.md](参数调优.md) 第 4.2 节）。

结论要说得准确一点：8.0 之后 **BNL 这个算法确实退场了，但它的名字、开关、hint 全都还在**，
而且 hint 换了职责。实测（两张 5000 行、连接列无索引的表，耗时取 `SHOW PROFILE` 的服务端时长）：

| 设置 | FORMAT=TREE 里的迭代器 | 服务端耗时（两轮） |
|---|---|---|
| 默认 | `Inner hash join` | 3.63 / 3.48 ms |
| `/*+ BNL(b) */` | `Inner hash join` | 4.16 / 4.10 ms |
| `/*+ NO_BNL(b) */` | `Nested loop inner join`（不挂缓冲） | 5077 / 5638 ms |
| `optimizer_switch='block_nested_loop=off'` | `Nested loop inner join`（不挂缓冲） | 5377 ms |

- 那个 **≈1400 倍**的差距才是"攒批"真正的价值：`BNL` / `NO_BNL` 现在管的是
  **要不要挂 join buffer**，底下的算法早就是哈希了，hint 名只是历史遗留；
- ⚠️ `optimizer_switch` 里的 `hash_join=on` 是**摆设**：实测单独设 `hash_join=off` 之后
  `SELECT @@optimizer_switch LIKE '%hash_join=off%'` 返回 1（开关确实改了），
  但 `EXPLAIN` 的 Extra 仍是 `Using where; Using join buffer (hash join)`；
  要两个开关一起关（`hash_join=off,block_nested_loop=off`）Extra 才变成光秃秃的 `Using where`；
- `join_buffer_size` 实测默认 **262144**（256 KB），调到 8 MB 在这份夹具上量不出差异
  （墙钟 19 / 21 ms，里面还含客户端启动的固定开销）—— 所以"调大它治慢 JOIN"在 8.0 上换不来什么，
  慢 JOIN 的正解仍然是**给联接列建索引**或**减少联接次数**。

### 6.3 「太多的联接」是 schema 问题，不是 SQL 问题

每多一张表参与联接，就多一次索引查找、多一处优化器可能估错的地方，
执行计划翻车的概率也乘一次。本书把它归到 schema 设计层面，判据有三条：

- **关联列的类型、字符集、排序规则必须一致**，否则隐式转换让内层索引用不上，
  直接退化回 2.1 的 ①（约束写法见 [数据建模.md](数据建模.md) 第 4.3 节）；
- **读多写少**的宽联接，用冗余列 / 组装好的宽表把 join 换成一次单表读，
  代价是更新要同步多份 —— 与缓存的一致性问题是同一类（见
  [缓存问题与方案.md](../../缓存/缓存问题与方案.md)）；
- **跨服务、跨库的联接不该写在 SQL 里**：这正是 1.3 的"多次单表查询 + 应用层拼接"，
  分库分表之后只有这一条路（见 [分表与路由.md](分表与路由.md)）。

## 七、反范式与冗余：什么时候该违反范式

**本节要点**：反范式不是"不规范"，是**用写入代价换读取代价** ——
先问清"读多写少吗、一致性要求多高"，再决定要不要冗余。

| 维度 | 规范化 | 反范式（冗余） |
|---|---|---|
| 读 | 要 JOIN，可能多次查 | **一次查完**，列表页最受益 |
| 写 | 只改一处 | **写放大**：一份数据要更新 N 个地方 |
| 一致性 | 天然一致 | ⚠️ 冗余副本可能不一致 |
| 空间 | 省 | 费 |
| 适用 | 写多、强一致、关系复杂 | **读多写少、能接受最终一致** |

**什么时候该冗余**（三条同时满足才做）：

1. 读**远多于**写，且这段读取在**热路径**上（列表页、详情页）；
2. 被冗余的字段**几乎不变**（用户名、商品名、类目名）—— 会变的字段要慎重；
3. 一致性**可以靠补偿收敛**：用定时对账 / 事件驱动去修，而不是让用户等。

**三种典型冗余手法**：

| 手法 | 做法 | 代价 |
|---|---|---|
| **字段冗余** | 订单表直接存 `user_name`，不 JOIN 用户表 | 用户改名后历史订单显示旧名（业务上常常可接受） |
| **计数冗余** | 帖子表存 `comment_count` | ⚠️ 并发更新同一行会成热点；要用原子 `+1` 或异步归并 |
| **宽表 / 物化视图** | 把多表结果**预计算**成一张宽表 | 更新有延迟；必须有重建任务 |

⭐ **宽表 vs 规范化**：宽表（`WHERE` / `ORDER BY` 都在一张表上）在高并发读场景完胜，
代价是**写放大 + 一致性维护**。判据是**读写比**：读:写 ≥ 10:1 且能接受最终一致时才做。

⚠️ 冗余字段一旦落地，**必须同时回答"谁来修它"**（定时对账 / 事件驱动 / 双写 + 校验），
否则就是一份迟早会错的数据。

## 八、8.0 给数据建模带来的新能力

**本节要点**：8.0 让一部分"必须靠冗余才能解决"的问题**不必要了** ——
窗口函数与 CTE 让 SQL 能表达更多逻辑，函数索引 / 多值索引让 JSON 也能进索引。

| 能力 | 版本 | 它改变了什么 |
|---|---|---|
| **CTE / 递归 CTE** | 8.0.1 | 把复杂子查询写成 `WITH`，可读性大幅提升；递归 CTE 能直接查**树形 / 层级**数据 |
| **窗口函数** | 8.0.2 | ⭐ **不必再为"组内排名 / 累计"加冗余列或回应用层算** |
| **降序索引** | 8.0 | 真正的降序存储，`ORDER BY a ASC, b DESC` 能用一个索引走完 |
| **不可见索引** | 8.0 | 删索引前先"藏起来"验证没人用，**给删索引留退路** |
| **函数索引** | 8.0.13 | 以前"函数导致索引失效"只能改 SQL，现在可以**给表达式建索引** |
| **多值索引** | 8.0.17 | `JSON` 数组的**每个元素**都能进索引（以前只能整段存） |
| **Hash Join** | 8.0.18 | 等值 JOIN 且无索引时不再只能走 BNL，大表关联快一个量级 |

### 8.1 窗口函数：为什么它减少了很多"为了查得快而冗余"

以前要"取每个分类下最新的 3 条"，常见做法只有两条：① 应用层查全量再切（数据一多就崩）；
② 加冗余列（如 `is_latest`）再用定时任务维护。

**窗口函数让它在一条 SQL 里完成**：

```sql
-- 每个 category 内按 created_at 倒序取前 3 条
SELECT id, category, title, created_at
FROM (
  SELECT id, category, title, created_at,
         ROW_NUMBER() OVER (PARTITION BY category ORDER BY created_at DESC) AS rn
  FROM article
) t
WHERE rn <= 3;
```

⚠️ 两条必须说清的：

1. **窗口函数不减少扫描量**。它是在**结果集上**做计算，`WHERE` 该走的索引还得走；
   它的价值是"少一次往返 / 少一份冗余"，**不是"扫描变快"**；
2. `ROW_NUMBER()` / `RANK()` / `DENSE_RANK()` 在**并列**时行为不同
   （`1,2,3,4` / `1,2,2,4` / `1,2,2,3`），选错会让业务口径出错。

> 8.0 索引能力（函数索引 / 多值索引 / 降序 / 不可见）的完整口径见
> [索引设计与EXPLAIN.md](索引设计与EXPLAIN.md) 的第十节。

| MySQL 类型 | Go（database/sql 默认扫描到） | Java（JDBC 默认映射） | 注意点 |
|---|---|---|---|
| `timestamp` | `time.Time` | `java.sql.Timestamp` / `LocalDateTime` | 存的是 UTC，**取出时按连接时区转换**；范围只到 2038 |
| `datetime` | `time.Time` | `java.sql.Timestamp` / `LocalDateTime` | 存的就是字面值，不随时区变；范围到 9999 |
| `date` | `time.Time`（时分秒为 0） | `java.sql.Date` / `LocalDate` | ⚠️ 时区偏移可能让「日期」差一天 |
| `bigint`（存毫秒时间戳） | `int64` | `long` / `Instant` | 无时区歧义，但可读性差、不能直接用 SQL 函数 |
| `varchar`（RFC3339 字符串） | `string` | `String` | 可读性最好，代价是排序/比较的语义与体积 |

**驱动侧必须显式配的两件事**：

```text
Go   DSN: ?parseTime=true&loc=UTC          # 不配 parseTime 会扫成 []byte 或报错

Java JDBC: serverTimezone=UTC（或在 URL 里写清时区）
           ⚠️ 8.x 驱动对 serverTimezone 更严格，缺失时行为随版本变化
```

**统一口径的三条建议**：

1. **同一个库只用一种时间语义**——要么全 UTC `timestamp`，要么全字面量 `datetime`，不要混用；
2. 应用层统一用 **UTC** 存、只在**展示层**按用户时区转换；
3. 时间列上做范围查询时，**别对列做函数运算**（`DATE(created_at) = ?` 会让索引失效，见 [索引设计与EXPLAIN.md](索引设计与EXPLAIN.md)）。

> ⭐ 这里的关键不是「谁是 8 字节」，而是**时区语义**：`timestamp` 存的是「某一时刻」，`datetime` 存的是「墙上时间」——业务要跨时区就必须说清选哪个，并把这个约定写进建表规范。

## 使用二：Go（拆 JOIN：并发单表查询 + 内存归并）⭐

### 1. 拆 JOIN：并发单表查询 + 内存归并

第一节的结论是「面向 C 端的高并发链路，拆成多次单表查询 + 应用层拼接」。落到代码要注意三件事：
**用批查而不是逐条查（N+1）**、**并发写变量不要用共享 `err`**、**归并用 map 而不是嵌套循环**。

```go
package joinfree

import (
	"context"
	"database/sql"
	"strings"

	"golang.org/x/sync/errgroup"
)

type User struct {
	ID   int64
	Name string
}

type Order struct {
	ID     int64
	UserID int64
	Amount int64
}

// OrderView 给前端的扁平结构——JOIN 想要的效果，用内存拼出来。
type OrderView struct {
	OrderID     int64  `json:"order_id"`
	Amount      int64  `json:"amount"`
	UserID      int64  `json:"user_id"`
	UserName    string `json:"user_name"`
	UserMissing bool   `json:"user_missing"` // 单表拼接必须显式表达"左连接补 NULL"的语义
}

// ✗ N+1：先查订单，再在循环里逐个查用户。100 条订单 = 101 次往返。
func listWithUserNPlusOne(ctx context.Context, db *sql.DB, uid int64) ([]OrderView, error) {
	orders, err := ordersByUsers(ctx, db, []int64{uid})
	if err != nil {
		return nil, err
	}
	out := make([]OrderView, 0, len(orders))
	for _, o := range orders {
		var u User
		if err := db.QueryRowContext(ctx, `SELECT id, name FROM users WHERE id = ?`, o.UserID).Scan(&u.ID, &u.Name); err != nil {
			return nil, err
		}
		out = append(out, OrderView{OrderID: o.ID, Amount: o.Amount, UserID: u.ID, UserName: u.Name})
	}
	return out, nil
}
```

上面是反例；下面是正确写法：两次单表查询并发跑，再在内存里按 map 归并出 JOIN 的效果。

```go
// ✓ 两次单表查询 + 并发 + 内存归并：总耗时 ≈ 较慢的那一次。
func ListWithUser(ctx context.Context, db *sql.DB, userIDs []int64) ([]OrderView, error) {
	if len(userIDs) == 0 {
		return nil, nil
	}

	var (
		orders []Order
		users  map[int64]User
	)

	// ⚠️ 两个 goroutine 分别持有自己的返回值，不要再共享外层 err 变量——
	// 共享 err 是数据竞争（go test -race 会报，go vet 不一定报）。errgroup 本身就负责传错误。
	g, gctx := errgroup.WithContext(ctx)
	g.Go(func() error {
		v, err := ordersByUsers(gctx, db, userIDs)
		orders = v
		return err
	})
	g.Go(func() error {
		v, err := usersByIDs(gctx, db, userIDs)
		users = v
		return err
	})
	if err := g.Wait(); err != nil {
		return nil, err
	}

	out := make([]OrderView, 0, len(orders))
	for _, o := range orders {
		v := OrderView{OrderID: o.ID, Amount: o.Amount, UserID: o.UserID}
		if u, ok := users[o.UserID]; ok { // map 查找 O(1)，别写成 for + for
			v.UserName = u.Name
		} else {
			v.UserMissing = true // 对应用户不存在/已删除——这是 LEFT JOIN 补 NULL 的等价物
		}
		out = append(out, v)
	}
	return out, nil
}
```

归并所依赖的两个批查函数放在最后，它们各自只做一条 `IN (...)` 的单表查询。

```go
func ordersByUsers(ctx context.Context, db *sql.DB, ids []int64) ([]Order, error) {
	args := make([]any, len(ids))
	for i, id := range ids {
		args[i] = id
	}
	q := `SELECT id, user_id, amount FROM orders WHERE user_id IN (` + strings.TrimSuffix(strings.Repeat("?, ", len(ids)), ", ") + `)`
	rows, err := db.QueryContext(ctx, q, args...)
	if err != nil {
		return nil, err
	}
	defer rows.Close()

	var out []Order
	for rows.Next() {
		var o Order
		if err := rows.Scan(&o.ID, &o.UserID, &o.Amount); err != nil {
			return nil, err
		}
		out = append(out, o)
	}
	return out, rows.Err()
}

func usersByIDs(ctx context.Context, db *sql.DB, ids []int64) (map[int64]User, error) {
	args := make([]any, len(ids))
	for i, id := range ids {
		args[i] = id
	}
	q := `SELECT id, name FROM users WHERE id IN (` + strings.TrimSuffix(strings.Repeat("?, ", len(ids)), ", ") + `)`
	rows, err := db.QueryContext(ctx, q, args...)
	if err != nil {
		return nil, err
	}
	defer rows.Close()

	out := make(map[int64]User, len(ids))
	for rows.Next() {
		var u User
		if err := rows.Scan(&u.ID, &u.Name); err != nil {
			return nil, err
		}
		out[u.ID] = u
	}
	return out, rows.Err()
}
```

> 上文第一节的示意代码里两个 `g.Go` 共用了外层 `err`，那是**数据竞争**写法；以本节 `ListWithUser` 为准。

## 使用三：Java（`groupingBy` + 并发批查）

### 1. 拆 JOIN：`groupingBy` + 并发批查

第一节的「应用层拼接」在 Java 里就是 `Stream` 分组归并（更多写法见 [Stream流实战.md](../../../../01-编程语言/java/Stream流实战.md)）：

```java
package notes.mysql.joinfree;

import java.util.List;
import java.util.Map;
import java.util.concurrent.CompletableFuture;
import java.util.function.Function;
import java.util.stream.Collectors;
import org.springframework.jdbc.core.JdbcTemplate;

public class OrderAssembler {

    private final JdbcTemplate jdbc;

    public OrderAssembler(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    public List<OrderView> list(List<Long> userIds) {
        if (userIds.isEmpty()) {
            return List.of();
        }

        // 两次单表批查，并发发起：总耗时取较慢的那个
        CompletableFuture<List<Order>> ordersF = CompletableFuture.supplyAsync(
                () -> jdbc.query("SELECT id, user_id, amount FROM orders WHERE user_id IN (?)",
                        (rs, i) -> new Order(rs.getLong("id"), rs.getLong("user_id"), rs.getLong("amount")),
                        join(userIds)));
        CompletableFuture<Map<Long, User>> usersF = CompletableFuture.supplyAsync(
                () -> jdbc.query("SELECT id, name FROM users WHERE id IN (?)",
                                (rs, i) -> new User(rs.getLong("id"), rs.getString("name")),
                                join(userIds))
                        .stream().collect(Collectors.toMap(User::id, Function.identity())));

        Map<Long, User> users = usersF.join();
        return ordersF.join().stream()
                .map(o -> {
                    User u = users.get(o.userId()); // null 就是 LEFT JOIN 补 NULL 的情况
                    return new OrderView(o.id(), o.amount(), o.userId(), u == null ? null : u.name(), u == null);
                })
                .toList();
    }

    // ⚠️ 这里为了省篇幅直接把 id 列表拼进 SQL：生产必须改用 ?占位符 或 NamedParameterJdbcTemplate。
    // 因为 Long 列表不存在引号问题，但拼 SQL 这个动作一旦被复制到字符串场景就是注入。
    private static String join(List<Long> ids) {
        return ids.stream().map(String::valueOf).collect(Collectors.joining(","));
    }

    record Order(long id, long userId, long amount) {}

    record User(long id, String name) {}

    record OrderView(long orderId, long amount, long userId, String userName, boolean userMissing) {}
}
```

> ⚠️ `CompletableFuture.supplyAsync` 默认用公共 `ForkJoinPool`，**会把数据库并发放大到 CPU 核数倍**；
> 生产要传专用线程池，且线程池大小要和 HikariCP 的 `maximumPoolSize` 对齐，否则只是在排队抢连接。

## 使用四：本地验证与 JOIN / 两次单表的实测

前面所有结论都可以在一台本地 MySQL 上跑出来，值得亲手验一次——尤其是「JOIN 不一定更快」。
本节下面的数字就是本机 8.0.46 按这段命令跑出来的（只有造数那一步要先抬递归深度，见实测补充）。

### 1. 起库与造数

```bash
docker run -d --name mysql8 -p 3306:3306 \
  -e MYSQL_ROOT_PASSWORD=root123456 -e MYSQL_DATABASE=test \
  mysql:8.0 --innodb-buffer-pool-size=256M

# 等就绪（健康检查比 sleep 可靠）
until docker exec mysql8 mysqladmin ping -uroot -proot123456 --silent; do sleep 1; done

docker exec -i mysql8 mysql -uroot -proot123456 test <<'SQL'
CREATE TABLE users (
  id BIGINT PRIMARY KEY,
  name VARCHAR(32) NOT NULL,
  KEY idx_name (name)
) ENGINE = InnoDB;

CREATE TABLE orders (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id BIGINT NOT NULL,
  amount BIGINT NOT NULL,
  KEY idx_user (user_id)            -- 被驱动表的连接列要有索引；缺了不一定当场更慢（实测见「使用三」），但优化器的行数估算会失控
) ENGINE = InnoDB;

-- 造 10 万用户
INSERT INTO users (id, name)
SELECT t.N, CONCAT('u', t.N) FROM (
  WITH RECURSIVE s(N) AS (SELECT 1 UNION ALL SELECT N + 1 FROM s WHERE N < 100000)
  SELECT N FROM s
) t;

-- 造 100 万订单（10 用户 × 10 万，故意做成倾斜分布，便于观察"数据量决定 JOIN 代价"）
INSERT INTO orders (user_id, amount)
SELECT u.id, 100 FROM users u JOIN users s ON s.id <= 10;
SQL
```

本机照抄这段跑了一遍，**第一处就撞墙**：`WITH RECURSIVE` 的默认递归深度只有 1000。

```text
ERROR 3636 (HY000): Recursive query aborted after 1001 iterations.
Try increasing @@cte_max_recursion_depth to a larger value.
```

造 10 万用户必须先抬这个会话变量：

```sql
SET SESSION cte_max_recursion_depth = 110000;   -- 默认 1000，抬到比目标行数大即可
```

抬完之后这份夹具是能跑出来的，实测（同一台实例，`innodb_buffer_pool_size` 用默认值）：

| 步骤 | 实测 |
|---|---|
| 10 万用户 | 371 ms |
| 100 万订单（文档这条自联接写法） | 35,139 ms |
| `orders` 体积 | 数据 17 MB + 索引 20 MB（`information_schema.tables`） |
| 倾斜分布确实生效 | 头部 `user_id` 各 10 万行 |

- ⚠️ `docker run -p 3306:3306` 在本机会撞已有端口，实测用 **13306**；
  容器名要自己新建，别复用别人的实例（本机用户已有 `seckill-mysql` 等）。
- 顺手量到的一个 DDL 数字：100 万行的表上 `DROP INDEX idx_user` 再 `ADD INDEX idx_user`，
  重建耗时 **1526 ms** —— 在线 DDL 的代价感可以拿这个数打底。

### 2. 同一需求的两种写法对比

```sql
-- 写法 A：INNER JOIN
SELECT o.id, o.amount, u.name
FROM orders o INNER JOIN users u ON o.user_id = u.id
WHERE u.name = 'u1000' LIMIT 50;

-- 写法 B：两次单表（应用层拼接）—— 等价于下面两条
SELECT id, name FROM users WHERE name = 'u1000';           -- 走 idx_name，1 行
SELECT id, user_id, amount FROM orders WHERE user_id = ? LIMIT 50;  -- 走 idx_user
```

**怎么判断谁快**（对 [架构与执行链路.md](架构与执行链路.md) 链路里「优化器选路径」做一次实测）：

```bash
# 分别看执行计划：重点看 type / key / rows / Extra
docker exec -i mysql8 mysql -uroot -proot123456 test -e "EXPLAIN FORMAT=JSON SELECT o.id,o.amount,u.name FROM orders o INNER JOIN users u ON o.user_id=u.id WHERE u.name='u1000' LIMIT 50\G"

# 看真实耗时（关闭查询缓存类干扰，8.0 本来也没有查询缓存）
docker exec -i mysql8 mysql -uroot -proot123456 test -e "SET profiling=1; SELECT COUNT(*) FROM orders o INNER JOIN users u ON o.user_id=u.id; SHOW profiles;"
```

`SHOW PROFILE` 在 8.0.46 上**仍然可用**（实测三次都出数），但它带着废弃告警：

```text
mysql> SET profiling=1; SELECT COUNT(*) FROM users; SHOW PROFILE;
Warning 1287: '@@profiling' is deprecated and will be removed in a future release.
| starting                       | 0.000033 |
| Opening tables                 | 0.000046 |
| System lock                    | 0.000008 |
| executing                      | 0.000029 |
| query end                      | 0.000004 |
| waiting for handler commit     | 0.000031 |
| closing tables                 | 0.000009 |
| freeing items                  | 0.000032 |
| cleaning up                    | 0.000008 |
```

- `SHOW PROFILES` 给整条语句的总时长（实测 `SELECT COUNT(*) FROM users` = `0.00032550` 秒）；
  只留最近 **15** 条（`@@profiling_history_size` 实测 15），长跑批会被挤掉；
- 长期方案是 `EXPLAIN ANALYZE` 的 `actual time`，或
  `performance_schema.events_statements_summary_by_digest` —— 实测同一张表的
  `SELECT COUNT(*) FROM users` 在 digest 里记的是 `avg_ms = 0.4741`（用法见
  [观测与诊断.md](观测与诊断.md)）；
- ⚠️ `SET profiling` 是**会话级**的：像上面这样另起一次 `mysql -e` 去查
  `SHOW VARIABLES LIKE 'profiling'` 会看到 `OFF`，前一条命令的设置已经随连接销毁了。
  要把设置和被测语句写进**同一次** `mysql -e`。

实测（同一份夹具；墙钟含 `mysql` 客户端启动 + 建连接的固定开销，所以只断言趋势）：

| 写法 | 三轮墙钟 |
|---|---|
| A：带 `WHERE u.name='u1000' LIMIT 50` 的 JOIN | 12 / 12 / 13 ms |
| B：两次单表（先 `users` 取 id，再按 `user_id` 取 `orders`） | 14 / 13 / 12 ms |
| A：去掉 `WHERE` 的全量 JOIN | 首轮 **2584 ms**（冷缓存），之后 601 / 612 ms |

结论按数字收得更紧：**驱动表选对 + 被驱动表有索引时，小结果集的 JOIN 和两次单表打平**，
"拆单表更快"在这个量级上量不出来。真正拉开差距的是**结果集规模**（全量 JOIN 到几百毫秒～秒级），
而这份代价拆成两次单表**同样在**（把 100 万行搬回应用内存里拼只会更慢）。
所以第 1.3 节那条"避免中间结果集"的价值不在快，而在**可控**：单表查询能 `LIMIT`、能分页、能缓存、能并行。

还有一个反直觉的实测结果值得记住：**把 `idx_user` 抽掉，这条全量 JOIN 并没有变慢**
（443~475 ms，和带索引时的 468~660 ms 落在同一个波动区间）。原因是 `users.id` 是主键，
内层仍然有索引可走，优化器只是把另一侧换成 hash join。
**要量出"连接列缺索引"的代价，得让两侧都没有索引**（第 2.1 节那两份 5000 行的小表就是为此准备的）。

### 3. 观察「连接池 / 预编译」这两环

```bash
# 实例当前缓存的预编译语句总数（⚠️ 不是"每个连接一份"，见下方实测）
docker exec -i mysql8 mysql -uroot -proot123456 -e "SHOW GLOBAL STATUS LIKE 'Prepared_stmt_count';"

# 高频 SQL 有没有走预编译：看 Com_stmt_prepare / Com_stmt_execute（名字实测过，见下）
docker exec -i mysql8 mysql -uroot -proot123456 -e "SHOW GLOBAL STATUS LIKE 'Com_pre%';"

# 当前谁在占用连接：连接池是否配小了、有没有慢 SQL 占着不放
docker exec -i mysql8 mysql -uroot -proot123456 -e "SHOW FULL PROCESSLIST;"
```

实测这台 8.0.46 上的变量名（两条 `SHOW GLOBAL STATUS LIKE`）：

```text
# SHOW GLOBAL STATUS LIKE 'Com_pre%'  —— 实测只有这两行
Com_preload_keys             0
Com_prepare_sql              1     <- SQL 层 PREPARE 语句的计数，确实还在
# SHOW GLOBAL STATUS LIKE 'Com_stmt%' —— 协议层那三个在这里
Com_stmt_prepare           140
Com_stmt_execute           420
Com_stmt_close             420
# SHOW GLOBAL STATUS LIKE 'Prepared_stmt_count'
Prepared_stmt_count          0
```

两处口径要修正：

- ⚠️ **`Com_pre%` 匹配不到 `Com_stmt_*`** —— 上面那三行来自 `LIKE 'Com_stmt%'`。
  巡检脚本按 `Com_pre%` 抓"高频 SQL 有没有走预编译"会**一条都抓不到**，只剩一个恒为 0 的
  `Com_preload_keys`；驱动 + 连接池那条路（Go 的 `db.Prepare`、MySQL Connector/J 默认行为）
  计入的是 `Com_stmt_prepare` / `Com_stmt_execute` / `Com_stmt_close`。
- `Prepared_stmt_count` 是**整个实例**当前缓存的预编译语句条数，不是"每个连接上缓存了多少" ——
  每连接一份是**客户端**（Go 的 `*sql.Stmt`、HikariCP 的 `prepareThreshold`）自己的行为，
  服务端这个数只是所有连接叠起来的总量，用它反推连接池配置会推错。
  顺带：它是 status 变量，`SELECT @@prepared_stmt_count` 报
  `ERROR 1193 (HY000): Unknown system variable 'prepared_stmt_count'`，别按系统变量去查。

> 与 Redis 那份笔记的呼应：MySQL 8.0 移除查询缓存 ≠ 不需要缓存，
> 而是把缓存职责交回应用层——具体实现见 [缓存问题与方案.md](../../缓存/缓存问题与方案.md)。

## 延伸追问

- **为什么时间戳不会有"存错"的问题？** → 它记录的是**绝对时刻**，
  时区只影响"怎么显示"，不影响"存的是什么"；展示错了改时区就能修正。
- **`ON UPDATE CURRENT_TIMESTAMP` 有什么坑？** → 只要这一行有任何其他列被改动，
  这列就会被自动刷新，**数据变更轨迹会被覆盖**——业务字段不要随便挂它。
- **2038 问题怎么解？** → 换 `DATETIME`，或者用 `BIGINT` 存时间戳；
  MySQL 8.0 的 `TIMESTAMP` 仍是 4 字节，上限并未扩展。
- **`int(11)` 里的 11 是什么意思？** → **显示宽度**（配合 `ZEROFILL` 才有意义），不限制取值范围也不限制写入；`INT` 永远是 4 字节。
  8.0.17 起该写法报 **Warning 1681「Integer display width is deprecated」**，且实测 `SHOW CREATE TABLE` 里**宽度直接被丢掉**（写成 `int(11)` 建出来的表显示为 `int`）。
- **金额为什么不能用 `FLOAT` / `DOUBLE`？** → 二进制浮点无法精确表示 `0.1` 这类十进制小数，累加会漂移、比较不能用 `=`。正确做法是 `BIGINT` 存最小货币单位（分），或 `DECIMAL(M,D)`。
- **为什么不用 UUID 做主键？** → 随机分布导致 B+Tree 频繁页分裂、索引膨胀，写入性能与空间都变差。需要不可猜测 ID 时用「内部自增 + 外部 ID 映射」或雪花算法。
- **`VARCHAR(255)` 建索引为什么会失败？** → 要看**行格式**。上限是**字节**不是字符数：
  `utf8mb4` 下 `VARCHAR(255)` 最坏 1020 字节 —— 实测在 8.0 默认的 DYNAMIC 行格式下**能建**（上限 3072，`VARCHAR(768)` 刚好过、`VARCHAR(769)` 报 `ERROR 1071 max key length is 3072 bytes`）；
  而 `ROW_FORMAT=COMPACT` / `REDUNDANT` 下上限只有 **767 字节**，同一列就报 `ERROR 1071 ... 767 bytes`。
  所以这句话只对**旧行格式或从 5.6 升上来的表**成立，别当成 8.0 的通识。解法：DYNAMIC 行格式、前缀索引或缩短列长。
- **`utf8` 和 `utf8mb4` 有什么区别？** → `utf8` 只是 `utf8mb3` 的别名，最多 3 字节，存不了 emoji 和部分生僻字。
  实测口径：写 `CHARACTER SET utf8` 建表会得到 **Warning 3719**（"现在是 utf8mb3，将来会变成 utf8mb4"），`SHOW CREATE TABLE` 落下来是 `CHARSET=utf8mb3`；
  塞 emoji 报 `ERROR 1366 Incorrect string value: '\xF0\x9F\x98\x80'`。**8.0 并没有禁止 `utf8`**，所以隐患是"语义会随版本漂移"，不是"已经废弃"。
- **为什么要求 join 列类型一致？** → 类型不一致时要做隐式转换，转换后的列用不上索引；
  而**排序规则不一致更硬**：实测两个 `utf8mb4` 列（一个 `0900_ai_ci`、一个 `general_ci`）直接 join，不是退化，而是
  `ERROR 1267 Illegal mix of collations (... ,IMPLICIT) and (... ,IMPLICIT) for operation '='`。
  用 `COLLATE` 强转能跑，但实测执行计划从 `type: ref` 退化成 `type: index`（整棵索引扫）—— 见 3.5 的实测块。
- **非严格模式下塞不进字符集会怎样？** → **不是截断成空串**，实测 `sql_mode=''` 时是 **Warning 1366 + 把放不下的字符替换成一个 `?`（0x3F）**：
  `'😀'` 变成 `?`、`'a😀b'` 变成 `a?b`。数据"存进去了但内容是坏的"，比直接报错更难发现。
- **字符集和排序规则谁决定"相等"？** → 排序规则。实测 `utf8mb4_0900_ai_ci` 下 `'é' = 'e'` 为 1、`utf8mb4_bin` 下为 0；
  同一个索引列上 `WHERE s = 'abc'` 能同时命中 `ABC` 与 `abc`。唯一约束、索引顺序、等值判断全按它算。
- **`INSTANT` 加列是零代价吗？** → 它只改数据字典元数据、不动行，但仍然要拿元数据锁（MDL）；表上有长事务未提交时，ALTER 会卡在 MDL 队列里，把后面的查询一并堵住（排查见 [观测与诊断.md](观测与诊断.md) 第 5.3 节）。
- **`TEXT` 有什么限制？** → 不能有默认值、不能整列建索引（只能前缀索引）、DYNAMIC 行格式下会行溢出（多一次 IO）、更容易落磁盘临时表。大字段应拆表或放对象存储。

- **MySQL 的 JOIN 到底有几种算法？** → 本质都是嵌套循环：无索引的 simple nested loop、内层走索引的 index nested loop、内层没索引时的攒批（8.0.18 之前是 BNL，之后是 hash join，8.0.20 起 BNL 完全不再使用）。所以「小表驱动大表」只在**大表侧没有可用索引**时才真正影响代价。
- **`EXPLAIN` 和 `EXPLAIN ANALYZE` 有什么区别？** → 后者会**真的执行**语句，按迭代器给出 `actual time` / `rows` / `loops`，用来核对估算与实际差距；8.0.18 起可用，只有 TREE 格式。
- **`join_buffer_size` 还值得调吗？** → 它是 join buffer 的大小（BNL 时代攒外层行，8.0 里同一块缓冲给 hash join 用）。实测 8.0.46 默认 262144，从 256 KB 调到 8 MB 在 5000×5000 的无索引联接上量不出差异；而且这内存**按连接分配**，调大等于给每个连接多要一块。真正决定代价的是 `block_nested_loop` 这个开关（关掉就退回不挂缓冲的 nested loop，实测慢约 1400 倍）和联接列有没有索引。
- **`INNER JOIN` / `LEFT JOIN` / `RIGHT JOIN` 的区别？** →
  内连接取交集；左连接以左表为准（右表无匹配补 NULL）；右连接反之。
- **`ON` 和 `WHERE` 的区别？** → **`ON` 是连接条件**（在生成连接结果时生效，
  外连接中放在 `ON` 里不会过滤掉左表的行）；**`WHERE` 是结果过滤**（在连接之后过滤，
  外连接中写在这里会把补 NULL 的行也过滤掉，**等价于退化成内连接**）。
- **JOIN 的驱动表怎么选？** → 一般**小表驱动大表**；
  优化器会自行判断，必要时可用 `STRAIGHT_JOIN` 强制顺序。
