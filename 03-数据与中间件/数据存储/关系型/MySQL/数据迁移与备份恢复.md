## 一、MySQL 把一张大表从生产库搬到另一台实例，有哪几种做法？（物理拷贝实操）

**本节要点**：核心是**你有没有真的做过数据迁移**。要讲的不是"用 mysqldump 导一下"，
而是你能不能讲清**每种手段的锁表风险、版本约束和适用场景**——
在生产库上的任何操作，第一句话都应该是"先评估对业务的影响"。

### 1.1 三类手段先做对比

| 手段 | 典型做法 | 适合场景 | 代价 / 风险 |
|---|---|---|---|
| **逻辑导出导入** | `mysqldump` 导出 SQL 再导入；或 `SELECT ... INTO OUTFILE` + `LOAD DATA` | 跨版本、跨厂商、只搬部分表或部分行、需要顺手改结构 | **慢**（要重写数据、重建索引）；默认逐表 `LOCK TABLES … WRITE`（实测 `lock-tables` 默认值就是 `TRUE`） |
| **物理拷贝**（可传输表空间） | 拷 `.ibd` 数据文件 + `.cfg` 元数据，目标库 `IMPORT TABLESPACE` | **同版本、同页大小**的实例之间搬大表，求快 | 源库要 `FLUSH TABLES ... FOR EXPORT`，**导出锁期间写入会被挂住**（实测 MDL 是 `SHARED_NO_WRITE`，见 1.3 节） |
| **主从复制** | 搭主从，让从库把 binlog 重放一遍，追平后切流量 | **不停服**在线迁移、可回滚、可跨机房 | 搭建成本高，有**复制延迟**，还要配套切换方案（见第二节） |

> 口诀：**要改结构 / 跨版本 → 逻辑导出；同版本搬大表求快 → 物理拷贝；不能停服 → 主从复制。**

### 1.2 逻辑导出：关键是 `--single-transaction`

```bash
# 导出：用一致性快照读，导出期间不锁业务表
mysqldump -uroot -p --single-transaction --default-character-set=utf8mb4 --databases mydb > mydb.sql
mysql -uroot -p mydb < mydb.sql          # 导入
```

- **`--single-transaction`**：导出前开一个可重复读事务拿到一致性快照，
  **导出全程不锁业务表**，是"不停服导出"的最低要求。
- ⚠️ 它**只对事务引擎生效**，而且**不能和 `--lock-all-tables`（`-x`）同时用** ——
  实测是直接报错，不是"退化成锁表"，原文照抄：

```text
mysqldump: You can't use --single-transaction and --lock-all-tables at the same time.
```

- ⚠️ 逐表锁 `--lock-tables` 才是 mysqldump 的**默认值**（实测 `lock-tables TRUE`），
  它可以和 `--single-transaction` 共存、实测不报错，别把这两个选项混为一谈。
- ⚠️ 库里混着 MyISAM 表时，`--single-transaction` **一句警告都不给**（stderr 为空），
  那张非事务表照样在导出时被逐表 `LOCK TABLES … WRITE` 锁走 ——
  "整库同一个时刻"这时候是假的，动手前自己先把引擎查一遍。
- 追求导入速度时，可在导入前临时关掉 `unique_checks` / `foreign_key_checks`，导入完再打开。

### 1.3 物理拷贝（可传输表空间）的完整步骤

就是把生产库的一张表搬到测试库，走的正是**物理拷贝**这条路：

| 步骤 | 在哪操作 | 做什么 |
|---|---|---|
| **① 拿到表定义** | 源实例 | `SHOW CREATE TABLE user;` 复制 DDL，在**目标库先建出同结构的空表**；默认值 / 默认格式按目标环境调整后再执行 |
| **② 丢弃表空间** | 目标库 | `ALTER TABLE user DISCARD TABLESPACE;` → 目标数据目录下的 `.ibd` 被删除 |
| **③ 确认属主** | 目标机 | 看 MySQL 数据目录里文件的属主（示例 uid=gid=**999**），待会儿拷进来的文件必须是这个属主 |
| **④ 刷盘 + 锁表导出** | 源实例 | `FLUSH TABLES user FOR EXPORT;` → **刷盘并进入只读状态**，同时生成 `user.cfg`（表空间元数据） |
| **⑤ 拷两个文件** | 源机 → 目标机 | 把 `user.ibd` 和 `user.cfg` 拷到目标实例的数据目录 |
| **⑥ 立刻解锁** | 源实例 | `UNLOCK TABLES;` —— **马上解锁，别让生产表长时间只读** |
| **⑦ 改属主** | 目标机 | `chown 999:999 user.ibd user.cfg`（改成 MySQL 运行用户），否则导入失败 |
| **⑧ 导入表空间** | 目标库 | `ALTER TABLE user IMPORT TABLESPACE;` |
| **⑨ 验证** | 目标库 | `SELECT COUNT(*) FROM user;` 核对行数（此例是 160 万行） |

上面的步骤表是当时做迁移记下来的手记。本机在同一台 8.0.46 实例上把
`FOR EXPORT → DISCARD → IMPORT` 整条往返真跑了一遍，顺序能对上，但**有三处要修正**：

```text
# ① 300 行的表，执行 FLUSH TABLES docverify.t_ts3 FOR EXPORT;（导出会话保持 14 秒）
-rw-r----- 1 mysql mysql    710  /var/lib/mysql/docverify/t_ts3.cfg    <- 只在导出锁期间存在
-rw-r----- 1 mysql mysql 114688  /var/lib/mysql/docverify/t_ts3.ibd
# 同期 performance_schema.metadata_locks 里这一行：
#   t_ts3 | SHARED_NO_WRITE | TRANSACTION | GRANTED
# 同期另一个会话的 INSERT（innodb_lock_wait_timeout=8）：挂了 11013 ms，
#   直到导出会话结束才写进去；同一条 INSERT 在无锁基线下只要 30 ms
# 同期 SELECT COUNT(*)：24 ms 正常返回 —— 读完全不受影响

# ② DISCARD TABLESPACE 之后：.ibd 直接消失，查询报错
$ ls /var/lib/mysql/docverify/t_ts2.*      ->  No such file or directory
ERROR 1814 (HY000): Tablespace has been discarded for table 't_ts2'

# ③ 把 .ibd 拷回去、但属主是 root:root
ERROR 1812 (HY000): Tablespace is missing for table `docverify`.`t_ts2`.
# 改回 chown mysql:mysql + chmod 660 之后 IMPORT 成功，数据一条不差
| rows_imported | checksum_id |   ->   300 | 45150 |
```

- **步骤 ④ 的"只读"要说准**：拦住的不是"表被设成只读"，而是**写入拿不到 MDL**
  （实测锁类型 `SHARED_NO_WRITE`）。读不受影响，写会一直挂着 —— 这一次挂了 11 秒，
  生产上导出锁持有多久，写入就堵多久。
- **步骤 ⑤ 的 `.cfg` 在同版本同实例的往返里不是必需的**：本机只拷 `.ibd` 回去也能
  `IMPORT TABLESPACE` 成功（8.0 的 `.ibd` 里已经带着 SDI 和表空间元数据）。
  ⚠️ 但**跨实例导入仍按"两个文件都拷"执行**，这条本机没法验（只有一台实例），
  不要拿同实例实测去省生产步骤。
- **步骤 ③ 的 `uid=gid=999` 对得上**：官方 `mysql:8.0` 镜像里 `id mysql` 就是
  `uid=999(mysql) gid=999(mysql)`；属主错了就是上面那个 `ERROR 1812`。

### 1.4 必须提前评估的风险（真正要提前评估的）

1. **`FLUSH TABLES ... FOR EXPORT` 期间写入会被挂住**——这里要反复强调：
   实测拦路的是 MDL 的 `SHARED_NO_WRITE`（读不受影响、写一直等，见第 1.3 节的 11 秒），
   **若业务此刻写入很活跃就不是明智选择**，会直接影响线上业务。
   迁移前必须确认业务低峰期，或者干脆改用主从复制方案。
2. **版本与页大小尽量一致**：源库和目标库的 MySQL 版本、`innodb_page_size`、字符集
   最好完全相同，否则 `.ibd` 可能导入失败。
3. **`innodb_file_per_table` 必须为 ON**，否则表没有独立的 `.ibd`，无从拷贝。
4. **文件属主 / 权限不对，`IMPORT TABLESPACE` 一定报错**（步骤 ⑦ 就是防这个）。

### 延伸追问

- **`mysqldump` 怎么做到不锁表？** → `--single-transaction`，用一致性快照读；
  但只对事务引擎生效，长事务期间要留意 undo 膨胀；实测它和 `--lock-all-tables` **互斥**
  （同时用直接报错），和默认的逐表锁 `--lock-tables` 却能共存。
- **物理拷贝和逻辑导出怎么选？** → 同版本、搬大表、求快 → 物理拷贝；
  跨版本 / 要改结构 / 只搬部分数据 → 逻辑导出。
- **还有没有不停服的方式？** → 有，**主从复制**：先在从库重放 binlog 追平，
  再切流量；GTID 模式下的切换流程见第二节。

## 二、MySQL 主从复制怎样不停服地从 binlog + position 切到 GTID 模式？

**本节要点**：核心是**在线改配置的能力**。默认的 `binlog + position` 复制里，
从库要把"主库的 binlog 文件名 + 位点"记下来，主库一换、位点一漂就出问题；
GTID 改用全局唯一的事务 ID 做自动定位。关键是**为什么切、以及怎么一步步安全地切**。

### 2.1 GTID 是什么，比 binlog + position 强在哪

**GTID（Global Transaction ID，全局事务标识）**：主库上每个提交的事务都会分配一个
全局唯一的编号，从库只需要记录"我执行过哪些 GTID"，这个集合就是 `Executed_Gtid_Set`。

| | **binlog + position** | **GTID** |
|---|---|---|
| 从库怎么找位点 | 显式指定 `MASTER_LOG_FILE` + `MASTER_LOG_POS` | **自动定位**：只找"自己没执行过的那个事务" |
| 主库故障 / 主从切换 | 要**重新算位点**，容易算错、算漏 | 换个主库直接继续，**不用算位点** |
| 配置复杂度 | 多、易错 | 少（这正是"简化配置"） |
| 出问题怎么查 | 只能比对 binlog 文件和位点 | 比对两边 `Executed_Gtid_Set`，**缺哪个事务一眼可见** |

一句话：**GTID 用"事务身份"取代了"事务位置"，让复制更稳定、更不容易出问题。**

### 2.2 `gtid_mode` 的四个取值（切换过程就是在这四个值之间走）

| 值 | 含义 |
|---|---|
| **`OFF`** | 完全关闭，禁用 GTID |
| **`OFF_PERMISSIVE`** | **宽松关闭**（过渡态）：自身不强制生成 GTID，但**收到 GTID 事务能兼容处理** |
| **`ON_PERMISSIVE`** | **宽松开启**（过渡态）：自身已经用 GTID，但**收到匿名事务（没有 GTID 的老事务）也能处理** |
| **`ON`** | 完全开启：**所有事务都必须带 GTID** |

> 两个 PERMISSIVE 过渡态的存在，就是为了**让线上不用停服**：
> 先能"收"，再能"发"，最后才强制。宽松态是给"历史遗留的匿名事务"留出的收尾窗口。

本机实测补充三条"资料里不会写"的细节：

```text
mysql> SET GLOBAL gtid_mode = ON;        -- 从 OFF 一步跳到底
ERROR 1788 (HY000): The value of @@GLOBAL.GTID_MODE can only be changed one step at a time:
OFF <-> OFF_PERMISSIVE <-> ON_PERMISSIVE <-> ON. Also note that this value must be stepped
up or down simultaneously on all servers. See the Manual for instructions.

mysql> SHOW STATUS LIKE 'Ongoing_anonymous_transaction_count';   -- 第 5 步要等的那个计数器
Ongoing_anonymous_transaction_count    0
```

- **四个取值只能一步步走**：`ERROR 1788` 是硬约束，脚本里"直接设成 ON"必然失败。
- **每改一次 `gtid_mode`，服务器自动切一个新 binlog 文件**：实测
  `binlog.000048 → 000049 → 000050 → 000052`，新文件起始位点都是 197，
  `SHOW BINARY LOGS` 里就是成片的 241 字节小文件（基本只装了一个 Rotate 事件）。
  所以"切换时先把位点记下来"这件事本身就不牢 —— 文件名一直在漂，
  这也是最后必须落到 `SOURCE_AUTO_POSITION = 1` 的原因之一。
- **每次切换都会在错误日志留一行**，可以直接当切换审计用：

```text
2026-10-04T04:00:38.315652Z 415 [System] [MY-010035] [Server] Changed GTID_MODE from OFF to OFF_PERMISSIVE.
2026-10-04T04:00:38.328032Z 415 [System] [MY-010035] [Server] Changed GTID_MODE from OFF_PERMISSIVE to ON_PERMISSIVE.
2026-10-04T04:00:38.339727Z 415 [System] [MY-010035] [Server] Changed GTID_MODE from ON_PERMISSIVE to ON.
```

### 2.3 生产环境不停服切换的九步

```sql
-- 第 1 步：只告警不阻断。线上可能暂时存在无法生成 GTID 的写法，先让它报警、不报错
SET @@GLOBAL.enforce_gtid_consistency = WARN;
-- 之后持续监控警告，把不兼容的操作逐个改掉，直到警告清零
-- （提醒：这个过程可能持续几天甚至半个月）

-- 第 2 步：告警 → 直接报错。此后不兼容的语句会执行失败
SET @@GLOBAL.enforce_gtid_consistency = ON;

SET @@GLOBAL.gtid_mode = OFF_PERMISSIVE;   -- 第 3 步：宽松关闭
SET @@GLOBAL.gtid_mode = ON_PERMISSIVE;    -- 第 4 步：宽松开启

-- 第 5 步：等所有匿名事务执行完，这个数字到 0 才算干净
SHOW STATUS LIKE 'Ongoing_anonymous_transaction_count';

-- 第 6 步：检查每一个副本的同步进度（多层复制要逐层查，直到全部追平）
SHOW REPLICA STATUS\G          -- MySQL 8.0；5.7 用 SHOW SLAVE STATUS\G

-- 第 7 步：若 binlog 还兼做备份 / 恢复用途，等所有含匿名事务的备份过期
--         （否则那些备份在完全开启 GTID 之后无法还原）

SET @@GLOBAL.gtid_mode = ON;   -- 第 8 步：完全开启
```

**第 9 步：把复制方式改成自动定位，并把配置写进配置文件。**

```sql
STOP REPLICA;
CHANGE REPLICATION SOURCE TO SOURCE_AUTO_POSITION = 1;   -- MySQL 8.0
-- MySQL 5.7 语法：CHANGE MASTER TO MASTER_AUTO_POSITION = 1;
START REPLICA;
```

```ini
# /etc/my.cnf —— 前面的 SET GLOBAL 都是运行时变量，重启就失效，必须落盘
[mysqld]
gtid_mode                = ON
enforce_gtid_consistency = ON
log_bin                  = /var/lib/mysql/mysql-bin   # GTID 依赖 binlog
log_replica_updates      = ON                         # 5.7 写法：log_slave_updates = ON
```

> ⚠️ 特别强调：**前面的设置都是运行时设置，服务器一重启就没了**。
> 所以最后一定要把 `gtid_mode` / `enforce_gtid_consistency` 写进配置文件，
> 并把复制连接改成 `SOURCE_AUTO_POSITION = 1`（5.7 为 `MASTER_AUTO_POSITION = 1`），
> 否则重启后复制会失败。

"重启就失效"这条在本机做过实测 —— 把 `gtid_mode` 推到 `ON` 之后重启实例：

```text
| mode_after_restart | enforce_after_restart | gtid_executed_persisted             |
| OFF                | OFF                   | b5b66ea4-...:1-21                 |
```

开关回落到配置文件里的默认值，**GTID 集合却没丢**（它持久化在 `mysql.gtid_executed` 表里）。
所以第 9 步落盘的不是位点、是开关：漏写配置的后果是重启后退回位点复制，
而从库已经带着 GTID 集合，两边对不上。

配置文件里 `log_bin = /var/lib/mysql/mysql-bin` 也是 5.7 时代的写法 ——
**8.0 的默认前缀是 `binlog`**（本机数据目录实测：`binlog.000001` 连续编号到 `binlog.000068`，
68 个文件再加一份 `binlog.index`；
`SHOW MASTER STATUS` 给出的同样是它；`ib_logfile*` 已经不存在，细节见
[架构与执行链路.md](架构与执行链路.md) 第 6.1 节）。

> ⚠️ **第 1、2 步在"纯 InnoDB 的 8.0 实例"上基本采集不到东西**（本机 8.0.46 实测）。
> 资料里背的那串"GTID 不兼容写法"，多数在 8.0 已经不再违规：
> `CREATE TABLE ... SELECT` 写入 InnoDB 自 8.0.21 起是原子语句，
> `enforce_gtid_consistency=ON` + `gtid_mode=ON` 下实测**照样成功**；
> `CREATE TEMPORARY TABLE`（含事务内建、事务内 DROP）在 `binlog_format=ROW` 下**也全部成功**；
> `enforce_gtid_consistency=WARN` 下 `SHOW WARNINGS` 是空的、错误日志里也没有对应告警 ——
> 因为没有违规可告。真正还会被拦的是**非事务引擎**，实测原文：

```text
mysql> CREATE TABLE m_ctas ENGINE=MyISAM AS SELECT 1 AS a;
ERROR 1786 (HY000): Statement violates GTID consistency: CREATE TABLE ... SELECT.
```

结论没变，判据要换：**第 1 步"边跑边找不兼容写法"盯的是库里有没有 MyISAM / MEMORY 表**，
而不是那串语句清单。顺带两条实测细节：`enforce_gtid_consistency` 是 **GLOBAL 专用变量**
（`SELECT @@SESSION.enforce_gtid_consistency` 报 `ERROR 1238`）；
`gtid_mode=ON` 必须在 `enforce_gtid_consistency=ON` 之后，顺序反了报
`ERROR 3111: SET @@GLOBAL.GTID_MODE = ON is not allowed because ENFORCE_GTID_CONSISTENCY is not ON.`
—— 第 1、2 步排在最前面就是在给这条顺序让路。

### 2.4 整条流程怎么记

```text
主从搭建（binlog + position）→ 追平延迟
   → ①告警 ②强制 ③宽松关闭 ④宽松开启
   → ⑤等匿名事务清零 ⑥查所有副本追平 ⑦等老备份过期 ⑧完全开启
   → ⑨配置文件落盘 + 自动定位 → 之后再做流量切换
```

### 延伸追问

- **为什么要有两个 PERMISSIVE 中间态？** → 为了**不停服**：先让历史数据能收尾，
  再让新事务都带上 GTID，避免切换瞬间主从复制断开。
- **`enforce_gtid_consistency = WARN` 和 `ON` 的区别？** → WARN 只告警不阻断，
  用来在线上"边跑边找不兼容写法"；ON 直接报错，是切换前的最后一道关卡。
- **怎么判断从库有没有追平？** → 看 `SHOW REPLICA STATUS` 里的 `Seconds_Behind_Source`，
  以及两边 `Retrieved_Gtid_Set` / `Executed_Gtid_Set` 的差集。
- **GTID 模式下还能用 `MASTER_LOG_FILE` 吗？** → 不能。位点复制和 GTID 复制**互斥**，
  `SOURCE_AUTO_POSITION = 1` 时再指定位点会直接报错，实测原文：
  `ERROR 1776 (HY000): Parameters SOURCE_LOG_FILE, SOURCE_LOG_POS, RELAY_LOG_FILE and RELAY_LOG_POS cannot be set when SOURCE_AUTO_POSITION is active.`

## 三、备份与恢复：凭什么说这份备份能救回来？

**来源**：《高性能 MySQL》（第 4 版）第 10 章「备份与恢复」的读后整理，按主题归纳而非逐字摘录。

**本节要点**：前两节解决"怎么搬"，这一节解决"出事怎么办"。
备份的价值不在文件本身，而在**它能被恢复**这件事被验证过。

### 3.1 先把四个维度分清

| 维度 | 取值 | 判据 |
| --- | --- | --- |
| 备份的是什么 | **逻辑**（SQL 语句 / 数据文件内容）vs **物理**（直接拷 InnoDB 文件） | 逻辑可跨版本、可挑表，但恢复要重放 SQL、慢；物理恢复快，强依赖版本与配置一致（第一节就是物理路径） |
| 实例在不在跑 | **冷备**（停实例拷文件）vs **热备**（在线备份） | 冷备最干净但几乎没有生产能接受；热备对 InnoDB 就是"一个一致性事务快照" |
| 备份的粒度 | 全量 / 增量 / 部分（单库单表） | 单表恢复需求极常见 —— 只有逻辑备份和表空间级物理拷贝能做到 |
| 能不能回到任意时刻 | 全量 + **binlog** 才能做 PITR | 只有全量文件时，能回到的时刻就是那次备份的时刻 |

### 3.2 一次可恢复的逻辑备份，选项是怎么配的

```bash
# 8.0.26 起：--source-data 取代（废弃的）--master-data，效果相同
mysqldump --single-transaction --source-data=2 \
          --routines --triggers --events \
          --databases mydb > mydb_$(date +%F).sql

# 8.0 还引入了并行的逻辑导出工具 mysqlpump（--default-parallelism 默认 2）
# ⚠️ mysqlpump 自 8.0.34 起已废弃，8.0.46 实测告警指向 mysqldump；更新的并行路径是 MySQL Shell 的 util.dumpInstance()
```

同一台实例上把选项默认值和废弃告警都跑了出来：

```text
# mysqldump --help --verbose 的默认值（节选）
lock-tables                               TRUE      <- 默认就锁，逐表
lock-all-tables                           FALSE
single-transaction                        FALSE
triggers                                  TRUE
routines                                  FALSE     <- 想导存储例程必须显式加
events                                    FALSE
max-allowed-packet                        25165824

# 8.0.26 起 --master-data 已废弃，实测原文：
WARNING: --master-data is deprecated and will be removed in a future version. Use --source-data instead.
# mysqlpump 也在废弃，但它的话锋指向 mysqldump：
WARNING: mysqlpump is deprecated and will be removed in a future version. Use mysqldump instead.
# mysqlpump --help --verbose 里 default-parallelism 确实是 2
```

所以 8.0.46 上的取舍很清楚：**为了并行去换 `mysqlpump` 已经不值得投入**。
MySQL Shell 的 `util.dumpInstance()` 是另一条更新的路，本机没实测（只装了 `mysqlsh`，
没跑过它的 dump 实例），照抄进工单前先自己验一遍。

三条必须写进备份脚本注释里的约定：

- **`--single-transaction` 靠的是 MVCC**：导出前发一个 `BEGIN`，读到一个一致性快照，
  全程不阻塞写。它**只对事务引擎有效** —— 库里混着 MyISAM 时这份"一致性"是假的，
  而且实测**一句警告都不给**（stderr 为空），那张非事务表照样被逐表锁走；
- **`--source-data` 会改变锁行为**：它默认会打开 `--lock-all-tables`，
  只有**同时**指定 `--single-transaction` 才变成"只在开头拿一下全局读锁"。
  实测这一对**可以共用**（第 3.3 节 PITR 的那个位点就是这么记下来的）；
  但别再手动补 `-x` / `--lock-all-tables` —— 它和 `--single-transaction` 互斥，同时给直接报错；
- **导出期间不要跑 DDL**：`--single-transaction` 的长事务会跟 DDL 在元数据锁上互相等，
  8.0.32 之前还可能导出不一致（这也是升级说明里反复强调的原因，见 [架构与执行链路.md](架构与执行链路.md) 第 6.2 节）。

`--source-data=2` 把位点写成**注释**，`--source-data=1` 直接写成可执行语句 ——
前者适合"这份文件将被人工用来搭从库"，后者适合脚本化恢复。

实测三种形态（三次都在同一时刻，位点都是 `binlog.000010` 的 9451）：

```text
# 只加 --single-transaction：文件里没有任何位点信息（grep CHANGE MASTER 为空）
# --single-transaction --source-data=2（dump 的第 19、22 行）：
-- Position to start replication or point-in-time recovery from
-- CHANGE MASTER TO MASTER_LOG_FILE='binlog.000010', MASTER_LOG_POS=9451;
# 只加 --source-data=1：同一行没有注释前缀，导入时会真的执行
CHANGE MASTER TO MASTER_LOG_FILE='binlog.000010', MASTER_LOG_POS=9451;
```

也就是说：**位点只有显式要求才会被记录**，记的就是当时的 `SHOW MASTER STATUS`，
而 `--single-transaction` 本身**不往文件里写任何东西**（加不加它，两次 dump 的 md5 完全相同 ——
文件里那句 `LOCK TABLES ... WRITE` 是给**导入**加速用的，跟导出锁无关）。

配套三条实测：`--set-gtid-purged` 在 `gtid_mode=OFF` 的实例上写 `ON` 直接
`Error: Server has GTIDs disabled.`；开着 GTID 时默认 `AUTO` 会往文件里写
`SET @@GLOBAL.GTID_PURGED=/*!80000 '+'*/ 'b5b66ea4-...:1-2';`，加 `--set-gtid-purged=OFF`
后这行变成 0 处；只搬部分行也验过 —— `--where="id<=2"` 让一张 4 行的表只导出 2 行。

### 3.3 PITR：恢复到"误删前十分钟"

```text
① 定位最近一次全量备份，读出它记录的位点（或 GTID 集合）
② 把全量还原到一台**新实例**（永远不要在生产实例上原地覆盖）
③ 用 mysqlbinlog 重放该位点之后的 binlog，重放到出事**之前**为止
      --start-datetime / --stop-datetime / --stop-position
      GTID 模式下还可以用 --exclude-gtids 把误操作那一笔事务直接跳过
④ 校验关键表 → 只把需要的表回灌，或整体切换流量
```

前提条件很硬：**binlog 必须开着且留得够久**（保留策略见 [复制与高可用.md](复制与高可用.md) 第 2.3 节）。
只有全量 dump 文件时，能回到的时刻就是备份那一刻，中间写的全部丢失。

本机把这条链路完整跑了一遍（5 行的表：备份 → 正常写 2 行 → 误删 3 行 → 还原 + 重放）：

```text
# ① 全量备份头部记录的位点
-- CHANGE MASTER TO MASTER_LOG_FILE='binlog.000058', MASTER_LOG_POS=2028;
# ② 事故前的正常写入（id=6、7）之后，SHOW MASTER STATUS 的位点
binlog.000058  2328
# ③ 误删 DELETE FROM t_pitr WHERE id>=4 之后的位点（源库此时只剩 3 行）
binlog.000058  2642

# ④ 把 2028~2642 这段翻译成人话（--base64-output=decode-rows -v）
### INSERT INTO `docpitr`.`t_pitr`
###   @1=6
###   @2='f'
### DELETE FROM `docpitr`.`t_pitr`
### WHERE
###   @1=4
###   @2='d'

# ⑤ 还原全量（得到 5 行）后，只重放到误删之前
mysqlbinlog --start-position=2028 --stop-position=2328 binlog.000058 | mysql docpitr
-> COUNT(*) = 7      <- 6、7 回来了，误删没进来
# ⑥ 对照组：重放越过误删位点
mysqlbinlog --start-position=2028 --stop-position=2642 binlog.000058 | mysql docpitr
-> COUNT(*) = 3      <- 事故被忠实地重演了一遍
```

`--start-datetime / --stop-datetime` 同样可用；`--exclude-gtids` 只在 binlog 里真有 GTID 事件时
才有意义（`gtid_mode=OFF` 的实例上那些事务是匿名的，过滤不到东西）。
三个只有跑过才会知道的坑：

- **`mysqlbinlog` 不在跑 `mysqld` 的那个镜像里**：本机 `mysql:8.0`（Oracle Linux 9 基础镜像）
  只有 `mysql` / `mysqldump` / `mysqlpump` / `mysqlsh` / `mysqladmin`，
  `command -v mysqlbinlog` 是空的；要么换带完整客户端的镜像（本次用 `mysql:8.0-debian`），
  要么把 binlog 文件拷出去解码。
- **别把自定义语句拼在重放文件前面**：`(echo "SET sql_log_bin=0"; cat incr.sql) | mysql`
  会破坏 mysqlbinlog 自己的语句边界，第一句就报
  `ERROR 1064 ... near 'SET @@SESSION.PSEUDO_SLAVE_MODE=1*/'`，**而后面的事件照常重放**，
  这个错误极容易被漏看；要关重放端的 binlog 请用 `mysql --init-command="SET SESSION sql_log_bin=0"`。
- **重放会在目标实例留下 binlog**：两趟重放（带与不带上面那句拼接）位点增量相同，各 **+307 字节**。
  这是"PITR 必须在新实例上做"的第二条理由 —— 不只怕盖数据，连日志一起写脏。

### 3.4 演练：把"有备份"变成"能恢复"

- **RPO**（能接受丢多长时间的数据）由"备份间隔 + binlog 是否异地留存"决定；
- **RTO**（多久能恢复）由"备份体积 ÷ 恢复吞吐"决定，逻辑备份的恢复速度通常是导入速度的瓶颈；
- 演练的最低标准：**把某天的备份真的恢复到一台实例并跑通业务查询**，
  而不是检查文件是否存在、大小是否合理；
- 误删的另一条捷径不是备份，而是**延迟从库**（见 [复制与高可用.md](复制与高可用.md) 第 8.4 节）：
  它把"发现事故 → 从库停止重放"的时间窗口从"备份间隔"拉长到人为设定的延迟。

### 延伸追问

- **为什么 `--single-transaction` 不能配 MyISAM 表？** → 它的一致性来自 InnoDB 的一致性快照，非事务引擎没有这个概念，导出的表之间不是同一时刻的状态。
- **只有全量备份能做到"恢复到任意时刻"吗？** → 不能，必须配合 binlog 重放（PITR）。所以 binlog 的保留时长和归档是备份策略的一部分。
- **`mysqlpump` 和 `mysqldump` 选哪个？** → 8.0 早期用 `mysqlpump` 换并行度；它在 8.0.34 已废弃，新项目应选 `mysqldump` 或 MySQL Shell 的并行 dump/load，别把工具写成长期依赖。

## 使用一：Go（迁移期：双写 + 分片校验）⭐

### 1. 迁移期：双写 + 分片校验

正文第一节的「物理拷贝 / 逻辑导出」都是**停服或高成本**路径；不停服迁移的标准结构是
**全量搬迁 → 增量追平（binlog）→ 双写 → 校验 → 切读 → 停写老库**，
其中最容易漏的是**校验**——没有校验就没法证明"可以切"。

```go
package sharddemo

import (
	"context"
	"database/sql"
	"errors"
	"fmt"
	"regexp"
	"strings"
)

// ChunkStat 一个主键区间的指纹。
// 用 COUNT + SUM(CRC32(...)) 而不是逐行比对：一次往返覆盖一批数据。
// ⚠️ SUM 的返回类型是 DECIMAL，驱动给回来的是 []byte——这里按字符串收，
// 既避开 bigint 溢出，也就不用自己处理小数位。要数值再 strconv.ParseInt。
type ChunkStat struct {
	Rows int64
	CRC  string
}

// Stat 扫描某张表的一个主键区间。cols 必须与源表、目标表**完全一致且同序**。
func Stat(ctx context.Context, db *sql.DB, table string, cols []string, lo, hi int64) (ChunkStat, error) {
	if err := validateIdent(table, cols); err != nil {
		return ChunkStat{}, err
	}

	// CONCAT_WS 里每一列都参与指纹；NULL 要显式变成可区分的标记，
	// 否则 CONCAT_WS 会直接跳过 NULL 列，"值为 NULL" 和 "值为空串" 就分不清了
	args := make([]string, len(cols))
	for i, c := range cols {
		args[i] = "IFNULL(`" + c + "`,'')"
	}
	q := `SELECT COUNT(*), COALESCE(SUM(CRC32(CONCAT_WS(0x01, ` + strings.Join(args, ",") + `))), 0)
          FROM ` + table + ` WHERE id >= ? AND id < ?`

	var s ChunkStat
	err := db.QueryRowContext(ctx, q, lo, hi).Scan(&s.Rows, &s.CRC)
	return s, err
}
```

下面用「区间指纹」把源表与目标表逐块比一遍，把不一致的区间挑出来。

```go
// Verify 对比源表与目标表，返回所有**不一致区间的左界**。
// 二分定位单行、或直接对这些区间做 pt-table-sync，都由调用方决定。
func Verify(ctx context.Context, db *sql.DB, src, dst string, cols []string, maxID int64, chunk int64) ([]int64, error) {
	if chunk <= 0 || maxID < 0 {
		return nil, fmt.Errorf("sharddemo: bad verify args maxID=%d chunk=%d", maxID, chunk)
	}

	var bad []int64
	for lo := int64(0); lo <= maxID; lo += chunk {
		if err := ctx.Err(); err != nil { // 校验通常是长跑批任务，必须可中断
			return bad, err
		}
		hi := min(lo+chunk, maxID+1)

		a, err := Stat(ctx, db, src, cols, lo, hi)
		if err != nil {
			return nil, fmt.Errorf("stat %s [%d,%d): %w", src, lo, hi, err)
		}
		b, err := Stat(ctx, db, dst, cols, lo, hi)
		if err != nil {
			return nil, fmt.Errorf("stat %s [%d,%d): %w", dst, lo, hi, err)
		}
		if a != b {
			bad = append(bad, lo)
		}
	}

	// 全红几乎不可能是数据问题，而是对比方式本身错了——直接报出来，别让人去查 256 张表
	if len(bad) > 0 && int64(len(bad)) == maxID/chunk+1 {
		return nil, errors.New("sharddemo: every chunk differs — check column order / charset / collation first")
	}
	return bad, nil
}

// validateIdent：表名与列名都是标识符，必须自己校验。
// 迁移工具的输入往往来自配置文件或运维命令行，同样要按"外部输入"对待。
func validateIdent(table string, cols []string) error {
	if !identRe.MatchString(table) {
		return fmt.Errorf("sharddemo: illegal table name %q", table)
	}
	if len(cols) == 0 {
		return errors.New("sharddemo: no columns to compare")
	}
	for _, c := range cols {
		if !identRe.MatchString(c) {
			return fmt.Errorf("sharddemo: illegal column name %q", c)
		}
	}
	return nil
}

// identRe 只允许"字母/下划线开头 + 字母数字下划线"，长度 ≤64（MySQL 标识符上限）。
var identRe = regexp.MustCompile(`^[A-Za-z_][A-Za-z0-9_]{0,63}$`)
```

校验之外，切换期还要双写：下面这段决定老库与新库的写入顺序与失败处理。

```go
// DualWrite 双写阶段的正确顺序：**以老库为准**，新库写失败只记补偿任务。
// 反过来"新库失败就整体回滚"会让灰度期新库的任何抖动直接打挂线上写。
func DualWrite(ctx context.Context, oldDB, newDB *sql.DB, userID, name string, logFailure func(error)) error {
	tx, err := oldDB.BeginTx(ctx, nil)
	if err != nil {
		return err
	}
	defer func() { _ = tx.Rollback() }()

	table := TableName(userID)
	const upsert = ` INSERT INTO %s (user_id, name) VALUES (?, ?) ON DUPLICATE KEY UPDATE name = VALUES(name)`

	if _, err := tx.ExecContext(ctx,
		fmt.Sprintf(upsert, table), userID, name); err != nil {
		return err
	}
	if err := tx.Commit(); err != nil {
		return err
	}

	// 老库已经成功了，新库只能"尽力 + 补偿"，不能回滚
	if _, err := newDB.ExecContext(ctx,
		fmt.Sprintf(upsert, "user_new"), userID, name); err != nil {
		logFailure(fmt.Errorf("dual write to new table: %w", err))
	}
	return nil
}
```

> ⚠️ `CRC32` 只能发现"不一样"，不能告诉你哪里不一样；**字符集/排序规则不一致时会全表误报**
> （`utf8mb4_general_ci` vs `utf8mb4_0900_ai_ci` 是 8.0 迁移最常见的坑）。
> 生产校验建议直接用 `pt-table-checksum`（见下面「使用二」）；本节 Go 实现更适合理解原理和做小表抽查。

## 使用二：迁移与切换的实操命令

正文第一节/第二节已经把九步流程和风险讲完了，这里只补**执行层面直接可用**的命令，避免重复阅读：

### 1. 全量搬迁与一致性快照

```bash
# 正文第一节的逻辑导出：--single-transaction 只对事务引擎有效（RR 快照读）；MyISAM 表仍被逐表锁走且不告警
docker exec -i mysql8 sh -c \
  'mysqldump -uroot -p --single-transaction --set-gtid-purged=OFF --source-data=2 \
     --databases test --tables user_0000 | gzip > /tmp/user_0000.sql.gz'

# 导入到目标实例
gunzip -c /tmp/user_0000.sql.gz | docker exec -i mysql8 mysql -uroot -p test
```

| 参数 | 为什么必须 |
|---|---|
| `--single-transaction` | 在一个 RR 事务里读，导出期间不锁业务表；**代价是导出时长内未提交的事务看不到**，所以要么停写、要么靠增量追平。⚠️ 实测：库里混 MyISAM 时它**不告警**，那张表照样被逐表锁走 |
| `--set-gtid-purged=OFF` | 不把源库 GTID 写进目标库，否则目标库会认为"这些事务我已经有了"而跳过复制。实测：`gtid_mode=OFF` 时写 `ON` 报 `Error: Server has GTIDs disabled.`；开着 GTID 时默认 `AUTO` 会往文件里写 `SET @@GLOBAL.GTID_PURGED=...`，`OFF` 让这行变成 0 处 |
| `--source-data=2`（8.0.26+，旧名 `--master-data`，实测已报废弃告警） | 在 dump 头部注释里记录**位点 / GTID**，增量从这里接上；实测 `=1` 是**不带注释前缀的可执行语句**。⚠️ 8.0 实测位点前缀是 `binlog.0000NN`，不是 `mysql-bin.0000NN` |

### 2. 校验：直接复用社区实现

```bash
# pt-table-checksum 主库执行：自动分块算 CRC，并对比从库；--no-check-replica-filters 视架构决定
pt-table-checksum --replication=1 --chunk-time=0.5 \
  --databases=test --tables='user_\d{4}' --where='1=1' \
  h=src-host,u=checksum,p=xxx

# 差异明细用 pt-table-sync（⚠️ --execute 会真的改数据，默认只打印）
pt-table-sync --print --replicate percona.checksums h=src-host,u=checksum,p=xxx h=dst-host,u=checksum,p=xxx
```

> `--chunk-time` 是**自适应分块**（自动调每块行数，让每块耗时 ≈0.5s），
> 对应 Go 侧 `Verify` 里手写的 `chunk` 参数——生产直接用这个思路，别写死行数。

### 3. 切换与回滚的关键命令

```sql
-- 正文九步里"只读 + 追平"的两条判据（第 6、7 步）
SELECT @@read_only, @@super_read_only;
SELECT WAIT_FOR_EXECUTED_GTID_SET('xxxxxxxx-xxxx-....:1-2000000', 30);  -- 返回 0 = 已追平

-- 切读流量后，回滚是**非对称**的：新库必须持续反向同步回老库，
-- 否则回滚那一刻老库缺的就是切换期间产生的全部写入（正文第一节风险的落地形式）
SHOW REPLICA STATUS\G   -- 看 Reverse 链路的 Seconds_Behind_Source 是否为 0
```

`WAIT_FOR_EXECUTED_GTID_SET()` 的返回值在本机验过（同一实例上构造两个集合就能覆盖两支）：

```text
mysql> SELECT WAIT_FOR_EXECUTED_GTID_SET('b5b66ea4-...:1-3', 3) AS ret_already;
+-------------+
| ret_already |
+-------------+
|           0 |      <- 已经追平，立刻返回
mysql> SELECT WAIT_FOR_EXECUTED_GTID_SET('b5b66ea4-...:1-99999999', 3) AS ret_timeout;
+-------------+
| ret_timeout |
+-------------+
|           1 |      <- 等待超时 = 还没追平
mysql> SELECT WAIT_FOR_EXECUTED_GTID_SET('not-a-gtid', 3);
ERROR 1772 (HY000): Malformed GTID set specification 'not-a-gtid'.
```

脚本里要把"返回 1"当成**继续等或报警**，而不是当成失败：它只说明这一笔还没到，
切换窗口内最常见的处理是把超时参数拉长再重试一轮。

**切换前的三条 checklist**（比脚本更重要）：

1. **业务写入口是否只有一个？** 双写期间出现第三条写入路径 = 数据静默分叉，校验会全红；
2. **自增值 / 序列怎么办？** 迁移后目标库的 `AUTO_INCREMENT` 必须超过源库最大值，否则切过去就主键冲突；
3. **回滚窗口多长？** 决定新库要不要**保留**老库的同步链路——"切完就停老库同步"等于关掉了回滚。
