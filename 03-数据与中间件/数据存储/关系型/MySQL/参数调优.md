# 参数调优

> 从操作系统和硬件一路看到 `my.cnf`：先判瓶颈类型，再算内存账与 I/O 账，最后才轮到那几十个参数。

## 一、MySQL 的性能到底被什么限制？

**本节要点**：调参之前必须先回答「瓶颈在哪一层」，否则参数只是在制造新的随机波动。

### 1.1 四类瓶颈与各自的判据

**来源**：《高性能 MySQL》（第 4 版）第 4 章「什么限制了 MySQL 的性能」。

| 瓶颈 | 典型表现 | 先看什么 | 参数能不能救 |
|---|---|---|---|
| CPU | 单条 SQL 吃满一个核，QPS 上不去但磁盘很闲 | 慢 SQL 的执行计划、扫描行数、表达式计算量 | 基本不能，要改 SQL 或加索引 |
| 内存 | 工作集放不下，缓冲池命中率低、频繁读盘 | 工作集大小 vs `innodb_buffer_pool_size`、swap 计数 | 能，但要先把连接级内存算清 |
| 磁盘 I/O | 写尖峰、脏页堆积、刷脏堵在提交点 | redo 容量与年龄、脏页率、`innodb_io_capacity` 是否配小了 | 能，这是参数最有效的区域 |
| 网络 | 跨可用区往返、大包重传 | 单条结果集大小、`max_allowed_packet`、连接是否复用 | 部分能，更多是架构问题 |

判据的关键是**同一时刻只看一层**：CPU 满而磁盘闲的时候调 `innodb_io_capacity`，
只会让上下文切换更多。

### 1.2 「工作集」才是内存够不够的判据

**来源**：《高性能 MySQL》（第 4 版）第 4 章「你的工作集是什么」。

工作集（working set）= **一段时期内被反复访问的那部分数据页**，不是数据总量。
它的意义在于：

- 数据 500 GB 不代表要 500 GB 内存。热点行集中在 60 GB 时，
  buffer pool 给到 64 GB 就已经"装得下全部热点"，剩下的都是顺序扫描类查询；
- 反过来，数据只有 80 GB 但每条查询都全表扫，工作集同样撑爆内存；
- 所以先估工作集，再定 `innodb_buffer_pool_size`；估不出来就用「表大小 × 被访问比例」粗算，
  或直接看 `SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read%'` 两个计数器的比值趋势。

### 1.3 为什么顺序是「硬件 → 操作系统 → 参数 → SQL」

第 4 版把硬件与 OS 单独成章、把参数放在其后，是有原因的：**参数只能在硬件给定的能力范围内做取舍**。

- `innodb_io_capacity` 声明的是"这台盘能承受多少 IOPS"，把它从 200 调到 2000 并不会让机械盘变快，
  只会让刷脏突发把盘打到排队；
- swap 没关掉、文件系统没用 `noatime`、磁盘调度器还是默认值，
  这些都会让任何 MySQL 参数的效果失真；
- 真正稳的做法是：硬件按工作集配齐 → OS 层把干扰项去掉 → 参数只改"确实和负载不匹配"的几项 →
  剩下的靠 SQL 与索引。

## 二、硬件与操作系统层：需要事先定的是什么？

**来源**：《高性能 MySQL》（第 4 版）第 4 章「如何为 MySQL 选择 CPU」「平衡内存和磁盘资源」「固态存储」「RAID 性能优化」「选择文件系统」「选择磁盘队列调度器」「内存和交换」「操作系统状态」。

### 2.1 CPU：高主频优先于核心数

MySQL 的一条 SQL 在绝大多数情况下**只用一个线程**（并行查询不属于 8.0 的通用能力），
所以单核性能直接决定最慢那条查询的下限；核心数决定的是"能同时跑多少条"。

判据：**先满足单条 SQL 的延迟目标，再谈并发**。同样的预算，4 个高频核往往优于 16 个低频核——
前提是并发量没到饱和。另外要注意：容器里改 CPU limit 等于改了一批参数的自动推导结果
（`innodb_buffer_pool_instances`、线程缓存的自动值都依赖检测到的资源）。

### 2.2 内存与磁盘的平衡

内存买得再多，也只是把 buffer pool 撑大；磁盘慢，冷数据与刷脏一样堵。第 4 版的取舍是：

- 内存要留够**操作系统页缓存**——Linux 上 InnoDB 读写数据文件默认仍经过 OS 的 page cache
  （除非用 `O_DIRECT`），"把内存全给 buffer pool"是错的；
- 磁盘预算优先给 **IOPS 与延迟**，容量是次要的；同样是 SSD，企业级的稳定延迟比标称吞吐更有价值。

### 2.3 固态存储：垃圾收集与写放大

**这是 SSD 上最容易踩的一条**：闪存按块擦除、按页写入，空闲页攒到一定程度要做垃圾收集（GC）。
GC 触发时会和 MySQL 的写抢带宽，表现为**盘用久了变慢**、写入延迟出现毛刺。

对应的做法：

- 预留一部分空间不要写满（厂商一般建议留 10%~25% 空余），别让 GC 无页可用；
- 文件系统与分区对齐，避免一次 16 KB 页写裂成两次物理写；
- `innodb_flush_neighbors` 在 8.0 默认已经是 `0`——**SSD 上"顺带写相邻页"没有收益，只增加写放大**；
  这条默认值的变化本身就说明第 4 版是按 SSD 时代写的；
- 别用 RAID5 做 MySQL 数据盘：写惩罚与 GC 会叠加（见 2.4）。

### 2.4 RAID：性能、故障与监控

| 级别 | 写代价 | 可用容量 | 适合 MySQL 吗 |
|---|---|---|---|
| RAID 1 / 10 | 一次数据写 + 镜像写 | 50% | ⭐ 首选，写惩罚可预测 |
| RAID 5 | 读快，写要算校验（小随机写惩罚最重） | (N-1)/N | 数据盘不推荐；日志盘也慎用 |
| RAID 0 | 无冗余 | 100% | 只在"能从备份重建"的测试环境 |

另外两条：**带电池/闪存保护的写缓存（BBU）能显著降低 `sync` 策略的代价**，
没有 BBU 时 RAID 卡的写缓存反而可能丢数据；RAID **重建期间性能会明显劣化**，
所以"有 RAID 就不用备份"不成立——RAID 防的是盘坏，不防误删。

### 2.5 文件系统、调度器与交换分区

- 文件系统：第 4 版的取向是 **XFS 或 ext4**，配 `noatime`——MySQL 每次读都会触碰 inode，
  关掉访问时间更新能省掉大量无意义的元数据写。
- 磁盘队列调度器：SSD/NVMe 用 **`none`**（设备自己会并行排队，内核再排序纯属浪费）；
  机械盘用 `mq-deadline`（旧 `deadline` 在多队列内核里的对应名字）。
  用 `cfq`/`bfq` 跑数据库，会把刷脏的突发变成排队。
- 交换分区：数据库主机上**要么关掉 swap，要么把 `vm.swappiness` 压到很低**。
  buffer pool 被换出后进程还活着，但每次访问都要等盘，是最难从 MySQL 侧解释的一类抖动。
  完全关 swap 则要留足内存，否则 OOM killer 会直接杀 `mysqld`。

### 2.6 OS 层先装的三样观测

「操作系统状态」「其他有用的工具」两节的实质是：**先能证明瓶颈在 OS 层，再动 MySQL 参数**。
最小集合是 `vmstat`（看 `si/so` 与 `wa`）、`iostat -x`（看 `%util`、`await`、队列长度）、
`top -H`/`pidstat`（看 mysqld 的线程分布）；进阶是 `pt-ioprofile`、`perf`。

## 三、改参数之前：MySQL 的配置是怎么工作的？

**来源**：《高性能 MySQL》（第 4 版）第 5 章「MySQL 的配置是如何工作的」「语法、作用域和动态性」「持久化系统变量」「设置变量的副作用」「规划变量的更改」「什么不该做」「创建 MySQL 配置文件」「最小化配置」「检查 MySQL 服务器的状态变量」。

### 3.1 作用域与动态性：三个必须先查的属性

每个变量要先分清三件事：

1. **作用域**：`Global` / `Session` / `Both`。只影响新建连接的项（如 `max_connections`）
   改完对现有连接无效；`Session` 级的（`sort_buffer_size`）要靠连接初始化或语句 hint。
2. **是否动态**：`Dynamic=Yes` 可 `SET` 生效；`No` 必须改配置文件并重启
   （典型：`innodb_buffer_pool_instances`、`innodb_flush_method`、`relay_log_recovery`）。
3. **配置文件与 SQL 的写法不同**：配置文件里是 `--innodb-buffer-pool-size`（短横线），
   SQL 里是 `innodb_buffer_pool_size`（下划线）。这是最常见的"改了没生效"原因之一。

给单条 SQL 临时调参还有第三种办法：**优化器 hint**
（`SELECT /*+ SET_VAR(join_buffer_size=8M) */ ...`），作用域只在这条语句上，不动全局。

### 3.2 持久化：`SET PERSIST` 与配置文件谁优先

8.0 起可以把变量写进数据目录下的 `mysqld-auto.cnf`（JSON 文件）：

```sql
SET PERSIST innodb_io_capacity = 2000;              -- 立即生效且重启后仍在
SET PERSIST_ONLY innodb_buffer_pool_instances = 8;  -- 只写文件，重启才生效
RESET PERSIST innodb_io_capacity;                   -- 从 mysqld-auto.cnf 里移除
```

加载顺序是 **编译默认 → 配置文件 → `mysqld-auto.cnf`**，所以 `SET PERSIST` 会盖住 `my.cnf` 里同名的配置。
坑在这里：**排查"为什么这个参数不是我看到的值"时两处都要查**。一条 SQL 就能看出每一项是谁设的：

```sql
SELECT VARIABLE_NAME, VARIABLE_SOURCE, DEFAULT_VALUE, VARIABLE_VALUE, SET_USER, SET_TIME
FROM performance_schema.variables_info
WHERE VARIABLE_SOURCE <> 'COMPILED'
ORDER BY VARIABLE_NAME;
```

### 3.3 副作用：一个变量会牵动另一批变量

「设置变量的副作用」「规划变量的更改」两节合起来是一句话：**参数不是独立的**。

- `innodb_buffer_pool_size` 变大 → 留给 OS 页缓存的内存变小 → 全表扫与备份读盘更依赖磁盘；
- `max_connections` 变大 → 连接级内存的最坏上限同步放大 → OOM 风险上升；
- `innodb_io_capacity` 变大 → 刷脏更积极 → 用户请求等待变少，但盘的带宽更常被占用。

所以动手之前要写下四件事：**这项参数为什么现在不合适、改成多少、用什么指标验证、怎么回滚**。

### 3.4 什么不该做

「什么不该做」是清单式警告，落到今天依然成立：

- ⚠️ **不要整份抄网上的 `my.cnf` 模板**：模板是别人负载下的结论，
  尤其别抄带年份的模板——`query_cache_size` 这类 8.0 已删除的变量会让实例直接起不来。
- ⚠️ **不要一次改一堆**：无法归因，也无法回滚。
- ⚠️ **不要动不理解的参数**：自旋、信号量、`innodb_adaptive_max_sleep_delay` 这类高级项，
  默认值针对通用硬件，没有测量证据不要碰。
- ⚠️ **不要在生产直接改 `Dynamic=No` 的项**：它要重启，先在于库验证重启时长与恢复流程（见第七节）。
- ⚠️ **不要把状态变量当配置变量读**：`SHOW GLOBAL STATUS` 的累计值没有意义，要看两次采样的差。

### 3.5 最小化配置 + 状态计数器的正确读法

第 5 章给的配置方式是**从最小配置开始**：只显式写与负载相关的那几项
（`innodb_buffer_pool_size`、`innodb_redo_log_capacity`、`max_connections`、
`innodb_flush_log_at_trx_commit` 与 `sync_binlog` 的持久化档位），其余留默认。
配置越少，升级与迁移时的意外越少。

看状态变量要用速率而不是累计值：

```bash
# 间隔 10 秒取两次，diff 出来的才是"这 10 秒内发生了什么"
mysql -e "SHOW GLOBAL STATUS" > /tmp/s1
sleep 10
mysql -e "SHOW GLOBAL STATUS" > /tmp/s2
diff /tmp/s1 /tmp/s2
```

实测时踩到一个坑：**`mysql:8.0` 镜像是最小化的，容器里没有 `diff`**（`swapon`、`pidof`、`findmnt` 同样没有）
→ 取差值改用 `awk` 自己配：

```bash
C="-uroot -p密码"
mysql $C -N -e "SHOW GLOBAL STATUS" > /tmp/s1
mysql $C docverify -N -e "SELECT COUNT(*) FROM t_x a JOIN t_y b ON a.k=b.k;" > /dev/null
mysql $C -N -e "SHOW GLOBAL STATUS" > /tmp/s2
awk 'NR==FNR{a[$1]=$2;next} ($1 in a) && a[$1] != $2 {printf "%-42s %s -> %s\n", $1, a[$1], $2}' /tmp/s1 /tmp/s2
```

两次采样之间只跑了一条 JOIN（494 个计数器里只有这些变了），实际输出：

```text
Com_select                         515 -> 519
Handler_read_rnd_next          181664 -> 188157
Innodb_buffer_pool_read_requests  149972 -> 153029
Innodb_rows_read                  41777 -> 47277
Opened_tables                        937 -> 941
Select_full_join                      65 -> 66
```

读法：`Handler_read_rnd_next` 涨约 6500、`Innodb_rows_read` 涨约 5500 同时出现，就是"这条语句在全表扫"的指纹；
`Innodb_buffer_pool_read_requests` 涨了约 3057，而 `Innodb_buffer_pool_reads` 一行没变 → **全部命中缓冲池，没有物理读**。

## 四、内存账：buffer pool 只是其中一块

**来源**：《高性能 MySQL》（第 4 版）第 5 章「配置内存使用」「每个连接的内存需求」「为操作系统保留内存」「InnoDB 缓冲池」「线程缓存」。

### 4.1 先把这几个默认值记住

| 参数 | 8.0 默认值 | 作用域 | 动态 | 什么时候要动 |
|---|---|---|---|---|
| `innodb_buffer_pool_size` | 134217728（128 MB） | Global | 是 | 按工作集给足，专用实例常配到内存的 50%~75% |
| `innodb_buffer_pool_instances` | 8；实测 128 MB 池下为 **1**（不足 1 GB 会被夹到 1） | Global | **否** | 池子大时增加分片，降低争用 |
| `thread_cache_size` | 配置默认 `-1` = 自动推导；实测 128 MB 池 + `max_connections=151` 时算出 **9** | Global | 是 | 高频短连接场景，减少线程创建开销 |
| `table_open_cache` | 4000 | Global | 是 | 表数量多、`Opened_tables` 持续增长时 |
| `sort_buffer_size` | 262144（256 KB） | Session | 是 | 排序落盘（`Sort_merge_passes` 增长）时按连接调 |
| `join_buffer_size` | 262144（256 KB） | Session | 是 | 无索引连接（块嵌套/哈希连接）时 |
| `tmp_table_size` / `max_heap_table_size` | 16777216（16 MB） | Both | 是 | `Created_tmp_disk_tables` 增长时（两个要一起看） |
| `max_allowed_packet` | 67108864（64 MB） | Both | 是 | 大 BLOB / 超大数据包复制时；**客户端侧也要配** |
| `innodb_log_buffer_size` | 16777216（16 MB） | Global | 是 | 大事务、出现 `Innodb_log_waits` 时 |

上表默认值已在 8.0.46 实测核对，一条 SQL 就能全拿：

```sql
SELECT @@innodb_buffer_pool_size, @@innodb_buffer_pool_instances, @@thread_cache_size,
       @@table_open_cache, @@max_connections,
       @@sort_buffer_size, @@join_buffer_size, @@read_buffer_size, @@read_rnd_buffer_size,
       @@tmp_table_size, @@max_heap_table_size, @@max_allowed_packet,
       @@binlog_cache_size, @@innodb_log_buffer_size;
```

实测一行输出（默认值依次对应上面的列）：

```text
134217728  1  9  4000  151  262144  262144  131072  262144  16777216  16777216  67108864  32768  16777216
```

⚠️ **换实例先跑这一条**：小版本会调默认值；而 `thread_cache_size` 的 9 是推导结果，不是字面配置值 ——
把 9 抄进 my.cnf 就失去了随 `max_connections` 联动的意义。

一个容易被记错的点：`table_open_cache` 在 5.7 是 400，**8.0 已经是 4000**——
网上大量"MySQL 参数优化"文章还在写 400，照抄等于白白调小了一个数量级。

### 4.2 每个连接的内存才是隐形炸弹

buffer pool 是一块固定的池子，而**会话级缓冲是"每个连接都可能各自分配一份"**：
`sort_buffer_size`、`join_buffer_size`、`read_buffer_size`、`read_rnd_buffer_size`、
`binlog_cache_size` 都在语句执行时按需分配，`tmp_table_size` 是临时表上限。

于是最坏情况的算法是：

```text
峰值内存 ≈ innodb_buffer_pool_size（+ 日志缓冲、字典等固定开销）
          + max_connections × Σ(会话级缓冲)
          + OS 页缓存 + 监控/备份进程
```

这就是「把 `max_connections` 调到 10 万」这类操作的根因问题：
它不是"允许更多连接"，而是**把最坏情况的可分配内存放大几倍到几十倍**。
正确的分工是：连接池与代理负责排队与限流（见 [软件架构.md](软件架构.md) 的连接池一节），
MySQL 侧只留够用的余量。

### 4.3 为操作系统保留内存

两条硬约束：

- Linux 上 InnoDB 读写数据文件默认仍经过 OS page cache；内存全给 buffer pool，
  page cache 归零，全表扫、备份、`CHECKSUM` 类读盘会立刻变慢（用 `O_DIRECT` 是另一套账）。
- 内存真的耗尽时，OOM killer 挑的往往是**占内存最大的进程——`mysqld`**。
  宁可 buffer pool 小一点，也不要让系统进到 swap 或 OOM 的边缘。

### 4.4 buffer pool 内部还影响命中率的三个参数

| 参数 | 8.0 默认值 | 作用 |
|---|---|---|
| `innodb_old_blocks_time` | 1000（毫秒） | 新读入的页要在 old 子链表待满 1 秒才可能晋升，**防全表扫冲刷热点页** |
| `innodb_lru_scan_depth` | 1024 | page cleaner 每轮回收脏页时扫描的深度，越大越"愿意提前刷" |
| `innodb_page_cleaners` | 4，但**会被夹到 `innodb_buffer_pool_instances`** | 刷脏线程数；官方建议与实例数取齐 |

这三个是"命中率明明不低却仍在等 buffer"时最先要查的组合。

⚠️ `innodb_page_cleaners` 的实测细节（三次重启对照，命令行只给 buffer pool 相关参数）：

```text
bp=128MB（默认）                      ->  inst=1  cleaners=1
bp=384MB 且 --innodb_buffer_pool_instances=3  ->  inst=1  cleaners=1
bp=2GB   且 --innodb_buffer_pool_instances=4  ->  inst=4  cleaners=4
```

两个结论：**buffer pool 不足 1 GB 时 `innodb_buffer_pool_instances` 只能是 1**（命令行给 3 也会被夹回去），
`innodb_page_cleaners` 跟着实例数走。两者都是**只读变量**，运行时改会报：

```text
ERROR 1238 (HY000): Variable 'innodb_page_cleaners' is a read only variable
```

## 五、I/O 账：redo、刷脏与组提交

**来源**：《高性能 MySQL》（第 4 版）第 5 章「配置 MySQL 的 I/O 行为」「InnoDB 事务日志」「日志缓冲区」「InnoDB 表空间」「其他 I/O 配置选项」「配置 MySQL 并发」。

### 5.1 redo 的容量参数在 8.0.30 换了名字

- **8.0.30 起**：`innodb_redo_log_capacity`（默认 104857600 = 100 MB），**可动态调整**；
- **8.0.30 之前**：由 `innodb_log_file_size`（默认 50331648 = 48 MB）× `innodb_log_files_in_group` 决定，
  改容量要重启；这两个参数已被官方标记为废弃。

实测（8.0.46）：

```sql
SET GLOBAL innodb_redo_log_capacity = 209715200;   -- 在线扩到 200 MB，不用重启
SET GLOBAL innodb_log_file_size = 62914560;        -- 期望被拒绝
```

```text
@@innodb_redo_log_capacity
209715200
ERROR 1238 (HY000): Variable 'innodb_log_file_size' is a read only variable
```

文件层的两个实测口径：

```text
ls /var/lib/mysql/#innodb_redo | wc -l        ->  32（新建空实例与扩容后的实例都是 32）
ls -l /var/lib/mysql/#innodb_redo            ->  #ib_redo9 + 一批 #ib_redo<N>_tmp
du -sh /var/lib/mysql/#innodb_redo           ->  101M（默认容量 100 MB 时）
```

也就是说 **8.0.30+ 预分配 32 个槽位文件**，`_tmp` 是还没启用的槽位，
`innodb_redo_log_capacity` 决定的是"同时启用多少"，**不是文件个数** ——
别拿 `ls | wc -l` 当容量判据。真正该盯的是这组状态计数器（实测输出）：

```text
Innodb_redo_log_read_only              OFF
Innodb_redo_log_uuid                   4114255518
Innodb_redo_log_checkpoint_lsn         29620908
Innodb_redo_log_current_lsn            29620908
Innodb_redo_log_flushed_to_disk_lsn    29620908
Innodb_redo_log_logical_size           512
Innodb_redo_log_physical_size          3276800
Innodb_redo_log_capacity_resized       104857600
Innodb_redo_log_resize_status          OK
Innodb_redo_log_enabled                ON
```

`Innodb_redo_log_logical_size` 就是 redo 的"年龄"：它逼近 `capacity` 时刷脏会被推到前台，
这正是 5.1 说的周期性写尖峰的可观测入口（`SHOW GLOBAL STATUS LIKE 'Innodb_redo%'`）。
另外 `@@innodb_log_file_size` 在 8.0.46 仍可读（返回 50331648），但它已经不再决定 redo 容量 ——
**照着老脚本里这个参数算容量，会算错一半**。

redo 是环形日志，检查点位置到已刷位置之间的这段"年龄"必须始终容得下未刷脏页对应的修改。
**redo 太小的连锁反应**：InnoDB 被迫提前刷脏，刷脏从后台挪到前台等待，
表现为**写入延迟出现周期性尖峰**——这也是很多人把问题误判成"索引没建好"的原因。

### 5.2 持久化档位是一对，不是一个

| 参数 | 8.0 默认 | 取值含义 |
|---|---|---|
| `innodb_flush_log_at_trx_commit` | 1 | 1 = 每次提交写 redo 并 fsync（已提交事务不丢）；0 = 每秒写盘，崩溃约丢 1 秒；2 = 每次提交写到 OS 缓存、每秒 fsync，只有 OS/主机崩溃才丢 |
| `sync_binlog` | 1 | 1 = 每次提交 fsync binlog；0 = 交给 OS 决定刷写时机 |

两条要**一起看**：只把 `innodb_flush_log_at_trx_commit` 设成 2 而 `sync_binlog` 仍是 1，
崩溃时 binlog 比 redo 更新的可能性反而更大，主从数据漂移更难解释。
这就是 [日志与落盘.md](日志与落盘.md) 里两阶段提交在参数层的落点——
**优化的本质是"在哪一侧少付一次 fsync"，而 fsync 的位置决定了故障时谁多谁少**。

组提交是 MySQL 对这对开关的自动补偿：`binlog_group_commit_sync_delay` 默认 0；
调成非 0 是"多等一下再一起刷"，用延迟换 fsync 次数，只在写密集型负载上考虑。

### 5.3 `innodb_io_capacity` 是最常被配错的一个

8.0 默认 `innodb_io_capacity = 200`，`innodb_io_capacity_max = 2 × innodb_io_capacity`（上限 2000）。
这个 200 是**机械盘时代的假设**：它告诉 page cleaner"这台盘每秒大约能承受 200 次 I/O"。
SSD/NVMe 上不显式调大，就会出现「盘很闲、脏页在堆积、偶尔集中刷」的三段式抖动。

判据：

- 按盘的**随机 IOPS 规格的 50%~60%** 起步，不要按标称峰值（要给正常读写留带宽）；
- `innodb_flush_neighbors` 保持 0（SSD 不需要相邻页合并）；
- 观察脏页数与 `Innodb_os_log_pending_writes` 是否还呈周期性堆积，再决定继续加。

### 5.4 其余 I/O 相关默认值速查

| 参数 | 8.0 默认 | 要点 |
|---|---|---|
| `innodb_flush_method` | 平台相关（Linux 上常配 `O_DIRECT`） | 绕过 page cache 免"双重缓存"；配错会让内存账整个变样 |
| `innodb_flush_sync` | ON | 刷脏同步等待，避免提交点被拖长；排查刷脏毛刺时先确认它 |
| `innodb_doublewrite` | ON | 双写缓冲防"半页写坏"；关它省 I/O，但**不要在有断电风险的盘上关** |
| `innodb_file_per_table` | ON | 每表独立 `.ibd`，才谈得上可传输表空间搬迁（见 [数据迁移.md](数据迁移.md)） |
| `innodb_change_buffering` | all | 二级索引的写先合并缓冲，写密集时降低随机 I/O |
| `innodb_adaptive_hash_index` | ON | 自适应哈希加速等值查找；出现相关争用时才考虑关 |

### 5.5 「配置 MySQL 并发」这一节的真实结论

这里的参数是**限流，不是加油**。自旋次数、信号量等待、`innodb_thread_concurrency`
默认都交给自动逻辑；只有当测量显示存在大量 mutex/lock 等待时才动，且一次只动一项。
指望"调大并发参数让 MySQL 并行跑一条 SQL"是不成立的。

## 六、`innodb_dedicated_server`：一条能替你算三项的参数

**来源**：《高性能 MySQL》（第 4 版）第 5 章「高级 InnoDB 设置」；自动配置的分档按 MySQL 8.0 官方文档核对。

`innodb_dedicated_server` 默认 **OFF**，且**只能在启动时设**（不是动态变量）。打开后 MySQL 按
**检测到的物理内存**自动配置下面几项：

| 检测到的内存 | 自动配置的 buffer pool | 自动配置的 redo 容量 |
|---|---|---|
| < 1 GB | 128 MB（即默认值） | 100 MB |
| 1 GB ~ 4 GB | 内存 × 0.5 | 1 GB ~ 2 GB 档为 100 MB，2 GB ~ 4 GB 档起按公式递增 |
| > 4 GB | 内存 × 0.75 | 4 GB ~ 10.66 GB、10.66 GB ~ 170.66 GB 各一档，上限 128 GB |

它同时会影响 `innodb_flush_method` 的自动选择；8.0.30 之前还会算 `innodb_log_file_size`
（buffer pool < 8 GB 时 512 MB，8~128 GB 时 1024 MB，更大 2048 MB）与 `innodb_log_files_in_group`。

三条必须一起记住的限制：

1. **只在"这台实例独占整机"时开**（官方举例：只跑 MySQL 的独立 VM 或容器）；
   和别的进程共享内存时开它，buffer pool 会挤掉别人的内存。
2. **只在启动时计算一次**。之后显式设置的值会覆盖它算出来的值；
   把变量设回 `DEFAULT` **不会**回到推导值，而是回到手册里的出厂默认。
3. 显式写了 `innodb_buffer_pool_size` 时，错误日志会打印一条 warning 说明该项被忽略——
   **写了的项以你写的为准，没写的项仍会被自动配**。

适用面很窄但很实用：全新实例、独占整机、还没来得及估工作集。
不适用：云上共享型规格、和大量 sidecar 同机的容器实例。

## 七、一次参数变更怎么落地？

### 7.1 顺序：从库 → 主库，一次一项

`Dynamic=No` 的项要重启，所以**先在从库验证重启时长与恢复流程**：
从库可以先摘流量、重启、追平延迟，再动主库。一次只改一项，
改完至少跑过一个完整业务高峰再改下一项。

### 7.2 验证要看哪几组指标

- 内存类：`Innodb_buffer_pool_read_requests` 与 `Innodb_buffer_pool_reads` 的比值趋势、
  是否出现 swap（`vmstat` 的 `si/so`）；
- I/O 类：脏页计数、`Innodb_os_log_pending_writes`、redo 年龄是否还周期性顶到上限；
- 连接类：`Aborted_connects`、`Threads_connected`、`Opened_tables`、`Created_tmp_disk_tables`；
- 端到端：**P95/P99 延迟**，不是平均延迟（原因见 [观测与诊断.md](观测与诊断.md) 第二节）。

### 7.3 云上很多参数你动不了

第 4 版第 12 章「云端的 MySQL」讲的正是这件事：托管实例通常锁住 `innodb_flush_method`、
路径类与专用服务器类参数，能调的只剩白名单几项。所以云上做容量规划时，
**先确认哪些参数不在你的控制范围内**，再决定要不要用托管实例。

计算存储分离类服务（书里点名的 Amazon Aurora）甚至让 5.1、5.2 两节的前提整体失效——
redo 被下沉到存储层，"刷脏/组提交"这本账要按服务方的文档重算，不能沿用自建实例的结论。

## 使用：参数与内存账的核查清单

✅ 以下 5 段在 Docker Desktop 的 `mysql:8.0`（**8.0.46**，Linux）容器里逐条跑过，输出抄自本机。
⚠️ 容器镜像里没有 `swapon` / `pidof` / `findmnt` 这三个命令 → 第 5 段给的是容器环境的替代写法。

### 1. 一次看清"当前值 / 默认值 / 谁设的"

```sql
SHOW VARIABLES WHERE Variable_name IN
  ('innodb_buffer_pool_size','innodb_redo_log_capacity','innodb_io_capacity',
   'innodb_flush_log_at_trx_commit','sync_binlog','max_connections','table_open_cache');

-- 只列被改过的项，并给出来源（命令行 / my.cnf / mysqld-auto.cnf）
-- ⚠️ 这张表里没有 DEFAULT_VALUE / VARIABLE_VALUE 两列，照抄报 1054
SELECT VARIABLE_NAME, VARIABLE_SOURCE, VARIABLE_PATH, MIN_VALUE, MAX_VALUE, SET_USER, SET_TIME
FROM performance_schema.variables_info
WHERE VARIABLE_SOURCE <> 'COMPILED'
ORDER BY VARIABLE_NAME;
```

实测这张表固定 8 列，`VARIABLE_SOURCE` 是枚举值：

```text
VARIABLE_NAME | VARIABLE_SOURCE | VARIABLE_PATH | MIN_VALUE | MAX_VALUE | SET_TIME | SET_USER | SET_HOST
enum('COMPILED','GLOBAL','SERVER','EXPLICIT','EXTRA','USER','LOGIN','COMMAND_LINE','PERSISTED','DYNAMIC')
```

所以**"当前值"要回去问 `SHOW VARIABLES`，"默认值"这张表不提供**（要默认值只能 `mysqld --verbose --help`
或对照官方变量表）；它能给的是"谁在什么时候设的 + 取值范围"。

`SET PERSIST` / `RESET PERSIST` 在这张表上的真实轨迹（同一变量、三个时刻）：

```text
-- 运行时 SET PERSIST max_connect_errors = 200 之后立刻查：
max_connect_errors | DYNAMIC   | (VARIABLE_PATH 为空) | root      | @@值 = 200

-- 重启之后同一条查询：
max_connect_errors | PERSISTED | /var/lib/mysql/mysqld-auto.cnf | root | @@值 = 200

-- RESET PERSIST max_connect_errors 之后，mysqld-auto.cnf 只剩：
{"Version": 2}
```

三个口径：`SET PERSIST` 当场生效时来源记的是 `DYNAMIC`，**只有重启后才显示 `PERSISTED`**；
`RESET PERSIST` 不带变量名会清掉**全部**持久化项（实测一次清空三个变量，重启后回默认值）；
持久化文件是 JSON，就在 datadir 里，叫 `mysqld-auto.cnf`。

### 2. 内存账：把"最坏情况"算成一个数

```sql
SELECT
  @@innodb_buffer_pool_size DIV 1048576                    AS buffer_pool_mb,
  @@innodb_buffer_pool_instances                           AS pool_instances,
  @@max_connections                                        AS max_conn,
  (@@sort_buffer_size + @@join_buffer_size
   + @@read_buffer_size + @@read_rnd_buffer_size) DIV 1024 AS per_conn_kb,
  @@max_connections * (@@sort_buffer_size + @@join_buffer_size
   + @@read_buffer_size + @@read_rnd_buffer_size) DIV 1048576 AS worst_conn_mb;
```

实测（默认配置、128 MB 池）：

```text
+----------------+----------------+----------+-------------+---------------+
| buffer_pool_mb | pool_instances | max_conn | per_conn_kb | worst_conn_mb |
+----------------+----------------+----------+-------------+---------------+
|            128 |              1 |      151 |         896 |           132 |
+----------------+----------------+----------+-------------+---------------+
```

默认配置下 132 MB 看着无害，但它随 `max_connections` 线性放大：把 `max_connections` 调到 5000，
`worst_conn_mb` 就是约 4400 MB。`worst_conn_mb` 远大于物理内存并不是 bug —— 它只是提醒：
**这个实例是靠连接池兜着的**，兜不住就会 OOM。

另一条实测更能说明"buffer pool 只是内存账的一块"：容器里 `mysqld` 是 PID 1，
跑完一轮建表与查询后 `grep VmRSS /proc/1/status` 是 **466408 kB**，而 buffer pool 只声明了
134217728 B（128 MiB）。差出来的部分可以用 `memory_summary_global_by_event_name` 拆开（实测 Top 项）：

```text
EVENT_NAME                                                        MiB      备注
memory/innodb/buf_buf_pool                                      130.88   137236480 B
memory/performance_schema/events_statements_summary_by_digest    40.28    42240000 B
memory/innodb/ut0link_buf                                        24.00
memory/innodb/log_buffer_memory                                  16.00
memory/performance_schema/events_statements_history_long         14.42
memory/mysys/KEY_CACHE                                            8.00
-----------
memory/performance_schema/* 合计                                218.76   229383592 B
```

⭐ 这个默认配置实例里最反直觉的一条：**performance_schema 自己的常驻内存（218.76 MiB）比 buffer pool（128 MiB）还大**。
它是在启动时按容量参数预分配的，跟你库里放了几行数据无关；单是一张 digest 表就 40 MiB
（`performance_schema_digests_size` 实测 10000，而当时表里只有 **6 行**摘要）。
这就是 [观测与诊断.md](观测与诊断.md) 里"先确认插桩开销再谈查询"的量化根据。

⚠️ 时序口径：RSS 随负载涨落 —— 同一容器重启后的两个时刻实测 398256 kB 与 466408 kB，
**只有"PS 常驻 > buffer pool"这个结构性结论是稳的**，绝对值必须按自己实例当下测。

### 3. 状态计数器：两次采样取差值

```bash
snap() {
  mysql -N -e "SHOW GLOBAL STATUS WHERE Variable_name IN
    ('Innodb_buffer_pool_read_requests','Innodb_buffer_pool_reads',
     'Innodb_buffer_pool_pages_dirty','Innodb_os_log_pending_writes',
     'Created_tmp_disk_tables','Opened_tables','Sort_merge_passes',
     'Com_commit','Innodb_buffer_pool_wait_free')"
}
snap > /tmp/mysql_status_a; sleep 2; snap > /tmp/mysql_status_b
paste /tmp/mysql_status_a /tmp/mysql_status_b \
  | awk '{printf "%-40s +%d / 2s\n", $1, $4-$2}'
```

⚠️ 计数器名单里的 `Innodb_data_waits` 在 8.0 **不存在**（实测 `SHOW GLOBAL STATUS WHERE Variable_name IN (...)`
返回的行里根本没有它，照抄会静默少一行）→ 换成 `Innodb_buffer_pool_wait_free`。

实测：因为用了 `mysql -N`（去表头、Tab 分隔），`paste` 后正好 4 列，`$4-$2` 就是差值。
两次采样之间跑了几条查询，真实输出（这次间隔取 2 秒）：

```text
Com_commit                               +0 / 2s
Created_tmp_disk_tables                  +0 / 2s
Innodb_buffer_pool_pages_dirty           +0 / 2s
Innodb_buffer_pool_read_requests         +3066 / 2s
Innodb_buffer_pool_reads                 +0 / 2s
Innodb_buffer_pool_wait_free             +0 / 2s
Innodb_os_log_pending_writes             +0 / 2s
Opened_tables                            +5 / 2s
Sort_merge_passes                        +0 / 2s
```

本机数据量太小（最大表 2500 行、全部在缓冲池里），所以物理读、临时表落盘、排序归并全是 0 ——
**这份输出只能证明写法通，不能用来证明"生产上这些指标不会涨"**（时序类数字按实例波动）。

### 4. 改一个动态项并持久化、回滚

```sql
SET GLOBAL innodb_io_capacity = 2000;    -- 立即生效，重启丢失
SET PERSIST  innodb_io_capacity = 2000;  -- 同时写入 mysqld-auto.cnf
RESET PERSIST innodb_io_capacity;        -- 撤销持久化项，但运行时值仍留着
```

实测：

```text
-- SET GLOBAL innodb_io_capacity = 2000 之后：@@innodb_io_capacity = 2000（当场生效，无需重启）
-- 取值边界在同一张 variables_info 表里，实测：
innodb_io_capacity        MIN=100                 MAX=4294967295
innodb_redo_log_capacity  MIN=8388608             MAX=549755813888
thread_cache_size         MIN=0                   MAX=16384
innodb_buffer_pool_size   MIN=5242880             MAX=9223372036854775807
sort_buffer_size          MIN=32768               MAX=18446744073709551615
```

把 `innodb_io_capacity` 从默认 200 调到 2000 是合法值，但正文 5.3 说过：**调的是你向 InnoDB 声明的盘能力，不是盘的真实能力**。
另外 `RESET PERSIST` 之后实测 `VARIABLE_SOURCE` 仍是 `DYNAMIC`、`@@值` 仍是 2000 ——
**"撤销持久化"不等于"撤销修改"**，值要改回去得再 `SET GLOBAL` 一次。

### 5. OS 侧先把干扰项排掉

```bash
cat /sys/block/nvme0n1/queue/scheduler      # 期望 [none]
swapon --show                               # 数据库主机上最好为空
cat /proc/$(pidof mysqld)/status | grep VmRSS   # 实际常驻内存 vs buffer pool
findmnt -no OPTIONS /data                   # 期望含 noatime
```

实测在 `mysql:8.0` 容器里只有第一行能跑通，其余三个命令**镜像里根本没装**（都报 `command not found`）
→ 容器环境的替代写法：

```bash
# 1) 有哪些块设备、当前调度器是什么（容器能看到宿主的全部设备）
for d in /sys/block/*/queue/scheduler; do echo "$d: $(cat $d)"; done
#    /sys/block/loop0/queue/scheduler: [none] mq-deadline kyber

# 2) 容器里 mysqld 就是 PID 1，直接读它
grep -E "VmRSS|VmHWM" /proc/1/status
#    VmHWM:     466408 kB   VmRSS:     466408 kB

# 3) 内存账要读 cgroup，别读 /proc/meminfo
cat /sys/fs/cgroup/memory.max       # 未限额时是 max
cat /sys/fs/cgroup/memory.current   # 实测 387846144（随时变，不是基线）
```

⚠️ 这里有个容易算错的点：容器里 `/proc/meminfo` 的 `MemTotal` 显示的是**宿主机内存**
（实测 6071564 kB，而容器并未限额、`memory.max` = `max`）。`innodb_dedicated_server` 这类"按物理内存自动算"
的参数在容器里判定的就是 `meminfo` 那份 → **第六节说的"独占整机"在容器环境下必须自己确认限额**。
实测调度器是 `[none] mq-deadline kyber`（当前选中 none），与第 2 节"SSD/NVMe 用 none"的期望一致。

## 延伸追问

- **`innodb_buffer_pool_size` 能热改吗？** → 能（`Dynamic=Yes`），8.0 按 chunk 逐步扩缩，
  扩容期间仍要留出真实内存；`innodb_buffer_pool_instances` **不能**热改，必须重启。
- **redo 太小会怎样？太大呢？** → 太小：被迫提前刷脏，出现周期性写尖峰与检查点等待；
  太大：刷脏更从容，但崩溃后要重放的日志更多。8.0.30 起 `innodb_redo_log_capacity` 可动态调，
  这条权衡才变成可以在线试错的事。
- **为什么 `sort_buffer_size` 不是越大越好？** → 它是**每连接（甚至每次排序）分配**的，
  调大等于放大最坏内存；只在单条语句出现 `Sort_merge_passes` 增长时，用 hint 或 session 值局部调。
- **`SET PERSIST` 和写 `my.cnf` 有什么区别？** → 持久化位置不同（`mysqld-auto.cnf` vs 配置文件），
  前者优先级更高，而且会记录是谁在什么时候改的；排查"参数为什么不是文件里写的值"时两处都要看。
- **`innodb_dedicated_server` 会覆盖我手动配的参数吗？** → 不会。显式写过的项以你写的为准，
  它只补没写的项；且只在启动时计算一次，设回 `DEFAULT` 也不会回到它的推导值。
- **调大 `max_connections` 有什么问题？** → 放大连接级内存的最坏上限、加剧上下文切换与锁争用，
  还把本该由连接池做的排队挪进 MySQL 内部。该做的是连接池上限 + 读池/代理排队。
- **SSD 上为什么保持 `innodb_flush_neighbors=0`？** → 相邻页合并是为机械磁头的顺序写设计的，
  闪存上"多写一页"只是多一份写放大，还会干扰设备自己的垃圾收集。
- **`table_open_cache` 默认到底是多少？** → 8.0 是 4000（5.7 才是 400）。
  照抄旧文章会把它白白调小一个数量级，表现是 `Opened_tables` 持续上涨。
- **云上实例参数改不动怎么办？** → 先列白名单再定容量方案：改不了的项（redo 下沉、刷脏策略）
  往往说明该用服务方的伸缩能力，而不是自己调参数。
