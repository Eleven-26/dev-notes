# 指标监控技术选型

> 指标（Metrics）是三大支柱里**成本最低、也最容易被基数打爆**的一个。本篇按「先定量级 → 再定采集模型 → 再选存储与长期化」的顺序展开：为什么一个 `user_id` 标签就能把 TSDB 内存吃光、Pull 与 Push 各自在什么场景下才是对的、五个候选怎么按「已有资产」分派，以及单机 Prometheus 的容量边界到了之后的三条扩容路。
>
> 内容整理自个人学习笔记。本篇只回答「指标放哪、怎么采、怎么控成本」，**不含导出器写法**（见 [手写Prometheus导出器.md](../../../../01-编程语言/go/可观测性/手写Prometheus导出器.md)）、**不含告警规则设计**（见 [可观测性选型对比.md](../可观测性选型对比.md) 第六节）、**不含时序引擎内部结构**（见 [时序数据库选型对比.md](../../../数据存储/时序数据库/时序数据库选型对比.md)）、**不含 Prometheus 自身的机制与 PromQL 求值**（见 [README.md](Prometheus/README.md) 那一册，6 篇零件）。

## 一、指标的成本只有两个变量

`成本 = 活跃时间序列数 × 保留时长`。保留时长由磁盘预算直接决定，是显式的；**活跃序列数则是隐式的，它藏在标签设计里**，出事时表现为「Prometheus 内存暴涨 / 抓取超时 / 查询超时」，而不是一句「标签写错了」。

一条时间序列的唯一标识是「**指标名 + 全部标签值**」的组合：

```text
http_requests_total{service="order", method="GET", status="200", path="/api/v1/orders"}
http_requests_total{service="order", method="GET", status="200", path="/api/v1/users"}   ← 另一条序列
```

⭐ **标签的每一个不同取值都会乘出一条新序列**。`path` 写模板（`/api/v1/orders/{id}`）是 1 个取值，写成真实 URL 就是「有多少订单 ID 就有多少条序列」。同理 `user_id`、`request_id`、`session_id`、`trace_id` 一律不能进标签——**高基数维度属于日志与链路，不属于指标**。

| 维度 | 能不能当标签 | 原因 |
| --- | --- | --- |
| `service` / `cluster` / `region` | ✅ | 取值有限、稳定 |
| `method`、`status`（归一到 2xx/4xx/5xx） | ✅ | 取值可枚举 |
| `path`（**路由模板**） | ✅ | 必须先归一，不能是原始 URL |
| `status`（原始三位码全量） | ⚠️ | 取值 20~40 个，可接受但会乘倍数 |
| `user_id` / `order_id` / `request_id` | ❌ | 无上限，**基数爆炸** |
| `error_message`（原文） | ❌ | 同上，且含变量 |

⚠️ 基数代价不是线性的：序列数涨 1000 倍，内存与索引开销接近同倍涨，而非「多一点」。具体量级实测（12 条序列 725 B → 24000 条序列 1.6 MB 的文本暴露体积）见 [手写Prometheus导出器.md](../../../../01-编程语言/go/可观测性/手写Prometheus导出器.md) 的「基数代价」一节。

⭐ **上线前必须估的一个数**：`服务数 × 端点模板数 × 状态码档数 × 实例数`。这个数超过十万就要开始砍维度，超过百万就该考虑 VictoriaMetrics / Mimir 这类为高基数设计的后端（见第六节）。

## 二、采集模型：Pull 与 Push 不是风格问题

| 模型 | 谁发起 | 代表 | 天然语义 |
| --- | --- | --- | --- |
| **Pull（抓取）** | 监控端定时抓 `/metrics` | Prometheus、VM 的 `vmagent`、Collector 的 `prometheus` receiver | 抓不到 = `target down`，**「服务没了」本身成为一条可告警的信号** |
| **Push（推送）** | 应用主动上报 | Pushgateway、OTLP、StatsD、远端写入 | 上报方决定何时发；**「没上报」与「上报了 0」无法区分** |

⭐ **Pull 的关键收益是「缺席即信息」**：一个实例挂了，Prometheus 侧会出现 `up == 0`，这是天然的健康检查。Push 模型里服务直接死掉时，后端只会看到「数据不再更新」，需要额外的「多久没更新算异常」判据。

⚠️ **Pushgateway 不能当通用推送通道**：它被设计给**短期批处理任务**，且**不会自动清理**——任务名复用会让上一次的旧值一直挂着。三轮实测（含「推完不删，指标永久残留」的复现）见 [手写Prometheus导出器.md](../../../../01-编程语言/go/可观测性/手写Prometheus导出器.md) 的 Pushgateway 一节。

### 2.1 混合栈里的四条常见接法

真实系统往往两种模型都有，接法要选对，否则会多一层无意义的转发：

| 场景 | 接法 | 说明 |
| --- | --- | --- |
| 应用 + Prometheus | 应用暴露 `/metrics`，Prometheus 直接抓 | 最简单，别加中间层 |
| 应用已用 OTel SDK | SDK → **OTLP** → Collector → `prometheus` exporter 暴露 → Prometheus 抓 | ⭐ 指标的协议与链路/日志统一，代价是多一跳 |
| 已有 Prometheus，要长期化 | Prometheus `remote_write` → 远端（VM / Mimir / Thanos Receive） | 保留原有抓取配置，只改写入目标 |
| 云上托管服务 | 云监控 `exporter` / 云厂商 Prometheus 服务的采集器 | 维度被云产品定义，自定义空间小 |

⚠️ 一个容易误判的点：**Collector 的 `prometheus` exporter 只是「被动暴露」，它自己不抓任何东西**。要在 Collector 侧抓取，得配 `prometheus` receiver。方向搞反时症状是「Collector 起来了但面板没数据」，且日志里不报错。

## 三、五个候选的对比

| 方案 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- |
| **Prometheus** | 事实标准；Pull 模型 + 服务发现天然贴合 K8s；PromQL 表达力强；导出器（exporter）生态最全 | 单机存储，本地盘容量即保留期上限；**高基数容易打爆内存**；原生集群与长期存储方案弱 | 中小规模（单集群 < 数百万活跃序列）、K8s 环境 |
| **VictoriaMetrics** | 兼容 PromQL；写入与压缩效率高，**同等数据量下存储与内存显著低于 Prometheus**；原生支持水平扩展与多租户 | 与 Prometheus 存在细节行为差异（部分函数/边界）；生态比 Prometheus 小 | 高基数、大流量、需要长保留期或多集群汇聚；⭐ 深度选型与部署见 [README.md](../../../数据存储/时序数据库/VictoriaMetrics/README.md) |
| **InfluxDB** | 时序场景专精，写入性能好；Flux 查询灵活 | 2.x/3.x 版本之间协议与授权策略变动大，生态分裂；集群版收费 | IoT、自研采集链路、非 K8s 场景 |
| **Zabbix** | Agent 采集 + 阈值告警非常成熟；主机/网络设备监控覆盖广 | 容器与云原生适配差；指标模型不适合微服务维度 | 传统虚机、IDC、网络设备监控 |
| **云托管监控**（云监控 / CMS） | 免运维、与云产品指标直连 | 维度定制受限；按量计费；PromQL 兼容性参差 | 已整体上云的团队 |

⭐ **判断依据是「活跃时间序列数」**：单 Prometheus 实例的舒适区在**百万级以内**。超过就要么上 VictoriaMetrics / Thanos / Mimir，要么**先降基数**（见第一节）。

⚠️ **别用「能不能存」来选**：五个候选都能存指标。真正的分野是**查询语言**（PromQL / MetricsQL / Flux / SQL）、**扩容方式**（单机 / 分片 / 远程写）与**多租户**（是否要按团队隔离）。

## 四、按「起点资产」分派，而不是按功能表

选型最容易犯的错是拿功能表逐项打分，结果选了个和现有栈处处冲突的方案。按手上的资产分派更快也更准：

| 起点资产 | 推荐路线 | 理由 |
| --- | --- | --- |
| 已有 Prometheus + Grafana + 告警规则 | **保留 Prometheus，只加长期化**（remote_write → VM / Mimir / Thanos） | 抓取配置、告警规则、面板全部可复用，改动面最小 |
| 全新栈，规模不大（< 百万序列） | **Prometheus 单机 + 本地盘 + 明确保留期** | 组件最少；先把保留期与容量算清楚，别急着上集群 |
| 全新栈，但指标量预期很高（IoT / 多租户 SaaS） | **VictoriaMetrics 或 Mimir**，PromQL 兼容 | 一开始就避免「高基数打爆单机」的重构 |
| 已全面使用 OTel | **OTel SDK → Collector → prometheus exporter / remote write** | 三信号同一套 SDK 与 resource，缝合成本最低（见 [OpenTelemetry与关联分析.md](../OpenTelemetry/OpenTelemetry与关联分析.md)） |
| 以虚机 / 网络设备为主 | **Zabbix**（或云监控） | 微服务指标模型不适用，别硬套 |

⭐ **一条硬约束**：指标后端**不要为了「统一」而迁到日志/链路的存储上**，除非那个引擎真的擅长时序（如 ClickHouse 写指标可以，但 PromQL 语义要自己补）。指标查询是**高频、短窗口、大量小查询**，与日志的**低频、大范围扫描**是相反的负载。

## 五、指标类型：选错类型的代价在查询期才出现

| 类型 | 语义 | 典型用途 | 陷阱 |
| --- | --- | --- | --- |
| **Counter** | 只增不减的累计值 | 请求数、错误数、字节数 | 重启会归零，**查询必须用 `rate()` / `increase()`**，直接比较绝对值会看到「断崖」 |
| **Gauge** | 可增可减的瞬时值 | 连接数、队列深度、内存占用 | 不适合算速率；`rate()` 用在 Gauge 上无意义 |
| **Histogram** | 分桶计数 + 总和 + 总数 | 延迟分布、请求大小 | ⭐ **`le` 是累计上界**（`le="0.5"` 的计数已包含 `le="0.1"` 的），分位数要用 `histogram_quantile()` 在各桶间插值，**桶边界选错则 P99 精度失真** |
| **Summary** | 客户端算好的分位数 | 单实例分位数 | ⚠️ **分位数不可跨实例聚合**——多个实例的 P99 求平均没有意义 |

⭐ **延迟指标优先 Histogram 而不是 Summary**：Summary 的客户端分位数在聚合时失效，而微服务排障几乎总要「按服务/实例聚合后看 P99」。代价是 Histogram 的桶边界要提前定，且分位数是插值估算值。

⚠️ **别用平均值描述延迟**：`sum(rate(duration_sum)) / sum(rate(duration_count))` 得到的是平均延迟，一条 1% 的慢请求会被 99% 的快请求稀释掉——延迟必须看分位数。

## 六、单机到集群：三条扩容路

单 Prometheus 的边界到了之后，有且只有三种走法，选错会推翻架构：

| 路线 | 做法 | 适合 | 代价 |
| --- | --- | --- | --- |
| **垂直 / 降基数** | 砍标签、加 recording rule 预聚合、缩短保留期 | 序列数在百万级上下徘徊 | 最省钱；但排障维度会永久变少 |
| **远程写汇聚**（Thanos / Mimir / VM cluster） | Prometheus 只做抓取与近期查询，长期数据写远端 | 多集群、要全局视图与长保留 | 多一套组件；跨集群查询有额外延迟 |
| **联邦 / 分片** | 按业务或集群拆多个 Prometheus，上层再聚合 | 组织上本来就有边界（多团队多集群） | 全局查询要靠上层组件，别指望 `federation` 做重活 |

⭐ 判据顺序：**先降基数 → 再考虑远端写 → 最后才分片**。反过来的团队通常会在分片后才发现「每片的基数都还是错的」。

⚠️ **保留期不是越长越好**：指标的价值随时间快速衰减，超过 90 天的原始指标很少被查。要长周期趋势就**降采样**（recording rule 出 5m/1h 粒度）而不是原样留一年。

## 七、与另两个支柱的边界

指标最擅长回答「**整体是否健康、趋势是否异常**」，最不擅长回答「**这一次请求为什么慢**」。三条边界要守住：

| 想做的事 | 该用什么 | 为什么不用指标 |
| --- | --- | --- |
| 发现「错误率涨了」 | ✅ 指标 + 告警 | 低基数、可长期、聚合快 |
| 定位「哪一次请求慢、慢在哪一跳」 | 链路（[链路追踪选型对比.md](../链路追踪/链路追踪选型对比.md)） | 指标聚合掉了单次请求的身份 |
| 查明「这次请求的具体参数与异常栈」 | 日志（[日志系统选型对比.md](../日志系统/日志系统选型对比.md)） | 指标没有正文 |
| 从异常指标直接跳到具体链路 | ⭐ **exemplar**（指标样本挂 `trace_id`） | 这是指标通往链路的**唯一出口**，见 [OpenTelemetry与关联分析.md](../OpenTelemetry/OpenTelemetry与关联分析.md) 第五节 |

⚠️ **不要用日志算指标**：把 ERROR 日志行数当错误率，既贵（日志基数高、要解析）又不准（同一次错误可能打多行）。**监控用指标，排障用日志**。

## 八、延伸追问

- **为什么指标要严格控基数？** → 每个标签组合都算一条独立时间序列，`user_id` / `request_id` / 完整 URL 做标签会造成「基数爆炸」，直接打爆 TSDB 内存。标签只放**低基数**维度（服务名、接口路由模板、状态码），高基数维度放日志或链路。
- **Pull 模型在被监控端不可达时怎么办？** → 这正是 Pull 的优点：`up == 0` 本身就是一条信号。若网络策略不允许监控端主动连（如跨防火墙、边缘节点），才改用 Push（OTLP / remote write），并额外补一条「多久没数据算异常」的判据。
- **Prometheus 抓不到数据，怎么按顺序排查？** → ① `/metrics` 是否可达（`curl` 自证）→ ② target 状态是否 `UP`（`/targets` 页面看 last error）→ ③ 指标名是否被 `honor_labels` / relabel 改掉 → ④ 时间戳是否超范围（抓到的样本太旧会被丢弃）。⚠️ 第 ④ 条最隐蔽，表现是「target UP 但没数据」。
- **Histogram 的桶边界怎么定？** → 按 SLO 阈值定，而不是按等比数列。要监控「P99 < 200ms」，就必须有 `le="0.2"` 这个桶，否则 `histogram_quantile` 只能在相邻桶间插值，误差不可控。
- **指标要不要带 `trace_id`？** → ❌ 绝对不能进标签（基数爆炸）。要关联就用 **exemplar**：样本外挂一个 `trace_id`，不增加序列数。
- **recording rule 和降采样有什么区别？** → recording rule 是**预计算**（把复杂 PromQL 算成新指标，查询更快，但序列数可能变多）；降采样是**降低时间精度**（长期存储省空间）。两者常一起用：先 recording rule 出 1m 粒度，长期层再降到 5m / 1h。
