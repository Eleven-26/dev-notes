# 日志查询语言与排障方法论

> 覆盖：查日志的能力上限由**索引模型**决定，语法只是外壳——同一句「按关键词找日志」，在 ES 上走倒排索引（毫秒），在 Loki 上是暴力扫描（与范围成正比）。本篇用本机 ES 8.19 与 Loki 3.5 的对照读数说明三件事：`term` 与 `match` 为什么差 20 倍、`wildcard` 为什么匹配不到你以为的内容、以及从告警到单条日志的四段路径每一步该在哪一层收窄。
>
> 不覆盖：索引结构与存储调优见 [Elasticsearch_ILM与调优.md](../后端运维/Elasticsearch_ILM与调优.md) 与 [Loki_存储架构与调优.md](../后端运维/Loki_存储架构与调优.md)；选哪个后端见 [日志系统选型对比.md](../日志系统选型对比.md)；字段该长什么样见 [应用侧日志规范与SDK设计.md](../治理与规范/应用侧日志规范与SDK设计.md)。
>
> 内容整理自个人学习笔记。实测环境 Elasticsearch **8.19.0**（300 条数据集，`level` / `service` / `user_id` 为 keyword，`message` 为 text）+ Loki **3.5.0**，全部读数来自本轮容器实跑，口径见第九节。

## 一、一句话定位：查得快不快，取决于「第一步能排除多少」

**本节要点**：所有日志系统的查询都分两步——**缩小范围**与**在范围内找**。ES 靠倒排索引同时做两件事；Loki 只能靠标签做第一步、靠扫描做第二步。语法差异都是表象，**「第一步能把范围压到多小」才是决定耗时的那个变量**。

| 系统 | 第一步（缩小范围） | 第二步（范围内找） | 典型耗时来源 |
| --- | --- | --- | --- |
| Elasticsearch | 倒排索引（任意字段） | 索引定位到文档 | 查询复杂度、聚合、页数 |
| Loki | 标签索引（仅标签） | **顺序扫描 + 解压 chunk** | 时间窗 × 命中 chunk 数 |
| ClickHouse | 主键/分区裁剪 + 跳数索引 | 列扫描 + 向量化 | 扫描的列数与行数 |

⭐ 一条判据：**「先问这个查询在第一步能不能排除 99% 的数据」**。能，就是毫秒级；不能，就取决于数据量——跟语法写得多漂亮无关。

## 二、核心概念：三种索引模型与四种语言

**本节要点**：同一套排障思路落到不同后端，写法差别很大，因为它们对「字段」的理解不同。

| 模型 | 代表 | 字段是什么 | 全文搜索 | 聚合 |
| --- | --- | --- | --- | --- |
| 倒排索引 | ES / OpenSearch | 强类型（mapping），text 会分词 | 原生支持 | 强（aggs） |
| 标签 + 扫描 | Loki | 只有标签是「字段」，正文是字符串 | 靠 `|~` 正则/`|=` 子串 | 只能先聚合再解析 |
| 列式 + SQL | ClickHouse | 表结构，按列存 | 靠 `tokenbf` / `ngrambf` 索引或 `LIKE` | 强（SQL） |

| 语言 | 用在哪 | 最小示例 |
| --- | --- | --- |
| **DSL**（JSON） | ES 原生 | `{"query":{"term":{"level":"error"}}}` |
| **KQL / Lucene** | Kibana 查询栏 | `level:error and service:"svc-a"` |
| **LogQL** | Loki / Grafana | `{service="svc-a"} |= "error"` |
| **SQL** | ClickHouse / 部分云日志 | `SELECT * FROM logs WHERE level='error'` |

⚠️ KQL 与 DSL **不是一一对应**：KQL 的 `field:value` 默认走 `match`（分词），想精确匹配要写 `field.keyword:value` 或 `field:"value"`。这层隐式转换是「Kibana 里查得到、代码里查不到」的常见原因。

## 三、整体架构：四段排障路径

![定服务、定时间窗、定类型、定单条四段并排，下面用依次变矮的色块标出每一段之后还剩多少数据](images/从告警到单条日志的四段收窄.svg)

四段的收窄顺序是固定的，**跳步会浪费大量时间**：

| 段 | 目标 | 用什么收窄 | 收窄后的量级 |
| --- | --- | --- | --- |
| 1 定服务 | 哪个服务出问题 | 指标（错误率、延迟） | 1 个服务 |
| 2 定时间窗 | 故障什么时候开始 | 告警时间 ± 前后 10 分钟 | 分钟级窗口 |
| 3 定类型 | 什么错误 | 标签/级别 + 关键词 | 几十~几百条 |
| 4 定单条 | 具体哪个请求 | `trace_id` / `user_id` | 1 条 |

⭐ 第 1 段不要用日志做：**「哪个服务出问题」用指标判断比用日志快一个数量级**。日志适合回答「为什么」，不适合回答「是哪」——这是把日志当指标用，成本最高。

## 四、部署：四类查询的最小写法

| 需求 | ES DSL | Loki LogQL |
| --- | --- | --- |
| 按枚举过滤 | `{"term":{"level":"error"}}` | `{level="error"}`（需 level 是标签） |
| 按关键词 | `{"match":{"message":"timeout"}}` | `{service="svc-a"} \|= "timeout"` |
| 按时间窗 | `{"range":{"@timestamp":{"gte":"now-15m"}}}` | `query_range?start=...&end=...` |
| 按 trace | `{"term":{"trace_id":"4bf9..."}}` | `{trace_id="4bf9..."}` 或 `\|= "4bf9..."` |
| 计数 | `aggs` / `_count` | `count_over_time({...}[5m])` |

⚠️ 最后一行的差异值得强调：**Loki 的日志查询必须带时间范围**，ES 的 `_search` 不必。本机把日志查询打到 Loki 的即时查询接口，直接得到：

```text
400  log queries are not supported as an instant query type,
     please change your query to a range query type
```

## 五、使用一：ES 的三种查询形态与代价

**本节要点**：`term` / `match` / `wildcard` 三者在「查什么」上完全不同——`term` 查的是**分词后的词条**，`match` 才会先分析再查，`wildcard` 也只作用于词条。搞混这三者的后果是「明明有这条日志却查不到」。

本机 300 条数据集（`message` 形如 `request handled path=/api/v1/orders/42 status=200`）：

| 查询 | 命中 | 耗时 |
| --- | --- | --- |
| `term level=ERROR`（keyword 字段） | 100 | 6 ms |
| `term message=orders`（text，分词后命中） | 300 | 11 ms |
| `term message="path=/api/v1/orders/42"`（整串） | **0** | 6 ms |
| `match message="path=/api/v1/orders/42"`（整串） | 300 | **144 ms** |
| `match_phrase message="request handled"` | 300 | 13 ms |
| `match_phrase message="handled request"`（顺序颠倒） | **0** | 82 ms |
| `wildcard message="*orders/42*"` | **0** | 79 ms |
| `prefix message=orders` | 300 | 63 ms |
| `term message_kw="path=/api/v1/orders/42"`（keyword 但 `index:false`） | **0** | 21 ms |

四条能直接用的结论：

1. **`term` 查 `text` 字段的「整串」必然 0 命中**——因为 `path=/api/v1/orders/42` 被分词成 `path`、`api`、`v1`、`orders`、`42` 等多个词条，没有任何一个词条等于整串。要精确匹配整串，字段必须是 `keyword`。
2. **`match` 比 `term` 慢 20 倍以上**（144 ms vs 6 ms）：因为 `match` 每次都要跑分析器。查询栏里随手写的都是 `match`，所以「Kibana 慢」往往不是集群慢。
3. **`match_phrase` 有顺序语义**：`request handled` 命中 300，`handled request` 命中 0。用错会静默查不到。
4. **`wildcard` 匹配的是词条，不是原文**：`*orders/42*` 期望匹配原文里的 `orders/42`，但分词后不存在这个词条，所以 0 命中；`wildcard` 还绕不过索引，`*` 开头时退化成全扫（79 ms，比 `term` 慢 13 倍）。

⚠️ 第 9 行那个坑值得单独记：**`keyword` 类型但 `"index": false` 的字段永远搜不到**。它常出现在「为了节省空间把 message 的 keyword 副本设成不索引」的配置里——字段存在、`_source` 里看得到，但任何查询都命中 0。

### 5.1 `track_total_hits` 的隐性成本

| 查询 | 耗时 |
| --- | --- |
| 默认（`track_total_hits` 上限 10 000） | 4 ms |
| `track_total_hits: true`（精确计数） | 20 ms |

**默认返回的 `hits.total.value` 可能是「≥10000」的下界**（`relation: gte`）。要做精确统计（比如「错误日志到底多少条」），必须显式开 `true`，代价是 5 倍耗时。

## 六、使用二：LogQL 的两段式——选择器 + 管道

**本节要点**：LogQL 的结构永远是 `{标签选择器} | 管道`。**花括号里只能写标签**（走索引），管道里才是正文过滤（走扫描）。把正文条件写进花括号是新手最常犯的错。

| 写法 | 走哪一步 | 本机读数 |
| --- | --- | --- |
| `{service="svc-a"}` | 索引 | 2 个 stream / 100 行 |
| `{service="svc-a"} \|= "error"` | 索引 + 扫描 | 2 个 stream / 20 行 |
| `{env="lab"} \|~ "status=5.."` | 索引 + 正则扫描 | 返回 400（写法见 6.2） |
| `sum by (service) (count_over_time({env="lab"}[1h]))` | 索引 + 计数，不取正文 | 5 个 service / 合计 10 200 行 |

### 6.1 四个管道操作符

| 操作符 | 含义 | 注意 |
| --- | --- | --- |
| `\|=` | 包含子串 | 最快，优先用 |
| `!=` | 不包含 | 同上 |
| `\|~` | 正则匹配 | 比 `\|=` 慢，正则别写太宽 |
| `\| json` / `\| logfmt` | 解析正文成字段 | 解析失败的行会被**丢掉**，不是报错 |

⭐ `| json` 那条是静默的：Loki 不会告诉你「有 30% 的行解析失败」，它们直接不出现在结果里。所以用 `| json` 之前先用 `|= "{"` 粗筛一遍，看量对不对。

### 6.2 语法错误的位置很准，但坑在花括号

```text
count_over_time("foo"[5m])
400  parse error at line 1, col 17: syntax error: unexpected STRING, expecting NUMBER or { or (
```

报错说「期望 `{` 或 `(`」，意思是**日志选择器必须是花括号包起来的标签集**，`("foo")` 不是合法选择器。这类报错给了行列号，比 ES 的 DSL 解析错误好定位。

### 6.3 `limit` 是总行数，不是每个 stream

本机 `limit=5000` 查 `{env="lab"}`，四个 stream 共 6 500 行只返回 5 000 行，于是「`svc-bulk` 的分片各只有 500 行」看起来像数据缺失。**要真实条数用 `count_over_time`，不要数返回行数。**

## 七、使用三：从告警到单条日志

**本节要点**：四段路径里，前三段都是在「排除」，只有第四段是「定位」。每一段用错工具，时间就花在下游。

### 7.1 每段的动作与判据

| 段 | 动作 | 判据（做到什么程度算够） |
| --- | --- | --- |
| 1 定服务 | 看指标：错误率、P99、QPS | 能指出一个服务或一个依赖 |
| 2 定时间窗 | 看告警时间与指标拐点 | 窗口 ≤ 30 分钟（再大就是扫描） |
| 3 定类型 | 按 `level` + 关键词过滤 | 结果 ≤ 200 条（再多要加条件） |
| 4 定单条 | 拿 `trace_id` 反查全链路 | 找到 1 条含完整上下文的日志 |

### 7.2 第 4 段的两种做法

| 做法 | 前提 | 速度 |
| --- | --- | --- |
| 日志里有 `trace_id` 字段且**索引**了 | 字段是 keyword / 是 Loki 标签 | 快（索引定位） |
| 日志正文里有 `trace_id`，靠 `\|=` 扫 | 无 | 慢（扫描 + 无索引） |

⭐ 这就是「字段设计决定查询能力」的具体体现：`trace_id` 放在正文里，Loki 上只能扫；放进标签，又因为基数太高而不可行。**Loki 的折中是把 `trace_id` 放 structured metadata，ES 的折中是单独建 `trace_id` keyword 字段。**

### 7.3 一条实用的收窄口诀

> **先用标签圈服务与时间，再用级别去噪，再用关键词定位，最后用 ID 收口。**

反过来（先搜 ID、再补时间窗）在 Loki 上代价极高，因为没时间窗就扫全量。

## 八、验证与排查：查不到的五种原因

**本节要点**：查不到时，先判断「是没打、没发、还是查询写错」——这三类的排查路径完全不同，混着查会浪费大量时间。

| 原因 | 怎么快速判别 | 典型现象 |
| --- | --- | --- |
| ① 日志根本没打 | 换一个肯定有数据的条件（如 `*` 或 `{env="prod"}`） | 什么都查不到 |
| ② 打了但没被采集 | 看采集器自己的指标/日志 | 其他服务有、这个服务没有 |
| ③ 采集了但没写进后端 | 看后端写入指标、429/400 计数 | 后端有别的索引在涨，这个没有 |
| ④ 写进去了但查询条件写错 | 放宽条件逐步还原（去掉 `term` 换 `match`） | 换个写法就有了 |
| ⑤ 写进去了但被采样/丢弃 | 对比采样率与总量 | 有日志但条数明显偏少 |

⭐ 两个高频具体错误：

1. **字段类型不匹配**：`term` 查 `text` 字段（第五节第 3 行）、`term` 查 `index:false` 的字段（第 9 行）——两者都是「命中 0 且不报错」。
2. **字段名大小写/拼写漂移**：`trace_id` vs `traceId` vs `tid`。这类问题只能靠一次全量字段统计发现（规范篇第八节）。

## 延伸追问

**Q：为什么 `match` 比 `term` 慢这么多，日常查询不都用 `match` 吗？**

`match` 要对查询串跑一遍分析器（分词、小写化、去停用词），再拿每个词条去查倒排索引；`term` 只查一次。数据量小的时候差距是「固定开销」，数据量大时 `match` 的多词条查询还要做评分合并。**实践上的折中是**：已知值精确匹配（枚举、ID、状态码）一律用 `term`；只有「用户自由输入的搜索框」才用 `match`。

**Q：Loki 上要按 `trace_id` 精确查，最佳实践是什么？**

两条路，取决于你的 Loki 版本：**3.x 用 structured metadata**（`structured_metadata` 字段，可过滤不进索引，基数不受限）；**更早版本只能接受扫描**，此时正确做法是「先用时间窗 + 服务标签把范围压到分钟级，再 `|=` 扫」。⚠️ 千万不要把 `trace_id` 放进标签——stream 数会等于日志条数。

**Q：`_count` 和 `size:0` 的 `_search` 有区别吗？**

`_count` 只返回数量、不做评分与取文档，通常更快；`size:0` 的 `_search` 仍会走完整的查询执行但跳过取回阶段，还能同时返回 `aggs`。**要数量用 `_count`，要数量 + 聚合用 `size:0` + `aggs`**。

**Q：排障时最该先看的三个字段是什么？**

`timestamp`（对齐时间窗）、`level`（去噪）、`trace_id`（收口到一次请求）。三个字段的可用性决定了排障速度——这也是为什么规范篇把它们列进保留字段表，而把「业务自定义字段」推向 `biz_*` 前缀。
