## 一、「网关」这个词可能指五种东西？

**本节要点**：选型前先把名词对齐——同一个「网关」在五个不同层次上被使用，选错了层就会拿
Kong 的插件清单去比 Nginx 的性能数字。

| 层 | 是什么 | 代表 | 流量方向 | 典型职责 |
|---|---|---|---|---|
| **① 流量网关** | 最外层的入口，通常就是 Nginx | Nginx / OpenResty | 南北向 | TLS 卸载、静态资源、L4/L7 转发、WAF、IP 黑白名单 |
| **② API 网关** | 面向 API 的治理层 | APISIX / Kong / Tyk / KrakenD | 南北向 | 认证鉴权、限流熔断、路由、灰度、协议转换、插件 |
| **③ 微服务网关** | 与注册中心集成的业务入口 | Spring Cloud Gateway / Kratos 网关 / go-zero | 南北向 | 服务发现、**按服务名路由**、负载均衡、聚合 |
| **④ K8s 入口网关** | 集群的入口抽象 | Ingress / Gateway API / Traefik | 南北向 | 把集群外的流量导到 Service |
| **⑤ 服务网格数据面** | 每个 Pod 旁边的代理 | Envoy（Istio）/ Linkerd / Cilium | **东西向** | mTLS、重试、熔断、遥测 |

**怎么快速判断说的是哪一层**，看两个问题就够了：

1. **流量从哪来？** 从公网/客户端进来 → ①~④；服务与服务之间 → ⑤。
2. **要不要「按服务名」路由？** 要（`/api/order` → `order-service`）→ ③；只是转发到固定上游 → ①。

> ⚠️ **最高频的混淆**：把 ⑤ 当成 ④ 的替代。**网关管入口、网格管内部**，两者不是同一件事，
> 可以同时存在，也可以都不要（单体的 K8s 集群既不需要 API 网关也不需要网格）。

## 二、选型先看这六个维度？

**本节要点**：六个维度里**只有前两个是硬约束**（决定「能不能用」），后四个是「用起来顺不顺」。

| 维度 | 要问的问题 | 为什么关键 |
|---|---|---|
| **① 动态路由** | 改一条路由要不要 **reload / 重启**？ | 决定「发布路由」的运维方式；高频变更场景下这是**决定性**的（见 3.2） |
| **② 插件 / 扩展方式** | 要的认证、限流、灰度能力**是否内置**？ | 缺什么就得自己写 Lua / 自己维护分叉；插件生态决定**要不要养一个平台团队** |
| ③ 性能与延迟 | 单实例能扛多少 QPS、加几毫秒延迟 | 绝大多数业务**到不了这个量级**，别把性能当第一判据 |
| ④ 运维成本 | 依赖哪些外部存储（etcd / PG）？几个组件？ | 多一个依赖就多一套备份、监控、升级、故障预案 |
| ⑤ 人才与资料 | 团队熟不熟？出问题能不能查到中文资料 | 决定了**线上出事时多快能定位**，比功能表重要 |
| ⑥ 语言栈契合 | 有没有本语言的 SDK / 控制面 | Go/Java/PHP 混合团队要的是「谁都能接」 |

⭐ **一条经验**：**先按 ① 和 ② 筛掉不合适的，剩下的再比性能**。
反过来（先看性能数字选型）最容易选的坑是——选了一个性能最好但**改路由要重启**的网关，
最后被迫在上层再写一套「配置下发 + 重启编排」，运维复杂度反而更高。

## 三、流量网关的能力边界在哪里？（Nginx / OpenResty）

**本节要点**：这一节要回答的是「**Nginx 到底够不够用**」——
下面四组实测分别对应四个高频疑问：reload 会掉流量吗、不改配置能不能换后端、
灰度能做到什么程度、上游挂了自动摘吗。

### 3.1 先明确：这一层的能力与写法

Nginx 的定位是**最外层入口**，写法（location 匹配、`proxy_pass` 斜杠、`rewrite` 的 flag）
见 [OpenResty.md](OpenResty.md) 第四节的实测，这里不重复。

| 能力 | Nginx 原生 | OpenResty（加 Lua） |
|---|---|---|
| TLS 卸载、静态、L4/L7 转发 | ✅ | ✅ |
| 路由（按 path / host / header） | ✅ `location` / `map` | ✅ + 可从外部读 |
| 灰度分流 | ✅ `split_clients` / `map`（见 3.4） | ✅ 可读 Redis / 注册中心 |
| 限流 | ✅ `limit_req` / `limit_conn` | ✅ `resty.limit.req`（支持突发与跨机共享） |
| 认证鉴权（JWT / 签名） | ❌ 需自己写 Lua 或上游做 | ✅ `access_by_lua*` |
| 上游健康检查 | ⚠️ **只有被动式**（见 3.5） | ✅ 可主动探测 + 动态摘除 |
| 动态改路由 / 上游 | ⚠️ 改配置要 reload（见 3.2）；**DNS 方案可绕开**（见 3.3） | ✅ `balancer_by_lua*` 完全动态 |

### 3.2 reload 到底掉不掉流量？（本机实测）

结论先给：**短连接零失败，但长连接会被断。**

**实验设计**：一条线程每 10ms 发一个请求到 `location = /ping`（纯内存返回，排除后端干扰），
持续 6 秒，在第 3 秒执行 `nginx -s reload`。

```text
$ nginx -s reload                      # 命令本身耗时 48 ms
=== 请求结果 ===
reload 之前： 134 个请求，成功 134（100.0%）
reload 之后： 137 个请求，成功 137（100.0%）
非 200 的请求：无

=== 进程变化（pid 文件给出 master pid）===
reload 前：master 8288 + worker 16296
reload 后：master 8288 + worker 9628     ← master 不变，worker 全部换新
```

⭐ **两条结论**：

1. **短连接完全平滑**：「reload 会掉流量」是**误解**——老 worker 会先把手上正在处理的请求做完
   （优雅退出），新请求由新 worker 接，所以**成功率不受影响**。
2. **代价是「全量替换」而不是「增量更新」**：worker 全部换新，**配置里改了一个字符，也是整体重建**。

**但长连接是例外**——同一台机器上另做一组对照，用同一条 keep-alive 连接：

```text
对照组（不 reload，同一连接连发 5 次）：[200, 200, 200, 200, 200]

实验组（同一连接：发 1 次 → reload → 再发 1 次，重复 3 轮）：
  第 1 轮：reload 前 200 → reload(rc=0) → reload 后 ERR:ConnectionAbortedError
  第 2 轮：reload 前 200 → reload(rc=0) → reload 后 ERR:ConnectionAbortedError
  第 3 轮：reload 前 200 → reload(rc=0) → reload 后 ERR:ConnectionAbortedError
```

⚠️ **这是 reload 真正的隐形代价**：reload 时老 worker 退出，**它持有的 keep-alive 连接被一起断掉**。

> 对短连接的浏览器无感（每次新建连接），但**连接池化的调用方会正面撞上**：
> Go 的 `http.Client`（默认 keep-alive 池）、Java `HttpClient`、gRPC 长连接、以及所有长轮询 /
> WebSocket 连接。表现是**偶发的 `connection reset`**，而这类故障最难查——因为它只在发布时刻出现。
>
> 所以「reload 平滑」这句话要加限定：**对无状态短连接平滑，对长连接不平滑**。
> 配置里可以用 `worker_shutdown_timeout` 给老 worker 一个宽限期，但**无法避免**——老 worker 终究要退出。

### 3.3 不改配置能不能换后端？（本机实测）

这直接回答「**不上 API 网关，动态路由能做到什么程度**」。

**实验 A：变量 `proxy_pass` + `map`——按请求维度切后端（配置一行不动）**

```nginx
map $http_x_stage $stage_backend {
    "beta"   "127.0.0.1:18082";     # 内测用户
    default  "127.0.0.1:18081";     # 普通用户
}
location /dyn/ { proxy_pass http://$stage_backend/; }    # ⚠️ 关键：proxy_pass 里带变量
```

```text
X-Stage: (无)   → 200  后端 = A-18081
X-Stage: beta   → 200  后端 = B-18082
```

**实验 B：`resolver` + 域名——改 DNS 就能换 IP（配置与 reload 都不用）**

```nginx
resolver 127.0.0.1:15353 valid=2s ipv6=off;    # 本机自建的极简 DNS（只回 A 记录）
location /svc/ {
    set $svc_host "svc.test";
    proxy_pass http://$svc_host:18085/;         # 带变量 → 运行时解析，而不是启动时解析一次
}
```

在**不改 nginx 配置、不执行任何 reload** 的前提下，只改 DNS 的返回：

```text
DNS 返回 127.0.0.1  → 请求 /svc/ 实际落到 SVC-A-127.0.0.1    ✅
DNS 返回 127.0.0.2  → 请求 /svc/ 实际落到 SVC-B-127.0.0.2    ✅
DNS 返回 127.0.0.1  → 请求 /svc/ 实际落到 SVC-A-127.0.0.1    ✅
```

⭐ **这就是「用 DNS 做服务发现」**：后端扩容、迁移、故障切换，只要改 DNS 记录，
`valid=` 到期后 nginx 自动跟着换。**代价是**：切换有 TTL 延迟（实测要等到缓存过期才生效）、
依赖 DNS 的可靠性、且**只能表达「一个域名对应一组 IP」，没有权重、没有按方法/参数的细粒度路由**。

| 需求 | Nginx 原生能做到吗 |
|---|---|
| 按请求头 / 参数 / 权重分流 | ✅ `map` + 变量 `proxy_pass` |
| 后端 IP 变了自动跟随 | ✅ `resolver` + 变量 `proxy_pass`（受 TTL 限制） |
| **upstream 成员动态增删** | ❌ **必须 reload**（`upstream` 块是启动期结构） |
| 按服务名路由 + 服务实例健康状态感知 | ❌ 需要 ③ 微服务网关或 ② API 网关 |

### 3.4 灰度分流能做到什么程度？（本机实测）

**按比例灰度**用 `split_clients`（对指定字符串做哈希）：

```nginx
split_clients "${arg_uid}gz-seed" $variant {
    30%     "gray";
    *       "stable";
}
```

```text
=== 1000 个不同 uid 的实际分布 ===
A-18081:  711 个   71.1%      ← 稳定组
B-18082:  289 个   28.9%      ← 灰度组（配置声明 30%）
```

⭐ 比「比例准不准」更重要的是 **`split_clients` 是确定性哈希、不是随机数**：

```text
uid=user-3    连续 5 次 → ['A', 'A', 'A', 'A', 'A']   幂等：✅ 始终同一组
uid=user-7    连续 5 次 → ['A', 'A', 'A', 'A', 'A']   幂等：✅ 始终同一组
uid=user-42   连续 5 次 → ['A', 'A', 'A', 'A', 'A']   幂等：✅ 始终同一组
```

> 这正是灰度最需要、也最容易做错的点：**同一个用户不能一会儿走新版本、一会儿走旧版本**
> （否则会话状态、缓存、埋点全乱）。用「随机数」做灰度就会踩这个坑，`split_clients` 不会。
>
> 加上 `map`（按 header / uid 白名单）就能组合出**「内部员工全量 + 外部用户 30%」**这类常见策略。

### 3.5 上游挂了会自动摘除吗？（本机实测）

**会，但只能「被动发现」**——必须**有请求打到故障节点**才知道它挂了。

**实验**：`upstream` 里放一个健康节点（18081）和一个无人监听的端口（18099），连发 8 个请求：

```nginx
upstream pool_dead {
    server 127.0.0.1:18081 max_fails=2 fail_timeout=5s;
    server 127.0.0.1:18099;                    # 无人监听
}
location /failover/ {
    proxy_next_upstream error timeout;         # ⭐ 失败后换下一个上游重试
    proxy_connect_timeout 1s;
    proxy_pass http://pool_dead/;
}
```

access_log（自定义格式记了 `$upstream_addr` 与 `$upstream_status`，这是观测重试的**唯一可靠手段**）：

```text
# 第 1 个请求：轮询正好选中健康节点
"GET /failover/" 200 upstream=127.0.0.1:18081                          ustatus=200        utime=0.000  rt=0.000

# 第 2 个请求：⭐ 打到死节点 → connect 超时(1s) → 自动重试健康节点
"GET /failover/" 200 upstream=127.0.0.1:18099, 127.0.0.1:18081        ustatus=504, 200   utime=1.005, 0.005  rt=1.010

# 第 3~8 个请求：死节点已被摘除（fail_timeout=10s 内不再尝试）
"GET /failover/" 200 upstream=127.0.0.1:18081                          ustatus=200        utime=0.001  rt=0.001
```

⭐ **三条结论**：

1. **客户端完全无感**：8 个请求全是 200（`proxy_next_upstream` 起了作用）；
2. **但代价是延迟**：踩到死节点那次 `rt=1.010s`——**整整多等了 `proxy_connect_timeout` 那一秒**。
   这是被动健康检查的固有成本：**第一个踩坑的用户必须等超时**；
3. **摘除是「时间窗」而非「探测」**：`max_fails=2 fail_timeout=5s` 意思是「5 秒窗口内失败 2 次就摘除」，
   过了窗口再试。**没有主动探测**，所以节点恢复了也不会立刻被重新启用（要等下一个请求撞上来）。

> ⚠️ **这就是 nginx 与 API 网关 / 网格的关键差距**：APISIX、Kong、Envoy 都有**主动健康检查**
> （定期探测 `GET /healthz`），节点挂掉和恢复都是**秒级、无用户代价**的；
> nginx 社区版**只有被动式**，主动探测是 Nginx Plus（商业版）或 OpenResty（自己写 Lua）的能力。
> 涉及「用户请求才知道节点挂了」的场景，这是选型时必须拿到台面上的一条。

### 3.6 小结：Nginx 够用到什么程度？

| 你的场景 | 判断 |
|---|---|
| 静态资源 + 少量固定上游 + 低频变更 | ✅ **Nginx 足够**，加 Lua/OpenResty 还能覆盖鉴权 |
| 路由变更不频繁（一天几次），能接受 reload | ✅ 够用；注意**长连接客户端会在发布时刻断连**（3.2） |
| 后端实例频繁扩缩容，但可以接受 DNS TTL 延迟 | ✅ 用 `resolver` + 变量 `proxy_pass`（3.3） |
| **路由需要秒级生效、且要按服务实例健康状态选路** | ❌ **上 API 网关**（第四节） |
| 需要 JWT 认证、按租户限流、多插件组合 | ⚠️ OpenResty 能写，但**维护成本可能超过直接上 APISIX** |
| 上游节点故障要「秒级摘除 + 秒级恢复」 | ❌ 社区版 nginx 做不到（3.5），需 API 网关或网格 |

## 四、南北向第二层：API 网关怎么选？

**本节要点**：这一层买的是「**动态配置 + 插件生态 + 可观测**」三件事，
选型的核心是「**谁来做配置的下发与审计**」，而不是「谁的性能高几个百分点」。

### 4.1 四款主流方案

| 方案 | 配置存哪 | 改路由要 reload 吗 | 插件生态 | 一句话定位 |
|---|---|---|---|---|
| **Apache APISIX** | **etcd** | ❌ **不用**，watch 到即生效 | 丰富（认证/限流/灰度/可观测/**WAF**） | 国内社区活跃，**动态路由与插件覆盖度最好的开源选择** |
| **Kong** | PostgreSQL / Cassandra / **DB-less 模式** | DB 模式不用；DB-less 需重载 | **最大**（企业版 + 商业支持最完善） | 国际化团队、要成熟商业支持 |
| **Tyk** | Redis / MongoDB | 不用 | 中（Dashboard 与开发者门户是亮点） | 需要**完整 API 管理平台**（含文档门户、密钥自助） |
| **KrakenD** | 配置文件 | 需重载 | 少（**聚合是强项**） | 只做「**API 聚合/编排**」这一件事，轻量 |

**共同点**（对比第三节的 nginx 原生）：**配置与数据面分离**——配置存在 etcd / DB，
数据面 watch 变更，**不动进程、不掉连接**。这恰好补掉了 3.2 与 3.5 的两个短板。

**取舍要点**：

- **要动态路由 + 不想引入太多依赖** → APISIX（只依赖 etcd，1 个组件）；
- **要商业支持 / 已有 Kong 经验** → Kong（⚠️ 但 Postgres 是**必须运维好的**组件）；
- **只是想把多个后端聚合成一个接口** → KrakenD（别为聚合上一个完整网关）；
- ⚠️ **同时被两个网关管理配置是灾难**：如果已有 OpenResty 手写路由，迁移要**先划清边界**
  （谁管哪些路由），否则排查问题时两边日志对不上。

### 4.2 选型必须问清楚的四个问题

| 问题 | 为什么问 |
|---|---|
| 配置变更**谁能改**？有没有**审计与回滚**？ | 网关是全站入口，一次错误路由 = 全站不可用；**没有审计的网关是运维黑洞** |
| 配置变更的**生效时间**？ | etcd watch 是秒级；如果实现是「轮询 + reload」，那和 nginx 没差别 |
| 挂了之后**降级策略**是什么？ | 网关自己挂了，整个集群就不可达——有没有多实例 + 配置中心高可用 |
| 插件是**进程内**还是**跨进程**？（如限流用 Redis） | 跨进程插件会引入一次网络往返，**把网关的延迟优势吃掉** |

## 五、微服务网关怎么选？

**本节要点**：微服务网关与 API 网关的区别在**「路由目标从哪来」**——
API 网关的路由是**人工配置**的，微服务网关的路由是**从注册中心自动发现**的。

| 方案 | 语言栈 | 路由来源 | 适合 |
|---|---|---|---|
| **Spring Cloud Gateway** | Java | Nacos / Eureka / Consul | **Java 微服务体系的标准入口**（基于 Reactor，性能取决于调优） |
| **Zuul 1** | Java | 同上 | ⚠️ **存量**（阻塞式模型），新项目不要选 |
| **Kratos 网关** | Go | etcd 注册中心 | Go + Kratos 体系的标配（见 [../../01-编程语言/go/工程实践/Kratos框架.md](../../01-编程语言/go/工程实践/Kratos框架.md)） |
| **go-zero / KubeSphere 等** | Go | 各自生态 | 已用该框架时的顺带选择 |
| **Nacos + Nginx（`resolver` 方案）** | 任意 | 注册中心间接提供 | ⚠️ 成本最低但不是自动发现，需要自己写「注册中心 → DNS」的同步器 |

⭐ **一条实践判据**：**「按服务名路由」这个需求出现时，才需要微服务网关**。
如果路由就是「`/api/order/*` → 一组固定 IP」，那用 Nginx 或 API 网关更简单——
**不要为了「微服务」三个字引入一个绑定语言的网关**。

> ⚠️ **别用南北向网关硬扛东西向流量**：服务间的调用（`order` → `inventory`）如果也绕回网关，
> 会多一跳、多一个故障点、多一份带宽成本。东西向的治理交给**服务网格**或**客户端负载均衡**
> （见 [../../04-架构与系统/分布式/服务治理/服务发现与负载均衡.md](../../04-架构与系统/分布式/服务治理/服务发现与负载均衡.md)）。

## 六、K8s 入口网关（Ingress / Gateway API）

**本节要点**：K8s 里「网关」是**集群的入口抽象**，
选型的本质是选**「用哪套 API + 哪家实现」**；细节对比见 [../../06-工程实践/部署/容器与编排选型.md](../../06-工程实践/部署/容器与编排选型.md) 第五节。

| 层 | 是什么 | 说明 |
|---|---|---|
| **Service** | 集群内的 L4 抽象 | 只做四层转发，**不做 HTTP 路由** |
| **Ingress** | 早期入口抽象 | 只覆盖 HTTP 基础路由，**扩展靠注解、各家实现不统一** |
| **Gateway API** | Ingress 的继任者 | 把**角色**（基础设施 / 集群运维 / 应用开发者）与**协议**（HTTP/TCP/gRPC）分离，可移植性与表达力更强 |
| **实现** | Nginx Ingress / Traefik / APISIX Ingress / Contour | ⚠️ **同一份 Ingress，换个实现行为可能不同**（注解不通用） |

⭐ **与前面几层的关系**：K8s 里的入口网关**可以就是 ② API 网关**（APISIX / Kong 都有 Ingress Controller），
所以真实项目里常常是「**一套 APISIX 同时扮演 K8s 入口和 API 网关**」，而不是额外再加一层。

> ⚠️ **别在 K8s 里再套一层「外部 nginx + 内部 Ingress」**，除非确实需要内外分离的合规边界——
> 两套入口意味着两次 TLS 卸载、两份证书、两处路由规则、两个排查入口。

## 七、跟服务网格是什么关系？还要不要上网格？

**本节要点**：网关与网格是**两个不同的治理平面**——
「要不要上网格」的完整三方对比（Istio / Linkerd / Cilium）见 [../../06-工程实践/部署/容器与编排选型.md](../../06-工程实践/部署/容器与编排选型.md) 第三节，
这里只回答**边界在哪、什么时候只需要其中一个**。

| 维度 | 网关（①~④） | 服务网格（⑤） |
|---|---|---|
| 流量方向 | **南北向**（外部 → 内部） | **东西向**（服务 ↔ 服务） |
| 部署形态 | 少数几个独立实例 | 每个 Pod 一个 Sidecar（或节点级代理） |
| 谁写配置 | **运维 / 平台**（人工或控制台） | **平台**（自动注入 + 声明式策略） |
| 典型诉求 | 暴露 API、鉴权、限流、灰度 | mTLS、重试/熔断、细粒度遥测、流量镜像 |
| 引入成本 | **1 个组件** | 一跳延迟 + 一套控制面 + **排障复杂度上升** |

**三条判断**：

1. **只需要南北向治理** → 用网关，**不要上网格**（这是绝大多数项目的答案）；
2. **服务间需要统一 mTLS / 重试 / 可观测，且服务数量多、语言多** → 网格的价值才显现；
3. ⚠️ **网格不能替代网关**：外部流量进来还是需要入口（Istio 的 `Gateway` 资源虽然叫 Gateway，
   但它本质上仍是**入口代理的配置**，与「API 网关的插件生态」不是一回事）。

## 八、组合拳：一层还是两层？

**本节要点**：这是落地时**最常被问的问题**——既然 Nginx 和 APISIX 能力有重叠，
到底装一个还是装两个？

| 组合 | 形态 | 适合 | 代价 |
|---|---|---|---|
| **单层 Nginx / OpenResty** | 1 个组件 | 路由变更低频、无复杂鉴权、团队只有 Nginx 经验 | 动态路由与健康检查的能力缺口（第三节） |
| **单层 APISIX（或 Kong）** | 1 个组件 | ⭐ **推荐起点**：既要动态路由又要插件，且能接受 etcd 依赖 | etcd 成为必须运维好的组件；静态资源性能不如 Nginx 极致 |
| **两层：Nginx/OpenResty + APISIX** | 2 个组件 | 大流量站点：Nginx 挡在最外层做 TLS/静态/WAF，APISIX 在其后做业务治理 | **多一跳**、两套配置、两处日志；⚠️ 两层都要**正确透传真实客户端 IP**，否则限流按 LB 的 IP 限，形同虚设 |
| **云厂商托管**（ALB / CLB / API 网关） | 0 个自建 | 不想运维、流量规模不大、能接受厂商绑定 | 深度定制受限、成本随流量上升、迁移成本高 |

⭐ **默认建议**：**先单层 APISIX**。
两层是**大流量 + 明确的性能诉求**出现后的优化，不是起点——
在没到瓶颈时引入两层，只是在给自己制造「怎么两边日志对不上」的排障成本。

> ⚠️ **两层时必须处理的三件事**：
> ① **真实 IP 透传**（Nginx 侧 `X-Real-IP` / `X-Forwarded-For`，APISIX 侧启用 `realip` 插件）——
> 否则第二层的**限流与黑白名单会按第一层的 IP 生效**，等于没配；
> ② **超时逐层收敛**（客户端超时 > 外层 > 内层 > 上游），否则会出现「外层还在等、内层已超时」的幽灵 502；
> ③ **探针路径放行**（健康检查不要被限流或鉴权拦住）。

## 九、决策速查表

**本节要点**：直接按自己的场景对号入座。

| 你的情况 | 推荐 |
|---|---|
| 静态站点 / 少量固定上游 / 「够用就好」 | **Nginx** |
| 需要在 Nginx 里写鉴权、复杂路由、响应改写 | **OpenResty**（写法见 [OpenResty.md](OpenResty.md)） |
| 路由需要**秒级生效**、要插件化鉴权限流、团队愿意维护 etcd | **APISIX** |
| 已有 Kong 经验 / 需要商业支持 / 要完整插件市场 | **Kong**（⚠️ 必须运维好 Postgres） |
| Java 微服务体系、路由跟着注册中心走 | **Spring Cloud Gateway** |
| Go + Kratos 体系 | **Kratos 网关** |
| 只要把多个后端**聚合成一个接口** | **KrakenD** |
| K8s 集群入口、想要可移植的标准 API | **Gateway API** + Nginx Ingress / Traefik |
| 服务间需要统一 mTLS 与遥测、服务多且语言杂 | **服务网格**（Istio / Cilium） |
| 不想自建、流量不大、能接受厂商绑定 | **云托管 API 网关** |

## 十、落地清单与常见的坑

**本节要点**：网关是全站入口，**一次配置错误 = 全站不可用**，所以下面每一条都值得在发布前过一遍。

### 10.1 上线检查单

| 项 | 要点 |
|---|---|
| **配置校验** | 每次发布前跑语法校验（`nginx -t` / `apisix validate`），**纳入 CI** |
| **配置回滚** | 有版本、有审计、能回滚；⚠️ **改路由前先备份当前配置** |
| **灰度发布** | 新版本先按权重/白名单切 1%，观察核心指标再放大（见 3.4） |
| **限流** | 至少按 IP + 按接口两个维度；⚠️ 两层架构下**确认拿到的是真实客户端 IP** |
| **超时** | 每层都配、逐层收敛；默认不配超时 = 上游卡死会拖垮网关 |
| **熔断 / 失败重试** | 重试要**幂等**才安全；⚠️ 重试会放大流量，**要限次数** |
| **健康检查** | 别只在网关上配，**上游也要有 `/healthz`**；探针路径放行 |
| **可观测** | 访问日志 + 上游状态码 + 延迟分位；⚠️ 日志格式里一定要有 `$upstream_addr`（3.5 就是靠它看到重试的） |
| **容量** | 网关是**有状态连接**的（keep-alive 池），按连接数而不只是 QPS 估算 |

### 10.2 五个高频的坑

1. **把业务逻辑写进网关** —— 订单校验、库存判断放在网关，会让**网关变成最难发布的组件**
   （任何业务改动都要动全站入口）。网关只做**横切关注点**：认证、限流、路由、灰度、日志。
2. **限流按错误的 IP 生效** —— 两层或经 LB 之后，`$remote_addr` 是上一跳的 IP；
   按它限流等于**把所有用户当成一个人限**。要用 `X-Forwarded-For` 的最左可信值。
3. **只配了连接超时，没配读超时** —— 上游「连上了但不回数据」是最常见的拖垮方式，
   `proxy_read_timeout` 不配会一直挂着连接。
4. **重试非幂等请求** —— `proxy_next_upstream` 默认包含 `error timeout`，
   如果上游在写库后返回超时，**重试会导致重复写入**；写接口要显式限制重试或不重试。
5. **灰度用随机数而不是哈希** —— 同一个用户在新旧版本之间来回跳（3.4 实测），
   会话、缓存、埋点全乱；用 `split_clients` 这类**确定性哈希**。

## 使用：photography-server 的入口怎么选？

**本节要点**：拿仓库里真实的多租户摄影 SaaS 后端（[photography-server](https://github.com/Eleven-26/photography-server)）对一遍——
它当前是「**Nginx 反向代理 + 应用层鉴权**」，这套配置按本篇的判据**够不够、边界在哪**。

**当前形态**（[photography-server](https://github.com/Eleven-26/photography-server) + PC admin / 小程序 / H5 三端）：

```text
PC admin(Vue) ─┐
小程序(uniapp) ─┼─→ Nginx ─→ Go 服务（Gin）─→ MySQL / Redis / Nacos
H5(同源)      ─┘         │
                        └─ 静态资源、TLS 卸载、location 转发
```

**按第二节六个维度逐条对**：

| 维度 | 现状 | 判断 |
|---|---|---|
| ① 动态路由 | 路由就是「`/api/*` → 后端」，**几乎不变** | ✅ Nginx 够用，不必为动态路由上 APISIX |
| ② 插件能力 | 鉴权在**应用层**（Go 中间件，JWT + `company_id`） | ✅ 放在应用层是**对的**——多租户逻辑与业务表强耦合，放网关反而要跨层查库 |
| ③ 性能 | 单实例、内部使用、QPS 不高 | ✅ 不构成瓶颈 |
| ④ 运维成本 | 只有 Nginx 一个组件 | ✅ 引入 etcd + APISIX = 多一套需要备份监控的系统 |
| ⑤ 人才 | 团队熟 Nginx | ✅ |
| ⑥ 语言栈 | Go 单栈 | ✅ 微服务网关（Spring Cloud Gateway / Kratos 网关）都不必要 |

⭐ **结论：继续用 Nginx，但补三个具体的缺口**（都能在现有 Nginx 里做完，不需要换组件）：

1. **多租户的 `company_id` 必须只信服务端** —— 入站请求要**剥离**外部传入的
   `X-Company-Id` / `X-Tenant-Id` 头，防止**越权跨租户**：

   ```nginx
   proxy_set_header X-Company-Id "";          # ⭐ 清空客户端的伪造值（配合应用层从 JWT 解出的值）
   proxy_set_header X-Real-IP $remote_addr;
   proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
   ```

2. **限流要按真实 IP** —— 上传 / 导出这类重接口在网关层加一道：

   ```nginx
   limit_req_zone $binary_remote_addr zone=upload:10m rate=5r/s;

   location /api/upload/ {
       limit_req zone=upload burst=3 nodelay;
       proxy_pass http://photography_backend;
   }
   ```

   ⚠️ 前提是上面那行 `X-Real-IP` 已经配好；否则 `$binary_remote_addr` 是上一跳的地址。

3. **给探针与健康检查放行** —— 如果将来加了网关层鉴权，`/healthz` 必须白名单，
   否则**健康检查被鉴权拦住 → 节点被误判为挂掉**。

**什么时候才需要升级到 API 网关**（触发条件，现在都不满足）：

| 触发条件 | 届时怎么做 |
|---|---|
| 要对外开放 API（第三方接入），需要**密钥自助 + 配额管理** | 上 APISIX / Kong（自建）或云托管 API 网关 |
| 路由从「1 个后端」变成「按租户/按版本分流」且**要求秒级生效** | APISIX（etcd 动态配置） |
| 静态资源与 API 流量都很大，需要**分工** | 两层：Nginx 在最外层 + APISIX 做业务治理（第八节） |
| 服务拆多了、服务间要统一 mTLS 与重试 | 先评估服务网格是否值得（第七节），而不是加网关 |

## 延伸追问

- **API 网关和服务网格，只选一个选谁？** → 看治理的流量是**南北向**还是**东西向**。
  对外暴露 API、要鉴权限流 → 网关；服务间要 mTLS/重试/遥测且服务多语言杂 → 网格。
  **两者不冲突**，但绝大多数项目只会有前者。
- **Nginx 和 OpenResty 是什么关系？** → OpenResty = **Nginx + LuaJIT + 一批 `lua-resty-*` 库**。
  它不是另一个网关，而是「让 nginx 能跑 Lua」的发行版；写法与六个典型应用见 [OpenResty.md](OpenResty.md)。
- **`nginx -s reload` 会不会导致线上抖动？** → 短连接**不会**（实测 271 个请求 100% 成功）；
  但**长连接会被断**（实测 3/3 轮 `ConnectionAbortedError`）。
  连接池化的客户端（Go `http.Client`、gRPC）会在发布时刻遇到 `connection reset`，这是 reload 模式的固有代价。
- **不上 API 网关，能自己实现动态路由吗？** → 能一部分：`map` + 变量 `proxy_pass` 按请求切后端、
  `resolver` + 域名改 DNS 换 IP（实测配置与 reload 都不需要）。
  **做不到的是 `upstream` 成员的热增删**——那是启动期结构，必须 reload。
- **`limit_req` 是令牌桶吗？** → **不是**。它是漏桶式的**排队整形**（要么排队、要么拒绝），
  语义与 [限流算法.md](../../04-架构与系统/分布式/服务治理/限流算法.md) 的令牌桶不同；
  要「允许突发 + 跨机共享配额」得用 OpenResty 的 `resty.limit.req` 或 Redis + Lua
  （见 [../../04-架构与系统/分布式/服务治理/限流降级熔断.md](../../04-架构与系统/分布式/服务治理/限流降级熔断.md)）。
- **网关该不该做协议转换（REST ↔ gRPC）？** → 该做，**这是网关最合理的职责之一**：
  对外 REST/JSON、内部 gRPC/Protobuf，把协议边界**收在网关一处**，
  而不是让每个服务同时支持多种协议（见 [../../02-计算机基础/网络/通信选型.md](../../02-计算机基础/网络/通信选型.md)）。
- **为什么业务逻辑不能写进网关？** → 网关在请求路径的**最上游**，
  它的一次发布影响**全部流量**。业务逻辑放进去之后，任何一个业务的改动都要动全站入口，
  发布风险与协作成本会指数上升。判据：**「这个逻辑改动是否需要业务方参与评审」——是，就不该在网关**。
- **K8s 里还需要单独的 API 网关吗？** → 通常**不需要再加一层**：
  APISIX / Kong 都有 Ingress Controller，可以**一套组件同时做 K8s 入口和 API 网关**。
  额外套一层外部 Nginx 只在需要内外隔离的合规场景才划算（第六节）。
