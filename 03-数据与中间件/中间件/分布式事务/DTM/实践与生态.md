# DTM 实践与生态

> 本篇按「语言 → 框架 → ORM → 场景」四条线，梳理 DTM 的生态边界：支持哪些语言、能接进哪些微服务框架、与常见 ORM 怎么配合、典型落地场景是什么。
> 具体接入代码见 [接入DTM.md](../../../../01-编程语言/go/工程实践/接入DTM.md)；本文不重复代码。
>
> 内容整理自个人学习笔记，素材来自 DTM 官方文档与官方仓库。素材见 [素材清单.md](../../../../素材清单.md)。

## 一、多语言 SDK 一览

**本节要点**：DTM 的 SDK 刻意做得很薄（一门语言某个模式的实现通常只有几十到一两百行），因此各语言的成熟度不齐——选语言前先看它覆盖了哪些模式。

| 语言 | 客户端 | 覆盖的模式 |
|---|---|---|
| **Go** | `dtm-labs/client`（与主仓 `client/` 同步，依赖更少） | SAGA / TCC / XA / 二阶段消息 / Workflow / 屏障（最完整） |
| **PHP** | `dtm-php/dtm-client`（协程版，Hyperf / Swoole） | SAGA / TCC / MSG / XA / 子事务屏障 |
| **PHP** | `dtm-labs/dtmcli-php`（普通版） | 仅 TCC |
| **C#** | `dtm-labs/dtmcli-csharp`（HTTP）/ `dtmgrpc-csharp`（gRPC） | TCC / SAGA / MSG / 子事务屏障 |
| **Python** | `dtm-labs/dtmcli-py` | TCC / SAGA / 子事务屏障 |
| **Java** | `dtm-labs/dtmcli-java` | SAGA / TCC / 子事务屏障 |
| **Node** | `dtm-labs/dtmcli-node` | 仅 TCC |

> ⚠️ 上表按官方 SDK 页整理，各语言覆盖的模式随版本演进，接入前以对应仓库 README 为准。跨语言是 DTM 相对 Seata 的核心差异，见 [分布式事务选型对比.md](../分布式事务选型对比.md) 第三节。
> 官方示例集中在 `dtm-labs/dtm-examples`（含 grpc / http / xa / msg / saga / tcc / barrier）与 `dtm-labs/quick-start-sample`。

## 二、微服务框架集成

**本节要点**：DTM 对主流微服务框架是「作为普通无状态服务接入」，多副本与注册发现直接复用框架方案。

| 框架 | 定位 | 接入要点 |
|---|---|---|
| **go-zero** | Go 微服务框架 | 屏障接入要求 go-zero ≥ v1.2.0；用 `conn.RawDB()` 拿到底层连接再包进屏障 |
| **go-kratos/kratos** | Go 微服务框架 | 作为外部服务接入，多副本沿用框架的服务发现方案 |
| **polarismesh/polaris** | 服务治理平台 | 注册发现与多副本复用平台能力 |

- **多副本**：DTM 无状态，副本数直接跟着框架的服务发现与负载均衡走，见 [部署与运维.md](部署与运维.md) 第五节。
- **回调可达**：无论接哪个框架，都必须保证 DTM 能回调到业务分支的真实地址（容器内不要写容器自身的 `localhost`）。

## 三、ORM 对接

**本节要点**：子事务屏障与 XA 都需要拿到本地事务对象，DTM 的接口以标准库 `sql.Tx` / `sql.DB` 为准，其他 ORM 需先转换出 `*sql.Tx` 或 `*sql.DB`。

- **接口形态**：屏障用 `BranchBarrier.Call(tx *sql.Tx, busiCall)` 或 `CallWithDB(db *sql.DB, busiCall)`；XA 本地分支用 `XaLocalTransaction(..., func(db *sql.DB, xa *Xa) error { ... })`。
- **常见 ORM 的转换方式**：

| ORM / 框架 | 屏障：怎么拿 `*sql.Tx` | XA：怎么拿 `*sql.DB` |
|---|---|---|
| **database/sql** | 直接传 `*sql.Tx` | 回调直接给 `*sql.DB` |
| **GORM** | 从会话里取底层连接池并断言为 `*sql.Tx` | 用 `gorm.Open(mysql.New(mysql.Config{Conn: db}))` 从 `*sql.DB` 构造 |
| **goqu** | `gdb.Begin()` 得到事务后传入 | `dialect.DB(db)` 包装 |
| **XORM** | `session.Tx().Tx` | `xorm.NewEngineWithDB(..., core.FromDB(db))` |
| **go-zero** | `conn.RawDB()` 后交给 `CallWithDB` | 由 `*sql.DB` 构造 `SqlConn` |

- **数据库侧**：支持 MySQL 系列（MySQL / MariaDB / TiDB / TDSQL）、Postgres、Redis、Mongo；使用 Postgres 时需先调用 `dtmcli.SetCurrentDBType("postgres")`。

## 四、典型应用场景

**本节要点**：DTM 的差异化场景集中在「不需要回滚的最终一致」和「跨存储组合」两类。

- **缓存一致性**：用二阶段消息保证「DB 与缓存」最终一致，比订阅 binlog 或纯队列方案更简洁。
- **秒杀扣库存**：把扣库存放在 Redis，通过 DTM 组合 Redis 与 MySQL 事务，让「Redis 里的精确库存」与「最终创建的订单数」对齐，减少人工调账。
- **非单体订单系统**：跨服务的订单 / 库存 / 账户操作交给 DTM 协调，避免把逻辑塞进一个大本地事务。
- **事件发布 / 订阅**：二阶段消息定位为比 Outbox 更优雅的事件外发方案，见 [事务模式.md](事务模式.md) 第四、六节。

## 延伸追问

- **为什么 DTM 的 SDK 能做这么薄？** → 因为它把能在服务端完成的逻辑都放在服务端，SDK 只负责 HTTP / gRPC 通信与 ID 生成，因此接一门新语言的成本很低。
- **go-zero 接入为什么有版本要求？** → 屏障需要拿到 `*sql.Tx` / `*sql.DB`，框架暴露底层连接的能力是从 v1.2.0 起才具备的。
- **Java 团队有必要选 DTM 吗？** → 栈统一在 Java 且吃 Seata 生态时，Seata 更顺；但只要有多语言并存、或想用子事务屏障简化幂等 / 空补偿 / 悬挂的编写，DTM 依然值得，见 [分布式事务选型对比.md](../分布式事务选型对比.md) 第四节。
- **用一个语言但不确定该选哪个模式怎么办？** → 先回到「需不需要回滚」：需要就 SAGA / TCC / XA，不需要（只要求本地提交与事件发布原子）就用二阶段消息，见 [事务模式.md](事务模式.md) 第一节。
