# gRPC 安全与认证

> 传输安全与身份：TLS 与 mTLS 怎么接、握手失败时会看到哪几种报错、**「CA 不对的客户端证书根本不会被发出去」**这条容易踩的坑、服务端能从 peer 里拿到什么、token 类凭据怎么带，以及「认证通过 ≠ 有权调用」的授权落点。
>
> 内容整理自个人学习笔记，实测基于本机 Docker Desktop（容器 `golang:1.26-alpine` 内 go1.26.8 + grpc-go v1.84.0），PKI 是**进程内现造的自签证书**（`crypto/x509`，不落盘、不联网），原始输出见 `.workbuddy/tmp/exp/grpclab/out/tls.txt`（两遍逐行相同）。素材见 [素材清单](../../../../素材清单.md)。

## 一、gRPC 的 TLS 接在哪里？

**本节要点**：TLS 接在**传输凭据**这一层（`TransportCredentials`），它比 HTTP/2 还靠下——所以换 TLS 不需要改任何调用代码，只换一个 dial/server 选项。

### 1.1 一层「凭据」管住了什么

```text
调用代码（conn.Invoke / 生成的存根）
      ↑ 不变
框架层：deadline / metadata / 状态码
      ↑ 不变
载荷层：Protobuf 或其它 codec
      ↑ 不变
传输层：HTTP/2 帧、流、多路复用
      ↑ 不变
凭据层：credentials.NewTLS(…)  ← 只换这一格
      ↑
TCP
```

所以「上 TLS」在 gRPC 里是**一个选项**的事；也正因为它在最底层，
**mTLS 的客户端证书与 HTTP 层的 header 是两回事**——前者是握手时出示的身份，后者是业务自己塞的字符串。

### 1.2 三行代码

```go
// 客户端：信任哪个 CA（RootCAs 为空则用系统根）
creds := credentials.NewTLS(&tls.Config{RootCAs: pool})
conn, _ := grpc.NewClient(addr, grpc.WithTransportCredentials(creds))

// 服务端：出示哪张证书；要求客户端证书就加后两行
tc := &tls.Config{
	Certificates: []tls.Certificate{srvCert},
	ClientAuth:   tls.RequireAndVerifyClientCert, // 要求并校验客户端证书
	ClientCAs:    pool,                          // 用什么 CA 验客户端证书
}
srv := grpc.NewServer(grpc.Creds(credentials.NewTLS(tc)))
```

`insecure.NewCredentials()` 就是「明文的等价物」——本目录早期几篇全程用它，所以那些读数都是 h2c 明文。

## 二、握手失败时你会看到哪一种报错？

**本节要点**：十种结局里只有 4 种是成功的；失败文案分三类——**明文对 TLS 的两个方向**、**证书链校验失败**、**mTLS 客户端证书问题**。把这三类背下来，看日志就能定位。

实测（`out/tls.txt`）：

```text
A1 明文客户端   → TLS 服务端   : code=Unavailable（desc 在 connection reset by peer / EOF 之间摆动）
A2 TLS 客户端   → 明文服务端   : rpc error: code = Unavailable desc = connection error: desc = "transport: authentication handshake failed: tls: first record does not look like a TLS handshake"
B  信 root1     → TLS 服务端   : <nil>
C  只用系统根   → TLS 服务端   : rpc error: code = Unavailable desc = connection error: desc = "transport: authentication handshake failed: tls: failed to verify certificate: x509: certificate signed by unknown authority"
D  ServerName 错 → TLS 服务端  : rpc error: code = Unavailable desc = connection error: desc = "transport: authentication handshake failed: tls: failed to verify certificate: x509: certificate is valid for localhost, not wrong.example.com"
E  跳过校验     → TLS 服务端   : <nil>
F  mTLS 不带客户端证书          : rpc error: code = Unavailable desc = connection error: desc = "transport: authentication handshake failed: remote error: tls: handshake failure"
G  mTLS 证书来自 root2（放 Certificates）: rpc error: code = Unavailable desc = connection error: desc = "transport: authentication handshake failed: remote error: tls: handshake failure"
G2 mTLS 证书来自 root2（GetClientCertificate 强行发出）: rpc error: code = Unavailable desc = connection error: desc = "transport: authentication handshake failed: remote error: tls: unknown certificate authority"
H  带 root1 的客户端证书 → mTLS : <nil>
```

归成三类：

| 类别 | 行 | 报错里的关键词 | 处置 |
|---|---|---|---|
| 明文 / TLS 用错 | A1、A2 | `first record does not look like a TLS handshake`、连接被 reset | 两侧口径要一致：要么都明文（h2c），要么都 TLS |
| 证书链校验失败 | C、D | `certificate signed by unknown authority`、`certificate is valid for X, not Y` | C 是**信任根不对**（客户端没带对 CA）；D 是**名字不对**（`ServerName` 与证书 SAN 不匹配） |
| 服务端拒绝客户端证书 | F、G、G2 | `handshake failure`、`unknown certificate authority` | 见第三节：先确认证书**有没有被发出去** |

### 2.1 三条容易被忽略的读法

- **A1 的 desc 不稳定**：明文客户端打 TLS 端口，服务端握手失败后关闭连接，
  客户端看到的可能是 `connection reset by peer`、也可能是 `EOF`——取决于 TCP 是 RST 还是 FIN。
  所以这一行**只能断言状态码 `Unavailable`**，别把 desc 写进告警规则。
- **D 的报错只列了 DNS 名**：`ServerName` 填的是域名（`wrong.example.com`）时，
  报错列的是证书里的 **DNS SAN**（`localhost`），IP SAN 不在这一行里；
  一句话：**`ServerName` 与 `:authority` 是两套东西**，前者校验证书、后者用于路由。
- **E 行能成功但别学**：`InsecureSkipVerify: true` 连名字都不校验了（实测用一个错的 `ServerName` 也能通），
  **等于放弃了整套证书校验**；只在本地调试的临时场景用。

### 2.2 一个实验设计上的坑（值得记）

F / G / G2 三行**必须把客户端 `MaxVersion` 钉在 TLS 1.2** 才稳定：

- **TLS 1.3 下客户端「以为握手成功了」**（1-RTT 的结构使然），会在读到手握失败之前
  先把 HTTP/2 前言写出去，于是错误**随机落在 `write: broken pipe` 与证书错误之间**；
- **TLS 1.2 下握手没完成就不会有应用数据**，服务端的 alert 一定先到，报错才稳定。

这不是 gRPC 的问题，是 TLS 1.3 握手时序的正常表现——但它解释了「同一套配置，报错怎么一会儿一个」这类灵异现象。

## 三、mTLS：客户端证书是怎么发出去、又怎么被验的？

**本节要点**：⭐ **一张「CA 不对」的客户端证书，放在 `tls.Config.Certificates` 里根本不会被发出去**——Go 会按服务端给出的 `AcceptableCAs` 过滤掉它，于是服务端看到的是「客户端没给证书」，报 `handshake failure`；只有 `GetClientCertificate` 才会强行发，报错才变成 `unknown certificate authority`。

### 3.1 F / G / G2 三行的差别在哪

三行都是「mTLS 服务端 + 客户端没有可用证书」，但**错误码不同**，根因也不同：

| 行 | 客户端配置 | 服务端看到什么 | 报错 |
|---|---|---|---|
| F | 完全不带客户端证书 | 空证书列表 | `handshake failure` |
| G | 证书来自 root2，放在 `Certificates` 里 | **空**证书列表（被过滤掉了） | `handshake failure` |
| G2 | 同一张证书，但用 `GetClientCertificate` 返回 | **收到了**这张证书，验 CA 失败 | `unknown certificate authority` |

```go
// G：走 Certificates —— Go 会按服务端 ClientCAs（AcceptableCAs）过滤，
//    发行者不在列表里的证书「根本不发」，所以错误和「没带证书」一模一样
&tls.Config{RootCAs: pool1, Certificates: []tls.Certificate{rogueClient}}

// G2：走 GetClientCertificate —— 返回值不再过那层过滤，证书真发出去了，
//     服务端验 CA 失败才报 unknown certificate authority
&tls.Config{RootCAs: pool1, GetClientCertificate: func(*tls.CertificateRequestInfo) (*tls.Certificate, error) {
	return &rogueClient, nil
}}
```

⭐ **这条对排障很重要**：线上看到 `handshake failure` 时，**不能立刻断定「客户端配置里没有证书」**——
它同样可能是「证书配了，但它的签发者不在服务端的 `ClientCAs` 里」。
两个方向都要查：客户端的 `Certificates` 与**服务端的 `ClientCAs`**。

### 3.2 服务端怎么验：`ClientAuth` 四档

| `tls.ClientAuth` | 行为 |
|---|---|
| `NoClientCert` | 不要客户端证书（单向 TLS，最常见） |
| `RequestClientCert` | 要，但不验（能用来自报身份，**不要拿它做授权**） |
| `RequireAnyClientCert` | 要有，但不验签发者（同样别用于授权） |
| `RequireAndVerifyClientCert` | 要有**且**验签发者（mTLS 的正解） |

⚠️ `RequireAnyClientCert` 看着像 mTLS，其实**只保证「有一张证书」**——
自签一张就能过，等于没有认证。要做身份就必须配 `ClientCAs` 且用 `RequireAndVerifyClientCert`。

## 四、服务端从 `peer` 里能拿到什么？

**本节要点**：`peer.FromContext(ctx)` 给出对端地址与 `AuthInfo`；TLS 场景下 `AuthInfo` 是 `credentials.TLSInfo`，里面有**协商出的版本、密码套件、对端证书链**——这就是授权的输入。

实测（服务端拦截器里打印，`out/tls.txt`）：

```text
  第1次到达服务端: authInfo=credentials.TLSInfo version=TLS 1.3 cipher=TLS_AES_128_GCM_SHA256 serverName="" peerCN=grpclab-client-1 verifiedChains=1
```

逐字段读：

| 字段 | 这次的值 | 用途 |
|---|---|---|
| `authInfo` 类型 | `credentials.TLSInfo` | 断言它才能拿到下面这些 |
| `version` | TLS 1.3 | 排查「协商到了什么版本」（老客户端可能只到 1.2） |
| `cipher` | `TLS_AES_128_GCM_SHA256` | 合规审计要的证据 |
| `serverName` | `""` | 服务端没要求 SNI；客户端侧的 `ServerName` 用于**校验**，不是这里 |
| `PeerCertificates[0].Subject.CommonName` | `grpclab-client-1` | ⭐ **mTLS 的身份来源**，授权的输入 |
| `VerifiedChains` 条数 | 1 | 有值说明**链验过了**；单向 TLS 时它是 0 或空 |

取它的代码只有三行：

```go
p, ok := peer.FromContext(ctx)
ti, isTLS := p.AuthInfo.(credentials.TLSInfo)
cn := ti.State.PeerCertificates[0].Subject.CommonName   // ⚠️ 先判 len > 0
```

⚠️ **`PeerCertificates` 可能为空**（单向 TLS、或 `ClientAuth` 没开），切片取下标会 panic——
线上出过这类问题的位置就在这里，先判长度再取。

## 五、凭据：token / JWT / API Key 怎么带？

**本节要点**：TLS 保证「链路是谁」，token 保证「调用者是谁」——两者叠加才是完整的认证。token 走 metadata，但要用**凭据接口**而不是手写 header，因为它自带「必须跑在安全传输上」的约束。

### 5.1 为什么不用手写 header

```go
// ❌ 手写：既没有「必须 TLS」的约束，也容易在日志里泄出去
ctx = metadata.AppendToOutgoingContext(ctx, "authorization", "Bearer "+tok)

// ✅ 用凭据接口：框架每次调用自动注入，且可声明「必须安全传输」
type tokenCred struct{ tok string }

func (c *tokenCred) GetRequestMetadata(ctx context.Context, uri ...string) (map[string]string, error) {
	return map[string]string{"authorization": "Bearer " + c.tok}, nil
}

// 返回 true：不允许在不安全的连接上使用这套凭据（明文时直接失败）
func (c *tokenCred) RequireTransportSecurity() bool { return true }

conn, _ := grpc.NewClient(addr,
	grpc.WithTransportCredentials(creds),
	grpc.WithPerRPCCredentials(&tokenCred{tok: token}),
)
```

### 5.2 三种凭据的分工

| 机制 | 解决什么 | 放哪 |
|---|---|---|
| TLS（单向） | 链路加密 + 服务端身份 | 传输凭据 |
| mTLS（双向） | 额外认证**客户端**身份（可做 CN 白名单） | 传输凭据 |
| Token / JWT / API Key（`PerRPCCredentials`） | 认证**调用者/租户**，可携带权限声明 | 每次调用的 metadata |

实践里常见组合是「**内网 mTLS 打底 + 网关层校验 token**」：
mTLS 让「谁能连上」可控，token 让「谁能调哪个方法」可控。两种都在时**授权判据要选一个为准**，
不要一处看 CN、一处看 token，否则排查时会互相矛盾。

⚠️ **`RequireTransportSecurity` 是硬约束不是建议**：返回 `true` 时，
客户端在明文连接上发调用会**直接失败**——这正是本目录早期几篇全程明文、无法直接用带 token 凭据的原因。

## 六、授权：认证通过 ≠ 有权调用

**本节要点**：证书链只能证明「你是谁」，**能不能调这个方法**是另一层。实测用 mTLS 的 CN 做白名单：不在白名单的证书（**同一 CA 签发、链也是合法的**）拿到 `PermissionDenied`。

实测（服务端一个按 CN 判定的拦截器，白名单只放 `grpclab-client-1`）：

```text
CN=grpclab-client-1 → 授权服务端: <nil>
CN=rogue-client（同一 CA 签发，只是不在白名单）→ 授权服务端: rpc error: code = PermissionDenied desc = client CN "rogue-client" not in allowlist
```

```go
// 授权拦截器：先取身份，再判权限；判不过就 PermissionDenied
func authz(ctx context.Context, req any, info *grpc.UnaryServerInfo, h grpc.UnaryHandler) (any, error) {
	p, _ := peer.FromContext(ctx)
	cn := ""
	if p != nil && p.AuthInfo != nil {
		if ti, ok := p.AuthInfo.(credentials.TLSInfo); ok && len(ti.State.PeerCertificates) > 0 {
			cn = ti.State.PeerCertificates[0].Subject.CommonName
		}
	}
	if cn != allowedCN {
		return nil, status.Errorf(codes.PermissionDenied, "client CN %q not in allowlist", cn)
	}
	return h(ctx, req)
}
```

三条工程口径：

- **认证失败用 `Unauthenticated`，授权失败用 `PermissionDenied`**——别混用，
  调用方靠这两个码决定「重新登录」还是「申请权限」；
- **别把授权判据只放在拦截器里**：方法级权限（谁能调哪个方法）通常还要在
  **服务端的方法注册/网关**上再确认一遍；拦截器只是最方便的那一层；
- **CN 白名单的维护成本**：证书轮换时 CN 会变，所以生产上多用**身份 → 角色**的映射表
  （CN / SPIFFE ID → 角色），白名单落在表上而不是代码里。

## 使用：证书生成与轮换清单

**本节要点**：本实验的 PKI 是进程内现造的——这对演示够用，但**生产要落盘并管生命周期**。下面是可抄的清单。

⚠️ **下面这一小节的 openssl 命令本身未实测**（本实验用的是 `crypto/x509` 在内存里签发，见 `cmd/tls/main.go`）；
命令按 openssl 的标准用法写，**没有在本机跑过**——它给的是「要在哪些地方写对」的清单，不是可复现读数。

### 1. 用 openssl 造一套（结构与实验里的内存版一致）

```bash
# 1) 根 CA（离线保存，只在签发时用）
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes \
  -keyout root.key -out root.crt -days 3650 -subj "/CN=grpclab-root-1"

# 2) 服务端证书：SAN 必须写对（用 IP 连就要写 IP，用域名连就要写域名）
openssl req -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes \
  -keyout srv.key -out srv.csr -subj "/CN=grpclab-tls-server"
openssl x509 -req -in srv.csr -CA root.crt -CAkey root.key -CAcreateserial \
  -out srv.crt -days 825 -extfile <(printf "subjectAltName=DNS:localhost,IP:127.0.0.1\nextendedKeyUsage=serverAuth")

# 3) 客户端证书：用途必须是 clientAuth（不是 serverAuth）
openssl req -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes \
  -keyout cli.key -out cli.csr -subj "/CN=grpclab-client-1"
openssl x509 -req -in cli.csr -CA root.crt -CAkey root.key -CAcreateserial \
  -out cli.crt -days 825 -extfile <(printf "extendedKeyUsage=clientAuth")
```

三条要注意的坑：**SAN 写错**（用 IP 连却没写 IP）报 `certificate is valid for ..., not ...`（实测 D 行）；
**`extendedKeyUsage` 写错**（客户端证书写成 `serverAuth`）会被 Go 的证书过滤规则挡掉，
症状与「没带证书」一样（第 3.1 节的 G 行）；**根证书泄漏**等于全都泄漏，DA 必须离线。

### 2. 轮换与热加载

- 服务端证书**要能热加载**：`tls.Config.GetCertificate` 里按 `ClientHelloInfo` 返回当前证书，
  顺手做 SNI 多证书；
- 客户端 CA 池同理：别在启动时 `ReadFile` 一次就完，轮换后新连接会全部失败；
- **`Notify` 别忘**：用 `GetCertificate` 拿证书的写法里，如果 `tls.Config` 直接给了 `Certificates`，
  轮换时不重建 Server 就不生效。

### 3. Go / Java 侧的关键差异

| 项 | Go | Java |
|---|---|---|
| 建凭据 | `credentials.NewTLS(&tls.Config{...})` | `GrpcSslContexts.forServer(cert, key).trustManager(ca).clientAuth(ClientAuth.REQUIRE)` |
| 取客户端身份 | `peer.FromContext(ctx).AuthInfo.(credentials.TLSInfo).State.PeerCertificates[0]` | `sslSession` 的 `getPeerCertificates()[0]`（`Grpc.TRANSPORT_ATTR_SSL_SESSION`） |
| 只信自签 CA | `x509.NewCertPool()` + `AddCert` | `GrpcSslContexts.forClient().trustManager(caFile)` |
| 跳过校验 | `InsecureSkipVerify: true`（**别在线上用**） | `InsecureTrustManagerFactory`（**别在线上用**） |

Java 侧完整依赖与写法见 [接入gRPC.md](../../../../01-编程语言/java/接入gRPC.md)。

## 延伸追问

- **TLS 接在哪一层、换它要改业务代码吗？** → 接在**传输凭据**层，比 HTTP/2 还靠下；
  换 TLS 只换一个 dial/server 选项，调用代码一行不改（第一节）。
- **`ServerName` 和 `:authority` 是一回事吗？** → 不是。前者用于**校验证书**（对不上就是 D 行那个错），
  后者是 HTTP/2 伪头、用于路由与虚拟主机（第二节 2.1）。
- **为什么报错一会儿 `broken pipe`、一会儿 `certificate required`？** → TLS 1.3 握手时序：
  客户端会先把 HTTP/2 前言写出去，谁先到不确定；钉到 TLS 1.2 就稳定了（第二节 2.2）。
- **客户端明明配了证书，服务端却说没收到？** → 很可能是**签发者不在服务端 `ClientCAs` 里，证书被 Go 静默过滤、根本没发出去**
  ——F 与 G 的报错完全相同（第三节 3.1）。
- **`RequireAnyClientCert` 算 mTLS 吗？** → 不算。它只要求「有一张证书」、不验签发者，
  自签一张就能过；做身份必须 `RequireAndVerifyClientCert` + `ClientCAs`（第三节 3.2）。
- **`PeerCertificates` 会不会是空？** → 会（单向 TLS / 没开 `ClientAuth`），
  取下标前必须判长度，否则 panic（第四节）。
- **token 为什么要用 `PerRPCCredentials` 而不是手写 header？** → 它每次调用自动注入，
  并且能声明「必须跑在安全传输上」（`RequireTransportSecurity`），手写 header 两样都没有（第五节）。
- **认证与授权分别该返回什么码？** → 认证失败 `Unauthenticated`、授权失败 `PermissionDenied`；
  混用会让调用方不知道该重新登录还是去申请权限（第六节）。
