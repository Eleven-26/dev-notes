# gRPC 故障排查与调试

> 一份按「症状 → 判据 → 处置」组织的排障手册：连不上、连上但调用失败、过网关报陌生错误、流式卡住、限额撞线、以及三类**静默失效**。每条都指向本目录某个篇目里的实测读数。
>
> 内容整理自个人学习笔记，实证与读数分散在本机 Docker Desktop 实验台（`.workbuddy/tmp/exp/grpclab/`，grpc-go v1.84.0 / grpc-java 1.60.0 / nginx 1.26.3）的 `out/*.txt` 里，本篇只做归类与指向，**不新增未标注的结论**。素材见 [素材清单](../../../../素材清单.md)。

## 一、第一步：先判断错误出在哪一层

**本节要点**：gRPC 的报错跨五层，**层与层的处置完全不同**（调限额 vs 改 DNS vs 换代理指令）；先定位层，再谈修法。

```text
              ┌──────────────────────────────────────────────┐
   症状        │ ① 应用层     ② HTTP/2 层   ③ 连接层  ④ DNS  ⑤ 代理 │
              └──────────────────────────────────────────────┘
  业务码不对 / NotFound ……                                    → ①
  ResourceExhausted（消息太大）                                → ①
  RST_STREAM / FRAME_SIZE_ERROR（头表太大）                    → ②
  GOAWAY(too_many_pings / graceful_stop)                      → ②
  Unavailable + connection refused / transport is closing      → ③
  READY 要等好几秒 / 跨容器连不上                               → ④
  no valid HTTP/1.0 header / 502                               → ⑤
```

**判据**：把报错里的**状态码**先分拣——`ResourceExhausted` / `NotFound` / `InvalidArgument` 是应用层的语义化错误；
出现 `RST_STREAM`、`FRAME_SIZE_ERROR`、`too_many_pings` 这些字眼就是协议层；
而 `Unavailable` 是个「筐」，它既可能是连不上，也可能是被 `GOAWAY` 掐断，**必须看 desc**。

## 二、连不上 / 首连特别慢

**本节要点**：八成不是「网络不通」，而是**名字解析**或**惰性连接**——前者看 DNS 三段查询，后者看有没有调用 `Connect()` 或发过 RPC。

| 症状 | 判据 | 处置 |
|---|---|---|
| 会 READY 但**首连多等 8 秒** | TXT 查询 `_grpc_config.<host>` 飙到秒级 | `passthrough:///host:port`，或 `GRPC_ENABLE_TXT_SERVICE_CONFIG=false` |
| 跨容器**完全连不上** | A/AAAA 能解析、TCP 也通，就是不走 | 确认 resolver 用的是容器名；别在客户端再解析一次 |
| 状态一直 `IDLE`、`WaitForStateChange` 等不到 | `grpc.NewClient` **是惰性的** | 调 `conn.Connect()`，或直接发一次 RPC |
| `Unavailable: dial tcp …: connect: connection refused` | 对端真没在监听 | 先 `netstat` 确认端口；这不是 gRPC 的问题 |

⚠️ **一个必踩的混淆**：`grpc.NewClient` 之后什么都不做，连接**永远停在 `IDLE`**——
探针第一版等 `WaitForStateChange(ctx, IDLE)` 等了 30 秒没有任何变化，就是这个原因。
「等不到 READY」与「首连慢 8 秒」是**两件独立的事**，读数与修法在 [生态与网关.md](生态与网关.md) 第五节。

## 三、连上了，但调用失败

**本节要点**：先按状态码分拣，再往四类根因上靠——**业务码写错**、**错误没包 status**、**超时预算断在中途**、**协议层掐断**。

### 3.1 状态码速查

`codes` 一共 17 个值（含 `OK`），完整表与实测输出在 [拦截器与元数据.md](拦截器与元数据.md) 第七节。排障时最常撞的六个：

| 码 | 常见根因 | 下一步看哪 |
|---|---|---|
| `Unknown` | **服务端返回了一个非 status 的裸 error**（框架兜底成 `Unknown`） | 服务端有没有 `status.Error` / `status.Errorf` |
| `Unavailable` | 对端没监听、被 `GOAWAY` 掐断、代理换机器 | 看 desc 里的 `connection refused` / `closing transport` / `goaway` |
| `DeadlineExceeded` | 预算到了；或下游慢 | 每一跳有没有传 `ctx` |
| `ResourceExhausted` | 消息超 4 MiB 限额；或真被限流 | 报错里会带「实际 vs 上限」两个数 |
| `NotFound` / `InvalidArgument` | 业务语义，正常 | 按业务处理 |
| `Unimplemented` | 方法名拼错或服务端没注册 | 核对 `/<服务全名>/<方法名>` 与 `ServiceDesc` |

### 3.2 「服务端明明返回了业务错误，客户端只看到 `Unknown`」

这是排障里最常见的一条。判据：客户端拿到 `Unknown`，而服务端日志里明明有明确的错误。
根因是**服务端返回的 error 不是 status**——裸 `errors.New("boom")` 经 wire 到客户端必然变成 `Unknown`：

```text
   裸 errors.New("boom")            : ok=true code=Unknown msg="boom"
   fmt.Errorf("%w", status.Error)   : ok=true code=NotFound msg="service layer: rpc error: code = NotFound desc = no such key: 7"
```

两条处置：错误从业务层往上抛之前**统一包成 `status.Error`**；已包了 status 的错误**不要再 `%w` 包一层**
（码能解出来，但 message 会变成整条链的字符串，前端拿到一坨）。

### 3.3 超时：`DeadlineExceeded` 但服务端还在跑

判据：客户端已返回，服务端日志还在打。

- 每一跳是否都传了同一个 `ctx`？断了的话，最外层的 80 ms 预算与内层无关，
  这就能解释「80 ms 的接口实际打了 3 秒」；
- 服务端 handler 有没有 `select` 等 `ctx.Done()`？只看业务耗时的 handler
  会在客户端放弃后把活干完（实测 60 ms 放弃 vs 300 ms 睡满，读数在
  [拦截器与元数据.md](拦截器与元数据.md) 第四节）。

## 四、过网关报了一个没见过的错

**本节要点**：`upstream sent no valid HTTP/1.0 header` 是「代理用 HTTP/1.1 跟 gRPC 后端说话」的专属报错；它**不会提协议不匹配**，最容易一头扎进业务代码。

判据（nginx 日志原文）：

```text
[error] upstream sent no valid HTTP/1.0 header while reading response header from upstream,
        request: "POST /demo.Echo/Unary HTTP/2.0", upstream: "http://192.168.16.2:50051/demo.Echo/Unary"
[error] readv() failed (104: Connection reset by peer) while reading upstream
```

三组对照说明「同一台后端、只差一行配置」的结果完全不同：

| 路径 | unary | 服务端流 | 双向流 |
|---|---|---|---|
| 直连后端 | OK | recv=5 EOF | recv=3 EOF |
| `grpc_pass grpc://...` | OK | recv=5 EOF | recv=3 EOF |
| `proxy_pass http://...` + `proxy_http_version 1.1` | `Internal`，header/trailer 全空 | recv=0 `DeadlineExceeded` | recv=0 `Internal` |

**处置**：出口改 `grpc_pass`（TLS 用 `grpcs://`）；⚠️ 前端那句 `http2 on` **只管打进来，不管打出去**——
两个方向是两个独立开关，只配一边就会出现「前端 h2c 接到手了、后端还是挂」。
完整清单在 [生态与网关.md](生态与网关.md) 的使用节。

## 五、流式调用卡住了

**本节要点**：流式的「卡住」几乎全在两处——**客户端没做半关闭**、**服务端不看取消与发送错误**；另有第三种是**把 `EOF` 当失败**。

| 症状 | 根因 | 处置 |
|---|---|---|
| 服务端一直等、不回汇总 | 客户端没 `CloseSend()`（Java 没 `onCompleted()`） | 发完立刻半关闭 |
| 服务端一直发、客户端早走了 | handler 里不看 `ctx.Done()`、不看 `SendMsg` 的 error | `return err` 向上抛；`select` 里带 `ctx.Done()` |
| 正常结束却走进错误分支 | 把 `io.EOF` 当成了错误 | 先判 `err == io.EOF` 再判 `err != nil` |
| 一元 handler 的拦截器不生效 | 手写 handler 里漏了 `interceptor(...)` 调用 | 补上（见第七节） |

服务的循环本来就只靠 `io.EOF` 退出（`bidiHandler` 是 `for i := 1; ; i++`，没有任何条件退出），
所以**客户端不半关闭，服务端就没有结束条件**——这不是玄学，是代码结构决定的。
读数与五个坑的逐条出处见 [四种通信模式.md](四种通信模式.md) 第五节。

## 六、限额撞线

**本节要点**：两个限额、两种报错、两套处置；把 `5242913` 当成「消息体大小」去反推是最常见的误判。

```text
resp 5MiB / default client: code=ResourceExhausted msg="grpc: received message larger than max (5242913 vs. 4194304)"
req 5MiB / default server: code=ResourceExhausted msg="grpc: received message larger than max (5242899 vs. 4194304)"
metadata 16384 KiB: code=Internal msg="stream terminated by RST_STREAM with error code: FRAME_SIZE_ERROR"
```

| 撞的是哪条线 | 报错 | 处置 |
|---|---|---|
| 消息超过 4 MiB（收方向） | `ResourceExhausted`，含「实际 vs 上限」 | 调 `MaxRecvMsgSize`（服务端）/ `MaxCallRecvMsgSize`（客户端）；**收发各自独立、两端各自独立** |
| 头列表超过 16 MiB | `RST_STREAM` + `FRAME_SIZE_ERROR` | 减 metadata 的体积与**条数**（每条另有 +32 字节开销）；调消息限额没用 |

两条容易错的判断：

- **别拿报错里的数字反推载荷**：`5242913` 是「收到的总字节数」，含 gRPC 的 5 字节头与消息其它字段开销；
- **别以为调大消息限额能救头表**：两者在不同层（细节见 [HTTP2机制.md](HTTP2机制.md) 第七节）。

## 七、三类**静默失效**（没有报错，最难查）

**本节要点**：gRPC 有三个「不报错但不生效」的坑——拦截器不生效、探针写死返回值、健康检查与服务状态脱节。它们的共同特征是**日志干净、行为不对**。

### 7.1 服务端一元拦截器不生效

判据：拦截器里打的日志一行都没有；本实验的表现是**空数组**（`interceptor srv: []`）。

根因：`grpc@v1.84.0/server.go:1284` 把 `s.opts.unaryInt` **传进** `md.Handler` 但不替你调，
手写 handler 里缺了那段 `interceptor(ctx, in, info, handler)` 就整条链失效。
**流拦截器不受影响**（框架自己包）。细节与对照表见 [拦截器与元数据.md](拦截器与元数据.md) 第二节。

### 7.2 健康探针写死返回 `SERVING`

判据：依赖的 DB / 下游挂了，K8s 依然认为 Pod 健康（流量还在打进来）。

根因：探针实现里直接 `return SERVING`，与服务真实能力**不同步**。
处置：健康状态要跟着会话能力走（依赖断了置 `NOT_SERVING`），并且**用 gRPC 健康协议而不是 TCP 探活**——
TCP 能连不等于服务可用。清单在 [生态与网关.md](生态与网关.md) 的使用节。

### 7.3 长连接让 LB 长期只往一批 Pod 打

判据：扩容了但新 Pod 流量上不去、老 Pod 一直满。这是**连接复用**的正常后果，不是故障。

处置：给服务端设 `MaxConnectionAge`（配合 `keepalive.ServerParameters`）让连接定期重建，
LB 才有机会重平衡。读数（200 次一元只拨号 1 次）在 [生态与网关.md](生态与网关.md) 第三节。

## 八、被掐断：`GOAWAY` 的两种情况

**本节要点**：`GOAWAY` 不是「网络抖动」，它是**对端明确要求你换连接**；看 debug data 就能区分是「你太吵」还是「我在退出」。

| debug data | 错误码 | 含义 | 处置 |
|---|---|---|---|
| `too_many_pings` | `ENHANCE_YOUR_CALM` | 客户端 ping 频率超过服务端 `EnforcementPolicy.MinTime` | 提高客户端 `Time`，或放宽服务端 `MinTime` |
| `graceful_stop` | `NO_ERROR` | 服务端在优雅退出 | 正常现象，客户端会自动重连到别的实例 |

两条非直觉的事实（都有实测与源码支撑，见 [连接与生命周期.md](连接与生命周期.md) 第三节）：

- **要 3 次违规才 GOAWAY**：源码里 `maxPingStrikes = 2` 而判据是 `pingStrikes > 2`；
- **一个「看起来很宽松」的 `MinTime` 也可能被断**：当连接上**没有活跃流**且服务端没开
  `PermitWithoutStream` 时，判定阈值是写死的 2 小时（`defaultPingTimeout`），与 `MinTime` 无关。

日志里还会有一行现成的提示（grpc-go 默认 logger 打的，实测输出）：

```text
ERROR: [transport] Client received GoAway with error code ENHANCE_YOUR_CALM and debug data equal to ASCII "too_many_pings".
```

## 使用：排查工具箱

**本节要点**：四件套——**反射 + grpcurl** 看服务形状、**打开 grpc-go 日志**看连接层抱怨、**channelz** 看连接与流计数、**自写代理 / Wireshark** 看帧。

### 1. 先把标题打开：`GRPC_GO_LOG_SEVERITY_LEVEL`

grpc-go 平时几乎不打日志，但**连接层的关键事件（GOAWAY、握手失败）是 ERROR 级别的、默认就会打**——
上面那行 `too_many_pings` 就是默认打出来的。要更啰嗦：

```text
GRPC_GO_LOG_SEVERITY_LEVEL=info      # 级别：info / warning / error
GRPC_GO_LOG_VERBOSITY_LEVEL=2        # 详细度（配合 info 用）
```

⚠️ 应用自己实现了 logger 的话，grpc 会写到**应用提供的 logger** 里；
本实验为了逐行可比把 grpc 的 logger 换成了自建缓冲（否则时间戳会污染输出）。

### 2. 看服务形状：反射 + grpcurl

服务端注册 `reflection.Register(srv)`（Java 侧 `ProtoReflectionService`）之后：

```bash
grpcurl -plaintext 127.0.0.1:50051 list                 # 列出服务
grpcurl -plaintext 127.0.0.1:50051 describe demo.Echo   # 看方法与方法签名
grpcurl -plaintext -d '{"seq":1,"body":"hi"}' 127.0.0.1:50051 demo.Echo/Unary
```

手上没有 `.proto` 时这是唯一能「问服务端自己」的路子（口径见 [生态与网关.md](生态与网关.md) 1.3）。
⚠️ 出问题**先 `list`**：连 `list` 都失败说明连接层没通，别再往下调方法。

### 3. 看连接与流的计数：channelz

channelz 能给出「每条连接的流数、收发字节、最后失败原因」，比 `netstat` 有用得多：
`netstat` 只能告诉你「有一条 TCP」，channelz 能告诉你「这条 TCP 上跑了几条流、为什么掉过」。

### 4. 看帧：自写代理或 Wireshark

两者都能看到 `HEADERS` / `DATA` / `GOAWAY` 的帧类型与长度；Wireshark 过滤器与
「明文能解、TLS 要密钥」的边界写在 [HTTP2机制.md](HTTP2机制.md) 的使用节。

### 5. 排障顺序（照这个顺序走，别跳）

```text
1. 报错码是什么层的？（应用层 / HTTP2 / 连接 / DNS / 代理）
2. Unavailable？→ 读 desc：connection refused 还是 goaway 还是 transport is closing
3. 连不上？→ 先证明「名字能解析 + 端口在监听」，再谈 gRPC
4. 连上了但业务报错？→ 用 grpcurl 直连后端，排除网关
5. 直连也报错？→ 看服务端是不是漏了 status.Error（Unknown 的来源）
6. 偶发？→ 打开 grpc-go 日志看有没有 GOAWAY / 握手失败
7. 都正常？→ 怀疑静默失效三连（第七节）
```

## 延伸追问

- **为什么 `Unavailable` 这么难查？** → 它是「筐」：连不上、被 GOAWAY、代理换机器都归它，
  必须读 desc 才能分层（第一节）。
- **`Unknown` 是不是「未知错误」？** → 不是。它几乎专指「服务端返回了非 status 的 error」，
  是排查服务端代码的信号，而不是「底层出了怪事」（第三节 3.2）。
- **网关配置看起来没问题，为什么还失败？** → 看两个方向是不是都配了：
  入口 `http2 on` 只管打进来，出口必须 `grpc_pass`（第四节）。
- **流式为啥总卡？** → 先查半关闭（`CloseSend` / `onCompleted`），再查取消与发送错误；
  服务端的退出条件本来就只在 `io.EOF` 上（第五节）。
- **调大限额为什么没用？** → 先确认撞的是哪条线：消息限额是应用层、头表限额是 HTTP/2 层，
  后者调消息限额一点用都没有（第六节）。
- **没有报错但功能不对，从哪查起？** → 静默失效三连：拦截器接线、探针返回值、LB 与长连接（第七节）。
- **怎么区分「网络抖动」和「被服务端要求换连接」？** → 看 `GOAWAY` 的 debug data：
  `too_many_pings` 是自己的问题，`graceful_stop` 是对方在退出（第八节）。
- **怎么在 CI 里提前拦住这些坑？** → 把「反射 list + 一条一元 + 一条流 + 一条健康 Check」
  做成部署后的冒烟测试，比加日志便宜（使用节）。
