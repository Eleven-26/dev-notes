## 一、拦截器链是怎么串起来的？

**本节要点**：拦截器是洋葱序——**先注册的包在外层**，进入时先跑、返回时后回；客户端与服务端都是同一套语义。

客户端与服务端都是「**先注册的先执行**」（`ChainUnaryInterceptor` 的顺序语义）：

```go
grpc.ChainUnaryInterceptor(a, b, c)   // 顺序：a → b → c → handler → c → b → a
```

先在的拦截器包在外层，进入时先跑、返回时后回。实测输出（`out/base.txt`）：

```text
interceptor cli: [unary-in /demo.Echo/Unary unary-out err=<nil>]
interceptor srv: [unary-in /demo.Echo/Unary unary-out err=<nil>]
```

所以日志、鉴权、指标这类「要先于业务逻辑」的事放在注册顺序的最前面；
而统计最终结果（含错误码）的拦截器应该在心里记住：**它拿到的是内层已处理完的结果**。

三条落地口径：

- **顺序 + 方向**：`ChainUnaryInterceptor`（一元）与 `ChainStreamInterceptor`（流）是**两串独立**的链，
  一个请求走哪串由它是一元还是流决定，不存在「一元链包着流链」这回事；
- **恢复 panic**：拦截器里 `defer recover()` 是**服务端**唯一能把 panic 转成 `Internal` 的地方（不写就是整个进程挂掉）；
- **客户端重试**要在链的最外层之前决定（见第五节），否则内层拦截器会被同一次逻辑调用执行多次。

## 二、服务端一元拦截器为什么常常「静默失效」？

**本节要点**：`grpc@v1.84.0/server.go:1284` 把 `s.opts.unaryInt` **当参数传给** `md.Handler`，但**不会替你调用**——手写 handler 里不写那一句，拦截器整条链静默失效、没有任何报错。

`grpc@v1.84.0` 的 `server.go:1284` 把 `s.opts.unaryInt` **当参数传给** `md.Handler`。
也就是说：只有老式 handler 里显式写 `interceptor(ctx, in, info, handler)` 才会生效——
不写就是**静默失效**。本实验踩过这一点，表现为 `interceptor srv: []` 这种空数组。

生成代码里那段 `if interceptor == nil { ... } else { ... }` 就是干这个的：

```go
// 手写 ServiceDesc 时，这段必须补上 —— 否则 ChainUnaryInterceptor 完全不生效
if interceptor == nil {
	return impl.Unary(ctx, in)
}
info := &grpc.UnaryServerInfo{Server: srv, FullMethod: "/demo.Echo/Unary"}
handler := func(ctx context.Context, req any) (any, error) {
	return impl.Unary(ctx, req.(*Msg))
}
return interceptor(ctx, in, info, handler)
```

对照一下：**流式 handler 不需要自己调**——`ChainStreamInterceptor` 是由框架包在 `stream` 上的。
两条链的行为不一致，是这一段最容易踩的地方（方向标志见下一节）。

## 三、流拦截器与一元拦截器写起来差在哪？

**本节要点**：一元拦截器拿到的就是「一条请求 + 一条响应」，流拦截器拿到的是一个**带方向标志**的 `ServerStream`——`clientStreams` 表示这条流还能收，`serverStreams` 表示还能发，两个标志直接来自 `StreamDesc` 的声明。

流拦截器拿到的 `ServerStream` / `ClientStream` 会带**方向标志**，实测输出：

```text
interceptor stream: [stream-in /demo.Echo/BiDi clientStreams=true serverStreams=true stream-out err=<nil>]
```

`clientStreams=true` 表示这条流还能收消息（客户端流 / 双向流的收侧），
`serverStreams=true` 表示还能发消息（服务端流 / 双向流的发侧）。
一元调用的封装里只有一个消息，所以一元拦截器用起来简单；**流拦截器必须自己处理这两个方向**。

| 项 | 一元拦截器 | 流拦截器 |
|---|---|---|
| 参数 | `(ctx, req, *UnaryServerInfo, handler)` | `(srv, ss, *StreamServerInfo, handler)` |
| 读方向 | 无（恒为一进一出） | `IsClientStream` / `IsServerStream` 两个 bool |
| 流从哪来 | — | 框架包好的 `grpc.ServerStream`，**不用自己调** |
| 拿完整 `Method` 串 | `info.FullMethod` | `info.FullMethod` |

方向写错不只是「拦截器里判断错」——`svc.go` 的注释点了同一条：**运行期会直接报错**。
所以改 handler 时方向标志要和实现一起改。

## 四、超时是怎么传到对端的？

**本节要点**：超时不是「客户端单方面不等了」，而是 **deadline 随请求传到对端**——客户端 60 ms 放弃时，服务端能从 `ctx.Done()` 提前醒来；每一跳不传 `ctx`，预算就断在内层。

超时不是「客户端单方面不等了」，而是 **deadline 随请求传到对端**。实测：

```text
deadline: client 60ms vs handler 300ms -> code=DeadlineExceeded cost=60ms
deadline: 同请求 2s deadline -> code=OK body=echo:slow
```

客户端给 60 ms、handler 睡 300 ms：客户端在 **60 ms 处**就拿到 `DeadlineExceeded`，
而不是等 handler 睡醒。同一个请求把 deadline 放宽到 2 s，就正常返回。

工程约定：**每一跳都要传 ctx**（Go）/ 用同一个 `Context`（Java），
否则内层的超时预算与最外层脱节，「80 ms 的接口实际打了 3 秒」就是这么来的。

服务端侧那条 `select` 才是「提前醒来」的关键——只 `time.Sleep` 不看 `ctx` 的 handler，
即使客户端已经放弃，它也会把活干完：

```go
select {
case <-time.After(time.Duration(in.DelayMs) * time.Millisecond):
	// 正常路径
case <-ctx.Done():
	return nil, ctx.Err()   // 对端已放弃：立刻退出，别把预算烧在无用的活上
}
```

## 五、重试应该配在哪一层、对哪些错误配？

**本节要点**：gRPC **默认不重试**，要重试必须显式配 `retryPolicy`；只对「服务端状态码」这类可重试码 + **幂等方法**开；`ResourceExhausted` 要退避或放弃，不能裸重试。

gRPC **默认不重试**，要重试必须显式配置（service config 的 `retryPolicy` /
Java 侧同名的 service config，或框架自带的策略）。配的时候守两条：

- **只对可重试的状态码**：典型是 `Unavailable`（对端不可达、正在重启）这类「请求可能压根没被处理」的；
- **只对幂等方法**：读接口、或带幂等键的写接口。

**不应该重试的几类**（重试只会放大问题或造成重复写入）：
`InvalidArgument` / `PermissionDenied` / `Unauthenticated` / `Unimplemented` / `NotFound`
这类「重试一百次结果也一样」的错误，以及 `DeadlineExceeded` / `Canceled`
这类「调用方预算已经用光」的错误。`ResourceExhausted`（限流）要格外谨慎：
重试风暴会把已经吃满的对端再压一遍，通常应该退避或直接放弃。

service config 里的形态（`retryPolicy` 只在 gRPC 能识别为「可重试码」时生效）：

```json
{
  "methodConfig": [{
    "name": [{"service": "demo.Echo"}],
    "retryPolicy": {
      "maxAttempts": 3,
      "initialBackoff": "0.1s",
      "maxBackoff": "1s",
      "backoffMultiplier": 2,
      "retryableStatusCodes": ["UNAVAILABLE"]
    }
  }]
}
```

两条容易忘的边界：

- **重试会吃最外层 deadline 的预算**：「重试次数 × 单次超时」必须小于最外层 deadline，
  否则重试还没跑完调用就超时了；
- **网关不能替你做业务级重试**：nginx 的 `grpc_next_upstream` 只在上游「还没开始返回」时换机器
  （见 [生态与网关.md](生态与网关.md) 的使用节）。

## 六、metadata 的透传约定

**本节要点**：metadata 是跨进程唯一能带业务信息的通道；四条约定——**键会小写**、`-bin` 后缀自动 base64、**不放敏感信息**、业务键统一 `x-` 前缀；另外 header 与 trailer 是两条路，可见时机不同。

metadata 是随请求发给对端的键值集合，也是**跨进程**唯一能带着业务信息走的通道。实测：

```text
metadata: err=<nil> respHeader.x-handler=[unary] respHeader.x-md-count=[1] respTrailer.x-trailer-note=[set-in-unary-handler]
```

四条约定：

- **键会小写**：客户端写 `X-Trace-Id`，服务端必须按 `x-trace-id` 查（大写查不到）；
- **`-bin` 后缀走 base64**：二进制值（如序列化后的 token、原型报文）加 `-bin` 后缀，
  框架自动 base64 编解码；
- **不放敏感信息**：metadata 会进日志、进抓包、进网关的错误页——等同于放进明文头部；
- **跨语言统一前缀**：业务键统一用 `x-` 前缀（`x-trace-id` / `x-user-id` / `x-real-ip`），
  避免与 gRPC 自带的 `:authority` / `content-type` / `user-agent` 撞名。

另外注意 header 与 trailer 是两条路：**header 在响应开始前送达，trailer 在流结束后送达**。
上面那行里 `x-handler` 走的是 header（第一个字节就能看到），
`x-trailer-note` 走的是 trailer（必须等流结束），
两者放什么应该按「读端什么时候需要」来定，而不是随手挑一个。

⚠️ Java 侧有两条对应关系要记：**trailer 不能直接写**（要包一层 `ServerCall` 覆写
`close(Status, Metadata)`），而 `Metadata.getAll(key)` 在键不存在时返回 **`null`** 而不是空集合。

## 七、状态码与「富错误」怎么用？

**本节要点**：`codes` 只有 17 个值（含 `OK`）；错误信息走 **trailer**，所以既不占消息体也不会被大响应挤掉；`status.New(...).WithDetails(errdetails...)` 能过 wire 并被客户端解回来；`%w` 包一层 status 会**保住码、丢掉 message 的结构**。

### 7.1 状态码就是这 17 个

`codes.Code(i).String()` 的完整输出（`out/status.txt`）：

```text
    0 OK                   6 AlreadyExists         12 Unimplemented
    1 Canceled             7 PermissionDenied      13 Internal
    2 Unknown              8 ResourceExhausted     14 Unavailable
    3 InvalidArgument      9 FailedPrecondition    15 DataLoss
    4 DeadlineExceeded    10 Aborted              16 Unauthenticated
    5 NotFound            11 OutOfRange
```

（上面为便于阅读重排成三列，实测是逐行 0~16。）

选码的三条经验：

- **`Unknown` 是兜底码**：服务端返回一个非 status 的裸 error，客户端看到的必然是 `Unknown`
  （下一小节有实测）——所以线上刷出 `Unknown` 通常意味着「某个服务端代码忘了包 status」；
- **`Unavailable` 才可重试**，`Internal` 不该裸重试（它是「服务端自己出错了」，多半重试也一样）；
- **业务「找不到」用 `NotFound`**，不要拿 `InvalidArgument` 顶——调用方要靠码做分支。

### 7.2 错误详情能过 wire，而且走的是 trailer

服务端造一个带详情的错误：

```go
st := status.New(codes.InvalidArgument, `field "page": must be > 0`)
st, err := st.WithDetails(
	&errdetails.BadRequest{FieldViolations: []*errdetails.BadRequest_FieldViolation{
		{Field: "page", Description: "must be > 0"},
	}},
	&errdetails.ErrorInfo{
		Reason:   "INVALID_PAGE",
		Domain:   "grpclab",
		Metadata: map[string]string{"request_id": "abc123"},
	},
)
return nil, st.Err()
```

客户端侧实测（`out/status.txt`）：

```text
   FromError: ok=true code=InvalidArgument msg="field \"page\": must be > 0"
   Details 个数=2
   [0] *errdetails.BadRequest violations=1 -> {page: must be > 0}
   [1] *errdetails.ErrorInfo reason=INVALID_PAGE domain=grpclab metadata=map[request_id:abc123]
   trailer 里的 grpc-status-details-bin: 条数=1 非空=true（status 走 trailer，不进消息体）
```

三条结论：① `WithDetails` 里的类型过 wire 后能被 `st.Details()` **解回具体类型**（断言即可用）；
② 详情装在 trailer 的 `grpc-status-details-bin` 里，**不占消息体**，所以服务端返回大响应时它照样能传到；
③ 客户端只要用 `status.FromError` 就能同时拿到码、message 与详情，不需要额外约定错误体。

### 7.3 三种「错误包装」的反例

```text
   裸 errors.New("boom")            : ok=true code=Unknown msg="boom"
   fmt.Errorf("%w", status.Error)   : ok=true code=NotFound msg="service layer: rpc error: code = NotFound desc = no such key: 7"（grpc-go 会 unwrap）
   普通 error 直接喂 FromError       : ok=false code=Unknown msg="not a status"
   业务侧 status.Error(NotFound)     : ok=true code=NotFound msg="no such key: 1" Is(NotFound)=true
```

逐条读：

- **裸 error 到客户端就是 `Unknown`**——服务端框架替你包了一层，码丢了、message 还在。
  所以「服务端明明返回了业务错误，客户端只看到 Unknown」的根因通常在**服务端没包 status**；
- **`fmt.Errorf("%w", status.Error(...))` 会 unwrap 出码**（这里是 `NotFound`），
  但 `message` 变成了整条链的字符串（`service layer: rpc error: code = NotFound desc = ...`）——
  想给前端一个干净的错误文案，就别把 status error 再包一层；
- **`status.FromError` 的 `ok` 只说明「这个 error 实现了 `GRPCStatus()`」**，不代表它是业务错误；
  真正想区分「是不是我已定义的业务错误」，用 `errors.Is` 比码更准（最后一行 `Is(NotFound)=true`）。

## 使用：Go 与 Java 的拦截器 / metadata 写法对照

**本节要点**：一份可抄的对照表——链的顺序、header 与 trailer 的写法、deadline 的传法，两侧各有几处不能想当然的地方。

### Go 侧

```go
// 服务端：一元链按注册顺序由外到内；流另有一串
srv := grpc.NewServer(
	grpc.ChainUnaryInterceptor(serverAuth, serverLog),
	grpc.ChainStreamInterceptor(serverStreamAuth),
)

// 一元拦截器：拿 metadata、写 header 与 trailer
func serverLog(ctx context.Context, req any, info *grpc.UnaryServerInfo, h grpc.UnaryHandler) (any, error) {
	md, _ := metadata.FromIncomingContext(ctx)
	_ = grpc.SetHeader(ctx, metadata.Pairs("x-handler", "unary", "x-md-count", fmt.Sprint(len(md.Get("x-trace-id")))))
	_ = grpc.SetTrailer(ctx, metadata.Pairs("x-trailer-note", "set-in-unary-handler"))
	return h(ctx, req)
}

// 客户端：发 metadata + 设 deadline
ctx = metadata.AppendToOutgoingContext(ctx, "x-trace-id", "t-1")
ctx, cancel := context.WithTimeout(ctx, 60*time.Millisecond)
defer cancel()
var header, trailer metadata.MD
err := conn.Invoke(ctx, "/demo.Echo/Unary", in, out, grpc.Header(&header), grpc.Trailer(&trailer))
```

### Java 侧

```java
// 服务端：拦截器自带一个 Metadata 参数，顺序用 ServerInterceptors.intercept 串
ServerInterceptor auth = new ServerInterceptor() {
  @Override
  public <ReqT, RespT> ServerCall.Listener<ReqT> interceptCall(
      ServerCall<ReqT, RespT> call, Metadata headers, ServerCallHandler<ReqT, RespT> next) {
    // ⚠️ 不要在拦截器里直接 call.sendHeaders(...)：
    //    一元 handler 首次 onNext 会撞 "sendHeaders has already been called"（实测踩过）
    return next.startCall(call, headers);
  }
};
Server server = ServerBuilder.forPort(50051)
    .addService(ServerInterceptors.intercept(new EchoImpl(), auth))
    .build();

// 客户端：附 metadata + 设 deadline
Metadata md = new Metadata();
md.put(Metadata.Key.of("x-trace-id", Metadata.ASCII_STRING_MARSHALLER), "t-1");
String resp = ClientCalls.blockingUnaryCall(
    channel, UNARY, CallOptions.DEFAULT.withDeadlineAfter(60, TimeUnit.MILLISECONDS).withExtraHeaders(md),
    "{\"body\":\"hello\"}");
```

### 逐项对照

| 动作 | Go | Java |
|---|---|---|
| 一元拦截器链 | `grpc.ChainUnaryInterceptor(a, b)` | `ServerInterceptors.intercept(svc, a, b)` |
| 流拦截器链 | `grpc.ChainStreamInterceptor(...)` | 同一个 `intercept(...)`，按 `ServerCallHandler` 分类 |
| 一元服务端拦截器是否要自己调 | **要**（`server.go:1284` 只传不调） | 不要，由 `ServerCallHandler` 包住 |
| 读取请求 metadata | `metadata.FromIncomingContext(ctx)` | 拦截器的第二个参数 `headers` |
| 写响应 header | `grpc.SetHeader(ctx, md)` | 覆写 `ServerCall.sendHeaders(...)` |
| 写 trailer | `grpc.SetTrailer(ctx, md)` | **包一层 `ServerCall` 覆写 `close(Status, Metadata)`** |
| 客户端发 metadata | `metadata.AppendToOutgoingContext(ctx, k, v)` | `CallOptions.withExtraHeaders(md)` |
| 客户端设超时 | `context.WithTimeout(ctx, d)` | `CallOptions.withDeadlineAfter(d, unit)` |
| 取 trailer | `grpc.Trailer(&md)` | `ClientCall.getTrailer()` / observer 里的 `Metadata` |
| `Metadata.getAll` 键不存在 | 返回空切片 | 返回 **`null`** |

Java 侧的完整实现与依赖版本见 [接入gRPC.md](../../../../01-编程语言/java/接入gRPC.md)。

## 延伸追问

- **拦截器里能改 metadata 吗？** → 能，但要分清方向：入站拦截器改的是「对端发来的」；
  要影响回包得往 header / trailer 里塞，两者的可见时机不同（第六节）。
- **为什么服务端一元拦截器不生效、却没有任何报错？** → 框架只把 `unaryInt` 传进 `md.Handler` 不替你调，
  合成代码里那段 `if interceptor == nil` 才是开关；缺了它就是空链（第二节）。
- **流拦截器会不会也「静默失效」？** → 不会。流那条链由框架包在 `ServerStream` 上，
  但**方向标志**写错会在运行期直接报错，而不是静默（第三节）。
- **`DeadlineExceeded` 和 `Canceled` 有什么区别？** → 前者是「预算到了」，后者是「有人主动撤了」
  （比如客户端提前 `cancel()` 或上游断开）；两者都不该重试。
- **重试和 deadline 冲突怎么办？** → 重试会消耗最外层 deadline 的预算，
  所以「重试次数 × 单次超时」必须小于最外层 deadline，否则重试还没跑完调用就超时了（第五节）。
- **客户端拿到 `Unknown` 该往哪查？** → 先查服务端是不是漏了 `status.Error(...)`（第七节的反例第一行）；
  框架对裸 error 一律兜底成 `Unknown`。
- **为什么 trailer 比 header 难写？** → header 在响应开始前就能发，trailer 必须等流结束；
  Java 侧因此要包一层 `ServerCall`，Go 侧则是一条 `grpc.SetTrailer`。
- **富错误要传结构化业务数据，该用 details 还是塞进 message？** → 用 details：
  它在 trailer 里、与消息体解耦、客户端能按类型断言；塞进 message 就只能靠解析字符串。
