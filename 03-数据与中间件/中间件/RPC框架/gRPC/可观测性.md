# gRPC 可观测性

> trace / metrics / log 三件套在 gRPC 里各落在哪、埋点位置为什么就是拦截器（或 StatsHandler）、语义约定里该写哪些属性、以及健康检查 / 反射 / channelz 这三个「另外的可观测面」。

>
> ⚠️ **未实测声明（三段式）**：
> **归属**：本篇所有结论来自 grpc-go / grpc-java 的公开接口与 OpenTelemetry 语义约定，不含本书或视频素材；
> **范围与边界**：只讲「在哪埋、埋什么、埋的陷阱」，不讲后端（Jaeger / SkyWalking / Prometheus）的部署与选型；
> **✅ 实测口径**：**无**——本实验台从头到尾**没有接入任何 tracing / metrics 后端**，所以本篇出现的库名、属性名、参数名都不是读数；
> **⚠️ 仍未实测**：`otelgrpc` 的实际产出、指标分桶在真实负载下的表现、采样率对可见性的影响——这三项**没有跑过**，不要引用成本篇的实测。

## 一、三件套在 gRPC 里各落在哪？

**本节要点**：gRPC 的可观测性没有「框架自带面板」——三件套都要**自己在拦截器那一层埋**；而埋点位置的统一答案是：**一元链 + 流链 + StatsHandler**。

| 件 | 要回答的问题 | 在 gRPC 里的落点 | 关键约束 |
|---|---|---|---|
| trace | 「这一次慢/错在链路的哪一跳」 | 客户端与服务端的拦截器（或 `StatsHandler`） | 上下文要**跨进程传播**，靠 metadata |
| metrics | 「整体健康度与趋势」 | 同样在拦截器里累加 | **标签基数**是唯一能把它搞垮的东西 |
| log | 「这一次具体发生了什么」 | 业务代码 + 拦截器兜底 | 必须带 `trace_id` 才能和上面两件串起来 |

⭐ 一句话判据：**trace 是抽样的事件流（贵、要采样）、metrics 是全量的聚合（便宜、要高基数警惕）、log 是完整的细节（最贵、要分级）**。
三者的取舍不同，所以不能「只接一件」——最常见的组合是 **metrics 兜底 + trace 抽样 + log 分级**。

## 二、trace：span 从哪来、属性写什么、上下文怎么传

**本节要点**：span **不需要在业务 handler 里手建**——服务端插桩会为每个 RPC 建好 root span，业务代码拿到的是「已经带 span 的 ctx」；跨进程传播靠 metadata，而这正是拦截器天生擅长的事。

### 2.1 埋点位置：StatsHandler 优先于拦截器

Go 侧主流有两套接法：

| 接法 | 形态 | 现在的建议 |
|---|---|---|
| `otelgrpc.NewServerHandler()` / `NewClientHandler()` | **`grpc.StatsHandler`** | 较新、信息更全（能拿到更细的连接与流事件） |
| `otelgrpc.UnaryServerInterceptor()` / `StreamClientInterceptor()` 等 | **拦截器** | 老写法，仍在用；新项目优先上一行 |

⚠️ **这套 API 正在迁移**：老代码里 `grpc.WithUnaryInterceptor(otelgrpc.UnaryClientInterceptor(...))` 是标准写法，
但新版已把重心移到 `StatsHandler`。**接之前先确认所用版本导出的是哪一组**——
两个都是真存在的接口，混用会出现「只埋了一半（一元有、流没有）」这类问题。

Java 侧对应的是 `io.opentelemetry.instrumentation` 的 grpc 模块提供的 `GrpcTelemetry`，
在 `ServerBuilder.intercept(...)` / `ManagedChannelBuilder.intercept(...)` 挂上去，形态与 Go 的拦截器一一对应。

### 2.2 属性写什么：别的模块要能对上

OpenTelemetry 的 RPC 语义约定里，**客户端与服务端 span 都要带的**几个属性是排障的骨架：

| 属性 | 说明 | 为什么必须有 |
|---|---|---|
| `rpc.system` | 例如 `grpc` | 后端能按协议聚类；HTTP 与 gRPC 的看板不同 |
| `rpc.service` | 服务全名（`demo.Echo`） | 与 `:path` 的第一段一致，能和日志对上 |
| `rpc.method` | 方法名（`Unary`） | 与 `:path` 的第二段一致 |
| `rpc.grpc.status_code` | 数字状态码 | 用**数字码**而不是字符串，便于聚合 |

⚠️ **status code 这一项最容易漏**：RPC 失败时 span 的 `status` 与 `rpc.grpc.status_code` 是两处信息，
只记前者会丢掉「到底是 `NotFound` 还是 `Unavailable`」——而这两者的处置完全不同
（见 [故障排查与调试.md](故障排查与调试.md) 第三节）。

### 2.3 上下文传播：就在 metadata 里

trace 的父子关系靠 **`grpc` 的 metadata** 跨进程携带（W3C Trace Context 或 B3 格式），
`otelgrpc` 的插桩自动完成注入与提取——**前提是链路上的每一跳都装了插桩**。

**断链的两个典型位置**：

- **自己手写的 handler / 自研网关**：绕过拦截器直接调 `conn.Invoke`，注入就没了；
- **producer / consumer 这类异步边界**：消息从队列出来时 trace 上下文已经不在 ctx 里，
  要显式把它塞进消息头再取出来。

排查「链路断在中途」的判据：看下游服务的 span 是不是**有独立 trace_id**——
是的话说明上下文没传过来，而不是「后端丢数据」。

### 2.4 采样

> ⚠️ 本节为官方口径，**未实测**。

- **头采样 vs 尾采样**：头采样在入口决定（便宜，但会丢掉「慢请求」）；尾采样等这次调用结束再决定
  （能保「错误必采」，代价是要在链路里缓冲 span）；
- **gRPC 的判据与 HTTP 相同**：错误率高的接口必须**必采**，否则「偶发的 `Unavailable`」永远看不见——
  而它正是 gRPC 里最需要 trace 的那类问题。

## 三、metrics：只记这几类就够

**本节要点**：gRPC 的指标要按「**方法 × 状态码**」两个维度切才可用；而**基数**是它唯一的致命风险——把 `user_id` 这类东西放进标签等于自杀。

### 3.1 一张必记清单

| 指标 | 维度 | 回答什么 |
|---|---|---|
| 请求量 / 错误量 | method、status_code | 「哪个方法在报错、报什么错」 |
| 请求耗时（histogram） | method、（可选）status_code | P50/P99 与「长尾在哪」 |
| 在途请求数（gauge） | method | 「是不是被慢请求占满了」 |
| 连接数 / 活跃流数 | — | 「连接有没有被复用、流有没有泄漏」 |
| 消息大小（histogram） | 方向（收/发） | 「什么时候会撞 4 MiB 限额」 |
| 连接状态 / GOAWAY 计数 | 原因 | 「连接受不受 keepalive 与滚动更新影响」 |

⭐ **最后两行很容易被忽略但很值**：消息大小的分布能提前预警限额撞线
（[HTTP2机制.md](HTTP2机制.md) 第七节）；`GOAWAY` 计数能区分「网络抖动」与「自己的 keepalive 太激进」
（[连接与生命周期.md](连接与生命周期.md) 第三节）。

### 3.2 基数是最大的坑

- **绝对不能进标签**：`user_id`、`trace_id`、`request_id`、原始 `:path`（把变量拼进路径就爆炸）、
  错误 message（长度与取值都不可控）；
- **可以进标签**：`method`（**收敛后的**，别用全路径）、`status_code`、连接状态；
- **怎么收敛**：方法名数量本身可控，但**路径里带 ID 的 REST 风格接口**必须先在网关层做模板化
  （`/orders/{id}` → `/orders/:id`），否则 `method` 这一维照样爆。

判据：**「这个标签的取值集合会不会随请求量增长？」会 → 不进标签，进 trace 或日志。**

### 3.3 直方图分桶

> ⚠️ 本节为官方口径，**未实测**。

RPC 耗时的分布通常是**双峰甚至三峰**的：接口本身的耗时（ms 级）、下游超时/重试（百 ms~秒级）、
连接问题（秒级以上）。默认线性分桶会把前两峰挤在头几个桶里，**P99 直接失真**。

一句话判据：**分桶要覆盖到「你的超时值」**（比如超时 3 s，桶就要有 3 s 附近的边界）；
否则「P99 = 200 ms」可能只是「桶不够，超时的那些都被塞进最后一个桶」。

## 四、log：三件套里最贵的一件

**本节要点**：日志必须能**单独定位一次调用**，所以 `trace_id` 是必需品；同时**别打 payload**——gRPC 的 metadata 与消息体里有 token 与用户数据。

四条落地口径：

- **带 `trace_id` / `span_id`**：日志里没有它，trace 与 log 就串不起来，
  三件套退化成三套孤立的系统；
- **别打 metadata 全量**：里面有 `authorization`、`x-user-id` 这类信息（[拦截器与元数据.md](拦截器与元数据.md) 第六节已经写过
  「metadata 等同于明文头部」）；要打就白名单字段；
- **别打消息体**：gRPC 的消息可能是几 MiB（限额 4 MiB），打全量既贵又可能含个人信息；
  要留证据就留**长度 + 摘要**；
- **错误日志只打一次**：拦截器兜底 + 业务层各打一遍是最常见的重复来源，
  建议约定「**谁包的 status，谁负责打**」。

## 五、另外三个「可观测面」

**本节要点**：健康检查、反射、channelz 严格说不是三件套，但它们回答了「服务活着吗 / 它有哪些方法 / 连接现在什么状态」——都是排障时最先要的三句话。

| 面 | 名字 | 回答什么 | 边界 |
|---|---|---|---|
| 健康检查 | `grpc.health.v1.Health`（`Check` / `Watch`） | 「这个实例现在能不能服务」 | 必须与服务真实能力同步，否则等于没探（见 [故障排查与调试.md](故障排查与调试.md) 第七节） |
| 反射 | `grpc.reflection.v1` | 「它注册了哪些服务与方法」 | 生产环境可关（会暴露内部接口形状）；排障期开 |
| channelz | grpc-go / grpc-java 内建 | 「每条连接的流数、收发字节、最后失败原因」 | 比 `netstat` 有用得多，但**要自己去读它的 API 或页** |

⭐ 三者的共同点：**它们走同一个端口、同一次连接**，不需要另开 HTTP 端点——
这正是「gRPC 服务不需要额外的运维接口」的原因（[生态与网关.md](生态与网关.md) 1.3）。

## 使用：Go 侧接入骨架与指标清单

**本节要点**：一段可直接改的骨架——服务端与客户端各挂一个 `StatsHandler`，再自己加一个业务拦截器补「方法级」的东西。

> ⚠️ 下面这段**未实测**：本实验台没有接后端，代码按公开接口写，**没有跑过**。
> 尤其是 `otelgrpc` 在「StatsHandler」与「拦截器」两套 API 之间的取舍，**接之前先核你所用版本的导出符号**。

### 服务端 / 客户端

```go
import (
	"go.opentelemetry.io/contrib/instrumentation/google.golang.org/grpc/otelgrpc"
	"google.golang.org/grpc"
)

// 服务端：插桩为每个 RPC 建 root span，并提取上游传来的 trace 上下文
srv := grpc.NewServer(
	grpc.StatsHandler(otelgrpc.NewServerHandler()),
	grpc.ChainUnaryInterceptor(myBizMetrics), // 自己补 method 维度的指标
)

// 客户端：插桩会注入当前 trace 上下文 + 记录 client span
conn, _ := grpc.NewClient(target,
	grpc.WithStatsHandler(otelgrpc.NewClientHandler()),
	grpc.WithTransportCredentials(creds),
)
```

### 指标清单（按 3.1 的表抄）

```text
# 命名建议：统一前缀 + 单位后缀，别把单位藏进名字
grpc_server_requests_total{method, status_code}
grpc_server_request_duration_seconds{method}            # histogram
grpc_server_inflight_requests{method}                   # gauge
grpc_client_requests_total{method, status_code}
grpc_client_request_duration_seconds{method}            # histogram
grpc_message_size_bytes{direction}                      # histogram
grpc_connections_total / grpc_connections_active
grpc_goaway_total{reason}                               # too_many_pings / graceful_stop / ...
```

### Prometheus 侧的插桩

grpc-ecosystem 有一套 gRPC 的 Prometheus 插桩中间件（提供 interceptor 与 `promhttp` 的对接）——
⚠️ **module path 与包结构在 v1 → v2 之间改过**，本篇不写死导入路径，
**接之前用 `go get` 核一下当前 module path**（本仓另一条同类经验：库名先查实再动笔）。

## 延伸追问

- **trace 和 metrics 能不能只接一个？** → 能，但取舍不同：metrics 便宜、能全量、看不出「哪一次慢」；
  trace 贵、要采样、能定位单次调用。实践里最常见是「metrics 兜底 + trace 抽样」。
- **为什么服务端 handler 里不用手建 span？** → 插桩已经为每个 RPC 建好了 root span，
  业务代码拿到的是带 span 的 ctx；手建会变成「span 套 span」，链路上多一层噪音。
- **哪个接口该 100% 采样？** → 错误率高的与关键路径上的；
  「偶发的 `Unavailable`」这类问题只有在必采的策略下才会留下证据（2.4）。
- **为什么 `method` 能当标签、`:path` 不行？** → 方法名集合是**有限且稳定**的；
  带 ID 的原始路径取值会随请求量增长，直接把时间序列数量顶爆（3.2）。
- **日志为什么必须带 `trace_id`？** → 不带就串不起三件套；trace 里看到一次慢调用却找不到对应日志，
  是这个坑最常见的表现（第四节）。
- **健康检查服务挂了还能被发现吗？** → 只有它的状态与服务真实能力同步时才有意义；
  写死返回 `SERVING` 等于没探（第五节）。
- **生产要不要开反射？** → 看场景。它方便 grpcurl 排障，但会暴露内部服务形状；
  常见做法是「内网开、公网关」，或只在排障窗口开。
- **消息大小为什么要记 histogram？** → 它能提前预警 4 MiB 限额撞线，
  而这正是最容易在业务增长后突然出现的故障（3.1）。
