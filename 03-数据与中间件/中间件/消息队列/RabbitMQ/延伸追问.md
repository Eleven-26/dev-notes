# 延伸追问

> 覆盖：把本目录六篇里最常被连环追问的问题集中成一页，每条给「一句话结论 + 指向详解」。**它的作用是暴露缺口，不是第一次学习**——建议读完前六篇后再回来。

## 一、定位与概念

- **RabbitMQ 和 Kafka / RocketMQ 最根本的差别是什么？** → **路由在 Broker、消费即删**。Kafka/RocketMQ 的「消息去哪儿」由生产者选分区决定，消息按保留策略留在日志里可重放；RabbitMQ 由 Broker 上的绑定表决定，ack 即删除。见 [核心概念与架构.md](核心概念与架构.md) 第一节。
- **Connection 和 Channel 到底怎么分工？** → Connection 是 TCP，Channel 是这条 TCP 上的多路复用虚拟连接；几乎所有 API 在 Channel 上，⚠️ **Channel 不是线程安全的**。见 [核心概念与架构.md](核心概念与架构.md) 第二节。
- **为什么 Channel 不是线程安全的？** → AMQP 帧头里只有 `channel id`、没有请求 id，两个线程同时写会把两段命令序列交错，Broker 无法区分谁是谁。
- **vhost 是什么，和数据库的 database 一样吗？** → 类似但更彻底：自带一套 Exchange/Queue/Binding，**跨 vhost 不能直接绑定**，权限也以 vhost 为粒度。连接串里 `/` 要写成 `%2F`。
- **一台机器能跑多少队列？** → 没有硬上限，但**每个队列一个 Erlang 进程**，几万个队列会让调度与内存压力明显上升。不要按「每用户一个队列」设计。

## 二、路由与交换机

- **四种交换机怎么一句话区分？** → direct 比字符串相等、fanout 不比（广播）、topic 按 `.` 分词做 `*`/`#` 通配、headers 比消息头键值。见 [核心概念与架构.md](核心概念与架构.md) 第三节。
- **`*` 和 `#` 的差别？** → `*` **恰好一个**词，`#` **零到多个**词。`order.*.created` 不匹配 `order.created`，而 `order.#` 匹配 `order`。
- **一次发布会落进几个队列？** → 零到多个，**与发布次数无关**。实测：3 条消息打进 4 个交换机（12 次发布）共产生 **15 条落点**，其中 `q.direct.paid` 是 0 条。
- **没有队列匹配会怎样？** → ⚠️ **静默丢弃**，`basicPublish` 不报错。要感知必须 `mandatory=true` 并监听 `basic.return`。
- **`headers` 交换机什么时候用？** → 几乎不用。它每次路由都逐个头比对、无法建索引，规则藏在消息头里排障困难；能用 topic 表达就别用它。
- **默认交换机 `""` 是什么？** → 每个队列自动绑定的系统交换机，BindingKey 就是队列名，所以 `basicPublish("", "queueName", …)` 等价于直投该队列。

## 三、队列类型与延迟

- **classic / quorum / stream 怎么选？** → 业务消息默认 **quorum**（多副本）；需要优先级或惰性模式时才用 classic；需要「按 offset 重读」用 stream。见 [队列类型与消息模式.md](队列类型与消息模式.md) 第一节。
- **镜像队列还能用吗？** → ❌ **4.0 已移除**。它基于 Mnesia 异步复制，故障切换可能丢已 ack 的消息；quorum 用 Raft 把「多数派写入」写进 ack 条件。
- **quorum 为什么要求奇数节点？** → 3 节点容忍 1 个故障，4 节点也只能容忍 1 个（多数派是 3）却多一份开销。按 3 / 5 / 7 规划。
- **延迟消息怎么做、有什么坑？** → 两条路：① TTL + DLX，不装插件但有**队头阻塞**（实测：1 秒 TTL 的消息实际等了 **6.0 秒**）；② `rabbitmq_delayed_message_exchange` 插件，支持任意延迟但消息暂存在交换机里、官方镜像**不内置**。见 [队列类型与消息模式.md](队列类型与消息模式.md) 第三节。
- **队列级 TTL 和消息级 `expiration` 有什么区别？** → 队列级对所有消息生效，消息级只对单条生效；**两者都只在队头判定**，所以都受队头阻塞影响。
- **DLX 什么时候触发？** → 三个条件：被 reject/nack 且 `requeue=false`、消息 TTL 过期、队列达到 `x-max-length` 上限被挤出。**死信不等于消费失败**。
- **`x-max-length` 超限时丢头还是拒新？** → 由 `x-overflow` 决定：`drop-head`（默认，进 DLX）、`reject-publish`（拒新，Confirm 会 nack）、`reject-publish-dlx`（拒新并转投 DLX）。

## 四、可靠性与一致性

- **怎么保证消息不丢？** → 三段都要管：生产端 **Publisher Confirm**（异步确认 + 失败重发，别用事务）；Broker 端 `durable` **+** `delivery_mode=2` **+** quorum 多副本；消费端 `autoAck=false`、**先处理再 ack**。见 [消息可靠性.md](消息可靠性.md) 第一节。
- **只设 `durable=true` 够吗？** → ❌ 不够。实测：`durable=true` + `delivery_mode=1` 的队列重启后**队列还在、消息变 0 条**；反过来队列不持久则重启后**队列整个不存在**。
- **`basic.ack`（Confirm）和 `basicAck`（消费确认）是一回事吗？** → ❌ 完全不是。前者是 Broker 告诉生产者「我收下了」，后者是消费者告诉 Broker「我处理完了」。两个确认点在链路两端。
- **Confirm 收到 ack 就一定安全了吗？** → 不一定。`basic.ack` 只代表「Broker 接受」；classic 队列若只落 PageCache 未刷盘，掉电仍可能丢。要用 quorum 压到最低。
- **为什么 quorum 队列在少数派下发布还「成功」？** → 因为 AMQP 的 publish 是**单向命令**，写完 socket 就返回；提交要等多数派。这就是**必须开 Confirm** 的直接理由。
- **消息重复怎么办？** → RabbitMQ 只保证 **at-least-once**，中间件不去重。消费端幂等：唯一索引 / 去重表 / `SETNX` / 状态机 CAS；⚠️ **去重键用业务唯一键，不要用消息 ID**。
- **`requeue=true` 有什么坑？** → 消息**回队头**，失败原因与内容相关时会无限重入队、CPU 空转。应 `requeue=false` 进死信 + 限次 + 告警。

## 五、消费与排障

- **prefetch 限制的是什么？** → **这个 Channel 上未 ack 的条数**，不是速率。不设（默认 0 = 不限）时 Broker 会把队列消息一次推完。见 [消费者与投递语义.md](消费者与投递语义.md) 第二节。
- **不设 prefetch 会怎样？有实测吗？** → 实测：20 条消息、慢消费者 150ms/条，`prefetch=0` 时慢消费者拿走 **20 条**、快消费者 **0 条**、耗时 **3.0s**；`prefetch=1` 时变成 **3 / 17**、耗时 **0.5s**——快 6 倍。
- **`basic.qos` 的 `global` 参数是什么？** → `false`（推荐）按消费者配额，`true` 按 Channel 共享配额。⚠️ 3.x 曾反过一次语义，老客户端要确认。
- **为什么消费会「莫名卡住」？** → 先看 `consumer_timeout`（默认 **30 分钟**）：超时不 ack 会被强制关闭 Channel，报 `delivery acknowledgement on channel N timed out`。长任务要拆或调大。
- **断线重连后要注意什么？** → ⚠️ **必须重建 Channel 并重设 `basic.qos`**。Java 的 `automaticRecoveryEnabled` 会做；Go 的 `amqp091-go` **什么都不做**，要自己监听 `NotifyClose` 全套重建。
- **`list_queues` 的 `state=running` 可信吗？** → ⚠️ **不可信**。实测 quorum 队列只剩 1/3 节点时它仍报 `running`，真相在 `quorum_status` 的 Raft State（`noconnection`）与消费报 `nodedown`。见 [运维与排障.md](运维与排障.md) 第三节。
- **发布返回成功但队列没涨，怎么回事？** → Broker 内存/磁盘告警触发了 **connection.blocked**。⚠️ `basicPublish` 照样返回 `nil`；实测告警期间发 1 条队列 0 新增，连发 20000 条 8.0s 没发完，告警解除后缓冲的 114 条一次性补投。
- **管理台登录后看不到队列？** → vhost 选错。右上角切 vhost，或 URL 里指定；`guest` 还只能从 localhost 登录。

## 两条答题链

**链一：从「消息会不会丢」一路问到「怎么证明它没丢」**

> 不丢的三段（[消息可靠性.md](消息可靠性.md) 第一节）→ 生产端的 Confirm 不是事务（第二节）→ Broker 端 durable × delivery_mode 四组合（第三节，实测 2→0 / 队列消失）→ quorum 多数派与少数派下的「假成功」（第四节）→ 既然只保证 at-least-once，幂等落消费端（第六节）→ 排障时怎么区分「没发出去」和「没落盘」（[运维与排障.md](运维与排障.md) 第二节的 blocked 读数）。

**链二：从「消费慢」一路问到「是加机器还是改参数」**

> 没有位点、只有未 ack 集合（[消费者与投递语义.md](消费者与投递语义.md) 第一节）→ prefetch 是欠账上限不是速率（第二节，实测 20/0 与 3/17）→ `global` 参数的作用域（第三节）→ 消费者卡住的两个原因：prefetch 与 `consumer_timeout`（第六节）→ 堆积的三层读数与处置顺序（[运维与排障.md](运维与排障.md) 第一节）→ 最后才谈扩容。
