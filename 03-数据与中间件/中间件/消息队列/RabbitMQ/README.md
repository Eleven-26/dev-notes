## 一、一句话定位与适用场景

RabbitMQ 是基于 **AMQP 0-9-1** 协议的开源消息代理，**Erlang 编写**（借 Erlang 的轻量进程做并发，单机万级到十万级 msg/s、延迟低），以**交换机 + 绑定 + 路由键三方解耦的路由能力**著称。

| 场景 | 落点 |
| --- | --- |
| 业务解耦 | 上游只发 Exchange，下游各自绑定自己的队列，加下游不改上游代码 |
| 按维度订阅 | topic 交换机的 `*` / `#` 通配让「按业务线 + 事件类型」组合订阅成为配置而非代码 |
| 广播与缓存刷新 | fanout 交换机一条消息复制进 N 个队列，各队列独立消费 |
| 延迟任务 | TTL + DLX 或 `rabbitmq_delayed_message_exchange` 插件（见 [队列类型与消息模式.md](队列类型与消息模式.md) 第三节） |
| 低延迟业务消息 | 单条消息的路由在 Broker 内存里完成，不落「先写日志再建索引」的两段 |

> ⭐ 一句话记忆：**RabbitMQ 把「消息去哪儿」从生产者代码里搬到了 Broker 的绑定表里；代价是这条路由链没有位点，消费即删。**

## 二、核心概念速览

| 概念 | 一句话 |
| --- | --- |
| **Connection** | 客户端到 Broker 的 **TCP 长连接**，一个进程通常只需一条 |
| **Channel** | ⭐ 复用在同一条 TCP 连接上的**虚拟连接**，绝大部分 API 都在 Channel 上；⚠️ **非线程安全** |
| **Exchange** | 接收生产者消息、按绑定规则路由到一个或多个队列；生产者**从不直接投队列** |
| **Queue** | 实际存储消息的实体，FIFO；**ack 后消息即删除**（消费即删，不能回溯） |
| **Binding** | Exchange 与 Queue 之间的连接关系，可带 BindingKey / 参数 |
| **RoutingKey / BindingKey** | 发送时指定 / 绑定时声明；direct 要求相等，topic 按通配匹配 |
| **VHost** | 逻辑隔离单元，自带一套 Exchange / Queue / Binding；⭐ 权限也以 vhost 为粒度 |
| **DLX** | 死信交换机：消息被拒、TTL 过期、队列超长时转投的兜底目标 |

> ⭐ **铁律：路由在 Broker 端完成。** 生产者只认 Exchange 与 RoutingKey，队列是「被绑定」出来的；这与 Kafka / RocketMQ「生产者选分区」是两种模型。

七条最值得记住的读数：

| 读数 | 值 | 出处 |
| --- | --- | --- |
| 12 次发布只产生 15 条落点 | 同一批 3 条消息打进 4 个交换机：`direct` 命中 1/2，`fanout` 2 个队列各 3 条，`topic` 三条绑定键分别 1/2/1，`headers` 的 `all`/`any` 分别 1/3 | [核心概念与架构.md](核心概念与架构.md) 第三节 |
| 1000 B 的消息完全不进内容存储 | 200 条 1000 B：`0.qi` 6464 / `0.qs` 233664 / 内容存储增量 **0**；再 200 条 5000 B：`0.qi` +6400（=200×32）、内容存储 +1037000 | [存储与投递过程.md](存储与投递过程.md) 第二节 |
| ack 之后内容存储一个字节都不少 | 400 条全部逐条 ack 后 `0.qi`/`0.qs` 整段消失，`msg_store_persistent` 差值 **0** | [存储与投递过程.md](存储与投递过程.md) 第三节 |
| 1 秒 TTL 的消息等了 **6.0 秒** | 队列级 `x-message-ttl=6000`，队内后两条 `expiration=1000`；t=6.0s 时三条一起进死信队列 | [队列类型与消息模式.md](队列类型与消息模式.md) 第三节 |
| `durable` 与 `delivery_mode` 缺一不可 | 重启后：`durable+persistent` 2→2；`durable+transient` 2→**0**；非持久队列**整个不存在** | [消息可靠性.md](消息可靠性.md) 第三节 |
| 不设 prefetch，快消费者一条也拿不到 | 20 条、慢消费者 150ms/条：`prefetch=0` 时 A=20 / B=0、耗时 3.0s；`prefetch=1` 时 A=3 / B=17、耗时 0.5s | [消费者与投递语义.md](消费者与投递语义.md) 第二节 |
| 发布「成功」不等于入队 | 磁盘告警下 `PublishWithContext` 仍返回 `nil`（0.0s），队列堆积保持 0；连发 20000 条时 8.0s 未发完 | [运维与排障.md](运维与排障.md) 第二节 |

## 延伸追问

- **只想补一块，最短路径是什么？** → 想弄懂「消息怎么被路由」读 [核心概念与架构.md](核心概念与架构.md) 第三节；线上堆积直接读 [运维与排障.md](运维与排障.md) 第一节；要写代码跳第 3 节的片段或语言分册。
- **这套实测环境怎么复现？** → [部署与配置.md](部署与配置.md) 第一、四节给了单机与三节点的完整 `docker run` / `join_cluster` 命令；客户端跑在同一个 user-defined 网络里，用容器名当主机名即可。
- **为什么「可靠性」和「消费者」要分成两篇？** → 读者不同：可靠性篇服务「设计参数」，消费侧篇服务「定位消费问题」。混在一篇里最容易把「丢消息」和「重复消费」当成同一类问题。
- **为什么「存储与投递过程」不并进核心概念？** → 核心概念第四节只给六段链路的**骨架**（每段出错会怎样），存储篇给的是**文件级过程**（哪个文件什么时候长、ack 后为什么不缩）。前者回答「顺序」，后者回答「容量」，合成一篇会让容量判据被链路图淹没。
- **为什么「队列与绑定设计」放在最后？** → 它是决策篇：不知道一个队列对应一个 Erlang 进程、不知道内嵌阈值 4096，就判断不出「一个事件一个队列」到底贵在哪。机制没读完时看它，只能记住结论记不住判据。
- **它和 Kafka / RocketMQ 的目录怎么对照着看？** → [README.md](../Kafka/README.md) 讲分区日志，[README.md](../RocketMQ/README.md) 讲混写 CommitLog + 定长索引；本文目录讲的是「绑定表路由 + 消费即删」这第三条路。
