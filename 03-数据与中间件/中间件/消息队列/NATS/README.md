## 一、一句话定位与它凭什么

NATS 是**云原生、轻量级、高性能**的发布订阅消息系统，CNCF 毕业项目。核心只有一个 `nats-server` 二进制（Go 编写、无外部依赖），设计哲学是「**简单 + 快 + 低延迟**」。

| 维度 | NATS | Kafka / RocketMQ |
| --- | --- | --- |
| 部署形态 | ⭐ 单二进制直接跑；集群靠 gossip 自动组网 | 依赖 ZooKeeper / KRaft / NameServer |
| 核心抽象 | Subject（轻量字符串）+ 通配符订阅 | Topic + Partition / MessageQueue |
| 默认语义 | Core NATS 是 At-Most-Once 纯内存转发 | 默认落盘、可回溯 |
| 延迟 | ⭐ 微秒~亚毫秒（Core NATS） | 毫秒级 |
| 定位 | 服务间通信 / 服务治理 / IoT / 边缘 | 大数据管道 / 日志流 / 削峰堆积 |

> 一句话记忆：**Kafka 是「分布式提交日志」，NATS 是「分布式消息总线」**。前者为吞吐与回溯而生，后者为低延迟与极简运维而生。
>
> ⚠️ 但「NATS 很轻」有个前提：**Core NATS 不持久化**。要可靠就得开 JetStream，而 JetStream 的副本、ACK、去重窗口都要单独配；不配就只是一个转发器。

## 二、核心概念速览

| 概念 | 一句话 |
| --- | --- |
| **Subject** | 消息地址，形如 `photography.order.created`，用 `.` 分层；支持 `*`（一层）与 `>`（剩余全部） |
| **Publish / Subscribe** | 发布者不关心有没有订阅者；无队列组时每个订阅者都收到一份（广播） |
| **Queue Group** ⭐ | 同一 Subject + 同一组名的订阅者**竞争消费**，一条消息只投给组内一个实例 |
| **Request-Reply** | 请求方 `Request()`，响应方回写 `msg.Reply`（自动生成的 `_INBOX.x`）；超时返回 `nats.ErrTimeout` |
| **JetStream** | 持久化层：Stream 落盘、ACK 重投、重放、KV、Object Store；服务端须以 `-js` 启动 |
| **Stream / Consumer** | Stream 是「消息集合 + 保留策略」，Consumer 是消费视图（游标 + ACK 状态） |
| **Leaf Node** | 叶子节点挂到远端 Hub，只同步关注的 Subject 子集 |
| **Durable** | JetStream 消费者的持久化名字，消费进度就挂在它上面 |

> ⭐ **铁律：Core NATS 没有「存」这个动作。** 订阅者不在线 = 消息消失；要「上线后补投」只能用 JetStream Consumer 的游标。

## 四、本轮实测坐标

| 项 | 值 |
| --- | --- |
| 镜像 / 版本 | `nats:2.10-alpine`，容器内 `nats-server --version` → `nats-server: v2.10.29` |
| 集群 | 单机两容器：`nats-lab`（`-js -sd /data`，宿主 14222 / 18222）、`nats-lab-nojs`（不开 JetStream，宿主 14223 / 18223） |
| 服务端默认值 | `max_payload=1048576`、`max_pending=67108864`、`ping_interval=120000000000` ns、`ping_max=2`、`max_control_line=4096`、`auth_timeout=2` s（`/varz` 读数） |
| 客户端 | Go `github.com/nats-io/nats.go v1.53.1`（真跑）；Java `io.nats:jnats 2.20.5`（JDK 17.0.20.1，真编译运行） |
| 场景 | `lab.core` / `lab.queue` / `lab.echo` / JetStream Stream `LAB`（`lab.>`，File 存储，`Duplicates: 2m`） |

六条最值得记住的读数：

| 读数 | 值 | 出处 |
| --- | --- | --- |
| 队列组 300 条的分发**每轮都在变** | 三轮分别 `114/94/92`、`93/95/112`、`99/114/87` —— 没有 key 亲和，也没有「轮流发」 | [订阅与消费语义.md](订阅与消费语义.md) 第二节 |
| Request-Reply 的往返延迟 | 100 次共 `113.75 ms`，平均 `1.14 ms`（本机回环、无业务处理） | [订阅与消费语义.md](订阅与消费语义.md) 第三节 |
| `Msg-Id` 去重只生效于窗口内 | 同一 `Msg-Id` 连发两次，Stream 消息数从 5 变 **6**（只多了一条），不是 7 | [消息可靠性.md](消息可靠性.md) 第三节 |
| `MaxAckPending=1` 会真的停投 | 取到 1 条不 ACK 后，`num_ack_pending=1`、`num_pending=4`（剩余 4 条压着不发） | [消息可靠性.md](消息可靠性.md) 第五节 |
| 长度字段写错**不报错** | `PUB demo.orders 99` 只发了 11 字节 → 服务端返回 **0 B**，连接不断、消息不投 | [NATS协议.md](NATS协议.md) 第三节 |
| 单机建副本流直接失败 | `replicas > 1 not supported in non-clustered mode`（2.10.29 原文） | [部署与配置.md](部署与配置.md) 第四节 |

> ⚠️ **未实测项**：集群（route mesh）、Super Cluster、Leaf Node 只按官方文档陈述——本机 `docker network create` 不可用，起不了多节点互访；NKey / JWT 鉴权未配；JetStream 的 `+ACK` / `-ACK` 流控字节未抓包。Java 客户端的队列组、请求-应答、JetStream 与 drain 均已实测，读数见 [java/工程实践/接入NATS.md](../../../../01-编程语言/java/工程实践/接入NATS.md)。

## 延伸追问

- **只想补一块，最短路径是什么？** → 想弄懂「为什么 Core 会丢」读 [消息可靠性.md](消息可靠性.md) 第一、二节；线上「发了没收到」直接读 [运维与排障.md](运维与排障.md) 第二节；要写代码跳语言分册。
- **这套实测环境怎么复现？** → [部署与配置.md](部署与配置.md) 第二节给了两个容器的完整 `docker run` 参数与 `nats.conf`；客户端连 `127.0.0.1:14222` 并带 token 即可。
- **为什么「队列组」和「JetStream」要分成两篇？** → 它们的读者不同：队列组篇服务「消息该谁处理」，可靠性篇服务「消息会不会丢」。把两者混在一篇里，最容易出现的错误是把「重复消费」当成「队列组没配对」。
