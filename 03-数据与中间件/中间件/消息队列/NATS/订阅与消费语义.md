# 订阅与消费语义

> 覆盖 NATS 的「一条消息发给谁」：广播与队列组的区别（含本机三轮分发读数）、Request-Reply 怎么用两个原语拼出来、JetStream Consumer 的 Durable / `DeliverPolicy` / Push 与 Pull 四种组合，以及 NATS 为什么给不了跨消息顺序。
>
> 不覆盖：ACK 的五种应答、重投与去重见 [消息可靠性.md](消息可靠性.md)；Stream 的保留与副本见 [部署与配置.md](部署与配置.md)；客户端代码见 [Go 接入](../../../../01-编程语言/go/工程实践/接入NATS.md)。
>
> 内容整理自个人学习笔记。**实测口径**：本轮在 `nats-server v2.10.29` 容器上实测了广播、队列组分发、Request-Reply 往返与 JetStream 推拉消费；集群下的队列组跨节点分发**未实测**。

## 一、一条消息到底会被谁收到？

**本节要点**：NATS 的分发只有三条规则——**没有队列组 → 每个订阅者都收到一份；有队列组 → 组内只挑一个；订阅者不存在 → Core 直接丢（JetStream 才留）**。除此之外没有路由、没有绑定、没有分区。

| 订阅方式 | 消息落到谁 | 消息份数 |
| --- | --- | --- |
| 普通 `SUB subject` | **每个**订阅该 Subject 的连接各收一份 | 订阅者数 |
| `SUB subject group sid` | 同 `subject` + 同 `group` 的订阅者中**挑一个** | 每组一份 |
| 两种混用 | 普通订阅者全收，队列组内各挑一个 | 普通订阅者数 + 组数 |
| 无人订阅 | Core：直接丢弃；JetStream：进 Stream 等消费者 | — |

> ⚠️ **「广播」是默认行为**：同一服务部署两个实例、都用普通 `Subscribe`，那么一条消息会被处理两次——这是 NATS 上最常见的「重复消费」来源，先检查是不是漏了队列组。

## 二、队列组：竞争消费是怎么分发的？

**本节要点**：队列组只改**分发策略**，不改存储、不改协议。组内成员是**随机派发**——不是轮流、也不是按 key 哈希。本机 3 个成员、300 条消息连跑三轮，分布每轮都不同。

```text
普通订阅：      SUB orders 1        SUB orders 2        → 两条都收到全量
队列组：        SUB orders workers 1   SUB orders workers 2   → 只有一条收到
不同组：        SUB orders w1 1     SUB orders w2 2     → 两组各收一份（组间广播）
```

**本轮实测**（3 个 `QueueSubscribe("lab.queue", "workers")`，发布 300 条，每轮重建订阅）：

| 轮次 | 成员 A | 成员 B | 成员 C |
| --- | --- | --- | --- |
| 第 1 轮 | 99 | 114 | 87 |
| 第 2 轮 | 114 | 94 | 92 |
| 第 3 轮 | 93 | 95 | 112 |

三轮都接近均分（100 上下），但**单个成员在同一轮内并不轮流**。这组读数要读出两件事：

- ⭐ **能均分**：组内负载基本均衡，队列组可以当负载均衡用。
- ⚠️ **无亲和**：同一个 `order_id` 的连续消息可能落到不同成员，**所以不能靠队列组保住业务顺序**。

**与另外两个产品的对照**：

| 维度 | NATS 队列组 | Kafka 消费组 | RabbitMQ 多消费者 |
| --- | --- | --- | --- |
| 分配单位 | 每条消息 | 每个分区 | 每条消息（同一队列） |
| 分配方式 | 服务端随机派 | 分区绑定成员 | 轮询派发 |
| 同 key 亲和 | ❌ 无 | ✅ 同 key 同分区同成员 | ❌ 无（除非单活跃消费者） |
| 成员变动 | 无需重平衡，直接换目标 | 触发 rebalance | 无需重平衡 |

> ⭐ **队列组就是「NATS 版的竞争消费」**，对应 RabbitMQ 的「同一队列多消费者」与 MQTT 5.0 的 `$share`。**它不改变存储（Core NATS 本来就不存）**，只改变分发策略。

## 三、Request-Reply 在 NATS 上怎么拼？

**本节要点**：NATS 协议里没有「请求」这个命令。它是**一个临时订阅 + 一条带 `reply` 的发布**拼出来的：请求方先订阅一个唯一收件箱（`_INBOX.<随机>`），把它作为 `reply` 发出去；响应方处理完向该收件箱回一条普通 `PUB`。

```text
① 请求方：SUB _INBOX.abc123 90
② 请求方：PUB svc.lookup _INBOX.abc123 5\r\nhello\r\n     ← 第二个参数是 reply-to
③ 响应方：MSG svc.lookup 1 _INBOX.abc123 5\r\nhello\r\n
④ 响应方：PUB _INBOX.abc123 5\r\nworld\r\n
⑤ 请求方：MSG _INBOX.abc123 90 5\r\nworld\r\n
```

**本轮实测**：`lab.echo` 响应方原样回写，请求方串行发 100 次、每次 2s 超时——总耗时 `113.75 ms`，平均 `1.14 ms`。这是本机回环、无业务处理的**下限**，真实链路要把下游耗时加上去。

| 参数 | 作用 | 注意 |
| --- | --- | --- |
| 超时 | 客户端侧等待上限，超时返回 `nats.ErrTimeout` | ⚠️ 超时不会取消服务端处理，响应回来也没人接 |
| `reply` 主题 | 指向请求方的收件箱 | ⚠️ `_INBOX.>` 前缀在服务端有特殊处理，不要自造前缀 |
| `no_responders` | `CONNECT` 里开启：无人订阅时**立刻**回一条空响应 | ⭐ 把「超时」变成「快速失败」，NATS 2.2+ |

> ⚠️ **请求方必须保持连接**：收件箱是本连接上的一个订阅，连接断了响应就无处可投。响应方也必须在**同一个连接**上能看到请求——跨集群时依赖 route / gateway 的转发。

## 四、JetStream 的 Consumer 有哪几种消费姿势？

**本节要点**：JetStream 把「消费进度」抽成了 Consumer 对象。三个维度决定它的行为：**是否有 Durable 名（进度存不存）、`DeliverPolicy`（从哪开始）、Push 还是 Pull（谁主动）**。

### 4.1 三个维度

| 维度 | 取值 | 含义 |
| --- | --- | --- |
| **Durable** | 有名字 / 匿名 | 有名字 → 进度（游标 + 未 ACK 集）持久化在服务端，断线重连继续；匿名 → 消费者消失即丢进度 |
| **DeliverPolicy** | `DeliverAll` / `DeliverLast` / `DeliverLastPerSubject` / `DeliverNew` / `DeliverByStartSequence` / `DeliverByStartTime` | ⭐ 决定**新建消费者时**从哪一条开始，只影响首次 |
| **Push / Pull** | `Subscribe` / `PullSubscribe` | Push：服务端推给客户端回调；Pull：客户端 `Fetch(n)` 主动取 |

### 4.2 Push 与 Pull 怎么选

| 维度 | Push | Pull |
| --- | --- | --- |
| 谁来拉 | 服务端主动推 | 客户端按批取 |
| 背压 | 靠 `MaxAckPending` 限在途 | ⭐ 天然背压：不 `Fetch` 就不发 |
| 吞吐 | 高（消息一到就投） | 批量大时更高 |
| 适用 | 实时处理、单条处理快 | 重负载、批量、要自己控节奏 |

> ⭐ **重负载下 Pull 优于 Push**：Push 的回调一旦跟不上，未 ACK 数涨到 `MaxAckPending` 就会停投；Pull 则由业务自己决定「这一批处理完再取下一批」，节奏完全可控。

### 4.3 两条常用组合

```text
实时链路：Push + Durable + ManualAck + MaxAckPending(64)
批量链路：Pull + Durable + Fetch(32) + 批内串行 + 逐条 Ack
竞争消费：QueueSubscribe + Durable（组名与 Durable 名要区分开）
```

> ⚠️ **`Durable` 名和队列组名是两件事**：队列组决定「组成员之间怎么分」，Durable 决定「进度存在哪」。JetStream 的队列订阅需要两者都写，否则重启后会从 `DeliverPolicy` 重新开始。

### 4.4 推拉消费的实测读数

| 场景 | 读数 |
| --- | --- |
| Push 广播 3 条 | `sent=3 received=3` |
| Pull 批量取 | `Fetch(32, 500ms)` 在 5 条消息上可分多批取完，空队列时返回 `nats.ErrTimeout`（属正常，不是错误） |

⚠️ **`Fetch` 的 `ErrTimeout` 不要当异常处理**：它表示「这批没取到消息」，退避一下继续即可；把它当错误重连，反而会造成连接抖动。

## 五、为什么 NATS 保证不了顺序？

**本节要点**：NATS 没有「分区」这个对象，也就没有「同一个 key 永远落同一条通道」的机制。队列组是随机派发，多个订阅者并行处理，顺序自然保不住。

| 想保住顺序的做法 | 代价 | 适用 |
| --- | --- | --- |
| 单订阅 + 串行回调 | 牺牲并行度，吞吐上限就是单订阅的处理速度 | 低流量、顺序强相关 |
| 按业务键分片到不同 Subject（`order.123.*`） | 需要自己维护分片数与路由 | ⭐ 推荐，等价于 Kafka 的分区 key |
| JetStream 单 Consumer + `MaxAckPending=1` | 严格串行，吞吐最低 | 极少数强顺序场景 |
| 消费端状态机校验 | 容忍乱序，靠业务规则拒绝旧状态 | 通用兜底 |

> ⚠️ **「单订阅 + 串行」也只在单个 Consumer 内成立**：同一个 Subject 上如果既有 Core 订阅又有 JetStream Consumer，两者的处理顺序互不相干。

## 应用场景

| 场景 | 选型 | 判据 |
| --- | --- | --- |
| 服务发现 / 健康探测 | Core + Request-Reply + `no_responders` | 需要「没人应答立刻知道」 |
| 通知类事件（积分、短信） | Core + 队列组 | 丢一条可接受，靠业务补偿 |
| 订单状态流转 | JetStream + Pull + Durable | 不能丢，且要控速率 |
| 同一实体严格有序 | 分片 Subject 或单 Consumer | 业务本身依赖先后 |
| 配置变更推送 | Core 广播（每实例都收） | 每个实例都要拿到全量 |

## 具体使用

```bash
# 装 CLI 后可直接观察订阅关系与分发（容器内自带 nats CLI 时可省去）
nats sub "lab.>"                 # 观察某棵子树上的全部消息
nats sub lab.queue --queue workers   # 以队列组成员身份订阅
nats pub lab.queue hello         # 发一条
nats request svc.echo hello --timeout 2s   # 请求-应答
nats consumer info LAB lab_pull  # 看某个 Durable 的游标与未 ACK 数
```

⚠️ 本机容器 `nats:2.10-alpine` 未带 CLI，上面的命令按官方 CLI 语义写出，**未在本容器验证**；本轮实测走的是 Go 客户端与手写 Python 探针。

## 延伸追问

- **队列组能保证同一 key 落到同一实例吗？** 不能。组内是随机派发，没有 key 概念。要亲和只能把 key 编进 Subject（`order.123.created`）再各自订阅，或用 JetStream 单 Consumer 串行。
- **Request-Reply 的收件箱会不会成为热点？** 单节点下不会，它只是普通 Subject。集群下 `_INBOX.>` 有专门优化以便把响应路由回请求方所在节点，**自建客户端不要自造前缀**。
- **`DeliverAll` 会不会把历史消息全推一边？** 会，它就是从 Stream 的第一条开始。生产上更常用 `DeliverNew`（只收新消息）或 `DeliverByStartTime`（从某个时间点补）。
- **Push 与 Pull 能混用吗？** 同一个 Stream 上可以有多个 Consumer，一个 Push 一个 Pull，各自维护游标，互不影响。
- **匿名 Consumer 什么时候用？** 只在「这次连接内消费完就走、不要进度」的场景（如临时导出）。生产几乎都该用 Durable。
