## 一、单机最小可跑怎么起？

**本节要点**：单机只需要一个容器 + 一个配置文件。**`-js` 与 `http_port` 是最容易漏的两项**——前者决定 JetStream 存不存在，后者决定健康检查能不能过。

```bash
# 本机实测：JetStream 版（宿主 14222 / 18222）
MSYS_NO_PATHCONV=1 docker run -d --name nats-lab \
  -p 14222:4222 -p 18222:8222 \
  -v D:/www/dev-notes/.workbuddy/tmp/nats-lab/nats.conf:/etc/nats/nats.conf:ro \
  nats:2.10-alpine -c /etc/nats/nats.conf -js

# 对照组：同一个镜像，不加 -js、不挂配置
docker run -d --name nats-lab-nojs -p 14223:4222 -p 18223:8222 nats:2.10-alpine
```

生产更常见的写法是 compose（`photography-server` 的形态）：

```yaml
# docker-compose.yml
services:
  nats:
    image: nats:2.10-alpine
    container_name: nats
    command: ["-c", "/etc/nats/nats.conf", "-js", "-sd", "/data"]  # -js 开 JetStream；-sd 落盘目录
    ports:
      - "4222:4222"   # 客户端连接
      - "8222:8222"   # HTTP 监控 / 健康检查
      - "6222:6222"   # 集群路由（单机可不开）
    volumes: ["./nats.conf:/etc/nats/nats.conf:ro", "./data:/data"]
    healthcheck:      # 依赖 nats.conf 里的 http_port: 8222，否则探针恒失败
      test: ["CMD-SHELL", "wget -q -O /dev/null http://127.0.0.1:8222/healthz || exit 1"]
      interval: 5s
      timeout: 3s
      retries: 12
    restart: unless-stopped
```

> ⚠️ **`-sd` 与 `jetstream.store_dir` 别同时写两处**：`-sd` 是命令行覆盖，配置里再写 `store_dir` 两者不一致时以命令行参数为准，排查时很容易看错配置文件。

## 二、`nats.conf` 里哪些项必须显式写？

**本节要点**：四个必写项——`port`、`http_port`、`authorization`、`jetstream`。其余都有默认值，但默认值决定了下限（例如 `max_payload` 默认 1 MiB）。

```conf
# nats.conf：令牌鉴权 + JetStream（本机实测配置）
port: 4222
http_port: 8222

authorization {
  token: "s3cret-token"     # 客户端侧：nats.Token("s3cret-token")
}

jetstream {
  store_dir: /data
  max_memory_store: 256MB
  max_file_store: 2GB
}
```

本机 `/varz` 读到的默认值（不写就是这些）：

| 字段 | 实测值 | 含义 |
| --- | --- | --- |
| `max_payload` | `1048576`（1 MiB） | 单条消息上限，超了服务端 `-ERR` 并断开 |
| `max_pending` | `67108864`（64 MiB） | 单连接写缓冲上限 |
| `ping_interval` | `120000000000` ns（120 s） | 服务端发 `PING` 的周期 |
| `ping_max` | `2` | 连续多少次没回 `PONG` 就断开 |
| `max_control_line` | `4096` | 单条协议行的上限（`PUB` 命令行太长会撞这个） |
| `auth_timeout` | `2` s | 建连后多久内必须 `CONNECT` |

> ⚠️ **`/healthz` 探针依赖 `http_port`**：没开监控端口时 `wget` 恒失败，容器被标成 unhealthy，而 NATS 本身其实跑得好好的——这是「假故障」最常见的一种。
>
> ⚠️ **`max_payload` 是「字节数」不是「字符数」**：1 MiB 的上限按 UTF-8 字节算，中文一个字 3 字节。自研客户端上报大 JSON 时要留余量。

## 三、鉴权怎么选？

**本节要点**：三种方式的差别不在「安全强度」，而在**能不能按 Subject 授权**与**服务端要不要存密钥**。

| 方式 | 配置 | 客户端（Go） | 适用 |
| --- | --- | --- | --- |
| Token | `authorization { token: "xxx" }` | `nats.Token("xxx")` | 内网最小成本 |
| User / Password | `users = [ { user, password, permissions } ]` | `nats.UserInfo("app", "pwd")` | ⭐ 可配 Subject 级权限 |
| NKey / JWT | `users = [ { nkey: "UD..." } ]` + `nsc` 账号体系 | `nats.Nkey(pub, sigCB)` | 生产多租户，Server 不存密钥 |

用户名密码方式可顺手做出最小权限：

```conf
authorization {
  users = [
    {
      user: "photo-app", password: "app-pass"
      permissions: {
        publish:   ["photography.>"]
        subscribe: ["photography.>", "_INBOX.>"]
      }
    }
  ]
}
```

> ⚠️ **漏了 `_INBOX.>` 的订阅权限，Request-Reply 会全部超时**：请求方要先订阅收件箱才能收响应，而 `_INBOX.>` 是另一个 Subject 子树，不在 `photography.>` 的匹配范围里。

## 四、集群怎么组？为什么单机不能设副本？

**本节要点**：集群只需要在**每个节点**写同一段 `cluster` 配置，互相列 `routes` 即可；JetStream 的副本数受节点数限制，**单机写 `Replicas: 2` 直接报错**。

```conf
# 集群节点（每个节点都要写，routes 指向其余节点的 6222）
cluster {
  name: "my_cluster"
  listen: 0.0.0.0:6222
  routes: ["nats://nats-1:6222", "nats://nats-2:6222", "nats://nats-3:6222"]
}

jetstream {
  store_dir: /data/jetstream
  max_file_store: 10GB
}
```

**本机实测的报错原文**（单节点、`Replicas: 2`）：

```text
nats: replicas > 1 not supported in non-clustered mode
```

| 部署形态 | 可用 `Replicas` | 说明 |
| --- | --- | --- |
| 单机 | 只能 `1` | 写 2 以上直接失败 |
| 3 节点集群 | `1` / `2` / `3` | `3` 才具备「挂一台仍可写」 |
| 2 节点集群 | `1` / `2` | ⚠️ `2` 没有多数派余量，挂一台整体不可写 |

> ⚠️ **`StreamConfig.Replicas` 只有在集群节点数 ≥ Replicas 时才有意义**；而且 Raft 的写要过多数派，**`Replicas: 2` 一点都不安全**——两台挂一台就凑不够多数派。
>
> ⚠️ **route 是全连接**：N 个节点要维护 N×(N-1)/2 条路由。节点数上到十几个之后，建议用 Super Cluster 分域，而不是继续加 route。

## 五、Leaf Node 适合什么场景？

**本节要点**：Leaf Node 是「**只订阅关心的 Subject 子集**」的一条连接，用来解决三件事：边缘弱网、跨域单向同步、多租户隔离。

| 场景 | 为什么用 Leaf | 注意 |
| --- | --- | --- |
| 边缘 / IoT 站点 | 断网时本地 NATS 继续工作，恢复后自动续上 | 边缘本地要单独落盘才有「断网不丢」 |
| 跨域 / DMZ | 只把需要的 Subject 引进来，不暴露整个集群 | 用 `import` / `export` 限制方向 |
| 多租户 | 每个租户一个 Leaf，天然隔离 Subject 空间 | 上层 Hub 要按账号做权限 |

```conf
# 叶子节点：挂到 Hub，只同步 photography.edge.>
leafnodes {
  remotes = [
    { url: "nats-leaf://hub.example.com:7422"
      account: "$G"
      deny_import: ">"
      deny_export: ">"
    }
  ]
}
```

⚠️ 上面的 Leaf 配置**按官方文档写出，本机未实测**——两个容器互访需要自定义网络，而本机 `docker network create` 因地址池耗尽不可用。

## 六、怎么确认它真的起对了？

**本节要点**：三步——**看日志有没有 `Server is ready`、`/healthz` 是不是 200、`/varz` 里的 `jetstream` 段有没有出来**。三步都过，才说明「能连、健康、持久化可用」。

```text
# ① 日志
[1] Server is ready
[1] Listening for client connections on 0.0.0.0:4222
[1] Starting http monitor on 0.0.0.0:8222
[1] Cluster name is my_cluster

# ② 健康检查（本机实测 200）
curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:18222/healthz

# ③ 监控端点：有 jetstream 段说明 -js 生效
curl -s http://127.0.0.1:18222/varz | head -40
```

> ⚠️ **「服务起来了」与「JetStream 开了」是两件事**：只加 `-js` 不加 `jetstream.store_dir` 也能跑（用默认目录），但容器重建就丢；反过来只配 `store_dir` 不加 `-js`，JetStream 根本没启用——**日志里不会有任何提示**，只有客户端调 `JetStream()` 时才报 `nats: jetstream not enabled`。


## 延伸追问

- **`-js` 与配置文件里的 `jetstream {}` 段什么关系？** `-js` 是总开关，`jetstream {}` 只配参数；**没有 `-js` 时该段被忽略**，不报错。
- **`-sd` 和 `store_dir` 写哪个？** 二选一。命令行优先，配置写清楚更利于审阅；两个都写且不一致时以命令行为准。
- **单机能不能「假装」集群来提高副本？** 不能。`Replicas` 校验的是真实集群成员数，单节点直接报 `replicas > 1 not supported in non-clustered mode`。
- **健康检查为什么不用 TCP 探测？** 可以，但 `http_port` 的 `/healthz` 还能反映 JetStream 的状态；只探 TCP 会出现「端口通但内部异常」的假健康。
- **容器重建后 JetStream 数据还在吗？** 看有没有把 `/data` 挂出来。本机 `nats-lab` 只挂了配置文件，**没挂数据目录**——容器删掉数据就没了，这是实验环境与生产的关键差别。
