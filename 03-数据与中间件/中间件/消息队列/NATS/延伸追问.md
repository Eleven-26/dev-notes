## 一、语义与模型

- **Core NATS 与 JetStream 是两套协议吗？** 不是。同一连接、同一套文本协议；区别只在「消息要不要进 Stream」。`nc.JetStream()` 封装的是 `$JS.API.>` 这些系统 Subject。详见 [核心概念与架构.md](核心概念与架构.md) 第二节。
- **Core NATS 会丢消息吗？** 会。无人订阅、订阅者离线、重连窗口内、pending 队列写满（默认 65536 条 / 64 MB 判 `SlowConsumer`）都会丢，发布端无回执。要可靠必须 JetStream。详见 [消息可靠性.md](消息可靠性.md) 第一节。
- **Queue Group 与 Kafka 消费者组的区别？** Kafka 是「分区分配给成员、共享一个 offset」，分区内有序、成员变动触发 rebalance；NATS 是「服务端把每条消息随机派给组内一个订阅者」，**不绑定分区、不保证同 key 同实例、不保证顺序**，但也没有 rebalance 停顿。详见 [订阅与消费语义.md](订阅与消费语义.md) 第二节。
- **Core NATS 和 JetStream 怎么共存？** 同一 `nats.Conn` 上的两种用法：`nc.Publish/Subscribe` 走内存，`nc.JetStream()` 走持久化。可对同一 Subject 并行——Core 做实时广播，JetStream Consumer 做可靠兜底。
- **NATS 为什么不需要外部队列协调组件？** 路由、成员发现、元数据与副本一致性全部内建：集群靠 gossip 收敛成全网状 route，JetStream 用内嵌 Raft 组维护 Stream 副本与 Consumer 状态。详见 [核心概念与架构.md](核心概念与架构.md) 第四节。

## 二、可靠性

- **JetStream 的 ACK 与重投怎么工作？** 必须在 `AckWait`（默认 30s）内 ACK；未 ACK 或 `Nak()` 即重投；累计到 `MaxDeliver` 后停止自动投递。`MaxAckPending` 限在途未 ACK 数，达到即暂停投递；长耗时用 `InProgress()` 续期。详见 [消息可靠性.md](消息可靠性.md) 第四、五节。
- **`MaxDeliver` 到了以后消息会消失吗？** 不会。它只是「这个消费者不再自动投」，消息仍在 Stream 里受 `MaxAge` / `MaxBytes` 淘汰；新建消费者仍能读到。⚠️ NATS **没有内建死信队列**，要靠 `$JS.EVENT.ADVISORY.CONSUMER.MAX_DELIVERIES.*` 自己转存。
- **At-Least-Once 下如何做到「业务上只执行一次」？** 两条腿：① 发布端带 `Msg-Id`，靠去重窗口（默认 2min）做服务端过滤；② 消费端幂等（唯一键 / 去重表 / 状态机条件更新），这是跨系统唯一可靠的手段。切勿依赖中间件的 Exactly-Once。
- **`Drain()` 和 `Close()` 的区别？** `Close()` 立即取消订阅、丢弃在途回调；`Drain()` 先取消订阅 → 等在途回调跑完 → 冲刷待发缓冲 → 再关闭。**生产停机用 Drain**，否则 JetStream 消息未 ACK 会在 `AckWait` 后被重投。
- **为什么 `MaxAckPending=1` 时消息会「停住」？** 服务端在途未 ACK 到达上限就停投，不是客户端不取。本机实测 `num_ack_pending=1`、`num_pending=4` 一条不动。详见 [消息可靠性.md](消息可靠性.md) 第六节。

## 三、顺序与性能

- **同一 Subject 上的消息如何保证顺序？** NATS 不提供跨消息顺序保证。只能：① 单订阅 + 串行回调（牺牲吞吐）；② 按业务键分片到不同 Subject / Stream；③ 消费端状态机校验，容忍乱序。**不要用加并发提吞吐**——会破坏顺序。
- **为什么不能靠队列组做「同 key 同消费者」？** 组内是随机派发，没有 key 概念。本机 300 条 / 3 成员的分布每轮都在变（99/114/87、114/94/92、93/95/112），能均分但不亲和。
- **提吞吐该加什么？** 按业务键分片到更多 Subject / Stream，或把慢处理搬出回调。无脑加 goroutine 只会让「队头阻塞」变成「顺序全乱」。
- **Core NATS 的延迟到底多低？** 官方口径微秒~亚毫秒。本机实测 Request-Reply 100 次平均 `1.14 ms`（回环、无业务处理），可以作为「上限参考」，但不要当成生产 SLA。

## 四、部署与协议

- **`-js` 与配置里的 `jetstream {}` 段什么关系？** `-js` 是总开关，`jetstream {}` 只配参数；**没有 `-js` 时该段被忽略且不报错**，客户端调 `JetStream()` 才返回 `nats: jetstream not enabled`。详见 [部署与配置.md](部署与配置.md) 第六节。
- **单机为什么不能设 `Replicas: 2`？** 副本校验的是真实集群成员数，单节点直接报 `replicas > 1 not supported in non-clustered mode`；两台节点设 `Replicas: 2` 也没有多数派余量。
- **长度字段为什么写错不报错？** 服务端按声明长度继续等剩余字节，连接不断、无 `-ERR`。本机实测声明 99 B 实际发 11 B，返回 **0 B**，消息永不投递。详见 [NATS协议.md](NATS协议.md) 第三节。
- **`-ERR` 之后连接还能用吗？** `proto:1` 下权限类 `-ERR` 不断连（只是这一条被拒），协议类（`Unknown Protocol Operation`、`Maximum Payload Violation`）通常会断。
- **服务端为什么主动发 `PING`？** 它要确认客户端还活着：默认 120 s 一次，连续 2 次没回 `PONG` 就断开。客户端必须在读循环里处理，不能只在「要发消息时」才读。

## 五、两条答题链

**① 「NATS 消息会不会丢？」** → Core NATS 四类丢法（无人订阅 / 离线 / 重连窗口 / SlowConsumer）→ JetStream 用 Stream 落盘 + Consumer 游标解决「不在线」→ ACK 超时与 NAK 带来重复 → `Msg-Id` 去重只在 2 分钟窗口内 → 最终靠消费端幂等兜底 → 停机用 `Drain` 避免在途消息被掐断。

**② 「为什么 NATS 保证不了顺序，又怎么补救？」** → 没有分区对象，队列组随机派发 → 多个订阅者并行处理，顺序无保证 → 补救三条：分片 Subject（推荐）、单订阅串行、状态机校验 → 注意「单订阅串行」也只在一个 Consumer 内成立。
