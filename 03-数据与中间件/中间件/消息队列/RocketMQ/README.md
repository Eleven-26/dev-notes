## 一、一句话定位与适用场景

RocketMQ 是阿里 2012 年开源、2016 年捐给 Apache（2017 年成为顶级项目）的分布式消息中间件，纯 Java 实现，单机十万级 TPS、支持万级队列；**原生支持延迟消息、事务消息、消息轨迹**，这是它与 Kafka / RabbitMQ 最直接的差异点。

| 场景 | 落点 |
| --- | --- |
| 削峰填谷 | 大促流量写 Topic，消费者按自身能力匀速拉取，堆积由 Broker 承担 |
| 系统解耦 | 上游只发消息，下游各自订阅同一 Topic，新增下游不改上游代码 |
| 异步处理 | 下单后发消息，积分 / 短信 / 风控异步消费，主链路 RT 大幅下降 |
| 最终一致性 | 事务消息把「本地事务」与「消息投递」绑定为最终一致 |
| 延迟消息 | 订单 30 分钟未支付自动关单、延迟重试、定时通知，不必写扫表定时任务 |

> ⭐ 一句话记忆：**RocketMQ 把「所有 Topic 混写进一条 CommitLog」当存储根基，用轻量定长索引换出万级队列；把「延迟 / 事务」做进了 Broker 而不是留给业务方。**

## 二、核心概念速览

| 概念 | 一句话 |
| --- | --- |
| **NameServer** | 路由注册中心，**无状态、纯内存、节点之间互不通信**，Broker 上报 Topic/队列信息，客户端按 Topic 拉全量路由 |
| **Broker** | 消息存储与转发；分 Master（`brokerId=0`）与 Slave（`brokerId>0`） |
| **Topic** | 消息的逻辑分类，由多个队列组成 |
| **MessageQueue（Queue）** | Topic 的最小并行单元，`queueId` 从 0 开始；⭐ **一个队列同一时刻只能被同消费组内一个消费者消费** |
| **Tag** | 二级分类，**只有一个**，在 Broker 端按 `tagCode` 过滤（便宜） |
| **Key** | 业务唯一标识，写入 IndexFile 供 `mqadmin queryMsgByKey` 排障 |
| **Offset** | 队列内消费位点；集群模式存 Broker，广播模式存消费者本地 |
| **ConsumerGroup** | 集群模式下组内平分队列，一条消息只被组内一个实例消费 |
| **CommitLog** | 全 Topic 混写的一条追加日志，**存储的唯一真身** |
| **ConsumeQueue** | 由 CommitLog 透析出的定长索引（20 字节 / 条），消费路径的入口 |

> ⭐ **铁律：顺序只在「同一个队列」内成立。** 要「同一实体的消息有序」，就用业务 Key 选队列（`MessageQueueSelector`），让同 Key 永远落同一队列。

| 项 | 值 |
| --- | --- |
| 镜像 / 版本 | `apache/rocketmq:5.3.1`（`V5_3_1`，`mqadmin clusterList` 实测） |
| 集群 | 单机：1 NameServer（`rmq-namesrv`，宿主 19876）+ 1 Broker（`rmq-broker`，宿主 19011），网络 `rocketmq-lab-net`；协议篇另起 1 Proxy（`rmq-proxy`，宿主 18080 Remoting / 18081 gRPC） |
| Broker 角色 | `brokerRole=ASYNC_MASTER`、`flushDiskType=ASYNC_FLUSH`（默认组合） |

六条最值得记住的读数：

| 读数 | 值 | 出处 |
| --- | --- | --- |
| 三层存储的文件尺寸 | CommitLog 单文件 **1,073,741,824 B（1 GiB）**；ConsumeQueue 单文件 **6,000,000 B**（30 万 × 20 B）；IndexFile 单文件 **420,000,040 B**（`40 + 500 万 × 4 + 2000 万 × 20`） | [核心概念与架构.md](核心概念与架构.md) 第四节 |
| 一个队列里的物理偏移**不连续** | 同一队列的 ConsumeQueue 条目物理偏移依次为 `0 / 223 / 892 / 1784`，差值说明中间夹着**别的 Topic 的消息** | [核心概念与架构.md](核心概念与架构.md) 第四节 |
| 顺序消息同 Key 落同一队列、偏移连续 | Java 与 Go 两侧都是同 Key 的 4 条消息全部落 `queueId=1`，偏移 `0,1,2,3` | [消息类型与语义.md](消息类型与语义.md) 第二节 |
| 刷盘服务的实现类在 **Broker 启动时**选定 | `SYNC_FLUSH` 必须写进 `broker.conf` 并**重启**才会切到 `GroupCommitService`（本机日志：`GroupCommitService service started`）；运行时 `updateBrokerConfig` 只改配置值，**不换实现类** | [消息可靠性.md](消息可靠性.md) 第五节 |
| 长轮询「写 3 秒却挂 5 秒」 | `sysFlag` 带 `0x02` 后，`suspendTimeoutMillis` 取 1000/2000/3000/4000 实测都 **5000 ms** 返回，取 6000 实测 **10000 ms**；挂起期间来新消息 **4 ms** 唤醒 | [RocketMQ协议.md](RocketMQ协议.md) 第六节 |
| 一个 `code` 字段其实是两套码表 | 请求侧 155 个 opcode 按号段分 11 个模块（`0-99` 收发、`100-199` 路由、`200-299` 管理面…`200000+` POP）；响应侧分 `0-4` / `10-28` / `200-215` 三层，负数只存在于客户端本地 | [RocketMQ协议.md](RocketMQ协议.md) 第四节 |

> ⚠️ **未实测项**：单机只有一个 Broker，**主从复制（`SYNC_MASTER` / DLedger）无法实测**，相关结论按官方文档口径陈述；`SYNC_FLUSH` 的 RT 对照做了动态切换实测（见 [消息可靠性.md](消息可靠性.md)）；事务消息的**回查**路径（60s 周期、15 次上限）只做了定性观察，未等到回查耗尽。

## 延伸追问

- **只想补一块，最短路径是什么？** → 想弄懂写入与 ACK 读 [核心概念与架构.md](核心概念与架构.md) 第四节；线上堆积直接读 [运维与排障.md](运维与排障.md) 第三节；要写代码跳语言分册；想弄明白「一条消息在线上长什么样」读 [RocketMQ协议.md](RocketMQ协议.md)。
- **这套实测环境怎么复现？** → [部署与配置.md](部署与配置.md) 第二节给了 NameServer + Broker 的完整 `docker run` 参数与 `broker.conf`；协议层实验另需一个 `mqproxy`（见 [RocketMQ协议.md](RocketMQ协议.md) 第九节）；容器内客户端用容器名互联即可。
- **为什么「可靠性」和「消费者」要分成两篇？** → 它们的读者不同：可靠性篇服务「设计参数」，消费侧篇服务「定位消费问题」。混在一篇里最容易出现的错误，是把「丢消息」和「重复消费」当成同一类问题。
