## 二、定位与核心概念

- **与 Kafka 的核心差异？** → ① 元数据：NameServer（无状态 AP）vs ZooKeeper / KRaft；② 存储：统一 CommitLog + ConsumeQueue（单机可挂万级队列）vs 每分区独立目录（分区多则文件数爆炸）；③ 功能：RocketMQ 原生延迟消息、事务消息、Tag/SQL 过滤、消息轨迹与消息查询，Kafka 靠分区吞吐与流式生态取胜。[README.md](README.md) 第一节、[核心概念与架构.md](核心概念与架构.md) 第四节
- **NameServer 为什么比 ZooKeeper 轻？** → 路由数据**允许短暂不一致**（Broker 上下线延迟几十秒可接受），所以不需要一致性协议；纯内存、无状态、节点互不通信，错误靠客户端重试自愈。[核心概念与架构.md](核心概念与架构.md) 第三节
- **长轮询和真正的 push 差在哪？为什么不做成 Broker 主动推？** → 差在连接方向：长轮询是「客户端挂起请求等结果」，Broker 不需要维护到客户端的反向连接。不做真推是因为客户端在 NAT / 负载均衡后面不可达，且 Broker 一维护连接就变成有状态。[核心概念与架构.md](核心概念与架构.md) 第六节

## 三、存储与索引

- **为什么 RocketMQ 单机能支持数万队列，而 Kafka 分区多了会变差？** → CommitLog 顺序写 + ConsumeQueue 轻量索引（每条约 20 字节，单文件 30 万条仅约 6 MB）让存储与队列数解耦；Kafka 每个分区一套日志段与索引文件，分区数增大带来随机 IO 与文件句柄压力。[核心概念与架构.md](核心概念与架构.md) 第四节
- **CommitLog 写放大为什么低？换来了什么代价？** → 全 Topic 混写 → 全机单追加点 + mmap 写 PageCache + 批量刷盘，磁盘接近顺序带宽。代价在读：单队列数据散落全日志，必须两跳（索引 → 正文）；本机实测同一队列的 ConsumeQueue 物理偏移依次 `0 / 223 / 892 / 1784`，明显不连续。[核心概念与架构.md](核心概念与架构.md) 4.1 节
- **IndexFile 怎么按 Key 找到消息？** → 哈希定位到定长文件的槽（实测 **500 万**槽、文件 **420,000,040** 字节），槽内存「最新条目偏移」，条目里带「同槽前一条偏移」形成链，沿链比对 keyHash + 时间差。写满覆盖最旧条目，所以只保证查到近期数据。[核心概念与架构.md](核心概念与架构.md) 4.3 节
- **`send` 成功就等于落盘了吗？** → 不等于。默认 `ASYNC_FLUSH` 只是写进 PageCache 就 ACK，持久化边界由「刷盘 × 复制」两个开关共同决定。[核心概念与架构.md](核心概念与架构.md) 第五节

## 四、消息类型与语义

- **RocketMQ 为什么不支持任意延迟（4.x）？** → 4.x 用固定 `delayLevel`，每个级别对应 `SCHEDULE_TOPIC_XXXX` 下一条队列 + 定时任务扫描，队列内天然按到期时间有序、无排序成本；任意延迟要求按到期时间排序，5.x 才用 TimerLog + 多级时间轮（`rmq_sys_wheel_timer`）做到毫秒级。[消息类型与语义.md](消息类型与语义.md) 第三节
- **顺序消息如何保证不丢、不跳？** → 生产端同 key 固定队列（实测同 Key 4 条全落 `queueId=1`、偏移连续 `0,1,2,3`）；消费端 `MessageListenerOrderly` 按队列加锁单线程消费，失败返回 `SUSPEND_CURRENT_QUEUE_A_MOMENT` 无限重试并阻塞队列，所以不会跳过；代价是队列卡死风险。[消息类型与语义.md](消息类型与语义.md) 2.1 节
- **事务消息的回查是怎么触发的？** → 半消息写入 `RMQ_SYS_TRANS_HALF_TOPIC`；Producer 未回 Commit/Rollback（UNKNOW、宕机、断网）时，Broker 每 60s 扫描超时半消息、反查 `checkLocalTransaction`，默认最多 15 次，回查逻辑必须幂等且能反查本地事务。本机实测：3 条半消息全进 HALF，真实 Topic 只有 1 条可见。[消息类型与语义.md](消息类型与语义.md) 第四节
- **为什么事务消息的可见性靠「索引缺席」而不是标志位？** → 消费者路径是真实 Topic → ConsumeQueue → CommitLog；半消息在真实 Topic 的 ConsumeQueue 里没有条目，按位点走不到它，所以「不可见」是存储结构自带的。[消息类型与语义.md](消息类型与语义.md) 4.1 节

## 五、可靠性与一致性

- **如何保证消息不丢、不重复？** → 不丢：生产端同步发送 + 重试 + 事务消息，Broker 端刷盘 × 复制按 SLA 组合，消费端处理成功后再提交位点；不重复：RocketMQ 只保证 at-least-once，只能消费端幂等（去重表 / Redis SETNX / 业务状态机），去重 key 用业务唯一键而非 msgId。[消息可靠性.md](消息可靠性.md) 第三节、第五节
- **什么时候必须上 DLedger？** → 需求是「Master 故障自动恢复**写**能力」时——原生主从的 Slave 不会自动升主，客户端故障规避只救发送不救该组写。代价：≥3 副本、多数派写抬高 RT、选主窗口不可写。本质是把 NameServer 不要的强一致，恰好补给「谁是 Master」这份不能靠重试消化的元数据。[消息可靠性.md](消息可靠性.md) 第一节
- **死信队列里消息放着就安全吗？** → 不：DLQ 队列容量有上限会被覆盖，消息同受全局保留期约束，到期物理删除——没人消费的死信等于丢了。标准动作是监控 DLQ 增量告警 + 专职消费者落库归档 + 按写降级补偿思路重放。[消息可靠性.md](消息可靠性.md) 第二节
- **为什么顺序消费不能走 `%RETRY%`？** → 重试 Topic 的队列与原 Topic 队列没有顺序映射关系，消息绕道回来时原队列的后继消息会被先消费，顺序直接破坏。所以顺序消费只能「挂起原队列、原地重试」，代价是毒消息卡死整队。[消息可靠性.md](消息可靠性.md) 第二节

## 六、消费与排障

- **rebalance 时一定会重复消费吗？怎么缓解？** → 并发消费的交接窗口（旧主未提交位点的缓存消息 + 新主从已提交位点重拉）无法在协议层消除——at-least-once 的下界；缓解靠减少 rebalance 频率 + 消费端幂等。顺序消费用 Broker 端队列分布式锁把「双主」变成「接管等待」。[消费者与消费位点.md](消费者与消费位点.md) 第三节
- **顺序消费的三件锁事各挡什么，少一件会怎样？** → 生产端 Key → 固定队列挡「入口分叉」；消费端单队列单线程挡「进程内并发乱序」；Broker 队列分布式锁挡「rebalance / 宕机时的双实例同队消费」。少任何一件都有对应的乱序路径。[消费者与消费位点.md](消费者与消费位点.md) 第三节
- **消息堆积怎么办？** → 先定位是消费慢还是生产突增；手段为提消费线程（≤ 队列数）、批量消费、下游异步化、先扩队列再扩实例；⚠️ 队列数不变时加消费者实例无效。[运维与排障.md](运维与排障.md) 第一、二节
- **位点不动但客户端不报错，先查什么？** → 拉取流控：ProcessQueue 缓存超阈值后客户端主动暂停该队列拉取并延后重试，日志层面无异常。[运维与排障.md](运维与排障.md) 第三节
- **RocketMQ 能不能像 Kafka 那样按 Topic 配不同的保留时长？** → 不能。CommitLog 全 Topic 混写，删除以 1 GiB 文件为最小单位、保留期（`fileReservedTime`）是集群全局参数；不同 SLA 的业务要拆集群。[运维与排障.md](运维与排障.md) 第四节

## 七、两条答题链（把散点串起来）

**链一：「RocketMQ 怎么做到不丢？」**

`send 成功 ≠ 落盘`（写 PageCache 即返回）→ 本机磁盘有没有靠 `flushDiskType`（`ASYNC_FLUSH` / `SYNC_FLUSH`）→ 别的机器有没有靠 `brokerRole`（`ASYNC_MASTER` / `SYNC_MASTER`）→ 两开关组合出四档语义 → 落在哪一段失败对应不同的补法 → 最终汇总成「三段责任表」：生产端 → Broker 存储 → 消费端，每段只对段内失败负责，跨段的窟窿由下一段兜 → 而「不重」Broker 完全不管，只有消费端幂等一道闸。

**链二：「RocketMQ 为什么能挂万级队列？」**

万级队列要求写吞吐与队列数解耦 → 若每队列一条日志，写头分散、顺序写退化成随机写 → 所以把全部 Topic **混写**进一条 CommitLog，全机只有一个追加点 → 代价是读某队列时数据散落全日志（实测物理偏移不连续） → 于是必须有二级索引把「逻辑顺序」重建出来 → 用**定长 20 字节**的 ConsumeQueue 让寻址变成纯算术（`queueOffset × 20`）→ 队列扩展成本降到「加一个索引文件」 → 万级队列可行；而 Kafka 是分区级日志、扩展成本是「加一套日志段与句柄」，所以数百分区就是警戒线。
