## 一、定位与选型

- **ActiveMQ 和 Artemis 是什么关系？** 不是版本升级，是**两套实现**：Artemis 源自 HornetQ 捐赠，核心协议（Core Protocol）、地址模型（Address / Queue 分离）、存储（分页 journal）与集群方式都重写；Classic 的 `activemq.xml` 在 Artemis 里不认。详见 [核心概念与架构.md](核心概念与架构.md) 第五节。
- **为什么 ActiveMQ 不适合做数据管道？** 存储是「一个 broker 一个 KahaDB 目录」，单队列不能拆分区，**吞吐上限 = 单 broker 上限**；且 ack 即删、无 retention 重放。Kafka 的分区日志恰好解决这两点。详见 [README.md](../Kafka/README.md)。
- **什么场景反而该选它？** 维护存量 JMS 系统、Spring JMS 绑定、需要 MQTT / STOMP / AMQP 多协议同进程接入且量不大。六款 MQ 的横向对照见 [消息队列选型对比.md](../消息队列选型对比.md)。
- **Classic 已经停止维护了吗？** 没有停止，但社区活跃度明显下降，Apache 的官方后继是 Artemis。**新项目的默认答案不再是它**，存量系统的迁移成本才是它的主要价值。

## 二、语义与顺序

- **Queue 和 Topic 最容易被忽略的差别是什么？** 不是「一对一 / 一对多」，而是**消费者离线期间消息归谁**：Queue 留着，Topic 直接丢（除非持久订阅）。详见 [消息类型与消费语义.md](消息类型与消费语义.md) 第一节。
- **怎么保证同一订单的消息有序？** 只能显式设 `JMSXGroupID`。本机实测：带 GroupID 时两个消费者各拿两组、每组 20 条整组归属；不带时同一业务键被拆成 `2/8`、`1/9`——**普通业务属性不会产生亲和**。详见 [消息类型与消费语义.md](消息类型与消费语义.md) 第三节。
- **selector 能当多租户隔离用吗？** 不能。它在 broker 侧过滤，但**被滤掉的消息仍占队列空间**，直到被消费或过期。隔离要用不同队列，selector 只做同队列内的细分。
- **prefetch 默认值是多少？** 本机 6.1.4 实测：queue **1000**、topic **32767**、queueBrowser **500**、durableTopic **100**。默认值偏向吞吐，多实例负载不均时先把它调小。
- **Topic 能当 Kafka 用吗？** 不能。Topic 只保留「持久订阅的游标」，没有日志保留与任意位点重放；没有订阅者时消息直接丢。

## 三、可靠性

- **`send()` 返回就代表消息落盘了吗？** 不一定。`useAsyncSend=true` 时只代表进了客户端发送缓冲；broker 崩溃会丢最后一批。要「发了就算数」用同步发送或事务提交。详见 [消息可靠性.md](消息可靠性.md) 第二节。
- **`maximumRedeliveries=2` 到底投几次？** **首次 + 2 次重投 = 3 次**，`JMSXDeliveryCount` 依次为 1、2、3，第 4 次取不到（已进 DLQ）。本机实测如此——把它当「总共 2 次」会算错一倍。详见 [消息可靠性.md](消息可靠性.md) 第四节。
- **怎么保证不丢消息？** PERSISTENT + `CLIENT_ACKNOWLEDGE`（先处理再 ack）+ `redeliveryPolicy` 兜底重投 + DLQ 有人消费 + 业务幂等；任何一环缺了，丢的形态都不一样。
- **怎么保证不重复？** 中间件不提供 exactly-once。`JMSXDeliveryCount` 只是观测工具，真正的方案是消费端幂等（唯一键 / 去重表 / 状态机条件更新）。
- **DLQ 会拖垮 broker 吗？** 会。死信仍是持久消息，占同一个 KahaDB store；DLQ 越积越多会推高 `StorePercentUsage`，最终触发全 broker 流控。上线时必须给 DLQ 配消费或归档任务。

## 四、部署与协议

- **为什么本机开了 61616 却连不上 STOMP？** 因为 STOMP 是 **61613**，且本机宿主只映射了 61616 / 8161。连接器在容器内存在，不等于宿主端口可达。详见 [部署与配置.md](部署与配置.md) 第二节。
- **延迟消息为什么不生效？** `schedulerSupport` 没开。本机未开时 `AMQ_SCHEDULED_DELAY=5000` 只延迟 **171 ms**，开启并重启后 **5113 ms**——属性被静默忽略，不报错。详见 [部署与配置.md](部署与配置.md) 第四节。
- **AMQP 5672 能直接用 RabbitMQ 客户端吗？** 不能。ActiveMQ 开的是 **AMQP 1.0**，RabbitMQ 生态主流是 **0-9-1**；TCP 能连上，握手失败。详见 [ActiveMQ协议.md](ActiveMQ协议.md) 第四节。
- **OpenWire 需要专门学吗？** 不需要。它是 Classic 私有协议、只有一家实现、无 RFC 级规范，Java 客户端已处理编解码；非 JVM 语言走 STOMP 更省。它真正的价值是解释「JMS 无字节、字节由 broker 定」。
- **生产者卡住但不报错是什么？** producer flow control：`MemoryPercentUsage` / `StorePercentUsage` 触顶后 broker 让 `send()` 等待，不抛异常。查水位，别重启。详见 [运维与排障.md](运维与排障.md) 第三节。

## 五、两条答题链

**① 「ActiveMQ 怎么保证消息不丢？」** → `DeliveryMode.PERSISTENT` 落 KahaDB → 同步发送或事务提交（`useAsyncSend` 的返回不代表落盘）→ 消费侧 `CLIENT_ACKNOWLEDGE`、先处理再 ack → 失败按 `redeliveryPolicy` 重投 → 超过 `maximumRedeliveries` 进 `ActiveMQ.DLQ` → DLQ 必须有消费 / 归档，否则占满 store 触发流控 → 全链路仍是 at-least-once，业务必须幂等。

**② 「为什么消息会重复，怎么做到只处理一次？」** → ack 与处理是两个动作，ack 前崩溃必然重投 → 事务会话只保证「一批要么全确认要么全回滚」，回滚后整批重投 → 所以重复是语义的一部分 → 业务侧用唯一键 / 去重表 / 状态机条件更新兜底 → `JMSXDeliveryCount` 用来观测重投率，不能用来去重。
