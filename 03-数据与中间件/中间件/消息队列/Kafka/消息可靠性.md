# 消息可靠性

> 覆盖「不丢」要在生产者 / Broker / 消费者三侧怎么配、「不重」为什么必须落在消费端、`acks=all` 到底保证到哪一步，以及一组本机实测：**ISR 少于 `min.insync.replicas` 时写入会被怎么对待**。

> 不覆盖：ISR 的定义与副本分布见 [核心概念与架构.md](核心概念与架构.md)；位点提交与重平衡的关系见 [消费者组与重平衡.md](消费者组与重平衡.md)；重复消费与积压的处置见 [运维与排障.md](运维与排障.md)。

## 一、「不丢」要在三处同时配置

端到端「不丢」必须在**生产者、Broker、消费者**三处同时成立，任何一处漏了都会丢。缺一不可的关系是：

| 环节 | 只做这一侧会怎样 |
| --- | --- |
| 生产者 `acks=all` | 消息确实送到了所有 ISR，但**消费端可能在业务处理前就提交了位点** |
| Broker `replication.factor≥3` | 副本多了，但**生产者没等确认**，或 ISR 只剩 1 个时「all」形同虚设 |
| 消费者手动提交 | 处理成功才提交，但**上游已经被丢掉了** |

> ⭐ 一句话：**丢消息从来不是某个参数没设，而是三处里有一处被漏掉了。**

## 二、生产者侧：`acks` / 重试 / 幂等 / 事务

| 配置 | 取值 | 语义 | 影响 |
| --- | --- | --- | --- |
| **`acks`** ⭐ | `0` | 发出即成功 | 最快、最可能丢 |
| | `1` | Leader 写入即成功 | 默认；Leader 刚写完就宕机则丢 |
| | `all`（=`-1`） | **ISR 全部同步完成**才成功 | 最可靠；须配合 `min.insync.replicas` |
| `retries` | 整数 | 可重试异常的重试次数 | 默认极大；由 `delivery.timeout.ms` 兜底 |
| **`enable.idempotence`** ⭐ | `true` | **幂等生产者**：按 `(PID, 分区, 序列号)` 去重 | 解决**重试导致的重复写**，是「不重」的第一道防线 |
| `max.in.flight.requests.per.connection` | 5 | 单连接未确认请求数 | 开幂等后可 >1 而不乱序 |
| 事务 | `transactional.id` | 跨分区**原子写** + 消费-处理-生产的 EOS | 有额外开销，主要用于流处理 |

```java
// 生产端最稳组合（幂等 + 全 ISR 确认）
props.put("acks", "all");
props.put("enable.idempotence", true);   // 自动要求 acks=all 且 retries>0
props.put("max.in.flight.requests.per.connection", 5); // 开启幂等后可 >1 仍不乱序
```

> ⚠️ 三个易错点：① `acks=all` 只保证「ISR 都收到并写进各自的 PageCache」，**不保证落盘**（是否刷盘由内核决定，实测 `log.flush.interval.messages` 默认是 `Long.MAX_VALUE`）；② 幂等只防**同一生产者实例的重试重复**，防不了业务重复提交与消费重复；③ `acks=all` 必须配 `min.insync.replicas ≥ 2`，否则 ISR 只剩 Leader 时也满足「all」，形同 `acks=1`。

## 三、Broker 侧：副本数与写入门槛

| 配置 | 作用 | 建议 | 实测默认值 |
| --- | --- | --- | --- |
| **`replication.factor`** | 每分区副本总数 | 生产 **≥ 3** | `default.replication.factor` 默认 **1** ⚠️ |
| **`min.insync.replicas`** ⭐ | 写入时要求 ISR 至少多少副本 | **≥ 2** | **1** |
| **`unclean.leader.election.enable`** ⚠️ | 是否允许**非 ISR 副本**当选 Leader | 保持 `false` | `false` |

> ⭐ 取舍口诀：**`acks=all` + `min.insync.replicas=2` + `replication.factor=3` + `unclean=false` = 不丢但可能拒写；把 `unclean` 开成 `true` = 不拒写但可能丢数据。**
>
> ⚠️ `unclean.leader.election.enable=true` 的代价是**永久丢数据**：落后副本顶替成为 Leader 后，它没同步到的那些消息就此消失。

## 四、消费者侧：手动提交与位点语义

| 配置 | 取值 | 语义 |
| --- | --- | --- |
| **`enable.auto.commit`** ⭐ | `false` | **手动提交**；默认为 `true` 会周期性自动提交，⚠️ 可能在业务处理**之前**就提交位点 → 处理失败即丢消息 |
| **`auto.offset.reset`** | `earliest` | 该组**无已提交位点**时，从头（最早）开始消费 |
| | `latest` | 无位点时只消费新消息（默认） |
| | `none` | 无位点直接抛异常，强制显式管理位点 |
| `isolation.level` | `read_committed` | 只读已提交的事务消息 |

> ⚠️ `auto.offset.reset` **只在「找不到已提交位点」时生效**（新组、位点过期被清理、手动重置），**不是**「每次启动都从这里开始」——这是最高频的误解。
>
> ⭐ 正确顺序永远是：**先处理业务，成功后再提交位点**。处理失败就不提交，靠消费端幂等承担重复。

## 五、实测：ISR 少于 `min.insync.replicas` 时会发生什么

这是「`acks=all` + `min.insync.replicas`」这条链上最容易含混的一步。本机实验设计：建两个 Topic，都用 3 分区 3 副本，唯一差别是 **`strict-events` 的 `min.insync.replicas=3`、`order-events` 的 `min.insync.replicas=1`**；然后停掉一台 broker，在**同一时刻、同一集群状态下**分别写入。

**第一步：ISR 会收缩。** 停掉 broker 3 并等待 `replica.lag.time.max.ms`（实测默认 30000 ms）后：

| Topic | 分区 | 停机前 Isr | 停机后 Isr | Leader 变化 |
| --- | --- | --- | --- | --- |
| `strict-events` | P1 | `3,1,2` | `1,2` | **Leader 由 3 改选为 1** |
| `order-events` | 全部分区 | `1,2,3` | `1,2` | 落在 broker 3 上的分区改选到其他副本 |

**第二步：`acks=all` 被拒。** 对 `strict-events` 写入时生产者连报三次重试后失败：

```text
WARN  ... Got error produce response ... Error: NOT_ENOUGH_REPLICAS
ERROR ... org.apache.kafka.common.errors.NotEnoughReplicasException:
           Messages are rejected since there are fewer in-sync replicas than required.
```

**第三步：`acks=1` 会被接受，但写下的数据「读不到」。** 同样条件下改用 `acks=1` 写 2 条：生产者**不报错**，但位点读数**纹丝不动**。

| 观察时刻 | `strict-events`（minIsr=3）位点 | `order-events`（minIsr=1）位点 |
| --- | --- | --- |
| 写入前 | `P0:3  P1:0  P2:0` | `P4:966` |
| 写入后（ISR=2） | `P0:3  P1:0  P2:0` —— **没动** | `P4:968` —— **立刻 +2** |
| broker 3 回归后 | `P0:3  P1:2  P2:2` —— **补齐了** | —— |

> ⭐ **结论：当 ISR 数量少于 `min.insync.replicas` 时，Leader 会停止推进 HW（高水位）。**
>
> - `acks=1` 的写入仍然被接受，数据也确实进了 Leader 的日志，但 **HW 不前进 → 消费者读不到**（消费者只能读到 HW 之前的消息）；`kafka-get-offsets.sh` 读到的位点就是被冻住的那个值。
> - 等副本回来、ISR 恢复后，位点**立刻补齐**（上表 `0 → 2` 正好是那两条消息）。
> - 对照组 `order-events`（`minIsr=1`）在同一时刻位点**正常推进**，说明冻住的原因是 `min.insync.replicas` 这个门槛，而不是「停了一台机器」本身。

这条现象的实用价值在两个方向：

| 场景 | 怎么用这条判据 |
| --- | --- |
| 排障 | 生产者还在「成功」写、消费者却突然不消费 → 先查 `--describe` 的 `Isr` 与 `min.insync.replicas`，而不是先怀疑消费者 |
| 选型 | 想让「ISR 不足时宁可拒写」，就把 `min.insync.replicas` 提上去（配 `acks=all`）；想「只要 Leader 活着就能写」，就接受 `acks=1` 那条更短但更脆的路径 |

## 六、结论表：「不丢」与「不重」怎么权衡

| 目标 | 生产者 | Broker | 消费者 |
| --- | --- | --- | --- |
| **不丢（At Least Once）** | `acks=all` + `retries>0` + 确认回调 | `replication.factor≥3`、`min.insync.replicas≥2`、`unclean=false` | **先处理业务，成功后再 `commitSync`** |
| **不重（幂等）** | `enable.idempotence=true` | —— | **消费端幂等**：唯一键去重表 / Redis SETNX / 状态机 CAS / DB 唯一索引 |
| **恰好一次（仅限流内）** | 事务 + `transactional.id` | `transaction.state.log.replication.factor≥3` | `isolation.level=read_committed` + 位点写入同一事务 |

> ⭐ 现实结论：Kafka 只能保证 At Least Once 的「不丢」，**「不重」必须靠消费端幂等**；「恰好一次」只在 Kafka 内部流处理链路（读 Topic → 写 Topic）严格成立，**跨系统（写 MySQL / 发 HTTP）永远做不到**，只能幂等等价实现。
>
> ⚠️ 幂等键要用**业务唯一键**，不要用 offset——重平衡后同一批消息会换 offset。

## 延伸追问

- **`acks=all` 就不会丢消息吗？** → 不一定。① 只保证 ISR 都收到并写进各自 PageCache，**不保证落盘**；② 若 `min.insync.replicas=1` 且 ISR 只剩 Leader，等价 `acks=1`；③ 生产端未处理发送异常仍会丢。要三处齐配：`acks=all` + `min.insync.replicas≥2` + `replication.factor≥3` + `unclean=false` + 消费端先处理后提交。
- **ISR 少于 `min.insync.replicas` 时，`acks=1` 还能写吗？** → 能写，但**消费者读不到**：Leader 停止推进 HW，位点读数冻住，直到 ISR 恢复（本机实测：`P1/P2` 从 `0` 冻住，副本回归后补到 `2`）。
- **`enable.auto.commit=true` 有什么风险？** → 它按 `auto.commit.interval.ms` 周期提交，可能在**业务处理成功之前**就提交了位点；此时消费者崩溃，重启后从已提交位点继续 → 那批消息永久丢失。高可靠场景一律 `enable.auto.commit=false` + 处理成功后手动 `commitSync`。
- **`unclean.leader.election.enable=true` 想解决什么、代价是什么？** → 它让「非 ISR 副本」也能当选 Leader，换来「不拒写」，代价是**落后副本没同步到的消息永久丢失**。默认 `false` 是刻意的取舍。
- **「不重」为什么不能靠 Kafka 配置解决？** → 幂等生产者只能防**自己实例的重试重复**；跨系统的「消费-处理-写库」没有分布式事务，所以只能靠消费端幂等（业务唯一键），或把位点与业务数据放进同一事务（仅限 Kafka 内部链路）。
