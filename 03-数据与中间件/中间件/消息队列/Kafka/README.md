## 一、一句话定位与它凭什么

**Kafka 是分布式事件流平台，不只是消息队列**——官方给它三重身份：**消息队列 + 存储系统 + 流处理平台**。一条消息写进来，既可以当队列消费，也可以当可重放、可长期留存的日志。

| 卖点 | 说明 |
| --- | --- |
| **高吞吐** | 顺序写 + PageCache + 零拷贝 + 批量压缩 + 分区并行，单机十几万 msg/s 量级 |
| **可持久化** | 落盘保留（默认 7 天），**不是消费即删** |
| **可重放** | 位点由消费者自己管理，可任意回退重读 |
| **水平扩展** | 加 Broker 分摊分区、加分区提并行度 |
| **生态事实标准** | Flink / Spark / Debezium / Connect 的数据总线默认落点 |

> ⭐ 与传统 MQ 最本质的差异：传统 MQ **消费即删**，Kafka **消费后不删除**，靠 Offset 标记进度，清理交给时间或大小到期删除——数据模型是一条 **append-only、不可变、可截断的分区日志**。
>
> 一句话记忆：**Kafka 的 Topic 是一条只会追加、不会插队的日志；消费者不是「拿走」消息，而是「往前挪自己的书签」。**
>
> ⚠️ 也正因为这套设定，Kafka **没有原生延迟消息、没有消息级 TTL、也没有半消息事务回查**——选型时这三项最容易直接筛掉它。

## 二、核心概念速览

| 概念 | 一句话 |
| --- | --- |
| **Broker** | 一个服务节点，承载若干分区的 Leader 或 Follower |
| **Topic** | 消息的**逻辑分类**，物理上由若干 Partition 承载 |
| **Partition** ⭐ | Topic 的**物理分片**，是并行与有序的**基本单位**（一份 append-only 日志） |
| **Offset** | 消息在**某个分区内**的递增序号，⚠️ 跨分区不可比 |
| **Consumer Group** ⭐ | 组内**分摊**分区、组间**各自独立**；一条消息在一个组内只被消费一次 |
| **Replica** | 分区副本，**Leader 读写、Follower 只拉取同步**（不对外服务） |
| **ISR** | 与 Leader 保持同步的副本集合 ⭐ `acks=all` 的「all」指的就是它 |
| **Controller** | 集群「大脑」，负责分区 Leader 选举与 Broker 上下线（KRaft 时代由 Controller Quorum 承担） |
| **`__consumer_offsets`** | 内部 Topic，存各消费组的提交位点（默认 50 分区） |

> ⭐ **铁律：分区内有序，分区之间无序。** 要「同一实体的消息有序」，就用业务 key 做分区路由（`hash(key) % 分区数`），让同 key 永远落同一分区。

## 四、本轮实测坐标

| 项 | 值 |
| --- | --- |
| 镜像 / 版本 | `apache/kafka:3.9.0`（KRaft，`broker,controller` 合并角色） |
| 集群 | 三节点容器 `kafka-lab-1/2/3`，网络 `kafka-lab-net`，宿主端口 19091/19092/19093 |
| 资源 | 4 核 / 5.79 GiB 内存 |
| 场景 Topic | `order-events`（6 分区 3 副本，按 key 生产 6000 条）、`strict-events`（3 分区 3 副本 + `min.insync.replicas=3`）、`zc-lab`（1 分区 1 副本，用于生产/消费 CPU 对照）、`go-lab`（3 分区 3 副本，用于 Go 客户端验证） |

三条最值得记住的读数：

| 读数 | 值 | 出处 |
| --- | --- | --- |
| 副本是真拷贝，不是校验块 | 同一分区在三个节点上的 `size` 完全相等、`offsetLag` 全为 0、`.log` 的 sha256 三节点一致 | [核心概念与架构.md](核心概念与架构.md) 第三节 |
| ISR 少于 `min.insync.replicas` 时位点会冻住 | `strict-events`（minIsr=3）在 ISR=2 期间位点 `0 → 0`，副本回归后补到 `2`；同期 `order-events`（minIsr=1）位点立刻 +2 | [消息可靠性.md](消息可靠性.md) 第五节 |
| 消费路径的 CPU 与数据量脱钩 | 同一份 300 MiB，Broker 进程 CPU 生产 ≈ 30.6 s、消费 ≈ 1.8 s（差约 17 倍） | [核心概念与架构.md](核心概念与架构.md) 第七节 |

> ⚠️ **未实测项**：零拷贝没有做系统调用级验证（本机容器内核未暴露 `/proc/<pid>/io`、镜像内无 `strace`），只有端到端 CPU 对照；Java 客户端未编译运行；事务（`transactional.id`）与 `unclean.leader.election.enable=true` 的丢数据路径未实测。
