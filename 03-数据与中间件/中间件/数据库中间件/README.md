## 一、这个目录回答什么问题？

**本节要点**：数据库中间件只解决三类问题——**放不下、读不动、连不上**。先判断瓶颈属于哪一类，再决定要不要加这一层。

![数据库中间件的三类问题与归属：分库分表、读写分离、连接池代理各自的主答案在哪](images/数据库中间件的三类问题与归属.svg)

这张图只做一件事：把「症状 → 该加什么 → 主答案在哪」固定下来。三类的共同前提是「索引、SQL、缓存都优化完仍不够」——中间件不是第一步手段。

## 三、按问题走阅读顺序

| 你现在的状态 | 读哪几节 |
|---|---|
| 单表快放不下了，先判断该不该分 | [中间件选型.md](../中间件选型.md) → [分表与路由.md](../../数据存储/关系型/MySQL/分表与路由.md) 第二节（先算三本账） |
| 决定分了，选哪种路由 | [分表与路由.md](../../数据存储/关系型/MySQL/分表与路由.md) 第一节（三种路由方案推演） |
| 路由选定，要在框架里落配置 | [ShardingSphere.md](ShardingSphere.md) 第二节（配置模型）→ 第三节（三类特殊表） |
| 主键用雪花，想知道能不能拿它分表 | [ShardingSphere.md](ShardingSphere.md) 第四节（实测：低位不是散列） |
| 有 JOIN、有分页、有 UPDATE，想知道哪些不能干 | [ShardingSphere.md](ShardingSphere.md) 第五节（支持边界与静默错误） |
| 报错了，想知道是哪一类配置问题 | [ShardingSphere.md](ShardingSphere.md) 6.2（报错对照表） |

⭐ 顺序判据：**先决策（该不该分）再选路（怎么分）最后落配置**。反过来做，往往在框架配置上耗掉几天，最后发现分片键选错了——那等于推倒重来。
