# 分布式协调选型对比

> 分布式锁 / Leader 选举 / 变更监听三类「协调」需求的底座选型：Redis、etcd、ZooKeeper 与数据库唯一键的取舍。
> ⭐ 这是 [中间件选型.md](../中间件选型.md) 协调族的**族内横评**（产品粒度）——「要不要引协调族、引哪一子类」的上一层判断在那篇，
> 本篇只回答「锁 / 选主 / 监听分别用哪个产品」。
>
> 内容整理自个人学习笔记，素材见 [素材清单.md](../../../素材清单.md)。

## 一、「分布式协调」要解决的是哪三类问题？

**本节要点**：先分清「协调」与「注册配置」的边界 —— 前者是**进程间的互斥与选举**，后者是**服务实例的路由信息**。
两者常被混为一谈，因为它们常由同一个底座（etcd / ZooKeeper）承担。

| 需求 | 一句话 | 对底座的核心要求 |
|---|---|---|
| **分布式锁** | 同一时刻只允许一个持有者进入临界区 | 互斥 + 自动释放（**租约 / 会话**，防止持有者宕机后死锁） |
| **Leader 选举** | 一主多从里选出唯一主 | 强一致（避免双主）+ **变更通知**（主挂了从要立刻知道） |
| **变更监听** | 配置 / 元数据变了，所有关心方收到推送 | Watch / 订阅机制 + 可靠的**推送语义** |

⭐ **一句话分界**：**注册与配置中心**管「谁在哪儿、配置是什么」（服务发现的路由信息），
**分布式协调**管「谁先谁后、谁说了算」（进程间的互斥与选举）。
现实中两者常共用同一套底座，但**职责不同、SLA 也不同**：协调组件短时挂会阻塞新锁与新选举，注册中心短时挂只影响新实例上下线。

## 二、四种底座怎么选？

**本节要点**：这张表只回答「用哪一个产品」。⚠️ 底层的 CP / AP 理论见
[一致性与CAP.md](../../../04-架构与系统/分布式/理论/一致性与CAP.md)，共识算法的原理见 [Raft协议.md](../../../04-架构与系统/分布式/理论/Raft协议.md)。

| 底座 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|
| **Redis**（`SET NX PX` / Redlock） | 性能最高（十万级 QPS）；部署最简单；开发最熟悉 | ⚠️ **主从异步复制**：主挂时锁可能被两个客户端同时持有；需自己实现续期、可重入、释放校验（Lua 比对 value） | 高并发互斥（防重复提交、幂等保护），**允许极小概率失效** |
| **etcd** | Raft 强一致；租约（Lease）到期自动释放；Watch 天然支持变更通知 | 写性能低于 Redis（万级）；不适合超高频写 | **Leader 选举**、分布式队列、强一致要求的锁 |
| **ZooKeeper** | 临时顺序节点 + Watch 成熟；久经考验 | 运维重；性能一般；羊群效应 | 「顺序 + 监听」语义（如分布式队列、选主），或已有 ZK 生态 |
| **数据库唯一键** | 零新增组件，事务天然保证 | 性能差、易成瓶颈 | 极低频兜底互斥（如一次性初始化） |

⭐ **一句话选型**：**要强一致 + 自动续期 → etcd；要性能 + 能接受极小概率双持 → Redis；已有 ZK 生态 + 需要顺序语义 → ZK。**

⭐ **契合语言**：三者都有官方多语言 client，**语言在这里几乎不构成约束** ——
与 [RPC框架选型对比.md](../RPC框架/RPC框架选型对比.md) 那类「客户端质量决定上线速度」的子类不同，
协调底座的判据退回**一致性要求**与**运维面**：etcd / ZooKeeper 是单二进制或小集群（但 ZK 有 JVM 调优负担），
Redis 通常已在栈内（边际成本最低），数据库唯一键则完全不需要新组件。

## 三、Redis 锁的争议：为什么不追求「绝对安全」？

**本节要点**：这是「选 Redis 还是 etcd 做锁」这个问题里最容易答错的一层 ——
争议的**不是实现细节，而是「在异步复制的系统上追求强一致是否可能」**。

Redis 主从是**异步复制**：主写入锁之后、还没来得及同步就宕机，从提升为主时**锁就丢了**，
于是可能出现**两个客户端同时持锁**。Redlock 试图用「多数派 + 时钟漂移上界」来补，
但它仍然依赖**时钟假设**与**各节点互相独立的失效模型**，因此一直存在争论。

⚠️ **工程上的正解不是「换一把更保险的锁」，而是让临界区本身幂等** ——
即使两个客户端都进了临界区，最终结果也正确（例如用唯一键去重、用版本号做 CAS）。
需要**强一致**时才改用 etcd / ZooKeeper；此时付出的是写性能与运维成本。

## 延伸追问

- **为什么 Redis 分布式锁有争议？** → 主从异步复制下，主写入锁后未同步就宕机，从提升为主时锁丢失，可能出现两个客户端同时持锁。⚠️ 工程解法不是「换更保险的锁」，而是让**临界区操作幂等**；强一致要求高则改用 etcd / ZK。
- **etcd 和 Redis 都能做选主，怎么选？** → 看是否需要**强一致 + 事件通知**：etcd 的租约到期自动释放 + Watch 变更通知，天然适合选主；Redis 需要自己实现续期与监听，但性能更高，适合「高频但可容忍极小概率失效」的场景。
- **为什么 ZooKeeper 逐渐被 etcd / KRaft 替代？** → ZK 是独立集群，运维成本高、元数据规模受限（分区数上限）、Controller 故障恢复慢；etcd 把「Raft + Watch」做得更轻，KRaft 让 Kafka 把元数据自管理。⚠️ 但存量大数据生态（HBase / Hadoop / 老版 Kafka）仍强依赖 ZK，撤不掉。
- **数据库唯一键也能做锁，为什么不推荐？** → 它能做（靠唯一索引冲突），但**性能差、易成瓶颈**，且缺少自动续期与变更通知。只在**极低频兜底互斥**（如系统初始化只跑一次）时才用它。
- **「注册中心」和「分布式协调」是同一个东西吗？** → 不是。注册中心管「**服务实例的路由信息**」（谁在哪儿），分布式协调管「**进程间的互斥与选举**」（谁说了算）。两者常共用 etcd / ZK 同一套底座，但职责与 SLA 不同。
