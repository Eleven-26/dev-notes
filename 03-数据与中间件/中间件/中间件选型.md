# 中间件技术选型

> 注册中心与配置中心、分布式协调底座、API 网关三类中间件的横向对比（技术 × 优缺点 × 适用场景），并汇总本仓库已有的消息队列、分布式定时任务选型。

## 一、选型先看这五个维度

中间件选型失败多半不是因为「选错了技术」，而是因为**没先想清楚约束**。统一按下面五条过一遍：

| 维度 | 要问的问题 |
| --- | --- |
| **一致性要求** | 允许短暂不一致吗（AP）？还是必须线性一致（CP）？ |
| **部署与运维成本** | 单二进制还是多组件？依赖外部存储吗？团队有人会调优吗？ |
| **性能量级** | 需要万级还是十万级 QPS？写入是高频还是低频？ |
| **生态与语言支持** | 项目语言（Go / Java / PHP）有官方 SDK 吗？社区是否活跃？ |
| **可观测与降级** | 有 metrics 端点吗？它挂了业务能起吗？有兜底路径吗？ |

⭐ **第一条铁律：同类中间件只引一种**。两套注册中心 = 两套运维 + 数据不一致 + 排查时不知道看哪个。引入新组件前先问一句：**不用它，用现有组件能不能解决？**

## 二、注册中心与配置中心怎么选？

这是最容易被「顺手多引一个」的地方。先明确两者的职责差异：

| 角色 | 解决什么 | 关键能力 |
| --- | --- | --- |
| **注册中心** | 服务实例的地址如何被动态发现 | 健康检查、实例上下线通知、本地缓存兜底 |
| **配置中心** | 配置如何集中管理并动态生效 | 版本管理、灰度发布、审计、回滚 |

| 对比维度 | **Nacos** | **etcd** | **Consul** | **ZooKeeper** | **Eureka** |
| --- | --- | --- | --- | --- | --- |
| 定位 | 注册 + 配置一体化 | 分布式 KV（K8s 的底座） | 服务网格配套：注册 + 健康检查 + KV + 多数据中心 | 分布式协调原语（临时节点 / Watch / 顺序节点） | 服务注册（Netflix OSS） |
| 一致性 | **AP + CP 双模型**：临时实例走 Distro（AP），持久实例与配置走 Raft（CP） | Raft（CP） | Raft（Server 间，CP）+ Gossip（成员管理） | ZAB（CP） | AP（无一致性协议，Peer 间异步复制） |
| 健康检查 | 客户端心跳（临时实例）/ 服务端主动探测（持久实例） | 租约（Lease）+ Watch | 客户端 / 服务端 / 脚本 / TTL 多种 | 会话（Session）心跳 | 客户端心跳 |
| 配置管理 | ⭐ 内置（命名空间 / 分组 / 灰度 / 历史版本） | 只有 KV，需自建下发（confd 等） | 有 KV，配置能力弱 | 有 ZNode，配置能力弱 | ❌ 不支持 |
| 控制台 | ⭐ 内置 Web | 无（需第三方 UI） | 内置 | 无（需 ZooInspector） | 内置（但已停更） |
| 多语言 | Java / Go / Python / Node / PHP 等 | ⭐ 官方多语言 client | 官方多语言 | 官方多语言 | 主要 Java |
| 运维复杂度 | **低**（单二进制 + MySQL 存储） | 低（单二进制） | 中 | **高**（JVM 调优 + 会话数敏感 + 需谨慎扩缩） | 低（但已停止演进） |
| 适用场景 | Java / Go 微服务，要「注册 + 配置」一体 | 已在 K8s、只要轻量服务发现与选主 | 多数据中心、多云、已用 HashiCorp 栈 | 存量大数据生态（HBase / Hadoop / 老版 Kafka） | 存量 Spring Cloud Netflix 项目 |

### 2.1 决策结论

| 你的情况 | 选它 | 理由 |
| --- | --- | --- |
| 新项目（Java / Go 微服务） | **Nacos** | 注册与配置一体、内置控制台、单二进制部署、国内社区成熟 |
| 已在 K8s，只需要服务发现 / 选主 | **etcd** | K8s 本身就跑在 etcd 上，不必再引一套；官方多语言 client 质量高 |
| 多数据中心 / 多云容灾 | **Consul** | 原生多 DC 与 WAN Gossip，跨地域成员管理是它的设计目标 |
| 存量大数据组件强依赖 ZK | **ZooKeeper** | Kafka（旧版）/ HBase / Hadoop 都依赖，撤不掉 |

### 2.2 三个高频误区

- ⚠️ **把 etcd 当配置中心**：etcd 只有 KV，没有版本管理、灰度、审计、回滚——这些恰恰是配置中心的核心价值。K8s 里用 ConfigMap 也有类似问题（无灰度、无审计）。
- ⚠️ **Nacos 的 AP/CP 搞混**：`ephemeral=true`（临时实例，默认）用 **Distro 协议（AP）**，实例挂了会被摘除，适合无状态服务；`ephemeral=false`（持久实例）用 **Raft（CP）**，适合需要「即使不健康也要保留地址」的场景（如数据库、MQ 节点）。
- ⚠️ **ZooKeeper 的会话数**：ZK 的会话数与 Watch 数量是内存与网络的主要压力来源，「Watch 羊群效应」（一个节点变更唤醒所有监听者）是经典问题，也是 Kafka 用 KRaft 取代 ZK 的动因之一。

## 三、分布式协调底座怎么选？（锁 / 选主 / 监听）

分布式锁、Leader 选举、配置监听都属「协调」，底座可以是 Redis、etcd 或 ZK。这三者的取舍非常典型：

| 底座 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- |
| **Redis**（`SET NX PX` / Redlock） | 性能最高（十万级 QPS）；部署最简单；开发最熟悉 | ⚠️ **主从异步复制**：主挂时锁可能被两个客户端同时持有；需自己实现续期、可重入、释放校验（Lua 比对 value） | 高并发互斥（防重复提交、幂等保护），**允许极小概率失效** |
| **etcd** | Raft 强一致；租约（Lease）到期自动释放；Watch 天然支持变更通知 | 写性能低于 Redis（万级）；不适合超高频写 | **Leader 选举**、分布式队列、强一致要求的锁 |
| **ZooKeeper** | 临时顺序节点 + Watch 成熟；久经考验 | 运维重；性能一般；羊群效应 | 「顺序 + 监听」语义（如分布式队列、选主），或已有 ZK 生态 |
| **数据库唯一键** | 零新增组件，事务天然保证 | 性能差、易成瓶颈 | 极低频兜底互斥（如一次性初始化） |

⭐ **一句话选型**：**要强一致 + 自动续期 → etcd；要性能 + 能接受极小概率双持 → Redis；已有 ZK 生态 + 需要顺序语义 → ZK。**

⚠️ Redis 锁的争议（Redlock 之争）本质是 **「在异步复制的系统上追求强一致是否可能」**：Redis 主从切换过程中锁可能被重复持有。工程上的处理是**不追求锁的绝对安全，而是让临界区本身幂等**（即使两个客户端都进了临界区，结果也正确）。

## 四、API 网关怎么选？（速查 + 详见专篇）

网关的关键区分在**流量方向**：南北向（外部 → 内部）与东西向（服务 ↔ 服务）。

| 方案 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- |
| **Nginx / OpenResty** | 性能天花板最高；运维与人才储备最厚；Lua 可扩展 | 动态路由需 reload 或自研控制面；无内置管理界面与插件市场 | 自建南北向入口；已有 Nginx 运维体系（怎么写见 [OpenResty.md](OpenResty.md)） |
| **Apache APISIX** | 配置存 etcd，**改路由无需 reload**；插件丰富（认证 / 限流 / 灰度 / 可观测）；国内社区活跃 | 生态相对新，深度定制资料少于 Nginx | 需要动态路由与丰富插件的 API 网关 |
| **Kong** | 插件生态最大；企业版与商业支持完善 | 依赖 PostgreSQL / Cassandra；性能略逊于 APISIX | 国际化团队、需要成熟商业支持 |
| **Spring Cloud Gateway** | 与 Spring 生态无缝；Java 开发者上手快 | 基于 Reactor 响应式，性能取决于调优；绑定 JVM | Java 微服务体系的标准入口 |
| **Traefik** | 与 K8s Ingress 集成极简，服务自动发现 | 复杂路由与插件能力弱于 APISIX / Kong | K8s 环境、轻量入口 |
| **Envoy** | 性能与可观测性极强（原生 metrics / tracing）；Istio 数据面标准 | 配置模型（xDS）复杂，不适合手写维护 | 服务网格数据面，由控制面下发配置 |

⭐ **取舍**：**南北向**用 Nginx / APISIX / Kong（要动态路由选 APISIX，要极致性能选 Nginx）；**东西向**用服务网格（Istio）或框架内置（Kratos 的 selector / Spring Cloud LoadBalancer），不要用南北向网关硬扛东西向流量。

⚠️ **网关该做与不该做**：认证鉴权、限流熔断、路由与灰度、协议转换、访问日志 —— 该做；**业务逻辑（订单校验、库存判断）不该做**，否则网关会变成最难发布的组件。

完整内容见 [网关选型.md](网关选型.md)：**「网关」五种含义的澄清**（流量网关 / API 网关 / 微服务网关 / K8s 入口 / 网格数据面）、Nginx 能力边界的**四组本机实测**（reload 到底掉不掉流量、不改配置能不能换后端、灰度能做到什么程度、上游挂了会自动摘吗）、微服务网关与 K8s 入口的选择、跟服务网格的边界、「一层还是两层」的组合建议、上线检查单与五个高频的坑。

## 五、消息队列选型（速查 + 详见专篇）

| 业务特征 | 推荐 | 契合语言（客户端主场） | 一句话理由 |
| --- | --- | --- | --- |
| 日志采集、埋点、大数据流处理、需要极高吞吐与回溯重放 | **Kafka** | Java/Scala 原生；Go 靠 `kafka-go` / `sarama`（纯 Go） | 吞吐之王（顺序写 + PageCache + 零拷贝），offset 回溯最友好 |
| 业务解耦 + 延迟消息 + 事务消息 + 严格顺序 + 金融级可靠 | **RocketMQ** | ⭐ **Java**（Spring Cloud Alibaba）；Go 客户端是特性子集 | 功能最全：18 级延迟、半消息事务、队列级顺序、同步刷盘 |
| 低延迟、协议成熟、插件与路由灵活、中小规模 | **RabbitMQ** | **语言无关**（AMQP 0-9-1），PHP `amqp` 扩展可直接用 | 微秒级延迟最低，AMQP 生态与插件成熟，运维最轻 |
| 多租户、存算分离、云原生、需要海量 Topic 与任意回溯 | **Pulsar** | Java 功能最全（4.x 要 JDK 17+）；Go 官方且纯 Go | 存算分离（Broker + BookKeeper），扩容只迁所有权不搬数据 |
| Go 技术栈的服务间广播 / Request-Reply / IoT、要求部署极简 | **NATS** | ⭐ **Go**（服务端与 `nats.go` 同源） | 单二进制零依赖 + gossip 组网；Core 不持久化，需要时开 JetStream |
| 存量 JMS 系统、Spring JMS 绑定、多协议接入（MQTT / STOMP / AMQP） | **ActiveMQ**（新项目评估 Artemis） | ⭐ **Java**（JMS 原生）；Go 无官方客户端，走 STOMP / MQTT | 协议最全的 JMS 参考实现；但单队列不可拆分、ack 即删无回放，只建议存量与兼容场景 |

完整对比（11 个维度，含「契合语言 / 客户端成熟度」）与「怎么选」决策表见 [消息队列选型.md](消息队列/消息队列选型.md)；单技术的原理与双语言接入见同目录 [Kafka.md](消息队列/Kafka.md)、[RocketMQ.md](消息队列/RocketMQ.md)、[RabbitMQ.md](消息队列/RabbitMQ.md)、[Pulsar.md](消息队列/Pulsar.md)、[Nats.md](消息队列/Nats.md)、[ActiveMQ.md](消息队列/ActiveMQ.md)。

> ⚠️ **别只看功能表**：功能相近的方案，主语言的客户端质量决定上线速度。Go 团队上 RocketMQ、Java 团队上 NATS，都会先撞上「所需 API 在这门语言的客户端里还没落地」这类问题。

## 六、分布式定时任务选型（速查 + 详见专篇）

| 场景 | 推荐 | 一句话理由 |
| --- | --- | --- |
| Java / Go 微服务里的业务定时任务（对账、报表、清理、补偿） | **XXL-JOB** | 调度与任务解耦、原生集群高可用、控制台可视化、多语言 SDK |
| 已在 K8s，任务是运维 / 一次性 Job | **K8s CronJob** | 无需额外组件，控制面保证不重复调度 |
| 有复杂 ETL 依赖、要回填历史数据 | **Airflow** | 原生 DAG，任务依赖与 SLA 能力最强 |
| 单机 JVM 小工具任务 | `@Scheduled` | 零依赖，够用即可 |
| 存量 Java 单体项目 | Quartz | 改造量最小，但要自建集群 `JobStore` |

⚠️ 多副本部署 + `@Scheduled` = **每个副本都会执行一次**，这是最常见的「定时任务重复执行」事故来源。完整对比（9 个维度）见 [xxl-job.md](xxl-job.md) 的第八节。

## 七、引入中间件的通用原则

1. **同类只引一种**：两套注册中心 / 两套 MQ 会让排查成本翻倍。
2. **先问「能不能不引」**：能靠现有组件（数据库唯一键、Redis、K8s 原生能力）解决就别加新组件——**中间件的长期成本是运维，不是 License**。
3. **优先选单二进制、无外部强依赖的**：`etcd` / `Nacos` / `Traefik` 这类部署成本远低于需要 ZK / 数据库 / JVM 调优的组合。
4. **必查三项**：社区活跃度（最近有没有发版）、项目语言的 SDK 质量（是官方还是社区维护）、**有没有 metrics 端点**（能不能接进可观测性体系）。
5. **必须设计降级路径**：注册中心挂了服务能不能启动（本地缓存）；MQ 挂了写请求是失败还是落本地表；配置中心挂了能不能用上次的配置启动。**没有降级路径的中间件不能上核心链路。**

## 八、延伸追问

- **Nacos 的 AP / CP 是怎么切换的？** → 按实例类型：`ephemeral=true`（临时实例，默认）走 **Distro 协议（AP）**，客户端心跳，实例失联即摘除；`ephemeral=false`（持久实例）走 **Raft（CP）**，不健康也保留地址。配置数据始终走 Raft。
- **注册中心挂了，服务还能互相调用吗？** → 能。客户端会**本地缓存**服务列表，短期调用不受影响；受影响的是①新实例注册不上②已下线实例摘不掉③配置无法动态刷新。所以注册中心属于「不能长时间挂，但短时挂可容忍」的组件。
- **为什么 Redis 分布式锁有争议？** → 主从异步复制下，主写入锁后未同步就宕机，从提升为主时锁丢失，可能出现两个客户端同时持锁。⚠️ 工程解法不是「换更保险的锁」，而是让**临界区操作幂等**；强一致要求高则改用 etcd / ZK。
- **Kafka 为什么从 ZK 转向 KRaft？** → ZK 是独立集群，运维成本高、元数据规模受限（分区数上限）、Controller 故障恢复慢。KRaft 把元数据作为内部 Raft 日志自管理，少一个组件、分区规模与恢复速度都更好。
- **网关该不该做鉴权？** → 该做**认证**（统一入口校验 Token，避免每个服务重复实现）；**授权**（细粒度权限）更适合放在每个服务里，因为网关不了解业务模型。
- **etcd 和 Redis 都能做选主，怎么选？** → 看是否需要**强一致 + 事件通知**：etcd 的租约到期自动释放 + Watch 变更通知，天然适合选主；Redis 需要自己实现续期与监听，但性能更高，适合「高频但可容忍极小概率失效」的场景。
- **怎么判断一个中间件该不该引入？** → 三问：现有组件能不能解决？它的故障会不会影响核心链路（有没有降级）？谁来运维（团队有没有人能调优与排障）？三个问题有一个答不上来，就先别引。
