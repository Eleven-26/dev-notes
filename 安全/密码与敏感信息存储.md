## 一、密码为什么不能明文保存

「密码」只是这类问题的代称：**其它敏感信息同样适用**——比如身份证信息、用户照片等。这类信息一旦验证通过，就**不能保存原信息**（涉及用户隐私，保存原始信息本身可能不合规）。

一般的方案是两类：

1. **验证通过后加密保存**（且不可逆），或
2. **不保存原信息，只标记「该用户已通过身份验证」**——要更换信息只能重新验证（和找回密码同理）。

⚠️ 本文以下以密码为例。注意第 2 条常被忽略：**很多场景根本不需要存那份原始数据**，只存「已核验」这个状态就够了——少存一份数据，就少一份泄露风险。

既然是密码，就不能保存明文，这不用多解释。不能明文，那只能是密文。而密文又分很多种方案：对称加密、非对称加密、散列算法。按「密文能否还原回明文」分为两类：

| 类型 | 能否解密 | 适用 |
| --- | --- | --- |
| 可解密（对称 / 非对称加密） | 可以 | 需要还原原值的场景（如站内加密的敏感字段） |
| **不可解密（散列算法）** | 不可以 | ⭐ **密码**——加密存储后不需要再查看原密码，忘记只能重置或找回 |

⭐ 所以**密码一律用散列算法**（哈希），而不是加密。理由很简单：如果系统自己都能解出密码，那库被脱了就等于密码全泄露。

## 二、散列算法：定长、不可逆，但有碰撞

常见的哈希算法有 **MD 家族的 MD4 / MD5**，**SHA 家族的 SHA-1 / SHA-224 / SHA-256 / SHA-384 / SHA-512**。

**优点**：

- **生成定长字符**：无论多长的字符串，经过哈希后都得到定长结果（MD5 得到 32 位长度的十六进制字符串）；
- **密文不可逆**：无法从密文反推明文。

**缺点**：

- **哈希碰撞不可避免**——因为无论多长的输入都映射到定长输出，必然存在不同输入得到相同输出的情况。原文的比方是：`abc` 和 `abcd` 散列后都输出 `123`（实际当然没这么简单）。

关于碰撞的严重性要有准确认识：

| 算法 | 现状 |
| --- | --- |
| **MD5** | ⚠️ **已被实际破解**（可构造碰撞），且速度极快——**不能用于密码或签名** |
| **SHA-1** | ⚠️ 已实现碰撞攻击（SHAttered），浏览器与 CA 均已弃用 |
| **SHA-256 / SHA-512** | 目前无实际碰撞，但**单独使用依然不适合存密码**（原因见第五节：太快） |

⚠️ 原文说「好的哈希算法几十万亿、几百万亿才出现碰撞，忽略即可」——这个判断对**完整性校验**成立，但对**密码存储**不成立：密码场景的真正威胁不是碰撞，而是**快**。这个问题在第四、五节展开。

## 三、四种密码攻击方式的区别 ⭐

理解攻击方式，才能理解为什么要那样存。原文列了四种，并特别区分了它们的场景：

| 攻击方式 | 前提 | 手段 | 处于什么阶段 |
| --- | --- | --- | --- |
| **猜密码** | 不知道加密方法 | 靠猜常用密码（`123456`、`admin123`、`admin888`，或以手机号 / 身份证后几位为密码） | 进入系统**前** |
| **字典攻击** | 不知道加密方法 | 准备常用密码 / 单词表，遍历比较哈希后的字符 | 进入系统**前** |
| **暴力破解（穷举）** | 不知道加密方法 | 逐个推算直到命中；理论上没有破解不了的密码，只是时间太长 | 进入系统**前** |
| **彩虹表攻击** | ⭐ **已知密码的 hash 值**（库已泄露） | 用预先计算好的「明文 → 哈希」大表反查（主流彩虹表 100G 以上） | 进入系统**后**（离线） |

⭐⭐ **原文对后两者的区分非常关键，也是这题最能体现理解深度的地方**：

```text
暴力破解、字典攻击：完全不知道密码 → 通过系统提供的认证接口不断尝试 → 获取原始口令 → 属于「进入系统前」
彩虹表攻击        ：已知密码 hash 值（用户密码密文已泄露）→ 用自己的工具与彩虹表离线查找 → 获取原始口令 → 属于「处理进入系统后」
```

**这个区别决定了防御手段完全不同**：

| 攻击 | 有效防御 |
| --- | --- |
| 猜密码 / 字典 / 暴力（在线） | **登录失败锁定、验证码、限流、密码复杂度要求**（这些都在「认证接口」这一层） |
| 彩虹表（离线，库已泄露） | ⭐ **加盐 + 慢哈希**（此时网络层的防护全部失效，只剩存储本身的强度） |

⚠️ **这是最容易答错的地方**：很多人一说「防暴力破解」就答「加盐」，但**加盐对在线暴力破解毫无作用**——攻击者是在猜明文，不是在查表。

> 彩虹表本质上是一种**空间换时间**的权衡：比「每次尝试都重新计算哈希」的暴力破解处理时间少、但存储空间多；比「对每条输入都查表」的查表法存储少、但处理时间多。

## 四、加盐：为什么能挡住彩虹表

既然直接用哈希存密码不可靠，就要加点「盐」一起加密。

**原理**：把每个口令与一个叫做「盐」（salt）的 n 位**随机数**关联。口令改变时随机数就改变；随机数以**未加密**的方式存在口令文件里（所以每个人都能读）。存储时不再只存「加密后的口令」，而是**先把口令和随机数连接起来再一同加密**，结果存进口令文件。

**好处**：即使两个用户密码相同，最终密文也不同（每个用户的盐唯一），从而抵挡彩虹表攻击，或大幅提高攻击成本。

### 4.1 实测：加盐前后的差别

**（1）不加盐 —— 同一密码每次注册得到完全相同的摘要**

```text
不加盐·第一次 : c4318372f98f4c46ed3a32c16ee4d7a7
不加盐·第二次 : c4318372f98f4c46ed3a32c16ee4d7a7
摘要相同吗    : true   ← 攻击者预计算一次即可命中所有用该密码的账户
```

**（2）加盐 —— 同一密码每次注册得到不同摘要**

```text
加盐·盐值 1   : 2591d01a2be06e5eb097de835e5ef0b1
加盐·盐值 2   : 8a3af07d4684207aa6a9b8e41eaccb97
第一次摘要    : 20da4bf626382d6d620d966f10a664b8
第二次摘要    : de05569ee1e862ad0ca664d94b8a9cf1
摘要相同吗    : false  ← 即使密码相同，密文也不同
```

**（3）模拟彩虹表攻击：预计算 20 万条常见密码**

```text
彩虹表规模    : 200000 条（摘要 → 明文）
未加盐存储    : 5 / 5 命中（100%）   ← 直接查出明文
加盐存储      : 0 / 5 命中（0%）     ← 表里没有「盐 + 密码」的组合
```

⭐⭐ 这组数字把加盐的价值说透了：**彩虹表命中的前提是「明文 → 摘要」的映射是全局唯一的**；加了盐之后，同一条摘要对应的明文组合变成 `密码 + 随机盐`，攻击者必须为**每一个盐**重新建表——工作量等于用户数 × 单表成本，彩虹表直接失去意义。

### 4.2 盐怎么生成（原文的写法需要修正）

原文生成盐的代码是：

```php
// 确保盐值唯一，用 MD5 加密，得到定长字符好存储
$salt = md5(mt_rand(100000,999999) . uniqid());
```

⚠️ **两处需要修正**：

| 问题 | 说明 |
| --- | --- |
| **随机源不是密码学安全的** | `mt_rand()` 是可预测的伪随机数（梅森旋转算法），`uniqid()` 基于微秒时间戳；攻击者可在有限空间内枚举。应改用 **CSPRNG**（PHP `random_bytes`、Go `crypto/rand`、Java `SecureRandom`） |
| **盐不需要「保密」，但必须「唯一」** | 用哈希处理随机数不是必需的；标准做法是**直接生成 16 字节随机字节**，与密文一起明文存储 |
| 补充 | 盐**无需每个用户都全局唯一**（碰撞概率足够低即可），但**长期存在、不随密码变更以外的时间改变** |

⚠️ 另一个常见错误：**全站共用同一个盐**——这等价于「换了种固定算法」，彩虹表只需为这一个盐重建一次即可，等于没加盐。

## 五、从「加盐 SHA」升级到「慢哈希」

原文的方案是 `sha1($pwd . $salt)`。**加盐解决了彩虹表，但没有解决「快」的问题**：SHA-1 / SHA-256 / MD5 都是**为「快」而设计**的（它们要能高效校验大文件），因此现代 GPU 每秒可以计算**数十亿次** SHA-256——加盐后虽然要重算，但单次成本太低，字典攻击仍然可行。

正确的方向是**慢哈希（password hashing）**：把「算一次很慢」变成设计目标，用**工作因子**把攻击成本抬到不可接受。

| 算法 | 特点 | 推荐度 |
| --- | --- | --- |
| **bcrypt** | 内置盐、有 **cost 工作因子**（每 +1 计算量翻倍）；输出自描述串；久经考验 | ⭐ 生产常用（向后兼容性最好） |
| **scrypt** | 除了计算还**吃内存**，抵抗 GPU / ASIC 并行 | 内存充裕时可选 |
| **Argon2**（id / i / d） | 密码哈希竞赛优胜者，可同时调**时间、内存、并行度**三个参数 | ⭐ 新项目首选（Argon2id） |
| **PBKDF2** | 标准、各语言内置、无内存开销；⚠️ 抗 GPU 能力弱于前两者 | 合规场景（如 FIPS）或作为兜底 |
| ❌ 加盐 MD5 / SHA-x / 单次哈希 | 太快，GPU 每秒数十亿次 | ⚠️ 不要用于新系统 |

### 5.1 实测：慢哈希到底有多慢

同一台机器上，用 PBKDF2-HMAC-SHA256 对同一个密码做一次派生：

| 迭代次数 | Go（手写 PBKDF2） | Java（`SecretKeyFactory`） | 单次耗时意味着什么 |
| --- | --- | --- | --- |
| 1 | ≈ 0 ms | 5.7 ms | 等同于普通哈希，毫无防护 |
| 1,000 | ≈ 0 ms | 8.8 ms | 仍然太快 |
| 10,000 | **7.55 ms** | 37.3 ms | 勉强可用 |
| 100,000 | **65.3 ms** | 220.3 ms | ⭐ 推荐量级（登录多等 65ms 无感） |
| 1,000,000 | **697 ms** | 2164 ms | 更安全，但登录明显变慢 |

⭐ 换算成攻击成本（以 100 万次字典尝试计）：**10 万次迭代 → 约 18 小时；100 万次迭代 → 约 194 小时**（Go 侧）。而如果是不加盐的 SHA-256，同样的 100 万次尝试是**秒级**完成。

**这就是慢哈希的全部意义**：它不是让攻击「不可能」，而是让攻击**从秒级变成天级、从「可批量脱库」变成「只能挑重点账号试」**——而**用户登录只多等几十毫秒**。这个不对称正是设计目标。

⚠️ 两点补充：

- **参数要跟着硬件升级**：今天推荐的 cost，五年后可能太便宜。所以密文要**自描述**（见 5.2），支持在用户下次登录成功时**静默升级**到新参数。
- **Java 侧的绝对耗时明显高于 Go**（约 3 倍）——因为 JCE provider 有固定初始化开销（迭代 1 次也要 5.7ms）。**跨语言比较时要看「量级与线性度」而不是绝对值**：两边都随迭代次数近似线性增长，说明成本确实来自迭代本身。

### 5.2 自描述的存储格式

bcrypt / scrypt / Argon2 的输出都是**自描述**的，例如：

```text
$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy
└┬┘└┬┘└──────────── 22 字符盐 ───────────┘└──────── 31 字符摘要 ────────┘
 │  └── cost（工作因子）：10 表示 2^10 轮
 └── 算法版本（2a = bcrypt）
```

自己实现时也应照此设计：

```text
pbkdf2-sha256$100000$<base64 盐>$<base64 派生密钥>
```

⭐ 好处：**算法与参数都写进密文**，将来提高迭代次数或换算法时，旧密文仍可验证（按它自己声明的参数算），**登录成功后再用新参数重新加密**——这就是「密码哈希平滑升级」的标准做法，没有这一步，参数就永远改不动。

## 六、实现一：Go

标准库没有 bcrypt / argon2（在 `golang.org/x/crypto` 里），这里用**手写 PBKDF2-HMAC-SHA256** 说明原理，生产直接用 `x/crypto/bcrypt` 或 `x/crypto/argon2`：

```go
// PBKDF2-HMAC-SHA256（RFC 8018）
func pbkdf2SHA256(password, salt []byte, iter, keyLen int) []byte {
	prf := hmac.New(sha256.New, password)
	hashLen := prf.Size()
	numBlocks := (keyLen + hashLen - 1) / hashLen
	var buf [4]byte
	dk := make([]byte, 0, numBlocks*hashLen)
	U := make([]byte, hashLen)

	for block := 1; block <= numBlocks; block++ {
		prf.Reset()
		prf.Write(salt)
		buf[0], buf[1] = byte(block>>24), byte(block>>16)
		buf[2], buf[3] = byte(block>>8), byte(block)
		prf.Write(buf[:4])
		dk = prf.Sum(dk)
		T := dk[len(dk)-hashLen:]
		copy(U, T)

		for n := 2; n <= iter; n++ {     // U2..Uc：反复迭代并异或
			prf.Reset()
			prf.Write(U)
			U = U[:0]
			U = prf.Sum(U)
			for x := range U {
				T[x] ^= U[x]
			}
		}
	}
	return dk[:keyLen]
}

// 盐必须用密码学安全随机源
func randSalt(n int) []byte {
	b := make([]byte, n)
	if _, err := rand.Read(b); err != nil {   // crypto/rand，不是 math/rand
		panic(err)
	}
	return b
}
```

**生成与校验的调用方式**：

```go
pwd := "Aa123456"
salt := randSalt(16)                                    // 16 字节盐，与密文一起明文存储
dk := pbkdf2SHA256([]byte(pwd), salt, 100_000, 32)      // 10 万次迭代，派生 32 字节
stored := fmt.Sprintf("pbkdf2-sha256$%d$%s$%s", 100_000,
	hex.EncodeToString(salt), hex.EncodeToString(dk))   // 自描述串入库

// 校验：解析出盐与参数 → 用同样参数重算 → 常量时间比较
```

实测输出（go1.26.5）：见 5.1 的耗时表；加盐 / 彩虹表数据见 4.1。

## 七、实现二：Java

Java 标准库自带 PBKDF2（`SecretKeyFactory`），无需第三方依赖：

```java
static byte[] pbkdf2(char[] password, byte[] salt, int iterations, int keyLen) throws Exception {
	// JDK 8u161+ 支持 WithHmacSHA256；更早版本回退到 SHA1
	SecretKeyFactory f = SecretKeyFactory.getInstance("PBKDF2WithHmacSHA256");
	PBEKeySpec spec = new PBEKeySpec(password, salt, iterations, keyLen * 8);
	byte[] out = f.generateSecret(spec).getEncoded();
	spec.clearPassword();               // ⭐ 用完立即清掉密码副本
	return out;
}

static byte[] randomSalt(int n) {
	byte[] b = new byte[n];
	SecureRandom rnd = new SecureRandom();   // 不是 java.util.Random
	rnd.nextBytes(b);
	return b;
}
```

**校验时必须用常量时间比较**：

```java
// ❌ Arrays.equals 会在第一个不同字节处提前返回，理论上泄漏「比较到第几位」
boolean bad  = Arrays.equals(inputDk, storedDk);

// ✅ MessageDigest.isEqual 是常量时间实现
boolean good = MessageDigest.isEqual(inputDk, storedDk);
```

实测输出（JDK 1.8）：算法为 `PBKDF2WithHmacSHA256`；未加盐 5/5 命中、加盐 0/5 命中（与 Go 版一致）；耗时见 5.1。

⚠️ **Java 侧的三个实践要点**：

1. **`PBEKeySpec` 用完要 `clearPassword()`**，避免密码明文在堆里长期存活（能被 heap dump 抓到）；
2. **用 `SecureRandom` 而不是 `Random`**；
3. **不要自己撸 bcrypt**——直接用 **Spring Security Crypto** 的 `BCryptPasswordEncoder`，或 `argon2-jvm`；它们内置了盐、参数编码与时序安全比较。

## 八、登录失败锁定与其它防护

原文最后强调：**单单加密保证不了密码安全，要结合多方面一起做**。列出的措施与工程落地：

| 措施 | 说明 |
| --- | --- |
| **密码复杂度要求** | 不少于 8 位、含大小写字母 / 数字 / 符号 |
| **错误提示不具体** | ⭐ 一律提示「用户名或密码不匹配」，**不要提示「用户不存在」**——否则攻击者能通过枚举确认哪些用户名有效 |
| **失败次数锁定** | 指定时间内输错多次后锁定账号（如一天 / 10 分钟） |
| **验证码 / 人机校验** | 图形验证码、滑块等，防止机器批量撞库 |
| **异地登录通知** | 记录真实 IP，IP 变动时通知用户 |
| **免密登录** | 用验证码登录替代密码（用户不必记密码），但要注意**登录有效期**与频繁获取验证码的体验问题 |

**失败计数的落地要点**（原文用 PHP + Redis 计数，这里是通用口径）：

```text
键设计   : login:fail:<日期>:<用户名>      ← ⚠️ 用「日期 + 账号」做维度，天然按天清零
计数     : 每次失败 INCR，并设置过期时间（避免长期堆积）
判定     : 计数 >= 阈值 → 拒绝并提示「已锁定，请稍后再试」
⚠️ 三个坑:
  1. 用户名可控 → 键里要做规范化和长度限制，防止被构造成超长 key 或跨维度碰撞
  2. 只按用户名限流 → 攻击者可换用户名爆破同一密码（应对「IP + 用户名」双维度）
  3. 只按账号锁定 → 可被用来「恶意锁死他人账号」，所以锁定时间要短、并配 IP 维度限流
```

⭐ 一条容易被忽略的**顺序问题**：**先校验锁定状态，再做密码校验**（原文的代码就是这个顺序）——否则锁定只是「事后提示」，攻击者依然能通过响应差异判断密码是否正确。

## 使用：密码存储的落地检查清单

上线前逐条过一遍：

```text
[ ] 密码字段类型能容纳自描述串（bcrypt 60 字符 / Argon2 更长），不要用 char(32)
[ ] 用 bcrypt(cost≥10) 或 Argon2id；PBKDF2 至少 10 万次迭代
[ ] 盐由 CSPRNG 生成（crypto/rand、SecureRandom、random_bytes），每个用户独立
[ ] 校验用常量时间比较（MessageDigest.isEqual / subtle.ConstantTimeCompare）
[ ] 密文自描述，支持参数升级 + 登录成功时静默重加密
[ ] 登录失败计数按（账号 + IP）双维度，带过期时间；先查锁定再验密码
[ ] 错误提示统一为「用户名或密码不匹配」
[ ] 限流 + 验证码 + 异地登录通知
[ ] 日志与 APM 里绝不打印密码或密文（含请求体采样）
[ ] 敏感信息能「只存核验状态」的就不要存原值（身份证、照片等）
```

⚠️ `char(32)` 是经典坑：早期 MD5 存 32 字符，换成 bcrypt（60 字符）后字段被截断，**登录全部失败**。选字段长度时就要按「未来要换的算法」留余量。

## 延伸追问

- **密码为什么用散列而不是加密？** → 加密可逆，系统能解出密码就意味着**库泄露 = 密码全泄露**；而密码存进去之后**永远不需要还原**（忘记只能重置），所以用不可逆的散列。要还原原值的敏感字段（如站内可解密的身份证号）才用对称加密。
- **加盐能防暴力破解吗？** → ❌ **不能**。加盐防的是**彩虹表**（离线、已知 hash 的场景）；在线暴力破解是在猜明文，盐对它毫无影响——它靠**失败锁定、验证码、限流**防御。⚠️ 这是本题最容易答错的地方。
- **为什么不用 MD5 加盐存密码？** → MD5 有两个问题：**已被实际碰撞破解**，以及**太快**（GPU 每秒数十亿次）。加盐只解决「彩虹表」，解决不了「单次成本太低」。正确做法是慢哈希：bcrypt / scrypt / Argon2。
- **`sha1($pwd . $salt)` 这种写法有什么问题？** → ①快（纯 SHA 无工作因子）②盐的随机源常被写成可预测的 `mt_rand`/`uniqid`（应用 CSPRNG）③**全站共用一个盐**等于没加盐。此外哈希拼接顺序（`pwd+salt`）本身不影响安全性（没有长度扩展问题，因为盐是前缀），但也不该自己发明构造——直接用标准算法。
- **bcrypt 的 cost 怎么定？** → 让**单次校验耗时落在 50~200ms**（实测：PBKDF2 10 万次约 65ms、100 万次约 700ms），在服务端 CPU 与用户体验之间取平衡；cost 每 +1 计算量翻倍。**必须定期重估**并借登录时机静默升级参数。
- **什么是「平滑升级」密码哈希参数？** → 密文自描述（算法 + 参数 + 盐 + 摘要都写在里面），校验时按密文自己声明的参数计算；登录成功后，若参数低于当前标准，就用新参数重新加密并写回。没有自描述格式，参数一旦定下就改不动。
- **校验密码为什么要用常量时间比较？** → `Arrays.equals` / `==` 会在第一个不同字节处提前返回，攻击者可通过响应时间差异**逐字节猜出摘要**（时序侧信道）。要用 `MessageDigest.isEqual`、`subtle.ConstantTimeCompare` 这类常量时间实现。
- **「用户不存在」和「密码错误」为什么不能分开提示？** → 分开提示等于提供**用户名枚举**接口，攻击者可先筛出有效账号再定向爆破。统一提示「用户名或密码不匹配」。
- **密码字段该用什么类型？** → 长度按**未来要换的算法**留余量：bcrypt 是 60 字符、Argon2 / 自描述串更长，用 `varchar(100)+` 而不是 `char(32)`。历史上从 MD5 换 bcrypt 时最常见的故障就是**字段截断导致登录全部失败**。
- **租户 / 多系统场景有什么额外考虑？** → 同一套凭证不要跨系统复用哈希（各系统独立盐与算法）；单点登录场景密码只存在身份提供方一处，业务系统**不应保存密码**；对外提供 API 的用 AK/SK 或 Token，不用用户名密码。
