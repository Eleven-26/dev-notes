## 一、数字摘要与数字签名分别是什么？怎么实现？

### 1.1 数字摘要

**定义**：数字摘要技术用于对所要传输的数据进行运算生成信息摘要，它**并不是一种加密机制**，但能产生信息的数字"指纹"，目的是确保数据没有被修改或变化，保证信息的**完整性**不被破坏。

**特点**：

- 信息摘要算法实际上是一个**单向散列函数**（不可逆：A 经算法得到 B，但 B 不能经算法还原出 A）
- 数据块经过单向散列函数得到一个**固定长度**的散列值；攻击者不可能通过散列值编造出数据块，使得其散列值与原来数据块的散列值相同
- 常用的信息摘要算法有 MD5、SHA 等

### 1.2 数字签名

**定义**：数字签名用来保证信息传输过程中的**完整性**、提供信息发送者的**身份认证**和**不可抵赖性**。使用公开密钥算法是实现数字签名的主要技术。

数字签名技术是对 **"非对称密钥加解密"和"数字摘要"两项技术的应用**：它将摘要信息用发送者的**私钥加密**，与原文一起传送给接收者。

> ⚠️ **数字签名只能验证数据的完整性，数据本身是否加密不属于数字签名的控制范围。**

**原理**：当用自己的私钥加密了一个信息并发送给朋友时，如果朋友能够用你的**公钥**解密出信息，他就能确定信息必定是从你那里发来的，而不是冒名顶替者——这就是数字签名的原理。

由于公开密钥算法的运算速度比较慢，因此可使用 HASH 函数对要签名的信息先做摘要处理，**减小使用公开密钥算法的运算量**。因此数字签名一般结合了数字摘要技术和公开密钥算法共同使用。

**举个场景**：A 委托 B 整理数据并承诺报酬，B 完成后 A 却否认此事。有了数字签名，A 的数据经其私钥加密后发给 B，就能证明 A 确实发送过原始数据；B 把整理结果签名后发给 A，也能证明 B 完成过整理工作。

**流程**：A 给 B 传送数据时同时用了信息摘要技术和数字签名技术，B 收到后用 A 的**公钥**解密传送过来的已加密摘要，再与原始数据的信息摘要核对——如果一样，则证明原始数据在传输过程中**没有被篡改**。

以上通信模型很好地解决了数据完整性与不可否认性，但**这个模型的关键依赖点是双方公钥**：公钥来源无法验证，且通信前如何获得每个人可信任的公钥成了整个系统的关键。因此需要一套系统来解决身份认证、数据完整性、密钥交换、操作不可否认性——它就是 **PKI**。

### 1.3 实现数字签名

**签名信息**：

1. 对信息 M 进行 HASH 函数处理，生成摘要 H
2. 用你自己（发送者）的**私钥**加密 H，获得数字签名 S
3. 发送 `{M, S}`

**验证签名信息**：

1. 接收 `{M, S}` 并将它们区分开
2. 对接收到的信息 M 进行 HASH 函数处理，生成摘要 H*
3. 取得发送者的**公钥**
4. 用公钥解密 S，获取 H
5. 比较 H 和 H*：相同即说明信息在发送过程中没有被篡改

> ⚠️ 由于数字签名后明文信息也通过网络传递，**做完数字签名后还要对整个信息（M + S）进行加密**，以保证信息的保密性。

## 二、数据加密和数字签名有什么区别？

| 维度 | 数据加密 | 数字签名 |
|---|---|---|
| **加密用的密钥** | 用**公钥**加密 | 用**私钥**加密 |
| **解密用的密钥** | 只能用自己的**私钥**解密，因私钥只有你自己有 | 只能用**公钥**解密，任何人都可以用公钥解密 |
| **保证什么** | 保证数据的**保密性**（别人无法看到内容） | 保证数据**肯定是从你这里发出的**，不可能是别人发的 |
| **使用的密钥对** | **接受方**的密钥对——任何知道接受方公钥的都可以向接受方发送消息，但只有拥有私钥的才能解密 | **发送方**的密钥对——任何接受方都可以用公钥解密，验证数据的正确性 |

**总结**：

- **数据加密**保证了数据**接受方**的数据安全性
- **数字签名**保证了数据**发送方**的数据安全性

⭐ 一句话：**加密解决「别人看不到」，签名解决「别人改不了 + 赖不掉」。** 两者可以叠加使用（先签名再加密），也可以各自独立使用。

## 三、HMAC 与数字签名怎么选？

两者都能做「完整性校验 + 来源确认」，但**信任模型与成本完全不同**。

| 维度 | **HMAC**（对称） | **数字签名**（非对称） |
| --- | --- | --- |
| 密钥 | 双方共享同一把密钥 | 一方持私钥签名，所有人持公钥验证 |
| 能否**防抵赖** | ❌ 不能（双方都能生成，无法证明是谁做的） | ✅ 能（只有私钥持有者能生成） |
| 验证方是否需保密 | ✅ 需要（有密钥就能伪造） | ❌ 不需要（公钥可以公开） |
| 性能 | ⭐ 快（纯哈希 + 一次异或） | 慢（大数运算） |
| 密钥分发 | 需要安全渠道分发共享密钥（N 个参与方需 N 把或统一一把） | 只需分发公钥 |
| 适用 | **内部服务间**校验、Webhook 验签、短链接防篡改 | **跨信任域**：JWT、开放平台 API、证书、代码/制品签名 |

### 3.1 实测：性能差两个数量级

同一台机器上，对 256 字节载荷重复 2000 次（JDK 1.8）：

```text
HMAC-SHA256   2000 次:   77.3 ms  （2.59 万次/秒）
SHA256withRSA 2000 次: 9234.8 ms  （0.02 万次/秒）
倍数差（签名慢多少倍）: 119 倍
```

> ⭐ 这就是「**内部服务之间用 HMAC（因为双方本来就互信），对外开放接口用非对称签名（因为验证方不可信且需要防抵赖）**」的量化依据。⚠️ 注意 RSA 签名的成本主要在私钥运算（`initSign` + `sign`），验签（公钥运算）会快得多——所以「签名慢」的压力落在**签发方**。

## 四、算法选择与弃用线

| 用途 | 已弃用（不要用于新系统） | 推荐 | 备注 |
| --- | --- | --- | --- |
| 摘要 | **MD5、SHA-1** | SHA-256 / SHA-512 / SHA-3 | MD5 与 SHA-1 均已实现**碰撞攻击**（可构造不同内容得到相同摘要），不能用于签名与证书 |
| 完整性校验（有共享密钥） | MD5 + 拼接密钥 | ⭐ **HMAC-SHA256** | 直接 `HASH(数据 + 密钥)` 存在**长度扩展攻击**风险，必须用 HMAC 构造 |
| 签名 | RSA-1024、RSA PKCS#1 v1.5（新系统尽量避免） | RSA-2048+ / **ECDSA P-256** / **Ed25519** | Ed25519 更快、签名更短、实现更简单（免随机数陷阱） |
| 口令存储 | MD5 / SHA-256 直存（含加盐） | **bcrypt / scrypt / Argon2 + 每用户随机盐** | 关键在于「慢哈希 + 工作因子」，而不是摘要长度 |

### 4.1 实测：摘要长度与签名长度

```text
原文长度        : 26 字节
MD5 摘要        : 0d81edd4658143c5b85ffe05fec8f9c5            (128 bit)
SHA-1 摘要      : 0a32070fa67aa375dc2bbafddc41d8e9e320f959    (160 bit)
SHA-256 摘要    : f2dc759530db067348d19313994e4401416ceca0f3905fdda28b4f5aa56149e7  (256 bit)
改一个字节后 SHA-256: 2201f03c8fc819e2e1599034c3b8c935aa58c1b1f535a4bd4554452ed786ecf2
```

⭐ 两条可以直接引用的规律：

- **摘要长度固定，与原文长度无关**（26 字节的输入 → 256 bit 输出），所以摘要**不能用来还原或压缩数据**；
- **雪崩效应**：只把 `99.00` 改成 `99.01`，SHA-256 输出完全面目全非——这是「摘要能检出篡改」的根本原因。

签名长度（实测）：

```text
RSA-2048 签名长度 : 256 字节（= 密钥长度 256 字节，与原文长度无关）
ECDSA P-256 签名长度: 70 字节（DER 编码，约 70~72）
```

⭐ **ECDSA P-256 的安全强度约等于 RSA-3072，但签名只有 70 字节、密钥也短得多**——这是证书链与移动端普遍转向 ECC 的原因（握手报文更小、验证更快）。⚠️ ECDSA 的实现陷阱是**随机数 k 必须每次唯一**（k 复用会直接泄露私钥，PS3 的著名事故）；Ed25519 通过确定性签名规避了这个问题。

### 4.2 实测：签名验的是「摘要是否一致」

```text
原文未改 → 验签   : true
改一个字节 → 验签 : false
```

⚠️ 两个必须澄清的边界：

- 验签成功**只说明「发送者持有对应私钥」且「内容未被改动」**，不说明内容合理、不说明发送时间、**也不说明内容没被别人看到**（签名不提供保密性）；
- 签名**不防重放**——攻击者可以原样重发一次合法请求，签名依然验得过。防重放要靠时间戳与随机数（见第五节）。

## 五、签名在生产里的三个典型场景

### 5.1 JWT：无状态令牌

结构是 `Header.Payload.Signature`，签名保证「Header + Payload 未被篡改」。

```text
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMDAxIiwiZXhwIjoxNzUwMDAwMDAwfQ.签名部分
└────────── Header（算法）──────────┘└────────── Payload（声明）──────────┘
```

⚠️ **四个高频坑**：

1. **`alg: none` 攻击**：某些实现会信任 Header 里声明的算法，攻击者改成 `none` 并去掉签名即可伪造。**服务端必须用白名单固定算法**，不能读 Header 决定。
2. **RS256 → HS256 混淆**：若服务端「按 Header 里的 alg 选算法」，攻击者把 RS256 改成 HS256，再用**公开的 RSA 公钥当 HMAC 密钥**签名，就能通过验证。
3. **Payload 是 base64 编码，不是加密**：任何人都能解开看内容——绝不能放密码、身份证号等敏感信息。
4. **无状态意味着无法主动失效**：签发出去的 JWT 在过期前一直有效。要支持「登出 / 踢人 / 改密即失效」，必须配合**短过期 + Refresh Token**，或维护黑名单（那就退化成有状态了）。

### 5.2 开放 API 签名：防篡改 + 防重放

这是**面试与实际都容易漏**的一块。只做「参数 + 密钥 → 摘要」只能防篡改，**不能防重放**。完整方案需要三要素：

| 要素 | 作用 | 缺了会怎样 |
| --- | --- | --- |
| **签名覆盖所有关键参数**（按字典序拼接，含 path / query / body 摘要） | 防篡改 | 攻击者改未覆盖的参数（如把 `amount` 从 body 挪到 query）即可绕过 |
| **timestamp**（并要求与服务端时间差在 N 分钟内） | 限制重放窗口 | 请求可以被无限期重放 |
| **nonce**（一次性随机串，服务端缓存去重） | 彻底阻止窗口内重放 | 窗口期内可以被反复重放（如重复下单） |

⚠️ 另一个常见错误：**把签名密钥放进 URL 或前端代码**。密钥只能存在于服务端。

### 5.3 制品签名：软件包、镜像、直传凭证

| 场景 | 手段 | 要点 |
| --- | --- | --- |
| 镜像 / 制品 | Co-sign、GPG、Notation | 在 CI 中签名，部署侧校验（准入控制可强制「未签名镜像不可部署」） |
| 对象存储直传 | 预签名 URL（OSS / S3） | ⭐ 有效期尽量短、限定 HTTP 方法与对象前缀、**不向客户端下发长期密钥** |
| 接口回调（Webhook） | HMAC 验签（如 `X-Signature` 头） | 回调方用共享密钥验签；⚠️ 必须做**时间戳校验 + 幂等**处理，否则回调会被重放成重复业务 |

⭐ 一条通用原则：**签名的校验必须在服务端做**。客户端验签只能用于「提示用户包被篡改」，攻击者完全可以跳过客户端校验。

## 面试官会追问什么

- **数字签名为什么不直接对原文签名？** → 原文可能很长且非对称算法极慢（实测：RSA 签名比 HMAC 慢约 **119 倍**），先做摘要再签名，既高效又只保护完整性。
- **为什么加了盐还要用 bcrypt 而不是 MD5+salt？** → bcrypt 内建工作因子与慢哈希设计，能显著提高暴力破解成本；MD5 无论怎么加盐都太快。
- **摘要和加密有什么区别？** → 摘要**不可逆**、用于完整性；加密**可逆**、用于机密性。两者解决的不是同一个问题，不能互相替代。
- **签名能验出"消息被篡改"还是"签名被伪造"？** → 只对前者负责：篡改会让摘要不匹配（实测：改一个字节 → 验签 `false`）；而伪造签名需要攻击者拿到私钥。所以**私钥的保护等级决定了整套体系的上限**。
- **HMAC 和数字签名怎么选？** → 内部互信双方用 **HMAC**（快、但无法防抵赖）；跨信任域、需要防抵赖、验证方不可信时用**非对称签名**。性能差距实测约 119 倍（RSA-2048 签发 vs HMAC-SHA256）。
- **为什么不能用 `HASH(数据 + 密钥)` 代替 HMAC？** → 存在**长度扩展攻击**：攻击者可以在不知道密钥的情况下，由 `HASH(数据 + 密钥)` 推导出 `HASH(数据 + 填充 + 附加内容 + 密钥)` 的合法摘要。HMAC 的双层哈希结构专门防这个。
- **签名能防重放吗？** → ❌ 不能。合法请求原样重发一次，签名依然有效。防重放必须叠加 **timestamp（限制窗口）+ nonce（一次性）**，并让签名覆盖全部关键参数。
- **JWT 的 `alg: none` 是什么攻击？** → 某些库信任 JWT Header 里声明的算法，攻击者改为 `none` 并省略签名即可通过校验。防御：**服务端固定算法白名单**，并拒绝 `none`；同理要防 RS256→HS256 的算法混淆。
- **签名和摘要的长度是固定的吗？** → 都固定。摘要长度由算法决定（MD5 128 bit / SHA-256 256 bit），签名长度由密钥与算法决定（RSA-2048 → 256 字节；ECDSA P-256 → 约 70 字节），与原文长度无关。
