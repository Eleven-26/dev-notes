# 装饰器模式：接口一字不改，行为一层层往上加

> 素材来源：博客系列 [PHP 设计模式(七)：装饰器模式](https://blog.csdn.net/weixin_43837229/article/details/102666163)。
> 重写版补上原文没讲透的四块：**PHP 的正解不是 `SplSubject` 那一套**（SPL 里根本没有装饰器基类，实测）、
> **装饰顺序会改变结果而且不报错**（gzip / base64 / 版本标记五条链的字节数与 md5 实测）、
> **`__call` 转发到底赔掉什么**（静态类型、typo 时机、链式 API 漏出内层对象，含 Guzzle 那一行的修法）、
> **它在项目里的三张脸**：PSR-15 中间件洋葱、`php://` 流过滤器、vendor 里的 `StreamDecoratorTrait`。
> 邻居模式见 [代理模式.md](代理模式.md)、[适配器模式.md](适配器模式.md)、[外观模式.md](外观模式.md)。

## 一、装饰器只回答一个问题：不改老类，行为加在哪

装饰器（Decorator，结构型）：**实现同一个接口，构造时接住被装饰者，在自己的方法里"加一点，再转手"**。
三条判据，缺一条就不是装饰器：

1. `implements` 的接口和被装饰者**同一个** —— 装饰完还能塞进任何期待原接口的形参里；
2. 被装饰者从**构造器进来**，不是内部 `new` 出来的（自己 new 就叫包装类，套不了链）；
3. 加的是**行为**（日志、重试、压缩、编码、限流）。如果加的是"延后才创建"或"谁能访问"，那是 [代理](代理模式.md)；
   如果 `implements` 的接口和被装饰者**不一样**（在做翻译），那是 [适配器](适配器模式.md)。

## 二、PHP 的标准形状，和两个冒牌货

PHP 圈讲装饰器常从 `SplSubject` / `SplObserver` 起手，但 SPL 给装饰器留的位置其实是空的：

```php
<?php
declare(strict_types=1);
interface Compressor { public function compress(string $s): string; }
final class Raw implements Compressor { public function compress(string $s): string { return $s; } }
// 标准形状：实现同一接口 + 构造注入被装饰者，inner 显式声明所以随时取得到
final class Gz implements Compressor { public function __construct(public Compressor $inner) {}
    public function compress(string $s): string { return gzencode($this->inner->compress($s), 9); } }
// 反过来，用 __get「自动转发」的装饰器：看着省事，读属性时就是坑
final class GzMagic implements Compressor { private Compressor $inner;
    public function __construct(Compressor $i) { $this->inner = $i; }
    public function compress(string $s): string { return gzencode($this->inner->compress($s), 9); }
    public function __get(string $n): mixed { return $this->inner->{$n} ?? null; } }
echo '声明属性 + 构造注入，inner 可显式取: ', get_class((new Gz(new Raw()))->inner), PHP_EOL;
echo '__get 自动转发读 ->inner: ', var_export((new GzMagic(new Raw()))->inner, true), ' （inner 是声明过的属性，__get 根本不触发）', PHP_EOL;
$st = new SplStack(); $st->push('A'); $st->push('B'); $st->push('C');
echo 'SPL 没有装饰器基类，只有 SplStack/SplObjectStorage 这类容器，链得自己维护: ', implode(',', iterator_to_array($st)), PHP_EOL;
```

```text
声明属性 + 构造注入，inner 可显式取: Raw
__get 自动转发读 ->inner: NULL （inner 是声明过的属性，__get 根本不触发）
SPL 没有装饰器基类，只有 SplStack/SplObjectStorage 这类容器，链得自己维护: C,B,A
```

三条结论：

- 标准形状只有一句：`final class X implements 同一个接口 { public function __construct(private 接口 $inner) {} }`，
  **没有基类可继承，也没必要有**——PHP 8.0 的构造器属性提升已经把样板压到两行。
- 想用 `__get` 省转发代码，读属性这条路是假的：`inner` 是**声明过**的属性，magic 方法只在"不可访问 / 不存在"时进场，压根不触发。
- 链自己维护：`SplSubject`/`SplObjectStorage` 是观察者那套，SPL 里**没有**装饰器基类（上面最后一行 `SplStack` 只是容器）。

## 三、顺序不是美学：换一层结果就变，而且不抛异常

```php
<?php
declare(strict_types=1);
interface Codec { public function encode(string $in): string; public function layers(): string; }
final class PlainCodec implements Codec { public function encode(string $in): string { return $in; }
    public function layers(): string { return 'Plain'; } }
// 标准写法：实现同一接口 + 构造注入被装饰者，自己只加一件事
final class Base64Codec implements Codec { public function __construct(private Codec $inner) {}
    public function encode(string $in): string { return base64_encode($this->inner->encode($in)); }
    public function layers(): string { return 'B64(' . $this->inner->layers() . ')'; } }
final class GzipCodec implements Codec { public function __construct(private Codec $inner, private int $level = 6) {}
    public function encode(string $in): string { return gzencode($this->inner->encode($in), $this->level); }
    public function layers(): string { return 'GZ' . $this->level . '(' . $this->inner->layers() . ')'; } }
// 版本标记装饰器：放进内层是"载荷的一部分"，套在外层是"协议尾"
final class TagCodec implements Codec { public function __construct(private Codec $inner, private string $tag = '|v2') {}
    public function encode(string $in): string { return $this->inner->encode($in) . $this->tag; }
    public function layers(): string { return 'Tag(' . $this->inner->layers() . ')'; } }
final class QpCodec implements Codec { public function __construct(private Codec $inner) {}
    public function encode(string $in): string { return quoted_printable_encode($this->inner->encode($in)); }
    public function layers(): string { return 'QP(' . $this->inner->layers() . ')'; } }

$payload = str_repeat('order-created;', 8);
$chains = ['GZ(B64)' => new GzipCodec(new Base64Codec(new PlainCodec())),
    'B64(GZ)' => new Base64Codec(new GzipCodec(new PlainCodec())),
    'GZ9(B64)' => new GzipCodec(new Base64Codec(new PlainCodec()), 9),
    'GZ(Tag)' => new GzipCodec(new TagCodec(new PlainCodec())),
    'Tag(GZ)' => new TagCodec(new GzipCodec(new PlainCodec()))];
printf("plain bytes = %d\n", strlen($payload));
foreach ($chains as $k => $c) { printf("%-9s %-20s out=%-4d md5=%s\n", $k, $c->layers(), strlen($c->encode($payload)), substr(md5($c->encode($payload)), 0, 8)); }
$tagOut = (new TagCodec(new Base64Codec(new PlainCodec())))->encode($payload);
$tagIn = (new Base64Codec(new TagCodec(new PlainCodec())))->encode($payload);
echo 'Tag 在外的密文尾 8 字符: ', substr($tagOut, -8), ' / Tag 在里的密文尾 8 字符: ', substr($tagIn, -8), PHP_EOL;
echo '顺序错了会抛异常吗: 非严格 base64_decode 长度=', strlen(base64_decode($tagOut)), '，解出内容含 |v2: ', var_export(str_contains(base64_decode($tagOut), '|v2'), true), PHP_EOL;
echo '严格模式 base64_decode($x, true): ', var_export(base64_decode($tagOut, true), true), PHP_EOL;
echo 'Tag 在里时解出来含 |v2: ', var_export(str_contains(base64_decode($tagIn), '|v2'), true), PHP_EOL;
echo 'gzip 侧呢，gzdecode 尾部多 3 字节仍还原: ', var_export(gzdecode((new TagCodec(new GzipCodec(new PlainCodec())))->encode($payload)) === $payload, true), PHP_EOL;

/** 链由配置数组决定，而不是由类图决定：这是"组合"相对"继承"的全部自由度 */
function build(array $stack): Codec
{
    $c = new PlainCodec();
    foreach (array_reverse($stack) as $k) { $c = match ($k) { 'b64' => new Base64Codec($c), 'gz' => new GzipCodec($c), 'qp' => new QpCodec($c) }; }
    return $c;
}
foreach ([['b64', 'gz'], ['gz', 'b64'], ['qp', 'b64', 'gz'], ['b64', 'gz', 'qp'], ['gz', 'b64', 'qp']] as $p) {
    $c = build($p); printf("config [%-12s] -> %-24s bytes=%-4d md5=%s\n", implode(',', $p), $c->layers(), strlen($c->encode($payload)), substr(md5($c->encode($payload)), 0, 8));
}
```

```text
plain bytes = 112
GZ(B64)   GZ6(B64(Plain))      out=82   md5=58cabaae
B64(GZ)   B64(GZ6(Plain))      out=52   md5=da942185
GZ9(B64)  GZ9(B64(Plain))      out=82   md5=406d3377
GZ(Tag)   GZ6(Tag(Plain))      out=40   md5=747cf95d
Tag(GZ)   Tag(GZ6(Plain))      out=40   md5=3a2c1057
Tag 在外的密文尾 8 字符: kOw==|v2 / Tag 在里的密文尾 8 字符: O3x2Mg==
顺序错了会抛异常吗: 非严格 base64_decode 长度=114，解出内容含 |v2: false
严格模式 base64_decode($x, true): false
Tag 在里时解出来含 |v2: true
gzip 侧呢，gzdecode 尾部多 3 字节仍还原: true
config [b64,gz      ] -> B64(GZ6(Plain))          bytes=52   md5=da942185
config [gz,b64      ] -> GZ6(B64(Plain))          bytes=82   md5=58cabaae
config [qp,b64,gz   ] -> QP(B64(GZ6(Plain)))      bytes=56   md5=d8d48c3b
config [b64,gz,qp   ] -> B64(GZ6(QP(Plain)))      bytes=56   md5=1dc54329
config [gz,b64,qp   ] -> GZ6(B64(QP(Plain)))      bytes=88   md5=3c578d84
```

同一份 112 字节明文，四条硬结论：

- **谁在外决定字节数**：`B64(GZ)` = 52、`GZ(B64)` = 82（base64 的 64 字符集把 gzip 能吃的冗余抬回去了）。
  这份载荷上"先压后编"才对，但**方向不能背**——第六节 Go 的实测就反过来。
- **同长度不等于同结果**：`GZ9` 和 `GZ6` 都是 82 字节，md5 不同；`[qp,b64,gz]` 和 `[b64,gz,qp]` 都是 56 字节，md5 也完全不同。
  光看长度看不出链条对不对，排查时留一个 `layers()` 这类自描述方法。
- **位置就是语义**：`Tag` 在外是协议尾（密文尾 `kOw==|v2`），`Tag` 在里是载荷的一部分（密文尾 `O3x2Mg==`）。
- **顺序错了不抛异常**：非严格 `base64_decode` 把尾巴 `|v2` 当非法字符**静默吃掉**（长度 114、结果里没有 `|v2`），
  严格模式才返回 `false`；`gzdecode` 更松，尾部多 3 字节照样还原成功。**装饰器顺序写错，多半是安静地产出错数据。**

下半段的 `build(array $stack)` 是组合相对继承的全部自由度：**链由配置数组决定，数组顺序 = 由外到内**，加减层、换顺序只动配置。
换成继承（`class GzB64Codec extends Base64Codec`）就得在类图上枚举组合、编译期焊死、运行时换不了——这才是"装饰器是运行期的子类化"的确切含义。

## 四、`__call` 转发：省两行样板，赔四件事

```php
<?php
declare(strict_types=1);
interface Notifier { public function send(string $msg): string; public function channel(): string; }
final class SmsNotifier implements Notifier { public function send(string $msg): string { return "sms:{$msg}"; }
    public function channel(): string { return 'sms'; }
    public function flushQueue(): string { return 'sms-queue-flushed'; } } // 接口里没写、只有具体类才有的能力
final class Loud implements Notifier { public function send(string $msg): string { return strtoupper($msg); }
    public function channel(): string { return 'loud'; }
    public function ping(): self { return $this; } }                       // 链式 API：返回 $this
// 老实实现接口的装饰器：接口里每个方法都得手写一遍
final class RetryDecorator implements Notifier { public array $tries = [];
    public function __construct(private Notifier $inner, private int $times = 2) {}
    public function send(string $msg): string { for ($i = 1; $i <= $this->times; $i++) { $this->tries[] = "try#{$i}";
            $r = $this->inner->send($msg); if ($r !== '') { return $r; } } return ''; }
    public function channel(): string { return $this->inner->channel(); } }
// 再套一层，并给最外层加一个 __call 去兜"接口外"的能力
class AuditDecorator implements Notifier { public function __construct(protected Notifier $inner) {}
    public function send(string $msg): string { return '[audit] ' . $this->inner->send($msg); }
    public function channel(): string { return $this->inner->channel(); }
    public function __call(string $n, array $a): mixed { return $this->inner->{$n}(...$a); } }
// Guzzle 的 StreamDecoratorTrait 在 __call 里多写一行，堵的就是下面这个漏
final class FixedAudit extends AuditDecorator { public function __call(string $n, array $a): mixed
    { $r = parent::__call($n, $a); return $r === $this->inner ? $this : $r; } }

$chain = new AuditDecorator(new RetryDecorator(new SmsNotifier()));
echo '接口内方法正常: ', $chain->send('hi'), ' / channel=', $chain->channel(), PHP_EOL;
try { $chain->flushQueue(); } catch (Throwable $e) { echo '调底层独有方法: ', get_class($e), ' -> ', $e->getMessage(), PHP_EOL; }
$two = new AuditDecorator(new SmsNotifier());
echo '去掉中间那层就能穿透: ', $two->flushQueue(), PHP_EOL;
echo '链式方法漏出内层对象: ', get_class((new AuditDecorator(new Loud()))->ping()), ' / 修一行后: ', get_class((new FixedAudit(new Loud()))->ping()), PHP_EOL;
try { $two->flushQeue(); } catch (Throwable $e) {
    $frames = count(array_filter($e->getTrace(), static fn ($t) => ($t['function'] ?? '') === '__call'));
    echo "方法名打错: ", $e->getMessage(), " / 栈里 __call 帧数={$frames}\n"; }
try { $chain->send(); } catch (Throwable $e) { echo 'send() 漏传参数: ', get_class($e), ' -> ', explode(', 0 passed', $e->getMessage())[0], PHP_EOL; }
$own = static fn (string $c): string => implode(',', array_map(static fn (ReflectionMethod $m): string => $m->getName(),
    array_filter((new ReflectionClass($c))->getMethods(ReflectionMethod::IS_PUBLIC), static fn (ReflectionMethod $m): bool => $m->getDeclaringClass()->getName() === $c)));
echo '接口方法数=2 [', implode(',', array_map(static fn (ReflectionMethod $m): string => $m->getName(), (new ReflectionClass(Notifier::class))->getMethods())),
    '] / 每个装饰器自己得写: Retry=[', $own(RetryDecorator::class), '] Audit=[', $own(AuditDecorator::class), ']', PHP_EOL;
```

```text
接口内方法正常: [audit] sms:hi / channel=sms
调底层独有方法: Error -> Call to undefined method RetryDecorator::flushQueue()
去掉中间那层就能穿透: sms-queue-flushed
链式方法漏出内层对象: Loud / 修一行后: FixedAudit
方法名打错: Call to undefined method SmsNotifier::flushQeue() / 栈里 __call 帧数=1
send() 漏传参数: ArgumentCountError -> Too few arguments to function AuditDecorator::send()
接口方法数=2 [send,channel] / 每个装饰器自己得写: Retry=[__construct,send,channel] Audit=[__construct,send,channel,__call]
```

赔掉的四件事，都能在上面找到对应行：

1. **接口内的方法一个都省不掉**：反射账是 `接口方法数=2` → 每个装饰器还是得写 `send` + `channel` + 构造器。
   `__call` 只兜"接口外"的能力，而**链式调用只要有一层没写 `__call`，穿透就断在那一层**——
   报的是 `RetryDecorator::flushQueue()` 未定义（中间层），不是最底下的 `SmsNotifier`，看错误信息会找错地方。
2. **typo 从编辑期红线退到运行期 Error**：`flushQeue` 要执行到那一行才炸，栈里还多出一帧 `__call`（实测帧数=1）。
3. **参数校验点移位**：`$chain->send()` 的 `ArgumentCountError` 指向 `AuditDecorator::send()`，真实调用点在别的文件。
   （同一条也适用于 [适配器模式.md](适配器模式.md) 第四节的 `__call` 万能适配器。）
4. **链式 API 会漏出内层对象**：`->ping()` 返回的是 `Loud` 本身，装饰层被绕过，后面再链的方法完全不经过审计。
   补法就是 Guzzle 那一行：`return $result === $this->stream ? $this : $result;`，实测返回的变成 `FixedAudit`。

**取舍**：接口内方法老实实现（保住类型和 IDE），只有"接口外的可选能力"交给 `__call`；
一旦内层是链式/fluent API，`__call` 必须带回装饰器自己，否则别写。

## 五、项目里真会撞上的三张脸

**（1）HTTP 中间件洋葱** —— PSR-15 的 `RequestHandlerInterface::handle()` 就是"吃 handler、吐 handler"的装饰器：

```php
<?php
declare(strict_types=1);

// 中间件 = 同一个签名的装饰器：吃 handler，吐 handler（PSR-15 的 process($req,$handler) 的柯里化形态）
$auth = static fn (callable $next): callable => static fn (string $r): string => 'auth(' . $next($r) . ')';
$timing = static fn (callable $next): callable => static fn (string $r): string => 'timing(' . $next($r) . ')';
$kernel = static fn (string $r): string => 'kernel';

/** 数组顺序 = 由外到内；用 reduce 从内往外套 */
$wrap = static fn (array $layers, callable $core): callable => array_reduce(
    array_reverse($layers), static fn (callable $c, callable $l): callable => $l($c), $core);

echo '注册顺序 [auth, timing]: ', $wrap([$auth, $timing], $kernel)('GET /order'), PHP_EOL;
echo '注册顺序 [timing, auth]: ', $wrap([$timing, $auth], $kernel)('GET /order'), PHP_EOL;

// 会短路的中间件：它不放行时，外层已经跑过、内层一次都跑不到
$deny = static fn (callable $next): callable => static fn (string $r): string => '401(短路)';
echo 'deny 在最外: ', $wrap([$deny, $timing], $kernel)('GET /order'), PHP_EOL;
echo 'deny 在最内: ', $wrap([$timing, $deny], $kernel)('GET /order'), PHP_EOL;
```

```text
注册顺序 [auth, timing]: auth(timing(kernel))
注册顺序 [timing, auth]: timing(auth(kernel))
deny 在最外: 401(短路)
deny 在最内: timing(401(短路))
```

框架里"中间件注册数组的顺序"不是风格问题，就是这里的装饰顺序：`deny` 在最外，`timing` 一次都不跑（401 拿不到耗时）；
`deny` 在最内，它照样被计时。会短路的前置、要覆盖全体（计时/埋点/CORS）的前置、改响应体的后置——这条排布是从上面四行推出来的。

**（2）`php://` 流过滤器** —— PHP 自带的装饰器，同样"套的顺序决定结果"：

```php
<?php
declare(strict_types=1);
// PHP 自带的装饰器：流过滤器（stream filter），同样是"套的顺序决定结果"
$via = static function (string $chain): string {
    $fh = fopen('php://memory', 'w+'); fwrite($fh, 'Hello PHP'); rewind($fh);
    foreach (explode('|', $chain) as $f) { stream_filter_append($fh, $f, STREAM_FILTER_READ); }
    $out = stream_get_contents($fh); fclose($fh); return $out;
};
echo 'b64            : ', json_encode($via('convert.base64-encode')), PHP_EOL;
echo 'b64 -> tolower : ', json_encode($via('convert.base64-encode|string.tolower')), PHP_EOL;
echo 'tolower -> b64 : ', json_encode($via('string.tolower|convert.base64-encode')), PHP_EOL;
```

```text
b64            : "SGVsbG8gUEhQ"
b64 -> tolower : "sgvsbg8guehq"
tolower -> b64 : "aGVsbG8gcGhw"
```

`convert.base64-encode|string.tolower` 得到的是"base64 结果的小写版"（`sgvsbg8guehq`），
反过来 `string.tolower|convert.base64-encode` 才是"小写明文的 base64"（`aGVsbG8gcGhw`）——和第三节同一件事。
区别只在形状：过滤器装饰的是**流**（`stream_filter_append` 只吃资源），适合边读边转；要对一个完整字符串负责，用第三节那种自己写的 Codec。

**（3）vendor 里现成的作业**：`vendor/guzzlehttp/psr7/src` 下 `CachingStream`、`NoSeekStream`、`LimitStream`、`PumpStream`、
`AppendStream` 清一色 `implements StreamInterface` + `use StreamDecoratorTrait`；那个 trait 干的就是第四节的三件事——
构造器接住 `$stream`、`__call` 转发、把 `return $this` 换回装饰器自己。本机路径与核对方式见「校验口径」，本篇代码块不依赖任何包。

## 六、Go / Java 对照

Go 没有继承可退，装饰器只剩"同接口的包装结构体"这一种写法，反而最接近原书形状：

```go
package main

import (
	"bytes"
	"compress/gzip"
	"encoding/base64"
	"fmt"
)

// Go 没有"继承"可退，装饰器只有"同接口的包装结构体"这一种写法
type Codec interface {
	Encode(in []byte) []byte
	Name() string
}

type plain struct{}

func (plain) Encode(in []byte) []byte { return in }
func (plain) Name() string            { return "Plain" }

type b64 struct{ inner Codec }

func (d b64) Encode(in []byte) []byte {
	return []byte(base64.StdEncoding.EncodeToString(d.inner.Encode(in)))
}
func (d b64) Name() string { return "B64(" + d.inner.Name() + ")" }

type gz struct{ inner Codec }

func (d gz) Encode(in []byte) []byte {
	var buf bytes.Buffer
	w := gzip.NewWriter(&buf)
	_, _ = w.Write(d.inner.Encode(in))
	_ = w.Close()
	return buf.Bytes()
}
func (d gz) Name() string { return "GZ(" + d.inner.Name() + ")" }

func main() {
	body := bytes.Repeat([]byte("go design pattern;"), 4)
	fmt.Printf("plain=%d bytes\n", len(body))
	for _, c := range []Codec{gz{b64{plain{}}}, b64{gz{plain{}}}} {
		out := c.Encode(body)
		fmt.Printf("%-16s bytes=%-4d head=% x\n", c.Name(), len(out), out[:3])
	}
}
```

```text
plain=72 bytes
GZ(B64(Plain))   bytes=50   head=1f 8b 08
B64(GZ(Plain))   bytes=60   head=48 34 73
```

**这份载荷上，Go 的结果和第三节的 PHP 反过来**：`GZ(B64)` = 50 比 `B64(GZ)` = 60 小。
72 字节明文太短，gzip 的固定开销占比很高（同一台机器实测 `strlen(gzencode(''))` = 20），谁在外就由冗余度决定，不取决于"哪种顺序更聪明"。
所以第三节的结论只能成立成这样：**顺序一定改变结果（52 vs 82、50 vs 60），哪边更省必须量。**
`head=1f 8b 08` 是 gzip 魔数、`48 34 73` 是 `"H4s"`（同一串 gzip 头的 base64），两行输出也顺带证明链条真的按标签嵌套。

| | PHP | Go | Java |
| --- | --- | --- | --- |
| 标准形态 | `implements 同接口` + 构造注入，**无基类**（第二节实测） | `struct{ inner Codec }` + 方法集 | `class X implements I`，标准库另有 `FilterInputStream` 这类抽象装饰器 |
| 少写转发 | 手写，或 `__call`（第四节实测四件代价） | 嵌入字段自动提升方法，但接口断言编译期固定 | 抽象基类里手写转发 |
| fluent 返回 `this` | `__call` 会漏出内层对象，需手工换回（实测） | 返回接口值，没有这条漏 | 基类转发要返回 `this`，写错就漏 |
| 运行期换顺序 | 改配置数组（第三节 `build()`） | 改构造表达式，同样运行期 | 同 |

## 面试官会追问什么

- **装饰器和继承哪个先考虑？** → 组合：链由配置数组决定（第三节 `build()`），继承要在类图上枚举组合、编译期焊死。
- **`SplSubject` 能当装饰器基类吗？** → 不能，那是观察者那套；SPL 里没有装饰器基类，链自己维护（第二节实测）。
- **多个装饰器顺序谁定？** → 会短路的（鉴权/限流）放最外（第五节实测：`deny` 在最外时 `timing` 一次不跑）；
  改数据形状的（压缩/编码）**量出来再排**，不能背（第三节 82 vs 52、第六节 50 vs 60 方向相反）。
- **`__call` 转发写不写？** → 接口内方法老实实现（保类型、保 IDE），只让接口外的可选能力走 `__call`；
  内层是 fluent API 时必须把 `return $this` 换回装饰器自己（第四节实测 `Loud` 泄漏）。
- **装饰器和代理都套同一接口，怎么分？** → 看动机：加行为 = 装饰器；延后创建 / 控制访问 = [代理](代理模式.md)。
- **装饰器链有性能/内存问题吗？** → 本篇未测，不给数字；只能说每层多一个对象、多一次方法调用。
