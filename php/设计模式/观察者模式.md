# 观察者模式：PHP 的观察者只活一次请求，通知语义还得自己兜底

> 素材来源：博客系列 [PHP 设计模式(三)：观察者模式](https://blog.csdn.net/weixin_43837229/article/details/102623997)。
> 原系列按"Subject 持列表 + `update()` 回调"讲结构，这部分今天依然成立；本篇补上它没讲的三件事：
> **内置 `SplSubject`/`SplObserver` 在本机 PHP 8.0.2 上的真实可用性**、**通知顺序/重入/异常传播的实测语义**、
> 以及和 Java 差别最大的一点——**php-fpm 下观察者表跨不了请求，跨请求事件必须落队列**（见第四节，进程模型见 [../PHP-FPM对接步骤.md](../PHP-FPM对接步骤.md)）。

## 一、SplSubject / SplObserver + SplObjectStorage：8.0.2 实测可用、零告警

网上一半文章说"SPL 那对接口别用，PHP 8 已废弃"——**结论要自己跑**。下面是可直接抄进项目的主题实现，`error_reporting(E_ALL)` 下零告警，并顺带验掉通知顺序、去重与快照语义：

```php
<?php

declare(strict_types=1);

error_reporting(E_ALL);   // 全开告警：看 SPL 这对接口在 8.0 上到底有没有被标记废弃

/** 主题：观察者表用 SplObjectStorage（按对象身份去重），通知前先 clone 出一份快照 */
final class Order implements SplSubject
{
    /** @var list<string> */
    public static array $trace = [];

    public string $event = '';

    private SplObjectStorage $observers;

    public function __construct()
    {
        $this->observers = new SplObjectStorage();
    }

    public function attach(SplObserver $observer): void
    {
        $this->observers->attach($observer);
    }

    public function detach(SplObserver $observer): void
    {
        $this->observers->detach($observer);
    }

    /** 接口规定 notify() 无参，事件名只能先挂在主题上（这对接口的历史包袱） */
    public function notify(): void
    {
        $this->publish($this->event);
    }

    /** @param bool $isolate true=逐个 try/catch 后汇总抛出；false=异常直接冒泡 */
    public function publish(string $event, bool $isolate = true): void
    {
        $this->event = $event;
        $errors = [];
        foreach (clone $this->observers as $observer) {
            try {
                $observer->update($this);
            } catch (Throwable $e) {
                if (!$isolate) {
                    throw $e;
                }
                $errors[] = get_class($observer) . ': ' . $e->getMessage();
            }
        }
        if ($errors !== []) {
            throw new RuntimeException('部分观察者失败 -> ' . implode(' | ', $errors));
        }
    }
}

/** 观察者：把 tag:event 记进 trace；after 钩子用来在 update() 里改注册表或抛异常 */
final class Listener implements SplObserver
{
    /** @var callable|null */
    private $after;

    public function __construct(private string $tag, ?callable $after = null)
    {
        $this->after = $after;
    }

    public function update(SplSubject $subject): void
    {
        Order::$trace[] = $this->tag . ':' . $subject->event;
        if ($this->after !== null) {
            ($this->after)($subject);
        }
    }
}

// 场景 1：通知顺序、B 在 update() 里摘掉 C 并挂上 D、同一实例重复挂载
$order = new Order();
$c = new Listener('C');
$d = new Listener('D');
$order->attach(new Listener('A'));
$order->attach(new Listener('B', function (SplSubject $s) use ($c, $d) {
    $s->detach($c);
    $s->attach($d);
}));
$order->attach($c);
$order->publish('OrderPaid');
$order->attach($d);          // D 已被 B 挂过一次，这里再挂一次
$order->publish('OrderShipped');
echo '1_detach_add_dedup : ', implode('>', Order::$trace), PHP_EOL;

// 场景 2：重入——update() 里再 publish 一次（事件级联）
Order::$trace = [];
$order = new Order();
$order->attach(new Listener('Coupon', function (SplSubject $s) use ($order) {
    static $once = false;
    if (!$once) {
        $once = true;
        $order->publish('CouponUsed');
    }
}));
$order->attach(new Listener('Stock'));
$order->publish('OrderPaid');
echo '2_reentrant        : ', implode('>', Order::$trace), PHP_EOL;

foreach (['SplObserver', 'SplSubject', 'Observer', 'Observable'] as $name) {
    printf("3_%-11s: %s\n", $name, var_export(interface_exists($name), true));
}
printf("3_%-11s: %s\n", 'PHP_VERSION', PHP_VERSION);
```

实测输出（`D:\phpstudy_pro\Extensions\php\php8.0.2nts\php.exe`，stderr 为空）：

```text
1_detach_add_dedup : A:OrderPaid>B:OrderPaid>C:OrderPaid>A:OrderShipped>B:OrderShipped>D:OrderShipped
2_reentrant        : Coupon:OrderPaid>Coupon:CouponUsed>Stock:CouponUsed>Stock:CouponUsed
3_SplObserver: true
3_SplSubject : true
3_Observer   : false
3_Observable : false
3_PHP_VERSION: 8.0.2
```

- **8.0.2 上 `SplSubject`/`SplObserver` 可用且零告警**，手册该页也没有废弃标记；但 **PHP 8.0 里没有不带 `Spl` 前缀的 `Observer`/`Observable`**（那是后续版本才补进 SPL 的），所以"自定义一对接口"在 8.0 上仍是必经动作，上面借用 `SplObserver` 只是为了少写一个接口。更高版本是否把这对接口标记废弃，本机无从验证（最高 8.0.2），升级前先自己跑一遍 `error_reporting(E_ALL)`。
- 通知顺序 = `attach` 顺序；`SplObjectStorage` **按对象身份去重**（`D` 被挂两次，第二轮只出现一次）。换成 `array` 存表既会重复通知，又得自己记键才能注销。
- **`detach` 和 `attach` 都挡不住本轮、也来不及本轮**：`C` 照样收到 `OrderPaid`，`D` 到第二轮才出现——因为遍历的是 `clone` 出的快照。用"注销监听"做权限控制的代码要特别小心这条。
- 把 `publish()` 里的 `clone` 去掉直接遍历活表，`update()` 里的 `detach` 会让 `foreach` 反复回到同一个节点：实测 `php -d memory_limit=64M` 几十毫秒内就 `Allowed memory size of 67108864 bytes exhausted`（stderr），连 `trace` 都没打出来。**clone 不是洁癖，是防死循环。**
- **重入是深度优先，而且会串事件名**：场景 2 里内层 `publish` 把 `$order->event` 改成了 `CouponUsed`，外层轮到 `Stock` 时读到的是内层的事件名——根因是 `SplSubject::notify()` 签名固定为无参、事件名只能挂在主题身上，**这也是它在真实事件总线里不够用、Laravel 要自己重写 `Event` 的原因**。级联请改成"投递下一个事件"，别在 `update()` 里同步 `publish`。

## 二、观察者抛异常：不隔离就有人根本收不到通知

接第一节代码，比较"异常冒泡"和"逐个 try/catch"：

```php
<?php

// 接第一节代码：复用已定义的 Order / Listener
declare(strict_types=1);

/** 会抛异常的观察者：模拟短信网关超时 */
final class Sms implements SplObserver
{
    public function update(SplSubject $subject): void
    {
        throw new RuntimeException('短信网关超时');
    }
}

foreach ([false, true] as $isolate) {
    $tag = $isolate ? '2_iso' : '1_raw';
    Order::$trace = [];
    $order = new Order();
    $order->attach(new Listener('Mailer'));
    $order->attach(new Sms());
    $order->attach(new Listener('Points'));
    try {
        $order->publish('OrderPaid', $isolate);
    } catch (Throwable $e) {
        printf("%s_threw  : %s: %s\n", $tag, get_class($e), $e->getMessage());
    }
    printf("%s_reached : %s\n", $tag, implode('>', Order::$trace));
}
```

```text
1_raw_threw  : RuntimeException: 短信网关超时
1_raw_reached : Mailer:OrderPaid
2_iso_threw  : RuntimeException: 部分观察者失败 -> Sms: 短信网关超时
2_iso_reached : Mailer:OrderPaid>Points:OrderPaid
```

`1_raw_reached` 里 `Points` 直接消失，主流程也被一起带崩。隔离版三条要点：`catch (Throwable)` 而不是 `Exception`（否则观察者里抛 `TypeError` 照样漏）；失败者攒起来、通知完**统一抛一次**——同步事件里"有监听器失败"必须冒泡，**要静默就改异步队列，靠重试兜底**；日志里记 `get_class($observer)`，能直接指到出问题的那个监听器。

## 三、php-fpm：观察者表跨不了请求，事件只能落队列

判据一句话：**副作用要和本次请求（乃至同一事务）共进退 → 同步观察者；可以延迟 → 事件序列化进队列**。
这也是和 Java 差别最大的一点：Java 的观察者挂在堆上，注册一次活到 JVM 结束；PHP 每个请求都要重新装配注册表。不用框架也能跑出来——脚本自己 spawn 一个子进程，等价于"下一个请求"：

```php
<?php

declare(strict_types=1);

/** 事件注册表：框架在每次请求里重新装配（这里手工装配），$done 记账同步副作用 */
final class EventBus
{
    public static array $map = [];    // 事件名 => 监听器类名

    public static array $done = [];   // 本请求内已发生的副作用
}

$q = sys_get_temp_dir() . '/dp-obs-queue.jsonl';

if (($argv[1] ?? '') === '--next') {          // 下一个请求 = 又一个全新进程
    printf("2_registry : %s\n2_done     : %s\n2_queue    : %s\n", json_encode(EventBus::$map), json_encode(EventBus::$done), trim((string) file_get_contents($q)));
    exit;
}

@unlink($q);                                  // 请求 1
EventBus::$map['OrderPaid'] = ['AuditListener', 'QueueingListener'];   // 表里存类名，派发那一刻才 new
foreach (EventBus::$map['OrderPaid'] as $listener) {
    EventBus::$done[] = $listener . ':OrderPaid';                      // 同步副作用：只活在本进程
    if ($listener === 'QueueingListener') {
        // 跨请求副作用：只投递。这里用文件替身，真实项目是 Redis Stream / RabbitMQ / Kafka
        file_put_contents($q, json_encode(['OrderPaid', ['orderId' => 1001]]) . PHP_EOL, FILE_APPEND | LOCK_EX);
    }
}
printf("1_registry : %s\n1_done     : %s\n", json_encode(EventBus::$map), json_encode(EventBus::$done));
echo '--- 下一个请求（全新进程）---', PHP_EOL;
echo rtrim((string) shell_exec(escapeshellarg(PHP_BINARY) . ' ' . escapeshellarg(__FILE__) . ' --next')), PHP_EOL;
```

```text
1_registry : {"OrderPaid":["AuditListener","QueueingListener"]}
1_done     : ["AuditListener:OrderPaid","QueueingListener:OrderPaid"]
--- 下一个请求（全新进程）---
2_registry : []
2_done     : []
2_queue    : ["OrderPaid",{"orderId":1001}]
```

`2_registry : []` 就是那堵墙——新进程里监听表是空的、同步副作用也没了，**唯一跨过进程边界的是被序列化出来的那行事件**。所以：注册表必须由框架每次请求重建（Laravel 在 `EventServiceProvider::boot()` 里 `Event::listen(...)`，Symfony 靠容器编译期的 `kernel.event_listener` tag），PHP 的观察者代码就长成"存类名的 map + 派发时才 `new`"，而不是启动时挂好对象；代价是监听器不能持有请求态数据（它还没被构造），好处是没触发的事件连监听器都不实例化。

真实项目里的领域事件形态（Laravel 公开用法，本机未装框架，**非实跑**）：`app/Events/OrderPaid.php` 只装数据、`app/Listeners/AuditListener.php` 只做一个动作、`Event::dispatch(new OrderPaid($order))` 派发；监听器实现 `ShouldQueue` 即自动从"同步执行"变成"投递队列"。常驻模型（Swoole / RoadRunner）下 `2_registry` 不再为空，注册表变成**跨请求共享状态**：注册只做一次，且监听器里绝不能存用户态数据（串号风险，与 [单例模式.md](单例模式.md) 第四节的静态属性是同一件事）。

## 四、Go / Java 对照：注册表活着，反注册就从"可选"变成"必须"

（本机 `go1.26.5` / `jdk1.8.0_321` 实跑。）同一套观察者搬到常驻语言里，第一节那些"进程结束就干净了"的好处全部消失，取而代之的是两个新问题：**通知期间的并发**，和**忘了 `remove` 就是内存泄漏**。

Go 版把"逐个隔离异常"写成 `recover`，把"遍历快照"写成 `append` 复制：

```go
package main

import "fmt"

type Listener func(event string)

type Bus struct{ listeners map[string][]Listener }

func NewBus() *Bus { return &Bus{listeners: map[string][]Listener{}} }

func (b *Bus) On(event string, l Listener) { b.listeners[event] = append(b.listeners[event], l) }

func (b *Bus) Publish(event string) {
	// 遍历快照：通知期间再 On/Delete 不影响本轮，等价于 PHP 篇里 publish() 的 clone
	snapshot := append([]Listener(nil), b.listeners[event]...)
	for _, l := range snapshot {
		func() {
			defer func() {
				if r := recover(); r != nil {
					fmt.Println("listener panic isolated:", r)
				}
			}()
			l(event)
		}()
	}
}

func main() {
	bus := NewBus()
	bus.On("OrderPaid", func(string) { fmt.Println("audit") })
	bus.On("OrderPaid", func(string) { panic("boom") })
	bus.On("OrderPaid", func(string) { fmt.Println("points") })
	bus.Publish("OrderPaid")
	fmt.Println("listeners after publish:", len(bus.listeners["OrderPaid"]))
}
```

```text
audit
listener panic isolated: boom
points
listeners after publish: 3
```

和 PHP 篇第二节实测的结论一致：**中间那个监听器炸了，后面的照样收到通知**，而且表里三个都还在（Go 这里靠 `recover`，PHP 靠 `catch (Throwable)`；不写这两样，表现都是"后面的静默收不到"）。

Java 版重点演示 PHP 里根本不存在的那个问题——观察者表跨请求存活，于是"每次请求挂一个监听器"会**累积**：

```java
import java.util.ArrayList;
import java.util.List;

interface Listener {
    void onOrderPaid(int orderId);
}

final class AuditListener implements Listener {
    public void onOrderPaid(int orderId) {
        System.out.println("audit order=" + orderId);
    }
}

final class Bus {
    private final List<Listener> listeners = new ArrayList<Listener>();

    void add(Listener l) { listeners.add(l); }

    void remove(Listener l) { listeners.remove(l); }

    int size() { return listeners.size(); }

    void publish(int orderId) {
        for (Listener l : new ArrayList<Listener>(listeners)) {
            l.onOrderPaid(orderId);
        }
    }
}

public class ObserverLeakDemo {
    public static void main(String[] args) {
        Bus leaky = new Bus();
        for (int req = 1; req <= 3; req++) {
            Listener l = new AuditListener();
            leaky.add(l);                    // 只注册不反注册：常驻进程里的典型写法
            leaky.publish(req);
            System.out.println("leaky  request=" + req + " listeners=" + leaky.size());
        }
        Bus tidy = new Bus();
        for (int req = 1; req <= 3; req++) {
            Listener l = new AuditListener();
            tidy.add(l);
            tidy.publish(req);
            tidy.remove(l);                  // 作用域结束就摘掉
            System.out.println("fixed  request=" + req + " listeners=" + tidy.size());
        }
    }
}
```

```text
audit order=1
leaky  request=1 listeners=1
audit order=2
audit order=2
leaky  request=2 listeners=2
audit order=3
audit order=3
audit order=3
leaky  request=3 listeners=3
audit order=1
fixed  request=1 listeners=0
audit order=2
fixed  request=2 listeners=0
audit order=3
fixed  request=3 listeners=0
```

`leaky` 那一列就是 Java 里最有名的内存泄漏来源之一：**监听器持有 Activity/Session/请求上下文，事件源是长生命周期单例，于是这些对象全被拽住不释放**，而且通知会重复投递——第 3 次请求 `order=3` 被打了三遍（三个历史监听器都还在表里）。`fixed` 版每次请求结束就 `remove`，表长恒为 0，同一事件只投一次。

三语言结论对照：

| | PHP（php-fpm） | Go / Java（常驻） |
| --- | --- | --- |
| 注册表生命周期 | 一次请求，进程结束自动干净 | 进程/JVM，**必须显式 `detach`/`remove`** |
| 忘反注册的后果 | 无（随请求销毁） | 内存泄漏 + 事件重复投递（上表实测 `listeners` 累积到 3） |
| 通知期间改表 | 遍历 `clone` 快照，本轮不受影响 | 遍历副本或加锁；并发下直接遍历原 slice/list 会 data race / `ConcurrentModificationException` |
| 一个观察者抛错 | `catch (Throwable)` 逐个隔离（实测不隔离则后面全收不到） | Go `recover`、Java `try/catch`，同样要逐个包 |
| 跨请求副作用 | 只能序列化进队列（第三节实测 `2_registry : []`） | 直接同步执行即可，这也是两边"要不要 MQ"判断相反的原因 |

## 五、校验口径

- 第一~三节 PHP 均在 `D:\phpstudy_pro\Extensions\php\php8.0.2nts\php.exe`（PHP 8.0.2 / Zend 4.0.2，CLI）上 `php -l` 通过后实跑，`text` 块是原始 stdout。第一、二节可独立复制运行，第三节是接第二节代码的片段（复用其 `Order`/`Listener`）。
- 第四节 Go 段：`go vet` 通过并 `go run`（`go1.26.5`）；Java 段：`javac -encoding UTF-8` 通过并 `java` 实跑（`jdk1.8.0_321`），两段 `text` 块都是原始 stdout。
- "活表 + `detach` 死循环"那条是把 `publish()` 里的 `clone` 去掉后单独跑的临时脚本（`memory_limit=64M`，**消息在 stderr**），正文以行内代码引用，没作为可复制代码块给出。
- 第三节脚本会 `shell_exec` 自己一次（`--next`）模拟下一个请求，并在系统临时目录读写 `dp-obs-queue.jsonl` 当队列替身；`shell_exec` 被禁用时，手工带 `--next` 再跑一次即可得到同样的 `2_registry : []`。
- 语法下限：构造器属性提升、`?callable`、箭头函数需 **PHP 7.4**；本篇未使用 `readonly`（8.1）与 `enum`（8.1）。
- **未验证项**：更高 PHP 版本是否把 `SplSubject`/`SplObserver` 标记废弃（本机最高 8.0.2）、Laravel/Symfony 内部实现（相关描述来自公开文档）、真实 MQ 行为、Java 侧的 `ConcurrentModificationException`（表中作为已知语言行为引用，本篇未实跑触发它）。

## 面试官会追问什么

- **`SplObjectStorage` 存观察者和 `array` 存有什么区别？** → 按对象身份去重、`detach` 不用记键、`clone` 快照便宜；`array` 版同一实例挂两次会被通知两次。
- **观察者里抛异常怎么办？** → 通知循环里逐个 `try/catch (Throwable)`，失败攒起来通知完再统一抛；要静默就改异步队列（实测不隔离时后面的观察者一个都收不到）。
- **一个观察者把另一个摘了，本轮还通知吗？** → 通知（遍历快照），下一轮才生效；不 clone 直接遍历活表会死循环到内存耗尽。
- **PHP 里观察者模式能替代 MQ 吗？** → 不能，监听表随请求结束销毁（实测 `2_registry : []`），跨请求/跨服务必须把事件序列化进队列。
- **和注册模式、中介者怎么选？** → 注册模式管"全局拿到实例"，观察者管"一对多通知"；事件多到互相依赖时用事件总线/中介者收口，别在 `update()` 里同步级联。
- **怎么保证通知幂等？** → 事件带唯一 ID，消费端记已处理集合去重；异步重试必然造成重复投递，观察者本身不保证"只通知一次"。
