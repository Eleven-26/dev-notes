# 外观模式：把一串子系统调用收敛成一个入口

> 素材来源：博客系列 [PHP 设计模式(八)：外观模式](https://blog.csdn.net/weixin_43837229/article/details/102681117)。
> 本篇重写版补齐原文没展开的三块：**外观与中介者的分工、"上帝服务"的可反射量化判据、分层/微服务项目里的用例方法形态**，并辨析 PDO / Flysystem / Laravel `Storage` 谁是真外观。
> 迪米特法则的"三跳变一跳"实测在 [六大原则.md](六大原则.md) 第六节，本篇交叉引用、不重复。

## 一、外观只做两件事：转发和编排，不产生新逻辑

外观（Facade，结构型模式）：为子系统的一组接口提供统一的高层接口。三条关键性质，缺一条就不是外观：

| 性质 | 含义 | 违反后的形态 |
| --- | --- | --- |
| 降接口面 | N 个子系统类 → 1 个业务入口 | 调用方仍要自己攒依赖 |
| 不独占 | 子系统可绕过外观直接使用 | 变成必经的"上帝类" |
| 无业务决策 | 方法体只有转发 + 顺序编排 | 退化成 God Service（第四节判据） |

```php
<?php

declare(strict_types=1);

final class OrderRepo { public function find(int $id): string { return "order#{$id}"; } }
final class PaymentGateway { public function charge(int $id): string { return "txn_{$id}"; } }
final class Mailer { public function send(string $to): string { return "mail->{$to}"; } }

// 外观：三个子系统类 + 固定调用顺序，收敛成一个业务入口
final class CheckoutFacade
{
    public function __construct(private OrderRepo $orders, private PaymentGateway $gw, private Mailer $mail) {}

    public function placeOrder(int $id, string $email): string
    {
        $this->orders->find($id);
        $txn = $this->gw->charge($id);
        $this->mail->send($email);
        return $txn;
    }
}

$facade = new CheckoutFacade(new OrderRepo(), new PaymentGateway(), new Mailer());
echo $facade->placeOrder(7, 'a@x.com'), PHP_EOL;
echo 'subsystem_alone: ', (new Mailer())->send('b@x.com'), PHP_EOL;
```

```text
txn_7
subsystem_alone: mail->b@x.com
```

第二行是重点：**外观存在不影响子系统独立使用**。某类若逼所有人只能经它干活，它已经不是可选的门面。实测均用 `D:\phpstudy_pro\Extensions\php\php8.0.2nts\php.exe`，下同。

## 二、外观 vs 中介者：一个降接口面，一个管对象间通信

| | 外观（结构型） | 中介者（行为型） |
| --- | --- | --- |
| 为谁服务 | 外部调用方：少记几个类 | 子系统内部：同事对象互相引用成网 |
| 依赖方向 | 单向：外观 → 子系统，子系统不知道外观 | 双向：每个同事持有中介者并回调它 |
| 解决的问题 | "用这套系统的人太多" | "系统内部模块互相调" |

现场判据一句话：**删掉它之后子系统是否依然完整可用**。完整可用 → 删掉的是可选的外观；对象立刻退回互相直连的蛛网 → 那是中介者。

## 三、分层/微服务项目里外观的真实形态：一个用例一个入口

教科书写法是"开机按电源→主板→CPU"；工程里的对应物是 Controller→Service→Repository 的调用链被收敛成一个**用例方法**（application service / command handler）：

```php
<?php

declare(strict_types=1);

final class Trace
{
    /** @var string[] */
    public static array $steps = [];
    public static function hit(string $s): void { self::$steps[] = $s; }
}

final class UserRepo
{
    public function find(int $id): string { Trace::hit('repo.find'); return "user#{$id}"; }
    public function save(string $user): void { Trace::hit('repo.save'); }
}

final class NameValidator
{
    public function check(string $name): bool { Trace::hit('validator.check'); return $name !== ''; }
}

final class AuditRepo
{
    public function put(string $line): void { Trace::hit('audit.put'); }
}

// 没有外观：调用方（Controller）自己按顺序拼链路
function rename_raw(UserRepo $repo, NameValidator $v, AuditRepo $a, int $id, string $newName): void
{
    $user = $repo->find($id);
    if (!$v->check($newName)) { return; }
    $repo->save($user);
    $a->put("rename {$id} -> {$newName}");
}

// 外观（应用服务/用例方法）：同一条链路收敛成一个入口
final class RenameUserUseCase
{
    public function __construct(private UserRepo $repo, private NameValidator $v, private AuditRepo $a) {}

    public function run(int $id, string $newName): void
    {
        $user = $this->repo->find($id);
        if (!$this->v->check($newName)) { return; }
        $this->repo->save($user);
        $this->a->put("rename {$id} -> {$newName}");
    }
}

$deps = [new UserRepo(), new NameValidator(), new AuditRepo()];
rename_raw($deps[0], $deps[1], $deps[2], 1, 'Ann');
$raw = Trace::$steps;
Trace::$steps = [];
(new RenameUserUseCase(...$deps))->run(1, 'Ann');
echo 'without: ', implode(' -> ', $raw), PHP_EOL;
echo 'with:    ', implode(' -> ', Trace::$steps), PHP_EOL;
echo 'same_chain: ', var_export($raw === Trace::$steps, true), PHP_EOL;
```

```text
without: repo.find -> validator.check -> repo.save -> audit.put
with:    repo.find -> validator.check -> repo.save -> audit.put
same_chain: true
```

微服务语境有两个变体：**BFF** 是给"一个页面"做的外观（聚合多个下游服务）；**防腐层** 是给"一个外部系统"做的外观（挡住对方模型泄漏进来）。判别标准相同：调用方只发一次意图（`run(1, 'Ann')`），不再关心链路里有几步。

## 四、外观不该变成"上帝服务"：三条可反射验证的判据

"先建个 Facade 方便"的项目，半年后门面试图替你决定一切。退化不靠感觉，用反射量化（判据对应第一节表格后两条性质）：

```php
<?php

declare(strict_types=1);

final class StripeGateway
{
    public function charge(float $amount): string { return sprintf('ch_%d', (int) ($amount * 100)); }
}

final class InvoiceRepo
{
    public function markPaid(int $id, string $txn): void {}
}

// 合格外观：方法只做"转发 + 顺序编排"，无业务分支、无内部状态
final class PaymentFacade
{
    public function __construct(private StripeGateway $gw, private InvoiceRepo $inv) {}

    public function charge(int $orderId, float $amount): string
    {
        $txn = $this->gw->charge($amount);
        $this->inv->markPaid($orderId, $txn);
        return $txn;
    }
}

// 变质的"上帝服务"：往"外观"里塞了会员折扣、风控分支、内部缓存
final class OrderGodService
{
    /** @var array<int,string> */
    private array $memo = [];

    public function __construct(private StripeGateway $gw, private InvoiceRepo $inv) {}

    public function handle(array $order): string
    {
        if (($order['vip'] ?? false) && $order['amount'] > 1000) {
            $order['amount'] *= 0.9;
        }
        foreach ($order['items'] ?? [] as $item) {
            if (($item['risk'] ?? false) === true) {
                return 'blocked';
            }
        }
        switch ($order['channel'] ?? 'web') {
            case 'app':
                $fee = 1;
                break;
            default:
                $fee = 2;
        }
        $txn = $this->gw->charge((float) $order['amount'] + $fee);
        $this->inv->markPaid((int) $order['id'], $txn);
        $this->memo[(int) $order['id']] = $txn;
        return $txn;
    }
}

function inspect(string $class): void
{
    $r = new ReflectionClass($class);
    $file = file($r->getFileName());
    foreach ($r->getMethods(ReflectionMethod::IS_PUBLIC) as $m) {
        if ($m->getName() === '__construct') { continue; }
        $src = implode('', array_slice($file, $m->getStartLine() - 1, $m->getEndLine() - $m->getStartLine() + 1));
        printf("%-16s %-8s body=%2d lines, branches=%d\n", $class, $m->getName(),
            $m->getEndLine() - $m->getStartLine() + 1, preg_match_all('/\b(if|switch|foreach|for)\b/', $src));
    }
    $params = array_map(static fn (ReflectionParameter $p): string => $p->getName(), $r->getConstructor()->getParameters());
    $internal = array_filter($r->getProperties(ReflectionProperty::IS_PRIVATE),
        static fn (ReflectionProperty $p): bool => !in_array($p->getName(), $params, true));
    printf("%-16s summary: 内部可变状态(非构造注入)属性数=%d\n", $class, count($internal));
}

inspect(PaymentFacade::class);
inspect(OrderGodService::class);
```

```text
PaymentFacade    charge   body= 6 lines, branches=0
PaymentFacade    summary: 内部可变状态(非构造注入)属性数=0
OrderGodService  handle   body=22 lines, branches=4
OrderGodService  summary: 内部可变状态(非构造注入)属性数=1
```

三条判据与实测对应：

1. **方法体短**：合格外观单方法 5~10 行（实测 6）；`handle` 22 行说明它已在替子系统做决定。
2. **无业务分支**：外观里出现依赖入参的 `if/switch`（实测 branches=4）说明领域规则住错了地方，该下沉到领域对象或 [策略模式.md](策略模式.md)。
3. **无内部可变状态**：构造注入的依赖不算，自己养缓存/累加器才算（实测 0 vs 1）。外观一旦有状态，就从"入口"变成"真相源"。

补救不是把上帝类拆小继续当上帝，而是**按用例拆**：一个动作一个外观类（`RenameUserUseCase` 优于 `UserService::handle($action)`）。这也是迪米特法则（[六大原则.md](六大原则.md) 第六节"三跳收成一跳"实测）的批量落地，判据 2 则防止"一跳"膨胀成"一跳带私货"。

## 五、PHP 生态的真实例子：别把三个"Facade"混为一谈

| 真实代码 | 外观在哪 | 辨析 |
| --- | --- | --- |
| `PDO` | 对 `pdo_mysql`/`pdo_pgsql`/`pdo_sqlite` 驱动 | 换驱动不改业务代码；`query()` 内部编排准备→执行→取回 |
| `League\Flysystem` | `Filesystem` 对 aws/s3、本地磁盘、FTP 各 adapter | 业务只调 `write()/read()`，不知道文件落在哪个云 |
| Laravel `Storage` | GoF 意义的外观是 Flysystem 这层 | `FilesystemManager` 按 config 造 Flysystem 实例 |

高频面试坑：**Laravel 的 `Illuminate\Support\Facades\Facade` 基类不是 GoF 外观**，是"静态代理"——`Storage::put()` 靠 `__callStatic` 从容器解析真实实例再转发，解决的是静态调用语法与可测试替换，与降接口面无关（对比见 [代理模式.md](代理模式.md)）。名字撞车纯属历史原因。

## 六、校验口径

- PHP 块：`D:\phpstudy_pro\Extensions\php\php8.0.2nts\php.exe`（PHP 8.0.2，CLI）。第一、三、四节的块各自独立成篇执行，`php -l` 无语法错误后整块运行，`text` 块是原始 stdout。语法用到构造器提升与箭头函数（**最低 PHP 8.0**），未用 8.1 特性。
- 第四节 `body=N / branches=N` 由 `ReflectionMethod` 与 `preg_match_all` 在该脚本上实测，改动方法排版会让数字如实变化。未附 Go/Java 对照块（篇幅取舍，Go 的 `database/sql` 对 driver 的关系与 PDO 同构可自查）；全篇无真实 SMTP/支付网关，示例域名与单号不指向可用服务。

## 面试官会追问什么

- **外观和适配器怎么选？** → 适配器是"已有接口不合调用方期望，改造形状"；外观是"接口太多，设计一个简化新口"。
- **外观是不是就是那个塞满方法的 `XxxService`？** → 大概率是反面教材，三条可反射判据见第四节。
- **Laravel Facade 是 GoF 外观吗？** → 不是，是静态代理 + 容器解析（第五节）。GoF 外观在 Laravel 里的对位物是应用服务层。
