# 面向切面编程：不用框架、不装扩展，纯 PHP 能写的四种切面

> 素材来源：博客 [面向切面编程](https://blog.csdn.net/weixin_43837229/article/details/102666842)。原文只有一个论点——"AOP 是 OOP 的补充"。本篇把它落成代码：横切代码散落的反例 + **纯 PHP 四种切面写法**（装饰器 / 闭包管道 / `__call` / 属性+反射）各自实跑，再对照 Go / Java，说清 PHP 的"切面"和字节码织入差在哪、什么时候不该用。所有代码块本机实测，紧随其后的 `text` 块为原始 stdout。

## 一、AOP 要解决的问题：同一件事在每个业务方法里都写一遍
日志、鉴权、事务、重试、计时这类代码有个共同点：**和方法是干什么的无关，但每个方法都要有**——横切关注点。OOP 的横向分层（Controller→Service→Model）装不下"竖着穿过每一层"的逻辑。反例（计时同理，这里用静态计数器实测重复次数）：
```php
<?php
final class BadOrderService
{
    public static int $auth = 0;
    public static int $log = 0;
    public function create(string $u): string { self::$auth++; self::$log++; return 'created'; }
    public function cancel(string $u): string { self::$auth++; self::$log++; return 'cancelled'; }
    public function pay(string $u): string { self::$auth++; self::$log++; return 'paid'; }
}
$svc = new BadOrderService();
$svc->create('u'); $svc->cancel('u'); $svc->pay('u');
echo 'methods=3 auth_calls=', BadOrderService::$auth, ' log_calls=', BadOrderService::$log, PHP_EOL;
```
```text
methods=3 auth_calls=3 log_calls=3
```
三个方法各粘同样的两行：**改鉴权要改 N 处，加一种横切还是 N 处**。AOP 的主张就一句话：横切逻辑只写一遍，再"声明"它作用于哪些方法。下面四种纯 PHP 写法，就是"声明"的四种做法。

## 二、切面一：装饰器包一层（次数与前后顺序都打进输出）
```php
<?php
interface OrderService { public function create(string $sku): string; }
final class LiveOrder implements OrderService
{
    public function create(string $sku): string { echo '  business: create(', $sku, ')', PHP_EOL; return 'ok'; }
}
final class TimingDecorator implements OrderService
{
    private int $calls = 0;
    private OrderService $inner;
    public function __construct(OrderService $inner) { $this->inner = $inner; }
    public function create(string $sku): string
    {
        echo 'aspect: start #' . (++$this->calls) . PHP_EOL;
        $r = $this->inner->create($sku); // 真实计时在这里放 microtime(true)，本篇刻意不打印耗时数值
        echo 'aspect: end   #' . $this->calls . PHP_EOL;
        return $r;
    }
}
$svc = new TimingDecorator(new LiveOrder());
$svc->create('a'); $svc->create('b');
```
```text
aspect: start #1
  business: create(a)
aspect: end   #1
aspect: start #2
  business: create(b)
aspect: end   #2
```
业务类零改动、实现同一接口调用方无感知（里氏替换成立）。代价：一个横切关注点一个类，两个切面叠加就 `new A(new B(new C(...)))`，类数量随切面数线性涨。

## 三、切面二：闭包管道——中间件背后的模型，实跑洋葱式前后顺序
不想建类：切面可以是"一个接收 `$next` 的函数"。极简 `pipeline`：
```php
<?php
function pipeline(array $pipes, callable $core): callable
{
    $next = $core;
    foreach (array_reverse($pipes) as $pipe) {
        $inner = $next;
        $next = function (string $passable) use ($pipe, $inner): string { return $pipe($passable, $inner); };
    }
    return $next;
}
$rateLimit = function (string $req, callable $next): string {
    echo '1-down: 限流 ', $req, PHP_EOL;
    $r = $next($req);
    echo '1-up:   限流', PHP_EOL;
    return $r;
};
$auth = function (string $req, callable $next): string {
    echo '2-down: 鉴权', PHP_EOL;
    $r = $next($req);
    echo '2-up:   鉴权', PHP_EOL;
    return $r;
};
$resp = pipeline([$rateLimit, $auth], function (string $req): string {
    echo 'core:   业务', PHP_EOL;
    return 'resp';
})('GET /order');
```
```text
1-down: 限流 GET /order
2-down: 鉴权
core:   业务
2-up:   鉴权
1-up:   限流
```
`1-down → 2-down → core → 2-up → 1-up` 就是"洋葱模型"：**外层切面的后置逻辑最后执行**，包裹顺序 = 注册顺序；某个环节不调 `$next` 就直接短路返回（限流拒绝的语义天然就有）。Laravel 的 HTTP middleware 在结构上就是这个 `pipeline`。

## 四、切面三：`__call` 一次拦截所有方法（不声明就拦全部，代价一并打出来）
```php
<?php
final class MagicOrderService
{
    public array $hit = [];
    public function __call(string $name, array $args)
    {
        $this->hit[] = $name;
        echo 'intercept: ', $name, '(', implode(',', $args), ')', PHP_EOL;
    }
}
$svc = new MagicOrderService();
$svc->create('a'); $svc->cancel(123); $svc->notARealMethod('x');
echo 'intercepted=', count($svc->hit), ' method_exists(create)=', var_export(method_exists($svc, 'create'), true), PHP_EOL;
```
```text
intercept: create(a)
intercept: cancel(123)
intercept: notARealMethod(x)
intercepted=3 method_exists(create)=false
```
最后一行就是代价的实证：`method_exists` 返回 false——`create` 在语言层面根本不存在，于是类型检查、IDE 补全、PHPStan/Psalm 静态分析三者同时全瞎；传 `int`、方法名拼错都不报错。只用在外围边界（RPC 客户端、动态 handler 表、老代码适配），别放进业务域模型。

## 五、切面四：属性注解 + 运行时反射——最接近"注解驱动"
`#[Attribute]` 是 PHP 8.0 特性（8.0 之前只能写 docblock 注释再靠 doctrine/annotations 解析）。给方法挂 `#[Log]`，调用前反射判断切面是否生效：
```php
<?php
#[\Attribute(\Attribute::TARGET_METHOD)]
final class Log { public function __construct(public string $tag = 'default') {} }
final class AnnotatedOrderService
{
    #[Log('order')]
    public function create(string $sku): string { echo '  business: create(', $sku, ')', PHP_EOL; return 'ok'; }
    public function plainQuery(): string { echo '  business: 未标注解, 切面不生效', PHP_EOL; return 'data'; }
}
function run(object $svc, string $method, array $args = [])
{
    $rm = new ReflectionMethod($svc, $method);
    $attrs = $rm->getAttributes(Log::class);
    if ($attrs === []) { return $rm->invokeArgs($svc, $args); }
    $tag = $attrs[0]->newInstance()->tag;
    echo 'aspect[', $tag, ']: before ', $method, PHP_EOL;
    $r = $rm->invokeArgs($svc, $args);
    echo 'aspect[', $tag, ']: after  ', $method, PHP_EOL;
    return $r;
}
$svc = new AnnotatedOrderService();
run($svc, 'create', ['a']); run($svc, 'plainQuery');
```
```text
aspect[order]: before create
  business: create(a)
aspect[order]: after  create
  business: 未标注解, 切面不生效
```
属性本身只是"休眠的元数据"，`getAttributes()` + `newInstance()` 才被反射变成对象——这就是"声明切面作用于哪个方法"的最小形态。把它和第二节的装饰器拼起来（启动时扫描容器里的服务，凡带 `#[Log]` 的自动包一层），就是注解式 AOP 的完整装配。

## 六、跨语言对照：Go 中间件、Java 动态代理（都真编译真跑）
Go（临时模块 `go vet` 通过并 `go run`）——`net/http` 中间件与下面的 `Middleware` 同构，Go 的"AOP"就是显式管道，没有魔法：
```go
package main
import "fmt"
type Handler func(req string) string
type Middleware func(next Handler) Handler // net/http 的中间件签名是 func(http.Handler) http.Handler，与此同构
func logging(next Handler) Handler {
	return func(req string) string {
		fmt.Println("1-down: logging", req)
		resp := next(req)
		fmt.Println("1-up:   logging")
		return resp
	}
}
func auth(next Handler) Handler {
	return func(req string) string {
		fmt.Println("2-down: auth")
		resp := next(req)
		fmt.Println("2-up:   auth")
		return resp
	}
}
func main() {
	h := logging(auth(func(req string) string {
		fmt.Println("core:   business")
		return "resp"
	}))
	fmt.Println("got:", h("GET /order"))
}
```
```text
1-down: logging GET /order
2-down: auth
core:   business
2-up:   auth
1-up:   logging
got: resp
```
Java（本机 `javac -encoding UTF-8` 编译通过并运行）——Spring 的 `@Around` 运行时真身就是下面这种动态代理，注释里标了对应关系，不引 Spring 依赖、只手写 JDK 等价物：
```java
import java.lang.reflect.InvocationHandler;
import java.lang.reflect.Method;
import java.lang.reflect.Proxy;
public class AopAround {
    public static void main(String[] args) {
        // 真实 Spring 写法：@Aspect 类里方法标 @Around，收到 ProceedingJoinPoint，
        // pjp.proceed() 等价于下面 invoke() 里的 method.invoke(...)；容器注入给你的
        // 就是这种代理对象（有接口走 JDK 动态代理，无接口走 CGLIB）。此处不引依赖手写等价物。
        OrderService proxy = (OrderService) Proxy.newProxyInstance(
                OrderService.class.getClassLoader(), new Class<?>[]{OrderService.class},
                new TimingHandler(new OrderServiceImpl()));
        proxy.create("a");
        System.out.println("calls=" + ((TimingHandler) Proxy.getInvocationHandler(proxy)).calls);
    }
    interface OrderService { String create(String sku); }
    static class OrderServiceImpl implements OrderService {
        public String create(String sku) { System.out.println("  business: create(" + sku + ")"); return "ok"; }
    }
    static class TimingHandler implements InvocationHandler {
        private final Object target;
        int calls = 0;
        TimingHandler(Object target) { this.target = target; }
        public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
            calls++;
            System.out.println("aspect: before #" + calls + " " + method.getName());
            Object r = method.invoke(target, args);
            System.out.println("aspect: after  #" + calls + " " + method.getName());
            return r;
        }
    }
}
```
```text
aspect: before #1 create
  business: create(a)
aspect: after  #1 create
calls=1
```

## 七、PHP 的"切面"和真正 AOP 的差距：织入 vs 代理 + 管道
复盘上面所有实现，机制只有两种：**管道**（第三节、六节 Go）和**代理**（二、四、五节与六节 Java）。Java 还有第三条路——AspectJ 在编译期/类加载期**直接改字节码**，切面进了方法本体，连 `this.other()` 自调用都在控制内。PHP 拿不到这个抓手：解释执行、php-fpm 每请求重建内存，没有可修改的驻留中间产物，"织入"没有落点——所以 PHP 生态里叫"AOP"的东西实际都是代理 + 管道：Laravel 的 middleware 就是第三节那个管道，Symfony 的 AOP 组件靠缓存预热时生成代理类（仍是代理）。代理模型留下两个原理性缺口（对 Spring 同样成立）：① **同类自调用绕过切面**——`$this->pay()` 不经过代理对象，注解标了也白标，"事务注解怎么不回滚"的根因多半在这；② **private 方法与构造期调用拦不住**——代理只能在对象外面包，进不到对象内部。

## 八、什么时候不该用切面
- **逻辑只对一两个方法生效：直接写**。切面收益和"被消除的重复处数"成正比，为两行代码建管道/反射扫描是纯亏，可读性还下降。
- **切面堆多了调用栈不可读**：限流→鉴权→日志→事务套五六层后，排查要猜在哪层被短路。经验阈值：入口管道里的切面数要能一屏列完，且每个都有名字。
- **把业务规则塞进切面是反模式**：切面只放技术性横切。判据一句话——**能公开广播给所有新人的**（"所有请求都会记日志"）才配当切面；"某订单一进这个方法会被悄悄改价"不行，那是业务，写进方法体。

## 面试官会追问什么
- **AOP 和装饰器模式的边界在哪？** → 代码形态可以完全相同（第二节的装饰器就是一种切面实现），差别在装配方式：装饰器由调用方**显式点名**（`new TimingDecorator(...)`），切面**按匹配规则生效**（注解、切点表达式、路由表），由容器或入口管道统一织入。一句话：装饰器是"我知道你在哪"，切面是"符合规则的都包上"。
- **事务为什么常被做成切面？** → begin/commit/rollback 是教科书式横切：穿过每个业务方法、代码形状固定（try-catch 包住调用）、漏写一次就是脏提交。切面化后业务方法只声明"我要事务"，回滚边界集中一处。再追问就给第七节缺口①：同类自调用绕过代理，注解标了也不回滚。
- **`__call` 做切面的代价？** → 类型检查、IDE、静态分析三者同时失明（第四节已用 `method_exists() === false` 实证），方法名拼错不再报错。适合边界适配，不适合域模型。
- **PHP 实现 AOP 为什么不如 Java 彻底？** → Java 有驻留的字节码这个可修改的中间表示，AspectJ 能编译期/加载期织入方法本体；PHP 解释执行、php-fpm 每请求重建，没有可改的驻留产物，只剩代理 + 管道两条运行时路，自调用与 private 拦截从原理上做不到。
