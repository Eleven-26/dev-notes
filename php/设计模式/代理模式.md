# 代理模式：包一层不是为了加功能，而是为了决定"谁能、什么时候碰到真对象"

> 素材来源：博客系列 [PHP 设计模式(十一)：代理模式](https://blog.csdn.net/weixin_43837229/article/details/102965194)。
> 重写版补上原文只停在"UML 图 + 定义"的部分：**虚拟代理"不访问就不构造"的打印时序实测**、
> **缓存代理的 memo 只活一次请求**（与 [单例模式.md](单例模式.md) 第四节同一约束）、
> **PHP 没有 Java 那种 JDK 动态代理**（`__call` 四条代价实测 + 代码生成这条路）、
> **`__call` 连类型声明都满足不了**（TypeError 实跑），以及全文的落点：代理 vs 适配器 vs 装饰器 vs 外观的一句话区分表。
> 邻居模式见 [装饰器模式.md](装饰器模式.md)、[适配器模式.md](适配器模式.md)、[外观模式.md](外观模式.md)。

## 一、代理只回答一个问题：怎么控制对某个对象的访问

代理（Proxy，结构型）：给目标对象占一个"替身"，**调用方面对替身，替身决定这次访问放不放行、什么时候真正落到目标上**。
四类代理控制的东西各不相同：

| 类别 | 控制什么 | 典型场景 |
| --- | --- | --- |
| 远程代理 | **网络边界**：序列化、延迟、断连，伪装成本地调用 | RPC client stub |
| 虚拟代理 | **构造成本**：重对象延迟到第一次被真正用到才 `new` | ORM 关联延迟加载 |
| 缓存代理 | **重复读**：同输入只回源一次，结果就地 memo | 请求内去重查询 |
| 保护代理 | **权限**：谁能调、能不能写，甚至接口里干脆没有这条路 | 鉴权包装、只读视图 |

三条判据，缺一条就不是代理：

1. 替身与目标**面向同一个接口**（只读视图是故意的例外：收窄到目标接口的子集，见第四节实测）；
2. 目标（或其"构造配方"：参数/地址）从**外面进来**，不是替身自己业务里造别的对象；
3. 加的那一层做的是**控制访问**（时机/次数/放行），不是新行为——加日志、压缩、重试是 [装饰器](装饰器模式.md)。

## 二、虚拟代理：没访问就不构造，这是打印出来的时序

```php
<?php

declare(strict_types=1);

interface UserQuery { public function findById(int $id): string; }

// 被代理的"重"对象：构造做贵的事（建连/加载元数据），echo 留下时序证据
final class RealUserRepo implements UserQuery
{
    public static int $ctorCount = 0;
    public function __construct() { self::$ctorCount++; echo '[real] 构造函数执行（模拟建连+加载元数据）', PHP_EOL; }
    public function findById(int $id): string { return "user#{$id}"; }
}

// 虚拟代理：实现同一接口，构造只记下参数，真正 new 推迟到第一次访问
final class UserRepoProxy implements UserQuery
{
    private ?RealUserRepo $real = null;
    public function __construct(private string $dsn) {}
    private function real(): RealUserRepo
    {
        if ($this->real === null) { echo '[proxy] 首次被访问，现在才构造', PHP_EOL; $this->real = new RealUserRepo(); }
        return $this->real;
    }
    public function findById(int $id): string { return $this->real()->findById($id); }
}

echo '--- 1. 只 new 代理，一次都不调用 ---', PHP_EOL;
$p = new UserRepoProxy('mysql:host=127.0.0.1');
echo '代理已就绪。上面没有任何 [real] 行 => 重对象根本没被构造', PHP_EOL;
echo '--- 2. 第一次调用 ---', PHP_EOL;
echo $p->findById(1), PHP_EOL;
echo '--- 3. 第二次调用 ---', PHP_EOL;
echo $p->findById(2), PHP_EOL;
echo 'RealUserRepo 构造次数: ', RealUserRepo::$ctorCount, PHP_EOL;
```

```text
--- 1. 只 new 代理，一次都不调用 ---
代理已就绪。上面没有任何 [real] 行 => 重对象根本没被构造
--- 2. 第一次调用 ---
[proxy] 首次被访问，现在才构造
[real] 构造函数执行（模拟建连+加载元数据）
user#1
--- 3. 第二次调用 ---
user#2
RealUserRepo 构造次数: 1
```

时序读法：第 1 步之后**一行构造输出都没有**——代理手里只有构造"配方"（那个 `$dsn` 字符串），不是实例；
第 2 步才补上构造；第 3 步 `ctorCount` 仍是 1，实例已挂在代理属性上。
**虚拟代理省的不是"让那次构造变快"，而是"这一分支根本没用到它"的整笔开销**——
请求走到的代码路径不碰关联对象，建连/加载元数据就一分不花。

## 三、缓存代理：memo 就几行，但它在 php-fpm 下只活一次请求

```php
<?php

declare(strict_types=1);

final class CacheProxy
{
    /** @var array<string, string> */
    private array $memo = [];
    public int $backendCalls = 0;
    public function __construct(private Closure $backend) {}
    public function get(string $key): string
    {
        // 用 array_key_exists 而不是 isset：值为 null 时 isset 漏判，每次都会回源
        if (!array_key_exists($key, $this->memo)) { $this->backendCalls++; $this->memo[$key] = ($this->backend)($key); }
        return $this->memo[$key];
    }
}

// 底层"贵读取"：真实场景这里换 SELECT / HTTP
$backend = static fn (string $key): string => "value-of-{$key}";
$p = new CacheProxy($backend);
foreach (['a', 'a', 'b', 'a', 'b'] as $k) { $p->get($k); }
echo "5 次 get（只有 2 个不同 key），底层实际被调用: {$p->backendCalls} 次\n";

$calls = 0; // 不写类，闭包版 memo 就是这个代理模式的全部内核
$memo = static function (callable $f): callable { $cache = [];
    return static function (string $k) use ($f, &$cache): string { return $cache[$k] ??= $f($k); }; };
$m = $memo(static function (string $k) use (&$calls): string { $calls++; return strtoupper($k); });
$m('x'); $m('x'); $m('y');
echo "闭包版 memo：3 次调用，底层被调用 {$calls} 次\n";
```

```text
5 次 get（只有 2 个不同 key），底层实际被调用: 2 次
闭包版 memo：3 次调用，底层被调用 2 次
```

两个坑都在输出里：5 次 get 只回源 2 次，**判定"缓存里没有"要用 `array_key_exists`**——
值为 `null`（查无此记录的负缓存）时 `isset` 和闭包版用的 `??=` 都会当成"没存过"，每次重新回源。

**生命周期红线**：[单例模式.md](单例模式.md) 第四节实测过 "PHP 是 **shared-nothing** 模型：php-fpm 每个请求结束后，
Zend 会回收用户态内存，静态属性随之消失"。这个 `$memo` 数组（包括闭包里 `use (&$cache)` 的那份）和用户态内存一起回收——
**php-fpm 下缓存代理省的是"一次请求内的重复读"**，省不了跨请求回源；要跨请求，得把结果放进独立的缓存进程/中间件
（Redis、APCu 这类），那时它是架构组件，已经不是设计模式意义上的"语言内对象"了。

## 四、保护代理：运行时拒绝与只读视图，报错时机差一层

```php
<?php

declare(strict_types=1);

interface Document { public function read(): string; public function write(string $s): string; }
final class FileDoc implements Document
{
    private string $body = 'v1';
    public function read(): string { return $this->body; }
    public function write(string $s): string { $this->body = $s; return "written:{$s}"; }
}

// 保护代理·鉴权版：接口一字不改，只在写路径上把关
final class AuthProxy implements Document
{
    public function __construct(private Document $inner, private string $role) {}
    public function read(): string { return $this->inner->read(); }
    public function write(string $s): string
    {
        if ($this->role !== 'editor') { throw new RuntimeException("403: 角色 {$this->role} 不能写"); }
        return $this->inner->write($s);
    }
}

// 保护代理·只读视图版：干脆不实现 write，调用方拿到的类型里就没有这条路
final class ReadOnlyDoc
{
    public function __construct(private Document $inner) {}
    public function read(): string { return $this->inner->read(); }
}

$editor = new AuthProxy(new FileDoc(), 'editor');
echo '1) editor 写: ', $editor->write('v2'), PHP_EOL;
$guest = new AuthProxy($editor, 'guest'); // 保护代理可以叠保护代理
try { $guest->write('hack'); } catch (Throwable $e) { echo '2) guest 写被拒: ', $e->getMessage(), PHP_EOL; }
echo '3) guest 读: ', $guest->read(), PHP_EOL;
$view = new ReadOnlyDoc($editor);
echo '4) 只读视图读: ', $view->read(), ' / 试着写: ';
try { $view->write('x'); } catch (Throwable $e) { echo get_class($e), ' -> ', explode(' in ', $e->getMessage())[0], PHP_EOL; }
```

```text
1) editor 写: written:v2
2) guest 写被拒: 403: 角色 guest 不能写
3) guest 读: v2
4) 只读视图读: v2 / 试着写: Error -> Call to undefined method ReadOnlyDoc::write()
```

两版的区别是**拦截发生在哪**：`AuthProxy` 保接口、运行时抛 403（调用方仍能把对象传给要求 `Document` 的形参，
适合"同一份代码、不同角色"）；`ReadOnlyDoc` 直接把 `write` 从类型里拿掉，误用是 `Error`（更适合把对象交给
不可信代码前收面——代价是它不再满足 `Document` 类型声明，见第五节实测的同款 TypeError）。

## 五、PHP 没有 JDK 动态代理：`__call` 与代码生成两条路

Java 可以在**运行期**生成一个"实现了指定接口"的代理类（第八节实跑）。PHP 做不到：运行期没有往类表里注入新类型、
让它 `implements` 任意接口的语言机制。于是 PHP 侧的"动态代理"只剩两条路，第一条先实测它赔什么：

```php
<?php

declare(strict_types=1);

interface OrderService { public function create(int $id): string; }
final class RealOrderService implements OrderService
{ public function create(int $id): string { return "order#{$id} created"; } }

// 只靠 __call 的"万能"代理：一个转发方法都不用手写
final class LogProxy
{
    /** @var string[] */
    public array $log = [];
    public function __construct(private object $inner) {}
    public function __call(string $name, array $args): mixed { $this->log[] = $name; return $this->inner->{$name}(...$args); }
}

$p = new LogProxy(new RealOrderService());
echo '1) 转发成功: ', $p->create(7), ' / 调用记录=', implode(',', $p->log), PHP_EOL;
try { $p->creat(7); } catch (Throwable $e) { // 代价 1：typo 到执行这行才炸，编辑期没有红线
    echo '2) 方法名打错: ', get_class($e), ' -> ', explode(' in ', $e->getMessage())[0], PHP_EOL; }
// 代价 2：LogProxy 没有 implements OrderService，满足不了类型声明
try { (static function (OrderService $s): void { echo '到了业务代码', PHP_EOL; })($p); } catch (Throwable $e) {
    echo '3) 传给要求 OrderService 的形参: ', get_class($e), ' -> ', explode(', called in', $e->getMessage())[0], PHP_EOL; }
// 代价 3：参数类型错要穿过 __call 打到最内层，报错指向 RealOrderService 而不是调用点
try { $p->create('x'); } catch (Throwable $e) {
    echo '4) create() 传了字符串: ', get_class($e), ' -> ', explode(', called in', $e->getMessage())[0], PHP_EOL; }
```

```text
1) 转发成功: order#7 created / 调用记录=create
2) 方法名打错: Error -> Call to undefined method RealOrderService::creat()
3) 传给要求 OrderService 的形参: TypeError -> {closure}(): Argument #1 ($s) must be of type OrderService, LogProxy given
4) create() 传了字符串: TypeError -> RealOrderService::create(): Argument #1 ($id) must be of type int, string given
```

四条代价，第一条是收益，后面三条全是实测：typo 从编辑期红线退化成运行时 `Error`；
**最致命的是第 3 行——纯 `__call` 代理没有 `implements`，进不了任何类型声明**，而代理模式的第一判据就是
"和目标同接口"，所以 `__call` 只能当"锦上添花的兜底转发"，当不了代理模式的正身（这条与
[装饰器模式.md](装饰器模式.md) 第四节"`__call` 省两行样板赔四件事"同源）。再补一条无法实测、属工具链常识的：
IDE 补全与静态分析看不见被 `__call` 转发的方法。

第二条路是**代码生成**：代理类在编译期/装配期就生成好源文件、由 autoload 加载，生成的类老老实实 `implements` 接口，
类型系统全额参与。ORM 的实体延迟加载代理、依赖注入容器为 `singleton` 服务生成的惰性代理，走的都是这条路
（**注：这是"框架常见做法"层面的推断，本篇未读任何框架源码、未实跑；思路是通用机制，不是对某个框架的实测结论**）。

真实场景四则，对号入座：延迟加载 ORM 关联 = 虚拟代理（第二节形状）；RPC client stub = 远程代理
（本地接口形状 + 底下序列化收发，超时/重试/幂等必须由代理层明说，别让调用方以为在调本地）；
鉴权包装 = 保护代理（第四节 `AuthProxy`）；只读视图 = 保护代理（第四节 `ReadOnlyDoc`，Go 版见第六节）。

## 六、Go 对照：同接口手写代理 + struct 嵌入省转发（实跑）

```go
package main

import "fmt"

type Repo interface {
	Find(id int) string
	Delete(id int) string
}

// 被代理的"重"对象：构造函数里打印，留时序证据
type realRepo struct{ rows map[int]string }

func newRealRepo() *realRepo {
	fmt.Println("[real] 构造：加载全量数据")
	return &realRepo{rows: map[int]string{1: "alice", 2: "bob"}}
}
func (r *realRepo) Find(id int) string   { return r.rows[id] }
func (r *realRepo) Delete(id int) string { delete(r.rows, id); return "deleted" }

// 虚拟代理：实现同一接口，第一次访问才 newRealRepo
type lazyProxy struct {
	real     *realRepo
	ctorRuns int
}

func (p *lazyProxy) ensure() *realRepo {
	if p.real == nil {
		fmt.Println("[proxy] 首次被访问，现在才构造")
		p.real = newRealRepo()
		p.ctorRuns++
	}
	return p.real
}
func (p *lazyProxy) Find(id int) string   { return p.ensure().Find(id) }
func (p *lazyProxy) Delete(id int) string { return p.ensure().Delete(id) }

// 保护代理（只读视图）：struct 嵌入 Repo 接口自动转发全部方法，只覆写 Delete 这一个
type readOnly struct{ Repo }

func (readOnly) Delete(int) string { return "403: 只读视图禁止删除" }

func main() {
	fmt.Println("--- 1. 只建代理，不访问 ---")
	p := &lazyProxy{}
	fmt.Println("上面没有 [real] 行 => 重对象还没被构造")
	fmt.Println("--- 2. 第一次 Find ---")
	fmt.Println(p.Find(1))
	fmt.Println("--- 3. 第二次 Find ---")
	fmt.Println(p.Find(2))
	fmt.Println("构造次数:", p.ctorRuns)
	var view Repo = readOnly{p}
	fmt.Println("嵌入转发的 Find:", view.Find(1), "/ 覆写的 Delete:", view.Delete(1))
}
```

```text
--- 1. 只建代理，不访问 ---
上面没有 [real] 行 => 重对象还没被构造
--- 2. 第一次 Find ---
[proxy] 首次被访问，现在才构造
[real] 构造：加载全量数据
alice
--- 3. 第二次 Find ---
bob
构造次数: 1
嵌入转发的 Find: alice / 覆写的 Delete: 403: 只读视图禁止删除
```

"未访问不构造"的时序与第二节 PHP 完全一致。Go 没有 `__call`，但**嵌入接口字段**把转发代码省到了零：
`readOnly` 只写一个 `Delete`，`Find` 靠嵌入的 `Repo` 自动提升（方法提升按深度算，显式方法赢过嵌入提升——
所以输出的 `Delete` 是 403 那行）。代价是接口换方法时要改所有手写代理，大项目一般靠 `go generate` 生成——思路级推断，本篇未实跑。

## 七、Java 对照：JDK 动态代理是语言自带的（JDK 8 实跑）

```java
import java.lang.reflect.InvocationHandler;
import java.lang.reflect.Method;
import java.lang.reflect.Proxy;
import java.util.ArrayList;
import java.util.List;

interface UserSvc {
    String find(int id);
    String save(String name);
}

class UserSvcImpl implements UserSvc {
    public String find(int id) { return "user#" + id; }
    public String save(String name) { return "saved:" + name; }
}

public class ProxyDemo {
    public static void main(String[] args) throws Exception {
        final UserSvc target = new UserSvcImpl();
        final List<String> log = new ArrayList<String>();
        // 代理类由 JVM 运行期生成：implements UserSvc，每个方法体都是回调 handler.invoke
        UserSvc proxy = (UserSvc) Proxy.newProxyInstance(UserSvc.class.getClassLoader(),
                new Class<?>[]{UserSvc.class}, new InvocationHandler() {
                    public Object invoke(Object proxy, Method m, Object[] a) throws Throwable {
                        log.add(m.getName());
                        if ("save".equals(m.getName())) {
                            throw new UnsupportedOperationException("403: save blocked by proxy");
                        }
                        return m.invoke(target, a);
                    }
                });
        System.out.println("find through proxy: " + proxy.find(1));
        try { proxy.save("bob"); } catch (Throwable e) {
            System.out.println("save blocked: " + e.getClass().getSimpleName());
        }
        System.out.println("invocation log: " + log);
        System.out.println("proxy class: " + proxy.getClass().getName());
        System.out.println("proxy instanceof UserSvc: " + (proxy instanceof UserSvc));
    }
}
```

```text
find through proxy: user#1
save blocked: UnsupportedOperationException
invocation log: [find, save]
proxy class: $Proxy0
proxy instanceof UserSvc: true
```

对照第五节的 PHP：`$Proxy0` 是 **JVM 运行期生成**的类，`instanceof UserSvc: true`——它真的实现了接口，
类型声明、多态全额可用；`[find, save]` 证明连"被拒绝的那次调用"也进了同一个 `invoke` 收口。
这正是 PHP 缺的那块能力，也是"Spring AOP 对接口用 JDK 代理"这类说法的机制底座（后半句是常识陈述，本篇未验框架）。

| | PHP 8.0 | Go 1.26 | Java 8 |
| --- | --- | --- | --- |
| 运行期生成代理类 | 无此机制 | 无（编译期嵌入 / `go generate`） | `Proxy.newProxyInstance`（上节实跑） |
| 满足接口类型声明 | 手写 `implements`；纯 `__call` 实测报 TypeError | 手写方法集，编译期断言 | 自动 implements 指定接口 |
| 少写转发的办法 | `__call`（代价见第五节） | 嵌入接口字段（第六节实测） | `invoke` 一个方法兜所有调用 |

## 八、落点：四个模式都在包一层，改的各不相同

| 模式 | 包一层在干什么 | 包完接口长什么样 | 调用方动机 |
| --- | --- | --- | --- |
| 代理 | **控访问**：时机/次数/放行 | 同一接口（只读视图故意收窄） | "什么时候、能不能"碰真对象 |
| 装饰器 | **加行为** | 同一接口 | 功能不变，多加一层日志/压缩/重试 |
| 适配器 | **改接口** | 和目标是**不同**接口（做翻译） | 老的形状不符合调用方要的 |
| 外观 | **收接口面** | 新开一个小接口 | 一次调用编排多个子系统 |

一句话判型：**看包的那层"干的事"——管时机和权限是代理，加功能是装饰器，翻签名是适配器，多合一收口是外观。**

## 校验口径

- 二~五节共 4 段 PHP 本机实跑：`D:\phpstudy_pro\Extensions\php\php8.0.2nts\php.exe`（PHP 8.0.2 / Zend 4.0.2，CLI），
  逐段 `php -l` 通过后执行，`text` 块是原始 stdout。**语法门槛 8.0**：`__call(): mixed` 需 8.0，
  类型化属性与构造器属性提升需 7.4+；未用 `readonly`/`enum`（8.1+，本机也没有）。
- 第六节 Go：临时模块（`module x` + `go 1.26`，实际 go1.26.5）`gofmt` 干净、`go vet ./...` + `go run .` 通过。
  第七节 Java：`jdk1.8.0_321`，`javac -encoding UTF-8` + `java -Dfile.encoding=UTF-8` 通过，纯 JDK 8 语法（匿名内部类，无 lambda）。
- **三处标了"推断/常见做法"、本篇未实跑的点**：框架代码生成代理类（第五节 ORM/DI 容器例子）、
  `go generate` 生成代理（第六节末）、Spring AOP 用 JDK 代理（第七节）——都只在"机制成立"层面陈述，不指向具体实现。
- 无外部依赖、无真实数据库（DSN 不指向可用实例），全文无耗时/吞吐数字：只有构造次数、回源次数、调用日志，都来自上面的实跑。

## 面试官会追问什么

- **代理和装饰器都套同一接口、都构造注入，怎么分？** → 看动机：控制访问（时机/次数/放行）是代理，加行为是装饰器（第八节表）。
- **PHP 能实现 Java 那种动态代理吗？** → 不能。运行期造不出 `implements` 接口的类型；`__call` 连类型声明都过不了（第五节实测 TypeError），只剩代码生成一条路。
- **缓存代理和 Redis 什么关系？** → 不是同一层。php-fpm 下代理对象里的 memo 只活一次请求（第三节），跨请求缓存是独立进程的架构组件。
- **虚拟代理能治 N+1 吗？** → 治不了。延迟加载让"没用的关联"零成本，但 100 次访问就是 100 次回源；N+1 要靠 eager load / batch fetch（通用结论，本篇未实测 ORM）。
- **只读视图和 `readonly` 属性是一回事吗？** → 不是。只读视图是**对象级**收面（第四节实测，方法从类型里消失）；`readonly`（PHP 8.1）是**属性级**写入限制，本篇代码未用到。
- **远程代理最容易出的事故是什么？** → 调用方把 stub 当本地对象：没设超时、重试不幂等、以为异常只有业务错误没有断连（第五节"别让调用方忘了网络"）。
