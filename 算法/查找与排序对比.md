## Q1. 常用查找算法与数据结构怎么对比？

因为查找算法的时间复杂度和数据的结构息息相关，所以这里一起介绍。

| 查找算法 / 数据结构 | 时间复杂度 | 稳定性 | 元素要求 | 说明 |
|---|---|---|---|---|
| 哈希表查找 | O(1) | 稳定 | 无序 | 数据量越大越不稳定，可用多次哈希提高效率（参考布隆过滤器）。可用作索引，MySQL 中的一种索引结构就是哈希 |
| 顺序查找 | O(n) | 不稳定 | 无序或有序 | 按顺序比较每个元素，直到找到关键字为止 |
| 二分查找 | O(log n) | 稳定 | 有序 | 也称折半查找。当待搜索的集合是**相对静态的有序数据集**时，二分查找是较好的选择 |
| 插值查找 | O(log₂(log₂n)) | 稳定 | 有序 | 基于二分查找算法的改进，可提高查找效率（适用于分布均匀的数据） |
| 斐波那契查找 | O(log₂n) | 稳定 | 有序 | 二分查找的一种提升算法，只用加减法定位中点 |
| 分块查找 | O(√n) ⚠️ | 较稳定 | 有序 | 又称索引顺序查找，是折半查找和顺序查找的改进：块间有序、块内可无序。⚠️ 原笔记记为 O(n²)，实际平均查找长度为 (b+s)/2+1，b=s=√n 时最优即 O(√n) |
| 二叉树 | O(log n) | 一般稳定 | 树形 | 看树的深度和偏移量，有些树太高，已退化成线型 |
| 平衡二叉树（AVL） | O(log n) | 稳定 | 树形 | 二叉树的改良版，所有节点的左右子树高度差不超过 1。**适合插入与删除次数比较少、但查找多**的情况 |
| 红黑树 | O(log n) | 稳定 | 树形 | 弱平衡二叉树。**对于搜索、插入、删除操作都较多**的情况，可用红黑树 |
| B-树（B-Tree） | O(log n) | 稳定 | 树形 | 读作 "B 树"，`-` 只是一个连接符，不是"B 减树"。多路平衡查找树，树形不一定是二叉的 |
| B+树（B+Tree） | O(log n) | 稳定 | 树形 | B 树的改良版，数据只在叶子节点且叶子间有链表。MySQL 中的另一种索引结构就是 B+Tree |

> ⚠️ **此处的"稳定性"指查找结果是否稳定可预测**，与排序算法的"稳定性"（相等元素相对顺序是否保持）不是同一个概念。

**查找算法怎么选**：

| 数据特征 | 推荐 |
|---|---|
| 无序、等值查找、数据量小 | 顺序查找 |
| 静态有序、随机访问 | 二分查找 |
| 动态、频繁增删 + 需有序 | 红黑树 |
| 查询远多于增删 | AVL |
| 磁盘存储、范围查询 | B+ 树 |
| 纯等值查找、内存中 | 哈希表 |

## Q2. 常用排序算法怎么对比？

| 排序算法 | 平均情况 | 最坏情况 | 最好情况 | 空间复杂度 | 稳定性 | 复杂性 |
|---|---|---|---|---|---|---|
| 冒泡排序 | O(n²) | O(n²) | O(n) | O(1) | 稳定 | 简单 |
| 快速排序 | O(n log n) | O(n²) | O(n log n) | O(log n) | **不稳定** | 较复杂 |
| 插入排序 | O(n²) | O(n²) | O(n) | O(1) | 稳定 | 简单 |
| 希尔排序 | O(n log n) | O(n log² n) | O(n log² n) | O(1) | **不稳定** | 较复杂 |
| 选择排序 | O(n²) | O(n²) | O(n²) | O(1) | **不稳定** | 简单 |
| 归并排序 | O(n log n) | O(n log n) | O(n log n) | O(n) | 稳定 | 简单 |
| 堆排序 | O(n log n) | O(n log n) | O(n log n) | O(1) | **不稳定** | 较复杂 |
| 计数排序 | O(n + k) | O(n + k) | O(n) | O(k) | 稳定 | 简单 |
| 桶排序 | O(n + k) | O(n²) | O(n + k) | O(n + k) | 稳定 | 较复杂 |
| 基数排序 | O(n × k) | O(n × k) | O(n × k) | O(n + k) | 稳定 | 复杂 |

**注**：

- `k` 表示数据范围或桶的数量；快速排序的空间复杂度 O(log n) 指递归调用栈深度
- **稳定性定义**：排序前后**相等元素的相对次序是否保持不变**
  - ✅ 稳定：冒泡、插入、归并、计数、桶、基数
  - ❌ 不稳定：快速、希尔、选择、堆
- 记忆口诀：**"快希选堆"不稳定**（快排、希尔、选择、堆排）

## Q3. 工程上怎么选查找与排序算法？

| 场景 | 推荐 | 原因 |
|---|---|---|
| 数据量小、基本有序 | 插入排序 | 近乎 O(n)，常数小 |
| 要求稳定 + 数据量大 | 归并排序 | O(n log n) 且稳定，代价是 O(n) 额外空间 |
| 追求平均性能、内存敏感 | 快速排序 | 平均 O(n log n)、原地排序，常数最优 |
| 只取前 K 个极值 | 堆 / 优先队列 | 维护大小 K 的堆即可，O(n log k) |
| 数据范围有限（年龄、分数、状态） | 计数排序 / 桶排序 | 可做到 O(n) 线性时间 |
| 定长多关键字（手机号、字符串） | 基数排序 | 按位分桶，无需比较 |
| 库函数优先 | `sort` / `slices.Sort`（Go）、`Arrays.sort`（Java） | 已是高度优化的混合排序（如 introsort / Timsort），别自己造 |

## Q4. 标准库为什么各选不同的排序？Top-K 的堆怎么选？

**没有"最好的排序算法"，只有"这组约束下的最优组合"**。约束只有四条：要不要稳定 / 能不能接受最坏退化 / 元素可否随机访问（数组 or 链表）/ 额外空间预算。

**混合策略（introsort 内省排序）的三段设计**——这是"工程上为什么不用纯快排"的标准答案：

| 触发条件 | 切换到 | 为什么 |
|---|---|---|
| 子数组很小（阈值经验值，几十到上百） | **插入排序** | 常数极小、顺序访存 cache 友好、无递归开销；小 n 时 O(n²) 反而更快 |
| 递归深度超过上限（约 2⌊log n⌋） | **堆排序** | 堆排最坏有保证 O(n log n)，专门用来兜"划分一直不均"的退化 |
| 划分前选 pivot | 三数取中 / 随机 | 从源头降低退化概率 |
| 大量相等元素 | 三路划分 | 把等于 pivot 的一整段直接排除，避免"全等元素退化成 n²" |

**语言/场景选择的对照**：

| 实现 | 用什么 | 为什么选它 |
|---|---|---|
| C++ `std::sort` | introsort（快排系） | 元素可随机访问、不要求稳定、只要平均最快 |
| Java `Arrays.sort(Object[])` | Timsort（归并 + 插入，利用已有序段） | 对象排序**要求稳定**，且真实数据常"基本有序" |
| Java `Arrays.sort(int[])` | 双轴快排 | 基本类型无需稳定，追求常数 |
| Python `sorted` | Timsort | 同样要稳定，且面向"现实里近乎有序"的数据 |
| Go `sort` / `slices` | 快排系 + 小数据插入（新版本引入更多模式识别） | 通用库；**具体策略以官方源码为准** |
| 外部排序（文件 > 内存） | **归并** | 只需顺序读写，稳定且 I/O 次数可控 |
| 值域受限（年龄、状态、定长字符串） | **计数 / 基数** | 用 O(n) 线性时间换掉"比较"这个前提 |

> ⚠️ 基数/计数的隐含前提：**k 不能太大**（值域远大于 n 时内存与初始化桶的成本会吞掉收益），且要求能按位/按值分桶（浮点、变长字符串需要先做序保持的转换）。

**Top-K：为什么用大小为 K 的堆，而不是全排序** ⭐

| 方案 | 时间 | 内存 | 能否流式（数据一条条来、装不下） | 拿到的结果 |
|---|---|---|---|---|
| 全排序取前 K | O(n log n) | O(n)，必须装下全部 | ❌ | 前 K 且内部有序 |
| **大小为 K 的小顶堆** | **O(n log k)** | **O(k)** | ✅ 边来边维护 | 前 K，内部无序（要再排一次 O(k log k)） |
| 快速选择（第 K 大） | 平均 O(n)、最坏 O(n²) | O(1)~O(log n) 栈 | ❌ 需随机访问全量 | 前 K 的集合，无序 |
| 直接遍历（K = 1） | O(n) | O(1) | ✅ | 单个极值 |

- ⭐ 三个真正的理由：**① K ≪ n 时 log k 远小于 log n；② 内存只占 K，海量/数据流场景这是能不能做的问题而不是快慢问题；③ 结果可增量输出**（每来一条就能知道当前 Top-K）。
- **为什么是小顶堆而不是大根堆**：堆顶要当"门槛"用。小顶堆的堆顶是**当前 K 个候选里最小的那个**（即第 K 大），新元素只需和它比一次，更大就换掉堆顶并下沉——判断成本 O(1)，更新成本 O(log k)。用大根堆的话，堆顶是最大值，"够不够格进来"这个判断就得把 K 个元素扫一遍。
- ⚠️ 什么时候**不该用堆**：K 接近 n（直接全排序更简单）；需要严格全局第 K 大且内存够（快速选择平均更快）；K=1（一个变量遍历即可，上堆纯属浪费）。
- 海量数据分片场景的常见组合见 [数据结构.md](数据结构.md) 的堆一节与 [海量数据存储设计.md](../分布式/系统设计/海量数据存储设计.md)（先分片各取 Top-K，再归并）。

## 面试官会追问什么

- **快排最坏为什么是 O(n²)？怎么避免？** → 每次划分都取到极值（已有序 + 固定取首元素）时退化；用**随机化取 pivot** 或三数取中即可把最坏概率降到极低。
- **为什么实际排序库不用纯快排？** → 快排在小数组上常数反而大、且最坏退化；实际实现是混合策略（小数组用插入排序、深层递归转堆排序），如 introsort（见 Q4）。
- **快排和归并都是 O(n log n)，为什么实际常常快排更快？** → Big-O 相同不等于成本相同：快排原地交换 + 顺序扫（cache 友好）、归并要额外数组和拷贝；常数与局部性差了数量级级别的意义。
- **Top-K 为什么用大小为 K 的小顶堆？堆顶代表什么？** → 堆顶是"当前第 K 大"的门槛，新元素只有比它大才有资格进来。全排序要装下整个数据集，堆只占 K，且天然支持数据流（见 Q4）。
- **数据已经基本有序时该用哪种排序？** → 插入排序 / Timsort 这类**自适应**算法接近 O(n)；库函数（Java 的 Timsort、Go 的 pdqsort）通常已带这个优化，自己手写快排反而会丢掉它。
