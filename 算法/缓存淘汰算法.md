## Q1. 缓存淘汰算法有哪些？LRU 的缺陷和 LFU 的代价是什么？

当缓存空间达到上限时，必须挑一些数据移除以腾出空间——挑谁走，就是淘汰算法要解决的问题。

### 2.1 LRU（Least Recently Used，最近最少使用）

**核心假设**：**最近被访问过的数据，将来被再次访问的概率更高**。因此淘汰**最久未被访问**的那一项。

**实现方式——哈希表 + 双向链表**（两者配合才能做到 O(1)）：

| 结构 | 作用 |
|---|---|
| **哈希表** | 存 `key → 链表节点`，使查找为 O(1) |
| **双向链表** | 维护访问顺序：**头部是最近使用**，**尾部是最久未使用** |

**操作过程**：

- `get(key)`：命中则把该节点**移动到链表头部**；未命中返回空
- `put(key, value)`：key 已存在则更新值并移到头部；不存在则新建节点插入头部，若超出容量则**删除尾部节点**

```
头部（最近使用） ⇄ ... ⇄ 尾部（最久未使用 → 优先淘汰）
        ↑ 访问后移到头部            ↑ 容量满时删除这个
```

> ℹ️ 手写 LRU 的关键点：**为什么必须用双向链表？** 因为淘汰尾部节点、把节点移到头部都需要 O(1) 地拿到前驱节点，单链表做不到。
> 语言内置方案：Java 的 `LinkedHashMap(16, 0.75f, true)` 重写 `removeEldestEntry` 即可；Go 需自己用 `container/list` + `map` 组合。

**缺点——缓存污染**：

- **偶发的批量扫描**（如全表遍历、定时任务扫全部 key）会把热点数据全部挤出去，导致命中率骤降
- 这类"只访问一次就不再访问"的数据本不该进缓存，却因为"最近被访问"而被保留

**改进变体**：

| 变体 | 思路 | 解决的问题 |
|---|---|---|
| **LRU-K** | 记录最近 **K 次**访问时间，只有访问达到 K 次才纳入缓存 | 过滤"只访问一次"的偶发数据 |
| **2Q** | 用两个队列（FIFO 队列 + LRU 队列）分级：新数据先进 FIFO，被二次访问才升入 LRU | 同上，实现更简单 |
| **LFU** | 淘汰**访问频率最低**的 | 更适合"热点长期稳定"的场景；但对新数据不友好，且需要频次计数 |
| **FIFO / 随机** | 按进入顺序或随机淘汰 | 实现最简单，命中率最差 |

### 2.2 淘汰算法对比

| 算法 | 淘汰依据 | 实现复杂度 | 优点 | 缺点 |
|---|---|---|---|---|
| **LRU** | 最久未访问 | 中（哈希表 + 双向链表） | 符合时间局部性，实现成熟 | 批量扫描会污染缓存 |
| **LFU** | 访问频率最低 | 中高（需维护计数） | 抗扫描，热点稳定时命中率高 | 新数据易被饿死、计数需衰减 |
| **FIFO** | 最早进入 | 低 | 简单 | 不考虑访问模式，命中率低 |
| **随机** | 任意 | 极低 | 开销最小 | 效果不可控 |

### 2.3 Redis 的近似 LRU ⭐

Redis 为了节省内存和 CPU，**没有实现严格的双向链表 LRU**，而是采用**近似 LRU**：

- 每个对象记录一个 **`lru` 时间戳字段**（最后一次访问时间）
- 淘汰时**随机采样 N 个 key**（由 `maxmemory-samples` 控制，默认 5），从中挑出最久未使用的淘汰
- 采样数量越大越接近真实 LRU，但 CPU 开销也越大

相关配置：`maxmemory-policy` 可取 `allkeys-lru` / `volatile-lru` / `allkeys-lfu` / `volatile-ttl` 等。

> ⭐ 这也是"为什么 Redis 的 LRU 不精确"这个面试问题的答案：**用采样换性能与内存**。

### 2.4 LRU 的 O(1) 是怎么凑出来的（示意伪代码）

**哈希表负责"找到节点"，双向链表负责"维持新旧顺序"——两个都必须，缺一个就退化**：只有哈希表则无法知道谁最久未用；只有链表则找 key 要 O(n)。

```text

get(key):
  node = map.get(key)
  if node == null: return MISS            # 未命中：交给上层回源
  list.moveToHead(node)                   # ⚠️ 命中也要提升，否则"最近使用"信息丢失
  return node.value

put(key, val):
  if map.contains(key): node.value = val; list.moveToHead(node)
  else:
    node = new Node(key, val)
    list.addFirst(node); map[key] = node
    if list.size > capacity:
      tail = list.removeLast()            # 尾巴就是最久未用
      map.remove(tail.key)                # ⚠️ 两边必须同步删，否则节点泄漏 + 查找命中已废弃数据
```

> 示意伪代码，只表达"两个结构如何配合"，不是任何语言的落地实现。

**两个只有写出来才会注意到的点**（"为什么必须双向"见 2.1 的说明）：

1. **"每次 get 都改结构"才是 LRU 在并发下慢的根因**：读操作变成了写操作（要移动节点），于是读也要加锁。工程缓解手段：**分段 LRU**（按 key 哈希分片，降低锁竞争）、**采样近似**（Redis 那条路）、**达到访问阈值才提升**（省掉大量无谓的链表移动）。
2. **容量口径**：淘汰判据要按"实际占用"算（value 大小、序列化后字节数），只按条目数算会被大 key 打穿（见 [缓存问题与方案.md](../数据存储/redis/缓存问题与方案.md) 的大 key 一节）。

### 2.5 ⭐ LRU 的两个致命缺陷（把"缓存污染"讲透）

2.1 的"缺点——缓存污染"里说了这事，这里要讲清**为什么必然中招**：LRU 手里只有一个信号——**最后一次访问的时间**。冷数据被扫一次，就获得和真热点完全同等的身份；下一次淘汰时它排在头部，谁都可能被换掉。

1. **一次性大扫描**：全表遍历/定时任务扫完所有 key 后，链表尾部（最久未用）恰好是原本的热点 → 命中率断崖，且回源洪峰会二次冲击数据库。补救都要引入**第二个信号**："是否被访问第二次"（2Q / LRU-K / W-TinyLFU 的准入判断）或"访问了多少次"（LFU）。
2. **热点被挤出 + 时间局部性假设本身失效**的两类负载：① **循环扫描**（每个 key 每隔 N 次才回来一次，N 略大于容量）——LRU 表现最差，因为每次轮到它都刚好被踢掉；② **长尾均匀访问**（每个 key 访问概率相同）——命中率上限由容量决定，任何淘汰算法都救不了，此时该讨论扩容而不是换算法。
3. **成本盲区**（第三条，最常被追问漏）：LRU 只看"最近"，不看"重新获取要花多少钱"。回源要跨 region 的远端数据和顺手就能取到的本地数据，在它眼里完全等价。工程做法是按 **性价比 = 命中收益 / 重新获取成本** 加权淘汰，而不是纯按时间。

> ⭐ 一句话总结：**"最久没被用" ≠ "最没用"**。LRU 的全部问题都来自它只用了一个信号。
>
> 数据库里的落地例子：InnoDB 的缓冲池没有用纯 LRU，而是把链表分成 young/old 两段、**新页先插在 old 段靠前的位置**，只有"在 old 段停留超过一段时间后又被访问"才晋升到 young 段——本质就是给 LRU 补上第二个信号，专门抗批量扫描（阈值参数以官方文档为准）。

### 2.6 LFU 的 O(1) 思路与它的新问题

**思路**：淘汰"访问频率最低"的——直接回应 2.5 的痛点（扫描一次不算数，反复访问才算热点）。朴素实现（map + 按频次排序/堆）淘汰是 O(log n)，且要处理一堆并列。

**O(1) 的经典做法：频率分桶 + 每个桶内一条双向链表**

```text

freq -> 该频率下的节点双向链表（链表内部按 LRU 排：尾部最久未用）
minFreq -> 当前最小频率桶的指针
命中：把节点从 freq 桶摘出、挂到 freq+1 桶头部；原桶空了且它等于 minFreq 则 minFreq++
淘汰：只在 minFreq 桶的尾部动手（O(1)），新插入的数据频率=1，天然落在 minFreq 桶
```

> 示意伪代码，表达"为什么能全 O(1)"：因为淘汰永远发生在 minFreq 桶，不需要遍历比较频次。
>
> ⚠️ 关键推论要能说出来：**新数据一进来就是"最低频"，所以最先被淘汰**——这是 LFU 对新热点不友好的结构性原因（需要给新数据初始频率或准入豁免）。

**LFU 换来的三个新问题**：

| 问题 | 表现 | 常见解法 |
|---|---|---|
| **频率历史粘滞** | 老热点攒了高频后就赖着不走，负载漂移后新热点进不来 | **衰减 / aging**：周期性把计数整体右移（近似除以 2）或只统计滑动窗口内的访问 |
| **计数本身占内存** | 每个 key 一个整数，key 基数大时很可观 | 概率计数（**count-min sketch**，见 2.8），用固定小内存换"够用的估计值" |
| **同频次并列** | 无法区分谁更该淘汰 | 桶内再用 LRU 兜底（就是上面那套分桶结构） |

> Redis 的 LFU 策略同样是"近似计数 + 衰减"路线（`lfu-log-factor` / `lfu-decay-time`，**具体语义以官方文档为准**）。

### 2.7 Clock（第二次机会）与 CLOCK-Pro：它们站在哪

| 算法 | 一句话 | 换来什么 | 代价 |
|---|---|---|---|
| **Clock / 最近未用（NRU）** | 淘汰队列是一个**环**，每个条目一个"引用位"；指针扫过时引用位为 1 就清 0 放过（给第二次机会），直到遇到 0 才淘汰 | **不需要移动节点**——把 move-to-head 换成"置一位"，读操作几乎零结构开销，常数与并发都更友好 | 近似程度不如 LRU；最坏要扫一整圈 |
| **第二次机会（改进版时钟）** | 链表单指针 + 引用位，同一思想的链式写法 | 同上 | 同上 |
| **CLOCK-Pro** | Clock 路线上的现代代表：按"冷热 / 新旧"把页面分几类，并为**已淘汰页**保留极小的元数据（ghost 队列）来记住"它最近被用过几次"，据此决定新页的可信度 | 用接近 O(1) 的时间与很小的额外内存，拿到明显好于纯 LRU 的表现，尤其**抗扫描** | 参数多、行为依赖负载特征，调优门槛高 |

> ⚠️ CLOCK-Pro 的分类规则与参数细节超出笔记范围，**以论文与官方文档为准**。定位记一句话就行：**它是"LRU 的低成本近似"这一条线，和"引入第二信号"的那条线（2Q / W-TinyLFU）是两条不同的路线。**

### 2.8 ⭐ W-TinyLFU（Caffeine 的骨架：只讲结构与取舍）

**目标很明确：同时要 LRU 的"跟得上热点变化"和 LFU 的"抗扫描"，还不付 LFU 的计数内存。** 结构是"一个小窗口 + 分段的主体 + 一道准入门"：

| 组成 | 作用 | 解决谁的毛病 |
|---|---|---|
| **window（占比很小的一部分容量）用小 LRU** | 所有新数据先进这里，被再次访问才有机会进 main | 补上 LFU 缺的"新热点能进来" |
| **main 分两段：protected（大头）+ probation（小头）** | 从 window 淘汰出来的进 probation；probation 再被访问才升到 protected；**protected 里的先降到 probation，不直接被淘汰** | 给老热点一道"第二次机会"，避免抖动 |
| **准入判断（admission）＝ TinyLFU** | window 溢出的候选者 vs probation 的淘汰候选者，**比谁的估计频率高**，输的一方离开缓存 | 抗扫描的核心：一次性冷数据频率低，直接挡在门外 |
| **count-min sketch 估计频率** | 几个小数组 + k 个哈希，用固定内存给任意 key 一个频率估计 | 精确计数器要 per-key 内存，key 一多就吃不消 |

**为什么"估计器有假阳性"却够用** ⭐：count-min sketch **只会高估、不会低估**（估计值 ≥ 真实值），而这里只拿它做"两个候选比大小"，不需要精确值——**这是"近似结构"在淘汰场景的典型用法：只要误差方向不致命，就能用极小内存换掉一个字典。**

**必须一起说的代价**：① 各段比例、准入阈值都是随负载变化的旋钮，没有普适值；② 频率要**周期衰减**，否则又回到 LFU 的历史粘滞；③ 实现与调试复杂度显著高于 LRU，出问题不如 LRU 好解释。

> ⚠️ 具体的分段比例、阈值与衰减实现**以 Caffeine 官方文档/源码为准**。本地缓存与 Redis 的两级缓存取舍（Caffeine 作 L1）见 [缓存选型与容量.md](../数据存储/redis/缓存选型与容量.md) 的"Redis 缓存和本地缓存该如何取舍"一节。

## Q2. WiredTiger 是怎么把块压缩与页淘汰组合起来的？

WiredTiger 是一个高性能、可扩展的数据库存储引擎，用于高效地在内存和磁盘上存储键值对、文档和图形数据。它为处理大量数据集而构建，尤其擅长提供低延迟和高吞吐量的服务。因优异的性能表现，它被广泛应用于多种数据库系统，最著名的是作为 **MongoDB 的默认存储引擎**。

**WiredTiger 如何组合使用本文件的算法**：

| 机制 | 采用的算法 | 说明 |
|---|---|---|
| **集合数据压缩** | **块压缩（默认 Snappy）** | 页面写入磁盘时压缩，从磁盘读入缓存时解压 |
| **索引压缩** | **前缀压缩（prefix compression）** | 索引键往往有共同前缀，去掉重复前缀可显著减小体积 |
| **缓存淘汰** | **LRU** | 常态下由后台 `evict` 线程负责淘汰页面 |

**淘汰的细节**：常态下由后台的 evict 线程负责淘汰页面；**如果内存非常紧张，用户线程也会加入缓存淘汰的工作**，此时表现为读写请求有一定阻塞。

> WiredTiger 采用的大多是以**空间换时间**的做法。
> MongoDB 默认采用 WiredTiger 引擎，所以 **MongoDB 相对较吃内存**。

### 页级压缩与缓存淘汰是**联动**的（这两节算法在这里咬合）

- 缓存里放的是**解压后的页**（`cacheSizeGB` 的口径是解压后数据大小，**以官方文档为准**）→ 结论：**压缩省的是磁盘和 IO，不省缓存内存**。想靠"开压缩"来省内存预算是常见误解。
- 淘汰的粒度是"一整页"，所以热点访问粒度 = 页大小：页越大 → 压缩比越好，但读放大和"为一个热行留一整页冷数据"的浪费也越大。这正好接上 1.5 那条"块大小是压缩比 vs 随机读放大的旋钮"。
- 于是"内存非常紧张 → 用户线程一起淘汰 → 请求阻塞"这条链上，还可能叠加**解压所费的 CPU**：读写路径同时被 IO、CPU、缓存淘汰三方拉扯。判断顺序也因此是三步：先看瓶颈在 IO 还是 CPU，再决定要不要开压缩、开多大块、给缓存多少预算。

> MongoDB 侧的引擎与内存参数见 [MongoDB.md](../数据存储/MongoDB.md)。

## 面试官会追问什么

- **手写 LRU 为什么必须用双向链表？** → 淘汰尾节点与移动节点到头部都要 O(1) 访问前驱，单链表需要 O(n) 遍历。
- **LRU 有什么致命缺陷？** → 批量扫描造成**缓存污染**，热点数据被挤出；解决方案是 LRU-K / 2Q，或在业务上做隔离。
- **Redis 的 LRU 精确吗？** → 不精确，是**采样近似**（默认采样 5 个），用少量精度换内存和 CPU。
- **LRU 和 LFU 怎么选？** → 热点随时间变化明显（如新闻热点）用 LRU；热点长期稳定（如配置数据）用 LFU。
- **LFU 怎么做到全 O(1) 淘汰？** → 频率分桶、每桶一条按 LRU 排的双向链表，并维护 `minFreq`；淘汰永远只碰 minFreq 桶的尾部，不需要比较频次。
- **LFU 为什么"饿死新数据"、又为什么赖着老热点？** → 新数据初始频率最低，正好落在被淘汰的那一桶；老热点的历史计数只增不减，负载漂移后仍占着位置——所以必须配**衰减**和**准入豁免**。
- **count-min sketch 有误差，为什么还敢拿它做淘汰决策？** → 它**只会高估不会低估**，而这里只需要"两个候选比大小"；误差方向不致命时，就能用固定小内存换掉一个 per-key 计数器字典。
- **W-TinyLFU 凭什么同时抗扫描和跟得上热点？** → 小窗口 LRU 保证新数据一定进得来（跟得上热点），进 main 时要和淘汰候选比估计频率（挡掉只访问一次的扫描流量）；再靠 protected/probation 两段给老热点第二次机会。
- **开了压缩能少用点缓存内存吗？** → 不能想当然：像 WiredTiger 这类引擎缓存里放的是**解压后的页**，压缩省磁盘与 IO，缓存占用按解压后算（口径以官方文档为准）。
