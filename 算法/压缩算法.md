## Q1. 压缩算法有哪些？块压缩和流压缩该怎么选？

### 1.1 Snappy

Google 开源（2011）的快速压缩库，属于**字节级、基于字典匹配的 LZ 系列算法**，设计目标是**速度优先**而非极致压缩比。

| 维度 | 说明 |
|---|---|
| **核心思想** | 在数据的**滑动窗口**内查找重复字节序列，用「长度 + 回溯距离」的短标记替换重复内容 |
| **压缩比** | 约 1.5 ~ 1.7 倍（低于 zlib 的 2.5 ~ 3 倍） |
| **速度** | 解压速度极快（通常 250 MB/s 以上，远快于 zlib），**压缩/解压速度约比 zlib 快一个数量级** |
| **定位** | 典型的**用压缩比换速度**：压缩比一般，但 CPU 开销极低 |
| **优点** | 无外部依赖、实现简单、解压几乎不分配内存、稳定 |
| **典型应用** | **MongoDB（WiredTiger 默认压缩）**、RocksDB、Kafka、Hadoop、LevelDB、Cassandra |

> ⭐ 一句话记忆：**Snappy 不是为"压得小"，而是为"压得快、解得更快"**——
> 数据库场景下压缩发生在写盘路径上，CPU 成本直接影响吞吐，所以选择速度优先。

### 1.2 LZW

LZW（Lempel-Ziv-Welch）是 1984 年由 Terry Welch 在 **LZ78** 基础上改进的**字典编码**算法，属于**无损压缩**。

**核心思想——边压缩边建字典**：

1. 初始化字典，包含所有可能的**单字符**（如 256 个 ASCII 字符各占一个码字）
2. 从输入流中读字符，尽可能匹配字典中**最长的已有前缀**
3. 输出该前缀的**码字**，并把「该前缀 + 下一个字符」作为**新词条加入字典**
4. 重复直到输入结束

**关键特性**：

| 特性 | 说明 |
|---|---|
| **字典是动态生成的** | 不需要预先知道数据的统计特性，也不需要额外传输字典 |
| **解压可同步重建字典** | 解压时按同样的规则边解码边建字典，因此**只需传输码字流**，这是 LZW 相比 LZ77 的最大便利 |
| **码字长度递增** | 字典从 9 位码字开始，随词条增加扩展到 10、11、12 位；字典满后需停止新增词条 |
| **适合的数据** | 重复模式多的数据（文本、图标、二值图像）压缩效果好；随机数据几乎无收益 |

**与 LZ 家族其他成员的区别**：

| 算法 | 做法 | 是否需要额外传输字典 |
|---|---|---|
| **LZ77** | 滑动窗口内查找重复，输出「距离 + 长度」 | 否（窗口内自包含） |
| **LZ78** | 显式构建词条字典 | 否（但字典构建规则需一致） |
| **LZW** | LZ78 变体，字典预置单字符、解码时可同步重建 | 否 |

**典型应用**：GIF（图像）、TIFF、Unix `compress` 命令、早期 PDF 与 PostScript。
⚠️ LZW 曾长期受专利（Unisys）困扰，这正是 GIF 后来被 PNG 取代的重要原因之一；相关专利已于 2003—2004 年陆续到期。

### 1.3 压缩算法选型

| 算法 | 压缩比 | 速度 | 特点 | 适用 |
|---|---|---|---|---|
| **Snappy** | 中低 | **极快** | 速度优先，CPU 开销低 | 数据库/消息队列的在线压缩 |
| **LZW** | 中 | 中 | 字典编码，无需传字典 | 图像格式、历史遗留格式 |
| **zlib（DEFLATE）** | 中高 | 中 | 兼容性最好，HTTP `Content-Encoding` 标配 | 通用网络传输 |
| **gzip** | 中高 | 中 | zlib 的文件封装，命令行常用 | 日志归档、离线压缩 |
| **Zstandard（zstd）** | 高 | 快 | 压缩比与速度可调，现代首选 | 新一代存储/传输 |
| **LZ4** | 中低 | **极快** | 与 Snappy 定位接近 | 内存压缩、实时流 |

### 1.4 Snappy / LZ4 / zstd 的定位差异（不谈倍数，只谈"为什么选它"）

三者都是 **LZ 系的字节匹配压缩**，差别在"愿意为压缩比付出多少 CPU"这一个轴上：

| 维度 | Snappy | LZ4 | zstd（Zstandard） |
|---|---|---|---|
| **设计取向** | 速度优先、压缩比让路 | 与 Snappy 同区间，实现更小、解压路径极短 | **可调级别**：低级别接近 LZ4，高级别追 zlib 以上的压缩比 |
| **小数据（几 KB 级）** | 冷启动字典建不起来，收益明显缩水 | 同上 | ✅ 可用**训练字典**（先拿样本喂出共享字典再压），小 payload 场景的决定性优势 |
| **可调旋钮** | 基本没有 | 加速/级别参数 | 级别 + 字典 + 多线程，最丰富 |
| **典型取位** | "写盘路径上不能慢"的默认值 | 嵌入式 / 内存内压缩 / 需要极小依赖 | 新一代存储与传输的通用首选 |

> ⚠️ **字典模式是否可用、API 怎么命名，各库差异较大，以官方文档/源码为准。** 但要能讲出结论：**数据块越小，"共享字典"这件事越值钱**——因为 LZ 的收益全来自"在窗口里找到重复"，块太短窗口就建不满。

### 1.5 ⭐ 块压缩 vs 流压缩：数据库页级压缩为什么只能选"块"

| | 块/独立单元压缩 | 流压缩 |
|---|---|---|
| **单元** | 每个块/页**独立**压缩，互不依赖 | 一整条流共用一个滑动窗口/字典状态 |
| **随机解压** | ✅ 想读第 N 块就只解第 N 块 | ❌ 通常必须从头解到那里 |
| **损坏影响** | 只坏这一块 | 后续内容可能整段解不出来 |
| **压缩比** | 偏低（窗口被切成小块，跨块重复用不上） | 偏高（窗口连续累积） |
| **代表** | Snappy/LZ4 的 block API、zstd 的单帧模式、数据库页压缩 | gzip 这类文件/流式封装 |

**推导**：数据库读的是 B+ 树的**某一页**（一次 16 KB 左右的随机读），它必须能被**单独解压**——所以只能选块压缩。若换成"整个文件一条流"，读一条记录要把前缀全部解开，压缩省下的磁盘会翻倍还回来变成 CPU 和 IO（这就是"某些流式方案被页级压缩直接排除"的原因）。

**旋钮在哪**：块越**大** → 窗口建得满、压缩比越好，但随机读的**读放大**和淘汰粒度也越大；块越**小** → 解压快、粒度细，但压缩比下降、元数据开销上升。消息队列走的是另一头：**按批（batch）压缩**，既保住顺序批量吞吐，又保住"按偏移定位到批"的能力（见 [Kafka.md](../中间件/消息队列/Kafka.md)）。

### 1.6 字典式压缩（LZ77 / LZW 这一族）的共有弱点

| 弱点 | 原因 |
|---|---|
| **对"已经压过/加密过"的数据无收益，甚至变大** | 这类数据看起来接近随机，窗口里找不到重复；还要额外背一个格式头 |
| **小块/短连接冷启动差** | 字典与窗口需要数据量才建得起来 → 所以才需要"训练字典"这类补救 |
| **收益随字典膨胀递减** | 码字位宽有上限（LZW 从 9 位涨到 12 位就得到头），满了只能停止新增或重置 |
| **解压侧资源不可控** | 输出规模不由输入规模决定 → **解压炸弹**风险，对外来的压缩数据必须限制"解压后最大字节数" |
| **历史授权问题** | 早期实现曾涉及专利，这也是新格式绕开 LZW 的原因之一 |

### 1.7 ⭐ 压缩什么时候反而更慢（这题最能区分"用过"和"背过"）

**一句话判据：压缩省的是磁盘/网络 IO，花的是 CPU 和内存带宽。瓶颈不在 IO 时，压缩就是纯亏。**

| 场景 | 为什么反而更亏 | 怎么办 |
|---|---|---|
| 数据本身已压缩/已加密（图片、视频、TLS 载荷、zip） | 找不到重复，白花 CPU 还可能体积膨胀 | 先探测再压；成熟库的兜底是"压完不小于原文就存未压缩标记" |
| 随机访问碎块（读 1 KB 要解压整块） | 读放大 + CPU 放大，延迟反而上升 | 块调小、只压冷数据、列/字段裁剪 |
| CPU 已是瓶颈（核快打满，或压缩同步卡在写路径上） | 压缩线程和业务线程抢同一份 CPU，吞吐掉、尾延迟涨 | 降压缩级别、换更快的算法、把压缩挪到后台/独立线程池 |
| 更新很频繁 | 解压 → 改 → 重压 的循环 = 额外写放大 | 热分区不压、只压历史/冷数据 |
| 内存带宽受限的机型 | 解压同样吃带宽，省了盘却堵在总线上 | 实测瓶颈位置再决定，别靠直觉 |

## 面试官会追问什么

- **Snappy 和 zlib 怎么选？** → 看瓶颈在哪：写盘/网络吞吐受限选 Snappy（快），存储空间受限或离线场景选 zlib/zstd（压得小）。
- **LZW 解压为什么不需要额外字典？** → 字典是**按固定规则边解压边重建**的，码字流本身包含了重建所需的全部信息。
- **为什么数据库页压缩几乎只能是块压缩？** → 读一页要能**单独解压**；流式压缩必须从头解到那个位置，省下的磁盘会变成翻倍的 CPU 和 IO，且一处损坏会污染后文。
- **几 KB 的小数据为什么压缩收益很差？怎么救？** → LZ 系的收益全来自"窗口里找得到重复"，块太短窗口建不起来；救法是**共享/训练字典**（zstd 这类支持），或干脆只对冷数据/大集合开压缩。
- **什么情况下开压缩反而更慢？** → 数据已压缩或已加密（无重复可找、还可能变大）、随机读碎块（解压放大）、CPU 已是瓶颈（抢核）、更新频繁（解压-改-重压的写放大）。判据：**压缩省 IO、花 CPU，瓶颈不在 IO 就是纯亏。**
- **压缩比越高越好吗？** → 不是。压缩比高通常意味着更大的块或更慢的算法，两者都会放大**随机读**的代价（读一行要解一整块）；离线归档看压缩比，在线服务看"解压速度 + 随机读放大"。
