## 四、收录门槛：一个知识点该不该进本目录

按这四条依次判：

1. **语言无关吗？** 只对某个语言 / 框架成立 → 归对应语言目录，那是**机制**不是算法（如 `context`、`Stream`、`channel`）；
2. **有独立原理层吗？** 能写出 ≥1 屏的原理（模型 / 参数 / 复杂度 / 优缺点 / 选型）→ 才值得独立成篇；
3. **≥2 个场景或语言会用到吗？** 只有一个组件用到的，跟着那个组件走；
4. 是某个**已成体系领域**的底座吗（GC / 密码学 / 数据库内核）？→ 留在该领域，不要搬散。

### 反过来：什么时候"实现"要拆出去

| 情况 | 处理 | 例 |
|---|---|---|
| 某语言的实现 / 工程用法 **≥1 屏**，且与该语言生态有关联 | **拆**：原理留本目录，实现进语言目录，**双向引用** | [限流算法.md](限流算法.md) ↔ [../go/并发/限流器.md](../go/并发/限流器.md) |
| 实现只是原理的**短示例**（直译、不足 1 屏） | **不拆**，同篇放一起 | [位图与布隆过滤器.md](位图与布隆过滤器.md) 里的 Go / Java 位图 |
| 是"**用某语言解决的具体问题**"（面试题、业务场景） | 写在语言目录 / **面试目录**，不进本目录 | [../面试/Go算法题.md](../面试/Go算法题.md)、[../go/并发/并发控制实战.md](../go/并发/并发控制实战.md) |
