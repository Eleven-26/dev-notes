## 一、两者差的是「下一步先走哪条边」

**本节要点**：DFS 与 BFS **不是两种数据结构，也不是两套算法**——它们是同一份伪代码，**差别只在一个容器**。看清这一点，后面所有取舍都是它的推论。

### 1.1 同一份伪代码，只换一行

```text
容器 = 栈（LIFO） 或 队列（FIFO）        ← 唯一的差别
把起点放入容器，并标记为「已访问」

while 容器不空:
    u = 容器.取出()
    访问 u
    for v in adj[u]:
        if v 未标记:
            标记 v                        ← ⚠️ 必须在「放入时」标记，不能等取出
            容器.放入(v)
```

把 `容器` 换成**栈**（后进先出，刚放进去的最先被取出）→ 沿着一条路一直往下钻 = **DFS**；
换成**队列**（先进先出，最早放进去的最先被取出）→ 一层铺完再铺下一层 = **BFS**。

⭐ 一句话记：**DFS 与 BFS 的差别不在"算法"，在"容器决定的下一个取谁"。** 所以：

- 想改扩展顺序？**换容器**（0-1 BFS 用双端队列、Dijkstra 用优先队列，都是同一个思路，见 [BFS广度优先遍历.md](BFS广度优先遍历.md) 第五节）。
- 为什么两者复杂度完全一样？因为它们连循环结构都一样，只是容器不同（推导见 [DFS深度优先遍历.md](DFS深度优先遍历.md) 第九节）。

### 1.2 对比表

| 维度 | DFS 深度优先 | BFS 广度优先 |
| --- | --- | --- |
| 口诀 | 一条路走到黑，走不通再退 | 一圈一圈往外扩 |
| 容器 | **栈**（递归调用栈或显式栈） | **队列**（FIFO） |
| 空间 | O(树高 / 路径长度) | O(**最宽一层的节点数**) |
| 能否保证最短（无权图） | ❌ 只保证「可达」，不保证「最近」 | ⭐ 保证：第一次到达即最短 |
| 典型用途 | 判环、拓扑排序、连通分量、回溯（全排列 / 子集 / 剪枝） | 最短路（无权）、层级遍历、邻域扩散、多源扩散 |
| 失败模式 | 递归过深 → 爆栈（见第三节实测） | 宽图 / 深解 → 队列吃内存 |
| 是否「回头」 | 会回溯，能携带路径状态 | 不回溯，只记最短信息 |

⭐ **遍历的本质是「顺序」，顺序必须画出来才看得清**。同一张图（一条 5 元环，边集 `0-1 1-2 2-3 0-4 4-3`，邻接表就按这个顺序插入）：

```text
        0
      /   \
     1     4
     |     |
     2 ─── 3

BFS（队列）   0 → [1 4] → [2 3]     层号即距离：dist = [0 1 2 2 1]
DFS（递归）   0 → 1 → 2 → 3 → 4     一条路钻到底，结果里没有「层」这个概念
DFS（显式栈） 0 → 4 → 3 → 2 → 1     ⚠️ 同一份邻接表，LIFO 把访问序整个反过来
```

> 三条顺序都来自本机实跑。读法：**点 4 的最短距离是 1**（`0→4`），BFS 第二轮就给出；递归 DFS 沿 `0→1→2→3→4` 走满 4 跳才碰到它——谁把「DFS 里的第几个」当成距离，谁就得到 4 这个错答案；而换成显式栈，4 反而第二个就被访问到。**顺序由容器决定，不由「DFS」这个名字决定。**

### 1.3 三条最容易被问倒的结论

| 结论 | 为什么 |
|---|---|
| **BFS 天然给出无权图最短路** | 队列按层推进，结点第一次入队时的层数就是到源点的边数；更短的路径必然经过更早的层，那层已经处理完了（完整反证见 [BFS广度优先遍历.md](BFS广度优先遍历.md) 第二节） |
| **DFS 没有最短性** | 它可能先钻一条十跳的路径抵达终点，然后再也不更新距离 |
| ⚠️ **「BFS 一定比 DFS 快」是错的** | 访问同一张连通图的每条边都是 O(V+E)，**渐近复杂度相同**；差别在内存画像、能否提前退出、是否需要最短性。DFS 常在「解很深很窄」或「找到第一个解就够用」时更快退出 |

## 二、怎么选：场景对照表 ⭐

**本节要点**：选型的判据只有三条——**要不要最短、要不要路径状态、图是宽还是深**。逐条对号入座即可。

| 我要解决 | 选 | 为什么 |
| --- | --- | --- |
| 两个结点是否连通 / 有几个连通块 | DFS（迭代显式栈） | 不需要最短性，栈 / 标记数组最省 |
| 无权图最短步数、最少转换次数 | **BFS** | 层数即距离，唯一正确选择 |
| 依赖先后顺序（编译、启动、建表） | Kahn（BFS 入度） | 天然输出层次 + 顺带判环 |
| 有向图是否有环 | DFS 三色 | 灰遇灰即环，二色会假阳性 |
| 全排列 / 子集 / 组合 / 数独 | **DFS + 回溯** | 需要「携带路径状态 + 撤销」，BFS 记不住整条路径 |
| 求子树聚合、删除整棵目录 | 后序 DFS | 孩子必须先算完 |
| 判断 / 修复 BST、输出有序序列 | 中序 DFS | BST 中序必升序 |
| 层级展示、按距离分波次 | 层序 BFS | 天然带「层」概念 |
| 状态空间巨大且解可能很深 | IDDFS 或双向 BFS | 平衡空间与最短性 |
| 带权图最短路 | [Dijkstra.md](../最短路/Dijkstra.md)（堆）/ 0-1 BFS | 普通 BFS 对带权图不成立 |
| GC 存活对象标记 | 原理上 DFS / BFS 都可 | ⭐ 标记阶段常用 **DFS**（内存峰值更低）；复制式 GC 里 **Cheney 是 BFS**、Fenichel-Yochelson 是 DFS，取舍见 [复制与分代回收.md](../../../垃圾回收/复制与分代回收.md) 与 [标记类GC算法.md](../../../垃圾回收/标记类GC算法.md) |

## 三、复杂度与内存画像（本机实测）

**本节要点**：时间复杂度**两者相同**（O(V+E)，邻接表），所以"选哪个"从来不是速度问题——**是内存画像问题**。三个实测给出量化答案。

### 3.1 实测一：BFS 队列峰值 = 最宽一层，DFS 栈深 = 树高

对完全二叉树（节点数 `2^d - 1`）跑层序，记录队列长度峰值（Go 1.26.5，windows/amd64）：

```text
高度 10（节点    1023）：BFS 队列峰值     512，DFS 最大栈深 10，峰值/节点 = 50.05%
高度 16（节点   65535）：BFS 队列峰值   32768，DFS 最大栈深 16，峰值/节点 = 50.00%
高度 20（节点 1048575）：BFS 队列峰值  524288，DFS 最大栈深 20，峰值/节点 = 50.00%
```

⭐ 结论：**满二叉树的最后一层占掉一半节点**，所以 BFS 的队列峰值约为总节点数的 50%，而 DFS 栈深只有 20。「宽而浅」的树 / 图用 DFS 更省内存；反过来「深而窄」的（链状）用 BFS 更省，且不容易爆栈。

```text
   ① 宽而浅 —— 完全二叉树（峰值在最后一层）

            1                     DFS 栈深 = 树高 = 3
          /   \                   BFS 队列峰值 = 最后一层 = 4 个
        2       3
       / \     / \                ⭐ 2^h-1 个节点里最后一层占 2^(h-1) 个 ≈ 一半
      4   5   6   7

   ② 深而窄 —— 链状图（结论整个反过来）

        0 → 1 → 2 → … → 199999    DFS 栈深 = n（Java 默认栈实测 ~2 万层爆栈）
                                  BFS 队列峰值 = 1（每个点只有一个后继）
```

⚠️ 所以「DFS 省内存」只对**宽图**成立；深而窄的图里 DFS 既费栈又危险——这正是 3.3 语言差异要命的地方。**选 DFS 还是 BFS，本质是在选「栈深 = 一条路径的长度」还是「队列 = 最宽一层」，跟哪个更快无关。**

### 3.2 实测二：最短路只有 BFS 给得出

图 `0-1-2-3`（长路）加 `0-4-3`（短路），就是第一节画过的那条 5 元环：

```text
BFS 距离  : [0 1 2 2 1]     # dist[3] = 2，走 0→4→3
DFS 可达  : [true true true true true]（只判可达，不含距离）
连通分量数: 1
```

> 同一个「顶点 3」：BFS 说"2 步"，DFS 只能说"能到"。**要距离就必须 BFS。**

### 3.3 实测三：递归深度上限的语言差异 ⭐

同一段「链状图递归 DFS」，Go 与 Java 表现完全不同（JBR 17，Windows x64）：

```text
# Go：100 万节点长链，三色判环
递归深度 1000000 的三色判环：hasCycle=false，耗时 359.8629ms（Go 协程栈自动增长，未爆栈）

# Java：默认栈
递归在深度 22503 抛 StackOverflowError
20 万长链三色判环（递归）：StackOverflowError，耗时 3ms
20 万长链连通分量（显式栈）：分量 1 个，耗时 34ms

# Java：-Xss64m
递归在深度 4160284 抛 StackOverflowError
20 万长链三色判环（递归）：hasCycle=false，耗时 215ms
20 万长链连通分量（显式栈）：分量 1 个，耗时 43ms
```

> ⭐ 三条推论：
>
> **① Java 侧「递归 DFS」在生产图上有实际爆栈风险**（默认栈只扛得住 ~2 万层，且同机两次实测分别给出 10410 / 22503，说明**阈值不稳定、不能作为设计依据**）；深图要么 `-Xss` 加大（治标），要么改显式栈（治本，实测显式栈版本在默认栈下 34ms 跑完 20 万长链）。
>
> **② Go 递归可以走百万层**：协程栈初始小、按需增长，因此「递归写法更安全」——但栈内存会涨（默认上限 1GB），深递归仍是 OOM 候选，不是免费的。
>
> **③ 同一算法换语言，工程结论会变**：Go 里「直接递归」是合理的默认写法，Java 里「深图必须显式栈」是硬约束（对照 [goroutine.md](../../../../01-编程语言/go/并发/goroutine.md) 的栈增长与 [JVM与垃圾回收.md](../../../../01-编程语言/java/运行时/JVM与垃圾回收.md) 的栈 / 堆内存）。

## 四、易错点速查

| 症状 | 原因 | 修法 |
| --- | --- | --- |
| 无向图遍历卡死 / 无限递归 | 忘了 `visited`，u-v 来回走 | 图上必带标记，且**入队时就标记** |
| 以为「DFS 先访问到谁，谁就离起点近」 | 访问序 ≠ 距离（第一节图里递归 DFS 走满 4 跳才碰到距离为 1 的点 4） | 要距离只用 BFS，别拿 DFS 的序去推断 |
| 换了实现（递归 ↔ 显式栈）后单测 / 快照挂掉 | 同一份邻接表，两种实现的访问序**互为逆序**（实测 `[0 1 2 3 4]` vs `[0 4 3 2 1]`） | 断言只校「集合相等 / 层号正确」，别把 DFS 的序写死进用例 |
| 判环把菱形依赖误报成环 | 只用二色 `visited` | 换三色：只有指向 **灰** 的边才是环（[DFS深度优先遍历.md](DFS深度优先遍历.md) 第六节） |
| 层序输出「层」不对 | 没先快照 `size` | 循环内先 `int size = q.size()` / `size := len(q)` |
| 后序迭代写不出来 | 想一条栈走到底 | 「根右左」变体 + 整体反转；或用 `prev` 记录上次弹出口 |
| 拓扑排序结果点数少于 n | 有环，入度永不归零 | 这是**判环信号**，不是 bug；先判环再产出 |
| Java 深图 `StackOverflowError` | 默认线程栈只扛 ~2 万层，且阈值随环境波动 | 改显式栈；线程池里还要给 worker 线程设 `-Xss` |
| Go 深递归 RSS 暴涨 | 协程栈按需增长不等于免费 | 限制深度 / 换显式栈 / 分批 |
| `ArrayDeque` 抛 NPE | 压了 `null` 哨兵 | 换可存 `null` 的结构，或改成「变体前序反转」 |
| BFS 算带权最短路出错 | 边权不等时层数 ≠ 距离 | 换 [Dijkstra.md](../最短路/Dijkstra.md) / 0-1 BFS |
| 网格 DFS 在大地图上崩 | 面积即深度（最坏 O(n) 层） | 改 BFS 或显式栈；LeetCode 岛屿类题的标准解法 |
| BFS 找最短路时提前返回算错 | 在**入队时**就返回，而不是出队时 | 首次入队即最短，可在入队处返回；但要确认后续不再需要该点的其他信息 |

## 六、附：统一示例图的表示

> ⭐ **单一来源**：[DFS深度优先遍历.md](DFS深度优先遍历.md) 与 [BFS广度优先遍历.md](BFS广度优先遍历.md) 的 Go 代码都直接使用下面这个类型，两篇不再各写一份。

```go
type Graph struct {
	n   int
	adj [][]int // ⭐ 邻接表：稀疏图的首选；邻接矩阵只在稠密 + 需要 O(1) 判边时用
}

func newGraph(n int) *Graph { return &Graph{n: n, adj: make([][]int, n)} }

func (g *Graph) addEdge(u, v int) {
	g.adj[u] = append(g.adj[u], v)
	g.adj[v] = append(g.adj[v], u) // 无向图加两条；有向图只加 g.adj[u] 这一条
}
```

⚠️ **两条使用注意**：

1. **邻接表顺序会改变遍历序**（不改变正确性）。两篇里的顺序全部基于"按编号升序插入"，换顺序访问序就变——这正是"遍历序不是结构固有属性"的证据。
2. **有向图只加一条弧**。若照抄 `addEdge` 会给有向图加上反向边，判环与拓扑排序的结果就全错了；有向图请写单独的 `addArc(u, v)`（见 [DFS深度优先遍历.md](DFS深度优先遍历.md) 第六节的 `Digraph`）。

## 延伸追问

- **DFS 和 BFS 的时间复杂度不是一样的吗，还选什么？** ⭐ → 渐近一样（O(V+E)），差的是**峰值内存画像**（BFS 装最宽一层、DFS 装一条路径）、**能否给出最短性**、**能否提前退出**、以及**是否需要路径状态**（回溯必须 DFS）。
- **为什么 BFS 能求最短路而 DFS 不能？** → 队列按层推进：节点首次入队时的层数就是最短距离；DFS 先探到的路径可能长得多，且它不会回头更新。⚠️ 前提是**边权相同**。
- **图上遍历和树上遍历最大的区别？** → 图有环，必须 `visited`；树无环不需要。忘标记会导致在一条无向边上无限来回。
- **为什么两者能用同一份伪代码？** → 因为"下一个取谁"完全由容器决定：栈是 LIFO（取最近放入的 → 深入），队列是 FIFO（取最早放入的 → 铺开）。换容器就换算法，这也是 0-1 BFS（双端队列）、Dijkstra（优先队列）的统一视角。
- **有向图的拓扑排序有两种实现，选哪个？** → 只想拿顺序 + 判环 → Kahn（BFS 侧，好写、层次直观、收到点数 `< n` 即环）；已经在做 DFS / 需要更强信息（SCC、关键路径） → DFS 后序反转。
- **BFS 队列会不会爆内存？** → 会。满二叉树的最后一层就占一半节点（实测高度 20 的树队列峰值 524288）。「宽」的图 BFS 内存压力大于 DFS；反之深而窄的图 DFS 栈压力大。
- **GC 的三色标记和判环的三色是一回事吗？** → 不是。同名不同义：GC 的颜色表达存活状态（用于并发标记 + 漏标分析），判环的颜色表达「是否在当前搜索路径上」。两处都被问到要能立刻区分。
- **为什么这个主题要拆成三篇？** → DFS 与 BFS 是**两个独立的知识点**（容器不同、性质不同、应用不同），共享的只有"对比"这一层。对比留在本篇（总纲），各自的机制各归其篇——这与 [分布式与微服务.md](../../../../04-架构与系统/分布式/分布式与微服务.md) 「零件各自成篇、总纲只写区别与判据」是同一个体例。
