## 一、多数元素问题与「两两抵消」的直觉

**本节要点**：全部机制一句话——**每次看到一个与当前候选不同的元素，就把它们配成一对消掉**。消到最后还剩下的，就是"消不完的那个"。看懂"抵消的是**一对不同的元素**"，证明就成功了一半。

### 1.1 问题定义与两种朴素解法

> **多数元素**：给定长度为 `n` 的数组，找出出现次数 **严格超过 `n/2`** 的元素；若不存在，返回"无"。

朴素解法有两条路：

| 解法 | 时间 | 空间 | 特点 |
|---|---|---|---|
| **哈希计数** | `O(n)` | `O(k)`（`k` 为不同值的个数） | 一遍统计、再扫一遍找最大；最坏 `k = n` |
| **排序取中位数** | `O(n log n)` | `O(n)`（要复制）或 `O(1)`（允许改写入参） | 有多数元素时它必然落在中位；不保证原数组顺序 |

⭐ 前者是"**用空间换时间**"，后者是"**用排序换判据**"。摩尔投票走的是第三条路：**不用额外空间，也不用排序** —— 代价是它只给"候选"，必须再验一次（2.3）。

### 1.2 抵消的直觉

想象把数组里的元素**两两配对**，每一对都要求"**两个元素不同**"：

```text
数组 [2 2 1 1 1 2 2]

把不同的配成对、消掉：
  2 ↔ 1      消掉一对
  2 ↔ 1      消掉一对
  1 ↔ 2      消掉一对
剩下的：2  2  2       ← 还有 3 个

⭐ 若某元素超过一半，它最多被消掉「其余元素的总数」个，必然还有剩余
```

⭐ **"不同的才能配对"是全部要点**。因为每一对里都至少有一个"不是多数元素"，所以多数元素**消耗得比它的对手慢**。用"不同元素相消"的算法能在不存全部元素的情况下模拟这个过程 —— 这就是投票算法。

### 1.3 算法的三步规则

| 情况 | 动作 |
|---|---|
| 净票数 `net == 0` | **换候选**：`cand = v`，`net = 1` |
| `v == cand` | 加票：`net++` |
| `v != cand` 且 `net > 0` | 减票：`net--`（等价于"把 `v` 和候选的一个副本配成对消掉"） |

```go
// Boyer-Moore 投票：返回候选与抵消后的净票数
func vote(a []int) (int, int) {
	cand, net := 0, 0
	for _, v := range a {
		if net == 0 {
			cand, net = v, 1 // 换候选
		} else if v == cand {
			net++ // 加票
		} else {
			net-- // 抵消一对不同的元素
		}
	}
	return cand, net
}
```

⚠️ **换候选只看 `net`，不看 `cand`**：`net` 归零时 `cand` 是什么已经不重要了 —— 它和它被消掉的对手"同归于尽"了。

## 二、为什么它一定成立？

**本节要点**：这一节给出**能讲出口的证明**。它的关键只有一个引理：**每次抵消消掉的两个元素一定不同** —— 由此推出任何元素被消掉的次数不超过"其它元素的个数"。

### 2.1 形式化证明

**定理**：若某元素 `x` 满足 `count(x) > n/2`，则算法结束时 `cand = x`，且 `net > 0`。

**证明**分两步。

**第一步（引理）：每个值 `x` 的副本被抵消的总数 ≤ `n − count(x)`。**

算法里每一次 `net--` 都是把"候选的一个副本"与"当前元素 `v`"配成一对消掉，而这一步只在 `v != cand` 时发生 —— 所以**每一对被消掉的元素，两个值一定不同**。

于是，一次抵消如果要消掉一个 `x` 的副本，就必须同时消掉一个**不等于 `x`** 的元素。而数组中不等于 `x` 的元素总共只有 `n − count(x)` 个，每个只能用在一对里。所以：

```text
被消掉的 x 副本数 ≤ n − count(x)
```

**第二步：`x` 消不完。**

```text
剩下的 x 副本数 ≥ count(x) − (n − count(x)) = 2·count(x) − n
```

因为 `count(x) > n/2`，所以 `2·count(x) − n > 0`：**至少还有一个 `x` 的副本没被消掉**。

而算法有一个不变量：**所有"没被消掉"的元素都是同一个值，也就是 `cand`**（无论走到哪一步，`net` 个副本全都是 `cand` 的）。既然 `x` 的副本活到了最后，那 `cand` 只能是 `x`。同时 `net ≥ 2·count(x) − n > 0`。∎

⭐ **换成一句话**：`x` 每被消掉一次，就要拉一个"非 `x`"陪葬；而非 `x` 的兵就那么多，用光了 `x` 还剩着。

### 2.2 本机实测：两种情况的对照

```text
========== 实验一：有多数元素 ==========
数组 : [2 2 1 1 1 2 2]
投票候选 : 2（抵消后净票数 1）
二次验证 : 2 出现 4 次，阈值 n/2=3 → 通过 = true
哈希计数 : 多数元素 = 2（出现 4 次）

========== 实验二：无多数元素（候选是假的） ==========
数组 : [1 2 3 4]
投票候选 : 3（抵消后净票数 0）
二次验证 : 3 出现 1 次，阈值 n/2=2 → 通过 = false
哈希计数 : 无元素超过 n/2 → 结论「不存在多数元素」
```

![摩尔投票的抵消过程](images/摩尔投票的抵消过程.svg)

### 2.3 ⚠️ 只能保证候选：必须二次验证

定理的方向**是单向的**：`有多数元素 → cand 是它`；反过来**不成立** —— 没有多数元素时算法照样会返回一个 `cand`（实验二返回 `3`，而 `3` 只出现 1 次）。

⭐ 所以**二次验证不是可选项**：

> 拿到 `cand` 之后，**再扫一遍数组数它的出现次数**，确认 `count(cand) > n/2`；否则结论是"不存在多数元素"。

代价是"多扫一遍"，但**仍然是 `O(n)` 时间、`O(1)` 空间**（第二次扫描不需要任何额外存储）。⚠️ 最容易犯的错就是把"抵消后剩下的那个"直接当成答案 —— 实验二正是这个错的反例。

### 2.4 `net` 不等于出现次数

⚠️ 另一个常见误解：`net` 是"**抵消后剩下的副本数**"，**不是**元素的实际出现次数。实验一里 `2` 出现 4 次，但 `net = 1`（另外 3 个被配掉了）。所以：

- 想要"出现次数"，必须二次验证时重新数；
- `net > 0` 只说明"这个值没被消光"，不说明它过半。

## 三、`n/3` 泛化：`k` 个候选对应 `n/(k+1)`

**本节要点**：把"两两抵消"扩成"**每次消掉 `k+1` 个互不相同的元素**"，就需要 `k` 个候选位与 `k` 个计数器。这一节讲清"为什么是 `k`"。

### 3.1 为什么候选数是 `k`

**先看一个事实**：同一个数组里，出现次数超过 `n/3` 的元素**最多只有 2 个**（三个都超过 `n/3`，加起来就超过 `n` 了）。

把它推广：出现次数超过 `n/(k+1)` 的元素最多只有 `k` 个。于是直觉上，**要"扣住"这些可能的多数派，就需要 `k` 个候选位**；而抵消的粒度也从"2 个不同元素"变成"`k+1` 个不同元素"。

**证明（`k=2` 版）**：设 `count(x) > n/3`。每次"三票互消"会消掉三个互不相同的元素，其中最多只有一个是 `x` 的副本 —— 也就是说，要消掉一个 `x` 的副本，需要**两个**非 `x` 的元素陪着。非 `x` 的元素总共 `n − count(x)` 个，所以：

```text
剩下的 x 副本数 ≥ count(x) − (n − count(x))/2 = (3·count(x) − n)/2 > 0   （因 count(x) > n/3）
```

`x` 消不完，所以它一定还留在某个候选位上。∎

⭐ 对照表：

| `k` | 目标阈值 | 候选位 | 一次抵消消掉几个不同值 | 最多有几个这样的元素 |
|---|---|---|---|---|
| 1 | 出现次数 > `n/2` | 1 个候选 + 1 个计数器 | 2 | 1 |
| 2 | 出现次数 > `n/3` | 2 个候选 + 2 个计数器 | 3 | 2 |
| `k` | 出现次数 > `n/(k+1)` | `k` 个候选 + `k` 个计数器 | `k+1` | `k` |

![n/3 泛化的两个候选](images/n分之3泛化的两个候选.svg)

### 3.2 两个候选的写法

```go
// n/3 泛化：两个候选 + 两个净票数
func voteTwo(a []int) (int, int) {
	c1, c2 := 0, 0
	n1, n2 := 0, 0
	for _, v := range a {
		switch {
		case n1 > 0 && v == c1:
			n1++ // 命中候选一
		case n2 > 0 && v == c2:
			n2++ // 命中候选二
		case n1 == 0:
			c1, n1 = v, 1 // 候选一空位 → 占用
		case n2 == 0:
			c2, n2 = v, 1 // 候选二空位 → 占用
		default:
			n1--
			n2-- // 三票互不相同 → 一起消掉
		}
	}
	return c1, c2
}
```

⚠️ **判据的顺序不能颠倒**：必须**先判"`v` 是否等于已有候选"**，再看"有没有空位"。若先填空位，那么当 `v` 恰好等于已有候选、而另一个候选位空着时，`v` 会被放进空位、变成两个候选相同 —— 抵消的粒度就错了。

### 3.3 本机实测：两个候选

```text
========== 实验三：n/3 泛化（两个候选） ==========
数组 : [1 1 1 2 2 2 3]（n=7，阈值 ⌊n/3⌋=2，需出现 ≥ 3 次）
两个候选 : 1 与 2
验证候选一 : 1 出现 3 次 → 通过 = true
验证候选二 : 2 出现 3 次 → 通过 = true
```

⭐ 注意最后一个 `3`：它既不是 `c1` 也不是 `c2`，且两个计数器都 `> 0`，于是**两个计数器同时减 1**（`3` 与候选一、候选二的一个副本三方互消）。抵消之后 `n1 = n2 = 2`，而 `1` 与 `2` 实际各出现 3 次 —— **再次说明 `net` 不等于出现次数**（2.4），所以两个候选都必须验证。

⚠️ 泛化版同样**必须二次验证**：没有超过 `n/3` 的元素时，两个候选位里仍可能留下非零计数。

## 四、与哈希计数、排序取中位数比，谁更好？

**本节要点**：三者都是正确的，差别在**时间、空间、以及是否需要改动原数据**。这一节给本机实测，并说清"复杂度表上的排序"与"实测出来的排序"为什么可能不一致。

### 4.1 三种方法的复杂度

| 方法 | 时间 | 额外空间 | 是否需要二次验证 | 会改写入参吗 |
|---|---|---|---|---|
| **摩尔投票** | `O(n)`（两遍：投票 + 验证） | `O(1)` | ⭐ **需要** | 否 |
| **哈希计数** | `O(n)`（一遍统计 + 遍历哈希表） | `O(k)`，`k` 为不同值个数（最坏 `O(n)`） | 不需要 | 否 |
| **排序取中位数** | `O(n log n)` | `O(n)`（复制）或 `O(1)`（原地排序） | 不需要（前提是**确实存在**多数元素） | 取决于实现 |

⚠️ 排序法的前提容易漏：**只有"确实存在多数元素"时，中位数才等于它**。没有多数元素时，中位数只是一个普通的元素 —— 所以排序法**也要验证**，它省掉的只是"找候选"这一步。

### 4.2 本机实测：同样的一百万个元素

`N = 1000000`，值域 `0..3` 且 `0` 占 60%（于是 `0` 就是多数元素）：

```text
========== 实验四：耗时对照（N=1000000，值域 0..3 且 0 占 60%） ==========
摩尔投票      : 平均  2.400 ms/趟（100 趟累加，3 次重复：2.696 / 2.180 / 2.323）
哈希计数      : 平均 24.334 ms/趟（5 趟累加，3 次重复：27.590 / 23.939 / 21.475）
排序取中位     : 平均 13.670 ms/趟（5 趟累加，3 次重复：14.920 / 12.852 / 13.239）
投票候选 0，出现 599459 次 > n/2=500000 → 通过 = true
哈希结论 0（出现 599459 次），哈希表键数 k=4

额外空间 : 投票 O(1)  vs  哈希 O(k=4)
```

```text
摩尔投票      : 平均  6.537 ms/趟（100 趟累加，3 次重复：6.349 / 6.894 / 6.369）
哈希计数      : 平均 35.615 ms/趟（5 趟累加，3 次重复：50.540 / 26.847 / 29.459）

哈希计数      : 平均 370.480 ms/趟（3 趟累加，3 次重复：364.976 / 376.935 / 369.529）
排序取中位     : 平均 161.885 ms/趟（5 趟累加，3 次重复：176.238 / 160.384 / 149.035）
```

⭐ **三个可下的结论**（都只是趋势，单次数字见上面的重复值）：

| 结论 | 证据 |
|---|---|
| **投票最快，且与值域无关** | 两语言、两种值域下都是最少的（毫秒级），因为它只做一次线性扫描、不分配任何结构 |
| **哈希计数的代价由 `k` 决定** | 值域小时 `k=4`；值域放大后 `k=632139`，同一份代码慢了一个数量级（Go 约 24 → 304 ms，Java 约 36 → 370 ms） |
| ⚠️ **"`O(n)` 的哈希"并不总是快过"`O(n log n)` 的排序"** | 值域小时排序反而更快（Go 13.7 优于 24.3；Java 20.3 优于 35.6） |

⚠️ **第三条最值得记住**：复杂度只描述**增长趋势**，不描述**常数**。值域只有 4 个时，排序面对的是"大量相等元素"（基准排序算法对此处理得很好），而哈希表每个元素的插入都要走一遍哈希与探测 —— 常数差距盖过了 `log n` 的差距。**只有在值域放大（`k` 逼近 `n`）之后，哈希的 `O(n)` 与排序的 `O(n log n)` 才在实测上体现出来**，而这时它又输在**空间**上（`O(k)` 对 `O(1)`）。

⚠️ 时序数字只断言**趋势**：同一方法在 3 次重复里的波动可达 2~3 倍（如 Java 值域 0..3 那组排序的 `31.3 / 13.4 / 16.3`），所以不要拿单次读数去比较两个只差一点的方法。

### 4.3 该用哪个

| 场景 | 选择 | 理由 |
|---|---|---|
| **流式 / 在线**，数据只扫一遍、内存紧张 | **摩尔投票** | `O(1)` 空间，一遍就得候选；代价是多一次验证扫描 |
| 要顺带拿到**每个值的出现次数** | **哈希计数** | 投票不给频次；哈希一次统计全部可用 |
| 数组**本来就要排序**（后续还要用有序性） | **排序取中位数** | 排序这一步是"顺手"的，不额外花钱 |
| 值域很小且已知（如 `0..255`） | **数组计数** | 比哈希表更快也更省：`O(值域)` 而不是 `O(k)` 个结点 |
| 只想知道**有没有**超过一半的元素，不要它是谁 | **投票 + 验证** | 不必构造任何结构 |

## 使用：它在你写过的代码里以什么形式出现

摩尔投票很少被"当成一个算法"调用，它出现的地方有一个共同特征：**数据量大到不适合建索引，但只需要一个"多数判断"**。结合本仓库其它篇目：

**第一层：流式统计里的"过半"判定**。日志流、埋点流里要回答"某个错误码是否占了超过一半"、"这批请求的来源是否集中在某一个源" —— 这类问题不需要完整频次表，只要"谁过半"。⚠️ **但工程里更常见的是先限流 / 采样再统计**：真正"过半"的异常往往在外层就被拦掉了。相关：[../../../04-架构与系统/分布式/服务治理/限流算法.md](../../../04-架构与系统/分布式/服务治理/限流算法.md)。

**第二层：与概率结构的取舍**。要"近似的最多"用 [../../数据结构/高级数据结构/基数与频率估计.md](../../数据结构/高级数据结构/基数与频率估计.md) 的 Count-Min Sketch / Space-Saving（`O(1)` 空间的近似，允许误差）；要"精确的过半"用投票（`O(1)` 空间、无误差、但只能回答"过半"这一个问题）。⚠️ **两者的取舍点是"你要的是排序还是判定"**：Count-Min Sketch 给的是"谁大概最多"，投票给的是"谁一定过半"。

**第三层：判定"多数派"这个概念本身**。分布式共识里的"多数派"是 `n/2 + 1` 个**节点**的**表态**，它靠的是计数与法定人数，**不是**"互相抵消"这个技巧 —— 两者经常被混着说。⚠️ 分辨方法：如果问题是"**数据里**有没有一个值占多数"，用投票；如果问题是"**节点足够多**才能达成一致"，那是共识协议的事（见 [../../../04-架构与系统/分布式/服务治理/限流降级熔断.md](../../../04-架构与系统/分布式/服务治理/限流降级熔断.md) 的降级决策里"多数节点可用"的那类判断）。

⭐ 归纳成一条判断：**当"空间"是瓶颈、而问题恰好是"有没有过半"，投票是唯一能同时满足 `O(n)` 与 `O(1)` 的选择；只要能多花一点空间，哈希计数总是更通用**（它顺带给出全部频次）。

## 延伸追问

- **为什么 `net` 归零时可以直接换候选？** → `net` 归零意味着"当前候选的副本已被全部消掉"（每一对消掉的都是不同值），所以它已经不具备任何"优势"，换谁都不影响正确性（1.3、2.1）。
- **为什么快慢指针那种"相遇"和这里的"抵消"不是一回事？** → 相遇靠的是**相对速度**（[双指针.md](双指针.md) 第三节），抵消靠的是**不同值配对**。两者都会"消掉一部分候选"，但一个是几何/速度论证，一个是计数论证。
- **没有多数元素时它返回什么？** → 返回一个**任意候选**（本机实测 `[1 2 3 4]` 返回 `3`），且 `net` 可能为 `0`。所以必须二次验证（2.3）。
- **`net` 是不是就是出现次数？** → 不是。它是"抵消后剩下的副本数"。实验一里 `2` 出现 4 次而 `net = 1`（2.4）。
- **`n/3` 为什么是两个候选而不是"跑两次 `n/2`"？** → 因为"超过 `n/3`"与"超过 `n/2`"是**不同的阈值**，跑两次 `n/2` 的判定只会得到一个候选（超过 `n/2` 的必定超过 `n/3`，但反之不成立）。`n/3` 需要的是 `k=2` 的抵消粒度（3.1）。
- **泛化版里 `k` 能不能随便大？** → 能，但每加一个候选就要多一个计数器，且**每轮抵消要凑齐 `k+1` 个不同值**。`k` 越大，"能凑齐"的机会越少，算法仍然正确、只是对"接近阈值的元素"更迟钝 —— 反正最后都要验证。
- **一定要两遍扫描吗？** → 一遍投票 + 一遍验证，共两遍，都是 `O(n)`。**想省掉第二遍就会犯错**（2.3）。
- **数组里有负数 / 字符串行不行？** → 行。算法只要求"能判等"，与值的类型无关；字符串用相等比较，负数直接用。
- **它能不能求"出现次数最多的元素"？** → 不能。**没有过半元素时，它给不出正确的"最多的那个"** —— 那是频次统计的活（哈希计数 / Count-Min Sketch）。
- **为什么实测里"排序"比"哈希"快，与复杂度表相反？** → 复杂度只描述增长趋势。值域很小时排序面对大量相等元素、常数极小，而哈希表每个元素的插入都要走一遍哈希与探测；值域放大后哈希的 `O(n)` 才体现出来，但它又输在 `O(k)` 的空间（4.2）。
