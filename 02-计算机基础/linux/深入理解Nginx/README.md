| Tengine | 3.1.0（基于 nginx 1.24.0） | — | ❌ | ✅ 15 篇（源码自建镜像） |

**关于版本号的三个坑**（都已按官方 Release Notes 核对）：

- **「ECH 推荐 OpenSSL 3.5.1+」有硬证据**：1.31.6 修的就是 `CVE-2026-90439` ——
  使用 **OpenSSL 3.5.0 及更早**版本编译的 HTTP/3 会触发堆溢出，所以 3.5.1 是事实上限；
- **njs 的快速演进**：`0.9.1` 是「QuickJS 引擎与 njs 引擎**功能对等**」，
  而 `?.` / `??=` / `||=` / `&&=` 这些 ES2023 语法要到 **0.9.6** 才补齐；
  当前最新已是 **njs 1.0.1**，且 **1.0.0 起自研引擎被标记为 deprecated**（推荐 `js_engine qjs`）；
- **1.31.5 是一整套「原生 API 网关」组合拳**，不止 Control API：还有
  `predicate locations`、`client_body_early_read`、`ngx_http_json_module` —— 四者配合才
  能做到「按请求体内容路由」而不引入 Lua / njs。

```text
① 编译安装与配置        ← 先能跑起来：configure / 配置语法 / 虚拟主机 / 现代特性
② 进程模型与基础架构    ← 再看它怎么跑：master-worker、模块化、信号与平滑升级
③ 事件驱动与epoll       ← 高并发的底座
④ HTTP框架执行流程      ← 一条请求的 11 个阶段（前四篇合起来 = 一次请求的完整旅程）
        ↓
⑤ 内存管理与数据结构    ← 开发模块前必须掌握的基础设施（内存池 / slab / buf / chain）
        ↓
⑥~⑩ 模块开发五篇        ← 从「写出第一个模块」到「变量机制」
        ↓
⑪ 现代特性（11、13）    ← HTTP/3、njs
        ↓
⑭⑮⑯ 生态与实战          ← OpenResty / Tengine / 一个完整模块
```

① 到 ④ 是**一条完整链路**：能跑起来 → 进程怎么组织 → 并发怎么实现 → 请求怎么走完。
第一次通读只走 ①②③④，⑤ 之后再回头补。

## 四、实测口径

本目录所有带读数的段落，都在**本机 Docker Desktop** 的同一套容器里跑出：

| 项 | 值 |
|---|---|
| 主镜像 | `nginx:mainline-alpine` = **1.31.6**（OpenSSL **3.5.7/3.5.8**） |
| 对照镜像 | `nginx:1.26-alpine` = **1.26.3** |
| ⭐ 模块编译镜像 | `nginx-dev:1.31.6` = **自建**（alpine + gcc + pcre2/openssl + nginx 1.31.6 源码，OpenSSL **3.3.7**） |
| ⭐ Tengine 镜像 | `tengine-lab:3.1.0` = **自建**（源码 `tengine.taobao.org`，含 7 个独有模块） |
| ⭐ OpenResty 镜像 | `openresty/openresty:1.31.1.1-alpine`（LuaJIT `2.1.ROLLING`） |
| 103 后端 | `python:3-alpine`（裸 socket 手写 103） |
| 内核 / 构建 | `Linux 6.18.40.1-microsoft-standard-WSL2` / `gcc 15.2.0 (Alpine 15.2.0)` |
| fd 上限 | `RLIMIT_NOFILE` = 1048576 |
| 网络 | 自建 bridge 网络，容器间用服务名解析 |

⚠️ 五个本机坑（都会让实验得出假结论）：

1. 官方镜像把 `/var/log/nginx/access.log`、`error.log` **软链到 `/dev/stdout`、`/dev/stderr`**，
   对它们 `tail -f` 会挂死 → 读日志一律用 `docker logs`；
2. `proxy_cache_path` **不配 `proxy_cache_valid` 时默认不缓存**，`X-Cache` 永远是 MISS；
   测「zone 容量」还须把 `inactive` 放大（默认 10m 会让条目先被**时间**淘汰掉）；
3. 容器里 nginx 以 `-g "daemon off;"` 运行 → `ngx_daemonized == 0`，**`WINCH` 信号被忽略**
   （源码：`if (ngx_daemonized) { ngx_noaccept = 1; }`）→ 平滑升级相关的信号实验在容器里
   测不出来，见 [02-进程模型与基础架构.md](02-进程模型与基础架构.md)；
4. ⚠️ **配置里写了 `daemon off;` 时不能再加 `-g "daemon off;"`** ——
   实测报 `[emerg] "daemon" directive is duplicate`，nginx **不会启动**（现象是所有请求连接被拒）；
5. ⚠️ **写 C 模块时，`configure` 打印「+ xxx was configured」不代表模块进了模块表** ——
   必须断言 `grep <模块名> objs/ngx_modules.c`。实测踩过：configure 成功、make 成功，
   但模块表里没有模块，现象是配置里写指令报 `unknown directive`，
   或 filter **静默不生效且无任何报错**（见 [06-HTTP模块开发入门.md](06-HTTP模块开发入门.md) 3.2、
   [09-HTTP过滤模块.md](09-HTTP过滤模块.md) 2.4）。

## 延伸追问

### 1. 这本书 2016 年出版了，现在还值得读吗？

值得，但**要换读法**：它的价值在第四部分（架构、事件、框架执行流程、内存池），
这些原理到 1.31 几乎没变 —— 本目录 01~05 的实测都能和书里的机制对上。
而 1.25 之后的东西（HTTP/3、predicate locations、Control API、原生 JSON）
**书里完全没有**，只能靠官方 Release Notes 与实测补，这就是第三部分存在的理由。
⭐ 所以正确姿势是：**用书搭框架，用版本坐标表和实测填血肉。**

### 2. 为什么要按「四部分」而不是按书的章节顺序读？

因为书的顺序是「编译 → 模块开发 → 原理」（先教你写模块，再解释原理），
这对开发者友好，对**只想搞懂 Nginx 的人**不友好。本目录把顺序倒过来：
先 ①②③④ 建立「能跑起来 → 进程怎么组织 → 并发怎么实现 → 请求怎么走完」的完整链路，
再进 ⑤ 与模块开发。⭐ 判据：**你现在的目标决定顺序** —— 要写模块就直接进第二部分，
要排障就按 ①→④ 走。

### 3. 版本坐标表该怎么看？

先看两列的**差**：「引入版本」与「书中覆盖」。❌ 的那些就是**书里查不到、只能靠官方文档**
的部分，其中 1.31.5 那一组四项（predicate / 早读 body / JSON / Control API）要**一起看**
才成立。⭐ 另注意「并入稳定版」列：`1.29.x` 的新能力在 `1.30.0 stable` 才拿到手，
生产环境用 stable 线时要确认目标特性是否已合并。

### 4. 实测口径那一节的三个坑，会影响结论吗？

会，而且是**方向性**的影响：① 日志软链到 `/dev/stderr` 会让「读日志」这一步失败，
容易误判成「nginx 没输出」；② 不配 `proxy_cache_valid` 时缓存**永远 MISS**，
容易得出「缓存功能坏了」；③ `inactive` 默认 10m 会让条目先被**时间**淘汰，
容易把「容量上限」误测成「时间窗口」。⭐ 三条都不是 nginx 的问题而是**测量方法**的问题 ——
遇到反直觉的读数，先怀疑观测手段。
