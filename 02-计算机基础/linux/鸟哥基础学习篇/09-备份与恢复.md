## 一、备份策略怎么选？

**本节要点**：先想清楚「**能丢多少数据（RPO）**、**能停多久（RTO）**」，再决定全量 / 增量与冷备 / 热备。

| 类型 | 含义 | 代价 |
|------|------|------|
| 全量 | 每次完整拷 | 空间大、耗时长、恢复最简单 |
| 增量 | 只拷「上次任意备份后的变化」 | 省空间、恢复要按链回放 |
| 差异 | 拷「上次全量后的所有变化」 | 折中，恢复只需全量 + 最后一次差异 |

| 方式 | 含义 | 适用 |
|------|------|------|
| 冷备 | 停机拷 | 一致性最好，代价是停服 |
| 热备 | 运行中拷 | 不停服，但要处理一致性（快照 / 事务日志） |

⭐ **3-2-1 原则**：至少 **3** 份副本、**2** 种介质、**1** 份异地。备份从来没「恢复过」的，等于没有备份。

## 二、tar 与 rsync 怎么用？

**本节要点**：`tar` 是**打包归档**（可压缩、可保留权限），`rsync` 是**增量同步**（只传差异，适合定期同步到异地）。

```bash
# tar：打包 + 压缩 + 排除
tar -czf /backup/etc-$(date +%F).tar.gz -C / etc
tar -czf app.tar.gz --exclude="*.log" --exclude="cache/" /srv/app
tar -tzf app.tar.gz | head          # 列出内容（不解包）
tar -xzf app.tar.gz -C /restore     # 解包

# rsync：增量同步（-a 保权限、-v 详情、-z 压缩、--delete 让目标与源一致）
rsync -avz --delete /srv/app/ backup@10.0.0.9:/backup/app/
rsync -avz --dry-run /srv/app/ /backup/app/   # ⭐ 先干跑看会动什么
```

⚠️ 源路径结尾的 **`/`** 含义不同：`rsync -a src/ dst/` 同步**内容**；`rsync -a src dst/` 会在 `dst` 下建 `src` 目录。先 `--dry-run` 再真跑。

## 三、XFS 用什么备份？

**本节要点**：XFS 分区首选自带的 `xfsdump` / `xfsrestore`——支持**增量级别**、保留 ACL 与扩展属性；跨文件系统才退回 tar / rsync。

```bash
sudo xfsdump -l 0 -f /backup/root.dump /          # 全量
sudo xfsdump -l 1 -f /backup/root.incr /          # 基于上次的增量
sudo xfsrestore -f /backup/root.dump /restore     # 还原到目录
```

| 维度 | xfsdump | tar / rsync |
|------|---------|-------------|
| 增量 | ✅ `-l 0/1/…` | ❌（需自己算差异） |
| 跨文件系统 | ❌ 只认 XFS | ✅ |
| 一致性 | 需配合快照 | 需配合快照 |

⚠️ `xfsdump` 不能凭空产出「一致视图」：在线 dump 一个正在被写的文件系统，结果可能不一致——正确姿势是**先打 LVM 快照，再 dump 快照**。

## 四、LVM 快照怎么用于备份？

**本节要点**：快照是原卷的「**写时复制的静止视图**」——原卷写多少它占多少；它的用途是「给备份提供一个时间点一致的源」，**不是备份本身**。

```bash
# ① 给原卷建快照（大小按「备份期间的原卷改动量」估）
sudo lvcreate -L 10G -s -n lv_data_snap /dev/vg_data/lv_data

# ② 挂快照并备份它（此时原卷可继续读写）
sudo mkdir -p /mnt/snap && sudo mount -o ro /dev/vg_data/lv_data_snap /mnt/snap
sudo tar -czf /backup/data-$(date +%F).tar.gz -C /mnt/snap .

# ③ 备份完立即卸载并删除快照（否则 Data% 涨满会失效）
sudo umount /mnt/snap && sudo lvremove -f /dev/vg_data/lv_data_snap
```

```bash
sudo lvs -o lv_name,lv_size,data_percent          # 看快照的 Data% 使用率
```

⚠️ ②③ 之间不能拖太久：快照空间按原卷改动增长，`Data%` 到 100% 快照就作废；给足空间、尽快删。

## 使用：把「配置 + 数据」备份并验证可恢复

**本节要点**：备份的价值只在「能恢复」——所以流程里必须包含**恢复演练**。

```bash
# ① 备份：打包关键配置与数据
sudo mkdir -p /backup
sudo tar -czf /backup/etc-$(date +%F).tar.gz -C / etc \
  --exclude=etc/ssh/ssh_host_*            # 排除会自动生成的

# ② 校验:能列出内容、能解到临时目录
tar -tzf /backup/etc-*.tar.gz > /dev/null && echo "archive ok"
sudo mkdir -p /tmp/restore && sudo tar -xzf /backup/etc-$(date +%F).tar.gz -C /tmp/restore
diff -r /etc /tmp/restore/etc | head     # 抽样对比（会有噪音，看关键文件）

# ③ 异地同步（rsync 到另一台）
rsync -avz --dry-run /backup/ backup@10.0.0.9:/backup/
rsync -avz /backup/ backup@10.0.0.9:/backup/

# ④ 清理临时
sudo rm -rf /tmp/restore
```

判据：`tar -t` 能列目录（归档没坏）、能解到别处（不是写着备份实际是空包）、`rsync --dry-run` 显示待传列表符合预期。

## 延伸追问

- **rsync 和 cp 的区别？**
  → `cp` 是**本地全量复制**；`rsync` 是**增量同步**（默认只传差异，可跨网络走 SSH），且支持 `--delete`（让目标与源一致）、`--dry-run`（预演）、保留权限 / ACL / 稀疏文件。定期同步大目录时 rsync 明显快得多。
- **LVM 快照能当备份吗？**
  → **不能**。快照与原卷在同一块物理盘 / VG 上，磁盘坏了两者一起没；它只是「给备份提供一个一致的时间点」的中间产物。真正的备份必须落到**别的介质 / 别的地点**（3-2-1 原则），且备份完快照就该删。
- **怎么验证备份可恢复？**
  → 三件事：① **能列出内容**（`tar -t` / `xfsrestore -t`）证明包完整；② **能解到别处**并抽样比对证明不是空包 / 损坏包；③ **定期做恢复演练**（真正还原到一个隔离环境）。⚠️ 只验证「备份文件存在」几乎等于没验证。
- **`increm` 增量链断了怎么办？**
  → 增量备份（`xfsdump -l 1`）依赖前一级的存在（记录在 `/var/lib/xfsdump/inventory`），中间任一环丢失，后面的增量都无法单独恢复。所以策略上要**定期做新的全量**（如每周 level 0），别让增量链无限长。
