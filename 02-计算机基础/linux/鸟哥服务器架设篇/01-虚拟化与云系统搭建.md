## 一、虚拟化到底解决了什么问题？

**本节要点**：虚拟机把「一台物理机」切成「多台各自独立、各自有内核的机器」，让「一个服务一个 OS」从口号变成可落地的模型。

- 虚拟化环境成熟、单机性能足够跑好几台虚拟机；
- 一台 PC 就能模拟「多台机器 + 内网 + 各类服务」的机房；
- 逼着人去想「服务之间怎么互动」，而不是把所有东西堆在一台机器上；
- 也是理解容器的前置：先懂「机器级隔离」，再看「进程级隔离」。

| 形态 | 隔离级别 | 启动速度 | 适合 |
|------|----------|----------|------|
| 虚拟机 | 硬件级（各自内核） | 慢（秒~分钟） | 完整 OS、异构内核、教学 |
| 容器 | 进程级（共享宿主内核） | 快（毫秒~秒） | 微服务、弹性伸缩 |

⭐ 这张表的关键一行是「**各自内核 vs 共享宿主内核**」——它同时决定了启动速度、镜像体积和「能不能换内核 / 加载模块」。容器侧的那一半在第 [11-容器化衔接.md](11-容器化衔接.md) 篇有实测对照。

### 1.1 虚拟化的三种实现方式

虚拟化不是只有一种做法，区别在于「**谁在模拟硬件、CPU 指令怎么执行**」：

| 方式 | 做法 | 代价 | 例子 |
|------|------|------|------|
| 全虚拟化 | Hypervisor 用软件模拟全部硬件，Guest 不知道自己被虚拟 | CPU 指令要二进制定点翻译，慢 | 早期 QEMU（纯软件）、VMware 的二进制翻译 |
| 硬件辅助虚拟化 | CPU 提供 VT-x（Intel）/ AMD-V 扩展，Guest 指令直接在 CPU 上跑 | 需要 CPU 与 BIOS 双开 | KVM（Rocky 9 默认路线） |
| 半虚拟化（virtio） | Guest 装「知道自己被虚拟」的驱动，用共享内存环通信，不模拟真硬件 | 需要 Guest 有 virtio 驱动（现代内核自带） | virtio-net、virtio-blk |

⭐ 现代实践是**硬件辅助 + virtio 混用**：CPU 靠 VT-x / AMD-V 硬扛，磁盘和网卡用 virtio 走共享环——把「最贵的 CPU 指令」交给硬件，把「最频繁的 I/O」交给半虚拟化驱动。

### 1.2 硬件辅助虚拟化的前提

要跑 KVM，主机必须先满足两件事：**CPU 有虚拟化扩展**（Intel 是 `vmx`，AMD 是 `svm`）且** BIOS / UEFI 里已开启**（很多机器出厂是关闭的）：

```bash
# 命令口径：确认 CPU 暴露了虚拟化扩展（有输出才代表可用）
grep -E "vmx|svm" /proc/cpuinfo | head -1
```

📎 **本机探测（容器里实测）**：CPU 型号 `Intel(R) Core(TM) i7-6700HQ CPU @ 2.60GHz`、`4` 个 processor、`/proc/cpuinfo` 的 `flags` 里能取到 `vmx`；但同一台机器上 `ls -l /dev/kvm` 报 `No such file or directory`——**CPU 支持虚拟化 ≠ 当前环境能用虚拟化**，Docker Desktop 的 WSL2 虚拟机默认不转发嵌套虚拟化的 `/dev/kvm`。原文见 `.workbuddy/tmp/round495/w15_a03_kvm_unavail.txt`。

⚠️ 这也是本篇正文里所有 `virsh` / `virt-install` 命令只能给「命令口径」的原因：本机没有可用的 KVM 设备节点，硬写输出就是伪造。

## 二、云系统母机是怎么装起来的？

**本节要点**：母机 = 装好虚拟化组件的最小化宿主机；关键是**装最小化系统 + 开虚拟化扩展 + 配好网络**。虚拟化其实由三个层次叠出来，先分清它们各管什么。

| 组件 | 是什么 | 职责 |
|------|--------|------|
| KVM | Linux 内核里的虚拟化模块（加载后 `/dev/kvm` 出现） | 让 Guest 的 CPU 指令在硬件虚拟化扩展上直接执行 |
| QEMU | 用户态的设备模拟器 | 模拟主板、磁盘、网卡、串口等一整套设备 |
| libvirt | 统一管理层（守护进程 `libvirtd`） | 统一 API / 配置 XML / 网络与存储池管理；`virsh` 和 `virt-manager` 都是它的前端 |

```bash
# 命令口径：装虚拟化组件（Rocky 9）
sudo dnf install -y qemu-kvm libvirt virt-install virt-manager
sudo systemctl enable --now libvirtd
sudo systemctl status libvirtd --no-pager
```

- **母机建议最小化安装**：虚拟化宿主上跑的服务越少，攻击面越小、资源越集中给虚拟机。这条与第 [02-主机安全与SELinux.md](02-主机安全与SELinux.md) 篇的「少开就是安全」是同一条原则在两个层面的落地。
- `qemu-kvm` 提供 QEMU 与 KVM 的接合，`virt-install` 是命令行装机入口，`virt-manager` 是图形界面（可选）。

### 2.1 装完先确认这四件事

```bash
# 命令口径
sudo virsh list --all        # ① 能不能连上 libvirtd 并列出虚拟机（空列表也算正常）
sudo virsh net-list --all    # ② 默认网络 default 在不在（NAT 模式靠它）
sudo virsh net-info default  # ③ 默认网络的网段、网桥名、是否 autostart
ls -l /dev/kvm               # ④ 内核的 KVM 模块是否加载成功（本机此处报 No such file）
```

⭐ 顺序很重要：`virsh` 连不上先看 `libvirtd` 状态（`systemctl status libvirtd`），`virsh` 能连但网络空则先 `virsh net-start default` 并 `virsh net-autostart default`——**默认网络不会随母机重启自动拉起**，这是新手最常踩的一格。

### 2.2 磁盘格式与存储池

虚拟磁盘有两种常见格式，选错会把后期能力锁死：

| 格式 | 分配方式 | 快照 | 性能 | 适合 |
|------|----------|------|------|------|
| `qcow2` | 精简置备（用多少长多少），支持内部快照 / 压缩 / 加密 | 支持 | 略低（有元数据开销） | 实验机、需要快照回滚 |
| `raw` | 预分配，体积即容量 | 不支持（靠外部快照） | 略高 | 追求 I/O 的固定盘 |

```bash
# 命令口径：看格式、看实际占用、做一次格式转换
qemu-img info /var/lib/libvirt/images/web01.qcow2
qemu-img convert -f qcow2 -O raw /var/lib/libvirt/images/web01.qcow2 /srv/raw/web01.img
```

⭐ `virsh` 里看到的**虚拟容量**（如 20G）不等于磁盘上占用的空间：`qcow2` 只按实际写入增长，`qemu-img info` 里的 `disk size`（虚拟容量）与 `du -h`（宿主机实际占用）经常差一个数量级。容量规划要按「实际增长」估，不是按虚拟容量加总。

## 三、虚拟机的三种网络模式怎么选？

**本节要点**：网络模式决定虚拟机**能不能上网、外面能不能直连它**——这是虚拟机建起来之后第一个要做的决策。

| 模式 | 虚拟机能否上网 | 外面能否直连虚拟机 | 类比 |
|------|----------------|--------------------|------|
| NAT（默认 `default`） | ✅ | ❌（需端口转发） | 家庭路由器后的设备 |
| 桥接（bridge） | ✅ | ✅（与母机同网段） | 局域网里的一台独立机器 |
| 仅主机（host-only / isolated） | ❌ | 仅母机可访问 | 纯内网实验 |

```bash
# 命令口径：用 virt-install 从 ISO 建一台虚拟机（NAT 网络）
sudo virt-install \
  --name web01 --memory 2048 --vcpus 2 \
  --disk size=20,path=/var/lib/libvirt/images/web01.qcow2 \
  --cdrom /var/lib/libvirt/images/Rocky-9.iso \
  --network network=default --graphics none --console pty,target_type=serial
```

- **NAT**：libvirt 起一个 `virbr0` 私网网桥，虚拟机走母机做地址转换出网；外部要访问虚拟机，只能在母机上做**端口转发**（`virsh` 的 `nat` 转发规则或宿主机 firewalld 的 `forward-port`）。
- **桥接**：在母机上建一个二层网桥 `br0`，把物理网卡「挂」进网桥，虚拟机的虚拟网卡也挂进去——虚拟机拿到的 IP 与母机**同一网段**，对外就是一台独立机器。桥接见第 [03-网络基础与规划.md](03-网络基础与规划.md) 篇的地址规划与第 [04-防火墙与NAT.md](04-防火墙与NAT.md) 篇的放行口径。
- **仅主机 / 隔离**：只连通母机与虚拟机之间，不出网、也不入网，适合纯内网实验（如自建 DNS 不污染外网）。

⭐ **做「模拟机房」的教学环境**：用 **桥接** 让每台虚拟机拿到局域网 IP、互相可访问，最接近真实机房；**NAT** 适合只在母机内部实验；**仅主机** 适合「只想在母机与本机之间试」。

⚠️ 桥接还有一个容易被忽略的前提：母机的物理网卡一旦挂进 `br0`，母机自己的 IP 也要挪到 `br0` 上——改错会让母机**直接失联**。远程操作母机时，桥接配置要么先在本地控制台做好，要么准备好带外通道。

## 四、虚拟机的身份、磁盘与状态怎么管？

**本节要点**：`virsh` 是命令行管理入口；**克隆**用于快速铺多台同类机器，**快照**用于「试验前存档」——但两者都不能当备份。

```bash
# 命令口径
sudo virsh list --all               # 所有虚拟机及状态
sudo virsh start web01
sudo virsh shutdown web01           # 优雅关机
sudo virsh reboot web01
sudo virsh console web01            # 进串口控制台（退出：Ctrl+]）

# 克隆（要先关机）
sudo virt-clone --original web01 --name web02 --file /var/lib/libvirt/images/web02.qcow2

# 快照（qcow2 支持内部快照）
sudo virsh snapshot-create-as web01 before-upgrade
sudo virsh snapshot-list web01
sudo virsh snapshot-revert web01 before-upgrade
```

⚠️ **克隆后必须改四样**：主机名、`/etc/machine-id`、`/etc/ssh/ssh_host_*`、静态 IP——否则多台机器会「撞身份」，SSH 互连也会报 host key 冲突。这四样在 [05-SSH远程连接.md](05-SSH远程连接.md) 篇有对应的验证方式（`hostnamectl`、`ssh-keygen -A`、重建 host key 后清 `known_hosts`）。

### 4.1 克隆、快照、备份三者的边界

这三个词经常被混着用，边界完全不同：

| 手段 | 复制了什么 | 依赖关系 | 能干什么 | 不能干什么 |
|------|-----------|----------|----------|-----------|
| 克隆 | 整份磁盘镜像（复制成新文件） | 独立，与源机无关 | 批量铺机器、留一台「母版」 | 快速回滚到某个时刻（克隆点是当下） |
| 快照 | 磁盘状态的时间点标记（内部快照写在同一个 qcow2 里） | **强依赖同一个镜像文件** | 升级 / 改配置前存档，出事回滚 | 当备份（镜像文件损坏，快照一起没） |
| 备份 | 把镜像 / 数据复制到**别的介质** | 独立 | 灾难恢复 | 快速回滚（要先恢复再起机器） |

⭐ 一句话判据：**「源文件毁了还能不能用」** —— 能，是备份；不能，是快照。

## 五、应用场景

**本节要点**：虚拟化是「一台机器上跑很多台机器」的地基，从公有云到今天的内核态开发都在用。

| 场景 | 用到本篇的哪一部分 | 说明 |
|------|--------------------|------|
| 公有云 / 私有云 | 硬件辅助虚拟化 + 存储池 | 云厂商的云主机底层大量是 KVM；OpenStack 等平台把 libvirt 当统一驱动层 |
| 多节点实验 / 教学机房 | 桥接网络 + 克隆 | 一台 PC 铺出「多台机器 + 内网」的拓扑，本篇第 [六节](#六、具体使用) 就是这条路 |
| CI / 测试机 | 快照 + 回滚 | 每次测试前 `snapshot-revert` 回到干净状态（注意：不能用快照当备份） |
| 需要异构内核 / 内核模块 | 硬件级隔离 | 容器共享宿主内核，跑不了别的内核；虚拟机各自有内核，能加载自己的模块 |
| 上容器之前的过渡形态 | 全篇 | 先把「机器级隔离」与「服务边界」想清楚，再迁到容器（见 [11-容器化衔接.md](11-容器化衔接.md)） |

本仓里与虚拟化相邻的两条线：**网络**看 [03-网络基础与规划.md](03-网络基础与规划.md)（桥接 / NAT 背后的地址与路由），**隔离机制**看 [容器原理.md](../../../06-工程实践/部署/docker/容器原理.md)（namespace 与 cgroup 怎么做到「进程级隔离」）。

## 六、具体使用

**本节要点**：一台母机 → 桥接网络 → 一台模板机 → 克隆成多台，是搭实验环境的标准流程；最后用一次环境探测把「本机能测到哪一步」说清楚。

### 6.1 从零铺一个三节点实验环境

```bash
# 命令口径：① 确认桥接网络存在（若没有，先建 br0）
sudo virsh net-list --all

# ② 装模板机（桥接）
sudo virt-install --name tmpl --memory 2048 --vcpus 2 \
  --disk size=20,path=/var/lib/libvirt/images/tmpl.qcow2 \
  --cdrom /var/lib/libvirt/images/Rocky-9.iso \
  --network bridge=br0 --graphics none --console pty,target_type=serial

# ③ 模板机里改好基础设置后关机，克隆
sudo virsh shutdown tmpl
sudo virt-clone --original tmpl --name node01 --file /var/lib/libvirt/images/node01.qcow2
sudo virt-clone --original tmpl --name node02 --file /var/lib/libvirt/images/node02.qcow2

# ④ 启动并逐个改身份（主机名 / machine-id / ssh host key）
sudo virsh start node01 && sudo virsh console node01
```

判据：`virsh list` 三台都在 running；每台 `hostname` 不同、`ip addr` 拿到独立 IP、能互相 `ping` 通（`ping -c 3 node02`）。

⭐ 模板机的正确顺序是**先改完再克隆**：把「系统更新、常用包、时区与 NTP、SSH 配置」在模板机上做完，克隆出来的三台就只剩「身份改写」这一步；反过来先克隆再一台台配，就等于把手工操作徒手复制了三遍。

### 6.2 本机环境探测（容器实测）

本片在一台机器上跑了「能不能用虚拟化」的前置探测，结论与命令口径对照如下：

```bash
# 实测：取 CPU 虚拟化标志、设备节点、内核版本
grep -m1 '^flags' /proc/cpuinfo | tr ' ' '\n' | grep -E '^(vmx|svm)$' | sort -u   # → vmx
ls -l /dev/kvm                                                                     # → No such file or directory
uname -r                                                                           # → 6.18.54.1-microsoft-standard-WSL2
```

| 探测项 | 实测结果 | 说明 |
|--------|----------|------|
| CPU 虚拟化扩展 | `vmx` | CPU 侧满足硬件辅助虚拟化的前提 |
| processor 数 | `4` | 能跑几台小规格实验机 |
| `/dev/kvm` | 不存在 | **当前环境不能用 KVM**，故本篇 KVM / libvirt 命令均为命令口径 |
| 内核版本 | `6.18.54.1-microsoft-standard-WSL2` | WSL2 定制内核；三个不同镜像（`alpine:3.21`、`nginx:1.26-alpine`、`python:3-alpine`）取到的版本完全一致 |

最后一行是理解「机器级隔离 vs 进程级隔离」的抓手：**三个不同镜像拿到同一个内核版本**，因为容器共享宿主内核；而虚拟机的判据恰好相反——每台虚拟机有自己的 `uname -r`。这条对照在第 [11-容器化衔接.md](11-容器化衔接.md) 篇继续展开。

## 延伸追问

- **虚拟机网络模式怎么选？**
  → 要「像局域网里的一台真机」用**桥接**（有独立 IP、可被外部访问，教学机房首选）；只要「能上网、不想暴露」用 **NAT**（默认网络，外部要访问得靠端口转发）；只做「母机与虚拟机之间」的实验用**仅主机 / 隔离**。
- **快照能当备份用吗？**
  → 不能。快照依赖**同一份镜像文件**（内部快照写在 qcow2 内部），镜像一损坏，快照一起没；它只适合「升级 / 试验前打个存档，出事就回滚」。真正的备份要把 qcow2 拷贝到**别的介质**（先关机或配合外部快照）。
- **KVM 和 VMware 的区别？**
  → KVM 是 **Linux 内核自带的虚拟化模块**（配合 QEMU + libvirt），免费、开源、与云平台（OpenStack / K8s 的虚拟机方案）契合；VMware（ESXi / Workstation）是商业产品，管理界面与生态成熟、企业支持好。功能上现代 KVM 已能覆盖绝大多数场景，云厂商的虚拟机底层大量用 KVM。
- **`qcow2` 和 `raw` 到底怎么选？**
  → 看你要不要「快照与精简置备」：实验机、需要回滚的用 `qcow2`；对 I/O 敏感、容量固定的盘用 `raw`。两者可以互转（`qemu-img convert`），所以真正的决策点是**这盘以后要不要打快照**。
- **为什么容器里 `/dev/kvm` 不存在，却还能看到 `vmx` 标志？**
  → 两者来源不同：`vmx` 读的是 `/proc/cpuinfo`（宿主 CPU 的真实能力），`/dev/kvm` 是宿主**决定要不要暴露给这个环境**的设备节点。虚拟化的可用性由后者决定——这也是云主机「CPU 支持嵌套虚拟化」与「实际开了嵌套虚拟化」是两件事的原因。
