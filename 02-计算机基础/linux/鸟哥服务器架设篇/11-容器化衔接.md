## 一、传统架设的手艺，哪些能直接搬进容器？

**本节要点**：**服务本身的知识 100% 复用**（HTTP / DNS / 邮件协议不会变），变的是**交付与隔离方式**——系统级装包配置 → 镜像 + 声明式编排。

| 传统架设（本目录前 10 篇） | 容器化对应 | 谁接管了 |
|----------------------------|------------|----------|
| 分区 / 文件系统 / 挂载 | Volume / bind mount | 镜像与 `-v` |
| 用户 / 权限 / SELinux | 镜像内 USER + 容器隔离 | 镜像构建 |
| systemd 管服务 | 容器入口进程（PID 1）+ 编排重启策略 | Docker / Compose / k8s |
| nmcli / 网段规划 | 容器网络（bridge / overlay） | CNI / Docker network |
| firewalld / NAT | 端口映射 + 网络策略 | `-p` / k8s NetworkPolicy |
| BIND DNS | 内置 DNS（服务发现） | CoreDNS / Docker DNS |
| Nginx / Apache | 同一软件 + 官方镜像 | 镜像 + 反代层 |
| 邮件服务器 | 容器化收益低（信誉绑定 IP） | 少见容器化 |

```text
# 同一件事，两种交付方式
传统：登录主机 → dnf install → 改 /etc → systemctl enable --now
容器：写 Dockerfile → docker build → docker run / compose up

传统：多台主机各自配置，容易漂移
容器：镜像即产物，声明式编排，环境一致
```

⚠️ 关键认知：**容器不改变协议与架构，只改变「怎么装、怎么跑、怎么扩」**。前面十篇解决的 DNS 记录怎么写、TLS 证书怎么配，在容器里**一模一样**——只是把它们从「手工改配置」搬进了镜像与编排文件。

🔗 **相关图（本篇不另画图，直接引用既有图）**：映射表里的三件事已经有现成图——镜像分层与写时复制、容器隔离结构（namespace 与 cgroup）、端口映射的 DNAT 数据包路径，分别见 [容器原理.md](../../../06-工程实践/部署/docker/容器原理.md) 的 [容器镜像分层与写时复制](../../../06-工程实践/部署/docker/images/容器镜像分层与写时复制.svg)、[容器Namespace与cgroup隔离](../../../06-工程实践/部署/docker/images/容器Namespace与cgroup隔离.svg)，以及 [网络与存储.md](../../../06-工程实践/部署/docker/网络与存储.md) 的 [Docker端口映射DNAT数据包路径](../../../06-工程实践/部署/docker/images/Docker端口映射DNAT数据包路径.svg)。本篇要讲的是「**手工配置 → 镜像与编排**」这条搬迁路径，画在同一页只会与那三张图重复。

## 二、Docker / Podman 的三个概念怎么对上？

**本节要点**：把「镜像（只读模板）→ 容器（运行实例）→ 数据卷（持久化）」三个概念与常用命令对上；Podman 无守护进程、可 rootless，是 RHEL 系默认选择。

| 概念 | 传统对应 | 说明 |
|------|----------|------|
| 镜像 image | 装机镜像 / 预装好的系统盘 | 只读，分层，可复用 |
| 容器 container | 一台跑着服务的主机 | 可写层 + 隔离命名空间 |
| 数据卷 volume | 独立挂载的磁盘分区 | 生命周期独立于容器 |

```bash
# 拉取并运行一个 Nginx（对应第 08 篇的 WWW 服务器）
docker run -d --name web01 -p 8080:80 -v /srv/www:/usr/share/nginx/html:ro nginx:alpine

# 查看 / 进入 / 停止
docker ps -a
docker exec -it web01 sh
docker stop web01 && docker start web01     # ⚠️ 保留容器便于复跑，不急着 rm

# 日志（对应第 07 篇 journalctl 的角色）
docker logs -f web01
```

```bash
# Podman：几乎同样的命令，RHEL / Rocky 默认自带
podman run -d --name web01 -p 8080:80 docker.io/library/nginx:alpine
podman generate systemd --new --name web01 > ~/.config/systemd/user/web01.service
```

### 2.1 容器里的「进程与服务」和 systemd 有什么不同（实测）

📎 同一个 Nginx 站点跑成容器后，四组读数把边界画清楚了：

| 观察 | 实测读数 | 含义 |
|------|----------|------|
| 容器内进程树 | `PID 1` = `nginx: master process nginx -g daemon off;`，`29`~`32` 四个 worker 的父进程是 `1` | **入口进程就是业务进程本身**，没有 systemd 这一层 |
| `systemctl` | `command -v systemctl` → `NO_SYSTEMCTL` | 容器镜像里通常不带 init 系统 |
| 卷 | `docker inspect` 的 `Mounts`：`volume w15vol2 -> /data` | 数据放在卷里，与容器生命周期解耦 |
| 重启策略 | `HostConfig.RestartPolicy.Name` = `unless-stopped` | 「服务自启」在容器里由运行时接管，不是 `systemctl enable` |

⚠️ 容器里的服务**不要再用 systemd 去管内部进程**（一个容器一个前台进程才是正道）；`systemctl` 在容器内常不可用，这是从传统架设迁过来最容易踩的思维惯性。「服务自启」这件事改由 `--restart`（单机）或编排层（集群）承担，对应关系是：

| 传统做法 | 容器做法 | 差异 |
|----------|----------|------|
| `systemctl enable --now nginx` | `docker run --restart unless-stopped` | 前者管进程，后者由守护进程拉活 |
| `systemctl restart nginx` | `docker restart <c>` | 重启的是容器，不是「容器内的服务」 |
| `journalctl -u nginx` | `docker logs <c>` | 日志走 stdout / stderr（12-factor 口径） |
| `systemctl status` | `docker ps` / `docker inspect` | 状态来自运行时而非 init |

## 三、什么时候仍然该用传统架设？

**本节要点**：容器不是万能——**需要固定公网 IP 信誉（邮件）、需要内核级能力（部分安全模块、裸设备）、追求极致性能或最小依赖**的场景，传统架设仍是更优解。

| 场景 | 倾向 | 原因 |
|------|------|------|
| Web / API 服务 | 容器 | 无状态、易扩缩、滚动发布 |
| DNS / DHCP | 都可以 | 简单服务，容器也行，需固定端口 |
| 邮件服务器 | **传统** | SMTP 信誉绑定固定公网 IP + PTR，容器化收益低 |
| 数据库 | 看需求 | 容器可行，但生产多为物理机 / 云 RDS（IO 与持久化） |
| 需要加载内核模块 | **传统** | 容器共享宿主内核，模块加载受限 |
| 裸设备 / 特殊硬件 | **传统** | 需设备直通或特权模式，隔离被削弱 |

⚠️ 判断口诀：**「无状态、可水平复制」优先容器；「有状态、绑定固定身份或硬件」优先传统**。第 [10-邮件服务器.md](10-邮件服务器.md) 篇的邮件服务器就是典型反例——IP 信誉一旦变化，容器再轻也没用。

📎 「共享宿主内核」不是一句空话，实测两条：

```bash
# 三个完全不同的镜像，取到同一个内核版本
docker run --rm alpine:3.21 uname -r          # → 6.18.54.1-microsoft-standard-WSL2
docker run --rm nginx:1.26-alpine uname -r    # → 6.18.54.1-microsoft-standard-WSL2
docker run --rm python:3-alpine uname -r      # → 6.18.54.1-microsoft-standard-WSL2

# 想加载内核模块：镜像里连模块目录都没有
docker run --rm alpine:3.21 sh -c 'ls /lib/modules; modprobe vfat'
#   → ls: /lib/modules: No such file or directory
#   → modprobe: can't change directory to '/lib/modules': No such file or directory
```

⭐ 这三行 `uname -r` 与 [01-虚拟化与云系统搭建.md](01-虚拟化与云系统搭建.md) 篇的判据正好互为镜像：**虚拟机每台有自己的内核版本，容器则共用同一个**。所以「需要换内核 / 加载模块 / 跑异构内核」的需求，容器从原理上就满足不了。原文见 `.workbuddy/tmp/round495/w15_e04_kernel_and_limits.txt`。

## 四、应用场景

**本节要点**：容器化解决的是「交付与弹性」，不是「协议与原理」；判断落点先问「这个服务有没有固定身份」。

| 场景 | 用到本篇的哪一部分 | 说明 |
|------|--------------------|------|
| Web / API 上容器 | 第一、二节 | 无状态服务，配合 [08-WWW服务器.md](08-WWW服务器.md) 的站点配置做成镜像 |
| 把既有单机服务迁成镜像 | 第五节 | 配置与内容进镜像，数据进卷，日志走 stdout |
| 多环境一致性 | 第一节的映射表 | 「镜像即产物」替代「登录主机改配置」，配合 [05-服务与systemd.md](../鸟哥基础学习篇/05-服务与systemd.md) 理解被替代的那一层 |
| 判断某个服务**不该**容器化 | 第三节 | 邮件、需内核模块、裸设备、强身份绑定的服务 |
| 容器底下的隔离机制 | 关联篇目 | 需要讲清 namespace / cgroup 时转到 [容器原理.md](../../../06-工程实践/部署/docker/容器原理.md) |

## 五、具体使用

**本节要点**：以第 [08-WWW服务器.md](08-WWW服务器.md) 篇的 Nginx 站点为例，演示「传统配置 → Dockerfile → 运行验证」的迁移四步，并保留可回退的对照。

```bash
# ① 传统做法（对照）
sudo dnf install -y nginx
sudo cp site.conf /etc/nginx/conf.d/
sudo systemctl enable --now nginx

# ② 写成镜像
cat > Dockerfile <<'EOF'
FROM nginx:1.26-alpine
COPY site.conf /etc/nginx/conf.d/default.conf
COPY html/ /usr/share/nginx/html/
EOF

# ③ 构建并运行
docker build -t w15web:1.0 .
docker run -d --name w15web2 --network w15net --ip 10.77.16.51 \
  -p 18082:80 --restart unless-stopped -v w15vol2:/data w15web:1.0

# ④ 验证（与容器化前用同样的判据）
curl -I http://localhost:18082/          # 期望 200
docker logs w15web2                      # 看启动与访问日志
```

📎 实测四步的读数（镜像 `w15web:1.0`，基础镜像 `nginx:1.26-alpine`）：

| 验证项 | 实测结果 |
|--------|----------|
| `docker build` | 三段 `COPY` / `FROM` 完成后 `naming to docker.io/library/w15web:1.0`，退出码 `0` |
| 宿主 `curl -I http://localhost:18082/` | `HTTP/1.1 200 OK`、`Server: nginx/1.26.3`，且带上站点配置里写的 `X-Lab: w15` |
| 访问日志（`docker logs`） | `10.77.16.1 - - [17/Oct/2026:07:34:02 +0000] "HEAD / HTTP/1.1" 200 0`、`"GET / HTTP/1.1" 200 32` |
| 网内访问（同网络另一容器） | `curl http://10.77.16.50/` → `code=200 size=32` |
| 端口映射（`docker inspect`） | `{"80/tcp":[{"HostIp":"0.0.0.0","HostPort":"18082"},{"HostIp":"::","HostPort":"18082"}]}` |
| 卷持久化 | 写入 `/data/state.txt` → `docker stop` + `docker start` → 重启后 `cat /data/state.txt` 仍读到 `state written before restart` |

判据：`curl -I` 返回 `HTTP/1.1 200`、`docker logs` 里能看到对应请求行、卷里的文件在重启后仍在，即迁移成功；配置内容与第 [08-WWW服务器.md](08-WWW服务器.md) 篇传统做法**完全一致**，变的只是交付方式。若要还原，`docker stop w15web2` 即可，宿主上的传统 Nginx 未受影响。

⚠️ 「容器内通、宿主不通」时的二分判据：先 `docker exec <c> curl -sS -o /dev/null -w '%{http_code}' http://127.0.0.1/` 确认**应用本身**在监听，再查 `docker inspect` 的端口映射与宿主上 `netstat -ano | findstr <端口>`（本片实测宿主端口若被本机其他监听占用，会出现「连上了却拿不到响应」的错觉，换一个宿主端口即可分开判断）。原文见 `.workbuddy/tmp/round495/w15_e05_host_access.txt`。

## 延伸追问

- **容器是不是「轻量级虚拟机」？**
  → 不是。**虚拟机虚拟硬件、跑独立内核；容器共享宿主内核、只隔离进程视图**（namespace）与资源（cgroup）。所以容器启动是毫秒级、镜像能被分层复用；代价是内核只有一份，跨内核版本或加载模块的需求无法满足。详见 [容器原理.md](../../../06-工程实践/部署/docker/容器原理.md)，实测对照见本篇第三节。
- **有了容器，前面十篇的传统架设知识还有用吗？**
  → 更有用。容器把「怎么装」自动化了，但**排障仍然要回到协议与系统层**：容器网络不通，你要懂 bridge / NAT；证书校验失败，你要懂 TLS 与证书链；DNS 解析不对，你要懂 zone 与记录。容器是「交付形态」，不是「知识替代品」。
- **什么服务适合容器化、什么不适合？**
  → 一句话：**无状态、可水平复制、不依赖固定身份**的适合（Web / API / 无状态中间件）；**有状态、绑定固定公网 IP 或硬件、需要内核能力**的不适合（邮件服务器、需要加载模块的服务）。灰度标准是「能否随时重建且不丢身份」。
- **容器里为什么不用 `systemctl` 管服务？**
  → 因为容器只保证**一个前台进程**活着，这个进程就是 PID 1；一旦它退出，容器结束。systemd 那套「后台守护 + 依赖排序 + 开机自启」在容器里既没必要也不可靠——自启交给 `--restart` / 编排层，依赖顺序交给 Compose 的 `depends_on` 或 k8s 的探针与就绪门控。
