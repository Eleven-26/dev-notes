## 一、抓包前先定两件事

**本节要点**：**在哪抓**决定你能看到什么（改写前 / 改写后），**抓多大**决定这台机器会不会被写满盘。
这两件事没定好，抓了也白抓。

### 1.1 在哪抓：同一个连接，三个位置三种样子

| 抓包点 | 看到的 | 拿它回答什么问题 |
|---|---|---|
| **客户端本机** | 源 IP 是**内网地址**（未被 SNAT） | 本机是否发出去了、是否收到回包、重传几次 |
| **服务端本机** | 源 IP 是**出口公网 / LB 地址** | 请求真的到了吗、到的是哪个实例 |
| **LB / 代理上** | **两个方向的连接**（客户端↔LB、LB↔后端） | 时间花在哪一段、后端是否健康 |

> ⚠️ **只有一端的抓包，结论只对那一端成立**：客户端看到"没有 ACK"，
> 可能只是回程走了另一条路（见 [网络通信链路详解.md 4.4](网络通信链路详解.md)）。

### 1.2 抓多少：两个旋钮

- **抓包长度**：`-s 0`（抓整包）vs `-s 96`（只抓头部）。
  排 TCP 问题只要头部；**要看 TLS / HTTP 内容就得整包**（而且内容本身是加密的，抓了也读不懂）；
- **抓多少条**：`-c 200` 限量、`-w` 直接落盘。⚠️ **长时间抓包必须设上限**——
  `-i any` + 不设限，几分钟就能写出几个 GB（日志把磁盘写满，比问题本身更麻烦）。

## 二、命令与过滤表达式

**本节要点**：`tcpdump` 的实际用法就是"**选网卡 + 写表达式 + 落盘**"三步；
表达式的核心只有三种词：`host` / `port` / `tcp[...]`（按字节取标志位）。

### 2.1 最常用的五条

```bash
# ① 看某个对端的所有流量（最常见的第一步）
sudo tcpdump -ni any -nn host 203.0.113.9
# ② 只抓某个端口（443 的握手过程）
sudo tcpdump -ni eth0 -nn 'tcp port 443'
# ③ 只抓 SYN / FIN（看连接建立与关闭的全貌，输出量小很多）
sudo tcpdump -ni any -nn 'tcp[tcpflags] & (tcp-syn|tcp-fin) != 0'
# ④ 只抓带 RST 的（连接被谁重置的）
sudo tcpdump -ni any -nn 'tcp[tcpflags] & tcp-rst != 0'
# ⑤ 落盘（给 Wireshark 分析）与回读
sudo tcpdump -ni any -nn -s 0 -c 5000 -w /tmp/cap.pcap host 203.0.113.9
tcpdump -nn -r /tmp/cap.pcap | head -50
```

### 2.2 表达式怎么读

| 写法 | 含义 | 备注 |
|---|---|---|
| `host A` | 源或目的是 A | `src` / `dst` 可单独限定 |
| `port 443` / `portrange 8000-8100` | 端口 | 不加 `tcp`/`udp` 则两者都抓 |
| `net 10.0.0.0/8` | 网段 | 排查"是不是内网流量" |
| `tcp[tcpflags] & tcp-syn != 0` | **TCP 标志位**：按字节取 `tcpflags` 字段再与标志做位与 | `tcp-syn` / `tcp-ack` / `tcp-fin` / `tcp-rst` |
| `not port 22 and host A` | 组合：`and` / `or` / `not`，括号要引号包住 | 太长的表达式建议写进 `-F` 文件 |

⭐ **`-nn` 一定要加**：不做 DNS 反解、不做端口名转换。
否则 `tcpdump` 会为每个包发一次 DNS 查询——**抓包本身变成了网络负载**，
还会让时间戳失真（排查延迟时这是致命的）。

### 2.3 Windows 侧：`pktmon`（系统自带，无需安装）

Windows 没有 `tcpdump`，但自 **Windows 10 1809** 起内置了 `pktmon`：

```bash
pktmon filter remove                          # 清空过滤器（先做，免得受上次残留影响）
pktmon filter add -p 443                      # 只抓 443 端口
pktmon filter list                            # 确认过滤器
pktmon start --capture --pkt-size 0 --file-name cap.etl   # 开始抓（0 = 整包）
pktmon stop                                   # 停止（会打印日志文件路径与"是否有事件丢失"）
pktmon format cap.etl -o cap.txt              # 转成文本（.etl 不能直接用 Wireshark 读）
```

> ⚠️ **`pktmon format` 输出的是 UTF-16 与 UTF-8 混合编码**：直接 `grep` 会漏一大半
> （本机实测：按 UTF-8 读命中 0 行、按 UTF-16LE 读命中 591 行）。
> 读取时**两种编码各试一次取命中多的那个**，见第四节的处理方法。

## 三、抓到的报文怎么读

**本节要点**：TCP 排查看**四个东西**——标志位、seq/ack 的对应关系、MSS/窗口选项、以及长度。
这四样齐了，绝大多数"慢 / 不通"都能定性。

### 3.1 三次握手：三个包的对应关系

```text
1) 客户端 → 服务端: Flags [S]      seq=x
2) 服务端 → 客户端: Flags [S.]     seq=y, ack=x+1      ← 注意 [S.] = SYN+ACK
3) 客户端 → 服务端: Flags [.]      ack=y+1             ← 纯 ACK（length 0）
```

**判据（一眼能看出来）**：

- `[S]` 后**没有** `[S.]` → 服务端没回（被防火墙丢、端口没监听、或者 SYN 到不了）；
- `[S.]` 后**没有**第三个 `[.]` → 回程被丢，或客户端没收到（**半连接堆积**在服务端，见
  [TCP三次握手.md](tcp/TCP三次握手.md) 的队列一节）；
- 反复出现 `[S]` 且 seq 相同 → **客户端在重传 SYN**（对端不回）。

### 3.2 重传、重复 ACK 与零窗口

| 现象 | 抓包里的样子 | 说明 |
|---|---|---|
| 超时重传 | **同一个 seq 反复出现**，间隔逐步拉长（RTO 退避） | 对端没收到，或 ACK 丢了 |
| 快速重传 | 先看到 3 个**重复 ACK**（同一个 ack 号），随后重传 | 丢包被后续包"顶出来"了 |
| 零窗口 | 对端 `win 0` | 接收方缓冲区满了，**是它对端慢，不是网络慢** |
| 窗口更新 | 之前 `win 0`，后来出现 `win >0` 的纯 ACK | 对端消化完了，可以继续发 |

### 3.3 MSS、MTU 与分片

- **MSS 是选项，不是长度**：`options [mss 1460]` 表示"我这边能收的最大段"，
  由**发送方按自己的 MTU 推算**（IPv4：1500 − 20 − 20 = 1460；**IPv6：1500 − 40 − 20 = 1440**）；
- 双方各自宣告，实际取**较小值**；
- **IP 分片**：`Flags [+]`（`MF` = More Fragments）与片偏移才叫分片；
  ⚠️ **TCP 层面的分段不是分片**（判据见 [TCP报文结构.md](tcp/TCP报文结构.md)）。

### 3.4 TLS 在哪：`ClientHello` 之后全部加密

TCP 握手之后的**第一个带载荷的包**通常是 **TLS ClientHello**（几十到几百字节）；
之后所有内容都是密文，**能看到的是：包的大小与节奏、以及 TLS 记录层的类型字节**。
所以"抓包看 HTTP 内容"在 HTTPS 下不成立——这是 TLS 的设计目的，不是抓包工具的缺陷。

### 3.5 ⚠️ 抓包里最容易骗人的三类假象

| 假象 | 为什么 | 正确理解 |
|---|---|---|
| **"包比 MTU 还大"** | **TSO / LRO / GRO 卸载**：大段交给网卡分段，抓包点在内核看到的是卸载前的"超级段" | 抓包点**在本机**时出现 ≥ 数 KB 的"段"是正常的；**要判断真实 MTU，看 MSS 选项而不是看包大小** |
| **"没收到 ACK"** | 抓包点只在一端；回程可能走另一条 AS 路径 | 结论只对抓包那一端成立 |
| **"有重传就是网络丢包"** | 也可能是**对端应用没读**（缓冲区满）、或本机网卡/驱动丢包 | 配合 `netstat -s`（重传计数）与对端窗口值一起判断 |

## 四、本机实测：用 `pktmon` 抓一条完整的 HTTPS 连接

**本节要点**：一次真抓，看清**握手 → TLS → 大段 → 挥手**的完整骨架。所有输出都是原始抓包结果。

### 4.1 抓包过程

```bash
$ pktmon filter remove && pktmon filter add -p 443
已删除所有筛选器。
已添加筛选器。
$ pktmon start --capture --pkt-size 0 --file-name cap.etl
$ curl --noproxy '*' -sS -o /dev/null -w 'HTTP %{http_code}  握手 %{time_connect}s\n' https://example.com
HTTP 200  握手 0.244005s
$ pktmon stop
正在合并元数据...
日志文件: C:\Users\Administrator\AppData\Local\Temp\cap.etl (无事件丢失)
$ pktmon format cap.etl -o cap.txt
已格式化事件数:    1381
```

⭐ **`无事件丢失` 这行要留意**：`pktmon stop` 会告诉你抓包缓冲区有没有溢出丢事件——
**丢事件的抓包不能作为"没收到包"的证据**。

### 4.2 抓到的报文（去重后，按时间顺序）

同一报文会被多个"组件"重复记录（Ethernet / WiFi / 组件 19…），去重后这条连接的骨架是：

```text
 1. [S]   → 443   seq=3081011777                      win=64800  len=0
      options [mss 1440, nop, wscale 8, nop, nop, sackOK]
      AC-2B-6E-22-B6-81 > 42-03-D3-78-7C-51, ethertype IPv6 (0x86dd), length 86:
      240e:47f:38f2:93cc:3565:1aa2:94b1:15d2.62867 > 2606:4700:10::ac42:93f3.443: Flags [S]
 2. [S.]  ← 443   seq=558876703  ack=3081011778        win=65535  len=0
      options [mss 1300, nop, nop, sackOK, nop, wscale 13]
 3. [P.]  → 443   seq=3081011778                       len=292        ← TLS ClientHello
 4. [P.]  ← 443   seq=558876704                        len=3900       ← 服务端首批数据（见 4.3 假象①）
 5. [.]   ← 443   seq=558880988  ack=...               len=1300       ← 正好一个 MSS
 6. [P.]  → 443   seq=3081012070                       len=80
 7. [P.]  → 443   seq=3081012150                       len=97
 8. [P.]  ← 443   seq=558882288                        len=238
 9. [P.]  ← 443   seq=558882526                        len=27
10. [P.]  → 443   seq=3081012247                       len=24
11. [F.]  → 443   seq=3081012271  ack=558882553        len=0          ← 客户端 FIN
12. [F.]  ← 443   seq=558882553  ack=3081012271        len=0          ← 服务端 FIN
```

### 4.3 逐条能读出什么

| 现象 | 读出的信息 |
|---|---|
| 走的是 **IPv6**（`ethertype 0x86dd`） | `curl` 优先用了 AAAA 记录；链路层目的 MAC **是网关的**（`42-03-D3-78-7C-51`），符合"跨网段只交接下一跳" |
| 客户端 `mss **1440**` | IPv6：1500 − 40（IPv6 头）− 20（TCP 头）= **1440**，比 IPv4 的 1460 少 20 —— **MSS 是算出来的** |
| 服务端 `mss **1300**`、`wscale 13` | 云 / CDN 节点常给保守 MSS（留隧道与额外封装余量）；`wscale 13` 表示窗口可左移 13 位（最大约 8 MB） |
| `len=292` 的第一个载荷 | **TLS ClientHello**（含 SNI、ALPN 提议、key_share），HTTP/3 的 `h3` 就在这里的 ALPN 列表里 |
| `len=3900` | ⚠️ **大于 MSS 1300 —— 这不是"网络有毛病"，是 TSO 卸载**（见 3.5 假象①） |
| 结尾两个 `[F.]` | **四次挥手**：两个 FIN 各带 ACK；主动关闭方之后会进 `TIME_WAIT`（见 [TCP四次挥手.md](tcp/TCP四次挥手.md)） |

### 4.4 读这份抓包的"坑"（附处理方法）

`pktmon format` 的文本是**混合编码**，直接 `grep "Flags"` 会得到 0 条：

```python
# UTF-8 读命中 0 行、UTF-16LE 读命中 591 行 → 两种各试一次，取命中多的
for enc in ("utf-8", "utf-16-le"):
    hits = [l for l in open("cap.txt", "rb").read().decode(enc, errors="ignore").split("\n")
            if "Flags [" in l and ">" in l]
```

另外**同一报文会重复记录**（每个经手的组件记一次），去重按"整行文本"即可：

```python
seen, uniq = set(), []
for line in hits:
    key = re.sub(r"\s+", " ", line.strip())
    if key not in seen:
        seen.add(key); uniq.append(key)
```

## 使用：三条最常用的抓包套路

```bash
# ① "连不上"——只看握手三包，看断在哪一步（SYN 无响应 / SYN+ACK 无第三次）
sudo tcpdump -ni any -nn 'tcp port 443 and tcp[tcpflags] & (tcp-syn|tcp-rst|tcp-fin) != 0'     # Linux/macOS
pktmon filter add -p 443 && pktmon start --capture --pkt-size 0 --file-name cap.etl            # Windows
# ② "很慢"——落盘后统计重传与重复 ACK（重传多 = 链路丢包；重复 ACK 多 = 乱序或丢包）
sudo tcpdump -ni any -nn -s 96 -c 20000 -w /tmp/slow.pcap host <对端>
tcpdump -nn -r /tmp/slow.pcap 'tcp[tcpflags] & tcp-ack != 0' | wc -l
# ③ "大包卡住"——只看 ICMP 类型 3（PMTU 黑洞的判据）与 MF 分片
sudo tcpdump -ni any -nn 'icmp[icmptype] == icmp-unreach'    # 有没有"需要分片"的 ICMP
sudo tcpdump -ni any -nn 'ip[6] & 0x20 != 0'                 # IPv4 的 MF 位置位 = 有分片
```

> ⚠️ **抓包的顺序原则**：先用 `ss` / `netstat` / `netstat -s` 定位到"大概哪一层"，
> 再用抓包**取证**。一上来就 `tcpdump -i any` 全量抓，通常只会得到一堆读不完的 pcap（见
> [网络通信链路详解.md 五、分层观测点](网络通信链路详解.md)）。

## 延伸追问

- **抓包时看到"包比 MTU 大"是网络故障吗？** → 不是。**TSO / LRO / GRO 卸载**让抓包点看到的是
  卸载前的"超级段"（本机实测到一个 3900 字节的段）。**判断真实 MTU 要看 MSS 选项，不能看包大小。**
- **为什么 `tcpdump` 一定要加 `-nn`？** → 不加时它会对每个地址做 DNS 反解、对端口做名称查询，
  **抓包本身产生网络流量**，还会让时间戳与丢包统计失真。
- **`pktmon` 的输出为什么 `grep` 不到？** → `pktmon format` 输出 UTF-16 与 UTF-8 混合编码
  （实测 UTF-8 命中 0 行、UTF-16LE 命中 591 行）；两种编码各试一次取命中多的。
- **三次握手哪一步没出现，能判断什么？** → 有 `[S]` 无 `[S.]` = 对端没回（防火墙 / 未监听）；
  有 `[S.]` 无第三个 `[.]` = 回程丢或客户端没收到，服务端半连接队列堆积。
- **`tcpdump` 能抓到 HTTPS 的明文吗？** → 不能，`ClientHello` 之后全部加密；
  要看明文只能在**端点上**用 `SSLKEYLOGFILE` 导出会话密钥给 Wireshark 解密（属端点侧手段，不是抓包能力）。
- **为什么同一报文在 `pktmon` 里出现好几次？** → 它在**多个组件/网卡层**各记录一次
  （Ethernet、WiFi、每个处理组件），按整行去重即可。
- **`pktmon stop` 报"有事件丢失"意味着什么？** → 抓包缓冲区溢出、丢了一部分事件，
  **这份抓包不能用来证明"某个包没收到"**；要加大缓冲区或收窄过滤条件重抓。
- **零窗口（`win 0`）说明什么？** → 接收方缓冲区满了、**是它那侧处理不过来**，
  不是网络慢；等它发"窗口更新"的 ACK 才能继续。
