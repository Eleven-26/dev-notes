# CPU 怎么执行一条指令

> 同一件事、同样的 2 亿次加法，三种写法耗时 **8.81 / 2.55 / 1.81 个时钟周期每加法**——差别只在「这几条加法之间有没有依赖」。CPU 从来不是「一条指令一个周期」地干活：它同时开着几十条指令在飞，能飞多快由**依赖关系**决定，不由指令条数决定。
>
> 本篇接在 [从可执行文件到第一条指令.md](../编译原理/从可执行文件到第一条指令.md) 之后：那边把 PC 设成 `e_entry` 就收笔了，这边讲 PC 拿到地址之后，那串字节在 CPU 里发生什么。字节怎么编码见 [机器码、字节码与opcode.md](../编译原理/机器码、字节码与opcode.md)。
>
> 素材来源：本机 Docker 实测，`perf-lab` 容器（debian:bookworm-slim + `linux-perf 6.1.190` + `gcc 12.2.0`），宿主 Intel i7-6700HQ，WSL2 内核 6.18.54.1，容器 `--privileged`、无 CPU 配额。

## 一、从零：同一件事，三种依赖结构

**本节要点**：三份代码做的是**同样的 2 亿次加法**，只因为「下一次加法要不要等上一次」，耗时差 4.85 倍。这个差值就是本篇要解释的全部内容。

### 1.1 三种循环

```c
/* chain.c —— 三种模式做同样多的加法，只有依赖结构不同 */
#include <stdio.h>
#include <string.h>

volatile long sink;
#define N 200000000L

int main(int argc, char **argv)
{
    if (argc < 2) return 2;

    if (strcmp(argv[1], "dep") == 0) {
        /* 单累加器：每次加法都要等上一次的结果 */
        long a = 0;
        for (long i = 0; i < N; i++) a += i;
        sink = a;
    } else if (strcmp(argv[1], "indep4") == 0) {
        /* 4 个累加器：4 条加法链互不相干 */
        long b0 = 0, b1 = 0, b2 = 0, b3 = 0;
        for (long i = 0; i + 3 < N; i += 4) {
            b0 += i; b1 += i + 1; b2 += i + 2; b3 += i + 3;
        }
        sink = b0 + b1 + b2 + b3;
    } else if (strcmp(argv[1], "indep8") == 0) {
        long b0 = 0, b1 = 0, b2 = 0, b3 = 0, b4 = 0, b5 = 0, b6 = 0, b7 = 0;
        for (long i = 0; i + 7 < N; i += 8) {
            b0 += i;     b1 += i + 1; b2 += i + 2; b3 += i + 3;
            b4 += i + 4; b5 += i + 5; b6 += i + 6; b7 += i + 7;
        }
        sink = b0 + b1 + b2 + b3 + b4 + b5 + b6 + b7;
    }
    return 0;
}
```

三种模式的总加法次数都是 2 亿：`dep` 跑 2 亿轮各 1 次，`indep4` 跑 5000 万轮各 4 次，`indep8` 跑 2500 万轮各 8 次。

⚠️ 这份代码**必须用 `-O0` 编译**。`-O1` 会把 `dep` 那个循环整个换成一条常量——原因和证据见第六节，那是本篇最重要的一个坑。

### 1.2 用 perf 拿读数

```bash
gcc -O0 -o chain0 chain.c

perf stat -e cycles,instructions,uops_issued.any ./chain0 dep
perf stat -e cycles,instructions,uops_issued.any ./chain0 indep4
perf stat -e cycles,instructions,uops_issued.any ./chain0 indep8
```

`perf` 在这个环境要自己装（镜像是精简版），实测可用的最小步骤：

```bash
docker run -d --name perf-lab --privileged debian:bookworm-slim sleep infinity
docker exec perf-lab sh -c "sed -i 's|deb.debian.org|mirrors.aliyun.com|g' \
  /etc/apt/sources.list.d/debian.sources && apt-get update -qq && \
  apt-get install -y -qq linux-perf gcc"
```

`--privileged` 是必需的：`perf_event_open` 要读 PMU 计数器。宿主 `perf_event_paranoid` 是 `2`，允许**测自己启动的进程**，但不允许测系统全局——所以 `perf stat ./prog` 能跑，`perf stat -a` 不行。

### 1.3 8.81 / 2.55 / 1.81

| 模式 | cycles | instructions | IPC | 每加法 cycles |
|---|---|---|---|---|
| `dep`（单累加器） | 1,761,766,012 | 1,002,052,137 | 0.57 | **8.81** |
| `indep4`（4 链） | 509,302,807 | 701,044,017 | 1.38 | **2.55** |
| `indep8`（8 链） | 362,881,617 | 650,931,270 | 1.79 | **1.81** |

![三种依赖结构的每加法时钟周期：8.81 / 2.55 / 1.81](images/三种依赖结构的cycles.svg)

读法：左轴是「每完成一次加法平均花几个时钟周期」，右轴是同时开着的独立加法链数量。链条从 1 条加到 8 条，单位成本降到五分之一——**加法次数一个没少，硬件也只是同一块 ALU**。

两点要提前说清楚，否则数字会被误读：

1. **指令数不同不是「做的事不同」**。`dep` 是 5 条指令 1 次加法，`indep8` 是 26 条指令 8 次加法——每 4 次或 8 次加法才付一次循环判断的开销，所以摊到每次加法上的指令数变少了（5.01 → 3.51 → 3.25）。这是循环展开的红利，与本篇的结论无关。
2. **IPC 全部小于 2**。这三份代码都在 `-O0` 下跑，每条加法前后都有一次内存往返（`-O0` 把所有局部变量放在栈上），所以达不到第四节能看到的 3.17。

## 二、原理：一条指令在 CPU 里走五段

**本节要点**：教科书把执行拆成取指 / 译码 / 执行 / 访存 / 写回五段。真实 CPU 的级数远多于此，但**五段的分工**是对的：前两段决定「拿到什么活」，后三段决定「这活什么时候能完」。

### 2.1 取指：地址从哪来

PC（x86 里叫 `RIP`）指着下一条要执行的指令。取指单元按 PC 去 L1i 拿一段字节——不是拿「一条」，是拿**一整段**窗口（Skylake 级别是 16 字节/周期，⚠️ 这个宽度本轮没测，属公开参数），因为 x86 指令是变长的，事先不知道这条有多长。

`从可执行文件到第一条指令.md` 2.4 节说内核把 `e_entry` 写进 `pt_regs->ip`。那是 PC 的**初值**；之后每一次取指，PC 都在自增或跳转。`e8 e5 ff ff ff` 里的 `-27` 就是跳转时 PC 该往哪偏。

⭐ 这里有个容易忽略的点：**取指是提前的**。CPU 不会等当前指令执行完才取下一条，它顺着预测的路径一直取下去。取错了就整段丢掉——第四节讲这个代价。

### 2.2 译码：变长字节变成定长微操作

译码器要做两件事：

1. **切边界**。`8b 04 b7` 是 3 字节还是 4 字节？靠边读边算（ModRM 的 `rm=100` 说「后面还有 SIB」）。
2. **翻译成微操作**（micro-op / µop）。x86 的指令语义复杂（`mov (%rdi,%rsi,4),%eax` 一条干四件事），后端执行单元却希望每条活都简单定长。所以前端把它拆成一到几个 µop，后端按 µop 调度。

**这是 x86 唯一一处「CISC 事实上变成了 RISC」的地方**：译码之后，后端看到的是定长、简单的 µop 流。所以「CISC vs RISC」在今天的分界不在指令集，在**前端译码**这一段。

### 2.3 发射与执行：乱序的起点

µop 进入调度器（reservation station），等它的**输入操作数就绪**就发射到执行单元。这里的关键是：

- 「就绪」是看**数据依赖**，不是看程序顺序。`b0 += i` 和 `b1 += i+1` 之间没有依赖，两条可以同时在两个 ALU 端口上跑。
- 这就是 1.3 那张表里 8.81 → 1.81 的全部原因。`dep` 里每次加法都要等上一次的结果，硬件再宽也只能一次一条。

⭐ 乱序执行的边界由**依赖关系图**决定，不由代码行数决定。同一条依赖链再短也是串行的，无关的两条链再长也能并行。

### 2.4 访存

访存单元（load/store unit）管两件事：load 要去 L1d 拿数据，store 要写回。这里有两个独立的延迟：

| 路径 | 典型量级 | 说明 |
|---|---|---|
| L1d 命中 | 4 ~ 5 周期 | 本机 L1d 32 KiB/核 |
| L2 命中 | 十几个周期 | 本机 256 KiB/核 |
| L3 命中 | 几十个周期 | 本机 6 MiB，两核共享 |
| 到内存 | 上百周期 | 需要 MMU 查页表，缺页则进内核 |

`-O0` 的三种模式全部命中 L1d（栈上就那几个变量），所以 8.81 这个数字**不含访存代价**，纯粹是依赖链的串行成本。

⚠️ 上表的周期数量级来自公开资料，**本轮没有逐一测**（要测需要构造不同工作集的逆序访问，本篇没做）。本机实际容量是 `lscpu` 读出来的：`L1d 64 KiB (2 instances)` = 每核 32 KiB。

### 2.5 退休：顺序提交

执行完的 µop 不能直接改架构状态（寄存器、内存），要先进入重排缓冲（ROB），**按程序顺序退休**。

为什么要多这一步？为了让**异常和中断是精确的**。如果乱序执行的结果直接生效，某个 µop 触发了缺页，此时更靠后的指令可能已经改了寄存器——现场就没法恢复，`SIGSEGV` 也就没法定位到「到底哪条指令出的事」。

⭐ 所以「乱序执行 + 顺序退休」是一对绑死的设计：**乱序是为了快，顺序是为了对**。

### 2.6 为什么必须是这五段

把五段串起来看，它们各解决一个不可省略的问题：

| 段 | 解决什么 | 去掉会怎样 |
|---|---|---|
| 取指 | 指令从哪来 | 变长编码下无法切边界 |
| 译码 | 复杂语义 → 简单 µop | 后端要为每条指令定制电路，等于回到 CISC 的硬件复杂度 |
| 发射/执行 | 依赖就绪就干 | 只能按顺序等，8.81 那档 |
| 访存 | 数据从哪来 | 寄存器和内存无法交互 |
| 退休 | 状态何时生效 | 异常不精确，中断无法恢复 |

## 三、流水线：IPC 为什么能大于 1

**本节要点**：IPC（instructions per cycle）大于 1 是「同一时刻有多条指令在不同阶段」的直接证据。它不是「CPU 造假」，是流水线重叠的必然结果。

### 3.1 三条指令同时在飞

一条指令走五段要 5 个周期，但如果每段各有一套电路，那么第 2 条指令可以在第 1 条进入译码时就开始取指：

| 周期 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|
| 指令 A | 取指 | 译码 | 执行 | 访存 | 退休 | | |
| 指令 B | | 取指 | 译码 | 执行 | 访存 | 退休 | |
| 指令 C | | | 取指 | 译码 | 执行 | 访存 | 退休 |

稳态下每周期完成一条（IPC = 1），而**单条指令的延迟仍是 5 周期**。这两个数字不矛盾——延迟和吞吐是两件事。

![五段流水线的时间重叠：单条 5 周期，稳态每周期完成一条](images/指令的五段与流水线重叠.svg)

读法：横轴是时钟周期，每一行是一条指令。对角线方向看是「同时在第几段」，竖直方向看是「同一周期有哪几条在飞」。第 5 周期开始每格填满，此后每周期退休一条。

### 3.2 实测 0.55 → 1.77 → 3.17

同一台机器上跑出来的三档 IPC：

| 程序 | 编译 | IPC | 卡在哪 |
|---|---|---|---|
| 分支随机（第四节） | `-O0` | **0.55** | 预测失败，流水线反复清空 |
| 分支排序（第四节） | `-O0` | **1.77** | 预测几乎全中，但 `-O0` 的访存拖后腿 |
| 分支程序 | `-O1` | **3.17** | 没有冗余访存，前端供得上 |

⭐ **3.17 是「超标量」的直接证据**：一个时钟周期内退休了 3 条以上指令，单发射的 CPU 做不到。

### 3.3 上限从哪来

IPC 的上限由最窄的那一段决定。对这台机器（Skylake 级别）来说，最窄的是**前端译码**：x86 的变长指令要靠译码器切边界，每周期能处理的指令条数远少于 RISC 的定长指令。

公开资料里这一代的退休宽度是 4 µop/周期，译码是 4 ~ 5 条/周期。⚠️ **这两个数字本轮没有单独测**（`perf` 的 `ls_lsd` / `idq` 一类事件可以间接反推，本篇没做）。实测能确定的是：3.17 已经摸到 4 附近，再往上要靠更宽的机器。

对照 [AOT、JIT与解释执行.md](../编译原理/AOT、JIT与解释执行.md) 3.2 的 `fib(32)`：Java 的 JIT 版本比 Go 的 AOT 版本快，本质也是**IPC 的差别**——C2 编出来的代码指令更少、分支更可预测，同样的 cycles 能干更多活。

## 四、分支预测：猜错的代价可以量化

**本节要点**：分支是流水线的天敌——取指单元不知道下一条该取哪，只能猜。猜对了毫无代价，猜错要丢掉已经做的所有事。这一节的读数把「所有事」量了出来：**4.32 倍的微操作被浪费掉**。

### 4.1 排序 vs 随机的经典实验

```c
/* branch.c */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

#define N 32768
static int arr[N];

static int cmp(const void *x, const void *y) { return *(const int *)x - *(const int *)y; }

int main(int argc, char **argv)
{
    unsigned int seed = 12345;
    long sum = 0;

    for (int i = 0; i < N; i++) {
        seed = seed * 1103515245u + 12345u;
        arr[i] = (int)((seed >> 16) & 0xFF);      /* 0 ~ 255 随机 */
    }
    if (argc > 1 && strcmp(argv[1], "sorted") == 0)
        qsort(arr, N, sizeof(int), cmp);

    for (int r = 0; r < 2000; r++)                 /* 重复扫 2000 遍 */
        for (int i = 0; i < N; i++)
            if (arr[i] >= 128) sum += arr[i];

    printf("%ld\n", sum);
    return 0;
}
```

随机数组里 `arr[i] >= 128` 大约一半真一半假，**分支走向没有规律**；排序之后前一半全假、后一半全真，**预测器只要记住「上次走了哪」就能全中**。

```bash
gcc -O0 -o branch0 branch.c
perf stat -e cycles,instructions,uops_issued.any,branch-misses ./branch0 random
perf stat -e cycles,instructions,uops_issued.any,branch-misses ./branch0 sorted
```

### 4.2 微操作数 3,832M vs 949M

| | cycles | instructions | IPC | uops_issued | **µop / 指令** | branch-misses | 时间 |
|---|---|---|---|---|---|---|---|
| `random` | 1,623,051,735 | 887,439,653 | 0.55 | 3,832,556,346 | **4.32** | 32,019,699 | 0.667 s |
| `sorted` | 509,054,047 | 902,208,237 | 1.77 | 948,693,519 | **1.05** | 201,268 | 0.215 s |

![分支预测的代价：指令数几乎相同，微操作数差 4 倍，时钟周期差 3.2 倍](images/分支预测的代价.svg)

读法：三组柱子都按 `random / sorted` 成对比较。**指令数几乎一样**（8.87 亿 vs 9.02 亿，差 1.7%），这是这个实验最关键的控制变量——两边做的活完全相同。差异全部出现在后两组：分支失败 159 倍，微操作 4 倍。

这里最值得看的是 **µop / 指令 = 4.32**：`sorted` 是 1.05，说明正常情况下一条 x86 指令约等于一个微操作；`random` 涨到 4.32，多出来的 3.27 倍全是**投机执行后又被丢弃的 µop**——CPU 沿着猜错的方向取了指、译了码、甚至执行了一部分，最后整段作废。

⭐ 这就是「分支预测失败」的真实成本：不是「重取一条指令」，而是**扔掉一条链路上已经做过的所有工作**。

### 4.3 为什么浪费 4 倍微操作只慢 3.2 倍

因为被浪费的工作里，**只有一部分在关键路径上**。乱序引擎在等待预测结果的同时，还能推进其他无关的指令（比如循环计数、下一轮的取指），所以「4.32 倍 µop」不必换算成「4.32 倍时间」。实测是 3.19 倍 cycles。

这个差值本身也说明了一件事：**CPU 的资源利用率在预测失败时并没有掉到底**——它还在用剩下的窗口干别的活。真正的性能杀手是「预测失败 + 长依赖链」同时出现，那时候没有别的活可以填。

## 五、乱序执行与写缓冲

**本节要点**：乱序让无关的工作并行，写缓冲让 store 不必等内存。两者都是性能的来源，也都破坏了「代码顺序 = 执行顺序」这个直觉——内存屏障就是为了把直觉还回来。

### 5.1 乱序不是乱来

乱序引擎只在一个前提下重排：**重排不改变单线程的可见结果**。做法是寄存器重命名——`b0 += i` 写的是「某个物理寄存器」，不是「架构寄存器 `rax`」，只要输出依赖没建立，两条指令就能同时跑。

所以 1.3 里的 `indep4` / `indep8` 不是「编译器变聪明了」，而是**硬件终于有活可干**：

- `dep`：一条链，任何时刻只有 1 条加法就绪，8 个 ALU 端口闲着 7 个。
- `indep8`：八条链，八条加法同时就绪，端口被填满，每周期接近完成一次加法。

⭐ 判据：**看代码就能估出并行度**——数一数「互不依赖的累加器」有几个。这就是为什么手写归约（reduction）时会用 4 路或 8 路累加器，而不是一个 `sum`。

### 5.2 写缓冲：store 为什么看起来提前了

store 写内存要等缓存行拿到独占权（MESI 的 `E`/`M` 态），可能要几十个周期。为了不等，CPU 把 store 先扔进**写缓冲**（store buffer），指令本身立刻退休。

于是出现一个反直觉的现象：

```text
线程 A：             线程 B：
  x = 1;               while (y == 0) {}
  y = 1;               print(x);   // 可能打印 0
```

程序顺序是「先写 x 再写 y」，但 x 可能还躺在写缓冲里，y 已经出去了。这就是**存储-加载重排**（StoreLoad）。

⚠️ x86 的内存模型（TSO）只允许这一种重排：store-store 不重排、load-load 不重排、load-store 不重排。所以上面这段在 x86 上依然可能出问题，而且只在多核、且 B 在另一个核上时。

### 5.3 `LOCK` 前缀在做什么

[Go内存模型.md](../../01-编程语言/go/并发编程/Go内存模型.md) 4.1 节给过汇编证据：

```text
main.go:12   LOCK XADDQ AX, 0(CX)     ; ← LOCK 前缀 = 完整内存屏障
```

那边说的是「清空写缓冲、使其他核心的对应缓存行失效」。这里的补充是**为什么要清**：

- 清写缓冲 → 让之前所有的 store 真正落到缓存一致性协议的视野里，解决 5.2 的重排；
- 拿缓存行的独占权 → 让别的核不能再改这一行，解决「两个核同时改」的竞争；
- 两者合起来，就是「顺序一致」在指令层能落地的最小动作集。

⭐ 所以 `LOCK` 不是一条「让指令变慢的开关」，它是**把乱序引擎攒下的债一次性还清**。这也解释了 Go 4.1 那句「每次 `atomic.Add` 都是一条带 `LOCK` 的指令」为什么是代价——它每次都还清，哪怕这次并没有别的核在看。

## 六、编译器决定喂给 CPU 什么

**本节要点**：所有「CPU 怎么执行」的测量都有一个前提——**CPU 拿到的是你想测的那份代码**。编译器有两种方式悄悄改掉它：把循环整个算成常量，把分支换成 `cmov`。两种都会让读数变成零信息。

### 6.1 第一种骗法：整个循环变成常量

把 1.1 的 `chain.c` 用 `-O1` 编，`dep` 那个循环的反汇编是：

```text
115a:  mov    $0xbebc200,%edx        ; 200,000,000
115f:  sub    $0x1,%rdx
1163:  jne    115f                   ; ← 空转 2 亿次
1165:  movabs $0x470de4d98c1f00,%rcx ; ← 直接写答案
116f:  mov    %rcx,0x2eaa(%rip)      ; sink = 结果
```

`0x470de4d98c1f00` 是多少？**19,999,999,900,000,000**，正好是 `200000000 × 199999999 / 2`——等差数列求和公式。

编译器把「循环 2 亿次累加」识别成了闭式解，只留一个空循环骗过「有副作用」的判断，然后把结果直接写进 `sink`。用这份代码测「依赖链的延迟」，测到的是 `sub` + `jne` 的循环开销，跟加法毫无关系。

⭐ 这就是 1.1 为什么必须用 `-O0`：`-O0` 不做归纳变量分析，循环是真实的。代价是 `-O0` 把局部变量放在栈上，每次加法带一次内存往返，所以 8.81 这个数字包含访存开销，不是纯 ALU 延迟。

### 6.2 第二种骗法：分支变成 `cmov`

用 `-O1` 编第四节那个分支程序，两档读数会**反过来**：

| | cycles | branch-misses |
|---|---|---|
| `random` | 166,143,831 | 18,465 |
| `sorted` | 188,794,706 | 188,432 |

排序反而更慢、分支失败反而更多。原因在反汇编里：

```text
0000000000001190 <clip>:
    1190:  31 d2          xor    %edx,%edx
    1192:  89 f8          mov    %edi,%eax
    1194:  83 ff 7f       cmp    $0x7f,%edi
    1197:  0f 4e c2       cmovle %edx,%eax      ; ← 没有 jcc
    119a:  c3             ret
```

**没有 `jcc` 了**。编译器把「条件跳转 + 赋值」改成了条件传送（`cmov`），于是根本不存在「预测」这件事——两种输入的数据依赖完全一样，耗时差异只剩数据局部性那点噪音。

这就是 4.2 的实验为什么也要用 `-O0`：`-O1` 会把你想测的分支删掉。

### 6.3 怎么判断

在相信任何 CPU 读数之前，先看反汇编：

| 现象 | 判据 |
|---|---|
| 循环次数少了、冒出大常量 | `movabs $0x...` 就是这个循环的答案 |
| 该有分支的地方没有 `jcc` | 被 `cmov` / `setcc` 替换了 |
| 循环体里根本没有 `call` | 递归被完全内联展开了（`fib` 从 49 字节涨到 958 字节） |
| 指令数远少于预期 | 先怀疑优化，再怀疑 perf 坏了 |

```bash
objdump -d --no-show-raw-insn chain | sed -n '/<main>:/,/^$/p'
```

⭐ 一条经验：**测 CPU 行为时，先证明「CPU 拿到的是我以为的那份代码」**。`objdump` 的成本只有一行命令。

## 七、出问题按什么顺序查

**本节要点**：看到「CPU 高、QPS 低」，先分清是「算得多」还是「等得多」。IPC 是这两者的判据——不是 CPU 利用率。

### 7.1 五层判据

| 现象 | 先看什么 | 说明 |
|---|---|---|
| CPU 100% 但 QPS 掉 | `perf stat -p <pid> -e cycles,instructions` | IPC 明显低于 1 → 在等（依赖/预测/访存），不是算力不够 |
| IPC 高（> 2）但处理慢 | `perf top` 看热点函数 | 确实是指令多，去看算法本身 |
| `branch-misses` 占比高 | 数据是否随机、分支是否可预测 | 4.2 的实验就是这种形状 |
| 多核扩展性差 | 缓存行是否被共享写 | 伪共享：两个核改同一行，`LOCK` 互相排队 |
| 换了编译选项结果全变 | `objdump -d` 对照 | 第六节的两种骗法 |

### 7.2 三个典型误判

**「CPU 利用率高说明在干活」**：错。利用率是「周期有没有被占用」，不是「有没有产出」。分支预测失败时流水线在空转，利用率照样 100%。

**「IPC 低就是代码写得差」**：不完全。`dep` 那种单累加器写法在 `-O0` 下 IPC 0.57，但改成 8 路就是 1.79——同一份逻辑，只改了变量个数。**IPC 是「喂给硬件的并行度」的证据，不是代码质量的证据**。

**「`perf stat` 的数字是绝对的」**：不是。本机读出的频率约 **2.4 GHz**（1,623,051,735 cycles / 0.6666 s = 2.435 GHz；509,054,047 / 0.2153 s = 2.365 GHz），而 `lscpu` 报的基准频率是 2.60 GHz。差的那部分就是降频与容器竞争——**cycles 是 CPU 自己的钟，不是墙钟**。

## 八、三组结论

1. **同一条依赖链决定上限，不是指令条数**。2 亿次加法，1 条链 8.81 周期/次，8 条链 1.81 周期/次，差 4.85 倍。硬件没变，只是「同一时刻有几条加法就绪」变了。
2. **IPC 大于 1 是流水线与超标量的直接证据**。实测 0.55 / 1.77 / 3.17 三档，最高一档说明每周期退休了三条以上指令。IPC 低的时候先查「在等什么」，别急着优化算法。
3. **所有读数都以「CPU 拿到的是你想测的代码」为前提**。`-O1` 会把 2 亿次加法算成一个常量（`0x470de4d98c1f00`），会把分支换成 `cmov`。测之前先 `objdump`。

## 校验口径

> ✅ 实测（`perf-lab` 容器 = debian:bookworm-slim + `linux-perf 6.1.190` + `gcc 12.2.0`，`--privileged`，无 CPU 配额；宿主 Intel i7-6700HQ，WSL2 内核 6.18.54.1，`perf_event_paranoid=2`）：

- **依赖结构**：`chain.c` 用 `gcc -O0` 编译，三种模式各跑一次，`perf stat -e cycles,instructions,uops_issued.any`。每加法 cycles = cycles / 200,000,000。
  - ⚠️ **只跑了 1 次，没有取多轮区间**。三档之间的差距（4.85 倍）远大于常见的抖动（同一程序重跑差异通常在 1% ~ 3%），但严格说这是单次读数。
- **分支预测**：`branch.c` 用 `gcc -O0` 编译，`random` 与 `sorted` 各跑一次，加 `-e branch-misses`。指令数 887,439,653 vs 902,208,237 是刻意核对过的控制变量。
- **`-O1` 对照**：同一份 `branch.c` 用 `gcc -O1` 再编一次，读数见 6.2（`random` 166,143,831 cycles、`sorted` 188,794,706）。
- **编译器删循环的证据**：`chain.c` 用 `gcc -O1` 编出的 `main`，`objdump -d` 里 `dep` 分支只剩 `sub`/`jne` 与 `movabs $0x470de4d98c1f00`。`0x470de4d98c1f00` = 19,999,999,900,000,000 = `200000000*199999999/2`，用十进制展开核对过。
- **`cmov` 的证据**：`bytes.c` 里 `clip(int i) { return i >= 128 ? i : 0; }`，`gcc -O2` 编出 `0f 4e c2`（`cmovle`），无 `jcc`。
- **字节解码**：`e8 e5 ff ff ff` 取自 `fib_O2fnoinline` 的递归调用，手算 `0x1186 + 5 - 27 = 0x1170`，与 `objdump` 显示的 `call 1170 <fib>` 一致。
- **机器信息**：`lscpu`（4 逻辑处理器 / 2 物理核 / L1d 64 KiB 共 2 个实例 / L2 512 KiB 共 2 个实例 / L3 6 MiB）。频率由 cycles ÷ 实测时间反推，与 `lscpu` 的 2.60 GHz 基准对照。

⚠️ **未实测 / 边界**：

- **流水线的级数、译码宽度、退休宽度（4 µop/周期）都不是本机测出来的**，来自公开的微架构资料。第三节只把「IPC 上限」当机制描述，不当读数。
- **没有测缓存层次**。2.4 那张表的周期数量级来自公开资料；本机只验证了容量（`lscpu`），没验证各级命中延迟。
- **没有构造 StoreLoad 重排实验**。5.2 的「可能打印 0」是 TSO 模型的推论，x86 上要观察它需要两个核 + 精确对齐的时序，本轮没做。5.3 的 `LOCK` 语义来自 Intel SDM，与 [Go内存模型.md](../../01-编程语言/go/并发编程/Go内存模型.md) 4.1 的汇编证据互证，但那边的汇编是另一台机器上的读数。
- **`-O0` 的读数混入了访存开销**。8.81 周期/加法里有相当一部分是栈变量的 load/store，不是纯 ALU 延迟。要测纯 ALU 延迟需要 `-O2` 且阻止闭式化（例如让累加不可归纳），本轮没做——因为那会把「依赖链」这个变量和「是否被优化」混在一起。
- **只有 x86-64 的读数**，且是 WSL2 虚拟机内的 4 个逻辑处理器，物理机上的绝对值会不同。

## 延伸追问

- **为什么 IPC 的实测上限是 4 而不是 8？** 因为瓶颈不在执行单元（ALU 端口有 4 个，能同时算 4 个整数加法），而在**前端**：x86 的变长指令要靠译码器切边界，每周期切不出 8 条。RISC-V 那种定长 32 位指令，译码就是「每 4 字节一条」，前端可以做得更宽——这是 RISC 在高 IPC 场景的优势来源。
- **分支预测器怎么学会「前一半假后一半真」？** 靠历史表（BHT）+ 全局历史寄存器：它记录「最近几十次分支的走向组合」，用这个组合去索引一张预测表。排序后的分支走向是「连续 16384 次假，再连续 16384 次真」，历史表能看到「上次这一条也是假」，于是预测假。随机数组则没有任何可利用的历史模式，只能 50% 猜。
- **`cmov` 为什么不是万能的？** 它把控制依赖变成了数据依赖——两条路都要算（`cmovle` 要等 `edx` 和 `eax` 都就绪），而且分支两端如果有昂贵操作就白算了。所以只在「两个简单值二选一」时划算。这也是为什么 `-O1` 下 `random` 反而比 `sorted` 快：`cmov` 的代价是恒定的，`sorted` 那点「数据局部性好」的红利抵不过 qsort 带来的缓存污染。
- **乱序窗口有多大？** 现代 x86 的 ROB 在几百条 µop 的量级（Skylake 是 224）。这个数字决定「乱序引擎能看多远」——如果一条依赖链的间隔超过窗口深度，后面的指令就只能在窗口外干等。本轮没测，因为它需要构造特定间隔的依赖链。
- **为什么 `-O0` 的 dep 是 8.81 周期而不是 ALU 的 1 周期？** 因为 `-O0` 把 `a` 放在栈上：每次加法都是 `mov -0x10(%rbp),%rax` → `add %rax,-0x8(%rbp)`，后一条的 load 必须等前一条的 store 完成（store-to-load forwarding，典型 4 ~ 5 周期），再加上循环控制。所以 8.81 ≈ 访存往返 5 + 加法 1 + 循环开销。要测纯 ALU 的 1 周期，得让累加器留在寄存器里（`-O2` + 阻止闭式化）。
