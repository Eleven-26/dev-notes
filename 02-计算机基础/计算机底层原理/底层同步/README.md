# 底层同步

> 本册收**多个核要改同一份数据时，什么叫出错、谁保证正确、这份保证要多少钱**：`happens-before` 的构造与数据竞争的判据、`LOCK` 前缀锁的是缓存行、CAS 失败怎么回报、无竞争时互斥为什么不进内核、三语言的壳各包了什么。判据是「**先把「正确」定义成一份可查的合同，再看硅与内核怎么履行它，语言壳只是组合者**」——所以 Go / C / Java 三份读数会落在同一档。
>
> 当前 **3 篇**：[内存重排、Happens-Before与数据竞争.md](内存重排、Happens-Before与数据竞争.md)（590 行 / 5 图）、[原子操作.md](原子操作.md)（445 行 / 3 图）、[互斥的实现.md](互斥的实现.md)（387 行 / 3 图）。后两篇由原来那篇 718 行的合并篇按「一条指令 vs 一个线程」拆开；第一篇是它们的前置定义，回答「凭什么说它错了」。
>
> 内容整理自个人学习笔记。

## 一、本册收什么

**本节要点**：一句话——「**凭什么说错了、`i++` 为什么会丢、丢了之后谁能救、救的代价是多少**」。这串问题有四段：先有一份合同定义「什么叫正确」（`happens-before` 与数据竞争），再是硅（一条带锁的指令）、内核（futex 睡眠）、语言壳（`sync.Mutex` / `ObjectMonitor` / `pthread_mutex_t`）各管一段。

⭐ 第一段是后三段的前提：**没有「竞争」的定义，「谁保证正确」这个问题就无法提问**。这也是为什么本册的第一篇不是关于硅或内核的，而是关于规范怎么定义对错。

## 二、分工表

**本节要点**：三篇的分界是「**一份合同**」「**一条指令**」「**一个线程**」——第一层是规范定义的判据，第二层是硅的属性，第三层是内核与语言壳的组合。后两层合成一篇 718 行时两套证据已经挤在一起，读的人分不清哪条读数在证什么；第一层则根本不属于这两层中的任何一层。

| 篇 | 回答什么 | 状态 |
|---|---|---|
| [内存重排、Happens-Before与数据竞争.md](内存重排、Happens-Before与数据竞争.md) | `happens-before` 怎么由两组边取传递闭包造出来；数据竞争为什么是它的补集；fence 式描述为什么不够；hb 的四条边界；`-race` 怎么执行这套判据 | ✅ 已落地（无 hb 的读写 200/200 读完；断链版 2000/2000 仍对但 `-race` 报 1；`-race` 开销 3.94 倍 / 19.55 倍；prob=100 跑 200 轮三次 0 报告） |
| [原子操作.md](原子操作.md) | `lock` 前缀锁什么；`xchg` 为什么不带前缀也原子；CAS 成败靠哪一位回报、重试为什么随竞争非线性上涨；x86 上四种内存序差几条指令 | ✅ 已落地（跨行 `LOCK` 8 → 1395 ns；CAS 15.44 → 96.48 ns） |
| [互斥的实现.md](互斥的实现.md) | 无竞争时为什么不进内核；futex 三态与 `EAGAIN`；200 万次加锁进内核几次；三语言壳的结构与慢路径落点 | ✅ 已落地（futex 556 / 248 / 124 次；一次系统调用 1.7 µs） |

⚠️ 拆分时有两个判断：

- **排查那一节按归属拆开**。「计数对不对 / 看汇编确认真是一条指令」留在原子操作篇（第五节）；「数系统调用 / 什么时候别改」进互斥篇（第五节）。整节搬给任何一边，另一边都会缺一条判据。
- **结论也拆**。原子的三条是「原子性是指令属性 / 锁的粒度是行 / 屏障大半白送」；互斥的三条是「无竞争不进内核 / 进内核贵两个数量级 / 三个壳只差慢路径」。六条各有独立证据，不重复。

## 三、读序

**本节要点**：按「合同 → 硅 → 内核」从上往下读：先搞清楚「什么算错」，再看不进内核的那条路，最后看不得不进内核的那条路。顺序反了会看不懂「为什么 `mu.Lock()` 编出来只有两条原子指令」，也会把「加锁了所以安全」当成推理。

1. 先读 [内存重排、Happens-Before与数据竞争.md](内存重排、Happens-Before与数据竞争.md)：从「跑对了也不等于对」出发，把 `hb` 的构造、数据竞争的定义、四条边界、检测器原理走一遍。这一篇不依赖任何硬件细节，先读不亏。
2. 再读 [原子操作.md](原子操作.md)：从零丢失率 → `LOCK` 锁什么 → CAS 失败怎么办 → 内存序差几条指令。这四节全是硅侧的事，不看内核也能懂。
3. 然后读 [互斥的实现.md](互斥的实现.md) 第一、二节：从「22 ns 与 1.7 µs 差 70 倍」这个不可能的比值出发，落到 futex 三态。从这里开始出现内核。
4. 最后读它的第三、四节：200 万次加锁的 futex 计数与三语言壳的对照。

## 五、实测坐标

**本节要点**：本册读数分两个环境，**绝对值不可相减，只可比量级**——Go 在 Windows 原生跑（`sema` 走 `WaitForSingleObject`），C/Java 在 WSL2 容器里跑（走 futex）。

| 项 | 值 |
|---|---|
| Go 侧 | `go1.26.5 windows/amd64`，Intel i7-6700HQ（4 核 8 线程） |
| C/Java 侧 | WSL2 容器 `nproc=4`、`gcc 12.2.0`、`glibc 2.36`、`Temurin 24.0.2` |
| 内核 | 6.18.54.1-microsoft-standard-WSL2 |
| `-race` 侧 | `golang:1.26-bookworm` 容器，`go1.26.x linux/amd64`，`nproc=4`；`-race` 用容器内自带的 gcc 与 cgo（本机 Windows 无 gcc，跑不了） |
| 关键方法 | `go build -gcflags='-S'` / `gcc -O2 -S` 看汇编；`strace -f -c -e trace=futex` 数调用；`unsafe.Sizeof` 与 `sizeof(pthread_mutex_t)` 量尺寸；`GORACE="halt_on_error=0"` 统计报告条数 |

⚠️ WSL2 把系统调用放大约一个量级（`getpid()` 1.6 µs），所以本册「原子操作 : 系统调用 = 1 : 200」在裸机上大概是 1 : 20~30。倍数变了，但「差两个数量级」的定性不变。
