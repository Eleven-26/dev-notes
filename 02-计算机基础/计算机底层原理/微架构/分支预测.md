# 分支预测

> 分支是流水线的天敌：取指单元不知道下一条该取哪，只能猜。猜对了几乎免费，猜错要把已经做的工作全丢掉。同一份代码、指令数只差 1.7%，只因为数组排了序，微操作数从 **3,832M 掉到 949M**（4.32 倍 / 1.05 倍），耗时从 0.667 s 掉到 0.215 s。
>
> 本篇讲两件事：**「猜」这件事的成本怎么被量化**，以及**什么时候它根本不存在**——编译器会把分支换成 `cmov`，第六节再把「改成算术」这个建议本身量一遍（随机数据快 4.8 倍、有序数据反而亏 30%）。流水线本身与乱序执行见 [CPU流水线与乱序执行.md](CPU流水线与乱序执行.md)；一条指令的五段见 [CPU怎么执行一条指令.md](CPU怎么执行一条指令.md)。
>
> 素材来源：本机 Docker 实测，`perf-lab` 容器（debian:bookworm-slim + `linux-perf 6.1.190` + `gcc 12.2.0`），宿主 Intel i7-6700HQ，WSL2 内核 6.18.54.1，容器 `--privileged`、无 CPU 配额。

## 一、从零：排序与随机，只差这一件事

**本节要点**：同一份代码、同一个数组长度、同一个分支条件，只把数组排了个序，耗时差 3.1 倍。控制变量做到了「指令数几乎相同」，所以差异只能归给「猜得准不准」。

### 1.1 实验代码

```c
/* branch.c */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

#define N 32768
static int arr[N];

static int cmp(const void *x, const void *y) { return *(const int *)x - *(const int *)y; }

int main(int argc, char **argv)
{
    unsigned int seed = 12345;
    long sum = 0;

    for (int i = 0; i < N; i++) {
        seed = seed * 1103515245u + 12345u;
        arr[i] = (int)((seed >> 16) & 0xFF);      /* 0 ~ 255 随机 */
    }
    if (argc > 1 && strcmp(argv[1], "sorted") == 0)
        qsort(arr, N, sizeof(int), cmp);

    for (int r = 0; r < 2000; r++)                 /* 重复扫 2000 遍 */
        for (int i = 0; i < N; i++)
            if (arr[i] >= 128) sum += arr[i];

    printf("%ld\n", sum);
    return 0;
}
```

随机数组里 `arr[i] >= 128` 大约一半真一半假，**分支走向没有规律**；排序之后前一半全假、后一半全真，**预测器只要记住「上次走了哪」就能全中**。

⚠️ 必须用 `-O0` 编译，否则第四节那个坑会让你测到完全相反的结论。

### 1.2 测量命令

```bash
gcc -O0 -o branch0 branch.c

perf stat -e cycles,instructions,uops_issued.any,branch-misses ./branch0 random
perf stat -e cycles,instructions,uops_issued.any,branch-misses ./branch0 sorted
```

四个事件各有分工：

| 事件 | 量什么 |
|---|---|
| `cycles` | CPU 自己的钟（不是墙钟） |
| `instructions` | 退休的指令条数（**控制变量**） |
| `uops_issued.any` | 发射过的微操作数（含后来被丢弃的） |
| `branch-misses` | 预测失败的分支次数 |

⭐ 第四个事件只数「几次」，不数「赔多少」——赔多少要靠第三个事件（µop）才能看出来。

## 二、微操作数 3,832M vs 949M

**本节要点**：两边指令数几乎一样（差 1.7%），分支失败差 159 倍，微操作数差 4 倍，时间差 3.1 倍。四个数的关系说明：**预测失败的代价是「扔掉了已经做的工作」，不是「重取一条指令」**。

### 2.1 读数

| | cycles | instructions | IPC | uops_issued | **µop / 指令** | branch-misses | 时间 |
|---|---|---|---|---|---|---|---|
| `random` | 1,623,051,735 | 887,439,653 | 0.55 | 3,832,556,346 | **4.32** | 32,019,699 | 0.667 s |
| `sorted` | 509,054,047 | 902,208,237 | 1.77 | 948,693,519 | **1.05** | 201,268 | 0.215 s |

![分支预测的代价：指令数几乎相同，微操作数差 4 倍，时钟周期差 3.2 倍](images/分支预测的代价.svg)

读法：三组柱子都按 `random / sorted` 成对比较。**指令数几乎一样**（8.87 亿 vs 9.02 亿，差 1.7%），这是这个实验最关键的控制变量——两边做的活完全相同。差异全部出现在后两组：分支失败 159 倍，微操作 4 倍。

### 2.2 4.32 这个数字是什么意思

这里最值得看的是 **µop / 指令 = 4.32**。`sorted` 是 1.05，说明正常情况下一条 x86 指令约等于一个微操作；`random` 涨到 4.32，多出来的 3.27 倍全是**投机执行后又被丢弃的 µop**——CPU 沿着猜错的方向取了指、译了码、甚至执行了一部分，最后整段作废。

⭐ 这就是「分支预测失败」的真实成本：不是「重取一条指令」，而是**扔掉一条链路上已经做过的所有工作**。

### 2.3 159 倍的分支失败是怎么来的

32,019,699 ÷ 201,268 ≈ 159。两个数各自对应一种预测器行为：

- `sorted`：前 16384 个元素全不满足、后 16384 个全满足。**每个分支在 2000 轮扫描里连续 16384 次走向相同**，预测器只要「记住上次」就基本全中。剩下的 20 万次失败来自每轮扫描交界处的那几次翻转（2000 轮 × 16384 元素，翻转点约 2000 次，实际失败 201,268，说明交界处平均赔了上百次）。
- `random`：走向与前 64 次历史无关，任何基于历史的预测器都只能 50% 猜。32,019,699 / (32768 × 2000) ≈ 0.49——**正好一半**，这就是「纯随机时预测器的天花板」。

⭐ 这个 0.49 反过来成了判据：**如果 `branch-misses` 占比接近 50%，说明分支本身没有可预测的模式，再怎么调代码也没用，只能改算法（分支换成算术）或改数据布局（让模式出现）**。

## 三、为什么浪费 4 倍微操作只慢 3.2 倍

**本节要点**：被浪费的工作里**只有一部分在关键路径上**。乱序引擎在等预测结果的同时还能推进其他无关的指令，所以 4.32 倍 µop 不必换算成 4.32 倍时间。

### 3.1 4.32 → 3.19 的折扣

实测 cycles 比是 1,623,051,735 / 509,054,047 ≈ 3.19，µop 比是 4.04。两者不等，差的那部分就是「乱序引擎在等待时干了别的活」。

这个差值本身也说明一件事：**CPU 的资源利用率在预测失败时并没有掉到底**——它还在用剩下的窗口干别的活。真正的性能杀手是「预测失败 + 长依赖链」同时出现，那时候没有别的活可以填。

### 3.2 什么情况下会赔满

| 条件 | 赔偿倍数 | 原因 |
|---|---|---|
| 分支密集 + 无其他工作 | 接近 µop 比 | 窗口里全是废活，没有别的可推进 |
| 分支密集 + 长依赖链 | 可能**超过** µop 比 | 清空后要重新等依赖，尾部延迟叠上来 |
| 分支稀疏 | 远小于 µop 比 | 一次失败的代价被大量正常指令摊薄 |

⭐ 判据：**看 µop / 指令 这个比值，而不是看 branch-misses 的绝对值**。3,832M 次 µop 摊在 8.87 亿条指令上就是 4.32——这个比值才是「每一次有用指令都被迫陪跑多少废活」。

## 四、编译器把分支换成 `cmov`

**本节要点**：用 `-O1` 编同一份代码，两档读数会**反过来**。原因不是预测器变了，而是**没有分支了**——编译器把「条件跳转 + 赋值」改成了条件传送。测分支行为时，这是最容易掉进去的坑。

### 4.1 读数反转

| | cycles | branch-misses |
|---|---|---|
| `random`（`-O1`） | 166,143,831 | 18,465 |
| `sorted`（`-O1`） | 188,794,706 | 188,432 |

排序反而更慢、分支失败反而更多。表面看起来「预测器变笨了」，实际是分支被删掉了。

### 4.2 反汇编证据

```text
0000000000001190 <clip>:
    1190:  31 d2          xor    %edx,%edx
    1192:  89 f8          mov    %edi,%eax
    1194:  83 ff 7f       cmp    $0x7f,%edi
    1197:  0f 4e c2       cmovle %edx,%eax      ; ← 没有 jcc
    119a:  c3             ret
```

**没有 `jcc` 了**。编译器把 `i >= 128 ? i : 0` 改成了条件传送（`cmov`），于是根本不存在「预测」这件事——两种输入的数据依赖完全一样，耗时差异只剩数据局部性那点噪音。

`-O1` 下 `sorted` 反而慢，是因为 `qsort` 这个过程本身污染了缓存，而 `random` 那档省掉了这一步（`random` 不排序）。**读数反转的真正原因是实验多做了一个 `qsort`，不是分支**——这也说明为什么「两档对比」必须让唯一的差别就是分支走向。

### 4.3 判据与验证

| 现象 | 判据 |
|---|---|
| 该有分支的地方没有 `jcc` | 被 `cmov` / `setcc` 替换了 |
| 排序反而更慢 | 先查两档之间是不是只有「排序」这一个差别 |
| `branch-misses` 在两档都极小 | 分支已经不存在，这个事件失去意义 |

```bash
objdump -d --no-show-raw-insn branch | sed -n '/<main>:/,/^$/p' | grep -E "j[a-z]+|cmov"
```

⭐ 一句话：**测分支预测之前，先证明那里真的还有分支**。

## 五、预测器靠什么记

**本节要点**：现代预测器不是「记住上次走哪」这么简单，而是用**全局历史 + 分支地址**索引一张模式表。这解释了为什么「一半一半的随机」不可救，而「周期性模式」即使不排序也能被学会。

### 5.1 两代结构

| 代 | 结构 | 能学会什么 | 学不会什么 |
|---|---|---|---|
| 一阶（bimodal） | 每地址一个 2 位饱和计数器 | 「这个分支通常走哪边」 | 依赖历史的条件分支 |
| 二阶（BHT + 全局历史） | 用「最近 k 次分支的走向组合」去索引计数器表 | 「这个模式出现过」 | 历史长度超过 k 的模式 |
| 现代（TAGE 类） | 多个不同长度的历史表叠加 + 长历史兜底 | 能从长历史里找出周期模式 | 真正的随机 |

关键是**全局历史寄存器**（GHR）：它把最近几十次分支的走向压成一个二进制串，这个串直接当索引的一部分。所以预测器看的是「上下文」，不是单条分支。

### 5.2 这解释了两个现象

**① 为什么排序之后全中**：排序后每个分支的走向与前 16384 次完全相同，GHR 里那一段历史是稳定的，索引到的计数器每次都是同一个，很快饱和到「全真」或「全假」。

**② 为什么随机之后正好 50%**：LCG 生成的 0~255 值与阈值 128 比较，走向与历史无关，任何索引到的计数器都在 50% 附近抖。实测 0.49 就是这个天花板。

### 5.3 周期扫描：台阶在 64 与 128 之间

让一条分支按固定周期交替，周期从 2 扫到 1024。**周期 ≤64 时每次翻转几乎不赔（≤0.02 次），到 128 突然赔到 1.82 次——差一百倍**。这是台阶，不是渐变。

```c
/* predict.c —— 分支用内联汇编手写，避免 -O2 把它换成 cmov */
#define BR(cond)                                                  \
    asm volatile("testq %1,%1\n\tjz 1f\n\taddq $1,%0\n1:"      \
                 : "+r"(acc) : "r"(cond) : "cc")

for (long i = 0; i < n; i++) {
    long c = (i >> s) & 1;        /* s = 0..9 → 走向周期 2^(s+1) */
    BR(c);
}
```

为什么必须手写这一段：第四节量过，`-O1` 会把条件赋值换成 `cmovle`，那时 `branch-misses` 直接失去意义。这里用 `-O2` 编外层循环（让循环本身跑得快），但**分支指令在汇编里，编译器动不了**。

外层跑 16 轮，每轮 2^23 次，共 2.688e8 个分支；每个 s 跑 3 次取最少的一轮：

| s | 走向周期 | branch-misses（3 轮） | 占分支总数 | **每次翻转赔几次** |
|---|---|---|---|---|
| 0 | 2 | 56,170 / 68,056 / 86,855 | 0.021% | 0.0004 |
| 1 | 4 | 64,207 / 40,792 / 38,966 | 0.014% | 0.0006 |
| 2 | 8 | 95,014 / 45,545 / 51,656 | 0.017% | 0.0014 |
| 3 | 16 | 62,417 / 51,837 / 54,505 | 0.019% | 0.0031 |
| 4 | 32 | 130,802 / 61,857 / 80,388 | 0.023% | 0.0074 |
| 5 | 64 | 73,571 / 134,937 / 97,935 | 0.027% | 0.0175 |
| 6 | 128 | **3,813,581** / 3,925,457 / 4,111,181 | **1.42%** | **1.82** |
| 7 | 256 | 3,400,869 / 3,558,918 / 3,539,272 | 1.27% | 3.24 |
| 8 | 512 | 1,688,477 / 1,729,266 / 1,733,854 | 0.63% | 3.22 |
| 9 | 1024 | 821,498 / 838,515 / 846,483 | 0.31% | 3.13 |

![预测器的历史覆盖台阶：周期 64 以内全中，128 起每次翻转都要赔](images/预测器的周期台阶.svg)

读法：**只看「占分支总数」那一列会得出错误结论**——s=7 比 s=6 的误判率更低（1.27% vs 1.42%），s=9 更是只有 0.31%，看上去「周期越长越好」。真相在最后一列：周期越长，翻转次数越少（总分支 ÷ 周期），所以误判总数下降，但**每次翻转要赔的次数从 0.0175 跳到了 1.8~3.2**。

⭐ 所以判据是「每次翻转赔几次」，不是「误判率多高」。这张表把它拆成两个量：

```text
每次翻转赔几次 = branch-misses ÷ (总分支数 ÷ 走向周期)
```

- 周期 ≤ 64：**≤0.0175**，也就是绝大部分翻转都没赔——预测器把整个周期记住了。
- 周期 ≥ 128：**1.8~3.2**，每次翻转都要赔，而且赔不止一次（TAGE 要几次才切换过来）。

结论：**这台机器的预测器能完整记住长度 ≤64 的走向模式，到 128 就记不全了**。所谓「容量台阶」落在这里——它是**历史覆盖长度**的台阶，不是表条目数的台阶。

### 5.4 分支个数从 1 加到 32：不跳

同一份代码里放 1 到 32 个静态分支点，每个都按「真一次假一次」交替。**每分支误判率始终在 0.005%~0.05% 之间，没有随分支数上升**。这说明 32 个分支点远没到预测器表的容量上限。

```c
/* K 个静态分支点排在一个循环体里，条件相同（每轮 i 交替一次） */
asm volatile(".rept " #K "\n\t"
             "testq %1,%1\n\tjz 1f\n\taddq $1,%0\n1:\n\t"
             ".endr"
             : "+r"(acc) : "r"(c) : "cc");
```

| 静态分支点 | 分支总数 | 最小 branch-misses | 每分支误判率 |
|---|---|---|---|
| 1 | 2.69e8 | 23,705 | 0.0088% |
| 2 | 4.04e8 | 188,716 | 0.047% |
| 4 | 6.72e8 | 97,035 | 0.014% |
| 8 | 1.21e9 | 76,589 | 0.0063% |
| 16 | 2.28e9 | 124,329 | 0.0055% |
| 32 | 4.43e9 | 208,880 | 0.0047% |

读法：六档全在同一个量级，没有单调上升的趋势（2 个分支点那档反而最高，0.047%，是本轮唯一一个说不清原因的读数）。**分支点数从 1 加到 32，预测器一点没吃力**。

⚠️ 这个实验只能证伪「容量小于 32」，证不出容量到底多少。要测容量得把分支点做到几千个——但那样循环体会超出 µop cache 的容量，读数里就混进了前端的成本（这个上限本身在 [CPU怎么执行一条指令.md](CPU怎么执行一条指令.md) 3.5 量过），所以本轮没继续往上加。

⭐ 实用判据：**热点代码里有几十个分支点，不用担心预测器的「条目数」**。真正会撞的是 5.3 那个「历史长度」上限——也就是**分支走向的周期超过 64 就会开始赔**，与分支有多少个无关。

### 5.5 为什么台阶偏偏落在 64

TAGE 类预测器由多张「不同历史长度」的表叠成，历史长度通常取 2 的幂。实测的「≤64 全中、128 起全赔」与「最长那张可用表的历史长度在 64~127 之间」这个结构吻合。**这是解释，不是证明。**

公开资料里 TAGE 的结构：好几张表，第 i 张用「最近 L_i 次分支的走向」当索引，L_i 一般取 8、16、32、64、128……这样的几何级数；预测时挑「命中的最长历史表」，都命不中就退回短表。

按这个结构对照实测：

| 实测现象 | 结构上的对应 |
|---|---|
| 周期 2~64 全中 | 有某张表的历史长度覆盖了整个周期，模式被完整记住 |
| 周期 128 起每次翻转都赔 | 最长可用的那段历史盖不住 128 的周期，只能退回短表猜 |
| 每次翻转赔 1.8~3.2 次而不是 1 次 | 翻转之后短表的计数器还没转到另一侧，要跟几次才到位 |

⚠️ 这是**用公开结构解释本机读数**，不是从读数反推结构。本机既拿不到 TAGE 的参数，也没跑通 `branch-stack` 一类的采样事件，所以「最长那张表到底几位」证不出来——只能说到「有效历史长度落在 64~127 之间」。

⭐ 对写代码的意义很直接：**分支走向的周期超过 64，预测器就帮不上忙了**。典型例子是「每 N 次走一次」的环形缓冲区边界判断（N > 64）、按固定步长轮询的哈希桶、周期上百的定时任务判断。这类分支的对策不是调优参数，是**改成算术**（`cmov` / 掩码）或者**改数据布局**让模式变短。

## 六、把分支换成算术，到底值不值

**本节要点**：同一份求和，一版留条件分支、一版用掩码写成无分支，跑同一份数据。**数据随机时无分支快 4.8 倍（12.86 → 2.69 周期每元素）；数据排好序后无分支反而慢 30%（2.06 → 2.69）**。分界线不在「有没有分支」，在「分支猜不猜得中」——无分支写法固定的代价是每元素多 4.5 条指令。

### 6.1 两版求和，只差条件怎么表达

前五节一直在说「猜错很贵」，也一直给同一个建议：把条件换成算术。但**这个建议从没被量过**——它值多少、什么时候亏，本节补上。

```c
/* branchfree.c —— 同一个数组、同一个求和、同一个阈值 128 */

/* 有分支：条件判断是真正的控制流 */
__attribute__((noinline)) static long sum_br(const int *a, long n)
{
    long s = 0;
    for (long i = 0; i < n; i++) {
        long v = a[i];
        asm volatile("cmpq $128, %1\n\tjl 1f\n\taddq %1, %0\n1:"
                     : "+r"(s) : "r"(v) : "cc");
    }
    return s;
}

/* 无分支：v >= 128 ? v : 0 写成掩码 v & -(v>=128) */
__attribute__((noinline)) static long sum_bf(const int *a, long n)
{
    long s = 0;
    for (long i = 0; i < n; i++) {
        long v = a[i];
        s += v & -(v >= 128);
    }
    return s;
}
```

有分支那版**必须手写汇编**：`if (a[i] >= 128) s += a[i];` 用 `-O2` 编出来是 `setg` / `neg` / `and`，也就是第四节那个坑——编译器早就替你换成无分支了，那时候两版就都成了无分支，实验失去意义。

编译用 `gcc -O2 -fno-tree-vectorize`（两边都关向量化，只比分支结构）：

```text
sum_bf:  mov (%rdi),%edx        # 取数
         xor %eax,%eax
         cmp $0x7f,%edx         # 和 127 比
         setg %al               # 条件 → 0/1，不是跳转
         add $0x4,%rdi          # 指针后移
         neg %eax               # 0 → 0，1 → -1
         and %edx,%eax          # 掩码：v & -(v >= 128)
         cltq
         add %rax,%rcx
         cmp %rdi,%rsi          # 循环回边
         jne ...

sum_br:  movslq (%rdi),%rdx     # 取数
         cmp $0x80,%rdx         # 和 128 比
         jl ...                 # ← 条件跳转在这里
         add %rdx,%rax          # 只有走这条路才执行
         add $0x4,%rdi
         cmp %rcx,%rdi
         jne ...
```

⭐ 无分支版每个元素多 **4.5 条指令**（实测 11.02 vs 6.53，见 6.2）——净增的是 `xor` / `setg` / `neg` / `and` / `cltq` 这一串。这就是它的**固定代价**：与数据无关，永远要付。

⚠️ 注意 `sum_br` 的 `add %rdx,%rax` **在分支里面**，只在条件成立时才执行。所以它的静态指令是 7 条，动态只有 6.53 条——另一半元素跳过了这一条。这个差额本身也是证据：有分支那版干的活更少，代价全在「跳错了要清空流水线」上。

### 6.2 读数：随机快 4.8 倍，排序慢 30%

数组 16384 个 `int`（0~255，恰好一半过阈值），外层重复 40000 次，共 6.5536 亿个元素。每档 3 轮取最快一轮：

| 档 | cycles | 周期/元素 | 指令/元素 | 条件分支误判率 | IPC |
|---|---|---|---|---|---|
| 有分支 + 随机 | 8,429,628,200 | **12.86** | 6.53 | 46% | 0.51 |
| 有分支 + 排序 | 1,349,255,137 | **2.06** | 6.52 | 0.05% | 3.16 |
| 无分支 + 随机 | 1,759,852,675 | **2.69** | 11.02 | — | 4.10 |
| 无分支 + 排序 | 1,760,053,243 | **2.69** | 11.02 | — | 4.10 |

![同一份数组：有分支在随机数据上慢 4.8 倍，在有序数据上反而快 30%](images/无分支写法的收益边界.svg)

读法：**先看「无分支」那一对——两个完全相同的 2.69**。它跟数据顺序一点关系都没有，因为它没有可预测性依赖：不管数据怎么排，每个元素都是同样的 11 条指令。

对比「有分支」那一对：同样的 6.5 条指令，随机 12.86、排序 2.06，差 6.2 倍。差别只在于那 46% 的误判——每元素平均赔 0.46 次误判，每次约 23 个周期（12.86 − 2.06 = 10.80 周期总差额 ÷ 0.462）。

三个能直接用的结论：

1. **随机数据下，无分支快 4.8 倍**（12.86 → 2.69）。多付 4.5 条指令，换掉 0.46 次误判，赚得极多。
2. **有序数据下，无分支慢 30%**（2.06 → 2.69）。这时那 4.5 条指令是纯亏——预测器本来一分钱不收。
3. **无分支版的 IPC 是 4.10**，已经贴着 4 宽退休上限。注意它比 [CPU怎么执行一条指令.md](CPU怎么执行一条指令.md) 3.4 量到的 3.78 条/周期**还高**：那个实验的循环体是 2048 条 nop，超出了 µop cache、每次要走译码器；这里循环体只有 16 条指令，常驻 µop cache，按微操作供给，不受译码带宽限制。两个读数不矛盾，量的是前端的两条不同路径。

### 6.3 判据：什么时候换，什么时候别换

不用猜数据分布，**量一件事就够**：这条分支的误判率。

| 误判率 | 该怎么写 | 理由 |
|---|---|---|
| < 5% | **保留分支** | 预测器几乎全中，无分支只是白付指令 |
| 5% ~ 20% | 看分支两端的代价 | 无分支要求两边都能先算出来；有副作用就不能换 |
| > 20% | **换成算术** | 本例 46% 时收益 4.8 倍，赔率极高 |

误判率怎么拿：`perf stat -e branch-misses,branches` 对着这段代码跑一次，两者相除。⚠️ 这是**采样整段程序**的数，不是单条分支的数；要单条的得用 `perf record` + 反汇编定位（`perf annotate`），本轮没做。

⭐ 两条不能换成算术的情形，与收益无关、与正确性有关：

- **分支两端有副作用**（写文件、改全局、抛异常）。掩码写法要求两边都能先算出来，副作用不能"算一半"。
- **分支两端代价差很大**（一边是函数调用或除法）。有分支时猜对就跳过，无分支则每次都要付两边的钱——这正是 [CPU流水线与乱序执行.md](CPU流水线与乱序执行.md) 4.5 那个「填充不能自己成为瓶颈」的同一条道理。

⚠️ 本节的「有分支」那一版是**手写汇编**，不是编译器自然产出的代码——因为 `-O2` 会把它换成 `setg`/`and`（见 6.1）。所以这张表量的是「两种表达方式的硬件代价」，不是「两份同样自然的 C 代码谁更快」。真实项目里你没得选：编译器基本都会选中无分支那一版。

## 七、五组结论

**本节要点**：赔偿要用「µop / 指令」这个比值来量，不是数分支失败次数；50% 是随机模式的天花板；容量台阶在历史长度上；把分支换成算术只在误判率高时划算；测之前先确认那里还有分支。

1. **预测失败的代价是「扔掉已做的工作」，不是「重取一条指令」**。控制住指令数后，µop / 指令 从 1.05 涨到 4.32，这才是赔偿的度量。
2. **50% 的分支失败率是随机模式的天花板**。看到这个数就别再调代码了——要么改算法（把分支变成算术，如 `sum += arr[i] & -(arr[i] >= 128)`），要么改数据布局（让模式出现，如分桶）。
3. **预测器的容量台阶在「历史长度」，不在「分支个数」**。走向周期 ≤64 时每次翻转只赔 0.0175 次，到 128 跳成 1.82 次（一百倍）；而静态分支点从 1 加到 32，每分支误判率一直停在 0.005%~0.05%，没有别名。判据要看「每次翻转赔几次」，不是「误判率百分比」。
4. **把分支换成算术的收益完全取决于误判率**。同一份求和，随机数据下无分支快 4.8 倍（12.86 → 2.69），排序数据下慢 30%（2.06 → 2.69）。无分支的固定代价是每元素多 4.5 条指令，收益是省掉 0.46 次误判——误判率低于 5% 就该保留分支。
5. **测之前先确认那里还有分支**。`-O1` 会把 `i >= 128 ? i : 0` 变成 `cmovle`，`branch-misses` 立刻失去意义，甚至让两档读数反转。

## 校验口径

> ✅ 实测（`perf-lab` 容器 = debian:bookworm-slim + `linux-perf 6.1.190` + `gcc 12.2.0`，`--privileged`，无 CPU 配额；宿主 Intel i7-6700HQ，WSL2 内核 6.18.54.1，`perf_event_paranoid=2`）：

- **主实验**：`branch.c` 用 `gcc -O0` 编译，`random` 与 `sorted` 各跑一次，`perf stat -e cycles,instructions,uops_issued.any,branch-misses`。指令数 887,439,653 vs 902,208,237 是刻意核对过的控制变量（差 1.7%）。
  - ⚠️ **各只跑了 1 次**，没有取多轮区间。三档之间的差距（3.1 倍）远大于常见抖动（1% ~ 3%），但严格说这是单次读数。
- **周期扫描（5.3）**：`predict.c` 用 `gcc -O2` 编译（分支在 `asm volatile` 里，`-O2` 换不成 `cmov`），`taskset -c 2` 绑核，`perf stat -x, -e cycles,instructions,branches,branch-misses`，s=0..9 每档 3 轮取最少。
  - 每档分支总数 2.688e8（16 轮 × 2^23）。误判率 = branch-misses ÷ 2.688e8；「每次翻转赔几次」= branch-misses ÷ (2.688e8 ÷ 走向周期)。
  - ⚠️ 3 轮之间抖动很大（`s=0` 56k~87k、`s=5` 74k~135k），所以取**最少**而不是平均：误判是只会多不会少的事件，最小值最接近「没有外部干扰」的那次。
- **分支个数扫描（5.4）**：同上的编译与绑核方式，K = 1/2/4/8/16/32，每档 3 轮取最少。分支总数随 K 线性增长（2.69e8 ~ 4.43e9）。
  - ⚠️ K=2 那档的 0.047% 明显高于其它各档，本轮**没有找到原因**，如实列出。
- **无分支对照（6.2）**：`branchfree.c` 用 `gcc -O2 -fno-tree-vectorize` 编译（两边都关向量化，只比分支结构），`taskset -c 2` 绑核，`perf stat -x, -e cycles,instructions,branches,branch-misses`，四档各 3 轮取最快一轮。
  - 总元素 6.5536e8（40000 轮 × 16384）。周期/元素 = cycles ÷ 6.5536e8：8,429,628,200 → 12.86；1,349,255,137 → 2.06；1,759,852,675 → 2.69；1,760,053,243 → 2.69。
  - ⚠️ **函数指针必须是 `volatile`**。第一版直接写 `tot += sum_bf(rnd, N)`，`-O2` 认出 `sum_bf` 是纯函数、参数又不变，把整次调用提到循环外——6.5 亿个元素只跑了 830 万条指令（0.015 周期/元素），读数完全无效。改成 `volatile` 函数指针后指令数才回到 7.22e9。
  - ⚠️ 有分支那版是**手写内联汇编**（`cmpq $128` + `jl`）。不这么写 `-O2` 会编成 `setg`/`neg`/`and`，两档就都成了无分支。反汇编已核对：`sum_br` 有 `jl`，`sum_bf` 除循环回边外无 `jcc`。
  - 两边校验和相同（62,965,920,000），确认在算同一件事。
- **`-O1` 对照**：同一份 `branch.c` 用 `gcc -O1` 再编一次，读数见 4.1（`random` 166,143,831 cycles、`sorted` 188,794,706）。
- **`cmov` 的证据**：`bytes.c` 里 `clip(int i) { return i >= 128 ? i : 0; }`，`gcc -O2` 编出 `0f 4e c2`（`cmovle`），无 `jcc`。
- **比值**：µop / 指令 = uops_issued / instructions，由上面两个数直接相除（3,832,556,346 / 887,439,653 = 4.32；948,693,519 / 902,208,237 = 1.05）。cycles 比 3.19 与 µop 比 4.04 的差额在 3.1 节讨论。

⚠️ **未实测 / 边界**：

- **预测器的结构、GHR 长度、TAGE 表数都不是本机测出来的**，来自公开的微架构资料，只当机制描述。5.3 只量到「有效历史长度在 64~127 之间」这个区间，**没有量出具体位数**。
- **单条分支的误判率没有单独测**（6.3 的判据依赖它）。6.2 拿到的是「整段程序」的 `branch-misses / branches`，要定位到具体某条分支需要 `perf record` + `perf annotate`，本轮没做。
- **`branch-misses` 的绝对值在虚拟化环境里可能偏**。WSL2 下的 PMU 是透传的，本轮没做裸机对照。
- **只有 x86-64 的读数**，且是 WSL2 虚拟机内的 4 个逻辑处理器。arm64 的预测器实现与分支指令形态不同，不能照搬。

## 延伸追问

- **分支预测器怎么学会「前一半假后一半真」？** 靠历史表（BHT）+ 全局历史寄存器：它记录「最近几十次分支的走向组合」，用这个组合去索引一张预测表。排序后的分支走向是「连续 16384 次假，再连续 16384 次真」，历史表能看到「上次这一条也是假」，于是预测假。随机数组则没有任何可利用的历史模式，只能 50% 猜。
- **`cmov` 为什么不是万能的？** 它把控制依赖变成了数据依赖——两条路都要算（`cmovle` 要等 `edx` 和 `eax` 都就绪），而且分支两端如果有昂贵操作就白算了。所以只在「两个简单值二选一」时划算。这也是为什么 4.2 里 `sorted` 反而慢：`cmov` 的代价是恒定的，`sorted` 那点「数据局部性好」的红利抵不过 `qsort` 带来的缓存污染。
- **分支能不能彻底消掉？** 能，代价是算力。`if (x >= 128) sum += x;` 可以写成 `sum += x & -(x >= 128);`——无分支，但每次都要算乘加。分支预测的收益本质上就是「省掉一半的算术」，所以数据随机时无分支写法反而更快（这在 `-O2` 下常被编译器自动选中）。
- **Spectre 和分支预测是什么关系？** 投机执行留下的痕迹（缓存状态）可以被另一个进程测出来，这就是 Spectre 一类攻击的物理基础。修补手段（`lfence` / `retpoline` / IBRS）本质上是「限制投机能走多远」，代价正是本篇量的那部分性能——所以每次 CPU 漏洞补丁都会带来几个百分点的性能回退。
