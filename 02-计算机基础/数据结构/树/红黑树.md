# 红黑树

> 不用「高度差」而用「**颜色**」约束平衡：五条性质共同推出「最长路径 < 2 × 最短路径」，
> 于是树高被钉在 `O(log n)`；插入修复只有三种情况 —— **变色可能 `O(log n)` 次，但旋转最多 2 次**。

## 一、红黑树的五条性质是什么？

**本节要点**：红黑树不用「高度差」约束，而用**颜色约束**。五条性质共同推出「最长路径 ≤ 2 × 最短路径」，从而保证 `O(log n)`。

### 1.1 五条性质

| # | 性质 | 作用 |
|---|---|---|
| **1** | 每个节点**非红即黑** | 定义域（颜色是一个 bit） |
| **2** | **根节点是黑** | 消除边界特判，便于归纳 |
| **3** | 所有 **NIL 叶子是黑** | 让「空孩子」也有颜色，路径长度才好对齐 |
| **4** | **红节点的两个孩子都是黑** | 禁止「父子双红」→ 红色不能连续 |
| **5** | 从任一节点到其所有 NIL 叶子的路径上，**黑节点数相同** | 核心：各路径的「黑高」一致 |

⭐ **性质 4 与 5 是主角**：**4 限制「红色不能连续」，5 限制「黑色分布均匀」** —— 两者合起来把树高夹住。

红黑树里，真正存储数据的节点叫内部节点。<br/>
如果一个内部节点没有左孩子或右孩子，那个“空位置”在算法上不当作真正的空，而是看作一个叶子节点，记作 NIL。
- NIL 不存数据，只是一个逻辑上的哨兵。
- 所有空指针都指向它，或者直接表示为 nil / null。
- 红黑树规定：这些 NIL 叶子的颜色是黑色。

### 1.2 「最长路径 ≤ 2 × 最短路径」的推导

设某节点的**黑高为 `bh`**（到 NIL 的路径上黑节点数，含 NIL 不含起点）。

**第一：最短路径 = `bh`（全黑）。** 由性质 5，每条路径的黑节点数都相同 = `bh`；路径上可能还有红节点，所以路径长度 ≥ `bh`。**取到 `bh` 的那条路（全黑）就是最短路径。**

**第二：最长路径 ≤ `2·bh − 1`。** 由性质 4，**红节点不能相邻** → 任一路径上「红节点数 ≤ 黑节点数」→ 路径上总节点数 ≤ `2 × 黑节点数 = 2·bh`。再抠掉端点细节，得到 `≤ 2·bh − 1`。

**第三：合起来** `最长 / 最短 ≤ (2·bh − 1) / bh < 2`。∎

⭐ **一句话直觉版**：**最短的那条路全黑，最长的那条路「红黑相间」** —— 红黑相间最多是「全黑」的两倍长，所以高度被夹在 `[bh, 2bh]` 里。

![红黑树：靠两条颜色性质把树高夹在 O(log n)](images/红黑树的性质与高度界.svg)

⭐ 图里三块分别回答三个问题：**黑高怎么数**（左）、**最长 / 最短怎么夹出来**（右上）、**校验器跑出来是什么样**（右下，就是 1.3 的读数）。

### 1.3 性质校验器实测

⚠️ **红黑树最值得写一个校验器**：五条性质是「不变量」，而旋转/变色的 case 极易写错（少一个变色、转错方向，树可能「看起来正常」但性质已破）。本机用 Go 手写插入 + 校验器，n = 10000 随机键（实跑）：

```text
===== 红黑树：插入 + 五条性质校验器 =====
n = 10000，插入 1..n 的随机排列
性质 1（节点非红即黑）      : 通过（颜色只有红/黑两种取值）
性质 2（根节点是黑）        : 通过（根 = 5804）
性质 3（所有 NIL 叶子是黑） : 通过（nil 一律按黑处理，无红叶子）
性质 4（红节点的孩子都是黑）: 通过
性质 5（各条路径黑高相同）  : 通过
整树黑高（把 NIL 也算作黑） : 9
最长根到叶路径（节点数）    : 16
最短根到叶路径（节点数）    : 11
最长 / 最短 = 1.45 ≤ 2       : 通过

===== 附：故意破坏性质，验证校验器真的在检查 =====
(a) 把根染红              → 性质 2 = 失败
(b) 把红节点 2737 的孩子染红 → 性质 4 = 失败
```

⭐ **最后两行是关键的自检**：**校验器如果永远只报「通过」，你没法确认它真的在查。** 故意把根染红、把一个红节点的孩子染红，校验器**立刻分别报出性质 2、性质 4 失败** —— 这才证明校验逻辑有效（这是「实验设计要自检」的一个具体例子）。

⭐ 顺带验证 1.2 的推导：`黑高 9`、`最长 16`、`最短 11`，`16 / 11 = 1.45 < 2` ✅ —— **实测的比值落在推导给出的 `[1, 2)` 区间内**。

### 1.4 插入修复的三种情况

红黑树的插入修复（`fixInsert`）只有三种情况（对称算六种）：

| 情况 | 条件 | 处理 |
|---|---|---|
| **1** | 叔叔是**红** | 父与叔叔染黑、祖父染红，**问题上移两层**继续 |
| **2** | 叔叔是黑，且新节点是「内侧」孩子 | 先**旋转**转成情况 3 |
| **3** | 叔叔是黑，且新节点是「外侧」孩子 | 父染黑、祖父染红，**绕祖父旋转**，结束 |

⭐ **注意「变色」与「旋转」的分工**：**情况 1 只变色、不旋转**（代价极小，且会往上传播）；**只有情况 2、3 才旋转**。这正是「红黑树插入最多 2 次旋转」的来源 —— **变色可能发生 `O(log n)` 次，但旋转最多 2 次**。

![红黑树插入修复的三种情况：叔叔是红只变色，叔叔是黑才旋转](images/红黑树的插入修复三种情况.svg)

⚠️ 三种情况的**前提都是「父是红」**（否则本来就不违反性质 4、无需修复）；修复循环结束后别忘了**把根染黑**（性质 2）。

## 二、应用场景

**本节要点**：红黑树是**工程上最常用的内存有序结构** —— 它把「平衡」放松到刚好够用，写维护成本最低。

### 2.1 应用场景总表

| 场景 | 具体产品 / 系统 | 为什么选红黑树 |
|---|---|---|
| **语言标准容器** | Java `TreeMap` / `TreeSet`、C++ `std::map` / `std::set`（⚠️ 常见实现，标准只保证接口与复杂度，不保证底层结构）、.NET `SortedDictionary` | 需要**有序遍历 + 范围查询**，且写操作频繁；红黑树删除旋转最多 3 次，AVL 可能 `O(log n)` 次 |
| **哈希表冲突退化** | Java `HashMap` 桶内链表长度 ≥ `8` 转红黑树（降到 `6` 退回链表） | 桶内元素少时链表够用，一多就退化成 `O(n)`；树化后最坏 `O(log n)`。阈值 `8` 的依据是理想哈希下的泊松分布（`k=8` 约 `6e-8`），退化用 `6` 是为了留回差、避免来回抖动 |
| **操作系统调度** | Linux CFS 调度器（`sched_entity` 按 `vruntime` 组织） | 需要**快速取最小 + 频繁增删**；⭐ 用树而不是堆，是因为要支持**按 `vruntime` 删除任意任务**（睡眠 / 唤醒 / 改权重） |
| **I/O 多路复用** | Linux `epoll` 的 fd 管理 | fd 集合频繁增删，且要快速查找；就绪的 fd 另挂就绪队列 |
| **定时器管理** | Linux `hrtimer`、Nginx 的 `ngx_rbtree` | 需要按到期时间有序，频繁插入 / 删除 |
| **内存区间管理** | Linux 进程地址空间的 VMA | 按地址区间组织，做快速区间查找 |
| **符号表** | 部分编译器的符号表 | 需要有序 + 快速查找 + 频繁插入 |

### 2.2 深入辨析：红黑树在各个系统里具体落在哪一层

**1. `TreeMap` / `TreeSet`：标准库里的有序容器（实跑）**

Java 直接把红黑树做成了 `TreeMap` / `TreeSet`（实跑；Java 侧有序容器与哈希容器的用法体系见 [集合容器.md](../../../01-编程语言/java/集合容器.md)）：

```text
===== Java TreeMap：标准库里的红黑树 =====
插入 5 3 8 1 9 2 7 后按序遍历:
  [1, 2, 3, 5, 7, 8, 9]
firstKey = 1   lastKey = 9
floorKey(6) = 5   ceilingKey(6) = 7
lowerKey(6) = 5   higherKey(6) = 7
subMap(3, true, 8, true) = [3, 5, 7, 8]
headMap(5) = [1, 2, 3]   tailMap(5) = [5, 7, 8, 9]
descendingMap = [9, 8, 7, 5, 3, 2, 1]
size = 7
```

⚠️ **一个诚实提醒**：`TreeMap` **不暴露节点颜色与旋转次数** —— 「它是一棵红黑树」是**文档保证**，不是能在 API 上验证的。**想验证五条性质，只能像 1.3 那样自己手写一棵。** 但它的**有序性 API**（`floorKey` / `ceilingKey` / `subMap`）正是「平衡 + 有序」能提供、而哈希表给不出的能力。

```text
有序插入 1..100000 耗时 : 56 ms（朴素 BST 会退化成 100000 高的链）
全部命中查询          : 100000/100000  耗时 28 ms
```

⭐ **对照 [平衡树.md](平衡树.md) 第一节的实测**：同样「有序插入 10 万键」，朴素 BST 会退化成 `100000` 高的链（查询 `O(n)`），而 `TreeMap` 依然维持 `O(log n)` —— **这就是「平衡」二字的全部价值**。（时序数字随机器波动，只断言「不退化」这个定性结论。）

**2. `HashMap` 的桶内树化：红黑树最容易被忽略的落点**

⭐ 很多人天天用 `HashMap`，**却不知道它内部藏着一棵红黑树**：JDK 8 起，当**同一个桶里的链表长度超过阈值 `8`**，这条链就被**树化（treeify）成红黑树**；元素减少到 **`6`** 时再**退化回链表（untreeify）**。这两个数字是 `HashMap` 源码里的常量 `TREEIFY_THRESHOLD = 8`、`UNTREEIFY_THRESHOLD = 6`（可核验）。

- **为什么不一律用红黑树？** 树节点比链表节点更重（多存 `left` / `right` / 颜色）。桶里元素少时，链表**更省内存、遍历也更快**，树化只在「桶被撞满了」时才有收益。
- **为什么阈值是 8？** 理想哈希下，一个桶内元素数服从泊松分布，`k = 8` 的概率**约 `6e-8`**（JDK 源码注释里的说法）—— 阈值 8 意味着**正常情况下几乎不会树化**，树化只是哈希分布极差（或哈希被恶意构造）时的**兜底**。
- **为什么退化用 6 而不是 8？** 留一个**回差（hysteresis）**，避免元素数在 8 附近反复增删时，**在链表与红黑树之间来回抖动**。

⚠️ **退化的判据是「桶内节点数」，不是「树还平不平衡」** —— 树化后它始终是一棵红黑树；节点太少时退化，只是「不再值得维持树的开销」。

**3. C++ `std::map` / `std::set`：分清「标准保证」与「常见实现」**

⭐ C++ 标准只规定 `std::map` / `std::set` / `std::multimap` / `std::multiset` 的**接口与复杂度**（有序、查找 / 插入 / 删除都是 `O(log n)`），**并不强制底层用红黑树**。实践中，**GCC 的 libstdc++ 用的确实是红黑树**（`std::_Rb_tree`）。

**教材里写「`std::map` 就是红黑树」，严格说是把「实现约定」当成了「语言保证」** —— 别的标准库实现完全可以合法地换一种满足那两个条件的结构。**「标准只保证行为、不保证数据结构」这种措辞，读文档时要能分辨。**

**4. Linux 内核：这套实现的名字叫 `rbtree`**

Linux 内核自带一套红黑树实现（内核里就叫 `rbtree`），是内核最常用的有序结构之一。公开资料里常见的落点：

- **CFS 调度器**：把每个可运行任务的 `sched_entity` 按**虚拟运行时间 `vruntime`** 组织成红黑树，**「挑下一个该跑的任务」就是取最左节点**（`vruntime` 最小的那个）。⭐ **为什么不是堆？** 因为要支持**任意任务的按 `vruntime` 删除 / 重插**（任务睡眠、唤醒、改权重），堆做不到「删除任意元素」这种操作。
- **`epoll`**：`epoll` 实例用红黑树管理**被监控的 fd 集合**（需要频繁增删 fd，又要快速查找；就绪的 fd 另挂在就绪队列里）。epoll 的整体机制与「为什么高效」见 [IO多路复用.md](../../网络/传输层/IO多路复用.md)。
- **高精度定时器（hrtimer）**：就绪定时器按**到期时间**组织，「下一个到期的」就是最小键。⚠️ 定时器还有「时间轮」这条路线，两者的代价对照见 [时间轮.md](../高级数据结构/时间轮.md)。
- **内存管理**：进程地址空间的**虚拟内存区域（VMA）**按**地址区间**组织成红黑树，用于快速的区间查找。Linux 侧地址空间与缺页的处理链路见 [内存管理.md](../../linux/内存管理.md)。

⚠️ 说「Linux 内核用了红黑树」时，**落点就是这几个子系统**；内核自己的实现**名字是 `rbtree`**，不是 `red-black tree`。

**5. Nginx：`ngx_rbtree`**

Nginx 也自带一份红黑树 `ngx_rbtree`，公开资料里最常见的落点是**事件定时器管理**（把各事件的超时时间挂到树上、取最近超时）；Nginx 源码里这套结构的用法见 [05-内存管理与数据结构.md](../../linux/深入理解Nginx/05-内存管理与数据结构.md)，它与事件循环的配合见 [03-事件驱动与epoll.md](../../linux/深入理解Nginx/03-事件驱动与epoll.md)。

**6. 为什么这些位置不用哈希表、也不用 AVL？**

| 位置 | 为什么不是哈希表 | 为什么不是 AVL |
|---|---|---|
| `TreeMap` / `std::map` | 要**有序**：范围查询、`floorKey` / `ceilingKey`、按序遍历 —— 哈希表给不出「下一个更大的键」 | 红黑树删除旋转更少、写更省 |
| CFS 选下一个任务 | 每次都要取「`vruntime` 最小的」，是**有序 + 取极值** | CFS **读写都频繁**（任务反复睡眠 / 唤醒），AVL 删除的多次旋转不划算 |
| `epoll` / `hrtimer` / VMA | 要按**时间 / 地址区间**取「最近的邻居」、或按 fd 频繁增删 —— 哈希表给不出「有序 / 最近」 | 高频插删，红黑树的维护代价更低 |
| `HashMap` 桶内树化 | —— | 桶内需要的是「有序 + 快查」，红黑树够用且比 AVL 写更省 |

⭐ **一句话**：**需要「有序」或「最近的邻居」 → 哈希表出局；既要频繁写又要保持有序 → 在平衡树里选红黑树而不是 AVL。** 这就是红黑树在系统代码里遍地开花的根本原因 —— 也解释了为什么 [平衡树.md](平衡树.md) 第二节的结论是「工程上更常用红黑树」。

### 2.3 收尾判据

**判据**：**内存里维护有序集合、且写操作不少** → 红黑树。
**不适用**：数据在磁盘（→ B+ 树）、写极少读极多且要求最坏树高更矮（→ AVL）、写极多且并发（→ 跳表）。
⭐ **反面对照**：**Redis 的有序集（ZSet）用的是跳表而不是红黑树** —— 见 [跳跃表.md](../高级数据结构/跳跃表.md)。

## 延伸追问

- **红黑树为什么能保证 `O(log n)`？** → 性质 4（红不连续）⇒ 红节点数 ≤ 黑节点数 ⇒ 路径长 ≤ `2 × 黑高`；性质 5（各路径黑高相同）⇒ 最短路径就是全黑的那条 = 黑高。两者合起来 `最长 / 最短 < 2`，树高被夹在 `O(log n)` 内（本节 1.2）。
- **怎么确认红黑树实现是对的？** → 写一个**五条性质的校验器**，且**故意破坏性质验证校验器真的在查**（本机实测：把根染红 → 报性质 2 失败；把红节点的孩子染红 → 报性质 4 失败）。⚠️ 「校验器永远只报通过」说明不了任何事。
- **红黑树插入为什么要「变色 + 旋转」两步？** → 变色处理「叔叔是红」的情况（代价极小、可往上传播），旋转处理「叔叔是黑」的情况。**变色可能 `O(log n)` 次、旋转最多 2 次** —— 这就是「红黑树插入最多 2 次旋转」的来源（本节 1.4）。
- **红黑树的删除呢？** → 删除修复的 case 比插入多，但**旋转仍然最多 3 次**；变色同样可能 `O(log n)` 次。对照 AVL 删除要沿路径回溯、最坏可能 `O(log n)` 次旋转 —— 这个量级差正是工程上更常用红黑树的第一条理由（见 [平衡树.md](平衡树.md) 第二节）。
- **为什么要求「根是黑」「NIL 是黑」？** → 根是黑消除边界特判、便于归纳；给「空孩子」也定成黑，是为了让**每条路径的黑节点数可对齐**（性质 5 才有统一口径）。这两条不是装饰，是让性质 5 能写成「处处相等」的前提。
- **`HashMap` 为什么要树化、阈值又为什么是 8 和 6？** → 桶内链表过长时（哈希分布极差或被恶意构造）查询退化成 `O(n)`，树化成红黑树把它拉回 `O(log n)`；阈值 8 是因为理想哈希下一桶落 8 个键的概率约 `6e-8`（**正常情况下几乎不触发**），退化阈值 6 是为了留一个**回差**、避免在 8 附近反复增删时来回抖动。见本节「Java 的另一半」。
- **Linux 内核为什么用红黑树而不用堆管理 CFS 就绪任务？** → 因为要支持**任意任务按 `vruntime` 删除 / 重插**（任务睡眠、唤醒、改权重），堆只能快速取极值、删除任意元素做不到。红黑树「有序 + 快速增删」正好覆盖这个需求（见本节「Linux 内核」）。
