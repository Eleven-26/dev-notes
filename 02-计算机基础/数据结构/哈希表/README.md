# 哈希表

> 本目录（`数据结构/哈希表/`）收**用「算地址」换掉「逐个比较」**的结构：散列表的原理与退化边界、
> 冲突解决的实现层。它回答的是「**等值查找为什么能 `O(1)`、又会在什么时候失效**」——
> 不管顺序、不管范围，只认「这个键在不在、对应的值是什么」。
>
> ⚠️ 与 [概率与统计/](../概率与统计/README.md) 的分工：那边的位图 / 布隆 / 布谷鸟 / HLL 用**精度**换空间，
> 允许结果出错；本目录的哈希表是**精确结构**，`O(1)` 是平均代价、不是概率保证。
> 判据是「**结果能不能错**」，不是「谁更快」。
>
> 本篇是**入口总纲** —— 回答「两篇各自管什么、什么时候该用哈希表、什么时候必须换结构」。
> 推导、实现与实测在零件篇里，本篇不重复。数据结构目录的整体判据见 [README.md](../README.md)。

## 二、什么时候该用哈希表？什么时候必须换？

**本节要点**：哈希表的唯一能力是**等值定位**。只要需求里出现「序」「范围」「前驱后继」「第 K 个」，它就直接出局 —— 这不是实现问题，而是散列把顺序信息丢掉了。

| 需求 | 能不能用哈希表 | 该换什么 |
|---|---|---|
| 判断键在不在、取对应的值 | ✅ 首选 | — |
| 去重（URL、请求 ID、订单号） | ✅ | — |
| 计数（词频、访问次数） | ✅ | — |
| 缓存 / 字典 / 路由表 | ✅ | — |
| 有序遍历、范围查询 `[a, b]` | ❌ | 平衡树 / B+ 树 / 跳表 |
| 前驱后继、Top-K、第 K 小 | ❌ | 平衡树 / 堆（Top-K 见 [堆与优先队列.md](../堆/堆与优先队列.md)） |
| 前缀匹配、最长前缀 | ❌ | [Trie.md](../树/空间与字符串树/Trie.md) / Radix |
| 超大集合的「可能存在」 | ⚠️ 太占内存 | [位图与布隆过滤器.md](../概率与统计/位图与布隆过滤器.md) |
| 基数 / 频次估算 | ❌ | [基数与频率估计.md](../概率与统计/基数与频率估计.md) |
| 磁盘索引 | ❌ | [B树与B+树.md](../树/磁盘存储树/B树与B+树.md) |

⭐ **一句话判据**：**只问「是哪一个」，用哈希；还要问「排第几、在哪个区间」，换有序结构。**

⚠️ **哈希表不是缓存本身**：LRU 是「哈希表 + 双向链表」的组合 —— 哈希负责 `O(1)` 定位，链表负责淘汰顺序。把哈希表直接叫缓存，会漏掉淘汰策略这一半（见 [缓存淘汰算法.md](../../../03-数据与中间件/数据存储/缓存/缓存淘汰算法.md)）。

## 三、退化防御分两层，不要只盯一层

**本节要点**：哈希表变慢只有两个来源 —— **桶内元素太多**（冲突层）与**负载因子太高**（结构层）。工程实现必须同时处理这两层；只看其中一层，都会在另一种压力下退化。

| 层 | 问题 | 典型手段 | 细节在哪 |
|---|---|---|---|
| **结构层** | 元素数 / 桶数过高，空桶变少 | 负载因子阈值、扩容、渐进式 rehash、桶内升级（链表 → 树） | [散列表.md](散列表.md) 第二节 |
| **冲突层** | 同一个桶里堆了太多键 | 链地址、开放寻址（线性 / 二次 / 双重散列）、Cuckoo、Robin Hood | [开放寻址与冲突解决.md](开放寻址与冲突解决.md) 第一至六节 |

⭐ **两层的代价方向相反**：结构层用**空间 + 一次重排**换低负载；冲突层用**探测 / 指针**换「桶内还能放几个」。⚠️ 只做冲突解决、不做扩容，负载因子最终会把任何探测序列拖成 `O(n)`；只做扩容、不处理冲突，哈希函数一旦集中仍会撞成一堆。

⚠️ **删除是冲突层的额外约束**：开放寻址不能直接把槽位置空，否则探测链断裂、后面的键查不到 —— 必须留**墓碑**（[开放寻址与冲突解决.md](开放寻址与冲突解决.md) 第四节）。链地址没有这个问题，但删除后要能回收节点。

## 五、延伸追问（通用）

- **哈希表为什么不能做范围查询？** → 散列函数把键打散到桶里，**桶序与键序无关**；相邻的键可能落在任意两个桶。范围查询需要「有序遍历」，只能换平衡树 / B+ 树 / 跳表。
- **负载因子为什么不能取 1？** → 桶越满，冲突概率与探测长度上升得越快；开放寻址在接近满时探测长度会急剧变长（见 [开放寻址与冲突解决.md](开放寻址与冲突解决.md) 第三节）。工程上要留余量并提前扩容。
- **链地址和开放寻址怎么选？** → 删除频繁、能接受指针开销 → 链地址；要省内存、缓存友好、以查找为主 → 开放寻址。⚠️ 开放寻址的删除必须留墓碑。
- **为什么开放寻址删除要留墓碑？** → 探测链上的槽位被清空会让后续查找提前停止，后面的键就「消失」了；墓碑标记「这里曾有元素」，保证探测继续。
- **哈希冲突能被恶意制造吗？** → 能。构造大量同哈希值的键可以把 `O(1)` 打成 `O(n)`；工程上用随机化哈希种子 / 带密钥的哈希增加预测难度，具体机制以官方实现为准。
- **哈希表和布隆过滤器是什么关系？** → 哈希表是**精确**存储，布隆是**位级摘要**、只回答「可能存在」。真实系统常串联：布隆先挡掉绝大多数不存在的键，剩下的回源到哈希表（[位图与布隆过滤器.md](../概率与统计/位图与布隆过滤器.md)）。
