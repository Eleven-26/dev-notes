# 基数与频率估计

> 三种**概率结构**的分工：布隆过滤器判"在不在"、HyperLogLog 估"有多少个不同的"、Count-Min Sketch 估"出现了几次"；以及它们的误差方向、内存量与工程取舍。配 Go 实测（HLL 的误差与理论值对照、CMS 的"只高不低"）。
>
> 本篇为**按主题归纳**的算法整理（非逐字摘录），主要依据 HyperLogLog 原始论文（Flajolet et al., 2007）与 Count-Min Sketch 原始论文（Cormode & Muthukrishnan, 2005）；本仓的素材来源索引见 [素材清单.md](../../../素材清单.md)。
>
> ⚠️ 成员判定（布隆）的细节见 [位图与布隆过滤器.md](位图与布隆过滤器.md)，本篇不重复。

## 一、三种概率结构，各自回答一个不同的问题

| 结构 | 回答的问题 | 误差方向 | 内存量级 |
|---|---|---|---|
| **布隆过滤器** | 这个元素**在集合里吗**？ | 只会**假阳性**（说"在"其实不在），**绝不假阴性** | m 个 bit |
| **HyperLogLog** | 集合里有**多少个不同元素**（基数）？ | 有误差，相对标准误 ≈ `1.04/√m` | m 个桶 × 6 bit |
| **Count-Min Sketch** | 这个元素**出现了多少次**（频次）？ | 只会**高估**（只高不低） | d × w 个计数 |

⚠️ 三者都是**用精度换空间**：把"精确"让出一部分，换来**常数级甚至对数级**的内存。所以铁律是——**任何涉及钱、配额、计费的数字都不能用它们**。

## 二、HyperLogLog：从"抛硬币"到估基数

### 2.1 直觉：连续出现 k 次正面，大概抛了 2^k 次

抛一枚均匀硬币，若最长一次连续出现了 **k** 次正面，那这轮实验大概抛了 **2^k** 次。HLL 用的就是这个性质，只不过把"硬币"换成了**哈希值**：

```text
把每个元素哈希成一个足够长的二进制串，看它「从低位起第一个 1 出现在第几位」——这个位置的期望正好是 2
```

⭐ 关键在**哈希的均匀性**：只要哈希够均匀，"前导零的个数"就和"不同的元素有多少个"建立了统计关系 —— **与元素本身是什么完全无关**。

### 2.2 一个桶不够 → 分桶 + 调和平均

单个观测的方差极大（看到 1 个前导零就说只有 2 个元素，太离谱），于是：

1. 把哈希值**切成两部分**：低位定**桶号**（m 个桶），其余位算**前导零位置**；
2. 每个桶记录**见过的最大前导零位置**；
3. 用**调和平均**（而不是算术平均，它对极端值不敏感）汇总 m 个桶，再乘常数修正：

```text
E ≈ α_m · m² / Σ 2^(−M[j])      α_m ≈ 0.7213 / (1 + 1.079/m)
```

### 2.3 误差公式：内存换来什么精度

```text
相对标准误 ≈ 1.04 / √m
```

| 桶数 m | 内存（6 bit/桶） | 相对标准误 |
|---|---|---|
| 1024 | 768 B | **3.25%** |
| 16384（Redis 默认） | 12 KB | **0.81%** |

⭐ **这就是 HLL 的全部价值**：统计 1 亿个 UV，精确去重要存上亿个 ID（GB 级），而 HLL 用 **12 KB** 就能给出 ±1% 以内的答案，而且多个 HLL 还能**直接合并**（`PFMERGE`，取各桶最大值）—— 精确方案做不到这一点。

### 2.4 工程要点

- **Redis**：`PFADD` / `PFCOUNT` / `PFMERGE`，每个 key 最多 12 KB；
- 内部有**稀疏 / 稠密**两种表示：元素少时用稀疏（省内存），超过阈值转稠密（定长 6 bit/桶）；
- ⚠️ 只能估**基数**，不能求交集（`PFCOUNT` 多个 key 是并集基数）；要交集只能自己用别的结构。

## 三、Count-Min Sketch：取最小值的那一行

要估"某个元素出现了多少次"，又不想为每个元素存一个精确计数，CMS 的做法是**多行哈希表**：

1. 开 **d 行 × w 列**的计数表，第 i 行配一个**独立的哈希函数**；
2. 来一个元素 x：把 **d 行对应的格子都 +1**；
3. 查 x 的次数：取出 d 行对应的值，**取最小值**。

⭐ **为什么取最小值**：某个格子的计数 = **真实值 + 所有哈希到它这里的其它元素的计数**，所以每一行都是"真实值 + 一些噪声"，**只会偏大**；而不同行的噪声来源不同，**取最小**就是在"挑噪声最小的那一行"。

**误差的方向是确定的**：

```text
CMS 估计值 ≥ 真实值（只高不低）
```

这与布隆"只可能假阳性"是同一种味道：**概率结构的误差是有方向的**，工程上可以据此选择"宁可高估还是宁可低估"。

**反方向的结构**：要"只低不高"的重元素估计，用 **Space-Saving / Misra-Gries**（维持一个固定大小的候选表，满了就把计数最小的元素挤出去）—— 它的特点是"频次高的元素不会被误删，但计数只会偏低"。

## 四、实测：两种结构的误差长什么样 ⭐

用确定性数据（20 万次插入，其中一半打向 100 个热点 key、一半打向 20 万个长尾 key）：

```text
总插入 200000 次，真实基数（去重后）= 78798 个不同 key

== HyperLogLog：基数估计 ==
桶数 m = 1024，内存 = 1024 字节（按 6 位/桶打包也只要 768 字节）
理论相对标准误 ≈ 1.04/√m = 3.25%
真实基数 78798 → 第 1 轮估算 77713（相对误差 -1.38%）
20 轮实测：平均偏差 -2.05%，标准差 3.11% ← 与理论值同一量级
→ 用 1KB 量级的内存把「有多少个不同 key」估到百分之几；精确计数要存下全部 key

== Count-Min Sketch：频次估计 ==
表：5 行 × 2000 列（40000 字节，若用 uint32）
key            真实次数       CMS 估算     偏差
user:40        1059       1100       +41
user:17        1058       1102       +44
user:26        1058       1085       +27
user:61        1055       1095       +40
user:56        1054       1101       +47
→ CMS 的误差恒为正（哈希冲突只会把别的 key 的计数算到你头上）—— 它就是「只高不低」
→ 想反过来（频次只低不高的重元素估计）用 Space-Saving / Misra-Gries；想判「在不在集合里」用布隆过滤器
```

⭐ **两个数字要会读**：HLL 的 **20 轮标准差 3.11%** 与理论 **3.25%** 基本吻合 —— 这说明"单次估算的误差"是随机的，**不能拿单次结果判断实现对不对**（单次偏 6% 也在 2σ 之内）；而 CMS 的偏差全是 **正号**，是**系统性**的。

## 五、选型：什么场景用哪个

| 需求 | 用 | 为什么 |
|---|---|---|
| 判"这个 key 是不是已存在"（爬虫去重、缓存穿透） | **布隆过滤器** | 只要"绝不漏判"即可，允许假阳性 |
| 统计 UV / PV 里有多少个不同用户 | **HyperLogLog** | 精确去重内存爆炸；HLL 12 KB 且可合并 |
| 找热点 key / 重元素（Top-K 频次、异常流量） | **Count-Min Sketch** 或 Space-Saving | 只需要"谁最频繁"，不需要精确次数 |
| 反垃圾 / 限流计数（次数略高可以接受） | **Count-Min Sketch** | 高估是安全方向（宁可多拦） |
| ⚠️ 计费、配额、对账、报表口径 | **精确结构** | 概率结构一律不能用 |

**三者可以叠着用**：先用布隆挡住"肯定不存在"的请求（省一次下游查询），再用 CMS 找热点，最后用 HLL 出报表 —— 这是典型的"漏斗式"用法。

## 延伸追问

- **布隆、HLL、CMS 三者到底怎么区分？** → 按**问题**分：布隆答"在不在"（只可能假阳性）、HLL 答"有多少个不同的"（有随机误差）、CMS 答"出现几次"（只可能高估）。三者的误差方向不同，决定了它们能用在哪些场景。
- **HyperLogLog 凭什么用 1KB 估准基数？** → 靠哈希的均匀性：**前导零位置**的分布只与"有多少个不同元素"相关，与元素内容无关；再用 m 个桶 + 调和平均压方差。误差 ≈ `1.04/√m`，m=16384 时约 0.81%。
- **HLL 的误差能"校准"掉吗？** → 单次误差是随机的、只能靠加大 m 降标准差；但**偏差（bias**）可用分段修正（小基数用线性计数、大基数做偏差表）—— 这也是为什么实测 20 轮的平均偏差（-2.05%）小于单次波动。
- **CMS 为什么取最小值，而不是平均值？** → 每一行的值都是"真实值 + 该行其它元素造成的噪声"，只多不少；不同行噪声独立，**取最小 = 挑噪声最小的那一行**。平均值反而会把噪声加进去。
- **CMS 的误差恒为正，这有什么好处？** → 可以据此选"安全方向"：比如反垃圾场景宁可多算（宁错杀），所以 CMS 合适；而对账要精确，就只能用精确结构。
- **为什么这些结构都不能用于计费？** → 它们的"节省"来自**放弃精确性**：布隆有假阳性、HLL 有 ±1% 误差、CMS 只高不低。计费 / 配额 / 对账一旦有偏差就是资损，必须用精确计数（哈希表、DB 计数器）。
- **HLL 的多个 key 能合并吗？** → 能，`PFMERGE` 取各桶最大值，因此可以"分片统计再合并"（按时段 / 按机房各存一个 HLL）；但**只能求并集基数**，想求交集得用别的办法。
