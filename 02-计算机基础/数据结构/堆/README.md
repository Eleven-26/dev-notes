## 三、选型判据：什么时候才换掉二叉堆？

二叉堆是默认解。只有出现下面四种需求之一，才轮到别的结构：

| 需求 | 首选 | 判据 / 代价 |
|---|---|---|
| 只做插入 + 取最小 / Top-K | **二叉堆** | 数组化、零指针、局部性好；`push` / `pop` 均 `O(log n)` |
| 两个堆要**反复合并** | **可并堆（左偏树 / 配对堆）** | 二叉堆合并只能 `O(n)` 重建；⚠️ 不涉及合并时上可并堆**反而更慢**（[可并堆与堆的变体.md](可并堆与堆的变体.md) 第七节） |
| 要**减小键**（decrease-key） | 工程：二叉堆 + `heap.Fix` / 懒惰删除；理论：斐波那契堆 `O(1)` 摊还 | 斐波那契堆常数极大、实现复杂，标准库都不提供（[可并堆与堆的变体.md](可并堆与堆的变体.md) 第五节） |
| 要**并发**安全 | `PriorityBlockingQueue` / `DelayQueue`（堆 + 锁） | 语言实现层，见 [并发容器.md](../../../01-编程语言/java/并发编程/并发容器.md) |

> ⭐ 一句话口诀：**只取极值用二叉堆，要合并用可并堆，要减小键先试懒惰删除，要并发看语言库。**

## 延伸追问

- **堆在物理上是一棵完全二叉树，为什么不算「树」？** → 树族的判据是「有序 / 范围 / 前缀」，而堆只保证**偏序**（堆顶是极值）、不支持范围与等值查找。能力边界不同，故 2026-10-16 单列。
- **什么时候才需要可并堆？** → 判据只有一条：**「两个堆需要被合并」且会发生多次**。只做插入 + 取最小就用二叉堆，实测里左偏树反而慢 1.7 倍。
- **斐波那契堆理论最好，工程为什么不用？** → `decrease-key` 的 `O(1)` 摊还优势被巨大的常数与实现复杂度吃掉；标准库都不提供，工程用「懒惰删除」模拟已足够。
- **Top-K 该用多大的堆、为什么？** → 大小为 K 的小顶堆：堆顶是「当前第 K 大」的门槛，新元素比它大才换进来。完整选型见 [Top-K问题.md](../../算法/基础算法/Top-K问题.md)。
