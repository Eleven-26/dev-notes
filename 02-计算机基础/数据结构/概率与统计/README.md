# 概率与统计

> 本目录（`数据结构/概率与统计/`）收**用精度换空间**的结构：位图与布隆过滤器、
> 布谷鸟过滤器、基数与频率估计。它们回答的都是「**极大集合上的近似判断**」——
> 判存在、判「可能存在」、估基数、估频次。
>
> ⚠️ 与 [高级数据结构/](../高级数据结构/README.md) 的分工：那边的单调栈、跳表、倒排索引、时间轮、并查集（堆另在 [堆/](../堆/README.md)）
> 给的是**确定性**保证；本目录的结构**允许结果出错**（误差方向固定），换来的空间收益是数量级的。
> 判据是「**这个结果能不能接受近似**」，不是「这个结构高不高级」。
>
> 本篇是**入口总纲** —— 回答「四个结构各自回答什么问题、硬前提是什么、什么时候该用哪个」。
> 各篇的推导、实现与容器实测在零件篇里，本篇不重复。数据结构目录的整体判据见 [README.md](../README.md)。

## 一、核心思想

**本节要点**：本目录的四个结构**回答四个不同的问题** —— 混用是最常见的错误来源。
它们共同的手段是**把「存原值」换成「存摘要」**：位图存状态位、布隆存哈希位、布谷鸟存指纹、HLL / CMS 存统计量。

| 结构 | 回答的问题 | 存的是什么 | 误差方向 | 内存量级 |
|---|---|---|---|---|
| **位图** | 这个整数**在不在**？ | 每个取值一个 bit | 无误差（范围有限时精确） | 值域 / 8 字节 |
| **布隆过滤器** | 这个元素**可能在不在**？ | `k` 个哈希位 | 只会**假阳性**，绝不假阴性 | `m` 个 bit |
| **布谷鸟过滤器** | 可能在不在？**且支持删除** | 8 bit 指纹 × 两个候选桶 | 只会假阳性，绝不假阴性 | 每元素约 8 bit |
| **HyperLogLog** | 有多少个**不同**元素？ | `m` 个桶的最大前导零 | 有误差（相对标准误 ≈ `1.04/√m`） | `m` 桶 × 6 bit |
| **Count-Min Sketch** | 某元素**出现了几次**？ | `d × w` 个计数器取最小 | 只会**高估**（只高不低） | `d × w` 个计数 |

⭐ **四个问题、四条判据**：在不在 → 位图；可能不在 → 布隆；要删 → 布谷鸟；
有多少个 / 出现几次 → HLL / CMS。**把「估基数」和「估频次」当成同一件事，是选型时最先犯的错。**

### 精确与近似的边界

| | 精确结构 | 概率结构（本目录后三个） |
|---|---|---|
| 结果 | 一定对 | 可能错，但**错的方向固定** |
| 空间 | 随元素数线性增长 | 固定预算，与元素数**无关** |
| 能否枚举原值 | 能 | 不能（布谷鸟只留指纹） |
| 适用 | 计费、库存、对账、去重后要拿原值 | 爬虫 URL 去重、缓存穿透、UV 估算、热点统计 |

⚠️ **铁律**：任何涉及**钱、配额、计费**的数字都不能用概率结构；它们可以用于「**挡掉绝大多数无效请求**」，
但最终判定必须回源到精确存储。

## 二、适用条件

**本节要点**：每个结构都有**一条硬前提** —— 违反它不是「慢一点」，而是「**静默给出错误答案**」或「内存直接爆掉」。

| 结构 | 硬前提 | 违反的后果 |
|---|---|---|
| **位图** | 取值范围有限且**较稠密** | ⚠️ 稀疏大范围（如 64 位用户 ID）内存爆炸 → 换 RoaringBitmap |
| **布隆过滤器** | 能接受假阳性，且**元素只增不删** | ⚠️ 不支持删除；清一位会顺带「删掉」其他元素，产生**假阴性** |
| **布谷鸟过滤器** | 桶数必须是 **2 的幂**（保证 `i₂ = i₁ XOR h` 的对合性） | ⚠️ 被踢出的指纹落进**查不回来**的桶 → **静默漏检**（实测非 2 的幂时 85000 个里漏检 4525 个） |
| **HyperLogLog** | 只关心**基数**、不关心具体元素 | 需要精确计数或要拿原值时不可用 |
| **Count-Min Sketch** | 能接受**只高不低**，且不用于容量硬判定 | 拿估计值当真实值会偏保守；热点挤占哈希桶时误差进一步放大 |

### 一条更实用的判据

```text
这个结果会被用来「做最终决定」吗？
├─ 会（计费 / 扣库存 / 对账 / 权限）
│   └─ 只能精确结构：位图 / 哈希表 / 排序数组
└─ 不会（先挡一层、估个规模、找热点）
    ├─ 只增不删 → 布隆过滤器
    ├─ 要删     → 布谷鸟过滤器
    ├─ 估基数   → HyperLogLog
    └─ 估频次   → Count-Min Sketch
```

⭐ 本目录的结构**只适合做「前置过滤」与「容量规划」**，不适合做「唯一事实来源」。

## 三、解题模板

**本节要点**：只需一步 —— **先问「我要回答哪个问题」**，再按决策树选结构。

```text
你要回答什么？
├─ 某个整数在不在？
│   ├─ 范围有限且稠密 → 位图（BitSet）                   [位图与布隆过滤器.md]
│   └─ 稀疏的大整数集 → RoaringBitmap
├─ 某个元素「可能」在不在？
│   ├─ 只增不删       → 布隆过滤器                       [位图与布隆过滤器.md]
│   └─ 需要删除       → 布谷鸟过滤器（⚠️ 桶数是 2 的幂）  [布谷鸟过滤器.md]
├─ 有多少个不同的元素？
│   └─ 接受误差       → HyperLogLog                      [基数与频率估计.md]
├─ 某元素出现了几次？
│   └─ 接受高估       → Count-Min Sketch                 [基数与频率估计.md]
└─ 要精确值 / 要枚举原值
    └─ 不属于本目录 → 哈希表 / 位图 / 排序数组           [../哈希表/散列表.md]
```

### ⭐ 三个自检

```text
□ 结果错了会不会造成事故？（会 → 不能用概率结构）
□ 元素会不会离开集合？（会 → 布隆不够，要布谷鸟或计数布隆）
□ 桶数 / 位数组大小是按预算算出来的，还是拍脑袋定的？
```

|---|---|---|

前者解决「在不在」，后者解决「有多少个 / 出现几次」；[布谷鸟过滤器.md](布谷鸟过滤器.md) 是前者的**可删除变体**。

## 五、正确性证明与复杂度保证

**本节要点**：本目录的「证明」都是**概率论证** —— 要说清的不是「一定对」，而是「**错的方向是什么、错多少**」。

| 结构 | 保证类型 | 关键论证 |
|---|---|---|
| [位图与布隆过滤器.md](位图与布隆过滤器.md) | **确定性**（位图）/ **概率**（布隆） | 布隆**无一假阴性**：判「不在」说明至少一个哈希位是 0，而插入时所有位都会被置 1 |
| [布谷鸟过滤器.md](布谷鸟过滤器.md) | **概率** | 同样**无假阴性**；误判率 ≈ `2b/2ᶠ`、**与元素数无关**；桶数取 2 的幂才能让 `i₂ = i₁ XOR h` 可逆 |
| [基数与频率估计.md](基数与频率估计.md) | **概率 + 单侧界限** | HLL 用调和平均压方差，相对标准误 ≈ `1.04/√m`；CMS 取 `d` 行最小值 ⇒ 计数器只会加不会减 ⇒ **只高不低** |

### ⭐ 两条最值得记住的推导

**① 布隆为什么「说不在一定对」**：插入时把 `k` 个位置**全部**置 1；查询时只要**有一位是 0**，
就说明这个元素从未被完整插入过 —— 因此「不在」是确定的，「在」才可能是碰撞造成的。

**② 布谷鸟为什么要求桶数是 2 的幂**：两个候选桶由 `i₂ = i₁ XOR hash(f)` 互相推导 —— 这要求 XOR 是对合运算。
桶数不是 2 的幂时，异或结果可能落到**桶数组之外**，踢出后的指纹再也查不回来，于是产生**静默漏检**。

## 六、常见陷阱

**本节要点**：本目录的坑集中在「**把近似当精确**」与「**前提被违反**」两类 —— 前者是业务事故，后者是静默算错。

| 陷阱 | 症状 | 怎么避免 |
|---|---|---|
| **位图用在稀疏大范围** | 内存爆炸 | 先看取值范围；超稀疏换 RoaringBitmap |
| **想删除布隆过滤器里的元素** | 做不到，或误判率飙升 | 布隆不支持删除；改用计数布隆或 [布谷鸟过滤器.md](布谷鸟过滤器.md) |
| **布谷鸟过滤器桶数不是 2 的幂** | **静默漏检** | 桶数一律取 2 的幂（实测非 2 的幂时 85000 个里漏检 4525 个） |
| **把 HLL 当精确计数** | 得到的数字有偏差 | 接受误差；计费 / 配额场景换精确结构 |
| **忽略 CMS 的「只高不低」** | 把估计值当真实值用 | 记住它只会高估；做容量判断要留余量 |
| **把「可能存在」当成「一定存在」** | 布隆误判被当成事实 | 判「在」之后仍要回源确认 |
| **用布谷鸟过滤器替代精确删除** | 同桶同指纹时有歧义，可能删错 | 需要精确删除时回源到哈希表；布谷鸟的删除是**指纹级**的 |

## 七、与其他思想对比

**本节要点**：概率结构**不是精确结构的替代品**，而是它的**前置闸门** —— 先用极小的空间挡掉大多数请求，
剩下的再交给精确结构。

### 概率结构 vs 精确结构

| 维度 | 精确结构（哈希表 / 位图） | 概率结构（布隆 / 布谷鸟 / HLL / CMS） |
|---|---|---|
| 空间 | 与元素数成正比 | 固定预算 |
| 结果 | 一定对 | 可能错，方向固定 |
| 典型用法 | 唯一事实来源 | 前置过滤 / 容量估算 |
| 代价 | 内存 | **精度** |

### 概率结构 vs 倒排索引

两者都用于「海量数据的检索」，但方向相反：

| 场景 | 用什么 |
|---|---|
| 判「这个词在不在集合里」 | 布隆过滤器 |
| 判「哪些文档含这个词」 | [倒排索引.md](../高级数据结构/倒排索引.md)（精确、可枚举） |

⭐ 真实系统里两者常**串联**：布隆先挡掉不存在的词，倒排索引再给出精确的文档集合。
