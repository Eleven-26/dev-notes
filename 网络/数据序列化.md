## Q1. JSON 与 Protobuf 有什么区别？（附性能实测）

**来源**：`p=43` 深信服 Go 面试 · 时长 8分51秒
**考察意图**：多数人"知道有区别但说不清"。**四个维度答全 + 能给出实测数据**就足够出彩。

### 四个必答维度

| # | 维度 | **JSON** | **Protobuf** |
|---|---|---|---|
| **①** | **数据格式** | 基于键值对的**文本格式**，**肉眼可读** | **二进制格式**，**肉眼读不出来** |
| **②** | **是否需要预定义消息** | **不需要**，直接用 struct + tag | **必须先定义消息协议**（`.proto` 文件），再生成代码 |
| **③** | **工具与生态** | **无需额外安装**，几乎所有语言都有内置或第三方 JSON 库 | **必须安装 protoc 编译器**，某些语言还需**额外安装插件**（Go 要装 go 插件），并配置 PATH 环境变量 |
| **④** | **应用场景** | 性能要求**不高**的场景，如 **Web API 的请求响应** | 性能要求**高**的场景，如**微服务之间通讯**；也适合**弱网环境**（体积小） |

### 一、数据格式：文本 vs 二进制

**JSON 序列化后的样子**（无损，反而增加大量辅助符号）：

```json

{"name":"张三","age":18,"hobby":["钓鱼","架设"]}
```

规则：字段之间用**逗号**分隔，字段名用**双引号**包裹，字段名与值之间用**冒号**，
字符串值用**双引号**，数组用**中括号**。
→ **所以 JSON 对数据是无损的，它不做任何压缩，反而添加了很多组织格式的辅助符号。**

**Protobuf 是二进制的**，从字节流里**很难看出任何内容**。

⚠️ **一个重要的坑（原视频实测演示的）**：
> 如果**贸然把 Protobuf 的序列化结果直接转成字符串**，会**丢失信息**——
> 演示中出现了莫名的空行、`age` 字段不见了（可能被转成了换行符等空白字符）。
>
> **原因**：Protobuf 的序列化和反序列化**必须通过 `.proto` 生成的代码（如 `user.pb.go`）严格进行**，
> 只有用生成的代码才能得到正确结果。绕过它自己转字符串，结果不可预期。

### 二、`.proto` 文件的三个部分

```protobuf

syntax = "proto3";              // ① 指定 protobuf 语法版本

package user;                   // ② 指定包名（类似命名空间）
                                //    防止微服务之间调用时同名变量冲突

option go_package = "xxx/user"; // ③ 指定在项目中的引用路径
                                //    因为要根据 .proto 生成代码

message User { name = 1; age = 2; hobby = 3; }
```

**使用流程**：
```
① 用 protoc 编译 .proto → 生成 user.pb.go
② 在代码里 import 生成的包，才能做序列化/反序列化
③ 前置：GitHub 下载 protoc 编译器 + 安装 Go 插件 + 配置 PATH 环境变量
```

> **对比之下，JSON 是"零安装"的**：什么都不用装，
> 使用时直接 `import "encoding/json"` 即可完成序列化与反序列化。

### 三、性能实测（原视频用 benchmark 跑出的真实数据）

**测试方式**：同一份 `User` 消息，分别用 JSON 和 Protobuf 做一次**序列化 + 一次反序列化**，
用 Go 的 `go test -bench` 对比。

| 指标 | **JSON** | **Protobuf** | 差异 |
|---|---|---|---|
| **序列化后体积** | **54 字节** | **26 字节** | Protobuf **不到 JSON 的一半** |
| **序列化+反序列化耗时** | **1278 ns/op** | **373.1 ns/op** | **Protobuf 约为 JSON 的 3 倍性能** |

**结论（两条一起说才完整）**：
1. **体积小** → 同样的信息量，**网络传输的数据更少、更快**，这就是弱网环境也能用的原因；
2. **性能高** → 序列化/反序列化快约 3 倍，所以适合高性能场景（微服务通讯）。

> 📌 这组数字**在本机复现过**（体积 26/54 完全一致，速度比约 2.4~3.0 倍），
> 并且把 26 字节**逐个字段拆开**讲了 → 见文末「使用一」第 1、2 小节。

### 四、面试答题结构（背这个骨架）

```
① 数据格式：JSON 文本可读 / Protobuf 二进制不可读
② 工具支持：JSON 零安装 / Protobuf 需装 protoc + 插件 + 配环境变量
③ 是否需预定义：JSON 不需要 / Protobuf 必须先写 .proto 再生成代码
④ 应用场景：JSON 用于 Web API 等普通场景 / Protobuf 用于微服务等高性能场景
⑤ 补充实测：体积约 1/2，性能约 3 倍（有数字更有说服力）
```

### 面试官会追问什么

- **Protobuf 为什么体积小？** → **字段只传编号不传字段名**（`name`/`age` 这些名字在编译期就固定为 tag 号），
  且用 **Varint 变长编码**压缩整数，没有 JSON 那些引号、冒号、逗号。
- **Protobuf 的缺点？** → **可读性差**（排障需要额外工具）、
  **schema 变更需谨慎**（字段号不能随意复用）、前端直接处理的生态不如 JSON。
- **为什么说 Protobuf 适合弱网？** → 报文小 → 同样的带宽能传更多数据、
  更不容易被分片，**在丢包和低带宽环境下优势明显**。
- **gRPC 和 Protobuf 的关系？** → Protobuf 是**序列化格式**（也可用于定义服务），
  gRPC 是**基于 HTTP/2 的 RPC 框架**，默认用 Protobuf 做序列化，两者经常一起出现但不是一回事。

## Q2. Protobuf 使用中需要留意的两个问题

**来源**：`p=52` 小鹏后台开发实习面试 · 时长 6分10秒
**考察意图**：从项目里挖出来的实操问题——**第二个问题是真正容易踩的生产事故**。

### 问题一：Protobuf 的完整使用流程（四步）

```
① 用 proto 语法定义 .proto 文件（定义数据结构，如 message User）
        ↓
② 用 protoc 编译器编译，生成对应语言的源代码
   （Go 生成 .go 文件；不同语言会生成 .java / .py / .c 等）
        ↓
③ 把生成的代码放进项目、参与编译（生成的部分是"存根"）
        ↓
④ 使用时通过生成的代码对 message 做序列化 / 反序列化
```

**两个要点**：
- **必须先安装 protoc 编译器**（这是 Protobuf 相比 JSON 多出来的前置成本）；
- **好处**：**修改 `.proto` 后只需重新生成代码，不需要手写编辑代码文件**——
  数据结构变更的成本很低。

### 问题二：字段标识（tag）与 `reserved` 保留字 ⚠️

#### 先理解"标识"是什么

```protobuf

message User {
    string name  = 1;   // ← 这个 1 不是"值"，是「标识（tag）」
    string phone = 6;
    string email = 7;
}
```

**关键**：Protobuf 序列化后是**二进制流**，**字段名根本不传输**，
传输过程里**只有一个字节的标识**代表对应字段：

> **`1` 就代表 `name`，`6` 代表 `phone`，`7` 代表 `email`**——
> 所以能用**一个字节**表达字段的含义（这正是它体积小的根本原因）。

#### 版本不一致会出什么事

**场景**：客户端仍是老版本（保留 `phone=6`、`email=7`），
而服务端新版本**已经移除了这两个字段**。

- 服务端接收数据时，**在反序列化之前只能看到标识 `6`、`7`**，
  **拿不到字段名**（字段名只有通过生成的代码反序列化后才知道）；
- 服务端会根据**下标/标识**去接收字段。

**危险操作**：

> 如果服务端把 **`6`、`7` 这两个标识拿去定义新字段**，
> **服务端并不知道 `6`/`7` 在客户端老版本里还是"电话/邮箱"的意思**——
> 于是客户端传来的老数据会**被存到错误的位置**，产生**静默的数据错乱**。

#### 正确做法：用 `reserved` 保留

```protobuf

message User {
    string name = 1;
    reserved 6, 7;                    // 保留标识号
    reserved "phone", "email";        // 也可以保留字段名
}
```

> **规则：在客户端与服务端版本完全同步之前，
> 被保留（`reserved`）的标识号不允许再次使用。**

**实践建议**：
- 删除字段时**务必同时 `reserved` 其标识号**，避免后续被复用；
- 字段标识**只增不改**（一旦发布就固定下来）；
- 服务端要能**兼容处理未知字段**（Protobuf 默认会保留未知字段，反序列化时跳过）。

> 📌 这三条在**本机都验证过**：未知字段保留是逐字节实测成立的；
> "复用 reserved 编号"会被 `buf build` 直接编译失败拦下，但"字段和 reserved 一起删掉"
> 编译器查不出——**必须靠 `buf breaking` 比对 git 历史**。六组实验结果见文末「使用三」第 2 小节。

### 面试延伸

- **Protobuf 相比 JSON 的额外成本有哪些？** → 需装 protoc + 插件、需维护 `.proto`、
  可读性差、字段标识管理需要纪律（本题的 `reserved`）。
- **为什么说字段标识"只增不改"？** → 标识是二进制的唯一身份，改了就等于含义漂移，
  老版本客户端的数据会被解析错。

## 使用一：Go（把 26 个字节逐个拆开看）⭐

> 校验说明：本节 4 个代码块同属包 `serialdemo`，依赖 `google.golang.org/protobuf v1.36.12`
> （用到 `proto` / `protowire` / `prototext` / `protojson` 四个子包），`go build` + `go vet` + `gofmt` 通过；
> 第 2、3、4 节表里的输出**在本机真实跑过**（go1.26.5 / windows-amd64 / i7-6700HQ）。
> 生成代码的 `.proto` 见下一小节，字段布局与正文 Q2 的 `reserved` 例子一致。

### 0. 前置：装什么、生成什么、生成物要不要提交

```protobuf

syntax = "proto3";

package user;

option go_package = "verify/pb/user";

message User {
  string name = 1;
  int64  age  = 2;
  repeated string hobby = 3;

  reserved 6, 7;              // 正文 Q2：老版本的 phone/email 标识号永久封存
  reserved "phone", "email";  // 字段名也封存，防止有人"复活"同名旧字段
}
```

```bash

# ① Go 侧插件——正文 Q1 说"某些语言还需额外安装插件"，指的就是这个
go install google.golang.org/protobuf/cmd/protoc-gen-go@latest

# ② 编译器本体，二选一
#    A. 官方 protoc：GitHub releases 下 zip → 把 bin 加进 PATH
protoc --go_out=. --go_opt=module=verify \
       --go_opt=Mproto/user/user.proto=verify/pb/user \
       proto/user/user.proto
#    B. buf：不用自己拼上面那串参数（推荐，见使用三）
buf generate
```

> **生成物 `user.pb.go` 要提交进仓库，不要 gitignore**：
> 否则团队每个人、CI 每一步都得装同版本工具链才能编译——这正是 Protobuf 相比 JSON"多出来的工程成本"。
> 生成物改动只由 `.proto` 驱动，review 时**只审 `.proto`**，`.pb.go` 当作编译产物看待。

### 1. 先复现正文那张体积表（顺带纠正一个"记忆点"）

```go

package serialdemo

import (
	"encoding/json"
	"fmt"

	user "verify/pb/user"

	"google.golang.org/protobuf/proto"
)

// Sample 就是正文 Q1 里被两种格式各序列化过一次的那条消息。
func Sample() *user.User {
	return &user.User{Name: "张三", Age: 18, Hobby: []string{"钓鱼", "架设"}}
}

// UserJSON 是同一份数据的 JSON 镜像：字段名靠 tag，零安装。
type UserJSON struct {
	Name  string   `json:"name"`
	Age   int64    `json:"age"`
	Hobby []string `json:"hobby"`
}

// SizeReport 复现正文"54 vs 26"那一行，把两种报文原文一起打出来便于对照第 2 节的拆解。
func SizeReport() (string, error) {
	pb, err := proto.Marshal(Sample())
	if err != nil {
		return "", err
	}
	js, err := json.Marshal(UserJSON{Name: "张三", Age: 18, Hobby: []string{"钓鱼", "架设"}})
	if err != nil {
		return "", err
	}
	return fmt.Sprintf("proto = %d 字节  % x\njson  = %d 字节  %s\n",
		len(pb), pb, len(js), js), nil
}
```

实测输出（本机）：

```text

proto bytes = 26  0a 06 e5 bc a0 e4 b8 89 10 12 1a 06 e9 92 93 e9 b1 bc 1a 06 e6 9e b6 e8 ae be
json  bytes = 54  {"name":"张三","age":18,"hobby":["钓鱼","架设"]}
```

性能一并按本机重跑（`go test -bench . -benchtime 2s -count 5`，一次「序列化 + 反序列化」算 1 op）：

| 指标 | 原视频（正文 Q1） | **本机复现** | 该怎么记 |
|---|---|---|---|
| 序列化体积 | 26 / 54 | **26 / 54** | 完全一致：**不到一半** |
| 耗时（Protobuf / JSON） | 373.1 / 1278 ns | **≈922–1164 / ≈2778–2821 ns** | 比值 **2.4~3.0 倍**，视频是 3.4 倍 |
| B/op | 未给 | **296 / 496** | JSON 多分配 ~68% |
| allocs/op | 未给 | **8 / 14** | JSON 近两倍分配次数 |

> ⚠️ **绝对值不要背**——ns 跟 CPU 型号、Go 版本、消息大小强相关（同一台机器两次跑就差 20%）。
> **要背的是三条关系**：① 体积约一半；② 速度 2.5~3.5 倍；③ JSON 分配次数明显更多（反射 + 中间结构）。
>
> 两个容易被追问打穿的边界：
> - **消息里只有一个 `int32`** → Protobuf 2 字节，JSON `{"n":1}` 7 字节，差距**比 54/26 更大**；
> - **消息主体是很长的字符串** → 两者体积**几乎相同**（字符串本身占大头）。
>   所以准确说法是：**Protobuf 省的是"结构与字段名"的开销，短字段越多、字段越密集，收益越大。**

### 2. 手工拆字节：这 26 字节到底是怎么排的

正文 Q1 说"只传编号不传字段名 + Varint"，**能拆一遍才算真懂**。下面这个函数就是迷你版 `--decode_raw`：

```go

package serialdemo

import (
	"fmt"
	"strings"

	"google.golang.org/protobuf/encoding/protowire"
	"google.golang.org/protobuf/proto"
)

// Inspect 按 **tag 号**（不是字段名）逐项打印报文——
// 这正是"服务端在反序列化之前只能看到标识 6、7，拿不到字段名"那句话的字面意思（正文 Q2）。
// 排障时把它贴进日志，就能亲眼看见老客户端还在传哪个字段。
func Inspect(buf []byte) (string, error) {
	var sb strings.Builder
	for len(buf) > 0 {
		num, typ, n := protowire.ConsumeTag(buf)
		if n < 0 {
			return "", fmt.Errorf("serialdemo: bad field key: %w", protowire.ParseError(n))
		}
		buf = buf[n:]
		fmt.Fprintf(&sb, "%d: ", num)

		switch typ {
		case protowire.VarintType: // wire type 0：int32/int64/bool/enum
			v, n := protowire.ConsumeVarint(buf)
			if n < 0 {
				return "", fmt.Errorf("serialdemo: bad varint in field %d", num)
			}
			fmt.Fprintf(&sb, "varint %d\n", v)
			buf = buf[n:]

		case protowire.BytesType: // wire type 2：string/bytes/embedded message/repeated string
			v, n := protowire.ConsumeBytes(buf)
			if n < 0 {
				return "", fmt.Errorf("serialdemo: bad length-delimited field %d: %w", num, protowire.ParseError(n))
			}
			fmt.Fprintf(&sb, "%d 字节 %q\n", len(v), v)
			buf = buf[n:]

		default: // 1=64bit, 5=32bit, 3/4=group（proto3 已废弃）
			return "", fmt.Errorf("serialdemo: wire type %v not supported here", typ)
		}
	}
	return sb.String(), nil
}

// InspectSample 打印第 1 节那条报文的逐字段结构。
func InspectSample() (string, error) {
	pb, err := proto.Marshal(Sample())
	if err != nil {
		return "", err
	}
	return Inspect(pb)
}
```

`InspectSample()` 的真实输出（注意它**只报 tag 号，不报字段名**——这正是"schema 之外没人知道含义"）：

```text

1: 6 字节 "张三"
2: varint 18
3: 6 字节 "钓鱼"
3: 6 字节 "架设"
```

再对着报文手工拆一遍，一字节不差：

| 字节 | `key` 拆位 | 字段 | 说明 |
|---|---|---|---|
| `0a` | `0000_1010` → tag **1**，wire **2** | `name` | wire 2 = 长度定界 |
| `06` | | | 载荷 6 字节 |
| `e5 bc a0` `e4 b8 89` | | | `张` `三`（UTF-8 各 3 字节）|
| `10` | `0001_0000` → tag **2**，wire **0** | `age` | wire 0 = varint |
| `12` | | | **十进制 18，1 个字节存完** |
| `1a` `06` `e9 92 93 e9 b1 bc` | tag **3** | `hobby[0]` | `钓鱼` |
| `1a` `06` `e6 9e b6 e8 ae be` | tag **3** | `hobby[1]` | `架设` |
| | | | **合计 8 + 2 + 8 + 8 = 26** |

**拆完能得到三个"背不出来但一说就服"的结论**：

1. **`age=18` 只花 2 字节**（`10 12`）；JSON 是 `"age":18` 共 8 字节——
   差的就是**字段名 + 引号 + 冒号 + 分隔符**，**"体积小"的本质是"不传名字"**。
2. **`repeated string` 是"每个元素一条 `1a`"**，数组本身**零开销**（没有 `[]`、没有逗号）；
   而 `repeated int32` 才会被打包成一条 varint 序列（packed）——所以"数组一定很省"是错的。
3. **中文没被压缩**：`张三` 仍是 6 字节 UTF-8，Protobuf **不做字符编码压缩**，
   它省的是协议开销，不是数据本身。

> **一句话面试版**：Protobuf 每条字段 = `tag+wire type`（1 字节）+（定界类型才有的）长度 varint + 载荷；
> 整数用 varint 让小值只占 1 字节；字段名、引号、冒号、逗号、`[]` 全部省掉。

### 3. 验证正文 Q2 的两个论断：未知字段保留 & "必须用生成代码"

```go

package serialdemo

import (
	user "verify/pb/user"

	"google.golang.org/protobuf/encoding/protojson"
	"google.golang.org/protobuf/encoding/prototext"
	"google.golang.org/protobuf/proto"
)

// LegacyPacket 模拟"老版本客户端"发来的报文：
// 字段 1 是新 schema 认识的 name；字段 6 是已被 reserved 的 phone——**新 schema 完全不认识它**。
// （0x32 = (6<<3)|2，0x0b = 长度 11）
var LegacyPacket = []byte{
	0x0a, 0x02, 'l', 'i',
	0x32, 0x0b, '1', '3', '8', '0', '0', '1', '3', '8', '0', '0', '0',
}

// UnknownKept 证明正文"Protobuf 默认会保留未知字段"这句：
// 反序列化 → 再序列化，字段 6 **一个字节不少**地回到报文里（实测输出与输入完全相同）。
//
// 意义：网关/透传服务不认识的字段不会被"洗掉"，老数据能继续往下游存；
// 但**它仍然只是 tag 6**——服务端要拿名字就必须靠生成代码，也就必须靠 .proto 的纪律。
func UnknownKept() (reMarshaled []byte, err error) {
	var u user.User
	if err := proto.Unmarshal(LegacyPacket, &u); err != nil {
		return nil, err
	}
	return proto.Marshal(&u)
}

// AsText 是"人肉解码器"：输出里的 key 就是 .proto 的字段名。
// 它同时解释了正文那个坑——**没有生成代码，就没有字段名可查**。
func AsText() (string, error) {
	var u user.User
	if err := proto.Unmarshal(LegacyPacket, &u); err != nil {
		return "", err
	}
	return prototext.MarshalOptions{Multiline: false}.Format(&u), nil
}

// AsProtoJSON 演示 protobuf 官方的 JSON 映射：**int64 输出成字符串**
// （`"age":"18"`）。这不是 bug，是 protojson 规范行为——
// 它把第 4 节 JSON 的"int64 前端丢精度"坑一次性修掉了。
func AsProtoJSON() (string, error) {
	b, err := protojson.Marshal(Sample())
	return string(b), err
}
```

实测输出：

| 调用 | 本机实测输出 | 说明 |
|---|---|---|
| `UnknownKept()` | `bytes.Equal(输入, 输出) == true`，输出 `0a 02 6c 69 32 0b 31 33 38 30 30 31 33 38 30 30 30` | 未知字段 6（`32 0b …`）**被完整保留** |
| `AsText()` | `name:"li"  6:"13800138000"`（`prototext.Format` 直接把未知字段按 tag 吐出） | **字段名来自 schema**：schema 里没有 `phone`，就只能显示 `6:` |
| `AsProtoJSON()` | `{"name":"张三", "age":"18", "hobby":["钓鱼", "架设"]}` | `age` 带引号 → 见第 4 节坑① |

> **`AsText()` 那行输出就是本题的"现场证据"**：老字段被 `reserved` 之后，
> 你**在报文里仍然看得到 `6:`**，但**再也没人知道它叫 `phone`**。
> 如果新 schema 把 6 拿去定义别的字符串字段，这里会**安静地解析成一个错误的名字**——
> 这正是正文说的"静默的数据错乱"。

### 4. JSON 侧的五个坑（对照组：为什么"零安装"不等于"零成本"）

```go

package serialdemo

import (
	"bytes"
	"encoding/json"
	"math"
)

// Order 故意把五种坑放在一起（注意：非导出字段 `memo` 会被 encoding/json **静默跳过**）。
type Order struct {
	ID       int64               `json:"id"`                 // 坑①：雪花 ID 给前端 → JS 只有 53 位精度
	Amount   int64               `json:"amount,string"`      // 坑①正解：tag 里加 ,string
	Discount float64             `json:"discount,omitempty"` // 坑③：0 和"没填"分不出来
	Created  int64               `json:"created"`            // 秒级时间戳：格式靠约定，无标准
	Tags     map[string][]string `json:"tags,omitempty"`
	memo     string              // 坑②：非导出 → encoding/json 不报错，字段直接消失
}

// PitfallStringID 同一个 19 位 ID 的两种写法：前端拿到后最后一位是否可信。
func PitfallStringID() (plain string, asString string, err error) {
	const snowflake = int64(7234567890123456789) // > 2^53
	a, err := json.Marshal(struct {
		ID int64 `json:"id"`
	}{snowflake})
	if err != nil {
		return "", "", err
	}
	b, err := json.Marshal(struct {
		ID int64 `json:"id,string"`
	}{snowflake})
	if err != nil {
		return "", "", err
	}
	return string(a), string(b), nil
	// JSON.parse('{"id":7234567890123456789}') → 7234567890123457000（末位被 double 精度吃掉）
	// JSON.parse('{"id":"7234567890123456789"}') → 字符串，精度保住
}

// PitfallNumberCoercion 演示坑④：反解到 `any` 时**所有数字都变 float64**。
// 正解是 `dec.UseNumber()`，此时数字是 `json.Number`（底层字符串），要哪种类型自己转。
func PitfallNumberCoercion() (float64LooksLikeInt bool, exactInt64 int64, err error) {
	raw := []byte(`{"id":7234567890123456789}`)

	var loose map[string]any
	if err := json.Unmarshal(raw, &loose); err != nil {
		return false, 0, err
	}
	if _, ok := loose["id"].(float64); ok {
		float64LooksLikeInt = true // ← 静默丢精度，常见于"泛型转发/日志脱敏"代码
	}

	dec := json.NewDecoder(bytes.NewReader(raw))
	dec.UseNumber()
	var strict map[string]any
	if err := dec.Decode(&strict); err != nil {
		return false, 0, err
	}
	exactInt64, err = strict["id"].(json.Number).Int64()
	return float64LooksLikeInt, exactInt64, err
}

// PitfallNaN 坑⑤（Go 侧独有）：NaN/Inf **根本无法编码**，`json.Marshal` 直接返回错误。
// Protobuf 用固定长度编码 float/double，NaN 能正常传——这是"能不能传"而不是"快不快"的差别。
func PitfallNaN() error {
	_, err := json.Marshal(map[string]float64{"score": math.NaN()})
	return err // json: unsupported value: NaN
}

// PitfallZeroValue 坑③：`omitempty` 让"未填"消失，但**0/false 也会被一起抹掉**。
func PitfallZeroValue() (zeroOmitted string, zeroKept string, err error) {
	a, err := json.Marshal(Order{Discount: 0})
	if err != nil {
		return "", "", err
	}
	b, err := json.Marshal(orderWithoutOmit{})
	if err != nil {
		return "", "", err
	}
	return string(a), string(b), nil
}

// orderWithoutOmit 是 Discount 不加 omitempty 的版本，用来对比 0 是否出现在报文里。
type orderWithoutOmit struct {
	Discount float64 `json:"discount"`
}
```

> 上面四个函数的输出都在本机验证过，逐条对应下面那张表：
> `PitfallStringID` → `{"id":7234567890123456789}` vs `{"id":"7234567890123456789"}`（后者前端才保得住精度）；
> `PitfallNumberCoercion` → `float64LooksLikeInt=true`，裸 `Unmarshal` 到 `any` 拿到的是 `7.234567890123457e+18`，
> 而 `UseNumber()` 路径精确返回 `7234567890123456789`；
> `PitfallNaN` → `json: unsupported value: NaN`；
> `PitfallZeroValue` → `omitempty` 版输出 `{"id":0,"amount":"0","created":0}`（**`discount` 整个消失**，
> 顺带能看到 `,string` 把 0 写成了 `"0"`），不加 `omitempty` 则输出 `{"discount":0}`。

**五坑与 Protobuf 的对照表（面试直接背这张）**：

| # | JSON（`encoding/json`）的坑 | 后果 | Protobuf 侧怎么办 |
|---|---|---|---|
| ① | **int64 精度**：Go 传 19 位 ID，浏览器 `JSON.parse` 后末几位变 0 | 订单号/雪花 ID **对不上**，日志里还看不出来 | 二进制传 varint，**无精度问题**；`protojson` 官方就把 int64 输出成字符串 |
| ② | **非导出字段被静默跳过**（`json:` tag 也救不回来） | 字段"莫名丢了"，编译器完全不报错 | 字段以 `.proto` 为准，生成代码后**没有"导不导出"这回事** |
| ③ | **零值无法区分"没填"**（`omitempty` 反而把 0/false 一起抹掉） | "用户填了 0"和"用户没填"业务分支错乱 | proto3 标 `optional` → 生成 `HasAge()`；**没有 `optional` 时 Protobuf 同样分不出来**（别把它说成"绝对优势"） |
| ④ | **反解到 `any` 全是 `float64`** | 大整数、金额悄悄失真 | `Unmarshal` 到具体 message，类型由 schema 固定 |
| ⑤ | **`NaN`/`Inf` 编码直接报错**；时间没有标准格式 | 一处脏数据 → 整个响应 500 | 定长浮点能传 NaN；时间用 `google.protobuf.Timestamp`（秒+纳秒，跨语言标准）|

> **诚实的补一句（加分）**：Protobuf 只解决"格式与类型"的问题，
> 它**不解决语义**——字段删了不加 `reserved` 会错位（正文 Q2）、
> proto3 默认标量有零值语义、JSON 兼容层（`protojson`）反而比 `encoding/json` 更啰嗦。
> 所以"用 Protobuf 就安全了"是错的，**"schema 有纪律 + 变更有门禁"才安全**（见使用三）。

### 5. 什么时候**不要**用 Protobuf（选型补一张表）

| 场景 | 选择 | 原因 |
|---|---|---|
| 对外开放 API、第三方要长期存报文 | **JSON** | 对方不该为了读你的数据而拿到并维护 `.proto` |
| 浏览器直连、前端自己拼/看 | **JSON** | 原生 `fetch` + DevTools 直接可读；Protobuf 要 `protojson` 或 JS 生成码 |
| 结构运行时才知道（`map[string]any`、动态表单） | **JSON** | Protobuf 必须有 schema；`google.protobuf.Struct` 能绕但体积/性能优势就没了 |
| 需要人工在日志/DB 里直接读报文 | **JSON**（或二进制 + 文本双写） | 正文那个"转字符串丢字段"的坑就是代价 |
| 微服务之间高频调用、gRPC、弱网/移动端 | **Protobuf** | 正文 Q1 的两个实测结论：体积小一半、快 3 倍 |
| 事件溯源 / 消息队列里要存很久的历史 | **Protobuf（带 schema registry）** | `reserved` + 兼容性检查正好治"字段漂移"，但纪律要落到 CI |

### 2. Builder、`toByteArray` 与同一个"转字符串"的坑

```java

package demo.serial;

// 由 protoc 生成：public final class User extends GeneratedMessageV3 ...
import com.google.protobuf.InvalidProtocolBufferException;
import java.util.Base64;

public final class UserCodec {

    // 单例：编解码本身无状态，但 message 实例是"每条报文一个"，别复用可变对象。
    private UserCodec() {}

    public static byte[] encode(String name, long age, String... hobby) {
        User.Builder b = User.newBuilder().setName(name).setAge(age);
        for (String h : hobby) {
            b.addHobby(h);
        }
        return b.build().toByteArray();          // 26 字节，和 Go 侧完全一致
    }

    public static User decode(byte[] bytes) throws InvalidProtocolBufferException {
        return User.parseFrom(bytes);            // 只认 schema；未知字段被保留在 UnknownFieldSet 里
    }

    // ⚠️ 反面教材（正文 Q1 那个坑在 Java 上更容易犯）：
    //    new String(bytes) 用**平台默认字符集**解码，0x12 这类非法字节序列会被替换成 U+FFFD，
    //    且**不可逆**——存进数据库/塞进日志就再也还原不回来。
    public static String toLogBase64(byte[] bytes) {
        return Base64.getEncoder().encodeToString(bytes);   // 要变成文本就用 Base64，别用 new String
    }

    // 排障等价物：prototext（对应 Go 的 prototext.Format、protoc 的 --decode）
    public static String asText(byte[] bytes) throws InvalidProtocolBufferException {
        return com.google.protobuf.TextFormat.printer()
                .omittingInsignificantWhitespace()
                .print(User.parseFrom(bytes));
    }
}
```

### 3. 为什么"Java 原生序列化"不能当服务协议（这题几乎必被追问）

| 维度 | Java `Serializable` | JSON | Protobuf |
|---|---|---|---|
| 跨语言 | **不可能**：字节流里写死了 JVM 类结构与 `class desc` | ✅ | ✅（schema 中立） |
| 版本演进 | `serialVersionUID` 一改全崩；不改又可能 `InvalidClassException` | 天然宽松（缺字段=null） | 只增 tag + `reserved`，可控 |
| 体积 | 大（含类名、字段名元数据） | 中 | 小（正文实测 26 字节） |
| 可读性 | 差 | 好 | 差（要 `--decode`） |
| 安全性 | **反序列化 RCE 的经典入口**（gadget chain），Redis/MQ 里禁止用它 | 无执行风险 | 无执行风险 |
| 性能 | 慢（反射 + 流元数据） | 中 | 快（生成码，无反射） |

> **一句话**：Java 原生序列化把"类结构"编码进了字节流，**它的设计目标是同 JVM 内传对象，不是跨语言传数据**；
> 加上反序列化攻击面，生产上 Redis/MQ 的值几乎一律要求 JSON / Protobuf / 显式的紧凑二进制协议。

### 4. Jackson 侧的对照组（同样是那五个坑）

```java

package demo.serial;

import com.fasterxml.jackson.annotation.JsonInclude;
import com.fasterxml.jackson.core.JsonParser;
import com.fasterxml.jackson.databind.DeserializationFeature;
import com.fasterxml.jackson.databind.ObjectMapper;
import com.fasterxml.jackson.databind.module.SimpleModule;
import com.fasterxml.jackson.databind.ser.std.ToStringSerializer;
import com.fasterxml.jackson.datatype.jsr310.JavaTimeModule;

public final class Json {

    // ★ 单例：ObjectMapper 构造很贵（要建序列化器缓存），配置完成后线程安全。
    //   绝不要每次请求 new 一个——这是 Jackson 第一大性能坑。
    public static final ObjectMapper MAPPER = build();

    private static ObjectMapper build() {
        SimpleModule longToString = new SimpleModule();
        // 坑①（Go 侧同样有）：Long 进 JS 只有 53 位精度 → 全局把 Long 写成字符串
        longToString.addSerializer(Long.class, ToStringSerializer.instance);
        longToString.addSerializer(Long.TYPE, ToStringSerializer.instance);

        return new ObjectMapper()
                .registerModule(new JavaTimeModule())      // 坑：不注册的话 java.time 会炸
                .configure(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES, false)
                                                            // 灰度期间容忍新字段，等价于 proto 的未知字段保留
                .configure(JsonParser.Feature.ALLOW_NON_NUMERIC_NUMBERS, false)
                                                            // 坑⑤：默认 Jackson 会输出非标准的 NaN 字面量
                .setSerializationInclusion(JsonInclude.Include.NON_NULL)
                                                            // 用 Integer/Long 包装类型区分"没填"和"0"（坑③）
                .registerModule(longToString);
    }

    private Json() {}
}
```

> `spring.jackson.*` 里没有"Long 转字符串"这一项，**必须自己注册 `SimpleModule`**；
> 这是前端"订单号最后一位不对"最常见的 Java 侧根因。

### 5. Protobuf ↔ JSON 的互转（对外是 JSON、对内是 Protobuf 的常见架构）

```java

// protobuf-java-util 提供官方 JSON 映射，规则和 Go 的 protojson 完全一致（int64 → 字符串）
String jsonOut = com.google.protobuf.util.JsonFormat.printer()
        .omittingInsignificantWhitespace()
        .print(user);                                     // {"name":"张三","age":"18",...}

User.Builder builder = User.newBuilder();
com.google.protobuf.util.JsonFormat.parser().merge(jsonIn, builder);
```

> **注意**：官方 JSON 映射与"手写 struct tag 的 JSON"**不是一回事**——
> 前者把 `int64` 输出成字符串、字段名默认转 lowerCamelCase。
> 跨端一致性问题优先用官方映射，别自己定规则。

## 使用三：工程化（buf 让 schema 变更变成 CI 门禁）+ 排障

> 校验说明：本节所有 `buf` 结论都在**本机跑过**（buf 1.73.0 + protoc-gen-go，配置 `buf.yaml` `version: v2`），
> 包括"故意改坏 `.proto` 看它报不报"的六组实验（数据见第 2 节表格，逐条是真实输出）。
> 标 ⚠️ 的命令依赖官方 `protoc`，本机未安装，**未实测**。

### 1. 两个配置文件（替代那一长串 `protoc` 参数）

```yaml

# buf.yaml —— 放在模块根（本例仓库根），modules 指向 .proto 源码目录
version: v2
modules:
  - path: proto
lint:
  use:
    - STANDARD
breaking:
  use:
    - FILE        # 最严的一档：改名、删字段（哪怕已 reserved）都会拦下，详见第 2 节
```

```yaml

# buf.gen.yaml —— 声明生成什么、生成到哪
version: v2
clean: true             # 生成前清空 out 目录，避免删掉的 .proto 留下孤儿 .pb.go
plugins:
  - local: protoc-gen-go
    out: pb
    opt: module=verify  # 让 import path 与 option go_package 对齐，省掉那一串 M 参数
```

> ⚠️ **`lint: STANDARD` 有一条会立刻让你 CI 变红的规则**（实测）：
> `Package name "user" should be suffixed with a correctly formed version, such as "user.v1".`
> 也就是说 buf 强制 **包名带版本**（`package user.v1;`）。这条规则**值得留着**——
> 它就是"同一份 schema 允许 v1/v2 并存、灰度期两套代码共存"的前提。
> 代价：`.pb.go` 的包路径、`--decode=user.v1.User` 的类型名都要跟着变。

### 2. 四条日常命令，和"改坏 schema 会怎样"的六组实测

```bash

buf lint                                  # ✅ 规范检查（命名/包版本/字段号）
buf format -d --exit-code                 # ✅ 只打印 diff；格式不统一就失败退出
buf build                                 # ✅ schema 自检（最便宜的一道防线）
buf generate                              # ✅ 生成代码（替代手写 protoc 长参数）
buf breaking --against '.git#ref=main'    # ★ CI 门禁：与主干历史比对
```

下面是**在本机逐个改坏 `.proto` 跑出来的真实结果**（`--against '.git#ref=HEAD'` 比工作区与提交点）：

| 故意做的改动 | `buf build` | `buf breaking`（WIRE） | `buf breaking`（FILE） | 实测输出（原文） |
|---|---|---|---|---|
| 加一个新字段 `nickname = 8` | ✅ | ✅ 放行 | ✅ 放行 | — |
| 删字段 `hobby=3`，**同时补 `reserved 3`** | ✅ | ✅ 放行 | ❌ 拦下 | `Previously present field "3" with name "hobby" on message "User" was deleted.` |
| 删字段 `hobby=3`，**没补 reserved** | ✅ | ❌ 拦下 | ❌ 拦下 | `... was deleted **without reserving the number "3"**.` |
| 改 tag：`name` 从 1 → 5 | ✅ | ❌ 拦下 | ❌ 拦下 | `Previously present field "1" with name "name" ... was deleted without reserving the number "1".` |
| 改类型：`age` 从 `int64` → `string` | ✅ | ❌ 拦下 | ❌ 拦下 | `Field "2" with name "age" ... changed type from "int64" to "string".` |
| **只改字段名** `name` → `full_name` | ✅ | ✅ 放行 | ❌ 拦下 | `changed option "json_name" from "name" to "fullName"` + `changed name from "name" to "full_name"` |
| 在**仍写着 `reserved 6, 7`** 的 message 里用 tag 6 定义字段 | ❌ **编译直接失败** | — | — | ``use of reserved field number `6` `` |

**这张表里三条最该记住的结论**：

1. **`reserved` 由编译器强制执行**——只要那行 `reserved 6, 7;` 还在，
   复用 6 号根本**编译不过**（`use of reserved field number`）。
   正文 Q2 的纪律**有一半是机器保证的**。
2. **但它管不了"字段和 reserved 那行一起删掉"**（实测 `buf build` 通过）——
   这时只有**跟 git 历史比对**的 `buf breaking` 能查出来。
   所以 **`reserved` + CI 历史比对，两者缺一不可**，这不是重复建设。
3. **`FILE` 连"改名"都拦**（因为它还管 `json_name`，而 JSON 映射对前端是真实的兼容性），
   **`WIRE` 只管字节流**（改名放行、删字段只要 reserved 就放行）。
   → **默认用 `FILE`**（正文那张"改字段名二进制无感"的表，在 JSON 层是**有感**的）；
   只有当你确认下游全是二进制、且希望减少误报时才降到 `WIRE`。

> ⚠️ `buf breaking` 依旧**不懂业务语义**：把 `int32 age` 改名成 `int32 months`、
> 或者把"金额单位从元改成分"这种 tag/类型都不变的变更，它一律放行——**这种只能靠 review 和 PR 模板**。

CI 里的顺序别写反（先判兼容，再花钱生成）：

```yaml

# GitHub Actions
- run: buf lint
- run: buf breaking --against '.git#ref=${{ github.event.pull_request.base.ref }}'
- run: buf generate && git diff --exit-code pb/   # ★ 忘了重新生成 .pb.go 也是常见事故
```

### 3. 排障：怎么把 26 字节的二进制报文看成人

```bash

# 没有 .proto（例如从中间件/磁盘捞到一段匿名报文）：按 tag 号输出
protoc --decode_raw < req.bin                                   # ⚠️ 需官方 protoc，本机未装，未实测
# 有 .proto：临时给报文挂上字段名表（正文 Q1 那个"转字符串"坑的正规解法）
protoc --decode=user.User --proto_path=proto proto/user/user.proto < req.bin   # ⚠️ 同上

# ❌ 实测结论：buf 不提供这两个能力，别指望它
buf alpha protoc --decode=user.User proto/user/user.proto < req.bin
#   → Failure: --decode is not supported by buf.

# ✅ Go 侧不需要 protoc：使用一第 3 小节的 serialdemo.Inspect / prototext.Format 就够
```

Go 侧的等价输出（**本机实测**，见使用一 §3）：

```text

# serialdemo.Inspect(LegacyPacket)  —— 相当于 --decode_raw，只有 tag 没有名字
1: 2 字节 "li"
6: 11 字节 "13800138000"

# prototext.Format(m) —— 相当于 --decode，名字来自 schema
name:"li"  6:"13800138000"
```

> 看那个 **`6:`**：**服务端 schema 里已经没有 `phone` 了，报文里却还带着 6 号字段**——
> 只要有人把 6 拿去定义新字段，这条老数据就会被静默写错位置。
> **排查顺序永远是：先按 tag 解出报文，再看 schema 里那个 tag 现在归谁。**
> 拿到真实生产报文时，`--decode_raw` 对字符串会输出八进制转义（`"\345\274\240…"`），
> 那不是乱码，**是同一份 UTF-8 字节的另一种写法**。

### 4. 变更自查清单（把这张表贴到 PR 模板里）

"工具会不会拦"一列来自第 2 节的实测，不是推测。

| 改动 | wire 兼容？ | 但要注意 | 正确做法 | 工具会不会拦 |
|---|---|---|---|---|
| 加一个新字段 | ✅ | 老客户端**看不到**它（不能当必填用） | 用**从未出现过的新 tag**，别紧挨着老 tag 复用 | 全放行（只能靠 review） |
| 删字段 | ✅ | ⚠️ **tag 号被释放** | **必须 `reserved <tag>;`（连同字段名）** | `WIRE`：加了 reserved 才放行；`FILE`：一律拦 |
| **在还写着 `reserved` 的号上定义新字段** | — | 编译期就挡住，**但前提是那行没被删** | 保留 reserved | ✅ `buf build` 直接失败 |
| 改字段名 | ✅ 二进制无感 | ✗ 破坏 `protojson` 输出、反射代码、调用方源码 | 尽量不改；要改就同步前端/网关的字段映射 | `FILE` 拦（含 `json_name`）；`WIRE` 放行 |
| 改 tag 号 | ✗ **数据直接错位** | 老客户端与新服务端互相解析错 | 视为**不兼容变更**（新 message 或新 tag） | ✅ 两档都拦 |
| 改字段类型 | int32↔int64、string↔bytes ✅；其余 ✗ | `sint32→int32`、`float→double` 都**不兼容** | 新 tag + 双写迁移 | ✅ 两档都拦 |
| `repeated int32` 加/去 `packed` | proto3 默认 packed ✅ | proto2 需两端一致 | 别动；要动就上双写灰度 | ⚠️ 未实测 |
| 改 `oneof` 成员 | ✗ | 会覆盖语义 | 新 tag 新增字段，老 `oneof` 保留 | ⚠️ 未实测 |
| 改**语义**（单位元→分、状态码重排） | ✅ 完全无感 | 这才是最阴的一类 | 变更要走接口评审 + 版本号 | ❌ 任何工具都查不出 |

### 5. 一句话收尾（面试可直接用）

> JSON 是**给人和浏览器看的自描述文本**，Protobuf 是**给机器看的、需要 schema 才能解读的紧凑二进制**；
> 前者成本在"运行期和精度"（实测多一倍分配、int64 丢精度、NaN 传不了），
> 后者成本在"工程和纪律"（工具链、schema 演进、`reserved` 与 CI 门禁）。
> **选型不是问哪个快，而是问：这条数据的读端，是否愿意也持有一份 schema。**
