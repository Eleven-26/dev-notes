## 一、一条链路到底由哪些节点组成？

**本节要点**：链路不是"客户端 → 服务器"一条直线。中间至少有**默认网关（NAT）、运营商网络、目标侧的调度与负载均衡**三类节点，
每一类都会**改写报文或终结连接**——把这三类节点的行为想清楚，端到端排查才有着力点。

### 1.1 时序图：一次请求在链路上怎么走

```text
客户端              出口网关(NAT)         目标 LB / 代理        服务端
  │                     │                     │                   │
  │ ① 查路由表（最长前缀匹配）→ ARP 拿网关 MAC → 交给网卡
  │ ② SYN  src = 10.44.147.x:54321
  │ ───────────────────► │                                       │
  │                     │ ③ SNAT：源改为 203.0.113.9:40001，并写一行 conntrack
  │                     │ ④ 经运营商 AS / BGP 逐跳转发：每跳重写 MAC、TTL − 1（IP 不变）
  │                     │ ───────────────────► │                 │
  │                     │                     │ ⑤ DNAT 到后端；若是 L7 代理则新开一条 TCP
  │                     │                     │ ─────────────────► │
  │ ◄───────────────────── ⑥ 请求 / 响应（回程可能走另一条 AS 路径）─────────────────── │
  │                     │ ⑦ 网关按 conntrack 反向还原 203.0.113.9:40001 → 10.44.147.x:54321
  │                     │                     │                   │
  ▼ 全链路只被改写了三处：源 IP:端口（③）、目的 IP（⑤）、每一跳的 MAC
```

> ⚠️ 两个容易画错的点：**⑥ 的回程不一定沿原路**（跨 AS 时两个方向各自选路）；
> 而 **③ 与 ⑦ 是同一张 conntrack 表的两面**——表项在中间设备上，**两端都看不见**，
> 这就是"长连接被静默断开"的根本原因。

### 1.2 全景：按报文实际经过的顺序

| # | 节点 | 它做什么 | 改了什么 | 出问题时的典型症状 |
|---|---|---|---|---|
| ① | **本机进程与协议栈** | 选源端口 → 查路由表 → ARP 拿网关 MAC → 交给网卡 | 不改 IP；只填 MAC | 本地端口耗尽、握手就失败 |
| ② | **接入交换机 / AP** | 二层转发（按 MAC 表） | 不改 | 二层环路、VLAN 配错、同网段不通 |
| ③ | **默认网关**（路由器 + NAT + 防火墙） | 逐跳转发；**SNAT**；维护 conntrack 会话 | **源 IP 与源端口被改写** | NAT 表满、会话超时（长连接被静默断） |
| ④ | **运营商网络**（AS 内 IGP + 跨 AS BGP） | 逐跳转发，**TTL 每跳减 1** | 每跳**重写源/目的 MAC** | 绕路、跨网抖动、丢包 |
| ⑤ | **CDN / Anycast 节点**（可选） | 就近接入，可能就地响应 | 可能直接回源或就地返回 | 就近性差 → 首包 RTT 偏高 |
| ⑥ | **入口负载均衡 / 反向代理** | L4 转发 或 L7 终结 | **DNAT / 改 MAC / 隧道封装 / 新开一条 TCP** | 空闲超时、客户端真实 IP 丢失 |
| ⑦ | **服务端协议栈与进程** | `accept` / `recv`，应答原路返回 | 不改 | 全连接队列满、`CLOSE_WAIT` 堆积 |

> ⭐ 一句话记法：**IP 只在 NAT 与 LB 处被改，MAC 每一跳都在改，端口只有 NAT 会改**。
> 记住这条，抓包时"为什么看到的源 IP 和客户端说的不一样"就能自己解释。

### 1.3 本机实测：一条真实链路的"前三跳"

**默认路由**（决定"出本机之后交给谁"）：

```text
网络目标        网络掩码          网关           接口             跃点数
0.0.0.0        0.0.0.0        10.44.147.58    10.44.147.158      35
```

**ARP 表**（拿到网关的 MAC，才能组帧发出去）：

```text
接口: 10.44.147.158
  Internet 地址         物理地址              类型
  10.44.147.x8          42-56-9b-93-48-29     动态        ← 默认网关的 MAC
  224.0.0.22            01-00-5e-00-00-16     静态
  224.0.0.251           01-00-5e-00-00-fb     静态
```

**traceroute 前 6 跳**（TTL 每次加 1，靠中间设备回 `ICMP Time Exceeded` 画出去程路径）：

```text
  1     3 ms     1 ms     1 ms  10.44.147.x8        ← 默认网关，1ms 内
  2     *        *        *     请求超时。           ← 中间设备不回 ICMP
  3     *        *        *     请求超时。
  4    20 ms    17 ms    16 ms  192.170.14.25       ← 已出内网（公网段），17~20ms
  5     *        *        *     请求超时。
  6     *        *        *     请求超时。
```

**读法**：内网只有一跳（网关），之后进入运营商网络；**中间大量 `*` 不代表丢包**——
很多骨干设备被配置为"不回 ICMP / 限速回 ICMP"，而 **`traceroute` 只能靠 ICMP 才画得出这一跳**。
这也是"为什么 traceroute 的结果看着断断续续"的标准解释。

## 二、完整链路示例：一次 `https://example.com` 的访问

**本节要点**：把前面的节点与逐跳知识串成**一条完整时间线**。整个过程分四段——
**① 找路（DNS）→ ② 建连（TCP + TLS + HTTP）→ ③ 逐层封装（本机内部，5~9 步）→ ④ 传输与回程（中间设备 + 服务端）**。
两条分界线要记牢：**5~9 步全是"本机内部的封装"，没有任何网络往返**；而 **1~4 步每一次都要等一个往返**，
这就是"冷启动第一次请求慢"的全部来源。

### 2.1 13 步全景：每一步落在哪一层、细节在哪一篇

⭐ **这张表同时是「网络」目录的入口**：每一步都指到讲它的那篇，本目录新增篇目也往这里挂。

| 步 | 做什么 | 属于 | 参与方 | 有网络往返吗 | 细节在哪 |
|---|---|---|---|---|---|
| ① | **DNS 解析** `example.com` → IP | 应用层（DNS 走 UDP 53） | 本机 ↔ DNS 服务器 | 有（往返 1 次起） | [DNS解析.md](DNS解析.md) |
| ② | **TCP 三次握手**（目的端口 443） | 传输层 | 客户端 ↔ 服务端 | 有（1 个往返） | [tcp/TCP三次握手.md](tcp/TCP三次握手.md) |
| ③ | **TLS 握手**：协商密钥 + 验证证书 | 应用层（TLS 记录层跑在 TCP 之上） | 客户端 ↔ 服务端 | 有（TLS 1.3 一个、TLS 1.2 两个） | [HTTPS与TLS.md](HTTPS与TLS.md) |
| ④ | **发送 HTTP 请求** `GET /` | 应用层 | 客户端 → 服务端 | 单向发送 | [HTTP与gRPC.md](HTTP与gRPC.md) |
| ⑤ | **应用层封装**：组装 HTTP 报文 | 应用层 | **仅本机** | 无 | 见 2.4 |
| ⑥ | **传输层加 TCP 头**（源端口 → 443） | 传输层 | **仅本机** | 无 | 见 2.4 |
| ⑦ | **网络层加 IP 头**（源 IP → 目标 IP） | 网络层 | **仅本机** | 无 | 见 2.4 |
| ⑧ | **链路层加以太网头**（目的 MAC = 网关） | 链路层 | **仅本机** | 无 | 见 2.4 |
| ⑨ | **物理层发送**（转成信号） | 物理层 | **仅本机** | 无 | 见 2.4 |
| ⑩ | 经交换机 → 路由器 → 运营商 → 目标侧 | 链路层 ~ 网络层 | 中间所有设备 | 逐跳转发 | 见第三节 |
| ⑪ | **服务端逐层解封装**（自下而上剥头） | 全栈 | 服务端 | 无 | 见 2.5 |
| ⑫ | 处理请求、生成响应 | 应用层 | 服务端 | 无 | 见 2.5 |
| ⑬ | **响应回程**（可能走不同路径）→ 浏览器渲染 | 全栈 | 服务端 → 客户端 | 单向返回 | 见 2.5 / 3.6 |

> ⭐ **一条最容易被忽略的分界**：**DNS 不是这次连接的一部分**——它通常走 UDP 53 独立发一次查询，
> 拿到 IP 之后才有 ② 的 TCP 握手。所以"第一次打开网页慢"里，**DNS 与 TLS 是两个独立的怀疑对象**。
>
> ⭐ **另一条分界**：**⑤~⑨ 是"纵向"的封装动作**（在一台机器内部从上往下走），
> **①~④ 与 ⑩ 是"横向"的网络往返**（跨机器走）。前者只在本篇 2.4 给一张示意图，
> **字节级算例与 IP 分片在 [网络分层与数据包旅程.md](网络分层与数据包旅程.md) 第七节**，两篇不重复。

> ⭐ **13 步的两端还有几篇**（同一条链上，但不在"一次请求"之内）：
>
> - **开始之前**——**DHCP** 先给本机四个参数（IP / 掩码 / 网关 / DNS），没有它连 ① 都发不出去 →
>   [DHCP.md](DHCP.md)；
> - **结束之后**——HTTP/1.1 默认 **keep-alive 复用**这条连接，不再复用才走 **四次挥手**关闭，
>   `TIME_WAIT` / `CLOSE_WAIT` 都诞生在这一步 → [tcp/TCP四次挥手.md](tcp/TCP四次挥手.md)；
> - **服务端侧**——⑪ 之前，443 端口的进程是怎么在成千上万条连接上同时等着的 →
>   [IO多路复用.md](IO多路复用.md)；
> - **应用层格式**——④ 的请求体长什么样（JSON / Protobuf）、协议怎么挑 →
>   [数据序列化.md](数据序列化.md)、[通信选型.md](通信选型.md)。
>
> 传输层的另外三个细节（报文结构、滑动窗口、Nagle 与延迟确认）见 [tcp/](tcp/) 下三篇。

### 2.2 阶段一（①）：先决定"发给谁"

```text
浏览器                本机解析器            首选 DNS 服务器         递归 / 权威链
  │                       │                      │                     │
  │ ① getaddrinfo("example.com")
  │ ────────────────────► │                      │                     │
  │                       │ 先查 hosts 文件与本地 DNS 缓存
  │                       │ 命中就直接返回 —— 一个报文都不发         │
  │                       │ ── UDP:53 查询 A / AAAA 记录 ──►          │
  │                       │                      │ ── 递归 / 迭代 ──►  │
  │                       │                      │ ◄────────────────── │
  │ ◄───────────────────── A: 104.20.23.154 / AAAA: 2606:4700:10::…   │
  ▼ 拿到的往往**不是源站 IP**，而是 CDN / Anycast 就近节点的 IP
```

三个要点：

1. **DNS 走 UDP 53**（响应过大被截断时自动回落 TCP 53）——它**自带重试与超时**，与后面 ② 的 TCP 是两套独立机制。
2. **返回多条 A / AAAA 记录**：客户端自行选一条（现代实现用 Happy Eyeballs：IPv6 与 IPv4 并行尝试、谁快用谁）。
3. **"域名 → IP"这一跳就决定了走不走 CDN**：如果解析出来的是 CDN 的 Anycast 地址，后面整条链路都落在离你最近的那个节点上
   （详见 3.5 的 CDN 调度）。**这就是"为什么同一域名在不同地方 `ping` 出来 IP 不同"的原因。**

> ⚠️ 教科书里的经典示例 `93.184.216.34` 是 IANA 长期给 `example.com` 用的地址，用来做文档演示。
> 本机今天实测解析到的是 **Cloudflare 的 `104.20.23.154` / `172.66.147.243`**（见 2.6）——
> 这个差异本身就是"链路里多了一层 CDN"的直接证据。

> 📎 解析本身怎么走（递归 / 迭代查询、资源记录类型、DNS 负载均衡与安全）见 [DNS解析.md](DNS解析.md)——
> 本节只讲**这一步在链路上意味着什么**。

### 2.3 阶段二（②~④）：让两端"说上话"

TCP 与 TLS **各自有各自的握手**，串起来看就是"先建管道、再在管道里协商加密"：

```text
客户端                                              服务端 example.com:443
   │                                                          │
   │ ===== ② TCP 三次握手：证明"双向可达" ======               │
   │ ──── SYN  seq=x, src=51816 → dst=443 ──────────────────►  │ SYN_RCVD
   │ ◄─── SYN+ACK  seq=y, ack=x+1 ──────────────────────────── │
   │ ──── ACK  ack=y+1 ────────────────────────────────────►   │ ESTABLISHED
   │                                                          │
   │ ===== ③ TLS 握手：协商密钥 + 验证证书 =====               │
   │ TLS 1.3（1 个往返）：                                      │
   │ ──── ClientHello（SNI=example.com + 支持的套件 + key_share）►│
   │ ◄─── ServerHello（选定套件 + key_share）+ {证书 + Finished}  │
   │ ──── Finished + 应用数据（此后全部加密）────────────────►  │
   │ TLS 1.2（2 个往返，比上面多一个来回）                      │
   │                                                          │
   │ ===== ④ 发出 HTTP 请求 =====                              │
   │ ──── GET / HTTP/1.1   Host: example.com ──────────────►   │
   ▼ 响应在 ⑫⑬ 回来（回到 2.5）
```

设计上的三个关键点：

- **SNI**：一个 IP 上可能挂着成千上万个站点，`ClientHello` 里的 **SNI 扩展**告诉服务端"我要哪个域名"，
  服务端据此挑证书——**这也是"IP + 443 无法区分站点"这个问题的答案**。
- **证书验证四件事**：链式签名能不能一路验到根 CA、域名与 SAN 匹配、是否在有效期内、用途与吊销状态。
  任一条不过，浏览器直接中止——**此时 TCP 已经建好了**，所以报错是"证书错误"而不是"连不上"。
- **加密从什么时候开始**：TLS 1.3 在 `ServerHello` 之后的所有报文（含证书）都已加密；
  TLS 1.2 的证书是明文的。所以中间设备能看到的越来越少，**这也是"中间设备只能靠 SNI / 目的 IP 做策略"的原因**。

**冷启动至少三个往返**：DNS 一次 + TCP 一次 + TLS 1.3 一次（TLS 1.2 则多一次）。
本机实测 TLS 1.3 与 1.2 的握手耗时差约**一个 RTT**（见 2.6 实测），这就是升级 TLS 1.3 的直接收益。

> 📎 握手本身的细节不在本篇：三次握手的逐步拆解与半连接 / 全连接队列见
> [tcp/TCP三次握手.md](tcp/TCP三次握手.md)；TLS 1.2 / 1.3 的完整握手与证书校验见
> [HTTPS与TLS.md](HTTPS与TLS.md)；请求格式与多路复用见 [HTTP与gRPC.md](HTTP与gRPC.md)。
> 本节只讲**这几次往返在链路上叠加成了什么延迟**。

### 2.4 阶段三（⑤~⑨）：发送侧逐层封装（全部发生在本机）

这一段是**纯本地动作，一次网络往返都没有**。数据每往下一层走，就被套上一层的头：

```text
⑤ 应用层 —— HTTP 报文（纯文本）
   GET / HTTP/1.1
   Host: example.com
   User-Agent: ...
   ← 空行之后是请求体（GET 没有体）
──────────────────────────────────────────────────── 交给传输层
⑥ 传输层 —— 加 TCP 头（20 字节）→ 这时叫「段 segment」
   源端口 51816 | 目的端口 443 | seq / ack 序号 | 标志位 PSH,ACK | 窗口 | 校验和
   ← 两个端口在这一层出现：用来在对端主机里找到「哪个进程」
──────────────────────────────────────────────────── 交给网络层
⑦ 网络层 —— 加 IP 头（20 字节）→ 这时叫「包 packet」
   源 IP 10.44.147.158 | 目的 IP 104.20.23.154 | 协议 = 6(TCP) | TTL = 64 | 校验和
   ← TTL 初始 64，每过一个路由器减 1，减到 0 就回 ICMP Time Exceeded
──────────────────────────────────────────────────── 交给链路层
⑧ 链路层 —— 加以太网头（14 字节）+ 帧尾 FCS（4 字节）→ 这时叫「帧 frame」
   目的 MAC = 网关的 MAC（不是服务器的 MAC！）| 源 MAC = 本机网卡 | 类型 0x0800(IPv4)
   ← 目的 IP 不在本网段，本机只能先把帧交给网关，由它继续转发
──────────────────────────────────────────────────── 交给物理层
⑨ 物理层 —— 转成电信号 / 光信号 / 无线电波，以比特流发出去
```

**分层与容量的关系**（本机 MTU = 1500）：

```text
1500（以太网载荷上限）
  − 20（IP 头）
  − 20（TCP 头）
= 1460 字节 = MSS（一个 TCP 段能装的最大应用数据）
```

> 所以"一个 GET 请求一般一个段就装下了"是算出来的，不是猜的：
> 请求头通常几百字节 < 1460。**而响应一大就必然分多个段**——这也解释了为什么
> "大响应出问题"往往要往 MSS / MTU 方向查（见 4.1 的 PMTUD 黑洞）。

> ⭐ **⑧ 是最容易答错的一步**：目的 MAC 填的是**网关 MAC**，不是服务器的 MAC——本机只把帧交给"下一跳"。
> **为什么是网关、以及一个 5000 字节的包怎么被拆成 4 个帧**（IP 分片的字节算例），
> 见 [网络分层与数据包旅程.md](网络分层与数据包旅程.md) 第七节——那篇讲"纵向怎么封装"，本节只讲"横向怎么走"。

### 2.5 阶段四（⑩~⑬）：在路上、解封装与回程

```text
⑩ 出本机之后，每一跳只做三件事：按目的 IP 查表 → 重写源/目的 MAC → TTL − 1
   本机 → 交换机 / AP → 默认网关（SNAT + 写 conntrack）→ 运营商 AS / BGP → 目标侧节点
   注意：在 NAT 处，**源 IP 与源端口被改写**（10.44.147.158:51816 → 203.0.113.9:40001）
──────────────────────────────────────────────────── 到达服务端
⑪ 服务端自下而上解封装 —— 每一层只负责剥掉自己那一层的头
   ① 物理层收信号 → ⑧ 网卡校验 FCS、比对该帧的目的 MAC 是不是自己
   → ⑦ IP 层：目的 IP 是我吗？TTL 还有效吗？校验和对吗？协议是 TCP 吗？
   → ⑥ TCP 层：校验和、序号是否连续、四元组对应哪个 socket
   → ⑤ 交给监听 443 端口、且已建立连接的那个进程（在 accept 队列被取出）
   ⚠️ 若入口是 L7 反向代理 / LB：它在这里**终结这条 TCP，再新开一条 TCP 连后端**——
      后端看到的源 IP 是 LB 的，要拿真实 IP 只能靠 X-Forwarded-For / PROXY protocol
────────────────────────────────────────────────────
⑫ 处理请求并生成响应（CDN 就近命中缓存时直接返回，未命中才回源）
──────────────────────────────────────────────────── 回程
⑬ 源与目的对调：104.20.23.154:443 → 10.44.147.158:51816
   回程**可能走完全不同的 AS 路径**；到出口网关后按 conntrack 表把地址还原
   10.44.147.158:51816 → 网关转发给本机 → 浏览器逐层剥头 → 渲染
```

> ⭐ 一句话收尾：**去程"加了四层头"，回程"剥了四层头"，中间每一跳都可能改写 MAC / IP / 端口**。
> 所以"抓包看到的源 IP 和客户端说的不一样"完全正常——**取决于你在哪儿抓**（见 4.4）。

## 三、逐跳详解

**本节要点**：每一跳只做很少的几件事。把"**谁改了什么**"逐跳对齐，比背协议栈更有用。

### 3.1 逐跳改写一览：一个包身上被改了哪些字段

```text
跳                          源 IP              目的 IP             MAC              TTL
① 出客户端网卡              10.44.147.x        203.0.113.9         客户端 → 网关      64
② 网关 SNAT 之后            203.0.113.9 ←改    203.0.113.9         逐跳重写          63
③ 途中每个路由器            不变               不变                逐跳重写          逐跳 − 1
④ LB DNAT 之后              203.0.113.9        10.0.0.8 ←改        LB → 后端         62
⑤ 服务端收到                203.0.113.9        10.0.0.8            服务端网卡         61
```

> **MAC 每跳都换、IP 只在 ② 与 ④ 换、端口只在 ② 换、TTL 每跳减 1** —— 四句话记住这张表。
> 回程就是把这张表**按列反过来用**：网关靠 conntrack 把 `203.0.113.9:40001` 还原回 `10.44.147.x:54321`。

### 3.2 出本机：路由表 → ARP → 源端口

| 步骤 | 做了什么 | 判据 |
|---|---|---|
| **路由决策** | 拿目的 IP 逐条比对路由表，**最长前缀匹配**；内网走直连，其余走 `0.0.0.0/0` 默认网关 | `route print`（Windows）/ `ip route`（Linux） |
| **ARP** | 目的不在同网段时，**先解析网关的 MAC**（同网段则解析对端 MAC） | `arp -a`、`ip neigh` |
| **选源端口** | 内核从 `ip_local_port_range` 里选一个空闲端口，与"对端 IP:端口"组成**四元组** | `ss -tan` 看 src/dst |

> 四元组一旦建好就是这条连接的"身份证"：**NAT、LB、conntrack 全都以它为键**。
> 所以"同一个客户端对同一个服务端只能建少量连接"、端口耗尽、以及连接复用问题，
> 本质都是四元组空间的问题。

### 3.3 第一跳网关：MAC 重写、TTL 减 1、SNAT

- **MAC 逐跳重写**：以太网帧的源/目的 MAC **每一跳都换**（网关替你把帧重新封装成"下一跳的 MAC"），
  而 IP 报文**原样保持**——这就是"IP 是端到端、MAC 是逐跳"的含义。
  （对比：[网络分层与数据包旅程.md](网络分层与数据包旅程.md) 讲的是"为什么要两套地址"，这里讲"每一跳谁在换"。）
- **TTL 每跳减 1**：减到 0 就丢弃并回 `ICMP Time Exceeded` —— `traceroute` 就是靠这个机制工作的。
- **SNAT（源地址转换）**：出口把 `内网 IP:端口` 换成 `出口公网 IP:端口`，并在 **conntrack 表**里记一行映射，
  回程报文靠这张表反向还原。由此带来三个必知后果：

| 现象 | 原因 |
|---|---|
| 服务端看到的是**网关的公网 IP**，不是客户端内网 IP | 源 IP 被改写了（要拿真实 IP 只能靠应用层头：`X-Forwarded-For` / `PROXY protocol`） |
| **长连接被"静默断开"** | NAT 会话有**空闲超时**：超时后映射被删，两侧还以为连着，下一次发数据才发现断 |
| NAT 表被打满 → 新连接失败 | 每个会话占一行；短连接风暴会耗尽（Linux `nf_conntrack: table full, dropping packet`） |

**超时量级（必须按设备/内核口径说，别背一个数）**：

| 环境 | 会话空闲超时 | 说明 |
|---|---|---|
| Linux `conntrack` | TCP **established 默认 5 天**，`tcp_fin_wait` 120 秒，UDP 30 秒 | 以内核与发行版文档为准 |
| 云厂商 NAT 网关 / SLB | 通常 **几十秒 ~ 几分钟** | 各家默认不同，以产品文档为准 |
| 家用路由器 / 办公出口 | 常见**几分钟 ~ 几十分钟** | 最容易"看起来莫名其妙断连"的地方 |

> 这就是**长连接必须配心跳（keepalive）**的根本原因：不是为了"探测存活"，而是为了**让中间设备的会话不过期**。
> 心跳间隔必须**小于链路上所有 NAT / LB 超时里最小的那个**——这是选心跳周期的唯一依据。

### 3.4 公网：AS、BGP、IXP 与"去回程不对称"

- AS 内部用 IGP（OSPF/IS-IS）选路；**AS 之间用 BGP** 交换可达性并选路。
- 常见互联方式：**对等（peering）**、**中转（transit，要付费）**、**在 IXP 交换中心互联**。
  所以"理论上最短"的路径不一定被选中——BGP 按**策略与商业关系**选路，绕路是常态。
- ⭐ **去程与回程通常不是同一条路**（不对称路由）：跨网的 a→b 与 b→a 由**两个方向的 AS 各自选路**。
  推论：**在客户端做的 `traceroute` 只画得出"去程"**，回程要看对端或中间设备。

### 3.5 入站：CDN、负载均衡与反向代理

**CDN 的两种调度**：

| 方式 | 怎么做 | 特点 |
|---|---|---|
| **DNS 调度** | 权威 DNS 按递归解析器（LDNS）的位置返回**就近节点**的 IP | 主流；调度粒度取决于 LDNS 位置，可能"就近判错" |
| **Anycast** | 同一 IP 段由 **BGP 宣告到多地**，路由系统自然把包带到最近的一点 | 天然抗 DDoS、切换快；⚠️ 路由变化会让同一连接落到不同节点，对长连接要谨慎 |

**四层负载均衡的三种转发模式**（三种模式的区别，核心在"回程走哪"）：

| 模式 | 改什么 | 回程是否过 LB | 特点 |
|---|---|---|---|
| **DR（直接路由）** | 只改**目的 MAC**（IP 不动），后端把 VIP 配在环回口上 | ❌ 不过 | 性能最好；要求 LB 与后端二层可达 |
| **NAT（LVS-NAT）** | 改**目的 IP/端口**，后端网关指向 LB | ✅ 必须过 | 配置简单；LB 成为回程瓶颈 |
| **隧道（IPIP / GRE）** | 在原始报文外再套一层 IP 头 | 取决于后端是否直接回 | 可跨网段；**会使 MTU 变小**（见 3.1） |

**七层反向代理**（Nginx / Envoy）：它是**终结者**——客户端与代理之间一条 TCP，代理与后端之间**另一条 TCP**。
推论：① 后端看到的对端是代理；真实客户端 IP 只能靠 `X-Forwarded-For` / `PROXY protocol` 传递；
② **TCP 层语义不再端到端**（如 TCP 快速打开、客户端侧的重传，代理不会替你传到对端）；
③ 代理自己的**空闲超时**往往比 NAT 短，是长连接被断开的第一嫌疑人。

> K8s 里的具体形态：`kube-proxy` 用 iptables / IPVS 做 **DNAT**，跨节点再套 **VXLAN / IPIP 封装**——
> 这就是容器里 MTU 常见被调成 **1450** 的原因（1500 − 隧道头开销）。

### 3.6 回程：为什么"发出去正常、收回来慢"

回程经过的节点**可能与去程完全不同**，且**你手里的工具大多只能看去程**。
所以"上传正常、下载慢"、"小请求正常、大响应卡住"这类现象，
优先怀疑：**回程路径上的拥塞 / 限速**、**MTU 问题**、或**回程被中间设备丢出方向的 ICMP**。

## 四、链路上的四个"隐形陷阱"

**本节要点**：这四个问题的共同点是——**配置看起来都是对的，报错也不指向真正的原因**。

### 4.1 MTU / MSS 与 PMTUD 黑洞

- 路径 MTU 由链路上**最小**的一段决定；`MSS = MTU − 40`（IPv4 的 IP 头 + TCP 头）。
- 发送方靠 **PMTUD**（Path MTU Discovery）发现更小的 MTU：发 DF=1 的大包 → 中间设备回
  **`ICMP Fragmentation Needed`** → 发送方据此调小 MSS。⚠️ **前提是 ICMP 能回来**。
- 一旦 ICMP 被防火墙/中间设备丢弃 → **PMTU 黑洞**：表现为"**小请求正常、大响应卡死**"
  （握手成功、`GET` 有响应头、一到大数据体就卡住直到超时）。

**本机实测（探测 PMTU 的前提是否成立）**：

```text
> ping -f -l 1472 -n 1 114.114.114.114
正在 Ping 114.114.114.114 具有 1472 字节的数据:
请求超时。
数据包: 已发送 = 1，已接收 = 0，丢失 = 1 (100% 丢失)
```

> ⚠️ **不要把这解读成"MTU 有问题"**：它只说明**带 DF 的探测包没拿到任何回应**。
> 而"ICMP 收不到"恰恰就是 **PMTUD 失效的条件**——在真实环境里表现为
> "握手正常、大包卡住"，排查时要用 `tcpdump` 看**是否发出去了 `ICMP Fragmentation Needed`**，
> 而不是只看 ping。本机 MTU 读数为 **1500**（`netsh interface ipv4 show subinterfaces`）。

**缓解手段**：把 MSS 钳到安全值（`tcp_mss_clamp`/网关侧 MSS clamping）、容器/隧道场景显式下调 MTU、
或确保 ICMP 类型 3 不被中间设备丢。

### 4.2 NAT / conntrack 超时：长连接的静默杀手

参见 3.3 的超时表。判断方法：**连接空闲一段时间后，第一个"业务请求"失败、重连后正常** → 基本可以判定是会话过期。
对策：心跳间隔 < 链路上最小超时；或用应用层重连（连接池要做"取出来先探活"）。

### 4.3 负载均衡的空闲超时：通常比 NAT 更早

LB 侧的"空闲连接回收"常是 60s 级，**比 NAT 短**——所以长连接被断的第一嫌疑人应该是 LB/代理，
排查顺序：**代理空闲超时 → NAT/conntrack → 服务端 keepalive → 客户端**。

### 4.4 路径不对称与"在哪儿抓包"

- **抓包位置决定你看到的是"改写前"还是"改写后"**：
  - 客户端本机抓：看到的是**未 SNAT** 的报文（源 IP 还是内网地址）；
  - 服务端抓：源 IP 是**出口公网/LB 地址**（要真实 IP 得看应用层头）；
  - LB 上抓：能看到**两个方向的连接**（客户端↔LB、LB↔后端）。
- 只在一端抓包时，"没有收到 ACK"这个结论**只对那一端成立**——中间设备可能已经收到并转发了。
- 常见误判：在客户端看到大量重传 → 结论"服务端丢包"，实际可能是**回程路径**在丢。

## 五、分层观测点：每层能回答什么

**本节要点**：**先分层定位，再抓包**。`tcpdump` 是最后手段而不是第一手段——它能证明"收到/没收到"，但解释不了"为什么"。

| 层次 | 工具（Windows 对应） | 能回答 | 不能回答 |
|---|---|---|---|
| 应用 | 日志 / trace_id / 错误码 | 业务是否走到、哪一步慢 | 网络层问题 |
| Socket | `ss -tanp`（`netstat -ano`） | 连接状态、队列长度、`CLOSE_WAIT` 堆积 | 包有没有丢在路上 |
| 内核协议栈 | `netstat -s`、`nstat`、`ss -ti` | 重传、乱序、丢弃计数、RTT/拥塞窗口 | 具体哪个中间设备干的 |
| 链路 / 抓包 | `tcpdump`、Wireshark（`pktmon`） | 实际报文的 seq/ack/重传/ICMP | 设备配置与策略原因 |
| 路由 / 路径 | `traceroute`、`mtr`、`ping` | 去程跳数、每跳时延与丢包 | 回程路径（需对端配合） |
| NAT / 会话 | 网关 `conntrack -L`、设备会话表 | 会话是否还在、超时值 | 应用层语义 |
| 对端 | LB 访问日志 / 服务端日志 | 是否到达、上游耗时拆分 | 客户端到 LB 那一段 |

## 使用：一条"端到端慢 / 不通"的排查路径

按链路顺序推进，每一步只回答一个问题：

```bash
# ① 本机：连接建起来了吗？（状态、队列、CLOSE_WAIT）
ss -tanp | head
# ② 本机：协议栈有没有重传/丢包？（先排除本机侧）
netstat -s | grep -iE "retrans|drop|overflow"
# ③ 路径：去程几跳、哪一跳开始变慢/丢包（连续跑，看抖动）
mtr -rwzc 20 <目标IP>
# ④ 网关/出口：会话还在吗、超时多少（长连接场景必查）
#    Linux: conntrack -L | grep <端口>
#    云上：看 NAT 网关 / SLB 会话超时设置
# ⑤ 抓包：定位"谁没回"（在两端各抓一次，对比才有效）
tcpdump -ni any host <对端IP> and port <端口> -c 200 -w /tmp/cap.pcap
# ⑥ 大包卡住：重点看 ICMP 类型 3 与 MSS（PMTUD 黑洞）
tcpdump -ni any icmp and host <对端IP>
# ⑦ 真实客户端 IP：看应用层头是否被正确传递
#    curl -H 'X-Forwarded-For: 1.2.3.4' 或看 LB 的 PROXY protocol 配置
```

**Windows 侧对应命令**（本机实测用到的就是这几条）：

```bash
route print -4                      # 路由表与默认网关
arp -a                              # 网关 MAC（出网第一跳靠它）
netsh interface ipv4 show subinterfaces   # 各接口 MTU（本机 1500）
tracert -d -h 6 <IP>                # 去程跳数（靠 ICMP）
netstat -ano                        # 连接状态 + PID
```

## 延伸追问

- **一个包从客户端到服务端，哪些字段被改了？** → **MAC 每跳都改**（逐跳重封装）；
  **IP 只在 NAT / LB（DNAT）处改**；**端口只有 NAT / DNAT 会改**；TTL 每跳减 1。记住这三条就不会答乱。
- **`traceroute` 的原理？为什么会有 `*`？** → 靠 TTL 逐跳 +1，让第 N 跳设备回 `ICMP Time Exceeded`；
  `*` 是那一跳**不回或限速回 ICMP**，不代表丢包。
- **NAT 之后服务端怎么拿到客户端真实 IP？** → 拿不到（IP 已被改写）。
  只能在应用层传：`X-Forwarded-For`（HTTP 层，要信任链校验）、`PROXY protocol`（L4 也能带），
  或让 LB 以 DR 模式转发（不改 IP）。
- **四层 LB 的三种模式区别？** → DR 只改目的 MAC（**回程不过 LB**，性能最好）；
  NAT 改目的 IP（**回程必须过 LB**）；隧道模式再套一层 IP 头（**MTU 会变小**）。
- **为什么 K8s 里 MTU 常见是 1450？** → 跨节点走 VXLAN / IPIP 隧道，**封装头占了 50 字节**，
  1500 − 50 = 1450；不调就会出现"小包正常、大包卡死"的 PMTU 黑洞。
- **长连接为什么会"静默断开"？怎么防？** → 链路上的 **NAT / LB 会话空闲超时**把映射删了，两端不知道。
  防法：心跳间隔小于**链路上最小的那个超时**；连接池取出时先探活。
- **去程和回程是同一条路吗？** → 不一定，**跨 AS 时两个方向各自用 BGP 选路**；
  所以在客户端 `traceroute` 只画出**去程**，回程问题要找对端或中间设备配合。
- **"上传正常、下载慢"怎么排？** → 优先怀疑**回程路径拥塞/限速**、**PMTUD 黑洞**（大包）、
  以及**中间设备丢出方向的 ICMP**；两端同时抓包对比才能定性。
- **抓包应该在哪儿抓？** → 看你要回答什么：客户端抓能看到**未 SNAT** 的报文；
  服务端抓看到的是**LB/NAT 改写后**的；要一次看全两个方向，就在 **LB 上抓**。**只在单端抓包时，"没收到"只对那一端成立。**
- **一次冷启动的 HTTPS 请求最少几个往返？** → **至少 3 个**：DNS 一次 + TCP 三次握手一次 + TLS 握手一次
  （TLS 1.3）。若服务端只支持 **TLS 1.2**，TLS 部分要**两个**往返，加起来 4 个——这就是 TLS 1.3 把 2-RTT 压成 1-RTT
  的直接收益（本机实测 TLS 1.3 中位 252 ms、TLS 1.2 中位 462 ms，差约一个 RTT）。
- **DNS 查询和后面的 TCP 是同一个连接吗？** → **不是**。DNS 通常走 **UDP 53** 的独立查询
  （响应过大被截断时才回落 TCP 53），拿到 IP 之后才建 TCP；两者的超时与重试机制互不相干。
  所以"第一次打开慢"要把 **DNS** 与 **TLS** 当两个独立怀疑对象分开测。
- **⑧ 里的目的 MAC 填谁的？** → **填网关的 MAC**，不是服务器的。本机只在"目的 IP 与自己在同一网段"时才会
  解析对端 MAC；跨网段时**本机只负责把帧交给下一跳**，剩下的路由由网关决定——**这是"接上网关就能访问全网"的根本原因**。
