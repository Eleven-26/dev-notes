## 一、类加载器有哪些？各自负责加载什么？

双亲委派机制，向上检查，向下委派。

在 Java 中，类加载器是用来加载 Java 类到 Java 虚拟机（JVM）中的组件。Java 提供了不同层次的类加载器，主要包括以下几种：

| 类加载器 | 实现语言 | 负责加载 |
|---|---|---|
| **启动类加载器**（Bootstrap Class Loader） | C++ | 最顶层，Java 核心类库（如 `java.lang` 包下的类），位于 JRE 的 `lib` 目录 |
| **扩展类加载器**（Extension Class Loader） | Java | 启动类加载器的子加载器，Java 扩展类库，位于 JRE 的 `lib/ext` 目录 |
| **应用程序类加载器**（Application Class Loader） | Java | 也叫系统类加载器，用户类路径（`classpath`）下的类，即自己写的类和第三方库 |
| **自定义类加载器**（Custom Class Loader） | Java | 按需自定义，继承 `ClassLoader` 类 |

### 1.1 实测：加载器层级与上下文类加载器

```java
System.out.println("String 的加载器           = " + String.class.getClassLoader());
System.out.println("本类的加载器              = ClassInitDemo.class.getClassLoader());
System.out.println("线程上下文类加载器（SPI 用）= " + Thread.currentThread().getContextClassLoader());
ClassLoader cl = ClassInitDemo.class.getClassLoader();
while (cl != null) {
    System.out.println("  " + cl);
    cl = cl.getParent();
}
```

本机 JDK 1.8 实测输出：

```text
String 的加载器           = null
    （null 表示 Bootstrap，C++ 实现，Java 侧不可见）
本类的加载器              = sun.misc.Launcher$AppClassLoader@73d16e93
线程上下文类加载器（SPI 用）= sun.misc.Launcher$AppClassLoader@73d16e93
父加载器链：
  1. sun.misc.Launcher$AppClassLoader@73d16e93
  2. sun.misc.Launcher$ExtClassLoader@15db9742
  3. Bootstrap（null）
```

⭐ 三个可以直接引用的细节：

- **`String.class.getClassLoader()` 返回 `null`**——不是「没有加载器」，而是 Bootstrap 由 JVM 用 C++ 实现，在 Java 侧没有对应的对象可返回。
- **父子链是「组合」不是「继承」**——`AppClassLoader` 并不是 `ExtClassLoader` 的子类，而是持有 `parent` 引用（这也是「双亲委派」而不是「父子继承」的原因）。
- **线程上下文类加载器默认就是 AppClassLoader**，它是 SPI 场景下「父加载器反向委托子加载器」的唯一通道（见第六节）。

## 二、双亲委派机制的工作原理是什么？

双亲委派机制的工作过程可以概括为「**先委托，后自己加载**」：

1. 当一个类加载器收到类加载请求时，它首先不会自己去尝试加载这个类，而是把这个请求**委派给父类加载器**去完成。
2. 每一层的类加载器都是如此，**依次向上委托**，直到到达启动类加载器。
3. 启动类加载器会尝试加载这个类，如果能加载则加载成功；如果不能加载，就会将加载任务**返回给子类加载器**，让子类加载器去尝试加载。
4. 依次向下，直到有类加载器成功加载该类，或者所有类加载器都尝试过仍无法加载，此时抛出 `ClassNotFoundException`。

> ⭐ 一句话记忆：**向上检查、向下委派**——先一路往上问「你能不能加载」，都不行再由下往上逐级尝试自己加载。

## 三、双亲委派有什么优点？

| 优点 | 说明 |
|---|---|
| **安全性** | 可以防止恶意代码替换 Java 的核心类库。核心类库由启动类加载器加载，即使用户编写了一个名为 `java.lang.String` 的类，也不会被加载 |
| **避免类的重复加载** | 父类加载器已加载过某个类时，子类加载器无需重复加载，保证类在 JVM 中的唯一性 |
| **层次结构清晰** | 不同层次的类加载器负责不同范围的类加载，管理更清晰有序 |

⚠️ 「保证唯一性」这句话有边界：它只保证**同一个加载器（及其委派链）内唯一**。**不同加载器加载同一个类，会得到两个不同的 `Class` 对象**——这正是「诡异的 `ClassCastException`」的来源（见第七节）。

## 四、类加载的五个阶段

一个类从字节码到能用，要经过五个阶段。**「准备 vs 初始化」的差别就在这张表里**：

| 阶段 | 做什么 | 关键细节 |
| --- | --- | --- |
| **加载（Loading）** | 把字节码读进内存，生成 `Class` 对象 | 来源可以是 class 文件、JAR、网络、动态代理生成 |
| **验证（Verification）** | 校验字节码是否合法、安全 | 文件格式 → 元数据 → 字节码 → 符号引用，四层校验 |
| **准备（Preparation）** | 为**静态变量**分配内存并设**零值** | ⭐ `static int a = 10` 在这一步 `a = 0`；`static final` 常量值此时就位（编译期已确定） |
| **解析（Resolution）** | 把常量池的**符号引用**替换为**直接引用** | 时机灵活：可懒解析（首次使用时） |
| **初始化（Initialization）** | 执行 `<clinit>()`，赋**真实值** | ⭐ 到这一步 `a` 才等于 10；`<clinit>` 由编译器收集所有静态变量赋值与 `static {}` 块按源码顺序生成 |

⭐⭐ **最容易答错的一点**：`static int a = 10` 在**准备阶段是 0**，到**初始化阶段才是 10**。所以「静态变量什么时候有值」的准确答案是「初始化阶段」。

另外两条：

- **`<clinit>()` 不是构造器**：构造器是 `<init>()`（实例级），`<clinit>()` 是类级初始化，由 JVM 保证**线程安全**（多线程同时初始化同一个类时，只有一个线程执行 `<clinit>`，其余阻塞等待）。
- **接口的 `<clinit>` 特殊**：接口初始化时不要求父接口先初始化（只有真正用到父接口中的变量时才初始化它），与类不同。

## 五、类初始化的时机：哪些会触发、哪些不会 ⭐

这是「类加载」最实用的一节——**线上「类没被初始化」的诡异问题基本都出在这里**。

### 5.1 会触发的五种（主动引用）

| 场景 | 示例 |
| --- | --- |
| `new` 一个对象 / 读写静态字段 / 调用静态方法 | `new Child()`、`Child.runtimeValue` |
| 反射调用 | `Class.forName("Child")` |
| 初始化子类时**先初始化父类** | `new Child()` 会先跑 `Parent.<clinit>` |
| 虚拟机启动时的主类 | 含 `main()` 的类 |
| `MethodHandle` / `invokedynamic` 解析到该类的静态成员时 | Lambda 绑定的目标类 |

### 5.2 **不会**触发的三种（被动引用）

| 场景 | 为什么不会触发 |
| --- | --- |
| 通过**子类名**访问**父类**的静态字段 | 只有真正声明该字段的类才被初始化 |
| 访问**编译期常量**（`static final` + 字面量） | 常量在**编译期已折叠进调用方的常量池**，运行时不涉及该类 |
| 定义该类的**数组** | 数组由 JVM 直接创建，元素类的初始化被推迟到真正使用元素时 |

### 5.3 实测证据

被测代码设计（顺序很关键）：子类 `Child extends Parent`，父子各带一个打印语句的 `static {}` 块，子类另有一个编译期常量 `COMPILE_CONST` 与一个运行期静态变量 `runtimeValue`。

```java
// 1. 通过子类名访问父类静态字段
System.out.println(Child.VALUE);
// 2. 访问子类的编译期常量
System.out.println(Child.COMPILE_CONST);
// 3. 定义子类数组
Child[] arr = new Child[2];
// 4. 读取子类的运行期静态变量
System.out.println(Child.runtimeValue);
```

本机 JDK 1.8 实测输出（已删去解释性打印）：

```text
=== 1. 通过子类名访问父类的静态字段（只初始化父类） ===
  [父类 Parent 的 <clinit> 执行]
Child.VALUE = 10
                        ⭐ 只看到父类的 <clinit>，子类未被初始化

=== 2. 访问编译期常量（不触发任何初始化） ===
Child.COMPILE_CONST = 20
                        ⭐ 没有任何 <clinit> 输出

=== 3. 定义子类数组（不触发元素类初始化） ===
数组长度 = 2
                        ⭐ 仍没有任何 <clinit> 输出

=== 4. 读取子类的非编译期常量（触发子类初始化） ===
  [子类 Child 的 <clinit> 执行]
Child.runtimeValue = 30
                        ⭐ 到这一步才初始化子类（父类已在第 1 步初始化，不重复）
```

### 5.4 常量为什么不需要初始化：`javap` 给出的铁证

`Child.COMPILE_CONST` 是 `static final int COMPILE_CONST = 20;`，看调用方 `main` 方法的字节码：

```bash
javap -c ClassInitDemo
```

```text
60: ldc           #16   // String Child.COMPILE_CONST = 20
62: invokevirtual #4    // Method java/io/PrintStream.println:(Ljava/lang/String;)V
```

⭐ **`"Child.COMPILE_CONST = " + 20` 整段被编译期折叠成了一个字符串常量**（`ldc #16`），连运行时拼接都没有发生——更不用说去读取 `Child` 类的字段。这就是「编译期常量不触发类初始化」的底层原因。

⚠️ **反面案例**：把 `static final int` 换成 `static final Integer`、或值是方法调用/随机数（`static final long NOW = System.currentTimeMillis()`），**常量折叠就不成立**，读取时会正常触发类初始化。

## 六、哪些情况会破坏双亲委派机制？

虽然双亲委派机制有很多优点，但在某些特殊场景下需要打破它：

- **Java Web 应用服务器**：为了实现类的隔离和热部署等功能，需要自定义类加载器并打破双亲委派机制。
- 典型例子还包括 **SPI 机制**（如 JDBC 驱动加载）、**OSGi** 等，它们需要父类加载器反向委托子类加载器去加载实现类。

### 6.1 SPI 为什么必须打破委派

以 JDBC 为例，矛盾在于：

- `java.sql.DriverManager` 在 **`rt.jar`** 里，由 **Bootstrap** 加载；
- 各数据库的驱动实现（`com.mysql.cj.jdbc.Driver`）在**应用 classpath** 里，只有 **AppClassLoader** 能加载；
- Bootstrap 看不到应用 classpath，**按双亲委派它根本加载不到驱动实现**。

解法是 **线程上下文类加载器（TCCL）**：

```java
// DriverManager 内部大致做的事（getConnection 时）
ServiceLoader<Driver> loader = ServiceLoader.load(Driver.class);   // 用的是 TCCL
```

`ServiceLoader.load` 默认取 `Thread.currentThread().getContextClassLoader()`（实测值就是 AppClassLoader），于是「父加载器（Bootstrap）委托子加载器（App）加载实现类」——**方向反了**，这就是「破坏双亲委派」的含义。

⚠️ 由此产生一个真实事故场景：**在容器（Tomcat / 线程池）里换掉 TCCL 后忘记还原**，会导致后续 `ServiceLoader` 加载不到预期实现，且报错位置与根因相隔很远。

## 七、类加载问题的排查手段

双亲委派相关的线上问题，表现都是「类找不到 / 类冲突 / 类版本不对」，先按下面的表分诊：

| 异常 | 含义 | 常见根因 |
|---|---|---|
| `ClassNotFoundException` | **编译期就依赖**，运行期在 classpath 里找不到 | 依赖没打进包、`Class.forName` 写错类名 |
| `NoClassDefFoundError` | 编译时在、运行时不在了（或首次加载已失败） | 静态初始化抛错、依赖冲突导致加载失败后不再重试 |
| `LinkageError` / `NoSuchMethodError` | 类加载到了，但**版本对不上** | 同一个类被两个 classpath 各加载了一份（父加载器与子加载器各一份） |

常用命令与开关：

```bash
java -verbose:class ...                   # 打印每个类由哪个加载器加载（定位重复加载）
jcmd <pid> VM.class_hierarchy <类名>      # 看某个类的加载器层级
jcmd <pid> GC.class_histogram | head      # 看哪些类实例最多（含动态代理类）
-XX:+TraceClassLoading -XX:+TraceClassUnloading   # 加载/卸载全过程
```

> ⭐ **同名类被两个加载器各加载一份**是「诡异的 `ClassCastException`」的经典成因——类名一样但 `Class` 对象不同，`instanceof` 必然为 false。Occurrence 常见于「容器 + 插件热部署 + 自写加载器」的组合。

## 延伸追问

- **为什么要打破双亲委派？** → 父加载器加载不到子加载器可见的实现类（如 SPI 场景：Bootstrap 加载的 `DriverManager` 需要 App 加载的驱动实现），需要线程上下文类加载器反向委托。
- **如何自定义一个类加载器？** → 继承 `ClassLoader`，重写 `findClass`（遵循委派）或 `loadClass`（可打破委派）。
- **同一个类被两个不同加载器加载会怎样？** → 会产生两个不同的 Class 对象，`instanceof` 与类型转换都会失败。
- **Tomcat 为什么要用多个类加载器？** → 各 Web 应用依赖版本可能冲突，需要按应用隔离（WebAppClassLoader 优先自己加载，打破委派）。
- **类加载的「准备」和「初始化」有什么区别？** → 准备阶段为静态变量分配内存并设**零值**（`static int a = 10` 此时是 0），初始化阶段执行 `<clinit>()` 才赋**真实值**（此时 a = 10）；`static final` 的编译期常量在准备阶段就已是最终值。
- **哪三种情况不会触发类初始化？** → ①通过子类名访问父类的静态字段（只初始化声明字段的类）②访问编译期常量（已折叠进调用方常量池）③定义该类的数组（元素类初始化被推迟）。
- **`<clinit>()` 是线程安全的吗？** → 是。JVM 保证同一个类只有一个线程执行 `<clinit>`，其余线程阻塞等待；这也是经典「静态初始化死锁」的来源（两个类互相在 `<clinit>` 里引用对方）。
- **JDK 9 之后类加载器有什么变化？** → 扩展类加载器（ExtClassLoader）被**平台类加载器（PlatformClassLoader**）取代，模块化（JPMS）下类加载按模块划分可见性。
