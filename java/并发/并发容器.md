# Java 并发容器

> `ConcurrentHashMap` 怎么做到高并发（JDK 7 分段锁 → JDK 8 CAS + 桶级 `synchronized`）、
> 它的四个反直觉行为（拒绝 null / `size` 是估算 / 复合操作不原子 / 迭代器弱一致）、
> `CopyOnWriteArrayList` 唯一适合的场景（**写密集慢 386 倍实测**）、
> 以及 `BlockingQueue` 家族与九种操作的三态语义。
>
> 内容整理自个人学习笔记。**全部结论配套本机 JDK 1.8.0_321 实测**（Windows / 8 核 CPU）。
> 背后的 `volatile` / CAS 原理见 [JMM与内存屏障.md](JMM与内存屏障.md)；锁的语义见 [锁与AQS.md](锁与AQS.md)；
> 队列在业务里的用法见 [线程池.md](线程池.md)。

## 一、`ConcurrentHashMap` 怎么做到高并发？

**本节要点**：核心思路只有一句话 —— **把「一把大锁」拆小**。但要能说清 JDK 7 与 JDK 8 拆的方式完全不同，而且 JDK 8 的读路径是**完全无锁**的。

### 1.1 两代的演进

| | JDK 7 | JDK 8 |
|---|---|---|
| 结构 | `Segment[]`（默认 16 个）+ 每个 Segment 一个 `HashEntry[]` | `Node[]`（一个数组，没有 Segment） |
| 锁粒度 | **每个 Segment 一把 `ReentrantLock`** | **每个桶（数组下标）一把 `synchronized`** —— 只锁住那一个桶的首节点 |
| 并发度 | 固定 = Segment 个数（默认 16） | ≈ 数组长度（随扩容增长） |
| 扩容 | Segment 内单独扩容 | **多线程协同扩容**（`transfer`，各线程领一段桶一起搬） |
| 读路径 | 也要**先定位 Segment，再读** | **完全无锁**：数组元素是 `volatile Node`，直接读 |
| 链表过长 | 一直链下去 | 长度 ≥ 8 且数组 ≥ 64 时**转红黑树** |

⭐ **并发度从「固定 16」变成「随容量增长」是 JDK 8 的关键改进**：JDK 7 的 16 个 Segment 在高并发下会变成新的瓶颈（16 个线程以上就开始互相等锁）。

### 1.2 一次 `put` 做了什么（JDK 8）

```text
put(key, value)
  ├─ 若 table 为空 → initTable()（CAS 抢一个 SIZECTL 标志，只让一个线程初始化）
  ├─ 计算 hash → 定位桶 (n-1) & hash
  ├─ 桶为空 → CAS 直接把新节点放进去（无锁）
  ├─ 桶正在扩容（hash == MOVED）→ 当前线程**加入扩容**
  └─ 桶不为空 → synchronized (桶首节点)      ← 只锁这一个桶
        ├─ 链表则遍历，key 相同就覆盖
        └─ 否则尾插；若链表长度 ≥ 8 → treeifyBin()
```

⭐ 三处要点：

1. **桶为空时是 CAS，不加锁** —— 这是无竞争路径（最常见的情况）极快的原因；
2. **只有桶非空时才 `synchronized`** —— 锁的对象是**桶的首节点**，不同桶完全并行；
3. **`size()` 用的不是一把锁**：JDK 8 用 `CounterCell[]`（本质是 `LongAdder` 的思路，分散计数、求和时汇总）—— 所以**并发下 `size()` 是估算值**。

### 1.3 实测：并发写吞吐

4 线程各写 5 万个**不同 key**（`MapLab.java` 实验 1，跑 3 轮取最小值）：

```text
== 实验 1：写入不同 key 的吞吐（每线程 5 万次）==
  ConcurrentHashMap         6.9 ms   最终 size=200000
  synchronizedMap          26.7 ms   最终 size=200000
  Hashtable                33.9 ms   最终 size=200000
```

两次运行的范围：

| 实现 | 耗时 | 相对 `ConcurrentHashMap` |
|---|---|---|
| `ConcurrentHashMap` | 6.0 ~ 6.9 ms | 1× |
| `Collections.synchronizedMap` | 26.7 ~ 27.6 ms | 约 4.2× |
| `Hashtable` | 33.9 ~ 35.5 ms | 约 5.3× |

⭐ **`ConcurrentHashMap` 快 4~5 倍的原因**：`synchronizedMap` 与 `Hashtable` 都是「一个对象一把锁」，4 个线程**完全串行化**；`ConcurrentHashMap` 在桶级加锁甚至无锁 CAS，4 个线程能真正并行。

⚠️ 注意这个实验写的是**不同 key**。如果所有线程抢同一个 key，`ConcurrentHashMap` 的优势会大幅缩水（都撞在同一个桶上）—— **它的高并发前提是 key 足够分散**。

## 二、`ConcurrentHashMap` 的四个反直觉行为

**本节要点**：前两个是「为什么这样设计」，后两个是**最容易踩的坑**。

### 2.1 不允许 null（实测）

```text
== 实验 2：能不能存 null ==
  HashMap            ：put(null, "v") 后 get(null) = value，put("k", null) 后 get("k") = null  → 允许 null
  ConcurrentHashMap  ：null key → NullPointerException
  ConcurrentHashMap  ：null value → NullPointerException
```

⭐ **理由**：并发下 `get(k)` 返回 `null` 会**有歧义** —— 是「没有这个 key」还是「key 存在但值是 null」？单线程时可以用 `containsKey` 二次判断，但在并发场景下「判断」与「取值」之间状态可能已变。**所以 `ConcurrentHashMap` 干脆禁止 null，让 `get` 返回 null 只有一种含义：key 不存在。** 这也是 `computeIfAbsent` 能安全工作的前提。

### 2.2 `size()` 是估算值

JDK 8 用 `CounterCell[]` 分散计数（思路同 `LongAdder`），代价是**并发写时 `size()` 不精确**。要精确值只能在**没有并发写**的时候调（比如服务启动后的初始化阶段），或者干脆不依赖它 —— **`size()` 只适合监控与粗略判断，不适合当业务判据**。

### 2.3 复合操作不原子（实测，最容易踩）

「先 `get` 再 `put`」在并发下会丢更新。4 线程各做 5 万次计数（`MapLab.java` 实验 3）：

```text
== 实验 3：同一个 key 上做「读-改-写」计数，4 线程各 5 万次 ==
  get + put            57.3 ms   结果 = 84142   期望 = 200000   丢了 115858
  merge(原子)          48.4 ms   结果 = 200000   期望 = 200000   ✅ 正确
  AtomicLong 对照      11.5 ms   结果 = 200000   期望 = 200000   ✅ 正确
```

⚠️ **期望 20 万，`get + put` 只数到 8.4 万 / 9.0 万 —— 丢了一半以上。** 而 `merge` 与 `AtomicLong` 都正确。

⭐ 这与 [JMM与内存屏障.md](JMM与内存屏障.md) 1.3 说的 `volatile++` 是同一类错误：**容器只保证「单次操作」线程安全，不保证「两次操作合起来」安全。** 要原子必须用容器提供的原子方法：

| 需求 | 用哪个 |
|---|---|
| 计数累加 | `merge(key, 1, Integer::sum)` 或 `compute` |
| 不存在才写入 | `putIfAbsent` / `computeIfAbsent` |
| 存在才替换 | `replace` / `computeIfPresent` |
| 「读-改-写」任意逻辑 | `compute`（整个 lambda 在桶锁内执行） |

⚠️ **`computeIfAbsent` 的一个真实陷阱**：它的 lambda **在桶锁内执行**，如果 lambda 里做了耗时操作（远程调用、复杂计算）或**递归修改同一个 map**，会造成长时间持锁甚至死锁。**把重活放到 `computeIfAbsent` 之后做。**

### 2.4 迭代器是「弱一致」的

`ConcurrentHashMap` 的迭代器**不抛 `ConcurrentModificationException`**，也**不保证看到某个时刻的完整快照**：遍历期间发生的新增/删除，可能看得到也可能看不到。这与 `CopyOnWriteArrayList` 的「强快照」语义不同（见 3.1）。

⭐ **判据**：需要「遍历一个稳定视图」用 `CopyOnWriteArrayList`；只是「扫一遍大概有哪些元素」用 `ConcurrentHashMap` 的迭代器（它不会炸，但别依赖精确性）。

## 三、`CopyOnWriteArrayList`：只适合一种场景

**本节要点**：它的读路径完全无锁（这是它的全部价值），代价是**每次写都要复制整个数组**。

### 3.1 语义：遍历的是快照

```text
== 实验 1：遍历过程中往集合里加元素 ==
  ArrayList          ：ConcurrentModificationException ← fail-fast
  CopyOnWriteArrayList：遍历到 [a, b, c]，遍历结束后内容 = [a, b, c, d] ← 不抛异常
```

同样是「遍历时 `add`」：

- **`ArrayList` 抛 `ConcurrentModificationException`**（fail-fast：迭代器发现 `modCount` 变了就立刻报错）；
- **`CopyOnWriteArrayList` 不抛异常**：迭代器持有的是**创建那一刻的不可变快照** `[a,b,c]`，新元素 `d` 加到了**新数组**里。所以遍历完内容是 `[a,b,c,d]`。

⭐ 这就是「遍历期间修改」不会被炸掉的原因 —— **迭代器和写者操作的是两个不同的数组**。

### 3.2 代价：写密集时慢到不可用（实测）

4 线程各 `add` 5 万次（`QueueLab.java` 实验 2）：

```text
== 实验 2：4 线程各 add 50000 次（写密集）==
  CopyOnWriteArrayList     10841.8 ms   size=200000
  synchronizedList            28.1 ms   size=200000
```

⚠️ **10841.8 ms vs 28.1 ms —— 慢约 386 倍。** 因为每次 `add` 都要：

1. 加锁（写侧**还是需要锁**的，只是读侧无锁）；
2. **复制整个底层数组**（O(n)）；
3. 替换引用。

再叠上 4 个线程的锁竞争，`size` 涨到 20 万时，每次 `add` 要复制 20 万个引用。

### 3.3 唯一适合的场景

```text
读 ：写 ≥ 极高（几乎不写） 且 集合本身不大 且 需要「遍历快照」
```

典型例子：**监听器列表 / 事件订阅者表 / 配置白名单 / 拦截器链**。

⭐ 判据一句话：**「写发生在系统启动或配置变更时、读发生在每次请求里」→ 用 `CopyOnWriteArrayList`；「写和读一个量级」→ 用 `ConcurrentHashMap` 或加锁的 `ArrayList`。**

⚠️ 反面教材：**别拿它当队列用**（`add` + `remove(0)` 是 O(n) 的复制，队列该用 `BlockingQueue`）；**别拿它存大列表**（复制成本随容量线性增长）。

## 四、`BlockingQueue` 家族与九种操作

**本节要点**：`BlockingQueue` 的方法是**严格的三组 × 三种失败行为**，把这九种记住，选方法就不会错。

### 4.1 九种操作（实测验证）

```text
== 实验 3：BlockingQueue 三组操作 × 三种失败行为（ArrayBlockingQueue(1)，先塞满）==
  队列已满（容量 1，已有 1 个）时的「入队」：
    add()    → 抛 IllegalStateException
    offer()  → 返回 false
    offer(50ms) → 返回 false（耗时 57 ms）
    put()    → 会**一直阻塞**

  队列空时的「出队」：
    remove() → 抛 NoSuchElementException
    poll()   → 返回 null
    poll(50ms) → 返回 null（耗时 62 ms）
    take()   → 会**一直阻塞**

  队列空时的「查看队首」：
    element() → 抛 NoSuchElementException
    peek()    → 返回 null
```

整理成表（**这张表值得背下来**）：

| 操作 | 抛异常 | 返回特殊值 | 阻塞 | 带超时 |
|---|---|---|---|---|
| **入队** | `add(e)` | `offer(e)` → `false` | `put(e)` | `offer(e, t, unit)` |
| **出队** | `remove()` | `poll()` → `null` | `take()` | `poll(t, unit)` |
| **查看队首** | `element()` | `peek()` → `null` | — | — |

⭐ **实践口径**：**生产代码优先用「带超时」的那一组**。

- 用 `put`：一旦下游挂了，调用线程**永久阻塞**，问题会从「一条消息丢了」放大成「整个线程池卡死」；
- 用 `offer()` 无超时：满了就直接丢，**没有重试窗口**；
- **`offer(e, 500ms)`**：既不永久阻塞，又给了短暂等待的机会 —— 这是最稳妥的默认选择。这也正是 [线程池.md](线程池.md) 「使用」一节里弹幕投递选 `offer` 的理由。

### 4.2 五种队列怎么选

| 队列 | 结构 | 适用 | 注意 |
|---|---|---|---|
| `ArrayBlockingQueue` | 数组，**有界** | ✅ 通用首选 | 容量必须显式给；单锁（JDK 8 用一把 `ReentrantLock`） |
| `LinkedBlockingQueue` | 链表，默认 **`Integer.MAX_VALUE`** | 需要高吞吐且能接受无界 | ⚠️ 不指定容量就有堆积 OOM 风险；双锁（入队出队各一把） |
| `SynchronousQueue` | **无容量**，交接 | 直接移交（`newCachedThreadPool` 用） | 见 4.3 |
| `PriorityBlockingQueue` | 堆，**无界** | 按优先级出队（如紧急任务优先） | 无界 + 优先级反转风险 |
| `DelayQueue` | 堆，按到期时间 | 延迟任务（见 4.3） | 无界 |

### 4.3 两个特殊队列（实测）

```text
== 实验 4：SynchronousQueue 没有容量 ==
  没有消费者等待时 offer("x") = false（没有容量可存）
  消费者在 take() 上等待后 offer("hello") = true（长度 5）← 一手交一手接
```

**`SynchronousQueue` 是「会合点（rendezvous）」**，不是队列 —— 它**不存储**元素，生产者必须**同时**有一个消费者在等。所以 `offer` 在没有消费者时直接返回 `false`。`newCachedThreadPool` 用它，效果就是「任务来了必须立刻有个线程接，接不了就新建/拒绝」。

```text
== 实验 5：DelayQueue 按到期时间出队 ==
  放入顺序 = [late-300ms, early-100ms, mid-200ms]，peek() = early-100ms（队首是**最早到期**的，不是最早放入的）
  未到期时 poll() = null（直接返回 null，不等待）
  take() 依次拿到：early-100ms@110ms  mid-200ms@205ms  late-300ms@314ms
```

⭐ **`DelayQueue` 的出队顺序完全由「到期时间」决定**，与放入顺序无关（放入顺序是打乱的）。`take()` 会阻塞到最早那个到期（实测拿到时间 110 / 205 / 314 ms，与 100 / 200 / 300 ms 的设定吻合，多出的约 10 ms 是唤醒开销）。⚠️ 元素必须实现 `Delayed` 接口，`getDelay()` 返回**剩余**时间。

**典型用途**：订单超时未支付自动关闭、延迟重试、会话过期清理。⚠️ **它是内存队列** —— 进程重启就丢了，对「不能丢」的延迟任务要用 MQ 的延迟消息或时间轮落库方案。

## 使用：弹幕系统的两张并发表

本项目里**真实存在**的 Java 并发容器用法在 [弹幕系统的Java实现.md](../../分布式/系统设计/弹幕系统的Java实现.md)。那篇里的两个结构正好是本节两类容器的典型用法：

### 第一张表：房间 → 订阅者（读极多、写极少）

```java
private final AtomicReference<List<Sub>> snap =
        new AtomicReference<>(Collections.emptyList());
synchronized void join(Sub s) { /* 造新列表 → snap.set(...) */ }
```

- **为什么不用 `ConcurrentHashMap<RoomId, List<Sub>>`**：这里的瓶颈是**读**（每条弹幕都要遍历订阅者），不是写。`ConcurrentHashMap` 能让写并行，但读路径上每个房间仍然是一个 list —— **要的是「读的时候连 list 都不用加锁」**。
- **为什么不用 `CopyOnWriteArrayList`**：它**本质上可以**（语义正是这个），但弹幕连接表变动频繁（用户频繁上下线），而 3.2 实测写密集下它慢 386 倍。**用 `AtomicReference` + 手写不可变快照，等于只保留「写时复制」的语义、但不承担 `CopyOnWriteArrayList` 的整体复制成本**（这里复制的是订阅者列表，且由 `synchronized` 保证一次只有一个写者）。
- ⭐ 反过来看：**`CopyOnWriteArrayList` 的真正适用面就是「监听器列表」那种几乎不变的集合**；一旦写变频繁，就该退化成「自己控制的不可变快照」。

### 第二张表：待投递消息（生产者-消费者）

```java
private final ArrayBlockingQueue<Msg> out;
// 投递：offer（非阻塞）
```

- **选 `ArrayBlockingQueue` 而不是 `LinkedBlockingQueue`**：前者容量**必须显式给**（有界，压力可见），后者默认 `Integer.MAX_VALUE`（几乎无界，堆积到 OOM 才报错）。
- **选 `offer` 而不是 `put`**：这正是 4.1 那张表的判据 —— `put` 在满时会**永久阻塞投递线程**，一个卡住的客户端就会把整个房间的推送拖死。
- **丢弃必须计数**：对应 [线程池.md](线程池.md) 里说的「拒绝次数必须成为指标」——**静默丢弃是 `DiscardPolicy` 的翻版，比报错难查得多**。

⭐ 归纳：**选并发容器的第一问是「读多还是写多」，第二问是「满了/空了该怎么办」。** 前者决定容器类型（无锁快照 / 桶级锁 / 全局锁），后者决定 API 的失败行为（抛异常 / 返特殊值 / 带超时阻塞）。

## 延伸追问

- **`ConcurrentHashMap` 的并发度是多少？** → JDK 7 是 Segment 个数（默认 16，构造时可指定）；JDK 8 **没有固定并发度**，锁粒度是「桶」，所以并发度 ≈ 数组长度（随扩容增长）。这也是 JDK 8 在高并发下更优的原因。
- **为什么 `ConcurrentHashMap` 桶空时用 CAS、桶非空时才加锁？** → 无竞争路径（桶为空的插入）是最常见的情况，用 CAS 完全避开锁；一旦发生哈希冲突（桶非空），说明该位置有竞争，这时才动用锁。**「无竞争走无锁路径」是无锁数据结构设计的通用套路。**
- **`computeIfAbsent` 里能做远程调用吗？** → **不要**。它的 lambda 在**桶锁内**执行，耗时越长持锁越久，会阻塞所有落在同一个桶上的操作；若 lambda 里又去改同一个 map 还可能死锁。正确做法：先 `get`（读多写少时通常都能命中），未命中时在锁外算好，再 `computeIfAbsent` 放进去。
- **`size()` 在并发下到底能信吗？** → 只能当**估算**。JDK 8 用 `CounterCell[]` 分散计数（同 `LongAdder` 思路），并发写时求和只是近似值。要精确值就在没有并发写的时候读，或者用别的机制（如自己维护一个 `AtomicLong` 精确计数器 —— 那又回到竞争问题上了）。
- **`Hashtable` 为什么还没被删掉？** → 历史遗留（`Hashtable` 是 JDK 1.0 的类，比 `Map` 接口还早）。**新代码不要用**：它是全表锁（性能差），并且不允许 null（这是它相对于 `HashMap` 的唯一「特性」，但它本身被 `ConcurrentHashMap` 完全覆盖了）。
- **`CopyOnWriteArrayList` 的读真的完全无锁吗？** → 是。读路径只是 `array[index]`（内部数组是 `volatile`），没有加锁、没有 CAS。但代价在写侧（3.2 实测慢 386 倍）。⭐ **它的本质是「把一致性成本全押在写侧」** —— 这就是「读多写少」才适用的根本原因。
- **`SynchronousQueue` 与容量为 0 的 `ArrayBlockingQueue` 一样吗？** → 不一样。`ArrayBlockingQueue` 的容量**必须 ≥ 1**，没法做成交接语义；`SynchronousQueue` 是专门实现「生产者和消费者必须同时在场」的。它的公平/非公平模式差别也很大（非公平模式用 LIFO 栈，公平模式用 FIFO 队列）。
- **队列满了除了丢弃还能做什么？** → 有三种正解：① **带超时的 `offer`**（短暂等待，给下游喘息）；② **回压到上游**（让调用方变慢，如 `CallerRunsPolicy` 之于线程池）；③ **落库/落 MQ 做延迟重试**（把内存压力变成持久化任务）。⚠️ 「加大队列容量」不是解法 —— 它只是把问题推迟到内存耗尽。
