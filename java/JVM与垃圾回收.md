# JVM 与垃圾回收

> 对象生命周期、可达性分析与 GC Roots、四种收集算法、三色标记与漏标修复、收集器分类与 JVM 常用命令。
>
> 内容整理自个人学习笔记。GC 算法本身（标记-清除/复制/压缩/分代/增量式等）的单一来源是 [GC基础算法.md](../垃圾回收/GC基础算法.md)。

## Q1. 对象的一生经历了什么？

```
创建 → 应用 → 不可见 → 不可达 → 收集 → 终结 → 空间重新分配
```

| 阶段 | 含义 |
|---|---|
| 创建 | 通过 `new` 等指令分配内存、初始化 |
| 应用 | 对象被至少一个引用持有，处于使用中 |
| 不可见 | 程序已无强引用可达，但对象仍可能存在（如局部变量已出作用域但未回收） |
| 不可达 | 从 GC Roots 出发不可达，可被回收 |
| 收集 | GC 将其内存回收 |
| 终结 | 若重写了 `finalize()`，在回收前可能被执行一次（JVM 不保证） |
| 空间重新分配 | 回收后的内存归还给分配器复用 |

## Q2. 怎么判断一个对象已经死了？

| 方案 | 原理 | 问题 |
|---|---|---|
| **引用计数法** | 每个对象维护引用计数，为 0 即可回收 | **无法解决循环引用**（A↔B 互相引用，计数永不为 0），JVM **不采用** |
| **可达性分析** ⭐ | 从 **GC Roots** 出发遍历引用链，不可达的对象判定为可回收 | JVM 实际采用 |

**可作为 GC Roots 的对象**：

- 虚拟机栈（栈帧中的局部变量表）中引用的对象
- 方法区中类静态属性引用的对象
- 方法区中常量引用的对象
- 本地方法栈中 JNI 引用的对象
- 活跃线程、被同步锁持有的对象、JVM 内部引用（基本类型对应的 Class 对象、常驻异常对象、系统类加载器）

> **对象真正"死亡"要经历两次标记**：第一次被标记为不可达后，若重写了 `finalize()` 且未被调用过，
> 会进入 `F-Queue` 等待一次执行机会；若在 `finalize()` 中重新与引用链建立关联，则"复活"，否则第二次标记后被回收。

## Q3. 有哪些垃圾收集算法？各自的代价是什么？

| 算法 | 做法 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **标记-清除**（Mark-Sweep） | 标记可回收对象后直接清除 | 实现简单 | **产生内存碎片**；标记与清除效率不稳定 | 老年代（CMS） |
| **标记-复制**（Mark-Copy） | 内存分两半，存活对象复制到另一半后整体清空原区 | 无碎片、分配快（指针碰撞） | **空间利用率仅 50%** | 新生代（Eden + 2 Survivor，实际按 8:1:1 使用） |
| **标记-整理**（Mark-Compact） | 标记后把存活对象向一端移动，再清理边界外内存 | 无碎片 | 移动对象成本高，需 STW | 老年代 |
| **分代收集**（Generational） | 按对象存活周期划分新生代/老年代，**各用各的算法** | 扬长避短，是 JVM 主流方案 | 需维护跨代引用（记忆集/卡表） | 整体策略 |

> **分代假说**：绝大多数对象朝生夕死（弱分代假说），熬过越多次 GC 的对象越难死（强分代假说）。
> 因此新生代用「复制」、老年代用「标记-清除 / 标记-整理」。

## Q4. 三色标记是怎么做的？漏标怎么修？

并发标记时，把对象抽象成三种颜色：

| 颜色 | 含义 |
|---|---|
| **白色** | 尚未被 GC 访问过（标记结束后仍是白色 = 可回收） |
| **灰色** | 自身已被访问，但其引用的对象还没全部扫描完（待处理队列） |
| **黑色** | 自身与其所有引用对象都已扫描完成（安全，不会漏） |

**标记过程**：初始时 GC Roots 为灰色 → 取出灰色对象，把它引用的白色对象染灰、自身染黑 → 重复直至无灰色对象。

### 并发标记的致命问题：对象消失（漏标）

并发标记期间用户线程仍在改引用，可能出现**黑对象指向了白对象，且该白对象已无其他灰色路径可达** →
这个白对象会被当作垃圾回收，但它其实还在使用中，程序出错。

**漏标必须同时满足两个条件**：

1. 赋值器**插入**了一条从黑色对象到白色对象的引用；
2. 赋值器**删除**了所有从灰色对象到该白色对象的直接或间接引用。

**只要破坏其中任意一个条件，就不会漏标**，于是有两种方案：

| 方案 | 破坏的是哪个条件 | 做法 | 使用者 |
|---|---|---|---|
| **增量更新**（Incremental Update） | 条件 1 | 记录黑色对象**新增**的引用，并发标记结束后以这些黑对象为根重新扫描（黑 → 灰） | **CMS** |
| **原始快照**（SATB） | 条件 2 | 记录灰色对象**删除**的引用，按**并发标记开始那一刻的对象图快照**来扫描 | **G1**、Shenandoah |

> ⭐ 顺口记：**增量更新盯"新加的黑"，原始快照存"删掉的旧"**。

## Q5. 垃圾收集器怎么分类、怎么选？

**按三个维度划分**：

| 维度 | 分类 |
|---|---|
| 线程数 | **串行**收集器（单线程）／**并行**收集器（多线程） |
| 工作模式 | **独占式**（Stop The World，全程暂停用户线程）／**并发式**（与用户线程交替或同时工作） |
| 优化目标 | **吞吐量优先**（Parallel Scavenge，适合后台计算）／**停顿时间优先**（CMS、G1，适合交互式服务） |

**常见收集器组合**：

| 收集器 | 分代 | 算法 | 特点 |
|---|---|---|---|
| Serial / Serial Old | 新生代 / 老年代 | 复制 / 标记-整理 | 单线程，Client 模式默认，简单高效 |
| ParNew | 新生代 | 复制 | Serial 的多线程版，常与 CMS 搭配 |
| Parallel Scavenge / Parallel Old | 新生代 / 老年代 | 复制 / 标记-整理 | **吞吐量优先**，可自适应调节 |
| **CMS** | 老年代 | 标记-清除 | **停顿时间优先**；并发标记用增量更新；有碎片、有并发失败风险，JDK 14 起移除 |
| **G1** | 整堆（Region 化） | 复制 + 标记-整理（整体） | 可预测停顿模型，按 Region 回收，标记用 SATB |
| ZGC / Shenandoah | 整堆 | 染色指针 / 读屏障 + 转发指针 | **超低停顿**（<10ms），JDK 15+ 生产可用 |

## Q6. JVM 常用命令有哪些？

| 命令 | 用途 |
|---|---|
| `jps` | 查看当前用户的 Java 进程与 PID |
| `jinfo` | 查看、动态调整 JVM 参数 |
| `jstat` | 监控运行时状态：GC 次数与耗时、各代容量、类加载、JIT 编译 |
| `jstack` | 打印线程栈 —— **排查死锁、CPU 飙高的首选** |
| `jmap` | 生成堆内存快照（`-dump`）、查看对象统计（`-histo`） |
| `jcmd` | 命令行全能工具，整合了上述多数功能 |
| `jhat` / MAT / VisualVM / Arthas | 分析堆快照、在线诊断 |

**排查套路**：CPU 高 → `top -Hp <pid>` 找到线程号 → 转十六进制 → `jstack <pid>` 里对照定位；内存涨 → `jmap -dump` 拿快照 → MAT 看支配树。

## 面试官会追问什么

- **为什么不采用引用计数法？** → 无法解决循环引用；且每次赋值都要维护计数，开销大、并发下难处理。
- **新生代为什么用复制算法？** → 朝生夕死，存活对象极少，复制成本低，只需付出少量 Survivor 空间。
- **对象什么时候进入老年代？** → 年龄达到阈值（默认 15，`-XX:MaxTenuringThreshold`）、大对象直接进入、Survivor 中同龄对象总和超一半（动态年龄判定）。
- **CMS 与 G1 的区别？** → 前者按分代、标记-清除、有碎片、增量更新；后者 Region 化、可预测停顿、SATB、无碎片。
- **什么情况下会 Full GC？** → 老年代不足、元空间不足、显式 `System.gc()`、CMS 并发失败退化。
- **三色标记为什么会有漏标？漏标必须满足什么条件？** → 只有"黑色对象新增了指向白色对象的引用 + 该白色对象到灰色对象的引用被删除"同时发生才会漏标；因此只需**增量更新**（记录黑→白，重新扫描黑色）或**原始快照 SATB**（记录灰→白删除）二者之一即可保证正确性。
