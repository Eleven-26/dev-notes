# JWT 与 API Key 鉴权

> 鉴权在网关上只有三件事：**凭证怎么带过来**、**怎么验**、**失败了怎么答**。
> 三件事都不难，但每一件都有一个「看起来能用、实际上留了洞」的写法 ——
> 比如「没有 `exp` 就不过期」等于签一次永久通行，比如 `401` 与 `403` 混用会让客户端做错决定。
>
> 内容整理自个人学习笔记，实测基于自研网关项目 [gateway](https://github.com/Eleven-26/gateway)（module `gwlab`，Go 1.26.5）的
> `internal/auth/`（本篇所有 `text` 块都是本机真实运行结果）。
>
> ⭐ **分工**：本篇讲**应用层的凭证协议与校验流程**（怎么带、怎么验、怎么答）。
> HMAC / 摘要 / 签名的**密码学原理**见 [摘要与数字签名.md](摘要与数字签名.md)；
> 口令该怎么存见 [密码与敏感信息存储.md](密码与敏感信息存储.md)；
> 证书体系与非对称见 [数字证书与PKI.md](数字证书与PKI.md)。

## 一、JWT 的三段结构，以及自己写一遍能看清的三件事

**本节要点**：JWT 不是一种加密，而是**一段能被任何人读、但改不了**的凭据。
它的结构简单到可以手写，而手写一遍才会发现三个「调库时被藏起来」的点。

```text
base64url(header) . base64url(payload) . base64url(HMAC-SHA256(前两段))
     {"alg":"HS256"}    {"sub":"u-1",...}       签名
```

⚠️ **payload 是明文可读的**（只是 base64，不是加密）——
所以**绝不能把敏感信息放进 JWT**（手机号、身份证、权限明细都算）。

### 1.1 签名覆盖的是「前两段的原始字符串」

```go
// ① 签名覆盖的是「前两段的原始字符串」，不是解析后的 JSON。
//    如果先 unmarshal 再重新 marshal 去验签，字段顺序一变签名就失效。
mac := hmac.New(sha256.New, []byte(secret))
mac.Write([]byte(parts[0] + "." + parts[1]))
```

⭐ **这条是「先解析再验签」这类实现的头号 bug 来源**。
JSON 的字段顺序在语义上无所谓，但**签名对字节敏感** ——
把 payload 解成 map 再序列化回去，键的顺序、空格、转义都可能变，签名必然对不上。

**所以正确的顺序永远是：先用原始字节验签，通过了再解析。**

### 1.2 验签必须用恒定时间比较

```go
// ② 必须用 hmac.Equal（恒定时间比较），不能用 == —— 否则会被时序攻击逐字节猜出签名。
if !hmac.Equal(want, got) { return nil, ErrBadSignature }
```

`==` 在第一个不同的字节处就返回，攻击者可以通过**测量响应时间**逐字节地猜出正确签名。
`hmac.Equal` 无论差在哪一位，耗时都一样。

> ⚠️ 同样的规则适用于 **API Key 比较**（本项目也是 `hmac.Equal`）和
> 「重置密码的 token」「会话 ID」这类**任何需要保密的字符串比对**。

### 1.3 签名过了 ≠ 凭证有效

```go
// ③ 签名合法 ≠ 凭证有效：exp / nbf 是业务校验，必须在验签之后再查。
if c.Exp > 0 && now > c.Exp { return nil, ErrExpired }
if c.Nbf > 0 && now < c.Nbf { return nil, fmt.Errorf("凭证尚未生效") }
```

把「签名」和「有效期」当成一件事是常见的理解错误：
签名只回答「**这张票是不是我们发的**」，期限回答的是「**这张票还能不能用**」。
两者是独立的两个检查，缺一不可。

### 1.4 本机实测：七种形态

```text
阶段 1：JWT 各种形态（同一条路由要求 jwt）
  正常 exp=+1h role=admin    → 通过  subject=u-1001 roles=[admin]
  无 exp（永久通行）           → 拒绝  status=401  code=token_no_expiry  凭证没有 exp（必须带过期时间）
  已过期 exp=-60s            → 拒绝  status=401  code=unauthorized  凭证已过期
  尚未生效 nbf=+60s           → 拒绝  status=401  code=unauthorized  凭证尚未生效
  寿命 48h（超 24h 上限）      → 拒绝  status=401  code=token_too_long_lived  凭证寿命超过上限
  签名错误（换密钥签）           → 拒绝  status=401  code=unauthorized  签名不合法
  格式错误（只有两段）           → 拒绝  status=401  code=unauthorized  凭证格式错误
```

⭐ 注意错误码的**两档设计**：

| 错误码 | 含义 | 该找谁 |
|---|---|---|
| `token_no_expiry` / `token_too_long_lived` | **签发侧**配置错了（或有人试图绕过） | 后端 / 运维 —— 客户端改不了 |
| `unauthorized`（含过期、签名错、格式错） | **凭证本身**有问题 | 客户端 —— 重新登录即可 |

**这个区分让排障快得多**：如果某个服务的日志里突然全是 `token_no_expiry`，
那不是用户在乱试，而是**签发服务的代码改坏了**（漏了 `exp`）。

## 二、`exp` 为什么必须存在？

**本节要点**：「没有 `exp` 就不过期」听起来像个方便的特性，实际上是个**没有止损点的设计**。

```go
// maxTokenLifetime 令牌寿命上限（exp - iat）。签名有效但寿命过长的令牌一律拒绝，
// 避免「签一次永久通行」—— 没有这个上限时，密钥泄露或内部误签发就没有止损点。
const maxTokenLifetime = 24 * time.Hour
```

JWT 是**无状态**的：签出去之后，服务端**没有任何办法撤销它**（除非引入黑名单，那就失去了无状态的意义）。
所以「有效期」是唯一的止损手段：

| 场景 | 有 `exp` | 无 `exp` |
|---|---|---|
| 密钥泄露 | 最多影响 `exp` 之前的令牌，24h 后自动失效 | **永久有效**，除非换密钥把所有人踢下线 |
| 内部误签发 | 同上 | 同上 |
| 用户离职 | 令牌到期即失效 | 永久可用 |

⭐ **两条配套规则**：

1. **没有 `exp` 的令牌直接拒绝**（本项目返回 `token_no_expiry`），而不是「当成永久有效」；
2. **寿命上限也要卡**（本项目 24h）：否则签发方可以「合法地」签一个 100 年有效的令牌，
   等于绕过了第 1 条。

> ⚠️ **`24h` 是网关侧的上限，不是推荐值**。真实的取值取决于业务：
> 面向用户的会话通常 15 分钟 ~ 几小时（配合 refresh token 续期），
> 服务间调用的令牌可以更短（几分钟）。**上限的意义是「兜底」，不是「标准」**。

## 三、`401` 和 `403` 必须分开

**本节要点**：这两个状态码回答的是不同的问题，混用会让客户端做错决定。

| 状态码 | 回答的问题 | 客户端该怎么做 |
|---|---|---|
| **401** Unauthorized | 「**你是谁**？」—— 没带凭证 / 凭证无效 | 去登录，或刷新令牌后重试 |
| **403** Forbidden | 「**你不能做这个**」—— 身份没问题，权限不够 | **别重试了**，重试多少次都一样 |

```go
func Status(err error) int {
    if errors.Is(err, ErrForbidden) { return http.StatusForbidden }
    return http.StatusUnauthorized
}
```

⭐ **混用的后果**：如果把「权限不足」也返回 401，客户端会以为令牌失效 → **触发刷新令牌 → 再试 → 还是 403 → 再刷新**……
形成刷新风暴，而问题根本不在令牌上。

本机实测（令牌有效，但路由要求 `admin`，而令牌的 role 是 `guest`）：

```text
阶段 3：角色校验（路由要求 admin，而令牌的 role=guest）
  role=guest   → 403 forbidden  ⭐ 与 401 区分
  role=admin   → 通过
```

## 四、`Bearer` 的大小写：一个 RFC 细节引发的 401

**本节要点**：`Authorization` 头的 **scheme 是大小写不敏感的**，但这条规则很容易被「朴素实现」违反。

第一版的写法是 `strings.CutPrefix(raw, "Bearer ")` —— 逐字节比较，
于是 `bearer xxx`、`BEARER xxx` **全部被判成「凭证格式错误」**。
而这些写法在 HTTP 规范里是完全合法的（RFC 7235 明确 scheme 大小写不敏感），
所以会出现「Postman 能过、某个 SDK 过不了」这种很难查的兼容性问题。

```go
// 只对 scheme 做 EqualFold，分隔符仍严格要求空格，
// 所以 `Token xxx` 这类别的 scheme 依旧被拒。
scheme, token, ok := strings.Cut(raw, " ")
if !ok || !strings.EqualFold(scheme, "Bearer") {
    return nil, ErrBadFormat
}
```

```text
阶段 2：Authorization 头本身的形态（scheme 大小写不敏感，但分隔符与 scheme 名要严格）
  Authorization=""                         → 拒绝 401 unauthorized
  Authorization="Bearer eyJhbGciOiJIUzI…"  → 通过
  Authorization="bearer eyJhbGciOiJIUzI…"  → 通过
  Authorization="BEARER eyJhbGciOiJIUzI…"  → 通过
  Authorization="BeArEr eyJhbGciOiJIUzI…"  → 通过
  Authorization="Token eyJhbGciOiJIUzI1…"  → 拒绝 401 unauthorized
  Authorization="eyJhbGciOiJIUzI1NiIsIn…"  → 拒绝 401 unauthorized
  Authorization="Bearer\teyJhbGciOiJIUzI…" → 拒绝 401 unauthorized
```

⭐ **「大小写不敏感」和「宽松」不是一回事**：

| 维度 | 规则 | 为什么 |
|---|---|---|
| scheme 名（`Bearer`） | ✅ 大小写不敏感 | RFC 7235 规定 |
| 分隔符 | ❌ 必须是空格，Tab 不行 | RFC 只允许 SP；`Bearer\ttoken` 里的 `\t` 会变成令牌的一部分 |
| scheme 名本身 | ❌ 必须是 `Bearer` | `Token xxx` 是另一种（已废弃的）方案，不能当成 Bearer 放行 |

⚠️ 注意 `Bearer\txxx` 被**拒绝**这一条：它看起来「更宽松」但实际上会**把 `\t` 当成令牌的一部分**，
拿去做验签必然失败 —— 早拒绝比晚失败好（错误信息也更准确）。

## 五、API Key：更简单，但有两个坑

**本节要点**：API Key 就是「一串长期有效的共享密钥」，简单到几乎不需要设计 —— 除了两件事。

```go
key := r.Header.Get("X-API-Key")
if key == "" {
    key = r.URL.Query().Get("api_key")   // 兼容不能改 header 的调用方
}
if !hmac.Equal([]byte(key), []byte(a.apiKey)) { return nil, ErrBadSignature }

subject := key
if len(subject) > 8 { subject = subject[:8] }   // 日志里只留前 8 位
```

### 5.1 坑一：放 query 会被写进日志和浏览器历史

```text
GET /open/orders?api_key=sk-live-abcdef123456  ← 这个 URL 会出现在
   ① 网关自己的访问日志   ② 上游的访问日志   ③ 浏览器历史   ④ Referer 头（跳转时）
```

⚠️ 所以 **query 只能作为兼容手段**，面向客户端的调用一律放 header。
更彻底的做法是**完全禁用 query 传法**，把「兼容」和「泄密」的权衡交给明确的配置开关。

### 5.2 坑二：日志里不能出现完整 key

`subject = key[:8]` 的意义是：日志里能看出「是哪一个 key」（用于排查是哪个调用方），
但**拿不到完整的 key**（8 位前缀不足以还原）。这是「可观测性」与「保密」之间的最小妥协。

⭐ **同一原则适用于所有密钥**：日志、指标标签、错误信息里**都不该出现完整密钥**。
本项目里 JWT 密钥与 API Key 都只通过环境变量注入，源码里的默认值明确标注了「上线前必须替换」。

### 5.3 本机实测

```text
阶段 4：API Key 三态 + 两种传法
  无 key            → 拒绝 401 unauthorized
  错误 key          → 拒绝 401 unauthorized
  头传正确 key       → 通过 subject=apikey:sk-live-（截断到 8 位）
  query 传正确 key   → 通过 subject=apikey:sk-live-（截断到 8 位）
```

## 六、JWT 与 API Key 该怎么选？

| | JWT（HS256） | API Key |
|---|---|---|
| 承载信息 | 有（`sub` / `role` / 自定义 claim） | 无（只有「是谁」） |
| 有效期 | 有（`exp`，必须） | 无（长期有效，靠人工轮换） |
| 撤销 | 难（无状态，只能等过期或换密钥） | 容易（换掉那个 key 即可） |
| 适用 | **用户会话**（谁登录了、有什么角色） | **服务间调用**（哪个系统在调我） |
| 泄露影响 | 有效期内的身份被冒用 | 直到被发现并轮换为止 |

⭐ **一条实践口径**：**JWT 给「人」，API Key 给「系统」**。

- 面向用户：JWT 能带角色信息（省掉一次查询），能按用户维度限流；
- 面向服务：API Key 更简单，且**可以单独轮换**（换一个服务商的 key 不影响别人）。

⚠️ 两个都要配的常见形态是本项目的做法：**同一条路由选一种**（`auth.scheme`），
而不是「两种都接受」—— 后者会让「究竟是谁在调用」变得模糊，鉴权日志也失去意义。

## 使用：给一条路由配鉴权

### 1) 配置

```json
{
  "routes": [
    { "name": "order-create", "path": "/api/orders", "path_type": "exact",
      "upstream": "order-svc",
      "auth": { "required": true, "scheme": "jwt", "roles": ["admin", "ops"] } },

    { "name": "open-api", "path": "/open/", "path_type": "prefix",
      "upstream": "order-svc",
      "auth": { "required": true, "scheme": "apikey" } },

    { "name": "public-health", "path": "/healthz", "path_type": "exact",
      "upstream": "self" }
  ]
}
```

### 2) 在流水线里的位置：**鉴权必须在限流之前**

```text
路由匹配 → 【鉴权】 → 限流 → 熔断 → 选节点 → 转发
```

| 顺序 | 为什么 |
|---|---|
| **鉴权 → 限流** | 限流要先知道「你是谁」才能按用户维度限。反过来只能按 IP 限，NAT 后面一整栋楼共用一个桶 |
| 鉴权**在最后**（而不是最先） | 鉴权成本比路由匹配高（要验签），先用路由把流量分流（例如放行 `/healthz`），再做昂贵的检查 |

> ⚠️ **代价**：未通过鉴权的请求**不受限流保护** —— 攻击者可以用无效令牌刷鉴权接口。
> 所以生产上会**两层都配**：最外层按 IP 挡洪水（粗），鉴权后再按用户精细限（细）。

### 3) 身份怎么传给上游

```go
// ⭐ 剥离客户端伪造的内部头 —— 不做这一步，任何人加一个 X-Company-Id 就能越权
for _, h := range internalHeaders { req.Header.Del(h) }
// 再把网关鉴权出来的身份重新写进去（此刻它才是可信的）
if id := identityFrom(req.Context()); id != nil {
    req.Header.Set("X-Forwarded-User", id.Subject)
}
```

⚠️ **顺序不能反**：必须**先剥**客户端的，**再写**网关自己的。
反过来的话，客户端伪造的头会覆盖掉网关写入的可信身份 —— 这是一类**极其常见**的越权入口。

细节见 [../../02-计算机基础/网络/反向代理原理与实现.md](../../02-计算机基础/网络/反向代理原理与实现.md)。

### 4) 三个必踩的坑

| 情况 | 现象 | 判定 |
|---|---|---|
| **`Role` 为空但路由要求角色** | 如果实现写成「`Role` 为空就跳过校验」，等于**无角色即放行** | 必须显式判断「要求的角色集合非空时，凭证里的角色必须有交集」 |
| **比较用 `==`** | 签名 / API Key 可被时序攻击逐字节猜出 | 一律 `hmac.Equal` |
| **把 payload 当可信数据用** | JWT payload 是**明文可改**的（改了签名就不过，但很多实现只验签名不验内容语义） | 只信「验签通过后」的 claim；不要把客户端传来的 claim 直接当权限 |

## 延伸追问

- **JWT 能不能放敏感信息？** → **不能**。payload 只是 base64，任何人拿到令牌都能读。
  这跟「签名保证不被篡改」是两件事 —— 不篡改不等于不可读。
- **为什么不用 RS256（非对称）而用 HS256？** →
  HS256 只有网关需要密钥（签发方与验签方是同一方或共享密钥），部署简单；
  但**所有验签方都持有「能签发」的密钥**，任何一个被攻破都能伪造令牌。
  多服务验签、且签发方与验签方要分离时，RS256 + JWKS 更合适（公钥可公开分发、可轮换）。
- **令牌怎么撤销？** → 无状态 JWT 撤销的代价很高，通常靠三招组合：
  ① 短有效期（真正的主力）；② refresh token 白名单（只对刷新动作有状态）；
  ③ 换密钥（代价是全量失效，用于事故响应）。**本项目当前没有撤销机制**，属于已知缺口。
- **`nbf` 有什么用？** → 它是「生效时间」，用在「令牌提前签发、到点才生效」的场景。
  单服务里用处不大，但在分布式部署中（各节点时钟有偏差）能避免「刚签发就被某个节点判为未来」。
- **为什么错误码要分得这么细（`token_no_expiry` 等）？** →
  因为**排障的方向完全不同**：`token_no_expiry` 指向签发方代码有问题，
  而 `unauthorized` 指向调用方凭证不对。混成一个「鉴权失败」，就只能靠翻日志逐条猜。
- **API Key 要不要加过期时间？** → 要，但通常不是「key 里的过期字段」，而是
  **密钥管理系统里的轮换策略**（如每 90 天换一次、新旧双活一段时间）。
  这属于运维流程而不是协议设计 —— **没有轮换流程的 API Key 等于永不过期**。
- **网关鉴权和业务里的权限校验是什么关系？** →
  网关只做**粗粒度**判断（有没有令牌、角色够不够），
  细粒度的**资源级**权限（这条订单是不是他的）必须留在业务层 ——
  网关不知道业务实体，也不该知道。
