# 可观测性技术选型

> Metrics / Logs / Traces 三支柱各自的定位与成本重心，链路追踪、指标监控、日志采集、存储后端、可视化告警五个层面的选型对比（技术 × 优缺点 × 适用场景），链路追踪额外按**契合语言**给出 Java / Go / PHP 的探针成熟度对照，以及三套可直接照搬的推荐组合。
>
> 内容整理自个人学习笔记。单技术的落地细节见 [Skywalking.md](Skywalking.md)、[Jaeger.md](Jaeger.md)，各语言接入分册见 [go/](../../01-编程语言/go/)、[java/](../../01-编程语言/java/)、[接入Skywalking.md](../../01-编程语言/php/接入Skywalking.md)；上下文传播机制见 [HTTP与gRPC.md](../../02-计算机基础/网络/HTTP与gRPC.md)。

## 一、先分清三个支柱各自解决什么

选型的第一原则：**先定「谁来看、看什么、留多久」，再选组件**。三支柱回答的是不同问题，成本重心也完全不同。

| 支柱 | 回答的问题 | 典型数据 | 基数量级 | 成本重心 | 保留期 |
| --- | --- | --- | --- | --- | --- |
| **Metrics 指标** | 系统整体健康吗？ | QPS、P99 延迟、错误率、CPU/内存 | **低**（受标签组合数控制） | 写入速率 × 保留期 | 长（数月~数年） |
| **Traces 链路** | 慢在哪一跳？跨服务怎么走的？ | Trace + Span 树 | **高**（每次请求一条） | **采样率** | 中（7~30 天） |
| **Logs 日志** | 这次请求究竟发生了什么？ | 结构化/半结构化文本 | **最高**（每行一句） | 存储 + 采集带宽 | 短（3~30 天） |

⭐ 三者的分工不是「谁替代谁」，而是**排查链条上的三段**：指标告警发现异常 → 链路定位到具体服务与操作 → 日志查明根因。把它们串起来的唯一纽带是 **TraceID**。

| 串联方式 | 做法 |
| --- | --- |
| Trace ↔ Log | 日志框架把当前 span 的 `trace_id` 写进每条日志字段，日志系统按 `trace_id` 聚合 |
| Metrics ↔ Trace | Prometheus 的 **exemplar**：指标样本上挂一个 `trace_id`，Grafana 面板可直接点进那条链路 |
| Trace ↔ Trace | W3C `traceparent` 头（HTTP）/ 消息 Header（MQ）逐跳传递，混用私有头会断链 |

⚠️ **最常见的误用**：用日志做监控（把 ERROR 行数当指标）。日志是高基数、需要解析、聚合慢的，做告警既贵又不准——**监控用指标，排障用日志**。

## 二、链路追踪怎么选？

这是「技术多、差异大」的典型场景。先说结论：**新项目一律用 OpenTelemetry 埋点**，因为埋点是最难迁移的部分（代码侵入、跨团队协调），协议先标准化；后端只是「可替换的实现」。

| 方案 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- |
| **SkyWalking** | 无侵入 Agent（字节码增强，几乎零改码）；内置 APM 大盘、拓扑图、告警规则；中文文档与社区友好；OAP 自带流式聚合 | 强绑定自家 Agent 与 `sw8` 协议；UI 定制能力弱；存储选型有限（BanyanDB / ES / H2）；生态活跃度不如 OTel | **Java 为主**、要开箱即用的 APM、团队没有专人做可观测性建设 |
| **Jaeger + OTel** | OTel 是事实标准、全语言天然支持；Jaeger v2 运行时即 OTel Collector；后端可替换（不锁厂商）；社区最活跃 | 只管链路，指标与告警要另配 Prometheus + Grafana；需自己埋点或引入 OTel Agent | **多语言**、已用或愿意用 OTel、要标准化、不想被单一厂商锁定 |
| **Zipkin** | 轻量、上手最快、依赖少 | 功能弱（无拓扑、无告警）；社区演进放缓；存储能力弱 | 小规模系统、内部工具、临时排查 |
| **Grafana Tempo** | 与 Grafana 生态无缝；成本极低（只索引 TraceID，Span 正文丢对象存储） | 只能按 TraceID 查，**无法按 tag 检索**（需配合 span metrics 或再加索引层） | 已用 Grafana LGTM 栈、链路主要用于「知道 ID 后精查」 |
| **云厂商托管**（阿里云 ARMS、腾讯云 APM、AWS X-Ray） | 免运维、开箱即用、与云资源天然打通 | 按量计费（流量大时贵）；数据出网与合规；深度绑定 | 小团队、无专职 SRE、用预算换人力 |

⭐ **决策路径**：先按**主语言**定方向，再看是否需要「开箱即用的 APM 大盘 + 拓扑 + 告警」。

- **Java 为主** + 要开箱即用 APM → SkyWalking 主线（Agent 无侵入、一天可上线）
- **Go 为主 / 多语言 / 已用 OTel** → Jaeger / Tempo + OTel，指标交 Prometheus（⚠️ SkyWalking 在 Go 侧只能编译期注入，插件集与灵活性都弱于 Java）
- **两者都不要并行双报**——双份探针 = 双份开销 + 两套 UI，只在按 ID 精查时按需临时开另一个

### 契合语言与团队栈怎么选 ⭐

同一份能力清单，落到不同语言上「探针成熟度、插件覆盖、运维工具」差别很大——**探针往往才是隐性成本最高的一项**（对照写法见 [消息队列选型](../../03-数据与中间件/中间件/消息队列/消息队列选型.md) 的同名维度）。

| 方案 | 服务端 | 最契合语言 | Java 侧实际体验 | Go 侧实际体验 | PHP / 其他 |
| --- | --- | --- | --- | --- | --- |
| **SkyWalking** | Java | ⭐ **Java** | 字节码增强最成熟，Spring 全家桶插件最全，`-javaagent` 一行接入（见 [接入Skywalking.md](../../01-编程语言/java/接入Skywalking.md)） | 只能**编译期 AST 注入**（`-toolexec` + `-a`），插件集有限、配置固化进二进制、运行期无法摘除（见 [接入Skywalking.md](../../01-编程语言/go/接入Skywalking.md)） | PHP 扩展（.so）+ 共享内存 + fork 上报进程，多进程模型下坑最多（见 [接入Skywalking.md](../../01-编程语言/php/接入Skywalking.md)）；Node.js 靠 monkey patch，必须在业务代码前加载 |
| **Jaeger + OTel** | Go | ⭐ **语言无关**（OTel 对各语言都是一等公民） | OTel Java Agent 同样零改码；Spring Boot 3 另有 Micrometer Tracing 路线（见 [接入Jaeger.md](../../01-编程语言/java/接入Jaeger.md)） | ⭐ **最顺**：OTel Go SDK 原生、contrib 覆盖 Gin/GORM/net/http，采样与导出地址运行期可配（见 [接入Jaeger.md](../../01-编程语言/go/接入Jaeger.md)） | OTel PHP 为社区实现，成熟度低于 Java/Go；各语言都走同一套 OTLP，混跑时唯一约束是「传播头统一」 |
| **Zipkin** | Java | Java（Brave） | Brave 库成熟，但需要显式改码埋点 | 第三方客户端，社区演进慢 | 各语言有客户端，功能收敛 |
| **Grafana Tempo** | Go | ⭐ **语言无关**（只收 OTLP） | 同 Jaeger，挂 OTel Java Agent | 同 Jaeger，用 OTel Go SDK | 同 Jaeger |
| **云厂商托管** | — | 取决于云厂商 SDK | 通常 Java Agent + SDK 双路都有 | 多数提供 Go SDK | ⚠️ PHP 侧支持参差，接入前逐个确认 |

> ⭐ 三条结论：
> **① Java 团队**：SkyWalking 收益最大——字节码增强覆盖面最广、拓扑与告警开箱即用，`-javaagent` 一行即可上线。
> **② Go 团队**：⚠️ **SkyWalking 在 Go 侧是「二等公民」**，没有运行时增强能力，只能编译期注入，插件集与配置灵活性都弱于 Java；此时 **OTel SDK + Jaeger 反而更顺**（运行期可配、contrib 生态广、后端可替换）。
> **③ PHP / 多语言混合团队**：优先 OTel 路线（协议统一、各语言同一套 OTLP），把「传播头一致」当作唯一的跨语言约束；若必须用 SkyWalking，先验证最弱那门语言的探针——PHP 的多进程 + 共享内存模型坑最多。
>
> ⚠️ 反面教训：探针不成熟不是「少几个 span」，而是**排障能力缺失**——拿不到方法级耗时、跨线程/跨协程断链、日志关联不上 traceId，出问题时只能靠加日志重发布。

## 三、指标监控怎么选？

| 方案 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- |
| **Prometheus** | 事实标准；Pull 模型 + 服务发现天然贴合 K8s；PromQL 表达力强；导出器（exporter）生态最全 | 单机存储，本地盘容量即保留期上限；**高基数容易打爆内存**；原生集群与长期存储方案弱 | 中小规模（单集群 < 数百万活跃序列）、K8s 环境 |
| **VictoriaMetrics** | 兼容 PromQL；写入与压缩效率高，**同等数据量下存储与内存显著低于 Prometheus**；原生支持水平扩展与多租户 | 与 Prometheus 存在细节行为差异（部分函数/边界）；生态比 Prometheus 小 | 高基数、大流量、需要长保留期或多集群汇聚 |
| **InfluxDB** | 时序场景专精，写入性能好；Flux 查询灵活 | 2.x/3.x 版本之间协议与授权策略变动大，生态分裂；集群版收费 | IoT、自研采集链路、非 K8s 场景 |
| **Zabbix** | Agent 采集 + 阈值告警非常成熟；主机/网络设备监控覆盖广 | 容器与云原生适配差；指标模型不适合微服务维度 | 传统虚机、IDC、网络设备监控 |
| **云托管监控**（云监控 / CMS） | 免运维、与云产品指标直连 | 维度定制受限；按量计费；PromQL 兼容性参差 | 已整体上云的团队 |

⭐ **判断依据是「活跃时间序列数」**：单 Prometheus 实例的舒适区在**百万级以内**。超过就要么上 VictoriaMetrics / Thanos / Mimir，要么**先降基数**（见第八节第 2 条）。

## 四、日志收集怎么选？

| 方案 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- |
| **ELK / EFK**（ES + Logstash/Fluent Bit + Kibana） | 全文检索能力最强；聚合分析成熟；生态与人才储备最厚 | 成本高（ES 吃内存与磁盘，副本 + 索引开销大）；运维重（分片、ILM、JVM 调优） | 日志量大且**需要复杂检索与聚合**、有专职运维 |
| **Loki** | **只索引标签，正文丢对象存储**，成本比 ES 低一个量级；与 Grafana 一体化 | 不做全文索引，检索靠标签缩小范围后暴力 grep，**查得慢且不灵活** | 已用 Grafana 栈、日志主要用于「按服务/时间排障」而非全文检索 |
| **ClickHouse** | 写入与聚合极快、压缩比高、SQL 友好、单位成本低 | 没有现成的 Kibana 式 UI，需自建采集管道（Vector / Fluent Bit）与查询界面；不适合行级频繁更新 | 日志量极大、**以分析为主**（如安全审计、行为分析） |
| **云日志服务**（SLS / CLS 等） | 免运维、采集器开箱可用、弹性 | 按量计费；查询语法私有，迁移成本高 | 小团队、日志不做长期自建 |
| **只落文件 + 集中 grep** | 零组件、零成本 | 无检索、无保留策略、多机排查靠登录 | 单机/小规模过渡期，⚠️ 不可长期使用 |

⚠️ **别被「日志成本占比」骗了**：成熟系统里日志往往是可观测性成本的最大头（常占 50%+）。降本手段是**分级保留**——ERROR 全留、WARN 短期、INFO 采样或降级为指标。

## 五、存储后端怎么选？

存储要按**查询模式**选，不是按「哪个名气大」选。

| 存储 | 优点 | 缺点 | 最适合承载                                         |
| --- | --- | --- |-----------------------------------------------|
| **Elasticsearch** | 成熟、聚合强、生态完整（Jaeger / SkyWalking / Loki 都能接） | 资源消耗大、成本高；高基数下分片与写入压力明显 | Trace 按 tag 检索、日志全文检索                         |
| **BanyanDB** | SkyWalking 官方自研，专为链路 + 时序模型设计，比 ES 更省资源、可分层存储 | 生态小、外部工具支持少 | SkyWalking 的默认推荐存储                            |
| **ClickHouse** | 高基数下**按 ID 精查**最优；写入吞吐与压缩比极高；Jaeger v2 官方原生支持 | 列式，不适合频繁点更新；需理解 MergeTree 调优 | Trace 明细、日志分析、大宽表聚合，Jaeger v2.18.0 开始默认推进存储 |
| **Prometheus TSDB / VictoriaMetrics** | 为指标模型量身定制，压缩好、查询快 | 只服务指标（其余数据不适用） | Metrics                                       |
| **对象存储**（S3 / OSS / MinIO） | 单位成本最低、容量无上限 | 延迟高，只能做冷数据 | Tempo 的 Span 正文、Loki 的日志正文、归档层                |

⭐ **分层保留**是控制成本的通用手段：热数据（7 天，SSD + 可检索）→ 温数据（30 天，普通盘）→ 冷数据（对象存储，只保索引可回捞）。

## 六、可视化与告警怎么选？

| 组件 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- |
| **Grafana** | 多数据源统一面板（Prometheus / Loki / Tempo / ES / CH）；仪表盘生态大、模板可复用 | 告警能力相对分散（依赖各数据源） | 事实标准，几乎必选 |
| **Kibana** | 与 ES 深度绑定，Discover 检索体验好 | 只服务 ES | 用 ELK 的团队 |
| **SkyWalking UI** | APM 专用视图（拓扑、服务指标、链路），开箱即用 | 定制能力弱，无法统一纳入其他数据源 | 用 SkyWalking 的团队，与 Grafana 分工（APM 看 SW，指标看 Grafana） |
| **Alertmanager** | 分组、抑制、静默、多通道（钉钉/飞书/邮件/Webhook）；与 Prometheus 天然配套 | 规则语法（PromQL）有学习成本；无 UI 配置 | 指标告警的标准选择 |

⚠️ **告警设计比告警工具更重要**：优先用**多窗口多燃烧率（multi-window burn rate**）的 SLO 告警替代「单点阈值告警」，否则告警疲劳会让团队直接忽略。

## 七、三套推荐组合（可直接照搬）

### 7.1 小团队起步（< 10 个服务）

```text
埋点：SkyWalking Agent（无侵入，改启动参数即可）
存储：BanyanDB（或内置 H2 仅用于试用）
UI：  SkyWalking UI（APM 大盘 + 拓扑）
日志：云日志服务（不自建，避免运维负担）
```

**理由**：一周内可上线，人力投入最小。⚠️ H2 只能用于试用，别上生产。⚠️ 这套组合的前提是**团队以 Java 为主**；Go 为主的团队请改走 7.2 的 OTel 路线（原因见第二节「契合语言」维度）。

### 7.2 标准微服务（10 ~ 100 个服务）

```text
埋点：OpenTelemetry SDK → OTLP
链路：OTel Collector（含 tail sampling）→ Jaeger → ClickHouse
指标：Prometheus + Alertmanager
日志：Loki（或云日志）
面板：Grafana（统一查询 Prom / Loki / Tempo）
```

**理由**：埋点标准化、后端可替换、成本可控；Collector 集中做采样与属性清洗。

### 7.3 大规模高基数（> 100 个服务，日增 TB 级）

```text
埋点：OTel SDK / eBPF（自动埋点）→ Collector（聚合 + 尾部采样）
链路：OTel Collector → ClickHouse（按 ID 精查）
指标：VictoriaMetrics（集群版，降基数 + 长保留）
日志：ClickHouse 或对象存储归档；ERROR 走 Loki 短期留存
面板：Grafana；告警：Alertmanager（SLO 燃烧率）
```

**理由**：把「查询模式」拆开——低基数长期指标走 TSDB，高基数按 ID 精查走 CH，冷数据下沉对象存储。

## 八、延伸追问

- **三支柱怎么关联起来？** → 唯一纽带是 `trace_id`：日志写进字段、指标挂 exemplar、跨进程用 W3C `traceparent` 传递。⚠️ 全链路头格式必须统一，混用 `sw8` / `uber-trace-id` / `traceparent` 会断链。
- **为什么指标要严格控基数？** → 每个标签组合都算一条独立时间序列，`user_id` / `request_id` / 完整 URL 做标签会造成「基数爆炸」，直接打爆 TSDB 内存。标签只放**低基数**维度（服务名、接口路由模板、状态码），高基数维度放日志或链路。
- **采样率怎么定？** → 头部采样（SDK 端按比例）简单但可能丢弃错误链路；**尾部采样**（Collector 侧按结果决策）能做到「错误与慢请求 100% 保留、正常请求抽样」，是成本与信息量的最优解。
- **无侵入 Agent 的代价是什么？** → 字节码增强带来 CPU/内存开销；与 JDK 版本、Glibc 版本、其他 agent 存在兼容风险；探针异常理论上可能影响业务进程——所以生产要灰度、要能一键摘除。
- **SkyWalking 对 Go 友好吗？** ⭐ → 这是选型最容易踩的坑。Go 没有 classloader，**「运行时无侵入」在 Go 上不成立**，skywalking-go 走的是编译期 AST 注入（`go build -toolexec=… -a`）：配置在编译期写死进二进制、运行期改不了也摘不掉、插件只覆盖官方列出的框架版本区间。所以 **Java 侧的「零改码 + 灵活」体验在 Go 侧会打折**，Go 为主的项目更该走 OTel SDK。参见 [接入Skywalking.md](../../01-编程语言/go/接入Skywalking.md)。
- **为什么不用日志做监控告警？** → 日志基数最高、需要解析、聚合慢且贵；监控需要的是低基数、可长期保存、能快速聚合的指标。
- **ES 和 ClickHouse 都能存 Trace，怎么选？** → 看查询模式：**按标签过滤 + 全文检索**选 ES；**按 TraceID 精查、高基数写入、要控成本**选 ClickHouse。Jaeger v2 对 CH 是一等公民。
- **可观测性成本怎么降？** → 四板斧：①尾部采样（链路）；②降基数（指标）；③分级保留 + 分层存储（日志与冷数据）；④把「只增不减」的 INFO 日志降级或采样。
- **告警怎么设计才不会被忽略？** → 用 SLO + 多窗口燃烧率替代单点阈值；设置抑制与静默规则（同一根因只告一条）；告警必须**可行动**——没有明确处置动作的告警直接删掉。
