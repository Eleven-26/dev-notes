## 一、内存管理

本篇讲 **Linux 内核**这一层：如何把物理内存抽象成地址空间、如何分配回收、如何把文件落到磁盘。它与 `../go/内存分配器.md` 是**不同层次**：Go 的 mheap/mcentral/mcache 是**用户态进程内部**的二次分配器，其"页"是**虚拟地址**，最终仍要通过内核的伙伴系统 + 缺页中断才能拿到物理页。

### 虚拟内存 vs 物理内存

| | 虚拟内存（进程视角） | 物理内存（硬件视角） |
|---|---|---|
| 谁能看到 / 地址 | 只有进程自己（`mm_struct` / 页表）；**虚拟地址 VA**，需经 MMU 转换 | 内核统一管理；真实 DRAM 单元 |
| 大小 / 连续性 | 64 位理论 128TB（内核常用 47 位）；**看起来连续** | 由内存条决定；可不连续，甚至暂时不在内存里 |

**为什么每个进程都要有独立地址空间**：① **隔离**——A、B 进程访问同一个 `0x400000` 落到不同物理页，互不可见互不破坏；② **简化链接**——所有程序都能从同一固定地址开始链接（叠加 ASLR 做随机化）；③ **超售与延迟分配**——`malloc` 只"预约"地址，真正用时才分配物理页，总量可超过物理内存；④ 支持内存映射文件与共享内存。⭐ 进程里"看到"的地址**全都是虚拟地址**，打印指针拿到的是 VA 而非物理地址。

### 地址空间布局（文字版）

64 位 Linux 用户进程，**低地址 → 高地址**：

```
0x0000000000000000
  ├─ 不可访问区（NULL 指针陷阱页）
  ├─ 代码段 text        ELF 机器指令，只读可执行
  ├─ 数据段 data + BSS  已初始化 / 未初始化的全局静态变量
  ├─ 堆 Heap       ─── 向上增长（brk / mmap），malloc 的地盘
  ├─ 文件映射区 mmap ── 向下增长：动态库、mmap 文件、匿名大块内存
  ├─ 栈 Stack      ─── 向下增长：局部变量、调用帧（默认 8MB，ulimit -s）
0x00007fffffffffff ──（其下为环境变量 / argv；再往上是非规范地址空洞）
0xffff800000000000 ── 内核空间：内核代码/页表/ZONE 映射
0xffffffffffffffff     ⭐ 用户态不可见、访问即段错误
```

- **堆与栈相向生长**，中间的 mmap 区是缓冲区，避免两者撞上。
- ⭐ **内核空间在每个进程地址空间里都占一份高位地址**，但所有进程共享同一份物理内核代码/数据，只有陷入内核态才能访问；大对象走 `mmap` 不在传统"堆"里——这也是 RSS 偏大的原因之一。

### 分页、页表与 TLB

| 概念 | 说明 |
|---|---|
| **页 Page / 页框** | 内核管理内存的**最小单位**，通常 **4KB**（大页 HugePage 为 2MB / 1GB）；物理内存中同样大小的 4KB 块称页框 |
| **页表** | 记录 VA → PA 的多级表（x86-64 为 **4~5 级**：PGD→P4D→PUD→PMD→PTE） |
| ⭐ **TLB** | **页表的高速缓存**，命中则地址转换一次完成 |

⭐ **TLB 为什么关键**：4 级页表意味着一次转换可能需 **4~5 次访存**，TLB 把开销压到接近零；**TLB miss 是进程切换的主要隐性成本**（切进程换页表基址 CR3，TLB 大面积失效）。大页（HugePage）的核心价值就是**减少 TLB 条目数**。

### 缺页中断（Page Fault）

进程访问了"页表项无效"的虚拟地址 → CPU 触发缺页异常 → 内核处理。

| 类型 | 触发原因 | 读盘 | 代价 |
|---|---|---|---|
| ⭐ **minor fault**（次缺页） | 页**已在物理内存**，只是没建映射：首次写 `malloc` 的内存、`fork` 后写共享页（COW） | ❌ | 微秒级 |
| ⭐ **major fault**（主缺页） | 页**不在物理内存**，须从磁盘/swap/文件读入：首次 mmap 读大文件、匿名页被换出后再访问 | ✅ | 毫秒级 |

### 内核分配：伙伴系统 + Slab/Slub

| 层次 | 解决什么 | 机制 |
|---|---|---|
| ⭐ **伙伴系统 Buddy** | **外部碎片**：空闲总量够，但没有足够大的**连续**块 | 以 **2^order 个连续页**为单位管理（order 0~10，即 1~1024 页）；分配时找不到合适的就**把大块对半分裂**，释放时若"伙伴"也空闲就**合并回大块** |
| ⭐ **Slab / Slub** | **内部碎片 + 小对象效率**：内核里大量 `task_struct`、`inode`、`dentry` 这种几十~几百字节的小对象，给一整页太浪费 | 从伙伴系统批发若干页，切成**同规格的对象缓存池**；释放后**不清零、不归还**，留池里复用 |

⭐ 一句话记：**Buddy 管"批发整页"（页级、消外部碎片），Slab 管"零售小件"（字节级、消内部碎片）**。

### swap

swap 是**磁盘上的一块空间**（分区或文件），作物理内存的溢出区：内存紧张时把不活跃的匿名页换出。

| 项 | 说明 |
|---|---|
| 作用 | ① 让"总用量 > 物理内存"成为可能；② 把长期不用的匿名页挪走，给 Page Cache 和活跃数据腾地方 |
| ⚠️ **swappiness** | `vm.swappiness`（0~100）：回收时**更倾向回收匿名页还是页缓存**。默认 60；设 **1** = 尽量不 swap、优先回收页缓存 |
| 谁能被换出 | 只有**匿名页**（堆、栈等无文件背景的页）；有文件背景的页直接丢弃/回写即可，无需 swap |

⚠️ **swap 打开的代价**：磁盘比内存慢 **3~4 个数量级**，热点页一旦被换出，延迟**数量级恶化**，且表现为**周期性抖动、极难定位**；换入换出还占 IO，容易雪崩，故**数据库、延迟敏感服务通常设 `swappiness=1` 或直接 `swapoff`**。⚠️ 但**完全关掉 swap**，内存打满时会直接触发 OOM Killer **杀进程**，而它选谁未必符合预期——留一点 swap 相当于给运维留缓冲时间。

## 二、内存回收与缓存 ⭐

### Page Cache 与 Buffer Cache ⚠️ 高频考点

| | **Page Cache（页缓存）** | **Buffer Cache（块缓冲）** |
|---|---|---|
| 缓存对象与场景 | **文件内容**，以**页（4KB）**为单位；普通文件的 `read/write` | **块设备的裸块**，以**块（512B/1KB/4KB）**为单位；读写裸设备与**文件系统元数据**（超级块、位图、间接块） |
| 关系 | ⚠️ **现代 Linux（2.4+）两者已统一**：Buffer Cache 只是 Page Cache 的特例（同一页切成若干 `buffer_head`），**不再有两份独立缓存**；`free` 里二者合称 `buff/cache` |

⭐ 标准答法：历史上 Cache 缓存**文件内容**、Buffer 缓存**块设备裸块**，两者独立；现在 Buffer Cache 已并入 Page Cache，`buff` 主要体现**块设备元数据**缓存，量通常远小于 `cache`。

### 为什么 `free` 显示"几乎用完"其实是好事

| 字段 | 含义 |
|---|---|
| `total` / `used` | 物理内存总量 / 已用量；`free` = **完全空闲、一点没用**的内存 |
| ⭐ `buff/cache` | 页缓存 + 块缓存，⚠️ **可回收，不算真正被"占用"** |
| ⭐ `available` | **真正该看的指标**：≈ free + 大部分可回收缓存，即还能给新进程用多少 |

```bash
$ free -h
              total        used        free      shared  buff/cache   available
Mem:           15Gi        11Gi       0.5Gi       1.0Gi       4.0Gi        3.4Gi
                            ↑ 别看 free      ↑ 可回收      ↑ 看这个
```

**原理**：内存不用也是浪费。Linux 的哲学是**空闲内存一律拿去做页缓存**，进程需要时再回收。所以 `free` 小、`buff/cache` 大 = **系统把闲置资源用起来了 = 好事**。⚠️ 判断内存是否吃紧，**只看 `available` 和 swap 是否增长**，不要看 `free`。

### 回收机制：kswapd、直接回收与 LRU

| 机制 | 触发时机 | 特点 |
|---|---|---|
| ⭐ **kswapd（后台回收）** | 内核线程，空闲页低于 **low 水位**时被唤醒，回收到 **high 水位**止 | **异步、不阻塞业务**；健康系统应只看到它工作 |
| ⭐ **直接回收 direct reclaim** | 分配时空闲页低于 **min 水位**，来不及等 kswapd | **同步阻塞**，当前进程自己回收，⚠️ 表现为**请求延迟尖刺** |
| **OOM Killer** | 直接回收也拿不到页 | 按 `oom_score` **挑一个进程杀掉**（通常挑占用最大、最不重要的） |

三个水位（`min` / `low` / `high`，见 `/proc/zoneinfo`）就是这套机制的门槛。可回收页挂在**活跃 active / 非活跃 inactive** 两条 LRU 链表上，**只从 inactive 尾部回收**：`新页 → inactive 头 →（再被访问）→ active →（久未访问降级）→ inactive 尾 → 回收`。

| 页类型 | 可回收 | 回收方式 |
|---|---|---|
| 干净文件页（未修改） | ✅ | **直接丢弃**，下次读盘即可（最快）⭐ 回收优先选它：代价最低 |
| 脏文件页（写了没回写） | ✅ | 先 **writeback 回写磁盘**再丢弃 |
| 匿名页（堆/栈） | ✅（有 swap） | 写入 swap 后释放 |
| 内核 slab / 页表 / 内核栈 / `mlock` / hugetlb | ❌ | — |

### ⚠️ "cached 很大"不等于内存泄漏

| 观察项 | 判读 |
|---|---|
| `available` 是否还很大 | 是 → 完全正常，缓存随时可让出 |
| swap 是否**持续增长** | 是 → 真的在往外换，内存确实紧张 |
| `vmstat 1` 的 `si/so` | 长期**非 0** → 正在换入换出，⚠️ 有问题 |
| 单进程 RSS 是否**单调上涨不回落** | ⭐ 这才是泄漏的判据——**看进程，不看全局**；全局 `cached` 大只是**特性** |

## 三、文件系统

### VFS（虚拟文件系统）

**VFS 是内核的一层抽象**：对上给系统调用统一的 `open/read/write/close`，对下定义"文件系统必须实现的操作集"，让 ext4、XFS、NFS、procfs **共存于同一棵目录树**。四大对象：`super_block`（一个已挂载文件系统）、⭐ `inode`（一个文件的元数据）、⭐ `dentry`（"路径名 ↔ inode"的目录项）、`file`（一次打开的实例，含读写偏移 `f_pos`）。同一份文件多次 `open` 互不影响：每次生成独立的 `file`（各自 offset），但指向**同一个 inode**。

### ext4 / XFS / Btrfs 对比 ⭐

| | **ext4** | **XFS** | **Btrfs** |
|---|---|---|---|
| 定位 | 最通用最稳的**默认选择** | **大文件 / 高并发**首选 | 写时复制（COW）的现代文件系统 |
| 日志 / 快照 / 校验和 | ✅ 有序日志，可关 / ❌ / ❌（仅元数据） | ✅ 元数据日志 / ❌ / ❌ | ❌ 靠 **COW + 校验和** / ✅ 原生快照 / ✅ 数据+元数据 |
| 最大文件 / fs | 16TB / 1EB | 8EB / 8EB | 16EB / 16EB |
| 在线扩容 / 缩容 | ✅ / ✅（缩容需卸载 resize） | ✅ / ❌ **不支持缩容** | ✅ / ✅ |
| 适用场景 | 通用服务器、根分区、**容器镜像层** | 大文件、视频/日志、**数据库**、并行 IO | 需要快照/压缩/多盘管理 |
| 成熟度 | 最高 | 高（RHEL 默认） | 较新，⚠️ RAID5/6 仍不推荐生产 |

### inode

**inode = 文件的"身份证"**，存**元数据**，⚠️ **不存文件名、不存文件内容**。

| inode 存什么 | inode 不存什么 |
|---|---|
| 文件类型（普通/目录/设备/符号链接） | ❌ **文件名**（在 dentry / 目录文件里） |
| 权限 `rwxrwxrwx`、UID/GID、大小、**链接数 Links** | ❌ 文件内容（在数据块里） |
| 三个时间戳 `atime` / `mtime` / `ctime`；扩展属性、ACL | |
| ⭐ **数据块指针**（指向内容所在的数据块） | |

inode 里只有**有限几个直接指针**，大文件靠**间接块**逐级扩展（ext4 改用 extent），是"大文件随机写慢"的结构性原因之一。

```bash
df -i            # ⭐ 看 inode 使用率（不是磁盘空间）
stat app.log     # inode 号、Links、三个时间戳
```

⚠️ **inode 数量在格式化时就固定**，只能重新格式化才能改（**XFS 例外：动态分配 inode，不会耗尽**）。

### dentry（目录项缓存）

**dentry 缓存的是"路径名 → inode"的映射**，避免每次访问都去磁盘逐层解析路径。`open("/var/log/app.log")` 需逐分量解析（`/`→`var`→`log`→`app.log`），每级都要读目录内容查 inode；结果缓存在 **dcache**，下次直接命中、**不碰磁盘**。dentry 由 **Slab 缓存**分配。硬链接 = **多个 dentry 指向同一 inode**。

### 硬链接 vs 软链接 ⭐

```bash
ln  src.txt  hard.txt     # 硬链接：多一个目录项指向同一 inode
ln -s src.txt soft.txt    # 软链接：新建"内容为目标路径字符串"的特殊文件
```

| | **硬链接** | **软链接（符号链接）** |
|---|---|---|
| inode | ⭐ **与源文件相同** | ⭐ **新的独立 inode** |
| 跨文件系统 | ❌ **不能**（inode 号只在同 fs 内唯一） | ✅ 可以，甚至可指向不存在的路径 |
| 删除源文件后 | ⚠️ **仍可用**（inode 还在，Links −1） | ⚠️ **失效**（断链，`ls` 闪红） |
| 能对目录创建 | ❌ **不能**（会形成环路，仅内核为 `.` `..` 创建） | ✅ 可以 |
| 本质 / `ls -l` | 目录里的**另一个名字**；普通文件，Links +1 | **存着路径字符串的小文件**；`lrwxrwxrwx` 显示 `-> src.txt` |

⭐ **删除文件的真正语义**：`rm` 是**解除一个 dentry 链接**，inode 的 `Links` 减 1；⚠️ **只有 Links 归 0 且无进程打开时，数据块才真正释放**。

### 文件描述符（fd）

| 项 | 说明 |
|---|---|
| 本质 / 查看 | 进程 `files_struct` 里**数组的下标**，指向内核 `file` 对象；默认三个 `0/1/2`（stdin/out/err） |
| ⭐ `ulimit -n` | **单进程可打开 fd 数上限**（默认常 1024），高并发服务必须调大 |
| 查看命令 | `lsof -p <pid>`；`ls -l /proc/<pid>/fd`（文件/socket/管道都算 fd） |

⚠️ **fd 泄漏的表现**：① 报 `too many open files`（`EMFILE`）；② `lsof -p <pid> | wc -l` 随时间**单调增长**；③ 大量连接停在 `CLOSE_WAIT`（对端关了本端没 close）。对策：`defer f.Close()` / try-with-resources 是底线，长连接服务要设 idle 超时主动关闭。

## 四、I/O 栈与落盘

### 一次 `write()` 的路径

```bash
① 用户缓冲区（bufio.Writer / BufferedWriter，用户态内存）
      ↓ write(fd, buf, n)  系统调用陷入内核
② ⭐ 页缓存 Page Cache（内核态；拷到这里 write 就返回了）→ 页标记 dirty，异步回写
③ 块层 Generic Block Layer：合并/排序请求 → IO 调度（mq-deadline / kyber / bfq）
④ 设备驱动（SCSI / NVMe）  →  ⑤ 磁盘 / SSD
```

⚠️ **关键：`write()` 在第 ② 步就返回成功了**——数据只进了页缓存，还没到磁盘。

### ⚠️ write 成功 ≠ 数据落盘

| 调用 | 作用 |
|---|---|
| ⭐ `fsync(fd)` | 该文件**所有脏页 + 元数据**（inode、大小、时间戳）**强制回写并等磁盘确认** |
| `fdatasync(fd)` | 只刷**数据**，不保证元数据（如 mtime），比 `fsync` 略快 |
| `sync()` / `sync` 命令 | 刷**整个系统**的脏页（生产慎用，会引发 IO 洪峰） |
| `msync(addr)` | 刷 **mmap 映射区**；`O_SYNC` = 每次 write 自动 fsync，⚠️ 慢很多 |

只有 `fsync` **返回 0**，数据才算"落盘"（断电不丢）。数据库 WAL 靠的就是它。

### 直接 IO 与 mmap

| | 说明 | 代价 / 风险 |
|---|---|---|
| ⭐ **O_DIRECT** | 打开时加此标志，**绕过页缓存**，直接在用户缓冲与设备间传输 | ⚠️ ① **必须自己保证对齐**（内存地址、长度、文件偏移都要按块对齐）；② 失去预读与缓存，**小随机 IO 变慢**；③ 与 Page Cache 并存可能不一致。适合**自带缓存的数据库**（MySQL 常用 `innodb_flush_method=O_DIRECT`） |
| ⭐ **mmap** | 把文件**映射成一段内存**，读写像操作字节数组，省掉 `read/write` 的**系统调用 + 一次用户/内核拷贝** | ✅ 零拷贝、随机访问友好、多进程共享天然可用；⚠️ 缺页中断开销（大文件首次访问抖动）、脏页回写**时机不可控**（需 `msync`）、**占 RSS**、32 位寻址受限 |

## 五、常用命令（精简表）

| 命令 | 看什么 |
|---|---|
| `free -h` | ⭐ 内存总览，**看 `available` 而不是 `free`** |
| `vmstat 1` / `vmstat -s` | `si/so`（swap 换入换出）、`bi/bo`、`cs` / 内存与缺页的**累计统计** |
| `sar -r 1` | 内存使用率历史，`%memused` / `%commit` |
| `df -h` / ⭐ `df -i` | 磁盘**空间** / ⭐ **inode** 使用率（"磁盘没满却写不进去"的元凶） |
| `du -sh *`、`du -x --max-depth=1` | 哪个目录占空间（`-x` 不跨文件系统） |
| `stat file` | inode 号、Links、**三个时间戳**、块大小 |
| `lsof -p <pid>`、`lsof +D /path` | 打开的 fd；⚠️ 找**已删除但仍被占用**的文件 |
| `lsblk` / `blkid`、`mount` / `findmnt` | 块设备树与 fs 类型 / 挂载点与挂载选项（`noatime`、`discard`） |
| `sync` | 手动回写所有脏页（关机/拔盘前）；详细排查见 [性能排查.md](性能排查.md) |

## 六、使用一：Go ⭐

### 进程内存指标：MemStats vs RSS

```go
package main

import (
	"fmt"
	"runtime"
)

func main() {
	var m runtime.MemStats
	runtime.ReadMemStats(&m)
	fmt.Printf("HeapAlloc=%dMiB HeapSys=%dMiB HeapIdle=%dMiB "+
		"StackSys=%dMiB Sys=%dMiB NumGC=%d\n",
		m.HeapAlloc>>20, m.HeapSys>>20, m.HeapIdle>>20,
		m.StackSys>>20, m.Sys>>20, m.NumGC)
}
```

| 指标 | 含义 | 与 RSS 的关系 |
|---|---|---|
| `HeapAlloc` | ⭐ **活着的对象**占的堆字节数 | 通常**远小于 RSS** |
| `HeapSys` | 向 OS **预约**的堆内存（含未使用、GC 未还的） | RSS 的上界之一 |
| `HeapIdle` | 堆里**空闲**的 span（可被归还） | `HeapSys − HeapAlloc` 的大头 |
| `Sys` | ⭐ 运行时**累计向 OS 申请的总字节数**（堆+栈+mspan+GC 元数据） | ⭐ **最接近 RSS**，但仍是虚拟内存口径 |
| `StackSys` / **RSS** | goroutine 栈占用 / ⭐ **进程实际占用的物理内存**（`ps -o rss`） | ⚠️ 运维与容器看的是 **RSS** |

### ⚠️ RSS 比 HeapAlloc 大很多的常见原因

| 原因 | 说明 | 对策 |
|---|---|---|
| **`GOGC` / madvise** | GC 后只把 span 标成 `HeapIdle`，**默认延迟归还 OS**；另按 arena（64MB）预留虚拟地址，RSS 只计真正 touched 的页 | 调 `GOGC`；Go 1.16+ 用 `debug.FreeOSMemory()` 或 `GODEBUG=madvdontneed=1` |
| **goroutine 栈** | 每 goroutine 2KB 起、按需增长；**上万 goroutine 就是几十 MB**（`StackSys`） | 控制并发度，防 goroutine 泄漏 |
| ⭐ **mmap** | ⚠️ `>32KB` 大对象、cgo、`syscall.Mmap` **直接走 mmap**，**完全不计入 MemStats 的堆** | 用 `/proc/<pid>/smaps` 看匿名映射段 |
| **GC 元数据 / mspan / cgo** | `bitmap`、`mspan` 结构；C 侧 malloc 的内存 Go 完全看不见 | 小头或需单独排查 |

⭐ 一句话：**MemStats 只描述 Go 堆，RSS 才是内核视角的全部**。

### 文件读写：`os` + `bufio` + `Sync()`

```go
package main

import (
	"bufio"
	"os"
)

func main() {
	f, err := os.OpenFile("app.log", os.O_CREATE|os.O_APPEND|os.O_WRONLY, 0644)
	if err != nil {
		panic(err)
	}
	defer f.Close()
	w := bufio.NewWriterSize(f, 64*1024) // ⭐ 64KB 用户缓冲，减少系统调用
	if _, err := w.WriteString("hello\n"); err != nil {
		panic(err)
	}
	if err := w.Flush(); err != nil { // ① 只刷进内核页缓存，还没落盘
		panic(err)
	}
	if err := f.Sync(); err != nil { // ② 等价 fsync(2)，才真正落盘
		panic(err)
	}
}
```

⚠️ **只 `Flush()` 不 `Sync()`**：进程崩溃数据还在（页缓存属内核），但**机器掉电就没了**。### `syscall.Mmap` 内存映射读写（Unix）

```go
package main

import (
	"fmt"
	"os"
	"syscall"
)

func main() {
	f, err := os.OpenFile("data.bin", os.O_RDWR|os.O_CREATE, 0644)
	if err != nil {
		panic(err)
	}
	defer f.Close()
	if err := f.Truncate(4096); err != nil { // ⚠️ 不能映射长度为 0 的文件
		panic(err)
	}
	// MAP_SHARED：修改写回文件；MAP_PRIVATE 是写时复制，不落盘
	b, err := syscall.Mmap(int(f.Fd()), 0, 4096,
		syscall.PROT_READ|syscall.PROT_WRITE, syscall.MAP_SHARED)
	if err != nil {
		panic(err)
	}
	defer syscall.Munmap(b)
	copy(b, []byte("hello mmap")) // 像操作普通 []byte 一样写
	// ⭐ 等价 msync(2)，刷脏页；不调用就等内核异步回写
	if err := syscall.Msync(b, syscall.MS_SYNC); err != nil {
		panic(err)
	}
	fmt.Println(string(b[:10]))
}
```

⚠️ `syscall.Mmap` 是 **Unix 专用**（Windows 无此调用），跨平台可用 `golang.org/x/exp/mmap`；Mmap 占用的页**计入 RSS**，大文件映射要留意容器内存 limit。应用层（mspan / size class / mheap）的分配细节见 [../go/内存分配器.md](../go/内存分配器.md)。
## 七、使用二：Java

### 堆内 vs 堆外

| | 堆内 `HeapByteBuffer` | ⭐ 堆外 `DirectByteBuffer` | ⭐ `MappedByteBuffer` |
|---|---|---|---|
| 分配 | `ByteBuffer.allocate(n)` | `ByteBuffer.allocateDirect(n)` | `FileChannel.map(...)` |
| 位置 | JVM 堆内 | **堆外本地内存**（malloc / mmap） | **mmap 映射的文件** |
| 受 GC 管理 | ✅ | ⚠️ **间接受**：靠 `Cleaner` 在 GC 时才释放，**不及时** | 同左，靠 `Cleaner` 触发 unmap |
| 上限 | `-Xmx` | ⚠️ `-XX:MaxDirectMemorySize`（默认≈Xmx） | 虚拟地址空间与文件大小 |
| 用途 / ⚠️ 风险 | 一般业务 / GC 压力 | **NIO 读写**（省一次堆内→堆外拷贝）/ **堆外泄漏：RSS 涨但堆 dump 看不出来** | 大文件随机读写、零拷贝 / 映射区不释放；磁盘满导致 SIGBUS |

```java
import java.nio.ByteBuffer;

// 堆外：RSS 会涨，但 JVM 堆监控完全看不到
ByteBuffer direct = ByteBuffer.allocateDirect(64 * 1024 * 1024);
direct.put("hello".getBytes());
direct.flip(); // ⚠️ 无显式 free()，依赖 GC 触发 Cleaner；建议池化 + 限 MaxDirectMemorySize
```

### `FileChannel.map` 的 mmap 示例 + `force()`

```java
import java.nio.ByteBuffer;
import java.nio.MappedByteBuffer;
import java.nio.channels.FileChannel;
import java.nio.charset.StandardCharsets;
import java.nio.file.*;

public class MmapDemo {
    public static void main(String[] args) throws Exception {
        Path p = Paths.get("data.bin");
        // mmap 映射文件；force() ⭐ 等价 msync，强制刷盘
        try (FileChannel ch = FileChannel.open(p, StandardOpenOption.CREATE,
                StandardOpenOption.READ, StandardOpenOption.WRITE)) {
            MappedByteBuffer buf = ch.map(FileChannel.MapMode.READ_WRITE, 0, 4096);
            buf.put("hello mmap".getBytes(StandardCharsets.UTF_8));
            buf.force();
        }
        // 普通写 + 落盘：force(true) ⭐ 连元数据一起刷，等价 fsync
        try (FileChannel ch = FileChannel.open(p, StandardOpenOption.WRITE,
                StandardOpenOption.APPEND)) {
            ch.write(ByteBuffer.wrap("hello\n".getBytes(StandardCharsets.UTF_8)));
            ch.force(true);
        }
    }
}
```

### JVM 与 OS 内存：为什么 RSS > Xmx

| 组成 | 说明 |
|---|---|
| Java 堆 | `-Xms` ~ `-Xmx`，受 GC 管理；⚠️ `-Xmx` **只限制这一块** |
| ⭐ **元空间 Metaspace** | 类元数据（`-XX:MaxMetaspaceSize` 默认不限，⚠️ 动态类加载会一直涨） |
| ⭐ **线程栈** | 每线程一份（`-Xss` 默认 1MB）；**线程数 × Xss**，1000 线程就是 ~1GB |
| ⭐ **直接内存 / GC 开销** | `DirectByteBuffer`（`-XX:MaxDirectMemorySize`）；G1/ZGC 的 remembered set、标记位图 |
| **Code Cache / JNI** | JIT 本地代码（`-XX:ReservedCodeCacheSize`）、第三方 so、Netty |

⚠️ 容器里**绝不能按 `Xmx == limit` 规划**，要给堆外留 25%~40% 余量，否则会被 cgroup OOM 杀掉。
## 八、生产实践与坑

### ⚠️ 容器里的内存限制与 OOM

| 坑 | 说明 |
|---|---|
| ⚠️ **容器被杀往往是超过自己的 limit，而非宿主机内存不足** | cgroup 的 `memory.max` 一旦触及，**该容器内进程被 OOM Killer 选中**，即使宿主机还有几十 GB 空闲。表现：`exit code 137`、`dmesg` 里 `Memory cgroup out of memory` |
| ⚠️ **容器内 `free` 看到的是宿主机内存** | ⚠️ **经典坑**：`free` / `/proc/meminfo` 在老内核（cgroup v1 未适配）**不做 cgroup 感知**。判断自身用量要看 `/sys/fs/cgroup/memory.max`（v2；v1 为 `memory.limit_in_bytes`）与 `memory.current`（v1 为 `memory.usage_in_bytes`） |
| **Go / JVM 不感知 cgroup（旧版本）** | Go < 1.19 的 `GOMAXPROCS` 与 GC 目标按宿主机算，在容器里"胆子太大"易被杀，可用 `automaxprocs`；JDK 8u191+/11+ 才默认开 `UseContainerSupport`。⭐ **`GOMEMLIMIT`（Go 1.19+）**是软限制，接近时 GC 更激进，**主动避免被 cgroup 杀**，建议设为 limit 的 80%~90% |

### ⚠️ inode 耗尽：磁盘没满却写不进去

```bash
df -h      # 空间还剩 40%  → 看起来没问题
df -i      # IUse% = 100%  → ⭐ 真凶
```

- 现象：`No space left on device`，但 `df -h` 还有空间；原因：**海量小文件**（日志碎片、缓存目录、容器镜像层、`/tmp`）。
- 定位：`for d in /*; do echo $(find $d -xdev -type f | wc -l) $d; done | sort -rn | head`；处理：清理小文件（⚠️ 目录内文件极多时 `rm -rf` 非常慢，可先 `mv` 走再慢慢删），根治是**重新格式化调大 inode 数**或改用 **XFS**（动态分配 inode）。

### ⚠️ 删除文件后空间未释放
`rm` 只是解除目录项。**只要有进程还持有该文件的 fd，数据块就不会释放**，`df` 也看不出空间回来。

```bash
lsof +L1                  # ⭐ 已删除但仍被占用的文件（deleted 标记）
lsof | grep -i deleted    # 同上，全量扫
```

| 场景与处理 | 日志被 `rm` 但进程还在写 → ⚠️ 正确做法是 **`> app.log`（截断清空、保留 inode）**，进程无需重启；必须回收则停掉持有 fd 的进程或在程序里 `close`（容器内 `rm` 大日志，宿主机 `df` 不会降） |

## 九、面试官会追问什么

1. **虚拟内存有什么用？** → 隔离（每进程独立地址空间）、简化链接与加载、**超售 + 延迟分配**（malloc 不立刻拿物理页）、支持内存映射文件与共享内存。核心是**"让进程以为自己独占一整块连续内存"**。
2. **页表与 TLB 是什么？为什么需要 TLB？** → 页表是 VA→PA 的多级映射表（x86-64 4~5 级）；TLB 是**页表的高速缓存**。多级页表意味着一次转换要多次访存，TLB 命中则一次完成，⭐ **TLB miss 是进程切换的隐性成本**，大页可减少 TLB 条目数。
3. **缺页中断有哪两种？** → **minor fault**：页已在物理内存、只是没建映射（首次写 malloc 的内存、COW），不读盘；**major fault**：页不在内存，须从磁盘/swap 读入，代价高 3 个数量级。
4. **伙伴系统和 Slab 分别解决什么问题？** → 伙伴系统按 2^order 连续页管理、分裂与合并，**解决外部碎片**；Slab/Slub 把页切成同规格对象池，**解决内部碎片并加速小对象分配**。类比：Buddy 批发整页，Slab 零售小件。
5. ⭐ **buffer 和 cache 有什么区别？** → 历史上 Cache 缓存**文件内容**（以页为单位）、Buffer 缓存**块设备裸块**；⚠️ **现代 Linux 两者已统一**，Buffer Cache 并入 Page Cache，`free` 里 `buff` 主要体现块设备元数据缓存。
6. ⭐ **为什么 `free` 显示内存用完了但系统不卡？** → 空闲内存被内核拿来做了 **Page Cache**，⚠️ **这部分随时可回收**。要看 `available` 而非 `free`；只有 `available` 很小、swap 持续增长、`si/so` 长期非 0 才是真紧张。
7. **inode 是什么、存什么？硬链接和软链接的区别？** → inode 存文件元数据（类型、权限、大小、**链接数**、时间戳、**数据块指针**），⚠️ 不存文件名与内容；硬链接**同 inode**、不能跨 fs、删源文件后仍可用、不能对目录创建，软链接是**独立 inode**、可跨 fs、源文件删除后失效、可对目录创建。
8. ⭐ **`write()` 返回成功数据就落盘了吗？** → ❌ 没有。`write` 只把数据拷进**页缓存**就返回，页被标脏后由内核异步回写。必须调用 **`fsync` / `fdatasync`**（mmap 用 `msync`）并等其返回 0，才保证断电不丢。
