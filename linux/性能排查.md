# Linux 性能排查

> 一句话说明本文件覆盖什么：线上「卡、慢、崩」时，如何**不靠猜、按章法**定位到进程、线程和代码行

## 一、排查方法论（先有章法，再谈命令）

> 性能排查最大的坑是「凭感觉调」：先改配置、再重启，问题消失了但不知道为什么。正确顺序是**先量化指标 → 再分层定位 → 最后才是改动**。

### 1.1 USE 方法：适用于资源类（CPU / 内存 / 磁盘 / 网卡）

对每个资源依次问三个问题（Brendan Gregg 提出）：

| 维度 | 含义 | 典型指标 |
|---|---|---|
| **U**tilization 使用率 | 资源有多忙（时间占比） | CPU 使用率、磁盘 `%util`、网卡带宽占用 |
| **S**aturation 饱和度 | 排队有多长（超额申请的量） | 运行队列长度、平均负载、`await`、swap 使用量 |
| **E**rrors 错误数 | 出错事件 | 网络重传、TCP 丢包、IO 错误、`dmesg` 里的 OOM |

⚠️ **使用率 100% 不等于饱和**，饱和度才代表「真的忙不过来，请求在排队」。典型例子：SSD 的 `%util` 100% 但 `await` 很低，只是并行度高、并没有排队（见第五节）。

### 1.2 RED 方法：适用于服务类（接口 / 微服务）

| 维度 | 含义 |
|---|---|
| **R**ate 请求量 | 每秒请求数（QPS） |
| **E**rrors 错误数 | 每秒失败数（区分 4xx/5xx/超时） |
| **D**uration 耗时 | 每个请求的耗时分布（**看 P99，不要只看平均值**） |

> USE 看「我的机器怎么了」，RED 看「我的用户感受到了什么」。线上一般是 RED 指标先告警，再用 USE 往下钻到资源层。

### 1.3 分层排查顺序 ⭐

| 步骤 | 做什么 | 用什么 |
|---|---|---|
| ① 看整体 | 判断是哪一类资源出问题 | `uptime` / `top` / `vmstat` |
| ② 分资源 | CPU、内存、磁盘 IO、网络四选一（用 USE 逐项过） | `mpstat` / `free` / `iostat` / `sar -n` |
| ③ 定进程 | 找出是哪个进程 | `pidstat` / `iotop` / `ss` |
| ④ 定线程与代码 | 定位到具体线程和代码行 | `top -Hp` + `jstack`、`pprof` |

⚠️ **不要在第①步就开 `strace`/`tcpdump`**——它们是精确定位工具，全局抓取会把机器压垮，必须先缩小范围再抓。

## 二、总览：三条命令定方向 ⭐

```bash

uptime          # 平均负载
top             # 整体资源 + 进程占用（htop 更好看）
vmstat 1        # 每秒采样：进程、内存、swap、IO、系统、CPU
```

### 2.1 `uptime` 与平均负载

```bash

$ uptime
 14:32:10 up 30 days,  4:12,  3 users,  load average: 4.20, 3.85, 2.10
```

> **平均负载 = 单位时间内，处于「可运行状态（R）」+「不可中断睡眠状态（D）」的进程平均数**
> （三个值分别是 1 / 5 / 15 分钟）

⚠️ 两个易错点：① 平均负载**不是** CPU 使用率，它统计的是进程数，**包含等 IO（D 状态）和等锁的进程**；② 判断标准要看 **CPU 核数**：`nproc` 为 4 时，负载 4 表示刚好跑满，负载 8 表示有一半在排队。

### 2.2 ⭐ 负载高但 CPU 使用率低 = 什么情况（高频考点）

| 现象 | 说明 |
|---|---|
| **负载高 + `wa` 高** | 大量进程阻塞在 **磁盘 IO**（D 状态） |
| **负载高 + `sy` 高/上下文切换多** | 线程数过多或**锁竞争激烈**，进程在疯狂被调度却干不了活 |
| **负载高 + CPU 空闲 + `st` 高** | **虚拟机被宿主机抢走了 CPU**（`st` = steal time） |

排查口诀：**负载高先看 `wa`，`wa` 高走 IO 排查；`wa` 低而 `sy` 高，走上下文切换排查。**

### 2.3 `vmstat 1` 各列速读

```bash

$ vmstat 1
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
 4  2      0 204800 102400 1536000    0    0   200  1500 3200 8500 30 15 40 15  0
```

| 列 | 含义 | 关注点 |
|---|---|---|
| `r` | **运行队列长度**（正在跑 + 等 CPU） | 持续 > CPU 核数 = CPU 饱和 |
| `b` | **不可中断睡眠**（等 IO）的进程数 | `b` 高 = IO 有瓶颈 |
| `si/so` | swap 换入/换出（KB/s） | 非 0 = 内存不足开始换页，性能会雪崩 |
| `bi/bo` | 块设备读/写（块/s） | 配合 `iostat` 看 |
| `in` | 每秒中断数 | 突增可能是网卡/硬件问题 |
| `cs` | **每秒上下文切换次数** | 见第三节「上下文切换」 |
| `us/sy/id/wa/st` | CPU 时间占比 | 见第三节 |

## 三、CPU 排查

### 3.1 CPU 各列含义（`top` 第三行 / `mpstat`）

| 列 | 含义 |
|---|---|
| `us` | **用户态**（应用程序）占用 |
| `sy` | **内核态**（系统调用、上下文切换、中断处理）占用 |
| `ni` | 被 `nice` 调整过优先级的进程占用 |
| `id` | **空闲** |
| `wa` | ⚠️ **iowait**——CPU 空闲但**有进程在等 IO** 的时间占比 |
| `hi` / `si` | 硬中断 / 软中断（网卡收发包、`ksoftirqd` 走 `si`） |
| `st` | ⚠️ **steal**——虚拟机想用 CPU 但**被宿主机（其他租户）占用**的时间 |

⚠️ **`wa` 高的真相**：CPU 其实很闲，只是进程在等 IO，**瓶颈在磁盘/网络，不在 CPU**，升级 CPU 毫无用处。
⚠️ **`st` 高的处理**：这是**宿主机超卖**（其他租户抢 CPU），本机改不了，只能迁移/扩容。

### 3.2 常用命令

```bash

top -Hp <pid>          # 线程级 CPU（-H 展开线程）
mpstat -P ALL 1        # 每颗 CPU 分别看 —— 判断是否是单核打满、其他核闲置
pidstat -u 1 -p <pid>  # 进程级 CPU，可区分 %usr / %system / %guest
sar -q 1               # 运行队列长度与平均负载历史（runq-sz、plist-sz、ldavg-1/5/15）
sar -u 1 3             # 取样 3 次，看 CPU 各列占比
```

⚠️ 单核打满常见于：**单线程死循环、GC 单线程、绑核不合理**；`mpstat -P ALL` 一眼看出。

### 3.3 上下文切换

```bash

vmstat 1               # 看 cs 列
pidstat -w 1           # 每个进程的 cswch/s（自愿）与 nvcswch/s（非自愿）
pidstat -wt 1 -p <pid> # 细化到线程
```

| 类型 | 含义 | 说明什么问题 |
|---|---|---|
| **自愿切换**（cswch/s） | 进程**主动让出** CPU（等 IO、等锁、`sleep`） | 多 = 大量 IO 或**锁竞争** |
| **非自愿切换**（nvcswch/s） | 时间片用完**被强制抢占** | 多 = **CPU 是真的不够用**（线程数 > 核数） |

> 经验值：`cs` 超过 **几万/秒**就要警惕；切换本身要保存/恢复寄存器、冲刷 TLB 和 cache，是纯损耗。

### 3.4 ⭐ 套路：CPU 飙高的完整流程

```bash

top                       # ① 找进程，记下 PID（假设 12345）
top -Hp 12345             # ② 找线程（-H 展开），记下 TID（假设 12350，十进制）
printf '%x\n' 12350       # ③ 转十六进制 → 303e（⚠️ 栈里 nid 是十六进制，最易忘）
jstack 12345 | grep -A 30 'nid=0x303e'    # ④ 抓线程栈并比对（Go 走 pprof，见第七节）
```

## 四、内存排查

### 4.1 `free` 输出解读

```bash

$ free -h
              total        used        free      shared  buff/cache   available
Mem:           7.7G        3.1G        512M        200M        4.1G        4.0G
Swap:          2.0G        300M        1.7G
```

| 字段 | 含义 |
|---|---|
| `free` | ⚠️ **完全没被使用的内存**，通常很小，看着像「内存不够」其实是假象 |
| `buff/cache` | **buffer（块设备缓存）+ cache（文件页缓存）**，内存紧张时可被回收 |
| `available` | ⭐ **真正可用的内存** = `free` + 可回收的 `buff/cache`，**看这个判断内存是否够** |

> **buffer 与 cache 的区别**（高频题）：
> `buffer` 是**块设备的读写缓冲**（写磁盘前的暂存，偏元数据/裸块）；
> `cache` 是**文件系统的页缓存**（读文件后缓存的内容，加速下次读）。

```bash

echo 3 > /proc/sys/vm/drop_caches   # ⚠️ 仅调试用：手动回收页缓存，生产慎用（会造成 IO 抖动）
```

### 4.2 OOM Killer

> 内存耗尽时，内核按 **`oom_score`**（主要看进程占用内存比例 + `/proc/<pid>/oom_score_adj`）挑一个进程 **直接 kill -9**，没有商量的余地。

```bash

dmesg | grep -i 'out of memory'      # 最直接的证据
grep -i 'killed process' /var/log/messages
journalctl -k | grep -i oom          # systemd 系统
cat /proc/<pid>/oom_score            # 查看某进程的 OOM 打分
```

日志里能看到 `Killed process 12345 (java) total-vm:... anon-rss:...`，⚠️ **被 kill 的往往不是「罪魁」而是「个头最大的那个」**，MySQL/Java 经常背锅。

### 4.3 内存泄漏怎么判断

```bash

sar -r 1            # 系统级：kbmemfree / kbmemused / %memused / kbbuffers / kbcached 趋势
pidstat -r 1 -p <pid>   # 进程级 RSS 变化
pmap -x <pid>       # 进程内存映射明细，看是哪一段（堆？mmap？共享库）在涨
watch -n 5 'ps -o rss= -p <pid>'    # 持续观察 RSS
```

| 现象 | 结论 |
|---|---|
| RSS **持续单调增长**，且 Full GC / 手动回收后不回落 | 泄漏嫌疑 |
| RSS 涨到某个平台后稳定 | 只是缓存预热，**不是泄漏** |
| `si/so` 长期非 0、swap 使用率上升 | **内存不足**，性能会断崖式下降 |

⚠️ **swap 使用率高意味着什么**：进程的热点数据被换出到磁盘，一次访问从 **纳秒级变成毫秒级**，表现为「机器没死但慢得要命」。此时应查内存占用大头，**不要简单调大 swap 掩盖问题**。

## 五、磁盘 / IO 排查

### 5.1 `iostat` 关键列

```bash

iostat -x 1          # -x 扩展统计，1 秒一次
iostat -x -d /dev/vda 1
```

| 列 | 含义 |
|---|---|
| `r/s` + `w/s` | 每秒读写请求数（**IOPS**） |
| `rkB/s` + `wkB/s` | 每秒读写吞吐量 |
| `r_await` / `w_await` | ⭐ 读/写请求的**平均等待时间（ms）**，含排队 + 服务时间 |
| `await` | 总的平均等待时间 |
| `svctm` | 设备**服务时间**（⚠️ 新版本 sysstat 已废弃，不可信） |
| `%util` | 设备**有 IO 请求在处理的**时间占比 |

⚠️ **坑：`%util` 高 ≠ 磁盘饱和**。`%util` 只统计「设备是否忙碌」的时间，**SSD 和 RAID 能并行处理多个请求**，因此 `%util` 轻松到 100% 但 `await` 只有 2ms——**并没有排队**。

⭐ **判断磁盘是否真的饱和，看 `await` 和队列长度（`aqu-sz`）**：机械盘 `await > 20ms`、SSD `await > 几 ms` 且 `aqu-sz` 持续大于 1，才算排队了。

### 5.2 定位到进程

```bash

iotop -o            # 只看真正在做 IO 的进程（需要 root / CONFIG_TASKSTATS）
pidstat -d 1        # 每个进程的 kB_rd/s、kB_wr/s、iodelay
lsof -p <pid>       # 这个进程到底在读写哪些文件
```

### 5.3 磁盘满 / inode 满

```bash

df -h               # 看块空间（No space left on device）
df -i               # ⚠️ 看 inode —— 空间没满但写不进去，八成是 inode 耗尽
du -sh *            # 逐层找大目录
du -sh * | sort -rh | head -20
```

⚠️ **典型坑：文件已删但空间没释放**——进程还持有已删除文件的 fd，磁盘块不会被释放
（日志切割 `rm app.log` 后进程仍往旧 fd 写，磁盘一路涨满但 `du` 看不到文件）：

```bash

lsof | grep deleted      # 或 lsof +L1
# 解决：重启该进程，或 > /proc/<pid>/fd/<fdnum> 截断（⚠️ 确认安全再操作）
```

## 六、网络排查

### 6.1 总览与流量

```bash

ss -s               # ⭐ 连接数总览（总 socket、TCP 各状态分布）
netstat -s          # 协议级统计：重传、丢包、监听队列溢出
sar -n DEV 1        # 每个网卡的 rxkB/s、txkB/s、pps —— 打满带宽/包量一眼看出
sar -n TCP,ETCP 1   # ⭐ active/s passive/s、retrans/s（重传）、isegerr/s
iftop -i eth0       # 实时看「谁在跟谁通信、占多少带宽」
```

| 指标 | 健康参考 |
|---|---|
| 重传率（`retrans/s` ÷ `seg/s`） | ⭐ **> 1% 就要查**（丢包、链路拥塞、对端处理慢） |
| 连接数 | 突增可能是**攻击、重试风暴、下游不可用导致堆积** |
| 带宽/包量 | 接近网卡上限 = 瓶颈 |

### 6.2 连接状态分布

```bash

ss -ant | awk '{print $1}' | sort | uniq -c | sort -rn
ss -ant state close-wait | head     # 直接筛 CLOSE_WAIT
ss -ant state time-wait | wc -l     # 统计 TIME_WAIT
```

| 状态堆积 | 原因 |
|---|---|
| ⚠️ **CLOSE_WAIT** | **被动关闭方没调 `close()`** → 应用有 bug（HTTP 连接池未释放、`defer resp.Body.Close()` 漏写）。**这是应用问题，调内核参数没用** |
| **TIME_WAIT** | 主动关闭方的正常状态（2MSL）。量大时可开 `tcp_tw_reuse`、用长连接/连接池，**一般不需处理** |
| **SYN_RECV** | SYN 洪泛或半连接队列被打满 |

```bash

# tcpdump 极简用法（⚠️ 一定先限定 host/port，避免抓爆机器）
tcpdump -i eth0 -nn host 10.0.0.1 and port 8080 -c 100            # 抓 100 个包看现象
tcpdump -i eth0 -nn -w /tmp/p.pcap port 3306                      # 存盘，事后用 Wireshark 分析
```

## 七、使用一：Go 服务的排查 ⭐

### 7.1 开启 pprof

```go

import _ "net/http/pprof"   // 副作用导入：自动向 DefaultServeMux 注册 /debug/pprof/*

func main() {
    // 建议单独监听端口，不要和业务端口混在一起暴露到公网
    go func() { log.Println(http.ListenAndServe("127.0.0.1:6060", nil)) }()
    // ...业务服务
}
```

> 若用了自定义 `ServeMux`（如 gin），需手动注册 `pprof.Index` 等 handler，或另起一个 `http.ServeMux`。

### 7.2 各端点说明 ⭐

| 端点 | 用途 |
|---|---|
| `/debug/pprof/goroutine?debug=2` | ⭐ **所有 goroutine 的完整栈**——查协程泄漏首选 |
| `/debug/pprof/heap` | 堆内存分配（默认 `inuse_space`；`?gc=1` 先 GC 再看） |
| `/debug/pprof/profile?seconds=30` | ⭐ **CPU profile**，采样 30 秒，查 CPU 飙高 |
| `/debug/pprof/block` | **阻塞**在 channel / select / sync 上的时长（需 `runtime.SetBlockProfileRate(1)`） |
| `/debug/pprof/mutex` | **锁竞争**（需 `runtime.SetMutexProfileFraction(1)`） |
| `/debug/pprof/allocs` | 历史累计分配，看「分配热点」 |
| `/debug/pprof/threadcreate` | 操作系统线程创建情况 |

### 7.3 分析：top 与火焰图

```bash

# CPU 采样 30 秒后进入交互式（top=flat 自身耗时，top -cum=含调用链累计，list FuncName=逐行，web=调用图）
go tool pprof 'http://127.0.0.1:6060/debug/pprof/profile?seconds=30'
go tool pprof -http=:8080 'http://127.0.0.1:6060/debug/pprof/profile?seconds=30'  # 火焰图：起本地 Web UI
go tool pprof -http=:8080 http://127.0.0.1:6060/debug/pprof/heap     # 内存同理
```

> 火焰图读法：**看最宽的「平顶」**，宽度 = 采样占比，越宽越耗时；上层是调用者，下层是被调者。

### 7.4 goroutine 泄漏定位 ⭐

```bash

curl 'http://127.0.0.1:6060/debug/pprof/goroutine?debug=2' > g.txt
# 按栈首行聚合，看哪一类 goroutine 在堆积
grep -oP '^goroutine \d+ \[.*\]:' g.txt | awk '{print $3}' | sort | uniq -c | sort -rn
```

同样状态（如大量 `[chan receive]` / `[IO wait]`）的 goroutine 数**只增不减**，且栈顶都指向同一处 → 就是泄漏点（channel 没人读、HTTP 连接没超时、`time.Ticker` 没 Stop）。

代码侧监控（`import _ "expvar"` 后指标自动暴露在 **`/debug/vars`**）：

```go

var gNum = expvar.NewInt("goroutines")            // /debug/vars 里可见
expvar.Publish("heap_inuse", expvar.Func(func() any {
    var ms runtime.MemStats
    runtime.ReadMemStats(&ms)                     // MemStats：HeapInuse/HeapAlloc/NumGC
    return ms.HeapInuse
}))
// 定时把 runtime.NumGoroutine() 上报到 Prometheus，配「持续增长」告警
```

> 详细泄漏与死锁案例见 [../go/协程泄漏与死锁.md](../go/协程泄漏与死锁.md)。

## 八、使用二：Java 服务的排查 ⭐

> Linux 侧只做一件事：**把「哪个线程吃 CPU」和「这个线程在跑什么代码」对上**。
> JVM 参数与 GC 详解见 [../java/JVM与垃圾回收.md](../java/JVM与垃圾回收.md)。

### 8.1 ⭐ 核心套路：`top -Hp` → 转十六进制 → `jstack`

```bash

jps -l                     # ① 找 Java 进程（也可用 top）
top -Hp 12345              # ② 找线程，假设最耗 CPU 的 TID = 12350（十进制）
printf '%x\n' 12350        # ③ ⚠️ 转十六进制 → 303e（最容易忘的一步）
jstack -l 12345 > /tmp/stack.txt
grep -A 30 -i 'nid=0x303e' /tmp/stack.txt    # ④ 栈里 nid 是十六进制
```

⚠️ **注意**：`jstack` 的 `nid` 是**十六进制**，`top -H` 给的是十进制，不转换**永远 grep 不到**。
建议连抓 3 次栈（`for i in 1 2 3; do jstack 12345 > s$i.txt; sleep 2; done`），
同一线程 3 次都停在同一行，才是真凶（一次抓栈可能抓到「刚好在跑」的假象）。

### 8.2 其他配合命令

```bash

jstack 12345 | grep -A 5 'deadlock'        # 死锁检测（jstack 会自动打印 Found one Java-level deadlock）
jstack 12345 | grep 'Thread.State' | sort | uniq -c | sort -rn             # 线程状态分布
jstat -gcutil 12345 1000                   # 每秒看 GC：YGC/YGCT/FGC/FGCT/O 区占比
jstat -gccapacity 12345                    # 各代容量
jmap -histo:live 12345 | head -30          # ⭐ 对象数量与占用（-histo 不触发 Full GC 可用；:live 会触发）
jmap -dump:format=b,file=/tmp/heap.hprof 12345   # ⚠️ 会 STW，生产慎用，之后用 MAT 看支配树
```

| 现象 | 说明 |
|---|---|
| `FGC` 频繁且 `FGCT` 大 | 老年代放不下 → 内存泄漏或堆太小 |
| `jstack` 里大量 `BLOCKED` | 锁竞争；看 `waiting to lock <0x...>` 的地址找持锁线程 |
| 大量 `WAITING (on object monitor)` 在线程池 | 线程池打满，下游慢 |

| 现象 | 可能原因 | 先看什么 | 定位命令 |
|---|---|---|---|
| **CPU 使用率高** | 死循环、正则回溯、频繁 GC、序列化热点 | `us` 高还是 `sy` 高 | `top` → `top -Hp <pid>` → `printf '%x'` → `jstack` / `go tool pprof profile` |

| **磁盘写不进去（空间有）** | ⚠️ **inode 耗尽**、文件已删仍被占用 | `df -i` | `df -i`、`du -sh *`、`lsof \| grep deleted` |
| **磁盘满** | 日志暴涨、临时文件、core dump | `df -h` | `df -h` → `du -sh * \| sort -rh \| head` |
| **连接数暴涨** | 重试风暴、爬虫/攻击、下游不可用导致堆积 | `ss -s`、重传率 | `ss -s`、`ss -ant \| awk '{print $1}' \| sort \| uniq -c`、`sar -n TCP 1` |

## 十、面试官会追问什么

1. **平均负载高但 CPU 使用率低，是什么原因？** → 负载统计的是 **R + D 状态进程数**，`D` 为**不可中断睡眠**（等磁盘 IO / 等锁），所以磁盘慢、NFS 卡死、锁竞争都会让负载升高而 CPU 空闲。排查：`vmstat 1` 看 `b` 与 `wa`，`b` 高走 `iostat -x`，`wa` 低而 `sy` 高走 `pidstat -w`。
2. **`free` 里 buffer 和 cache 有什么区别？`free` 很小却说内存够？** → buffer 是块设备缓冲、cache 是文件页缓存，**都能在内存紧张时回收**；`available = free + 可回收部分`，**要看 `available` 而不是 `free`**。
3. **iowait 高说明什么？** → CPU 空闲但**有进程在等 IO**，瓶颈在**磁盘/网络**，加 CPU 无用。需再查 `iostat -x` 的 `await`/`aqu-sz` 判断是真饱和还是并行度高。
4. **怎么排查 CPU 飙高的 Java 进程？** → `top` 找 PID → `top -Hp <pid>` 找 TID → **`printf '%x'` 转十六进制** → `jstack` 里 grep `nid=0x...`（连抓 3 次确认）→ 看栈顶方法。
5. **`%util` 到 100% 是不是磁盘就饱和了？** → 不一定。`%util` 只表示「设备一直在处理请求」，**SSD/RAID 可并行**所以 100% 是常态；要看 **`await`（等待时长）和 `aqu-sz`（队列长度）** 才知是否真排队。
6. **磁盘空间没满但写不进去怎么办？** → ① **inode 耗尽**（`df -i`，海量小文件）；② **文件已删但仍被进程持有**（`lsof | grep deleted`，重启进程或截断 fd）；③ 磁盘配额（quota）或只读挂载。
7. **CLOSE_WAIT 很多是什么原因？** → 被动关闭方**收到对端 FIN 但自己没发 FIN**，即**应用没调 `close()`**（连接池未释放、漏 `defer resp.Body.Close()`）。**这是应用 bug，调内核参数解决不了**；TIME_WAIT 多才是可调参的正常现象。
8. **系统开始用 swap 意味着什么？怎么处理？** → 物理内存不足，热点数据被换出，**延迟从纳秒级变毫秒级**，表现为「没死但极慢」。处理：查谁在吃内存（`pidstat -r`、`ps --sort=-rss`）并治理，**不要靠加大 swap 掩盖**，可调低 `vm.swappiness`。
9. **上下文切换多一定是坏事吗？怎么区分？** → 看 `pidstat -w`：**自愿切换多**（cswch）→ 等 IO / 等锁；**非自愿切换多**（nvcswch）→ CPU 核数不够、线程太多。
