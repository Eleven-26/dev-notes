## 一、进程是什么？有哪些状态？上下文切换是怎么回事？

**来源**：`p=48` 小鹏后台开发实习面试 · 时长 10分45秒
**考察意图**：这是**为"进程与线程的区别"打基础**的一题（三点答法见本文第三节）。

### 一、进程的定义

> **进程 = 应用程序运行的实例（运行实力）**，
> 同时也是**操作系统进行资源分配的基本单位**。

**怎么理解"运行实例"**（按顺序推演）：

```text
写代码（人类可读）
   ↓ 编译（转成机器可读）
可执行二进制文件（应用程序）
   ↓ 执行
进程 ← 应用程序的运行实例
```

**为什么说是"资源分配的基本单位"**：
> 进程启动后，操作系统会为它**分配独立的内存空间**；
> 进程活动时会**占用一定的 CPU**。

### 二、进程的四个特点

| 特点 | 说明 |
|---|---|
| **① 独立性** | **每个进程有独立的内存空间**，互不干扰——<br>A 进程修改自己的内存**不会导致 B 进程异常** |
| **② 并发性** | 多个进程可同时运行，**通过时间片轮转实现并发**。⚠️ 注意：<br>**进程是资源分配的基本单位，线程才是 CPU 调度的基本单位**；<br>不特别说明时进程只有一个主线程，所以时间片轮转本质是**对线程的 CPU 时间片轮转**。<br>**进程与线程是包含关系：进程包含一个或多个线程** |
| **③ 动态性** | 可**动态地创建、运行、暂停、终止**（点一下图标就启动，就是一个动态过程） |
| **④ 结构性** | 由三部分组成：**程序段**（代码）+ **数据**（变量等运行所需数据）+ **进程控制块 PCB** |

**PCB（进程控制块）**：内核中 `task_struct` 结构体实例化出来的对象，
保存进程相关的全部信息——

| PCB 保存的内容 |
|---|
| 进程标识符（**PID**，用于标识/查找进程） |
| 进程状态、优先级 |
| 资源分配情况 |
| 程序计数器、寄存器等 **CPU 上下文** |

> **每个进程都有且只有一个 PCB 对象。**

### 三、理解"并发"与"并行"（用图示思路讲）

**并发（单处理器）**：

> 一台机器只有一个处理器，但我们能同时开记事本、浏览器等一堆程序。
> 为什么？因为**应用程序不是每时每刻都需要 CPU**——
> 比如在记事本里打字属于 **IO 输入行为**，此时**CPU 处于空闲**，可以交给其他任务。
>
> **本质：多个任务交替使用同一个 CPU**，让我们"感觉"能开大量应用。

**并行（多处理器）**：

> 有多个处理器、多个任务，**每个任务独占一个处理器同时执行**，
> 这才是**真正的同时进行**，**充分利用多核优势**。

### 四、进程的五个状态与转换

| 转换 | 触发条件 |
|---|---|
| **就绪 → 运行** | 被调度器选中，分配到 CPU |
| **运行 → 就绪** | **时间片用完且任务未完成**，回到就绪队列等下一轮分配 |
| **运行 → 阻塞** | 需要**等待某个事件**（如等待键盘输入、等待 IO 返回） |
| **阻塞 → 就绪** | 事件完成。⚠️ **不是直接回到运行态**——<br>而是回到就绪队列**等待下一次被调度**。<br>原因：事件（键盘输入）很慢，而 CPU 调度相对快得多，所以需要重新排队 |
| **运行 → 结束** | 任务成功执行完毕 |

（另有**挂起状态**。）

### 五、进程控制与上下文切换

**两个队列**（与状态对应，通常用**链表**实现，便于插入删除）：

| 队列 | 内容 |
|---|---|
| **就绪队列** | 已就绪、等待 CPU 的进程 |
| **阻塞队列** | 正在等待事件的进程 |

> **单核机器只有一个运行指针；多核机器有多个**。
> 进程就绪后进入就绪队列；运行时把 PCB 交给运行指针；
> 遇到阻塞就移入阻塞队列；事件完成后再回到就绪队列等下一次调度。

**上下文切换（Context Switch）到底是什么**：

> CPU 时间片用完，当前进程**不能再继续执行**，需要把 CPU 交给其他进程。
> 但当前进程**任务还没完成**，所以必须：

```text
① 保存当前进程的上下文（CPU 寄存器等）→ 写回它自己的 PCB
② 从下一个进程的 PCB 中加载上下文
③ 从上次被中断的位置继续执行
```

**为什么要保存上下文**：
> 因为交出 CPU 时进程**并没有完成任务**，必须把"当时执行到哪儿、寄存器是什么值"记下来，
> 下次被调度时才能**还原当时的现场、继续往下跑**。

### 面试官会追问什么

- **进程切换的代价在哪里？** → **保存/恢复上下文 + 缓存失效**（TLB、CPU cache 需要重新填充），
  所以进程切换比线程切换更贵。
- **僵尸进程和孤儿进程？** → 子进程已退出但父进程未回收（`wait`）→ 僵尸进程（占 PCB）；
  父进程先退出而子进程还在 → 孤儿进程被 init/1 号进程收养。
- **`fork` 后发生什么？** → 复制父进程的 PCB，采用**写时复制（COW）**延迟复制内存页。

## 二、Linux 线程是什么？三种实现方式有什么区别？

**来源**：`p=49` 小鹏后台开发实习面试 · 时长 11分37秒
**考察意图**：考**「为什么 Linux 没有独立的线程概念」**。关键结论是内核用 `clone` / `task_struct` 统一描述进程与线程、两者只是**共享资源不同**；能再对比用户级 / 内核级 / 混合三种实现方式就是完整答案。

### 一、线程的定义

> **线程 = CPU 调度的基本单位**，也是**操作系统能够进行运算调度的最小单位**；
> 是**进程中的一个执行流程（执行单元）**。

**关系要点**：
- 一个进程**可以包含多个线程**；
- 这些线程**共享进程的资源**（内存、打开的文件等）；
- 但**每个线程有自己的上下文**：程序计数器、寄存器、**以及自己的栈空间**。

> **进程分配资源，线程执行计算**——进程要真正对数据进行计算和操作，
> 是由它内部的线程去完成的。

### 二、用户线程与内核线程的三种对应关系

| 关系 | 说明 |
|---|---|
| **多对一** | 多个用户线程对应 1 个内核线程。内核**不知道**这些用户线程的存在，<br>能用多少 CPU **取决于那 1 个内核线程被分配了多少** |
| **一对一** | 用户线程与内核线程一一对应。**内核知道启动了多少线程**，<br>可以直接对线程进行调度 |
| **多对多** | 内核的**哪个 CPU 空闲，就把用户线程放到哪个 CPU 上执行**，<br>**充分利用多核、提高并发性能**。<br>**Go 的 GMP 模型就是这一类的典型**（多个 G 通过 P 协调到多个 M 上执行） |

### 三、三种线程实现方式

#### ① 用户线程

**做法**：在**用户空间**实现，与内核无关——
线程的创建、调度、回收、销毁**完全由用户态的线程库（以及开发者）管理**。
→ 对应上面的"**多对一**"。

| | 说明 |
|---|---|
| **优点** | **轻量级**、**可定制性高**（完全由用户控制）、**跨平台** |
| **缺点** | **无法直接利用多核**；<br>⚠️ **一个线程阻塞，会导致该进程内所有线程都被阻塞** |

**为什么"一个阻塞全阻塞"**：
> 用户空间里一个进程有多个用户线程，但**这个进程只对应一个内核线程**。
> 内核线程**同一时刻只能执行其中一个线程的任务**——
> 一旦某个线程阻塞，**内核线程也随之阻塞**，
> 而此时内核根本不知道还有其他用户线程在等着执行（它看不到它们）。

#### ② 内核线程

**做法**：由**内核**创建和管理，用户线程与内核线程**一对一**。

| | 说明 |
|---|---|
| **优点** | **能充分利用多核**；<br>内核**直接调度**线程，**并发性好**（不会因为一个线程阻塞而拖死全部） |
| **缺点** | 创建/切换**需要内核态参与，开销较大**；<br>调度由内核决定，**灵活性和可定制性不如用户线程**（用户空间可能拿不到某些内核才有的资源） |

#### ③ 轻量级进程（LWP）

**定位**：**介于用户线程与内核线程之间**，说白了就是**综合两者的优点**。

- **LWP 与内核线程是 1:1 的关系**；
- 它在**用户线程与内核线程之间做了一个中间层**，由这个中间层去协调两者；
- **支持多种模式**：`1:1`（一个用户线程对一个 LWP）、`N:1`、`M:N`，
  甚至可以**组合使用**。

> **所以 LWP 的价值在于"可配置"**：
> 根据应用场景选择不同的映射模式——要极致轻量就多路复用到少量 LWP，
> 要充分利用多核就给每个用户线程配一个 LWP。

### 面试官会追问什么

- **Go 的 goroutine 属于哪一种？** → **M:N（多对多）**：
  G（协程，用户态）通过 P 映射到 M（内核线程），
  阻塞的系统调用不会拖死整个进程（P 会被交给其他 M）。
- **线程栈和进程栈的区别？** → 每个线程有**独立的栈**（Go 的 goroutine 初始栈仅 2KB 且可增长），
  但**共享堆**。
- **为什么线程切换比进程切换便宜？** → 线程切换**不需要切换地址空间**（同一进程内共享页表），
  只需切换寄存器和栈，**缓存/TLB 命中率更高**。

## 三、进程与线程的区别是什么？（完整答题结构）

**来源**：`p=51` 小鹏后台开发日常实习面试 · 时长 10分33秒
**考察意图**：这是一道**高频且容易答得零散**的题。
原视频给了一个非常清晰的**三段式答题结构**，照这个讲不会失分。

### 三段式答题结构（先记住骨架）

```text
① 先说对进程/线程的理解 + 两者的关系
② 再说：既然有了进程，为什么还需要线程？（从痛点反推）
③ 最后说：多线程带来了哪些问题？（体现思考的完整性）
```

### 第一段：概念与关系

| | 进程 | 线程 |
|---|---|---|
| **定位** | **资源分配的基本单位** | **CPU 调度的基本单位**、进程内的**执行单元** |
| **资源** | 拥有独立的内存等资源 | **共享所属进程的资源** |

**核心关系**：**包含与被包含**——一个进程可包含多个线程。

**一个容易讲错的点（务必澄清）**：
> 操作系统**调度的是线程，不是进程**。
> 我们平常说"进程调度"，是因为**默认情况下进程里有一个主线程**——
> 即使你没有写多线程代码，进程内部也至少有一个线程。

### 第二段：既然有了进程，为什么还需要线程？

**从"痛点"反推**（这样讲比罗列优点更有说服力）：

| 为什么需要线程 | 说明 |
|---|---|
| **① 更轻量级** | 创建进程要**分配内存、文件、描述符**等；<br>线程是在进程内部、**基于已分配给进程的资源**做再分配，**开销小得多** |
| **② 更高的资源利用率** | **进程无法直接利用多核**——要多核只能**创建多个进程**；<br>线程可以让**多核被高效利用** |
| **③ 更高效的通信** | 线程**共享内存**，线程间通信只需要读写共享内存；<br>而**进程之间相互独立**，进程间通信（IPC）要"调接口"，**成本高得多** |
| **④ 更好的响应、避免阻塞** | 并发/并行处理多个任务，其中**一个线程 IO 阻塞不会影响其他线程执行**。<br>（⚠️ 注意：这与实现方式有关——<br>**用户线程模式下，一个线程阻塞会影响其他线程**） |
| **⑤ 充分利用多核做并行计算** | **一个进程只能在一个 CPU 上运行**；<br>多线程后，调度器**直接调度到线程**，可实现真正的并行 |

### 第三段：多线程会带来哪些问题？（体现深度）

> 多线程虽然带来好处，但**它不是只有优点**。
> 关键在于：**内核和进程已经是一套完整的体系，而"用不用多线程"是开发者自己决定的**——
> **凡是人为决定的东西，就一定会带来人为因素导致的问题。**

| 问题 | 说明 |
|---|---|
| **① 竞态条件** | 多个线程对同一内存操作 → **结果不可预测**。<br>必须加锁/信号量等同步机制，而**人为干预就可能出错**（该加锁的没加） |
| **② 死锁** | 某线程占用了临界区资源却**没有释放**（或释放过程出问题），<br>其他线程访问不了 → **死锁或超时** |
| **③ 资源消耗** | **线程不是越多越好**：少了性能不够，多了性能反而变差。<br>通常**线程数与 CPU 核心数相近**时性能最好——<br>因为线程最终都要靠 CPU 执行，**CPU 不够时起再多线程也没用**。<br>线程数远大于 CPU 数还会导致**频繁上下文切换，产生额外 CPU 开销** |
| **④ 线程安全问题** | 平时一个很简单的操作，在多线程环境下**可能报错或得到不可预测的结果**（对应分册 02 的"非线程安全"专题） |
| **⑤ 调试复杂性** | 单线程调试简单、流程清晰；<br>多线程下问题**难以复现、难以定位** |

### 面试官会追问什么

- **线程数应该怎么定？** → 分场景：**CPU 密集型** ≈ 核数（或核数+1）；
  **IO 密集型**可远大于核数（因为线程大部分时间在等 IO）。
- **协程比线程轻在哪？** → 用户态调度（不陷入内核）、**栈可动态增长**（初始很小）、
  切换只需保存少量寄存器，**不需要切换地址空间**。
- **进程间通信有哪些方式？** → 管道、消息队列、共享内存、信号量、Socket、信号。

> ⭐ 上面这三条"标准答案"里有两条**经不起追问数字**：
> "轻多少倍""核数附近最好"是怎么知道的？下面两章就是**在自己机器上把它们量出来**，
> 并且顺手纠正了两个流传很广的不准确说法。

### 骨架一：跨平台的测量原语（`proc/proc_1.go`）

```go
package proc

import (
	"context"
	"os"
	"os/exec"
	"runtime"
	"sync"
	"sync/atomic"
	"time"
)

// 本册第一节~第三节全是概念（PCB、时间片、上下文切换、线程数怎么定）。
// 这一包把这些说法**变成能在自己机器上量出来的数字**：
//   - "线程创建比进程轻得多"   → 各起 N 个，比耗时
//   - "线程数与核数相近时性能最好" → CPU 密集型 worker 数扫描
//   - "上下文切换有额外开销"   → 乒乓切换的单次成本
//   - "goroutine 初始栈仅 2KB"  → 起一批阻塞协程，量栈内存的跳档
//
// 跨平台部分在 Windows/Linux/macOS 都能跑；
// 依赖 fork/wait、/proc 与信号的部分单独放在 proc_2.go（//go:build unix）。

// BusyN 做 n 轮固定工作量。不依赖时钟，用来做 worker 数扫描：
// 总工作量固定，才能比较"不同并发度下多久做完"。
func BusyN(n int) float64 {
	x := 0.0
	for r := 0; r < n; r++ {
		for i := 0; i < 200000; i++ {
			x += float64(i) * 1.000001
		}
	}
	return x
}

// Scaling 用 g 个 goroutine 分摊 total 份工作量，返回总耗时。
//
// ★ 正文"线程数与 CPU 核心数相近时性能最好"的测法：
// 把 g 从 1 一路扫到 8×核数，看加速比在哪一段**停住**。
// 用 goroutine 测**看不到"开太多反而变慢"**——Go 的调度器会让空闲的 G 主动让出；
// 想看那个效应要用 ScalingOSThreads。
func Scaling(g, total int) time.Duration {
	return runScaled(g, total, false)
}

// ScalingOSThreads 同上，但每个 worker 用 LockOSThread **钉住一个内核线程**。
// 这才是正文说的"线程数远大于 CPU 数"的场景：线程是真存在的，
// 超订之后就要靠内核抢占来轮流上 CPU。
func ScalingOSThreads(g, total int) time.Duration {
	return runScaled(g, total, true)
}

func runScaled(g, total int, pin bool) time.Duration {
	chunk := total/g + 1
	sums := make([]float64, g) // **每个 worker 写自己的格子**
	start := time.Now()
	var wg sync.WaitGroup
	for i := 0; i < g; i++ {
		wg.Add(1)
		go func(i int) {
			defer wg.Done()
			if pin {
				runtime.LockOSThread() // 这个 goroutine 独占一个 M（内核线程）
				defer runtime.UnlockOSThread()
			}
			sums[i] = BusyN(chunk)
		}(i)
	}
	wg.Wait()
	var s float64
	for _, v := range sums {
		s += v
	}
	sink = s
	return time.Since(start)
}

// sink 只在最后收一次，避免 worker 之间争用同一个变量。
var sink float64

// PingPong 量"两个执行流之间切换一次"的成本：一个发、一个回，共 rounds 个来回。
//
// ⚠️ 这测的是**用户态调度 + 唤醒**，不等于内核线程切换的开销
// （后者要陷入内核，量不了这么干净）。
// 但它是"每处理一条消息要在两个执行流之间倒一手"这件事的量级参考。
func PingPong(rounds int) time.Duration {
	a, b := make(chan int), make(chan int)
	go func() {
		for v := range a {
			b <- v
		}
	}()
	start := time.Now()
	for i := 0; i < rounds; i++ {
		a <- i
		<-b
	}
	return time.Since(start)
}

// GoroutineStacks 起 n 个**阻塞**的 goroutine，返回它们的栈占用（字节）。
// 对应正文"goroutine 初始栈仅 2KB 且可增长"——这里量的就是那句话的代价。
//
// ★ 必须等 n 个都真的跑起来再测：只是 `go func()` 提交而未调度时，
//
//	栈可能还没实际分配，测出来会偏小。
//
// withDefer 是**对照组**：如果 StackInuse 随闭包深浅变化，说明量的是真实用量；
// 若不变化（实测就是不变化），说明量到的是栈 span 的**分配粒度**（8KB）。
// 这个对照是必要的——否则会把"8KB/个"错当成"每个协程真的用了 8KB 栈"，
// 也会把正文"初始栈 2KB"讲成精确的内存数字。
func GoroutineStacks(n int, withDefer bool) uint64 {
	gate := make(chan struct{})
	var started atomic.Int64
	var wg sync.WaitGroup

	runtime.GC()
	var base runtime.MemStats
	runtime.ReadMemStats(&base)

	for i := 0; i < n; i++ {
		wg.Add(1)
		if withDefer {
			go func() {
				defer wg.Done()
				defer func() { _ = recover() }() // 对照组：故意多加一层 defer
				started.Add(1)
				<-gate
			}()
			continue
		}
		go func() {
			defer wg.Done()
			started.Add(1)
			<-gate // 全部阻塞在这里，只花栈的内存
		}()
	}
	for int(started.Load()) < n {
		runtime.Gosched()
	}
	runtime.GC()
	var peak runtime.MemStats
	runtime.ReadMemStats(&peak)

	close(gate)
	wg.Wait()
	if peak.StackInuse <= base.StackInuse {
		return 0
	}
	return peak.StackInuse - base.StackInuse
}

// helperMode 标记"我是被当作子进程拉起来的"。
// go test 编译出的二进制本身就是可执行文件，用它跑一次"立刻退出"，
// 就能在**任何平台**测进程创建成本，不依赖 /bin/true 这类 Unix 才有的程序。
const helperMode = "PROC_HELPER_EXIT"

// SpawnProcesses 串行起 n 个子进程并各自等它退出，返回总耗时。
//
// ★ 每次 Wait 都是必需的：**只 Start 不 Wait 就会留下僵尸进程**（正文第一节的追问）：
// 子进程已经退出，但它的退出状态还没被父进程取走，PCB 就一直占着。
// 用 CommandContext 是为了"父进程被取消时顺带 kill 掉子进程"，不留孤儿。
func SpawnProcesses(ctx context.Context, n int) (time.Duration, error) {
	start := time.Now()
	for i := 0; i < n; i++ {
		cmd := exec.CommandContext(ctx, os.Args[0], "-test.run=TestHelperExit", "-test.v=true")
		cmd.Env = append(os.Environ(), helperMode+"=1")
		if err := cmd.Run(); err != nil {
			return time.Since(start), err
		}
	}
	return time.Since(start), nil
}
```

```go
// 在 Windows 上跑不到这些语义，所以本文件的校验方式是交叉编译：
//
//	GOOS=linux go build ./... && GOOS=linux go vet ./proc/
//
// ⚠️ **没有在 Linux 实例上实测过**（本机是 Windows），
// 下面的数字请自己在 Linux 机器上取；**代码里的行为约定（必须 Wait、先 TERM 后 KILL）是通用的**。

// RunChild 起子进程拿输出。**CombinedOutput 内部已经做了 Wait**，
// 所以不会留僵尸——这是最推荐的默认写法。
func RunChild(ctx context.Context, name string, args ...string) (string, error) {
	cmd := exec.CommandContext(ctx, name, args...)
	out, err := cmd.CombinedOutput()
	return string(out), err
}

// SpawnDetached 异步起一个子进程，并**用后台协程兜底 Wait**。
//
// ★ 正文追问"僵尸进程怎么产生"：就是 `cmd.Start()` 之后再也不 `Wait()`——
//
//	子进程退出了，退出状态没人取，内核里的 PCB 一直留着，`ps` 里显示 <defunct>。
//	要么同步 Wait，要么像这样后台 Wait；**不能两者都不做**。
func SpawnDetached(name string, args ...string) (int, error) {
	cmd := exec.Command(name, args...)
	cmd.Stdout, cmd.Stderr = os.Stdout, os.Stderr
	if err := cmd.Start(); err != nil {
		return 0, err
	}
	go func() { _ = cmd.Wait() }() // 回收 = 让内核释放 PCB
	return cmd.Process.Pid, nil
}

// StopGracefully 优雅停子进程：**先 SIGTERM 给它收尾的机会，超时才 SIGKILL**。
//
// 直接 Kill 会丢正在写的数据（子进程可能正在 flush）。
// Go 1.20+ 也可以只设 `cmd.WaitDelay`，让标准库在超时后代劳。
func StopGracefully(cmd *exec.Cmd, grace time.Duration) error {
	if cmd.Process == nil {
		return fmt.Errorf("proc: 子进程还没 Start")
	}
	if err := cmd.Process.Signal(syscall.SIGTERM); err != nil {
		return err
	}
	done := make(chan error, 1)
	go func() { done <- cmd.Wait() }()
	select {
	case err := <-done:
		return err // 正常退出：err 可能是 nil，也可能是它自己的退出码
	case <-time.After(grace):
		_ = cmd.Process.Kill() // SIGKILL：不可捕获、不可忽略，内核直接回收
		return <-done
	}
}

// ContextSwitches 读 /proc/<pid>/status 里的两个计数：
//
//	voluntary_ctxt_switches    ：主动让出（等 IO、等锁、时间片没用完就睡了）
//	nonvoluntary_ctxt_switches ：被动抢占（**时间片用完被赶走** = 正文"运行 → 就绪"）
//
// ★ 这两个数是"上下文切换开销"最直接的证据：
// 一个 CPU 密集型进程如果 nonvoluntary 涨得飞快，说明线程数已经远超可用核数。
// ⚠️ /proc 是 **Linux 专有**（macOS 没有），这段在 macOS 上会返回错误。
func ContextSwitches(pid int) (voluntary, nonvoluntary uint64, err error) {
	f, err := os.Open(fmt.Sprintf("/proc/%d/status", pid))
	if err != nil {
		return 0, 0, err
	}
	defer f.Close()
	sc := bufio.NewScanner(f)
	for sc.Scan() {
		line := sc.Text()
		if !strings.Contains(line, "ctxt_switches") {
			continue
		}
		k, v, ok := strings.Cut(line, ":")
		if !ok {
			continue
		}
		n, err := strconv.ParseUint(strings.TrimSpace(v), 10, 64)
		if err != nil {
			return 0, 0, err
		}
		if strings.HasPrefix(k, "voluntary") {
			voluntary = n
		} else {
			nonvoluntary = n
		}
	}
	return voluntary, nonvoluntary, sc.Err()
}

// Nice 调整优先级（正文"PCB 里保存优先级"的可操作对应物）。
// 需要权限；线上一般用 systemd 的 Nice= 而不是代码里调。
// ⚠️ Linux/macOS 语义不完全一致，未实测。
func Nice(delta int) error { return syscall.Setpriority(syscall.PRIO_PROCESS, 0, delta) }
```

### 实测一：进程 vs 协程的创建成本（对应第三节第二段"① 更轻量级"）

| 执行流 | 单个成本 | 样本量 |
|---|---|---|
| **进程**（起子进程并等它退出） | ≈ **25.3 ~ 25.9 ms** | 串行 20 个，共 506 ~ 518 ms |
| **goroutine** | ≈ **5.0 ~ 5.7 µs** | 1 万个，共 50 ~ 57 ms |
| **比值** | ≈ **4500 ~ 5000 倍** | |

三点要讲准：

- 进程那一项**包含"跑完 + 被回收"的全周期**（`cmd.Run()` 内含 `Wait`）。
  只 `Start()` 不等它，数字会小很多——但那是在攒僵尸进程（见骨架二 `SpawnDetached`）。
- 测的是"进程 vs **协程**"，不是"进程 vs 线程"。线程的数字在**使用二**里，
  三者放一起是 进程 : 线程 : 协程 ≈ **6000 : 25 : 1**。
- 这里的"进程"是**我自己编译出来的测试二进制**（启动即退出，什么都没干）；
  使用二里 Java 起的是 `cmd.exe`，所以两边的绝对值不同（25ms vs 35ms），**别横向比这两个数**。

### 实测二：worker 数扫描（对应第三节第三段"③ 资源消耗"）

总工作量固定（`BusyN` 4000 份），只变并发度。
两列分别是普通 goroutine 和 `runtime.LockOSThread()` **钉住的内核线程**——后者才是正文说的"线程"：

| worker | goroutine | 钉住的内核线程 | 加速比（对 1 worker） |
|---|---|---|---|
| 1 | 1.311 ~ 1.321 s | 1.316 s | 1.0x |
| 2 | 656 ~ 657 ms | 655 ~ 659 ms | 2.0x |
| **8（= 逻辑核数）** | 217 ~ 244 ms | 243 ~ 259 ms | **≈ 5.5x** |
| 16 | 223 ~ 254 ms | 226 ~ 246 ms | ≈ 5.7x |
| 32 | 211 ~ 232 ms | 213 ~ 241 ms | ≈ 5.9x |
| 64 | 201 ~ 265 ms | 204 ~ 239 ms | ≈ 6.0x |

★ **这里有一处和正文说法对不上，而它正是要讲的点**：

1. **"核数附近就到顶"成立** —— 2→8 近似线性，8→64 几乎不再变快。
   "CPU 密集型线程数取核数"这条经验就是这张表。
2. **但"开太多反而明显变慢"在这台机器上没稳定复现**。
   原因是**总工作量不变**：多出来的线程只是让同一批活换着手上 CPU，
   墙钟时间基本不变，变贵的是**切换次数**和**单条任务的排队延迟**。
   （有一轮测到 64 线程 697 ms ≈ 3 倍劣化，复测两次都没再现——
   与其当结论，不如当成"这台机器当时有别的东西在吃 CPU"。）
   ⚠️ 所以面试时别说"线程开多了吞吐会掉"，要说：
   **吞吐不一定掉，但延迟会变差、CPU 会浪费在切换上**——对延迟敏感的服务这才是问题。
3. 为什么加速比只有 5.5x 而不是 8x：`NumCPU()` 的 8 是**逻辑** CPU，
   笔记本的 P 核 + E 核 / 超线程不等于 8 个同等吞吐的核，再加上后台进程抢占。

### 实测三：上下文切换的成本（对应第一节第五段"上下文切换"）

```text
协程乒乓切换 200000 次：166 ~ 201 ms → 单次 ≈ 830 ns ~ 1.0 µs
```

口径必须说清楚：这测的是 **Go 用户态调度 + 唤醒**，不陷入内核，
所以**不等于**内核线程切换的开销（后者还要陷入内核、可能刷 TLB 与 cache，量不干净）。
正确用法是把它当**下限**：连最便宜的"两个执行流倒一手"都要约 1 µs，
一条消息处理链上倒十手就是 10 µs —— 这就是"别把每个小操作都拆成一个 goroutine"的量化理由。

想在 Linux 上量**真**的切换次数，用骨架二的 `ContextSwitches(pid)` 读
`/proc/<pid>/status`，或者 `pidstat -w -p <pid> 1`。
**⚠️ 本文件全部代码都没在 Linux 上实跑过**（本机是 Windows），这两项请自己取数。

### 实测四：栈内存（对应第二节追问"协程比线程轻在哪"）

| 项 | 实测（go1.26.5 / Windows） |
|---|---|
| 10 万个阻塞 goroutine 的 `StackInuse` | **7.96 KB/个** |
| 同样的协程、闭包里多一层 `defer` | **7.97 KB/个**（**没变**） |
| 换算 100 万个协程 | ≈ **7.6 GB** |
| 100 万个内核线程（Linux 默认栈 8MB 是**预留**） | = **7812 GB** 地址空间 |

★ 这张表纠正一个流传很广的说法：**"每个协程 2KB"推不出"100 万个协程只要 2GB"**。

- 加 defer 数字不动 → 说明 8KB 是**栈 span 的分配粒度**（记账口径），
  不是"每个协程真的用掉 8KB 栈"。正文说的 2KB 讲的是**栈的初始大小**（可增长的起点）。
- 结论仍然成立，只是别用错量级：**协程按 KB 计、线程按 MB 计，差三个数量级**——
  所以"百万协程"可行，"百万线程"连地址空间都开不出来。
- 反过来也别拿 2KB 做容量规划：真要开 100 万协程，**按 8 GB 这个粒度估内存**。

### 实测五：GOMAXPROCS 与"并发 vs 并行"（对应第一节第三段）

第一节说"进程是资源分配单位、线程才是调度单位"。8 个 CPU 密集型 goroutine，只改一个环境变量：

| GOMAXPROCS | 耗时 | 加速比 |
|---|---|---|
| 1 | 654 ~ 665 ms | 1.0x |
| 8 | 127 ~ 146 ms | **4.5 ~ 5.2x** |

`GOMAXPROCS=1` 时多个 goroutine **仍然并发**（一个让出另一个上），但**不并行**——
这就是第一节"并发 vs 并行"那两张图的可复现版本：
**同样的代码，只调并发度，就从"看起来同时"变成"真的同时"**。

### 实测六：不加锁计数（对应第三节第三段"① 竞态条件 / ④ 线程安全"）

8 个 goroutine 各加 1000 次，`counter++` 不加同步，五轮：

| 轮 | 不加锁 | `sync.Mutex` 对照组 |
|---|---|---|
| 1 | 8000 | 8000 |
| 2 | **7194** | 8000 |
| 3 | **7482** | 8000 |
| 4 | **6050** | 8000 |
| 5 | 8000 | 8000 |

⚠️ **五轮里有两轮"恰好正确"** —— 这就是竞态最难查的地方：
**测试通过不等于没有竞态**，压力一上来它就冒出来。
加对照组（同样工作量、加锁）是为了确认"数字变小"是竞态造成的，而不是工作量变了。

有 GCC 的机器上换成 `RACE_DEMO=1 go test -race ./proc/ -run TestRaceDemo`，
它还能直接指出**哪一行在读、哪一行在写**（本机 `-race` 起不来，见开头口径）。

### 三条只有量过才讲得准的话

1. **"线程创建比进程轻"** → 我量到的是**进程 vs 协程**差 ~4500 倍；
   进程 : 线程 : 协程 ≈ 6000 : 25 : 1（线程数据在使用二）。
2. **"线程数 = 核数最好"** → 准确说法是"**到核数为止有加速，之后没有加速**"，
   而不是"超过就变慢"（实测二第 2 条）。
3. **"协程 2KB"** → 那是**初始栈大小**，不是内存账；记账粒度实测 **8KB/个**（实测四）。

### 二、创建成本：进程 / 线程 / 协程 放一张表

```java
static long threadCreate(int n) throws InterruptedException {
	CountDownLatch gate = new CountDownLatch(1);
	CountDownLatch started = new CountDownLatch(n);
	Thread[] ts = new Thread[n];
	long start = System.nanoTime();
	for (int i = 0; i < n; i++) {
		ts[i] = new Thread(() -> {
			started.countDown();
			try {
				gate.await(); // 全部挂在这里，只花线程本身的成本
			} catch (InterruptedException e) {
				Thread.currentThread().interrupt();
			}
		});
		ts[i].setDaemon(true);
		ts[i].start();
	}
	started.await();
	long cost = System.nanoTime() - start;
	gate.countDown();
	for (Thread t : ts) {
		t.join(50); // 对应 Go 侧的 Wait：不回收就是攒僵尸
	}
	return cost;
}
```

| 执行流（同一台 Windows 机器） | 单个成本 | 相对 |
|---|---|---|
| Java 进程（`ProcessBuilder` + `waitFor`） | **34.9 ~ 39.5 ms** | 1x |
| Java 内核线程（`new Thread().start()`） | **132 ~ 159 µs** | ≈ **1/250** |
| Go goroutine（实测一） | **5.0 ~ 5.7 µs** | ≈ **1/6000** |

→ **第三节第二段"① 更轻量级"的三个数量级差，这张表一次讲完**：
进程 : 线程 : 协程 ≈ **6000 : 25 : 1**。

**那"只 start 不 wait"能省多少？** 实测 **7.3 ~ 7.8 ms/个**（对 34.9 ms 是 **4~5 倍**快）。
⚠️ 而这正是僵尸进程的来源：Linux 上 `fork` 完不 `wait`，
子进程退出后 PCB 一直留着（`ps` 里的 `<defunct>`）。
**省下来的那部分成本，就是"没做的回收工作"**——快是用泄漏换的。

### 三、线程数扫描：真内核线程超订会怎样

```java
static long scaling(int workers, long totalUnits) throws InterruptedException {
	long chunk = totalUnits / workers + 1;
	final double[] sums = new double[workers]; // ★ 每个 worker 写自己的格子
	final CountDownLatch done = new CountDownLatch(workers);
	long start = System.nanoTime();
	for (int i = 0; i < workers; i++) {
		final int id = i;
		Thread t = new Thread(() -> {
			sums[id] = busy(chunk);
			done.countDown();
		});
		t.setDaemon(true);
		t.start();
	}
	done.await();
	return System.nanoTime() - start;
}
```

| worker | 耗时（两轮） | 加速比 |
|---|---|---|
| 1 | 2697 ~ 2703 ms | 1.0x |
| 2 | 1224 ~ 1226 ms | 2.2x |
| **8（= 核数）** | 364 ~ 365 ms | **≈ 7.4x** |
| 16 | 353 ~ 398 ms | ≈ 7.4x |
| 32 | 357 ~ 382 ms | ≈ 7.4x |
| 64 | 356 ~ 360 ms | ≈ 7.6x |

- **和 Go 侧同一个结论**：核数处到顶，超订不再变快（也没明显变慢，理由见实测二第 2 条）。
- Java 侧能多证明一点：**这里没有任何用户态调度，全是真内核线程**，
  所以"频繁上下文切换的额外开销"体现在 **CPU 时间**里而不是墙上时间——
  要抓它得用 `pidstat -w -p <pid> 1`（看 `cswch/s`、`nvcswch/s`），
  或 Go 骨架二的 `ContextSwitches(pid)` 读 `/proc/<pid>/status`。**⚠️ 两条都没在本机实测过。**
- Java 8 worker 能到 7.4x、Go 只有 5.5x：**别横向比这两个数**。
  两边的 `busy` 循环不是一套指令（JIT 会把纯浮点累加向量化/部分消除），
  这个差异大到能盖过调度模型的差异。同语言内比才有意义。

### 四、竞态复现（和 Go 侧同一套对照组）

```java
static int unsafeAdd(int g, int n) throws InterruptedException {
	final int[] counter = {0}; // ⚠️ 故意不用 AtomicInteger：就是让它出错
	Thread[] ts = new Thread[g];
	for (int i = 0; i < g; i++) {
		ts[i] = new Thread(() -> {
			for (int j = 0; j < n; j++) {
				counter[0]++; // 读-改-写三步，不是原子的
			}
		});
		ts[i].setDaemon(true);
		ts[i].start();
	}
	for (Thread t : ts) {
		t.join();
	}
	return counter[0];
}
```

实测（8 线程 × 1000 次，两轮各 5 次，对照组 `synchronized` 恒为 8000）：

| | 不加锁出现的值 |
|---|---|
| 第 1 轮 | 8000、8000、**7349**、8000、8000 |
| 第 2 轮 | 8000、**7830**、8000、8000、8000 |

⚠️ 和 Go 侧完全同一个教训：**大部分时候它是对的**，
所以"跑了一遍没问题"永远不能拿来排除竞态。
Java 侧对应 `-race` 的工具是 **ThreadSanitizer**（`-XX:+UnlockDiagnosticVMOptions -XX:+WhiteBoxAPI` 那套）
或者更常用的 **jcstress**；日常靠 review + `Atomic*`/锁的纪律。

### 五、线程池：不要每请求 `new Thread`

`new Thread` 就是一个内核线程（130 µs 起 + 一个栈），**而且没有上限保护**——
一次请求风暴能把机器打到
`OutOfMemoryError: unable to create new native thread`。
所以线上只有池，且**池是进程级单例**（Spring `@Bean` 注入），不是每次请求新建：

```java
// ⚠️ 不用 Executors.newFixedThreadPool：它的队列是**无界** LinkedBlockingQueue，
// 任务堆积会先撑爆堆，而不是触发拒绝策略。
ThreadPoolExecutor pool = new ThreadPoolExecutor(
		Runtime.getRuntime().availableProcessors(),         // 核心数 = CPU 核数（对应实测三的拐点）
		Runtime.getRuntime().availableProcessors() * 2,     // 只有 IO 密集型才把上限调大
		60, TimeUnit.SECONDS,
		new ArrayBlockingQueue<>(1000),                     // ★ 有界队列
		new ThreadPoolExecutor.CallerRunsPolicy());         // 满了让调用方自己跑 = 背压
```

| 场景 | 线程数怎么定 | 依据 |
|---|---|---|
| **CPU 密集型**（加解密、压缩、图像） | ≈ 核数（核数 +1 补偿偶发阻塞） | 实测三：核数处就到顶 |
| **IO 密集型**（RPC、DB、文件） | 远大于核数，粗算 `核数 / (1 − 阻塞比)` | 线程大部分时间在等，不占 CPU |
| **虚拟线程 / 协程** | 不用定，按任务数开 | 实测四：成本按 KB 计 |

Java 21+ 的**虚拟线程**就是 Java 侧的 goroutine（M:N 挂到载体线程上，
`Thread.ofVirtual()` / `Executors.newVirtualThreadPerTaskExecutor()`）。
用它之后上面那张"IO 密集型线程数怎么定"的表**基本作废**——
不用再靠堆线程掩盖延迟了，但**⚠️ 池化的仍然是载体线程，`synchronized` 长临界区仍会 pin 住载体线程**。

### 六、Go 骨架二 ↔ Java 的对应写法

| 语义 | Go（骨架二） | Java |
|---|---|---|
| 回收子进程 | `cmd.Wait()` / 后台协程兜底 Wait | `p.waitFor()`；⚠️ 不 wait 在 Linux 上留僵尸 |
| 优雅停止 | SIGTERM → 超时 → SIGKILL（`StopGracefully`） | `p.destroy()` → 超时 → `p.destroyForcibly()`（后者才等价 SIGKILL） |
| 拿输出 | `cmd.CombinedOutput()`（内部已 Wait） | `p.getInputStream()` **要读**，否则管道满了子进程会卡死 |
| 线程数量 | `runtime.NumGoroutine()` / 读 `/proc` | `ThreadMXBean.getThreadCount()`（只有数量，没有切换次数） |
| 栈大小 | goroutine 自动增长，不可配 | `-Xss`（默认 512KB~1MB），⚠️ 是**预留**不是驻留 |

⚠️ Java 这一栏只有"线程数量 / 线程池 / 创建成本"三项在本机跑过；
`destroy` 与 `destroyForcibly` 的差别、`getInputStream` 卡死，
都是**语义层面的约定，没有做破坏性实验去验证**。
