## Q1. 场景题：设计一个直播弹幕系统

**来源**：`p=10` 抖音 Go 一面 · 时长 6分59秒
**考察意图**：开放设计题。**面试官不是要一个完美方案，而是要看你的分层思路**，
然后他会补充条件、提出疑问，你再迭代——**这个过程本身就是考察内容**。

### 面试方法论（先讲这个，比方案本身更加分）

> 场景设计题的节奏是：**先给出大体思路 → 与面试官讨论需求和现有资源约束 →
> 他补充关键元素或提出疑问 → 你据此调整设计 → 逐步完善**。
>
> **它不是一开始就有一个一成不变的设计**。有缺陷没关系，**关键是必须要有思路能拿出来讨论**。

### 完整设计（四层）

#### 第 1 层：接入限流（防刷屏）

客户端发弹幕 → 服务端**第一步先限流**：

- 限流维度：**按用户 / 设备 ID / 客户端**；
- 频率：如 10 分钟 1 条、1 分钟 1 条——**由业务需求决定**；
- 触发限流 → **直接丢弃**，不再往下走。

#### 第 2 层：双路径分流

通过限流后，弹幕数据要走**两条路**：

| 路径 | 目的 |
|---|---|
| **推送链路** | 推送到前端**实时展示** |
| **持久化链路** | 保存数据，供**直播回放**展示或**弹幕数据分析** |

#### 第 3 层：持久化 —— 为什么必须走缓存

**弹幕数据的特征**：
- 属于**娱乐性数据**，重要性低，**丢几条不影响业务**，不涉及经济损失和核心体验；
- **生产成本极低**——用户只需编辑发送，没有任何成本门槛；
- 因此**发送频率极高**（即使加了限流，量依然很大）。

**为什么不能直接写数据库**：

> 如果每发一条弹幕就写一次库，**弹幕的写入 TPS 会和数据库的查询 TPS 相当**，
> 而这类高频插入正是数据库最不擅长的。

**方案**：
1. **先写入 Redis 缓存**（读写性能远高于 MySQL 这类数据库）；
   - 代价：缓存可能因主动淘汰丢数据——但对弹幕来说，**丢了就丢了，可以接受**；
2. **通过定时任务或消息队列批量落库**；
3. 落库目标可选**关系型数据库**或 **MongoDB 这类文档型数据库**，取决于具体方案。

> **原则**：尽量避免"每条新数据都写一次库"，**尽可能改成批量操作**。

#### 第 4 层：推送链路 —— 用 Redis 发布订阅打通分布式节点

**问题**：服务端是**分布式部署**的，前面有负载均衡：
- 一个请求**具体落到哪台服务器不确定**；
- 用户的 **WebSocket 长连接建立在哪台服务器上也不确定**（可能连 1 号、2 号、3 号都能连）。

**如果只靠单机内存维护连接映射，就会出现"弹幕推给了没有这个连接的机器"**。

**解法：引入 Redis 发布订阅**

```
所有服务器都订阅同一个主题
        ↓
收到弹幕数据的服务器 → PUBLISH 到该主题
        ↓
所有持有 WebSocket 连接的服务器都能收到通知
        ↓
各自通过 WebSocket 推送给自己的在线用户
```

这样，**弹幕的推送不再依赖"用户恰好连在哪台机器"**。

### 面试时怎么讲

1. **先给框架**：限流 → 双路径（实时推送 + 持久化）；
2. **主动解释关键权衡**：弹幕可容忍丢失 → 所以缓存优先、批量落库；
3. **主动暴露分布式的坑**：负载均衡下连接位置不确定 → 所以需要发布订阅；
4. **等面试官追问**：他会补充元素或质疑设计，你据此迭代。

## Q2. 文件服务器如何选型？（Ceph vs 对象存储）

**来源**：`p=15` 百度 Go 前端一面 · 时长 13分36秒
**考察意图**：**这题考的是"选型方法"而不是"性能对比"**——
面试官想听你先问需求，而不是先比较参数。

### 选型第一原则（先答这个）

> **从需求出发，从熟悉程度出发，而不是从性能出发。**

原因：
- **成型的文件系统不会有太拉垮的性能**，性能差异通常在百分之几；
- 很多业务**根本到不了需要考虑那百分之几性能的量级**；
- 所以更该关注的是：**哪个方案能更好解决实际问题、团队更熟悉哪个**。

### 三类方案的适用场景

#### ① 分布式文件系统（Ceph 等）—— 需要共享

**场景**：K8s 环境。所有容器/Pod **部署在多台机器上**，机器之间需要**共享文件或磁盘**。

具体例子：
- 在 K8s 里搭建 **Docker 私有镜像仓库**，把镜像都存在一个位置，
  **所有集群节点共享同一个文件系统**（镜像存在这里）；
- **有状态应用**（etcd、Redis、MySQL）：每个 Pod 需要一块**独立的存储块设备**（RBD），
  这类也用 Ceph 提供。

**原理**：把设备以**类似网盘 / 共享文件夹**的形式**挂载到操作系统**的某个目录上。
对使用者来说，**操作它就是复制文件到目录、从目录取文件**，
与本地文件夹**几乎没有区别**。

**唯一区别**：**挂载动作需要权限校验**，之后的读写就不需要了。
好处是**隐藏了文件上传/下载的细节**——开发时就像操作本地目录。

#### ② 对象存储（COS / OSS 等）—— 不需要共享

**场景**：普通网站里的**图片、用户头像**等静态文件。

特征：
- **不需要在多个操作系统/节点之间共享**；
- 只需要**持久化保存**，以及**偶尔被用户查看**。

满足这两点，用对象存储就够了。

### 传输失败怎么办？（第二问）

取决于**上传方式**——如果是"业务服务器上传到文件服务器"，失败处理如下：

**① 断点续传 + 重试**

重试要做**退避策略**，不要无脑重试：

```
第 1 次失败 → 5 秒后重试
第 2 次失败 → 10 秒后重试
第 3 次失败 → 1 分钟后重试
第 4 次失败 → 5 分钟后重试
最多重试 5~10 次
```

**为什么要退避**：
- **正常的请求**（如网络抖动）重试一两次就会成功；
- **不正常的请求**（如资源不存在、权限错误）**重试多少次都不会成功**，
  只会白白消耗资源。

**② 监控告警**

- 用 **Prometheus** 监控文件服务器，或由业务服务器**上报失败指标**；
- 多次失败后通过**邮件 / 企业微信**通知开发人员，及时感知重试情况。

### 要不要经过业务服务器？（第三问，加分点）

**判断标准很简单**：

> **如果文件上传到业务服务器后"什么都不做"，只是原样转发给文件服务器，
> 那就没有理由经过业务服务器——直接绕过。**

**绕过的好处（前端直传对象存储）**：
- 文件从客户端 → 业务服务器 → 对象存储，**要走两次网络**
  （消耗两次带宽，也消耗两倍时间）；
- 直传只有**一次上传**，**减少一次上传时间，同时大幅降低业务服务器负载**。

**必须经过业务服务器的例外**：
- 文件**需要在业务侧处理**，例如报表文件需要**导入数据库**；
- 处理完之后，再把文件**备份到文件服务**。

### COS 直传的两步实现（以腾讯云 COS 为例）

| 步骤 | 谁做 | 内容 |
|---|---|---|
| **① 换临时密钥** | 后端 | 用**永久密钥换取临时密钥**，临时密钥有**有效期**（如 30 分钟 / 1 小时）——避免把永久密钥暴露给前端 |
| **② 生成预签名 URL** | 后端 | 根据文件名等信息**签名**，下发预签名上传地址和访问地址 |
| **③ 上传** | 前端 | 对预签名 URL 发 **PUT** 请求，**以二进制方式**传输文件内容 |

**验证方式**：上传返回 **HTTP 200** 即表示成功，可直接用返回的访问地址下载核对内容。

> **安全要点**：**前端永远拿不到永久密钥**，只拿到**有时效的临时凭证和预签名 URL**，
> 即使泄露也只在有效期内可用。

## Q3. 场景题：设计一个朋友圈

**来源**：`p=60` 字节跳动后端面试 · 时长 20分30秒
**考察意图**：场景题**没有标准答案**，考的是**应变能力和思考过程**——

> **面试官要的不是"标准的微信朋友圈方案"，
> 而是你自己的思路：为什么这么设计、设计时有哪些考量。**
>
> **答案离谱不行，但有思路、有取舍、能讲清理由，就是好答案。**

### 一、第一步：要素分析（先想清楚"有什么"）

划出**三类核心信息**：

| 要素 | 说明 |
|---|---|
| **① 朋友与用户** | 朋友圈一定涉及"人" |
| **② 图文、视频等信息** | 即朋友圈的**条目 / 动态** |
| **③ 评论与点赞** | 针对动态产生的互动 |

> **注意**：面试时想不到所有细节是**正常的**——
> 实际开发也一样，**先定大方向，后续开发中遇到问题再迭代**，
> 不会一开始就设计得极其细致。

### 二、第二步：分析朋友圈的三个特点

| 特点 | 内容 |
|---|---|
| **① 数据展示范围固定** | 展示**自己通讯录里所有朋友 + 自己**发的动态 |
| **② 数据展示顺序固定** | **按时间倒序**——最新的在最上面 |
| **③ 热点数据** | 用户通常只看**一小时以内**的，最多**一天以内**。<br>→ **保守设计为"两天内的热点数据"**；<br>后续可根据**数据打点**再决定是两小时、一天还是两天 |

> 关于第 ③ 点要**主动承认这是拍脑袋**：
> "先按两天设计，后续根据打点数据调整"——**这种诚实的表达反而加分**。

### 三、第三步：ER 图与表设计

| 表 | 关系 | 说明 |
|---|---|---|
| **用户表** | — | 用户主体信息 |
| **朋友表（通讯录表）** | **用户 ↔ 朋友：多对多** | A 加 B、B 加 A 是**相互**的，本质是用户与自己的关系（用独立表表达） |
| **动态表** | **用户 → 动态：一对多** | 一个用户可发多条动态 |
| **用户-动态关系表** | **用户 ↔ 动态：多对多** | **决定"这个用户能看到哪些动态"** |
| **评论表 / 点赞表** | **动态 → 评论/点赞：一对多** | 无特殊逻辑 |

**⭐ 为什么一定要建"用户-动态"多对多关系表？（这是本题最重要的设计思考）**

> **朋友圈的「发布量」远小于「查看量」。**
>
> 举例：100 个人里，可能 **90 个人只是在看、点赞、评论，只有 10 个人在发布**。
>
> **所以**：
> - **在「发布」时维护这份多对多关系**（写少，代价可控）；
> - **避免在「查看」时再去关联查找**（读多，必须快）。
>
> **如果不这样设计**，查看时要先查朋友关系 → 再查这些朋友发的动态，
> **每次查询都要多绕几步**；而查看的频次是发布的好几倍。
>
> **本质：用空间换时间**——发布时多存一份关系（消耗空间），
> 换来查询时**可以直接从关系表命中**（不消耗额外的关联开销）。

### 四、第四步：数据分层与缓存设计

**三层结构**：

#### 第 1 层：DB（按数据特征选型）

| 数据 | 存储 | 理由 |
|---|---|---|
| 用户、朋友关系、评论、点赞 | **MySQL（关系型）** | 这些是**结构化数据**，每行字段一致 |
| 动态（图文/图片/视频/链接） | **MongoDB（文档型）** | 动态的**格式不固定**（可能纯文字、可能图文、可能视频），<br>用文档型更合适 |

> （原视频也说了：**都用 MySQL 存也可以**，只是选型上文档型更贴合动态数据特征。）

**为什么需要缓存层（讲清动机，比讲方案更重要）**：

> 如果不区分热点数据——**全放数据库扛不住**；
> **全放缓存又浪费大量缓存空间、成本上升**。
> 所以要**按热点范围缓存**。

#### 第 2 层：缓存（Redis），缓存两类数据

| 缓存内容 | 策略 |
|---|---|
| **动态数据** | **两天内的动态全量缓存**。<br>新增数据用**双写**（写库 + 写缓存）；<br>或**应用启动时预热**（把两天内的数据全量加载进缓存） |
| **用户-动态多对多关系** | 缓存这份关系 → **直接就能拿到"我两天内能看的朋友圈"**，<br>无需回表关联 |

**两天之前的数据**：
> 需要时**回源 DB**，再放进缓存，**设置一天的有效期**；
> 过期后从缓存移除，下次加载再回源。

#### 第 3 层：应用层 / 客户端

| 设计 | 说明 |
|---|---|
| **分页加载** | 一次加载一页，**每页 10~20 条**，最多不超过 50 条 |
| **应用本地缓存** | 用户退出朋友圈再进来时，**本地已有数据就不用再拉** |

### 五、面试答题结构（三步走）

```
① 要素与特点分析  → 人 / 动态 / 互动，范围固定、时间倒序、热点两天
② 表设计（ER 图） → 用户、朋友（多对多）、动态（一对多）、用户-动态（多对多）
                    ★ 重点讲清"为什么要在发布时维护多对多关系"
③ 数据分层与缓存  → MySQL 存结构化 / MongoDB 存动态 / Redis 缓存动态与关系
                    / 应用层分页 + 本地缓存
```

> **最值钱的是第 ② 步里那个"发布量 << 查看量 → 空间换时间"的判断**，
> 以及第 ③ 步里"为什么要区分热点数据"的动机说明。

### 面试官会追问什么

- **朋友关系为什么要多对多，不能一对多吗？** → 一对多会出现**重复条目**（A 加 B、B 加 A 各存一条），
  而且**反查"谁加了我"**很麻烦；多对多关系表天然解决双向问题。
- **删除好友怎么办？** → 删关系表记录，同时按需清理相关缓存（**注意缓存与 DB 的一致性**）。
- **大 V 发一条动态要写给几千万人吗？** → **不能**（写扩散爆炸）。
  这类**读扩散**场景要改成 **Pull 模式**（拉取时聚合），
  或**混合模式**（普通用户写扩散、大 V 读扩散）——**这是本题最好的加分回答**。
- **怎么保证动态的顺序？** → 用**发号器（雪花算法）** 生成有序 ID，
  按 ID 倒序即等价于按时间倒序（**避免同一秒内时间戳无法区分先后**）。

## Q4. 视频文件上传：放业务服务器和放文件服务器有什么差异？

**来源**：`BV1xSRXBwEeM p=40` 百度 Go 实习二面 · 时长 6分55秒
**考察意图**：表面在问"文件放哪"，实际考的是**"无状态 vs 有状态"这条分布式设计的基本原则**——
文件放业务服务器，就把一个无状态服务变成了有状态服务。

### 一、先看部署结构

```
客户端 → 网关（负载均衡）→ [业务服务器1 | 业务服务器2 | 业务服务器3] → 文件服务器集群
```

### 二、核心结论：文件放业务服务器 = 把服务做成"有状态"

| 维度 | **文件放业务服务器（本地）** | **文件放文件服务器（中心化）** |
|---|---|---|
| **服务状态** | 每个节点存的内容都不一样（A 存 A 文件、B 存 B 文件）→ **变成有状态服务，跟数据库一样** | 业务节点**不存任何数据，只做计算** → **无状态** |
| **扩缩容** | 扩容的新节点**没有历史文件**；缩容**要撤掉的节点上还挂着文件** → **不敢缩** | 加机器 / 减机器只影响算力，**随时可扩可缩** |
| **路由复杂度** | 负载均衡过后"**到底该访问哪台服务器**"不知道 → 只能再维护一份"文件↔节点"映射 | 文件的定位由**文件系统自己解决**，业务侧不关心 |
| **本质** | 相当于**自己在开发一套文件系统**，而且和业务**深度耦合** | 业务只调**标准接口 / SDK**，背后怎么实现完全隐藏 |
| **带宽** | 客户端 → 业务服务器 → 文件系统，**走两次网络** | 直传只走一次（详见 Q2） |

### 三、为什么必须做无状态（最值钱的一句）

> **业务服务器要尽可能做到无状态——本地不保存任何数据，只做计算。**
>
> 这样：**流量激增 → 直接加机器加节点，处理能力立刻变强**；
> **流量回落 → 把多余资源撤下来**。整个过程**没有任何数据迁移问题**。

**换个角度理解**：这和"为什么要用中心化的 Redis 缓存、中心化的 DB"是**同一件事**——

> 把数据放到数据中心、缓存放到缓存中心、Session 放到 Session 中心、**文件放到文件中心**，
> 业务服务器只通过标准接口调用它们。
> **文件系统用 Ceph 也好、对象存储也好、自研也好，对业务服务器都是隐藏的，业务只关心调用结果。**

### 四、和 Q2 的关系（避免答串）

| | **Q2（追问：要不要经过业务服务器）** | **本题（Q4）** |
|---|---|---|
| 关注点 | **链路效率与安全**：能不能前端直传、临时密钥怎么签发 | **服务架构**：文件存在业务节点会把服务做成有状态 |
| 结论 | 中间"什么都不做"就直传，避免多一次网络与带宽消耗 | 文件**存**在业务节点本地 → 破坏无状态、扩缩容受阻 |

> 两题其实是**同一原则的两个侧面**：**业务节点只做计算，数据一律中心化。**

### 面试官会追问什么

- **文件放业务服务器，就一定要自己实现文件系统吗？** → 是的。
  因为请求轮询到哪台不确定，**你就得维护"文件在哪台节点"的映射**——
  这份映射加上定位逻辑，就是文件系统在做的事（相当于自己造一个）。
- **业务节点一点都不缓存文件吗？** → 可以缓存（如本地磁盘做 CDN 前置），
  但**缓存必须可重建、可淘汰**，不能是"唯一副本"，否则又变回有状态。
- **无状态服务的代价是什么？** → **每次都要走网络访问中心化存储**，
  延迟高于本地读写 → 用**缓存、CDN、就近接入**来补。
- **有状态服务就一定是错的吗？** → 不是。**数据库、缓存、消息队列本身就是有状态的**，
  关键是**把"状态"收敛到专门的有状态系统里**，而不是散落在业务节点上。

## Q5. 开放题：如何设计微信的海量数据存储系统？

**来源**：`BV1xSRXBwEeM p=71` 微信 Go 面试 · 时长 5分49秒
**考察意图**：**开放性题目，没有标准答案**。考的是**临场拆解能力**——
能不能自己找到"突破点"，再顺着突破点和面试官一层层聊下去。

### 一、先定方法论：这类题怎么答

> 1. 开放题**不可能一听到就给出完整方案**，面试官也不会这样要求；
> 2. 它一定会**涉及多轮对话**——你在过程中怎么思考、遇到问题怎么调整，**这个过程本身就是考核内容**；
> 3. 所以第一件事是：**找到相对明确的突破点**，把话题拉进自己熟悉的领域。

**从题干能直接抽出两个突破点**：

| 突破点 | 含义 |
|---|---|
| **① 微信 = 聊天工具 → 数据类型** | 聊天记录（文本 / 语音 / 图片 / 视频 / 文件）+ 用户信息 |
| **② 海量 → 量级问题** | 必须分布式、必须分层、必须能水平扩展 |

### 二、突破点一：按数据类型选存储

| 数据类型 | 特征 | 存储选型 |
|---|---|---|
| **用户信息**（姓名、性别、年龄、头像） | **结构化**、字段固定 | **关系型数据库**（MySQL） |
| **聊天记录** | **非结构化**（文本/语音/图片/视频混合）、**按时间顺序**、**有明显热点** | **非关系型**（MongoDB / 时序数据库 / 自研 KV） |
| **文件（图片、视频、附件）** | 大对象、一次写多次读 | **对象存储 / 分布式文件系统** |

> **"按时间顺序"这个特征很关键**：聊天记录天然是**时间序列**，
> 且"最近的消息天天看，久远的几乎不看"→ 直接引出下一个突破点：**分层**。

### 三、突破点二：海量 → 分布式 + 分层

**① 分布式（量的问题）**

> **不可能单节点存下**，而且数据量和用户量都持续增长 → 必须用**分片 + 集群**架构，
> 选**可水平扩展（scale out）**的存储，如 **TiDB**（分布式关系型）或 **MongoDB**（分片集群）。

**② 分层（冷热的问题）**

| 数据层级 | 判定标准（示例） | 存储策略 |
|---|---|---|
| **热数据** | **7 天以内** | **缓存**（Redis 等），**快是第一优先级** |
| **温数据** | **1 个月以内** | 性能与成本折中（普通磁盘 DB / 冷热混合） |
| **冷数据** | **1 个月以前** | **低成本大容量存储**（对象存储 / 归档存储） |

> **分层的本质**：**把不同访问频率的数据放到不同"价位的介质"上**——
> 让"快"的只服务少数请求，让"大"的用便宜介质兜住。

### 四、综合方案（把两个突破点合起来讲）

```
接入层：IM 网关（长连接）+ 短连接 API，承载连接与鉴权
   ↓
业务层：消息收发、会话服务、用户服务（无状态，可水平扩容）
   ↓
存储层（按数据类型分）
   ├─ 用户信息 / 关系      → 分库分表的 MySQL（或分布式关系型）
   ├─ 聊天记录（海量时序） → 按 用户 / 会话 维度分片；冷热分层
   └─ 图片 / 视频 / 文件   → 对象存储 + CDN
   ↓
缓存层：Redis 缓存 7 天内的热点消息与会话元数据
```

**讲到这里可以主动抛"真实方案参考"**（微信公开的技术实践方向）：

| 机制 | 作用 |
|---|---|
| **一致性哈希** | 让数据分片在**增删节点时只迁移少量数据**（普通取模会导致**全量重分布**） |
| **分库分表 / 按用户维度分片** | 同一用户的数据尽量落同一分片，**单用户读放大最小** |
| **冷热分离** | 近期消息留在高性能存储，历史消息下沉低成本存储，**按需回捞** |
| **多级缓存** | 客户端本地 → 接入层缓存 → Redis → 存储，**逐层拦截** |

### 五、面试答题结构

```
① 先声明这是开放题，按"数据类型 + 数据量"两个突破点展开
② 类型维度：结构化 → MySQL；非结构化/时序 → MongoDB 或自研 KV；文件 → 对象存储
③ 量级维度：分片 + 集群 + 可水平扩展；一致性哈希减少迁移
④ 时间维度：7 天热 / 1 月温 / 更久冷，分层存储
⑤ 交互：主动抛"某类数据量预估多少、要不要压缩"等话题，引导面试官继续对话
```

### 面试官会追问什么

- **聊天记录为什么不用 MySQL？** → 非结构化、量级极大、写多读少且**冷热分层明显**；
  MySQL 分库分表能做到，但**成本和复杂度更高，文档型 / 自研 KV 更贴合**。
  （注意：**不是不能用** MySQL，而是选型贴合度问题。）
- **按用户分片还是按会话分片？** → 按**用户**分片利于"拉取我的会话列表"，
  但**群聊**消息读写会跨用户 → 群消息常单独按**群 ID 分片**，成员侧只存**引用 / 收件箱**。
- **冷数据回捞延迟大怎么办？** → **异步回捞 + 缓存预热**；
  对可预判的场景（如跳转历史消息）**提前加载**。
- **数据一致性怎么保证？** → **单用户 / 单会话内部强一致**（同一分片），
  **跨用户最终一致**（异步写扩散 + 补偿），而不是追求全局强一致。
- **消息不丢怎么保证？** → 写入先落存储再回 ACK；客户端本地也有副本；
  服务端提供**离线消息 + 多端同步**机制。

## Q6. 场景题：如何让数据统计页面加载速度变快？

**来源**：`BV1xSRXBwEeM p=78` 小红书面试场景题 · 时长 1分47秒
**考察意图**：短平快的场景题。答案核心只有一句——**别让"查询"去做"统计"**，提前把结果算好。

### 一、核心思路：少查询，把统计前移

> **让统计页面变快的唯一有效办法是：不要在查询时做实时统计。**
> **统计页面慢，就慢在"每次打开都在重新算一遍"。**

**做法：定时任务预计算**

```
每天（或每小时）定时任务 → 统计前一天的数据 → 把统计结果写入「结果表」
        ↓
用户打开统计页面 → 直接查结果表（不做任何聚合计算）
```

> 实时统计"**既麻烦又慢**"：要扫全量、要聚合、要排序。
> 而结果表里只有算好的数字，**查起来几乎没有成本**。

### 二、配套手段

| 手段 | 做法 |
|---|---|
| **分页查询** | 结果表按页取（如每次 10 条 / 20 条），**避免一次拉全量** |
| **查询语句优化** | 优化要放在**统计（写结果表）的时候做**，<br>**而不是每次查询的时候做**——查询路径只留最简单的 `WHERE + LIMIT` |
| **缓存结果** | 结果表外面还可以再套一层缓存（Redis / 本地缓存），<br>尤其是"当天实时看板"这类会被反复刷新的页面 |
| **异步 / 物化** | 更复杂的口径用**物化视图或异步聚合任务**，把重计算从查询链路剥离 |
| **索引** | 结果表按 `维度 + 日期` 建索引，保证分页与筛选都走索引 |

### 三、面试答题结构

```
① 一句话给结论：不要在查询时做统计，提前算好（定时任务 → 结果表）
② 查询路径：只从结果表分页读，语句保持最简
③ 更优解：结果再加缓存 / 用物化视图 / 异步聚合
④ 主动补一句：查询语句优化要放到统计阶段做，在查询阶段做收益有限
```

> **原视频的落点很直白**：**定时任务预计算 + 查结果表 + 分页**，
> 就是这类"统计页面变快"性价比最高的方案；**查询语句优化起不到决定性作用**。

### 面试官会追问什么

- **统计口径变了怎么办？** → 预计算任务**支持按日期重跑（补算历史）**，
  口径变更时回刷结果表；**不要靠实时查询兜底**。
- **业务要实时看板怎么办？** → **冷热两套**：历史区间走预计算结果表，
  **当天数据走实时聚合 + 缓存**（秒级刷新），第二天再由定时任务合并。
- **为什么不直接在结果表上再聚合？** → 每多一层聚合就多一次全表扫描，
  **结果表的价值就在于"已经聚合到最细查询粒度"**。
