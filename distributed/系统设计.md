## Q1. 场景题：设计一个直播弹幕系统

**来源**：`p=10` 抖音 Go 一面 · 时长 6分59秒
**考察意图**：开放设计题。**面试官不是要一个完美方案，而是要看你的分层思路**，
然后他会补充条件、提出疑问，你再迭代——**这个过程本身就是考察内容**。

### 面试方法论（先讲这个，比方案本身更加分）

> 场景设计题的节奏是：**先给出大体思路 → 与面试官讨论需求和现有资源约束 →
> 他补充关键元素或提出疑问 → 你据此调整设计 → 逐步完善**。
>
> **它不是一开始就有一个一成不变的设计**。有缺陷没关系，**关键是必须要有思路能拿出来讨论**。

### 完整设计（四层）

#### 第 1 层：接入限流（防刷屏）

客户端发弹幕 → 服务端**第一步先限流**：

- 限流维度：**按用户 / 设备 ID / 客户端**；
- 频率：如 10 分钟 1 条、1 分钟 1 条——**由业务需求决定**；
- 触发限流 → **直接丢弃**，不再往下走。

#### 第 2 层：双路径分流

通过限流后，弹幕数据要走**两条路**：

| 路径 | 目的 |
|---|---|
| **推送链路** | 推送到前端**实时展示** |
| **持久化链路** | 保存数据，供**直播回放**展示或**弹幕数据分析** |

#### 第 3 层：持久化 —— 为什么必须走缓存

**弹幕数据的特征**：
- 属于**娱乐性数据**，重要性低，**丢几条不影响业务**，不涉及经济损失和核心体验；
- **生产成本极低**——用户只需编辑发送，没有任何成本门槛；
- 因此**发送频率极高**（即使加了限流，量依然很大）。

**为什么不能直接写数据库**：

> 如果每发一条弹幕就写一次库，**弹幕的写入 TPS 会和数据库的查询 TPS 相当**，
> 而这类高频插入正是数据库最不擅长的。

**方案**：
1. **先写入 Redis 缓存**（读写性能远高于 MySQL 这类数据库）；
   - 代价：缓存可能因主动淘汰丢数据——但对弹幕来说，**丢了就丢了，可以接受**；
2. **通过定时任务或消息队列批量落库**；
3. 落库目标可选**关系型数据库**或 **MongoDB 这类文档型数据库**，取决于具体方案。

> **原则**：尽量避免"每条新数据都写一次库"，**尽可能改成批量操作**。

#### 第 4 层：推送链路 —— 用 Redis 发布订阅打通分布式节点

**问题**：服务端是**分布式部署**的，前面有负载均衡：
- 一个请求**具体落到哪台服务器不确定**；
- 用户的 **WebSocket 长连接建立在哪台服务器上也不确定**（可能连 1 号、2 号、3 号都能连）。

**如果只靠单机内存维护连接映射，就会出现"弹幕推给了没有这个连接的机器"**。

**解法：引入 Redis 发布订阅**

```
所有服务器都订阅同一个主题
        ↓
收到弹幕数据的服务器 → PUBLISH 到该主题
        ↓
所有持有 WebSocket 连接的服务器都能收到通知
        ↓
各自通过 WebSocket 推送给自己的在线用户
```

这样，**弹幕的推送不再依赖"用户恰好连在哪台机器"**。

### 面试时怎么讲

1. **先给框架**：限流 → 双路径（实时推送 + 持久化）；
2. **主动解释关键权衡**：弹幕可容忍丢失 → 所以缓存优先、批量落库；
3. **主动暴露分布式的坑**：负载均衡下连接位置不确定 → 所以需要发布订阅；
4. **等面试官追问**：他会补充元素或质疑设计，你据此迭代。

### 落地实现：最小可运行骨架（Go，已编译校验 + 已实测）

> 本篇是**纯设计题**，所以没有"客户端怎么连"的使用方法章节，而是把上面四层
> 落成一份**能跑、能测出数字**的骨架——四层各自对应一个文件，
> 顺序就是数据流经它们的顺序。
>
> **校验口径**：`go build` / `go vet` / `gofmt -l` 全部通过（go 1.26、`github.com/redis/go-redis/v9 v9.22.0`）；
> 下面所有表格都是 `go test` 在本机的**实测输出**。
>
> ⚠️ **只有 `RedisPublisher` 没连真实 Redis 跑过**（本机没有 Redis 实例）——
> 它只做了编译校验，"Pub/Sub 不保留消息""订阅独占连接"这两条语义
> 沿用 [redis/缓存与分布式锁.md](redis/缓存与分布式锁.md) 的 Q7（两种发布订阅对比）与官方文档。
> 跨机器那一维是用**进程内 `Bus`** 顶替验证的：
> **它只能证明"逻辑对不对"，证明不了网络与多进程**。
>
> 结构是语言无关的——**下面「Java 版骨架」把这四段逐类型搬了一遍并重新实测**，
> 两处最容易走样的原语是
> `atomic.Pointer[[]*Sub]` → `AtomicReference<List<Sub>>`、`select{case ch<-m: default}` → `offer` + 有界 `ArrayBlockingQueue`。

**四层各自的落点**：

| 正文层级 | 落点类型 | 必须记住的那一句 |
|---|---|---|
| 第 1 层 限流 | `Limiter` 接口 + `FixedWindow` | 触发限流**直接丢弃**，不进入后面任何链路 |
| 第 2 层 双路径 | `Node.Accept` | 一个方法里同时喂**推送**（Publish）和**持久化**（Enqueue）两条路 |
| 第 3 层 批量落库 | `BatchWriter` | 攒批 + 定时 + **队列满就丢并计数**，三个开关缺一个就是事故 |
| 第 4 层 跨节点扇出 | `Publisher` / `RedisPublisher` / `Bus` + `Room` | 订阅关系用 **copy-on-write 快照**，慢连接用**非阻塞投递**隔离 |

#### 骨架 ①：数据面 + 第 1 层限流 + 第 4 层的抽象与 Redis 实现

```go

package barrage

import (
	"context"
	"strings"
	"sync"
	"time"

	"github.com/redis/go-redis/v9"
)

// Msg 是一条弹幕。Seq 由服务端分配，客户端用它做去重和乱序重排。
type Msg struct {
	Room string `json:"room"`
	UID  string `json:"uid"`
	Text string `json:"text"`
	Seq  int64  `json:"seq"`
}

// Encode/Decode 是推送与订阅两端的线格式。
//
// ⚠️ 这里**故意用 tab 分隔而不是 JSON**：正文第 4 层说"弹幕量极大"，
// 而序列化开销是**乘在推送链路上的**。实测（同一条弹幕：房间名 12 字符 + uid 9 字符 + 6 个汉字）：
// 线格式 48 字节，encoding/json 82 字节，**省 1.7 倍**；
// 换成 Protobuf 还能再小一半以上（字段名不进载荷，见 network/数据序列化.md 使用一的实测）。
// 一句话：**这里省的不是 CPU，是每台机器每秒几万条 × 连接数的那份带宽。**
func (m Msg) Encode() string {
	return strings.Join([]string{m.Room, m.UID, m.Text}, "\t") + "\t" + itoa(m.Seq)
}

func Decode(s string) (Msg, bool) {
	p := strings.SplitN(s, "\t", 4)
	if len(p) != 4 {
		return Msg{}, false
	}
	return Msg{Room: p[0], UID: p[1], Text: p[2], Seq: atoi(p[3])}, true
}

func itoa(v int64) string {
	if v == 0 {
		return "0"
	}
	var b [20]byte
	i := len(b)
	neg := v < 0
	if neg {
		v = -v
	}
	for v > 0 {
		i--
		b[i] = byte('0' + v%10)
		v /= 10
	}
	if neg {
		i--
		b[i] = '-'
	}
	return string(b[i:])
}

func atoi(s string) int64 {
	var v int64
	for _, r := range s {
		if r < '0' || r > '9' {
			return v
		}
		v = v*10 + int64(r-'0')
	}
	return v
}

// ── 第 1 层：限流 ─────────────────────────────────────────────────────────

// Limiter 只暴露一个方法，方便接 distributed/限流降级熔断.md 里的 RedisLimiter。
// 算法本身那篇已经写透了，这里只保留**接入点**。
type Limiter interface {
	Allow(ctx context.Context, uid string) bool
}

// FixedWindow 是"1 分钟 1 条"级别的最小占位实现（单机、按 uid）。
// 它只够跑通链路和做实验；**多节点部署时限流必须换成共享计数**，
// 否则 N 台机器各放一遍 = 实际限额是配置值的 N 倍。
type FixedWindow struct {
	mu   sync.Mutex
	seen map[string]time.Time
	dur  time.Duration
}

func NewFixedWindow(dur time.Duration) *FixedWindow {
	return &FixedWindow{seen: map[string]time.Time{}, dur: dur}
}

func (w *FixedWindow) Allow(_ context.Context, uid string) bool {
	w.mu.Lock()
	defer w.mu.Unlock()
	if t, ok := w.seen[uid]; ok && time.Since(t) < w.dur {
		return false // 触发限流：直接丢弃，不进入后续任何链路
	}
	w.seen[uid] = time.Now()
	return true
}

// ── 第 4 层：跨节点扇出的抽象 ────────────────────────────────────────────

// Publisher 是"把一条弹幕广播给所有节点"这件事的接口。
// 两个实现：RedisPublisher（生产）与 Bus（本机跑通链路、做实验）。
type Publisher interface {
	Publish(ctx context.Context, topic string, m Msg) error
	Subscribe(ctx context.Context, topic string, handler func(Msg)) (cancel func(), err error)
	Seq(ctx context.Context, topic string) (int64, error)
}

// RedisPublisher 用 Redis 发布订阅打通分布式节点（正文第 4 层）。
//
// ⚠️ 两个生产注意点（正文没提，但踩了才知道）：
//  1. **订阅必须用单独的连接**：rdb.Subscribe() 会独占一条连接，
//     拿它去干别的命令会一直阻塞——所以 Client 是单例，但 Subscript 是独立长连接。
//  2. **Pub/Sub 不保留消息**：节点订阅之前发的消息**永久丢失**，
//     断线重连后要用 Seq 从持久化链路补齐（见 barrage_4.go 的 BatchWriter）。
type RedisPublisher struct{ RDB *redis.Client }

func (p RedisPublisher) Publish(ctx context.Context, topic string, m Msg) error {
	return p.RDB.Publish(ctx, topic, m.Encode()).Err()
}

func (p RedisPublisher) Subscribe(ctx context.Context, topic string, handler func(Msg)) (func(), error) {
	sub := p.RDB.Subscribe(ctx, topic)
	ch := sub.Channel(redis.WithChannelSize(1024)) // 有界：慢消费者会在这里丢消息，而不是打爆内存
	go func() {
		for s := range ch {
			if m, ok := Decode(s.Payload); ok {
				handler(m)
			}
		}
	}()
	return func() { _ = sub.Close() }, nil
}

// Seq 用 INCR 拿全局递增序号（**它是"补漏"的依据**，不只是排序）。
func (p RedisPublisher) Seq(ctx context.Context, topic string) (int64, error) {
	return p.RDB.Incr(ctx, topic+":seq").Result()
}

```

> **`Client` 必须是单例**：`RedisPublisher{RDB: ...}` 只持有指针，
> 整个进程共用一个 `*redis.Client`（写法见 [redis/缓存与分布式锁.md](redis/缓存与分布式锁.md) 使用一的 `sync.OnceValue`）。
> 每个房间、每条连接各建一个 client，等于把连接池按请求数放大。

#### 骨架 ②：第 4 层的连接侧 —— 慢连接怎么隔离（`Sub` / `Room`）

```go

package barrage

import (
	"sync"
	"sync/atomic"
)

// Sub 是"一条 WebSocket 长连接"的抽象：正文第 4 层的所有结论都落在这个类型上。
//
// ★ 两个必须想清楚的点（正文只说了"各自推送给自己的在线用户"）：
//  1. 每个连接一个**有界**缓冲，而不是无界队列——
//     一个卡住的客户端（弱网、手机切后台）会把整房间的消息堆在自己队列里，
//     最终 OOM 的是**服务端**，不是客户端。
//  2. 投递用 **select + default 的非阻塞发送**：队满就丢并计数。
//     正文说"丢几条不影响业务"，这就是那句判断的代码形态——
//     **宁可丢，也绝不能让一个慢连接阻塞整个房间的广播**。
type Sub struct {
	ID string

	out     chan Msg
	dropped atomic.Int64
	sent    atomic.Int64
	closed  atomic.Bool
	once    sync.Once
}

func NewSub(id string, buf int) *Sub {
	return &Sub{ID: id, out: make(chan Msg, buf)}
}

func (s *Sub) trySend(m Msg) bool {
	if s.closed.Load() {
		return false
	}
	select {
	case s.out <- m:
		s.sent.Add(1)
		return true
	default:
		s.dropped.Add(1) // 慢客户端：丢这一条，继续服务别人
		return false
	}
}

// Out 交给该连接的写协程消费（真实项目里这里就是 ws WriteMessage 循环）。
func (s *Sub) Out() <-chan Msg { return s.out }

// Sent / Dropped 必须暴露给监控：**丢弃率是弹幕系统的健康度指标**。
// 只报 QPS 不报丢弃率，等于把"用户看不到弹幕"这件事藏起来。
func (s *Sub) Sent() int64    { return s.sent.Load() }
func (s *Sub) Dropped() int64 { return s.dropped.Load() }

// Close 幂等：主动离开、心跳超时、连接断开三条路径都会走到这里。
func (s *Sub) Close() {
	s.once.Do(func() {
		s.closed.Store(true)
		close(s.out)
	})
}

// Room 是一个房间的订阅集合。
//
// ★ 广播**读多写少**（每秒上千次广播、偶尔进出），
// 所以用 copy-on-write 快照，而不是"广播时持锁遍历 map"：
// 广播路径只 Load 一个指针；加人/踢人才整体换切片。
// 这和《服务发现与负载均衡》使用一里 Resolver 的 Snapshot 是同一个手法。
type Room struct {
	name string

	mu     sync.Mutex
	subs   map[string]*Sub
	snap   atomic.Pointer[[]*Sub]
	seq    atomic.Int64
	online atomic.Int64
}

func NewRoom(name string) *Room {
	r := &Room{name: name, subs: map[string]*Sub{}}
	empty := []*Sub{}
	r.snap.Store(&empty)
	return r
}

func (r *Room) Name() string { return r.name }

// Join 挂上一条连接并重建快照。重复 Join 同一个 ID 视作重连：先摘旧的。
func (r *Room) Join(s *Sub) {
	r.mu.Lock()
	if old, ok := r.subs[s.ID]; ok && old != s {
		delete(r.subs, s.ID)
		old.Close()
	}
	r.subs[s.ID] = s
	list := r.lockedListLocked()
	r.mu.Unlock()

	r.snap.Store(&list)
	r.online.Store(int64(len(list)))
}

// Leave 摘掉连接。**必须幂等**，且要 Close 释放那条连接的缓冲与写协程。
func (r *Room) Leave(id string) {
	r.mu.Lock()
	s, ok := r.subs[id]
	if !ok {
		r.mu.Unlock()
		return
	}
	delete(r.subs, id)
	list := r.lockedListLocked()
	r.mu.Unlock()

	r.snap.Store(&list)
	r.online.Store(int64(len(list)))
	s.Close()
}

// lockedListLocked 调用方必须持锁：把 map 摊成一份不可变切片。
func (r *Room) lockedListLocked() []*Sub {
	list := make([]*Sub, 0, len(r.subs))
	for _, s := range r.subs {
		list = append(list, s)
	}
	return list
}

// Online 返回当前连接数（读快照长度，不进临界区）。
func (r *Room) Online() int64 { return r.online.Load() }

// Broadcast 尽力投递给房间内所有连接，返回成功条数。
//
// 这里**没有锁**：慢连接的成本已经被 trySend 的 default 分支付掉了。
// 也**不改写 m.Seq**——序号在入口（Node.Accept）统一分配，
// 广播层再分配一次就会和持久化链路里的序号对不上，客户端没法去重。
func (r *Room) Broadcast(m Msg) int {
	list := *r.snap.Load()
	ok := 0
	for _, s := range list {
		if s.trySend(m) {
			ok++
		}
	}
	return ok
}

```

#### 骨架 ③：第 4 层的节点侧 —— `Node.Accept` 就是把四层串起来的顺序

```go

package barrage

import (
	"context"
	"fmt"
	"sync"
	"sync/atomic"
)

// Bus 是 Publisher 的**进程内实现**：用来在没有 Redis 的机器上跑通链路、做实验。
//
// 语义与 Redis Pub/Sub 对齐：
//   - 只投递给"当前已订阅该 topic"的处理函数（**不保留历史**）；
//   - 一次 Publish = 同步调用该 topic 的全部订阅者。
//
// ⚠️ 它是**单进程**的，只能验证"逻辑对不对"；
//
//	"跨机器"那一维必须由 RedisPublisher 承担（见 barrage_1.go）。
type Bus struct {
	mu   sync.Mutex
	next int64
	hand map[string]map[int64]func(Msg)
	snap atomic.Pointer[map[string][]func(Msg)]

	seq   atomic.Int64 // 进程内发号器（Redis 版是 INCR）
	noSub atomic.Int64 // 发出时该 topic 一个订阅者都没有 = 正文说的"推给了没有连接的机器"
}

func NewBus() *Bus {
	b := &Bus{hand: map[string]map[int64]func(Msg){}}
	m := map[string][]func(Msg){}
	b.snap.Store(&m)
	return b
}

// buildSnapshotLocked 由 hand 重算快照。调用方必须持锁。
// 读路径只 Load 指针、遍历时无锁，所以订阅关系变化不阻塞弹幕广播。
func (b *Bus) buildSnapshotLocked() map[string][]func(Msg) {
	out := make(map[string][]func(Msg), len(b.hand))
	for topic, hs := range b.hand {
		list := make([]func(Msg), 0, len(hs))
		for _, f := range hs {
			list = append(list, f)
		}
		out[topic] = list
	}
	return out
}

// Publish 把消息交给该 topic 的所有订阅者。
func (b *Bus) Publish(_ context.Context, topic string, m Msg) error {
	list := (*b.snap.Load())[topic]
	if len(list) == 0 {
		b.noSub.Add(1) // **静默丢失**：这就是 Pub/Sub 的语义，也是它必须配持久化链路的原因
		return nil
	}
	for _, f := range list {
		f(m)
	}
	return nil
}

// Subscribe 返回 cancel。**必须能用 cancel**：节点下线、房间关闭时不取消就会双份投递。
func (b *Bus) Subscribe(_ context.Context, topic string, handler func(Msg)) (func(), error) {
	b.mu.Lock()
	if b.hand[topic] == nil {
		b.hand[topic] = map[int64]func(Msg){}
	}
	id := b.next
	b.next++
	b.hand[topic][id] = handler
	snap := b.buildSnapshotLocked()
	b.mu.Unlock()
	b.snap.Store(&snap)

	var once sync.Once
	return func() {
		once.Do(func() { // 幂等：重复 cancel 不出错
			b.mu.Lock()
			defer b.mu.Unlock()
			delete(b.hand[topic], id)
			s := b.buildSnapshotLocked()
			b.snap.Store(&s)
		})
	}, nil
}

// Unsubscribed 是"发出去但没有任何节点订阅"的条数——正文那个坑的可观测指标。
func (b *Bus) Unsubscribed() int64 { return b.noSub.Load() }

// Seq 用进程内自增充当发号器。
// ⚠️ 多节点部署时它**必须**换成全局唯一（Redis INCR 或雪花），
//
//	否则两个节点会发出同一个 Seq，客户端去重就直接把弹幕吃掉。
func (b *Bus) Seq(_ context.Context, _ string) (int64, error) { return b.seq.Add(1), nil }

// Node 是一台弹幕服务器：本机持有若干房间连接，并订阅全局 topic 把弹幕扇给本机连接。
type Node struct {
	Name string

	pub     Publisher
	limiter Limiter
	bw      *BatchWriter // 可为 nil：纯推送节点不负责落库

	mu        sync.RWMutex
	rooms     map[string]*Room
	received  atomic.Int64
	delivered atomic.Int64
}

func NewNode(name string, pub Publisher, limiter Limiter, bw *BatchWriter) *Node {
	return &Node{Name: name, pub: pub, limiter: limiter, bw: bw, rooms: map[string]*Room{}}
}

// Room 取（或建）一个房间。
func (n *Node) Room(name string) *Room {
	n.mu.RLock()
	r, ok := n.rooms[name]
	n.mu.RUnlock()
	if ok {
		return r
	}
	n.mu.Lock()
	defer n.mu.Unlock()
	if r, ok := n.rooms[name]; ok {
		return r
	}
	r = NewRoom(name)
	n.rooms[name] = r
	return r
}

// ServeTopic 订阅弹幕 topic，把收到的每条弹幕投给本节点该房间的连接。
//
// ★ 这三行就是正文第 4 层的全部收益：
//
//	从此刻起，"用户连在哪台机器"和"弹幕打到哪台机器"**无关**。
func (n *Node) ServeTopic(ctx context.Context, topic string) (func(), error) {
	return n.pub.Subscribe(ctx, topic, func(m Msg) {
		n.received.Add(1)
		n.delivered.Add(int64(n.Room(m.Room).Broadcast(m)))
	})
}

// Accept 是弹幕进来的完整链路（正文第 1~4 层的顺序就在这一个方法里）。
// 返回 false = 被限流丢弃，调用方**不要重试**。
func (n *Node) Accept(ctx context.Context, m Msg, topic string) (bool, error) {
	if !n.limiter.Allow(ctx, m.UID) {
		return false, nil // 第 1 层：直接丢弃，不进入后续任何链路
	}
	seq, err := n.pub.Seq(ctx, topic)
	if err != nil {
		return false, fmt.Errorf("barrage: seq: %w", err)
	}
	m.Seq = seq
	m.Room = topic // 房间名 = topic 名：不给"发错房间"留机会
	if err := n.pub.Publish(ctx, topic, m); err != nil {
		return false, fmt.Errorf("barrage: publish: %w", err)
	}
	if n.bw != nil {
		n.bw.Enqueue(m) // 持久化链路：进批量缓冲，不直写 DB
	}
	return true, nil
}

// Received / Delivered：本节点"收到多少条"和"成功推给多少条连接"。
// 两个数一起看才知道丢在扇出还是在连接缓冲。
func (n *Node) Received() int64  { return n.received.Load() }
func (n *Node) Delivered() int64 { return n.delivered.Load() }
```

#### 骨架 ④：第 3 层的批量落库（`BatchWriter`）

```go

package barrage

import (
	"context"
	"sync"
	"sync/atomic"
	"time"
)

// Sink 是"批量落库"这一步的出口：生产是 MySQL/Mongo 的 batch insert
// （写法见 mysql/事务与日志.md、mysql/数据迁移与分表.md 的批量导入示例），
// 这里只约定接口，不重复写驱动。
type Sink interface {
	Write(ctx context.Context, batch []Msg) error
}

// BatchWriter 把正文第 3 层"尽可能改成批量操作"变成能用的东西。
//
// ★ 三个必须同时存在的开关，缺一个就是事故：
//  1. **攒够 N 条 flush**（吞吐）；
//  2. **超过 T 时间也 flush**（否则低峰期弹幕会**一直躺在内存里**，
//     进程一挂全丢——弹幕能容忍丢，但"因重启而丢一批未落盘的数据"是可避免的丢）；
//  3. **缓冲满时怎么办**（背压）。弹幕的答案是**丢掉新的并计数**，
//     而不是阻塞生产者——阻塞会顺着调用栈一路卡住 WebSocket 读循环。
type BatchWriter struct {
	sink   Sink
	max    int           // 单批条数
	interv time.Duration // 最长等待

	ch      chan Msg
	closed  chan struct{}
	once    sync.Once
	queued  atomic.Int64
	dropped atomic.Int64
	flushed atomic.Int64
	errs    atomic.Int64
}

func NewBatchWriter(sink Sink, max int, interv time.Duration, queueCap int) *BatchWriter {
	return &BatchWriter{
		sink: sink, max: max, interv: interv,
		ch: make(chan Msg, queueCap), closed: make(chan struct{}),
	}
}

// Enqueue 非阻塞入队。返回 false 表示这条弹幕**被丢弃**（必须打点）。
func (w *BatchWriter) Enqueue(m Msg) bool {
	select {
	case w.ch <- m:
		w.queued.Add(1)
		return true
	default:
		w.dropped.Add(1) // 背压时丢新数据：保内存、保推送链路，不保持久化
		return false
	}
}

// Run 是消费循环：攒批 + 定时 flush。用 ctx 控制退出。
func (w *BatchWriter) Run(ctx context.Context) {
	batch := make([]Msg, 0, w.max)
	t := time.NewTicker(w.interv)
	defer t.Stop()

	for {
		select {
		case m := <-w.ch:
			batch = append(batch, m)
			if len(batch) >= w.max {
				w.flush(ctx, batch)
				batch = batch[:0]
			}
		case <-t.C:
			if len(batch) > 0 {
				w.flush(ctx, batch)
				batch = batch[:0]
			}
		case <-ctx.Done():
			if len(batch) > 0 { // 退出前把剩下的写掉：**不要**把已入队的直接丢了
				w.flush(context.Background(), batch)
			}
			return
		}
	}
}

// flush 失败时**不重试**：弹幕是可容忍丢失的娱乐性数据，
// 重试要引入磁盘队列/退避，收益远小于复杂度。
// ⚠️ 换成订单、余额这类数据，这里**必须**改成"落本地 WAL + 重试 + 告警"。
func (w *BatchWriter) flush(ctx context.Context, batch []Msg) {
	if err := w.sink.Write(ctx, batch); err != nil {
		w.errs.Add(1)
		return
	}
	w.flushed.Add(int64(len(batch)))
}

// Stats 返回 (入队, 已落库, 丢弃, 失败批次数)。
// ⚠️ 丢弃率 / 入队 是这条链路的**核心 SLO**，别只报 QPS。
func (w *BatchWriter) Stats() (int64, int64, int64, int64) {
	return w.queued.Load(), w.flushed.Load(), w.dropped.Load(), w.errs.Load()
}

// MemSink 是跑通链路用的内存出口（生产请换成真实 batch insert）。
type MemSink struct {
	mu     sync.Mutex
	Msgs   []Msg
	Blocks time.Duration // >0 时模拟"落库变慢"，用来观察背压
}

func (s *MemSink) Write(_ context.Context, batch []Msg) error {
	if s.Blocks > 0 {
		time.Sleep(s.Blocks)
	}
	s.mu.Lock()
	s.Msgs = append(s.Msgs, batch...)
	s.mu.Unlock()
	return nil
}

// Written 返回已落库条数。
func (s *MemSink) Written() int {
	s.mu.Lock()
	defer s.mu.Unlock()
	return len(s.Msgs)
}
```

以下全部是 `go test` 的真实输出（本机单进程、内存版 `Bus`，不是编的理想值）。

**① 慢连接隔离：缓冲大小直接决定丢弃率**（一次广播 1000 条，两个订阅者：慢的不消费、快的正常消费）

| 每连接缓冲 | 慢连接收到 | 慢连接丢弃 | 快连接收到 |
|---|---|---|---|
| 0 | 0 | 1000 | 1000 |
| 1 | 1 | 999 | 1000 |
| 8 | 8 | 992 | 1000 |
| 64 | 64 | 936 | 1000 |
| 1024 | 1000 | 0 | 1000 |

> **要点不是"缓冲越大越好"**：快连接始终收到 1000 条，
> 说明**慢连接的丢弃完全没有传染给别人**——这才是第 4 层真正要买的东西。
> 缓冲取"能容忍卡顿多久"：`缓冲 / 每秒条数 = 可容忍的卡死秒数`。

**② 有没有共享总线 = 正文那个坑**（A、B 两个节点，用户在 B 上，弹幕从 A 进来）

| 场景 | A 节点 | B 节点 | 结论 |
|---|---|---|---|
| 只有单机内存映射 | 收到 100，投递 64 | **收到 0，投递 0** | B 上那个用户**永远看不到**弹幕 |
| 接入 Pub/Sub | 收到 100 | 收到 100 | 两端连接各收到 64 条 |
| topic 没有任何节点订阅 | — | — | `Unsubscribed=1`：消息**静默消失**，重连也补不回来 |

> 第 3 行是**必须配持久化链路的理由**：Pub/Sub 不保留消息，
> 断线期间错过的弹幕只能靠 `Seq` 从库里补——**这两条路径不是冗余，是互补**。

**③ 批量落库的背压**（队列容量 500、单批 100、入队 2000 条，出口耗时可调）

| 单批落库耗时 | 入队成功 | 丢弃 | 已落库 | 失败批次 |
|---|---|---|---|---|
| 0（不阻塞） | 500 | 1500 | 500 | 0 |
| 5ms | 600 | 1400 | 600 | 0 |

> 两行合起来的结论是：**队列一满就开始丢，落库变快变慢都救不回来**——
> 因为生产速度（纳秒级入队）远高于消费速度。
> 真正能救的是**加大队列 + 加消费协程**，或者反过来给入口限流（回到第 1 层）。
> 具体数字受调度影响，多次运行会在 500~600 之间浮动。

**④ 吞吐与限流**

| 指标 | 实测 |
|---|---|
| 广播 2000 条 × 1000 连接 = 2,000,000 次投递 | 484ms；**单次投递 ≈242ns，单条扇出 ≈242µs** |
| `FixedWindow(1 分钟/人)` 同一 uid 尝试 1000 条 | **放行 1 条**（其余 999 条在入口处就被丢，不占用后面三层任何资源） |
| 线格式 vs JSON（同一条弹幕） | 48 字节 vs 82 字节，**省 1.7 倍** |

> "单条扇出 242µs"这个数很值得记住：**它意味着单机广播的理论上限约 4000 条/秒/房间**，
> 而这是纯内存投递、不含 WebSocket 写与 TLS 加密。真算容量时要在这个数上再乘以
> 序列化 + 网络写的开销——**面试时报出"我量过单条扇出"这句话本身就是加分项**。

| Go（上面四段） | Java（本节） | 差在哪 |
|---|---|---|
| `chan Msg`（带缓冲） | `ArrayBlockingQueue<Msg>` | Java 没有 0 缓冲队列，`buf` 至少 1 |
| `select { case ch <- m: default }` | `queue.offer(m)` | **一模一样**：非阻塞、满了返回 false |
| `atomic.Pointer[[]*Sub]` 快照 | `AtomicReference<List<Sub>>` | Java 侧快照必须**不可变**（`List.copyOf`），否则读侧会看到写者的中间状态 |

| `go func(){ for range ch }` | `new Thread(...)` | ★ 一个连接 = **一个内核线程**，成本见下面第四组 |
| `context.WithCancel` | `volatile` 标志位 + 线程 `interrupt` | — |
| `sync.Once` | `AtomicBoolean.compareAndSet` | — |

**片段一：一条连接 = 有界队列 + 非阻塞投递 + 毒丸退出**（对应 `barrage_2.go` 的 `Sub`）

```java

	static final class Sub {
		final String id;
		/** 毒丸：见 close()。seq = -1 是正常弹幕不会用到的取值。 */
		static final Msg POISON = new Msg("", "", "", -1);

		private final ArrayBlockingQueue<Msg> out;
		private final AtomicLong sent = new AtomicLong();
		private final AtomicLong dropped = new AtomicLong();
		private final AtomicBoolean closed = new AtomicBoolean();

		Sub(String id, int buf) {
			this.id = id;
			this.out = new ArrayBlockingQueue<>(Math.max(1, buf)); // Java 没有 0 缓冲队列，见 main() 第四组的说明
		}

		/** 等价 Go 的 select+default：满了立刻返回 false，绝不阻塞调用方。 */
		boolean trySend(Msg m) {
			if (closed.get()) {
				return false;
			}
			if (out.offer(m)) {
				sent.incrementAndGet();
				return true;
			}
			dropped.incrementAndGet(); // 慢客户端：丢这一条，继续服务别人
			return false;
		}

		/** 丢弃率必须暴露给监控：只报 QPS 等于把"用户看不到弹幕"藏起来。 */
		long sent() {
			return sent.get();
		}

		long dropped() {
			return dropped.get();
		}

		/**
		 * 幂等：主动离开、心跳超时、连接断开三条路径都会走到这里。
		 *
		 * ⚠️ Java 没有 `close(chan)` 这种"关广播"的原语，等价做法是**塞一个毒丸**
		 * 让消费线程自己退出。队列满时毒丸可能塞不进——这里接受这个不完美，
		 * 因为消费线程是 daemon，进程退出时自然回收；
		 * 生产上要么给毒丸留一个空位（入队侧预留），要么改用 poll 超时轮询 closed 标志。
		 */
		void close() {
			if (closed.compareAndSet(false, true)) {
				out.offer(POISON);
			}
		}

		/**
		 * 该连接的写协程（真实项目里就是 ws WriteMessage 循环）。
		 * 用**无限期 take()**而不是 poll(超时)：轮询会把"1000 个连接各自每 20ms 醒一次"
		 * 变成一份稳定的空转开销，测出来的扇出成本就不干净了。
		 */
		void drain(Consumer<Msg> writer) throws InterruptedException {
			while (true) {
				Msg m = out.take();
				if (m == POISON) {
					return;
				}
				writer.accept(m);
			}
		}
	}
```

**片段二：房间的 COW 快照**（对应 `barrage_2.go` 的 `Room`，广播路径**不进锁**）

```java

	static final class Room {
		private final String name;
		private final Map<String, Sub> subs = new HashMap<>();
		private final AtomicReference<List<Sub>> snap = new AtomicReference<>(Collections.emptyList());
		private final AtomicLong online = new AtomicLong();

		Room(String name) {
			this.name = name;
		}

		String name() {
			return name;
		}

		synchronized void join(Sub s) {
			Sub old = subs.put(s.id, s);
			if (old != null && old != s) {
				old.close(); // 同 ID 重连：先摘旧的
			}
			publish();
		}

		synchronized void leave(String id) {
			Sub s = subs.remove(id);
			if (s == null) {
				return; // 幂等
			}
			publish();
			s.close();
		}

		/** 持锁时把 map 摊成一份不可变快照，读侧遍历它、不进临界区。 */
		private void publish() {
			snap.set(List.copyOf(subs.values()));
			online.set(subs.size());
		}

		long online() {
			return online.get();
		}

		/** 尽力投递给房间内所有连接，返回成功条数。<b>这里没有锁</b>。 */
		int broadcast(Msg m) {
			int ok = 0;
			for (Sub s : snap.get()) {
				if (s.trySend(m)) {
					ok++;
				}
			}
			return ok;
		}
	}
```

```java

		 * 消费循环。Go 用 select{case ch / case ticker / case ctx.Done}，

				sink.write(new ArrayList<>(batch));
```

**Java 侧实测**（5 次取的区间；完整文件是可直接跑的 `BarrageDesign.java`，

|---|---|---|---|
| ① 慢连接丢弃（缓冲 1 / 8 / 64 / 1024） | 丢 999 / 992 / 936 / 0 | **丢 999 / 992 / 936 / 0** | ✅ 逐格相同，快连接始终收到 1000 |
| ② 无共享总线 | A 收 100 投 64，B 收 0 | **A 收 100 投 64，B 收 0** | ✅ 相同 |
| ② 接 Pub/Sub | A、B 各收 100，两端连接各 64 | **完全相同**；`Unsubscribed=1` | ✅ 相同 |
| ③ 队列 500 / 入队 2000 | 入队 500~600 | 出口不阻塞时入队 **600~1461**（5 次：1461 / 925 / 836 / 696 / 600）；出口 5ms 时 500~600 | ⚠️ 结论同（队满即丢、落库数=入队数），但 Java 浮动更大：消费者线程**启动时机**直接决定它抢到多少条 |
| ④ 单次投递（2000 条 × 1000 连接） | ≈242~303 ns | **≈3.2~4.1 µs** | ❌ **差 10 倍以上，这一条最值得讲** |

第四组拆开看（Java 侧，每轮内部再取 3 轮最小，共跑 5 次程序）：

| 配置 | 单次投递 | 说明 |
|---|---|---|
| 1000 个连接**没有**消费者 | **≈69~83 ns** | 队列 + 锁本身就这么贵 |
| 1000 个**内核线程**消费者 | **≈3.2~4.1 µs** | ★ 唤醒成本占了 **≈98%** |
| 1000 个**虚拟线程**消费者（JDK 21） | **≈180~264 ns** | 回到 Go 量级（Go ≈242~303 ns） |

**三条只有把两边都跑过才讲得出的话**：

1. **广播的贵不贵在队列，而在"叫醒 1000 个内核线程"**：
   同一套结构，把消费者摘掉是 69ns，接上内核线程是 3.2µs —— 98% 是唤醒。
   Go 之所以量不出这一层，是因为它那 1000 个"连接写协程"本来就是协程。
2. **Java 21 的虚拟线程让这道题重新变成"结构问题"**：
   `BarrageVirtual.java` 只改了线程的创建方式（`Thread.ofVirtual()`），
   房间/队列/投递逻辑一行没动，单次投递就落到 180~264ns ≈ Go 的 242~303ns。
   这就是 [linux/进程与线程.md](linux/进程与线程.md) 里"协程轻在调度"最直接的证据。
3. **`close(chan)` 在 Java 里没有等价物**，只能塞毒丸，而毒丸**可能被满队列挡住**。
   这不是语法差异而是模型差异：Go 的通道是**一等公民**（可关闭、可广播给所有读者），
   Java 的队列只是一个容器。**面试里能指出这一条，比背"Java 并发包很丰富"有用得多。**

> 另外两处小差异也记一下，免得以为是 bug：
> ① Java 没有 0 缓冲队列，所以 Go 表里"缓冲 0 → 丢 1000"那档在 Java 侧不存在；
> ② 线格式体积两边完全一致（48 字节 vs JSON 82 字节），
> 但 Java 侧的 JSON 是按 `encoding/json` 的等价输出**手工拼**的（本机没引 Jackson），只用于体积对比。

#### 一句话收口

> 四层的骨架其实只有三件事：**入口把不合规的挡掉（限流直接丢）、
> 扇出把慢的隔离掉（有界缓冲 + 非阻塞投递 + COW 快照）、
> 落库把散的攒起来（攒批 + 定时 + 背压丢）**；
> 而 `Node.Accept` 里那 15 行，就是"双路径分流"这句话的全部实现。

## Q2. 文件服务器如何选型？（Ceph vs 对象存储）

**来源**：`p=15` 百度 Go 前端一面 · 时长 13分36秒
**考察意图**：**这题考的是"选型方法"而不是"性能对比"**——
面试官想听你先问需求，而不是先比较参数。

### 选型第一原则（先答这个）

> **从需求出发，从熟悉程度出发，而不是从性能出发。**

原因：
- **成型的文件系统不会有太拉垮的性能**，性能差异通常在百分之几；
- 很多业务**根本到不了需要考虑那百分之几性能的量级**；
- 所以更该关注的是：**哪个方案能更好解决实际问题、团队更熟悉哪个**。

### 三类方案的适用场景

#### ① 分布式文件系统（Ceph 等）—— 需要共享

**场景**：K8s 环境。所有容器/Pod **部署在多台机器上**，机器之间需要**共享文件或磁盘**。

具体例子：
- 在 K8s 里搭建 **Docker 私有镜像仓库**，把镜像都存在一个位置，
  **所有集群节点共享同一个文件系统**（镜像存在这里）；
- **有状态应用**（etcd、Redis、MySQL）：每个 Pod 需要一块**独立的存储块设备**（RBD），
  这类也用 Ceph 提供。

**原理**：把设备以**类似网盘 / 共享文件夹**的形式**挂载到操作系统**的某个目录上。
对使用者来说，**操作它就是复制文件到目录、从目录取文件**，
与本地文件夹**几乎没有区别**。

**唯一区别**：**挂载动作需要权限校验**，之后的读写就不需要了。
好处是**隐藏了文件上传/下载的细节**——开发时就像操作本地目录。

#### ② 对象存储（COS / OSS 等）—— 不需要共享

**场景**：普通网站里的**图片、用户头像**等静态文件。

特征：
- **不需要在多个操作系统/节点之间共享**；
- 只需要**持久化保存**，以及**偶尔被用户查看**。

满足这两点，用对象存储就够了。

### 传输失败怎么办？（第二问）

取决于**上传方式**——如果是"业务服务器上传到文件服务器"，失败处理如下：

**① 断点续传 + 重试**

重试要做**退避策略**，不要无脑重试：

```
第 1 次失败 → 5 秒后重试
第 2 次失败 → 10 秒后重试
第 3 次失败 → 1 分钟后重试
第 4 次失败 → 5 分钟后重试
最多重试 5~10 次
```

**为什么要退避**：
- **正常的请求**（如网络抖动）重试一两次就会成功；
- **不正常的请求**（如资源不存在、权限错误）**重试多少次都不会成功**，
  只会白白消耗资源。

**② 监控告警**

- 用 **Prometheus** 监控文件服务器，或由业务服务器**上报失败指标**；
- 多次失败后通过**邮件 / 企业微信**通知开发人员，及时感知重试情况。

### 要不要经过业务服务器？（第三问，加分点）

**判断标准很简单**：

> **如果文件上传到业务服务器后"什么都不做"，只是原样转发给文件服务器，
> 那就没有理由经过业务服务器——直接绕过。**

**绕过的好处（前端直传对象存储）**：
- 文件从客户端 → 业务服务器 → 对象存储，**要走两次网络**
  （消耗两次带宽，也消耗两倍时间）；
- 直传只有**一次上传**，**减少一次上传时间，同时大幅降低业务服务器负载**。

**必须经过业务服务器的例外**：
- 文件**需要在业务侧处理**，例如报表文件需要**导入数据库**；
- 处理完之后，再把文件**备份到文件服务**。

### COS 直传的两步实现（以腾讯云 COS 为例）

| 步骤 | 谁做 | 内容 |
|---|---|---|
| **① 换临时密钥** | 后端 | 用**永久密钥换取临时密钥**，临时密钥有**有效期**（如 30 分钟 / 1 小时）——避免把永久密钥暴露给前端 |
| **② 生成预签名 URL** | 后端 | 根据文件名等信息**签名**，下发预签名上传地址和访问地址 |
| **③ 上传** | 前端 | 对预签名 URL 发 **PUT** 请求，**以二进制方式**传输文件内容 |

**验证方式**：上传返回 **HTTP 200** 即表示成功，可直接用返回的访问地址下载核对内容。

> **安全要点**：**前端永远拿不到永久密钥**，只拿到**有时效的临时凭证和预签名 URL**，
> 即使泄露也只在有效期内可用。

### 落地实现：直传凭证的最小可运行骨架（Go，已编译校验 + 已测）

> 正文给了三步（换临时密钥 / 生成预签名 URL / 前端 PUT），
> 但那句"**前端永远拿不到永久密钥**、即使泄露也只在有效期内可用"是**一句可以被测出来的话**。
> 这一节就把凭证写成能跑的实现，再用篡改测试逐条验证。
>
> **校验口径**：`go build` / `go vet` / `gofmt -l` 通过（go 1.26，纯标准库），
> 下面的表是 `go test` 的真实输出。
>
> ⚠️ 这里实现的是**通用 HMAC 预签名**（结构与 AWS SigV4 / 腾讯云 COS 一致，但字段名和算法不同）。
> **接真实对象存储时请直接用官方 SDK 的 PresignedUpload**，不要拿这套签名去对厂商的格式。

```go

package upload

import (
	"crypto/hmac"
	"crypto/sha256"
	"encoding/hex"
	"errors"
	"fmt"
	"net/http"
	"net/url"
	"strconv"
	"strings"
	"time"
)

// 直传的落地形态只有三件事：**后端签名、前端 PUT、后端只发凭证**。
// 正文那句"前端永远拿不到永久密钥"在这段代码里是可验证的：
// 前端拿到的是**一个带过期时间的签名串**，拿不到 secret 本身。
//
// ⚠️ 这里实现的是**通用 HMAC 预签名**（与 AWS SigV4 / 腾讯云 COS 的字段不同但结构一致），
// 用来把"签名 → 校验 → 过期"这条链路跑通并测出行为。
// **接真实对象存储时请直接用官方 SDK 的 PresignedUpload**，不要手改这套签名格式。

// Policy 是一次上传的授权范围。**签名必须把所有授权字段全签进去**：
// 只签 key 的话，前端把 size 上限或有效期改掉，签名照样通过 = 授权形同虚设。
//
// 注意这里**没有 secret 字段**——secret 只作为参数传给 Sign/Verify。
// 混进结构体就会被顺手 JSON 序列化下发出去，正文"前端永远拿不到永久密钥"那句就破功了。
type Policy struct {
	Key         string    // 对象键，通常带用户前缀：uid/2026/09/uuid.png
	MaxSize     int64     // 字节
	ExpireAt    time.Time // 过期时刻（UTC）
	ContentType string    // 允许的 Content-Type，空 = 不限
}

// canonical 是签名覆盖的原文。**签发和校验必须走同一个函数、同一套字段顺序**，
// 否则就会踩中"签名算法两边各写一遍、某天对不上"这个经典事故。
func canonical(method, key, max, ctype, exp string) string {
	return strings.Join([]string{method, key, max, ctype, exp}, "\x00")
}

func (p Policy) canonical() string {
	return canonical(http.MethodPut, p.Key, strconv.FormatInt(p.MaxSize, 10), p.ContentType,
		p.ExpireAt.UTC().Format(time.RFC3339))
}

// signWith 是**唯一的**签名实现：签发与校验必须共用同一个函数。
// 两边各写一遍是这类手工签名最常见的事故——某天字段顺序变了，
// 只有服务端发现，前端已经发出去的一批 URL 全在报 403。
func signWith(secret, canon string) string {
	mac := hmac.New(sha256.New, []byte(secret))
	mac.Write([]byte(canon))
	return hex.EncodeToString(mac.Sum(nil))
}

// Sign 对授权字段做 HMAC-SHA256。字段间用 \x00 分隔，
// 避免"字段里含分隔符"造成签名歧义（拼接式签名的经典坑）。
func (p Policy) Sign(secret string) string { return signWith(secret, p.canonical()) }

// PresignedURL 是给前端的完整地址：凭证全在 query 里，前端不需要任何密钥。
//
// ⚠️ 必须用 url.Values 编码，不能手拼字符串：对象键是用户可影响的输入，
// 里面出现 & 或 + 时手拼会把参数结构改掉（等价于参数注入）。
func (p Policy) PresignedURL(host, secret string) string {
	q := url.Values{}
	q.Set("key", p.Key)
	q.Set("max", strconv.FormatInt(p.MaxSize, 10))
	q.Set("ctype", p.ContentType)
	q.Set("exp", p.ExpireAt.UTC().Format(time.RFC3339))
	q.Set("sig", p.Sign(secret))
	return strings.TrimSuffix(host, "/") + "/upload?" + q.Encode()
}

// 下面每种拒绝原因都要**分开打点**：只报一个模糊的 403，线上就查不动"为什么传不上去"。
var (
	ErrNoSecret  = errors.New("upload: 服务端未配置 secret")
	ErrNoCred    = errors.New("upload: 凭证字段缺失")
	ErrBadSign   = errors.New("upload: 签名不匹配（被篡改或密钥不一致）")
	ErrBadFormat = errors.New("upload: 凭证字段格式非法（签发端与校验端不一致）")
	ErrExpired   = errors.New("upload: 凭证已过期")
	ErrTooLarge  = errors.New("upload: 超过授权大小")
	ErrBadType   = errors.New("upload: Content-Type 不在授权范围内")
	ErrBadMagic  = errors.New("upload: 文件头与允许类型不符（伪造扩展名）")
)

// Verify 是接收端（或网关）的校验。
//
// ★ 顺序就是这段代码的意义：**先验签，再信字段**。
// 如果先解析 max/exp 去判断大小和过期，攻击者只要改一个字段就能绕开限制——
// 未验签的输入一律当作不可信，格式错误也必须在验签之后才可能出现在"合法"凭证上。
func Verify(r *http.Request, secret string, now time.Time) error {
	if secret == "" {
		return ErrNoSecret
	}
	q := r.URL.Query()
	key, maxS, expS, ctype, sig :=
		q.Get("key"), q.Get("max"), q.Get("exp"), q.Get("ctype"), q.Get("sig")
	if key == "" || sig == "" || expS == "" {
		return ErrNoCred
	}
	// 1) 用**原始字符串**重算签名再比对（定时安全比较，不要用 ==）
	if !hmac.Equal([]byte(signWith(secret, canonical(http.MethodPut, key, maxS, ctype, expS))), []byte(sig)) {
		return ErrBadSign
	}
	// 2) 验签通过后字段就是自己签出去的，这里解析失败只可能是两端格式不一致
	max, err1 := strconv.ParseInt(maxS, 10, 64)
	exp, err2 := time.Parse(time.RFC3339, expS)
	if err1 != nil || err2 != nil {
		return ErrBadFormat
	}
	if !now.Before(exp) {
		return ErrExpired
	}
	if r.ContentLength > max {
		return ErrTooLarge
	}
	if ctype != "" && !strings.EqualFold(r.Header.Get("Content-Type"), ctype) {
		return ErrBadType
	}
	return nil
}

// magicOf 按文件头判断真实类型。**扩展名和 Content-Type 都是客户端说了算的**，
// 只要文件之后会被浏览器直接打开，就必须校验文件头：
// 别人传一个"后缀 .png 内容是 HTML"的片子，访问时被当网页执行 = 存储型 XSS。
// （这也是正文 Q4"文件别放业务服务器"的延伸：放在自己域名下时，这类漏洞算你头上。）
func magicOf(b []byte) (string, bool) {
	head := func(n int) string {
		if len(b) < n {
			return ""
		}
		return hex.EncodeToString(b[:n])
	}
	switch {
	case strings.HasPrefix(head(8), "89504e470d0a1a0a"):
		return "image/png", true
	case strings.HasPrefix(head(3), "ffd8ff"):
		return "image/jpeg", true
	case strings.HasPrefix(head(6), "474946383761"), strings.HasPrefix(head(6), "474946383961"):
		return "image/gif", true
	case len(b) >= 12 && string(b[4:8]) == "ftyp":
		return "video/mp4", true
	default:
		return "", false
	}
}

// CheckMagic 校验开头的若干字节：真实类型必须是 allow 里的一个。
func CheckMagic(head []byte, allow []string) error {
	got, ok := magicOf(head)
	if !ok {
		return fmt.Errorf("%w: 认不出文件头", ErrBadMagic)
	}
	for _, a := range allow {
		if a == got {
			return nil
		}
	}
	return fmt.Errorf("%w: 实际 %s 不在允许列表 %v", ErrBadMagic, got, allow)
}

```

#### 实测：把正文那句"安全要点"逐条攻击一遍

| 攻击 / 场景 | 结果 | 说明 |
|---|---|---|
| 正常凭证 PUT | **通过** | 下发的 URL 里只有 `sig=`，**不含 secret** |
| 把 `max` 改大到 1GB | 签名不匹配 | 大小上限**被签进了签名**，改不动 |
| 把有效期延到 10 年后 | 签名不匹配 | 同上——"只在有效期内可用"是这么保证的 |
| 换 `key` 写到别人目录（越权） | 签名不匹配 | 对象键也在签名里 |
| 把 `ctype` 清空以放开类型 | 签名不匹配 | 连"留空"这个动作都会改变签名 |
| 直接去掉 `sig` | 凭证字段缺失 | 与"签名不对"分开打点 |
| 用另一把服务端 secret 校验 | 签名不匹配 | 密钥轮换期间的双验要自己加，这里只演示单密钥 |
| 凭证过期 1 小时后使用（签名仍合法） | **凭证已过期** | 校验的是 `now`，**不是客户端时间** |
| `Content-Length` 超过 `max` | 超过授权大小 | 签名合法也拦得住实际大小 |
| 声明 `image/png` 实际发 HTML | 类型不符 / 文件头认不出 | **扩展名与 Content-Type 都不可信**，必须看文件头 |

#### 三条只有写出来才会注意到的点

1. **先验签、再信字段**：`Verify` 里判断大小和过期的 `max`/`exp` 都来自 query，
   如果解析在比对之前，攻击者改字段就能绕限制——**顺序本身就是安全属性**。
2. **签发与校验共用 `canonical` + `signWith`**：两处各写一遍签名逻辑，
   早晚会不一致（表现为"一部分前端拿的 URL 突然全 403"）。
   比对签名用 `hmac.Equal` 而不是 `==`。
3. **凭证里不能塞 secret 字段**、query 必须用 `url.Values` 编码：
   前者会被顺手 JSON 下发，后者在手拼时会被 `&`/`+` 改变参数结构。

> **面试时怎么把这段讲出来**：正文的三步是流程，
> 这段代码回答的是"**为什么这样就不会泄露密钥**"——
> 因为授权范围（键名、大小、类型、有效期）**全都在签名里，改任何一项签名就废**，
> 而且**过期判断用的是服务端时间**。能补上这一句，这题就从"背流程"变成"懂原理"。

## Q3. 场景题：设计一个朋友圈

**来源**：`p=60` 字节跳动后端面试 · 时长 20分30秒
**考察意图**：场景题**没有标准答案**，考的是**应变能力和思考过程**——

> **面试官要的不是"标准的微信朋友圈方案"，
> 而是你自己的思路：为什么这么设计、设计时有哪些考量。**
>
> **答案离谱不行，但有思路、有取舍、能讲清理由，就是好答案。**

### 一、第一步：要素分析（先想清楚"有什么"）

划出**三类核心信息**：

| 要素 | 说明 |
|---|---|
| **① 朋友与用户** | 朋友圈一定涉及"人" |
| **② 图文、视频等信息** | 即朋友圈的**条目 / 动态** |
| **③ 评论与点赞** | 针对动态产生的互动 |

> **注意**：面试时想不到所有细节是**正常的**——
> 实际开发也一样，**先定大方向，后续开发中遇到问题再迭代**，
> 不会一开始就设计得极其细致。

### 二、第二步：分析朋友圈的三个特点

| 特点 | 内容 |
|---|---|
| **① 数据展示范围固定** | 展示**自己通讯录里所有朋友 + 自己**发的动态 |
| **② 数据展示顺序固定** | **按时间倒序**——最新的在最上面 |
| **③ 热点数据** | 用户通常只看**一小时以内**的，最多**一天以内**。<br>→ **保守设计为"两天内的热点数据"**；<br>后续可根据**数据打点**再决定是两小时、一天还是两天 |

> 关于第 ③ 点要**主动承认这是拍脑袋**：
> "先按两天设计，后续根据打点数据调整"——**这种诚实的表达反而加分**。

### 三、第三步：ER 图与表设计

| 表 | 关系 | 说明 |
|---|---|---|
| **用户表** | — | 用户主体信息 |
| **朋友表（通讯录表）** | **用户 ↔ 朋友：多对多** | A 加 B、B 加 A 是**相互**的，本质是用户与自己的关系（用独立表表达） |
| **动态表** | **用户 → 动态：一对多** | 一个用户可发多条动态 |
| **用户-动态关系表** | **用户 ↔ 动态：多对多** | **决定"这个用户能看到哪些动态"** |
| **评论表 / 点赞表** | **动态 → 评论/点赞：一对多** | 无特殊逻辑 |

**⭐ 为什么一定要建"用户-动态"多对多关系表？（这是本题最重要的设计思考）**

> **朋友圈的「发布量」远小于「查看量」。**
>
> 举例：100 个人里，可能 **90 个人只是在看、点赞、评论，只有 10 个人在发布**。
>
> **所以**：
> - **在「发布」时维护这份多对多关系**（写少，代价可控）；
> - **避免在「查看」时再去关联查找**（读多，必须快）。
>
> **如果不这样设计**，查看时要先查朋友关系 → 再查这些朋友发的动态，
> **每次查询都要多绕几步**；而查看的频次是发布的好几倍。
>
> **本质：用空间换时间**——发布时多存一份关系（消耗空间），
> 换来查询时**可以直接从关系表命中**（不消耗额外的关联开销）。

### 四、第四步：数据分层与缓存设计

**三层结构**：

#### 第 1 层：DB（按数据特征选型）

| 数据 | 存储 | 理由 |
|---|---|---|
| 用户、朋友关系、评论、点赞 | **MySQL（关系型）** | 这些是**结构化数据**，每行字段一致 |
| 动态（图文/图片/视频/链接） | **MongoDB（文档型）** | 动态的**格式不固定**（可能纯文字、可能图文、可能视频），<br>用文档型更合适 |

> （原视频也说了：**都用 MySQL 存也可以**，只是选型上文档型更贴合动态数据特征。）

**为什么需要缓存层（讲清动机，比讲方案更重要）**：

> 如果不区分热点数据——**全放数据库扛不住**；
> **全放缓存又浪费大量缓存空间、成本上升**。
> 所以要**按热点范围缓存**。

#### 第 2 层：缓存（Redis），缓存两类数据

| 缓存内容 | 策略 |
|---|---|
| **动态数据** | **两天内的动态全量缓存**。<br>新增数据用**双写**（写库 + 写缓存）；<br>或**应用启动时预热**（把两天内的数据全量加载进缓存） |
| **用户-动态多对多关系** | 缓存这份关系 → **直接就能拿到"我两天内能看的朋友圈"**，<br>无需回表关联 |

**两天之前的数据**：
> 需要时**回源 DB**，再放进缓存，**设置一天的有效期**；
> 过期后从缓存移除，下次加载再回源。

#### 第 3 层：应用层 / 客户端

| 设计 | 说明 |
|---|---|
| **分页加载** | 一次加载一页，**每页 10~20 条**，最多不超过 50 条 |
| **应用本地缓存** | 用户退出朋友圈再进来时，**本地已有数据就不用再拉** |

### 五、面试答题结构（三步走）

```
① 要素与特点分析  → 人 / 动态 / 互动，范围固定、时间倒序、热点两天
② 表设计（ER 图） → 用户、朋友（多对多）、动态（一对多）、用户-动态（多对多）
                    ★ 重点讲清"为什么要在发布时维护多对多关系"
③ 数据分层与缓存  → MySQL 存结构化 / MongoDB 存动态 / Redis 缓存动态与关系
                    / 应用层分页 + 本地缓存
```

> **最值钱的是第 ② 步里那个"发布量 << 查看量 → 空间换时间"的判断**，
> 以及第 ③ 步里"为什么要区分热点数据"的动机说明。

### 面试官会追问什么

- **朋友关系为什么要多对多，不能一对多吗？** → 一对多会出现**重复条目**（A 加 B、B 加 A 各存一条），
  而且**反查"谁加了我"**很麻烦；多对多关系表天然解决双向问题。
- **删除好友怎么办？** → 删关系表记录，同时按需清理相关缓存（**注意缓存与 DB 的一致性**）。
- **大 V 发一条动态要写给几千万人吗？** → **不能**（写扩散爆炸）。
  这类**读扩散**场景要改成 **Pull 模式**（拉取时聚合），
  或**混合模式**（普通用户写扩散、大 V 读扩散）——**这是本题最好的加分回答**。
- **怎么保证动态的顺序？** → 用**发号器（雪花算法）** 生成有序 ID，
  按 ID 倒序即等价于按时间倒序（**避免同一秒内时间戳无法区分先后**）。

### 落地实现：最小可运行骨架（Go，已编译校验 + 已实测）

> 正文给了 ER 图和数据分层，但两句最值钱的话——**"发布时维护多对多关系（空间换时间）"
> 和"大 V 不能写扩散"**——只有落成代码才看得出各自的代价。
> 这一节就把它们写成两份能跑的文件，并把**写放大、读放大、游标分页稳定性**实测出来。
>
> **校验口径**：`go build` / `go vet` / `gofmt -l` 全部通过（go 1.26，纯标准库，无第三方依赖）。
>
> ⚠️ **这是纯内存骨架**：`map[int64][]Post` 顶替的是 MySQL/Redis 的位置，
> 所以**测出来的是"算法复杂度"，不是"线上延迟"**——真实系统里读扩散那 1001 次查询
> 是 1001 次网络往返，比这里测到的还要贵几个数量级。
> 单机、单进程，**没有验证过分库分表、缓存一致性与故障恢复**。
>
> `Graph` / `PushTimeline` / `PullTimeline` 三个类型是语言无关的——
> **下面「Java 版骨架」把它们逐类型搬了一遍并重新实测**，写放大与分页稳定性的数字两边完全一致。

**正文每一步的落点**：

| 正文的那句话 | 落点类型 | 实测出来的代价 |
|---|---|---|
| "按 ID 倒序即等价于按时间倒序" | `Flake.Next` | 单实例 20 万个号无重复且单调 |
| "朋友是多对多" | `Graph`（following + followers 两份反向索引） | — |
| "发布量 << 查看量 → 空间换时间" | `PushTimeline`（写扩散） | 200 粉写 **202** 份，读 **0.4µs** |
| "大 V 发一条要写给几千万人吗？→ 不能" | `PullTimeline`（读扩散） | 写 **1** 份，读 **811µs**（关注 1000 人时） |
| "混合模式（普通用户写扩散、大 V 读扩散）" | `HybridTimeline` + 粉丝数阈值 | 大 V 写 **1** 份，读 **155µs** |

#### 骨架 ①：发号器 + 关系图 + 写扩散/读扩散两条路径

```go

package moments

import (
	"sort"
	"sync"
	"time"
)

// Flake 是正文追问里"怎么保证动态顺序"的答案：**带时间戳的单调 ID**。
//
// 为什么不能用 created_at 排序：同一毫秒内多人并发发布，时间戳相同，
// 分页时"上一页最后一条"和"下一页第一条"就会重复或漏掉。
// 用单调递增 ID 排序 = 天然唯一 + 天然有序，游标分页才有稳定边界。
type Flake struct {
	mu   sync.Mutex
	last int64
	seq  int64
}

// 位分配：41 位毫秒时间戳 | 10 位机器号 | 12 位序列号（够用 24 年 × 1024 台 × 每毫秒 4096 条）
const (
	nodeBits = 10
	seqBits  = 12
	maxSeq   = 1<<seqBits - 1
)

func (f *Flake) Next(node int64) int64 {
	f.mu.Lock()
	defer f.mu.Unlock()

	ms := time.Now().UnixMilli()
	switch {
	case ms > f.last:
		f.seq = 0
	case f.seq < maxSeq:
		// 同一毫秒继续取号。**ms < f.last 就是时钟回拨**（NTP 校时、虚机迁移）：
		// 这里沿用上一次的毫秒位、只递增序列号，宁可"看起来慢一毫秒"也不让 ID 倒退。
		ms = f.last
		f.seq++
	default:
		// 序列号用满 → 等到下一毫秒，**绝不回绕**（回绕必然产生重复 ID）
		for ms <= f.last {
			ms = time.Now().UnixMilli()
		}
		f.seq = 0
	}
	f.last = ms // ⚠️ 必须在这里统一写回：漏掉这一步，下一毫秒的首个号会和上一个重复
	return ms<<(nodeBits+seqBits) | (node&((1<<nodeBits)-1))<<seqBits | f.seq
}

// Time 从 ID 反解出毫秒时间戳：游标里只存 ID，前端展示时间靠它。
func Time(id int64) time.Time {
	return time.UnixMilli(id >> (nodeBits + seqBits))
}

// Post 是一条动态。
type Post struct {
	ID     int64
	Author int64
	Text   string
}

// Graph 是关注关系。正文说"朋友是多对多"，这里用两份反向索引表达：
// following 决定"我能看到谁"，followers 决定"我发一条要写多少份"。
type Graph struct {
	mu        sync.RWMutex
	following map[int64]map[int64]bool
	followers map[int64]map[int64]bool
}

func NewGraph() *Graph {
	return &Graph{following: map[int64]map[int64]bool{}, followers: map[int64]map[int64]bool{}}
}

func (g *Graph) Follow(from, to int64) {
	g.mu.Lock()
	defer g.mu.Unlock()
	if g.following[from] == nil {
		g.following[from] = map[int64]bool{}
	}
	if g.followers[to] == nil {
		g.followers[to] = map[int64]bool{}
	}
	g.following[from][to] = true
	g.followers[to][from] = true
}

// Unfollow 删关系。⚠️ 正文追问"删好友怎么办"：
// 光删关系表**不够**，已经写进对方时间线（写扩散）的动态必须一并处理，
// 否则"删了好友还能看到对方动态"。这里的做法是重建该用户时间线。
func (g *Graph) Unfollow(from, to int64) {
	g.mu.Lock()
	defer g.mu.Unlock()
	delete(g.following[from], to)
	delete(g.followers[to], from)
}

func (g *Graph) Following(u int64) []int64 {
	g.mu.RLock()
	defer g.mu.RUnlock()
	out := make([]int64, 0, len(g.following[u]))
	for v := range g.following[u] {
		out = append(out, v)
	}
	sort.Slice(out, func(i, j int) bool { return out[i] > out[j] }) // 大 ID = 新，方便后面归并
	return out
}

func (g *Graph) Followers(u int64) []int64 {
	g.mu.RLock()
	defer g.mu.RUnlock()
	out := make([]int64, 0, len(g.followers[u]))
	for v := range g.followers[u] {
		out = append(out, v)
	}
	return out
}

// PushTimeline 是**写扩散**：发布时就把动态塞进每个粉丝的时间线。
// 对应正文那句"发布量 << 查看量，所以发布时多存一份关系，用空间换时间"。
type PushTimeline struct {
	mu   sync.RWMutex
	feed map[int64][]Post // key = 用户 ID，值已按 ID 倒序
	// writes 统计"这条动态实际落了几份"——写放大的直接指标
	writes int64
}

func NewPushTimeline() *PushTimeline {
	return &PushTimeline{feed: map[int64][]Post{}}
}

// dedup 对目标集合去重。★ 一个很容易踩到的真实 bug：
//
//	作者关注了自己（互关场景下的自引用）时，Followers(author) 里已经有 author，
//	再无脑 append(author) 就把同一条动态写两份 → 时间线里出现重复条目，
//	游标翻页时表现为"上一页 7 条、下一页还是这 7 条"。
//
// 结论：**写扩散 / 读归并之前，先对目标集合去重。**
func dedup(ids []int64) []int64 {
	seen := make(map[int64]bool, len(ids))
	out := make([]int64, 0, len(ids))
	for _, id := range ids {
		if seen[id] {
			continue
		}
		seen[id] = true
		out = append(out, id)
	}
	return out
}

// insertDesc 把一条动态插入**倒序**列表的正确位置。
//
// ⚠️ 不能无脑头部插入：生产上扩散是异步的（MQ、多节点、失败重投），
// 更早的动态可能后到，头部插入会让列表失序 → 游标分页重复或漏条目。
func insertDesc(list []Post, p Post) []Post {
	i := 0
	for i < len(list) && list[i].ID > p.ID {
		i++
	}
	list = append(list, Post{})
	copy(list[i+1:], list[i:])
	list[i] = p
	return list
}

// Publish 往作者所有粉丝（含自己）的时间线插一条，返回实际写的份数。
func (t *PushTimeline) Publish(p Post, g *Graph) int {
	targets := dedup(append(g.Followers(p.Author), p.Author))
	t.mu.Lock()
	defer t.mu.Unlock()
	for _, u := range targets {
		// 按 ID 插入有序位置：列表始终倒序，读的时候直接切前 N 条，**零排序成本**
		t.feed[u] = insertDesc(t.feed[u], p)
	}
	t.writes += int64(len(targets))
	return len(targets)
}

// Feed 是**读路径**：只切一段，不做任何聚合。
func (t *PushTimeline) Feed(uid int64, before int64, limit int) []Post {
	t.mu.RLock()
	defer t.mu.RUnlock()
	list := t.feed[uid]
	out := make([]Post, 0, limit)
	for _, p := range list {
		if before != 0 && p.ID >= before { // before = 上一页最后一条的 ID（游标）
			continue
		}
		out = append(out, p)
		if len(out) == limit {
			break
		}
	}
	return out
}

// Writes 返回写扩散累计落库份数。
func (t *PushTimeline) Writes() int64 {
	t.mu.RLock()
	defer t.mu.RUnlock()
	return t.writes
}

// PullTimeline 是**读扩散**：只存"我发的动态"，读的时候把关注对象的列表归并。
type PullTimeline struct {
	mu    sync.RWMutex
	posts map[int64][]Post // key = 作者 ID
}

func NewPullTimeline() *PullTimeline { return &PullTimeline{posts: map[int64][]Post{}} }

// Publish 只写一份——这就是读扩散唯一的优势。
func (t *PullTimeline) Publish(p Post) int {
	t.mu.Lock()
	defer t.mu.Unlock()
	t.posts[p.Author] = insertDesc(t.posts[p.Author], p)
	return 1
}

// Feed 归并 k 个有序列表取前 limit 条（k = 关注数）。
//
// 每多关注一个人，读一次就要多扫一段：**读放大 = 关注数**。
// 大 V 关注数没有限制，所以纯读扩散撑不住"关注了 2000 人"的用户。
func (t *PullTimeline) Feed(uid int64, g *Graph, before int64, limit int) []Post {
	authors := dedup(append(g.Following(uid), uid)) // 去重同 PushTimeline.Publish
	t.mu.RLock()
	defer t.mu.RUnlock()

	heads := make([]int, len(authors)) // 每个列表的消费位置
	out := make([]Post, 0, limit)
	for len(out) < limit {
		best, bestID := -1, int64(0)
		for i, a := range authors {
			list := t.posts[a]
			if heads[i] >= len(list) {
				continue
			}
			id := list[heads[i]].ID
			if before != 0 && id >= before {
				heads[i]++
				continue
			}
			if id > bestID {
				best, bestID = i, id
			}
		}
		if best == -1 {
			break
		}
		out = append(out, t.posts[authors[best]][heads[best]])
		heads[best]++
	}
	return out
}

// Scanned 返回读一次需要 peek 的列表数（读扩散的读放大指标）。
func (t *PullTimeline) Scanned(uid int64, g *Graph) int {
	return len(dedup(append(g.Following(uid), uid)))
}

```

#### 骨架 ②：混合模式 —— 正文那句"最好的加分回答"长什么样

```go

package moments

import "sync"

// HybridTimeline 是正文那句最好的加分回答的落地形态：
//
//	普通用户 → 写扩散（发布时推给粉丝）
//	大 V     → 读扩散（读时再聚合，避免一条动态写几千万份）
//
// 判断依据只有一个：**粉丝数是否超过阈值**。这个阈值必须是配置项，
// 因为它取决于"单条动态最多愿意写多少份"这个成本上限，而不是业务语义。
type HybridTimeline struct {
	mu        sync.RWMutex
	threshold int64 // 粉丝数 > threshold 视为大 V
	push      *PushTimeline
	pull      *PullTimeline
	bigV      map[int64]bool
}

func NewHybrid(push *PushTimeline, pull *PullTimeline, threshold int64) *HybridTimeline {
	return &HybridTimeline{push: push, pull: pull, threshold: threshold, bigV: map[int64]bool{}}
}

// IsBigV 判定 + 登记。**生产上这个判定结果要缓存**（粉丝数是低频变化的值）。
func (h *HybridTimeline) IsBigV(uid int64, followers int) bool {
	h.mu.Lock()
	defer h.mu.Unlock()
	big := int64(followers) > h.threshold
	if big {
		h.bigV[uid] = true
	}
	return big
}

// Publish 返回这条动态实际写了多少份（写放大的直接指标）。
//
// ★ 注意：大 V 也要**同时**写进 push——但只写给自己的"订阅缓存"是没意义的，
//
//	所以这里大 V 只写一份到 pull，读的时候由粉丝侧聚合。
func (h *HybridTimeline) Publish(p Post, g *Graph) int {
	if h.IsBigV(p.Author, len(g.Followers(p.Author))) {
		h.pull.Publish(p)
		return 1
	}
	return h.push.Publish(p, g)
}

// Feed 把"自己 + 关注的普通人"的写扩散结果，和"关注的大 V"的读扩散结果归并。
//
// 分页游标沿用同一条规则：**ID 倒序 + before 游标**，两路数据都是有序的，
// 所以归并代价是 O(limit × 大V数)，而不是 O(总动态数)。
func (h *HybridTimeline) Feed(uid int64, g *Graph, before int64, limit int) []Post {
	merged := h.push.Feed(uid, before, limit)

	h.mu.RLock()
	bigFollowed := make([]int64, 0, 4)
	for _, v := range g.Following(uid) {
		if h.bigV[v] {
			bigFollowed = append(bigFollowed, v)
		}
	}
	h.mu.RUnlock()

	// 逐个大 V 取其最新 limit 条，再与 merged 归并
	for _, v := range bigFollowed {
		for _, p := range h.pull.postsOf(v) {
			if before != 0 && p.ID >= before {
				continue
			}
			merged = insertSorted(merged, p, limit)
		}
	}
	return merged
}

// postsOf 取某个作者自己的动态列表（读扩散用）。
func (t *PullTimeline) postsOf(author int64) []Post {
	t.mu.RLock()
	defer t.mu.RUnlock()
	return t.posts[author]
}

// insertSorted 插入倒序列表并截断到 limit（归并路径需要控制结果长度）。
func insertSorted(list []Post, p Post, limit int) []Post {
	list = insertDesc(list, p)
	if len(list) > limit {
		list = list[:limit]
	}
	return list
}

```

#### 实测一：写放大 —— "空间换时间"到底换掉了多少空间

一人发一条动态，实际写多少份：

| 模式 | 普通人（200 粉） | 大 V（50000 粉） |
|---|---|---|
| 纯写扩散 | 202 | **50002** |
| 纯读扩散 | 1 | 1 |
| 混合（阈值 10000） | 202 | **1** |

> 50002 这个数字就是正文那句"**不能**（写扩散爆炸）"的量化的形态：
> 把粉丝数换成 1000 万，一次发布就是 1000 万次写，
> 而**发一条动态的用户体验和刷 100 页的时间线相比，前者是低频操作**——
> 低频侧花代价、高频侧省代价，这才是"空间换时间"的判断依据。
> 混合模式买的正是这一点：**普通用户照写（202 份），大 V 只写 1 份**。

#### 实测二：读放大 —— 一个用户刷首页要付多少钱

读首页 20 条，5000 次 × 3 轮取最小（本机、纯内存）：

| 关注数 | 写扩散 | 读扩散 | 混合 | 读扩散需归并的列表数 |
|---|---|---|---|---|
| 50 | 0.43µs | 25.65µs | 5.04µs | 50 |
| 300 | 0.60µs | 192.04µs | 35.48µs | 300 |
| 1000 | 0.32µs | 810.73µs | 155.48µs | 1000 |

> 三列的形状比数值更重要：
> - **写扩散是常数**（只切列表头 20 条，与关注数无关；这一列 0.2~0.6µs 之间的来回是 GC 噪声，不是趋势）；
> - **读扩散线性于关注数**（每取一条要 peek 全部 k 个列表头 → `O(limit × k)`），1000 关注时约 0.8ms；
> - **混合介于两者之间**，代价正比于"**关注的大 V 数**"而不是"关注总数"。
>
> 换算到线上：读扩散那 1001 个列表在 MySQL 上就是 1001 次范围查询 = 1001 次网络往返，
> 比这里测到的 0.8ms 还要贵几个数量级——**所以正文说"查看的频次是发布的好几倍，必须快"**。

#### 实测三：游标分页与发号器的稳定性（这里抓出了两个真 bug）

| 场景 | 实测结果 |
|---|---|
| **逆序发布**（ID 小的最后才到，模拟异步扩散晚到）后按 ID 游标翻 9 页取 60 条 | 重复 **0** 条、缺失 **0** 条 |
| 作者自关注（互关）时发 1 条 | 写 **2** 份（未去重时是 3 份），自己时间线里同一条出现 **1** 次 |
| 单实例连续取 200000 个号 | 全部唯一且**单调递增**，其中 199947 个落在同一毫秒内（靠序列号区分） |
| 单实例一次取 4195 个（超过每毫秒 4096 的容量） | 无重复，多出的部分在等下一毫秒（耗时 1ms） |
| **时钟回拨 5 秒**（把 last 抬到未来） | 下一个 ID 仍然更大：毫秒位沿用旧值、只递增序列号 |
| 8 个协程并发取号 | 无重复 |
| 从 ID 反解时间 | 首个 ID 解出 2026-09-24T14:56:55 → **游标只需存 ID，不用存时间** |

**两个被抓出来的实现级 bug**（值得在面试里主动讲）：

1. **目标集合没去重**：`Followers(author)` 里可能已经有 author 自己（自关注/互关），
   再 `append(author)` 就把同一条动态写两份 → 表现是"上一页 7 条、下一页还是这 7 条"。
2. **用头部插入代替按 ID 插入**：只要发布链路是异步的（MQ、多节点、失败重投），
   ID 小的动态可能后到，头部插入就让列表失序 → 游标分页重复**并且**漏条目。

> 这两条都**不是**设计层面的错——正文"发布时维护多对多关系"完全成立，
> 错的是实现细节。**能讲出"我这样测才发现它重复/漏，改法是什么"，比背一遍方案更能证明真做过。**

**片段一：发号器（位结构与回拨处理和 Go 版逐行对应）**

```java

		synchronized long next(long node) {
			long ms = System.currentTimeMillis();
			if (ms > last) {
				seq = 0;
			} else if (seq < MAX_SEQ) {
				// 同一毫秒继续取号。ms < last 就是**时钟回拨**：
				// 沿用上一次的毫秒位、只递增序列号，宁可"看起来慢一毫秒"也不让 ID 倒退。
				ms = last;
				seq++;
			} else {
				// 序列号用满 → 等到下一毫秒，**绝不回绕**（回绕必然产生重复 ID）
				while (ms <= last) {
					ms = System.currentTimeMillis();
				}
				seq = 0;
			}
			last = ms; // ⚠️ 必须在这里统一写回：漏掉这步，下一毫秒首个号会和上一个重复
			return (ms << (NODE_BITS + SEQ_BITS)) | ((node & ((1L << NODE_BITS) - 1)) << SEQ_BITS) | seq;
		}
```

**片段二：写扩散的目标集合——★ 顺序写反，正文那个 bug 就自己回来了**

```java

		synchronized int publish(Post p, Graph g) {
			// ★ 顺序必须是"先追加自己、再整体去重"（和 Go 版 dedup(append(...)) 一致）：
			// 反过来先 dedup 再 add，作者本人若已在粉丝集合里就会被写两份。
			List<Long> withSelf = new ArrayList<>(g.followers(p.author()));
			withSelf.add(p.author()); // 自己的时间线也要有
			List<Long> targets = dedup(withSelf);
			for (long u : targets) {
				// 列表始终倒序，读的时候直接切前 N 条，**零排序成本**
				insertDesc(feed.computeIfAbsent(u, k -> new ArrayList<>()), p);
			}
			writes += targets.size();
			return targets.size();
		}
```

> **这不是纸上推演**：移植第一版我就是写成"先 `dedup` 再 `add(author)`"，
> 结果测试直接复现了 Go 版抓出的那两个现象——
> 自关注时**写 3 份而不是 2 份**、游标翻页 60 条里**重复 16 条**。

**片段三：读扩散的 k 路归并**

```java

		/**
		 * 归并 k 个有序列表取前 limit 条（k = 关注数）。
		 * 每多关注一个人，读一次就要多扫一段：**读放大 = 关注数**。
		 */
		synchronized List<Post> feed(long uid, Graph g, long before, int limit) {
			List<Long> withSelf = new ArrayList<>(g.following(uid));
			withSelf.add(uid);
			List<Long> authors = dedup(withSelf);
			List<Post> out = new ArrayList<>(limit);
			int[] heads = new int[authors.size()]; // 每个列表的消费位置
			while (out.size() < limit) {
				int best = -1;
				long bestId = 0;
				for (int i = 0; i < authors.size(); i++) {
					List<Post> list = posts.getOrDefault(authors.get(i), Collections.emptyList());
					if (heads[i] >= list.size()) {
						continue;
					}
					long id = list.get(heads[i]).id();
					if (before != 0 && id >= before) {
						heads[i]++;
						continue;
					}
					if (id > bestId) {
						best = i;
						bestId = id;
					}
				}
				if (best == -1) {
					break;
				}
				out.add(posts.get(authors.get(best)).get(heads[best]));
				heads[best]++;
			}
			return out;
		}
```

| 8 个并发体取号 | 无重复 | 8 个**内核线程**并发取号无重复 | ✅ 相同 |

**三点只有真移植一遍才说得出的话**：

1. **这类设计题的答案是语言无关的**：写扩散/读扩散/混合三档的数字在两边逐格对齐，
   说明正文那套"发布低频、查看高频 → 用空间换时间"的判断**不依赖 Go 的协程或通道**。
2. **移植是最好的一致性检查**：把 Go 实现换成 Java 时，
   任何"顺序、边界、去重"上的隐患都会以同样的错误现象重现一遍
   （我这里就是翻页重复 16 条）。**比 review 代码有效得多。**
3. **两边的差异集中在"归并那一步怎么插"**：
   Go 版 `insertSorted` 每次 `append(list, Post{})` 都可能触发整块重分配（列表已到 cap 时），
   Java 版 `ArrayList.add(index, e)` 是在已有数组上做 arraycopy ——
   混合模式那一列 Java 快 2.5~3.8 倍，**大概率就是这个来源（我没有逐项 profile，只做了形状对照）**。
   另外"每次读都重算关注列表"两边都做了，生产上这个判定结果必须缓存
   （粉丝数是低频变化值）——**这条正文讲过，两边的数字替它做了注脚**。

#### 一句话收口

```
① 顺序  → 单调 ID（时间位|机器位|序列位）：排序、游标分页、断线补漏共用同一个数
② 选型  → 粉丝数 > 阈值 ? 只写 1 份读时归并 : 推给每个粉丝（阈值是配置项，不是业务语义）
③ 代价  → 写扩散：写 202 份 / 读 0.4µs；读扩散：写 1 份 / 读 811µs —— 用数字选，而不是用感觉选
```

## Q4. 视频文件上传：放业务服务器和放文件服务器有什么差异？

**来源**：`BV1xSRXBwEeM p=40` 百度 Go 实习二面 · 时长 6分55秒
**考察意图**：表面在问"文件放哪"，实际考的是**"无状态 vs 有状态"这条分布式设计的基本原则**——
文件放业务服务器，就把一个无状态服务变成了有状态服务。

### 一、先看部署结构

```
客户端 → 网关（负载均衡）→ [业务服务器1 | 业务服务器2 | 业务服务器3] → 文件服务器集群
```

### 二、核心结论：文件放业务服务器 = 把服务做成"有状态"

| 维度 | **文件放业务服务器（本地）** | **文件放文件服务器（中心化）** |
|---|---|---|
| **服务状态** | 每个节点存的内容都不一样（A 存 A 文件、B 存 B 文件）→ **变成有状态服务，跟数据库一样** | 业务节点**不存任何数据，只做计算** → **无状态** |
| **扩缩容** | 扩容的新节点**没有历史文件**；缩容**要撤掉的节点上还挂着文件** → **不敢缩** | 加机器 / 减机器只影响算力，**随时可扩可缩** |
| **路由复杂度** | 负载均衡过后"**到底该访问哪台服务器**"不知道 → 只能再维护一份"文件↔节点"映射 | 文件的定位由**文件系统自己解决**，业务侧不关心 |
| **本质** | 相当于**自己在开发一套文件系统**，而且和业务**深度耦合** | 业务只调**标准接口 / SDK**，背后怎么实现完全隐藏 |
| **带宽** | 客户端 → 业务服务器 → 文件系统，**走两次网络** | 直传只走一次（详见 Q2） |

### 三、为什么必须做无状态（最值钱的一句）

> **业务服务器要尽可能做到无状态——本地不保存任何数据，只做计算。**
>
> 这样：**流量激增 → 直接加机器加节点，处理能力立刻变强**；
> **流量回落 → 把多余资源撤下来**。整个过程**没有任何数据迁移问题**。

**换个角度理解**：这和"为什么要用中心化的 Redis 缓存、中心化的 DB"是**同一件事**——

> 把数据放到数据中心、缓存放到缓存中心、Session 放到 Session 中心、**文件放到文件中心**，
> 业务服务器只通过标准接口调用它们。
> **文件系统用 Ceph 也好、对象存储也好、自研也好，对业务服务器都是隐藏的，业务只关心调用结果。**

### 四、和 Q2 的关系（避免答串）

| | **Q2（追问：要不要经过业务服务器）** | **本题（Q4）** |
|---|---|---|
| 关注点 | **链路效率与安全**：能不能前端直传、临时密钥怎么签发 | **服务架构**：文件存在业务节点会把服务做成有状态 |
| 结论 | 中间"什么都不做"就直传，避免多一次网络与带宽消耗 | 文件**存**在业务节点本地 → 破坏无状态、扩缩容受阻 |

> 两题其实是**同一原则的两个侧面**：**业务节点只做计算，数据一律中心化。**

### 面试官会追问什么

- **文件放业务服务器，就一定要自己实现文件系统吗？** → 是的。
  因为请求轮询到哪台不确定，**你就得维护"文件在哪台节点"的映射**——
  这份映射加上定位逻辑，就是文件系统在做的事（相当于自己造一个）。
- **业务节点一点都不缓存文件吗？** → 可以缓存（如本地磁盘做 CDN 前置），
  但**缓存必须可重建、可淘汰**，不能是"唯一副本"，否则又变回有状态。
- **无状态服务的代价是什么？** → **每次都要走网络访问中心化存储**，
  延迟高于本地读写 → 用**缓存、CDN、就近接入**来补。
- **有状态服务就一定是错的吗？** → 不是。**数据库、缓存、消息队列本身就是有状态的**，
  关键是**把"状态"收敛到专门的有状态系统里**，而不是散落在业务节点上。

## Q5. 开放题：如何设计微信的海量数据存储系统？

**来源**：`BV1xSRXBwEeM p=71` 微信 Go 面试 · 时长 5分49秒
**考察意图**：**开放性题目，没有标准答案**。考的是**临场拆解能力**——
能不能自己找到"突破点"，再顺着突破点和面试官一层层聊下去。

### 一、先定方法论：这类题怎么答

> 1. 开放题**不可能一听到就给出完整方案**，面试官也不会这样要求；
> 2. 它一定会**涉及多轮对话**——你在过程中怎么思考、遇到问题怎么调整，**这个过程本身就是考核内容**；
> 3. 所以第一件事是：**找到相对明确的突破点**，把话题拉进自己熟悉的领域。

**从题干能直接抽出两个突破点**：

| 突破点 | 含义 |
|---|---|
| **① 微信 = 聊天工具 → 数据类型** | 聊天记录（文本 / 语音 / 图片 / 视频 / 文件）+ 用户信息 |
| **② 海量 → 量级问题** | 必须分布式、必须分层、必须能水平扩展 |

### 二、突破点一：按数据类型选存储

| 数据类型 | 特征 | 存储选型 |
|---|---|---|
| **用户信息**（姓名、性别、年龄、头像） | **结构化**、字段固定 | **关系型数据库**（MySQL） |
| **聊天记录** | **非结构化**（文本/语音/图片/视频混合）、**按时间顺序**、**有明显热点** | **非关系型**（MongoDB / 时序数据库 / 自研 KV） |
| **文件（图片、视频、附件）** | 大对象、一次写多次读 | **对象存储 / 分布式文件系统** |

> **"按时间顺序"这个特征很关键**：聊天记录天然是**时间序列**，
> 且"最近的消息天天看，久远的几乎不看"→ 直接引出下一个突破点：**分层**。

### 三、突破点二：海量 → 分布式 + 分层

**① 分布式（量的问题）**

> **不可能单节点存下**，而且数据量和用户量都持续增长 → 必须用**分片 + 集群**架构，
> 选**可水平扩展（scale out）**的存储，如 **TiDB**（分布式关系型）或 **MongoDB**（分片集群）。

**② 分层（冷热的问题）**

| 数据层级 | 判定标准（示例） | 存储策略 |
|---|---|---|
| **热数据** | **7 天以内** | **缓存**（Redis 等），**快是第一优先级** |
| **温数据** | **1 个月以内** | 性能与成本折中（普通磁盘 DB / 冷热混合） |
| **冷数据** | **1 个月以前** | **低成本大容量存储**（对象存储 / 归档存储） |

> **分层的本质**：**把不同访问频率的数据放到不同"价位的介质"上**——
> 让"快"的只服务少数请求，让"大"的用便宜介质兜住。

### 四、综合方案（把两个突破点合起来讲）

```
接入层：IM 网关（长连接）+ 短连接 API，承载连接与鉴权
   ↓
业务层：消息收发、会话服务、用户服务（无状态，可水平扩容）
   ↓
存储层（按数据类型分）
   ├─ 用户信息 / 关系      → 分库分表的 MySQL（或分布式关系型）
   ├─ 聊天记录（海量时序） → 按 用户 / 会话 维度分片；冷热分层
   └─ 图片 / 视频 / 文件   → 对象存储 + CDN
   ↓
缓存层：Redis 缓存 7 天内的热点消息与会话元数据
```

**讲到这里可以主动抛"真实方案参考"**（微信公开的技术实践方向）：

| 机制 | 作用 |
|---|---|
| **一致性哈希** | 让数据分片在**增删节点时只迁移少量数据**（普通取模会导致**全量重分布**） |
| **分库分表 / 按用户维度分片** | 同一用户的数据尽量落同一分片，**单用户读放大最小** |
| **冷热分离** | 近期消息留在高性能存储，历史消息下沉低成本存储，**按需回捞** |
| **多级缓存** | 客户端本地 → 接入层缓存 → Redis → 存储，**逐层拦截** |

### 五、面试答题结构

```
① 先声明这是开放题，按"数据类型 + 数据量"两个突破点展开
② 类型维度：结构化 → MySQL；非结构化/时序 → MongoDB 或自研 KV；文件 → 对象存储
③ 量级维度：分片 + 集群 + 可水平扩展；一致性哈希减少迁移
④ 时间维度：7 天热 / 1 月温 / 更久冷，分层存储
⑤ 交互：主动抛"某类数据量预估多少、要不要压缩"等话题，引导面试官继续对话
```

### 面试官会追问什么

- **聊天记录为什么不用 MySQL？** → 非结构化、量级极大、写多读少且**冷热分层明显**；
  MySQL 分库分表能做到，但**成本和复杂度更高，文档型 / 自研 KV 更贴合**。
  （注意：**不是不能用** MySQL，而是选型贴合度问题。）
- **按用户分片还是按会话分片？** → 按**用户**分片利于"拉取我的会话列表"，
  但**群聊**消息读写会跨用户 → 群消息常单独按**群 ID 分片**，成员侧只存**引用 / 收件箱**。
- **冷数据回捞延迟大怎么办？** → **异步回捞 + 缓存预热**；
  对可预判的场景（如跳转历史消息）**提前加载**。
- **数据一致性怎么保证？** → **单用户 / 单会话内部强一致**（同一分片），
  **跨用户最终一致**（异步写扩散 + 补偿），而不是追求全局强一致。
- **消息不丢怎么保证？** → 写入先落存储再回 ACK；客户端本地也有副本；
  服务端提供**离线消息 + 多端同步**机制。

## Q6. 场景题：如何让数据统计页面加载速度变快？

**来源**：`BV1xSRXBwEeM p=78` 小红书面试场景题 · 时长 1分47秒
**考察意图**：短平快的场景题。答案核心只有一句——**别让"查询"去做"统计"**，提前把结果算好。

### 一、核心思路：少查询，把统计前移

> **让统计页面变快的唯一有效办法是：不要在查询时做实时统计。**
> **统计页面慢，就慢在"每次打开都在重新算一遍"。**

**做法：定时任务预计算**

```
每天（或每小时）定时任务 → 统计前一天的数据 → 把统计结果写入「结果表」
        ↓
用户打开统计页面 → 直接查结果表（不做任何聚合计算）
```

> 实时统计"**既麻烦又慢**"：要扫全量、要聚合、要排序。
> 而结果表里只有算好的数字，**查起来几乎没有成本**。

### 二、配套手段

| 手段 | 做法 |
|---|---|
| **分页查询** | 结果表按页取（如每次 10 条 / 20 条），**避免一次拉全量** |
| **查询语句优化** | 优化要放在**统计（写结果表）的时候做**，<br>**而不是每次查询的时候做**——查询路径只留最简单的 `WHERE + LIMIT` |
| **缓存结果** | 结果表外面还可以再套一层缓存（Redis / 本地缓存），<br>尤其是"当天实时看板"这类会被反复刷新的页面 |
| **异步 / 物化** | 更复杂的口径用**物化视图或异步聚合任务**，把重计算从查询链路剥离 |
| **索引** | 结果表按 `维度 + 日期` 建索引，保证分页与筛选都走索引 |

### 三、面试答题结构

```
① 一句话给结论：不要在查询时做统计，提前算好（定时任务 → 结果表）
② 查询路径：只从结果表分页读，语句保持最简
③ 更优解：结果再加缓存 / 用物化视图 / 异步聚合
④ 主动补一句：查询语句优化要放到统计阶段做，在查询阶段做收益有限
```

> **原视频的落点很直白**：**定时任务预计算 + 查结果表 + 分页**，
> 就是这类"统计页面变快"性价比最高的方案；**查询语句优化起不到决定性作用**。

### 面试官会追问什么

- **统计口径变了怎么办？** → 预计算任务**支持按日期重跑（补算历史）**，
  口径变更时回刷结果表；**不要靠实时查询兜底**。
- **业务要实时看板怎么办？** → **冷热两套**：历史区间走预计算结果表，
  **当天数据走实时聚合 + 缓存**（秒级刷新），第二天再由定时任务合并。
- **为什么不直接在结果表上再聚合？** → 每多一层聚合就多一次全表扫描，
  **结果表的价值就在于"已经聚合到最细查询粒度"**。

### 落地实现：预聚合结果表（DDL 未实测 + Go 骨架已编译校验并测）

> 正文的结论是"定时任务预计算 + 查结果表 + 分页"。这一节把它落成三件具体的东西：
> **结果表 DDL、定时任务的骨架、以及"重跑会不会把数字算成两份"的测试**。
>
> **校验口径分两半**：
> - ⚠️ **DDL 未实测**（本机没有 MySQL 实例，也没起 Docker），语法按 MySQL 8.0 书写，

>   下面的表是 `go test` 的真实输出（内存版 `Store` 顶替结果表，

#### 结果表 DDL（⚠️ 未实测，按 MySQL 8.0 书写）

```sql

-- 主键就是页面的查询粒度：维度 + 日期。**顺序反了就走不了索引**
CREATE TABLE stat_daily (
    day        DATE            NOT NULL COMMENT '归桶日期，写入侧就折算好时区',
    kind       VARCHAR(32)     NOT NULL COMMENT '事件类型/指标维度',
    pv         BIGINT UNSIGNED NOT NULL DEFAULT 0,
    uv         BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '上游用 HLL/位图算好后写入',
    updated_at TIMESTAMP       NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (day, kind)
) ENGINE = InnoDB COMMENT '统计页专用：只写不改，页面只读';

-- 定时任务的写入口：**整行覆盖，绝不累加**（累加 = 重跑一次数字翻倍）
INSERT INTO stat_daily (day, kind, pv, uv)
VALUES (?, ?, ?, ?), (?, ?, ?, ?)
AS new
ON DUPLICATE KEY UPDATE pv = new.pv, uv = new.uv;  -- 8.0.14+ 的别名写法；老写法 VALUES(pv) 已废弃

-- 页面的读路径：没有任何聚合、没有排序（主键就是 (day,kind)，倒序天然有序）
SELECT day, kind, pv, uv FROM stat_daily
WHERE day BETWEEN ? AND ? ORDER BY day DESC LIMIT 20;

```

> **`AS new` 而不是 `VALUES(pv)`**：后者在 8.0.20 起被标记废弃，
> 而且和 `INSERT ... VALUES` 里的括号嵌套容易看错列。

#### 骨架：定时任务 = 筛窗口 → 纯函数聚合 → upsert

```go

package rollup

import (
	"context"
	"sort"
	"sync"
	"time"
)

// 正文那句"不要在查询时做统计"落到实现上，其实只有三个动作：
// **聚合 → 幂等写结果表 → 按窗口回刷**。
// 其中"幂等"和"回刷窗口"是预计算最容易出事的两处：
// 口径变了要重算、数据迟到了要重算，而**重算绝不能把数字算成两份**。

// Event 是一条原始明细（正文里"要扫全量、要聚合"的那部分数据）。
type Event struct {
	Day    string // 归桶日期，如 2026-09-24。**写入时就折算好时区**，别让查询侧算
	Kind   string // 事件类型：view / click / publish
	UID    string
	Arrive time.Time // 落库时间，用来判断"这条是不是迟到的"
}

// Row 是结果表里的一行：维度 + 日期 + 算好的数字。
// UV 在这里是精确值（用 set 数出来的）；**生产上要换成 HLL / 位图**，
// 因为几千万 UV 不可能在内存里数。
type Row struct {
	Day  string
	Kind string
	PV   int
	UV   int
}

// Aggregate 把明细聚成 (day, kind) 粒度的结果。**纯函数、不碰数据库**，
// 所以重跑一次和跑十次得到的是同一份输出——"幂等"是从这里来的。
func Aggregate(events []Event) []Row {
	pv := map[string]int{}
	uv := map[string]map[string]bool{}
	for _, e := range events {
		k := e.Day + "\x00" + e.Kind
		pv[k]++
		if uv[k] == nil {
			uv[k] = map[string]bool{}
		}
		uv[k][e.UID] = true
	}
	out := make([]Row, 0, len(pv))
	for k, n := range pv {
		day, kind := splitKey(k)
		out = append(out, Row{Day: day, Kind: kind, PV: n, UV: len(uv[k])})
	}
	// 排序是**必需的**：不排序则每次跑出来的行序随 map 遍历变化，
	// 分批 upsert 时"失败后从第几批续跑"就不稳定，排查时对不上。
	sort.Slice(out, func(i, j int) bool {
		if out[i].Day != out[j].Day {
			return out[i].Day > out[j].Day // 日期倒序：页面默认看最近
		}
		return out[i].Kind < out[j].Kind
	})
	return out
}

func joinKey(day, kind string) string { return day + "\x00" + kind }

func splitKey(k string) (day, kind string) {
	for i := 0; i < len(k); i++ {
		if k[i] == 0 {
			return k[:i], k[i+1:]
		}
	}
	return k, ""
}

// Store 是结果表的写入口。生产实现就是
// `INSERT ... ON DUPLICATE KEY UPDATE pv=VALUES(pv), uv=VALUES(uv)`（DDL 见正文小节）。
type Store interface {
	Upsert(ctx context.Context, rows []Row) error
	Get(day, kind string) (Row, bool)
}

// MemStore 是跑通链路用的内存实现。
type MemStore struct {
	mu   sync.Mutex
	data map[string]Row
}

func NewMemStore() *MemStore { return &MemStore{data: map[string]Row{}} }

// Upsert **整行覆盖，不是累加**——这是重跑幂等的关键。
// 写成 `pv = pv + VALUES(pv)` 的话，重跑一次数字就翻倍，
// 而"重跑"在预计算里是常态（补算、口径变更、任务失败重试）。
func (s *MemStore) Upsert(_ context.Context, rows []Row) error {
	s.mu.Lock()
	defer s.mu.Unlock()
	for _, r := range rows {
		s.data[joinKey(r.Day, r.Kind)] = r
	}
	return nil
}

func (s *MemStore) Get(day, kind string) (Row, bool) {
	s.mu.Lock()
	defer s.mu.Unlock()
	r, ok := s.data[joinKey(day, kind)]
	return r, ok
}

// DaysBack 是**回刷窗口**：定时任务不只算"昨天"，而是把最近 N 天整体重算一遍。两个理由：
//  1. **迟到数据**——客户端批量补传、跨天边界的请求，只算昨天就会永久少掉；
//  2. **口径变更**——统计规则改了，历史要能跟上（正文追问"口径变了怎么办"的答案就是回刷）。
//
// N 取"业务能容忍的迟到时长"，**不是越大越好**：窗口越长，单次任务扫的明细越多。
func DaysBack(now time.Time, n int, layout string) []string {
	days := make([]string, 0, n)
	for i := 0; i < n; i++ {
		days = append(days, now.AddDate(0, 0, -i).Format(layout))
	}
	return days
}

// FilterDays 按天窗口筛明细（生产里这一步是 SQL 的 `WHERE day IN (...)`）。
func FilterDays(events []Event, days []string) []Event {
	want := make(map[string]bool, len(days))
	for _, d := range days {
		want[d] = true
	}
	out := make([]Event, 0, len(events))
	for _, e := range events {
		if want[e.Day] {
			out = append(out, e)
		}
	}
	return out
}

// RunJob 是一次定时任务的骨架：筛窗口 → 聚合 → upsert。
// 返回写了多少行，便于打点（**跑没跑成、写了多少行，必须能看出来**）。
func RunJob(ctx context.Context, store Store, events []Event, days []string) (int, error) {
	rows := Aggregate(FilterDays(events, days))
	if err := store.Upsert(ctx, rows); err != nil {
		return 0, err
	}
	return len(rows), nil
}

```

#### 实测：幂等、回刷窗口、以及查询成本转移

| 测试 | 实测输出 | 结论 |
|---|---|---|
| 同一批明细连跑 3 次 | 每次都"写 5 行，2026-09-24/view = PV 3 UV 2" | **重跑不翻倍**（PV 3 条里有 1 条同一 UID 重复访问 → UV 2，聚合口径也测到了） |
| 窗口=1 天，一条 09-22 的明细在 09-24 补传上来后再跑 | `2026-09-22/view` 存在=**false** | **迟到数据永久漏掉**，事后重跑也救不回来 |
| 窗口=3 天，同样补传后再跑 | `2026-09-22/view = PV 2 UV 2`，存在=true | 回刷窗口把迟到数据吸收了 |
| 一次页面加载（3 天 × 2 指标） | 实时聚合要扫 **7 条明细** + 内存分组；查结果表是 **5 次主键命中** | 明细规模放大 100 倍时，前者线性变贵、后者不变 |

> **表里那个"存在=false"就是预聚合最阴的坑**：结果表里**没有行**和**这行是 0** 是两件事。
> 页面若直接 `rows[i].pv`，缺桶会渲染成空白或干脆跳过那一天，
> 用户看到的就是"22 号没人访问"。**查询侧必须按日期补零**（或任务对全维度笛卡尔积落行）。

#### 一句话收口

> 预聚合的全部实现难度不在"算"，而在**三件让重跑变安全的事**：
> **聚合写成纯函数、写库用整行覆盖的 upsert、任务按窗口回刷而不是只算昨天**——
> 做到这三条，正文那句"口径变了支持按日期重跑"才是真的能做到。
