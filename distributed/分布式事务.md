# 分布式事务

> 介绍分布式事务的问题域、主流方案与选型，并给出 Seata、dtm 的落地方法和高频面试追问。
>
> 内容整理自个人学习笔记。事务消息的三种方案见 [../middleware/消息队列选型.md](../middleware/消息队列选型.md)；CAP 与一致性见 [一致性与CAP.md](一致性与CAP.md)。

## 一、一句话定位与问题域
> **分布式事务要解决的是：跨服务、跨库的一组操作，如何保证要么都成功，要么都失败。**
单机事务依靠同一个数据库内核管理日志、锁和提交点；跨库后，每个数据库只能决定自己的本地事务，无法天然感知其他参与者的结果。
网络可能超时、断开或重复传输，调用方看到的“失败”也可能只是响应丢失；各参与者还可能在不同时间提交，且不存在覆盖全部资源的全局数据库锁。
因此，本地 ACID 不是失效了，而是它的**原子性边界只覆盖单个资源管理器**；分布式事务是在多个本地事务之上增加协调、补偿、重试和对账。
单机事务、隔离级别与 MVCC 已在 [../mysql/并发控制与MVCC.md](../datastore/mysql/并发控制与MVCC.md) 说明，本篇不再重复。
典型问题包括：订单创建成功但库存未扣减、支付扣款成功但商户入账失败、跨库转账只完成一边，以及业务落库成功但事件没有可靠发布。
## 二、理论基础
### 2.1 XA / DTP 模型
X/Open DTP 把系统分为三个角色：**AP（Application Program）** 发起业务，**TM（Transaction Manager）** 协调全局事务，**RM（Resource Manager）** 管理数据库、消息系统等资源。
XA 是 TM 与 RM 之间的标准接口，RM 需要支持 `prepare`、`commit`、`rollback` 等能力；一个全局事务由多个 XA 分支组成。
XA 解决的是协议与角色分工，不代表天然高可用；协调者、网络和参与者故障仍需要日志恢复、超时与重试。
### 2.2 BASE 理论
BASE 是 **Basically Available、Soft State、Eventually Consistent**：系统优先维持基本可用，允许短时间中间状态，最终通过异步处理恢复一致。
它不是“不要一致性”，而是把一致性从“每次请求返回前立即完成”放宽为“在明确时间窗口内最终完成”。
落地 BASE 必须有可重试操作、幂等、状态可观测、补偿和对账，否则只是把错误推迟暴露。
### 2.3 与 ACID、CAP 的关系
ACID 描述事务边界内的正确性，BASE 描述跨边界时常用的工程取舍；两者不是互斥关系，最终一致方案的每个分支通常仍依靠本地 ACID。
强一致协议用阻塞、锁和较低可用性换确定性，业务补偿方案用短暂不一致换吞吐与可用性。
CAP 只说明网络分区下的一致性与可用性取舍，定义与示例见 [一致性与CAP.md](一致性与CAP.md)。
## 三、解决方案全景 ⭐
### 3.1 七种方案大对比
| 方案 | 一致性强度 | 业务侵入性 | 性能 | 典型场景 | 典型失败处理 | 实现复杂度 |
| --- | --- | --- | --- | --- | --- | --- |
| **2PC（XA）** | 强一致倾向；故障恢复期间可能阻塞 | 低，依赖 RM/XA | 低，长时间占连接与锁 | 同构数据库、短事务、低并发核心操作 | TM 日志恢复，二阶段重试 | 中 |
| **3PC** | 强一致倾向；分区下仍非绝对 | 低到中 | 比 2PC 更低，多一次网络往返 | 理论研究、少量特定系统 | 超时自动决策、恢复协调 | 高 |
| **TCC** | 业务层强一致倾向，最终完成 Confirm/Cancel | ⭐ 高 | 高，无数据库长锁 | 支付、账户、库存等高并发核心链路 | 幂等重试、事务栅栏、人工补偿 | ⭐ 高 |
| **Saga** | 最终一致 | 中，需要补偿动作 | 高，分支可独立提交 | 长事务、跨多个服务、流程型业务 | 正向恢复或逆向补偿 | 中到高 |
| **本地消息表** | 最终一致 | 中，需要消息表与投递任务 | 中到高 | 不依赖特定 MQ 的异步一致 | 扫表重投、消费幂等、对账 | 中 |
| **事务消息** | 最终一致，通常更及时 | 低到中 | 高 | 本地事务与事件发布原子性 | 半消息回查、重复投递幂等 | 中 |
| **最大努力通知** | 弱一致 / 最终可对账 | 低 | 高 | 支付结果通知、非核心外部通知 | 有限重试、查询接口、对账 | 低到中 |
> ⭐ 没有万能方案：先确定一致性目标和可接受的不一致窗口，再评估吞吐、资源锁定时间、业务改造成本与补偿可行性。
### 3.2 2PC（Two-Phase Commit / XA）
**原理步骤：**
1. **Prepare 阶段**：TM 向所有 RM 发起准备请求；RM 执行业务、写入恢复日志并持有锁，但不最终提交。
2. 所有 RM 都返回 Yes，TM 将全局决议持久化为 Commit；任一 RM 返回 No 或超时，则决议为 Rollback。
3. **Commit/Rollback 阶段**：TM 向每个 RM 下发最终决议，RM 完成本地事务、释放锁并确认。
4. 未确认分支由 TM 根据持久化日志持续恢复，RM 重启后也根据 XA 状态继续完成。
**优点：**协议标准、对业务代码侵入较低；在协调者与参与者正常工作时，应用可获得接近本地事务的提交语义。
**缺点与三个必答问题：**
- ⚠️ **协调者单点**：TM 故障会让全局事务失去决策者；集群和持久化日志能提高可用性，但不能消除协议依赖。
- ⚠️ **同步阻塞**：Prepare 成功后 RM 必须持有数据库连接和锁等待决议，慢分支会放大锁竞争并拖低吞吐。
- ⚠️ **数据不一致**：二阶段中部分 RM 已 Commit、另一些因网络或宕机未执行；已提交分支无法普通回滚，只能依赖恢复重试，极端永久故障需人工修复。
**适用：**参与者都支持 XA、事务很短、并发量可控、无法接受业务补偿语义的场景；不适合长流程和高峰交易链路。
### 3.3 3PC（Three-Phase Commit）
**原理步骤：**
1. **CanCommit**：协调者询问参与者是否具备执行条件，不持有最终资源。
2. **PreCommit**：全部同意后执行并预提交，参与者记录状态并应答。
3. **DoCommit**：协调者下发提交；任一阶段失败则按协议中止或基于超时策略继续。
**优点：**在 2PC 基础上增加预询问和超时决策，缩短部分场景的阻塞时间，参与者不必无限等待协调者。
**缺点：**多一次网络往返和更多状态；网络分区时，不同节点可能基于超时作出不同判断，仍可能不一致；工程收益通常不足以抵消复杂度。
**适用：**更多用于理解提交协议的演进，通用业务系统很少直接采用；实践中通常选择成熟 XA、TCC 或 Saga。
### 3.4 TCC ⭐
**原理步骤：**
1. **Try**：完成业务校验并预留资源，例如冻结余额、锁定库存额度；不能直接做不可逆副作用。
2. **Confirm**：所有 Try 成功后执行确认，消费预留资源；原则上不再做业务校验，并且必须最终成功。
3. **Cancel**：任一 Try 失败或全局事务超时后释放预留资源，恢复到 Try 前状态；同样必须最终成功。
**优点：**控制粒度在业务层，不长期持有数据库锁；可跨数据库、缓存和外部服务，性能与并发能力通常优于 XA。
**缺点：**每个动作都要实现三套逻辑，冻结字段、流水和状态机会增加模型复杂度；Confirm/Cancel 失败需要持续重试与运维介入。
**适用：**高并发、短事务、资源可预留且一致性要求高的核心链路，如资金冻结、库存预占、优惠额度锁定。
#### TCC 三个必处理问题 ⭐
| 问题 | 发生方式 | 正确处理 |
| --- | --- | --- |
| **幂等** | Confirm/Cancel 的响应丢失，协调者重复调用 | 以 `xid + branch_id + action` 建唯一约束或事务栅栏；已成功再次调用仍返回成功 |
| **空回滚** | Try 未到达或未执行，Cancel 因超时先到 | Cancel 发现无 Try 记录时不操作业务资源，但原子写入“已回滚”标记并返回成功 |
| **悬挂** | Cancel 已完成，迟到的 Try 随后执行并再次冻结资源 | Try 先检查事务栅栏；发现“已回滚”标记立即拒绝，栅栏检查与资源预留必须在同一本地事务 |
> ⚠️ 空回滚解决“没有 Try 却收到 Cancel”，悬挂解决“Cancel 之后又来了迟到 Try”；二者都不能只靠内存标志，必须持久化并与业务更新同事务提交。
### 3.5 Saga
Saga 把长事务拆成一串可独立提交的本地事务，每个步骤 `Ti` 配一个语义相反的补偿 `Ci`；它不撤销数据库日志，而是执行新的业务操作抵消影响。
**原理步骤：**
1. 按业务顺序提交 `T1、T2...Tn`，每一步完成后立即释放本地资源。
2. 全部成功则 Saga 完成；中途失败时选择恢复策略。
3. **正向恢复（Forward Recovery）**：持续重试失败步骤，最终走完后续流程，适合“必须完成”的订单履约。
4. **逆向补偿（Backward Recovery）**：按 `Cn...C2、C1` 逆序执行补偿，适合每一步都存在可靠撤销语义的流程。
**优点：**无全局长锁，适合持续数分钟到数天、参与服务多的流程；每个服务仍只处理本地事务。
**缺点：**不提供隔离性，中间状态可能被其他请求看到；补偿不等于物理回滚，汇率变化、已发货等动作可能无法完全逆转。
**适用：**旅行预订、订单履约、跨组织审批、长时间工作流；不可补偿动作应尽量后置，并在前面设置可失败的校验步骤。
#### 编排与协同
| 实现 | 工作方式 | 优点 | 风险与适用 |
| --- | --- | --- | --- |
| **编排 Orchestration** | 中央协调器显式调用下一步并记录状态 | 流程可视、超时补偿集中管理 | 协调器复杂且关键；适合步骤多、规则清晰的核心流程 |
| **协同 Choreography** | 服务发布领域事件，其他服务订阅后继续 | 解耦、扩展新订阅者容易 | 链路隐式、循环依赖与排障困难；适合步骤少、事件驱动系统 |
### 3.6 本地消息表
**结论：**业务数据与待发送事件在同一本地事务落库，再异步投递并幂等消费，适合允许最终一致且不绑定特定 MQ 的场景；流程、优缺点与事务消息对比见 [../middleware/消息队列选型.md](../middleware/消息队列选型.md#事务消息)。
### 3.7 事务消息（RocketMQ 半消息）
**结论：**半消息、提交/回滚与事务回查保证“本地事务和消息发布”最终一致，消费端仍必须幂等；完整步骤和边界见 [../middleware/消息队列选型.md](../middleware/消息队列选型.md#事务消息)。
### 3.8 最大努力通知
**结论：**通知方按退避策略有限重试，接收方提供幂等处理和结果查询，最终由对账修复，适合支付回调等允许延迟的弱一致场景；详细对比见 [../middleware/消息队列选型.md](../middleware/消息队列选型.md#事务消息)。
## 四、选型建议
### 4.1 决策清单
| 问题 | 选择倾向 |
| --- | --- |
| 必须强一致，参与数据库支持 XA，事务可在很短时间结束？ | **2PC / XA** |
| 核心链路高并发，资源能冻结/预留，团队能维护三阶段逻辑？ | **TCC** |
| 跨多个服务或第三方，流程持续时间长，每步可补偿？ | **Saga** |
| 只需保证“本地落库后一定发布事件”，允许短暂不一致？ | **本地消息表 / 事务消息** |
| 下游属于外部系统，只能重复通知并查询结果？ | **最大努力通知 + 对账** |
| 业务动作不可逆、没有补偿接口？ | 先重构边界：校验前置、不可逆动作后置；不要硬套 Saga |
### 4.2 推荐判断顺序
1. 写清楚一致性不变量，例如“总账恒等”“库存不能为负”，不要先选框架。
2. 明确最长可接受不一致窗口，以及失败时能否向用户展示“处理中”。
3. 判断资源是否支持 XA、能否冻结、能否补偿、是否允许重复执行。
4. 估算峰值吞吐、分支数量与最长耗时，排除会长期占锁/连接的方案。
5. 最后比较中间件成熟度、团队经验、监控与人工修复成本。
## 五、使用一：Java 与 Seata ⭐
Seata 由 TC（事务协调者）、TM（事务管理器）和 RM（资源管理器）组成；应用通过 XID 把多个分支注册到同一全局事务。
### 5.1 四种模式对比
| 模式 | 核心机制 | 隔离/一致性 | 侵入性 | 适用 |
| --- | --- | --- | --- | --- |
| **AT** | SQL 代理生成前后镜像，`undo_log` 反向补偿，全局锁防脏写 | 最终完成回滚；默认全局读未提交 | ⭐ 低 | 关系型数据库、普通 CRUD |
| **TCC** | 业务实现 Try/Confirm/Cancel，可启用事务栅栏 | 业务层强一致倾向 | 高 | 高并发核心资源操作 |
| **Saga** | 状态机编排本地事务和补偿 | 最终一致，无全局隔离 | 中 | 长事务、多服务流程 |
| **XA** | 数据库原生 XA Prepare/Commit | 强一致倾向 | 低 | 短事务、数据库支持 XA |
### 5.2 AT 模式接入
#### 依赖坐标
```xml

<properties>
    <seata.version>2.6.0</seata.version>
</properties>
<dependency>
    <groupId>io.seata</groupId>
    <artifactId>seata-spring-boot-starter</artifactId>
    <version>${seata.version}</version>
</dependency>
```
> 版本应与 Seata Server 和 Spring Cloud Alibaba 兼容矩阵一致；关键坐标是 `io.seata:seata-spring-boot-starter`。
#### 客户端配置与数据源代理
```yaml

seata:
  enabled: true
  tx-service-group: order_tx_group
  data-source-proxy-mode: AT
  enable-auto-data-source-proxy: true
  service:
    vgroup-mapping:
      order_tx_group: default
    grouplist:
      default: 127.0.0.1:8091
```
Starter 默认自动把应用 `DataSource` 包装为 `DataSourceProxy`，RM 才能拦截 SQL、记录镜像并注册分支。
若关闭 `enable-auto-data-source-proxy`，可手动用 `new DataSourceProxy(originDataSource)` 暴露 `@Primary DataSource`；⚠️ 自动代理和手动代理只能选一种，避免重复代理。
每个参与 AT 的业务库都要建 `undo_log`，并保证业务表存在单列主键。
```sql

CREATE TABLE `undo_log` (
  `id` BIGINT NOT NULL AUTO_INCREMENT,
  `branch_id` BIGINT NOT NULL,
  `xid` VARCHAR(128) NOT NULL,
  `context` VARCHAR(128) NOT NULL,
  `rollback_info` LONGBLOB NOT NULL,
  `log_status` INT NOT NULL,
  `log_created` DATETIME NOT NULL,
  `log_modified` DATETIME NOT NULL,
  `ext` VARCHAR(100) DEFAULT NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `ux_undo_log` (`xid`, `branch_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```
#### 全局事务入口
```java

import io.seata.spring.annotation.GlobalTransactional;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Service;
@Service
@RequiredArgsConstructor
public class OrderApplicationService {
    private final OrderRepository orderRepository;
    private final InventoryClient inventoryClient;
    private final AccountClient accountClient;
    @GlobalTransactional(name = "create-order", rollbackFor = Exception.class)
    public void createOrder(OrderCommand command) {
        orderRepository.insert(command);
        inventoryClient.deduct(command.skuId(), command.quantity());
        accountClient.debit(command.userId(), command.amount());
    }
}
```
AT 一阶段在同一本地事务内提交业务数据和 `undo_log`，提交前获取 TC 管理的全局锁；二阶段提交只需异步清理日志，回滚则校验数据镜像后按 `undo_log` 生成反向 SQL。
⚠️ 被调服务也要接入 Seata 并透传 XID；入口若吞掉异常，`@GlobalTransactional` 感知不到失败，全局事务不会按预期回滚。
### 5.3 TCC 模式接口写法
```java

import io.seata.rm.tcc.api.BusinessActionContext;
import io.seata.rm.tcc.api.BusinessActionContextParameter;
import io.seata.rm.tcc.api.LocalTCC;
import io.seata.rm.tcc.api.TwoPhaseBusinessAction;
import java.math.BigDecimal;
@LocalTCC
public interface AccountTccAction {
    @TwoPhaseBusinessAction(
        name = "accountTccAction",
        commitMethod = "commit",
        rollbackMethod = "rollback",
        useTCCFence = true
    )
    boolean prepare(
        BusinessActionContext context,
        @BusinessActionContextParameter(paramName = "orderId") String orderId,
        @BusinessActionContextParameter(paramName = "amount") BigDecimal amount
    );
    boolean commit(BusinessActionContext context);
    boolean rollback(BusinessActionContext context);
}
```
```java

import io.seata.rm.tcc.api.BusinessActionContext;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Service;
@Service
@RequiredArgsConstructor
public class AccountTccActionImpl implements AccountTccAction {
    private final AccountService accountService;
    @Override
    public boolean prepare(BusinessActionContext context, String orderId, BigDecimal amount) {
        return accountService.freeze(orderId, amount);
    }
    @Override
    public boolean commit(BusinessActionContext context) {
        String orderId = String.valueOf(context.getActionContext("orderId"));
        return accountService.confirmFrozen(orderId);
    }
    @Override
    public boolean rollback(BusinessActionContext context) {
        String orderId = String.valueOf(context.getActionContext("orderId"));
        return accountService.cancelFrozen(orderId);
    }
}
```
`@TwoPhaseBusinessAction` 标注的 `prepare` 就是 Try；Seata 根据方法名调用 Confirm/Cancel，并用 `BusinessActionContext` 传递业务参数。
`useTCCFence = true` 时还要在参与库创建官方版本对应的 `tcc_fence_log` 表，用持久化栅栏处理幂等、空回滚和悬挂；业务冻结流水仍应以 `orderId` 建唯一约束。
全局入口仍由 `@GlobalTransactional` 包裹，然后调用一个或多个 `prepare(null, ...)`。
## 六、使用二：Go 与 dtm ⭐
Go 生态没有与 Seata 完全对等的官方统一方案；`github.com/dtm-labs/dtm` 同时提供 Saga、TCC、二阶段消息、XA 和多语言客户端，是 Go 分布式事务的事实标准选择之一。
### 6.1 服务端部署要点
| 项目 | 要点 |
| --- | --- |
| 端口 | HTTP 默认 `36789`，gRPC 默认 `36790`；客户端地址通常为 `http://host:36789/api/dtmsvr` |

### 6.2 Saga：完整最小示例
把代码保存为独立 `main.go`，安装代码中导入的模块并启动 DTM；运行后请求 `POST http://localhost:8081/start` 即可发起事务。
分支处理器中的日志位置替换为各自的本地事务，正向与补偿都必须幂等。
```go

package main
import (
    "log"
    "net/http"
    "github.com/dtm-labs/dtm/client/dtmcli"
    "github.com/gin-gonic/gin"
    "github.com/lithammer/shortuuid/v3"
)
const (
    dtmServer = "http://localhost:36789/api/dtmsvr"
    business  = "http://localhost:8081/api"
)
type TransReq struct {
    Amount int64 `json:"amount"`
}
func ok(name string) gin.HandlerFunc {
    return func(c *gin.Context) {
        log.Printf("execute %s", name)
        c.JSON(http.StatusOK, dtmcli.ResultSuccess)
    }
}
func main() {
    app := gin.Default()
    app.POST("/api/TransOut", ok("TransOut"))
    app.POST("/api/TransOutCompensate", ok("TransOutCompensate"))
    app.POST("/api/TransIn", ok("TransIn"))
    app.POST("/api/TransInCompensate", ok("TransInCompensate"))
    app.POST("/start", func(c *gin.Context) {
        req := &TransReq{Amount: 30}
        saga := dtmcli.NewSaga(dtmServer, shortuuid.New()).
            Add(business+"/TransOut", business+"/TransOutCompensate", req).
            Add(business+"/TransIn", business+"/TransInCompensate", req)
        if err := saga.Submit(); err != nil {
            c.JSON(http.StatusInternalServerError, gin.H{"error": err.Error()})
            return
        }
        c.JSON(http.StatusOK, dtmcli.ResultSuccess)
    })
    log.Fatal(app.Run(":8081"))
}
```
### 6.3 TCC：完整最小示例
此示例与上一个示例分别运行；请求 `POST http://localhost:8082/start`，两个 Try 都成功后 DTM 调 Confirm，任一 Try 失败则调 Cancel。
```go

package main
import (
    "log"
    "net/http"
    "github.com/dtm-labs/dtm/client/dtmcli"
    "github.com/gin-gonic/gin"
    "github.com/go-resty/resty/v2"
    "github.com/lithammer/shortuuid/v3"
)
const (
    dtmServer = "http://localhost:36789/api/dtmsvr"
    business  = "http://localhost:8082/api"
)
type TransReq struct {
    Amount int64 `json:"amount"`
}
func ok(name string) gin.HandlerFunc {
    return func(c *gin.Context) {
        log.Printf("execute %s", name)
        c.JSON(http.StatusOK, dtmcli.ResultSuccess)
    }
}
func main() {
    app := gin.Default()
    app.POST("/api/TransOutTry", ok("TransOutTry"))
    app.POST("/api/TransOutConfirm", ok("TransOutConfirm"))
    app.POST("/api/TransOutCancel", ok("TransOutCancel"))
    app.POST("/api/TransInTry", ok("TransInTry"))
    app.POST("/api/TransInConfirm", ok("TransInConfirm"))
    app.POST("/api/TransInCancel", ok("TransInCancel"))
    app.POST("/start", func(c *gin.Context) {
        gid := shortuuid.New()
        err := dtmcli.TccGlobalTransaction(
            dtmServer,
            gid,
            func(tcc *dtmcli.Tcc) (*resty.Response, error) {
                req := &TransReq{Amount: 30}
                resp, err := tcc.CallBranch(
                    req,
                    business+"/TransOutTry",
                    business+"/TransOutConfirm",
                    business+"/TransOutCancel",
                )
                if err != nil {
                    return resp, err
                }
                return tcc.CallBranch(
                    req,
                    business+"/TransInTry",
                    business+"/TransInConfirm",
                    business+"/TransInCancel",
                )
            },
        )
        if err != nil {
            c.JSON(http.StatusInternalServerError, gin.H{"error": err.Error()})
            return
        }
        c.JSON(http.StatusOK, dtmcli.ResultSuccess)
    })
    log.Fatal(app.Run(":8082"))
}
```
真实分支应使用 dtm 的 **Sub-Transaction Barrier（子事务屏障）** 把栅栏记录和业务更新放进同一本地事务，以自动防止重复执行、空回滚和悬挂。
### 6.4 二阶段消息（Msg）要点
```go

msg := dtmcli.NewMsg(dtmServer, shortuuid.New()).
    Add(business+"/TransIn", &TransReq{Amount: 30})
err := msg.DoAndSubmitDB(
    business+"/QueryPrepared",
    db,
    func(tx *sql.Tx) error {
        _, err := tx.Exec("UPDATE account SET balance = balance - ? WHERE id = ?", 30, 1)
        return err
    },
)
```
`DoAndSubmitDB` 在同一本地事务内完成业务更新和 Msg 的 Prepare 记录，然后提交消息；若提交响应丢失，DTM 调 `QueryPrepared` 查询本地屏障记录。
接收分支至少执行一次，因此仍需幂等；它适合“本地事务成功后异步触发下游”，不是同步跨服务回滚。
### 6.5 XA 要点
```go

err := dtmcli.XaGlobalTransaction(dtmServer, shortuuid.New(), func(xa *dtmcli.Xa) (*resty.Response, error) {
    resp, err := xa.CallBranch(&TransReq{Amount: -30}, business+"/TransOutXa")
    if err != nil {
        return resp, err
    }
    return xa.CallBranch(&TransReq{Amount: 30}, business+"/TransInXa")
})
```
每个分支接口内部还要调用 `dtmcli.XaLocalTransaction`，数据库驱动和数据库本身必须支持 XA；不要在 XA 本地事务中做慢 RPC。
XA 适合短事务和同类数据库资源，吞吐、锁等待和 `in-doubt` 事务恢复必须压测与监控。
## 七、生产实践与坑
### 7.1 必备工程能力
| 能力 | 落地要求 |
| --- | --- |
| **幂等设计** | 业务唯一键 + 数据库唯一索引优先；状态机使用带条件 `UPDATE`，幂等记录与业务写同事务 |
| **全局事务 ID 透传** | Seata 透传 XID，dtm 透传 gid；HTTP/RPC/MQ Header、日志、Trace 和业务流水统一关联 |
| **超时与重试** | 业务失败立即终止；网络异常按指数退避加抖动；每次重试有上限、截止时间和幂等保证 |
| **补偿可见性** | 展示全局/分支状态、重试次数、最后错误和下一次重试时间；禁止“后台悄悄重试但无人知道” |
| **告警** | 补偿超过阈值、事务超时、积压增长、XA 悬挂、对账差异均需分级告警 |
| **人工介入** | 提供按 xid/gid 查询、重试、跳过、补偿和生成修复单的受控后台，操作必须审计 |
| **对账与兜底** | 定时按业务不变量核对上下游，以权威数据源为准生成差异单；自动修复失败后转人工 |
### 7.2 幂等表示例
```sql

CREATE TABLE idempotency_record (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  action VARCHAR(64) NOT NULL,
  business_id VARCHAR(128) NOT NULL,
  status VARCHAR(16) NOT NULL,
  result_json JSON NULL,
  created_at DATETIME NOT NULL,
  updated_at DATETIME NOT NULL,
  UNIQUE KEY uk_action_business (action, business_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```
⚠️ 不要采用“先查有没有，再执行写入”的非原子流程；两个并发请求都可能查不到。应让唯一约束裁决，或使用带状态条件的单条更新。
### 7.3 超时、重试与补偿
- 区分**业务失败**与**技术失败**：余额不足不应重试，连接超时可以重试；未知结果先查询状态再决定。
- Try/正向操作设置较短超时，Confirm/Cancel/补偿以“最终成功”为目标持续恢复，但达到阈值必须告警。
- 重试使用指数退避和随机抖动，设置单分支超时、全局截止时间与熔断，避免故障服务被重试风暴压垮。
- 补偿接口也可能失败，必须和正向接口同等级监控；补偿参数要保留业务快照，不能依赖可能已变化的当前值。
### 7.4 长事务拆分的正确姿势
1. 按业务状态拆成可独立提交的小步骤，每一步都产生可查询的持久化状态。
2. 把校验和可回滚动作放前面，把发货、外部打款等不可逆动作后置。
3. 不在数据库事务内等待用户输入、第三方回调或慢 RPC；提交本地状态后异步推进。
4. 对外展示“处理中/补偿中”，不要为了伪装同步体验而长期持锁。
5. 为每一步定义成功、业务失败、技术失败、超时和人工接管路径，并用故障注入验证。
## 八、面试官会追问什么 ⭐
| # | 问题 | 回答要点 |
| --- | --- | --- |
| 1 | **2PC 有什么问题？** | 协调者单点、Prepare 后同步阻塞、二阶段部分成功导致暂时或永久不一致；HA 和日志恢复只能缓解，不能消除协议代价 |
| 2 | **3PC 为什么没有普及？** | 多一次往返与更多状态只能降低部分阻塞；网络分区下超时自主决策仍可能不一致，收益通常不如成熟 XA/TCC/Saga |
| 3 | **TCC 的 Try/Confirm/Cancel 分别做什么？** | Try 校验并预留，Confirm 消费预留且不再业务校验，Cancel 释放预留；后二者要求幂等并最终成功 |
| 4 | **空回滚与悬挂是什么，怎么解决？** | Cancel 先于未执行 Try 是空回滚；Cancel 后迟到 Try 再冻结是悬挂；用持久化事务栅栏、唯一键并与业务更新同事务解决 |
| 5 | **Saga 与 TCC 怎么选？** | 短事务、高并发、资源可冻结且要求更强隔离选 TCC；长流程、多服务、允许中间态且动作可补偿选 Saga |
| 6 | **Saga 编排和协同有什么差别？** | 编排由中心协调器显式控流程，易观测但中心复杂；协同靠事件自治，耦合低但流程隐式、排障困难 |
| 7 | **分布式事务能做到强一致吗？** | XA/TCC 可提供强一致倾向，但网络分区、阻塞、恢复窗口和外部不可事务资源决定了绝对强一致代价很高；需先限定故障模型 |
| 8 | **为什么大厂常选最终一致 + 对账？** | 它缩短锁时间、提升可用性和吞吐，适配异构资源；用幂等、补偿、监控和对账把风险变成可发现、可恢复的工程问题 |
| 9 | **Seata AT 的原理是什么？** | 数据源代理拦截 SQL，一阶段把业务写与 `undo_log` 同事务提交并获取全局锁；二阶段提交清日志，回滚按镜像生成反向 SQL |
| 10 | **如何解决重复请求和重复补偿？** | 使用业务幂等键、数据库唯一索引、状态机条件更新或事务栅栏；幂等判定与业务结果必须位于同一本地事务 |
**一句话速记：**短而强一致看 XA，高并发核心资源看 TCC，长流程看 Saga，异步最终一致看消息方案，所有方案最后都要落到幂等、可观测、补偿和对账。
