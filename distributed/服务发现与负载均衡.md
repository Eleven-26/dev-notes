## Q1. 负载均衡和服务发现是怎么做的？

**来源**：`p=59` 携程云计算工程师一面 · 时长 9分41秒
**考察意图**：典型**项目相关题**。答的时候要**分类讲方案**，而不是只说"用 Nginx"。

### 一、服务发现（两种方案）

#### 方案 A：用 etcd（或 Zookeeper 等组件）自建

```
① 部署 etcd 集群（etcd 内部是键值对数据库）
        ↓
② 服务端启动时向 etcd 注册：写入键值对
        ↓
③ 客户端监听以「服务名」为前缀的 key，拿到实例列表
        ↓
④ 客户端本地缓存列表，用它来访问服务端
```

**⚠️ 关键细节 1：注册时必须带「租约 + 有效期」**

> 往 etcd 注册**不是写一次就完事**。
> 因为**服务端一旦中断，etcd 里的数据必须能自动过期**（否则客户端会拿到已挂掉的地址）。
>
> **做法**：
> - 创建**租约**，设置有效期（通常 **5~10 秒**）；
> - 服务存活期间**不断刷新**租约——
>   例如设置 10 秒，**不到 5 秒就重置回 10 秒**，如此循环。
>
> **效果**：只要服务一直存活，数据就永不过期；
> **服务一旦中断，租约到期、数据自动消失** → 实现"**自动下线**"。

**⚠️ 关键细节 2：客户端用「监听 + 本地缓存」，而不是每次拉取**

> 客户端**监听**该服务名前缀下的所有 key（如 User 服务 3 台机器 → 3 个键值对）。
> **这些 key 只要变化，客户端就同步更新**。
>
> 客户端拿到列表后**缓存到本地**，访问时**从本地缓存取地址**；
> 一旦收到 etcd 的变更通知，**同步更新本地缓存**即可。
>
> **这样就不必每次请求都去 etcd 拿最新列表**——这是性能上的关键设计。

**方案 A 的适用场景**：自行部署机器，或自行用 Docker 部署。

#### 方案 B：用云原生组件（内置服务发现）

> **Docker Swarm 和 Kubernetes 本身就自带服务注册发现，不需要额外做什么。**

| 编排平台 | 服务发现方式 |
|---|---|
| **Docker Swarm** | 内置服务发现 |
| **Kubernetes** | **DNS 发现**（默认），也支持**环境变量**方式 |

**使用体验**：调用时**直接把服务名传进去**即可，**地址完全不用考虑**。

### 二、负载均衡（先分类再展开）

```
负载均衡
├── 硬负载（F5 等硬件设备）        ← 一般不用考虑
└── 软负载
      ├── 客户端负载均衡
      └── 服务端负载均衡（反向代理）
            ├── L4 传输层
            └── L7 应用层
+ 云厂商负载均衡（购买服务）
```

#### ① 客户端负载均衡

> **客户端自己维护实例列表并选择目标**——
> 例如客户端从 etcd 拿到服务列表后，**由客户端决定调哪一台**。
> （gRPC 结合 etcd 就是典型形态）

#### ② 服务端负载均衡（反向代理）

**分为两小类**：

| 层级 | 说明 | 代表实现 |
|---|---|---|
| **L4 传输层** | 只根据 IP/端口转发 | **Docker Swarm**、**K8s Service**——<br>用容器编排时**直接用即可，它们已经帮你做了传输层负载均衡** |
| **L7 应用层** | 能识别 HTTP 内容，可按路径/域名分发 | **Nginx 反向代理**：把多个目标地址配置进去，**默认按轮询（round-robin）分发**；<br>**K8s Ingress** 也属于应用层负载均衡，底层可以是 **Nginx / Kong** 等 |

#### ③ 云厂商负载均衡

> 直接**购买云厂商提供的负载均衡服务**（如 CLB/ALB），适合上云场景。

### 三、面试答题结构

```
【服务发现】
  传统方案：etcd/Zookeeper 注册 + 租约续期 + 客户端监听与本地缓存
  云原生方案：Swarm/K8s 内置（K8s 走 DNS），调用方只需传服务名

【负载均衡】
  客户端负载均衡（客户端自己选实例）
  服务端负载均衡：L4（Swarm/K8s Service）、L7（Nginx / K8s Ingress）
  云厂商 LB
```

> **答题要点**：**先分类，再结合自己的项目说用了哪一档、为什么**——
> 这比单纯罗列名词有价值得多。

## Q2. 微服务的注册、发现与健康检查是怎么实现的？（以 etcd 为例）

**来源**：`BV12qjA6aErF p=77` 百度 Go 研发日常实习 · 时长 10分13秒
**说明**：Q6 讲了"有哪些方案"，本题**补上 etcd 方案的实现细节**——
尤其是**租约（lease）这个机制**，以及**健康检查到底是怎么"自动生效"的**。

### 一、先讲清"为什么要做这件事"（目的比实现更重要）

| 要解决的问题 | 说明 |
|---|---|
| **服务注册与发现的目的：解耦客户端与服务端** | 分布式服务**有多个节点**，节点**动态管理**——<br>说不准哪台就宕机了、要补新节点，**新节点的 IP 可能就变了**。<br>**如果因此要改客户端代码，耦合就太高了。** |
| **健康检查的目的** | 注册中心**怎么发现"某个服务不好使了"**，<br>从而**通知客户端别再访问它** |

> **面试技巧**：先讲目的，再讲实现——面试官会立刻知道你理解这套机制**为什么存在**。

### 二、etcd 的租约（lease）：与 Redis 的关键差异 ⭐

**先记住这个差异**：

> **Redis**：**给每个 key** 单独设置有效时间（或者不设）。
>
> **etcd**：**租约是一个"容器"，一个租约下面可以挂多个 key-value。**

**所以**：想给某个 KV 设置有效时间，**必须先创建租约**，再把 KV 挂到这个租约上。

### 三、服务注册的三步流程

#### 第 1 步：创建租约

> **目的**：确保**服务信息在 etcd 中能够过期**。
> 通常租约时长设为 **10 秒**（原因见第 3 步）。

#### 第 2 步：写入 KV（用"服务名"组织 key）

```
key   = 服务名（前缀） + IP:端口（后缀）
```

> 因为既然是**服务注册**，就需要一个**服务名称**——
> **一个服务名下面会有多个地址**，
> 客户端**通过服务名就能发现这个服务的所有地址**。
>
> 这样 key 是唯一的，并且带着租约，**服务信息在 etcd 中有 10 秒有效期**。

#### 第 3 步：KeepAlive（续约）—— 这是健康检查的实现基础

**问题**：如果只写一次，10 秒后就过期了，**服务注册就毫无意义**。

**解法**：etcd 提供 **KeepAlive 机制**：

> **只要连接一直保持，租约就会不断续期**——
> 例如租约是 10 秒，**当剩余不足 5 秒时，自动续回到 10 秒**。
>
> **效果：服务信息一直保持在约 10 秒的有效期内。**

### 四、⭐ 健康检查是怎么"自动"实现的：被动式

**这是本题最漂亮的一点**：

```
KeepAlive 本质 = 服务端主动向 etcd 发送「心跳」
        ↓
etcd 收到心跳 → 对该 key 的租约进行续期
        ↓
服务宕机 → 续约停止
        ↓
租约到期 → key 自动过期删除
        ↓
客户端从监听到的变更中得知：这个地址没了
```

> **所以健康检查不需要额外的探测器**——
> **"服务挂了 → 心跳停 → 租约过期 → key 自动消失"**，
> 这是一条**被动式**的健康检查链路，完全靠租约机制自然实现。

### 五、服务发现的两个机制

#### 机制 1：拉取列表（Get）

```
客户端按「服务名」前缀向 etcd 发起请求
        ↓
拿到该服务下的全部地址列表
        ↓
在客户端本地构建一个 list（地址1、地址2、地址3…）
        ↓
每次请求时，客户端从本地 list 里选一个地址访问（★ 客户端负载均衡）
```

> **为什么按"服务名"发现**：**名称不会变**——
> 服务器宕机后重新加入的新节点，**依然在这个服务名下**。

#### 机制 2：Watch 监听（保证本地列表实时）

**问题**：本地 list 缓存了，但服务端节点会变化，怎么同步？

```
etcd 的前缀下有任何 key 发生变化
        ↓
etcd 通过「监听通道」把变更推送给客户端
        ↓
客户端据此更新本地 list：
   • 消失的地址 → 删掉
   • 新增的地址 → 加上
```

> **两个机制配合的效果**：
> **拉取列表保证"初始有数据"，Watch 保证"数据始终是最新的"**——
> 既避免了每次请求都去 etcd 拉全量（性能），又保证不会用过期地址（正确性）。

### 六、完整链路一图总结

```
【注册】
服务启动 → 创建租约(10s) → 写入 KV(服务名+IP:端口) → 周期性 KeepAlive 续约
                                                          ↓
                                              服务挂掉 → 心跳停 → key 过期删除
                                                          ↓
【发现】                                        （等价于被动健康检查）
客户端 → 按服务名拉取地址列表 → 本地 list + 本地负载均衡
       → Watch 监听前缀变化 → 实时更新本地 list
       → 用最新地址与服务端通信
```

### 面试官会追问什么

- **为什么租约设 10 秒？** → 是"**故障发现延迟**"与"**续约开销**"的折中：
  太长则服务挂了要很久才被发现；太短则心跳频繁、etcd 压力大。
- **etcd 和 Zookeeper 做注册中心的区别？** → etcd 基于 **Raft**（易理解、易运维）、
  提供 **Watch + 租约**、有 gRPC 接口；ZK 基于 **ZAB**、需要自己实现会话超时语义。
- **和 K8s 的关系？** → K8s 内部**也是用 etcd 存服务与端点信息**，
  并提供 **Service + Endpoints + Readiness Probe**，
  相当于把这套机制**做成了平台能力**——所以用了 K8s 就不用自己实现（见 Q6 方案 B）。
- **客户端负载均衡和服务端负载均衡怎么选？** → 客户端 LB **少一跳、性能好**，
  但**每个客户端都要实现服务发现逻辑**；服务端 LB（如 K8s Service / Nginx）
  **对客户端透明**，运维更简单。

## Q3. 为什么用注册中心而不用配置文件？

**来源**：`BV12qjA6aErF p=7` B站 Go 面试真题 · 时长 10分16秒
**考察意图**：这是**"为什么要有服务注册发现"的根问题**。很多人只会用不会讲动机——
要能从**分布式部署**这个前提出发，推出"配置文件方案行不通"的**具体痛点**。

### 一、前提：一切都是因为"分布式部署"

> 同一个应用程序**通常有多份副本、多台节点**在跑。一旦有多个节点，就冒出两个必须解决的问题：

1. **配置文件如何在这多个节点之间同步、保持一致？**
2. **节点 / 地址发生变化时，如何通知到客户端？**

**配置文件方案在这两件事上都很难做好**，于是才需要注册中心。

### 二、配置文件方案的五个痛点

| 痛点 | 说明 |
|---|---|
| **① 无法动态感知变化** | 改完配置，运行中的服务**不知道**；只能重启或人工触发重载 |
| **② 扩缩容必须逐个改配置** | 加了两台机器 → **每台客户端节点的配置都得改一遍**；IP 变了更是灾难 |
| **③ 没有健康检查** | 配置文件里写着地址，但**服务挂了它照样写着**，客户端会一直往死地址发请求 |
| **④ 多节点维护成本高** | 2~3 台还能手改；**20~30 台时人工修改很难保证正确，回滚更麻烦** |
| **⑤ 没有统一治理入口** | 配置散在各机器上，**没法统一查看"现在有哪些实例在线"** |

**第 ④ 点的实际疼法**（视频里讲得很具体）：

> 少量节点可以手改，也可以用脚本分发（改一台后执行脚本同步到其他机器）——
> 但**始终麻烦、容易出错**；**规模一大就失控，出了问题回滚也是麻烦事**。

### 三、注册中心到底解决什么（三个问题）

| 问题 | 实现 |
|---|---|
| **① 服务注册** | 服务端启动时向注册中心**写入自己的地址**（`服务名 + IP:端口`，以服务名为前缀） |
| **② 服务发现** | 客户端**按服务名**拉取该服务下的**全部地址清单**，并在**本地维护列表** |
| **③ 健康检查** | 靠 **KeepAlive（心跳续约）**：服务挂掉 → 心跳停 → **租约到期 → 记录自动过期** |

**三方角色**（说清这个，面试官就知道你是真懂）：

```
注册中心（如 etcd）  ←→  服务端（Server：写数据 + 保活）
        ↑
     客户端（Client：按名拉列表 + Watch 变更 + 本地列表 + 本地负载均衡）
```

### 四、用了注册中心，两个痛点怎么被消掉

**① 配置同步 → 监听 + 拉取**

> 配置统一更新到注册中心 / 配置中心，**每个应用只需实现"监听变化 + 拉取最新值"的逻辑**，
> 就能**非常方便地保证多节点配置一致**，不用再写同步脚本，也不怕回滚。

**② 服务地址变动的实时同步 → 注册 + 发现 + Watch**

> 服务端**注册**，客户端**按服务名发现**，节点增减由**注册中心监听并推送**——
> 客户端**不需要知道具体地址，也永远拿到最新的地址**。

### 五、和 K8s Service / DNS 方案的关系

| 方案 | 说明 |
|---|---|
| **自建注册中心** | 用 **etcd**（或 Zookeeper、Nacos、Consul）；<br>**单节点 Redis 也能凑合当注册中心用**（简单场景） |
| **K8s / Docker Swarm** | **本身就自带服务注册与发现，不需要额外部署注册中心**：<br>K8s 走 **Service + DNS**，调用方**直接把服务名传进去，地址完全不用管** |

> **所以"要不要注册中心"本质是"你的运行环境有没有提供这套能力"**：
> 用 K8s 就吃平台能力；自己管机器 / 容器就自己部署一套。

### 六、选型对比

| 组件 | 一致性协议 | 特点 | 适用 |
|---|---|---|---|
| **etcd** | **Raft** | 强一致、**Watch + 租约**原生支持、gRPC 接口、运维简单；**K8s 的选择** | 云原生、Go 生态首选 |
| **Consul** | Raft | 服务发现 + 健康检查 + KV + **多数据中心**，功能全 | 多机房、需要主动健康检查与 DNS 接口 |
| **Nacos** | Raft（CP）/ **Distro（AP）可选** | **服务发现 + 配置中心一体**、带控制台、Java / Spring Cloud 生态好 | 国内微服务、同时需要配置中心 |
| **Eureka** | **AP（无一致性协议）** | 只保可用性、**去中心化对等节点**、客户端缓存容错；**已停止维护** | 老 Spring Cloud 项目 |

> **一句话选型**：**K8s 环境直接吃平台能力；非 K8s 的 Go 项目优选 etcd；
> 需要"配置中心 + 控制台"选 Nacos；多机房选 Consul。**

### 面试答题结构

```
① 前提：分布式部署 → 配置同步 + 节点变化通知两个问题
② 配置文件方案五痛：不能动态感知 / 扩缩容要改配置 / 无健康检查 / 多节点维护与回滚难 / 无统一治理
③ 注册中心三件事：注册、发现（按服务名 + 本地列表）、健康检查（KeepAlive 自动下线）
④ 落地：etcd / Redis / 直接用 K8s 的 Service + DNS
⑤ 选型：etcd（云原生）/ Nacos（配置一体）/ Consul（多机房）/ Eureka（AP、已停维护）
```

### 面试官会追问什么

- **单节点 Redis 也能当注册中心，为什么不用它？** → 简单场景够用，
  但**没有 Watch 的一致性语义与强一致保证**（主从切换可能丢注册信息），
  续约与过期还要自己做；**etcd 的租约 + Watch 是为这件事专门设计的**。
- **注册中心自己挂了怎么办？** → **客户端本地已有列表可继续用**（这正是本地缓存的容错价值），
  只是**无法感知新的变更**；所以注册中心本身要做**集群（Raft 多数派）**。
- **它和"配置中心"是一回事吗？** → 不完全。**服务发现关注"谁在线、地址是什么"**，
  配置中心关注"参数值是什么"；**Nacos 把两者做在一起**，etcd 也能兼做配置中心。
- **健康检查是主动还是被动？** → etcd 方案是**被动式**：
  **不额外起探测器**，靠"心跳停 → 租约到期 → key 消失"自然实现（详见本册 Q2）。
- **服务名为什么必须是"名称"而不是 IP？** → **名称不变、地址会变**：
  **宕机后重新加入的新节点依然挂在同一个服务名下**，客户端代码因此无需修改。
