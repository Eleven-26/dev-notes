## Q1. Redis 缓存雪崩是什么？如何解决和预防？

**来源**：`p=2` 滴滴 Go 后端一面 · 时长 7分57秒
**考察意图**：能否讲清"故障链路"，而不只是背"加随机过期时间"这一个招式。

### 现象与成因

一句话：**大量 key 在同一时刻集中过期，请求不再命中缓存，全部打到数据库，把数据库打挂**。

用数字描述这个链路更清楚：

| 环节 | 量级 |
|---|---|
| 每秒打到 Redis 的请求 | 10000 QPS |
| 其中真正需要落库的（下单等） | 约 100 QPS |
| 数据库承受能力 | 约 1000 QPS |

正常情况下 Redis 消化掉 99% 的流量，数据库只承担 100 QPS，很安全。
但一旦 `goods:*`、`user:*` 这类 key **在 1~2 秒内集中过期**，10000 QPS 会直接砸到数据库——
数据库每秒只能处理 1000，积压至少要 10 秒才能消化完，期间响应超时、连接池耗尽，最终**整个服务不可用**。

### 解决方案（按层次给）

**1）分散过期时间（最直观）**
不要统一设 1 小时/半小时，而是在某个区间内**取随机值**，例如：

```go

// 原本：所有 key 都是 1 小时过期 -> 同一时刻集中失效
// 改为：在 [0, 12h) 内随机，让失效点均匀打散
expire := time.Duration(rand.Intn(12*3600)) * time.Second
rdb.Set(ctx, key, val, expire)
```

效果：把"1~2 秒内集中过期"摊平到 12 小时上，数据库在这 12 小时里**分散分担压力**，不会瞬间被打垮。

**2）分散过期的副作用，必须一起回答（这是加分点）**

| 副作用 | 说明 | 应对 |
|---|---|---|
| 缓存利用率下降 | 大量 key 长期处于无效状态，读请求频繁回源重载 | 随机区间不要开太大，按业务容忍度取值 |
| 缓存与数据库不一致 | 商品信息已修改，但缓存还没到期，读到的仍是旧值 | ① 修改数据时**主动更新/删除缓存**；② 后台**定时任务**提前刷新（如 5 分钟巡检一次，发现快过期就动态续期并回源） |

**3）兜底：限流 + 熔断降级（保护数据库）**
即使缓存全部失效，也不能让流量无差别打到数据库。在数据库前做最后一层保护：

- 超过数据库处理能力（如 1000 QPS）的请求**直接拒绝**；
- 服务降级：牺牲一部分用户体验，**保住数据库和整体服务的可用性**。

不这么做的代价：数据库挂掉后，恢复可能要从半小时到一小时，期间服务完全不可用。

### 面试官会追问什么

- **随机过期时间会不会导致缓存命中率下降？** → 会，需要在"打散程度"和"命中率"之间按业务取平衡点。
- **缓存和数据库不一致怎么保证？** → 见上表：写时更新缓存 + 定时兜底刷新。
- **只有雪崩吗？** → 顺带区分三个概念：
  | 问题 | 成因 | 特征 |
  |---|---|---|
  | 缓存雪崩 | 大量 key 集中过期 / 缓存服务宕机 | 大面积回源 |
  | 缓存击穿 | **单个热点 key** 过期 | 单点高并发回源 |
  | 缓存穿透 | 查询**根本不存在的数据** | 每次都绕过缓存打到库，需布隆过滤器/空值缓存 |

**易错点**：只答"加随机过期时间"就结束。这是第一层，面试官想听的是**缓存失效后的兜底设计**。

## Q2. 一个 key 的访问量巨大该怎么办？（热 key / 大 key）

**来源**：`p=11` 抖音 Go 一面 · 时长 8分32秒
**考察意图**：面试官补充的追问场景。考的是**能不能先梳理清楚"热点 key 会引发哪些问题"**，
而不是直接抛解决方案。

### 第一步：先把三个概念分清楚（面试必答）

| 问题 | 成因 | 特征 |
|---|---|---|
| **缓存雪崩** | **大量** key 在**同一时间**大面积过期 | 请求大面积回源，数据库整体被打垮 |
| **缓存击穿** | **单个热点 key** 过期 | 单点高并发绕过缓存，直接打库，后果与雪崩类似 |
| **缓存穿透** | 查询**根本不存在的数据** | 缓存永远加载不上（库里也查不到），每次请求都落到库，缓存形同虚设 |

**击穿的解法**：
1. **热点 key 设置为永不过期**，由后台任务定时更新；
   或在**会影响热点数据的操作发生时主动更新**缓存；
2. **数据库保护手段**：熔断降级——
   数据库只接收它能承受的请求量，**超出的绝大部分请求直接抛弃**，保住数据库不被打死。

**穿透的解法**：布隆过滤器 / 缓存空值（本题未展开，面试常追问）。

### 第二步：热点 key 除了击穿，还会带来 3 个问题（这是加分点）

**① 单线程阻塞**
不管是单 key 还是多 key，只要有**巨量访问**都会有问题：
Redis 核心处理是**单线程模型**，所有命令进入**同一个命令队列**逐个执行。
巨量请求必然在队列里排队，导致整体延迟上升。
→ 单节点只能**升配**或**加节点**（集群 / 读写分离）。

**② 网络带宽过载**
如果这个 key 的 **value 很大**，而访问量又高，每次访问都是一次网络请求——
**带宽会被打满**，造成网络拥堵。

**③ 集群倾斜（最容易被忽略）**
Redis 集群**按 key 做哈希分片**，而**同一个 key 永远落在同一个分片节点上**。
于是所有对热点 key 的请求都压在这一个节点上：

> 做集群本来是为了**通过扩展规模提升并发处理能力**，
> 结果热点全打在单个节点上 → **一个节点特别忙，其他节点很闲**，集群白做了。

### 第三步：对应的解决方案

**① 多 key 打散（针对集群倾斜）**
把同一个 Value 复制成**多个内容相同的 key**，分散到不同节点：

```go

key := fmt.Sprintf("hot:item:%d:%d", itemID, rand.Intn(N)) // N 个副本
```

读请求随机挑一个 key 访问，把压力摊到 N 个节点上。

**② 大 Value 拆成多个小 key（针对带宽过载）**
按**使用场景**拆分，而不是一股脑塞一个 key 里。以用户信息为例：

| 使用频率 | 数据 | 建议 key |
|---|---|---|
| 高频（每次请求都用） | 用户名、token、昵称 | `user:base:{uid}` |
| 低频 | 收货地址、联系人、通讯录 | `user:addr:{uid}` |

原则：**不同需求获取不同数据**，只取用得到的字段，减少每次的网络传输量。

> 注意与方案 ① 的区别：①是**内容相同的多副本**，用于打散集群压力；
> ②是**内容不同的小 key**，用于减少单次传输量。**这两个不是一回事**，面试时别混。

**③ 应用层本地缓存（针对单线程阻塞）**
在应用进程内再加一层本地缓存，**减少对 Redis 的访问次数**。

本地缓存的过期设计有个技巧：
> **不依赖本地缓存自身的过期时间**，而是把 Redis 中的过期时间**作为数据一起缓存到本地**，
> 本地缓存读取时依据数据里携带的过期时间来判断是否过期。

**需要注意的新问题**：引入本地缓存后，**一致性链路变长了**——
本地缓存与 Redis 的一致性、Redis 与数据库的一致性，都要一并考虑。

### 面试答题结构（可直接套用）

```
① 先定义场景：这是"热点 key 击穿" + 集群倾斜问题
② 列出会引发的问题：单线程阻塞 / 带宽过载 / 集群倾斜
③ 逐个给方案：多副本打散 / 大 value 拆分 / 本地缓存 + 熔断降级兜底
④ 补充代价：引入本地缓存会带来一致性成本
```

## Q3. 场景题：爬虫反复抓冷门数据，把热数据挤出缓存导致雪崩，怎么解决？

**来源**：`BV1xSRXBwEeM p=74` 虾皮 Go 后端面试 · 时长 7分57秒
**考察意图**：这是**"缓存雪崩 + 淘汰策略被污染"的组合场景题**。
面试官想看的不是背一遍雪崩定义，而是**能不能定位到"淘汰策略缺陷"这个根因**，再给出分层方案。

### 一、先判断：这是不是"真正的"雪崩？

**不一定，要先区分三种情况：**

| 情况 | 成因 |
|---|---|
| **① 淘汰策略缺陷（本题根因）** | 爬虫**批量访问冷门数据**，这些 key **在最近被使用过** → **被策略误判为热数据**；<br>而真正的长期热数据因为"近期不常访问"，**反而被优先淘汰** |
| **② 缓存空间不足（更根本）** | 缓存容量本身就小于数据量，**必然触发淘汰**；空间不足 + 策略缺陷 = 热数据被挤掉 |
| **③ 放大成雪崩** | 热数据被挤出后**请求全部回源数据库**，DB 吞吐远不及缓存 → **服务不可用** |

> **LFU 更危险**：它在"爬虫执行阶段"把**瞬时高频的冷门数据**当成高频 key，
> 长期热数据的"近期频率"反而落后 → **热数据被淘汰**。
> 也就是说，**"最近使用 / 访问频率"这个信号本身会被批量爬虫流量污染**。

### 二、解决思路（按优先级）

**① 隔离：爬虫流量和业务缓存分开（最优解）**

> **先问一句：被爬的数据和业务热数据是不是同一个业务？**
> - **是同一个业务** → 没办法隔离，只能走后面的手段；
> - **不是同一个业务** → **给爬虫单独一套缓存**（独立实例 / 独立 DB index / 独立命名空间），
>   让它**挤自己的空间，不污染业务缓存**。

这是**第一优先级**——**能隔离就隔离，别在淘汰策略上做文章**。

**② 热点数据保护**

| 手段 | 说明 |
|---|---|
| **永不过期 / 超长 TTL** | 热点数据物理上不设 TTL，避免"到期即失效回源" |
| **TTL 错落不一致** | 同批热 key **不要过期时间一致**，否则 30 分钟后**大面积同时过期**，<br>不需要冷数据来挤，自己就形成雪崩（详见 Q1） |
| **独立前缀 / 独立实例** | 给热数据用独立前缀或独立实例，**淘汰范围天然隔离** |

> ⚠️ 视频里提到"给热数据打标志"**意义有限**——
> **淘汰是系统级策略做的，不是业务代码按标记淘汰的**。
> 所以更实在的是"独立实例/前缀" + "永不过期"。

**③ 监控与告警（提前发现，而不是被打挂后救火）**

| 监控项 | 阈值示例 | 含义 |
|---|---|---|
| **缓存空间使用量** | 用到 1.5G / 1.8G（总量 2G）时告警 | **提前扩容**，别等写满 |
| **缓存命中率** | **5 分钟内低于 80%** 就告警 | 命中率骤降 = **热点被替换**或缓存设计不合理，<br>意味着大量流量要砸到 DB |
| **写入量 / key 数量突增** | 突增告警 | 判断是否有爬虫之类的**异常流量** |

> 原视频用 **Prometheus** 举例：**监控命中率是发现"热数据被挤出"最快的手段**。

**④ 调整淘汰策略（最后手段）**

> **不是首选**：空间够、隔离做好、热点保护做了，策略基本不用动。
> **只有真的空间受限时**才考虑调策略。

| 算法 | 思路 |
|---|---|
| **LRU-K** | 记录对象**最近 K 次**的访问历史，**访问次数达到 K 次**才进入淘汰候选范围——<br>**被爬虫扫一遍的冷门数据只有第 1 次访问，进不了候选** |
| **2Q** | 用两个队列（FIFO 准入队列 + LRU 主队列），<br>**新 key 先进准入队列，被再次访问才晋升到主队列**——同样过滤一次性访问 |

### 三、面试答题结构

```
① 定位根因：不是"雪崩"本身，而是"淘汰策略把冷门数据当热数据"→ 挤掉热数据 → 回源 → 雪崩
② 第一优先级：爬虫与业务是否同业务？不同 → 缓存隔离（独立实例 / 命名空间）
③ 热点保护：永不过期 / 超长 TTL / TTL 错落
④ 监控告警：空间使用量 + 命中率（低于 80% 即告警）
⑤ 最后才考虑：调整淘汰策略（LRU-K / 2Q 过滤一次性访问）
⑥ 兜底：数据库侧熔断限流（与 Q1 一致）
```

### 面试官会追问什么

- **为什么 LFU 会在这里失效？** → LFU 统计的是**访问频率**，
  爬虫短时间内把冷门数据刷成高频 → **频率信号被污染**；LRU 同样会被"最近访问过"骗到。
- **LRU-K / 2Q 的代价是什么？** → 需要**额外记录访问历史 / 多队列**，
  **实现更复杂、有额外内存与 CPU 开销**，且对"真正的首次热点访问"有**冷启动惩罚**。
- **隔离成两套缓存的运维成本怎么摊？** → 优先用**独立 DB index / 命名空间**而不是再起一套实例，
  资源隔离程度按爬虫量级决定。
- **命中率 80% 这个阈值合理吗？** → **按业务自定**：
  要看"未命中的流量砸到 DB 后 DB 扛不扛得住"；DB 余量大可放宽，余量小就要收紧。
- **和 Q1 的雪崩解法有什么区别？** → Q1 解决"**过期**导致的大面积失效"，
  本题解决"**淘汰**导致的热数据被挤掉"——**根因不同，但兜底手段（限流熔断）共用**。

## 使用一：Go（场景级封装）⭐

> 客户端初始化、五种数据结构操作、Pipeline、Lua、SetNX 基础版见 [命令与使用.md](命令与使用.md) 第七节，本节只写**把本文各题方案落成代码**的封装。
> 依赖与校验：以下 Go 代码在 `go-redis v9.22` / `bigcache v3.2` / `x/sync v0.23` 下 `go build` + `go vet` + `gofmt` 通过；因本机没有 Redis 实例，**未做运行时验证**。

### 0. 前置：中间件实例必须是单例

`redis.Client` 内部是**连接池**（默认每个 worker 一条连接，`PoolSize` 默认 10×CPU 数），`go-redis` 的 Client **本身并发安全**，全进程共用一个即可。所以：

```go

package cachePool

import (
	"os"
	"sync"
	"time"

	"github.com/redis/go-redis/v9"
)

// Client 是惰性单例：首次调用建连接池，之后所有 goroutine 复用同一实例。
// sync.OnceValue 自带 happens-before 保证，不存在"初始化与读取并发"的数据竞争（Go 1.21+），
// 比手写 sync.Once + 包级变量更不容易用错。用法：cachePool.Client().Get(...)
var Client = sync.OnceValue(func() *redis.Client {
	opt, err := redis.ParseURL(os.Getenv("REDIS_URL")) // 形如 redis://127.0.0.1:6379/0
	if err != nil {
		panic("cachePool: bad REDIS_URL: " + err.Error())
	}
	opt.PoolSize = 50                         // 默认 10×CPU 数；总连接数 ≈ 实例数 × PoolSize，必须小于服务端 maxclients
	opt.MinIdleConns = 5                      // 预热空闲连接，避免流量突增时集中建连抖动
	opt.DialTimeout = time.Second             // ⚠️ 三个超时都必须显式设：
	opt.ReadTimeout = 500 * time.Millisecond  //    不设的话 Redis 一卡，请求协程就无限堆积，
	opt.WriteTimeout = 500 * time.Millisecond //    最终把"缓存故障"放大成"整个服务不可用"
	return redis.NewClient(opt)
})
```

**为什么这条要写在最前面**：下面所有封装都是**有状态的**——`cachex.Cache` 持有 `singleflight.Group`，`multilayer.MultiLevel` 持有 L1 与订阅协程。如果按请求 `New` 一个出来：

| 每次请求新建 | 后果 |
|---|---|
| `redis.NewClient(...)` | 每个请求一套连接池，QPS 稍高就 `too many connections`，且池的空闲连接要等回收 |
| `cachex.New(...)` | 每次新的 `singleflight.Group` → **同 key 并发完全合不并，防击穿形同虚设**（Q1 击穿） |
| `multilayer.New(...)` | 每次一个新的 bigcache（L1 命中率归零 + 内存翻着倍涨）+ 多起一个 `Subscribe` 协程 → **协程泄漏** |

Java 侧同理：`StringRedisTemplate` / `RedissonClient` 由 Spring 容器管理，**默认就是单例 Bean**，用构造注入拿；**不要**在方法里 `new Jedis(...)`（Jedis 非线程安全且连接必须从 `JedisPool` 借还），也**不要**在方法里 `Caffeine.newBuilder().build()`——本地缓存每建一次就是一块新的堆内存。

### 1. 缓存三件套：TTL 打散 + singleflight 防击穿 + 空值防穿透

一个 `Get` 同时解决 Q1 的雪崩（打散过期）与 Q2 的击穿/穿透：

```go

package cachex

import (
	"bytes"
	"context"
	"errors"
	"math/rand"
	"time"

	"github.com/redis/go-redis/v9"
	"golang.org/x/sync/singleflight"
)

// ErrNotFound 表示数据库里确实没有这条数据（区别于"缓存未命中"）。
var ErrNotFound = errors.New("cachex: not found")

var nilValue = []byte("<nil>")

// Cache 把「读缓存 → 未命中回源 → 回填」收敛成一个入口。
// ⚠️ 全进程只建一个：g 是并发合并状态，见第 0 节。
type Cache struct {
	rdb *redis.Client
	g   singleflight.Group
	ttl time.Duration // 基准过期时间
}

func New(rdb *redis.Client, ttl time.Duration) *Cache {
	return &Cache{rdb: rdb, ttl: ttl}
}

// jitterTTL 在 [ttl, ttl*1.2) 内随机，把集中过期摊平（Q1 方案一）。
// 只在基准值上加 20%：区间开太大，缓存利用率会明显下降（Q1 的副作用）。
func (c *Cache) jitterTTL() time.Duration {
	return c.ttl + time.Duration(rand.Int63n(int64(c.ttl/5)))
}

// Get 未命中时用 loader 回源。loader 返回 ErrNotFound 会被缓存成空值，
// 这样同一个不存在的 key 在 TTL 内只会打库一次（Q2 的穿透解法）。
func (c *Cache) Get(ctx context.Context, key string, loader func(context.Context) ([]byte, error)) ([]byte, error) {
	v, err := c.rdb.Get(ctx, key).Bytes()
	if err == nil {
		if bytes.Equal(v, nilValue) { // 命中"空值缓存"
			return nil, ErrNotFound
		}
		return v, nil
	}
	if !errors.Is(err, redis.Nil) {
		return nil, err // Redis 自身故障要往上抛，不能默默回源打爆 DB
	}

	// Do 把「同一个 key 的并发回源」合并成一次，防止热点 key 过期瞬间 N 个请求同时打库（Q1 击穿）。
	// key 用副本 key 时，同副本内仍会合并，跨副本各自回源一次——这是打散方案的固有代价。
	shared, err, _ := c.g.Do(key, func() (interface{}, error) {
		data, lerr := loader(ctx)
		if lerr == ErrNotFound {
			if serr := c.rdb.Set(ctx, key, nilValue, c.jitterTTL()/4).Err(); serr != nil {
				return nil, serr
			}
			return nil, ErrNotFound
		}
		if lerr != nil {
			return nil, lerr
		}
		if serr := c.rdb.Set(ctx, key, data, c.jitterTTL()).Err(); serr != nil {
			return nil, serr
		}
		return data, nil
	})
	if err != nil {
		return nil, err
	}
	return shared.([]byte), nil
}
```

要点：

- **`errors.Is(err, redis.Nil)` 与"Redis 故障"必须分开处理**。把连接超时当成未命中去回源，等于在 Redis 宕机时主动制造雪崩——这正是 Q1 里"缓存服务宕机"那条成因。
- **空值缓存的 TTL 要短**（示例取基准的 1/4）：太长会让"数据刚写入却仍读到空值"的窗口变长。
- `singleflight` 只在**单进程内**合并；多实例部署时每台机器各回源一次，量级是"实例数"而不是"并发数"，通常够用。要跨实例合并只能靠锁（见 [分布式锁.md](分布式锁.md)），代价是延迟，一般不值。

### 2. 热 key 多副本 + 大 value 拆分（Q2 方案①②）

```go

package hotkey

import (
	"context"
	"fmt"
	"math/rand"
	"time"

	"github.com/redis/go-redis/v9"
)

// Read 从 N 个内容相同的副本里随机挑一个读，把压力摊到集群的不同分片上。
// 注意 key 的哈希要真的会落到不同槽：Redis Cluster 用 {tag} 决定路由，
// 因此副本后缀必须放在花括号之外，否则全部副本会被强制分到同一个节点。
func Read(ctx context.Context, rdb *redis.Client, itemID int64, replicas int) ([]byte, error) {
	key := fmt.Sprintf("hot:item:%d:%d", itemID, rand.Intn(replicas))
	return rdb.Get(ctx, key).Bytes()
}

// Write 需要把同一份 value 写满所有副本；删除同理。
func Write(ctx context.Context, rdb *redis.Client, itemID int64, replicas int, value []byte, ttl time.Duration) error {
	pipe := rdb.Pipeline()
	for i := 0; i < replicas; i++ {
		pipe.Set(ctx, fmt.Sprintf("hot:item:%d:%d", itemID, i), value, ttl)
	}
	_, err := pipe.Exec(ctx)
	return err
}
```

**⚠️ 这里的坑**：如果习惯用 `hot:item:{123}:0` 这种带 hash tag 的写法（为了和别的 key 进同一个槽以便事务/Lua），副本会**全部落在同一分片**，打散直接失效。写之前用 `CLUSTER KEYSLOT hot:item:123:3` 验一下不同副本是否落到不同槽。

**大 value 按使用频率拆 key**（Q2 方案②）是建模层面的事，落地时按表定义清楚即可：

```go

// 高频字段：几乎每次请求都要，单独一个 key，value 控制在 1KB 内
const userBaseKey = "user:base:%d"

// 低频字段：只在个人主页等少数场景用，读不到再回源，不跟 base 一起加载
const userAddrKey = "user:addr:%d"
```

### 3. 爬虫污染场景的隔离落地（Q3 方案①）

隔离优先用**独立 DB index 或独立实例**，代码上就是两条客户端配置，不要在业务里加 `if isCrawler` 判断：

```go

var (
	// 业务缓存：独立实例，淘汰策略按业务量配置，命中率和空间是它的 SLA
	bizRDB = redis.NewClient(&redis.Options{Addr: "redis-biz:6379", DB: 0})
	// 爬虫缓存：同一实例的不同 DB，或更稳妥的独立实例（DB 之间不隔离内存与淘汰）
	crawlerRDB = redis.NewClient(&redis.Options{Addr: "redis-biz:6379", DB: 7})
)
```

**⚠️ 同实例不同 DB 只隔离 key 空间，不隔离内存**：Redis 的淘汰是**实例级**行为，爬虫把 DB 7 写满照样会淘汰 DB 0 的 key（`maxmemory-policy` 默认 `allkeys-*` 时会跨 DB 淘汰）。所以真正的隔离要么给爬虫**独立实例**，要么在能配 `maxmemory-policy` 时确认其影响范围——**别把"换了 DB 号"当成容量隔离**。

上面的包级变量本身就是单例（进程启动时初始化一次）；如果偏好第 0 节的写法，就为两套缓存各建一个 `sync.OnceValue`，例如 `BizClient()` / `CrawlerClient()`，**关键是"每套缓存一个、全进程复用"**，不要在请求函数里 `redis.NewClient`。

## 使用二：Java（Spring Data Redis）
### 1. TTL 打散 + 防击穿（与 Go 版对应）

```java

@Service
public class GoodsCacheService {

    private final StringRedisTemplate redis;
    private final GoodsMapper mapper;
    // 同一 JVM 内合并并发回源：Caffeine 的 build 阶段天然对同 key 加锁，能起 singleflight 作用
    private final Cache<String, String> inflight = Caffeine.newBuilder()
            .maximumSize(10_000)
            .expireAfterWrite(Duration.ofSeconds(5)) // 只用来合并瞬时并发，不长期持有数据
            .build();

    private static final Random RANDOM = new Random();
    private static final Duration BASE_TTL = Duration.ofMinutes(30);
    private static final String NIL = "<nil>";

    public GoodsCacheService(StringRedisTemplate redis, GoodsMapper mapper) {
        this.redis = redis;
        this.mapper = mapper;
    }

    /** 基准 TTL 上再加 0~20% 随机，避免同批 key 集中过期（Q1 方案一）。 */
    private Duration jitterTtl() {
        return BASE_TTL.plusMillis(RANDOM.nextLong(BASE_TTL.toMillis() / 5));
    }

    public String get(Long id) {
        String key = "goods:" + id;
        String cached = redis.opsForValue().get(key);
        if (NIL.equals(cached)) {
            return null; // 命中空值缓存，说明库里确实没有（Q2 穿透）
        }
        if (cached != null) {
            return cached;
        }
        // ⚠️ 不要用 Redis 异常来触发回源：把连接失败 catch 掉当未命中，等于主动雪崩
        return inflight.get(key, k -> loadAndCache(k, id));
    }

    private String loadAndCache(String key, Long id) {
        String db = mapper.selectContentById(id);
        if (db == null) {
            // 空值也缓存，TTL 取 1/4，缩短"刚写入仍读到空"的窗口
            redis.opsForValue().set(key, NIL, BASE_TTL.dividedBy(4));
            return null;
        }
        redis.opsForValue().set(key, db, jitterTtl());
        return db;
    }
}
```

### 2. 热 key 打散与大 value 拆分（Q2）

```java

// 多副本打散：随机挑一个副本读，副本必须落在不同槽（集群下不要用 {tag} 把 key 钉在同一分片）
private static final int REPLICAS = 8;

public String readHotItem(RedisTemplate<String, String> redis, long itemId) {
    String key = "hot:item:" + itemId + ":" + RANDOM.nextInt(REPLICAS);
    return redis.opsForValue().get(key);
}

public void writeHotItem(RedisTemplate<String, String> redis, long itemId, String value) {
    // Pipeline 一次写满所有副本，避免 N 次往返
    redis.executePipelined((RedisCallback<Object>) conn -> {
        for (int i = 0; i < REPLICAS; i++) {
            byte[] k = ("hot:item:" + itemId + ":" + i).getBytes(StandardCharsets.UTF_8);
            conn.stringCommands().setEx(k, Duration.ofMinutes(30).toSeconds(), value.getBytes(StandardCharsets.UTF_8));
        }
        return null;
    });
}
```

## 使用三：热 key / 大 key 与命中率监控实操

方案能不能落地，取决于**先发现**。以下命令与指标对应 Q2（热 key / 大 key）、Q3（缓存污染），以及 [缓存选型与容量.md](缓存选型与容量.md) 里容量类问题的排查步骤：

```bash

# 1) 找大 key：SCAN 遍历采样，不阻塞（⚠️ 不要用 KEYS *，O(N) 会卡死单线程）
redis-cli -h 127.0.0.1 -p 6379 --bigkeys

# 2) 找热 key：要先开 maxmemory-policy=lfu 系或 4.0+ 的 IDLETIME 统计
redis-cli --hotkeys
redis-cli --freq                      # LFU 模式下看访问频率

# 3) 看单条命令耗时分布，确认是否被某个大 key 拖住
redis-cli --latency-history -i 1

# 4) 命中率（Q3 的告警项：5 分钟内 < 80% 告警）
redis-cli INFO stats | grep -E 'keyspace_(hits|misses)'
# 命中率 = hits / (hits + misses)，注意 hits/misses 是累计值，
# 告警要用"两次采样的差值"算窗口命中率，直接用累计值会被历史稀释

# 5) 内存与淘汰：used_memory 逼近 maxmemory 且 expired_keys/evicted_keys 突增 = 热数据正在被挤
redis-cli INFO memory | grep -E 'used_memory_human|maxmemory_human|maxmemory_policy'
redis-cli INFO stats | grep -E 'evicted_keys|expired_keys'

# 6) 实时看谁在打进来（临时定位爬虫类流量）
redis-cli MONITOR | head -n 2000      # ⚠️ 生产开启会明显掉吞吐，只能秒级采样
```

- **Prometheus 侧**：用 `redis_exporter`，核心告警是 `redis_keyspace_hits_total` / `misses_total` 的 rate 比值、`redis_evicted_keys_total`、`redis_memory_used_bytes / redis_memory_max_bytes`（如 2G 用到 1.5G 预警），对应 Q3 的三项监控。
- **Go/Java 里主动打点**：把 `Cache.Get` 的命中/未命中计数上报，才能算**业务维度**的命中率（Redis 侧的 hits 分不清是哪个接口掉的多）。
- **数据库兜底**（Q1 方案三）：限流器实现在 [限流器.md](../../Go/并发/限流器.md)，Java 侧配 Sentinel，见 [限流降级熔断.md](../../分布式/限流降级熔断.md)。
