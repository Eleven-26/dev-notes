## 一、Redis 的两种发布订阅分别怎么实现？

**来源**：`p=69` 腾讯云智后台开发一面 · 时长 5分18秒
**考察意图**：**很多人只知道第一种 Pub/Sub，不知道 Redis 5.0 还有 Stream**——
能讲清"两种"的差别就是本题的区分点。

### 总览：两种发布订阅

| | **① Pub/Sub（传统）** | **② Stream（Redis 5.0+）** |
|---|---|---|
| **消息存储** | **无**（没有消息存储中间件） | **可持久化** |
| **能否丢消息** | **可能丢失** | 不会（可持久化） |
| **能否读历史消息** | 后订阅者**拿不到历史消息** | 可以（按需从指定位置读） |
| **是否需要确认** | 无 | **有消费者组 + ACK 机制** |
| **类比** | **群聊** | **Kafka / RabbitMQ** |

### 一、Pub/Sub（传统发布订阅）

**特点**：

| 特征 | 说明 |
|---|---|
| **只在发布者和订阅者之间存在联系** | **没有消息存储的中间件** |
| **消息可能丢失** | 例如**发布者先发了消息，订阅者之后才订阅** → 订阅者拿不到这条 |
| **后续消息都能收到** | 订阅之后的消息可以正常收到 |
| **广播语义** | **所有订阅了同一频道的订阅者都能收到该频道的所有消息** |

**类比（很好记）**：
> 就像**群聊**——只要有人进了群，
> 之后有人发一条消息，**所有群成员都能收到**。

**局限**：**没有"消息确认"机制**，无法保证"这条我处理过了、不要再发给我"。

### 二、Stream（Redis 5.0 引入）

**定位**：**可以持久化的消息队列数据结构**——
在一定程度上和 **Kafka、RabbitMQ 是类似的**，可以承担消息队列的角色。

#### 四个核心概念

```text
消息日志（Stream） + 生产者 + 消费者 + 消费者组
```

#### 基本操作

**① 发布消息：`XADD`**

```bash
XADD mystream * field1 value1 field2 value2
```

> **`*` 表示消息 ID 自动生成**——因为**每条消息都有一个唯一 ID**。
> 一条消息里可以带**多个字段**。

**② 普通读取：`XREAD`（不推荐）**

```bash
XREAD BLOCK 0 STREAMS mystream $
```

> 客户端**阻塞读取** Stream。多个客户端同时阻塞读取时，
> 只要有 `XADD` 添加一条数据，**所有在读的客户端都能收到**。
>
> ⚠️ **但它没有消息确认机制**——
> 如果你想"我消费过了，不要再收到"，**只能人为处理**。
> **所以这种方式一般不用**。

**③ 消费者组方式（推荐）**

**创建消费者组**：

```bash
XGROUP CREATE mystream mygroup $      # $：从最新记录开始消费（之前的读不到）
XGROUP CREATE mystream mygroup 0      # 0：从最开始的位置消费（能读到历史记录）
```

> **消费者组的语义**：同一类型的消费者放在一个组里，
> **组内任何一个消费者消费了这条记录，就认为该记录已被消费**（互斥分发，不重复投递）。

**读取消息：`XREADGROUP`**

```bash
XREADGROUP GROUP mygroup consumer1 COUNT 1 STREAMS mystream >
```

**⚠️ `>` 和 `0` 的区别（这是最容易搞混的点）**：

| 标识 | 含义 |
|---|---|
| **`>`** | 读取一条**从未被任何消费者读取过的新数据**。<br>→ 组内有 10 个消费者时，**实际上只有一个消费者能读到这些新数据** |
| **`0`** | 读取**历史未确认的数据**（从指定 ID 开始找**第一条未确认**的记录） |

**消息确认：`XACK`**

```bash
XACK mystream mygroup <消息ID>
```

> 处理完业务后，**用 `XACK` 显式确认**，这条消息才算真正消费完成。
> （消息 ID 在读取时就能拿到，直接传进来即可。）

**适用场景**：和 **RabbitMQ、Kafka 类似的场景**——
需要**可靠投递、消费者组、消息确认**的消息队列需求。

### 三、怎么选（面试答题落点）

| 需求 | 选择 |
|---|---|
| **实时广播、允许丢消息** | **Pub/Sub**（更简单，如配置推送、轻量通知） |
| **需要可靠投递、消费者组、能重放** | **Stream**（如订单异步处理、事件驱动） |

> **答题亮点**：**主动说出"Pub/Sub 没有持久化和 ACK，所以只适合允许丢失的广播场景；
> 需要可靠性就用 Stream 或者干脆上 Kafka"**——
> 这说明你不只是"用过 API"，而是**理解两者的定位差异**。

### 面试官会追问什么

- **Pub/Sub 适合做业务消息队列吗？** → **不适合**。无持久化、
  订阅者掉线期间的消息永久丢失、无 ACK 重投。**只适合"丢了也没关系"的广播**。
- **Stream 相比 Kafka 的劣势？** → 单机/单分片吞吐和扩展性远不如 Kafka，
  集群方案不成熟；**适合中小规模**，超大规模仍应上 Kafka。
- **Redis 挂了消息会丢吗？** → 取决于持久化配置（AOF everysec 最坏丢 1 秒），
  以及主从切换是否丢同步中的数据。**要求严格不丢就不能只靠 Redis**。
