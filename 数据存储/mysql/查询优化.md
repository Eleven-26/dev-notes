# 查询优化

> 素材来源：《高性能 MySQL》（第 4 版）「查询性能优化」章的读后整理，**按主题归纳而非逐字摘录**，
> 行为以 InnoDB（MySQL 5.7 / 8.0）为准。
>
> 本篇讲"**在索引已经建好的前提下，怎么把一条 SQL 改快**"：优化器怎么决策、查询怎么重写、
> `COUNT` / 排序 / 分组 / JOIN 各自的优化点。
> 索引本身的结构与设计见 [索引设计.md](索引设计.md)；索引失效场景与慢查询排查流程见 [索引与优化.md](索引与优化.md)；
> 一条 SQL 的执行链路见 [查询链路.md](查询链路.md)。
>
> ⚠️ 本篇**不含实测输出块**：本机未连 MySQL 实例，凡涉及参数默认值与执行计划行为均取自
> 《高性能MySQL》与 MySQL 官方文档；文中 SQL 是可执行的**示例**，不是本机跑出来的结果。

## 一、先想清楚：优化到底在优化什么

书里把这件事归结成一句话：**减少访问的行数，减少返回的列数**。

| 方向 | 手段 | 收益来源 |
| --- | --- | --- |
| **少访问行** | 加/改索引、改查询写法（让条件能走索引） | 少一次磁盘 IO |
| **少返回列** | 只 `SELECT` 需要的列（覆盖索引） | 少一次**回表**（随机 IO） |
| **少查几次** | 缓存、预计算、冗余字段 | 根本不产生这次查询 |
| **少读数据** | 分页、延迟关联、异步化 | 分摊到多次小查询 |

⭐ **"最快的查询是不查"**：一条 SQL 优化到极致，也不如"结果已经在缓存里"。
所以排查性能问题时，**先问"这个查询是不是必须每次都算"**，再动手改索引。

两个常见的思维误区：

| 误区 | 纠正 |
| --- | --- |
| "把 SQL 写短一点会更快" | **优化器不看你写了几个字符**，它按执行计划走。改名、换大小写、拆行都不影响 |
| "加索引就能解决" | 索引解决"访问行数"，解决不了"要返回 10 万行给前端"——那是分页或异步的问题 |

## 二、优化器怎么选执行计划

### 2.1 基于成本，不是基于规则

MySQL 的优化器是**基于成本的**（cost-based）：它会枚举可行的执行计划，**估算每个计划的成本**，选最低的。

| 成本类型 | 估算依据 |
| --- | --- |
| **IO 成本** | 需要读多少个页（数据页 + 索引页） |
| **CPU 成本** | 需要比较多少行、排序多大结果集 |

**查看当前查询的估算成本**（单位是"页"）：

```sql
SHOW STATUS LIKE 'Last_query_cost';
```

这个值**只是估算**：它反映"优化器以为要花多少"，而不是真实开销。

### 2.2 为什么会选错索引

| 原因 | 说明 |
| --- | --- |
| **统计信息不准确** | `Cardinality` 是采样估算（见 [索引设计.md](索引设计.md) 第二节），分布倾斜时误差很大 |
| **估算模型简化** | 优化器假设"每个值均匀分布"、索引页都在内存里，与真实情况不符 |
| **条件之间有相关性** | 它假设 `WHERE city=? AND age=?` 两个条件相互独立，实际常常相关 |
| **没考虑 ORDER BY / LIMIT 的收益** | 走索引顺带排序可能更划算，但成本模型未必反映出来 |
| **多表 JOIN 时组合爆炸** | 表一多，优化器会放弃穷举，改用启发式（可能错过更优计划） |

**对策**：

| 手段 | 说明 |
| --- | --- |
| `ANALYZE TABLE t;` | 刷新统计信息（注意**它会隐式提交事务**） |
| 改写 SQL 引导优化器 | 比如把 `IN` 换成 `EXISTS`、加冗余条件让某个索引更"便宜" |
| `FORCE INDEX` / `USE INDEX` | **兜底手段**，会锁死计划，后续数据变化可能反而变差 |
| 上 `8.0` 的直方图 | `ANALYZE TABLE ... UPDATE HISTOGRAM ON col` —— 对有倾斜的列比采样更准 |

### 2.3 "全表扫描"不一定是错的

优化器选择 `type=ALL` 时，先看 `rows`：

| 情形 | 是否合理 |
| --- | --- |
| `rows` 只有几十 / 几百，表也小 | ✅ 合理 —— 随机 IO 的开销可能大于顺序全扫 |
| 查询要返回表中**大部分行**（如 `WHERE status != 'x'` 命中 90%） | ✅ 合理 —— 走索引反而要回表 90% 的行 |
| `rows` 很大、且只用到少量行 | ❌ 有问题 —— 缺索引或索引没用上 |

⭐ **判据**：**"要读的行占总行数的比例"**。经验上超过 20%~30% 时，全表扫描可能比走二级索引更快（因为二级索引要走两次：索引 + 回表）。

## 三、查询重写：10 个能直接落地的套路

| # | 反例 | 改法 | 为什么 |
| --- | --- | --- | --- |
| 1 | `WHERE YEAR(created_at) = 2026` | `WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01'` | **函数包住列 → 索引失效**，改成范围条件即可用索引 |
| 2 | `WHERE phone = 13800000000`（`phone` 是 varchar） | `WHERE phone = '13800000000'` | **隐式类型转换**等价于对列做函数运算 → 索引失效 |
| 3 | `WHERE a = 1 OR b = 2`（a、b 各有索引） | 拆成两条 + `UNION ALL` | 索引合并（index merge）多数情况不如两条 `ref` 查询；**注意用 `UNION ALL` 而不是 `UNION`**（后者要额外去重） |
| 4 | `SELECT * FROM t WHERE ...` | 只列需要的列 | 争取**覆盖索引**，直接省掉回表 |
| 5 | `LIMIT 1000000, 20` | 游标分页 / 延迟关联 | 深分页要丢弃前 100 万行；做法见 [索引与优化.md](索引与优化.md) |
| 6 | `WHERE id NOT IN (SELECT ...)` | 改 `LEFT JOIN ... WHERE x IS NULL` 或 `NOT EXISTS` | `NOT IN` 遇 NULL 语义诡异，且常无法用索引 |
| 7 | 主表小、子表大时用 `IN (SELECT ...)` | 改 `EXISTS` | 存在性判断提前短路（反之：子表小则用 `IN`） |
| 8 | 超大 `IN (1,2,...,5000)` | 分批（每批几百个） | 单条 SQL 解析+执行成本高，且可能撑爆 `max_allowed_packet` |
| 9 | 在 `WHERE` 里做运算 `WHERE amount + 100 > 500` | 移到右侧 `WHERE amount > 400` | 同上：列上不套运算 |
| 10 | `GROUP BY x ORDER BY NULL`（旧写法） | 8.0 里直接去掉 `ORDER BY NULL` | **8.0 起 `GROUP BY` 不再隐式排序**，这个"优化技巧"已过时 |

⚠️ 第 3 条的补充：**`OR` 不一定要拆**。如果同一列上的多个值（`WHERE a = 1 OR a = 2`），
直接用 `IN (1,2)` 即可（等价的索引范围扫描）；只有**不同列**上的 `OR` 才考虑拆或依赖索引合并。

## 四、`COUNT` 的优化

### 4.1 先说清语义差别

| 写法 | 语义 | 说明 |
| --- | --- | --- |
| `COUNT(*)` | 数**行数** | 不忽略任何行，`NULL` 行也算 |
| `COUNT(1)` | 数**行数** | 与 `COUNT(*)` 等价（**8.0 里执行计划完全相同**） |
| `COUNT(col)` | 数该列**非 NULL** 的个数 | **会漏掉 NULL**，语义完全不同 |

⚠️ **"`COUNT(1)` 比 `COUNT(*)` 快"是错误的**：优化器会把 `COUNT(*)` 转成数行操作，
且会**挑最小的那棵二级索引树**来扫（不读聚簇索引，省 IO）。所以两者没有性能差别，**别为了性能改写法，改了反而可能改错语义**。

### 4.2 InnoDB 的 `COUNT(*)` 为什么慢

MyISAM 把"总行数"存在表头，`SELECT COUNT(*)` 直接读一个数字（所以 MyISAM 的 `COUNT(*)` 极快，**但带 `WHERE` 就一样慢**）。

InnoDB **做不到**，因为 MVCC 下"有多少行可见"取决于**当前事务的快照** —— 同一条 `COUNT(*)`，不同事务看到的行数可能不同。**所以它必须逐行判断可见性。**

### 4.3 四个优化方向

| 方案 | 适用 | 代价 |
| --- | --- | --- |
| **维护计数表 / 计数列** | 需要精确值、更新不频繁 | 要保证与主表一致（同一事务内 `+1/-1`，或用触发器/异步补偿） |
| **Redis 计数** | 高并发、可容忍短时不准 | 与数据库的一致性要靠业务兜底 |
| **近似值** | "大概多少"够用时 | `EXPLAIN` 的 `rows` 是估算值，够快也够糙；`SHOW TABLE STATUS` 的 `Rows` 同理 |
| **只判断"是否超过 N"** | 分页只要展示"还有下一页" | `SELECT COUNT(*) FROM (SELECT 1 FROM t WHERE ... LIMIT 1001) x` —— **扫够 1001 行就停**，比全量数快得多 |

⭐ **第 4 条最实用**：前端"共 N 条"里的 N 本身就不可靠（翻到第 3 页数据可能已经变了）。
很多系统真正需要的只是"有没有下一页"，用一个带 `LIMIT` 的子查询就能把成本从"全表"降到"扫 1001 行"。

## 五、排序优化

### 5.1 `filesort` 的两种算法

`Extra` 里出现 `Using filesort` 时，MySQL 会在内存（或磁盘临时文件）里排序。它有两种策略：

| 算法 | 做法 | 内存占用 | 代价 |
| --- | --- | --- | --- |
| **全字段排序** | 把 `SELECT` 需要的**所有列**放进排序缓冲区，排完直接返回 | 大 | 无额外回表 |
| **rowid 排序** | 只放**排序键 + 主键**，排完再按主键**回表**取其余列 | 小 | 多一次随机 IO |

**选择依据**：单行长度是否超过 `max_length_for_sort_data`（默认 1024 字节）。
超过了就用 rowid 排序（省内存、多回表）。

⚠️ **由此可推出一个优化点**：如果一个查询既 `filesort` 又 `SELECT *`，
**它会走 rowid 排序并大量回表** —— 改成只 `SELECT` 少数字段，可能让它变成全字段排序，减少回表。

### 5.2 什么时候能用索引排序（避免 filesort）

三个条件同时满足：

1. `ORDER BY` 的列顺序与某个索引的列顺序**一致**；
2. 每一列的排序方向**一致**（都是 `ASC` 或都是 `DESC`；8.0 之前不支持混合方向，8.0 可用降序索引）；
3. `WHERE` 条件是该索引的**最左前缀等值条件**（一旦出现范围条件，后面的列就不再有序）。

```sql
-- 索引 (city, age)
SELECT age FROM users WHERE city = 'BJ' ORDER BY age;        -- ✅ 用索引排序
SELECT age FROM users WHERE city > 'A'  ORDER BY age;        -- ⚠️ city 是范围 → age 不再有序
SELECT age FROM users WHERE city = 'BJ' ORDER BY name;       -- ❌ 排序键不在索引里
```

### 5.3 `ORDER BY` + `LIMIT` 的细节

- 有 `LIMIT` 时 MySQL 会用**优先队列**（堆）而不是完整排序，只保留前 N 行 —— 这是 `ORDER BY ... LIMIT 10` 通常不慢的原因；
- 但**深分页**（`LIMIT 1000000, 10`）依然要**丢弃**前 100 万行，堆排序省不了这一步 → 用游标分页；
- **排序列有 NULL 时**，索引里 NULL 排在前面，可能打乱预期的顺序。

## 六、`GROUP BY` 与 `DISTINCT`

`GROUP BY` 通常隐含着"需要按分组键有序"或"需要临时表"：

| 执行方式 | 触发条件 | 表现 |
| --- | --- | --- |
| **松散索引扫描**（loose index scan） | 分组键是索引最左前缀，且不需要扫描全部行 | 最快，`Extra` 显示 `Using index for group-by` |
| **紧凑索引扫描**（tight index scan） | 分组键是索引前缀，但需要读全部匹配行 | 较快，无临时表 |
| **临时表 + 排序** | 分组键没有可用索引 | ❌ `Using temporary; Using filesort`（最慢） |

```sql
-- 索引 (city, age)
SELECT city, COUNT(*) FROM users GROUP BY city;              -- ✅ 松散索引扫描
SELECT city, COUNT(*) FROM users GROUP BY age;               -- ❌ 非最左前缀 → 临时表
SELECT city, COUNT(*) FROM users WHERE city = 'BJ' GROUP BY age;  -- ⚠️ 常量条件可跳过，看优化器判断
```

⚠️ **8.0 的一处行为变化**：8.0 之前 `GROUP BY` **隐式排序**（所以老代码里到处是 `GROUP BY x ORDER BY NULL` 来关掉排序）；
**8.0 移除了隐式排序**，需要排序就显式写 `ORDER BY` —— 老文章里的"`ORDER BY NULL` 优化"已经过时。

`DISTINCT` 的实现与 `GROUP BY` 类似（都可以用索引或临时表），**能用索引消重就不要用临时表**。

## 七、JOIN 优化

### 7.1 表连接的三个要点

| # | 要点 | 说明 |
| --- | --- | --- |
| 1 | **小表驱动大表** | 驱动表的每一行都要去被驱动表查一次；驱动表小，外层循环次数少 |
| 2 | **被驱动表的连接列必须有索引** | 没有索引就会退化成块嵌套循环（`Using join buffer`），复杂度从 `N × log M` 变成 `N × M` |
| 3 | **关联字段的类型必须一致** | 字符集或类型不一致会导致**隐式转换** → 被驱动表的索引失效（这是"JOIN 突然变慢"的常见原因） |

### 7.2 四种 JOIN 算法

| 算法 | 出现条件 | 复杂度 |
| --- | --- | --- |
| **NLJ**（嵌套循环） | 被驱动表连接列有索引 | `N × log M` ✅ |
| **BNL**（块嵌套循环） | 被驱动表连接列**无索引** | `N × M` ❌（`Extra` 会显示 `Using join buffer (Block Nested Loop)`） |
| **BKA**（批量键访问） | NLJ + MRR，把多行的键批量传给引擎一次读 | 比 NLJ 少一些随机 IO |
| **Hash Join**（8.0.18+） | 等值连接且无可用索引时**自动启用**，替代 BNL | 显著快于 BNL ✅ |

⭐ **看到 `Using join buffer (Block Nested Loop)` 就该警觉**：优先给被驱动表的连接列加索引；
实在加不了（或 8.0.18+ 已自动用 Hash Join），再评估是否需要改写查询。

### 7.3 两条实践建议

- **不要盲目 `STRAIGHT_JOIN`**：它强制驱动顺序，锁死了优化器的选择。只在"确认优化器选错、且数据分布稳定"时用；
- **JOIN 表数别太多**：MySQL 对 JOIN 的优化是"从左到右"的（不是全排列），表越多越容易选错驱动顺序 —— 单条 SQL 关联 5 张以上就该考虑拆查询或用应用层组装（这也正是互联网架构"少用 JOIN"的原因之一，见 [JOIN与反范式.md](JOIN与反范式.md)）。

## 八、优化的流程：别凭感觉改

```text
① 定位：慢查询日志  →  ② 排序：按总耗时排序，先改最值钱的  →  ③ 分析：EXPLAIN
→  ④ 判断层次：索引问题 / SQL 问题 / 架构问题  →  ⑤ 改一处，复测，再改下一处
```

**第 ④ 步的"三个层次"是核心判断**：

| 层次 | 症状 | 手段 |
| --- | --- | --- |
| **索引问题** | `key = NULL`、`type = ALL`、`Using filesort` | 加/改索引，改写 SQL 让条件能用索引 |
| **SQL 问题** | 索引没问题，但逻辑本身要求大量数据（深分页、全表 COUNT、大结果集） | 改写法（游标分页、延迟关联、只判断"是否超过 N"） |
| **架构问题** | 单条 SQL 已经最优，但量级上不去了（热点行、超大表、强一致读） | 加缓存、读写分离、分表、异步化、预计算 |

⚠️ **用架构手段解索引问题，或用索引手段解架构问题，都是白费力气**。
一条 SQL 的瓶颈在"每次都要扫描上万行"时，加机器也没用；反过来，量级到亿级之后，
再精妙的索引也救不回"每次都要随机读很多页"。

另外两条纪律：**一次只改一处**（否则不知道是谁起的作用）、**用数据说话**（改前改后都要 EXPLAIN + 计时）。

## 九、面试官会追问什么

- **优化的总思路是什么？** → 两句话：**减少访问的行数、减少返回的列数**；再加一句"**最快的查询是不查**"（能缓存/预计算就别每次算）。
- **优化器为什么会选错索引？** → 统计信息是**采样估算**（可能失真）、成本模型假设值均匀分布、条件之间实际相关、JOIN 表多时放弃穷举。对策：`ANALYZE TABLE`、8.0 直方图、改写 SQL，`FORCE INDEX` 只作兜底。
- **优化器选全表扫描一定是问题吗？** → 不一定。判据是"**要读的行占总行数的比例**"，超过 20%~30% 时全扫可能更快（走二级索引要索引 + 回表两次）。先看 `rows`。
- **`COUNT(*)` 和 `COUNT(1)`、`COUNT(col)` 有什么区别？** → 前两者**完全等价**（8.0 执行计划相同）；`COUNT(col)` **会漏掉 NULL**，语义不同。**"`COUNT(1)` 更快"是错的**。
- **为什么 InnoDB 的 `COUNT(*)` 慢，MyISAM 的快？** → MyISAM 存了总行数（但带 `WHERE` 一样慢）；InnoDB 因为 MVCC，**"可见行数"取决于事务快照**，必须逐行判断。
- **`COUNT(*)` 怎么优化？** → 维护计数表/Redis（要接受一致性成本）、用近似值（`EXPLAIN` 的 `rows`）、或者**只判断"是否超过 N"**（`LIMIT 1001` 子查询，最实用）。
- **`filesort` 是怎么排的？** → 两种：**全字段排序**（把 `SELECT` 列都放进排序缓冲区）和 **rowid 排序**（只放排序键 + 主键，排完回表）。分界是单行长度与 `max_length_for_sort_data`（默认 1024 字节）。**`SELECT *` + `filesort` 会退化成 rowid 排序并大量回表**。
- **怎么让 `ORDER BY` 用上索引？** → 三个条件：列顺序与索引一致、排序方向一致、`WHERE` 是该索引的最左前缀**等值**条件（有范围条件后面的列就不有序了）。
- **`GROUP BY` 为什么慢？** → 没有合适的索引时会用**临时表 + filesort**（`Using temporary`）。分组键是索引最左前缀时能走松散/紧凑索引扫描。**8.0 起 `GROUP BY` 不再隐式排序**，老文章里的 `ORDER BY NULL` 技巧已过时。
- **JOIN 的核心优化点？** → 三条：**小表驱动大表**、**被驱动表的连接列必须有索引**（否则退化成 BNL）、**关联字段类型/字符集一致**（否则隐式转换让索引失效）。8.0.18+ 无索引时会自动用 Hash Join。
- **`Using temporary` 一定不好吗？** → 它是"需要临时表"的信号，通常要消除；但别看到就改 —— **小结果集用临时表代价很低**，为它多建一个索引往往更亏。
- **加索引能解决所有慢查询吗？** → 不能。分三个层次判断：**索引问题 / SQL 问题 / 架构问题**。用错层次的手段都是白费力气（比如用加索引去解决"深分页"或"每次要返回 10 万行"）。
