## Q1. User 表分表之后，怎样用非分表键（A 或 B 字段）定位数据在哪张表？

**来源**：`BV12qjA6aErF p=53` 百度 AIGC Go 后端开发 · 时长 9分24秒
**考察意图**：这是一道**分库分表的场景设计题**。面试官想听的顺序是：
**先讲分表键该满足什么条件** → 再给**几种路由方案并对比代价** → 最后说出**你的选择理由**，
而不是一上来就报一个方案名字。

### 一、问题还原

`user` 表数据量太大，已经按 `user_id` 哈希分成了 256 张表（`user_0000` ~ `user_0255`）；
现在业务要求：**用 A 字段或 B 字段**（比如手机号、邮箱）也能查到"这条数据在哪张表"。

### 二、分表键（sharding key）必须满足的四个条件

| 条件 | 说明 |
|---|---|
| **① 可哈希** | 能被稳定地哈希 / 映射到某张表。**分表的本质和"在单表里建索引"是一样的**：索引负责"定位到行"，分表键负责"定位到表" |
| **② 不可变** | 分表键一旦变化，数据就要**在表之间搬家**。比如用手机号分表，用户换个号就得把整行从 1 表迁到 2 表；**就像索引列频繁更新会带来额外维护开销** |
| **③ 分布均匀** | ID 连续递增时分布天然均匀；但**手机号按号段分布是不可控的**——可能出现某号段占 80% 数据、其余 255 张表只占 20% 的严重倾斜，**分表就失去意义了** |
| **④ 唯一性** | 分表键最好在单表内就是**主键或具备唯一性**（如 `user_id`），否则无法保证定位准确 |

### 三、三种路由方案（视频的完整推演）

**方案一：独立哈希 `Hash(A)` / `Hash(B)` —— ❌ 不可行**

```text
Hash(A) → table_id = 17
Hash(B) → table_id = 93      ← 同一条数据，两个字段算出来不是同一张表
```

数据**只存了一份**，而 A 和 B 指向不同的表，**无法确定数据到底在哪**——直接否定。

**方案二：双哈希冗余存储（同一条数据存两份）—— ⚠️ 可行但费空间**

按 A 哈希存进 `table_17`，再按 B 哈希存一份进 `table_93`。两个入口都能查到，
但**同一份数据占了两倍空间**，且两份数据要保证一致（写入、更新、删除都要双写），**维护成本高**。

**方案三：路由表 / 全局索引表（二次索引）—— ✅ 视频作者倾向的方案**

**单独维护一张"业务字段 → 表序号"的映射表**，业务表里不放任何冗余数据：

```sql
-- 路由表：只存映射关系，不存业务数据
CREATE TABLE user_route (
  id           BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id      BIGINT           NOT NULL,
  phone        VARCHAR(20)      NOT NULL,
  email        VARCHAR(64)      NOT NULL,
  table_suffix TINYINT UNSIGNED NOT NULL,   -- 0~255，表示落在 user_0000 ~ user_0255
  UNIQUE KEY uk_user_id (user_id),
  UNIQUE KEY uk_phone   (phone),
  UNIQUE KEY uk_email   (email)
) ENGINE=InnoDB;
```

查询分两步：**① 用 A（或 B）查 `user_route` 拿到 `table_suffix` → ② 拼出真实表名 `user_00xx`，按主键查业务数据。**

**为什么倾向它**：

- 只多消耗**索引表**的空间，**不需要双倍的数据空间**；
- 通过 A 或 B 都能稳定找到同一条数据，**一致性由路由表本身保证**；
- 代价是**多一次查询**（可以用缓存兜住），以及写入时要**同步维护路由表**。

### 四、三种方案对比

| 方案 | 空间代价 | 一致性 | 额外查询 | 结论 |
|---|---|---|---|---|
| 独立哈希 A / B | 无 | ❌ 定位不确定 | — | 不可行 |
| 双哈希冗余存储 | **2 倍数据空间** | 需要双写保证 | 无 | 可行但成本高 |
| 路由表（二次索引） | 1 份索引空间 | 由路由表保证 | **多一次查表** | ✅ 推荐 |

### 五、补充：业界另外两种常见做法（视频未展开）

| 做法 | 思路 |
|---|---|
| **基因法** | 把分表键的"基因"编码进另一个字段的尾部，让非分表键也能反推出路由。例如按 `user_id` 分 256 张表时，把 `user_id` 的低 8 位拼进生成的订单号低位，这样**用订单号也能直接算出该去第几张表**，连映射表都省了 |
| **异构索引（再建一份数据）** | 用 B 字段作为分表键**再建一份数据**（通常通过 binlog / MQ 异步同步），两份数据各自服务不同的查询入口；本质是"数据异构 + 各自路由"，代价与方案二的冗余存储类似 |

### 面试官会追问什么

- **分表键为什么要求"不可变"？** → 值一变就要跨表搬数据，类似索引列频繁更新带来的额外开销。
- **手机号为什么不适合直接当分表键？** → 号段分布不均，会造成严重的数据倾斜。
- **路由表会不会成为瓶颈？** → 会，所以通常**加缓存**（本地缓存 + Redis），
  或者只在"非分表键查询"这一条链路上引入它，主链路仍按分表键直接定位。
- **表数扩容了怎么办？** → 路由表方案只需**改映射**；纯哈希路由扩容会引发大规模数据搬迁，
  可以用**一致性哈希**减少迁移量，或者**成倍扩容**（256 → 512）来摊薄重分布成本。
- **分表键的值怎么生成？** → 常用**雪花算法**生成全局唯一且趋势递增的 ID，
  既保证唯一性，也让 `user_id` 这类分表键分布均匀。

### 1. 分表路由：表名只能由整数生成，条件值仍然走占位符

`?` 占位符**只能代表值，不能代表标识符**（表名、列名），所以分表必然要拼表名。
安全的前提是：**拼进去的字符串只能由自己格式化出来，绝不包含外部输入**。

```go
package sharddemo

import (
	"context"
	"database/sql"
	"fmt"
	"hash/fnv"
)

// TableCount 是"基因位宽"的来源，改动会连带影响 ID 兼容性（见第 3 节）。
const TableCount = 256

// Hash 暴露**原始**哈希值：扩容时只换除数、不换哈希（见第 4 节）。
func Hash(shardKey string) uint32 {
	h := fnv.New32a()
	_, _ = h.Write([]byte(shardKey)) // hash 实现不会返回错误
	return h.Sum32()
}

// Route 用 FNV-1a 算表序号。
// ⚠️ 只用于**不可变且分布均匀**的分表键（user_id / 雪花 ID）。
// 手机号、邮箱前缀这类输入直接 Route，会得到严重倾斜的分布——正文 Q1 条件 ③。
func Route(shardKey string) int {
	return int(Hash(shardKey) % TableCount)
}

// TableName 是表名的**唯一**来源：整数格式化，不含任何外部字符串 → 没有注入面。
func TableName(shardKey string) string {
	return fmt.Sprintf("user_%04d", Route(shardKey))
}

// MustTableName 用于路由表回查到的后缀（正文方案三），同样要校验范围。
func MustTableName(suffix int) (string, error) {
	if suffix < 0 || suffix >= TableCount {
		return "", fmt.Errorf("sharddemo: bad table suffix %d, out of [0,%d)", suffix, TableCount)
	}
	return fmt.Sprintf("user_%04d", suffix), nil
}

// GetUser 的正确形态：表名自己拼，值走占位符。
func GetUser(ctx context.Context, db *sql.DB, userID string) (string, error) {
	q := `SELECT name FROM ` + TableName(userID) + ` WHERE user_id = ?`
	var name string
	err := db.QueryRowContext(ctx, q, userID).Scan(&name)
	return name, err
}
```

**三种写法的边界**（面试和 code review 都常被问到）：

| 写法 | 结果 |
|---|---|
| `SELECT ... FROM ? WHERE id = ?` | ❌ **语法错误**：占位符不能代表标识符 |
| `SELECT ... FROM user_00` + 外部输入拼接 | ❌ 注入面：输入 `/tmp` 之外的任何东西都能改写语句 |
| `TableName(key)`（整数格式化）+ 值用 `?` | ✅ 唯一正确形态 |
| ORM/QueryBuilder 里 `Table(userInput)` | ⚠️ 必须自己校验白名单，ORM **不会**替你转义表名 |

### 2. 路由表方案（正文的方案三）：缓存 + singleflight 防击穿

正文的结论是「路由表要加缓存，否则它自己就成了瓶颈」。注意**瓶颈有两种**：
数据库读放大（缓存解决）和**冷 key 并发回源**（singleflight 解决）——只做前者仍然会打穿。

```go
package sharddemo

import (
	"context"
	"database/sql"
	"fmt"
	"sync"
	"time"

	"golang.org/x/sync/singleflight"
)

type routeEntry struct {
	suffix int
	expire time.Time
}

// Router 必须**单例**使用：它的缓存和 flight 都是实例状态，
// 每次请求 new 一个 Router 等于没有缓存，也合并不了并发回源。
type Router struct {
	db  *sql.DB // 注入的连接池
	ttl time.Duration

	mu    sync.RWMutex
	cache map[string]routeEntry

	// ⚠️ singleflight.Group 内含 mutex，不可拷贝；因此 Router 只能以 *Router 传递。
	flight singleflight.Group
}

func NewRouter(db *sql.DB, ttl time.Duration) *Router {
	return &Router{db: db, ttl: ttl, cache: make(map[string]routeEntry)}
}

// routeColumn：非分表键 -> 路由表列名，**白名单映射**。
// 这里必须 switch，绝不能 `"WHERE " + field + " = ?"`——那就是把注入面 reopened。
func routeColumn(field string) (string, error) {
	switch field {
	case "phone", "email":
		return field, nil
	default:
		return "", fmt.Errorf("sharddemo: unsupported route field %q", field)
	}
}

// Lookup 两步查：本地缓存 -> 合并并发回源 -> 路由表。
func (r *Router) Lookup(ctx context.Context, field, value string) (int, error) {
	col, err := routeColumn(field)
	if err != nil {
		return 0, err
	}
	key := col + "\x00" + value // 分隔符防止 ("a","bc") 与 ("ab","c") 撞 key

	r.mu.RLock()
	e, ok := r.cache[key]
	r.mu.RUnlock()
	if ok && time.Now().Before(e.expire) {
		return e.suffix, nil
	}

	// 缓存过期时，1000 个并发会同时打到路由表；Do 让它们只发一次查询
	v, err, _ := r.flight.Do(key, func() (any, error) {
		q := `SELECT table_suffix FROM user_route WHERE ` + col + ` = ?`
		var suffix int
		if err := r.db.QueryRowContext(ctx, q, value).Scan(&suffix); err != nil {
			return nil, err // sql.ErrNoRows 原样返回，让调用方决定"未注册"怎么处理
		}
		if _, err := MustTableName(suffix); err != nil {
			return nil, err // 路由表被写脏时宁可报错，也不要拼出一个不存在的表
		}
		r.mu.Lock()
		r.cache[key] = routeEntry{suffix: suffix, expire: time.Now().Add(r.ttl)}
		r.mu.Unlock()
		return suffix, nil
	})
	if err != nil {
		return 0, err
	}
	return v.(int), nil
}

// Drop 在换绑手机号 / 注销时精确失效，不要清整张表缓存。
func (r *Router) Drop(field, value string) {
	col, err := routeColumn(field)
	if err != nil {
		return
	}
	r.mu.Lock()
	delete(r.cache, col+"\x00"+value)
	r.mu.Unlock()
}

// Register：业务表和路由表**必须同一事务**，否则会出现
// "业务数据在 0137 表、路由表里没有 phone" 的孤儿数据（正文方案三的代价）。
func (r *Router) Register(ctx context.Context, userID int64, phone, email string) error {
	suffix := Route(fmt.Sprint(userID))

	tx, err := r.db.BeginTx(ctx, nil)
	if err != nil {
		return err
	}
	defer func() { _ = tx.Rollback() }()

	table := fmt.Sprintf("user_%04d", suffix)
	if _, err := tx.ExecContext(ctx,
		`INSERT INTO `+table+` (user_id, name) VALUES (?, ?)`, userID, "u"+fmt.Sprint(userID)); err != nil {
		return err
	}
	if _, err := tx.ExecContext(ctx,
		`INSERT INTO user_route (user_id, phone, email, table_suffix) VALUES (?, ?, ?, ?)
         ON DUPLICATE KEY UPDATE phone = VALUES(phone), email = VALUES(email), table_suffix = VALUES(table_suffix)`,
		userID, phone, email, suffix); err != nil {
		return err
	}
	if err := tx.Commit(); err != nil {
		return err
	}

	r.Drop("phone", phone) // 写入成功后必须失效旧缓存，否则 TTL 内还会路由到旧表
	r.Drop("email", email)
	return nil
}
```

> ⚠️ 两个真实运维坑：
> ① `user_route` 自身也是单表，**它迟早成为新的容量瓶颈**——它只存映射，所以可以先按 `user_id` 分表，
> 或者整张表塞进 Redis（数据结构用 `SET`/`HASH`，见 [命令与使用.md](../redis/命令与使用.md)）；
> ② 换手机号是**改路由表 + 清缓存**两个动作，必须做成"先改库、再失效、失败就告警"，
> 只失效不改库或只改库不失效都会留下长期的错路由。

### 3. 基因法：让订单号自带路由信息（Q1 第五节补充方案的最小实现）

这是最省事的方案——**连映射表都不要**。代价是位宽被写死：256 张表占 8 位，扩到 512 张就要 9 位。

```go
package sharddemo

import (
	"errors"
	"fmt"
	"sync"
	"time"
)

var ErrClockMoved = errors.New("sharddemo: clock moved backwards")

// 位布局（int64，共 63 位可用）：
//
//	|<---------- 38 位 毫秒(相对 epoch) --------->|<7 位机器>|<10 位序列>|<8 位基因>|
//	 63                                     25   24      18   17       8   7       0
//
// 基因 = Route(user_id) 的结果放在**最低 8 位**，于是订单号本身就能反推出表号。
const (
	geneBits  = 8
	seqBits   = 10
	machineBt = 7 // 7 + 10 + 8 = 25 位低区，时间戳左移 25
	epochMs   = 1767225600000
)

type IDGen struct {
	mu      sync.Mutex
	lastMs  int64
	seq     int64
	machine int64
	now     func() time.Time // 便于测试注入
}

func NewIDGen(machine int64) (*IDGen, error) {
	if machine < 0 || machine >= 1<<machineBt {
		return nil, errors.New("sharddemo: machine id out of 7-bit range")
	}
	return &IDGen{machine: machine, now: time.Now}, nil
}

// Next 生成订单号。gene 必须来自与写路径**同一个** Route(user_id)——
// 两边算法/表数只要不一致，反查就会把请求路由到一张没有这条数据的表。
func (g *IDGen) Next(gene int) (int64, error) {
	if gene < 0 || gene >= 1<<geneBits {
		return 0, errors.New("sharddemo: gene out of 8-bit range")
	}

	g.mu.Lock()
	defer g.mu.Unlock()

	ms := g.now().UnixMilli() - epochMs
	switch {
	case ms < g.lastMs:
		// ⚠️ 时钟回拨：宁可报错让上层重试/切机器，也不要生成重复 ID
		return 0, ErrClockMoved
	case ms == g.lastMs:
		g.seq++
		if g.seq >= 1<<seqBits {
			return 0, errors.New("sharddemo: sequence overflow in one millisecond")
		}
	default:
		g.seq = 0
		g.lastMs = ms
	}

	return ms<<(geneBits+seqBits+machineBt) |
		g.machine<<(geneBits+seqBits) |
		g.seq<<geneBits |
		int64(gene), nil
}

// RouteByOrderID 反查表号：这就是基因法的全部收益——省掉一次路由表查询。
func RouteByOrderID(orderID int64) int {
	return int(orderID & (1<<geneBits - 1))
}

// OrderTable 由订单号直接得到表名。
func OrderTable(orderID int64) string {
	return fmt.Sprintf("order_%04d", RouteByOrderID(orderID))
}
```

```go
package sharddemo

// 扩容时位宽就变了：256 表 -> 8 位，512 表 -> 9 位。
// 已生成的订单号里低 9 位不保证为 0，所以只能：
//
//	① 新建 ID 空间（新订单走 9 位、老订单仍按 8 位读），或
//	② 提前把基因位宽留够（常见做法是固定留 16 位，代价是时间戳位数变少）。
const DoublingSafeGeneBits = 16
```

### 4. 表数扩容：为什么"成倍扩"搬迁量最小

正文追问「表数扩容了怎么办」，成倍扩容可以落到一行判断上：

```go
package sharddemo

import "fmt"

// DoublingRoute：从 oldCount 扩到 newCount（要求正好翻倍）时，
// 同一个 key 的新表号只可能是 old 或 old+oldCount——
// 因为 h % (2N) ∈ {h % N, h % N + N}。于是搬迁可以**以旧表为单位**整批做，不必逐 key 重算。
func DoublingRoute(shardKey string, oldCount, newCount int) (int, error) {
	if newCount != oldCount*2 {
		return 0, fmt.Errorf("sharddemo: only doubling is supported (got %d -> %d)", oldCount, newCount)
	}
	return int(Hash(shardKey) % uint32(newCount)), nil
}

// RouteBoth 是迁移期的关键用法：**同一个原始哈希**分别对旧/新表数取模。
// ⚠️ 千万不要"拿旧表号再哈希一次"或对 Route 的结果取模——那是对哈希做二次哈希，
// 分布性质会变差，而且失去"只搬两张表"的保证。
func RouteBoth(shardKey string, oldCount, newCount int) (int, int) {
	h := Hash(shardKey)
	return int(h % uint32(oldCount)), int(h % uint32(newCount))
}

// PlanDoubling：旧表 oldSuffix 的数据在新表数下只会落到这两张表 → 按表整批搬迁即可。
func PlanDoubling(oldSuffix, oldCount int) (string, string) {
	return fmt.Sprintf("user_%04d", oldSuffix), fmt.Sprintf("user_%04d", oldSuffix+oldCount)
}

// MigrateDoubling 用一条 SQL 完成"旧表 -> 新表"的整表拆分（示意：真实场景要分批 + 限速）。
// 判据就是新增的那一位：h % (2N) >= N 的行才需要搬。
//
// ⚠️ 只有当路由函数**本身就是整数取模**（如 user_id % 256）时，才能这样将哈希下推到 SQL。
// 本包用的是应用层 FNV-1a，MySQL 里没有对应函数——硬写成 CRC32 会让"迁移脚本算的表号"
// 和"线上路由算的表号"不一致，属于静默错路由。真实做法是要么把路由函数写成取模，
// 要么在应用层算好目标表名再逐行搬（下面 Java 侧 ShardingSphere 的 HASH_MOD 就是取模路由）。
func MigrateDoubling(oldSuffix int, shardCol string, oldCount int) string {
	src, dst := PlanDoubling(oldSuffix, oldCount)
	return fmt.Sprintf(
		`INSERT INTO %s SELECT * FROM %s WHERE MOD(%s, %d) >= %d;
         DELETE FROM %s WHERE MOD(%s, %d) >= %d;`,
		dst, src, shardCol, oldCount*2, oldCount, src, shardCol, oldCount*2, oldCount)
}
```

> ⚠️ 上面 `hashKey` 是**故意留的反例**：它对 `Route` 的结果再取模，等于对哈希做二次哈希，分布性质会变差。
> 正确做法是保留原始 32 位哈希值（`routeBoth` 里的 `fnvHash`），只对**取模的除数**做变化。
> 需要"扩容时只动 K/N 的数据"就用一致性哈希（见 [服务发现与负载均衡.md](../../分布式/服务发现与负载均衡.md) 的一致性哈希一节）。

## 使用二：Java（ShardingSphere-JDBC 与动态表名）

> ⚠️ 本节代码按 Apache ShardingSphere 5.x + Spring Boot 3.x 书写，**未编译校验**。

### 1. 声明式分表：把路由交给中间件

正文方案三（路由表）和方案「基因法」在 Java 生态里都有现成实现，不必自己写 `TableName()`：

```yaml
# application-sharding.yml —— 按 user_id 哈希分 256 张表
spring:
  datasource:
    driver-class-name: com.mysql.cj.jdbc.Driver
    url: jdbc:shardingsphere:classpath:sharding.yaml
---
# sharding.yaml
dataSources:
  ds_0:
    dataSourceClassName: com.zaxxer.hikari.HikariDataSource   # ⚠️ 连接池仍然在底层，每库一个
    jdbcUrl: jdbc:mysql://127.0.0.1:3306/test?useSSL=false
    username: root
    password: root123456
    maximumPoolSize: 20          # 与《索引与优化》里的池参数一致：显式设，别用默认
rules:
  - !SHARDING
    tables:
      user:
        actualDataNodes: ds_0.user_00${[0..9]},ds_0.user_0${[10..99]},ds_0.user_${[100..255]}
        tableStrategy:
          standard:
            shardingColumn: user_id
            shardingAlgorithmName: user_hash     # 对应 Go 侧的 Route()
        keyGenerateStrategy:
          column: user_id
          keyGeneratorName: snowflake            # 对应 Go 侧的 IDGen（含基因位需自定义）
    bindingTables: [user, user_route]
shardingAlgorithms:
  user_hash:
    type: HASH_MOD
    props:
      sharding-count: 256
  # 非分表键查询走 hint 或广播，不要指望它自动优化
keyGenerators:
  snowflake:
    type: SNOWFLAKE
    props:
      worker-id: 1
      # ⚠️ 默认 SNOWFLAKE 不含"基因"，要用订单号反查表必须自定义 KeyGenerator：
      # 把 user_id % 256 写进 ID 低 8 位（与 Go 侧 IDGen 的位布局保持一致）
```

```java
// 非分片键（手机号）查询：显式走路由表，而不是让中间件广播 256 张表
@Repository
public class UserRouteDao {

    private final JdbcTemplate jdbc;

    public UserRouteDao(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    public OptionalInt suffixByPhone(String phone) {
        // ⚠️ 逻辑表名 user_route 必须被排除在分片规则之外（不分片 / 单表），
        // 否则这里会被当成"广播查询"打到 256 张表上。
        return jdbc.query("SELECT table_suffix FROM user_route WHERE phone = ?",
                rs -> rs.next() ? OptionalInt.of(rs.getInt(1)) : OptionalInt.empty(), phone);
    }
}
```

**选型结论**：路由逻辑（正文方案三/基因法）自己实现只在一层薄代码里，
数据量大、多语言共享时交给 ShardingSphere；**两者都要防同一个风险——非分片键查询退化成全库广播**。

### 2. MyBatis 动态表名：`${}` 是唯一必须严格校验的地方

```java
// ❌ 直接把外部输入拼进表名 —— ${} 是字面替换，没有参数化保护
// <select id="q">SELECT * FROM ${table} WHERE user_id = #{id}</select>

// ✅ 表名先过白名单，再交给 ${}；值仍然用 #{}
public static String safeTable(String input) {
    if (input == null || !input.matches("user_\\d{4}")) {
        throw new IllegalArgumentException("illegal table name: " + input);
    }
    return input;
}
```

> Java 侧 `String.matches` 每次调用都会编译正则，热路径上应改成 `static final Pattern`；
> 这与 Go 侧「表名只能由整数格式化生成」是同一原则的两种实现——**能不拼就不拼，必须拼就限死格式**。
