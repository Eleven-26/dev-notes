## Q1. JSON 与 Protobuf 有什么区别？（附性能实测）

**来源**：`p=43` 深信服 Go 面试 · 时长 8分51秒
**考察意图**：多数人"知道有区别但说不清"。**四个维度答全 + 能给出实测数据**就足够出彩。

### 四个必答维度

| # | 维度 | **JSON** | **Protobuf** |
|---|---|---|---|
| **①** | **数据格式** | 基于键值对的**文本格式**，**肉眼可读** | **二进制格式**，**肉眼读不出来** |
| **②** | **是否需要预定义消息** | **不需要**，直接用 struct + tag | **必须先定义消息协议**（`.proto` 文件），再生成代码 |
| **③** | **工具与生态** | **无需额外安装**，几乎所有语言都有内置或第三方 JSON 库 | **必须安装 protoc 编译器**，某些语言还需**额外安装插件**（Go 要装 go 插件），并配置 PATH 环境变量 |
| **④** | **应用场景** | 性能要求**不高**的场景，如 **Web API 的请求响应** | 性能要求**高**的场景，如**微服务之间通讯**；也适合**弱网环境**（体积小） |

### 一、数据格式：文本 vs 二进制

**JSON 序列化后的样子**（无损，反而增加大量辅助符号）：

```json
{"name":"张三","age":18,"hobby":["钓鱼","架设"]}
```

规则：字段之间用**逗号**分隔，字段名用**双引号**包裹，字段名与值之间用**冒号**，
字符串值用**双引号**，数组用**中括号**。
→ **所以 JSON 对数据是无损的，它不做任何压缩，反而添加了很多组织格式的辅助符号。**

**Protobuf 是二进制的**，从字节流里**很难看出任何内容**。

⚠️ **一个重要的坑（原视频实测演示的）**：
> 如果**贸然把 Protobuf 的序列化结果直接转成字符串**，会**丢失信息**——
> 演示中出现了莫名的空行、`age` 字段不见了（可能被转成了换行符等空白字符）。
>
> **原因**：Protobuf 的序列化和反序列化**必须通过 `.proto` 生成的代码（如 `user.pb.go`）严格进行**，
> 只有用生成的代码才能得到正确结果。绕过它自己转字符串，结果不可预期。

### 二、`.proto` 文件的三个部分

```protobuf
syntax = "proto3";              // ① 指定 protobuf 语法版本

package user;                   // ② 指定包名（类似命名空间）
                                //    防止微服务之间调用时同名变量冲突

option go_package = "xxx/user"; // ③ 指定在项目中的引用路径
                                //    因为要根据 .proto 生成代码

message User { name = 1; age = 2; hobby = 3; }
```

**使用流程**：
```
① 用 protoc 编译 .proto → 生成 user.pb.go
② 在代码里 import 生成的包，才能做序列化/反序列化
③ 前置：GitHub 下载 protoc 编译器 + 安装 Go 插件 + 配置 PATH 环境变量
```

> **对比之下，JSON 是"零安装"的**：什么都不用装，
> 使用时直接 `import "encoding/json"` 即可完成序列化与反序列化。

### 三、性能实测（原视频用 benchmark 跑出的真实数据）

**测试方式**：同一份 `User` 消息，分别用 JSON 和 Protobuf 做一次**序列化 + 一次反序列化**，
用 Go 的 `go test -bench` 对比。

| 指标 | **JSON** | **Protobuf** | 差异 |
|---|---|---|---|
| **序列化后体积** | **54 字节** | **26 字节** | Protobuf **不到 JSON 的一半** |
| **序列化+反序列化耗时** | **1278 ns/op** | **373.1 ns/op** | **Protobuf 约为 JSON 的 3 倍性能** |

**结论（两条一起说才完整）**：
1. **体积小** → 同样的信息量，**网络传输的数据更少、更快**，这就是弱网环境也能用的原因；
2. **性能高** → 序列化/反序列化快约 3 倍，所以适合高性能场景（微服务通讯）。

### 四、面试答题结构（背这个骨架）

```
① 数据格式：JSON 文本可读 / Protobuf 二进制不可读
② 工具支持：JSON 零安装 / Protobuf 需装 protoc + 插件 + 配环境变量
③ 是否需预定义：JSON 不需要 / Protobuf 必须先写 .proto 再生成代码
④ 应用场景：JSON 用于 Web API 等普通场景 / Protobuf 用于微服务等高性能场景
⑤ 补充实测：体积约 1/2，性能约 3 倍（有数字更有说服力）
```

### 面试官会追问什么

- **Protobuf 为什么体积小？** → **字段只传编号不传字段名**（`name`/`age` 这些名字在编译期就固定为 tag 号），
  且用 **Varint 变长编码**压缩整数，没有 JSON 那些引号、冒号、逗号。
- **Protobuf 的缺点？** → **可读性差**（排障需要额外工具）、
  **schema 变更需谨慎**（字段号不能随意复用）、前端直接处理的生态不如 JSON。
- **为什么说 Protobuf 适合弱网？** → 报文小 → 同样的带宽能传更多数据、
  更不容易被分片，**在丢包和低带宽环境下优势明显**。
- **gRPC 和 Protobuf 的关系？** → Protobuf 是**序列化格式**（也可用于定义服务），
  gRPC 是**基于 HTTP/2 的 RPC 框架**，默认用 Protobuf 做序列化，两者经常一起出现但不是一回事。

## Q2. Protobuf 使用中需要留意的两个问题

**来源**：`p=52` 小鹏后台开发实习面试 · 时长 6分10秒
**考察意图**：从项目里挖出来的实操问题——**第二个问题是真正容易踩的生产事故**。

### 问题一：Protobuf 的完整使用流程（四步）

```
① 用 proto 语法定义 .proto 文件（定义数据结构，如 message User）
        ↓
② 用 protoc 编译器编译，生成对应语言的源代码
   （Go 生成 .go 文件；不同语言会生成 .java / .py / .c 等）
        ↓
③ 把生成的代码放进项目、参与编译（生成的部分是"存根"）
        ↓
④ 使用时通过生成的代码对 message 做序列化 / 反序列化
```

**两个要点**：
- **必须先安装 protoc 编译器**（这是 Protobuf 相比 JSON 多出来的前置成本）；
- **好处**：**修改 `.proto` 后只需重新生成代码，不需要手写编辑代码文件**——
  数据结构变更的成本很低。

### 问题二：字段标识（tag）与 `reserved` 保留字 ⚠️

#### 先理解"标识"是什么

```protobuf
message User {
    string name  = 1;   // ← 这个 1 不是"值"，是「标识（tag）」
    string phone = 6;
    string email = 7;
}
```

**关键**：Protobuf 序列化后是**二进制流**，**字段名根本不传输**，
传输过程里**只有一个字节的标识**代表对应字段：

> **`1` 就代表 `name`，`6` 代表 `phone`，`7` 代表 `email`**——
> 所以能用**一个字节**表达字段的含义（这正是它体积小的根本原因）。

#### 版本不一致会出什么事

**场景**：客户端仍是老版本（保留 `phone=6`、`email=7`），
而服务端新版本**已经移除了这两个字段**。

- 服务端接收数据时，**在反序列化之前只能看到标识 `6`、`7`**，
  **拿不到字段名**（字段名只有通过生成的代码反序列化后才知道）；
- 服务端会根据**下标/标识**去接收字段。

**危险操作**：

> 如果服务端把 **`6`、`7` 这两个标识拿去定义新字段**，
> **服务端并不知道 `6`/`7` 在客户端老版本里还是"电话/邮箱"的意思**——
> 于是客户端传来的老数据会**被存到错误的位置**，产生**静默的数据错乱**。

#### 正确做法：用 `reserved` 保留

```protobuf
message User {
    string name = 1;
    reserved 6, 7;                    // 保留标识号
    reserved "phone", "email";        // 也可以保留字段名
}
```

> **规则：在客户端与服务端版本完全同步之前，
> 被保留（`reserved`）的标识号不允许再次使用。**

**实践建议**：
- 删除字段时**务必同时 `reserved` 其标识号**，避免后续被复用；
- 字段标识**只增不改**（一旦发布就固定下来）；
- 服务端要能**兼容处理未知字段**（Protobuf 默认会保留未知字段，反序列化时跳过）。

### 面试延伸

- **Protobuf 相比 JSON 的额外成本有哪些？** → 需装 protoc + 插件、需维护 `.proto`、
  可读性差、字段标识管理需要纪律（本题的 `reserved`）。
- **为什么说字段标识"只增不改"？** → 标识是二进制的唯一身份，改了就等于含义漂移，
  老版本客户端的数据会被解析错。
