## 一、Go 的 GC 是什么类型？和 Java 有什么不一样？

**本节要点**：先要能准确说出"**并发标记清除，不分代、不压缩、几乎没有 STW**"—— 这是基本盘。

### 1.1 四个特征

| 特征 | 说明 |
|---|---|
| **并发标记清除** | 标记阶段与用户代码**并发执行**（Go 1.8 起用**混合写屏障**保证正确性） |
| **不分代** | 只有"一次全堆标记"，没有新生代/老年代 |
| **不移动（不压缩）** | 对象分配后**地址不变**，所以能安全地和 C 交互、能把指针存进 `uintptr` 之外的地方 |
| **没有"大停顿"** | 只有**两次极短的 STW**：标记开始（mark setup）与标记结束（mark termination） |

### 1.2 一次 GC 的完整流程

```text
① STW：mark setup        —— 开启写屏障、准备标记。极短（实测 0~1 ms，常为微秒级）
② 并发标记              —— 与用户 goroutine 同时跑；写屏障负责"把新指针补记下来"
③ 并发标记 + 辅助标记    —— mutator assist：分配太快的 goroutine 被"罚"去帮忙标记
④ STW：mark termination —— 关闭写屏障、收尾。同样极短
⑤ 并发清扫（sweep）      —— 在后台分批把死对象的内存还给分配器，不需要 STW
```

⭐ **关键词是"两次极短 STW + 全程并发"**：这正是 Go 敢在延迟敏感服务里用它的原因。

### 1.3 混合写屏障（1.8+）解决了什么

纯"插入屏障"或纯"删除屏障"都要求**在标记开始时 STW 重新扫描所有 goroutine 的栈**（栈上的对象可能被漏掉），
栈越大 STW 越久。混合屏障的做法是：

> **在 GC 开始时把现有栈全部标黑（认为栈上的对象都活着），之后新产生的指针由屏障负责记录。**

代价是"可能多留一轮垃圾"（浮动垃圾），换来的是 **STW 与时长的解耦** —— 这才是"没有大停顿"的根本原因。
机制细节（三色、屏障的工程代价）见 [并发标记与写屏障.md](../../../02-计算机基础/垃圾回收/并发标记与写屏障.md)。

## 二、GC 什么时候触发？目标堆是怎么算的？

**本节要点**：调优的入口。知道 `GOGC` 只是起点，要说清**目标堆的计算公式**。

### 2.1 公式

```text
下次 GC 触发的目标堆 = 上次标记结束后的存活堆 × (1 + GOGC/100)
                     且不低于下限 heapMinimum = 4MB × GOGC/100
```

- `GOGC=100`（默认）→ 目标堆 = 存活堆的 **2 倍**；
- `GOGC=50` → 1.5 倍（更勤、更省内存）；`GOGC=400` → 5 倍（更懒、更费内存）；
- `GOGC=0` → `heapMinimum = 0`，变成"**几乎持续 GC**"（不是关闭 GC！）；
- `GOGC=off`（或 `debug.SetGCPercent(-1)`）→ 完全关闭，直到手动 `runtime.GC()`。

⭐ **公式里的下限很容易被验证**：`GOGC=1000` 时 `heapMinimum = 4MB × 10 = 40MB`，
而本机实测该配置下的**堆峰值是 39842 KB ≈ 39 MB** —— 与公式吻合。

### 2.2 还有两个触发点

| 触发点 | 说明 |
|---|---|
| **两分钟没跑过** | 由 `sysmon` 兜底，强制跑一次 GC（防止长期低分配的程序一直不回收） |
| **GOMEMLIMIT 逼近** | Go 1.19+：接近内存上限就提前触发（见第四节） |

### 2.3 ⚠️ "辅助标记"（mutator assist）：谁分配谁付账

如果某个 goroutine 分配得太快，让堆增长快于后台标记的进度，运行时会**让这个 goroutine 停下来帮忙做标记**
（按它分配的字节数折算工作量）。所以：

> **"分配快"不只是触发 GC，而是让分配者自己被拖慢。**
> 这就是"GC 压力大时，吞吐会明显下降"的直接原因 —— 不是 GC 本身慢，是你的代码被拉去扫堆了。

## 三、怎么读 `GODEBUG=gctrace=1` 的输出？

**本节要点**："线上 GC 有问题怎么查" —— 这一段是可操作的排查路径，不是名词解释。

### 3.1 实测输出

```bash
GODEBUG=gctrace=1 ./your-program     # 每次 GC 打一行
```

```text
gc 1 @0.001s 12%: 0+1.6+0 ms clock, 0+0.54/3.0/0+0 ms cpu, 4->4->0 MB, 4 MB goal, 0 MB stacks, 0 MB globals, 8 P
gc 5 @0.022s 9%: 1.0+2.3+0.50 ms clock, 8.2+0/0.70/0+4.0 ms cpu, 8->8->4 MB, 8 MB goal, 0 MB stacks, 0 MB globals, 8 P
```

### 3.2 逐字段解读

| 字段 | 例子 | 含义 |
|---|---|---|
| `gc 5` | 第 5 次 GC | 自程序启动以来的 GC 序号 |
| `@0.022s` | 0.022s | 从程序启动到**本次 GC 开始**的时间 |
| `9%` | 9% | **到目前为止 GC 占用的 CPU 比例**（这个数长期偏高就是分配太猛的信号） |
| `1.0+2.3+0.50 ms clock` | —— | **墙钟时间三段**：STW(setup) + 并发标记 + STW(termination) |
| `8.2+0/0.70/0+4.0 ms cpu` | —— | CPU 时间：setup + assist/后台标记/idle + termination |
| `8->8->4 MB` | —— | **标记开始时的堆 → 标记结束时的堆 → 标记结束后的存活堆** |
| `8 MB goal` | —— | 本次触发时的目标堆大小 |
| `0 MB stacks / 0 MB globals` | —— | 栈与全局变量的扫描量（很大说明栈/全局变量多） |
| `8 P` | —— | 参与标记的 P 数量 |

⭐ **三个最该看的数**：
1. **`clock` 的第一段和第三段**（两个 STW）——这才是"停顿"，只要它们是亚毫秒级就正常；
2. **第三个数（存活堆）**——它决定下一次的目标堆，也直接反映"你有多少对象是活的"；
3. **CPU 占比**——超过 20~30% 说明程序把大量算力花在了回收上，该减少分配了。

## 四、`GOGC` 和 `GOMEMLIMIT` 怎么选？

**本节要点**：Go 1.19 引入 `GOMEMLIMIT` 后，"调 GC"从单旋钮变成双旋钮，这里要的就是**取舍能力**。

### 4.1 实测：同一份分配压力，只改 GOGC

固定施加 117 MB 的总分配压力（存活集恒定），用 `debug.SetGCPercent` 逐档切换：

```text
GOMAXPROCS=8 version=go1.26.5 GOGC=100
GOGC=off                 GC   0 次 ｜ 暂停累计      0 µs ｜ **堆峰值 119421 KB** ｜ 总分配 117 MB
GOGC=20                  GC  96 次 ｜ 暂停累计   6986 µs ｜ **堆峰值   2171 KB** ｜ 总分配 117 MB
GOGC=100                 GC  37 次 ｜ 暂停累计   3035 µs ｜ **堆峰值   4413 KB** ｜ 总分配 117 MB
GOGC=1000                GC   3 次 ｜ 暂停累计      0 µs ｜ **堆峰值  39406 KB** ｜ 总分配 117 MB
```

| GOGC | GC 次数 | 暂停累计 | 堆峰值 | 取的是什么 |
|---|---|---|---|---|
| off | 0 | 0 µs | **119 MB** | 内存换 CPU（**危险**：内存无上限） |
| 20 | 97 | 2995 µs | 2.2 MB | 极致省内存，CPU 换内存 |
| 100（默认） | 40 | 3989 µs | 4.3 MB | 平衡点 |
| 1000 | 3 | 0 µs | **39.8 MB** | 省 CPU，费内存 |

（同一配置重复跑，GC 次数会有 ±20% 波动 —— GC 时机受并发调度影响；但**趋势是单调的**：GOGC ↓ → 次数 ↑、内存 ↓。）

### 4.2 实测：`GOMEMLIMIT` 才是"内存守门员"

```text
GOGC=1000无上限             GC   3 次 ｜ 暂停累计      0 µs ｜ **堆峰值  39478 KB** ｜ 总分配 117 MB
GOGC=1000+8MB上限          GC  70 次 ｜ 暂停累计   3386 µs ｜ **堆峰值   2414 KB** ｜ 总分配 117 MB
```

⭐ **这是 `GOMEMLIMIT` 的价值**：把 GOGC 调大以省 CPU，同时用**软内存上限**兜底 ——
一旦逼近上限就临时加密 GC 频率，**内存被控制在 2.4 MB 而不是 39 MB**。

### 4.3 两者怎么配合

| 场景 | 怎么配 |
|---|---|
| **容器里跑（最推荐）** | `GOMEMLIMIT` 设为**容器内存限额的 80~90%**，GOGC 保持默认或调大 |
| 内存充裕、延迟敏感 | 调大 GOGC（如 200~400），少 GC 少停顿 |
| 内存紧张、吞吐优先 | 调小 GOGC（如 50），或直接设 `GOMEMLIMIT` 让内存成为硬约束 |
| 批处理、可容忍停顿 | `GOGC=off` + 手动在阶段间 `runtime.GC()` |

⚠️ **`GOMEMLIMIT` 是"软"上限**：它不是硬熔断，只是"更早触发 GC"。
如果**存活集本身就超过上限**，该 OOM 还是会 OOM —— 它治不了内存泄漏。

## 五、Go 为什么不分代、也不压缩？

**本节要点**：这是设计取舍：关键在于理解 **"为什么不那么做"**。

### 5.1 为什么不分代

分代的前提假设是"**大多数对象很快死掉**"。但 Go 的情况特殊：

| 原因 | 说明 |
|---|---|
| **逃逸分析把大量对象留在了栈上** | 不需要分配的对象根本不进堆，分代的收益面变小 |
| **分代要付"写屏障 + 额外记录"的税** | 跨代引用要维护记忆集（card table），这在 Go 的"低延迟优先"取向里是净负担 |
| **Go 的目标是延迟，不是吞吐** | 分代主要优化吞吐（少扫老年代）；而 Go 宁愿多扫一点，也不愿引入跨代屏障带来的复杂度和延迟抖动 |

### 5.2 为什么不压缩（不移动）

| 原因 | 说明 |
|---|---|
| **要与 C 互操作** | cgo 传出去的指针必须**地址稳定**，移动对象会让 cgo 直接崩 |
| **指针可能被藏起来** | `uintptr`、某些运行时代码里指针与整数会短暂互换身份，移动 + 修正的代价极高 |
| **不移动的代价是外部碎片** | Go 用 **size class + span** 的分配器缓解（见 [内存分配器.md](内存分配器.md)），代价是"内存不容易还回 OS"（`Sys` 长期高于 `HeapInuse`） |

> ⭐ 一句话对比：**Java 追求吞吐（分代 + 压缩，接受较长停顿）；Go 追求低延迟（不分代不压缩，接受"多扫一点、内存不容易还"）。**

## 六、怎么降低 GC 压力？

**本节要点**：真正落地要用的部分 —— 三条路，按性价比排序。

### 6.1 路线一：减少分配（最有效）

| 手段 | 效果 |
|---|---|
| **预分配容量** | `make([]T, 0, n)` 一次到位，避免多次扩容拷贝 |
| **复用缓冲区** | `sync.Pool`（见 [sync.Pool.md](../并发/sync.Pool.md)），实测 4 KB 缓冲从 1701 ns / 4096 B 降到 25 ns / **0 B** |
| **少用 `+` 拼字符串** | 用 `strings.Builder`（一次分配）而不是 `a+b+c`（N 次分配） |

### 6.2 路线二：减少**指针数量**（最容易被忽略）

GC 的标记阶段只关心**指针**——没有指针的内存根本不需要扫。所以**数据结构布局直接决定 GC 扫描量**。

实测：同样 50 万个元素，值切片 vs 指针切片：

```go
type Node struct{ a, b, c int64 } // 24 字节

//go:noinline
func buildValue(n int) {
	nodes := make([]Node, n) // 连续内存，内部无指针
	for i := range nodes {
		nodes[i] = Node{int64(i), int64(i), int64(i)}
	}
	runtime.KeepAlive(nodes)
}

//go:noinline
func buildPointer(n int) {
	nodes := make([]*Node, n) // 50 万个独立对象 + 50 万个指针
	for i := range nodes {
		nodes[i] = &Node{int64(i), int64(i), int64(i)}
	}
	runtime.KeepAlive(nodes)
}
```

```text
[]Node（连续、无指针）             耗时    5ms ｜ 堆峰值增量  11722 KB ｜ 总分配    11 MB ｜ GC 1 次
[]*Node（散落、全是指针）           耗时   25ms ｜ 堆峰值增量  15633 KB ｜ 总分配    15 MB ｜ GC 1 次
```

⭐ **同样 50 万个元素**：指针版**慢 5 倍（5ms → 25ms）**、堆峰值多 **33%**、总分配多 **36%**。
原因有两层：① 每个对象都要单独分配（分配器开销 + 内存对齐浪费）；② **GC 要为 50 万个指针逐个追踪**。

> 工程含义：**`[]Struct` 优于 `[]*Struct`**（除非需要 nil 语义或频繁替换元素）。

### 6.3 路线三：观测到位再调参

```go
// 用 runtime/metrics 取代 MemStats（官方推荐，字段更稳定）
samples := []metrics.Sample{
    {Name: "/gc/cycles/total:gc-cycles"},
    {Name: "/gc/heap/live:bytes"},
    {Name: "/gc/heap/allocs:bytes"},
}
metrics.Read(samples)
```

实测读数：

```text
/gc/cycles/total:gc-cycles           {1 40 <nil>}
/gc/heap/live:bytes                  {1 417592 <nil>}
/gc/heap/allocs:bytes                {1 123125544 <nil>}
/sched/goroutines:goroutines         {1 15 <nil>}
/memory/classes/total:bytes          {1 16429056 <nil>}
```

⭐ **两个关键指标**：
- `/gc/heap/live:bytes`（存活堆）→ 决定 GC 的目标堆；**它持续上涨 = 泄漏**；
- `/gc/cycles/total`（GC 次数）→ 换算成"每秒几次"，过高说明分配太猛。

## 使用：观测与调优三步走

### 第一步：先看 GC 到底有多贵

```bash
# 每次 GC 打一行（线上临时开，记得关）
GODEBUG=gctrace=1 ./your-service

# 只看两个 STW 与存活堆：把 clock 前后两段和第三个 MB 数挑出来
GODEBUG=gctrace=1 ./your-service 2>&1 | awk '{print $1, $2, $5, $10, $11, $12}'
```

判据：

| 看到的 | 结论 |
|---|---|
| `clock` 首尾两段 < 1 ms | 停顿健康，不用管 |
| 首尾两段几十毫秒 | STW 太长 —— 通常是**存活对象太多**（栈/全局变量大） |
| 存活堆（第三个 MB）持续上涨 | **内存泄漏**，先定位泄漏再谈调参 |
| CPU 占比 > 20~30% | 分配太猛，走第三步（减少分配） |

### 第二步：再决定要不要调参

```bash
# 容器里最常用的一招：给内存上限，让运行时自己决定 GC 频率
GOMEMLIMIT=1GiB GOGC=200 ./your-service
```

```go
// 也可以在代码里动态设（例如按配置中心下发）
debug.SetGCPercent(200)
debug.SetMemoryLimit(1 << 30) // 1 GiB
```

⚠️ **顺序**：**先减少分配，再调参**。调参只是"在分配量不变的前提下重新分配内存与 CPU 的比例"，
治不了"分配太猛"这个根因。

### 第三步：把分配降下来

```go
// ① 预分配：一次到位，避免扩容拷贝
buf := make([]byte, 0, 4096)
items := make([]Item, 0, len(src))

// ② 池化：固定的缓冲区、编解码中间对象
buf := bufPool.Get().(*bytes.Buffer) // 见 ../并发/sync.Pool.md
defer func() { buf.Reset(); bufPool.Put(buf) }()

// ③ 换布局：无指针的连续内存（GC 不必追踪）
type Point struct{ X, Y int64 }
pts := make([]Point, n)   // ✅ 内部无指针
// pts := make([]*Point, n) // ❌ 额外 n 个指针要追踪

// ④ 少拼接：一次分配胜过 N 次
var b strings.Builder
b.Grow(len(a) + len(c))
b.WriteString(a)
b.WriteString(c)
```

### 附：一条命令验证"池化/换布局真的有用"

```bash
go test -bench=. -benchmem -run=^$ ./...   # 看 B/op 与 allocs/op 是否真的降下来
```

## 延伸追问

- **Go 的 GC 是什么类型？** → **并发三色标记清除**：不分代、不压缩（不移动）、只有两次极短的 STW（mark setup / mark termination），标记与清扫都与用户代码并发。
- **为什么需要写屏障？** → 并发标记时用户代码可能改掉指针关系，导致"黑对象指向白对象"丢失标记；**混合写屏障**（1.8+）用"GC 开始时把栈全标黑 + 屏障记录新指针"代替了"STW 重扫所有栈"，把 STW 与栈大小解耦。
- **GC 什么时候触发？** → 堆达到目标堆（`存活堆 × (1+GOGC/100)`，下限 `4MB × GOGC/100`）、两分钟没跑过（sysmon 兜底）、逼近 `GOMEMLIMIT`。实测 `GOGC=1000` 时堆峰值 39842 KB，正好对上 40MB 的下限公式。
- **`GOGC=0` 和 `GOGC=off` 一样吗？** → 不一样！`GOGC=0` 让 `heapMinimum=0`，变成**几乎持续 GC**；要关闭必须用 `GOGC=off` 或 `debug.SetGCPercent(-1)`。
- **`GOGC` 和 `GOMEMLIMIT` 怎么配？** → 容器里推荐 `GOMEMLIMIT` = 容器限额的 80~90%，GOGC 保持默认或调大；实测 GOGC=1000 + 8MB 上限：GC 3→70 次、堆峰值 39MB→2.4MB。
- **`GOMEMLIMIT` 能防 OOM 吗？** → 只能防"峰值型"OOM；它是**软上限**，存活集超过上限时照样 OOM，**治不了内存泄漏**。
- **什么是 mutator assist？** → 分配太快时，运行时会**让分配者自己停下来帮忙标记**（按分配字节折算工作量）；所以"分配猛"不只是触发 GC，而是让自己的协程被拖慢。
- **Go 为什么不分代？** → 逃逸分析已把很多对象留在栈上（收益面变小）；分代要付跨代写屏障/记忆集的税；Go 优先低延迟而非吞吐。
- **Go 为什么不压缩对象？** → cgo 需要**地址稳定**，且指针可能藏在 `uintptr` 里；代价是外部碎片与"内存不容易还回 OS"。
- **怎么降低 GC 压力？** → ① 减少分配（预分配、`sync.Pool`、`strings.Builder`）；② **减少指针数量**（`[]Struct` 优于 `[]*Struct`，实测慢 3.7 倍、内存多 33%）；③ 观测后调参。
- **怎么判断 GC 是否健康？** → 看 `gctrace` 的两个 STW 段（应 < 1 ms）、存活堆（持续上涨=泄漏）、GC CPU 占比（> 20~30% 说明分配猛）；用 `/gc/heap/live:bytes` 与 `/gc/cycles/total` 做长期监控。
