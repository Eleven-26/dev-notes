> 素材来源：《Go 语言核心编程》（李文塔）**第 4 章「接口」**（4.1 基本概念 / 4.2 接口运算 / 4.3 空接口 / 4.4 接口内部实现）的读后整理，**按主题归纳而非逐字摘录**。

## 一、接口变量的"静态类型"和"动态类型"分别指什么？

**一句话答案**：**静态类型**是编译期写在声明里的那个接口名；**动态类型**是运行期装进去的具体类型——接口变量**同时持有"类型"和"值"两份信息**，这一点是后面所有坑的根源。

### 1.1 声明、初始化与零值

```go
var r Reader               // 零值：动态类型为 nil，r == nil 为 true
r = File{name: "a.txt"}    // 赋值后：动态类型 File，动态值 a.txt 那份数据
```

```text
静态类型（编译期）= Reader；动态类型（运行期）= main.File
reflect 看到的动态类型 = File，Kind = struct
接口零值的动态类型 = <nil>，r == nil 判定 = true
```

- 编译器只认静态类型：`r` 上只能调 `Reader` 声明的方法，别的方法**编译期就报错**；
- 运行期认动态类型：`r.Read()` 实际调到的是 `File.Read`；
- `reflect.TypeOf(r)` 拿到的是**动态类型**，接口零值则返回 `nil`。

### 1.2 接口可以嵌入接口

```go
type Reader interface{ Read() string }
type Closer interface{ Close() error }

type ReadCloser interface {
    Reader
    Closer
}
```

```text
ReadCloser 同时具备两个方法："data of b.txt" / <nil>
它也能直接当 Reader 用（方法集是子集就自动成立）："data of b.txt"
```

⭐ **子集关系自动成立**：`ReadCloser` 的方法集包含 `Reader` 的方法，所以 `ReadCloser` 值**可以直接当 `Reader` 用**，不需要显式声明继承。这就是"小接口 + 组合"能替代继承的根本原因（见 [Go语言设计与横向对比.md](../../../07-面试/Go语言设计与横向对比.md)）。

### 1.3 接口满足是"编译器替你做"的静态检查

`File` 从没写过 `implements Reader` 这种声明——它只要**方法集包含接口要求的全部方法**就自动满足。⚠️ 代价是：**接口定义方和使用方谁都不知道对方的存在**，重构时方法名改错要到编译期才暴露。

## 二、类型断言和类型查询怎么用？

### 2.1 两种形式，行为完全不同

| 写法 | 断言失败时 |
|---|---|
| `v, ok := i.(T)` | `v` = `T` 的零值，`ok` = false，**不 panic** |
| `v := i.(T)` | **panic**（`interface conversion: ...`） |

⭐ **生产代码一律用双值形式**；单值形式只在你已经用 `type switch` 或别的方式确认过类型时使用。

### 2.2 断言的目标可以是"具体类型"也可以是"接口"

```go
if f, ok := r.(File); ok { // 断言到具体类型
    fmt.Printf("断言到具体类型 File 成功，name = %q\n", f.name)
}
_, okFile := r.(File)
_, okCloser := r.(Closer)
_, okStringer := r.(fmt.Stringer)
fmt.Printf("断言结果：File=%v Closer=%v Stringer=%v\n", okFile, okCloser, okStringer)
```

```text
断言到具体类型 File 成功，name = "a.txt"
断言结果：File=true Closer=true Stringer=true
```

### 2.3 断言失败的两种边界

```go
var only Reader = OnlyRead{}   // OnlyRead 只有 Read，没有 Close
_, okFail := only.(Closer)
fmt.Printf("对不满足的接口断言，ok 形式返回 %v（不 panic）\n", okFail)

var nilR Reader
v, okNil := nilR.(File)
fmt.Printf("对 nil 接口断言：值 = %+v，ok = %v\n", v, okNil)
```

```text
对不满足的接口断言，ok 形式返回 false（不 panic）
对 nil 接口断言：值 = File()，ok = false
```

⭐ **对 nil 接口断言**返回零值 + `false`，**不会 panic**——所以"先断言再判 `ok`"是安全的，不需要先判 `i != nil`。

### 2.4 类型查询：`type switch`

```go
switch val := any(r).(type) {
case File:
    fmt.Printf("type switch 命中 File：%s\n", val.String())
case fmt.Stringer:
    fmt.Printf("type switch 命中 Stringer：%s\n", val.String())
default:
    fmt.Printf("未命中，兜底类型 %T\n", val)
}
```

```text
type switch 命中 File：File(a.txt)
```

⚠️ 三个容易忘的细节：
1. `val` 在各 `case` 里是**对应类型**（`case File` 里 `val` 就是 `File`），`default` 里保持原接口类型；
2. 一个 `case` 可以列多个类型（`case File, OnlyRead:`），此时 `val` 退回接口类型；
3. **没有 `fallthrough`**，命中即结束。

### 2.5 ⚠️ 只能对接口做断言

```text
fail\non_iface_assert\main.go:6:6: invalid operation: x (variable of type int) is not an interface
```

## 三、空接口 `interface{}` 和 nil 的坑 ⭐

**这是全书最值得背的一节**，也是线上最容易变成"莫名的空指针 panic"的地方。

### 3.1 先看现象

```go
type MyErr struct{ msg string }

func (e *MyErr) Error() string { return e.msg }

// 反面写法：把「类型为 *MyErr、值为 nil」的指针装进 error 返回
func badErr() error {
    var p *MyErr
    return p
}

// 正确写法：先判空再返回
func goodErr() error {
    var p *MyErr
    if p == nil {
        return nil
    }
    return p
}
```

```text
var e error 未赋值：      e == nil -> true
返回 (*MyErr)(nil) 之后： e == nil -> false  ⚠️ 不是 nil！
  它的动态类型 = *main.MyErr，动态值 = <nil>
但那个具体指针本身：(*MyErr)(nil) == nil -> true
goodErr() 先判空再返回：  e == nil -> true
对 e2 调用方法会 panic：runtime error: invalid memory address or nil pointer dereference
```

### 3.2 为什么会这样

接口变量有**两个字**：类型字 + 数据字。`return p` 时类型字被填成 `*MyErr`、数据字是 `nil`——**类型字非 0，整个接口就不等于 `nil`**。但真的调方法时，方法实现里又要解引用那个 nil 数据字，于是 panic。

判断口诀：**`i == nil` 判的是"类型字是否为 0"，不是"数据字是否为 0"。**

### 3.3 三种正确的写法

```go
// ① 最推荐：中间变量用具体类型，返回前判空
func newErr(code int) error {
    var e *MyErr
    if code != 0 {
        e = &MyErr{msg: fmt.Sprintf("code=%d", code)}
    }
    if e == nil {
        return nil
    }
    return e
}

// ② 接口变量直接声明，永远不要"先声明具体指针再返回"
func f() error {
    return nil // 显式返回 nil，而不是返回一个 nil 的 *T
}

// ③ 万不得已要判断一个 any 是不是"真 nil"，用反射（工具代码见本篇「使用」段）
if IsNilInterface(err) { /* ... */ }
```

⚠️ **这个坑最常见的三个现场**：函数返回 `error`、`context.Context` 里存 `any`、`map[string]any` 里放自定义指针类型。**根因都一样：具体类型的 nil 指针进了接口。**

## 四、接口在内存里长什么样？

书里把接口分成了两种结构（`runtime` 源码里的名字，只是未导出）：

| | 用于 | 第 1 个字 | 第 2 个字 |
|---|---|---|---|
| **eface** | 空接口 `interface{}`（`any`） | `_type`（指向类型元数据） | `data`（指向数据） |
| **iface** | 非空接口（有方法的） | `*itab`（接口-类型匹配表） | `data` |

`itab` 的字段（书上叫"接口调用过程分析"）：

```go
type itab struct {
    inter *interfacetype // 接口本身的类型信息
    _type *_type         // 具体类型信息
    hash  uint32         // 具体类型的哈希，用于类型断言快速否定
    _     [4]byte
    fun   [1]uintptr     // 方法表：按接口方法声明顺序排列的函数地址
}
```

### 4.1 实测：用 `unsafe` 把两个字读出来

```go
// iface / eface 在 64 位下都是 2 个字：第一个字是类型信息，第二个字是数据指针
func rawWords(p unsafe.Pointer) (unsafe.Pointer, unsafe.Pointer) {
    w := (*[2]unsafe.Pointer)(p)
    return w[0], w[1]
}

// 与 runtime.itab 前 5 个字段一一对应
type itabMirror struct {
    inter unsafe.Pointer // *interfacetype
    typ   unsafe.Pointer // *_type
    hash  uint32
    _     [4]byte
    fun   [1]unsafe.Pointer
}

f := File{name: "c.txt"}

var ef any = &f
typeWord, dataE := rawWords(unsafe.Pointer(&ef))
var ifc Reader = &f
tabPtr, dataI := rawWords(unsafe.Pointer(&ifc))

fmt.Printf("eface：第 1 个字（*_type）非空 = %v，第 2 个字（data）非空 = %v\n", typeWord != nil, dataE != nil)
fmt.Printf("iface：第 1 个字（*itab）非空 = %v，第 2 个字（data）非空 = %v\n", tabPtr != nil, dataI != nil)
fmt.Printf("装同一份数据时，两个接口的 data 字指向同一地址 = %v\n", dataE == dataI)

var nilIface Reader
nw0, nw1 := rawWords(unsafe.Pointer(&nilIface))
fmt.Printf("nil 接口的两个字都为 nil = %v（全 0 才等于 nil）\n", nw0 == nil && nw1 == nil)

tab := (*itabMirror)(unsafe.Pointer(tabPtr))
fmt.Printf("itab.inter 非空 = %v\n", tab.inter != nil)
fmt.Printf("itab._type 非空 = %v\n", tab.typ != nil)
fmt.Printf("itab.hash 非空 = %v（接口断言靠它做快速否定）\n", tab.hash != 0)
fmt.Printf("itab.fun[0] 非空 = %v（方法表首项，指向 File.Read 的代码地址）\n", tab.fun[0] != nil)
fmt.Printf("itab._type 就是具体类型的 *_type 吗？%v\n", tab.typ == typeWord)
```

```text
eface：第 1 个字（*_type）非空 = true，第 2 个字（data）非空 = true
iface：第 1 个字（*itab）非空 = true，第 2 个字（data）非空 = true
装同一份数据时，两个接口的 data 字指向同一地址 = true
nil 接口的两个字都为 nil = true（全 0 才等于 nil）
itab.inter 非空 = true
itab._type 非空 = true
itab.hash 非空 = true（接口断言靠它做快速否定）
itab.fun[0] 非空 = true（方法表首项，指向 File.Read 的代码地址）
itab._type 就是具体类型的 *_type 吗？true
```

### 4.2 从实测能读出三件事

1. **`nil` 接口 = 两个字全 0**（第三节的坑由此而来）；
2. **同一份数据被两个接口指着时，`data` 字是同一个地址**——接口赋值**不复制数据**，只填两个字；
3. **`itab._type` 就是 `any` 里的 `_type`**——两种接口的"类型身份"是同一套元数据，`itab` 只是额外多了一张方法表。

### 4.3 itab 是"懒生成 + 缓存"的

运行时不会在编译期为所有"类型 × 接口"组合预生成 itab，而是**首次赋值时生成、之后放进哈希表缓存**。所以：

- 稳态下类型断言和接口调用不会反复分配；
- ⚠️ 但**大量不同"类型 × 接口"组合**（比如插件式架构里动态注册几百种类型）会让 itab 表长大，属于另一类内存增长来源。

## 五、接口的代价到底有多大？

书里 4.4.3 的结论是"接口调用有额外开销"，把它量出来：

```go
// 两侧都穿过 noinline 边界，避免编译器把方法体内联进循环、把动态调用「去虚化」
//
//go:noinline
func directCall(c Concrete, a, b int) int { return c.Add(a, b) }

//go:noinline
func ifaceCall(x Adder, a, b int) int { return x.Add(a, b) }
```

```text
BenchmarkDirectCall-8     524617225    2.267 ns/op    0 B/op    0 allocs/op
BenchmarkIfaceCall-8      259245280    4.560 ns/op    0 B/op    0 allocs/op
BenchmarkAssertThenCall-8 179184147    6.442 ns/op    0 B/op    0 allocs/op
BenchmarkAssertOnly-8     465000388    2.611 ns/op    0 B/op    0 allocs/op
BenchmarkBoxInt-8          50539934   22.98  ns/op    8 B/op    1 allocs/op
```

（同一台机器连跑三次，ns/op 波动在 ±0.1 以内，数字稳定。）

| 操作 | 本机耗时 | 相对直接调用 |
|---|---|---|
| 直接调用具体类型方法 | ≈ 2.3 ns | 1.0× |
| 通过接口调用 | ≈ 4.6 ns | **2.0×** |
| 先断言再调用 | ≈ 6.2 ns | **2.7×** |
| 只做一次类型断言 | ≈ 2.6 ns | 1.1× |
| 把一个 int 装箱进 `any` | ≈ 22.5 ns | 10×（并分配 8 B） |

### 5.1 代价来自哪里

- **间接跳转**：`itab.fun[i]` 取地址再 call，CPU 分支预测不如直接调用；
- **无法内联**：编译期不知道具体类型，方法体进不了调用方——**这才是大头**（上面的 2.3 ns 里已经含了 noinline 的调用开销，真实项目里"能内联 vs 不能内联"的差距往往更大）；
- **装箱分配**：值类型进空接口要分配（见下）。

### 5.2 ⚠️ 编译器会"去虚化"，所以微基准容易骗人

如果动态类型在编译期可证（`var x Adder = Concrete{}; x.Add()`），编译器会把接口调用**直接替换成静态调用**。我第一次跑基准时这个 case 出来是 `0.56 ns/op`，和直接调用**一模一样**——不是接口变快了，而是接口调用被优化掉了。**所以量接口开销必须穿过 `//go:noinline` 边界。**

### 5.3 装箱：什么时候给接口赋值会分配内存

用 `testing.AllocsPerRun` 量（值以**参数**形式传入 `noinline` 函数，否则常量会被编译成静态数据、测不出分配）：

```text
常量 300 直接赋给 any                分配 0.00 次
参数传 42 再赋给 any                 分配 0.00 次
参数传 300 再赋给 any                分配 1.00 次
参数传 string 再赋给 any             分配 1.00 次
参数传 *File 再赋给 any              分配 0.00 次
参数传 Big{}(128B) 再赋给 any        分配 1.00 次
```

| 装进去的东西 | 分配 | 为什么 |
|---|---|---|
| 常量（编译期已知） | 0 | 编译进只读数据区，直接指向静态副本 |
| 0~255 的整数 | 0 | 运行时有一张 `staticuint64s` 小整数表 |
| 其它整数 | 1（8 B） | 每次装箱新分配一个盒子 |
| `string`（16 字节头） | 1 | 头比一个字大，必须堆上放一份 |
| **指针** | **0** | 指针本身就占一个字，直接当 `data` 用 |
| 128 字节大结构体 | 1 | 整份数据拷到堆上 |

⭐ **两条可立即使用的优化**：
1. **方法用指针接收者 / 传指针进接口可以避免装箱**——这是"大对象实现接口时用 `*T`"的另一个理由；
2. 热路径上一次装箱 22 ns，一秒钟百万次调用就是 22 ms + 百万次小对象分配（给 GC 加压力）。**这正是 `zap`、`fasthttp` 这类库刻意避开 `any` 的原因。**

## 使用：判断一个 `any` 是不是"真 nil"

第三节那个坑在生产里防不胜防（尤其是 `map[string]any`、`context.Value`、插件返回值）。下面这个小工具可以把"装着 nil 指针的接口"识别出来，建议直接放进项目 `internal/` 里用。

```go
package main

import (
	"errors"
	"fmt"
	"reflect"
)

type MyErr struct{ code int }

func (e *MyErr) Error() string { return fmt.Sprintf("code=%d", e.code) }

// IsNilInterface 区分「真 nil 接口」与「装着 nil 指针的接口」
func IsNilInterface(i any) bool {
	if i == nil {
		return true // 两个字都是 0
	}
	v := reflect.ValueOf(i)
	switch v.Kind() {
	case reflect.Ptr, reflect.Map, reflect.Slice, reflect.Chan, reflect.Func, reflect.Interface:
		return v.IsNil()
	}
	return false
}

func main() {
	var a error                 // 真 nil
	var b error = (*MyErr)(nil) // 装着 nil 指针
	var c error = errors.New("boom")
	var d any = []int(nil)
	var e any = map[string]int(nil)

	fmt.Printf("未赋值的 error       : ==nil -> %-5v  IsNilInterface -> %v\n", a == nil, IsNilInterface(a))
	fmt.Printf("(*MyErr)(nil) 装进去 : ==nil -> %-5v  IsNilInterface -> %v\n", b == nil, IsNilInterface(b))
	fmt.Printf("errors.New(\"boom\")  : ==nil -> %-5v  IsNilInterface -> %v\n", c == nil, IsNilInterface(c))
	fmt.Printf("any = []int(nil)     : ==nil -> %-5v  IsNilInterface -> %v\n", d == nil, IsNilInterface(d))
	fmt.Printf("any = map(nil)       : ==nil -> %-5v  IsNilInterface -> %v\n", e == nil, IsNilInterface(e))
}
```

```text
未赋值的 error       : ==nil -> true   IsNilInterface -> true
(*MyErr)(nil) 装进去 : ==nil -> false  IsNilInterface -> true
errors.New("boom")  : ==nil -> false  IsNilInterface -> false
any = []int(nil)     : ==nil -> false  IsNilInterface -> true
any = map(nil)       : ==nil -> false  IsNilInterface -> true
```

**三个使用要点**：

1. **先用它**：所有"从 `any` 里取出来判空"的地方（缓存命中判断、可选返回值、插件结果）都该用它，而不是 `== nil`；
2. **别滥用**：反射有成本，**契约层能修就修**——最根本的解法还是第三节的写法（返回前判空）；
3. **注意 `[]int(nil)` / `map(nil)` 也会被判成 nil**：这是刻意的（它们的"值"确实是空的），如果你的语义里"空切片"和"没有切片"不同，得单独判 `v.IsValid()` 之外的字段。

## 延伸追问

- **接口变量的零值是什么？和装着 nil 指针的接口有什么区别？** → 零值两个字都是 0，等于 `nil`；装着 nil 指针时类型字非 0，**接口 `!= nil`**，调方法会 panic（实测见第三节）。
- **为什么 `var e error = (*MyErr)(nil)` 之后 `e != nil`？** → `== nil` 判的是类型字是否为 0；`*MyErr` 这个类型存在，类型字就非 0。
- **怎么避免这个坑？** → 返回前判空、不要"先声明具体指针再 return"；兜底用 `reflect.ValueOf(i).IsNil()`（见「使用」段）。
- **`i.(T)` 单值形式和双值形式的区别？** → 双值形式失败返回零值 + `false`；单值形式失败 **panic**。生产代码一律用双值。
- **对 `nil` 接口做类型断言会 panic 吗？** → 不会，返回零值 + `false`。
- **`type switch` 里 `val` 是什么类型？** → 各 `case` 里是对应的具体类型；多类型 `case` 或 `default` 里是原接口类型。
- **接口在内存里占几个字？** → 64 位下 2 个字：空接口是 `(*_type, data)`，非空接口是 `(*itab, data)`（实测第 1、2 个字都非 0）。
- **`itab` 里有什么？** → 接口类型、具体类型 `_type`、类型哈希（断言快速否定用）、方法表 `fun`。首次赋值时懒生成并缓存。
- **接口调用比直接调用慢多少？** → 本机实测约 **2 倍**（2.3 → 4.6 ns）；慢在**间接跳转 + 无法内联**，不是慢在查表。
- **为什么我的基准里接口调用和直接调用一样快？** → 编译器**去虚化**了（动态类型编译期可证）；要量真实开销必须穿过 `//go:noinline`。
- **值放进接口会分配内存吗？** → 常量、0~255 整数、**指针**不分配；其它整数（8 B）、`string`（16 B 头）、大结构体各分配 1 次。**大对象实现接口时用 `*T` 可以避免装箱。**
- **什么时候不该用接口？** → 热路径上的小方法（装箱 + 无法内联）、只为"看起来解耦"而抽象出的单实现接口（Go 社区共识：**接口应该由使用方定义，而不是实现方**）。
