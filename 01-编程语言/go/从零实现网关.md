## 一、把网关拆成一条流水线？

**本节要点**：网关不是「一个反向代理」，而是**一串按固定顺序执行的横切关注点**。
顺序错了功能还能跑，但会出现「限流按错误的维度生效」「熔断永远不触发」这类难查的问题。

```text
客户端请求
   │
   ├─ ⑦ 生成/透传 TraceID          ← 最先做，后面所有日志都带它
   ├─ ① 路由匹配（Host/Path/Method/Header）  ← 不匹配 → 404
   ├─ ② 认证鉴权（JWT / API Key）    ← 失败 → 401/403
   ├─ ③ 限流（令牌桶，按用户或 IP）   ← 拒绝 → 429 + Retry-After
   ├─ ③ 熔断检查（三态机）           ← 打开 → 503 快速失败
   ├─ ④ 选一个上游节点（轮询/加权/最少连接/一致性哈希）
   ├─ ⑤ 协议转换（HTTP→gRPC）或 ⑥ 反向代理
   └─ ⑦ 记指标 + 写访问日志（含命中规则、命中原因、落点、耗时）
```

**三条顺序上的硬约束**（不是风格问题）：

| 顺序 | 为什么必须这样 |
|---|---|
| **鉴权 → 限流** | 限流要先知道「你是谁」才能按用户维度限。反过来只能按 IP，NAT 后面一栋楼共用一个桶 |
| **限流 → 熔断** | 限流是保护自己不被压垮（看**入口速率**），熔断是保护自己不被上游拖死（看**上游错误率**）。先挡掉超额流量，再判断要不要放弃上游 |
| **熔断 → 选节点** | 熔断打开时要**直接快速失败**；若先选节点再熔断，等于白算一次，还会把无意义的连接建到挂掉的上游上 |

**装配代码**（`main.go` 的核心，删去了错误分支）：

```go
func (g *Gateway) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	start := time.Now()
	traceID := EnsureTraceID(r.Header)                 // ⑦ 最先
	sw := &statusWriter{ResponseWriter: w, status: http.StatusOK}
	entry := LogEntry{TraceID: traceID, Method: r.Method, Path: r.URL.Path, Host: r.Host}

	defer func() {                                     // ⑦ 无论走哪条分支都要记账
		entry.Status, entry.Latency, entry.Bytes = sw.status, time.Since(start), sw.bytes
		entry.Err = proxyErr(r)
		g.metrics.Observe(entry.Route, entry.Status, entry.Latency)
		g.alog.Write(entry)
	}()

	m, ok := g.router.Match(r)                         // ① 路由
	if !ok { fail(sw, 404, "route_not_found", "没有匹配的路由", traceID); return }
	entry.Route, entry.MatchWhy = m.Route.Name, m.Reason

	identity, err := Authenticate(r, m.Route.Auth)     // ② 鉴权
	if err != nil { fail(sw, authStatus(err), "unauthorized", err.Error(), traceID); return }
	entry.Identity = identity.Subject

	if p := m.Route.Limit; p.RatePerSec > 0 {          // ③ 限流（在鉴权之后）
		ip, _, _ := net.SplitHostPort(r.RemoteAddr)
		if ok, retry := g.limiter.Bucket(limitKey(m.Route.Name, identity.Subject, ip), p).Allow(1); !ok {
			sw.Header().Set("Retry-After", strconv.Itoa(int(retry.Seconds())+1))
			fail(sw, 429, "rate_limited", "触发限流", traceID); return
		}
	}

	cb := g.breakerFor(svc)                            // ③ 熔断（在选节点之前）
	if err := cb.Allow(); err != nil {
		fail(sw, 503, "circuit_open", "上游熔断中，请稍后重试", traceID); return
	}

	up, err := g.balancerFor(svc).Pick(hashKey)        // ④ 选节点
	entry.Upstream = up.Addr

	if m.Route.Transcode != nil {                      // ⑤ 协议转换
		out, err := Transcode(ctx, g.grpcPool, up.Addr, m.Route.Transcode, body, m.Groups, md)
		cb.Report(err == nil)
		writeJSON(sw, 200, map[string]any{"code": 0, "data": out, "via": "grpc"})
		return
	}
	g.proxyFor(svc, up, m.Route.StripPrefix).ServeHTTP(sw, r)   // ⑥ 反向代理
	cb.Report(sw.status < 500)                         // 5xx 视为上游不健康
}
```

## 二、① 路由匹配：Path / Host / Header 的优先级怎么定？（速查 + 详见专篇）

**本节要点**：匹配规则本身不难，难的是**优先级** —— 顺序写反会出现「兜底规则抢走本该由正则处理的请求」，
而这个 bug 只有在同时配了「正则」与「宽前缀」时才会暴露。

**配置模型**：一条路由 = 匹配条件 + 上游 + 横切策略。

```go
type Route struct {
	Name        string            // 规则名，出现在日志与指标里
	Host        string            // 空/`*` = 任意；支持 *.example.com
	Path        string
	PathType    PathType          // exact | prefix | regex
	Methods     []string
	Headers     map[string]string // 必须全部匹配（值支持 * 通配）
	Upstream    string
	StripPrefix string            // 转发前剥掉的前缀
	Auth        AuthPolicy
	Limit       LimitPolicy
	Transcode   *TranscodePolicy
}
```

**优先级刻意做成与 Nginx location 同构**，这样从 Nginx 迁过来行为不突变：

```go
// 精确(exact) > 正则(regex) > 最长前缀(prefix)
// ⚠️ 「正则优先于普通前缀」这一条最容易写反 —— 顺序错了，^/api/users/\d+$
//    会被兜底的 location / 抢走（本机实测踩过，见下）。
switch c.PathType {
case PathExact:
	if path == c.Path {
		if score := 3; score > bestScore { /* 命中 */ }
	}
case PathRegex:
	if m := c.re.FindStringSubmatch(path); m != nil {
		if score := 2; score > bestScore { best.Groups = m[1:] }
	}
case PathPrefix:
	if strings.HasPrefix(path, c.Path) {
		// 同级前缀取最长的那个
		if score := 1; score > bestScore || (score == bestScore && len(c.Path) > bestLen) { /* 命中 */ }
	}
}
```

**一个值得抄走的设计**：匹配结果**带上「为什么命中」**。

```go
type MatchResult struct {
	Route  *Route
	Reason string   // "exact /api/orders" / "prefix /api/order/" / "regex ^/api/users/\d+$"
	Groups []string // 正则捕获组，供协议转换补参数
}
```

写进访问日志后，`route=order-prefix via=prefix /api/users/\d+$` 一行就能回答
「这个请求为什么没走我预期的那条规则」，不用再去读一遍配置。

> ⚠️ **本机实测抓到的错**：第一版把 `prefix` 的 score 写成 2、`regex` 写成 1，
> 结果 `/api/users/42` 命中兜底规则而不是正则规则。日志里 `route=fallback via=prefix /` 一眼可见 ——
> **这正是 `via` 字段的价值**：如果只记状态码（200），这个问题会被完全掩盖。

```text
修正前：path=/api/users/42  route=fallback     via=prefix /
修正后：path=/api/users/42  route=user-regex   via=regex ^/api/users/\d+$
```

**Host 与 Header 的匹配**：

```go
func hostMatch(rule, host string) bool {
	if h, _, ok := strings.Cut(host, ":"); ok { host = h }   // 先剥端口
	if strings.HasPrefix(rule, "*.") { return strings.HasSuffix(host, rule[1:]) }
	return strings.EqualFold(rule, host)
}
```

> 📎 **本节是速查版**：三种 path 语义的完整规则、优先级写反的后果（**含反例实测**）、头值通配与 `EqualFold` 的大小写差异、正则预编译的 benchmark，见 [网关路由匹配.md](网关路由匹配.md)。

## 三、② 认证鉴权：JWT 自己写一遍要注意什么？（速查 + 详见专篇）

**本节要点**：JWT 的结构就是 `base64url(header).base64url(payload).base64url(HMAC)`，
自己写一遍能看清三件**调库时会被隐藏**的事。

```go
func VerifyJWT(token string, secret string) (*Claims, error) {
	parts := strings.Split(token, ".")
	if len(parts) != 3 { return nil, ErrBadFormat }

	// ① 签名覆盖的是「前两段的原始字符串」，不是解析后的 JSON。
	//    如果先 unmarshal 再重新 marshal 去验签，字段顺序一变签名就失效。
	mac := hmac.New(sha256.New, []byte(secret))
	mac.Write([]byte(parts[0] + "." + parts[1]))
	want := mac.Sum(nil)
	got, err := b64decode(parts[2])
	if err != nil { return nil, ErrBadFormat }

	// ② 必须用 hmac.Equal（恒定时间比较），不能用 == —— 否则会被时序攻击逐字节猜出签名。
	if !hmac.Equal(want, got) { return nil, ErrBadSignature }

	// ③ 签名合法 ≠ 凭证有效：exp / nbf 是业务校验，必须在验签之后再查。
	var c Claims
	payload, _ := b64decode(parts[1])
	_ = json.Unmarshal(payload, &c)
	now := time.Now().Unix()
	if c.Exp > 0 && now > c.Exp { return nil, ErrExpired }
	if c.Nbf > 0 && now < c.Nbf { return nil, fmt.Errorf("凭证尚未生效") }
	return &c, nil
}
```

⭐ **`401` 与 `403` 必须分开**：没凭证/凭证无效 → 401（你可以带对再来）；
身份合法但权限不够 → 403（别再试了）。

```go
func authStatus(err error) int {
	if errors.Is(err, ErrForbidden) { return http.StatusForbidden }
	return http.StatusUnauthorized
}
```

**API Key 的两种传法与恒定时间比较**：

```go
key := r.Header.Get("X-API-Key")
if key == "" { key = r.URL.Query().Get("api_key") }   // 兼容不能改 header 的调用方
if !hmac.Equal([]byte(key), []byte(apiKeyValue)) { return nil, ErrBadSignature }
```

⚠️ **API Key 放 query 会被写进访问日志与浏览器历史**，只适合服务端之间调用；面向客户端一律放 header。

> 📎 **本节是速查版**：`exp` 为什么必须存在、寿命上限、401 / 403 的取舍、
> `Bearer` 大小写这个 RFC 细节、以及 7 种 JWT 形态与 8 种 `Authorization` 头形态的实测，
> 见 [JWT与APIKey鉴权.md](../../06-工程实践/安全/JWT与APIKey鉴权.md)。

**本机实测**（路由 `order-prefix` 要求 JWT，`order-create` 要求 JWT + 角色，`open-api` 要求 API Key）：

```text
路由 order-prefix（要求 JWT）：
  无凭证                  → 401  unauthorized
  格式错误(非 Bearer)       → 401  unauthorized
  签名错误(换密钥签)         → 401  unauthorized
  已过期(exp=-60s)        → 401  unauthorized
  完全正确(admin)          → 200  ok

路由 order-create（要求角色 admin/user）：
  角色 guest             → 403  forbidden      ← 与 401 区分开
  角色 admin             → 200  ok

路由 open-api（要求 API Key）：
  无 key / 错误 key       → 401
  正确 key               → 200
```

## 四、③ 限流：令牌桶为什么必须「惰性补充」？（速查 + 详见专篇）

**本节要点**：令牌桶的两条不变式很朴素，但工程上有两个坑：
**补充不能靠定时任务**（空闲连接白占资源）、**必须回收空闲桶**（按 IP 建桶会把内存吃光）。

```go
type TokenBucket struct {
	mu     sync.Mutex
	rate   float64 // 每秒补充的令牌
	burst  float64 // 桶容量 = 允许的突发量
	tokens float64
	last   time.Time
	seen   time.Time // 最后一次使用，用于回收
}

func (b *TokenBucket) Allow(n float64) (bool, time.Duration) {
	b.mu.Lock()
	defer b.mu.Unlock()

	now := time.Now()
	// ① 惰性补充：按「距上次请求过了多久」一次性补，而不是起一个 ticker 定时加
	b.tokens += now.Sub(b.last).Seconds() * b.rate
	if b.tokens > b.burst { b.tokens = b.burst }
	b.last, b.seen = now, now

	if b.tokens >= n { b.tokens -= n; return true, 0 }
	need := n - b.tokens
	return false, time.Duration(need / b.rate * float64(time.Second)) // 给 Retry-After 用
}
```

**空闲桶回收**——不限流回收的话，每个 IP 一个桶，扫描量一大内存就爆：

```go
func (l *Limiter) gc() {
	for range time.Tick(time.Minute) {
		cut := time.Now().Add(-l.ttl)
		for k, b := range l.buckets {
			if b.idleBefore(cut) { delete(l.buckets, k) }
		}
	}
}
```

**限流维度**：已登录按用户、未登录回落到 IP —— 这就是「限流必须挂在鉴权下游」的原因。

```go
func limitKey(routeName, subject, ip string) string {
	if subject != "" && subject != "anonymous" { return "route:" + routeName + "|user:" + subject }
	return "route:" + routeName + "|ip:" + ip
}
```

**本机实测**（路由 `open-api` 配 `rate=5/s, burst=2`，连续打 12 次）：

```text
第 1 次 → 200 ✅      第 3 次起 → 429 🚫  Retry-After: 1   X-RateLimit-Policy: 5/s burst=2
第 2 次 → 200 ✅      …
结果：200 × 2，429 × 10

等 1 秒让令牌回补后再打 3 次：200 / 200 / 429
```

⭐ **首批通过 2 次而不是 3 次**，正说明惰性补充是按真实时间算的：
桶初始装满 `burst=2` 个令牌，连打时几乎没有时间流逝，补不到新令牌 ——
**「突发」能力由桶容量决定，而不是「容量 + 1」**。

> 见 [限流算法.md](../../04-架构与系统/分布式/服务治理/限流算法.md)；Go 侧的独立实现（`x/time/rate`）
> 见 [限流器.md](并发/限流器.md)；⭐ 而**「限在途数」是另一根轴**（限速率的孪生问题：QPS 限制在下游变慢时

## 五、③ 熔断：三态机比限流难在哪？（速查 + 详见专篇）

**本节要点**：限流保护自己不被压垮（**入口速率**），熔断保护自己不被上游拖死（**上游错误率**）。
熔断的三个易错点全在状态迁移上。

```text
       失败率超阈值
  ┌───────────────────────┐
  ▼                       │
closed ──────────────► open ────── 冷却到期 ──────► half-open
  ▲                       ▲                          │
  │                       └──── 探测失败 ─────────────┘
  └──────────── 探测全部成功（放行 HalfOpenMax 个）────┘
```

```go
func (b *Breaker) Allow() error {
	b.mu.Lock()
	defer b.mu.Unlock()
	switch b.state {
	case StateOpen:
		if time.Since(b.openedAt) >= b.cfg.OpenFor {
			b.toHalfOpenLocked(); b.halfInFlight++   // 冷却结束 → 放少量探测流量
			return nil
		}
		return ErrBreakerOpen                        // ① 打开后必须快速失败，不再发起真实调用

	case StateHalfOpen:
		if b.halfInFlight >= b.cfg.HalfOpenMax { return ErrBreakerOpen }
		b.halfInFlight++
		return nil

	default:
		return nil
	}
}
```

```go
func (b *Breaker) Report(success bool) {
	switch b.state {
	case StateHalfOpen:
		if !success { b.toOpenLocked(); return }     // ② 探测失败 → 立刻回 open（而不是回 closed）
		b.halfOK++
		if b.halfOK >= b.cfg.HalfOpenMax { b.toClosedLocked() }
		return
	}
	// closed：③ 用滑动窗口，不能用累计计数（否则一次历史抖动会永久影响判定）
	if b.window[b.idx] { b.failures-- }
	b.window[b.idx] = !success
	if !success { b.failures++ }
	b.idx = (b.idx + 1) % len(b.window)
	if b.filled < len(b.window) { b.filled++ }

	if b.filled >= b.cfg.MinRequests {               // 样本不足时不打开，防止刚启动就被一次抖动打断
		if float64(b.failures)/float64(b.filled) >= b.cfg.FailRatio { b.toOpenLocked() }
	}
}
```

⚠️ **为什么必须有 half-open**：如果冷却到期后直接回 `closed`，
一个还没恢复的上游会被瞬间打满 → 再次雪崩 → 再次熔断，反复横跳。
half-open 的意义就是**只放极少量流量去试探**（本例 `HalfOpenMax=2`）。

**本机实测**（单节点上游，窗口 10 / 失败率 ≥50% 且样本 ≥4 才打开 / 冷却 3 秒 / 半开放行 2 个）：

```text
[1] 让上游开始返回 500
[2] 连打 8 次 /flaky：
    第 1~4 次 → 500  上游 500 透传
    第 5~8 次 → 503  circuit_open   ⭐ 熔断打开，快速失败
[3] 让上游恢复：
    立即再打 1 次 → 503（还在冷却期，仍快速失败）
    等 3.2 秒后连打 4 次 → 200 / 200 / 200 / 200（半开探测成功 → 回到 closed）

/metrics：gw_breaker_trips_total{service="flaky-svc"} 1
```

⭐ 注意第 5 次就打开了：`MinRequests=4` 说明**前 4 个真实请求就是「学费」**——
这 4 个用户必然失败。这是熔断的固有代价，也解释了为什么大厂会额外做**主动健康检查**
（nginx 社区版同样只有被动式，见 [网关选型.md](../../03-数据与中间件/中间件/网关与代理/网关选型.md) 第 3.5 节）。

## 六、④ 负载均衡：四种算法与一个哈希陷阱（速查 + 详见专篇）

**本节要点**：四种算法的差别只在两处 —— **是否需要会话粘性**、**节点能力是否相同**。
但一致性哈希有个**比虚拟节点更前置的坑**：哈希函数选错，虚拟节点会完全失效。

### 6.1 四种算法

| 算法 | 适用 | 关键实现点 |
|---|---|---|
| **轮询** | 节点同质、无状态 | 一个原子计数器取模即可 |
| **加权轮询** | 节点配置不同 | 用 Nginx 的**平滑**算法：每次选当前权重最大者，选完减去总权重、其余加自身权重 |
| **最少连接** | 请求耗时差异大 | 维护在途计数，请求结束要 `Done()` 归还 |
| **一致性哈希** | 需要会话粘性 / 缓存命中 | 哈希环 + **虚拟节点** |

**加权轮询为什么不能用「按权重重复放入列表」**：

```go
// 平滑加权轮询：权重 3:1 的输出是 A A B A，而不是 A A A B
// 后者会把三倍流量在时间上堆成一段，造成瞬时倾斜
func (b *weightedRR) Pick(string) (*Upstream, error) {
	best, bestIdx := -1<<31, 0
	for i, u := range b.ups {
		b.current[i] += weight(u)
		if b.current[i] > best { best, bestIdx = b.current[i], i }
	}
	b.current[bestIdx] -= b.total
	return &b.ups[bestIdx], nil
}
```

### 6.2 一致性哈希：虚拟节点

```go
const vnodesPerNode = 150

type hashRing struct {
	keys  []uint64          // 环上的位置，升序
	owner map[uint64]string // 位置 → 真实节点
}

func (r *hashRing) Pick(key string) (*Upstream, error) {
	h := hashOf(key)
	// 顺时针找第一个 >= h 的虚拟节点，找不到就绕回环首
	i := sort.Search(len(r.keys), func(i int) bool { return r.keys[i] >= h })
	if i == len(r.keys) { i = 0 }
	return lookup(r.owner[r.keys[i]]), nil
}
```

### 6.3 ⚠️ 一个比虚拟节点更前置的坑：哈希函数的雪崩性

第一版用了 `hash/fnv`（标准库、零依赖、看起来理所当然），结果**分布严重倾斜**。
直觉会归咎于「虚拟节点不够」，但**实测显示 `vnodes=1` 与 `vnodes=10` 的分布完全一样** ——
这不可能，除非虚拟节点根本没起作用。

查下去才发现根因：

```text
=== ① 哈希函数的雪崩性：同一节点的连续虚拟节点落在环的哪里？===
  FNV-1a         A#0..A#9 落在 [18059311470525726540, 18059323565153636861]
                 跨度占整环 0.000066%          ← 10 个虚拟节点挤在环的一处！
  MD5(前8字节)     A#0..A#9 落在 [3826117742805930969, 17906019882190577578]
                 跨度占整环 76.327302%         ← 均匀散布
```

**FNV-1a 对「末尾只差一个字符」的字符串几乎不产生变化**（`A#0`/`A#1`/`A#2`… 的哈希值连成一片），
于是同一节点的 150 个虚拟节点变成**一个**虚拟节点。虚拟节点数量再多也没用。

换成 MD5 截断后（标准库、无依赖）：

```text
=== ② 哈希函数对分布的影响（每节点 150 个虚拟节点，10 万个 key）===
  FNV-1a            A=17310  B=39560  C=43130   最大偏差 48.1%   ❌
  MD5(前8字节)       A=33344  B=34625  C=32031   最大偏差  3.9%   ✅

=== ③ 虚拟节点数的影响（哈希固定为 MD5）===
  每节点 1 个        A=3101   B=56668  C=40231   最大偏差 90.7%
  每节点 10 个       A=24801  B=45855  C=29344   最大偏差 37.6%
  每节点 50 个       A=28105  B=34314  C=37581   最大偏差 15.7%
  每节点 150 个      A=33344  B=34625  C=32031   最大偏差  3.9%
  每节点 500 个      A=33447  B=34068  C=32485   最大偏差  2.5%
  每节点 2000 个     A=33997  B=32362  C=33641   最大偏差  2.9%   ← 边际收益已尽
```

⭐ **两条结论**：

1. **哈希函数必须先选对**：生产用 xxhash / murmur3（比 MD5 快且雪崩好）；
   用 MD5 截断是「标准库可用」的走法，但**绝不能用 FNV**。
2. **虚拟节点数 150 是甜点**：从 1 → 150 偏差从 90.7% 降到 3.9%，再往上（500 / 2000）几乎无改善。

### 6.4 扩容迁移率（这才是用哈希环的真正理由）

```text
=== ④ 扩容迁移率（每节点 150 个虚拟节点，10 万 key）===
  哈希环  3 → 4 节点：迁移  22.8%（理想 1/4 = 25.0%）   ✅
  取模    3 → 4 节点：迁移  74.8%（理想 3/4 = 75.0%）   ❌ 几乎全量重排
```

这就是「为什么不直接用 `hash(key) % N`」的量化答案：
**取模扩容时几乎每个 key 都要换节点**（缓存全部失效）；
哈希环只迁移落在新增节点区间的那部分（约 `1/N`）。

### 6.5 本机实测（网关内，300 个用户）

```text
④ 一致性哈希分布 —— 路由 user-mobile → user-svc
   后端 A:  85 个 ( 28.3%)  ██████████████
   后端 B: 111 个 ( 37.0%)  ██████████████████
   后端 C: 104 个 ( 34.7%)  █████████████████
   理想值 100.0 个/节点（33.3%）

   幂等性：同一 X-User-Id 连打 5 次
     user-7     → ['C','C','C','C','C']  ✅ 恒定
     user-13    → ['C','C','C','C','C']  ✅ 恒定
     user-99    → ['B','B','B','B','B']  ✅ 恒定
     user-250   → ['A','A','A','A','A']  ✅ 恒定
```

轮询则严格交替：

```text
④-A 轮询：GET /anything（→ order-svc）打 9 次
   落点序列: B C A B C A B C A     分布: {B:3, C:3, A:3}
```

> ⚠️ 顺带一个容易误判的现象：第一次测负载均衡时输出里出现大量 `?`（解析不到 `backend` 字段）。
> 那不是负载均衡坏了，而是**限流生效**了 —— 被 429 拦下的响应体里没有 `backend`。
> **排查时先看状态码，再看内容**。

## 七、⑤ 协议转换：HTTP 请求怎么变成 gRPC 调用？（速查 + 详见专篇）

**本节要点**：协议转换是网关最合理的职责之一 —— 客户端只会说 JSON，服务端只会说 protobuf，
翻译放在网关一处，就不会散落到每个服务里。两个工程要点：**连接必须复用**、**方法名可以不用生成代码**。

```go
// ① 连接池：gRPC 连接建立要握手 + HTTP/2 SETTINGS，每请求新建会吃掉全部收益
func (p *GRPCPool) Conn(addr string) (*grpc.ClientConn, error) {
	if c, ok := p.conns[addr]; ok { return c, nil }
	c, err := grpc.DialContext(ctx, addr,
		grpc.WithTransportCredentials(insecure.NewCredentials()),
		grpc.WithDefaultCallOptions(grpc.CallContentSubtype("json")), // 用自定义 codec
		grpc.WithBlock())
	if err != nil { return nil, err }
	p.conns[addr] = c
	return c, nil
}

// ② 不需要生成的 stub：方法名就是 "/包.服务/方法" 这个字符串
func Transcode(ctx context.Context, pool *GRPCPool, addr string, t *TranscodePolicy,
	body []byte, groups []string, hdr map[string]string) (map[string]any, error) {

	conn, err := pool.Conn(addr)
	if err != nil { return nil, fmt.Errorf("连接上游 %s 失败: %w", addr, err) }

	req := map[string]any{}
	if len(body) > 0 {
		if err := json.Unmarshal(body, &req); err != nil { return nil, fmt.Errorf("请求体不是合法 JSON: %w", err) }
	}
	for i, g := range groups { req[fmt.Sprintf("param%d", i+1)] = g }  // 路径参数从正则捕获组补

	// 只透传白名单 metadata，避免把 Cookie / User-Agent 之类塞进 gRPC 头
	ctx = metadata.NewOutgoingContext(ctx, metadata.Pairs(kv...))

	out := map[string]any{}
	if err := conn.Invoke(ctx, "/"+t.Service+"/"+t.Method, &req, &out); err != nil { return nil, err }
	return out, nil
}
```

**REST → gRPC 的映射规则**：

| REST 侧 | gRPC 侧 |
|---|---|
| 请求体 JSON | 请求消息（字段名一一对应） |
| 路径参数（`/api/users/42`） | 路由正则的捕获组 → `param1` |
| 白名单请求头 | metadata（`x-trace-id`、`x-user-id`） |
| HTTP 状态码 | gRPC status（`codes.OK` → 200，其余 → 502 + 原始错误） |

⚠️ **关于本机的 JSON codec**：本机没有 `protoc`（只有 `protoc-gen-go`），所以注册了一个 JSON codec
代替 protobuf。**传输层仍是真正的 gRPC**（HTTP/2 多路复用、帧、超时传播、metadata 都在），
只是编解码换成 JSON。换成 protobuf 只需两步：去掉 `encoding.RegisterCodec`、
把 `map[string]any` 换成生成的消息结构体，其余逻辑一行不动。

**本机实测**：

```text
⑥ 协议转换：外部 REST/JSON → 内部 gRPC
   POST /api/orders  {"sku":"A1","qty":2}   （方法 /order.OrderService/CreateOrder）

   状态: 200
   {
     "code": 0,
     "data": {
       "accepted_by": "A",
       "order_id": "SO-20260930-9600",
       "protocol": "gRPC over HTTP/2 (json codec)",   ← ⭐ 这行是 gRPC 服务端返回的
       "received": {"company_id": 77, "qty": 2, "sku": "A1"},
       "trace": "4f485d1f56bb3fcf2a36cad965907350"    ← metadata 里的 trace 原样透传
     },
     "trace": "4f485d1f56bb3fcf2a36cad965907350",
     "via": "grpc"
   }
```

`protocol` 与 `trace` 两个字段都来自 gRPC 服务端，证明请求确实经过了 HTTP/2 + gRPC 帧，
而不是被普通 HTTP 转发。

> 📎 **本节是速查版**：不生成 stub 怎么调（`Invoke` + 方法名字符串）、换 codec 与手写 `ServiceDesc`、转码连接池的三个约束，见 [不使用protoc的gRPC.md](不使用protoc的gRPC.md)。

## 八、⑥ 反向代理：ReverseProxy 帮你做了什么？（速查 + 详见专篇）

**本节要点**：标准库 `httputil.ReverseProxy` 已经处理了最容易出错的部分，
你只需要管**三件事** —— 改写目标、治理头部、处理错误。

**它替你做的**：
- 逐跳头（Hop-by-hop）剔除：`Connection` / `Keep-Alive` / `TE` / `Transfer-Encoding` 等不能转发；
- 流式转发请求体与响应体（不会把大文件读进内存）；
- 支持 HTTP/1.1 升级（WebSocket）；
- **自动追加 `X-Forwarded-For`**（⚠️ 见下方踩坑）。

**你要做的三件事**：

```go
inner := &httputil.ReverseProxy{
	Director: func(req *http.Request) {
		req.URL.Scheme, req.URL.Host = target.Scheme, target.Host

		// (1) StripPrefix：把网关侧的前缀剥掉再转发
		if stripPrefix != "" && strings.HasPrefix(req.URL.Path, stripPrefix) {
			req.URL.Path = strings.TrimPrefix(req.URL.Path, stripPrefix)
			if req.URL.Path == "" { req.URL.Path = "/" }
		}

		// (2) 头部治理 —— ⚠️ X-Forwarded-For 不要在这里设（ReverseProxy 会自己追加，
		//     两边都做就会出现 "127.0.0.1, 127.0.0.1"，本机实测踩过）
		clientIP, _, _ := net.SplitHostPort(req.RemoteAddr)
		req.Header.Set("X-Real-IP", clientIP)
		req.Header.Set("X-Forwarded-Host", req.Host)
		req.Header.Set("X-Forwarded-Proto", scheme(req))

		// (3) ⭐ 剥离客户端伪造的内部头 —— 不做这一步，任何人加一个 X-Company-Id 就能越权
		for _, h := range internalHeaders { req.Header.Del(h) }
		// 再把网关鉴权出来的身份重新写进去（此刻它才是可信的）
		if id := identityFrom(req.Context()); id != nil { req.Header.Set("X-Forwarded-User", id.Subject) }

		req.Host = target.Host
	},
	Transport: &http.Transport{
		Proxy:               nil,  // 明确不走环境变量里的代理
		MaxIdleConnsPerHost: 50,   // ⚠️ 默认只有 2，网关这种场景必须调大
		IdleConnTimeout:     90 * time.Second,
		DialContext:         (&net.Dialer{Timeout: 2 * time.Second, KeepAlive: 30 * time.Second}).DialContext,
	},
	FlushInterval: 100 * time.Millisecond,  // SSE / 流式响应更平滑
	ErrorHandler: func(w http.ResponseWriter, r *http.Request, err error) {
		// 区分超时与连不上：运维排障时这两个的处置完全不同
		status, msg := http.StatusBadGateway, "upstream error"
		switch {
		case errors.Is(err, context.DeadlineExceeded), os.IsTimeout(err):
			status, msg = http.StatusGatewayTimeout, "upstream timeout"
		case isConnRefused(err):
			status, msg = http.StatusBadGateway, "upstream refused"
		}
		...
	},
}
```

**头部治理的本机实测**（客户端故意伪造 `X-Company-Id` / `X-Tenant-Id` / `X-Forwarded-User`）：

```text
后端回显的 headers：
  X-Forwarded-For: 127.0.0.1          ← 修正后只有一个（此前是 "127.0.0.1, 127.0.0.1"）
  X-Forwarded-Host: 127.0.0.1:18080
  X-Forwarded-Proto: http
  X-Forwarded-User: anonymous         ← ⭐ 客户端伪造的 admin-hacker 被剥掉，换成了可信身份
  X-Real-IP: 127.0.0.1
  X-Trace-Id: my-own-trace-id         ← 客户端自带的 trace 被沿用（跨系统链路能串起来）
```

⭐ `X-Company-Id` / `X-Tenant-Id` **完全没有出现**，说明剥离生效。
这两行是**多租户系统的必修项**：只要网关不剥，上游任何一处写了 `c.Request.Header.Get("X-Company-Id")`
就会被越权（详见 [网关选型.md](../../03-数据与中间件/中间件/网关与代理/网关选型.md) 使用段）。

> 📎 **本节是速查版**：`StripPrefix` 的**段边界坑**（`/apifoo` 被 `/api` 误剥）、
> 为什么 `X-Forwarded-For` 不能手写、「出站请求被 Clone 导致 Header 传不回来」这个隐蔽的坑、
> `Transport` 的四个必调参数与「TLS 失败绝不静默降级」，见
> [反向代理原理与实现.md](../../02-计算机基础/网络/反向代理原理与实现.md)；
> 「客户端真实 IP 该信哪个头」见 [客户端真实IP与可信代理.md](../../02-计算机基础/网络/客户端真实IP与可信代理.md)。

## 九、⑦ 可观测性：一条请求的三个切面（速查 + 详见专篇）

**本节要点**：TraceID、日志、指标解决的是三个不同问题，缺一个都会在排障时卡住。

| 手段 | 回答的问题 | 成本 |
|---|---|---|
| **TraceID** | 这一次请求经过了哪些环节 | 极低（透传 + 生成） |
| **日志** | 这一次请求发生了什么（可读、可检索） | 中（存储与索引） |
| **指标** | 一万次请求整体怎么样（聚合、便宜） | 低 |

**TraceID：优先沿用上游传进来的**（网关常常是链路中间一环）：

```go
func EnsureTraceID(h http.Header) string {
	if v := h.Get(traceHeader); v != "" { return v }   // 复用，而不是覆盖
	var b [16]byte
	_, _ = rand.Read(b[:])
	id := hex.EncodeToString(b[:])
	h.Set(traceHeader, id)
	return id
}
```

**访问日志：结构化 key=value**（人可读，也能被 Filebeat / Vector 直接切成字段）：

```go
parts := []string{
	"ts=" + time.Now().Format("15:04:05.000"),
	"trace=" + short(e.TraceID),
	"method=" + e.Method, "host=" + e.Host, "path=" + e.Path,
	"route=" + orDash(e.Route),      // ⭐ 命中了哪条规则
	"via=" + orDash(e.MatchWhy),     // ⭐ 为什么命中（exact/prefix/regex）
	"who=" + orDash(e.Identity),     // ⭐ 鉴权出来的身份
	"upstream=" + orDash(e.Upstream),
	"status=" + fmt.Sprint(e.Status),
	"latency=" + fmt.Sprintf("%.1fms", float64(e.Latency.Microseconds())/1000),
}
```

**实际日志**（路由 bug 就是靠 `route=` 与 `via=` 一眼定位的）：

```text
ts=18:03:22.041 trace=bd5d6b43 method=GET host=api.example.com path=/api/order/123
  route=order-prefix via=prefix /api/order/ who=u-1001 upstream=127.0.0.1:19002
  status=200 latency=12.4ms bytes=299 breaker=closed
```

**指标：直接输出 Prometheus 文本格式**（`/metrics` 可被抓取，不引 SDK）：

```text
gw_requests_total{route="flaky",status="500"} 4
gw_requests_total{route="flaky",status="503"} 5
gw_requests_total{route="open-api",status="429"} 1
gw_request_duration_ms{route="order-create",quantile="p95"} 2
gw_limit_rejected_total{route="open-api"} 1
gw_breaker_trips_total{service="flaky-svc"} 1

```

## 使用：怎么跑起来、怎么接到 photography-server

**本节要点**：把代码跑起来只需要 4 个进程；接进真实项目时，
**本篇的三个设计点直接对应 [photography-server](https://github.com/Eleven-26/photography-server) 的三个真实风险**。

### 拿到代码

```bash
git clone https://github.com/Eleven-26/gateway.git && cd gateway
go build -o bin/gateway.exe ./cmd/gateway
go build -o bin/backend.exe ./cmd/backend
```

⚠️ **下面的命令按本篇实测时的产物名写**（`gw.exe` / `backend.exe`）。仓库现在把入口拆到 `cmd/` 下的
四个目录（`gateway` / `backend` / `statestore` / `hashring`），产物落在 `bin/`，名字以你 `go build -o` 为准。

### 本地跑起来（4 个进程）

```bash
# 1) 三个后端（A 同时提供 HTTP 与 gRPC）
./backend.exe -http 127.0.0.1:19001 -grpc 127.0.0.1:19100 -name A &
./backend.exe -http 127.0.0.1:19002 -name B &
./backend.exe -http 127.0.0.1:19003 -name C &

# 2) 网关
./gw.exe
# gateway listening on http://127.0.0.1:18080  (routes=9 services=5)

# 3) 验证
curl -s 127.0.0.1:18080/healthz
curl -s 127.0.0.1:18080/metrics | head
curl -s 127.0.0.1:18080/debug/logs | python -m json.tool | head
```

### 接进 photography-server：三个设计点正好对上三个风险

| 本篇的设计点 | [photography-server](https://github.com/Eleven-26/photography-server) 的风险 | 怎么接 |
|---|---|---|
| **剥离 `X-Company-Id` / `X-Tenant-Id`**（第八节） | 多租户越权：客户端伪造租户头即可跨租户读数据 | 在网关 Director 里 `Del`，只信应用层从 JWT 解出的值 |
| **限流按用户而不是 IP**（第四节） | 摄影工作室常在同一 NAT 后（门店/园区），按 IP 限会误伤整栋楼 | 先过鉴权拿到 `company_id` / `userId`，再按用户维度建桶 |
| **`X-Forwarded-For` 只由网关写**（第八节） | 审计日志里记录的是 LB 的 IP，出事后追不到人 | Director 不设 XFF（交给 ReverseProxy），审计只读最左可信值 |

**迁移路径**（不必一次全换）：现在的 Nginx 先继续跑，
把**需要动态路由 / 按租户限流**的那几条路径先切到 Go 网关；
其余仍走 Nginx。判据见 [网关选型.md](../../03-数据与中间件/中间件/网关与代理/网关选型.md) 第三节 ——
**不要为了「有网关」而引入第二个入口**。

> ⚠️ **生产化还缺什么**（本篇刻意没做的部分，避免篇幅失控）：
> 配置热更新（现在改配置要重编译）、TLS 终止、WebSocket 透传（需要实现 `Hijacker`）、
> 分布式限流（多实例共享配额，需要 Redis + Lua，见 [稳定性三件套.md](../../04-架构与系统/分布式/服务治理/稳定性三件套.md)）、
> 配置校验与回滚、pprof 与优雅退出。这些在选型篇的「上线检查单」里都有对应条目。

## 延伸追问

- **为什么限流要放在鉴权之后？** → 限流维度需要「你是谁」。放在鉴权之前，只能按 IP 限，
  NAT 后的一整栋楼共用一个桶，正常用户会被误伤。**代价是未通过鉴权的请求不受限流保护** ——
  所以生产上会**两层都配**：网关最外层按 IP 挡洪水，鉴权后再按用户精细限。
- **熔断打开后，请求去哪了？** → **直接快速失败**（503），不发往上游。
  这是熔断与限流最大的区别：限流是「不让你进来」，熔断是「我不去调用他了」。
  如果打开后还继续调用，就只是把 500 换成了 503，没有任何收益。
- **为什么要 half-open 而不直接恢复？** → 上游可能只是短暂抖动，也可能根本没恢复。
  直接回 `closed` 会让恢复期的上游瞬间被打满 → 再次雪崩 → 再次熔断，来回横跳。
  half-open 只放极少量探测流量，用真实结果决定去留。
- **一致性哈希的虚拟节点要设多少？** → 本机实测：每节点 150 个时最大偏差 3.9%，
  500 个降到 2.5%，2000 个反而 2.9%（边际收益已尽、内存白占）。
  ⚠️ 但**前提是哈希函数雪崩性够好** —— 用 FNV-1a 时虚拟节点完全失效（见 6.3）。
- **JWT 验签为什么不能用 `==` 比较签名？** → 字符串比较会在第一个不同的字节处提前返回，
  攻击者可以据此逐字节猜出正确签名（时序攻击）。必须用 `hmac.Equal`（恒定时间）。
- **`httputil.ReverseProxy` 需要自己设 `X-Forwarded-For` 吗？** → **不需要**，它自己会追加。
  手动再设一次会得到 `"127.0.0.1, 127.0.0.1"`（本机实测）。但 `X-Real-IP` /
  `X-Forwarded-Host` / `X-Forwarded-Proto` 它不管，必须自己补。
- **网关里该不该做业务逻辑？** → 不该。网关在请求路径最上游，一次发布影响全部流量。
  判据：**「这个改动是否需要业务方参与评审」—— 是，就不该在网关**。
  该做的只有横切关注点：认证、限流、熔断、路由、灰度、日志。
- **这套实现和 APISIX / Kong 差在哪？** → 差在**动态配置**（本篇改配置要重编译，
  它们是 etcd / DB + watch）、**插件生态**、**主动健康检查**、**多实例限流共享**、**运维接口**。
  但核心七件事的实现思路是同一套 —— 这也是本篇的价值：**看懂它，选型时就不容易被名词唬住**。
- **协议转换为什么要放网关，不放在每个服务里？** → 放服务里意味着**每个服务都要同时支持**
  **REST 与 gRPC**、重复实现一遍参数映射与错误码转换。放网关则只有一处翻译，
  服务可以对外只暴露 gRPC（见 [通信选型.md](../../02-计算机基础/网络/通信选型.md) 的「把协议边界放在网关」）。
- **为什么指标要输出 Prometheus 文本格式而不是自己写 JSON？** → 文本格式的 `# HELP` / `# TYPE`
  是抓取端的约定，Prometheus / VictoriaMetrics 直接能抓；自己写 JSON 等于自建一套采集协议，
  还要再写一个 exporter。
