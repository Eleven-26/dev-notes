## 一、如何用 Go 实现一个限流器？

**本节要点**：**令牌桶**这个限流模型的原理，以及**参数的实际含义**。

> ⚠️ 模型与参数语义（令牌桶 / 漏桶的算法层）见 [限流算法.md](../../../04-架构与系统/分布式/服务治理/限流算法.md)；本节讲它在 Go 标准库里怎么落地。

### 1.1 先说工程实践（加分点）

> **通常直接用现成的轮子**——第三方 Go 库或**官方标准库**，
> **没有必要重复造轮子**。
>
> Go 官方的是 **`golang.org/x/time/rate`**（令牌桶实现）。
>
> **但原理必须能讲清楚**——这才是重点。

### 1.2 令牌桶的字段（看源码能对上的结构）

| 字段 | 作用 |
|---|---|
| **互斥锁** | 多个请求都要"取令牌"，都要**访问共享资源**（桶里还有多少令牌），所以要加锁 |
| **`limit`** | 每秒恢复速率 |
| **`burst`** | 桶容量（处理能力上限） |
| **`tokens`** | **当前令牌数量**，满足 `tokens <= burst` |
| **最后一次限流事件的时间** | **根据这个时间差来恢复令牌** |

**直观理解**：
- 桶的**高度**由 `Burst` 决定（令牌数量最多就这么多）；
- `Limit` 决定**每秒能补多少个**。

## 延伸追问

- **怎么实现"每用户限流"？** → 按用户维度维护独立的限流器
  （`map[userID]*rate.Limiter`），注意**要清理不活跃用户，避免内存泄漏**。
- **`Wait` 和 `Allow` 的区别？** → `Wait` 会**阻塞等待**到能取到令牌；
  `Allow`/`AllowN` **立即返回**是否允许，适合 quick-reject 场景。
  ⚠️ 补一句 `Wait` 的坑：它的报错有**三种**（超过 `Burst`、deadline 不够、ctx 被取消），
  其中**只有 ctx 取消**那一类等于 `ctx.Err()` —— 见本文件「使用」一节的实测。
- **`rate` 是单机限流，多实例部署怎么算总量？** → 全局速率 = **实例数 × `Limit`**。要么按实例数把 `Limit` 均分，要么把桶挪到 Redis 做全局限流（见 [限流算法·第九节](../../../04-架构与系统/分布式/服务治理/限流算法.md)）。
- **调参需要重建限流器吗？** → 不需要，`SetLimit` / `SetBurst` 可以**热更新**（实测见「使用」一节）；临时放行可以把速率设成 `rate.Inf`。

## 使用：把 rate 接进接口，并用实测把理论读数量出来

`golang.org/x/time/rate` 的 API 很小（`Allow` / `Wait` / `Reserve` 三族），
但参数语义和报错都很容易踩坑。下面按「接入骨架 → 把理论结论量出来 → 三个坑」看下去。
实测环境：**go1.26.5 + `golang.org/x/time/rate@v0.1.0`**。

### 接入骨架：网关快速拒绝、后台任务排队、按用户分桶

```go
package main

import (
	"context"
	"net/http"
	"sync"
	"time"

	"golang.org/x/time/rate"
)

// ① 建限流器：两个参数就是算法篇第二节的 Limit（每秒恢复多少）与 Burst（桶容量）
//    ⚠️ NewLimiter 起步是满桶而不是空桶 —— 见下面「三个坑」第 1 条
var apiLimiter = rate.NewLimiter(10, 100)

// ② 网关入口用 Allow 做 quick-reject：立即返回，不排队、不占住 goroutine
func gateway(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		if !apiLimiter.Allow() { // 桶里没令牌 → false，直接拒（算法篇第四、五节）
			http.Error(w, "too many requests", http.StatusTooManyRequests)
			return
		}
		next.ServeHTTP(w, r)
	})
}

// ③ 后台任务 / MQ 消费用 Wait 排队：阻塞到取到令牌，天然形成背压
func consume(ctx context.Context, job func() error) error {
	if err := apiLimiter.Wait(ctx); err != nil { // 失败形态有三种，见「三个坑」第 3 条
		return err
	}
	return job()
}

// ④ 按用户维度限流：一人一个桶，懒创建 + 定期清理（算法篇追问里那条）
//    rate.Limiter 自身并发安全，但 map 不是 → 锁必须包住 map 的全部读写
type perUserLimiter struct {
	mu       sync.Mutex
	buckets  map[string]*rate.Limiter
	lastSeen map[string]time.Time
	limit    rate.Limit
	burst    int
	idle     time.Duration // 超过这个时长没请求就回收，否则 map 只增不减 → 内存泄漏
}

func (u *perUserLimiter) Allow(id string) bool {
	u.mu.Lock()
	defer u.mu.Unlock()
	l, ok := u.buckets[id]
	if !ok {
		l = rate.NewLimiter(u.limit, u.burst) // 新用户也是从满桶开始
		u.buckets[id] = l
	}
	u.lastSeen[id] = time.Now()
	return l.Allow()
}

func (u *perUserLimiter) gc(now time.Time) { // 定时调，比如每分钟一次
	u.mu.Lock()
	defer u.mu.Unlock()
	for id, t := range u.lastSeen {
		if now.Sub(t) > u.idle {
			delete(u.buckets, id)
			delete(u.lastSeen, id)
		}
	}
}
```

### 实测：把算法篇的说法量出来

算法篇说「令牌是每 100ms 恢复 1 个，不是攒满一秒一次性给」「空桶要 10 秒才能填满」——
这两句都能直接读数验证：用 **`Reserve` 的 `Delay()`**，不必真的等 10 秒。

```go
lim := rate.NewLimiter(10, 100)
fmt.Printf("Limit=%v/s Burst=%d Tokens=%.0f\n", lim.Limit(), lim.Burst(), lim.Tokens())

// 突发：桶满时连打 101 个请求
pass, reject := 0, 0
for i := 0; i < 101; i++ {
	if lim.Allow() {
		pass++
	} else {
		reject++
	}
}
fmt.Printf("通过 %d / 拒绝 %d，剩余 Tokens=%.0f\n", pass, reject, lim.Tokens())

// 平滑生成：掏空后连续 Reserve 3 个，看 Delay 是不是 +100ms 递增。
// 统一拿同一个 base 调 DelayFrom —— 读到的就是理论值，不受打印耗时影响。
base := time.Now()
lim.AllowN(base, 100) // 掏空
r1 := lim.ReserveN(base, 1)
r2 := lim.ReserveN(base, 1)
r3 := lim.ReserveN(base, 1)
fmt.Printf("第 1/2/3 个令牌 Delay=%v / %v / %v\n",
	r1.DelayFrom(base).Round(time.Millisecond),
	r2.DelayFrom(base).Round(time.Millisecond),
	r3.DelayFrom(base).Round(time.Millisecond))

// 攒满一桶要多久：换一个同样参数的新桶来问，避免受上面 3 次预支的影响
full := rate.NewLimiter(10, 100)
full.AllowN(base, 100)
fmt.Printf("空桶攒满 100 个令牌 Delay=%v\n",
	full.ReserveN(base, 100).DelayFrom(base).Round(time.Millisecond))
```

```text
Limit=10/s Burst=100 Tokens=100
通过 100 / 拒绝 1，剩余 Tokens=0
第 1/2/3 个令牌 Delay=100ms / 200ms / 300ms
空桶攒满 100 个令牌 Delay=10s
```

`Delay` 是**线性递增**的，所以「平滑生成」成立；一次要 100 个要等满 10 秒，
正好对上算法篇「需要 10 秒才能重新填满」。接着验证 `Burst` 与 `Wait` 的行为：

```go
// 实验五：Burst=1 → 退化成严格串行（速率仍是 10/s 也没用）
serial := rate.NewLimiter(10, 1)
start := time.Now()
for i := 0; i < 4; i++ {
	_ = serial.Wait(context.Background())
}
fmt.Printf("Burst=1 连续 Wait 4 次总耗时 %v\n", time.Since(start).Round(10*time.Millisecond))

// 实验六：Allow 立即返回 vs Wait 阻塞等待
l6 := rate.NewLimiter(5, 1) // 5/s → 每 200ms 补 1 个
fmt.Printf("第 1 次 Allow=%v，紧接着 Allow=%v\n", l6.Allow(), l6.Allow())
ctx, cancel := context.WithTimeout(context.Background(), time.Second)
defer cancel()
start = time.Now()
err := l6.Wait(ctx)
fmt.Printf("Wait → err=%v，等了 %v\n", err, time.Since(start).Round(10*time.Millisecond))

// 实验七：Wait 的三种失败形态（只有第三种返回 ctx.Err()）
l7 := rate.NewLimiter(10, 5)
err = l7.WaitN(context.Background(), 6) // 6 > Burst
fmt.Printf("(a) %v\n", err)
l7 = rate.NewLimiter(1, 1)
l7.Allow() // 掏空，下一个令牌 1 秒后才有
ctxB, cancelB := context.WithTimeout(context.Background(), 50*time.Millisecond)
defer cancelB()
start = time.Now()
err = l7.Wait(ctxB)
fmt.Printf("(b) %v，用时 %v，errors.Is(DeadlineExceeded)=%v\n",
	err, time.Since(start).Round(time.Millisecond), errors.Is(err, context.DeadlineExceeded))
l7 = rate.NewLimiter(1, 1)
l7.Allow()
ctxC, cancelC := context.WithCancel(context.Background())
time.AfterFunc(300*time.Millisecond, cancelC) // 等待途中被取消
start = time.Now()
err = l7.Wait(ctxC)
fmt.Printf("(c) %v，errors.Is(Canceled)=%v，用时 %v\n",
	err, errors.Is(err, context.Canceled), time.Since(start).Round(10*time.Millisecond))
```

```text
Burst=1 连续 Wait 4 次总耗时 300ms
第 1 次 Allow=true，紧接着 Allow=false
Wait → err=<nil>，等了 200ms
(a) rate: Wait(n=6) exceeds limiter's burst 5
(b) rate: Wait(n=1) would exceed context deadline，用时 0s，errors.Is(DeadlineExceeded)=false
(c) context canceled，errors.Is(Canceled)=true，用时 300ms
```

最后是按用户限流与调参：

```go
// 实验八：按用户维度限流 —— 各人的桶互不干扰
ul := &perUserLimiter{
	buckets:  map[string]*rate.Limiter{},
	lastSeen: map[string]time.Time{},
	limit:    2, burst: 2, idle: time.Minute,
}
for i := 1; i <= 3; i++ {
	fmt.Printf("用户 A 第 %d 次 → %v\n", i, ul.Allow("A"))
}
fmt.Printf("用户 B 第 1 次 → %v\n", ul.Allow("B")) // B 用自己的桶，不受 A 影响

// 清理：伪造一个 2 分钟没请求的用户 C
ul.buckets["C"] = rate.NewLimiter(2, 2)
ul.lastSeen["C"] = time.Now().Add(-2 * time.Minute)
ul.gc(time.Now())
fmt.Printf("gc 后剩余桶数量=%d\n", len(ul.buckets))

// 实验九：热更新 —— 实例可复用，配置中心推新参数时不用重建
apiLimiter.SetLimit(1000)
apiLimiter.SetBurst(2000)
fmt.Printf("调参后 Limit=%v/s Burst=%d\n", apiLimiter.Limit(), apiLimiter.Burst())

// 实验十：想让「启动即严格按速率」，先把初始满桶扣掉（见「三个坑」第 1 条）
drain := rate.NewLimiter(10, 100)
drain.AllowN(time.Now(), drain.Burst()) // 初始那一桶令牌全扣掉
fmt.Printf("掏空后 Tokens=%.0f，Allow=%v\n", drain.Tokens(), drain.Allow())
time.Sleep(150 * time.Millisecond) // 10/s → 150ms 约恢复 1.5 个
fmt.Printf("150ms 后 Allow=%v\n", drain.Allow())
```

```text
用户 A 第 1 次 → true
用户 A 第 2 次 → true
用户 A 第 3 次 → false
用户 B 第 1 次 → true
gc 后剩余桶数量=2
调参后 Limit=1000/s Burst=2000
掏空后 Tokens=0，Allow=false
150ms 后 Allow=true
```

### 三个坑

**坑 1：`NewLimiter` 起步就是满桶，不是空桶。**

实测 `Tokens()=100`、`Allow()` 立刻为 `true` —— 后果是**服务刚启动就能放行一整个 `Burst` 的突发**。
若想「启动即严格按 `Limit` 的速率」，先手动掏空：`lim.AllowN(time.Now(), lim.Burst())`
（实测掏空后 `Tokens=0`、`Allow=false`，150ms 后才恢复出第 1 个令牌）。

**坑 2：`Burst` 才是并发上限，`Limit` 再大也救不了。**

实测 `Burst=1` 时 `Limit=10/s` 形同虚设：4 次 `Wait` 花了 **300ms**，退化成「每 100ms 才放一个」。
所以 `Burst` 要按「**这个接口允许同时过多少个**」来设；设成 1 就等于把这个接口串行化。

**坑 3：`Wait` 的错误有三种，只有一种等于 `ctx.Err()`。**

| 情况 | 返回的错误 | 是否等于 `ctx.Err()` |
|---|---|---|
| `n > Burst`（一次要的令牌比桶还大） | `rate: Wait(n=6) exceeds limiter's burst 5` | ❌ |
| 预测到 deadline 前拿不到令牌（实测 ctx 50ms vs 令牌 1s） | `rate: Wait(n=1) would exceed context deadline`，**立即返回** | ❌ 实测此刻 `ctx.Err()` 仍是 `nil`（ctx 还有 50ms 才到期），`errors.Is(err, context.DeadlineExceeded)` 也是 **false** |
| 等待途中 ctx 被取消 / 超时 | 就是 `ctx.Err()`（`context canceled`） | ✅ |

所以两类判断不要混：想知道**是不是 ctx 引发的失败**看 `ctx.Err()`（别看错误串），
想知道**有没有拿到令牌**则 `err != nil` 就够了 —— `Wait` 只在没拿到令牌时才返回错误。

```go
err := apiLimiter.Wait(ctx)
switch {
case err == nil: // 拿到令牌，继续处理
case ctx.Err() != nil: // 请求方超时 / 主动断开 → 如实返回
	return ctx.Err()
default: // 等不到令牌（deadline 不够、n 超过 Burst 等）→ 按限流拒绝处理，比如回 429
	return err
}
```

另外两点工程提醒：

- **`rate.Inf` 表示不限流**：`rate.NewLimiter(rate.Inf, 0)` 放行一切（实测连 `Burst=0` 也
  `Allow()=true`、`AllowN(10)=true`），做灰度开关或紧急放流很方便；
- **`rate` 是单机限流**：多实例部署时全局速率 = **实例数 × `Limit`**。要么按实例数把
  `Limit` 均分，要么把桶挪到 Redis 做全局限流（见
  [稳定性三件套.md](../../../04-架构与系统/分布式/服务治理/稳定性三件套.md)）。
