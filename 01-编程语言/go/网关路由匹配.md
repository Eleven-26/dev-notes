# 网关路由匹配

> 内容整理自个人学习笔记，实测基于自研网关项目 [gateway](https://github.com/Eleven-26/gateway)（module `gwlab`，Go 1.26.5）的 `internal/router/`（本篇 `text` 块都是本机真实运行结果）。

---

## 一、三种路径语义为什么不能只留一种？

**本节要点**：`exact` / `regex` / `prefix` 不是三种实现风格，而是**三档表达能力**——分别对应「单点资源」「带参数的资源路径」「一族接口」。删掉任何一档，就会有一类路由写不出来。

匹配的输入是一张 `Route` 表，每条规则声明 `Host` / `Path` / `PathType` / `Methods` / `Headers`（见 `internal/config/types.go`）：

```go
type Route struct {
	Name     string            `json:"name"`
	Host     string            `json:"host"`      // 空 = 任意；支持 *.example.com 通配
	Path     string            `json:"path"`
	PathType PathType          `json:"path_type"` // exact | prefix | regex
	Methods  []string          `json:"methods,omitempty"` // 空 = 任意
	Headers  map[string]string `json:"headers,omitempty"` // 必须全部匹配（值支持 * 通配）
	Upstream string            `json:"upstream"`
}
```

### 1.1 exact：单点资源，语义最硬

`PathType: exact` 的判据是**字符串完全相等**（`internal/router/route.go:128`）：

```go
case config.PathExact:
	if path == c.Path { /* 命中 */ }
```

它适合 `/healthz`、`POST /api/orders`（建单）、`/flaky` 这类**固定端点**。特点是"锁死"：前缀和正则都会顺带匹配别的路径，精确不会——`/api/users/42` 的 exact 规则不会命中 `/api/users/42/detail`。成本也最低：一次字符串比较。

### 1.2 regex：带参数的资源路径

`PathType: regex` 用正则**整体**匹配 URI（已锚定）。它要解决的是前缀表达不了的需求：

```text
^/api/users/\d+$

/api/users/42   → 命中（这一段是数字）
/api/users/me   → 不命中   ← 前缀 /api/users/ 会把它一起吞掉
/api/users/abc  → 不命中   ← 前缀同样会吞掉
```

即"这一段必须是数字 / UUID / 某种形态"。正则还能给出**捕获组**（把 `\d+` 括起来）供下游补齐路径参数（见第五节）。代价是匹配成本高于前缀，写不好还会有回溯。

### 1.3 prefix：一族接口 + 兜底

`PathType: prefix` 用 `strings.HasPrefix` 判据，**同级取最长**（`internal/router/route.go:147`）：

```go
case config.PathPrefix:
	if strings.HasPrefix(path, c.Path) {
		// 同级前缀取最长的那个 —— 与 Nginx 一致
		if scorePrefix > bestScore || (scorePrefix == bestScore && len(c.Path) > bestLen) {
			// 命中
		}
	}
```

`/api/order/` 覆盖该家族全部子路径、转发到同一上游；`/` 则是**兜底路由**（catch-all），只在没有更优规则时才命中。

### 1.4 为什么不能只留一种

| 只留 | 表达不了什么 |
|---|---|
| 只有 prefix | `/api/users/{id}` 与 `/api/users/me` 无法区分；「id 必须是数字」无从表达 |
| 只有 regex | 日常「某前缀一族」要写成 `^/api/order/.*$`，可读性与性能双输；「最长前缀优先」还得靠规则顺序模拟 |
| 只有 exact | 路由表爆炸——每个 id 都要写一条 |

三档合起来才完整：**exact 锁单点、regex 收带参资源、prefix 兜一族**。这也正是 Nginx `location` 必须同时提供 `=` / `~` / 无修饰前缀三种写法的原因。

## 二、优先级为什么必须是「精确 > 正则 > 最长前缀」？

**本节要点**：这个顺序不是"谁更具体"的直觉，而是**与 Nginx `location` 逐条同构的判定链**：精确命中即停 → 正则命中即停 → 最后才回落到最长前缀。顺序写反，兜底的 `/` 会抢走本该走正则的请求，表象是"正则路由永远命中不到"。

### 2.1 与 Nginx location 的对照

| 本篇 `PathType` | Nginx `location` | 匹配规则 |
|---|---|---|
| `exact` | `location = /x` | URI 完全相等，命中即**停止搜索** |
| `regex` | `location ~ /x`（`~` / `~*`） | 正则命中即用；Nginx 按配置顺序取**第一个命中**的 |
| `prefix` | `location /x`（无修饰） | 记住**最长**前缀；遍完正则都没命中才用它 |

⚠️ Nginx 还有第 4 档 `location ^~ /x`——「最长前缀一旦带 `^~`，就跳过全部正则」。本篇**刻意没有实现这一档**：迁移配置时若原站依赖 `^~`，行为会突变，需要把它改写成精确或更长前缀来表达。

### 2.2 得分就是排序 key，顺序敏感

匹配是一次**全表扫描取最优**，得分的定义（`internal/router/route.go:38`）：

```go
const (
	scoreExact  = 3
	scoreRegex  = 2
	scorePrefix = 1
)
```

顺序敏感的地方有三处：

1. **优先级 key =（score, 前缀长度）**。精确、正则**不比长度**；只有同为 `prefix` 时才用 `len(c.Path)` 打破平局（最长前缀优先）。
2. **同分的精确 / 正则是"先到先得"**（判定用严格 `>`）。等价于 Nginx「正则按配置顺序，第一个命中即停」。
3. **绝不能用 map 遍历路由表**。`Router.routes` 是 slice，顺序确定；改成 map 会让同分路由的命中结果不稳定。`internal/config/validate.go:233` 也因此直接拒绝「匹配条件完全相同」的两条路由，报错原文是"命中顺序会不确定"。

### 2.3 顺序写反，后果是什么

把得分改成 `prefix(2) > regex(1)`（第一版真实踩过的写法），对照 `internal/router/route_test.go` 里的 `priorityRoutes`：

```text
规则声明顺序：id-exact, num-regex, fallback(/ 兜底前缀)

写反后 path=/api/users/7 → route=fallback  reason=prefix /
写对后 path=/api/users/7 → route=num-regex reason=regex ^/api/users/\d+$
```

`/api/users/42` 两条顺序都命中 `id-exact`（3 最高，不受影响），所以**问题只在"正则 vs 兜底前缀"同时命中时才暴露**。表现就是：正则规则明明写了、`go test` 也不报错，但线上永远走兜底——因为 `location /` 把请求抢走了。

### 2.4 本机实测：优先级与反例

下面两块是同一张三条路由（精确 / 正则 / 兜底前缀）的真跑结果：一块用仓库里的真实匹配器，一块用**把优先级改反**的对照实现。

```text
=== ① 优先级顺序：三条路由都会覆盖 /api/users/7 ===
  path=/api/users/42  → route=id-exact    reason=exact /api/users/42
  path=/api/users/7   → route=num-regex   reason=regex ^/api/users/\d+$
  path=/other         → route=fallback    reason=prefix /
  规则声明顺序：id-exact, num-regex, fallback(/ 兜底前缀)
```

```text
=== ② 反例：把得分顺序改成 prefix(2) > regex(1) ===
  path=/api/users/42  → route=id-exact    reason=exact /api/users/42
  path=/api/users/7   → route=fallback    reason=prefix /
  path=/other         → route=fallback    reason=prefix /
  对照：/api/users/7 本该走 num-regex，写反后被 fallback(/) 抢走
```

⭐ 两块**唯一不同的就是 `/api/users/7` 那一行**——精确不受顺序影响、兜底不受影响，只有"正则 vs 前缀"的相对高低变了。这也解释了这类 bug 为什么难查：绝大多数路径（`/other`）表现完全正常。

## 三、头值匹配为什么「一半大小写敏感、一半不敏感」？

**本节要点**：头值支持三种写法，其中「含 `*` 走大小写敏感正则、不含 `*` 走 `EqualFold`」这个**不一致是刻意的**——它是预编译重构前后逐字一致的行为契约。顺手给通配正则加 `(?i)` 就改了语义。

### 3.1 三种取值

`headersMatch`（`internal/router/route.go:178`）对每个声明的头分三路：

```go
for k, v := range c.Headers {
	got := req.Header.Get(k)
	if got == "" {
		return false // ⚠️ 头不存在、或存在但值为空串 → 一律不匹配
	}
	if v == "*" { // ① 存在即过
		continue
	}
	if strings.Contains(v, "*") { // ② 通配：走预编译好的锚定正则，大小写敏感
		re := c.headerRes[k]
		if re == nil || !re.MatchString(got) {
			return false
		}
		continue
	}
	if !strings.EqualFold(got, v) { // ③ 字面值：EqualFold，大小写不敏感
		return false
	}
}
```

| 规则里的值 | 语义 | 大小写 |
|---|---|---|
| `*` | 只要有这个头（非空）就算过 | 不适用 |
| 含 `*`（如 `mobile*`、`a*b`） | `^` + `QuoteMeta` + `\*`→`.*` + `$` 锚定正则 | **敏感** |
| 其它字面值（如 `mobile`） | `strings.EqualFold` | **不敏感** |

### 3.2 哪种更符合直觉

字面值这路符合直觉：HTTP 头**值**在很多场景里本就不区分大小写，`X-Client: MOBILE` 与 `mobile` 视为同一个值不奇怪。问题出在通配这路——

```text
规则值 mobile*   请求头值 mobile9  → 命中=true   (大小写敏感)
规则值 mobile*   请求头值 Mobile9  → 命中=false  (大小写敏感)
规则值 mobile    请求头值 MOBILE   → 命中=true   (EqualFold 不敏感)
```

同一个头，**只因为规则里多了一个 `*`，大小写行为就反了**。这就是那个"刻意的不一致"。

### 3.3 为什么会这样，该怎么统一

根因是改动前的实现（逐字）：

```go
regexp.MatchString("^" + strings.ReplaceAll(regexp.QuoteMeta(v), `\*`, ".*") + "$", got)
```

`QuoteMeta` 让 `.` `+` 等元字符按字面量走，但**没有**加 `(?i)`——Go 的 `regexp` 默认大小写敏感。预编译是**纯性能重构**，行为必须与改动前逐字一致，所以既没加 `(?i)`，也没把字面值改成大小写敏感。

要"统一"有三种选项，各有代价：

| 方案 | 代价 |
|---|---|
| 给通配正则加 `(?i)` | 与字面值一致，但**改了语义**：老配置里 `Mobile9` 原来不命中、现在会命中；正则引擎还要走大小写折叠路径 |
| 让字面值也敏感（`got == v`） | 一致但更严格，容易误伤按惯例发大小写混排头值的客户端 |
| 保持现状 + 文档写清 | 最省事，但靠约定——**本篇选这个**，因为预编译只允许等价重构 |

### 3.4 头值不能配成空串

`got == ""` 提前返回，意味着**头存在但值为空串**与**头缺失**在匹配器眼里是同一件事。推论很直接：

```text
规则值 *    请求头值 空串 → 命中=false (视为缺失)
```

所以配置里把某个头配成 `""` 等于配了一条永远不命中的路由——`*` 也救不回来。这是"规则里的每个头都必须存在"这条语义的必然结果。

## 四、正则为什么必须预编译？

**本节要点**：含 `*` 的头值正则在旧实现里是「每个请求、每个通配头值现编一次」——`regexp.MatchString` 内部会 `Compile`，既吃 CPU 又分配内存。预编译把这份成本挪到启动期 `New`，匹配阶段只剩一次 `Regexp.MatchString`。

### 4.1 旧写法的问题

```go
// 旧：每个请求、每个含 * 的头值都走一遍
regexp.MatchString("^" + strings.ReplaceAll(regexp.QuoteMeta(v), `\*`, ".*") + "$", got)
```

`regexp.MatchString` 并不是"用现成正则匹配"——它的实现是**编译一次、丢掉、再匹配**。正则编译要走解析 + NFA 构建，是 CPU 密集操作；网关在**热路径**上，每请求做一遍等于把编译成本乘上 QPS。

### 4.2 预编译的落点

`New` 一次性编译，结果挂在 `compiledRoute.headerRes[k]`（`internal/router/route.go:74`），匹配阶段只做一次 `MatchString`：

```go
type compiledRoute struct {
	config.Route
	re        *regexp.Regexp
	headerRes map[string]*regexp.Regexp // 含 * 的头值预编译结果，key 为头名
}
```

两条都要编译：`PathType == regex` 的路径正则、含通配符的头值正则。**任何一条编译失败都让 `New` 返回错误**——路由表是启动期资产，配置错就该启动即失败，而不是等第一个请求才暴露（旧实现里 `regexp.MatchString` 把编译错误静默吞掉了）。

⚠️ **绝不能在 `headersMatch` 里回退成"没查到就现编"**：`headerRes[k]` 取不到（例如测试手搓的 `compiledRoute`）时按"不匹配"处理——否则又把每请求现编搬了回来。

### 4.3 实测读数

仓库内 `BenchmarkMatch`（请求打中带通配头值的那条路由，`-benchtime 200ms`；此处略去 goos / cpu 头几行）：

```text
BenchmarkMatch-8   	  125420	      4208 ns/op	     120 B/op	       4 allocs/op
PASS
ok  	gwlab/internal/router	2.656s
```

仓库里已经没有"每请求现编"的旧写法可对拍（重构已落地），所以另起一个**独立实验台**复刻旧实现：同一张路由表、同一个请求，两种实现并排跑。

```text
goos: windows
goarch: amd64
cpu: Intel(R) Core(TM) i7-6700HQ CPU @ 2.60GHz
BenchmarkPrecompiled-8         	  216633	      1102 ns/op	     120 B/op	       4 allocs/op
BenchmarkPerRequestCompile-8   	   25246	      9730 ns/op	    4153 B/op	      55 allocs/op
PASS
```

> 上面第二块略去了含实验台目录的 `pkg` / `ok` 两行；实验台放在**未进版本库的临时目录**里，只作对拍证据。

⭐ 对拍读数：`1102 ns/op` 对 `9730 ns/op`（约 **8.8×**），分配从 `55 allocs/op` 降到 `4 allocs/op`（`4153 B/op` → `120 B/op`）。这几十次分配全部来自"每请求现编正则"，预编译后归零，只剩 `MatchResult` 自身的一次分配。这是时序类数字，**只主张趋势：预编译版本显著更快、分配显著更少**，具体倍数随 CPU 与路由表变化。

⭐ **同一台机器上复跑同一个 benchmark，数字会差好几倍** —— 本机另一次运行时 `BenchmarkMatch-8` 读到的是 `999.6 ns/op`（上表那次是 `4208 ns/op`）。所以这类读数**只能用来比较数量级与分配次数**（`4 allocs` vs `55 allocs` 是稳的），不要把它当成「性能提升了 N 倍」的结论。

`TestNewPrecompilesHeaderWildcards` 锁住落点：`*` 与纯字面量值**不占正则**，没有通配头值的路由 `headerRes` 保持 `nil`（不给每条路由白付一个 map）。

## 五、匹配结果怎么表达？捕获组为什么按序编号？

**本节要点**：匹配结果不只说明"命中哪条"，还带**为什么命中**与**捕获组**——前者让排障不用猜配置，后者是路径参数（`param1` / `param2`）的唯一来源。

```go
type MatchResult struct {
	Route  *config.Route
	Reason string   // "exact /api/orders" / "prefix /api/order/" / "regex ^/api/users/\d+$"
	Groups []string // 正则捕获组
}
```

- **`Route`**：命中的那条配置，后续流水线（鉴权 / 限流 / 转发）都读它。
- **`Reason`**：写进访问日志后，`route=fallback reason=prefix /` 一行就能解释"为什么没走我预期的那条规则"——第二节那个 bug 正是靠它定位的（若只记状态码 200，问题会被完全掩盖）。
- **`Groups`**：正则的 `m[1:]`，即**捕获组按序排列**。

### 5.1 为什么按序编号

路径里的参数顺序天然由 URL 结构决定，正则里 `(` 的出现顺序就是参数在路径里的出现顺序，所以直接按下标命名即可：

```go
for i, g := range groups {
	req[fmt.Sprintf("param%d", i+1)] = g // param1 / param2 / …
}
```

协议转换（REST → gRPC）用它补齐路径参数：`/api/users/(\d+)` 命中后 `param1 = "42"`。

命名捕获组（`(?P<id>\d+)`）看起来更可读，但需要额外解析与"名字 → 下游字段"的映射，而不同路由的参数名互不相同，反而多一层约定。代价是 `param1` / `param2` 本身不可读——**路由的注释里必须写清哪个 `paramN` 对应什么**。

- **两处细节**：只有 `regex` 会填 `Groups`；`exact` / `prefix` 命中时它是 `nil`。
- 正则命中但**没有捕获组**时是空切片 `[]string{}` 而非 `nil`（`route_test.go` 里 `wantGroups: []string{}` 就是在锁这个差异）。

## 使用：怎么把一张路由表配得优先级正确

**本节要点**：路由表是声明式的，**声明顺序不影响结果**（同分正则除外），真正决定命中的是 `path_type` 与路径长度。下面是一份真实配置片段，逐条看语义。

### 真实配置片段（`deploy/config.example.json`）

```json
"routes": [
  {
    "name": "order-list",
    "host": "api.example.com",
    "path": "/api/order/list",
    "path_type": "exact",
    "methods": ["GET"],
    "upstream": "order-svc",
    "limit": { "rate_per_sec": 50, "burst": 10 }
  },
  {
    "name": "order-prefix",
    "host": "api.example.com",
    "path": "/api/order/",
    "path_type": "prefix",
    "strip_prefix": "/api",
    "upstream": "order-svc",
    "auth": { "required": true, "scheme": "jwt" },
    "limit": { "rate_per_sec": 20, "burst": 5 }
  },
  {
    "name": "order-create",
    "host": "*",
    "path": "/api/orders",
    "path_type": "exact",
    "methods": ["POST"],
    "upstream": "grpc-order-svc",
    "auth": { "required": true, "scheme": "jwt", "roles": ["admin", "user"] },
    "transcode": { "service": "order.OrderService", "method": "CreateOrder" }
  }
]
```

逐条语义：

| 路由 | 语义 | 会被谁抢 / 抢谁 |
|---|---|---|
| `order-list` | `api.example.com` 上 `GET /api/order/list` 精确命中 | 同路径的 prefix 抢不走它 |
| `order-prefix` | 同 host 下 `/api/order/` 一族，转发前剥掉 `/api` | 对 `/api/order/list` 它短于精确路径，抢不过；对其他子路径它是最长前缀 |
| `order-create` | 任意 host 上 `POST /api/orders` 精确命中，转 gRPC | 路径是 `/api/orders`（**不带尾斜杠**），与 `order-prefix` 的 `/api/order/` 不冲突 |

### 正则与头值两条（内置默认路由表的 JSON 形态）

正则与头值没出现在上面的示例文件里，但它们在同一张表的 schema 内（取自 `internal/config/config.go` 的 `defaultRoutes`）：

```json
[
  {
    "name": "user-regex",
    "host": "*",
    "path": "^/api/users/\\d+$",
    "path_type": "regex",
    "upstream": "user-svc"
  },
  {
    "name": "user-mobile",
    "host": "*",
    "path": "/api/users/me",
    "path_type": "exact",
    "headers": { "X-Client": "mobile" },
    "upstream": "user-svc"
  }
]
```

- `user-regex` 收 `/api/users/42` 这类"id 是数字"的资源，且**一定排在兜底前缀之前**（第二节的优先级保证，与声明顺序无关）。
- `user-mobile` 是「精确 + 头」：只有带 `X-Client: mobile` 的 `/api/users/me` 才命中。头不满足时这条**整条出局**，不会"降级"命中别的规则（`route_test.go` 的"头不满足的路由不参与打分"）。

**四条落地判据**：

1. **别写"全能前缀"**：`/api/` 这类宽前缀只做兜底；真正区分资源的路径用 exact 或 regex，否则一族接口会互相抢。
2. **正则一定锚定首尾**（`^…$`），否则 `\d+` 会命中 `/api/users/42/detail`。
3. **兜底的 `/` 要么不配、要么配得最窄**：配了它，任何未命中请求都会落到它，第二节的反例正是它抢走了正则。
4. **头值不要写空串**；要"不区分大小写的通配"当前需自行注意（见 3.3）。

## 延伸追问

- **为什么是「正则优先于前缀」，而不是"更长者优先"？** → 更长者优先会让宽前缀里的长路径压过窄正则，"id 必须是数字"这类约束就无处安放。Nginx 的选择是正则整体优先于普通前缀，本篇照搬以保证迁移不突变。⚠️ 代价是普通前缀**永远**抢不过正则——若确实需要"这个前缀优先于正则"，本篇没有 `^~` 这一档，只能改用精确或更长前缀来表达。
- **两条路由匹配条件完全相同时会怎样？** → 启动即被 `validate.go` 拒绝，报"命中顺序会不确定"。匹配是全表扫描，同分同条件下谁先扫到谁赢，这正是"不确定"的直接来源，所以在配置校验阶段就堵死。
- **头值要一个"不区分大小写的通配"怎么办？** → 当前 `mobile*` 是大小写敏感的。要么把可能的大小写形态逐一列举，要么改 `headerValuePattern` 加 `(?i)`——但那会改语义，属于配置方与实现方要一起确认的变更（见 3.3）。
- **前缀路由怎么避免 `/api` 误伤 `/apifoo`？** → 带尾斜杠：用 `/api/` 而不是 `/api`。`strings.HasPrefix` 只看字符串前缀，不做段边界判断。
- **预编译之后热路径上还有分配吗？** → 有，`MatchResult{Route: &c.Route, …}` 每次命中都会分配（实测恒为 `4 allocs/op`）。要压到零分配需把结果改成复用结构或返回索引，但会牺牲 `Reason` / `Groups` 的表达力，本篇刻意不做。
- **路径正则为什么也让"编译失败即启动失败"？** → 路由表是启动期资产。若学旧实现静默吞错，配置里一个 `([` 会让那条路由**永不命中**且毫无提示，比启动失败难查得多。
