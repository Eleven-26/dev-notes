# 配置热重载与快照

> 「改个路由要重启网关」是很贵的：重启期间连接断掉、缓存冷启动、没法灰度回滚。
> 热重载要解决这件事，但它同时引入了一类**新的正确性问题** ——
> 「重载时哪些运行时状态该保留、哪些可以丢」，答错了会出现「熔断刚打开，一重载又全放开了」。
>
> 内容整理自个人学习笔记，实测基于自研网关项目 [gateway](https://github.com/Eleven-26/gateway)（module `gwlab`，Go 1.26.5）的
> `internal/config/` 与 `internal/gateway/reload.go`。
> 相关回归测试：`TestReloadSwapsRoutesAndPrunes`、`TestReloadKeepsBreakerState`、
> `TestReloadFailureKeepsOldConfig`、`TestReloadRebuildsBalancerOnTopologyChange`（项目 `go test ./internal/...` 全绿）。
>
> ⭐ **分工**：本篇讲**配置的快照化与重载时的状态保留契约**；
> 被保留的熔断器状态本身见 [熔断器.md](../../../04-架构与系统/分布式/服务治理/熔断器.md)；
> 配置中心（Nacos / etcd）的产品侧对比见 [Nacos.md](../../../03-数据与中间件/中间件/注册与配置中心/Nacos.md) 第七节。

## 一、「改配置要重启」到底贵在哪？

**本节要点**：重启的成本不只是「几秒不可用」，而是**它把配置变更变成了一个高风险动作**。

| 代价 | 说明 |
|---|---|
| 连接断开 | 长连接（WebSocket / SSE / gRPC 流）全部被切断，客户端要重连 |
| 冷启动 | 连接池空、DNS 缓存空、JIT / 预热丢失，前几秒的延迟明显偏高 |
| 无法灰度 | 配置一旦发布就是**全量生效**，出问题只能再重启一次回去 |
| 不可回滚 | 新旧配置之间没有「切回去」的动作，只有「再改一次 + 再重启」 |

⭐ 于是团队会**不敢改配置** —— 该加限流的不加、该调超时的不调，因为改一次的风险比不改更大。
热重载解决的正是这种「变更成本」问题。

⚠️ 但热重载不是免费的：它把「配置」从一个**启动期一次性输入**，
变成了**随时可能变化的外部状态**。所有依赖配置的东西都必须回答「它变了怎么办」——
这就是本篇后面全部内容的主线。

## 二、快照：把「可变配置」变成「不可变对象」

**本节要点**：不要在请求路径上读配置，而是在重载时把配置**编译成不可变快照**，
请求只读快照。这是让热重载不拖慢热路径的关键。

一份配置里有些东西**不能每次请求现算**：

```go
// newState：启动 / 重载时把配置「编译」成一份完整快照
func newState(cfg *config.Config) (*state, error) {
    // 启动/重载即校验：错误配置在启动期暴露，而不是等某个请求打进来变成 500
    if err := cfg.Validate(); err != nil {
        return nil, fmt.Errorf("配置校验失败: %w", err)
    }
    trusted, err := clientip.ParseTrusted(cfg.TrustedProxies)   // CIDR → 前缀集合
    if err != nil {
        return nil, fmt.Errorf("TrustedProxies 解析失败: %w", err)
    }
    r, err := router.New(cfg.Routes)                            // 正则编译 + 排序
    if err != nil {
        return nil, err
    }
    return &state{
        cfg:            cfg,
        router:         r,
        trustedProxies: trusted,
        authn:          auth.New(cfg.JWTSecret, cfg.APIKey),
    }, nil
}
```

⭐ **三件事都只在重载时做一次**：

| 编译产物 | 为什么不能每次请求做 |
|---|---|
| `router`（正则已编译、优先级已排好） | 正则编译是**毫秒级**操作，挂在每请求上等于把性能砍半（本项目实测正则预编译收益约 39×） |
| `trustedProxies`（CIDR → 前缀集合） | 每次请求解析一遍 CIDR 列表纯属浪费；且解析错误应该在启动期暴露 |
| `authn`（验签器） | 密钥变更需要重建 |

**请求路径上只做一次无锁读**：

```go
func (g *Gateway) snapshot() *state { return g.st.Load() }   // g.st 是 atomic.Value
```

`atomic.Value` 的 `Load` 是无锁的 —— 这是「快照模式」最大的好处：
**配置变更不会给请求路径带来任何锁竞争**，代价只是「一个请求可能用到新旧两份快照中的任意一份」，
而这个不一致窗口只有**一次 `Store` 的时间**。

## 三、重载时要保住什么、可以丢什么？

**本节要点**：这是热重载**唯一真正难的部分**。
答错就会出现「刚熔断的服务，一重载又全放开了」。

先看一个反例：

```text
10:00:00  上游 db-svc 挂了 → 熔断器打开（open，冷却 30s）
10:00:05  运维改了一条无关的路由 → 触发重载
          ❌ 如果重载时把熔断器一起重建：新熔断器的状态是 closed
          → 全量流量立刻打向还没恢复的 db-svc → 二次雪崩
```

所以规则是**按状态的性质分类**：

| 运行时状态 | 重载时 | 依据 |
|---|---|---|
| **熔断器** | ⭐ **按服务名复用，绝不重建** | 它的状态是「花真实失败换来的结论」，重建等于把学费白交 |
| **均衡器** | 只在「算法 / 节点列表 / 摘除参数」变了时重建 | 重建会丢节点级摘除计数，但这属于**可自愈**状态（几秒内重新学出来） |
| **代理缓存** | 按新配置**清理**失效条目 | `service\|addr\|strip` 的 key 只增不减，改了上游地址会留下永不释放的旧代理 |
| 连接池 / 限流桶 / 指标 / 访问日志 | **原样保留** | 它们是资源与累计量，重建等于泄漏（见第五节） |

⭐ **可自愈 vs 不可自愈**是这里唯一需要的判据：

```text
不可自愈（必须保留）：熔断状态 —— 重建后要重新经历「真实失败 N 次」才能回到同样的结论
可自愈（可以丢）  ：节点摘除计数 —— 重建后几秒内会自动重新学出来
必须清理（不能留）：代理缓存 —— 留着就是内存泄漏 + 用到过期配置
```

代理缓存的清理是**按新配置反推白名单**，而不是「清空重建」：

```go
// 只保留新配置里仍然可能用到的 key
allowed := map[string]bool{}
for _, rt := range cfg.Routes {
    svc := cfg.Services[rt.Upstream]
    if svc == nil { continue }
    for _, up := range svc.Upstreams {
        allowed[svc.Name+"|"+up.Addr+"|"+rt.StripPrefix] = true
    }
}
for k := range g.proxies {
    if !allowed[k] {
        delete(g.proxies, k)
        sum.ProxiesPruned++
    }
}
```

⭐ **为什么要这样绕一圈**：如果直接「全清空」，正在飞的那些请求的 `proxy.Proxy` 也会被释放，
而它们还在用 —— 更稳妥的做法是**保留仍可能用到的、清掉不可能再用到的**，
让「正在飞的请求」自然用完后被 GC 回收。

### 3.1 重载要返回一份「做了什么」的摘要

```go
type ReloadSummary struct {
    Routes          int
    Services        int
    BreakerKept     []string // 复用原有熔断器（状态不丢）
    BalancerRebuilt []string // 算法 / 节点列表 / 摘除参数变了 → 重建
    BalancerKept    []string // 拓扑没变 → 原样保留
    Removed         []string // 新配置里已不存在的服务
    ProxiesPruned   int      // 被清理的旧代理缓存条目
}
```

⭐ **这个摘要不是日志装饰，而是可观测性**：线上「重载之后某服务开始报错」时，
`BalancerRebuilt` 这一栏能立刻回答「是不是这次重载把它的摘除计数清了」。

## 四、失败时必须保持旧快照

**本节要点**：重载是「**全有或全无**」的，绝不能有「半新半旧」的中间态。

```go
func (g *Gateway) Reload(cfg *config.Config) (*ReloadSummary, error) {
    st, err := newState(cfg)      // ← 编译在锁外完成
    if err != nil {
        return nil, err           // 校验/编译任一失败 → 直接返回，当前快照保持不变
    }
    g.mu.Lock()
    defer g.mu.Unlock()
    ...                            // 复用熔断器 / 重建均衡器 / 清理代理
    g.st.Store(st)                 // ← 最后一步才让请求看到新配置
    return sum, nil
}
```

⭐ 两个顺序上的讲究：

1. **`newState` 在加锁之前**：编译要花时间（正则编译、CIDR 解析），
   放在锁里会让所有请求卡住 —— 而编译失败时**根本不需要动锁**；
2. **`Store` 是最后一步**：前面任何一步出错都不会留下半成品，
   读者永远不会看到「路由换了但鉴权器还是旧的」这种状态。

**启动期校验就是这条链的第一环**：本机实测（构造各类错配置，逐个调用 `Validate`）：

```text
=== ⑤ 配置优先级与启动期校验 ===

② 启动期校验：把能想到的错配置各造一个
  ListenAddr 为空              → 拒绝: ListenAddr 为空
  没有任何路由                  → 拒绝: 没有任何路由
  路由缺少 Name                 → 拒绝: 第 1 条路由缺少 Name（它会进日志与指标）
  路由名重复                    → 拒绝: 路由名重复: public-health
  PathType 非法                → 拒绝: 路由 public-health 的 PathType="wildcard" 不合法（只能是 exact / prefix / regex）
  正则编译失败                  → 拒绝: 路由 public-health 的正则 "^/api/([0-9+$" 编译失败: error parsing regexp: missing closing ]: `[0-9+$`
  上游服务不存在                 → 拒绝: 路由 public-health 引用了不存在的上游服务 "no-such-svc"
  Limit.Burst 为 0 但有速率      → 拒绝: 路由 public-health 配了 RatePerSec 但 Burst=0：桶容量为 0 会拒绝所有请求

③ 默认配置本身应当通过校验
  ✅ Default().Validate() = nil
```

⭐ **每一条都有存在的理由**，而且都能对应一种真实的线上事故：

| 校验项 | 不校验的后果 |
|---|---|
| `ListenAddr` 为空 | 起来就崩，或者监听在意外地址上 |
| 路由名重复 | 指标与日志里两条规则混成一条，排障时无法区分 |
| `PathType` 非法 | 静默当成默认类型（例如当成前缀匹配），**命中范围悄悄变大** |
| 正则编译失败 | 运行到该规则时才 panic / 500 |
| 上游服务不存在 | 请求走到这里才发现 502，而配置阶段就能拦住 |
| `Burst=0` 但有速率 | 桶容量为 0 → **拒绝所有请求**（看着像「配了限流」，实际是全拒） |

> ⚠️ **`Burst=0` 这条特别值得注意**：它是一个「零值恰好是合法值但语义危险」的例子。
> 类似地，熔断的 `FailRatio=0`（失败率阈值 0 → 一次失败就跳闸）、
> 摘除的 `Cooldown=0`（摘除瞬间立即失效）都属于同一类 ——
> **零值不是「不启用」，而是「启用了但用最激进的参数」**。
> 这类字段要么给非零默认值，要么在校验里显式拒绝。

## 五、为什么是「原地替换」而不是新建一个网关实例？

**本节要点**：新建实例看起来很干净，但会**丢掉不该丢的东西**。

```text
✅ 原地替换（本项目）：只换 g.st 快照，其它字段（连接池 / 限流桶 / 指标 / 日志）继续用同一份
❌ 新建实例：g2 := New(cfg2); 然后切换引用
      → gRPC 连接池重建 = 所有已建连接泄漏（除非显式 Close 旧实例）
      → 限流桶重建 = 限流额度被重置（「重载即可重置配额」会变成漏洞）
      → 指标重置 = 计数归零，监控曲线断裂
```

⭐ 判据：**问「这个字段是配置的产物，还是运行时的累积」**。

- 配置的产物（路由表、可信网段、验签器）→ 放快照里，重载时整体替换；
- 运行时的累积（连接池、限流桶、指标、日志缓冲）→ 留在 `Gateway` 上，重载时**不动**。

⚠️ 如果确实要新建实例，那**必须**先把旧实例 `Close()`，否则连接池泄漏 ——
本项目在注释里专门标注了这一点，因为这是一个「改成整体替换时才会暴露」的陷阱。

## 六、变更怎么被发现：轮询、监听，还是显式触发？

| 机制 | 延迟 | 复杂度 | 适合 |
|---|---|---|---|
| **文件 mtime 轮询**（本项目，3s） | ≤3s | 极低（一个 ticker + `os.Stat`） | 单机 / 少量实例 |
| 文件监听（`fsnotify`） | 毫秒 | 中（跨平台差异、编辑器原子写要处理） | 单机、需要快反应 |
| **显式 HTTP 触发**（`POST /reload`） | 即时 | 低，但要给接口加鉴权 | 运维手动触发 |
| **配置中心 watch**（Nacos / etcd） | 毫秒 | 高（引入客户端依赖与长连接） | 多实例、需要统一推送 |

⭐ **轮询是性价比最高的起点**：3 秒的延迟对绝大多数配置变更都够用，
而它的实现成本几乎为零（一个 `time.Ticker` + 比对 mtime），并且**天然支持「配置在别的机器上」**。

⚠️ 但轮询有一个必须处理的问题：**编辑器保存文件不是原子的**。
不少编辑器（尤其是 Windows 上的）会「先截断再写入」，
轮询正好落在中间那一刻就会读到**空文件或半个文件** ——
所以**必须写成「临时文件 + rename」**（rename 在同一文件系统上是原子的），
或者让加载器容忍「解析失败时保持旧配置」（本项目就是后者 + 校验兜底）。

## 七、配置校验：怎么把错误配置挡在启动之前？

**本节要点**：第四节讲「重载失败要保住旧快照」，那**什么算失败**？答案就是启动期这套自检 ——
它的目标只有一个：让错误配置**启动即失败**，而不是等某个请求打进来才 500。

### 7.1 为什么非做不可：三个真实例子

| 配置错误 | 不做校验时的表现 | 为什么难发现 |
|---|---|---|
| 路由的 `Upstream` 写错服务名 | 找到路由、进了流水线，取上游时才发现 → 请求 500 `bad_config` | 要**真有请求打到这条路由**才暴露 |
| `Breaker.MinRequests(8) > WindowSize(5)` | 熔断器**永远打不开** | 不报错、不 panic，功能静默失效 |
| 路由声明了 `Transcode`，但上游节点没标 `GRPC: true` | 一直连到 HTTP 端口上 | 要等第一次转码失败才看得见，且会伪装成「上游不稳定」 |

⭐ 三者共同点：**都是「运行期才暴露、而且暴露得不明显」**。第三类尤其阴 ——
现象指向网络，真正的错误却躺在启动时那份配置里。
而检查成本只有**一次遍历**，收益是「上线前就知道」。

### 7.2 检查项分四类

本机实测（`go test ./internal/config/ -count=1 -v`）：**46 个用例全绿**，其中 `TestValidate` 下 **35 个子用例**。

**① 拓扑一致性**：引用的东西必须存在，且两处写法必须一致。

```text
路由缺少 Name / 路由名重复 / 匹配条件完全相同
上游服务不存在 / 服务没有节点 / 节点重复 / 节点地址不是 host:port
服务 Name 与 map key 不一致（缓存以 Name 为 key）
```

**② 组合约束**：⭐ 单看每个字段都合法，**组合起来才荒谬** —— 这一类最值得抄进自己的项目。

| 组合 | 报错文案（原样） |
|---|---|
| `MinRequests > WindowSize` | `Breaker.MinRequests(8) 大于 WindowSize(5)，熔断器永远不会打开` |
| 有速率但桶容量为 0 | `配了 RatePerSec 但 Burst=0：桶容量为 0 会拒绝所有请求` |
| 有摘除阈值但没冷却 | `配了 Ejection.FailThreshold 但 Cooldown<=0：节点被摘除后就再也回不来` |
| 有排队但没并发上限 | `Overload.MaxQueue=10 但没设 MaxInflight：不限制并发就谈不上排队` |

**③ 资源与超时**：这些数字配错，线上表现是「慢」而不是「错」，最难归因。

```text
服务 Timeout 必须 > 0（它是上游往返的唯一超时来源）
Retry.Attempts 不能过大（上限 5）：重试是流量放大器
Retry.PerTryTimeout < 10ms：几乎必然全部超时
配了 tls 但 scheme 不是 https / CA 文件读不到 / mTLS 只给证书没给私钥
```

**④ 书写错误**：能当场判定的语法问题。

```text
PathType 只能是 exact / prefix / regex；正则编译失败；前缀与 StripPrefix 必须以 / 开头
Limit / Timeout / Overload 参数不能为负
JSON 里拼错的字段名（DisallowUnknownFields）
```

### 7.3 两条边界判据

| 情况 | 处理 | 判据 |
|---|---|---|
| `Host` 为空 | **归一化成「任意」**，不报错 | 空 = 匹配任意 Host，这是**合法写法**，与路由匹配的语义一致 |
| 下划线开头的 key | 跳过（当注释用） | JSON 不能写注释，这是刻意留的补丁 |
| **拼错的字段名** | ⚠️ **必须报错** | 静默忽略 ＝「配置看起来生效了，其实没有」，正是不做校验时最难查的那类故障 |

⭐ 一句话记住这条界线：**「能确定它就是错的」报错，「只是另一种写法」归一化。**

### 7.4 和热重载的关系（两条必须遵守）

1. **重载必须复用同一个 `Validate`** —— 否则会出现「运行期能进来、启动期不允许」的配置，
   等于把上面四类检查在热重载这条路上整条短路；
2. **校验失败就保持旧快照**（第四节），并把错误原文写进日志 —— **绝不允许「部分生效」**。

## 使用：给网关配热重载

### 1) 配置来源的优先级

```text
环境变量  >  GW_CONFIG 指向的 JSON 文件（字段级合并）  >  内置默认值
```

本机实测（JSON 只写想改的字段）：

```text
Default(): ListenAddr=127.0.0.1:18080 AdminListenAddr=127.0.0.1:18081 路由=9 服务=6

① JSON 覆盖：只写想改的字段
  覆盖后: ListenAddr=127.0.0.1:28080 max_inflight=64 max_queue=8 路由=9（JSON 里没写 routes → 保持默认的 9 条，字段级合并）
```

⭐ 注意「字段级合并」而不是「整体替换」：
**JSON 里没写的字段沿用默认值**，写了的才覆盖。
这让配置文件可以只写「与默认不同的部分」，是运维最省事的形式。

### 2) 坏 JSON 必须报错，不能静默吞掉

```text
④ 坏 JSON 不该被静默吞掉
  OverlayJSON({"listen_addr": 123}) → 解析 JSON 配置失败（字段名拼错也会在这里报）:
      json: cannot unmarshal number into Go struct field fileConfig.listen_addr of type string
```

⚠️ **「字段名拼错也在这里报」这一点很重要**：
JSON 默认忽略未知字段，所以 `"listen_addr"` 拼成 `"listen_adr"` 的话，
反序列化会**静默成功**（那个字段保持默认值）—— 运维会以为改了配置但没生效。
本项目在解码时开启严格模式（未知字段报错），这也是为什么错误信息里能看到 `fileConfig.listen_addr`。

### 3) 三个必踩的坑

| 情况 | 现象 | 判定 |
|---|---|---|
| **重载把熔断器一起重建** | 刚熔断的服务被重新放开 → 二次雪崩 | 熔断器**按名字复用**，绝不重建 |
| **代理缓存不清理** | 改了上游地址后内存只增不减 | 按新配置反推白名单清理；并把这个数字放进重载摘要 |
| **重载里做了耗时的事** | 重载瞬间所有请求卡住（锁竞争） | 编译放锁外，只有最后的切换在锁内 |

### 4) 重载之后要看什么

```text
routes=9 services=6 熔断器复用=6 均衡器重建=[slow-svc] 拓扑未变=[user-svc order-svc ...] 服务删除=[] 代理清理=0
```

| 字段 | 异常时的含义 |
|---|---|
| `熔断器复用` 数量 < 服务数 | 有熔断器被重建了 → 检查是否改成了整体替换 |
| `均衡器重建` 里出现不该变的服务 | 拓扑比较逻辑有问题（例如把 map 遍历顺序当成变化） |
| `代理清理` 持续增长 | 上游地址在反复变（或 key 构造里有不稳定成分） |

## 延伸追问

- **为什么用 `atomic.Value` 而不是 `sync.RWMutex` 包住配置？** →
  读多写极少（配置重载是分钟级甚至天级的动作），`RWMutex` 的读也要加锁开销；
  `atomic.Value` 的读是**无锁**的，代价是「同一时刻不同请求可能看到不同快照」——
  而这个不一致窗口只有一次 `Store` 的时间，对网关这种无状态处理完全可接受。
  反过来说：**如果处理请求需要读两次配置并期望它们一致，就要显式取一次快照变量再用**。
- **重载期间正在飞的请求怎么办？** → 它们已经拿到了旧快照的引用，
  会**整条走完**旧配置的逻辑。这不是 bug —— 强行让它们改道反而会造成请求语义撕裂
  （前半段按旧路由、后半段按新上游）。
- **配置里哪些字段改了必须重启？** → 监听地址、管理端口、共享状态服务地址这类
  「进程级绑定」的字段。它们不是快照的一部分，改它们等于换一个进程 ——
  所以配置文档里必须明确标出「改这些要重启」。
- **轮询 mtime 会不会漏掉变更？** → 会。如果两次轮询之间配置被改了又改回原样，
  mtime 也回到了原值（某些文件系统上），就会漏。
  更稳的做法是比较**内容哈希**而不是 mtime，代价是每次轮询都要读一遍文件
  （对几 KB 的配置完全可以接受）。
- **多个实例热重载会不会有时间差？** → 会，而且**无法避免**（除非用配置中心推送）。
  所以热重载的正确心态是「**最终一致**」：不要设计出「A 实例先加载完、B 还没加载时就要保证跨实例不变量」的依赖。
- **为什么不干脆上配置中心？** →
  配置中心解决的是「多实例分发 + 版本管理 + 权限」，
  而热重载解决的是「**拿到新配置后怎么安全地换掉旧的**」。后者任何方案都要做，
  前者可以后加 —— 本项目先把后者做对，前者的接入点在 `config.Load()` 一处。
