# Java 本目录导读

> 本目录收 **Java 语言的机制与实现**：运行时 12 篇（JVM 怎么装类、怎么排内存、怎么编译与回收）、
> 并发编程 13 篇（线程、内存模型、锁、工具、异步与诊断）、基础容器、框架（Spring Boot）以及接入类手册。
>
> ⚠️ **这里不重复 [目录.md](../../目录.md) 的知识点描述** —— 那篇按技术栈列「有什么」，
> 本篇只回答「**从哪读、按什么顺序、谁是谁的前置**」。按「Java 这条线」系统过一遍时从这里进。
>
> **实测坐标**：`运行时/` 与 `并发编程/` 各有一条主线，各自的容器、JDK 版本与未实测清单在其目录总纲第五节各维护一份 ——
> 见 [运行时/README.md](运行时/README.md) 与 [并发编程/README.md](并发编程/README.md)；每篇篇首再各自写明「哪些真跑、哪些未实测」。

## 一、先读哪几篇

| 先读 | 为什么是它 |
|---|---|
| [类文件与字节码.md](运行时/类文件与字节码.md) | 整条运行时线的**输入侧**：`.class` 的十段结构、常量池、栈式字节码。后面类加载「装的是什么」、JIT「编的是什么」、诊断工具「打印的是什么」，都以它为底 |
| [线程基础与生命周期.md](并发编程/线程基础与生命周期.md) | 整条并发线的**起点**：六格状态、`interrupt` 的八种落点、`join` 的本质、一个线程的栈与内存账。分不清 `BLOCKED` 与 `WAITING`，后面所有结论都只能背 |
| [垃圾回收原理与收集器.md](运行时/垃圾回收原理与收集器.md) | JVM 的 GC 是什么类型：堆怎么分代、对象什么时候进老年代、收集器怎么演进、G1 为什么切 region、ZGC 凭什么亚毫秒。**不读它，后面所有「为什么会有这个问题」都缺一个解释框架** |
| [锁与AQS.md](并发编程/锁与AQS.md) | 并发的地基。`synchronized` 的对象头、`ReentrantLock` 的四条能力差、AQS「一个 `state` 四种语义」—— 线程池、并发容器、`CompletableFuture` 的默认池全部建立在这套机制上 |

⭐ 这四篇也是**与 Go 对照反差最大**的四篇：Go 用 goroutine + channel（CSP），Java 用线程 + 锁（共享内存）。
如果你是从 Go 过来看 Java，「线程基础」「锁与AQS」「并发容器」三篇的「读它理由」最足。

## 二、两条主线（各按依赖顺序读）

**本节要点**：`运行时/` 12 篇与 `并发编程/` 13 篇各自有一条主线，**两线的分工表、逐篇读序、篇间依赖与实测坐标已整体迁入各自的目录总纲** ——
[运行时/README.md](运行时/README.md) 与 [并发编程/README.md](并发编程/README.md)，同一张表只在那两处各维护一份，本节只留组级划分、入口判据与下面的横切明细表。

### 主线 A：运行时（12 篇，自下而上）

⭐ **逐篇位次、五组分工（输入与装载 / 内存布局 / 执行与控制 / 回收与调优 / 观测与现场）与篇间依赖见 [运行时/README.md](运行时/README.md) 第二至第四节**，本篇不再重复一份。

只给两个入口判据：**顺序不能倒** —— GC 回收的是「运行时数据区」里的东西，而数据区的前提是类已经被加载，所以从 [类文件与字节码.md](运行时/类文件与字节码.md) 起读；只做线上排查就从 [JFR与诊断工具.md](运行时/JFR与诊断工具.md) 进，但它给出的每个字段都来自前面那几组。旁支两篇（`Unsafe与内存布局.md`、`堆外内存与内存映射.md`）不吃主线位次，分别接在 ④ 与 ⑦ 之后插读。

三篇「被别的篇反复引用」的：[类加载机制.md](运行时/类加载机制.md)（双亲委派与 SPI，框架类问题都落在这）、[运行时数据区与栈帧.md](运行时/运行时数据区与栈帧.md)（`-Xss` / `StackOverflowError` 与线程池的内存账）、[线上问题排查.md](运行时/线上问题排查.md)（CPU 高与线程池打满的现场流程）—— 它们的位次、前置与同组分工在总纲第三、第四节。

### 主线 B：并发编程（13 篇，自原理到工具）

⭐ **逐篇位次、五组分工（地基 / 排队与不排队 / 池与容器 / 异步与并行 / 成本与缺陷）与篇间依赖见 [并发编程/README.md](并发编程/README.md) 第二至第四节**，本篇不再重复一份。

只给两个入口判据：[线程基础与生命周期.md](并发编程/线程基础与生命周期.md) 与 [锁与AQS.md](并发编程/锁与AQS.md) 是其余各篇的前提 —— 分不清 `BLOCKED` 与 `WAITING`、不知道 AQS 那一个 `state` 有四种语义，线程池与并发容器的结论就只能背；「让线程排队」与「拆掉共享点」是两条并行路线，同一个问题两边都能解，按冲突密度任选先后 —— 后一条就是 [原子类与无锁.md](并发编程/原子类与无锁.md)，`LongAdder` 分段与 ABA 版本号在那篇。

最后两篇收口：[线程与进程开销.md](并发编程/线程与进程开销.md) 给一条线程的真实成本（与 Go 侧 `协程与线程成本.md` 同批实验、绝对值不可直接比），[死锁与并发缺陷诊断.md](并发编程/死锁与并发缺陷诊断.md) 按现场症状检索；位次与前置在总纲第三、第四节。

再按 [README.md](../../02-计算机基础/算法/README.md) 第四节的口径判「独立成篇还是并入已有篇」。

## 六、四条反直觉提醒（读完容易忘的）

| 提醒 | 依据 |
|---|---|
| **`volatile` 不保证原子性** | `volatile int i; i++` 是「读-改-写」三步，4 线程各加 50 万次实测**丢约 2/3**（[锁与AQS.md](并发编程/锁与AQS.md) 3.2） |
| **公平锁的代价约 300 倍** | 非公平 23.9~24.3 ms vs 公平 7369~8926 ms。**默认用非公平**，`synchronized` 本身就是非公平（[锁与AQS.md](并发编程/锁与AQS.md) 3.3） |
| **`submit` 会静默吞掉异常** | `execute` 的异常打到 stderr 且线程死亡；`submit` 的异常被 `FutureTask` 收走，**只有 `get()` 才抛**（[线程池.md](并发编程/线程池.md) 第六节） |
| **回调不一定在你以为的线程里跑** | `thenApply` 在「完成它的那个线程」上跑；`thenApplyAsync` 才换线程，默认换到 `commonPool`（[CompletableFuture与异步编排.md](并发编程/CompletableFuture与异步编排.md)） |
