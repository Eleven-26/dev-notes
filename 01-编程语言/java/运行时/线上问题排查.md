# 线上问题排查

> 覆盖：Java 服务线上排查的两条主线——用 `top -Hp` → 转十六进制 → `jstack` 把「哪个线程吃 CPU」和「它在跑什么」对上，以及用 Arthas 把这套手工流程自动化；另附线程栈里的死锁 / 阻塞判读。
> 不覆盖：GC 日志、`jstat` / `jcmd` / `jmap` / `jinfo` 的现场诊断见 [JVM与垃圾回收.md](JVM与垃圾回收.md) 的使用一节；JVM 内存结构与栈帧见 [运行时数据区与栈帧.md](运行时数据区与栈帧.md)；Linux 侧的资源指标与四步下钻见 [性能排查.md](../../../02-计算机基础/linux/性能排查.md)。
>
> 内容整理自个人学习笔记。⚠️ 本篇的命令均**未在本机实测**（需要一个在跑的 Java 服务与 JDK 工具链），列出的是通用语义与易踩点；`jstack` 的 `nid` 是十六进制这一点在 JDK 各版本一致。

## 一、CPU 飙高怎么定位到代码行？

**本节要点**：Linux 侧只做一件事——**把「哪个线程吃 CPU」和「这个线程在跑什么代码」对上**。卡点几乎总是同一处：`top -Hp` 给的是**十进制** TID，而 `jstack` 里的 `nid` 是**十六进制**，不转换永远 grep 不到。

```bash
jps -l                     # ① 找 Java 进程（也可用 top）
top -Hp 12345              # ② 找线程，假设最耗 CPU 的 TID = 12350（十进制）
printf '%x\n' 12350        # ③ ⚠️ 转十六进制 → 303e（最容易忘的一步）
jstack -l 12345 > /tmp/stack.txt
grep -A 30 -i 'nid=0x303e' /tmp/stack.txt    # ④ 栈里 nid 是十六进制
```

⚠️ **建议连抓 3 次栈**，同一线程 3 次都停在同一行，才是真凶（一次抓栈可能抓到「刚好在跑」的假象）：

```bash
for i in 1 2 3; do jstack 12345 > s$i.txt; sleep 2; done
```

| 步骤 | 命令 | 关键点 |
|---|---|---|
| ① 找进程 | `jps -l` / `top` | `jps` 只列 JVM 进程，`-l` 带主类 |
| ② 找线程 | `top -Hp <pid>` | `-H` 展开线程，看 `%CPU` 列 |
| ③ 转换 | `printf '%x\n' <tid>` | ⭐ 十进制 → 十六进制，最易漏 |
| ④ 抓栈比对 | `jstack <pid>` + `grep nid=0x…` | 连抓 3 次确认，别只看一次 |

## 二、线程栈里怎么看死锁与阻塞？

**本节要点**：`jstack` 能自动发现 Java 级死锁；大量 `BLOCKED` 指向锁竞争，要靠 `waiting to lock <0x…>` 的地址找到**持锁线程**；大量 `WAITING (on object monitor)` 扎堆在线程池，说明池被打满、下游变慢。

```bash
jstack 12345 | grep -A 5 'deadlock'        # 死锁检测（jstack 会自动打印 Found one Java-level deadlock）
jstack 12345 | grep 'Thread.State' | sort | uniq -c | sort -rn             # 线程状态分布
jstat -gcutil 12345 1000                   # 每秒看 GC：YGC/YGCT/FGC/FGCT/O 区占比
jmap -histo:live 12345 | head -30          # ⭐ 对象数量与占用（-histo 不触发 Full GC 可用；:live 会触发）
```

| 现象 | 说明 |
|---|---|
| `FGC` 频繁且 `FGCT` 大 | 老年代放不下 → 内存泄漏或堆太小 |
| 大量 `BLOCKED` | 锁竞争；看 `waiting to lock <0x...>` 的地址找持锁线程 |
| 大量 `WAITING (on object monitor)` 在线程池 | 线程池打满，下游慢 |

⚠️ 内存与 GC 的进一步判读（`jstat -gc` / `jcmd GC.heap_info` / `jmap -histo` 的读数与坑）见 [JVM与垃圾回收.md](JVM与垃圾回收.md) 的使用一节。

## 三、Arthas：把上面两节的手工流程自动化

**本节要点**：Arthas 是线上无侵入诊断工具，`thread -n` 本质就是自动化了第一节「转十六进制 + grep 栈」的全过程；`trace` 能把一个方法内部的逐层耗时打出来。

```bash
curl -O https://arthas.aliyun.com/arthas-boot.jar && java -jar arthas-boot.jar
```

| 命令 | 作用 |
|---|---|
| `dashboard` | ⭐ 一屏看线程、内存、GC、Runtime |
| `thread -n 3` | ⭐ **CPU 占用最高的 3 个线程及栈**（省掉手工转十六进制） |
| `thread -b` | 一键找出**阻塞其他线程的那个线程**（死锁 / 锁竞争） |
| `trace <class> <method>` | ⭐ 方法内部逐层耗时，定位慢在哪一行 |
| `watch <class> <method> '{params, returnObj}'` | 观察入参与返回值 |
| `heapdump /tmp/h.hprof` | 导出堆快照 |

⚠️ Arthas 需要 attach 到目标 JVM：连不上通常是**目标 JDK 版本与 Arthas 不匹配**，或容器里没装可用 JDK；生产环境还需评估它对应用的影响。

## 延伸追问

- **为什么 `jstack` 里 grep 十进制 TID 查不到？** → `nid` 一律是十六进制；`top -Hp` 与 `/proc/<pid>/task` 给的是十进制，必须先 `printf '%x'`（第一节）。
- **一次抓栈为什么不够？** → 线程可能只是「刚好在跑」某个热点方法；连抓 3 次都停在同一行才是真凶（第一节）。
- **`BLOCKED` 和 `WAITING` 有什么不同？** → `BLOCKED` 是等**内置锁**（`synchronized`）；`WAITING` 是调了 `wait()` / `join()` / `park()` 主动挂起——前者查锁竞争，后者查等待链条（第二节）。
- **`jmap -dump` 能随便打吗？** → 不能，它会 **STW**；生产环境用 `-histo`（不触发 Full GC）先看概览，确需快照再评估停顿时长。
- **Java 21 的虚拟线程给排查带来什么变化？** → 虚拟线程栈不在 `jstack` 的常规输出里，要用 `jcmd <pid> Thread.dump_to_file` 看结构化的线程转储。
