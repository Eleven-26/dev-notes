## 一、`ArrayList` 与 `LinkedList` 该怎么选？

**本节要点**：`LinkedList` 只在**一个**场景下值得用 —— 头部/中间的高频插入。只要涉及**下标访问**，它必然惨败。

### 1.1 五组对照（一次跑完）

同一个 `LinkedList`，在五种操作下的表现完全不同（`ListLab.java`，N = 20 万；耗时取 3 轮最小值）：

| 操作 | `ArrayList` | `LinkedList` | 倍数 | 谁赢 |
|---|---|---|---|---|
| 尾部 `add` | 3.2 ~ 4.0 ms | 4.3 ~ 4.7 ms | 1.1 ~ 1.4× | ArrayList 略快 |
| **头部 `add(0, i)`** | 2507 ~ 3065 ms | 2.6 ~ 3.5 ms | **747 ~ 1110×** | **LinkedList 大胜** |
| **按下标 `get(i)`** ×5 万 | 1.9 ~ 2.8 ms | 1869 ~ 2567 ms | **685 ~ 1500×** | **ArrayList 大胜** |
| 顺序遍历（20 万） | 2.7 ~ 3.8 ms | 1.9 ~ 3.0 ms | 0.7 ~ 0.9× | 无差别 |
| 顺序遍历（200 万） | 6.3 ~ 7.7 ms | 16.6 ~ 17.1 ms | 2.2 ~ 2.6× | ArrayList |

### 1.2 逐条读这张表

**① 尾部 `add` 两者都是 O(1)，`LinkedList` 只是略慢。** 它多做的事是「为每个元素 `new` 一个 `Node` 对象」。**注意结论只到这里** —— 实测差 1.1~1.4 倍，没有数量级差距。不要夸大成「LinkedList 插入慢」。

**② 头部 `add` 是 `LinkedList` 唯一大胜的场景（快 747~1110 倍）。** 因为 `ArrayList.add(0, x)` 每次都要 `System.arraycopy` **搬动全部已有元素**（O(n)），20 万次下来就是 O(n²)；`LinkedList` 只改两个指针（O(1)）。

**③ 按下标 `get(i)` 是 `LinkedList` 的死穴（慢 685~1500 倍）。** 它没有数组下标，`get(i)` 必须**从表头一步步走 i 步**（JDK 8 做了优化：`i` 在后半段就从表尾走，但仍是 O(n)）。

⭐ **判据**：`LinkedList` 的可用场景极窄 —— **「只在头部/中间频繁插入删除，且几乎不按下标访问」**。而在真实业务里，「按 key 查找」用 `Map`、「按条件过滤」用 `Stream`、「顺序处理」用数组——**留给 `LinkedList` 的位置基本只剩下「当栈或队列用」**，而那个场景还有更好的选择（见 1.4）。

**④ 顺序遍历：本机测出了「规模效应」。** 20 万时两者没差别（`LinkedList` 甚至略快 0.7~0.9×），200 万时才拉出 2.2~2.6× 的差距。

⚠️ **这一条要谨慎表述**：理论上 `LinkedList` 的节点分散在堆上、缓存不友好，遍历应该慢。实测在小规模下**没测出来** —— 大概率是因为顺序遍历时 `Node` 按分配顺序排列、堆地址基本连续，预取器照样能命中；规模超过缓存容量后劣势才显现。**所以「`LinkedList` 遍历一定慢」是有条件成立的，别当绝对结论写死。**

### 1.3 内存账：`LinkedList` 不是省内存，而是**多花一个数量级**

| | 结构 | 10 万元素的粗略占用 |
|---|---|---|
| `ArrayList` | 1 个数组对象 + 容量个引用 | 16（对象头）+ 8 + 100000 × 4（压缩指针）≈ **400 KB** |
| `LinkedList` | 100000 个 `Node` 对象 | 每个 = 16（对象头）+ 8（prev）+ 8（next）+ 4（引用，压缩）+ 4（填充）= 40 字节 → **≈ 4 MB** |

⭐ 而且 `LinkedList` 的元素分散在堆上，**GC 扫描时也要逐个追踪**，代价比 `ArrayList` 高得多。

⚠️ 顺带纠正一个常见误解：**「`LinkedList` 省内存」是错的**。它省的是「不需要连续内存」，但**对象头与两个指针的开销远大于数组**。

### 1.4 那该用什么替代

| 需求 | 更好的选择 |
|---|---|
| 当队列（FIFO） | `ArrayDeque` —— 循环数组，比 `LinkedList` 快且省内存 |
| 当栈（LIFO） | `ArrayDeque`（`push` / `pop`）或直接用数组 |
| 头部频繁插入 | 如果只是要「倒序」，插入完 `add` 再 `Collections.reverse()` 更划算 |
| 要按下标访问 | `ArrayList`（没有第二个选项） |

⭐ **一句话记法：JDK 官方文档自己就建议「需要栈/队列时用 `ArrayDeque`，不要用 `LinkedList`」。** `LinkedList` 保留它主要是历史原因（它同时实现了 `List` 和 `Deque`）。

## 二、`ArrayList` 的扩容机制

**本节要点**：三个数字 —— **懒初始化、默认 10、1.5 倍**。全都是反射读出来的真实值。

### 2.1 实测扩容轨迹

```text
== 实验 1：ArrayList 的扩容轨迹（反射读 elementData.length）==
  new ArrayList<>()         容量 = 0（注意：不是 10，而是空数组——懒初始化，第一次 add 才给 10）
  容量变化：10 → 15(第11个) → 22(第16个) → 33(第23个) → 49(第34个) → 73(第50个) → 109(第74个) → 163(第110个) → 244(第164个) → 366(第245个) → 549(第367个)
  new ArrayList<>(200000) 的初始容量 = 200000
```

- **`new ArrayList<>()` 时容量是 0，不是 10。** 内部存的是 `DEFAULTCAPACITY_EMPTY_ELEMENTDATA`（**共享的空数组**），第一次 `add` 才真正分配 10。这是为了**避免大量空列表各占一个数组**。
- **扩容公式是 `oldCap + (oldCap >> 1)`**：10 → 15 → 22 → 33 → 49 → 73 → 109 → 163 → 244 → 366 → 549。**恰好 1.5 倍（向下取整）**。
- ⚠️ 每次扩容都要 `Arrays.copyOf` 复制整个数组。**已知规模时用 `new ArrayList<>(expectedSize)` 预分配**（实测 `new ArrayList<>(200000)` 的初始容量直接就是 200000，一次扩容都不用）。

### 2.2 为什么是 1.5 倍而不是 2 倍

| 倍数 | 代价 |
|---|---|
| 太小（如 1.1×） | 扩容次数多，每次都要 O(n) 复制 |
| **1.5×** | 空间利用率与复制次数之间的折中；且**旧数组的空间有机会被后续分配复用** |
| 2× | 复制次数少，但**峰值内存**要能容纳「旧 + 新」两份；且理想情况下总有一半空间浪费 |

⭐ 与 `HashMap` 的 2 倍扩容形成有趣对照（见 3.2）：`ArrayList` 不需要「容量是 2 的幂」这个约束，所以可以取 1.5；而 `HashMap` 因为要用 `(n-1) & hash` 定位，**必须**是 2 的幂。

## 三、`HashMap` 的底层结构

**本节要点**：JDK 8 的 `HashMap` = **数组 + 链表 + 红黑树**。要能答出「数组什么时候分配」「容量怎么涨」「什么条件才树化」。

### 3.1 结构

```text
Node<K,V>[] table      ← 桶数组，每个桶是一条链表（或一棵红黑树）
  ├── 桶为空        → 直接放一个新 Node
  ├── 桶是链表      → 遍历，key 相同则覆盖；否则尾插；长度超标可能树化
  └── 桶是红黑树    → 按 hash 与 key 比较后插入/覆盖

Node { hash, key, value, next }       链表节点
TreeNode extends Node { parent, left, right, prev, red }   红黑树节点
```

### 3.2 容量与阈值（实测）

```text
== 实验 1：默认容量与阈值，以及第一次 put 才分配数组 ==
  new HashMap<>()      table = null，threshold = 0（数组是懒分配的，此时还没有 table）
  第 1 次 put 后        table.length = 16，threshold = 12（16 × 0.75 = 12，超过 12 才扩容）
```

```text
== 实验 2：一直 put，观察 table.length 的变化 ==
  16(第1个) → 32(第13个) → 64(第25个) → 128(第49个) → 256(第97个) → 512(第193个)
```

| 容量 | 阈值（容量 × 0.75） | 装到第几个触发扩容 |
|---|---|---|
| 16 | 12 | 第 13 个 |
| 32 | 24 | 第 25 个 |
| 64 | 48 | 第 49 个 |
| 128 | 96 | 第 97 个 |

⭐ **三个要点**：

1. **数组也是懒分配**（`new HashMap<>()` 时 `table == null`），第一次 `put` 才建 16 长度的数组 —— 与 `ArrayList` 同理；
2. **容量翻倍**（16 → 32 → 64 → 128），不是 1.5 倍；
3. **触发条件是「元素数 > 容量 × 负载因子」**，默认负载因子 0.75。

### 3.3 为什么容量必须是 2 的幂（实测）

定位桶用的是 `(n - 1) & hash`（n 为容量）：

```text
== 实验 3：定位桶用的是 (n-1) & hash，n 为 2 的幂时等价于取模 ==
  n=16  hash=17     (n-1)&hash = 1    hash%n = 1    一致=true
  n=16  hash=33     (n-1)&hash = 1    hash%n = 1    一致=true
  n=16  hash=100    (n-1)&hash = 4    hash%n = 4    一致=true
  n=16  hash=1000   (n-1)&hash = 8    hash%n = 8    一致=true
```

两层理由：

1. **`(n-1) & hash` 与 `hash % n` 结果完全相同，但位运算比取模快得多**（取模要走除法指令）；
2. **扩容时元素的新位置只取决于一个 bit**：容量翻倍后 `(n-1)` 只多了一个高位 `1`，所以元素要么**留在原位**、要么移到「原位 + 旧容量」。JDK 8 的 `resize()` 就是靠 `(e.hash & oldCap) == 0` 一次判断完成拆分 —— **完全不需要重新计算 hash**。

⚠️ 如果容量不是 2 的幂，第 2 条就不成立（扩容要重算全部元素），第 1 条也会出现「某些桶永远用不到」的分布不均。

### 3.4 hash 扰动在防什么（实测）

`HashMap` 会把 `hashCode` 再做一次扰动：`h ^ (h >>> 16)`。取一组「只有高位在变、低 16 位全是 0」的 hashCode：

```text
== 实验 4：hash 扰动（高低 16 位异或）到底在防什么 ==
  取一组「只有高位在变、低 16 位全是 0」的 hashCode（现实中很常见，如整倍数、浮点哈希）：
    hash=0x00010000   不扰动 → 桶 0  | 扰动后 → 桶 1
    hash=0x00020000   不扰动 → 桶 0  | 扰动后 → 桶 2
    hash=0x00030000   不扰动 → 桶 0  | 扰动后 → 桶 3
    hash=0x00040000   不扰动 → 桶 0  | 扰动后 → 桶 4
```

⭐ **一眼看懂**：容量只有 16 时，`(n-1) & hash` 只用了 hash 的**低 4 位**。如果一批 key 的 hashCode 只在高位有差异（低位是 0 或固定），**不扰动就会全部撞进同一个桶**（全落桶 0）；扰动函数把高 16 位折下来混进低位，4 个 key 立刻分散到 4 个桶。

**这就是扰动函数存在的唯一理由：让高位也参与定位。** 它是「用一个异或代替一次完整散列」的廉价补偿。

### 3.5 树化的两个条件（实测精确触发点）

**常见说法「链表长度到 8 就转红黑树」不完整。** 实测逐个插入 hashCode 全相同的 key：

```text
  连续插入 hashCode 全相同的 key，逐个记录容量与桶内节点类型：
    第  1 个元素   容量=16   桶下标=10  节点类型=Node
    ...
    第  8 个元素   容量=16   桶下标=10  节点类型=Node
    第  9 个元素   容量=32   桶下标=10  节点类型=Node
    第 10 个元素   容量=64   桶下标=42  节点类型=Node
    第 11 个元素   容量=64   桶下标=42  节点类型=TreeNode
    第 12 个元素   容量=64   桶下标=42  节点类型=TreeNode
```

| 元素数 | 容量 | 桶下标 | 节点类型 |
|---|---|---|---|
| 1 ~ 8 | 16 | 10 | `Node`（链表） |
| 9 | 32 | 10 | `Node` |
| 10 | 64 | 42 | `Node` |
| **11** | 64 | 42 | **`TreeNode`** |

⭐ **树化需要两个条件同时满足**：

1. 链表长度超过 `TREEIFY_THRESHOLD`（8）；
2. 数组长度 ≥ `MIN_TREEIFY_CAPACITY`（**64**）。

⚠️ **容量不足 64 时不会树化，而是优先 `resize()` 扩容** —— 设计意图是「先试图靠扩容把冲突打散」，因为扩容比维护红黑树便宜。所以本机实测的树化点是**第 11 个冲突元素**（前两次触发树化检查时容量还不够，被转成了扩容：16 → 32 → 64）。

⚠️ 顺带注意**桶下标从 10 变成了 42**：因为容量从 16 涨到 64，`42 & 15 = 10`，而 `42 & 63 = 42`。同一个 key 在扩容后换了桶 —— 这正是 3.3 第 2 条说的「扩容只需判断一个 bit」。

### 3.6 `hashCode` 与 `equals` 的契约（实测）

```text
== 实验 6：只重写 hashCode、不重写 equals 会怎样 ==
  a 与 b 的 hashCode 相同（都是 7），内容相同，但 equals 用的是 Object 的引用比较 → 不相等
  put(a, "A") 再 put(b, "B") 后 size = 2（两个都被当成不同 key 存下来了）
  get(new HalfKey(7)) = null  ← 取不到
```

⭐ **key 必须同时正确重写 `hashCode` 与 `equals`**，否则会出现两类静默错误：

| 只重写 | 后果 |
|---|---|
| 只写 `hashCode`（本实验） | 内容相同的 key 被当成两个 → **同一逻辑 key 存了多份**，且 `get` 取不到 |
| 只写 `equals` | hash 不同 → **直接落到不同桶**，连冲突都不会发生，比上一种更隐蔽 |

**记忆口径**：`equals` 相等的两个对象，`hashCode` **必须**相等（反之不要求）。所以「重写一个就必须重写另一个」。

## 四、Map 家族的选型

**本节要点**：`HashMap` 是默认答案，另三个各有明确的专属场景。

| 实现 | 有序性 | 底层 | 适用 |
|---|---|---|---|
| **`HashMap`** | ❌ 无序 | 数组 + 链表 + 红黑树 | ✅ 默认选择，O(1) 查找 |
| `LinkedHashMap` | ✅ **插入序 / 访问序** | `HashMap` + 双向链表 | 需要「按放入顺序输出」；**访问序 + `removeEldestEntry` 就是现成的 LRU 缓存** |
| `TreeMap` | ✅ **按 key 排序** | 红黑树 | 需要范围查询（`subMap` / `headMap`）、按 key 排序遍历；代价 O(log n) |
| `EnumMap` | 按枚举声明序 | 数组 | key 是枚举时**最省内存最快**（内部就是一个数组，无哈希无链表） |
| `IdentityHashMap` | ❌ | 数组 | 按**引用相等**（`==`）比较 key，用于特殊场景（如序列化图遍历） |

⭐ 两个高价值细节：

1. **`LinkedHashMap` 的访问序就是 LRU**：构造时传 `accessOrder = true`，再重写 `removeEldestEntry` 返回 `size() > capacity` —— 十几行就是一个线程不安全但语义完整的 LRU 缓存。原理与 [缓存淘汰算法.md](../../03-数据与中间件/数据存储/缓存/缓存淘汰算法.md) 里讲的 LRU 完全一致（哈希表 + 双向链表）。
2. **`EnumMap` 是「key 是枚举」时的性能与内存双优解** —— 内部只是一个 `Object[]`，按枚举的 `ordinal()` 直接下标访问，连哈希都不算。⚠️ 但要注意 `ordinal()` 依赖枚举的声明顺序，**改动枚举顺序会让已落盘的数据错位**（所以别把 `ordinal()` 持久化）。

## 使用：一个「按用户统计」的场景，为什么最后选了 `HashMap` + `ArrayList`

本项目里**真实存在**的 Map/List 用法在 [服务发现的Java实现.md](../../04-架构与系统/分布式/服务治理/服务发现的Java实现.md) 与 [Java实现.md](../../04-架构与系统/系统设计/弹幕系统/Java实现.md)。拿「实例列表的本地缓存 + 按服务名分组」这条链路逐环节拆：

**第一步：先问「要不要按下标访问」。** 这条判断单独就能砍掉一半选项 —— 实例列表是**遍历**用的（轮询要按顺序走），**不按下标随机取**。所以直接排除 `LinkedList`（1.2 实测它的下标访问慢 685~1500 倍，而这里完全不需要下标）。

**第二步：选 `ArrayList` 还是 `ArrayDeque`？** 这里只需要「追加 + 顺序遍历」，不需要在头部插入，所以 `ArrayList` 就够（1.1 实测尾部 `add` 与遍历都不差）。`ArrayDeque` 的价值在「用作出队/入队」，这里用不上。

**第三步：Map 选哪个？** 真实代码里用的是 `AtomicReference<List<String>> snapshot` + `ConcurrentHashMap<String, Instant> firstSeen`：

- **`AtomicReference<List<...>>`**：解决的是**跨线程可见性**（推送线程更新、业务线程读取），不是并发读写 —— 这是 [JMM与内存屏障.md](并发/JMM与内存屏障.md) 讲的「安全发布」；
- **`ConcurrentHashMap<String, Instant>`**：key 是**服务名**（数量少、稳定、读多写少），用来记录「第一次见到某个实例的时间」。选它的理由是 2.1 那类操作需要原子性（`computeIfAbsent` 记录首次时间），而不是为了并发写吞吐。

**第四步：容量要不要预设？** 实例数量在启动时就大致知道（比如 50 个服务），所以可以 `new ArrayList<>(expectedSize)` 或 `new ConcurrentHashMap<>(expectedSize)` —— 对应 2.1 实测的「预分配直接省掉全部扩容」。

⭐ 归纳成一条可复用的判断顺序：

```text
① 要不要按下标访问？      要 → ArrayList；不要 → 继续
② 要不要在头部/中间插入？  要 → LinkedList（但先问问能不能换思路）
③ 要不要按 key 查找？      要 → Map（默认 HashMap）
④ 要不要排序 / 范围查询？   要 → TreeMap；要插入序 → LinkedHashMap
⑤ 要不要并发？            要 → 见 并发/并发容器.md（ChM / COW）
⑥ 规模已知吗？            已知 → 预分配容量（ArrayList / HashMap / StringBuilder 都同理）
```

## 延伸追问

- **`ArrayList` 的默认容量到底是 10 还是 0？** → **声明为 10，实际初始是 0**。`new ArrayList<>()` 存的是共享的空数组，第一次 `add` 时才分配 10。所以「默认容量 10」指的是「第一次扩容后的容量」，不是对象创建时的容量 —— 本机反射实测印证了这一点。
- **`LinkedList` 到底还有没有适用场景？** → 极窄。① 头部/中间高频插入（1.1 实测快 747~1110 倍）；② 需要同时当 `List` 和 `Deque` 用。**JDK 官方文档自己就建议用 `ArrayDeque` 替代它做栈和队列** —— 所以真实项目里它基本不该出现。
- **为什么 `ArrayList` 扩容 1.5 倍，`HashMap` 却是 2 倍？** → 约束不同。`HashMap` 需要容量是 2 的幂（3.3 的两条理由），只能按幂次翻倍；`ArrayList` 没有这个约束，1.5 倍是「复制次数」与「空间浪费」之间更划算的折中 —— 且旧数组释放后更容易被后续分配复用。
- **负载因子为什么是 0.75？** → 时间与空间的折中：太高（如 1.0）冲突多、查询退化；太低（如 0.5）数组大但一半空着。0.75 是在「泊松分布下冲突概率」与「空间利用率」之间算出来的经验值（JDK 源码注释里有对应的概率推导）。
- **树化的阈值为什么是 8？** → 源码注释给出了依据：在理想散列下，桶内节点数服从泊松分布，**长度达到 8 的概率约为 0.00000006**。也就是说正常情况下几乎不会树化 —— **一旦树化，说明 hashCode 实现有问题**（比如本机实验里把 hashCode 固定成 42）。这比「8 是经验值」这种说法准确得多。
- **`HashMap` 的 `put` 是头插还是尾插？** → **JDK 8 是尾插**（JDK 7 是头插）。JDK 7 的头插在并发扩容时会形成**环形链表**（并发的 `HashMap` 扩容是个经典事故），JDK 8 改成尾插后不再有环，但**并发写仍然会丢数据** —— 所以并发场景该用 `ConcurrentHashMap`，不是「JDK 8 的 HashMap 就安全了」。
- **`HashMap` 扩容时元素一定会重新分布吗？** → 不一定。JDK 8 用 `(e.hash & oldCap) == 0` 判断：为 0 的留在原下标，否则移到「原下标 + 旧容量」。所以**大部分元素其实没动**——这就是 3.3 第 2 条的工程价值。
- **`TreeMap` 与 `HashMap` 的性能差多少？** → `TreeMap` 是 O(log n)（红黑树），`HashMap` 是 O(1)（理想情况）。**只有在确实需要排序或范围查询时才用 `TreeMap`**；「只是想让输出有序」用 `LinkedHashMap`（插入序）或排一次序即可，不必付 O(log n) 的代价。
