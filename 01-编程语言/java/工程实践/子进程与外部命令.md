## 一、`ProcessBuilder` 默认不过 shell，为什么还会被注入？

**本节要点**：Java 的 `ProcessBuilder` 天生不过 shell，所以**「被注入」通常是你主动写 `sh -c` 造成的**；反过来说，`Runtime.exec("a | b")` 这种写法连管道都不支持，想要管道只能自己拼 shell——那就回到注入问题上。

```java
// 反例：主动套一层 bash，输入里的 "; touch pwned" 就会被当成命令执行
new ProcessBuilder("bash", "-c", "grep ERROR " + userInput);

// 正例：命令与参数分开，ProcessBuilder 不起 shell，特殊字符只是普通字符
new ProcessBuilder("grep", "ERROR", userInput);
```

实测（两边各自建临时目录，跑完看有没有多出文件）：

| 写法 | `pwned` 文件被创建 |
|---|---|
| 反例（拼进 `bash -c`） | **true** ← 注入成功 |
| 正例（参数分开传） | **false** |

**跑法**（不用另装 JDK，IDEA 自带的 JBR 里有 javac）：

```bash
JBR="<IDEA 安装目录>/jbr/bin"    # IDEA 自带的 JBR 17，路径按自己的安装位置替换
"$JBR/javac.exe" -Xlint:all -encoding UTF-8 -d out CmdMeasure.java
"$JBR/java.exe" -Dstdout.encoding=UTF-8 -cp out CmdMeasure
```

## 二、超时：`waitFor(timeout)` 为什么会慢 17 倍？

**本节要点**：「设了超时」≠「按时返回」。卡点都在「孙子进程活着 + 管道没断」——`Process.waitFor(long, TimeUnit)` 只能等**直接子进程**，所以必须自己处理进程树。

```java
// ⚠️ 第一版的写法：先读干输出，再 waitFor(300ms)
String out = new String(p.getInputStream().readAllBytes(), UTF_8); // ← 时间花在这
boolean finished = p.waitFor(300, MILLISECONDS);                    // ← 到这里早就不止 300ms

// 正解：另起看门狗线程到点就杀，而且**先杀子孙再杀自己**
Thread watchdog = new Thread(() -> {
	try {
		if (!p.waitFor(timeoutMs, TimeUnit.MILLISECONDS)) {
			p.descendants().forEach(ProcessHandle::destroyForcibly); // ★ 关键
			p.destroyForcibly();
		}
	} catch (InterruptedException e) {
		Thread.currentThread().interrupt();
	}
});
watchdog.setDaemon(true);
watchdog.start();
```

| 写法 | 给 300 ms 超时，`bash -c "sleep 5"` 实测 |
|---|---|
| 只 `waitFor(300)` | **5083 ~ 5088 ms**，而且 `finished=true`（**误判成「没超时」**） |
| 看门狗 + 只杀父进程 | 仍然 ~5 s（孙子 `sleep` 还握着管道，读不到 EOF） |
| 看门狗 + **先杀 descendants** | **362 ms** ✅ |

→ 和 Go 侧同一个结论（Go：300ms → 5.08s → 加 `WaitDelay` 800ms）：**「设了超时」≠「按时返回」**，卡点都在「孙子进程活着 + 管道没断」。

## 三、退出码语义

**本节要点**：与 Go 侧完全一致——**必须先读干输出再等它结束**，否则子进程写满管道缓冲区（几 KB）就卡死，这是 Java 里最常见的 `waitFor()` 挂死原因。

```java
record RunResult(String out, long costMs, int code, boolean timedOut) {}
// code 只在进程真的退出时才有意义；被看门狗杀掉时给 -1
```

| 场景 | 实测 |
|---|---|
| `grep` 没搜到 | 退出码 **1**（不是异常，`exitValue()` 正常返回） |
| `grep` 文件不存在 | 退出码 **2** |
| 超时被杀 | `timedOut=true`，`code=1`（⚠️ Windows 上被 kill 的码不是 128+n） |

⚠️ 需要合并 stdout / stderr 时显式 `pb.redirectErrorStream(true)`。

## 四、词频统计：为什么对拍要挪到 Go 侧做？

**本节要点**：纯 Java 复刻很快（19~27 ms），但**从 JVM 起一条真 bash 管道却慢到不可用**（一次 114 s 且结果不完整，另几次直接卡死）——**「用代码调 shell 管道」这条路，连性能都要看宿主语言与环境的组合**。

```java
static Map<String, Integer> countJava(Path log, List<String> words) throws IOException {
	List<String> quoted = new ArrayList<>();
	for (String w : words) {
		quoted.add(Pattern.quote(w)); // ★ 关键词不能当正则用：. * [ 都是元字符
	}
	Pattern re = Pattern.compile(String.join("|", quoted));
	Map<String, Integer> times = new LinkedHashMap<>();
	try (BufferedReader br = Files.newBufferedReader(log, UTF_8)) {
		String line;
		while ((line = br.readLine()) != null) {
			Matcher m = re.matcher(line);
			while (m.find()) {                       // ① 等价 grep -o
				times.merge(m.group(), 1, Integer::sum); // ②③ 等价 sort | uniq -c
			}
		}
	}
	List<Map.Entry<String, Integer>> entries = new ArrayList<>(times.entrySet());
	entries.sort(Comparator.<Map.Entry<String, Integer>>comparingInt(Map.Entry::getValue)
		.reversed().thenComparing(Map.Entry::getKey)); // ④ 等价 sort -rn，次数相同给确定顺序
	Map<String, Integer> out = new LinkedHashMap<>();
	for (Map.Entry<String, Integer> e : entries) {
		out.put(e.getKey(), e.getValue());
	}
	return out;
}
```

实测（同一份 920 行日志：INFO 300 / ERROR 500 / WARNING 120）：

| 项 | 结果 |
|---|---|
| 纯 Java 复刻耗时 | **19 ~ 27 ms** |
| Java 侧顺序 | `{ERROR=500, INFO=300, WARNING=120}` ← 与 Go 侧一致 |
| ⚠️ 从 JVM 起真 bash 管道做对拍 | **一次 114152 ms 且结果不完整，另几次直接卡死到 300s 超时被杀** |

★ 最后那行不是「忘了测」，而是**本篇最值得记住的一条**：同一条命令在 Go 里稳定 115~184 ms，从 JVM 起却慢到不可用（Windows + Git bash 的组合问题）。**所以能在语言里做，就别起进程**；对拍因此改到 Go 侧做（那边逐项一致）。

关键词有包含关系时，Java 与 Go 同一个坑（都是**左起优先**，与 `grep -E` 的**最长匹配**不同）：

| 输入 100 行 `WARNING`，统计 `WARN\|WARNING` | 实测 |
|---|---|
| Java，`WARN` 在前 | `{WARN=100}` ← 和 `grep -E` 不一样 |
| Java，`WARNING` 在前 | `{WARNING=100}` |

→ 修法一样：**长词排前面**。

## 五、端口占用与 `mkdir -p`

**本节要点**：同样是「不要解析 `netstat` 输出」——`new ServerSocket(port)` 抛 `BindException` 就是「被占用」的确定答案；`Files.createDirectories` 等价 `mkdir -p`，同样幂等。

```java
try (ServerSocket ss = new ServerSocket(0)) {   // 0 = 让内核分配空闲端口
	int port = ss.getLocalPort();
	ServerSocket again = null;
	try {
		again = new ServerSocket(port);          // 同一个端口再 bind
	} catch (IOException e) {                    // ★ BindException 就是"被占用"的答案
		System.out.printf("再 bind 同一端口 → %s%n", e.getClass().getSimpleName());
	} finally {
		if (again != null) again.close();
	}
}
Files.createDirectories(dir.resolve("a/b/c"));   // 等价 mkdir -p，幂等
Files.createDirectories(dir.resolve("a/b/c"));   // 第二次：不报错
```

实测：

| 断言 | 结果 |
|---|---|
| `new ServerSocket(0)` 拿空闲端口 | ✅ 拿到 52828 |
| 同一端口再 bind | ✅ **`BindException`**（和 Go 的 `net.Listen` 失败同一条路） |
| `new Socket("127.0.0.1", port)` 判连通 | ✅ true |
| `Files.createDirectories` 连建两次 | ✅ 不报错，目录存在 = true（幂等，等价 `mkdir -p`） |

⚠️ Java 侧同样**不要去解析 `netstat` 输出**；要「哪个进程占了端口」用 `ProcessHandle.allProcesses()` 只能列本机 JVM 看得见的进程，真要知道端口归属还是得 `ss -ltnp`（那是运维动作，不是代码动作）。

## 六、流式读（`tail -f` 场景）

**本节要点**：实测 `bash -c "echo 1; sleep 1; echo 2"`，逐行读时**第 1 行在 59 ms 到达**（命令总共约 1 s），与 Go 侧 `Stream` 的 40~50 ms 同一结论。

Java 里对应的写法就是 `p.getInputStream()` 上套 `BufferedReader` 循环 `readLine()`。⚠️ 两个必踩点：

1. **不读就 `waitFor()`** → 管道缓冲区满，子进程写不出去，两边互等成死锁；
2. **`readAllBytes()`** 会把整份日志吃进内存，`tail -f` 那种永不结束的流直接把堆撑爆。

## 七、Go ↔ Java ↔ 命令 三方对照

| 目标 | 命令行 | Go | Java |
|---|---|---|---|
| 跑一条命令 | `grep ERROR app.log` | `exec.Command("grep","ERROR",f)` | `new ProcessBuilder("grep","ERROR",f)` |
| 不注入 | — | 参数分开传 | 参数分开传（默认不过 shell） |
| 超时 | `timeout 3 …` | `CommandContext` + **`WaitDelay`** | **看门狗线程** + `descendants()` 先杀子孙 |
| 取退出码 | `$?` | `errors.As(&ExitError)` → `ExitCode()` | `p.exitValue()` |
| 判端口占用 | `netstat -tunlp` | `net.Listen` 失败即占用 | `new ServerSocket(port)` 抛 `BindException` |
| 递归建目录 | `mkdir -p a/b/c` | `os.MkdirAll` | `Files.createDirectories` |
| 词频统计 | `grep -o\|sort\|uniq -c\|sort -rn` | `regexp`+`map`+`sort.Slice` | `Pattern`+`merge`+`entries.sort` |
| 实时读输出 | `tail -f` | `StdoutPipe`+`Scanner` | `getInputStream()`+`readLine()` |
| 回收子进程 | — | `cmd.Wait()` | `p.waitFor()` / `destroyForcibly().waitFor()` |

## 延伸追问

- **Java 为什么比 Go 更容易被注入？** → 不是更容易，而是**更容易自己造出来**：`ProcessBuilder` 默认不起 shell，但 `Runtime.exec("a | b")` 不支持管道，想用管道就得自己拼 `sh -c`（第一节）。
- **`p.destroy()` 和 `destroyForcibly()` 有什么区别？** → 前者等价 SIGTERM（可被捕获），后者等价 SIGKILL；超时兜底要**先杀 `descendants()` 再杀自己**，否则孙子进程还握着管道（第二节）。
- **纯 Java 复刻为什么要和真管道对拍？** → 只有对拍才能发现「`|` 是左起优先还是最长匹配」这类口径差异，否则它会安静地留在报表里（第四节）。
- **`Files.createDirectories` 是幂等的吗？** → 是，等价 `mkdir -p`；中间层已存在且是普通文件时才报错（第五节）。
- **`tail -f` 为什么不能用 `readAllBytes()`？** → 流永不结束，会把堆撑爆；要逐行读并给读到的行立刻处理（第六节）。
