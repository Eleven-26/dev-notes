## Q1. MySQL 查询一条数据经历了哪些过程？

**来源**：`p=19` 百度 Go 实习一面 · 时长 3分13秒
**考察意图**：要能**按顺序说出整条链路**，并指出 8.0 之后哪一环被移除了。

### 完整链路（7 步）

```
客户端 → ① 查询缓存 → ② 解析器 → ③ 预处理器 → ④ 查询优化器
      → ⑤ 执行引擎 → ⑥ 存储引擎 → ⑦ 返回结果
```

| 步骤 | 做什么 |
|---|---|
| **① 查询缓存** | 根据 SQL 语句**直接找缓存的结果集**，命中就直接返回。<br>⚠️ **MySQL 8.0 已移除**（8.0 之前存在） |
| **② 解析器** | **词法解析 + 语法解析**，检查 SQL 是否符合语法规则 |
| **③ 预处理器** | 验证**对象是否存在**、**权限校验**、**处理默认值**等，形成新的解析树 |
| **④ 查询优化器** | 生成**执行计划**，选择最优访问路径。<br>执行计划**通常不缓存**，除非使用**预编译语句** |
| **⑤ 查询执行引擎** | 按执行计划，通过 **API 接口**调用存储引擎 |
| **⑥ 存储引擎** | 从 Buffer Pool / 磁盘取数据（InnoDB） |
| **⑦ 返回结果** | 结果集返回给客户端 |

### 为什么 8.0 要移除查询缓存？

> MySQL 主要是**增删改查混合**的负载。一旦表上有任何写操作，**该表相关的查询缓存会全部失效**。
> 结果就是：**缓存的有效期极短、命中率极低**，维护缓存的成本反而超过收益。
>
> 所以 8.0 干脆**移除了查询缓存**——这也解释了为什么现在主流做法是**在应用层用 Redis 做缓存**。

### 加分点：预编译语句与执行计划缓存

> 如果 SQL 使用**预编译（占位符 `?`）**，执行计划会被**提前申请并缓存**，
> 真正查询时只需把参数替换进去，**省掉了每次重新解析和生成执行计划的开销**。
> 这也是 Go 里 `database/sql` 的 `Prepare` 和各类 ORM 的**预编译逻辑**的收益来源，
> 同时它还**天然防 SQL 注入**（参数与语句分离）。

## Q2. 请介绍一下 MySQL 的软件架构

**来源**：`p=24` 百度 Go 实习一面 · 时长 8分49秒
**考察意图**：能**自顶向下分层讲清** MySQL 由哪些部分组成，并区分关系型与非关系型数据库。

### 先答：关系型 vs 非关系型数据库

| | **关系型（SQL）** | **非关系型（NoSQL）** |
|---|---|---|
| **代表** | **MySQL** | **Redis**（key-value）、**MongoDB**（文档型） |
| **数据结构** | 必须**严格预定义**：哪些表、哪些字段、什么类型 | **不要求预先定义**结构 |
| **数据模型** | 关系模型，以**表格**形式存储 | **多样化**（KV、文档、图……） |
| **表间关系** | 有**主外键关系**，可多表操作 | 通常无关系概念 |
| **记录字段** | 同一表所有行字段一致 | **每条记录的字段可以不同** |
| **擅长** | 复杂查询、事务处理、大量**结构化数据**管理 | 缓存、灵活 schema、高并发读写 |
| **主要用途** | **结构化数据的持久化** | Redis 常用作**缓存层** |

### MySQL 软件架构（自顶向下 7 层）

```
客户端连接层
  ↓
服务层工具（备份/恢复/安全/复制）
  ↓
SQL 接口（DML / DDL / 存储过程 / 触发器 / 视图）
  ↓
解析器 → 优化器 → 缓存
  ↓
存储引擎层（InnoDB 等）
  ↓
文件系统 / 操作系统层（真正落盘）
```

| 层次 | 内容 |
|---|---|
| **① 客户端连接层** | 各种语言实现的客户端库、命令行工具。<br>**关键：连接池** |
| **② 服务层工具** | 备份、恢复、安全管理、数据复制等 |
| **③ SQL 接口** | DML（增删改查）、DDL（表结构操作）、存储过程、触发器、视图——<br>**是客户端与服务端交互的接口组件** |
| **④ 解析器** | **词法解析 + 语法解析**。SQL 本质是一种语言，需要把**人类可读的语句转成计算机可读的形式** |
| **⑤ 优化器** | 我们写的 SQL **未必是最优的**，优化器自动做一些优化，例如**选择使用哪个索引、选择访问路径** |
| **⑥ 缓存** | 包含查询缓存（**8.0 已移除**）、表元数据缓存、key 缓存等 |
| **⑦ 存储引擎层** | 支持多种引擎，**最常见的是 InnoDB** |
| **⑧ 文件系统/OS 层** | 最终由操作系统把数据、日志文件真正写到磁盘 |

### 为什么要有连接池？（这层最值得展开）

**要解决的问题**：频繁**创建和销毁连接**的开销很大。建立一条连接需要：
- **TCP 三次握手（断开时四次挥手）**；
- **认证与安全性校验**；
- 其他初始化动作。

**连接池的做法**：

> 客户端**用完之后不立即销毁连接对象，而是归还到连接池缓存起来**。
> 由于这些初始化动作在**创建连接时就已完成**，被缓存下来的连接**再次使用时就无需重复初始化**，
> 从而**避免频繁创建/销毁带来的性能消耗**。

### 面试官会追问什么

- **为什么 8.0 移除查询缓存？** → 数据频繁增删改导致缓存**失效率极高、有效期极短**，
  维护成本超过收益。（详见本册 Q3）
- **InnoDB 和 MyISAM 的区别？** → InnoDB 支持**事务、行级锁、外键、崩溃恢复（redo log）**；
  MyISAM 只有表级锁、不支持事务，但计数和全表扫描更快。**生产默认用 InnoDB**。

## Q3. MySQL 的 JOIN 怎么用？在什么场景下才该用？

**来源**：`p=53` 小鹏后台开发二面（日常实习）· 时长 8分07秒
**考察意图**：这题的**标准答案偏向"少用 JOIN"**，
能讲出"互联网为什么不推荐 JOIN"就是答到了点上。

### 一、JOIN 是什么

最常用的是**内连接（`INNER JOIN`）**：

```sql

SELECT o.id, o.amount, u.name
FROM orders o
INNER JOIN users u ON o.user_id = u.id;
```

> **两张表里都有、且能相互匹配的数据才会被查出来**——
> 相当于**把两张表的数据拼到一起，再查出所需字段**。

### 二、⚠️ 关键认知：JOIN 不一定更快

> **`INNER JOIN` 只是"能一次性把数据查出来"，它并不是"性能最优"的选择。**

**传统企业 vs 互联网企业的思路差异**：

| | 思路 |
|---|---|
| **传统企业** | **想尽一切办法一次性把所需数据都查出来**（更看重"一次拿到完整结果"） |
| **互联网企业** | **想尽办法加快单次请求的过程**（更看重延迟） |

**核心判断**：

> **数据量大之后，一次 JOIN 的查询效率往往比不过两次单表查询。**

### 三、互联网的常见替代做法：拆成单表查询 + 应用层拼接

```
① 先查 table1
② 再查 table2
③ 在应用程序的内存里把两次结果拼接起来，得到最终数据
```

**为什么这样更快**：

| 原因 | 说明 |
|---|---|
| **避免大表 JOIN 的中间结果集** | JOIN 会产生笛卡尔积式的中间结果，数据量大时内存/临时表压力剧增 |
| **两次查询都能走索引** | 单表按主键/索引精确查询，**每次都是 O(log n) 级别的定位** |
| **可并行** | 两次查询甚至可以用 `errgroup` 并发执行，**总耗时取较慢的那个** |
| **易缓存** | 两张表的结果可以分别进 Redis，**命中率比 JOIN 结果高得多** |
| **便于分库分表** | 拆表后天然支持分片；JOIN 在分片后几乎无法使用 |

**Go 中的做法示例**：

```go

// 用 errgroup 并发两次单表查询，再在内存拼接
g, ctx := errgroup.WithContext(ctx)
var users map[int64]*User
var orders []*Order

g.Go(func() error { users, err = userRepo.BatchGet(ctx, ids); return err })
g.Go(func() error { orders, err = orderRepo.ListByUserIDs(ctx, ids); return err })
if err := g.Wait(); err != nil { return err }
// 内存里按 user_id 归并
```

### 四、什么场景下才适合用 JOIN

**原视频给的两类场景**：

| 场景 | 说明 |
|---|---|
| **企业管理内部系统** | 数据量不大、开发效率优先，JOIN 很方便 |
| **报表统计 / 跑定时任务** | 例如**凌晨跑任务统计、抓取数据**——不在业务高峰，性能压力小 |

**⚠️ 一个重要的风险提示**：

> 当表里的数据特别大时，如果**同一个数据库既给前端业务用、又给企业后端用**，
> 那么**用 JOIN 可能会影响前端系统**（一次重查询会占满 IO/CPU）。
>
> 所以内部/报表类查询**最好走只读从库**，与线上业务隔离。

### 五、结论（可以直接背）

> **能用单表查询就用单表查询，尽可能避免连接查询。**
>
> **需要 JOIN 的场景，基本是企业管理系统和离线报表/定时任务**；
> 而**面向 C 端的高并发链路**，应当**拆成多次单表查询 + 应用层拼接 + 缓存**。

### 面试官会追问什么

- **`INNER JOIN` / `LEFT JOIN` / `RIGHT JOIN` 的区别？** →
  内连接取交集；左连接以左表为准（右表无匹配补 NULL）；右连接反之。
- **`ON` 和 `WHERE` 的区别？** → **`ON` 是连接条件**（在生成连接结果时生效，
  外连接中放在 `ON` 里不会过滤掉左表的行）；**`WHERE` 是结果过滤**（在连接之后过滤，
  外连接中写在这里会把补 NULL 的行也过滤掉，**等价于退化成内连接**）。
- **JOIN 的驱动表怎么选？** → 一般**小表驱动大表**；
  优化器会自行判断，必要时可用 `STRAIGHT_JOIN` 强制顺序。
- **分库分表后怎么做关联查询？** → 通过**冗余字段、宽表、异步同步（binlog→ES/数仓）**，
  或**在同一分片键下保证数据落在同一库**，避免跨库 JOIN。

### 1. 预编译：什么时候真的省了开销

Q1 的加分点说「预编译能缓存执行计划」。在 Go 里这句话要拆成三种情况，否则容易配反 DSN：

| 情况 | 网络往返 | 执行计划 | 说明 |
|---|---|---|---|
| `db.Query(sql, args...)` + **未开** `interpolateParams` | 首次 `PREPARE`+`EXECUTE`，之后只 `EXECUTE` | **服务端缓存** | 驱动按**连接**缓存 prepared statement（LRU，上限 1000 条）。同一条 SQL 文本命中同一连接即省掉解析 |
| `db.Query(sql, args...)` + **开了** `interpolateParams=true` | 一次 `COM_QUERY` | 每次都要重新解析 | 驱动在客户端把参数转义后拼进去。**转义由驱动完成，仍然防注入**，但拿不到计划缓存 |
| 字符串拼 SQL | 一次 `COM_QUERY` | 每次都要重新解析 | ❌ **唯一真正危险的写法**：值里一个引号就能改写语义 |

**选型结论**：核心高频链路（SQL 文本固定、QPS 高）关掉 `interpolateParams`，让计划缓存生效；
低频、极在意一次往返的场景可以开着它换 RTT。两种模式下**都禁止手写拼接**。

```go

package prepstmt

import (
	"context"
	"database/sql"
	"strings"
)

// ✗ 反例：拼字符串。author 传 "x' OR '1'='1" 就把 WHERE 条件整个改写了。
func badListByAuthor(ctx context.Context, db *sql.DB, author string) (string, error) {
	q := "SELECT id FROM article WHERE author = '" + author + "'"
	var id int64
	err := db.QueryRowContext(ctx, q).Scan(&id)
	return q, err // 返回 q 只是为了让这一行不被编译器判为无用，业务里应直接删掉
}

// Placeholders 生成 "?, ?, ?"，这是唯一安全的"动态拼 SQL"方式：
// 拼进去的只有占位符，值永远走参数，不参与 SQL 语法解析。
func Placeholders(n int) string {
	return strings.TrimSuffix(strings.Repeat("?, ", n), ", ")
}

// ListByIDs 演示 IN 列表的正确写法。
// 注意 SQL 文本随 len(ids) 变化，计划缓存按文本分桶，
// 所以生产上通常把 n 分档（1/5/10/50…）或固定批大小，否则每个批长度都是一条新语句。
func ListByIDs(ctx context.Context, db *sql.DB, ids []int64) ([]Article, error) {
	if len(ids) == 0 {
		return nil, nil // 空集合必须提前返回：拼出 "IN ()" 是语法错误
	}
	args := make([]any, len(ids))
	for i, id := range ids {
		args[i] = id
	}
	q := `SELECT id, title, author FROM article WHERE id IN (` + Placeholders(len(ids)) + `)`

	rows, err := db.QueryContext(ctx, q, args...)
	if err != nil {
		return nil, err
	}
	defer rows.Close() // 必须 defer：Scan 报错提前 return 时也要关，否则连接不归还池

	var out []Article
	for rows.Next() {
		var a Article
		if err := rows.Scan(&a.ID, &a.Title, &a.Author); err != nil {
			return nil, err
		}
		out = append(out, a)
	}
	return out, rows.Err() // 迭代器本身可能因网络中断失败，漏掉这行会静默拿到半截结果
}

type Article struct {
	ID     int64
	Title  string
	Author sql.NullString // 列可为 NULL 时必须用 NullXxx / 指针，否则 Scan 直接报 converting NULL
}

// CountByAuthorPrepared 显式 Prepare 一次、执行多次：
// 适合批量导数、定时任务里同一条语句跑上万次的场景。
func CountByAuthorPrepared(ctx context.Context, db *sql.DB, authors []string) (map[string]int, error) {
	stmt, err := db.PrepareContext(ctx, `SELECT COUNT(*) FROM article WHERE author = ?`)
	if err != nil {
		return nil, err
	}
	defer stmt.Close()

	out := make(map[string]int, len(authors))
	for _, a := range authors {
		if err := ctx.Err(); err != nil { // 长循环一定要看点是否被取消
			return nil, err
		}
		var n int
		if err := stmt.QueryRowContext(ctx, a).Scan(&n); err != nil {
			return nil, err
		}
		out[a] = n
	}
	return out, nil
}
```

> ⚠️ `*sql.Stmt` 也**并发安全**，但它跟着 `DB` 走：连接池里每条连接各自准备一份，所以高并发下会看到
> `Com_prepare` 计数涨得比调用次数快——这不是泄漏，是驱动的每连接语句缓存。

### 2. 拆 JOIN：并发单表查询 + 内存归并

Q3 的结论是「面向 C 端的高并发链路，拆成多次单表查询 + 应用层拼接」。落到代码要注意三件事：
**用批查而不是逐条查（N+1）**、**并发写变量不要用共享 `err`**、**归并用 map 而不是嵌套循环**。

```go

package joinfree

import (
	"context"
	"database/sql"
	"strings"

	"golang.org/x/sync/errgroup"
)

type User struct {
	ID   int64
	Name string
}

type Order struct {
	ID     int64
	UserID int64
	Amount int64
}

// OrderView 给前端的扁平结构——JOIN 想要的效果，用内存拼出来。
type OrderView struct {
	OrderID     int64  `json:"order_id"`
	Amount      int64  `json:"amount"`
	UserID      int64  `json:"user_id"`
	UserName    string `json:"user_name"`
	UserMissing bool   `json:"user_missing"` // 单表拼接必须显式表达"左连接补 NULL"的语义
}

// ✗ N+1：先查订单，再在循环里逐个查用户。100 条订单 = 101 次往返。
func listWithUserNPlusOne(ctx context.Context, db *sql.DB, uid int64) ([]OrderView, error) {
	orders, err := ordersByUsers(ctx, db, []int64{uid})
	if err != nil {
		return nil, err
	}
	out := make([]OrderView, 0, len(orders))
	for _, o := range orders {
		var u User
		if err := db.QueryRowContext(ctx, `SELECT id, name FROM users WHERE id = ?`, o.UserID).Scan(&u.ID, &u.Name); err != nil {
			return nil, err
		}
		out = append(out, OrderView{OrderID: o.ID, Amount: o.Amount, UserID: u.ID, UserName: u.Name})
	}
	return out, nil
}

// ✓ 两次单表查询 + 并发 + 内存归并：总耗时 ≈ 较慢的那一次。
func ListWithUser(ctx context.Context, db *sql.DB, userIDs []int64) ([]OrderView, error) {
	if len(userIDs) == 0 {
		return nil, nil
	}

	var (
		orders []Order
		users  map[int64]User
	)

	// ⚠️ 两个 goroutine 分别持有自己的返回值，不要再共享外层 err 变量——
	// 共享 err 是数据竞争（go test -race 会报，go vet 不一定报）。errgroup 本身就负责传错误。
	g, gctx := errgroup.WithContext(ctx)
	g.Go(func() error {
		v, err := ordersByUsers(gctx, db, userIDs)
		orders = v
		return err
	})
	g.Go(func() error {
		v, err := usersByIDs(gctx, db, userIDs)
		users = v
		return err
	})
	if err := g.Wait(); err != nil {
		return nil, err
	}

	out := make([]OrderView, 0, len(orders))
	for _, o := range orders {
		v := OrderView{OrderID: o.ID, Amount: o.Amount, UserID: o.UserID}
		if u, ok := users[o.UserID]; ok { // map 查找 O(1)，别写成 for + for
			v.UserName = u.Name
		} else {
			v.UserMissing = true // 对应用户不存在/已删除——这是 LEFT JOIN 补 NULL 的等价物
		}
		out = append(out, v)
	}
	return out, nil
}

func ordersByUsers(ctx context.Context, db *sql.DB, ids []int64) ([]Order, error) {
	args := make([]any, len(ids))
	for i, id := range ids {
		args[i] = id
	}
	q := `SELECT id, user_id, amount FROM orders WHERE user_id IN (` + strings.TrimSuffix(strings.Repeat("?, ", len(ids)), ", ") + `)`
	rows, err := db.QueryContext(ctx, q, args...)
	if err != nil {
		return nil, err
	}
	defer rows.Close()

	var out []Order
	for rows.Next() {
		var o Order
		if err := rows.Scan(&o.ID, &o.UserID, &o.Amount); err != nil {
			return nil, err
		}
		out = append(out, o)
	}
	return out, rows.Err()
}

func usersByIDs(ctx context.Context, db *sql.DB, ids []int64) (map[int64]User, error) {
	args := make([]any, len(ids))
	for i, id := range ids {
		args[i] = id
	}
	q := `SELECT id, name FROM users WHERE id IN (` + strings.TrimSuffix(strings.Repeat("?, ", len(ids)), ", ") + `)`
	rows, err := db.QueryContext(ctx, q, args...)
	if err != nil {
		return nil, err
	}
	defer rows.Close()

	out := make(map[int64]User, len(ids))
	for rows.Next() {
		var u User
		if err := rows.Scan(&u.ID, &u.Name); err != nil {
			return nil, err
		}
		out[u.ID] = u
	}
	return out, rows.Err()
}
```

> 上文 Q3 的示意代码里两个 `g.Go` 共用了外层 `err`，那是**数据竞争**写法；以本节 `ListWithUser` 为准。

### 3. 读写分离：业务走主库、报表走从库

Q3 的风险提示是「重查询会打满 IO/CPU，内部/报表类查询最好走只读从库」。
在 Go 里这就是**两个单例池 + 按请求选池**，而不是把库名硬编码进 SQL。

```go

package rwsplit

import (
	"context"
	"database/sql"
	"fmt"
	"os"
	"sync"
	"time"

	_ "github.com/go-sql-driver/mysql"
)

type ctxKey struct{ name string }

var forceMasterKey = ctxKey{"force-master"}

// 主/从各一个单例池。⚠️ 千万不要在请求路径里 sql.Open。
var (
	Master  = sync.OnceValue(func() *sql.DB { return open("MYSQL_MASTER_ADDR") })
	Replica = sync.OnceValue(func() *sql.DB { return open("MYSQL_REPLICA_ADDR") })
)

func open(addrEnv string) *sql.DB {
	addr := os.Getenv(addrEnv)
	if addr == "" {
		panic("rwsplit: env " + addrEnv + " is empty") // 配置缺失属于启动失败
	}
	dsn := fmt.Sprintf("%s:%s@tcp(%s)/%s?charset=utf8mb4&parseTime=true",
		os.Getenv("MYSQL_USER"), os.Getenv("MYSQL_PASS"), addr, os.Getenv("MYSQL_DB"))

	db, err := sql.Open("mysql", dsn)
	if err != nil {
		panic("rwsplit: open: " + err.Error())
	}
	db.SetMaxOpenConns(20)
	db.SetMaxIdleConns(5)
	db.SetConnMaxLifetime(10 * time.Minute)
	db.SetConnMaxIdleTime(3 * time.Minute)

	ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
	defer cancel()
	if err := db.PingContext(ctx); err != nil {
		panic("rwsplit: ping " + addrEnv + ": " + err.Error())
	}
	return db
}

// ForceMaster 打标记：写之后的读、事务内的读都必须走主库，
// 否则会被主从延迟坑到（原因与三种处理方案见 [事务与日志.md](事务与日志.md) 的「读己之写」）。
func ForceMaster(ctx context.Context) context.Context {
	return context.WithValue(ctx, forceMasterKey, true)
}

// Pick 返回本次查询该用的池。默认从库，标记过的和事务内的走主库。
func Pick(ctx context.Context, inTx bool) *sql.DB {
	if inTx {
		return Master() // 事务只能跑在一个连接上，跨池不存在"一个事务两个库"
	}
	if forced, _ := ctx.Value(forceMasterKey).(bool); forced {
		return Master()
	}
	if err := ping(context.Background(), Replica()); err != nil {
		return Master() // 从库不可用要能降级；⚠️ 代价是报表流量会挤占业务库
	}
	return Replica()
}

func ping(ctx context.Context, db *sql.DB) error {
	ctx, cancel := context.WithTimeout(ctx, time.Second)
	defer cancel()
	return db.PingContext(ctx)
}

// Report 是"重查询"的落点：显式走从库 + 单独超时预算。
func Report(ctx context.Context, since time.Time) (int, error) {
	ctx, cancel := context.WithTimeout(ctx, 60*time.Second) // 报表可以给 60s，C 端接口不行
	defer cancel()

	var n int
	q := `SELECT COUNT(*) FROM orders WHERE created_at >= ?`
	if err := Pick(ctx, false).QueryRowContext(ctx, q, since).Scan(&n); err != nil {
		return 0, err
	}
	return n, nil
}
```

> ⚠️ 每次 `Pick` 都 Ping 一次等于给每个请求加一个 RTT。生产做法是后台定时探活 + 缓存健康状态，
> 或干脆用中间件（ProxySQL / MyCat / 云厂商代理）在**连接层**做分离，应用只拿到一个地址。
> 本节的目的是让「谁是主、谁是从」在代码里显式可辨，而不是散落在字符串里。

## 使用二：Java（JdbcTemplate / MyBatis + 读写分离）

> ⚠️ 本节 Java 代码按 Spring Framework 6.x / Spring Boot 3.x API 书写，**未编译校验**。
> 与 Go 侧的三条结论完全对应：参数化预编译、拆 JOIN、按请求选库。

### 1. 参数化：`?` 与命名参数，永远不用字符串拼

```java

package notes.mysql.prepstmt;

import java.util.List;
import java.util.Map;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.core.RowMapper;
import org.springframework.jdbc.core.namedparam.MapSqlParameterSource;
import org.springframework.jdbc.core.namedparam.NamedParameterJdbcTemplate;

public class ArticleDao {

    private final JdbcTemplate jdbc;
    private final NamedParameterJdbcTemplate named;

    public ArticleDao(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
        this.named = new NamedParameterJdbcTemplate(jdbc);
    }

    // ✓ 占位符：JdbcTemplate 内部走 PreparedStatement，参数不参与语法解析
    public List<String> titlesByAuthor(String author) {
        RowMapper<String> mapper = (rs, i) -> rs.getString("title");
        return jdbc.query("SELECT title FROM article WHERE author = ?", mapper, author);
    }

    // ✓ IN 列表：命名参数自动展开占位符，不要自己拼 "?" 也不要拼值
    public List<Long> idsIn(List<Long> ids) {
        if (ids.isEmpty()) {
            return List.of();
        }
        return named.queryForList(
                "SELECT id FROM article WHERE id IN (:ids)",
                new MapSqlParameterSource("ids", ids),
                Long.class);
    }

    // ✗ 反例（写出来只为了说明它为什么错）：值直接进入 SQL 文本
    // jdbc.queryForList("SELECT id FROM article WHERE author = '" + author + "'", Long.class);

    // ✗ 另一个坑：MyBatis 里 ${} 是字面替换，等同于拼字符串；#{} 才是占位符
    //   <select id="q">SELECT id FROM article WHERE author = '${author}'</select>

    // ⚠️ ORDER BY / 表名这类"结构位"没法参数化（? 只能代表值），
    // 只能靠白名单映射，不要拼前端传进来的字符串。
    public List<Map<String, Object>> sorted(String sortBy) {
        String column = Map.of("id", "id", "time", "created_at", "views", "views")
                .getOrDefault(sortBy, "id");
        return jdbc.queryForList("SELECT id, title FROM article ORDER BY " + column + " DESC LIMIT 50");
    }
}
```

### 2. 拆 JOIN：`groupingBy` + 并发批查

Q3 的「应用层拼接」在 Java 里就是 `Stream` 分组归并（更多写法见 [../java/Stream流实战.md](../java/Stream流实战.md)）：

```java

package notes.mysql.joinfree;

import java.util.List;
import java.util.Map;
import java.util.concurrent.CompletableFuture;
import java.util.function.Function;
import java.util.stream.Collectors;
import org.springframework.jdbc.core.JdbcTemplate;

public class OrderAssembler {

    private final JdbcTemplate jdbc;

    public OrderAssembler(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    public List<OrderView> list(List<Long> userIds) {
        if (userIds.isEmpty()) {
            return List.of();
        }

        // 两次单表批查，并发发起：总耗时取较慢的那个
        CompletableFuture<List<Order>> ordersF = CompletableFuture.supplyAsync(
                () -> jdbc.query("SELECT id, user_id, amount FROM orders WHERE user_id IN (?)",
                        (rs, i) -> new Order(rs.getLong("id"), rs.getLong("user_id"), rs.getLong("amount")),
                        join(userIds)));
        CompletableFuture<Map<Long, User>> usersF = CompletableFuture.supplyAsync(
                () -> jdbc.query("SELECT id, name FROM users WHERE id IN (?)",
                                (rs, i) -> new User(rs.getLong("id"), rs.getString("name")),
                                join(userIds))
                        .stream().collect(Collectors.toMap(User::id, Function.identity())));

        Map<Long, User> users = usersF.join();
        return ordersF.join().stream()
                .map(o -> {
                    User u = users.get(o.userId()); // null 就是 LEFT JOIN 补 NULL 的情况
                    return new OrderView(o.id(), o.amount(), o.userId(), u == null ? null : u.name(), u == null);
                })
                .toList();
    }

    // ⚠️ 这里为了省篇幅直接把 id 列表拼进 SQL：生产必须改用 ?占位符 或 NamedParameterJdbcTemplate。
    // 因为 Long 列表不存在引号问题，但拼 SQL 这个动作一旦被复制到字符串场景就是注入。
    private static String join(List<Long> ids) {
        return ids.stream().map(String::valueOf).collect(Collectors.joining(","));
    }

    record Order(long id, long userId, long amount) {}

    record User(long id, String name) {}

    record OrderView(long orderId, long amount, long userId, String userName, boolean userMissing) {}
}
```

> ⚠️ `CompletableFuture.supplyAsync` 默认用公共 `ForkJoinPool`，**会把数据库并发放大到 CPU 核数倍**；
> 生产要传专用线程池，且线程池大小要和 HikariCP 的 `maximumPoolSize` 对齐，否则只是在排队抢连接。

### 3. 读写分离：`AbstractRoutingDataSource`

```java

package notes.mysql.rwsplit;

import java.util.HashMap;
import java.util.Map;
import javax.sql.DataSource;
import org.springframework.jdbc.datasource.AbstractRoutingDataSource; // 实际是 lookup 的基类，见下方说明
import org.springframework.jdbc.datasource.lookup.AbstractRoutingDataSource;

public class MasterReplicaRouting extends AbstractRoutingDataSource {

    // 路由键放 ThreadLocal：这是"按请求选库"的关键，业务代码不感知库地址
    private static final ThreadLocal<Boolean> FORCE_MASTER = ThreadLocal.withInitial(() -> Boolean.FALSE);

    public static void forceMaster() {
        FORCE_MASTER.set(Boolean.TRUE);
    }

    public static void clear() {
        FORCE_MASTER.remove(); // ⚠️ 必须 remove：线程池会复用线程，留着会把后续请求一路带进主库
    }

    @Override
    protected Object determineCurrentLookupKey() {
        return FORCE_MASTER.get() ? "master" : "replica";
    }

    @Override
    public void afterPropertiesSet() {
        Map<Object, Object> targets = new HashMap<>();
        // targetDataSources 需要由外部注入真实 DataSource，这里仅示意键名对应关系
        super.afterPropertiesSet();
    }
}
```

> 说明：`AbstractRoutingDataSource` 需要在配置类里 `setTargetDataSources(Map.of("master", ds1, "replica", ds2))`
> 并 `setDefaultTargetDataSource(ds1)`；`determineCurrentLookupKey` 的返回值用来查这张表。
> 拦截 `@Transactional(readOnly = true)` 自动切从库是**各中间件的行为**（ShardingSphere、
> `baomidou/dynamic-datasource`），Spring 自身只认 `readOnly` 标志并把它下推给连接的 `setReadOnly()`。

**结论对齐 Go 侧**：`FORCE_MASTER` ≈ Go 的 `ForceMaster(ctx)`；
只是 Java 用 ThreadLocal（因为 Spring 的连接绑定在线程上），Go 用 `context`（因为 `database/sql` 按调用点选池）。

## 使用三：本地验证与 JOIN / 两次单表的实测

前面所有结论都可以在一台本地 MySQL 上跑出来，值得亲手验一次——尤其是「JOIN 不一定更快」。

### 1. 起库与造数

```bash

docker run -d --name mysql8 -p 3306:3306 \
  -e MYSQL_ROOT_PASSWORD=root123456 -e MYSQL_DATABASE=test \
  mysql:8.0 --innodb-buffer-pool-size=256M

# 等就绪（健康检查比 sleep 可靠）
until docker exec mysql8 mysqladmin ping -uroot -proot123456 --silent; do sleep 1; done

docker exec -i mysql8 mysql -uroot -proot123456 test <<'SQL'
CREATE TABLE users (
  id BIGINT PRIMARY KEY,
  name VARCHAR(32) NOT NULL,
  KEY idx_name (name)
) ENGINE = InnoDB;

CREATE TABLE orders (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id BIGINT NOT NULL,
  amount BIGINT NOT NULL,
  KEY idx_user (user_id)            -- 被驱动表的连接列必须有索引，否则 JOIN 一定慢
) ENGINE = InnoDB;

-- 造 10 万用户
INSERT INTO users (id, name)
SELECT t.N, CONCAT('u', t.N) FROM (
  WITH RECURSIVE s(N) AS (SELECT 1 UNION ALL SELECT N + 1 FROM s WHERE N < 100000)
  SELECT N FROM s
) t;

-- 造 100 万订单（10 用户 × 10 万，故意做成倾斜分布，便于观察"数据量决定 JOIN 代价"）
INSERT INTO orders (user_id, amount)
SELECT u.id, 100 FROM users u JOIN users s ON s.id <= 10;
SQL
```

### 2. 同一需求的两种写法对比

```sql

-- 写法 A：INNER JOIN
SELECT o.id, o.amount, u.name
FROM orders o INNER JOIN users u ON o.user_id = u.id
WHERE u.name = 'u1000' LIMIT 50;

-- 写法 B：两次单表（应用层拼接）—— 等价于下面两条
SELECT id, name FROM users WHERE name = 'u1000';           -- 走 idx_name，1 行
SELECT id, user_id, amount FROM orders WHERE user_id = ? LIMIT 50;  -- 走 idx_user
```

**怎么判断谁快**（对 Q1 链路里「优化器选路径」做一次实测）：

```bash

# 分别看执行计划：重点看 type / key / rows / Extra
docker exec -i mysql8 mysql -uroot -proot123456 test -e "EXPLAIN FORMAT=JSON SELECT o.id,o.amount,u.name FROM orders o INNER JOIN users u ON o.user_id=u.id WHERE u.name='u1000' LIMIT 50\G"

# 看真实耗时（关闭查询缓存类干扰，8.0 本来也没有查询缓存）
docker exec -i mysql8 mysql -uroot -proot123456 test -e "SET profiling=1; SELECT COUNT(*) FROM orders o INNER JOIN users u ON o.user_id=u.id; SHOW profiles;"
```

预期与结论一致：**驱动表选对 + 被驱动表有索引时，小结果集的 JOIN 并不慢**；
一旦连接结果集变大（去掉 `WHERE`）、或连接列缺索引，JOIN 的中间结果集就会让
它明显输给「两次单表 + 内存拼接」——这正是 Q3 那条结论的来源。

### 3. 观察「连接池 / 预编译」这两环

```bash

# 每个连接上缓存了多少 prepared statement（对应 Go 侧"每连接一份语句缓存"）
docker exec -i mysql8 mysql -uroot -proot123456 -e "SHOW GLOBAL STATUS LIKE 'Prepared_stmt_count';"

```

> 而是把缓存职责交回应用层——具体实现见 [../redis/缓存与分布式锁.md](../redis/缓存与分布式锁.md)。
