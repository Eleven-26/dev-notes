## Q1. MySQL 查询一条数据经历了哪些过程？

**来源**：`p=19` 百度 Go 实习一面 · 时长 3分13秒
**考察意图**：要能**按顺序说出整条链路**，并指出 8.0 之后哪一环被移除了。

### 完整链路（7 步）

```
客户端 → ① 查询缓存 → ② 解析器 → ③ 预处理器 → ④ 查询优化器
      → ⑤ 执行引擎 → ⑥ 存储引擎 → ⑦ 返回结果
```

| 步骤 | 做什么 |
|---|---|
| **① 查询缓存** | 根据 SQL 语句**直接找缓存的结果集**，命中就直接返回。<br>⚠️ **MySQL 8.0 已移除**（8.0 之前存在） |
| **② 解析器** | **词法解析 + 语法解析**，检查 SQL 是否符合语法规则 |
| **③ 预处理器** | 验证**对象是否存在**、**权限校验**、**处理默认值**等，形成新的解析树 |
| **④ 查询优化器** | 生成**执行计划**，选择最优访问路径。<br>执行计划**通常不缓存**，除非使用**预编译语句** |
| **⑤ 查询执行引擎** | 按执行计划，通过 **API 接口**调用存储引擎 |
| **⑥ 存储引擎** | 从 Buffer Pool / 磁盘取数据（InnoDB） |
| **⑦ 返回结果** | 结果集返回给客户端 |

### 为什么 8.0 要移除查询缓存？

> MySQL 主要是**增删改查混合**的负载。一旦表上有任何写操作，**该表相关的查询缓存会全部失效**。
> 结果就是：**缓存的有效期极短、命中率极低**，维护缓存的成本反而超过收益。
>
> 所以 8.0 干脆**移除了查询缓存**——这也解释了为什么现在主流做法是**在应用层用 Redis 做缓存**。

### 加分点：预编译语句与执行计划缓存

> 如果 SQL 使用**预编译（占位符 `?`）**，执行计划会被**提前申请并缓存**，
> 真正查询时只需把参数替换进去，**省掉了每次重新解析和生成执行计划的开销**。
> 这也是 Go 里 `database/sql` 的 `Prepare` 和各类 ORM 的**预编译逻辑**的收益来源，
> 同时它还**天然防 SQL 注入**（参数与语句分离）。

## Q2. 请介绍一下 MySQL 的软件架构

**来源**：`p=24` 百度 Go 实习一面 · 时长 8分49秒
**考察意图**：能**自顶向下分层讲清** MySQL 由哪些部分组成，并区分关系型与非关系型数据库。

### 先答：关系型 vs 非关系型数据库

| | **关系型（SQL）** | **非关系型（NoSQL）** |
|---|---|---|
| **代表** | **MySQL** | **Redis**（key-value）、**MongoDB**（文档型） |
| **数据结构** | 必须**严格预定义**：哪些表、哪些字段、什么类型 | **不要求预先定义**结构 |
| **数据模型** | 关系模型，以**表格**形式存储 | **多样化**（KV、文档、图……） |
| **表间关系** | 有**主外键关系**，可多表操作 | 通常无关系概念 |
| **记录字段** | 同一表所有行字段一致 | **每条记录的字段可以不同** |
| **擅长** | 复杂查询、事务处理、大量**结构化数据**管理 | 缓存、灵活 schema、高并发读写 |
| **主要用途** | **结构化数据的持久化** | Redis 常用作**缓存层** |

### MySQL 软件架构（自顶向下 7 层）

```
客户端连接层
  ↓
服务层工具（备份/恢复/安全/复制）
  ↓
SQL 接口（DML / DDL / 存储过程 / 触发器 / 视图）
  ↓
解析器 → 优化器 → 缓存
  ↓
存储引擎层（InnoDB 等）
  ↓
文件系统 / 操作系统层（真正落盘）
```

| 层次 | 内容 |
|---|---|
| **① 客户端连接层** | 各种语言实现的客户端库、命令行工具。<br>**关键：连接池** |
| **② 服务层工具** | 备份、恢复、安全管理、数据复制等 |
| **③ SQL 接口** | DML（增删改查）、DDL（表结构操作）、存储过程、触发器、视图——<br>**是客户端与服务端交互的接口组件** |
| **④ 解析器** | **词法解析 + 语法解析**。SQL 本质是一种语言，需要把**人类可读的语句转成计算机可读的形式** |
| **⑤ 优化器** | 我们写的 SQL **未必是最优的**，优化器自动做一些优化，例如**选择使用哪个索引、选择访问路径** |
| **⑥ 缓存** | 包含查询缓存（**8.0 已移除**）、表元数据缓存、key 缓存等 |
| **⑦ 存储引擎层** | 支持多种引擎，**最常见的是 InnoDB** |
| **⑧ 文件系统/OS 层** | 最终由操作系统把数据、日志文件真正写到磁盘 |

### 为什么要有连接池？（这层最值得展开）

**要解决的问题**：频繁**创建和销毁连接**的开销很大。建立一条连接需要：
- **TCP 三次握手（断开时四次挥手）**；
- **认证与安全性校验**；
- 其他初始化动作。

**连接池的做法**：

> 客户端**用完之后不立即销毁连接对象，而是归还到连接池缓存起来**。
> 由于这些初始化动作在**创建连接时就已完成**，被缓存下来的连接**再次使用时就无需重复初始化**，
> 从而**避免频繁创建/销毁带来的性能消耗**。

### 面试官会追问什么

- **为什么 8.0 移除查询缓存？** → 数据频繁增删改导致缓存**失效率极高、有效期极短**，
  维护成本超过收益。（详见本册 Q3）
- **InnoDB 和 MyISAM 的区别？** → InnoDB 支持**事务、行级锁、外键、崩溃恢复（redo log）**；
  MyISAM 只有表级锁、不支持事务，但计数和全表扫描更快。**生产默认用 InnoDB**。

## Q3. MySQL 的 JOIN 怎么用？在什么场景下才该用？

**来源**：`p=53` 小鹏后台开发二面（日常实习）· 时长 8分07秒
**考察意图**：这题的**标准答案偏向"少用 JOIN"**，
能讲出"互联网为什么不推荐 JOIN"就是答到了点上。

### 一、JOIN 是什么

最常用的是**内连接（`INNER JOIN`）**：

```sql
SELECT o.id, o.amount, u.name
FROM orders o
INNER JOIN users u ON o.user_id = u.id;
```

> **两张表里都有、且能相互匹配的数据才会被查出来**——
> 相当于**把两张表的数据拼到一起，再查出所需字段**。

### 二、⚠️ 关键认知：JOIN 不一定更快

> **`INNER JOIN` 只是"能一次性把数据查出来"，它并不是"性能最优"的选择。**

**传统企业 vs 互联网企业的思路差异**：

| | 思路 |
|---|---|
| **传统企业** | **想尽一切办法一次性把所需数据都查出来**（更看重"一次拿到完整结果"） |
| **互联网企业** | **想尽办法加快单次请求的过程**（更看重延迟） |

**核心判断**：

> **数据量大之后，一次 JOIN 的查询效率往往比不过两次单表查询。**

### 三、互联网的常见替代做法：拆成单表查询 + 应用层拼接

```
① 先查 table1
② 再查 table2
③ 在应用程序的内存里把两次结果拼接起来，得到最终数据
```

**为什么这样更快**：

| 原因 | 说明 |
|---|---|
| **避免大表 JOIN 的中间结果集** | JOIN 会产生笛卡尔积式的中间结果，数据量大时内存/临时表压力剧增 |
| **两次查询都能走索引** | 单表按主键/索引精确查询，**每次都是 O(log n) 级别的定位** |
| **可并行** | 两次查询甚至可以用 `errgroup` 并发执行，**总耗时取较慢的那个** |
| **易缓存** | 两张表的结果可以分别进 Redis，**命中率比 JOIN 结果高得多** |
| **便于分库分表** | 拆表后天然支持分片；JOIN 在分片后几乎无法使用 |

**Go 中的做法示例**：

```go
// 用 errgroup 并发两次单表查询，再在内存拼接
g, ctx := errgroup.WithContext(ctx)
var users map[int64]*User
var orders []*Order

g.Go(func() error { users, err = userRepo.BatchGet(ctx, ids); return err })
g.Go(func() error { orders, err = orderRepo.ListByUserIDs(ctx, ids); return err })
if err := g.Wait(); err != nil { return err }
// 内存里按 user_id 归并
```

### 四、什么场景下才适合用 JOIN

**原视频给的两类场景**：

| 场景 | 说明 |
|---|---|
| **企业管理内部系统** | 数据量不大、开发效率优先，JOIN 很方便 |
| **报表统计 / 跑定时任务** | 例如**凌晨跑任务统计、抓取数据**——不在业务高峰，性能压力小 |

**⚠️ 一个重要的风险提示**：

> 当表里的数据特别大时，如果**同一个数据库既给前端业务用、又给企业后端用**，
> 那么**用 JOIN 可能会影响前端系统**（一次重查询会占满 IO/CPU）。
>
> 所以内部/报表类查询**最好走只读从库**，与线上业务隔离。

### 五、结论（可以直接背）

> **能用单表查询就用单表查询，尽可能避免连接查询。**
>
> **需要 JOIN 的场景，基本是企业管理系统和离线报表/定时任务**；
> 而**面向 C 端的高并发链路**，应当**拆成多次单表查询 + 应用层拼接 + 缓存**。

### 面试官会追问什么

- **`INNER JOIN` / `LEFT JOIN` / `RIGHT JOIN` 的区别？** →
  内连接取交集；左连接以左表为准（右表无匹配补 NULL）；右连接反之。
- **`ON` 和 `WHERE` 的区别？** → **`ON` 是连接条件**（在生成连接结果时生效，
  外连接中放在 `ON` 里不会过滤掉左表的行）；**`WHERE` 是结果过滤**（在连接之后过滤，
  外连接中写在这里会把补 NULL 的行也过滤掉，**等价于退化成内连接**）。
- **JOIN 的驱动表怎么选？** → 一般**小表驱动大表**；
  优化器会自行判断，必要时可用 `STRAIGHT_JOIN` 强制顺序。
- **分库分表后怎么做关联查询？** → 通过**冗余字段、宽表、异步同步（binlog→ES/数仓）**，
  或**在同一分片键下保证数据落在同一库**，避免跨库 JOIN。
