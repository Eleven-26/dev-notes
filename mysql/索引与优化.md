## Q1. MySQL 慢查询如何优化？索引为什么会失效？

**来源**：`p=5` 滴滴 Go 后端一面 · 时长 8分28秒
**考察意图**：面试官想听的是**一套可执行的排查流程**，而不是零散的优化技巧。

### 第一步：定位 —— 用工具找出"真正值得优化"的慢查询

不要凭感觉挑。用 `mysqldumpslow` 等工具分析慢查询日志，但**默认的"按平均查询时长排序"往往选错目标**：

> 一个平均耗时最长的 SQL，可能一天只出现 5 次，而且都发生在非高峰的深夜——
> 优化它收益极小。

应该换排序维度：
- **按总耗时排序**（平均时长 × 次数）→ 找出真正消耗数据库总资源的 SQL；
- **按出现次数排序** → 找出高频但单次不慢的 SQL（积少成多）。

### 第二步：分析 —— 用 `EXPLAIN` 看查询计划

拿到目标 SQL 后，用 `EXPLAIN` 看优化器打算怎么执行，重点看三件事：

| 关注点 | 判断标准 |
|---|---|
| **有没有用到索引** | `type` 是否出现 `ALL`（全表扫描） |
| **扫描行数** | `rows` 越小越好；**即使走了索引，扫描行数太多也快不了** |
| **是否用到子查询** | 子查询往往无法有效利用索引，考虑改写成 JOIN |

### 第三步：优化 —— 两大类原因

#### 类型 A：没用上索引

**A1. 根本没有索引 / 没有对应的索引字段**
→ 按实际查询条件建索引：条件固定的多字段查询建**联合索引**，否则建**单列索引**。

**A2. 有索引但"索引失效"**（这是面试重点，要能逐条举例）

| 失效场景 | 说明 | 正确写法 |
|---|---|---|
| **索引列上使用函数** | `WHERE DATE(created_at) = '2026-01-01'` | 改成范围条件 `created_at >= '2026-01-01' AND created_at < '2026-01-02'` |
| **`OR` 连接了无索引的字段** | 只要有一个条件没索引，整个查询可能放弃索引 | 给所有 `OR` 分支字段建索引，或拆成两次查询 `UNION` |
| **`LIKE` 以 `%` 开头** | `LIKE '%abc'` 无法利用 B+ 树有序性 | 把 `%` 放到后面：`LIKE 'abc%'` |
| **联合索引未遵循最左前缀** | 索引 `(a,b,c)`，查询只用 `b` / `c` | 补齐最左列，或按查询模式重建索引 |

#### 类型 B：用上了索引但还不够快

**B1. 使用覆盖索引，避免回表** ← 性价比最高的一招

如果查询需要的字段**全部都在索引里**，就不用再去主键索引（聚簇索引）取数据，少一步"回表"。
类比查字典：**已经直接在目录页看到了需要的信息，就不用翻到正文那一页**。

```sql
-- 假设有联合索引 idx_name_age(name, age)
-- ✗ 需要回表：select 的 address 不在索引里
SELECT name, age, address FROM users WHERE name = 'zhang';

-- ✓ 覆盖索引：所需字段都在索引中，无需回表
SELECT name, age FROM users WHERE name = 'zhang';
```

**B2. 表连接优化：用小表驱动大表**

原则：**行数少的表放左边**（驱动表），行数多的放右边。
用 `INNER JOIN` 时，执行方式是"拿小表的结果集去匹配大表"，小表越大范围越小的效果越好。

**B3. 先缩小范围，再做连接**

举例：要查 10 万行表与 50 万行表的连接结果，但最终只需要 1000 条：

```sql
-- 思路：先用条件把 10 万条数据过滤成 1000 条，再用这 1000 条去连接 50 万条的大表
-- 结果集非常小，比"10 万条直接连 50 万条"快得多
```

进一步可以把过滤后的结果集做成**临时表**，再做连接，减少中间数据量。

### 面试官会追问什么

- **`EXPLAIN` 你最关注哪几个字段？** → `type`、`key`、`rows`、`Extra`（看有没有 `Using filesort`、`Using temporary`）。
- **联合索引的最左前缀原则是什么？** → 索引 `(a,b,c)` 只能从最左列开始匹配；跳过 `a` 直接用 `b` 用不上索引。
- **回表一定会发生吗？** → 不一定。如果查询字段被索引覆盖，或者走的是主键/聚簇索引，就不需要额外回表。

**易错点**：一上来就罗列"加索引、少用 `SELECT *`、分库分表"这类泛泛之谈。
面试官要的是**从定位 → 分析 → 优化的完整闭环**。

## Q2. 索引是什么？有哪些分类？什么时候该用 / 不该用索引？

**来源**：`p=21` 百度 Go 实习一面 · 时长 26分08秒
**考察意图**：索引的**系统化认知**。这题信息量大，能答全"六种分类"的人不多。

### 一、索引的本质：空间换时间

**生活类比**（先讲类比，比背定义更有说服力）：
- **查字典**：按拼音查、按偏旁部首查——这就是字典的两种索引。
  **如果把索引部分撕掉，就只能一页页翻**，这就是**全表扫描**；
- **收货地址**：省 → 市 → 县 → 街道 → 门牌，逐级缩小范围，这就是索引的过程。

**目的**：**快速定位到需要的数据，加快查询效率。**

**代价（必须主动讲）**：
> 索引**本身也是数据**，需要单独维护。创建索引要**消耗存储空间**，
> 数据的增删改也会**触发索引维护、消耗性能**。
> **索引是用写入性能换查询性能**——写多读少的表要慎重建索引。

### 二、六种分类（面试逐条过）

#### ① 按数据结构分

| 类型 | 说明 |
|---|---|
| **B+ 树索引** | **最常用**。主键索引、唯一索引、普通索引都基于 B+ 树。<br>支持**等值、范围、前缀匹配**（`LIKE 'abc%'`），也能用于排序分组 |
| **哈希索引** | key → value 结构。**Memory 引擎**支持显式创建；<br>**InnoDB 有"自适应哈希索引"**：自动为**热点数据**维护哈希结构，加速等值查询。<br>⚠️ **局限：只支持等值比较（`=`），不支持范围查询** |
| **全文索引** | 类 ES 的思路：**把文本切分成单词**，建立"单词 → 文档 ID 列表"的倒排映射。<br>查询时按单词找文档 ID，再按业务需求**取交集或并集**；还能算相关性排序 |
| **空间索引** | 处理**地理坐标/几何数据**。典型场景：电子围栏、**判断共享单车是否停在指定区域内**、计算两点距离 |

#### ② 按字段数量分

- **单列索引**；
- **复合索引（联合索引）** —— ⚠️ 必须遵循**最左匹配原则**：
  只有当**最左列出现在查询条件中**（且位于条件最左侧）时，索引才能被用上。

#### ③ 按约束条件分

| 类型 | 约束 | 每表数量 |
|---|---|---|
| **普通索引** | 无任何约束 | 多个 |
| **唯一索引** | 值必须唯一，**但允许为 NULL** | 多个 |
| **主键索引** | **非空 + 唯一**，用于标识一行数据 | **只能有一个** |
| **外键索引** | 保证表间**引用完整性** | — |

> **实战经验**：工作中**经常不实际创建外键索引**，只在**约定层面**保证关联关系。
> 因为外键对写入操作的要求更高（额外的校验开销、级联操作限制），
> 在互联网高并发场景下通常由**应用层保证一致性**。

#### ④ 按存储方式分（**回表概念就出自这里**）

| 类型 | 特点 | 是否回表 |
|---|---|---|
| **聚簇索引（主键索引）** | **叶子节点直接存放完整的行数据** | 通过主键查询**不需要回表** |
| **非聚簇索引（二级索引）** | 叶子节点只存**索引列 + 主键值**，不含完整行数据 | **需要二次查询**（回表）才能拿到完整数据 |

**什么是回表**：
> 通过二级索引查找数据时，**索引的叶子节点不包含查询需要的字段**，
> 只能先拿到主键，**再回到聚簇索引（表）里取一次数据**——这一步就叫**回表**。
>
> 这也是二级索引"要做两次查找才能拿到完整数据"的原因。

#### ⑤ 按功能分

- **前缀索引**：对长字段只取前 N 个字符建索引；
- **覆盖索引（避免回表的核心手段）**：

  ```sql
  -- 已有 email 单列索引
  SELECT email FROM users WHERE email = 'a@b.com';        -- ✅ 不回表（email 就在索引里）

  -- 现在还要查 department
  SELECT email, department FROM users WHERE email = 'a@b.com';  -- ❌ 需回表取 department

  -- 解法：建联合索引 (email, department) → 变成覆盖索引
  CREATE INDEX idx_email_dept ON users(email, department);
  SELECT email, department FROM users WHERE email = 'a@b.com';  -- ✅ 不回表
  ```

  **覆盖索引 = 索引本身包含了查询需要的所有字段** → 不需要回表 → **显著提升查询性能**。

- **函数索引**：把**函数计算后的值**作为索引。
  例：字段本身区分大小写，但业务上希望**统一按小写查找** →
  对 `LOWER(name)` 建索引，查询 `WHERE LOWER(name) = 'abc'` 就能用上索引。

#### ⑥ 按可见性分

- **可见索引**（默认）：会被优化器选中；
- **不可见索引**：**索引仍然维护**，但优化器**不选择它**，可随时切换为可见。

**应用场景**：
1. **测试某个索引对性能的实际影响**——想评估"维护这个索引的写入代价有多少"，
   就先建为不可见，观察一段时间；
2. **临时禁用**某个索引（不改代码即可回退）；
3. 索引重建、灰度验证等。

### 三、什么时候该用 / 不该用索引

**适合建索引的列**：

| 条件 | 原因 |
|---|---|
| ① **经常用于查询条件** | 最核心的收益来源。不常查的列建索引基本没意义 |
| ② **经常用于表连接** | JOIN 的关联列是索引的高价值场景 |
| ③ **经常用于排序、分组** | 可避免 `Using filesort` / `Using temporary` |
| ④ **有约束需求的列** | 唯一性、主键约束 |

**不适合建索引的情况**：

| 情况 | 原因 |
|---|---|
| ① **数据量很小的表** | **全表扫描可能比走索引更快**（索引本身也要读一次） |
| ② **列基数低**（大量重复值） | 最典型的反例是**性别**。如果男女各占一半，走索引相当于**把"全表扫描"变成"半表扫描"**，付出索引维护成本却几乎没收益 |
| ③ **频繁更新的列** | 每次更新都要**维护索引**，写入开销被放大 |
| ④ **查询中经常被函数/表达式包裹的列** | 索引会失效（可考虑建**函数索引**补救） |

**一个极端的反例（原视频举的）**：
> 10 万行数据**内容完全一样**、且没有主键，查询性能极慢。
> 因为索引的意义建立在"**不同行的字段值有区分度**"之上——
> **如果所有值都一样，索引有和没有完全没区别**。
>
> **结论：索引列的基数（区分度）必须足够高。**

## Q3. 10 万条数据的分页查询怎么优化？

**来源**：`p=61` 字节跳动 Go 一面 · 时长 6分51秒
**考察意图**：数据量不算特别小的时候，**`LIMIT offset` 会出现明显性能问题**，考的就是这个。

### 一、先看"普通分页"的问题在哪

**常见写法**：

```sql
SELECT * FROM t
WHERE <条件>
ORDER BY <字段>
LIMIT 20 OFFSET 10000;     -- 翻到第 500 页
```

**问题**：

> **`OFFSET` 越大，查询越慢。**
> 因为 MySQL 必须**先扫描并丢弃前 `OFFSET` 条记录**，才能返回后面那 20 条——
> 翻到第 500 页时，前面 10000 条**都要被读取再丢掉**。

### 二、优化点一：索引优化

| 做法 | 效果 |
|---|---|
| **给查询条件 / 排序字段建索引** | 让 MySQL 能**快速定位到数据范围**，而不是全表扫描 |
| **主键索引** | InnoDB 的**主键索引叶子节点包含整行数据** →<br>**按 ID 查询时不需要回表** |
| **覆盖索引** | 让**索引里就包含查询需要的全部字段** → **无需回表** |

**覆盖索引举例**：

```sql
-- 查询只用到 name 和 age，那就建联合索引 (name, age)
CREATE INDEX idx_name_age ON users(name, age);

SELECT name, age FROM users WHERE name = 'zhang';
-- ✅ 所需字段都在索引里，直接从索引取数据，不回表
```

> **结论：主键索引和覆盖索引都能让查询"无需回表"**，
> 少一次"从二级索引拿主键、再回聚簇索引取数据"的过程。

### 三、优化点二：用「游标分页」替代 `OFFSET`（关键）

#### 适用场景：按**自增 ID** 排序的分页

**思路**：**不要用 `OFFSET`，改成记住"上一页最后一条记录的 ID"**。

```sql
-- 第一页
SELECT * FROM t WHERE id > 0            ORDER BY id LIMIT 10;

-- 第二页：把上一页最后一条的 id 传进来
SELECT * FROM t WHERE id > 12345        ORDER BY id LIMIT 10;
```

**为什么快**：

> **`WHERE id > lastID` 可以直接用主键索引定位到起点**，
> **不需要扫描并丢弃前面 N 条**——
> `OFFSET` 越大越慢的问题**从根上消失了**。

#### 扩展场景：排序字段"类似 ID 但不完全唯一"

**问题**：如果用来分页的字段**可能有重复值**（不像 ID 那样唯一），
用 `>` 可能会**漏掉同一值的其他记录**。

**做法：动态调整 `LIMIT`**——

```
本次取 10 条，如果最后一条的值与前面的值相同，就多取几条，
直到取完该值的所有条目为止。
```

**⚠️ 一条硬性要求**：

> **必须保证"当前这一页"把该值的所有条目全部取出来**，
> 否则**分页过程中会漏掉相同值的其他数据**。
>
> 所以页大小变得**不固定**（可能 10 条，也可能 12 条、20 条），
> 但**总体差别不大**，是可以接受的。

> 更严谨的做法是**复合游标**：`WHERE (created_at, id) > (?, ?)`
> ——用**排序字段 + 唯一字段（ID）组成联合游标**，
> 既保证不重不漏，又保持页大小固定。**这是面试最漂亮的答案。**

### 四、面试答题结构

```
① 指出问题：LIMIT OFFSET 越大越慢（要扫描并丢弃前 N 条）
② 索引优化：条件/排序字段建索引；主键索引与覆盖索引避免回表
③ 分页方式优化：游标分页（WHERE id > 上一页最后 ID）替代 OFFSET
④ 边界处理：排序字段非唯一时用动态 limit 或 (字段, id) 复合游标
```

### 面试官会追问什么

- **游标分页的缺点？** → **不能随机跳页**（不能直接跳到第 500 页），
  只能"上一页/下一页"；适合 **feed 流、无限滚动**，不适合后台管理的页码跳转。
- **后台管理必须跳页怎么办？** → 如果表数据量大且必须支持跳页，
  考虑**限制最大页数**、**改用搜索条件收敛数据**、或用 **ES** 承接复杂分页。
- **`LIMIT 1000000, 10` 还能怎么优化？** → 先 `WHERE id > X` 缩小范围再 `LIMIT 10`；
  或**先只查主键**（`SELECT id ... LIMIT 1000000, 10`）**再回表关联**——
  这样回表只发生 10 次，而不是 100 万次。**这个技巧非常实用，值得记住。**

## Q4. 怎样排查慢查询？（`mysqldumpslow` 实操）

**来源**：`BV12qjA6aErF p=76` 百度 Go 开发日常实习一面 · 时长 19分55秒
**考察意图**：Q1 讲的是"优化思路"，本题讲的是**手上的具体动作**——
**怎么把慢查询日志开起来、怎么用它挑出该优化的 SQL**。
面试官答完这题一定会接着问"那怎么优化"，所以两题要连着准备。

### 一、排查分两步

```
① 启用 MySQL 慢查询日志
② 用工具分析慢查询日志文件，挑出最该优化的那几条
```

### 二、第 1 步：启用慢查询日志（两种方式）

| 方式 | 做法 | 适用 |
|---|---|---|
| **临时开启** ⭐ | 在**运行中的 MySQL 上直接设置变量** | **生产环境推荐**——可以周期性开关，减少性能开销 |
| **永久开启** | 修改**配置文件（my.cnf）并重启 MySQL 服务** | 新建服务时可用；<br>⚠️ **正在稳定运行的生产服务不要这么做**（不要为了开个日志去重启） |

```sql
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;       -- 超过 1 秒算慢查询
SHOW VARIABLES LIKE 'slow_query_log_file';   -- ★ 拿到日志位置（分析要用）
```

**三个必须确认的信息**：
1. **`long_query_time`** —— 多久算慢；
2. **开启状态**；
3. **慢日志文件的位置** —— 后面分析必须用到。

**容器化场景的两个坑**：

> 1. 用 `docker inspect` 看 **Mounts**，确认数据目录和配置文件都挂到宿主机了
>    （否则容器一删，数据就没了）；
> 2. **慢日志未必挂载出来** → 那就需要**从容器里 `docker cp` 出来**再分析。

### 三、第 2 步：用 `mysqldumpslow` 分析

**工具来源**：`mysqldumpslow` **默认和 MySQL 安装包打包在一起**——
Windows/Linux 装 MySQL 都会有。

**⚠️ 容器化运行 MySQL 的坑**：

> 容器镜像遵循**最小原则**构建，**无关紧要的内容不打进镜像**（为了减小体积）——
> 所以进容器后会发现 **`mysqldumpslow` 不存在**，甚至 **`mysql` 客户端也没有**。
>
> **解法**：在**宿主机本地安装**即可。
> 因为 **`mysqldumpslow` 只是分析日志文件，不需要连接 MySQL 服务器**。

**常用参数**（重点记 `-s` / `-t` / `-a` / `-g`）：

| 参数 | 作用 |
|---|---|
| **`-s`** | **排序规则**：`-s t` 按**总时间**、`-s at` 按**平均查询时间**、`-s c` 按**出现次数** |
| **`-r`** | **反转排序结果**（默认从高到低，反转后从低到高） |
| **`-t`** | 显示**前 N 条** |
| **`-a`** | **不做抽象化**（默认数字→`N`、字符串→`S`）。<br>见下方"抽象化"说明 |
| **`-n`** | 抽象化名称中**至少包含数字**（如 `-n 3` 会把 `id=3` 抽象成 `id=N`） |
| **`-g`** | **过滤**（正则）：只看包含某模式的查询 |
| **`-h`** | 指定**主机名/实例名**（慢日志里有多个主机时筛选） |
| **`-l`** | **不从总时间中减去锁等待时间**（默认保留原始总时间） |

**什么是"抽象化"（默认行为）**：

> 默认会把**数字替换成 `N`、字符串替换成 `S`**。
>
> 所以 `WHERE id=10` 和 `WHERE id=20` 会被**归为同一条语句**（这是好事，
> 因为它们本质是同一类查询，只是参数不同）。
>
> **加 `-a` 则显示原始值**，于是"同一条语句"会被**按不同参数拆成多条记录
> 分别呈现**——条数会明显变多。

### 四、⭐ 核心洞察：按「总时间」排序，而不是「平均时间」

**反例（一定要讲这个）**：

```
A 语句：一天出现 100 次，每次 1.5 秒
B 语句：一天出现 1 次，  每次 2.0 秒
```

**按平均查询时间排序** → 先优化 **B**（因为 2.0 > 1.5）。
**但 B 一天才访问一次，优化它收益极低。**

**按总时间排序（`-s t`）**：
- A 总耗时 = 100 × 1.5 = **150 秒**
- B 总耗时 = 1 × 2.0 = **2 秒**

→ **A 的"影响"远大于 B**，应该**优先优化 A**。

> **结论**：**总时间反映的是"这条 SQL 对系统的实际影响"**——
> 而平均时间只反映"单次有多慢"。**优化总时长最大的，通常收益最高。**

**优化的迭代逻辑**：

```
找出总耗时最大的 SQL → 优化它
      ↓
优化完，第二名变成第一名 → 继续优化
      ↓
如此迭代，逐步把性能问题清掉
```

> **所以只需要关注前 5 条 / 前 10 条**，不需要全看。

**日志文件里有什么**（分析时能筛的字段）：
时间、用户、主机、**查询时间**、**锁定时间**、**返回行数**、**扫描行数**。

### 五、下一步：优化阶段的套路与反例

**用 `EXPLAIN` 看查询计划**——它会返回一条或多条记录，告诉我们**这条 SQL 慢在哪里**。

**常见优化策略**：如**把子查询改写成 JOIN**（因为子查询可能全表扫描）。

**⚠️ 但策略未必好使（这段很实用）**：

> **两个大表直接 JOIN 会非常慢。**
>
> 但可以换个顺序：
> ```
> ① 先用 B 表的条件把数据范围缩到几十 / 100 条以内
> ② 把这个小结果集做成临时表（temp）
> ③ 再让 A 表去 JOIN 这个 temp
> ```
> **即使 temp 是全表扫描、即使它占内存，也比"大表直接 JOIN 大表"快得多。**
>
> **结论：先缩小数据范围，再做 JOIN。**

> **提示**：优化策略都是"可参考"的，**必须结合实际业务和实际情况判断哪种更优**，
> 不存在放之四海皆准的套路。
