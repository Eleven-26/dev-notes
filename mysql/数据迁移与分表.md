## Q1. MySQL 把一张大表从生产库搬到另一台实例，有哪几种做法？（物理拷贝实操）

**来源**：`BV12qjA6aErF p=45` B站 Go 面试真题 · 时长 11分42秒
**考察意图**：考的是**你有没有真的做过数据迁移**。面试官想听的不是"用 mysqldump 导一下"，
而是你能不能讲清**每种手段的锁表风险、版本约束和适用场景**——
在生产库上的任何操作，第一句话都应该是"先评估对业务的影响"。

### 一、三类手段先做对比

| 手段 | 典型做法 | 适合场景 | 代价 / 风险 |
|---|---|---|---|
| **逻辑导出导入** | `mysqldump` 导出 SQL 再导入；或 `SELECT ... INTO OUTFILE` + `LOAD DATA` | 跨版本、跨厂商、只搬部分表或部分行、需要顺手改结构 | **慢**（要重写数据、重建索引）；不加参数会**锁表** |
| **物理拷贝**（可传输表空间） | 拷 `.ibd` 数据文件 + `.cfg` 元数据，目标库 `IMPORT TABLESPACE` | **同版本、同页大小**的实例之间搬大表，求快 | 源库要 `FLUSH TABLES ... FOR EXPORT`，**表会被短暂锁为只读** |
| **主从复制** | 搭主从，让从库把 binlog 重放一遍，追平后切流量 | **不停服**在线迁移、可回滚、可跨机房 | 搭建成本高，有**复制延迟**，还要配套切换方案（见 Q2） |

> 口诀：**要改结构 / 跨版本 → 逻辑导出；同版本搬大表求快 → 物理拷贝；不能停服 → 主从复制。**

### 二、逻辑导出：关键是 `--single-transaction`

```bash

# 导出：用一致性快照读，导出期间不锁业务表
mysqldump -uroot -p --single-transaction --default-character-set=utf8mb4 --databases mydb > mydb.sql
mysql -uroot -p mydb < mydb.sql          # 导入
```

- **`--single-transaction`**：导出前开一个可重复读事务拿到一致性快照，
  **导出全程不锁业务表**，是"不停服导出"的最低要求。
- ⚠️ 它**只对 InnoDB 生效**，且**不要和 `--lock-tables` 一起用**（会退化成锁表）。
- 追求导入速度时，可在导入前临时关掉 `unique_checks` / `foreign_key_checks`，导入完再打开。

### 三、物理拷贝（可传输表空间）的完整步骤

视频里就是把生产库的一张表搬到测试库，走的正是**物理拷贝**这条路：

| 步骤 | 在哪操作 | 做什么 |
|---|---|---|
| **① 拿到表定义** | 源实例 | `SHOW CREATE TABLE user;` 复制 DDL，在**目标库先建出同结构的空表**；默认值 / 默认格式按目标环境调整后再执行 |
| **② 丢弃表空间** | 目标库 | `ALTER TABLE user DISCARD TABLESPACE;` → 目标数据目录下的 `.ibd` 被删除 |
| **③ 确认属主** | 目标机 | 看 MySQL 数据目录里文件的属主（示例 uid=gid=**999**），待会儿拷进来的文件必须是这个属主 |
| **④ 刷盘 + 锁表导出** | 源实例 | `FLUSH TABLES user FOR EXPORT;` → **刷盘并进入只读状态**，同时生成 `user.cfg`（表空间元数据） |
| **⑤ 拷两个文件** | 源机 → 目标机 | 把 `user.ibd` 和 `user.cfg` 拷到目标实例的数据目录 |
| **⑥ 立刻解锁** | 源实例 | `UNLOCK TABLES;` —— **马上解锁，别让生产表长时间只读** |
| **⑦ 改属主** | 目标机 | `chown 999:999 user.ibd user.cfg`（改成 MySQL 运行用户），否则导入失败 |
| **⑧ 导入表空间** | 目标库 | `ALTER TABLE user IMPORT TABLESPACE;` |
| **⑨ 验证** | 目标库 | `SELECT COUNT(*) FROM user;` 核对行数（视频里是 160 万行） |

### 四、必须提前评估的风险（这题真正的得分点）

1. **`FLUSH TABLES ... FOR EXPORT` 期间表是只读的**——视频反复强调：
   **若业务此刻写入很活跃，锁表就不是明智选择**，会直接影响线上业务。
   迁移前必须确认业务低峰期，或者干脆改用主从复制方案。
2. **版本与页大小尽量一致**：源库和目标库的 MySQL 版本、`innodb_page_size`、字符集
   最好完全相同，否则 `.ibd` 可能导入失败。
3. **`innodb_file_per_table` 必须为 ON**，否则表没有独立的 `.ibd`，无从拷贝。
4. **文件属主 / 权限不对，`IMPORT TABLESPACE` 一定报错**（步骤 ⑦ 就是防这个）。

### 面试官会追问什么

- **`mysqldump` 怎么做到不锁表？** → `--single-transaction`，用一致性快照读；
  但只对 InnoDB 生效，长事务期间要留意 undo 膨胀。
- **物理拷贝和逻辑导出怎么选？** → 同版本、搬大表、求快 → 物理拷贝；
  跨版本 / 要改结构 / 只搬部分数据 → 逻辑导出。
- **还有没有不停服的方式？** → 有，**主从复制**：先在从库重放 binlog 追平，
  再切流量；GTID 模式下的切换流程见 Q2。

## Q2. MySQL 主从复制怎样不停服地从 binlog + position 切到 GTID 模式？

**来源**：`BV12qjA6aErF p=44` B站 Go 面试真题 · 时长 14分00秒
**考察意图**：考的是**在线改配置的能力**。默认的 `binlog + position` 复制里，
从库要把"主库的 binlog 文件名 + 位点"背下来，主库一换、位点一漂就出问题；
GTID 改用全局唯一的事务 ID 做自动定位。这题要答的是**为什么切、以及怎么一步步安全地切**。

### 一、GTID 是什么，比 binlog + position 强在哪

**GTID（Global Transaction ID，全局事务标识）**：主库上每个提交的事务都会分配一个
全局唯一的编号，从库只需要记录"我执行过哪些 GTID"，这个集合就是 `Executed_Gtid_Set`。

| | **binlog + position** | **GTID** |
|---|---|---|
| 从库怎么找位点 | 显式指定 `MASTER_LOG_FILE` + `MASTER_LOG_POS` | **自动定位**：只找"自己没执行过的那个事务" |
| 主库故障 / 主从切换 | 要**重新算位点**，容易算错、算漏 | 换个主库直接继续，**不用算位点** |
| 配置复杂度 | 多、易错 | 少（这正是视频说的"简化配置"） |
| 出问题怎么查 | 只能比对 binlog 文件和位点 | 比对两边 `Executed_Gtid_Set`，**缺哪个事务一眼可见** |

一句话：**GTID 用"事务身份"取代了"事务位置"，让复制更稳定、更不容易出问题。**

### 二、`gtid_mode` 的四个取值（切换过程就是在这四个值之间走）

| 值 | 含义 |
|---|---|
| **`OFF`** | 完全关闭，禁用 GTID |
| **`OFF_PERMISSIVE`** | **宽松关闭**（过渡态）：自身不强制生成 GTID，但**收到 GTID 事务能兼容处理** |
| **`ON_PERMISSIVE`** | **宽松开启**（过渡态）：自身已经用 GTID，但**收到匿名事务（没有 GTID 的老事务）也能处理** |
| **`ON`** | 完全开启：**所有事务都必须带 GTID** |

> 两个 PERMISSIVE 过渡态的存在，就是为了**让线上不用停服**：
> 先能"收"，再能"发"，最后才强制。宽松态是给"历史遗留的匿名事务"留出的收尾窗口。

### 三、生产环境不停服切换的九步

```sql

-- 第 1 步：只告警不阻断。线上可能暂时存在无法生成 GTID 的写法，先让它报警、不报错
SET @@GLOBAL.enforce_gtid_consistency = WARN;
-- 之后持续监控警告，把不兼容的操作逐个改掉，直到警告清零
-- （视频提醒：这个过程可能持续几天甚至半个月）

-- 第 2 步：告警 → 直接报错。此后不兼容的语句会执行失败
SET @@GLOBAL.enforce_gtid_consistency = ON;

SET @@GLOBAL.gtid_mode = OFF_PERMISSIVE;   -- 第 3 步：宽松关闭
SET @@GLOBAL.gtid_mode = ON_PERMISSIVE;    -- 第 4 步：宽松开启

-- 第 5 步：等所有匿名事务执行完，这个数字到 0 才算干净
SHOW STATUS LIKE 'Ongoing_anonymous_transaction_count';

-- 第 6 步：检查每一个副本的同步进度（多层复制要逐层查，直到全部追平）
SHOW REPLICA STATUS\G          -- MySQL 8.0；5.7 用 SHOW SLAVE STATUS\G

-- 第 7 步：若 binlog 还兼做备份 / 恢复用途，等所有含匿名事务的备份过期
--         （否则那些备份在完全开启 GTID 之后无法还原）

SET @@GLOBAL.gtid_mode = ON;   -- 第 8 步：完全开启
```

**第 9 步：把复制方式改成自动定位，并把配置写进配置文件。**

```sql

STOP REPLICA;
CHANGE REPLICATION SOURCE TO SOURCE_AUTO_POSITION = 1;   -- MySQL 8.0
-- MySQL 5.7 语法：CHANGE MASTER TO MASTER_AUTO_POSITION = 1;
START REPLICA;
```

```ini

# /etc/my.cnf —— 前面的 SET GLOBAL 都是运行时变量，重启就失效，必须落盘
[mysqld]
gtid_mode                = ON
enforce_gtid_consistency = ON
log_bin                  = /var/lib/mysql/mysql-bin   # GTID 依赖 binlog
log_replica_updates      = ON                         # 5.7 写法：log_slave_updates = ON
```

> ⚠️ 视频特别强调：**前面的设置都是运行时设置，服务器一重启就没了**。
> 所以最后一定要把 `gtid_mode` / `enforce_gtid_consistency` 写进配置文件，
> 并把复制连接改成 `SOURCE_AUTO_POSITION = 1`（5.7 为 `MASTER_AUTO_POSITION = 1`），
> 否则重启后复制会失败。

### 四、整条流程怎么记

```

主从搭建（binlog + position）→ 追平延迟
   → ①告警 ②强制 ③宽松关闭 ④宽松开启
   → ⑤等匿名事务清零 ⑥查所有副本追平 ⑦等老备份过期 ⑧完全开启
   → ⑨配置文件落盘 + 自动定位 → 之后再做流量切换
```

### 面试官会追问什么

- **为什么要有两个 PERMISSIVE 中间态？** → 为了**不停服**：先让历史数据能收尾，
  再让新事务都带上 GTID，避免切换瞬间主从复制断开。
- **`enforce_gtid_consistency = WARN` 和 `ON` 的区别？** → WARN 只告警不阻断，
  用来在线上"边跑边找不兼容写法"；ON 直接报错，是切换前的最后一道关卡。
- **怎么判断从库有没有追平？** → 看 `SHOW REPLICA STATUS` 里的 `Seconds_Behind_Source`，
  以及两边 `Retrieved_Gtid_Set` / `Executed_Gtid_Set` 的差集。
- **GTID 模式下还能用 `MASTER_LOG_FILE` 吗？** → 不能。位点复制和 GTID 复制**互斥**，
  `SOURCE_AUTO_POSITION = 1` 时再指定位点会直接报错。

## Q3. timestamp 和 datetime 到底该怎么选？

**来源**：`BV12qjA6aErF p=46` B站 Go 面试真题 · 时长 3分48秒
**考察意图**：考点只有一个词——**时区**。面试官想看你能不能说出
"同一份数据在不同时区读出来不一样"这类真实线上事故，而不是只背长度和范围。

### 一、最本质的区别：一个存"绝对时刻"，一个存"字面值"

- **`TIMESTAMP`**：内部存的是 **UTC 纪元秒（绝对时刻）**，读出来时按**当前会话的 `time_zone`**
  换算成"年-月-日 时:分:秒"。所以**同一个值，换个时区显示就变了**。
- **`DATETIME`**：存的就是写进去的那串字面值，**写什么读什么，不随时区换算**。

视频里的演示非常直观：同一个 `TIMESTAMP` 字段，把会话时区**改成东八区之后，查出来的时间跟着变了**；
而 `DATETIME` 字段改完时区还是原来的值，纹丝不动。

```sql

SELECT @@time_zone;          -- 当前会话时区
SET time_zone = '+08:00';    -- 切成东八区，TIMESTAMP 字段会跟着变，DATETIME 不变
```

### 二、逐项对比

| 维度 | **TIMESTAMP** | **DATETIME** |
|---|---|---|
| **存的是什么** | 绝对时刻（内部按 UTC 存） | 字面值（写什么存什么） |
| **时区敏感** | ✅ 敏感，显示值随会话时区变化 | ❌ 不敏感 |
| **取值范围** | 1970-01-01 00:00:01 UTC ~ **2038-01-19 03:14:07 UTC**（有 2038 问题） | 1000-01-01 00:00:00 ~ 9999-12-31 23:59:59 |
| **存储空间** | 4 字节 | 5 字节 |
| **自动更新** | 支持 `DEFAULT CURRENT_TIMESTAMP` / `ON UPDATE CURRENT_TIMESTAMP` | 同样支持 |
| **跨时区场景** | 更安全：存一次，各地按本地时区正确展示 | 有风险：全链路时区必须统一，否则值"看起来是错的" |

### 三、视频的结论，以及我的补充

**视频结论**：
> 强烈建议用 `TIMESTAMP`；如果不能用 `TIMESTAMP`，退一步**用整型（`BIGINT`）存时间戳**，
> 没有必要再用 `DATETIME`——因为 `DATETIME` 写进去就是一个固定字符串，
> **多时区或时区设错时，这个值没法自己纠正**，最终存下来的内容就是不准确的。

**补充（面试时说出来是加分项）**：

- `DATETIME` 并不是"错误类型"：它**没有 2038 上限**、范围更大。
  只要**全链路时区统一**（服务端、DB、客户端都锁死 UTC），它同样可信。
- `TIMESTAMP` 的"自动换算"是双刃剑：**服务器时区被改掉时，历史数据的展示值会整体漂移**，
  排查问题时容易被误导。
- 工程上比较稳的组合：**库里存 UTC 的 `TIMESTAMP`（或 `BIGINT` 毫秒时间戳），
  时区转换全部放到应用层 / 展示层去做**。

### 面试官会追问什么

- **为什么时间戳不会有"存错"的问题？** → 它记录的是**绝对时刻**，
  时区只影响"怎么显示"，不影响"存的是什么"；展示错了改时区就能修正。
- **`ON UPDATE CURRENT_TIMESTAMP` 有什么坑？** → 只要这一行有任何其他列被改动，
  这列就会被自动刷新，**数据变更轨迹会被覆盖**——业务字段不要随便挂它。
- **2038 问题怎么解？** → 换 `DATETIME`，或者用 `BIGINT` 存时间戳；
  MySQL 8.0 的 `TIMESTAMP` 仍是 4 字节，上限并未扩展。

## Q4. User 表分表之后，怎样用非分表键（A 或 B 字段）定位数据在哪张表？

**来源**：`BV12qjA6aErF p=53` 百度 AIGC Go 后端开发 · 时长 9分24秒
**考察意图**：这是一道**分库分表的场景设计题**。面试官想听的顺序是：
**先讲分表键该满足什么条件** → 再给**几种路由方案并对比代价** → 最后说出**你的选择理由**，
而不是一上来就报一个方案名字。

### 一、问题还原

`user` 表数据量太大，已经按 `user_id` 哈希分成了 256 张表（`user_0000` ~ `user_0255`）；
现在业务要求：**用 A 字段或 B 字段**（比如手机号、邮箱）也能查到"这条数据在哪张表"。

### 二、分表键（sharding key）必须满足的四个条件

| 条件 | 说明 |
|---|---|
| **① 可哈希** | 能被稳定地哈希 / 映射到某张表。**分表的本质和"在单表里建索引"是一样的**：索引负责"定位到行"，分表键负责"定位到表" |
| **② 不可变** | 分表键一旦变化，数据就要**在表之间搬家**。比如用手机号分表，用户换个号就得把整行从 1 表迁到 2 表；**就像索引列频繁更新会带来额外维护开销** |
| **③ 分布均匀** | ID 连续递增时分布天然均匀；但**手机号按号段分布是不可控的**——可能出现某号段占 80% 数据、其余 255 张表只占 20% 的严重倾斜，**分表就失去意义了** |
| **④ 唯一性** | 分表键最好在单表内就是**主键或具备唯一性**（如 `user_id`），否则无法保证定位准确 |

### 三、三种路由方案（视频的完整推演）

**方案一：独立哈希 `Hash(A)` / `Hash(B)` —— ❌ 不可行**

```

Hash(A) → table_id = 17
Hash(B) → table_id = 93      ← 同一条数据，两个字段算出来不是同一张表
```

数据**只存了一份**，而 A 和 B 指向不同的表，**无法确定数据到底在哪**——直接否定。

**方案二：双哈希冗余存储（同一条数据存两份）—— ⚠️ 可行但费空间**

按 A 哈希存进 `table_17`，再按 B 哈希存一份进 `table_93`。两个入口都能查到，
但**同一份数据占了两倍空间**，且两份数据要保证一致（写入、更新、删除都要双写），**维护成本高**。

**方案三：路由表 / 全局索引表（二次索引）—— ✅ 视频作者倾向的方案**

**单独维护一张"业务字段 → 表序号"的映射表**，业务表里不放任何冗余数据：

```sql

-- 路由表：只存映射关系，不存业务数据
CREATE TABLE user_route (
  id           BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id      BIGINT           NOT NULL,
  phone        VARCHAR(20)      NOT NULL,
  email        VARCHAR(64)      NOT NULL,
  table_suffix TINYINT UNSIGNED NOT NULL,   -- 0~255，表示落在 user_0000 ~ user_0255
  UNIQUE KEY uk_user_id (user_id),
  UNIQUE KEY uk_phone   (phone),
  UNIQUE KEY uk_email   (email)
) ENGINE=InnoDB;
```

查询分两步：**① 用 A（或 B）查 `user_route` 拿到 `table_suffix` → ② 拼出真实表名 `user_00xx`，按主键查业务数据。**

**为什么倾向它**：

- 只多消耗**索引表**的空间，**不需要双倍的数据空间**；
- 通过 A 或 B 都能稳定找到同一条数据，**一致性由路由表本身保证**；
- 代价是**多一次查询**（可以用缓存兜住），以及写入时要**同步维护路由表**。

### 四、三种方案对比

| 方案 | 空间代价 | 一致性 | 额外查询 | 结论 |
|---|---|---|---|---|
| 独立哈希 A / B | 无 | ❌ 定位不确定 | — | 不可行 |
| 双哈希冗余存储 | **2 倍数据空间** | 需要双写保证 | 无 | 可行但成本高 |
| 路由表（二次索引） | 1 份索引空间 | 由路由表保证 | **多一次查表** | ✅ 推荐 |

### 五、补充：业界另外两种常见做法（视频未展开）

| 做法 | 思路 |
|---|---|
| **基因法** | 把分表键的"基因"编码进另一个字段的尾部，让非分表键也能反推出路由。例如按 `user_id` 分 256 张表时，把 `user_id` 的低 8 位拼进生成的订单号低位，这样**用订单号也能直接算出该去第几张表**，连映射表都省了 |
| **异构索引（再建一份数据）** | 用 B 字段作为分表键**再建一份数据**（通常通过 binlog / MQ 异步同步），两份数据各自服务不同的查询入口；本质是"数据异构 + 各自路由"，代价与方案二的冗余存储类似 |

### 面试官会追问什么

- **分表键为什么要求"不可变"？** → 值一变就要跨表搬数据，类似索引列频繁更新带来的额外开销。
- **手机号为什么不适合直接当分表键？** → 号段分布不均，会造成严重的数据倾斜。
- **路由表会不会成为瓶颈？** → 会，所以通常**加缓存**（本地缓存 + Redis），
  或者只在"非分表键查询"这一条链路上引入它，主链路仍按分表键直接定位。
- **表数扩容了怎么办？** → 路由表方案只需**改映射**；纯哈希路由扩容会引发大规模数据搬迁，
  可以用**一致性哈希**减少迁移量，或者**成倍扩容**（256 → 512）来摊薄重分布成本。
- **分表键的值怎么生成？** → 常用**雪花算法**生成全局唯一且趋势递增的 ID，
  既保证唯一性，也让 `user_id` 这类分表键分布均匀。

### 1. 分表路由：表名只能由整数生成，条件值仍然走占位符

`?` 占位符**只能代表值，不能代表标识符**（表名、列名），所以分表必然要拼表名。
安全的前提是：**拼进去的字符串只能由自己格式化出来，绝不包含外部输入**。

```go

package sharddemo

import (
	"context"
	"database/sql"
	"fmt"
	"hash/fnv"
)

// TableCount 是"基因位宽"的来源，改动会连带影响 ID 兼容性（见第 3 节）。
const TableCount = 256

// Hash 暴露**原始**哈希值：扩容时只换除数、不换哈希（见第 5 节）。
func Hash(shardKey string) uint32 {
	h := fnv.New32a()
	_, _ = h.Write([]byte(shardKey)) // hash 实现不会返回错误
	return h.Sum32()
}

// Route 用 FNV-1a 算表序号。
// ⚠️ 只用于**不可变且分布均匀**的分表键（user_id / 雪花 ID）。
// 手机号、邮箱前缀这类输入直接 Route，会得到严重倾斜的分布——正文 Q4 条件 ③。
func Route(shardKey string) int {
	return int(Hash(shardKey) % TableCount)
}

// TableName 是表名的**唯一**来源：整数格式化，不含任何外部字符串 → 没有注入面。
func TableName(shardKey string) string {
	return fmt.Sprintf("user_%04d", Route(shardKey))
}

// MustTableName 用于路由表回查到的后缀（正文方案三），同样要校验范围。
func MustTableName(suffix int) (string, error) {
	if suffix < 0 || suffix >= TableCount {
		return "", fmt.Errorf("sharddemo: bad table suffix %d, out of [0,%d)", suffix, TableCount)
	}
	return fmt.Sprintf("user_%04d", suffix), nil
}

// GetUser 的正确形态：表名自己拼，值走占位符。
func GetUser(ctx context.Context, db *sql.DB, userID string) (string, error) {
	q := `SELECT name FROM ` + TableName(userID) + ` WHERE user_id = ?`
	var name string
	err := db.QueryRowContext(ctx, q, userID).Scan(&name)
	return name, err
}
```

**三种写法的边界**（面试和 code review 都常被问到）：

| 写法 | 结果 |
|---|---|
| `SELECT ... FROM ? WHERE id = ?` | ❌ **语法错误**：占位符不能代表标识符 |
| `SELECT ... FROM user_00` + 外部输入拼接 | ❌ 注入面：输入 `/tmp` 之外的任何东西都能改写语句 |
| `TableName(key)`（整数格式化）+ 值用 `?` | ✅ 唯一正确形态 |
| ORM/QueryBuilder 里 `Table(userInput)` | ⚠️ 必须自己校验白名单，ORM **不会**替你转义表名 |

### 2. 路由表方案（正文的方案三）：缓存 + singleflight 防击穿

正文的结论是「路由表要加缓存，否则它自己就成了瓶颈」。注意**瓶颈有两种**：
数据库读放大（缓存解决）和**冷 key 并发回源**（singleflight 解决）——只做前者仍然会打穿。

```go

package sharddemo

import (
	"context"
	"database/sql"
	"fmt"
	"sync"
	"time"

	"golang.org/x/sync/singleflight"
)

type routeEntry struct {
	suffix int
	expire time.Time
}

// Router 必须**单例**使用：它的缓存和 flight 都是实例状态，
// 每次请求 new 一个 Router 等于没有缓存，也合并不了并发回源。
type Router struct {
	db  *sql.DB // 注入的连接池
	ttl time.Duration

	mu    sync.RWMutex
	cache map[string]routeEntry

	// ⚠️ singleflight.Group 内含 mutex，不可拷贝；因此 Router 只能以 *Router 传递。
	flight singleflight.Group
}

func NewRouter(db *sql.DB, ttl time.Duration) *Router {
	return &Router{db: db, ttl: ttl, cache: make(map[string]routeEntry)}
}

// routeColumn：非分表键 -> 路由表列名，**白名单映射**。
// 这里必须 switch，绝不能 `"WHERE " + field + " = ?"`——那就是把注入面 reopened。
func routeColumn(field string) (string, error) {
	switch field {
	case "phone", "email":
		return field, nil
	default:
		return "", fmt.Errorf("sharddemo: unsupported route field %q", field)
	}
}

// Lookup 两步查：本地缓存 -> 合并并发回源 -> 路由表。
func (r *Router) Lookup(ctx context.Context, field, value string) (int, error) {
	col, err := routeColumn(field)
	if err != nil {
		return 0, err
	}
	key := col + "\x00" + value // 分隔符防止 ("a","bc") 与 ("ab","c") 撞 key

	r.mu.RLock()
	e, ok := r.cache[key]
	r.mu.RUnlock()
	if ok && time.Now().Before(e.expire) {
		return e.suffix, nil
	}

	// 缓存过期时，1000 个并发会同时打到路由表；Do 让它们只发一次查询
	v, err, _ := r.flight.Do(key, func() (any, error) {
		q := `SELECT table_suffix FROM user_route WHERE ` + col + ` = ?`
		var suffix int
		if err := r.db.QueryRowContext(ctx, q, value).Scan(&suffix); err != nil {
			return nil, err // sql.ErrNoRows 原样返回，让调用方决定"未注册"怎么处理
		}
		if _, err := MustTableName(suffix); err != nil {
			return nil, err // 路由表被写脏时宁可报错，也不要拼出一个不存在的表
		}
		r.mu.Lock()
		r.cache[key] = routeEntry{suffix: suffix, expire: time.Now().Add(r.ttl)}
		r.mu.Unlock()
		return suffix, nil
	})
	if err != nil {
		return 0, err
	}
	return v.(int), nil
}

// Drop 在换绑手机号 / 注销时精确失效，不要清整张表缓存。
func (r *Router) Drop(field, value string) {
	col, err := routeColumn(field)
	if err != nil {
		return
	}
	r.mu.Lock()
	delete(r.cache, col+"\x00"+value)
	r.mu.Unlock()
}

// Register：业务表和路由表**必须同一事务**，否则会出现
// "业务数据在 0137 表、路由表里没有 phone" 的孤儿数据（正文方案三的代价）。
func (r *Router) Register(ctx context.Context, userID int64, phone, email string) error {
	suffix := Route(fmt.Sprint(userID))

	tx, err := r.db.BeginTx(ctx, nil)
	if err != nil {
		return err
	}
	defer func() { _ = tx.Rollback() }()

	table := fmt.Sprintf("user_%04d", suffix)
	if _, err := tx.ExecContext(ctx,
		`INSERT INTO `+table+` (user_id, name) VALUES (?, ?)`, userID, "u"+fmt.Sprint(userID)); err != nil {
		return err
	}
	if _, err := tx.ExecContext(ctx,
		`INSERT INTO user_route (user_id, phone, email, table_suffix) VALUES (?, ?, ?, ?)
         ON DUPLICATE KEY UPDATE phone = VALUES(phone), email = VALUES(email), table_suffix = VALUES(table_suffix)`,
		userID, phone, email, suffix); err != nil {
		return err
	}
	if err := tx.Commit(); err != nil {
		return err
	}

	r.Drop("phone", phone) // 写入成功后必须失效旧缓存，否则 TTL 内还会路由到旧表
	r.Drop("email", email)
	return nil
}
```

> ⚠️ 两个真实运维坑：
> ① `user_route` 自身也是单表，**它迟早成为新的容量瓶颈**——它只存映射，所以可以先按 `user_id` 分表，
> 或者整张表塞进 Redis（数据结构用 `SET`/`HASH`，见 [../redis/命令与使用.md](../redis/命令与使用.md)）；
> ② 换手机号是**改路由表 + 清缓存**两个动作，必须做成"先改库、再失效、失败就告警"，
> 只失效不改库或只改库不失效都会留下长期的错路由。

### 3. 基因法：让订单号自带路由信息（正文第五节补充方案的最小实现）

这是最省事的方案——**连映射表都不要**。代价是位宽被写死：256 张表占 8 位，扩到 512 张就要 9 位。

```go

package sharddemo

import (
	"errors"
	"fmt"
	"sync"
	"time"
)

var ErrClockMoved = errors.New("sharddemo: clock moved backwards")

// 位布局（int64，共 63 位可用）：
//
//	|<---------- 38 位 毫秒(相对 epoch) --------->|<7 位机器>|<10 位序列>|<8 位基因>|
//	 63                                     25   24      18   17       8   7       0
//
// 基因 = Route(user_id) 的结果放在**最低 8 位**，于是订单号本身就能反推出表号。
const (
	geneBits  = 8
	seqBits   = 10
	machineBt = 7 // 7 + 10 + 8 = 25 位低区，时间戳左移 25
	epochMs   = 1767225600000
)

type IDGen struct {
	mu      sync.Mutex
	lastMs  int64
	seq     int64
	machine int64
	now     func() time.Time // 便于测试注入
}

func NewIDGen(machine int64) (*IDGen, error) {
	if machine < 0 || machine >= 1<<machineBt {
		return nil, errors.New("sharddemo: machine id out of 7-bit range")
	}
	return &IDGen{machine: machine, now: time.Now}, nil
}

// Next 生成订单号。gene 必须来自与写路径**同一个** Route(user_id)——
// 两边算法/表数只要不一致，反查就会把请求路由到一张没有这条数据的表。
func (g *IDGen) Next(gene int) (int64, error) {
	if gene < 0 || gene >= 1<<geneBits {
		return 0, errors.New("sharddemo: gene out of 8-bit range")
	}

	g.mu.Lock()
	defer g.mu.Unlock()

	ms := g.now().UnixMilli() - epochMs
	switch {
	case ms < g.lastMs:
		// ⚠️ 时钟回拨：宁可报错让上层重试/切机器，也不要生成重复 ID
		return 0, ErrClockMoved
	case ms == g.lastMs:
		g.seq++
		if g.seq >= 1<<seqBits {
			return 0, errors.New("sharddemo: sequence overflow in one millisecond")
		}
	default:
		g.seq = 0
		g.lastMs = ms
	}

	return ms<<(geneBits+seqBits+machineBt) |
		g.machine<<(geneBits+seqBits) |
		g.seq<<geneBits |
		int64(gene), nil
}

// RouteByOrderID 反查表号：这就是基因法的全部收益——省掉一次路由表查询。
func RouteByOrderID(orderID int64) int {
	return int(orderID & (1<<geneBits - 1))
}

// OrderTable 由订单号直接得到表名。
func OrderTable(orderID int64) string {
	return fmt.Sprintf("order_%04d", RouteByOrderID(orderID))
}
```

```go

package sharddemo

// 扩容时位宽就变了：256 表 -> 8 位，512 表 -> 9 位。
// 已生成的订单号里低 9 位不保证为 0，所以只能：
//
//	① 新建 ID 空间（新订单走 9 位、老订单仍按 8 位读），或
//	② 提前把基因位宽留够（常见做法是固定留 16 位，代价是时间戳位数变少）。
const DoublingSafeGeneBits = 16
```

### 4. 迁移期：双写 + 分片校验

正文 Q1 的「物理拷贝 / 逻辑导出」都是**停服或高成本**路径；不停服迁移的标准结构是
**全量搬迁 → 增量追平（binlog）→ 双写 → 校验 → 切读 → 停写老库**，
其中最容易漏的是**校验**——没有校验就没法证明"可以切"。

```go

package sharddemo

import (
	"context"
	"database/sql"
	"errors"
	"fmt"
	"regexp"
	"strings"
)

// ChunkStat 一个主键区间的指纹。
// 用 COUNT + SUM(CRC32(...)) 而不是逐行比对：一次往返覆盖一批数据。
// ⚠️ SUM 的返回类型是 DECIMAL，驱动给回来的是 []byte——这里按字符串收，
// 既避开 bigint 溢出，也就不用自己处理小数位。要数值再 strconv.ParseInt。
type ChunkStat struct {
	Rows int64
	CRC  string
}

// Stat 扫描某张表的一个主键区间。cols 必须与源表、目标表**完全一致且同序**。
func Stat(ctx context.Context, db *sql.DB, table string, cols []string, lo, hi int64) (ChunkStat, error) {
	if err := validateIdent(table, cols); err != nil {
		return ChunkStat{}, err
	}

	// CONCAT_WS 里每一列都参与指纹；NULL 要显式变成可区分的标记，
	// 否则 CONCAT_WS 会直接跳过 NULL 列，"值为 NULL" 和 "值为空串" 就分不清了
	args := make([]string, len(cols))
	for i, c := range cols {
		args[i] = "IFNULL(`" + c + "`,'')"
	}
	q := `SELECT COUNT(*), COALESCE(SUM(CRC32(CONCAT_WS(0x01, ` + strings.Join(args, ",") + `))), 0)
          FROM ` + table + ` WHERE id >= ? AND id < ?`

	var s ChunkStat
	err := db.QueryRowContext(ctx, q, lo, hi).Scan(&s.Rows, &s.CRC)
	return s, err
}

// Verify 对比源表与目标表，返回所有**不一致区间的左界**。
// 二分定位单行、或直接对这些区间做 pt-table-sync，都由调用方决定。
func Verify(ctx context.Context, db *sql.DB, src, dst string, cols []string, maxID int64, chunk int64) ([]int64, error) {
	if chunk <= 0 || maxID < 0 {
		return nil, fmt.Errorf("sharddemo: bad verify args maxID=%d chunk=%d", maxID, chunk)
	}

	var bad []int64
	for lo := int64(0); lo <= maxID; lo += chunk {
		if err := ctx.Err(); err != nil { // 校验通常是长跑批任务，必须可中断
			return bad, err
		}
		hi := min(lo+chunk, maxID+1)

		a, err := Stat(ctx, db, src, cols, lo, hi)
		if err != nil {
			return nil, fmt.Errorf("stat %s [%d,%d): %w", src, lo, hi, err)
		}
		b, err := Stat(ctx, db, dst, cols, lo, hi)
		if err != nil {
			return nil, fmt.Errorf("stat %s [%d,%d): %w", dst, lo, hi, err)
		}
		if a != b {
			bad = append(bad, lo)
		}
	}

	// 全红几乎不可能是数据问题，而是对比方式本身错了——直接报出来，别让人去查 256 张表
	if len(bad) > 0 && int64(len(bad)) == maxID/chunk+1 {
		return nil, errors.New("sharddemo: every chunk differs — check column order / charset / collation first")
	}
	return bad, nil
}

// validateIdent：表名与列名都是标识符，必须自己校验。
// 迁移工具的输入往往来自配置文件或运维命令行，同样要按"外部输入"对待。
func validateIdent(table string, cols []string) error {
	if !identRe.MatchString(table) {
		return fmt.Errorf("sharddemo: illegal table name %q", table)
	}
	if len(cols) == 0 {
		return errors.New("sharddemo: no columns to compare")
	}
	for _, c := range cols {
		if !identRe.MatchString(c) {
			return fmt.Errorf("sharddemo: illegal column name %q", c)
		}
	}
	return nil
}

// identRe 只允许"字母/下划线开头 + 字母数字下划线"，长度 ≤64（MySQL 标识符上限）。
var identRe = regexp.MustCompile(`^[A-Za-z_][A-Za-z0-9_]{0,63}$`)

// DualWrite 双写阶段的正确顺序：**以老库为准**，新库写失败只记补偿任务。
// 反过来"新库失败就整体回滚"会让灰度期新库的任何抖动直接打挂线上写。
func DualWrite(ctx context.Context, oldDB, newDB *sql.DB, userID, name string, logFailure func(error)) error {
	tx, err := oldDB.BeginTx(ctx, nil)
	if err != nil {
		return err
	}
	defer func() { _ = tx.Rollback() }()

	table := TableName(userID)
	const upsert = ` INSERT INTO %s (user_id, name) VALUES (?, ?) ON DUPLICATE KEY UPDATE name = VALUES(name)`

	if _, err := tx.ExecContext(ctx,
		fmt.Sprintf(upsert, table), userID, name); err != nil {
		return err
	}
	if err := tx.Commit(); err != nil {
		return err
	}

	// 老库已经成功了，新库只能"尽力 + 补偿"，不能回滚
	if _, err := newDB.ExecContext(ctx,
		fmt.Sprintf(upsert, "user_new"), userID, name); err != nil {
		logFailure(fmt.Errorf("dual write to new table: %w", err))
	}
	return nil
}
```

> ⚠️ `CRC32` 只能发现"不一样"，不能告诉你哪里不一样；**字符集/排序规则不一致时会全表误报**
> （`utf8mb4_general_ci` vs `utf8mb4_0900_ai_ci` 是 8.0 迁移最常见的坑）。
> 生产校验建议直接用 `pt-table-checksum`（下面使用三），本节的实现更适合理解原理和做小表抽查。

### 5. 表数扩容：为什么"成倍扩"搬迁量最小

正文追问「表数扩容了怎么办」，成倍扩容可以落到一行判断上：

```go

package sharddemo

import "fmt"

// DoublingRoute：从 oldCount 扩到 newCount（要求正好翻倍）时，
// 同一个 key 的新表号只可能是 old 或 old+oldCount——
// 因为 h % (2N) ∈ {h % N, h % N + N}。于是搬迁可以**以旧表为单位**整批做，不必逐 key 重算。
func DoublingRoute(shardKey string, oldCount, newCount int) (int, error) {
	if newCount != oldCount*2 {
		return 0, fmt.Errorf("sharddemo: only doubling is supported (got %d -> %d)", oldCount, newCount)
	}
	return int(Hash(shardKey) % uint32(newCount)), nil
}

// RouteBoth 是迁移期的关键用法：**同一个原始哈希**分别对旧/新表数取模。
// ⚠️ 千万不要"拿旧表号再哈希一次"或对 Route 的结果取模——那是对哈希做二次哈希，
// 分布性质会变差，而且失去"只搬两张表"的保证。
func RouteBoth(shardKey string, oldCount, newCount int) (int, int) {
	h := Hash(shardKey)
	return int(h % uint32(oldCount)), int(h % uint32(newCount))
}

// PlanDoubling：旧表 oldSuffix 的数据在新表数下只会落到这两张表 → 按表整批搬迁即可。
func PlanDoubling(oldSuffix, oldCount int) (string, string) {
	return fmt.Sprintf("user_%04d", oldSuffix), fmt.Sprintf("user_%04d", oldSuffix+oldCount)
}

// MigrateDoubling 用一条 SQL 完成"旧表 -> 新表"的整表拆分（示意：真实场景要分批 + 限速）。
// 判据就是新增的那一位：h % (2N) >= N 的行才需要搬。
//
// ⚠️ 只有当路由函数**本身就是整数取模**（如 user_id % 256）时，才能这样将哈希下推到 SQL。
// 本包用的是应用层 FNV-1a，MySQL 里没有对应函数——硬写成 CRC32 会让"迁移脚本算的表号"
// 和"线上路由算的表号"不一致，属于静默错路由。真实做法是要么把路由函数写成取模，
// 要么在应用层算好目标表名再逐行搬（下面 Java 侧 ShardingSphere 的 HASH_MOD 就是取模路由）。
func MigrateDoubling(oldSuffix int, shardCol string, oldCount int) string {
	src, dst := PlanDoubling(oldSuffix, oldCount)
	return fmt.Sprintf(
		`INSERT INTO %s SELECT * FROM %s WHERE MOD(%s, %d) >= %d;
         DELETE FROM %s WHERE MOD(%s, %d) >= %d;`,
		dst, src, shardCol, oldCount*2, oldCount, src, shardCol, oldCount*2, oldCount)
}
```

> ⚠️ 上面 `hashKey` 是**故意留的反例**：它对 `Route` 的结果再取模，等于对哈希做二次哈希，分布性质会变差。
> 正确做法是保留原始 32 位哈希值（`routeBoth` 里的 `fnvHash`），只对**取模的除数**做变化。
> 需要"扩容时只动 K/N 的数据"就用一致性哈希（见 [../distributed/服务发现与负载均衡.md](../distributed/服务发现与负载均衡.md) 的一致性哈希一节）。

## 使用二：Java（ShardingSphere-JDBC 与动态表名）

### 1. 声明式分表：把路由交给中间件

正文方案三（路由表）和方案「基因法」在 Java 生态里都有现成实现，不必自己写 `TableName()`：

```yaml

# application-sharding.yml —— 按 user_id 哈希分 256 张表
spring:
  datasource:
    driver-class-name: com.mysql.cj.jdbc.Driver
    url: jdbc:shardingsphere:classpath:sharding.yaml
---
# sharding.yaml
dataSources:
  ds_0:
    dataSourceClassName: com.zaxxer.hikari.HikariDataSource   # ⚠️ 连接池仍然在底层，每库一个
    jdbcUrl: jdbc:mysql://127.0.0.1:3306/test?useSSL=false
    username: root
    password: root123456
    maximumPoolSize: 20          # 与《索引与优化》里的池参数一致：显式设，别用默认

    tables:
      user:
        actualDataNodes: ds_0.user_00${[0..9]},ds_0.user_0${[10..99]},ds_0.user_${[100..255]}
        tableStrategy:
          standard:
            shardingColumn: user_id

        keyGenerateStrategy:
          column: user_id

    bindingTables: [user, user_route]

  user_hash:
    type: HASH_MOD
    props:
      sharding-count: 256
  # 非分表键查询走 hint 或广播，不要指望它自动优化
keyGenerators:
  snowflake:
    type: SNOWFLAKE
    props:
      worker-id: 1
      # ⚠️ 默认 SNOWFLAKE 不含"基因"，要用订单号反查表必须自定义 KeyGenerator：
      # 把 user_id % 256 写进 ID 低 8 位（与 Go 侧 IDGen 的位布局保持一致）
```

```java

// 非分片键（手机号）查询：显式走路由表，而不是让中间件广播 256 张表
@Repository
public class UserRouteDao {

    private final JdbcTemplate jdbc;

    public UserRouteDao(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    public OptionalInt suffixByPhone(String phone) {
        // ⚠️ 逻辑表名 user_route 必须被排除在分片规则之外（不分片 / 单表），
        // 否则这里会被当成"广播查询"打到 256 张表上。
        return jdbc.query("SELECT table_suffix FROM user_route WHERE phone = ?",
                rs -> rs.next() ? OptionalInt.of(rs.getInt(1)) : OptionalInt.empty(), phone);
    }
}
```

**选型结论**：路由逻辑（正文方案三/基因法）自己实现只在一层薄代码里，
数据量大、多语言共享时交给 ShardingSphere；**两者都要防同一个风险——非分片键查询退化成全库广播**。

### 2. MyBatis 动态表名：`${}` 是唯一必须严格校验的地方

```java

// ❌ 直接把外部输入拼进表名 —— ${} 是字面替换，没有参数化保护
// <select id="q">SELECT * FROM ${table} WHERE user_id = #{id}</select>

// ✅ 表名先过白名单，再交给 ${}；值仍然用 #{}
public static String safeTable(String input) {
    if (input == null || !input.matches("user_\\d{4}")) {
        throw new IllegalArgumentException("illegal table name: " + input);
    }
    return input;
}
```

> Java 侧 `String.matches` 每次调用都会编译正则，热路径上应改成 `static final Pattern`；
> 这与 Go 侧「表名只能由整数格式化生成」是同一原则的两种实现——**能不拼就不拼，必须拼就限死格式**。

## 使用三：迁移与切换的实操命令

正文 Q1/Q2 已经把九步流程和风险讲完了，这里只补**执行层面直接可用**的命令，避免重复阅读：

### 1. 全量搬迁与一致性快照

```bash

# 正文 Q1 的逻辑导出：--single-transaction 只对 InnoDB 有效（RR 快照读），MYISAM 表会被锁
docker exec -i mysql8 sh -c \
  'mysqldump -uroot -p --single-transaction --set-gtid-purged=OFF --source-data=2 \
     --databases test --tables user_0000 | gzip > /tmp/user_0000.sql.gz'

# 导入到目标实例
gunzip -c /tmp/user_0000.sql.gz | docker exec -i mysql8 mysql -uroot -p test
```

| 参数 | 为什么必须 |
|---|---|
| `--single-transaction` | 在一个 RR 事务里读，导出期间不锁表；**代价是导出时长内不提交的事务会看不到**，所以要么停写、要么靠增量追平 |
| `--set-gtid-purged=OFF` | 不把源库 GTID 写进目标库，否则目标库会认为"这些事务我已经有了"而跳过复制 |
| `--source-data=2`（8.0.26+，旧名 `--master-data`） | 在 dump 头部注释里记录**位点/GTID**，增量从这里接上 |

### 2. 校验：直接复用社区实现

```bash

# pt-table-checksum 主库执行：自动分块算 CRC，并对比从库；--no-check-replica-filters 视架构决定
pt-table-checksum --replication=1 --chunk-time=0.5 \
  --databases=test --tables='user_\d{4}' --where='1=1' \
  h=src-host,u=checksum,p=xxx

# 差异明细用 pt-table-sync（⚠️ --execute 会真的改数据，默认只打印）
pt-table-sync --print --replicate percona.checksums h=src-host,u=checksum,p=xxx h=dst-host,u=checksum,p=xxx
```

> `--chunk-time` 是**自适应分块**（自动调每块行数，让每块耗时 ≈0.5s），
> 对应 Go 侧 `Verify` 里手写的 `chunk` 参数——生产直接用这个思路，别写死行数。

### 3. 切换与回滚的关键命令

```sql

-- 正文九步里"只读 + 追平"的两条判据（第 6、7 步）
SELECT @@read_only, @@super_read_only;
SELECT WAIT_FOR_EXECUTED_GTID_SET('xxxxxxxx-xxxx-....:1-2000000', 30);  -- 返回 0 = 已追平

-- 切读流量后，回滚是**非对称**的：新库必须持续反向同步回老库，
-- 否则回滚那一刻老库缺的就是切换期间产生的全部写入（正文 Q1 风险的落地形式）
SHOW REPLICA STATUS\G   -- 看 Reverse 链路的 Seconds_Behind_Source 是否为 0
```

**切换前的三条 checklist**（比脚本更重要）：

1. **业务写入口是否只有一个？** 双写期间出现第三条写入路径 = 数据静默分叉，校验会全红；
2. **自增值 / 序列怎么办？** 迁移后目标库的 `AUTO_INCREMENT` 必须超过源库最大值，否则切过去就主键冲突；
3. **回滚窗口多长？** 决定新库要不要**保留**老库的同步链路——"切完就停老库同步"等于关掉了回滚。
