## Q1. Redis 缓存雪崩是什么？如何解决和预防？

**来源**：`p=2` 滴滴 Go 后端一面 · 时长 7分57秒
**考察意图**：能否讲清"故障链路"，而不只是背"加随机过期时间"这一个招式。

### 现象与成因

一句话：**大量 key 在同一时刻集中过期，请求不再命中缓存，全部打到数据库，把数据库打挂**。

用数字描述这个链路更清楚：

| 环节 | 量级 |
|---|---|
| 每秒打到 Redis 的请求 | 10000 QPS |
| 其中真正需要落库的（下单等） | 约 100 QPS |
| 数据库承受能力 | 约 1000 QPS |

正常情况下 Redis 消化掉 99% 的流量，数据库只承担 100 QPS，很安全。
但一旦 `goods:*`、`user:*` 这类 key **在 1~2 秒内集中过期**，10000 QPS 会直接砸到数据库——
数据库每秒只能处理 1000，积压至少要 10 秒才能消化完，期间响应超时、连接池耗尽，最终**整个服务不可用**。

### 解决方案（按层次给）

**1）分散过期时间（最直观）**
不要统一设 1 小时/半小时，而是在某个区间内**取随机值**，例如：

```go

// 原本：所有 key 都是 1 小时过期 -> 同一时刻集中失效
// 改为：在 [0, 12h) 内随机，让失效点均匀打散
expire := time.Duration(rand.Intn(12*3600)) * time.Second
rdb.Set(ctx, key, val, expire)
```

效果：把"1~2 秒内集中过期"摊平到 12 小时上，数据库在这 12 小时里**分散分担压力**，不会瞬间被打垮。

**2）分散过期的副作用，必须一起回答（这是加分点）**

| 副作用 | 说明 | 应对 |
|---|---|---|
| 缓存利用率下降 | 大量 key 长期处于无效状态，读请求频繁回源重载 | 随机区间不要开太大，按业务容忍度取值 |
| 缓存与数据库不一致 | 商品信息已修改，但缓存还没到期，读到的仍是旧值 | ① 修改数据时**主动更新/删除缓存**；② 后台**定时任务**提前刷新（如 5 分钟巡检一次，发现快过期就动态续期并回源） |

**3）兜底：限流 + 熔断降级（保护数据库）**
即使缓存全部失效，也不能让流量无差别打到数据库。在数据库前做最后一层保护：

- 超过数据库处理能力（如 1000 QPS）的请求**直接拒绝**；
- 服务降级：牺牲一部分用户体验，**保住数据库和整体服务的可用性**。

不这么做的代价：数据库挂掉后，恢复可能要从半小时到一小时，期间服务完全不可用。

### 面试官会追问什么

- **随机过期时间会不会导致缓存命中率下降？** → 会，需要在"打散程度"和"命中率"之间按业务取平衡点。
- **缓存和数据库不一致怎么保证？** → 见上表：写时更新缓存 + 定时兜底刷新。
- **只有雪崩吗？** → 顺带区分三个概念：
  | 问题 | 成因 | 特征 |
  |---|---|---|
  | 缓存雪崩 | 大量 key 集中过期 / 缓存服务宕机 | 大面积回源 |
  | 缓存击穿 | **单个热点 key** 过期 | 单点高并发回源 |
  | 缓存穿透 | 查询**根本不存在的数据** | 每次都绕过缓存打到库，需布隆过滤器/空值缓存 |

**易错点**：只答"加随机过期时间"就结束。这是第一层，面试官想听的是**缓存失效后的兜底设计**。

## Q2. Redis 的淘汰策略有哪些？什么情况下触发？

**来源**：`p=7` 滴滴 Go 后端一面 · 时长 4分33秒
**考察意图**：是否清楚"淘汰"是内存不足时的兜底，而非日常清理手段。

### 什么时候触发

- **内存充足时：不触发淘汰**。过期 key 由另外两条路径清掉：
  1. **惰性删除**：访问 key 时顺带检查是否过期，过期就删；
  2. **定期删除**：后台线程周期性抽样扫描过期 key 并删除；
  3. 做**内存碎片整理**时，也会顺带清理过期 key。
- **内存达到 `maxmemory` 上限时：才开始触发淘汰策略**，腾出空间给后续写入。

### 三大类淘汰策略

**第一类：不淘汰（`noeviction`）**
内存满了新写入直接**报错**，但允许删除操作。
适用场景：**数据不允许丢失**（不只是当缓存用，还承担持久化职责）。
应对方式不是淘汰，而是**扩容 / 升配内存**。

**第二类：只在设置了过期时间的 key 中淘汰**
| 策略 | 含义 |
|---|---|
| `volatile-ttl` | 优先淘汰**剩余存活时间最短**的 key |
| `volatile-random` | 在设了过期时间的 key 中**随机**淘汰 |
| `volatile-lru` | 在设了过期时间的 key 中淘汰**最久未使用**的 |
| `volatile-lfu` | 在设了过期时间的 key 中淘汰**最不经常使用**的 |

**第三类：全库范围淘汰（不区分是否设了过期时间）**
`allkeys-lru`、`allkeys-random`、`allkeys-lfu`。
适用场景：这些数据**都可以丢**。

### 怎么选（面试答题逻辑）

1. **先问数据能不能丢**：不能丢 → `noeviction` + 业务层主动删除 + 扩容；
2. **能丢且冷热区分明显** → LRU 或 LFU；
   - 访问**频率差异大**（少数 key 极高频、大量 key 极低频）→ 优先 **LFU**，比 LRU 更能抵御"偶发批量扫描"污染；
   - 只看**最近是否被访问** → LRU；
3. 只关心"设了过期时间的 key" → 用 `volatile-*` 系列，缩小淘汰范围。

**易错点**：把淘汰策略当成"清理过期 key 的机制"。它是内存不足时才生效的兜底手段。

## Q3. Redis 分布式锁如何实现？需要考虑哪些问题？

**来源**：`p=9` 抖音 Go 一面 · 时长 12分57秒
**考察意图**：这是 Redis 题里**区分度最高**的一题。原理一句话就讲完，"需要考虑哪些问题"才是真正的考察点。

### 加锁与解锁原理

**为什么用 `SETNX` 而不是 `SET`？**
- `SET` 是**覆盖写**，多个节点同时执行都会成功，谁最后写谁生效 → 无法互斥；
- `SETNX` 是**"key 不存在时才写入"**，多个节点并发调用**只有一个能成功** → 天然实现互斥。

```go

ok, err := rdb.SetNX(ctx, lockKey, nodeUID, expire).Result()
```

解锁更简单：**删掉这个 key**。
但正因为"解锁 = 删 key"这条链路太简单，才引出了下面 6 个必须考虑的问题。

### 必须考虑的 6 个问题（逐条对应真实故障）

**① 加锁失败时的重试要"有间隔"**
加锁失败的节点必然要不断重试。如果**无间隔**地狂请求 Redis，会白白浪费 Redis 资源（自己打自己）。
→ 用**随机等待**打散，例如 50ms ~ 200ms（甚至 500ms），让请求错开。

**② 必须设置过期时间（`TTL`）**
不设 TTL 的风险：**持锁节点宕机，锁永远不释放**，所有其他节点全部阻塞。
→ 加锁时就要带上过期时间。

**③ 过期时间不够用，需要"续期"（watchdog）**
问题：TTL 到了但业务还没处理完，锁自动释放，**别的节点进来了** → 临界区被并发进入。
→ 后台启动一个**续期线程/协程**，定时检查：剩余时间小于阈值（如 TTL 的一半）就重新续到 5s / 10s。
→ **关键副作用（加分点）**：如果节点异常退出，续期线程也随之消失，TTL 自然到期释放锁——
这恰好**避免了宕机节点长期占锁**，是个"良性副作用"。

**④ 有必要时设置"业务超时时间"，避免无限续期**
如果调用第三方资源一直无响应，续期会一直续下去，锁永远不放。
→ 设置整体超时（通常 30s 或 60s，不需要太长），超时后**停止续期并自动解锁**。

**⑤ 解锁要防止"误删别人的锁"⚠️ 最经典的坑**

时序：
1. 节点 A 加锁，TTL 到期自动删除；
2. 节点 B 加锁成功；
3. 此时 A 的业务"反应过来了"，执行 `DEL key` → **把 B 的锁删掉了**。

→ 解法：**value 存节点唯一标识（UUID）**，删除前先校验：

```lua

-- 用 Lua 保证"判断 + 删除"的原子性
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

**⑥ 主从架构下的锁失效 → 需要 RedLock（防脑裂）**

故障场景：
- 锁**写入主节点**，但客户端可能**从从节点读**——A 在主节点加锁成功，B 访问从节点发现"没这个锁"，加锁也成功了；
- 更严重：主节点**在数据同步到从节点之前宕机**，新晋升的主节点没有这把锁 → 其他节点可以加锁成功，
  **同一段临界区逻辑被多个节点并发执行**。

→ 解法：**RedLock**——向多个**相互独立**的 Redis 节点申请锁，**多数节点成功**才认为加锁成功。
概率虽低但确实存在，属于必须知道的进阶点。

### 一句话总结（面试可直接背）

Redis 分布式锁，**加锁用 `SETNX` + 过期时间，解锁用"校验 UID 后删除"**；
真正要答的是六个问题：**重试防打爆 Redis、必须设 TTL、TTL 不够要续期、业务要设超时、
解锁防误删、主从要防脑裂**。这六个问题不一定要全部解决，按业务重要程度取舍。

## Q4. 一个 key 的访问量巨大该怎么办？（热 key / 大 key）

**来源**：`p=11` 抖音 Go 一面 · 时长 8分32秒
**考察意图**：面试官补充的追问场景。考的是**能不能先梳理清楚"热点 key 会引发哪些问题"**，
而不是直接抛解决方案。

### 第一步：先把三个概念分清楚（面试必答）

| 问题 | 成因 | 特征 |
|---|---|---|
| **缓存雪崩** | **大量** key 在**同一时间**大面积过期 | 请求大面积回源，数据库整体被打垮 |
| **缓存击穿** | **单个热点 key** 过期 | 单点高并发绕过缓存，直接打库，后果与雪崩类似 |
| **缓存穿透** | 查询**根本不存在的数据** | 缓存永远加载不上（库里也查不到），每次请求都落到库，缓存形同虚设 |

**击穿的解法**：
1. **热点 key 设置为永不过期**，由后台任务定时更新；
   或在**会影响热点数据的操作发生时主动更新**缓存；
2. **数据库保护手段**：熔断降级——
   数据库只接收它能承受的请求量，**超出的绝大部分请求直接抛弃**，保住数据库不被打死。

**穿透的解法**：布隆过滤器 / 缓存空值（本题未展开，面试常追问）。

### 第二步：热点 key 除了击穿，还会带来 3 个问题（这是加分点）

**① 单线程阻塞**
不管是单 key 还是多 key，只要有**巨量访问**都会有问题：
Redis 核心处理是**单线程模型**，所有命令进入**同一个命令队列**逐个执行。
巨量请求必然在队列里排队，导致整体延迟上升。
→ 单节点只能**升配**或**加节点**（集群 / 读写分离）。

**② 网络带宽过载**
如果这个 key 的 **value 很大**，而访问量又高，每次访问都是一次网络请求——
**带宽会被打满**，造成网络拥堵。

**③ 集群倾斜（最容易被忽略）**
Redis 集群**按 key 做哈希分片**，而**同一个 key 永远落在同一个分片节点上**。
于是所有对热点 key 的请求都压在这一个节点上：

> 做集群本来是为了**通过扩展规模提升并发处理能力**，
> 结果热点全打在单个节点上 → **一个节点特别忙，其他节点很闲**，集群白做了。

### 第三步：对应的解决方案

**① 多 key 打散（针对集群倾斜）**
把同一个 Value 复制成**多个内容相同的 key**，分散到不同节点：

```go

key := fmt.Sprintf("hot:item:%d:%d", itemID, rand.Intn(N)) // N 个副本
```

读请求随机挑一个 key 访问，把压力摊到 N 个节点上。

**② 大 Value 拆成多个小 key（针对带宽过载）**
按**使用场景**拆分，而不是一股脑塞一个 key 里。以用户信息为例：

| 使用频率 | 数据 | 建议 key |
|---|---|---|
| 高频（每次请求都用） | 用户名、token、昵称 | `user:base:{uid}` |
| 低频 | 收货地址、联系人、通讯录 | `user:addr:{uid}` |

原则：**不同需求获取不同数据**，只取用得到的字段，减少每次的网络传输量。

> 注意与方案 ① 的区别：①是**内容相同的多副本**，用于打散集群压力；
> ②是**内容不同的小 key**，用于减少单次传输量。**这两个不是一回事**，面试时别混。

**③ 应用层本地缓存（针对单线程阻塞）**
在应用进程内再加一层本地缓存，**减少对 Redis 的访问次数**。

本地缓存的过期设计有个技巧：
> **不依赖本地缓存自身的过期时间**，而是把 Redis 中的过期时间**作为数据一起缓存到本地**，
> 本地缓存读取时依据数据里携带的过期时间来判断是否过期。

**需要注意的新问题**：引入本地缓存后，**一致性链路变长了**——
本地缓存与 Redis 的一致性、Redis 与数据库的一致性，都要一并考虑。

### 面试答题结构（可直接套用）

```
① 先定义场景：这是"热点 key 击穿" + 集群倾斜问题
② 列出会引发的问题：单线程阻塞 / 带宽过载 / 集群倾斜
③ 逐个给方案：多副本打散 / 大 value 拆分 / 本地缓存 + 熔断降级兜底
④ 补充代价：引入本地缓存会带来一致性成本
```

## Q5. MySQL 与 Redis 有什么区别？各自的适用场景？

**来源**：`p=29` 百度 Go 开发日常实习面试 · 时长 4分39秒
**考察意图**：**不是考背诵，而是考你能不能根据业务场景决定用哪个**——
面试官真正想问的是"你懂不懂各自的取舍"。

### 五个维度对比

| 维度 | **MySQL** | **Redis** |
|---|---|---|
| **数据模型** | **关系型**数据库，表结构，有主外键关系 | **非关系型**，**键值对（KV）**模型 |
| **存储介质与性能** | **磁盘存储**，读写性能**受磁盘 IO 限制**，相对较慢 | **内存数据库**，读写**非常快** |
| **持久化** | **数据必须落盘**，持久化是核心职责 | **持久化是可选项**。通常作缓存用，**数据可丢，一般不需要考虑持久化** |
| **事务与一致性** | **完整 ACID 事务**：支持原子性、多种隔离级别、支持回滚，依赖 **redo log 强化持久性** | **事务不完整**：只有"命令打包顺序执行"。<br>执行**前**发生的错误可以整体不执行（放弃）；<br>执行**后**中途出错**没有回滚** |
| **适用场景** | **结构化数据的持久化**；支持**复杂查询**与**事务处理** | **高并发读写、缓存、实时数据处理** |

> ⚠️ **Redis 事务的准确表述**：`MULTI`/`EXEC` 只是把命令**排队后一次性顺序执行**，
> **不具备回滚能力**。入队时就报错的命令会导致整个事务被放弃（`EXECABORT`）；
> 但如果是运行时（执行中）报错（比如对字符串执行 `INCR`），**其他命令照样执行，不会有任何回滚**。
> 这是与 MySQL 事务最本质的差别。

### 三个必须答出来的点（原视频强调）

1. **数据模型**：MySQL 关系型 / Redis 非关系型——**必须能说出来**；
2. **存储**：MySQL 磁盘 / Redis 内存——**必须搞清楚**；
3. **适用场景**：MySQL 做**数据持久化**，Redis 通常用于**缓存**——**必须能证明（举例说明）**。

### 场景举例（这样答才算"会用"）

**例 1：用户登录系统**

| 数据 | 放哪 | 理由 |
|---|---|---|
| 用户 ID、密码、注册时间等**结构化信息** | **MySQL** | 这是**持久化**过程，数据不能丢 |
| **会话信息、登录状态、token** | **Redis** | **登录状态检查极其频繁**，需要 Redis 的高并发读写与实时处理能力 |

**例 2：电商秒杀**

| 环节 | 放哪 | 理由 |
|---|---|---|
| **订单** | 最终**落库到 MySQL** | 涉及钱和交易，必须持久化、必须强一致 |
| **库存扣减、分布式锁** | **Redis** | 秒杀瞬间**高并发**，Redis 内存操作能扛住，且能实现原子扣减与互斥 |

> **判断逻辑**：**数据能不能丢 → 能不能接受最终一致 → 访问频率高不高**。
> 丢不得、要强一致的落 MySQL；高频读写、能容忍短暂不一致的放 Redis。

### 面试官会追问什么

- **Redis 挂了数据不就丢了？** → 所以 Redis 只放**可重建**的数据（缓存、会话），
  真正的数据源始终是 MySQL；必要时开启 AOF/RDB 持久化提高抗风险能力。
- **为什么不用 MySQL 加内存缓存代替 Redis？** → MySQL 的 Buffer Pool 是**页级缓存**，
  无法按业务 key 做精细的过期/淘汰策略，也无法跨进程共享。
- **缓存与数据库的一致性怎么保证？** → Cache Aside（先更新库再删缓存）、
  延时双删、binlog 订阅（Canal）异步刷新等。（详见本册 Q1）

## Q6. Redis 与 MySQL 的性能量级差多少？缓存应该放在哪一层？

**来源**：`p=53` 小鹏后台开发二面（日常实习）· 时长 8分07秒
**考察意图**：Q5 讲的是"区别"，这题讲的是**"量级差多少"以及"如何用缓存把流量拦住"**——
**给出数字比描述形容词有说服力得多**。

### 一、先给量级数字（面试直接说这个）

| | **MySQL** | **Redis** |
|---|---|---|
| **单连接 QPS（简单查询/操作）** | **约 500 ~ 2000** | **约 10000 ~ 100000** |

> **两者不是一个量级**——差了 **1~2 个数量级**（约 10 倍到 50 倍）。
> **记住这两个数字区间，比说"Redis 很快"有效得多。**

### 二、为什么量级差这么多

- **MySQL** 是**磁盘存储**，受**磁盘 IO** 限制，还要做 SQL 解析、优化、事务、锁等；
- **Redis** 是**内存数据库**，纯内存操作 + 单线程无锁竞争模型。

### 三、正确架构：三层拦截，尽量别让请求打到数据库

```
用户请求
   ↓
① CDN（页面/内容缓存）      ← 静态页面在这里就被拦下了
   ↓
② Redis（热点数据缓存）      ← 大部分动态查询在这里被拦下
   ↓
③ MySQL（持久化存储）        ← 只有真正需要落库的请求才到这里
```

**① CDN 层的作用**：
> 如果有一万并发请求同一个页面，**这一秒内请求到的页面内容是一样的**，
> 那就**不需要走到后台**——CDN 上缓存页面即可。

**② Redis 层的作用（用"购物"举例，非常直观）**：

> 买一个东西，可能**查询请求发生上百次**（货比三家、挑型号、比款式），
> 但**最终下单请求只有一次**。
>
> 所以**商品、订单这类数据是典型的热点数据**，查询需求远大于写入需求。
> 把它们放进 Redis，**大量查询请求会被缓存拦截**；
> 只有**数据真正变化、订单真正成交时才落库**。

**③ MySQL 层**：承担**结构化数据的持久化**。

**量化收益（原视频的说法）**：
> 一万个请求进来，**最后打到 DB 的可能不到 100 个**——
> 这样**同样的数据库配置能承担更多的并发**。

**为什么必须这么设计**：
> **数据库本身并不方便扩展**。所以思路是：
> **尽可能让相同的配置达到更高的并发**——
> 加大量的缓存，甚至再加消息队列。
> （原视频提到很多 MySQL 相关的"高可用"，本质上是在用架构手段弥补单机扩展性的不足。）

### 四、⚠️ 引入缓存的代价（必须主动说）

> **加了一层缓存后，应用的请求量本身已经远超 MySQL 的承受能力**——
> 一旦**缓存层出问题**，所有请求会**直接砸到 MySQL**，
> **MySQL 会立刻崩溃**。
>
> 所以**必须同时考虑缓存三大经典问题**：**缓存穿透、缓存击穿、缓存雪崩**。
> （详见本册 Q1、Q4）

**这就是"用缓存"和"会缓存"的区别**：
**加了缓存就必须为缓存失效准备兜底方案。**

### 五、面试答题结构

```
① 给量级数字：MySQL 500~2000 / Redis 1万~10万 QPS
② 给架构分层：CDN → Redis → MySQL，逐层拦截
③ 给业务例子：商品查询上百次、下单只有一次 → 热点数据放 Redis
④ 给量化收益：1 万请求 → 打库不到 100
⑤ 主动说代价：缓存必须配三大问题的兜底，否则 MySQL 会被打崩
```

## Q7. Redis 的两种发布订阅分别怎么实现？

**来源**：`p=69` 腾讯云智后台开发一面 · 时长 5分18秒
**考察意图**：**很多人只知道第一种 Pub/Sub，不知道 Redis 5.0 还有 Stream**——
能讲清"两种"的差别就是本题的区分点。

### 总览：两种发布订阅

| | **① Pub/Sub（传统）** | **② Stream（Redis 5.0+）** |
|---|---|---|
| **消息存储** | **无**（没有消息存储中间件） | **可持久化** |
| **能否丢消息** | **可能丢失** | 不会（可持久化） |
| **能否读历史消息** | 后订阅者**拿不到历史消息** | 可以（按需从指定位置读） |
| **是否需要确认** | 无 | **有消费者组 + ACK 机制** |
| **类比** | **群聊** | **Kafka / RabbitMQ** |

### 一、Pub/Sub（传统发布订阅）

**特点**：

| 特征 | 说明 |
|---|---|
| **只在发布者和订阅者之间存在联系** | **没有消息存储的中间件** |
| **消息可能丢失** | 例如**发布者先发了消息，订阅者之后才订阅** → 订阅者拿不到这条 |
| **后续消息都能收到** | 订阅之后的消息可以正常收到 |
| **广播语义** | **所有订阅了同一频道的订阅者都能收到该频道的所有消息** |

**类比（很好记）**：
> 就像**群聊**——只要有人进了群，
> 之后有人发一条消息，**所有群成员都能收到**。

**局限**：**没有"消息确认"机制**，无法保证"这条我处理过了、不要再发给我"。

### 二、Stream（Redis 5.0 引入）

**定位**：**可以持久化的消息队列数据结构**——
在一定程度上和 **Kafka、RabbitMQ 是类似的**，可以承担消息队列的角色。

#### 四个核心概念

```
消息日志（Stream） + 生产者 + 消费者 + 消费者组
```

#### 基本操作

**① 发布消息：`XADD`**

```bash

XADD mystream * field1 value1 field2 value2
```

> **`*` 表示消息 ID 自动生成**——因为**每条消息都有一个唯一 ID**。
> 一条消息里可以带**多个字段**。

**② 普通读取：`XREAD`（不推荐）**

```bash

XREAD BLOCK 0 STREAMS mystream $
```

> 客户端**阻塞读取** Stream。多个客户端同时阻塞读取时，
> 只要有 `XADD` 添加一条数据，**所有在读的客户端都能收到**。
>
> ⚠️ **但它没有消息确认机制**——
> 如果你想"我消费过了，不要再收到"，**只能人为处理**。
> **所以这种方式一般不用**。

**③ 消费者组方式（推荐）**

**创建消费者组**：

```bash

XGROUP CREATE mystream mygroup $      # $：从最新记录开始消费（之前的读不到）
XGROUP CREATE mystream mygroup 0      # 0：从最开始的位置消费（能读到历史记录）
```

> **消费者组的语义**：同一类型的消费者放在一个组里，
> **组内任何一个消费者消费了这条记录，就认为该记录已被消费**（互斥分发，不重复投递）。

**读取消息：`XREADGROUP`**

```bash

XREADGROUP GROUP mygroup consumer1 COUNT 1 STREAMS mystream >
```

**⚠️ `>` 和 `0` 的区别（这是最容易搞混的点）**：

| 标识 | 含义 |
|---|---|
| **`>`** | 读取一条**从未被任何消费者读取过的新数据**。<br>→ 组内有 10 个消费者时，**实际上只有一个消费者能读到这些新数据** |
| **`0`** | 读取**历史未确认的数据**（从指定 ID 开始找**第一条未确认**的记录） |

**消息确认：`XACK`**

```bash

XACK mystream mygroup <消息ID>
```

> 处理完业务后，**用 `XACK` 显式确认**，这条消息才算真正消费完成。
> （消息 ID 在读取时就能拿到，直接传进来即可。）

**适用场景**：和 **RabbitMQ、Kafka 类似的场景**——
需要**可靠投递、消费者组、消息确认**的消息队列需求。

### 三、怎么选（面试答题落点）

| 需求 | 选择 |
|---|---|
| **实时广播、允许丢消息** | **Pub/Sub**（更简单，如配置推送、轻量通知） |
| **需要可靠投递、消费者组、能重放** | **Stream**（如订单异步处理、事件驱动） |

> **答题亮点**：**主动说出"Pub/Sub 没有持久化和 ACK，所以只适合允许丢失的广播场景；
> 需要可靠性就用 Stream 或者干脆上 Kafka"**——
> 这说明你不只是"用过 API"，而是**理解两者的定位差异**。

### 面试官会追问什么

- **Pub/Sub 适合做业务消息队列吗？** → **不适合**。无持久化、
  订阅者掉线期间的消息永久丢失、无 ACK 重投。**只适合"丢了也没关系"的广播**。
- **Stream 相比 Kafka 的劣势？** → 单机/单分片吞吐和扩展性远不如 Kafka，
  集群方案不成熟；**适合中小规模**，超大规模仍应上 Kafka。
- **Redis 挂了消息会丢吗？** → 取决于持久化配置（AOF everysec 最坏丢 1 秒），
  以及主从切换是否丢同步中的数据。**要求严格不丢就不能只靠 Redis**。

## Q8. Redis 缓存和本地缓存该如何取舍？

**来源**：`BV1xSRXBwEeM p=36` 百度 Go 后端二面 · 时长 8分38秒
**考察意图**：很多人一听到"缓存"就默认 Redis。这题考的是**能不能说清"什么场景根本不需要中心化缓存"**——
先判断本地缓存能不能解决，而不是无脑上 Redis。

### 一、先纠正前提：这不是二选一

> **Redis 与本地缓存不是非此即彼的取舍**，而是"什么场景适合用什么"。
> 适合本地缓存的就用本地缓存，适合 Redis 的用 Redis，**两者可以配合使用**。

判断顺序：**能用本地缓存解决、且成本不大 → 优先本地缓存；本地缓存满足不了 → 再上 Redis 这类中心化缓存。**

### 二、为什么要中心化缓存（Redis 存在的理由）

典型结构：`客户端 → 负载均衡 → [应用节点1 | 应用节点2 | 应用节点3] → 中心化 DB / 中心化缓存`。

数据库要做成中心化，有**两个**理由，第二个常被忽略：

| 理由 | 说明 |
|---|---|
| **① 持久化** | 数据不能丢 |
| **② 跨节点可见（关键）** | 数据**不能只属于"提交它的那个节点"**——其他节点也必须能查到 |

**缓存其实也是一种数据库**，所以中心化缓存的理由完全相同：**多个节点需要共享同一份状态**。

**典型反例：Session**

> 分布式部署 + 负载均衡下，用户第一次请求落到节点 1，第二次落到节点 2，第三次落到节点 3。
> **Session 缓存在应用本地，换个节点登录态就丢了** → 必须放 Redis 做 **Session 中心**。

另一个例子：把 DB 里的热数据加载进缓存给数据库减压，让应用直接读缓存——这也是中心化缓存。

### 三、什么场景该用本地缓存

判断标准：**这份数据"每个节点各自加载出来的都一样"，且节点之间不需要感知它的变化。**

**最典型的就是配置中心**：

| 阶段 | 做法 |
|---|---|
| **统一管理** | 配置统一放在中心化存储（Redis 配置中心 / etcd 等） |
| **启动时拉取** | 应用启动时从中心**拉一次**配置 |
| **之后读本地** | 只要应用不重启，**配置相关读取全部走本地缓存** |
| **变更时** | 配置变更通常伴随**重启或热更新推送**，重新从中心加载 |

理由：**配置对每个应用节点内容相同、且几乎不变，节点之间无需交互"你的配置变成什么样了"**——
既然不存在"节点间需要交互"这个问题，就**没理由每次都去中心化缓存读**。

### 四、对比表（面试直接给这张）

| 维度 | **本地缓存（bigcache / freecache / go-cache）** | **Redis（中心化缓存）** |
|---|---|---|
| **访问延迟** | 纳秒~微秒级（进程内内存，无网络） | 百微秒~毫秒级（一次网络往返 + 序列化） |
| **容量** | 受**单机内存**限制 | 可**独立扩容 / 集群**，容量大得多 |
| **一致性** | **多实例之间天然不一致** | 多节点共享同一份，**天然一致** |
| **进程隔离** | 进程挂了缓存就没了（**可重建**，通常无妨） | 独立进程，**与应用生命周期解耦** |
| **GC 友好性** | 取决于实现——`map[string]*T` 大量小对象会**加剧 GC 压力**；<br>**bigcache / freecache 用 ring buffer + 大块内存规避 GC** | 数据不在 Go 堆上，**对业务进程 GC 无影响** |
| **典型用途** | 配置、字典、几乎不变的小数据、极热 key | Session、共享状态、跨节点热数据 |

> **`go-cache` 与 `bigcache` / `freecache` 的差别**：前者的 value 是 `interface{}`，
> 会在堆上产生大量对象、**GC 压力大**，胜在支持任意类型 + 自带 TTL；
> 后者把 **key/value 序列化成字节塞进预分配的大块内存（ring buffer）**，
> **几乎不产生需要 GC 扫描的对象**，适合几十万~百万级缓存，
> 代价是**只支持 `[]byte`、需自行预估容量、bigcache 不支持单个 key 的 TTL**。

### 五、进阶：L1 + L2 多级缓存

既然两者不冲突，工程上常见的就是**多级缓存**：

```
请求 → L1 本地缓存（进程内，纳秒级） → 未命中
     → L2 Redis（毫秒级）           → 未命中
     → DB（回源）→ 逐层回填
```

- **L1 承担"极热、几乎不变"的数据**（配置、榜单、字典），把最多请求挡在进程内；
- **L2 承担"热、可能变"的共享数据**，保证多节点看到一致结果。

**收益**：Redis 的 QPS 被 L1 挡掉一大截；**代价**：**一致性链路从 1 段变 2 段**（L1↔L2、L2↔DB）。

### 六、一致性怎么解决（L1 的真实难点）

本地缓存最大的问题：**A 节点收到写请求更新了 DB，B 节点的本地缓存还是旧值。**

| 手段 | 做法 | 适用 |
|---|---|---|
| **① 短 TTL（最省事）** | 给 L1 设很短的过期时间（如 1~5 秒），**用"能容忍的最大延迟"换实现简单** | 绝大多数场景，**首选** |
| **② 主动失效（广播）** | 写操作后**发布失效消息**（Redis Pub/Sub / 消息队列），所有节点收到后删掉本地 key | 变更不频繁、对一致性要求高 |
| **③ 版本号 / 逻辑过期** | value 里带版本号；本地缓存发现版本落后就丢弃重取 | 需要更强的正确性保证 |

> 注意 **② 与 Q7 的 Pub/Sub 局限呼应**：Pub/Sub **不持久化**，
> 节点恰好在那一刻掉线就会漏掉失效消息 → **②必须配 ① 的短 TTL 兜底**，不能只靠广播。

### 七、"多实例本地缓存不一致"的工程处理（追问落点）

1. **能接受延迟就别做无谓的一致性**：L1 一律设短 TTL（1~5s），把不一致窗口**限制在秒级**；
2. **写路径不碰 L1**：**更新 DB → 删除 L2 → 广播删除各节点 L1**（先库后缓存，Cache Aside）；
3. **广播不可靠，TTL 兜底**：掉线节点靠 TTL 自然恢复正确性；
4. **明确哪些数据"根本不该进 L1"**：**强一致、频繁变更、涉及金额/库存的数据只走 Redis，不进本地缓存**。

### 面试官会追问什么

- **为什么不用 Nginx 或 MySQL 的 Buffer Pool 当本地缓存？** → 前者是 HTTP 层缓存，
  无法按业务 key 精细失效；后者是**页级缓存**，**不按业务 key 管理、也无法跨进程共享**（详见本册 Q5）。
- **bigcache / freecache 为什么不加剧 GC？** → 数据存进**预分配的大块 `[]byte`**，
  Go 堆上只有这块大对象，**GC 需要扫描的对象数骤减**。
- **本地缓存要不要设淘汰？** → 要。**没有容量上限的本地缓存就是内存泄漏**，
  用 LRU + 分片容量上限控制（可参考 Q2 的策略选择）。
- **L1 命中率和一致性怎么权衡？** → TTL 越长命中率越高、不一致窗口越大；
  按业务的容忍延迟取，**一般以秒级为主**。

## Q9. Redis 数据量很大、内存放不下了怎么办？

**来源**：`BV1xSRXBwEeM p=37` 百度 Go 后端二面 · 时长 5分05秒
**考察意图**：**这是个陷阱题**——八股会把你带到"该用哪个淘汰策略"，而淘汰策略**在使用时就已确定了**，
改它解决不了"数据量本来就大"。面试官想看的是**你会不会先回到数据和业务层面找原因**。

### 一、先破除八股反射：淘汰策略不是答案

> **淘汰策略（LRU / LFU / Random）在搭建缓存时就已经选定**，
> 它们的本质都是"淘汰不常用的数据"，只是规则有细微差别——
> **无论选哪个，都改变不了"数据量很大"这个事实**。
>
> 而且生产上**除了最初搭建，几乎不会去改淘汰策略**。

所以第一步**不是选策略，而是做数据体检**。

### 二、数据体检三步（先问三个问题）

| 序号 | 问题 | 对应处理 |
|---|---|---|
| **①** | **这些数据是不是都该进缓存？** 缓存的数据选型是否合理？ | 剔除**不该缓存**的数据（大 value、可直接查库的、一次性结果） |
| **②** | **这些数据是否都设置了过期时间？** | 找出"本该设 TTL 却没设"的长命数据，**补上合理有效期** |
| **③** | **已设 TTL 的数据，有效期是否合理？** | 本该存 3~5 秒的设成 3~5 分钟、本该 20~30 分钟的设成 2~3 小时 → **收紧 TTL** |

> **这三步才是本题的核心答案**：先解决"为什么大""为什么这些都在缓存里"，
> 而不是讨论"满了以后淘汰谁"。**容量问题是设计问题，不是策略问题。**

### 三、淘汰策略的正确定位：缓冲，不是救命稻草

**唯一的例外**：**压根没配淘汰策略**（`noeviction`）时，内存写满会导致**新数据写不进去**，
进而**影响整个应用的可用性**。

| 目的 | 说明 |
|---|---|
| **该配淘汰策略** | 内存打满后能腾出空间，**保证后续写入成功、业务继续运行** |
| **配置它的目的** | **不是"用淘汰替代扩容"**，而是为扩容争取**一段缓冲时间** |
| **常见选择** | `allkeys-lru`（只看最近使用）或 `allkeys-lfu`（看访问频率，抗扫描污染） |

> ⚠️ 千万别答成"内存不够就靠淘汰策略解决"——那等于说"我不打算扩容"。

### 四、扩容与分片（真正解决容量）

| 手段 | 说明 |
|---|---|
| **垂直扩容（升配）** | 加大单机内存。最简单，但**单机内存有上限、成本非线性上升、故障域不变** |
| **水平扩容（分片/集群）** | Redis Cluster / 分片代理，**按 key 哈希把数据摊到多节点**，容量与吞吐同步线性提升 |
| **冷热数据分离** | 热数据留 Redis，**冷数据下沉到 DB / 对象存储**，需要时再加载回缓存（回源） |
| **数据压缩与序列化优化** | 用 **Protobuf / MessagePack 替代 JSON**、缩短 key 名、按场景拆小 value，<br>**同样的物理内存装更多业务数据** |

> 与 Q4"大 value 拆 key"呼应：拆分不是为了省内存本身，
> 而是**让存储与传输的粒度匹配访问场景**。

### 五、TTL 分级与热点永不过期（别把"减量"做成"雪崩"）

**收紧 TTL 时最容易踩的坑**：一刀切缩短 TTL → **大量 key 同时过期 → 雪崩（详见 Q1）**。

| 措施 | 做法 |
|---|---|
| **TTL 分级** | 按数据热度分档设有效期（秒级 / 分钟级 / 小时级 / 天级），**不要让所有数据类型共用一个 TTL** |
| **TTL 加随机抖动** | 同批写入的 key，过期时间在区间内取随机值，把失效点摊平 |
| **热点 key 永不过期 + 逻辑过期** | 物理上**不设 TTL（或设超长 TTL）**，value 中**携带逻辑过期时间戳**；<br>读到"逻辑已过期"→ **异步回源刷新 + 旧值兜底返回**，避免请求穿透到 DB |
| **主动删除 + 兜底刷新** | 确实无用的数据**主动 `DEL`**，而不是干等 TTL 到期；<br>后台任务提前刷新即将过期的热数据（详见 Q1） |

### 六、面试答题结构

```
① 先否掉八股答案：淘汰策略在搭建时已定，改它解决不了数据量问题
② 数据体检：该不该缓存？有没有 TTL？TTL 合不合理？→ 剔除 + 收紧
③ 淘汰策略的定位：只是"写满后的缓冲"，为扩容争取时间（没配的必须补上）
④ 扩容：垂直升配 / 水平分片集群 / 冷热分离 / 压缩与序列化优化
⑤ 防副作用：TTL 分级 + 随机抖动 + 热点逻辑过期，别把"减量"做成"雪崩"
```

### 面试官会追问什么

- **改淘汰策略能解决问题吗？** → **不能**。它只决定"满了淘汰谁"，
  **要腾出的是空间，不是换策略**；容量问题只有"少存"和"扩容"两条路。
- **为什么优先做压缩/序列化而不是直接扩容？** → **扩容有成本上限**，
  而值压缩是**一次改造、长期省内存**（Protobuf 相比 JSON 常省 30%~60%）。
- **`noeviction` 有什么风险？** → 内存满后**写命令直接报错**；
  如果业务把 Redis 当存储用，会**直接表现为写入失败、应用报错**。
- **冷热分离后，冷数据回源延迟怎么控？** → 回源走异步 + 缓存预热（访问过的冷数据回填），
  并用 **Q8 的 L1 本地缓存**兜住回源瞬间的并发。

## Q10. 场景题：爬虫反复抓冷门数据，把热数据挤出缓存导致雪崩，怎么解决？

**来源**：`BV1xSRXBwEeM p=74` 虾皮 Go 后端面试 · 时长 7分57秒
**考察意图**：这是**"缓存雪崩 + 淘汰策略被污染"的组合场景题**。
面试官想看的不是背一遍雪崩定义，而是**能不能定位到"淘汰策略缺陷"这个根因**，再给出分层方案。

### 一、先判断：这是不是"真正的"雪崩？

**不一定，要先区分三种情况：**

| 情况 | 成因 |
|---|---|
| **① 淘汰策略缺陷（本题根因）** | 爬虫**批量访问冷门数据**，这些 key **在最近被使用过** → **被策略误判为热数据**；<br>而真正的长期热数据因为"近期不常访问"，**反而被优先淘汰** |
| **② 缓存空间不足（更根本）** | 缓存容量本身就小于数据量，**必然触发淘汰**；空间不足 + 策略缺陷 = 热数据被挤掉 |
| **③ 放大成雪崩** | 热数据被挤出后**请求全部回源数据库**，DB 吞吐远不及缓存 → **服务不可用** |

> **LFU 更危险**：它在"爬虫执行阶段"把**瞬时高频的冷门数据**当成高频 key，
> 长期热数据的"近期频率"反而落后 → **热数据被淘汰**。
> 也就是说，**"最近使用 / 访问频率"这个信号本身会被批量爬虫流量污染**。

### 二、解决思路（按优先级）

**① 隔离：爬虫流量和业务缓存分开（最优解）**

> **先问一句：被爬的数据和业务热数据是不是同一个业务？**
> - **是同一个业务** → 没办法隔离，只能走后面的手段；
> - **不是同一个业务** → **给爬虫单独一套缓存**（独立实例 / 独立 DB index / 独立命名空间），
>   让它**挤自己的空间，不污染业务缓存**。

这是**第一优先级**——**能隔离就隔离，别在淘汰策略上做文章**。

**② 热点数据保护**

| 手段 | 说明 |
|---|---|
| **永不过期 / 超长 TTL** | 热点数据物理上不设 TTL，避免"到期即失效回源" |
| **TTL 错落不一致** | 同批热 key **不要过期时间一致**，否则 30 分钟后**大面积同时过期**，<br>不需要冷数据来挤，自己就形成雪崩（详见 Q1） |
| **独立前缀 / 独立实例** | 给热数据用独立前缀或独立实例，**淘汰范围天然隔离** |

> ⚠️ 视频里提到"给热数据打标志"**意义有限**——
> **淘汰是系统级策略做的，不是业务代码按标记淘汰的**。
> 所以更实在的是"独立实例/前缀" + "永不过期"。

**③ 监控与告警（提前发现，而不是被打挂后救火）**

| 监控项 | 阈值示例 | 含义 |
|---|---|---|
| **缓存空间使用量** | 用到 1.5G / 1.8G（总量 2G）时告警 | **提前扩容**，别等写满 |
| **缓存命中率** | **5 分钟内低于 80%** 就告警 | 命中率骤降 = **热点被替换**或缓存设计不合理，<br>意味着大量流量要砸到 DB |
| **写入量 / key 数量突增** | 突增告警 | 判断是否有爬虫之类的**异常流量** |

> 原视频用 **Prometheus** 举例：**监控命中率是发现"热数据被挤出"最快的手段**。

**④ 调整淘汰策略（最后手段）**

> **不是首选**：空间够、隔离做好、热点保护做了，策略基本不用动。
> **只有真的空间受限时**才考虑调策略。

| 算法 | 思路 |
|---|---|
| **LRU-K** | 记录对象**最近 K 次**的访问历史，**访问次数达到 K 次**才进入淘汰候选范围——<br>**被爬虫扫一遍的冷门数据只有第 1 次访问，进不了候选** |
| **2Q** | 用两个队列（FIFO 准入队列 + LRU 主队列），<br>**新 key 先进准入队列，被再次访问才晋升到主队列**——同样过滤一次性访问 |

### 三、面试答题结构

```
① 定位根因：不是"雪崩"本身，而是"淘汰策略把冷门数据当热数据"→ 挤掉热数据 → 回源 → 雪崩
② 第一优先级：爬虫与业务是否同业务？不同 → 缓存隔离（独立实例 / 命名空间）
③ 热点保护：永不过期 / 超长 TTL / TTL 错落
④ 监控告警：空间使用量 + 命中率（低于 80% 即告警）
⑤ 最后才考虑：调整淘汰策略（LRU-K / 2Q 过滤一次性访问）
⑥ 兜底：数据库侧熔断限流（与 Q1 一致）
```

### 面试官会追问什么

- **为什么 LFU 会在这里失效？** → LFU 统计的是**访问频率**，
  爬虫短时间内把冷门数据刷成高频 → **频率信号被污染**；LRU 同样会被"最近访问过"骗到。
- **LRU-K / 2Q 的代价是什么？** → 需要**额外记录访问历史 / 多队列**，
  **实现更复杂、有额外内存与 CPU 开销**，且对"真正的首次热点访问"有**冷启动惩罚**。
- **隔离成两套缓存的运维成本怎么摊？** → 优先用**独立 DB index / 命名空间**而不是再起一套实例，
  资源隔离程度按爬虫量级决定。
- **命中率 80% 这个阈值合理吗？** → **按业务自定**：
  要看"未命中的流量砸到 DB 后 DB 扛不扛得住"；DB 余量大可放宽，余量小就要收紧。
- **和 Q1 的雪崩解法有什么区别？** → Q1 解决"**过期**导致的大面积失效"，
  本题解决"**淘汰**导致的热数据被挤掉"——**根因不同，但兜底手段（限流熔断）共用**。

## 使用一：Go（场景级封装）⭐

> 客户端初始化、五种数据结构操作、Pipeline、Lua、SetNX 基础版见 [命令与使用.md](命令与使用.md) 第七节，本节只写**把本册各题方案落成代码**的封装。
> 依赖与校验：以下 Go 代码在 `go-redis v9.22` / `bigcache v3.2` / `x/sync v0.23` 下 `go build` + `go vet` + `gofmt` 通过；因本机没有 Redis 实例，**未做运行时验证**。

### 0. 前置：中间件实例必须是单例

`redis.Client` 内部是**连接池**（默认每个 worker 一条连接，`PoolSize` 默认 10×CPU 数），`go-redis` 的 Client **本身并发安全**，全进程共用一个即可。所以：

```go

package cachePool

import (
	"os"
	"sync"
	"time"

	"github.com/redis/go-redis/v9"
)

// Client 是惰性单例：首次调用建连接池，之后所有 goroutine 复用同一实例。
// sync.OnceValue 自带 happens-before 保证，不存在"初始化与读取并发"的数据竞争（Go 1.21+），
// 比手写 sync.Once + 包级变量更不容易用错。用法：cachePool.Client().Get(...)
var Client = sync.OnceValue(func() *redis.Client {
	opt, err := redis.ParseURL(os.Getenv("REDIS_URL")) // 形如 redis://127.0.0.1:6379/0
	if err != nil {
		panic("cachePool: bad REDIS_URL: " + err.Error())
	}
	opt.PoolSize = 50                         // 默认 10×CPU 数；总连接数 ≈ 实例数 × PoolSize，必须小于服务端 maxclients
	opt.MinIdleConns = 5                      // 预热空闲连接，避免流量突增时集中建连抖动
	opt.DialTimeout = time.Second             // ⚠️ 三个超时都必须显式设：
	opt.ReadTimeout = 500 * time.Millisecond  //    不设的话 Redis 一卡，请求协程就无限堆积，
	opt.WriteTimeout = 500 * time.Millisecond //    最终把"缓存故障"放大成"整个服务不可用"
	return redis.NewClient(opt)
})
```

**为什么这条要写在最前面**：下面所有封装都是**有状态的**——`cachex.Cache` 持有 `singleflight.Group`，`multilayer.MultiLevel` 持有 L1 与订阅协程。如果按请求 `New` 一个出来：

| 每次请求新建 | 后果 |
|---|---|
| `redis.NewClient(...)` | 每个请求一套连接池，QPS 稍高就 `too many connections`，且池的空闲连接要等回收 |
| `cachex.New(...)` | 每次新的 `singleflight.Group` → **同 key 并发完全合不并，防击穿形同虚设**（Q1 击穿） |
| `multilayer.New(...)` | 每次一个新的 bigcache（L1 命中率归零 + 内存翻着倍涨）+ 多起一个 `Subscribe` 协程 → **协程泄漏** |

Java 侧同理：`StringRedisTemplate` / `RedissonClient` 由 Spring 容器管理，**默认就是单例 Bean**，用构造注入拿；**不要**在方法里 `new Jedis(...)`（Jedis 非线程安全且连接必须从 `JedisPool` 借还），也**不要**在方法里 `Caffeine.newBuilder().build()`——本地缓存每建一次就是一块新的堆内存。

### 1. 缓存三件套：TTL 打散 + singleflight 防击穿 + 空值防穿透

一个 `Get` 同时解决 Q1 的雪崩（打散过期）与 Q4 的击穿/穿透：

```go

package cachex

import (
	"bytes"
	"context"
	"errors"
	"math/rand"
	"time"

	"github.com/redis/go-redis/v9"
	"golang.org/x/sync/singleflight"
)

// ErrNotFound 表示数据库里确实没有这条数据（区别于"缓存未命中"）。
var ErrNotFound = errors.New("cachex: not found")

var nilValue = []byte("<nil>")

// Cache 把「读缓存 → 未命中回源 → 回填」收敛成一个入口。
// ⚠️ 全进程只建一个：g 是并发合并状态，见第 0 节。
type Cache struct {
	rdb *redis.Client
	g   singleflight.Group
	ttl time.Duration // 基准过期时间
}

func New(rdb *redis.Client, ttl time.Duration) *Cache {
	return &Cache{rdb: rdb, ttl: ttl}
}

// jitterTTL 在 [ttl, ttl*1.2) 内随机，把集中过期摊平（Q1 方案一）。
// 只在基准值上加 20%：区间开太大，缓存利用率会明显下降（Q1 的副作用）。
func (c *Cache) jitterTTL() time.Duration {
	return c.ttl + time.Duration(rand.Int63n(int64(c.ttl/5)))
}

// Get 未命中时用 loader 回源。loader 返回 ErrNotFound 会被缓存成空值，
// 这样同一个不存在的 key 在 TTL 内只会打库一次（Q4 的穿透解法）。
func (c *Cache) Get(ctx context.Context, key string, loader func(context.Context) ([]byte, error)) ([]byte, error) {
	v, err := c.rdb.Get(ctx, key).Bytes()
	if err == nil {
		if bytes.Equal(v, nilValue) { // 命中"空值缓存"
			return nil, ErrNotFound
		}
		return v, nil
	}
	if !errors.Is(err, redis.Nil) {
		return nil, err // Redis 自身故障要往上抛，不能默默回源打爆 DB
	}

	// Do 把「同一个 key 的并发回源」合并成一次，防止热点 key 过期瞬间 N 个请求同时打库（Q1 击穿）。
	// key 用副本 key 时，同副本内仍会合并，跨副本各自回源一次——这是打散方案的固有代价。
	shared, err, _ := c.g.Do(key, func() (interface{}, error) {
		data, lerr := loader(ctx)
		if lerr == ErrNotFound {
			if serr := c.rdb.Set(ctx, key, nilValue, c.jitterTTL()/4).Err(); serr != nil {
				return nil, serr
			}
			return nil, ErrNotFound
		}
		if lerr != nil {
			return nil, lerr
		}
		if serr := c.rdb.Set(ctx, key, data, c.jitterTTL()).Err(); serr != nil {
			return nil, serr
		}
		return data, nil
	})
	if err != nil {
		return nil, err
	}
	return shared.([]byte), nil
}
```

要点：

- **`errors.Is(err, redis.Nil)` 与"Redis 故障"必须分开处理**。把连接超时当成未命中去回源，等于在 Redis 宕机时主动制造雪崩——这正是 Q1 里"缓存服务宕机"那条成因。
- **空值缓存的 TTL 要短**（示例取基准的 1/4）：太长会让"数据刚写入却仍读到空值"的窗口变长。
- `singleflight` 只在**单进程内**合并；多实例部署时每台机器各回源一次，量级是"实例数"而不是"并发数"，通常够用。要跨实例合并只能靠锁（见下面第 3 节），代价是延迟，一般不值。

### 2. 热 key 多副本 + 大 value 拆分（Q4 方案①②）

```go

package hotkey

import (
	"context"
	"fmt"
	"math/rand"
	"time"

	"github.com/redis/go-redis/v9"
)

// Read 从 N 个内容相同的副本里随机挑一个读，把压力摊到集群的不同分片上。
// 注意 key 的哈希要真的会落到不同槽：Redis Cluster 用 {tag} 决定路由，
// 因此副本后缀必须放在花括号之外，否则全部副本会被强制分到同一个节点。
func Read(ctx context.Context, rdb *redis.Client, itemID int64, replicas int) ([]byte, error) {
	key := fmt.Sprintf("hot:item:%d:%d", itemID, rand.Intn(replicas))
	return rdb.Get(ctx, key).Bytes()
}

// Write 需要把同一份 value 写满所有副本；删除同理。
func Write(ctx context.Context, rdb *redis.Client, itemID int64, replicas int, value []byte, ttl time.Duration) error {
	pipe := rdb.Pipeline()
	for i := 0; i < replicas; i++ {
		pipe.Set(ctx, fmt.Sprintf("hot:item:%d:%d", itemID, i), value, ttl)
	}
	_, err := pipe.Exec(ctx)
	return err
}
```

**⚠️ 这里的坑**：如果习惯用 `hot:item:{123}:0` 这种带 hash tag 的写法（为了和别的 key 进同一个槽以便事务/Lua），副本会**全部落在同一分片**，打散直接失效。写之前用 `CLUSTER KEYSLOT hot:item:123:3` 验一下不同副本是否落到不同槽。

**大 value 按使用频率拆 key**（Q4 方案②）是建模层面的事，落地时按表定义清楚即可：

```go

// 高频字段：几乎每次请求都要，单独一个 key，value 控制在 1KB 内
const userBaseKey = "user:base:%d"

// 低频字段：只在个人主页等少数场景用，读不到再回源，不跟 base 一起加载
const userAddrKey = "user:addr:%d"
```

### 3. 分布式锁：把 Q3 的 6 个问题逐个写进代码

```go

package redlock

import (
	"context"
	"crypto/rand"
	"encoding/hex"
	"errors"
	mrand "math/rand"
	"time"

	"github.com/redis/go-redis/v9"
)

// ErrLockBusy 表示在给定等待时间内没抢到锁。
var ErrLockBusy = errors.New("redlock: lock busy")

// 解锁脚本：value 校验 + 删除必须原子（Q3 问题⑤，防误删别人的锁）
var unlockScript = redis.NewScript(`
if redis.call('GET', KEYS[1]) == ARGV[1] then
	return redis.call('DEL', KEYS[1])
end
return 0`)

// 续期脚本：同样要先确认锁还在自己手上，否则会给别人的锁续命
var renewScript = redis.NewScript(`
if redis.call('GET', KEYS[1]) == ARGV[1] then
	return redis.call('PEXPIRE', KEYS[1], ARGV[2])
end
return 0`)

type Lock struct {
	rdb     *redis.Client
	key     string
	value   string // 节点唯一标识，解锁时校验
	ttl     time.Duration
	maxHold time.Duration // 业务总超时（Q3 问题④），到点停止续期
	stop    chan struct{}
}

func newValue() string {
	b := make([]byte, 16)
	_, _ = rand.Read(b)
	return hex.EncodeToString(b)
}

// TryLock 抢锁：SET NX PX + 随机间隔重试。
// wait 为总等待时间，超过返回 ErrLockBusy；ttl 是单次持锁时间。
func TryLock(ctx context.Context, rdb *redis.Client, key string, ttl, wait time.Duration) (*Lock, error) {
	l := &Lock{rdb: rdb, key: key, value: newValue(), ttl: ttl, maxHold: 60 * time.Second, stop: make(chan struct{})}
	deadline := time.Now().Add(wait)
	for {
		// 一次调用就完成 SET NX PX，避免"加成功但没设上过期"的中间态（Q3 问题②）
		ok, err := rdb.SetNX(ctx, key, l.value, ttl).Result()
		if err != nil {
			return nil, err
		}
		if ok {
			go l.watchdog()
			return l, nil
		}
		delay := retryDelay()
		if time.Now().Add(delay).After(deadline) {
			return nil, ErrLockBusy
		}
		// 随机等待，避免所有失败节点同频狂轰 Redis（Q3 问题①）
		time.Sleep(delay)
	}
}

func retryDelay() time.Duration {
	return time.Duration(50+mrand.Int63n(150)) * time.Millisecond
}

// watchdog 在剩余时间不足一半时续期（Q3 问题③）。
// 进程异常退出 → 续期协程消失 → TTL 自然到期，锁不会被宕机节点长期占用。
func (l *Lock) watchdog() {
	interval := l.ttl / 2
	ticker := time.NewTicker(interval)
	defer ticker.Stop()

	renewCtx, cancel := context.WithTimeout(context.Background(), l.maxHold)
	defer cancel()

	for {
		select {
		case <-l.stop:
			return
		case <-renewCtx.Done(): // 问题④：业务卡死时不再无限续期，让锁按 TTL 过期
			return
		case <-ticker.C:
			// 续期不能复用请求的 ctx：请求 ctx 可能已被 cancel，而锁仍需要维护
			c := context.Background()
			if n, err := renewScript.Run(c, l.rdb, []string{l.key}, l.value, l.ttl.Milliseconds()).Int64(); err != nil || n == 0 {
				return // 锁已丢失（过期或被别人拿走），继续续期没有意义
			}
		}
	}
}

func (l *Lock) Unlock(ctx context.Context) error {
	close(l.stop) // 先停续期，再删锁，避免删完又被续期脚本"复活"别人的锁
	return unlockScript.Run(ctx, l.rdb, []string{l.key}, l.value).Err()
}
```

使用：

```go

lock, err := redlock.TryLock(ctx, cachePool.Client(), "lock:order:"+orderID, 5*time.Second, 3*time.Second)
if errors.Is(err, redlock.ErrLockBusy) {
	return nil // 抢不到就放弃，让上游重试或返回"操作太频繁"
}
if err != nil {
	return err
}
defer lock.Unlock(context.Background()) // ⚠️ 用 Background，别用可能已取消的请求 ctx
// ... 临界区业务 ...
```

**这段实现没有解决的问题**：主从切换导致的丢锁（Q3 问题⑥）。单实例锁在"主节点写入后、同步到从节点前宕机"时必然丢，**不要自己写 RedLock**，直接用 `github.com/go-redsync/redsync/v4` 的 `redisgoredisv8pool`（多独立节点 + 多数派）；同时接受它的代价——**QPS 下降、运维要维护 N 个独立实例、GC/时钟偏斜会影响正确性**。库存扣减这类强需求更适合改成"数据库唯一约束 + 状态机"来兜底，而不是把正确性压在锁上。

### 4. L1 + L2 多级缓存：bigcache 挡极热数据，Pub/Sub 广播失效（Q8）

```go

package multilayer

import (
	"context"
	"errors"
	"time"

	"github.com/allegro/bigcache/v3"
	"github.com/redis/go-redis/v9"
)

const invalidChannel = "cache:invalidate"

type MultiLevel struct {
	l1  *bigcache.BigCache
	c   *redis.Client // 复用第 0 节的单例连接池，不在这里再 new 一个
	ttl time.Duration
}

// New 只在进程启动时调用一次，把返回值保存为单例；bigcache 与订阅协程都是有状态的。
func New(c *redis.Client, ttl time.Duration) (*MultiLevel, error) {
	l1, err := bigcache.NewBigCache(bigcache.Config{
		Shards:             256,             // 分片数，必须是 2 的幂，降低锁竞争
		LifeWindow:         3 * time.Second, // ⚠️ L1 一律短 TTL：不一致窗口控制在秒级（Q8 第七节）
		CleanWindow:        1 * time.Second, // 后台清理频率，小于 1s 反而浪费 CPU
		MaxEntriesInWindow: 1000 * 10,       // 仅用于估算 shard 初始容量：估准了后续不再额外分配内存
		MaxEntrySize:       500,             // 单条平均字节数，同样只参与初始容量估算
		HardMaxCacheSize:   512,             // ⚠️ 单位 MB，默认 0 = 无上限；不设上限的本地缓存就是内存泄漏（Q8 追问）
		Verbose:            false,
	})
	if err != nil {
		return nil, err
	}
	return &MultiLevel{l1: l1, c: c, ttl: ttl}, nil
}

func (m *MultiLevel) Get(ctx context.Context, key string, loader func(context.Context) ([]byte, error)) ([]byte, error) {
	if v, err := m.l1.Get(key); err == nil {
		return v, nil // L1 命中：进程内，无网络往返
	}
	v, err := m.c.Get(ctx, key).Bytes()
	if errors.Is(err, redis.Nil) { // 只有"key 确实不存在"才回源
		v, err = loader(ctx)
		if err != nil {
			return nil, err
		}
		if serr := m.c.Set(ctx, key, v, m.ttl).Err(); serr != nil {
			return nil, serr
		}
	} else if err != nil {
		return nil, err // ⚠️ Redis 故障不能当未命中：否则缓存一挂，全量流量直接砸到 DB（Q1 的宕机成因）
	}
	if serr := m.l1.Set(key, v); serr != nil { // bigcache 只支持 []byte，本层不需要序列化
		return nil, serr
	}
	return v, nil
}

// Invalid 是写路径：更新 DB 之后调用，删 L2 并广播删各节点 L1（Cache Aside，先库后缓存）。
func (m *MultiLevel) Invalid(ctx context.Context, key string) error {
	if err := m.c.Del(ctx, key).Err(); err != nil {
		return err
	}
	return m.c.Publish(ctx, invalidChannel, key).Err()
}

// SubscribeInvalidate 每个进程只跑一个协程（与 New 一样是启动期的一次性动作，别按请求起）。
// ⚠️ Pub/Sub 不持久化，掉线期间的消息会永久丢失，所以必须有上面的 3s 短 TTL 兜底（Q8 第六节）。
func (m *MultiLevel) SubscribeInvalidate(ctx context.Context) {
	sub := m.c.Subscribe(ctx, invalidChannel)
	ch := sub.Channel()
	for {
		select {
		case <-ctx.Done():
			return
		case msg := <-ch:
			_ = m.l1.Delete(msg.Payload)
		}
	}
}
```

**bigcache 的取舍**（对应 Q8 的对比表）：只支持 `[]byte`、容量要预估、单个 key 不能设独立 TTL（只有全局 `LifeWindow`）。需要 per-key TTL 或任意类型时用 `freecache`，或直接用 `github.com/hashicorp/golang-lru/v2/expirable`（支持泛型 + 单 key TTL，但 value 在堆上，量大会加剧 GC）。

### 5. 爬虫污染场景的隔离落地（Q10 方案①）

隔离优先用**独立 DB index 或独立实例**，代码上就是两条客户端配置，不要在业务里加 `if isCrawler` 判断：

```go

var (
	// 业务缓存：独立实例，淘汰策略按业务量配置，命中率和空间是它的 SLA
	bizRDB = redis.NewClient(&redis.Options{Addr: "redis-biz:6379", DB: 0})
	// 爬虫缓存：同一实例的不同 DB，或更稳妥的独立实例（DB 之间不隔离内存与淘汰）
	crawlerRDB = redis.NewClient(&redis.Options{Addr: "redis-biz:6379", DB: 7})
)
```

**⚠️ 同实例不同 DB 只隔离 key 空间，不隔离内存**：Redis 的淘汰是**实例级**行为，爬虫把 DB 7 写满照样会淘汰 DB 0 的 key（`maxmemory-policy` 默认 `allkeys-*` 时会跨 DB 淘汰）。所以真正的隔离要么给爬虫**独立实例**，要么在能配 `maxmemory-policy` 时确认其影响范围——**别把"换了 DB 号"当成容量隔离**。

上面的包级变量本身就是单例（进程启动时初始化一次）；如果偏好第 0 节的写法，就为两套缓存各建一个 `sync.OnceValue`，例如 `BizClient()` / `CrawlerClient()`，**关键是"每套缓存一个、全进程复用"**，不要在请求函数里 `redis.NewClient`。

### 1. TTL 打散 + 防击穿（与 Go 版对应）

```java

@Service
public class GoodsCacheService {

    private final StringRedisTemplate redis;
    private final GoodsMapper mapper;
    // 同一 JVM 内合并并发回源：Caffeine 的 build 阶段天然对同 key 加锁，能起 singleflight 作用
    private final Cache<String, String> inflight = Caffeine.newBuilder()
            .maximumSize(10_000)
            .expireAfterWrite(Duration.ofSeconds(5)) // 只用来合并瞬时并发，不长期持有数据
            .build();

    private static final Random RANDOM = new Random();
    private static final Duration BASE_TTL = Duration.ofMinutes(30);
    private static final String NIL = "<nil>";

    public GoodsCacheService(StringRedisTemplate redis, GoodsMapper mapper) {
        this.redis = redis;
        this.mapper = mapper;
    }

    /** 基准 TTL 上再加 0~20% 随机，避免同批 key 集中过期（Q1 方案一）。 */
    private Duration jitterTtl() {
        return BASE_TTL.plusMillis(RANDOM.nextLong(BASE_TTL.toMillis() / 5));
    }

    public String get(Long id) {
        String key = "goods:" + id;
        String cached = redis.opsForValue().get(key);
        if (NIL.equals(cached)) {
            return null; // 命中空值缓存，说明库里确实没有（Q4 穿透）
        }
        if (cached != null) {
            return cached;
        }
        // ⚠️ 不要用 Redis 异常来触发回源：把连接失败 catch 掉当未命中，等于主动雪崩
        return inflight.get(key, k -> loadAndCache(k, id));
    }

    private String loadAndCache(String key, Long id) {
        String db = mapper.selectContentById(id);
        if (db == null) {
            // 空值也缓存，TTL 取 1/4，缩短"刚写入仍读到空"的窗口
            redis.opsForValue().set(key, NIL, BASE_TTL.dividedBy(4));
            return null;
        }
        redis.opsForValue().set(key, db, jitterTtl());
        return db;
    }
}
```

### 2. Redisson：Q3 六个问题的现成实现

Redisson 的 `RLock` 已经把「SET NX + 唯一标识 + Lua 原子解锁 + 看门狗续期」全做了，**生产环境优先用它而不是手写**：

```java

@Service
public class StockLockService {

    private final RedissonClient redisson;

    public StockLockService(RedissonClient redisson) {
        this.redisson = redisson;
    }

    public void deduct(String orderNo) throws InterruptedException {
        RLock lock = redisson.getLock("lock:stock:" + orderNo);
        // waitTime：抢不到最多等 3s（对应 Q3 问题①的重试与放弃）
        // leaseTime：显式给 10s —— 关键取舍，见下方说明
        if (!lock.tryLock(3, 10, TimeUnit.SECONDS)) {
            throw new BizException("操作太频繁，请稍后重试");
        }
        try {
            doDeduct(orderNo);
        } finally {
            if (lock.isHeldByCurrentThread()) { // 防止误删别人的锁（Q3 问题⑤）
                lock.unlock();
            }
        }
    }
}
```

**`leaseTime` 到底给不给（Redisson 最容易踩的点）**：

| 写法 | 行为 | 后果 |
|---|---|---|
| `lock()` 或 `tryLock(waitTime, unit)`（**不给 leaseTime**） | 启用**看门狗**，默认每 `30/3 = 10s` 续期一次，锁续到 30s | 业务卡死时锁被无限续（Q3 问题④），只能靠进程退出才释放 |
| `tryLock(waitTime, leaseTime, unit)`（**给了 leaseTime**） | **不启**看门狗，到点无条件释放 | 业务没跑完锁先没了 → 临界区被并发进入（Q3 问题③） |

所以「给 leaseTime」和「靠看门狗」是互斥的两种取舍：leaseTime 必须**明显大于 P99 业务耗时**，否则就交给看门狗并接受"卡死不释放"。

多节点 RedLock（Q3 问题⑥）对应 `RedissonRedLock`（把多个独立节点的 `RLock` 合成一把）——但 RedLock 存在争议（时钟漂移、节点重启导致的安全窗口），**能用数据库约束保证正确性就别依赖它**。

### 3. 热 key 打散与大 value 拆分（Q4）

        return null;
    });

@Configuration
public class L1CacheConfig {

## 使用三：热 key / 大 key 与命中率监控实操

方案能不能落地，取决于**先发现**。以下命令与指标对应 Q4/Q9/Q10 的排查步骤：

```bash

# 1) 找大 key：SCAN 遍历采样，不阻塞（⚠️ 不要用 KEYS *，O(N) 会卡死单线程）
redis-cli -h 127.0.0.1 -p 6379 --bigkeys

# 2) 找热 key：要先开 maxmemory-policy=lfu 系或 4.0+ 的 IDLETIME 统计
redis-cli --hotkeys
redis-cli --freq                      # LFU 模式下看访问频率

# 3) 看单条命令耗时分布，确认是否被某个大 key 拖住
redis-cli --latency-history -i 1

# 4) 命中率（Q10 的告警项：5 分钟内 < 80% 告警）
redis-cli INFO stats | grep -E 'keyspace_(hits|misses)'
# 命中率 = hits / (hits + misses)，注意 hits/misses 是累计值，
# 告警要用"两次采样的差值"算窗口命中率，直接用累计值会被历史稀释

# 5) 内存与淘汰：used_memory 逼近 maxmemory 且 expired_keys/evicted_keys 突增 = 热数据正在被挤
redis-cli INFO memory | grep -E 'used_memory_human|maxmemory_human|maxmemory_policy'
redis-cli INFO stats | grep -E 'evicted_keys|expired_keys'

# 6) 实时看谁在打进来（临时定位爬虫类流量）
redis-cli MONITOR | head -n 2000      # ⚠️ 生产开启会明显掉吞吐，只能秒级采样
```

- **Prometheus 侧**：用 `redis_exporter`，核心告警是 `redis_keyspace_hits_total` / `misses_total` 的 rate 比值、`redis_evicted_keys_total`、`redis_memory_used_bytes / redis_memory_max_bytes`（如 2G 用到 1.5G 预警），对应 Q10 的三项监控。
- **Go/Java 里主动打点**：把 `Cache.Get` 的命中/未命中计数上报，才能算**业务维度**的命中率（Redis 侧的 hits 分不清是哪个接口掉的多）。
- **数据库兜底**（Q1 方案三）：限流器实现在 [../go/限流器.md](../../go/限流器.md)，Java 侧配 Sentinel，见 [../distributed/限流降级熔断.md](../../distributed/限流降级熔断.md)。
