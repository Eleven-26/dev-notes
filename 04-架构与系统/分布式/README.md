# 分布式笔记索引（本目录导读）

> 本目录回答的是「**从单机走向多机之后，新增了哪些问题**」，分两条线：
> **理论线**（`理论/`）回答「为什么难」——一致性、共识、跨服务事务、全局 ID；
> **治理线**（`服务治理/`）回答「怎么做」——注册发现、负载均衡、限流与过载保护。
> 根目录的 [分布式与微服务.md](分布式与微服务.md) 是**两条线共同的总纲**。
>
> 内容整理自个人学习笔记。**本文件只给阅读顺序与依赖关系**——每篇的知识点描述见
> [全仓知识点目录](../../目录.md)，本目录**不重复描述**；跨目录的延伸见「四、与其它目录的分工」。

## 二、两条线各自的顺序

### 2.1 理论线：`理论/`（为什么难）

```text
① 一致性与CAP        ← 入口：强 / 弱 / 最终一致的差别 + CAP 取舍
        ↓
② Raft协议           ← 共识怎么落地：三种角色、日志复制、选主（etcd 三节点实测）
        ↓
③ 分布式事务         ← 跨服务写入的一致性：XA / TCC / Saga / 本地消息表 / 事务消息
④ 分布式ID           ← 拆库之后自增主键没了：雪花 / 号段 / Leaf
```

### 2.2 治理线：`服务治理/`（怎么做）

```text
① 服务发现与负载均衡      ← 入口：注册 / 发现 / 健康检查 / LB 的分工与选型
        ↓
② 接入三篇（按手上的语言挑）
     服务注册与发现的Go实现   ← Go：租约注册 + KeepAlive + Watch 增量
     客户端负载均衡的Go实现   ← Go：轮询 / 平滑加权 / 一致性哈希与实测
     服务发现的Java实现      ← Java：Spring Cloud + Nacos 的对应词汇
     一致性哈希             ← 上面那种「一致性哈希策略」的算法本体（环 / 虚拟节点 / 建环代价）
        ↓
③ 限流算法               ← 速率限制的算法层（令牌桶 / 漏桶 / 四种窗口算法）
        ↓
④ 并发限制器             ← 在途数限制 + 自适应（AIMD / Vegas / Gradient2）
⑤ 稳定性三件套            ← 三件套的**关系**与工程落地（含 Redis + Lua 分布式限流）
        ↓
⑥ 熔断器                 ← ⑤ 里「熔断」那一件的组件级展开（三态机 / 窗口 / 调参）
⑦ 节点级被动摘除          ← 比熔断更细一级：先摘坏节点，整片不行才轮到熔断
⑧ 负载保护               ← 与 ③ 互补的另一轴：限「并发」而不是「速率」
⑨ 多副本共享状态          ← 多副本下 ③⑥ 的判定依据怎么统一（扩容后阈值被放大 N 倍）
```

> ⚠️ **③④⑤ 的分工最容易混**，一句话记住：`限流算法` 限**速率**（进多快）、
> `并发限制器` 限**在途数**（积多少）、`稳定性三件套` 讲**限流 / 熔断 / 降级三者的关系与落地**。

## 三、专题线：只想补某一块

| 目的 | 按这个顺序读 |
|---|---|
| **只想搞懂「为什么要把系统拆开」** | 分布式与微服务（第一、二节）→ 服务发现与负载均衡（拆开之后多出来的事） |
| **搞懂「一致性」到底是什么** | 一致性与CAP（三种强度）→ Raft协议（多数派怎么保强一致）→ 分布式事务（跨服务怎么补） |
| **服务治理从零入门** | 服务发现与负载均衡 → 三篇接入（按语言挑一篇读透）→ 限流算法 |
| **防止被流量打穿** | 限流算法 → 并发限制器 → 稳定性三件套 → 负载保护 → 熔断器 → 节点级被动摘除 |
| **上线多副本之前** | 多副本共享状态（限流阈值被放大 `副本数` 倍，且没有任何报错） |
| **要在 Go 里落地** | 服务注册与发现的Go实现 → 客户端负载均衡的Go实现 |
| **要在 Java 里落地** | 服务发现的Java实现 → 分布式事务（Seata 接入一节） |
| **排查「偶发不一致 / 脏读」** | 一致性与CAP（先分清是哪一种一致性被破坏）→ Raft协议（脑裂与多数派）→ 分布式事务 |

## 五、本目录的边界与缺口

**边界**：本目录只收**多机之后新增的问题**——从「为什么要拆、拆完多出什么」到
「服务之间怎么找到彼此、怎么不被对方拖垮」为止。

| 本目录收 | 不收（在哪） |
|---|---|
| 一致性模型、共识协议、跨服务事务、全局 ID | **单机的并发与锁** → [并发编程/](../../01-编程语言/go/并发编程/)、[并发/](../../01-编程语言/java/并发/) |
| 服务注册发现、负载均衡、限流与过载保护 | **组件的具体用法**（Nacos / Redis / MQ）→ [03-数据与中间件/](../../03-数据与中间件/) |
| 分布式系统的**理论取舍** | **容器编排与部署形态** → [部署/](../../06-工程实践/部署/) |
| | **链路追踪的实现**（SDK 接入、采集链路）→ [可观测性/](../../03-数据与中间件/中间件/可观测性/) |

**已知缺口**（2026-10-02 按主题全仓 grep 实测，不是凭印象列）：

| 缺口 | 实测现状 | 结论 |
|---|---|---|
| **逻辑时钟**（Lamport / 向量时钟 / HLC） | **全仓 0 次** | ⭐ **值得补**——「分布式里没有全局时钟」是很多结论的前提，目前只能靠读者自己补 |
| **Paxos** | 仅 7 次提及（Raft 篇做对照） | 暂不补：Raft 已覆盖工程主流用法，Paxos 留作对照即可 |
| **PACELC** | **全仓 0 次** | 可并入 `理论/一致性与CAP.md`（CAP 的延迟维度延伸，一段话的体量） |
| **拜占庭容错**（PBFT） | **全仓 0 次** | 暂不补：属区块链领域，与后端服务主线较远 |
| **CRDT** | **全仓 0 次** | 暂不补：协同编辑场景，本仓库暂无对应落点 |
| **分布式快照**（Chandy-Lamport） | **全仓 0 次** | 暂不补：Flink checkpoint 用的，本仓库未做流处理 |
| **选主算法**（Bully / Ring） | **全仓 0 次** | 暂不补：Raft 选主已覆盖工程实际用法 |

> ⭐ 缺口是**按主题 grep 实测**得出的（含「全仓 0 次」这类硬结论）——
> 写阅读顺序时顺手把缺口查出来，是加目录导读的意外收获。
