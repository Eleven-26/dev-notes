# 多副本共享状态

> 单机跑的限流与熔断，**一上多副本就会悄悄失效**：
> 3 个副本各配 `100/s`，实际放行是 **300/s**；一个副本已经把某服务熔断了，另外两个还在往里打流量。
> 共享状态要解决的就是这件事：让所有副本对同一件事有**同一个答案**。
>
> 内容整理自个人学习笔记，实测基于自研网关项目 [gateway](https://github.com/Eleven-26/gateway)（module `gwlab`，Go 1.26.5）的
> `internal/gateway/sharedstate.go`、`internal/breaker/store.go`、`internal/ratelimit/backend.go`；
> 相关回归测试见项目 `go test ./internal/...`（12 个包 270 个用例全绿，含本节引用的 6 个共享状态用例）。
> ⚠️ 需要起「两个副本 + 一个状态服务」才能观察的现象，已标注为未实测。
>
> ⭐ **分工**：本篇讲**共享状态的抽象设计与失败策略**；
> 用 Redis + Lua 做集中式配额的方案见 [稳定性三件套.md](稳定性三件套.md)；
> 熔断器本身的判定逻辑见 [熔断器.md](熔断器.md)。

## 一、多副本让哪些机制悄悄失效？

**本节要点**：失效是**静默**的 —— 压测（单副本）一切正常，扩容后阈值直接乘了副本数。

### 1.1 限流：阈值 × 副本数

```text
配置：某路由 100 req/s
单副本：实际放行 100/s        ✅ 符合预期
三副本：每个副本各有自己的桶 → 实际放行 300/s   ❌ 上游收到三倍压力
```

⚠️ **这是扩容时最容易忽略的陷阱**：你的压测是单副本做的，
上生产起了 3 个 Pod 之后，「限流已经配好了」这句话就变成了假话 ——
而且**没有任何报错**，只是上游被打得更狠。

### 1.2 熔断：样本被稀释 + 各自重新发现同一个坏上游

熔断器是**进程内**状态，多副本时有两个后果：

| 后果 | 说明 |
|---|---|
| **样本被稀释** | 全局 100 req/s 分到 3 个副本，每个只有 33/s —— 低流量下谁都攒不到 `MinRequests`，熔断**永远不触发** |
| **重复发现** | 副本 A 已经判定某服务不可用并熔断了，副本 B 还在一无所知地往里打流量；等 B 也失败够了次数，再自己熔一遍 |

⭐ 注意熔断和限流的**共享需求程度不同**：

- 限流**必须**共享（否则配额被放大 `副本数` 倍，这是实打实的超发）；
- 熔断**共享是优化**（不共享只是「多付几次学费」，不共享不会导致超发）。

这个差别直接决定了后面「共享粒度」的不同设计。

## 二、抽象该怎么设计：「取桶」是一个走不通的接口

**本节要点**：这是设计分布式限流时**最容易走错的一步** —— 接口签名选错，后半程全部返工。

先说结论：**接口必须设计成「一次判定」，而不是「取一个桶回来自己判」**。

```go
// ✅ 对的：一次判定
type Backend interface {
    Allow(key string, p config.LimitPolicy) (bool, time.Duration)
    Name() string
}

// ❌ 错的：取桶
// GetBucket(key) *Bucket    // 拿到桶之后 Bucket.Allow() 在本地执行
```

**为什么「取桶」在远程实现里根本写不出来**：

```text
要实现 GetBucket(key)：
  方案 a：把桶缓存到本地 → 本地判 → 又变回「各算各的」，共享了个寂寞
  方案 b：每个请求 GetBucket + Allow 两次往返 → 延迟翻倍，且两次调用之间有竞态
  方案 c：GetBucket 时就把桶锁在服务端 → 那就是「一次判定」了，签名骗了人而已
```

⭐ **一条判据**：**凡是「先取状态、再在本地改状态」的接口，都无法正确地远程化** ——
因为「读—改—写」之间必然有窗口，而这个窗口在分布式下会被放大成正确性问题。
远程接口应该表达**意图**（「我要放行一个」），而不是**暴露状态**（「给我那个桶」）。

> ⚠️ 同一类错误在别处也常见：分布式锁的 `Lock()/Unlock()` 如果拆成 `GetLockState()` + `SetLock()`
> 就完全失去意义；库存扣减的 `GetStock()` + `SetStock()` 也必然超卖。
> **一次调用完成一次判定**，是分布式接口的基本形状。

## 三、两条路线：集中式存储 vs 服务化共享

| | 集中式存储（Redis + Lua） | 服务化共享（HTTP 状态服务） |
|---|---|---|
| 判定在哪 | 在存储侧执行 Lua 脚本 | 在一个独立的服务里 |
| 一致性 | 强（单点原子执行） | 强（同样是单点判定） |
| 延迟 | 一次 Redis RTT（通常 <1ms） | 一次 HTTP RTT（通常 1~5ms） |
| 依赖 | 需要 Redis 客户端与运维 | 只需 `net/http`，状态服务可用任何语言写 |
| 可扩展性 | 成熟方案多（`redis-cell` 等） | 需要自己写状态服务 |
| 适合 | 已有 Redis、对延迟敏感 | 不想引入客户端依赖、或状态逻辑较复杂 |

⭐ **选型判据**：**先看延迟预算**。
限流判定挂在每个请求的路径上，如果一次判定要多花 5ms，而你的 P99 预算是 50ms，
那就是 10% 的成本 —— 这时 Redis 的低延迟是硬优势。
反过来，如果共享的**不只是计数**（例如还要做跨副本的配额分配、配额续租、限流规则下发），
自建状态服务表达力更强。

> ⚠️ 本项目选 HTTP 服务化路线，原因是**项目定位**（除 gRPC 外只用标准库，引 Redis 客户端会破坏这条约束），
> 而不是因为 HTTP 更优。**这是一个受约束的取舍，不是普遍结论** ——
> 真实项目里已有 Redis 时，Redis + Lua 通常是更省事也更快的选择。

## 四、共享服务挂了怎么办：fail-open 还是 fail-closed？

**本节要点**：这个选择**必须显式做**，不能靠「异常了就算了」默认掉。

```text
共享状态服务抖动 3 秒，这 3 秒里限流怎么判？

fail-closed（全部拒绝）：状态服务一次抖动 = 把自己的网关打成全站 503
                       —— 比被刷更糟（被刷只是超发，全拒是彻底不可用）
fail-open（全部放行）：限流暂时失效，但服务还活着
                       —— 用一个「可能超发」换「一定可用」
```

**默认取 fail-open**，但有一个**不能省的前提**：

```go
// 默认 fail-open，并且必须计数：
// 静默放行等于把「限流失效」藏起来，只有指标能让你发现它
store.OnError(func(error) { metrics.IncStateError("breaker") })
```

⭐ **静默降级是最危险的降级**。`gw_shared_state_errors_total{backend="ratelimit"}` 这个计数器
是「限流此刻其实没在生效」的**唯一信号** —— 没有它，你会以为一切正常，直到上游被打挂。

**降级粒度也要想清楚**：

| 机制 | 共享服务读不到时 | 理由 |
|---|---|---|
| 限流 | 退回**本地**桶继续判（不是全放） | 本地桶还在，能挡住一部分；比全放强、比全拒好 |
| 熔断 | 退回**本地状态机** | 熔断本来就允许各副本独立判定，退化成单副本语义可接受 |

> ⚠️ 注意「退回本地」≠「fail-open」：本地桶仍然会限流，只是限额变成了「每个副本各一份」。
> 真正的 fail-open 是「压根不限」，那会让共享状态服务成为**限流的单点开关** ——
> 谁把它打挂，谁就获得了无限配额。

## 五、两类状态的共享粒度完全不同

**本节要点**：限流每次判定都要问远程；熔断只需要同步「打开到什么时候」。

### 5.1 限流：每次判定一次往返

配额是精确的计数，**没有任何本地缓存能保证正确性** —— 每次 `Allow` 都必须问。

代价：每个请求一次 RTT。所以**只在确实需要跨副本一致的路由/服务上打开**
（本项目配置里是逐路由/逐服务开关的），没必要为内网调用付这个成本。

### 5.2 熔断：只共享「打开到什么时候」，方向是刻意不对称的

```go
type Store interface {
    Publish(service string, until time.Time) error      // 只在本地跳闸时调用
    Snapshot() (map[string]time.Time, error)            // 周期拉取
}
```

⭐ **三处刻意的设计**：

| 设计 | 理由 |
|---|---|
| 只共享「打开到 `until`」，**不共享滑动窗口的原始计数** | 各副本的流量样本本来就不同，把原始计数汇总既贵又没意义。判定结果（结论）才是要共享的东西 |
| `Publish` **只在本地跳闸时**触发（单向） | 如果每个副本把收到的状态再转发一遍，会形成**发布风暴** |
| `Snapshot` 是**周期拉取**（默认 1s）而不是每请求查询 | 熔断在热路径上，每请求远程问一遍既慢、又会让状态服务成为瓶颈 |

代价是**副本之间生效有一个 `SyncInterval` 的窗口**（默认 1s）：

```text
副本 A 在第 0.1s 判定 order-svc 不可用并发布
副本 B 最迟在第 1.1s 采纳这个结论 → 这 1 秒内它还在往 order-svc 打流量
```

⭐ **这个窗口可以接受，是因为熔断不是精确配额** ——
晚 1 秒熔断，后果是「多几个请求失败」，而晚 1 秒限流，后果是「配额被超发」。
**对精确性要求越高的状态，同步周期必须越短**；反之可以放宽。

### 5.3 发布绝不能在请求路径上做网络 IO

```go
// publishTrip 把一次本地跳闸放进发布队列。非阻塞：状态服务再慢也不能拖住请求。
func (g *Gateway) publishTrip(service string, until time.Time) {
    select {
    case g.tripCh <- tripEvent{service, until}:
    default:
        metrics.IncStateError("breaker-publish-dropped")   // 队列满就丢，并计数
    }
}
```

⚠️ **为什么这里必须是队列 + 后台协程**：跳闸**恰好发生在请求里**
（`Report` 是在一次业务调用结束时调的）。
如果在那一刻同步 POST 状态服务，而这个服务正好也在抖 ——
**熔断这个「保护机制」本身就成了请求路径上的新故障点**。

队列满时丢弃是**安全的**：丢一次发布只会让别的副本晚一个周期知道，
本地的熔断不受影响（本地状态机已经跳了）。

## 使用：给多副本网关配共享状态

### 1) 配置

```json
{
  "shared_state": {
    "url": "http://127.0.0.1:18090",
    "timeout": "200ms",
    "sync_interval": "1s"
  },
  "routes": [
    { "name": "open-api", "path": "/open/", "upstream": "order-svc",
      "limit": { "rate_per_sec": 100, "burst": 20, "shared": true } }
  ]
}
```

| 字段 | 默认 | 说明 |
|---|---|---|
| `url` | 空 | **空 = 全部在进程内**（单副本语义）。留空是最好的默认值：多副本才需要它 |
| `timeout` | 200ms | ⚠️ 必须**远小于**你的请求超时 —— 判定本身不该成为瓶颈 |
| `sync_interval` | 1s | 只影响熔断状态的采纳速度（限流是每请求实时的） |

### 2) 状态服务的最小协议

```text
POST /ratelimit  {"key":"route:open-api|ip:1.2.3.4","rate":100,"burst":20}  → {"allowed":true,"retry_ms":0}
POST /breaker    {"service":"order-svc","until_ms":1730000000000}
GET  /breaker                                                              → {"services":{"order-svc":1730000000000}}
```

⭐ 协议刻意做成**无状态服务 + 两个端点**：状态服务不读配置、不做业务判断，
只维护「谁被限了多少 / 谁被熔断到什么时候」。
**把判定逻辑留在网关侧**，状态服务越薄越不容易成为一致性问题的来源。

### 3) 三个必踩的坑

| 情况 | 现象 | 判定 |
|---|---|---|
| **单副本压测通过就上线多副本** | 限流阈值被放大 `副本数` 倍，且无任何报错 | 扩容前必须确认「哪些限流是共享的」 |
| **共享服务没配 `timeout`** | 状态服务卡住 → 网关线程全挂在等响应上 | 超时要**远小于**请求超时（本项目默认 200ms） |
| **降级路径没有计数** | 状态服务挂了一周，限流一直没生效，没人发现 | fail-open **必须**配 `gw_shared_state_errors_total` |

### 4) 本地兜底：为什么要留一个「本地桶」

```text
共享后端不可用 → 退回 LocalBackend
   → 仍然是「每个副本各一份配额」（3 副本 = 3 倍）
   → 但比「完全不限」好得多：至少挡住了单副本内的刷接口
```

⭐ 这个设计让状态服务从**单点开关**降级为**精度级别**：
它挂了，「跨副本的精确配额」退化成「单副本的近似配额」，服务不中断。
**任何集中式组件都应该想清楚「它挂了以后系统退到哪一档」**，而不是只有「能用」和「不可用」两态。

## 延伸追问

- **限流状态能不能用「每个副本分一段配额」来近似，不用共享？** →
  可以，这叫**配额分段**（每个副本拿 `总配额/N`，用完为止）。优点是零依赖、延迟低；
  缺点是**负载不均时浪费**（A 副本的段用完了，B 副本还有余量也不借给它）。
  流量均匀时够用，突发时精度差。
- **为什么熔断不共享滑动窗口的原始计数？** →
  各副本看到的流量不是同一个样本，把计数汇总成「全局失败率」既需要额外往返，
  又会因为样本到达延迟导致判定滞后。**共享结论比共享原始数据便宜得多**。
- **`Publish` 为什么不做成双向同步（每个副本都转发收到的状态）？** →
  会形成发布风暴：N 个副本互相转发，一次跳闸变成 N² 级消息。
  **单向发布 + 周期拉取**是这类状态同步的通用形状。
- **`SyncInterval` 取 1s 会不会太慢？** →
  取决于状态的性质：熔断晚 1 秒只是「多几次失败」，可以接受；
  若是配额类状态（必须精确），1 秒的窗口就可能超发，那就必须走同步判定（每请求往返）而不是周期同步。
- **状态服务自己要不要做高可用？** →
  要，但**优先级低于「网关必须能降级」**。先把降级路径做对（本地兜底 + 计数告警），
  再考虑状态服务的主从或分片 —— 否则状态服务会成为整个网关集群的单点。
- **共享状态会不会成为性能瓶颈？** →
  会，而且它会**随副本数线性增长**（N 个副本 × 每请求一次判定）。
  两个缓解方向：① 只对真正需要精确性的维度开共享；
  ② 状态服务侧按 key 分片（限流 key 天然可哈希分片，熔断按服务名分片）。
