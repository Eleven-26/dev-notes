# 负载保护（过载闸门）

> 限流管的是「**每秒进来多少**」，负载保护管的是「**此刻有多少在飞**」。
> 这两件事看起来像，但在一种最常见的故障下结果完全相反：
> **上游慢了 10 倍，请求数一个没多** —— 限流器一切正常，系统却雪崩了。
>
> 内容整理自个人学习笔记，实测基于自研网关项目 [gateway](https://github.com/Eleven-26/gateway)（module `gwlab`，Go 1.26.5）的
> `internal/overload/`。
>
> ⭐ **分工**：本篇讲**网关入口的并发闸门**（有界排队 + 快速拒绝）这一具体实现；
> 「在途数」这个量本身的理论（Little 定律）与自适应限流算法（AIMD / Vegas / Gradient2）见
> [并发限制器.md](并发限制器.md)；按速率限流见 [限流算法.md](限流算法.md)；
> 上游已经不行时的止损见 [熔断器.md](熔断器.md)。

## 一、为什么限流救不了「上游变慢」？

**本节要点**：限流看的是入口速率，而雪崩往往由**延迟**引起，两者是不同的坐标轴。

用 Little 定律 `L = λ × W`（在途数 = 到达率 × 平均停留时间）看这件事最清楚：

```text
正常：λ = 100/s，W = 20ms   → L = 2      （同时只有 2 个请求在处理）
上游变慢：λ = 100/s 不变，W = 2s → L = 200
```

**请求数一个没增加，在途数涨了 100 倍**。这些在途请求各自占着：

- 一个 goroutine 的栈（还有它引用的请求体、响应缓冲）；
- 一条到上游的连接（或连接池里的一个等待位）；
- 上游那侧的并发额度。

于是链条是这样的：

```text
上游变慢 → 网关在途数涨 → 内存与连接数涨
   → 连健康检查、管理接口这些「本来能跑完的请求」都挤不进来
   → 「网关把自己压死了」（典型雪崩）
```

⭐ **所以负载保护的判据不是「谁在用」，而是「网关和上游此刻扛不扛得住」**：

| | 限流 | 负载保护 |
|---|---|---|
| 管什么 | **速率**（每秒多少） | **并发**（此刻多少在飞） |
| 维度 | 谁在用（用户 / IP / 路由） | 系统此刻的整体水位 |
| 触发场景 | 流量突增、恶意刷接口 | 上游变慢、依赖抖动 |
| 拒绝理由 | 「你超配额了」（429 + `Retry-After`） | 「系统忙不过来」（503 + `Retry-After`） |

## 二、闸门的三条设计

**本节要点**：一个并发闸门看着只有「计数 + 上限」两件事，但真写起来有三个必须处理好的细节。

### 2.1 快路径不能进排队逻辑

绝大多数请求应该**一次 `select` 就拿到槽位**，不产生任何额外开销：

```go
// ① 先试非阻塞地拿到槽位：绝大多数请求走这条路
select {
case g.slots <- struct{}{}:
    g.inflight.Add(1)
    return g.releaseFunc(), "", nil
default:
}
// ② 走到这里才说明并发已满，进入排队判定
```

⭐ 用 **`chan struct{}` 当槽位**而不是自己维护一个计数器 + 条件变量，有两个便宜可占：

1. `channel` 的等待队列**天然 FIFO** —— 排队公平性不需要自己实现；
2. 拿槽位 = 往 channel 里送一个值，归还 = 从里面取出来，**语义与「容量」天然对齐**。

### 2.2 队列必须有界

**本节要点**：无限排队只是把超时往后推，客户端看到的是「一直转圈」。

```text
并发满了 → 排无限长的队 → 每个请求都要等很久 → 客户端早就超时了
   → 但服务端还在为这些「已经没人要」的请求干活 → 资源浪费在死请求上
```

**正确做法是立刻告诉它「稍后重试」**（503 + `Retry-After`），让它有机会去重试或降级。
这就是为什么队列必须**有长度上限**、并且**有等待时限**。

```go
// ② 需要排队：先看队列还有没有位置
if g.waiting.Add(1) > g.maxQueue {
    g.waiting.Add(-1)
    return nil, ReasonQueueFull, ErrQueueFull   // 连排队都不让排
}
defer g.waiting.Add(-1)

select {
case g.slots <- struct{}{}:
    g.inflight.Add(1)
    return g.releaseFunc(), "", nil
case <-ctx.Done():
    return nil, ReasonQueueTimeout, ErrQueueTimeout   // 排了但等到超时
}
```

⭐ **为什么要区分 `queue_full` 与 `queue_timeout` 两种拒绝原因**：
两者的运维含义完全不同 —— 前者说明「瞬时的并发争抢太激烈」（该调大队列或扩容），
后者说明「槽位周转太慢」（该查上游为什么慢）。把它们都写成「过载」，
排障时就没有下手的地方。

> ⚠️ `waiting` 这个计数**是准入控制而不是精确的队列长度**（`select` 成功后立刻减回去），
> 所以高并发下允许轻微超发 —— 换来的是不用再加一把锁。这里的误差不影响保护效果，
> 因为真正的上限由 `slots` 的容量保证。

### 2.3 `release` 必须幂等

**本节要点**：漏掉一次 `release` 就等于永久少一个并发额度，最后闸门会把自己关死。

```go
// releaseFunc 返回幂等的归还函数
func (g *Gate) releaseFunc() func() {
    var once sync.Once
    return func() {
        once.Do(func() {
            <-g.slots
            g.inflight.Add(-1)
        })
    }
}
```

`sync.Once` 兜住的是这种场景：

```go
rel, _, err := gate.Acquire(ctx)
if err != nil { return err }
defer rel()          // 正常路径
...
if something {
    rel()            // 某条分支里又还了一次（或 defer 与显式调用撞车）
    return
}
```

没有 `sync.Once` 的话，第二次 `release` 会把 channel 里的值多取一个 ——
**额度凭空多出来**，闸门从此失效（而且这种 bug 只在特定分支下出现，非常难查）。

## 三、本机实测：三种结局

配置：并发上限 2、队列上限 1、排队超时 200ms。

```text
=== ③ 负载保护闸门 ===

建闸门：并发上限 Limit()=2、队列上限 1

取第 1、2 个槽位: reason="" / "" → inflight=2 waiting=0
第 3 个已在排队: inflight=2 waiting=1
第 4 个（队列只有 1 位）: reason="queue_full" err="并发已满且队列已满"
释放 1 个槽位后 → 第 3 个: reason=""（空 = 排到了）

排队超时（并发 1 / 队列 1，释放的槽位被立刻抢走，排队者一直等不到）:
  队列位被占后第 3 个: reason="queue_full" err="并发已满且队列已满"
  排队者等到超时: reason="queue_timeout"（预期 queue_timeout）

release 幂等（sync.Once）:
  连调 release() 3 次后 inflight=0（预期 0，不会把额度还多）

nil 闸门（MaxInflight=0 = 不启用）:
  nil.Acquire → reason="" err=<nil>（直接放行）; nil.Limit()=0
```

⭐ 四个读数分别证明了四件事：

| 读数 | 证明了 |
|---|---|
| 第 3 个 `reason=""` | **排队真的能救活请求**：并发满时它不是立刻拒绝，而是等一个槽位 |
| 第 4 个 `queue_full` | 队列长度是**硬上限**，不是建议 |
| 排队者 `queue_timeout` | 等不到就必须**按时限放弃**，不能让请求无限挂起 |
| 连调 3 次 release 后 `inflight=0` | 归还**幂等**，额度不会被还多 |

> ⚠️ **实验里的一次修正**：第一版用 `time.Sleep(50ms)` 来「等第 3 个进入排队」，
> 结果 goroutine 调度顺序不定，输出里「第 4 个」打印在「第 3 个」之前。
> 改成**先轮询 `Stats()` 确认 `waiting > 0` 再测第 4 个** ——
> 凡是用 sleep 猜并发时序的实验，都该换成「用可观测状态做同步」。

## 四、闸门放在流水线的哪个位置？

**本节要点**：负载保护必须在**鉴权之前**，但**健康检查之后**。

```text
/healthz 等 self 路由  → 【负载保护闸门】 → 鉴权 → 限流 → 熔断 → 选节点 → 转发
        ↑ 必须先于闸门              ↑ 必须在鉴权之前
```

两条顺序约束，理由完全不同：

| 约束 | 为什么 |
|---|---|
| **self 路由 → 闸门** | 过载时如果把 `/healthz` 也拒了，负载均衡会认为整个网关挂了，把**所有**流量摘走 —— 本来只是「忙」，变成「全站不可用」。**闸门只应该 shed 业务流量** |
| **闸门 → 鉴权** | 闸门要省的是「资源」（goroutine / 连接），而鉴权本身要查签名、比密钥、可能要读缓存 —— **过载时更不该先做昂贵的事** |

⭐ 一句话口径：**闸门是入口的第一道成本控制**，但要给「不产生上游负载的自我检查接口」留门。

本项目对这条有专门的回归测试：`TestOverloadDoesNotShedHealthz`。

## 使用：给网关开负载保护

**本节要点**：`max_inflight` 不能拍脑袋取，它有一个**可测量的拐点**。

### 1) 配置

```json
{
  "overload": {
    "max_inflight": 128,
    "max_queue": 32,
    "queue_timeout": "1s"
  }
}
```

| 字段 | 含义 | 0 值语义 |
|---|---|---|
| `max_inflight` | 全局并发上限 | **0 = 不启用负载保护** |
| `max_queue` | 允许同时排队的请求数 | 0 = 不排队，并发满立刻 503 |
| `queue_timeout` | 排队等待上限 | 默认 1s |

### 2) `max_inflight` 怎么定：找压测拐点，取 70%

不要凭经验拍一个数，**做一次并发扫描**：

```text
并发数:   1     8     32     64    128    256    512
QPS:    850  6100  21000  33000  35000  34000  29000
P99:     2ms   4ms    9ms   21ms   55ms  180ms  900ms
                                ↑ 吞吐见顶、延迟开始非线性上涨 = 拐点
```

拐点（`inflight ≈ 128`）之后再往上加并发，**吞吐不再增长而延迟继续涨** ——
这就是「系统已经过载，多出来的并发只是在排队」的信号。

⭐ 取拐点的 **70% 左右**作为 `max_inflight`，留 30% 的余量给突发。
留余量的理由：拐点是在**稳态流量**下测出来的，而生产上总有瞬时尖峰；
把上限压在拐点上，尖峰一来就直接触发拒绝。

> 📎 本项目做过完整的并发扫描与共享限流的 A/B 对照，方法与原始读数见项目的
> `docs/性能压测报告.md`（含「可复现命令」一节）；⚠️ 那份报告里的绝对数字依赖具体机器与后端，
> 只有**拐点的位置**与**趋势**是可迁移的结论。

### 3) 与其他三道防线的关系

| 防线 | 触发条件 | 拒绝码 | 恢复 |
|---|---|---|---|
| 限流 | 速率超配额 | 429 | 等下一个窗口 |
| **负载保护** | 并发超水位 | **503 + Retry-After** | 等槽位释放 |
| 熔断 | 上游错误率超标 | 503 | 冷却 + 半开探测 |
| 节点摘除 | 单节点连续失败 | （不拒绝，换节点） | 冷却 + 探测 |

⭐ 注意**负载保护与熔断都返回 503，但含义完全不同**：前者是「我这里忙」，
后者是「上游不行了」。所以响应体里的原因码必须区分（本项目的 `reason` 字段：
`queue_full` / `queue_timeout` / `circuit_open`），否则前端与 SRE 都看不出该重试还是该降级。

### 4) 三个必踩的坑

| 情况 | 现象 | 判定 |
|---|---|---|
| **配了 `max_queue` 但 `max_inflight=0`** | 队列永远用不上（不启用时闸门是 nil） | 启动期校验直接拒绝这种「半配」 |
| **队列配得太大** | 过载时请求全部堆在网关里等 → 内存涨、客户端早超时 | 队列只用来吸收**突发**，不是用来扛**持续过载** |
| **闸门放在鉴权之后** | 过载时先花掉鉴权成本，再拒绝 —— 保护效果打折 | 顺序必须是「闸门 → 鉴权」 |

## 延伸追问

- **负载保护和并发限制器是同一个东西吗？** → 机制相似（都是限并发），**位置和作用域不同**：
  并发限制器通常限**对某个下游**的并发（客户端侧），负载保护限的是**网关自己**的全局并发。
  自适应算法（AIMD 等）属于前者的进阶话题，见 [并发限制器.md](并发限制器.md)。
- **为什么排队比直接拒绝好？** → 因为**并发满往往是瞬时的**：一个槽位几毫秒后就空出来，
  排一下就能排到。但排队必须有界 —— 无限排队只是把「立刻失败」换成「等很久后失败」。
- **`Retry-After` 写多少？** → 不写具体值的做法（固定 1 秒）在有队列的系统里是错的：
  真实等待时间取决于槽位周转速度。**有队列时应该按排队模型估一个值**，或干脆用很短的固定值 + 随机抖动，
  让客户端重试自然错开（避免重试风暴）。
- **过载时该不该给所有接口同样的上限？** → 通常不该。读接口和写接口的代价不同、
  幂等性不同、业务价值也不同。更细的做法是**按路由设权重**（或分出独立的闸门），
  但要注意别把闸门搞得太复杂 —— 它需要在最热的路径上极快做完判断。
- **负载保护和「自适应限流」有什么区别？** → 前者的上限是**配置的死数**，
  后者按实时延迟/在途反馈**动态调整上限**。死数简单可控但需要人工压测；
  自适应省心但在故障时可能把上限调得过低（需要下限保护）。
- **闸门拒绝了请求，是不是就等于「服务不可用」？** →
  不是。503 + `Retry-After` 是一个**明确的、可动作的信号**（稍后重试），
  比「连上去超时」或「连不上」都更好 —— 后者会让客户端分不清是自己的问题还是服务端的问题。
