## 一、场景题：如何让数据统计页面加载速度变快？

**本节要点**：短平快的场景题。答案核心只有一句——**别让"查询"去做"统计"**，提前把结果算好。

### 1.1 核心思路：少查询，把统计前移

> **让统计页面变快的唯一有效办法是：不要在查询时做实时统计。**
> **统计页面慢，就慢在"每次打开都在重新算一遍"。**

**做法：定时任务预计算**

```text
每天（或每小时）定时任务 → 统计前一天的数据 → 把统计结果写入「结果表」
        ↓
用户打开统计页面 → 直接查结果表（不做任何聚合计算）
```

> 实时统计"**既麻烦又慢**"：要扫全量、要聚合、要排序。
> 而结果表里只有算好的数字，**查起来几乎没有成本**。

### 1.2 配套手段

| 手段 | 做法 |
|---|---|
| **分页查询** | 结果表按页取（如每次 10 条 / 20 条），**避免一次拉全量** |
| **查询语句优化** | 优化要放在**统计（写结果表）的时候做**，<br>**而不是每次查询的时候做**——查询路径只留最简单的 `WHERE + LIMIT` |
| **缓存结果** | 结果表外面还可以再套一层缓存（Redis / 本地缓存），<br>尤其是"当天实时看板"这类会被反复刷新的页面 |
| **异步 / 物化** | 更复杂的口径用**物化视图或异步聚合任务**，把重计算从查询链路剥离 |
| **索引** | 结果表按 `维度 + 日期` 建索引，保证分页与筛选都走索引 |

### 1.3 答题结构

```text
① 一句话给结论：不要在查询时做统计，提前算好（定时任务 → 结果表）
② 查询路径：只从结果表分页读，语句保持最简
③ 更优解：结果再加缓存 / 用物化视图 / 异步聚合
④ 主动补一句：查询语句优化要放到统计阶段做，在查询阶段做收益有限
```

> **结论很直白**：**定时任务预计算 + 查结果表 + 分页**，
> 就是这类"统计页面变快"性价比最高的方案；**查询语句优化起不到决定性作用**。

## 延伸追问

- **统计口径变了怎么办？** → 预计算任务**支持按日期重跑（补算历史）**，
  口径变更时回刷结果表；**不要靠实时查询兜底**。
- **业务要实时看板怎么办？** → **冷热两套**：历史区间走预计算结果表，
  **当天数据走实时聚合 + 缓存**（秒级刷新），第二天再由定时任务合并。
- **为什么不直接在结果表上再聚合？** → 每多一层聚合就多一次全表扫描，
  **结果表的价值就在于"已经聚合到最细查询粒度"**。

#### 结果表 DDL（✅ 已在 8.0.46 上实测）

```sql
-- 主键就是页面的查询粒度：维度 + 日期。**顺序反了就走不了索引**
CREATE TABLE stat_daily (
    day        DATE            NOT NULL COMMENT '归桶日期，写入侧就折算好时区',
    kind       VARCHAR(32)     NOT NULL COMMENT '事件类型/指标维度',
    pv         BIGINT UNSIGNED NOT NULL DEFAULT 0,
    uv         BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '上游用 HLL/位图算好后写入',
    updated_at TIMESTAMP       NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (day, kind)
) ENGINE = InnoDB COMMENT '统计页专用：只写不改，页面只读';

-- 定时任务的写入口：**整行覆盖，绝不累加**（累加 = 重跑一次数字翻倍）
INSERT INTO stat_daily (day, kind, pv, uv)
VALUES (?, ?, ?, ?), (?, ?, ?, ?)
AS new
ON DUPLICATE KEY UPDATE pv = new.pv, uv = new.uv;  -- 8.0.14+ 的别名写法；老写法 VALUES(pv) 已废弃

-- 页面的读路径：没有任何聚合、没有排序（主键就是 (day,kind)，倒序天然有序）
SELECT day, kind, pv, uv FROM stat_daily
WHERE day BETWEEN ? AND ? ORDER BY day DESC LIMIT 20;
```

> **`AS new` 而不是 `VALUES(pv)`**：后者在 8.0.20 起被标记废弃，
> 而且和 `INSERT ... VALUES` 里的括号嵌套容易看错列。

建完回读的结构、两种 upsert 写法的实际行为、以及读路径的执行计划，本机逐条对上：

```text
# ① 原样执行 CREATE TABLE，SHOW CREATE TABLE 回读（表注释、列注释都在）
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='统计页专用：只写不改，页面只读'

# ② AS new 写法：首次插入 2 行
| affected_first_run | 2          <- ROW_COUNT()，插入两条各算 1
| affected_rerun     | 0          <- 同一条再跑一遍：值没变，一行都没"改"
# 换成不同数值再 upsert（覆盖语义，不是累加）
| 2026-09-23 | view | 999 | 888 | <- pv=999 而不是 100+999

# ③ 老写法 VALUES(pv)：能跑，但每引用一列给一条废弃告警
Warning 1287 | 'VALUES function' is deprecated and will be removed in a future release.
             | Please use an alias (INSERT INTO ... VALUES (...) AS alias) and
             | replace VALUES(col) in the ON DUPLICATE KEY UPDATE clause with alias.col instead
（两条 —— pv、uv 各一次）

# ④ 读路径：WHERE day BETWEEN ? AND ? ORDER BY day DESC LIMIT 20
| type: range | key: PRIMARY | key_len: 3 | rows: 3 | Extra: Using where; Backward index scan
-> Limit: 20 row(s)  (cost=0.861 rows=3) (actual time=0.246..0.255 rows=3 loops=1)
    -> Filter: (stat_daily.`day` between '2026-01-01' and '2026-09-24')
        -> Index range scan on stat_daily using PRIMARY over ('2026-01-01' <= day <= '2026-09-24') (reverse)
```

四条正文断言的对账结果：

- **"整行覆盖，绝不累加"成立**：`ROW_COUNT()` 首次 2、重跑 0（值相同所以没改动任何一行），
  换值之后 pv 是 999 而不是累加 —— 幂等这件事由 `ON DUPLICATE KEY UPDATE pv = new.pv` 保证，
  **脚本里把 `=` 写成 `pv = pv + new.pv` 才是"重跑翻倍"的来源**。
- **`AS new` 是 8.0.14+ 的写法，`VALUES(pv)` 在 8.0.46 上仍是可执行语句**，只是带
  `Warning 1287`；它**按列各给一条**告警，所以别指望"日志里只出现一次"。
- **"倒序天然有序"成立，但要看清它靠的是 `Backward index scan`**：主键是升序的，
  `ORDER BY day DESC` 让 8.0 反向扫索引，`Extra` 里没有 `Using filesort`。
  ⚠️ 这个优化**要求排序列就是主键前缀**，排序字段换成非主键列就要 filesort 了。
- **"主键顺序反了就走不了索引"实测为真**：同一份数据建成 `PRIMARY KEY (kind, day)` 之后，
  同样的 `WHERE day BETWEEN …` 变成
  `type: ALL | possible_keys: NULL | key: NULL | Extra: Using where; Using filesort`。

`updated_at ... ON UPDATE CURRENT_TIMESTAMP` 也顺手验了：`UPDATE ... SET pv = pv + 1` 之后
只有被改的那一行时间戳往前跳（`04:35:31 → 04:35:32`），另一行保持原值 ——
**它是"最后写入时间"，不是"数据口径时间"**，重算历史日期会把 `updated_at` 一起刷掉，
排查"这份统计是什么时候算的"时别把它当版本标记用。

⚠️ **仍未实测**：分区表 / `pt` 大表的写入放大、真实 UV 的 HLL 存储、以及"定时任务连不上库时
结果表落后几天"的运维现象 —— 这些需要生产数据量与调度环境。

#### 骨架：定时任务 = 筛窗口 → 纯函数聚合 → upsert

```go
package rollup

import (
	"context"
	"sort"
	"sync"
	"time"
)

// 正文那句"不要在查询时做统计"落到实现上，其实只有三个动作：
// **聚合 → 幂等写结果表 → 按窗口回刷**。
// 其中"幂等"和"回刷窗口"是预计算最容易出事的两处：
// 口径变了要重算、数据迟到了要重算，而**重算绝不能把数字算成两份**。

// Event 是一条原始明细（正文里"要扫全量、要聚合"的那部分数据）。
type Event struct {
	Day    string // 归桶日期，如 2026-09-24。**写入时就折算好时区**，别让查询侧算
	Kind   string // 事件类型：view / click / publish
	UID    string
	Arrive time.Time // 落库时间，用来判断"这条是不是迟到的"
}

// Row 是结果表里的一行：维度 + 日期 + 算好的数字。
// UV 在这里是精确值（用 set 数出来的）；**生产上要换成 HLL / 位图**，
// 因为几千万 UV 不可能在内存里数。
type Row struct {
	Day  string
	Kind string
	PV   int
	UV   int
}

// Aggregate 把明细聚成 (day, kind) 粒度的结果。**纯函数、不碰数据库**，
// 所以重跑一次和跑十次得到的是同一份输出——"幂等"是从这里来的。
func Aggregate(events []Event) []Row {
	pv := map[string]int{}
	uv := map[string]map[string]bool{}
	for _, e := range events {
		k := e.Day + "\x00" + e.Kind
		pv[k]++
		if uv[k] == nil {
			uv[k] = map[string]bool{}
		}
		uv[k][e.UID] = true
	}
	out := make([]Row, 0, len(pv))
	for k, n := range pv {
		day, kind := splitKey(k)
		out = append(out, Row{Day: day, Kind: kind, PV: n, UV: len(uv[k])})
	}
	// 排序是**必需的**：不排序则每次跑出来的行序随 map 遍历变化，
	// 分批 upsert 时"失败后从第几批续跑"就不稳定，排查时对不上。
	sort.Slice(out, func(i, j int) bool {
		if out[i].Day != out[j].Day {
			return out[i].Day > out[j].Day // 日期倒序：页面默认看最近
		}
		return out[i].Kind < out[j].Kind
	})
	return out
}

func joinKey(day, kind string) string { return day + "\x00" + kind }

func splitKey(k string) (day, kind string) {
	for i := 0; i < len(k); i++ {
		if k[i] == 0 {
			return k[:i], k[i+1:]
		}
	}
	return k, ""
}
```

聚合是纯函数，生产上还要有落点；下面是结果表的写入口 `Store`，以及跑通链路用的内存实现。

```go
// Store 是结果表的写入口。生产实现就是
// `INSERT ... ON DUPLICATE KEY UPDATE pv=VALUES(pv), uv=VALUES(uv)`（DDL 见正文小节）。
type Store interface {
	Upsert(ctx context.Context, rows []Row) error
	Get(day, kind string) (Row, bool)
}

// MemStore 是跑通链路用的内存实现。
type MemStore struct {
	mu   sync.Mutex
	data map[string]Row
}

func NewMemStore() *MemStore { return &MemStore{data: map[string]Row{}} }

// Upsert **整行覆盖，不是累加**——这是重跑幂等的关键。
// 写成 `pv = pv + VALUES(pv)` 的话，重跑一次数字就翻倍，
// 而"重跑"在预计算里是常态（补算、口径变更、任务失败重试）。
func (s *MemStore) Upsert(_ context.Context, rows []Row) error {
	s.mu.Lock()
	defer s.mu.Unlock()
	for _, r := range rows {
		s.data[joinKey(r.Day, r.Kind)] = r
	}
	return nil
}

func (s *MemStore) Get(day, kind string) (Row, bool) {
	s.mu.Lock()
	defer s.mu.Unlock()
	r, ok := s.data[joinKey(day, kind)]
	return r, ok
}
```

结果表能幂等写入之后，剩下的问题是一次任务该扫哪些天；最后三个函数把回刷窗口、明细筛选和整个任务串起来。

```go
// DaysBack 是**回刷窗口**：定时任务不只算"昨天"，而是把最近 N 天整体重算一遍。两个理由：
//  1. **迟到数据**——客户端批量补传、跨天边界的请求，只算昨天就会永久少掉；
//  2. **口径变更**——统计规则改了，历史要能跟上（正文追问"口径变了怎么办"的答案就是回刷）。
//
// N 取"业务能容忍的迟到时长"，**不是越大越好**：窗口越长，单次任务扫的明细越多。
func DaysBack(now time.Time, n int, layout string) []string {
	days := make([]string, 0, n)
	for i := 0; i < n; i++ {
		days = append(days, now.AddDate(0, 0, -i).Format(layout))
	}
	return days
}

// FilterDays 按天窗口筛明细（生产里这一步是 SQL 的 `WHERE day IN (...)`）。
func FilterDays(events []Event, days []string) []Event {
	want := make(map[string]bool, len(days))
	for _, d := range days {
		want[d] = true
	}
	out := make([]Event, 0, len(events))
	for _, e := range events {
		if want[e.Day] {
			out = append(out, e)
		}
	}
	return out
}

// RunJob 是一次定时任务的骨架：筛窗口 → 聚合 → upsert。
// 返回写了多少行，便于打点（**跑没跑成、写了多少行，必须能看出来**）。
func RunJob(ctx context.Context, store Store, events []Event, days []string) (int, error) {
	rows := Aggregate(FilterDays(events, days))
	if err := store.Upsert(ctx, rows); err != nil {
		return 0, err
	}
	return len(rows), nil
}
```

#### 实测：幂等、回刷窗口、以及查询成本转移

| 测试 | 实测输出 | 结论 |
|---|---|---|
| 同一批明细连跑 3 次 | 每次都"写 5 行，2026-09-24/view = PV 3 UV 2" | **重跑不翻倍**（PV 3 条里有 1 条同一 UID 重复访问 → UV 2，聚合口径也测到了） |
| 窗口=1 天，一条 09-22 的明细在 09-24 补传上来后再跑 | `2026-09-22/view` 存在=**false** | **迟到数据永久漏掉**，事后重跑也救不回来 |
| 窗口=3 天，同样补传后再跑 | `2026-09-22/view = PV 2 UV 2`，存在=true | 回刷窗口把迟到数据吸收了 |
| 一次页面加载（3 天 × 2 指标） | 实时聚合要扫 **7 条明细** + 内存分组；查结果表是 **5 次主键命中** | 明细规模放大 100 倍时，前者线性变贵、后者不变 |

> **表里那个"存在=false"就是预聚合最阴的坑**：结果表里**没有行**和**这行是 0** 是两件事。
> 页面若直接 `rows[i].pv`，缺桶会渲染成空白或干脆跳过那一天，
> 用户看到的就是"22 号没人访问"。**查询侧必须按日期补零**（或任务对全维度笛卡尔积落行）。

#### 一句话收口

> 预聚合的全部实现难度不在"算"，而在**三件让重跑变安全的事**：
> **聚合写成纯函数、写库用整行覆盖的 upsert、任务按窗口回刷而不是只算昨天**——
> 做到这三条，正文那句"口径变了支持按日期重跑"才是真的能做到。
