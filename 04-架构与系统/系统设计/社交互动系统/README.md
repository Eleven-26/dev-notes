## 一、场景题：设计一个社交互动系统

**本节要点**：这道题**不考"你能堆多少组件"**，考的是「**每份数据被多少人同时读、同时改**」以及「**代价放在哪一侧**」。
下面按「先分清有哪些数据 → 判它是不是共享可变量 → 选原子手段 → 把代价落点说清」的顺序推，每一步都附本机实测读数。

**先看这张清单** —— 互动层的十三个问题点、各自的手段、落在哪一篇哪一节：

| # | 问题 | 手段 | 落在哪 |
|---|---|---|---|
| 1 | **计数**（点赞数 / 评论数 / 粉丝数） | Redis 计数器 + 异步落库 | [评论点赞设计.md](评论点赞设计.md) 一 |
| 2 | **去重**（一人一赞） | `SADD` 原子判重 + DB 唯一索引兜底 | [评论点赞设计.md](评论点赞设计.md) 二 |
| 3 | **缓存** | 计数本身就是「可 O(1) 读写的状态」，不是缓存一个查询结果 | [评论点赞设计.md](评论点赞设计.md) 1.3 |
| 4 | **异步写** | 攒批落库（把 N 次提交摊成 1 次） | [评论点赞设计.md](评论点赞设计.md) 三 |
| 5 | **热 key** | 单实例拆 key **零收益**，跨实例才有效；先判节点是否饱和 | [评论点赞设计.md](评论点赞设计.md) 四 |
| 6 | **排行榜结构** | Redis ZSET（哈希表 + 跳表） | [排行榜设计.md](排行榜设计.md) 一 |
| 7 | **分页** | ZSET 深分页不慢（O(log N + M)），但 offset 会**重复** → 游标 / 快照 | [排行榜设计.md](排行榜设计.md) 二 |
| 8 | **实时更新** | `ZINCRBY` O(log N)，改完立刻改名次 | [排行榜设计.md](排行榜设计.md) 三 |
| 9 | **持久化** | RDB 丢整个快照窗口、AOF 丢约 1 秒 | [排行榜设计.md](排行榜设计.md) 四 |
| 10 | **关系存储** | 邻接表双索引 / Redis SET；两个方向**都要快** | [关注粉丝设计.md](关注粉丝设计.md) 一 |
| 11 | **分片** | 分片键只优化一个方向，另一个方向**必须广播** | [关注粉丝设计.md](关注粉丝设计.md) 二 |
| 12 | **推拉结合** | 写扩散 vs 读扩散，比「粉丝数 × 发帖频次」与「关注数 × 读频次」 | [关注粉丝设计.md](关注粉丝设计.md) 三 |
| 13 | **大 V 问题** | 超阈值转拉；发帖写次数从**粉丝数**降到 **1** | [关注粉丝设计.md](关注粉丝设计.md) 四 |

⚠️ 这三篇的分工是**按数据形态切的，不是按功能切的** —— 计数、有序集合、关系图是三种不同形态的数据，
用的 Redis 结构不同、代价结构也不同，不能拿一套方案硬套。

### 1.1 第一步：要素分析（先想清楚"有什么"）

一个社交互动系统，绕不开这四类**基础对象**与两类**派生数据**：

| 类别 | 例子 | 说明 |
|---|---|---|
| **① 用户** | uid、昵称、头像 | 互动的主体 |
| **② 内容** | 帖子 / 视频 / 商品 | 互动的受体 |
| **③ 互动** | 点赞、评论 | 用户对内容产生的动作 |
| **④ 关系** | 关注 / 粉丝 / 好友 | 用户与用户之间的边 |
| **⑤ 派生·计数** | 点赞数、评论数、粉丝数 | 由①②③④算出来的**一个数字** |
| **⑥ 派生·榜单** | 热度榜、贡献榜 | 由计数**排序**出来的一张表 |

⭐ 关键动作是**把⑤⑥从③④里分出来** —— 很多人一上来就把"点赞数"当成"点赞记录的一个查询"，
于是掉进第一节那个 O(k) 的坑。**能压成一个数字的，就不要每次去数**。

### 1.2 第二步：按「数据形态」分四类（这道题真正的分类轴）

| 形态 | 例子 | 读特征 | 写特征 | 首选结构 |
|---|---|---|---|---|
| **计数器** | 点赞数、粉丝数 | 极高频读、期望 O(1) | 高频写、**必须原子** | Redis `INCR` / `HINCRBY` |
| **有序集合** | 热度榜、时间线 | 范围读、要按序 | 高频改分 | Redis `ZSET` |
| **关系图** | 关注 / 粉丝 | **双向**查询 | 中频、成对写 | 邻接表（双索引）/ Redis `SET` |
| **内容本身** | 评论正文 | 分页读 | 低频、要持久 | DB / 文档库 |

⭐ 四类的**代价结构完全不同**：计数器的痛点是「原子性与读放大」、有序集合的痛点是「翻页一致性」、
关系图的痛点是「分片键选谁」、内容本身的痛点是「存储与检索」。**这就是为什么这三篇要分开写。**

### 1.3 第三步：三步骨架（把三个子问题串起来）

不管写哪一个环节，都可以按这三步回答：

1. **判「是不是共享可变量」** —— 计数、名次、关系，本质都是「一份状态被多个请求同时改」。
   是 → 必须原子；不是（如评论正文，一条一写、互不影响）→ 按普通写入处理。
2. **选原子手段** —— 三档，从快到慢：
   - Redis **单命令**（`INCR` / `SADD` / `ZINCRBY` 自带原子性）；
   - Redis **Lua 脚本**（多条命令要一起原子时，如「判重 + 计数」）；
   - DB **条件更新 / 唯一索引**（`UPDATE ... WHERE stock > 0`、`INSERT IGNORE`）—— 落库侧的最终防线。
3. **定代价落点** —— 这步最见功力，三个典型取舍：
   - **异步**：把 fsync 摊薄（实测 2000 条：13.7s → 136ms），代价是攒批窗口内的丢失窗口；
   - **推 / 拉**：写放大 vs 读放大，比的是「粉丝数 × 发帖频次」与「关注数 × 读频次」；
   - **分片**：单分片快 vs 广播慢，比的是「哪类查询高频」。

⭐ 一句话：**前两步保证"不会错"，第三步决定"划不划算"** —— 面试里出错的分水岭往往在第三步：
方案是对的，但代价落错了地方（见 [评论点赞设计.md](评论点赞设计.md) 第四节：单实例拆热 key 是本机实测的**零收益**）。

### 1.4 第四步：答题结构（怎么把上面讲完）

| 步骤 | 说什么 | 别说成什么 |
|---|---|---|
| 1 | 先列**数据形态**（计数 / 有序集合 / 关系 / 内容） | ❌ 别上来就报组件清单 |
| 2 | 对每类说**痛点**（原子性 / 分页一致性 / 分片键 / 存储） | ❌ 别只说"我用 Redis" |
| 3 | 给**手段**并说清**原子边界**（哪一步是原子的、哪一步不是） | ❌ 别提了原子却留着竞态窗口 |
| 4 | 说**代价落点**（异步丢多少、推拉谁吃亏、分片谁广播） | ❌ 别把取舍说成"没缺点" |
| 5 | 补**兜底**（对账、监控热 key、降级） | ❌ 别假设"上面都成功了" |

⚠️ 最容易答砸的是第 4 步。**"我用了 Redis / MQ / 分片"不是答案，把它们各自的代价说出来才是** ——
本目录三篇的每一个 `text` 块，都是为了给"代价"这句话提供本机读数。

## 延伸追问

- **为什么把互动层单独拎出来做场景题？** → 因为它是「高并发读 + 高并发写 + 强共享状态」三件事**同时**出现的少数场景。普通业务要么读多写少（缓存解决），要么写多读少（队列解决），互动层两个都多，逼着你把原子性、削峰、分片全走一遍。
- **这三篇能合并进 [秒杀系统/](../秒杀系统/README.md) 那套吗？** → 手段可以，数据不行。秒杀的核心是「稀缺资源扣减」，互动层没有"扣减"；反过来互动层的「计数与排序」秒杀里也没有。两套场景共用原子判定、异步、分片这些**手段**，但痛点不同 —— 所以是并列的两个目录，不是同一篇的子节。
- **如果只让讲一个最容易被忽略的点？** → **热 key 的收益不在"拆"，在"拆到哪"**。本机实测：单实例上把一个热 key 拆成 8 份，最快值与不拆**完全相同**（173ms vs 174ms）—— 这个反直觉结论恰好是面试里区分"背过"与"想过"的地方。
- **和 [朋友圈设计.md](../朋友圈设计.md) 什么关系？** → 那篇是 **feed 视角**（内容怎么分发到人、推拉怎么分层）；本目录是 **互动数据视角**（计数/榜单/关系怎么存）。两篇的"推拉"是同一组概念的两个应用面。
