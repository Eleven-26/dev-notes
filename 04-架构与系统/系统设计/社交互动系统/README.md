# 社交互动系统

> 本目录收**社交互动系统**这道场景题：一篇**总体设计** + 六篇零件篇 + 一篇存储横切篇。
> 本篇是目录导读，只给「这个系统有哪几个核心问题、有哪些零件、怎么读」三件事，
> 每个问题的解法在零件篇里；本目录不重述具体方案。
>
> 内容整理自个人学习笔记；参考资料与原始素材见 [素材清单](../../../素材清单.md)。
> **落地实现**：各篇实验全部在本机 Docker 环境跑通（Redis 7.4.11 / MySQL 8.0.46），代码为 Go；
> 正文所有 `text` 块都是本机真实运行结果。

## 一、这个系统有哪几个核心问题？

**本节要点**：这道题**不考"你能堆多少组件"**，考的是「**每份数据被多少人同时读、同时改**」以及「**代价放在哪一侧**」—— 分类轴不是功能，而是**数据形态**。

| # | 问题（数据形态） | 一句话 |
|---|---|---|
| ① | **计数器** | 点赞数、粉丝数：读极高频期望 O(1)、写必须原子 —— 压成一个数字，**别每次去数** |
| ② | **有序集合** | 热度榜、时间线：范围读、要按序、高频改分 —— 痛点是**翻页一致性** |
| ③ | **关系图** | 关注 / 粉丝 / 好友：双向查询、成对写 —— 痛点是**分片键选谁**，一个方向只能广播 |
| ④ | **内容本身** | 评论正文：分页读、低频写、要持久 —— 落 DB / 文档库 |

⭐ 四类的**代价结构完全不同**：计数器的痛点是「原子性与读放大」、有序集合的痛点是「翻页一致性」、关系图的痛点是「分片键选谁」、内容本身的痛点是「存储与检索」。**这就是为什么这几篇要分开写** —— 能不能拿一套方案硬套，见 [总体设计.md](总体设计.md) 第一节。

![四类互动数据按形态分格：计数器、有序集合、关系图、内容本身，各自的首选结构与痛点](images/互动层四类数据形态.svg)

图怎么读：四格是四条独立的代价结构，分类轴是**数据形态**而不是功能。① 计数器（点赞数、粉丝数）读极高频期望 O(1)、写必须原子，首选 `INCR` / `HINCRBY`，痛点是原子性与读放大——压成一个数字，别每次去数；② 有序集合（热度榜、时间线）要范围读且按序、高频改分，首选 `ZSET`，痛点是翻页一致性；③ 关系图（关注、粉丝）双向查询、成对写，首选邻接表双索引 / `SET`，痛点是分片键选谁——一个方向能单分片，另一个方向只能广播；④ 内容本身（评论正文）低频但要持久，落 DB / 文档库。上面那张表与这张图是同一件事的两种画法，也正是这几篇分开写的理由。

### 2.1 四类形态与篇目的对应

```text
计数器    → 评论点赞设计.md（计数 / 去重 / 异步写 / 热 key）
```

## 三、按什么顺序读？

**本节要点**：先看**总体设计**（要素分析 + 四类数据形态 + 三步骨架），再按形态依次读**计数器 → 有序集合 → 关系图**（关注型 → 双向），然后用 **feed 视角**两篇换一个面看同一批数据，最后用存储全景收口。

### 3.1 推荐顺序

```text
① 总体设计.md          ← 总体设计：整体形态 + 三个核心取舍 + 一次互动走哪几步
        ↓
② 评论点赞设计.md      ← 计数器：计数 / 去重 / 异步写 / 热 key
        ↓
③ 排行榜设计.md        ← 有序集合：ZSET / 分页 / 实时更新 / 持久化
        ↓
④ 关注粉丝设计.md      ← 关系图（关注型）：关系存储 / 分片 / 推拉 / 大 V
        ↓
⑤ 好友关系设计.md      ← 关系图（双向好友）：状态机 / 双向模型 / 缓存一致
        ↓
⑥ 朋友圈设计.md        ← feed 视角：要素分析 / ER 表 / 数据分层 / 推拉
        ↓
⑦ 朋友圈骨架.md        ← 落地骨架：Go / Java 三组实测（写放大 / 读放大 / 分页稳定性）
        ↓
⑧ 存储全景.md          ← 横切收口：以上几篇的数据分别落在哪、怎么同步
```

**反过来也成立**：如果只关心"双向好友怎么建、状态机怎么流转"，可以直接从 [好友关系设计.md](好友关系设计.md) 读起 —— 它不依赖排行榜与 feed 那两篇。

### 3.3 三种常见的读错顺序

| 读法 | 后果 |
|---|---|
| 先读分片、后读形态 | 分片键选谁讲得通，但"为什么关系图与计数器要分开"体会不到 |
| 只读排行榜、跳过计数 | ZSET 用法记住了，但"榜单的分数从哪来、丢了怎么办"接不上 |
| 七篇各读一半 | 计数、榜单、关系、feed 各一条线，在"一份数据被多少人同时读写"上对不齐 |

## 延伸追问

- **互动层为什么单独拎出来做场景题？** → 因为它是「高并发读 + 高并发写 + 强共享状态」三件事**同时**出现的少数场景。普通业务要么读多写少（缓存解决），要么写多读少（队列解决），互动层两个都多，逼着你把原子性、削峰、分片全走一遍。
- **互动层和秒杀，是同一套题吗？** → 手段相通、痛点不同。秒杀的核心是「稀缺资源扣减」，互动层没有"扣减"；互动层的「计数与排序」秒杀里也没有。两套场景共用原子判定、异步、分片这些**手段**，所以是并列的两个目录，不是同一篇的子节。
- **这套笔记哪些是实测的？** → [评论点赞设计.md](评论点赞设计.md)、[排行榜设计.md](排行榜设计.md)、[关注粉丝设计.md](关注粉丝设计.md)、[好友关系设计.md](好友关系设计.md) 的 `text` 块为本机 Docker 实测（Redis 7.4.11 / MySQL 8.0.46）；[朋友圈骨架.md](朋友圈骨架.md) 的 Go / Java 骨架附三组实测。
- **读完能回答的最小闭环是什么？** → "一份互动数据被多少人同时读写"：先判形态（计数 / 有序集合 / 关系 / 内容）→ 选原子手段 → 把代价落在异步 / 推拉 / 分片上 —— 展开见 [总体设计.md](总体设计.md) 第二节。
