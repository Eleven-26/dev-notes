# 排行榜设计

> 场景题：实时排行榜 —— 为什么用 Redis ZSET、分页怎么翻、分数怎么实时更新、宕机了丢多少，四个环节都附本机实测。
>
> 内容整理自大厂 Go 后端面试真题；参考资料与原始素材见 [素材清单](../../../素材清单.md)。
> **落地实现**：本机 Docker（Redis 7.4.11）+ Go 实测，正文 `text` 块都是本机真实运行结果。

---

## 一、排行榜为什么用 ZSET：跳表给了什么？

**本节要点**：排行榜的本质是「**按分数排序 + 频繁查第 K 名 + 频繁改分数**」。要同时满足这三条，只有「有序结构 + O(log N) 改分」这一条路。Redis ZSET 底层的跳表，正是为这三个操作设计的。

### 1.1 三个操作决定了选型

| 操作 | 排行榜要它做什么 | 哈希表 | 有序数组 | 平衡树 | 跳表（ZSET） |
|---|---|---|---|---|---|
| 按分数定位名次 | 「我排第几」 | 不支持 | 二分 O(log N) 查，但插入要搬移 | O(log N) | O(log N) |
| 范围取前 N 名 | 「前 100 名是谁」 | 不支持 | 连续内存，缓存友好 | 中序遍历 | 沿途顺链，O(log N + M) |
| 改分数 | 「又得了 5 分」 | O(1) 但失序 | O(N) 搬移 | O(log N) + 旋转 | O(log N) + 改链 |

ZSET 的做法是**两套结构并存**：哈希表存「成员 → 分数」（O(1) 查分），跳表存「分数 → 成员」的有序链（范围与名次）。两套结构一起维护，所以 `ZADD` / `ZINCRBY` 是 O(log N)，`ZSCORE` / `ZREVRANK` 也是。

### 1.2 为什么不用平衡树

面试常追问这点。跳表的答案很实际：

- **范围查询天然顺链** —— 定位到起点后顺序遍历即可，不需要中序遍历的递归与栈；
- **实现与调试成本低** —— 平衡树的旋转/染色是错误高发区；
- **并发局部修改的优势用不上** —— Redis 单线程执行命令，平衡树在这方面的优势（无锁改造）在这里没有场景。

### 1.3 代价：ZSET 是内存结构

一条成员在 ZSET 里要占两份存储（哈希项 + 跳表节点）。**百万级榜单的 ZSET 常驻内存**，这是必须提前算的账：要么给榜单设有效期（日榜/周榜），要么只保留 top N（把长尾踢出 ZSET）。

## 二、分页：为什么 ZSET 深分页不慢，但 offset 分页仍然要换？

**本节要点**：这是本篇最容易被想岔的一节。ZSET 的 `ZREVRANGE start stop` **不是** SQL `LIMIT offset` 那种「跳过 offset 行」的代价 —— 它是 O(log N + M)。但**性能不慢 ≠ 结果正确**：榜单在变，用 offset 翻页会重复和漏。

### 2.1 实测：20 万成员榜单，翻到很深也不慢

```text
命令                                  耗时
ZREVRANGE rank:big 0      ..9          143µs
ZREVRANGE rank:big 100000 ..100009     267µs
ZREVRANGE rank:big 199990 ..199999     309µs
```

⭐ 读法：翻到第 20 万名，耗时只从 143µs 涨到 309µs（约 2 倍，而不是 SQL 里那种「offset 越大线性变慢」）。原因：跳表带 `span`（每层记录跨越的节点数），定位第 K 名是 **O(log N)** 的跳跃，不是逐个走。所以「ZSET 深分页慢」这个说法不成立。

### 2.2 ⚠️ 但 offset 分页仍然会重复 —— 这不是性能问题，是正确性问题

```text
第 1 页（ZREVRANGE 0 1）        : [A B]
← 此时 X（95 分）插入
第 2 页（ZREVRANGE 2 3）        : [B C]   ← B 重复出现
第 2 页（游标 ZREVRANGEBYSCORE (90 -inf LIMIT 0 2）: [C D]   ← 不重复
```

读法：第 1 页读完后插入了一个比 B 分高的 X，**整体后移一位**，于是第 2 页的第一个又变成了 B。用户会看到「B 出现了两次」，更糟的情况是漏掉一个。

### 2.3 两条路线

| 路线 | 做法 | 适合 |
|---|---|---|
| **游标分页** | 用「上一页最后一个成员的分数」作锚点：`ZREVRANGEBYSCORE key (lastScore -inf LIMIT 0 N` | 无限下拉、结果集持续变化 |
| **快照分页** | 定时（如每分钟）把榜单固化成一个不可变的 key，翻页都读快照 | 要「第 X 名」这种页码语义、且能接受分钟级延迟 |

⭐ 电商/直播榜单常见的是**两者都要**：「第 1~100 名」用快照（读起来稳定）、「继续下滑」用游标。纯 offset 分页在实时榜上是错的。

### 2.4 判据

| 问题 | 判据 |
|---|---|
| ZSET 深分页要不要怕？ | 不用怕性能（实测 20 万成员第 20 万名仍 309µs）；要怕的是**一致性** |
| 用游标还是快照？ | 用户要「第几页」→ 快照；用户要「一直往下翻」→ 游标 |
| ⚠️ 同分怎么排？ | ZSET 按 `(score, member)` 排序，member 是字典序。同分时名次由 member 决定 —— 要稳定名次就得把「时间戳/uid」编进 member，别指望插入顺序 |

## 三、实时更新：分数改了，名次要多快变？

**本节要点**：`ZINCRBY` 改分是 O(log N)，改完立刻可按新分数读名次 —— **不需要任何额外的排序或重建**。这是 ZSET 相对「定时重算榜单」的核心优势。

### 3.1 实测：一次 `ZINCRBY` 立刻改变名次

```text
carol 更新前：分数 80，第 3 名
ZINCRBY rank:live 500 carol
carol 更新后：分数 580，第 1 名
```

⭐ 读法：`ZINCRBY` 同时完成「跳到新分数位置」与「更新哈希表里的分数」，读 `ZREVRANK` 立即返回新名次。整个过程 O(log N)。

### 3.2 什么时候不该用 ZSET 实时榜

| 场景 | 建议 |
|---|---|
| 每秒几万次改分 | 可以。`ZINCRBY` 是 O(log N)，且 Redis 单键操作原子 |
| 分值是「聚合出来的」（如按多维度加权） | 别在 Redis 里算加权 —— 应用侧算好增量再 `ZINCRBY`，否则要把明细都搬到 Redis |
| 榜单要「每日重置」 | 用日期做 key（`rank:20261004`），配 TTL 自动过期，别在一个 key 上手动清零 |
| 需要「历史名次曲线」 | ZSET 只留当前值；历史要另存（时序库/快照表），别指望从 ZSET 里复原 |

### 3.3 ⚠️ 两个一致性坑

1. **分数与明细必须能对账**。ZSET 是「聚合后的状态」，一旦写入失败或重复，榜单就与真实数据脱钩。要能定时用明细重算 top N 并与 ZSET 比对。
2. **名次是「读时算」的**。同一个人两次读之间名次可能变（正常）。但如果业务要「发奖时必须按某个确定名次」，那就得先把榜单快照下来，否则发奖那一刻的名次无法复现。

## 四、持久化：RDB 和 AOF 到底丢多少？

**本节要点**：排行榜常被当成「丢了重算就行」的缓存，但很多时候它承载了**唯一的分数状态**（分数不在别处）。那就必须回答：宕机了丢多少。**RDB 是快照 —— 丢的是两次快照之间的全部写入；AOF 是日志 —— 丢的只是最后一次 fsync 之后的一小段。**

### 4.1 实测：写入 20 万成员，然后 `docker kill`（SIGKILL，不给优雅退出机会）

```text
                 写入后        崩溃重启后
RDB 容器          200000   →   0          ← 全丢
AOF 容器          200000   →   200000     ← 全保
```

两个容器的配置（`CONFIG GET`）：

```text
RDB: save 3600 1 300 100 60 10000
AOF: appendonly yes / appendfsync everysec
```

### 4.2 读法：为什么会差这么远

- **RDB 是定时快照**：默认触发条件是「900 秒 1 次修改 / 300 秒 100 次 / 60 秒 10000 次」任一满足。在**距离上次快照不足 60 秒**时崩溃，这段时间的全部写入都还没落盘 → 实测全丢。
- **AOF 是追加日志**：`appendfsync everysec` 每秒把缓冲刷一次盘 → 最多丢约 1 秒。本次写入后 `sleep 2` 再 kill，所以一条没丢。
- ⚠️ **这不是「AOF 一定比 RDB 好」** —— RDB 的丢弃窗口是**有上界的**（最多到下一个触发点），把默认配置改成 `save 60 10000` 之外更密的点、或主动 `BGSAVE`，窗口就缩短。**关键是把窗口说清楚，而不是祈祷**。

### 4.3 代价：AOF 文件明显更大

```text
RDB  dump.rdb                 3,088,999 字节  ≈ 3.0 MB
AOF  appendonly.aof.1.incr.aof  20,133,462 字节  ≈ 19.2 MB
```

同一份 20 万成员数据，AOF 增量文件约为 RDB 的 **6.5 倍**。原因是 RDB 存的是「压缩后的最终状态」，AOF 存的是「所有写命令」。所以生产上常见的是**两者都开**：AOF 保数据（丢得少），RDB 用于快速重启与备份。

⚠️ AOF 也不是无限增长 —— 它靠 `BGREWRITEAOF` 重写成新基线。实测容器里能看到基线文件与增量文件是分开的：

```text
appendonly.aof.1.base.rdb        89 字节        ← 重写后的基线（RDB 格式）
appendonly.aof.1.incr.aof        20,133,462 字节 ← 基线之后累积的写命令
appendonly.aof.manifest          88 字节        ← 清单
```

### 4.4 判据

| 问题 | 判据 |
|---|---|
| 排行榜能丢吗？ | 分数能重算 → 可以只开 RDB（甚至不开）；分数是唯一状态 → 必须开 AOF |
| 选 RDB 还是 AOF？ | 要「丢得少」选 AOF；要「重启快、文件小、方便备份」选 RDB；生产通常都开 |
| ⚠️ 怎么验证真的没丢？ | **不能只看配置**。要像本次一样真做一次「写入 → SIGKILL → 重启 → 数一遍」，配置写了不等于生效（本次 RDB 第一次测试就因为已超过 60 秒而「意外没丢」，第二次收紧时间窗才复现全丢） |

## 使用：排行榜的 Go 骨架

> ⚠️ 下面三段是骨架片段（省略了 import、类型定义与错误包装）。**改分与分页**的写法取自本机实测程序（读数见第二、三节）；**定时快照**是按语义补全的示意（未单独实测）。

### 第一段：改分与读榜

```go
// 改分：O(log N)，不需要重建榜单
func AddScore(ctx context.Context, rdb *redis.Client, board string, uid int64, delta float64) error {
	return rdb.ZIncrBy(ctx, "rank:"+board, delta, strconv.FormatInt(uid, 10)).Err()
}

// 前 N 名（带名次与分数）
func TopN(ctx context.Context, rdb *redis.Client, board string, n int64) ([]redis.Z, error) {
	return rdb.ZRevRangeWithScores(ctx, "rank:"+board, 0, n-1).Result()
}

// 我的名次（ZREVRANK 从 0 开始，对外 +1）
func MyRank(ctx context.Context, rdb *redis.Client, board string, uid int64) (int64, error) {
	r, err := rdb.ZRevRank(ctx, "rank:"+board, strconv.FormatInt(uid, 10)).Result()
	if err == redis.Nil {
		return 0, nil // 不在榜上
	}
	return r + 1, err
}
```

### 第二段：游标分页（翻页中途有写入也不会重复）

```go
// 游标分页：以上一页最后一个成员的分数为锚点，取「严格小于该分数」的下一页。
// ⚠️ 用 offset（ZREVRANGE 2 3）在榜单变化时会重复/漏（实测见第二节）。
// ⚠️ 锚点必须是「(分数」开区间：用闭区间会把上一页最后一个成员再取一次。
func PageByCursor(ctx context.Context, rdb *redis.Client, board string, lastScore float64, n int64) ([]redis.Z, error) {
	return rdb.ZRevRangeByScoreWithScores(ctx, "rank:"+board, &redis.ZRangeBy{
		Max:    "(" + strconv.FormatFloat(lastScore, 'f', -1, 64), // 「(」= 不含锚点本身
		Min:    "-inf",
		Offset: 0,
		Count:  n,
	}).Result()
}
```

### 第三段：定时快照（让「第 X 名」可复现，⚠️ 示意）

```go
// 每分钟把实时榜固化成一个不可变 key，供「第 X 页」这类页码语义读取。
// 好处：① 翻页期间榜单不变，不再重复/漏；② 发奖时能复现当时的排名。
func Snapshot(ctx context.Context, rdb *redis.Client, board string) error {
	now := time.Now().Format("200601021504")
	dst := "rank:" + board + ":snap:" + now
	// ZUNIONSTORE 把实时榜整体复制过去，并给快照设过期（如 1 天）
	if err := rdb.ZUnionStore(ctx, dst, &redis.ZStore{Keys: []string{"rank:" + board}}).Err(); err != nil {
		return err
	}
	return rdb.Expire(ctx, dst, 24*time.Hour).Err()
}
```

## 延伸追问

- **ZSET 和「有序集合」有什么本质区别？** → 没有，ZSET 就是 Redis 对有序集合的实现，区别只在于它把「哈希表 + 跳表」两套结构绑在一起，所以「按成员查分」和「按分数排名」都是 O(log N)。
- **榜单要「带用户信息」怎么办？** → ZSET 只存 member（uid 或 uid 字符串）。用户昵称、头像要另存（Hash 或 DB），读榜时批量取 —— 别把 JSON 塞进 member，那会让 `ZREVRANK` 与按分数定位都变味。
- **同分怎么保证名次稳定？** → ZSET 按 `(score, member)` 排序。要让同分有确定顺序，把排序因子编进 member（如 `score:timestamp:uid` 形式的复合串），或在应用层二次排序。
- **`ZRANGEBYLEX` 和 `ZREVRANGEBYSCORE` 什么时候用哪个？** → 分数有意义（时间、热度）用 `ZREVRANGEBYSCORE`；分数全部相同时（如按字典序排的 ID 集合）用 `ZRANGEBYLEX`。
- **榜单很大（千万级）怎么办？** → 只留 top N：改分时 `ZADD`，同时用一个「第 N+1 名的分数」当水位线，把掉出榜尾的成员 `ZREM` 掉；全量榜下沉到离线算。
