# 关注粉丝设计

> 场景题：社交关系链 —— 关系怎么存、分片键怎么选、推拉怎么结合、大 V 为什么必须特殊处理，四步都附本机实测。
>
> 内容整理自大厂 Go 后端面试真题；参考资料与原始素材见 [素材清单](../../../素材清单.md)。
> **落地实现**：本机 Docker（MySQL 8.0.46 / Redis 7.4.11）+ Go 实测，正文 `text` 块都是本机真实运行结果；**图数据库一行的多跳对照**另用本仓 Neo4j 5.26 实测（10 万点 / 30 万边，见 [选型与落地案例.md](../../../03-数据与中间件/数据存储/图数据库/Neo4j/选型与落地案例.md)）。

## 一、关系存哪：邻接表、SET，还是图数据库？

**本节要点**：关注关系是**有向的**，「我关注了谁」和「谁关注了我」是两种完全不同的查询。所以第一条判据不是「用什么存储」，而是「**这两个方向都要不要快**」——要，就得为两个方向各准备一份索引（或一份数据）。

### 1.1 实测：5 万用户 / 15.2 万条边，查 uid=0 的两个方向

```text
方式                          查「我关注了谁」                                        查「谁关注了我」
MySQL 邻接表·双索引            type=ref key=PRIMARY rows=3 0.60ms (3 行)              type=ref key=idx_followee rows=2003 1.79ms (2003 行)
MySQL 邻接表·缺反向索引        type=ref key=PRIMARY rows=3 0.60ms (3 行)              type=index key=PRIMARY rows=152000 39.21ms (2003 行)
Redis SET·双向                0.31ms（3 个成员）                                      1.44ms（2003 个成员）
```

### 1.2 读法：一行之差，22 倍

- **双索引**：`PRIMARY KEY (follower_id, followee_id)` 服务「我关注了谁」，`KEY idx_followee (followee_id)` 服务「谁关注了我」。查粉丝时 `type=ref key=idx_followee rows=2003` —— 估算行数就是结果行数，**直接命中**。
- **缺反向索引**：同一个查询变成 `type=index key=PRIMARY rows=152000` —— 沿主键索引**整条扫过去**，只为了挑出 2003 行。实测 39.21ms 对 1.79ms，**约 22 倍**。
  ⚠️ 注意它的 `rows` 是 **152000** 而结果只有 **2003** —— 这就是「扫了 15 万行挑出 2000 行」的直接证据，也是为什么要看 `EXPLAIN` 的 `rows` 而不是只看耗时。
- **Redis SET**：两个方向各存一份（`following:{uid}` / `followers:{uid}`），定位 O(1) + 取值 O(成员数)。0.31ms 对 1.44ms，**代价是内存与双写一致性**。

### 1.3 选型判据

| 方案 | 适合 | 代价 |
|---|---|---|
| **MySQL 邻接表**（双索引） | 关系要持久、要按属性查（关注时间、分组）、要事务 | 冷关系也占磁盘；两个方向各要一份索引 |
| **Redis SET**（见 [数据类型.md](../../../03-数据与中间件/数据存储/NoSQL/Redis/数据类型.md)） | 只做「谁关注谁」的集合运算（`SINTER` 算共同关注、二度人脉）、要求低延迟 | 内存成本高；要自己保证与 DB 一致 |
| **图数据库**（Neo4j） | 三跳以上的遍历是**主查询**（三度人脉、最短路径） | 引入新组件；本仓用 10 万点 / 30 万边实测：**1~3 跳并不比 MySQL 快**，6 跳才拉开（约 230 µs vs 16.9 ms）—— 见 [选型与落地案例.md](../../../03-数据与中间件/数据存储/图数据库/Neo4j/选型与落地案例.md) |

⭐ 一句话：**单跳关系用邻接表就够了**；Redis SET 的收益在「**集合运算**」而非单跳查询；图数据库只在**多跳成为主查询**时才划算 —— 且要到**三跳以上**才拉开差距。

### 1.4 判据汇总

| 问题 | 判据 |
|---|---|
| 两个方向都要快吗？ | 都要 → 双索引（或双写）；只有一个方向被查 → 单索引就够，别白加写代价 |
| 用不用 Redis SET？ | 问「是不是要做集合运算」（共同关注/推荐）→ 是才值得引入；只查单跳，DB 足够 |
| ⚠️ 怎么验证索引真的用上了？ | 看 `EXPLAIN` 的 `type` 与 `rows`：`ref` + `rows≈结果行数` 才对；`index`/`ALL` + `rows` 远大于结果行数就是漏索引 |
| 什么时候该升级到图数据库？ | 问「**三跳以上的遍历是不是主查询**」→ 是才值得引入；单跳 / 两跳（共同关注、二度人脉）用邻接表 + `SINTER` 足够（实测判据见 [选型与落地案例.md](../../../03-数据与中间件/数据存储/图数据库/Neo4j/选型与落地案例.md)） |

## 二、分片：为什么「分片键」决定了一类查询必须广播？

**本节要点**：关系数据一大就要分片，而**一个分片键只能优化一个方向**。这是本节最值钱的一句 —— 分片键选错，另一个方向的查询就得打穿所有分片。

### 2.1 实测：按 `follower_id` 分成 4 片

```text
查「uid=0 关注了谁」 : 命中 1 片（follow_0）        0.53ms（3 行）
查「谁关注了 uid=0」 : 必须查全部 4 片               6.16ms（2003 行）  ← 约单片的 12 倍
```

### 2.2 读法

- 按 `follower_id` 分片后，「uid=0 的关注边」全都落在 `follow_0`（因为 `0 % 4 == 0`）→ 查关注列表**只碰一个分片**。
- 但「关注 uid=0 的人」是 2003 个不同的用户，他们的关注边按**各自的 `follower_id`** 散在 4 个分片里 → 查粉丝列表**必须广播到所有分片**再合并。
- 12 倍 = 4 次查询/网络往返（每次约 0.5ms 往返）叠加 4 次索引扫描。**分片数越多，广播越贵**。

### 2.3 两条出路

| 出路 | 做法 | 代价 |
|---|---|---|
| **双写两份**（正排 + 倒排） | 一份按 `follower_id` 分片（服务「关注列表」），一份按 `followee_id` 分片（服务「粉丝列表」） | 写放大 2 倍；两份数据要保证一致 |
| **接受广播 + 合并** | 查粉丝时并发打所有分片，应用层归并 | 分片数受限（分片越多越慢）；尾延迟由最慢分片决定 |

⭐ 大型社交系统几乎都走第一条：**存两份、按两个维度各分一次片** —— 用写放大换两个方向都不广播。这也解释了「为什么关注/取关是重操作」。

### 2.4 判据

| 问题 | 判据 |
|---|---|
| 分片键怎么选？ | 问「哪类查询的 QPS 高」→ 让高频方向单分片，低频方向接受广播 |
| 要不要存两份？ | 两个方向都高频 → 存两份（写放大 2 倍换读不广播）；否则别浪费 |
| ⚠️ 分片数与广播代价？ | 广播代价 ∝ 分片数 → 分片数不能无限加，要配合「双写」方案一起规划 |

## 三、推还是拉：写放大 vs 读放大

**本节要点**：这条不是存储问题，而是**把成本放在哪**的问题。发一条内容后，是**立刻写给所有粉丝**（推/写扩散），还是**等粉丝来读时再聚合**（拉/读扩散）？两者的代价结构正好相反。

### 3.1 实测：一次发帖

```text
推模式（写扩散）：发 1 条 → 写 10000 个粉丝收件箱，耗时 117ms（10000 次 LPUSH，批量）
                    读自己的收件箱 1 次，耗时 314µs
拉模式（读扩散）：发 1 条 → 只写自己的发件箱 1 次，耗时 303µs
                    读时聚合 3 个关注对象，耗时 894µs
```

### 3.2 读法

- **推**：发帖成本 ∝ **粉丝数**（这里 1 万粉 = 117ms）；读自己的收件箱是 O(1)（314µs）。
- **拉**：发帖成本 O(1)（303µs）；读要聚合 **关注数** 个发件箱（3 个关注 = 894µs，且要归并排序 + 去重）。
- 两者的**总代价**取决于四个量：粉丝数、关注数、发帖频次、读频次。**没有普适答案**，只有「这个业务里哪个量更大」。

| 业务特征 | 更适合 |
|---|---|
| 粉丝数 >> 关注数（微博/明星）、读远多于写 | **推** —— 一次写、多次读，把成本摊在写上 |
| 关注数大、粉丝少（信息聚合/订阅）、写远多于读 | **拉** —— 写克制，读时才聚合 |
| 僵尸粉多、活跃粉丝少 | **推拉结合**：只推给在线/活跃粉丝，其余拉 |

⭐ 与 [朋友圈设计.md](../朋友圈设计.md) 的分工：那边讲的是 feed 的整体分层与「为什么朋友圈可以推」（好友数有上限、读多写少），本篇讲的是**关系链本身的存储与分片**以及推拉在「关注型」关系下的代价结构。

### 3.3 判据

| 问题 | 判据 |
|---|---|
| 推还是拉？ | 比 `粉丝数 × 发帖频次` 与 `关注数 × 读频次` 哪个大；大的一侧用另一侧承担 |
| 推模式的收件箱存哪？ | 短期（只留最近 N 条）放 Redis List/ZSET，长期下沉 DB；否则收件箱会无限膨胀 |
| ⚠️ 推模式的一致性？ | 粉丝列表可能变化（新关注/取关），推是基于「**发帖那一刻的粉丝列表**」→ 取关后残留、新关注后漏推，都要靠读时过滤/补齐 |

## 四、大 V 问题：为什么必须混合

**本节要点**：纯推模式的写放大 = 粉丝数。当粉丝数是百万级，一次发帖就是百万次写 —— 这不是「慢一点」，而是**不可行**。所以大 V 必须单独走一条路。

### 4.1 实测：粉丝数 vs 发帖写次数

```text
粉丝数            纯推·发帖写次数          混合·发帖写次数
100            100                  100
10000          10000                10000
100000         100000               1  ← 超阈值（10 万）转拉
5000000        5000000              1  ← 超阈值（10 万）转拉
```

### 4.2 读法

- **纯推**：一个 500 万粉的大 V 发一条，要写 **500 万次**（本机 1 万次 117ms，线性外推到 500 万次是**分钟级**，且这还只是一条内容）。发帖高峰直接打满。
- **混合**：粉丝数超阈值（示例取 10 万）就**不推**，只写自己一份；粉丝来读时，从关注列表里挑出「大 V」，**现场拉**他们的最新内容。于是大 V 发帖的扩散成本是 **1 次**。
- ⭐ 关键直觉：**推的目的是「让读变便宜」，但如果一条内容注定被极多人读，那为每个人都提前写一份反而浪费** —— 大 V 的内容就是这种「人人都要读」的，现场拉一份共享的即可。

### 4.3 ⚠️ 混合的代价

1. **读路径要合并两份数据**：粉丝自己的收件箱（推来的）+ 从大 V 现场拉的 → 要归并排序、去重（大 V 也可能被推过）、分页。读逻辑明显变复杂。
2. **阈值要靠数据定**，不能拍脑袋：按「粉丝数 × 平均发帖频次」估算写放大，超出一个可接受的写 QPS 阈值就转拉。本机 1 万次批量 LPUSH = 117ms，可据此反推阈值。
3. **大 V 名单本身要维护**：粉丝数会涨落，谁算大 V 是动态的 —— 通常由一个离线任务定期刷。

### 4.4 判据

| 问题 | 判据 |
|---|---|
| 谁算大 V？ | 按「发帖时的写放大」定：`粉丝数 × 发帖频次` 超过可接受写 QPS 的就是 |
| 大 V 判定要实时吗？ | 不要。离线定期算（如每天），在线按名单走 —— 实时判定会让发帖路径依赖一个易变的量 |
| ⚠️ 读合并怎么保证不重不漏？ | 用「内容 ID + 时间戳」做归并键，去重按内容 ID；分页必须走**游标**（见 [排行榜设计.md](排行榜设计.md) 第二节），否则合并出的顺序会漂 |

## 使用：关注链路的 Go 骨架

> ⚠️ 下面三段是骨架片段（省略了 import、类型定义与错误包装）。**双向写入**与**分片路由**的写法取自本机实测程序（读数见第一、二节）；**推拉合并读**是按语义补全的示意（未单独实测）。

### 第一段：关注 / 取关（两个方向一起写）

```go
// 关注是「两个方向各写一份」：正排（我关注了谁）+ 倒排（谁关注了我）。
// ⚠️ 实测：只建一个方向的索引，另一个方向会退化成全索引扫描（39.21ms vs 1.79ms，22 倍）。
func Follow(ctx context.Context, db *sql.DB, me, target int64) error {
	tx, err := db.BeginTx(ctx, nil)
	if err != nil {
		return err
	}
	defer tx.Rollback()
	// 正排 + 倒排：两条记录在同一事务里写，避免只写一半
	if _, err := tx.ExecContext(ctx,
		"INSERT IGNORE INTO follow(follower_id, followee_id) VALUES(?,?)", me, target); err != nil {
		return err
	}
	if _, err := tx.ExecContext(ctx,
		"INSERT IGNORE INTO follow_reverse(followee_id, follower_id) VALUES(?,?)", target, me); err != nil {
		return err
	}
	return tx.Commit()
}
```

### 第二段：分片路由（同一个索引键决定单分片还是广播）

```go
// 按 follower_id 分片：查「我的关注列表」只碰一片。
func MyFollowing(ctx context.Context, db *sql.DB, me int64) ([]int64, error) {
	shard := me % shards // 单分片：follow_{shard}
	return queryIDs(ctx, db, fmt.Sprintf("SELECT followee_id FROM follow_%d WHERE follower_id=?", shard), me)
}

// 查「我的粉丝」必须打全部 N 片：粉丝的 follower_id 散在各分片。
// ⚠️ 实测：4 片时约 6.16ms，是单片的 12 倍 —— 分片数越多广播越贵。
func MyFollowers(ctx context.Context, db *sql.DB, me int64) ([]int64, error) {
	out := make([]int64, 0, 64)
	for i := 0; i < shards; i++ {
		ids, err := queryIDs(ctx, db,
			fmt.Sprintf("SELECT follower_id FROM follow_%d WHERE followee_id=?", i), me)
		if err != nil {
			return nil, err
		}
		out = append(out, ids...)
	}
	return out, nil
}
```

### 第三段：推拉合并读（⚠️ 示意，未单独实测）

```go
// 粉丝打开「关注流」时：自己的收件箱（推来的）+ 大 V 现场拉的，合并去重。
func Timeline(ctx context.Context, db *sql.DB, rdb *redis.Client, me int64, cursor int64, n int) ([]Item, error) {
	// ① 推来的：直接读自己的收件箱（O(1)）
	inbox, err := rdb.ZRevRangeByScoreWithScores(ctx, "inbox:"+strconv.FormatInt(me, 10), &redis.ZRangeBy{
		Max: "(" + strconv.FormatInt(cursor, 10), Min: "-inf", Offset: 0, Count: int64(n),
	}).Result()
	if err != nil {
		return nil, err
	}
	// ② 大 V 现场拉的：只查 vip 名单里的人（阈值见第四节）
	vips, err := queryIDs(ctx, db, "SELECT followee_id FROM follow_vip WHERE follower_id=?", me)
	if err != nil {
		return nil, err
	}
	pulled := make([]redis.Z, 0, n)
	for _, v := range vips {
		zs, _ := rdb.ZRevRangeByScoreWithScores(ctx, "outbox:"+strconv.FormatInt(v, 10), &redis.ZRangeBy{
			Max: "(" + strconv.FormatInt(cursor, 10), Min: "-inf", Offset: 0, Count: int64(n),
		}).Result()
		pulled = append(pulled, zs...)
	}
	// ③ 归并 + 按内容 ID 去重（大 V 可能既被推过、又被拉过）
	return mergeDedup(inbox, pulled, n), nil
}
```

## 延伸追问

- **双向好友（互关）怎么存？** → 存两行（A→B、B→A），不要试图用一行加状态位表示「互为好友」—— 那样两个方向的查询都要拆条件，索引也用不上。
- **「共同关注」怎么算？** → 关系存 DB 时用 `INNER JOIN` 两个正排表；存 Redis SET 时直接 `SINTER`。这正是 Redis SET 真正划算的地方（集合运算），见第一节判据。
- **关注数有上限（如 5000）对设计有什么影响？** → 上限让「关注列表」可控，于是**拉模式的读聚合代价有界** —— 这就是微博把关注数卡在 2000、微信好友卡在 5000 的原因之一：给下游留出确定性的最坏情况。
- **取关后收件箱里的旧内容怎么办？** → 推模式是按「发帖那一刻的粉丝列表」写的，取关者收件箱里会有残留 → 读时按当前关注关系过滤（用 `ZSET` 或布隆过滤器判断），或干脆接受残留（成本更低）。
- **关系的「计数」（粉丝数）和第一节的点赞计数是同一个问题吗？** → 是同一类问题（详见 [评论点赞设计.md](评论点赞设计.md)）：粉丝数也要用计数器而非 `COUNT(*)`；且粉丝数变化频繁，判重与计数要一起原子更新。
- **什么时候该把关系网搬进图数据库？** → 只有一条准入门槛：**三跳以上的遍历是不是主查询**（三度人脉、资金链路、攻击路径）。本仓实测 10 万点 / 30 万边上，**1~3 跳 Neo4j 与 MySQL 递归 CTE 都在亚毫秒**、图库并无优势，**6 跳才拉开量级**（约 230 µs vs 16.9 ms，且 MySQL 每加一跳就明显变慢）。所以「偶尔有一条多跳查询」不足以支撑引入图库；关系只是属性时，邻接表 + 索引（+ 缓存 + 分片）就够。完整判据见 [选型与落地案例.md](../../../03-数据与中间件/数据存储/图数据库/Neo4j/选型与落地案例.md)。
