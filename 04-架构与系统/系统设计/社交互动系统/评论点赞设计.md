# 评论点赞设计

> 场景题：社交互动里的评论与点赞 —— 计数 / 去重 / 缓存 / 异步写 / 热 key 五个硬问题，每个都附本机实测。
>
> 内容整理自大厂 Go 后端面试真题；参考资料与原始素材见 [素材清单](../../../素材清单.md)。
> **落地实现**：本机 Docker（Redis 7.4.11 / MySQL 8.0.46）+ Go 实测，正文 `text` 块都是本机真实运行结果。

## 一、点赞数存在哪：为什么不能在 DB 上 `COUNT(*)`？

**本节要点**：点赞数是典型的「**一个数字被无数人读、被无数人改**」。如果每次都去 DB 数一遍，读放大就是 O(参与人数) —— 参与人数越长越大，这条路就越走不通。把答案**压成一个计数器**，才是这类问题的正解。

### 1.1 直接 `COUNT(*)` 的代价

最直觉的写法是：点一次赞插一行 `post_like`，读的时候 `SELECT COUNT(*) FROM post_like WHERE post_id = ?`。

在有 `(post_id, uid)` 索引时它并不算「全表扫」，走的是索引区间扫描（`type=ref`、`Using index`），看起来还挺优雅。但它的复杂度是 **O(该帖点赞数)** —— 帖子越热，读一次越贵。

### 1.2 实测：`COUNT(*)` 随点赞数线性变慢，`GET` 恒定

同一条帖子，点赞数从 100 涨到 100 万，分别测「DB 数一遍」与「Redis 读一个计数器」：

```text
点赞数      DB COUNT(*)      Redis GET
100        440µs            126µs
1000       678µs            258µs
10000      2.926ms          302µs
100000     35.227ms         251µs
1000000    294.806ms        302µs
```

⭐ 读法：`COUNT(*)` 从 440µs 涨到 **294.806ms**（约 670 倍，且与点赞数同阶）；`GET` 始终在 **126~302µs** 之间抖动，**没有趋势**。

⚠️ 这正是「缓存」在计数场景的正确用法 —— 不是「缓存一个查询结果」，而是**把计数本身做成一个可 O(1) 读写的状态**。缓存的是一张 `COUNT(*)` 的结果值，命中率再高也还是要考虑失效后回源到那条 O(k) 的查询；而一个 Redis 计数器根本不存在回源。

### 1.3 两种「计数器」不是一回事

| 方案 | 真源在哪 | 读性能 | 一致性 | 适合 |
|---|---|---|---|---|
| **DB 计数 + 缓存数字** | DB | 命中缓存 O(1)，未命中 O(k) | 缓存可能陈旧，靠失效策略收敛 | 读多写少、不能容忍短时不准 |
| **Redis 计数 + 异步落库** | Redis | 恒 O(1) | 最终一致（Redis 与 DB 有一段窗口） | 高频写、可接受短时不准 |

⭐ 判据只有一条：**这个数字短时间不准，业务会不会塌？** 点赞数差几个不会有人投诉 → 选后者；账户余额差一分就是事故 → 只能选前者。

### 1.4 判据汇总

| 问题 | 判据 |
|---|---|
| 计数放哪？ | 数字短时不准能否接受？能 → Redis 计数器；不能 → DB 为准 + 缓存加速 |
| 要不要缓存 `COUNT(*)` 结果？ | 要，但它是「加速回源」，不解决回源本身 O(k) 的问题 → 计数器才是根治 |
| ⭐ 计数器的底线 | 计数器一旦与明细脱钩，**必须能对账**：定时用明细重算一次，与计数器比对，对不上先告警不自动改 |

## 二、怎么保证「一人一赞」：为什么必须原子判重？

**本节要点**：点赞的第二个坑是**去重**。少了它，计数就失去意义 —— 同一个人的 1000 次点击会被记成 1000 个赞。而判重必须是**原子的**：任何「先查有没有、再决定写不写」的两步写法，在并发下都会漏。

### 2.1 实测：同一用户重复点赞 1000 次，三种写法

```text
无去重（INCR 直接累加）      : 计数 = 1000   ← 凭空放大 1000 倍
Redis SADD 判重              : 计数 = 1      ← SADD 返回 0/1 是原子判重
DB 唯一索引 INSERT IGNORE    : 行数 = 1      ← 落库侧的最终防线
```

### 2.2 读法：错在哪、对在哪

- **无去重**：`INCR` 只是把「点击次数」当成「点赞人数」。写得再快也是错的。
- **`SADD` 判重**：`SADD key uid` 返回 `1`（新增）或 `0`（已存在），**判重与写入在同一次服务端执行里完成**，不存在竞态窗口。所以「`SADD` 返回 1 时才 `INCR`」是原子的。
- **唯一索引**：`UNIQUE KEY (post_id, uid)` + `INSERT IGNORE` 让落库侧也不重复。它防的是**另一层**问题 —— Redis 判重名单失效（key 过期、实例重启、缓存穿透）后同一请求重复落库。

### 2.3 ⚠️ 两个必须一起说的坑

1. **`SET` 的 TTL 别乱设** —— 给判重名单设了短 TTL，TTL 一到名单就没了，同一用户又能再赞一次。要么不设 TTL（占内存，靠定期清理/迁移到 DB），要么把 TTL 设得长于「业务允许的重复窗口」。
2. **判重键里必须有 `uid`** —— 只按 `post_id` 判重会让「第二个人点不了」；键要写成 `like:set:{post_id}`，成员是 `uid`。

### 2.4 判据

| 问题 | 判据 |
|---|---|
| 能不能撤销点赞？ | 能（要 `SREM`）→ 判重名单必须是集合，且集合与计数器要一起改；不能（只增不减）→ 用 `SET`/`SADD` 均可 |
| 判重放哪？ | Redis 挡在写入前（快、原子）；DB 唯一索引兜底（最终真相） |
| ⚠️ 判重名单会丢吗？ | 会（TTL / 重启 / 内存淘汰）→ 必须有唯一索引兜底，否则「一个人点几次算几次」 |

## 三、点赞写在哪：同步写 DB 还是先落 Redis？

**本节要点**：点赞是**高频低价值**的写 —— 每条都要及时落库吗？不必。但「异步」不等于「随便攒攒」，它的收益来自**把 N 次事务提交合并成 1 次**，代价是**攒批窗口内的数据必然有丢失窗口**。

### 3.1 实测：2000 次点赞落库

```text
同步逐条 INSERT（2000 次提交，每次一次 fsync） : 13.709s
攒批一次 INSERT（1 次提交）                  : 136ms
→ 相差约 101 倍
```

### 3.2 读法：100 倍差在哪

不是 SQL 慢，是**提交次数**。MySQL 默认 `innodb_flush_log_at_trx_commit=1`，每次 `COMMIT` 都要等 redo 日志真正落盘（fsync）。逐条写 = 2000 次 fsync；攒批 = 1 次。

⭐ 所以「异步写」的收益本质是**摊薄 fsync**，和「写 Redis 快」关系不大。哪怕不用 Redis，只要能把 2000 条攒成一批，收益同样存在。

### 3.3 代价与兜底

| 收益 | 代价 |
|---|---|
| 提交次数 2000 → 1 | 攒批窗口（如 100ms）内进程崩溃 → 整批丢失 |
| 请求侧不被落库阻塞 | Redis 与 DB 之间出现不一致窗口 |

兜底三件：① Redis 开持久化（见 [排行榜设计.md](排行榜设计.md) 第四节）；② 攒批上限设死（时间或条数，先到先刷）；③ 定时对账，用明细重算计数。

### 3.4 判据

| 问题 | 判据 |
|---|---|
| 要不要异步？ | 这条数据丢了业务会不会塌？点赞可接受（重新点一次）→ 可以异步；涉及钱 → 不能只靠内存攒批 |
| 攒批窗口怎么定？ | 时间（如 100ms）× 条数（如 1000）双上限，先到先刷 —— 只设一个会出问题（低峰期攒不满、高峰期窗口内堆积） |
| ⚠️ 请求侧要不要等落库？ | 不要。先写 Redis 判重+计数，立即返回；落库交给后台。等落库就把 DB 的延迟搬到了用户脸上 |

## 四、热 key：为什么「拆 key」在单实例上一点用都没有？

**本节要点**：热点内容的点赞 key 会被所有请求打同一个 key —— 在 Redis Cluster 里这意味着**打同一个 slot、同一个节点**。直觉答案是把 key 拆成 N 份，但**拆 key 本身不产生任何收益**：Redis 是单线程，所有命令本来就串行执行，单 key 查找也是 O(1)。收益只来自「**拆到不同节点**」。

### 4.1 实测：10 万次 `INCR`，三种分法（管道批量 50，预热后连跑 5 次取区间）

```text
单实例 · 单 key              : 173ms ~ 496ms   ≈ 201713 ~ 577079 次/秒
单实例 · 分 8 个子 key         : 174ms ~ 285ms   ≈ 350380 ~ 576140 次/秒
两实例 · 分片到 2 实例           : 142ms ~ 179ms   ≈ 557591 ~ 706558 次/秒
```

交叉核对（用镜像自带的 C 版 `redis-benchmark`，各 20 万次、50 连接、管道 16）：

```text
单实例 · 单 key  : 280505 次/秒
单实例 · 多 key  : 329489 次/秒
两实例并发合计   : 211193 + 185701 = 396894 次/秒
```

### 4.2 读法：三条结论

1. ⭐⭐ **单实例内「拆 key」几乎没有收益** —— Go 侧 `173ms`（单 key）对 `174ms`（8 子 key），**最快值完全一样**；benchmark 侧 28.0 万对 32.9 万，也在同一量级。原因：Redis 单线程，所有命令串行过一遍；单个 key 的查找本身是 O(1)，key 数量不改变单实例的 CPU 上限。
2. ⭐ **收益只在跨实例/跨分片时出现** —— Go 侧 `142ms`（两实例）对 `173ms`（单实例）≈ 1.2 倍；benchmark 侧 39.7 万对 28.0 万 ≈ 1.4 倍。因为那才是「**两个 CPU 核心 / 两个节点**」。
3. ⚠️ **本机远达不到「2 倍」** —— 瓶颈先落在容器网络与客户端上，不是 Redis 的 CPU。这恰恰是「热 key 要不要拆」的正确判据：**先看单节点是否先被打满**（`redis-cli --latency`、节点 CPU、`INFO stats` 的 `instantaneous_ops_per_sec`），打不满就别拆。

### 4.3 拆分的代价

把计数拆成 N 个子 key 后，**读计数要聚合 N 个 key**：

```text
聚合  1 个 key 的计数 : 130µs
聚合  4 个 key 的计数 : 318µs
聚合  8 个 key 的计数 : 205µs
聚合 16 个 key 的计数 : 214µs
```

⭐ 读法：聚合读落在 **205~318µs**，约为单 key（130µs）的 1.6~2.4 倍（用管道取值，所以不是线性叠加）。这还只是**读取代价**，没算：① 某个子 key 写失败 → 计数少算，需要补偿；② 聚合逻辑污染业务代码；③ 子 key 数量一旦写死就与分片数耦合。

### 4.4 判据

| 问题 | 判据 |
|---|---|
| 要不要拆热 key？ | **先看单节点是否被打满**。没打满 → 拆了也没收益（本机实测：单实例拆 8 份，最快值与不拆完全相同） |
| 怎么拆才有收益？ | 拆到**不同实例/分片**上（本机 1.2~1.4 倍）；且分片数要与子 key 数对齐，否则某个分片仍会热 |
| 有没有更省事的做法？ | ① 本地缓存 + 合并写入（把同一 key 的 N 次 `INCR` 在应用侧合并成 1 次）；② 读写分离 + 从节点分担读；③ 热点内容下沉到本地（[商品详情页设计.md](../秒杀系统/商品详情页设计.md) 的多级缓存） |
| ⚠️ 拆完就没事了？ | 不是。**热 key 是一种现象，不是一个固定名单** —— 需要监控（`--hotkeys` 或采样）持续发现新的热点，而不是一次性拆完 |

## 使用：点赞链路的 Go 骨架

> ⚠️ 下面三段是骨架片段（省略了 import、类型定义与错误包装）。**判重与计数的 Lua 逻辑**、**攒批落库**的写法取自本机实测程序（读数见第二、三节）；**热 key 分片写**是按语义补全的示意（未单独实测）。

### 第一段：Lua 原子判重 + 计数（判重与计数压进一次服务端执行）

```lua
-- KEYS[1] = like:set:{post_id}   ARGV[1] = uid
-- 返回 1 = 首次点赞（计数已 +1）；0 = 已经赞过
if redis.call('SADD', KEYS[1], ARGV[1]) == 1 then
  redis.call('INCR', 'like:count:' .. KEYS[2])
  return 1
end
return 0
```

```go
// 关键：用同一段脚本完成「判重 + 计数」，中间没有任何网络往返。
// 拆成 SADD 再 INCR 两条命令，看似也行 —— 但两条命令之间进程可能崩溃，
// 导致「名单加了、计数没加」，之后这个人再也点不上（永久少一个赞）。
func Like(ctx context.Context, rdb *redis.Client, postID, uid int64) (bool, error) {
	n, err := redis.NewScript(likeScript).Run(ctx, rdb,
		[]string{"like:set:" + strconv.FormatInt(postID, 10),
			strconv.FormatInt(postID, 10)},
		uid).Int()
	if err != nil {
		return false, err
	}
	return n == 1, nil
}
```

### 第二段：攒批落库（把 N 次提交摊成 1 次）

```go
// 后台每 100ms 或攒够 1000 条就刷一次库；两个上限先到先刷。
func (w *LikeWriter) loop(ctx context.Context) {
	tick := time.NewTicker(100 * time.Millisecond)
	defer tick.Stop()
	buf := make([]likeRow, 0, 1000)
	flush := func() {
		if len(buf) == 0 {
			return
		}
		// 一次 INSERT 多条：提交次数从 len(buf) 降到 1（实测 2000 条：13.7s → 136ms）
		w.bulkInsert(ctx, buf)
		buf = buf[:0]
	}
	for {
		select {
		case <-ctx.Done():
			flush() // 退出前必须先刷，否则丢最后一批
			return
		case <-tick.C:
			flush()
		case r := <-w.ch:
			buf = append(buf, r)
			if len(buf) >= 1000 {
				flush()
			}
		}
	}
}
```

### 第三段：热 key 分片写（⚠️ 示意，未单独实测）

```go
// 把一个热计数拆到 N 个子 key；读时求和。
// ⚠️ 本机实测：在【单实例】上拆 8 份与不拆，最快值完全相同（173ms vs 174ms）——
//    拆 key 本身零收益，收益只来自【拆到不同节点】。
//    所以要拆，必须让子 key 落在不同实例/分片上，并且监控是否还有单点热点。
const shards = 8

func shardKey(postID int64, uid int64) string {
	return fmt.Sprintf("like:count:%d:%d", postID, uid%shards)
}

// 读计数：聚合 N 个子 key（实测：1 个 key 130µs → 8 个 205µs）
func LikeCount(ctx context.Context, rdb *redis.Client, postID int64) (int64, error) {
	keys := make([]string, shards)
	for i := range keys {
		keys[i] = fmt.Sprintf("like:count:%d:%d", postID, i)
	}
	vals, err := rdb.MGet(ctx, keys...).Result()
	if err != nil {
		return 0, err
	}
	var sum int64
	for _, v := range vals {
		if n, ok := v.(string); ok {
			x, _ := strconv.ParseInt(n, 10, 64)
			sum += x
		}
	}
	return sum, nil
}
```

## 延伸追问

- **点赞数用 Redis `INCR`，重启会不会丢？** → 会，取决于持久化配置。RDB 可能丢整个快照窗口、AOF everysec 最多丢约 1 秒 —— 实测对比见 [排行榜设计.md](排行榜设计.md) 第四节。所以计数器要么能接受丢失后重算，要么必须开 AOF。
- **能不能只用 DB 唯一索引判重，不要 Redis 名单？** → 能，但那就是「每次都打 DB」，写峰值扛不住。Redis 名单的作用是把绝大多数重复请求挡在 DB 之前，唯一索引只兜底。
- **`SADD` 名单和计数器不在同一个 key 上，Lua 只保证脚本内的原子性 —— 够吗？** → 够，因为 Lua 脚本整体串行执行，脚本内的两条命令中间不会被插入其他命令；但**跨 key 的失败仍然可能**（如脚本执行到一半实例被 kill），所以要配合明细对账。
- **点赞的「取消」怎么处理？** → `SREM` + `DECR`，同样要压进同一个 Lua 脚本；并且要判「取消一个本来就没赞过的」，`SREM` 返回 0 时不能 `DECR`。
- **评论系统本身比点赞复杂在哪？** → 评论是**有层级、有顺序、可删除、要过滤**的内容数据：树形结构（盖楼/嵌套）、分页要稳定、删除要软删、还要过内容安全。它更接近「内容存储 + 关系」，与点赞的「计数 + 判重」是两类问题；本条只做区分，不展开。
