## 一、Feed 到底在解什么问题？

**本节要点**：Feed 不是"把内容按时间排一排"这么简单。它的全部工程难点可以收敛成**三个互相牵制的问题**：内容怎么送到用户面前（拉取模型）、这份结果存在哪、怎么一页页取出来（存储与分页）、以及取出来的顺序对不对、会不会重复（排序与去重）。这三件事里任何一件单独看都不难，难在**它们耦合在一起** —— 改分页方式会反过来约束排序键，改拉取模型会改变存储的形态。

### 1.1 三个核心问题

| # | 问题 | 一句话 | 主要落在哪一篇 |
|---|---|---|---|
| 1 | **拉取模型** | 发布时就把内容写进每个粉丝的时间线（推 / 写扩散），还是等用户来读时才去聚合关注对象（拉 / 读扩散）？ | [写扩散与读扩散.md](写扩散与读扩散.md) |
| 2 | **时间线存储与分页** | 这份"某人的 Feed 长什么样"存在哪、用什么结构、怎么从任意位置继续往下翻？ | [时间线存储与分页.md](时间线存储与分页.md) |
| 3 | **排序与去重** | 按什么排？多个来源合并时按什么去重？翻页过程中有新内容进来，顺序会不会乱？ | [排序与去重.md](排序与去重.md) |

⭐ 判断顺序很重要：**先定拉取模型，再定存储，最后定排序**。因为拉取模型决定了"送到读侧的是已经排好的一份，还是需要现场合并的几份"，存储和排序都要跟着它走。反过来先纠排序键，很可能写着写着发现这一步本该在写入时就算完。

### 1.2 为什么三个问题会互相牵制

- **拉取模型 → 存储形态**：写扩散下，每个用户有一条**自己专属**的时间线，写入方要定位到这条线；读扩散下，没有"专属时间线"，只有每个发布者的**发件箱**，读侧要现场合并多个发件箱。
- **存储结构 → 分页方式**：如果时间线按分数（时间戳或热度）存在有序集合里，翻页天然可以按分数做游标；如果存成普通列表靠下标翻，就会撞上 [时间线存储与分页.md](时间线存储与分页.md) 第二节说的**漂移与重复**。
- **排序键 → 去重口径**：排序键必须**全局唯一且稳定**，否则同一个内容在两路合并里会被当成两条；去重靠的也是同一个键。

> 一句话概括：**Feed 的三个问题是"一条时间线上、一次读取里"同时出现的**，所以只能放在一起设计，不能拆开各写各的。

## 二、这个目录由哪些零件拼成？

**本节要点**：把上面三个问题再拆一层，就得到六个可独立讨论的**零件**。这张清单是全目录的地图：每一行告诉你"这个问题是什么、判据是什么、落在哪一节"。

### 2.1 零件清单

| # | 零件 | 核心判据 | 落在哪 |
|---|---|---|---|
| 1 | **写扩散（推）** | 发一条的成本 ∝ 粉丝数；读写比决定划不划算 | [写扩散与读扩散.md](写扩散与读扩散.md) 一 |
| 2 | **读扩散（拉）** | 发一条的成本 O(1)；读要现场合并关注对象的发件箱 | [写扩散与读扩散.md](写扩散与读扩散.md) 一 |
| 3 | **混合模式与大 V 阈值** | 粉丝数超过阈值就转拉；阈值按"粉丝数 × 发帖频次"估写放大 | [写扩散与读扩散.md](写扩散与读扩散.md) 二 |
| 4 | **时间线存储与游标分页** | 分数唯一且单调 → 才能用"上一页最后一个分数"当游标 | [时间线存储与分页.md](时间线存储与分页.md) 一、二 |
| 5 | **多路合并去重** | 合并按排序键，去重按内容 ID；两路都可能含同一内容 | [时间线存储与分页.md](时间线存储与分页.md) 三 |
| 6 | **稳定排序键与兜底默认序** | 多信号折进一个可比较的键；无个性化时退回时间倒序 | [排序与去重.md](排序与去重.md) 二、五 |

### 2.2 三个问题与六个零件的对应

```text
问题① 拉取模型      → 零件 1 / 2 / 3（推、拉、混合与大 V）
问题② 存储与分页    → 零件 4（存哪 + 怎么翻）与 零件 5（多路怎么合）
问题③ 排序与去重    → 零件 5 / 6（合并去重、稳定键、兜底序）
```

> 注意 **零件 5「多路合并去重」同时属于问题②和③** —— 它是三个问题的**接缝**。凡是"多路来源"的 Feed（推来的收件箱 + 现场拉的大 V + 广告/推荐插入），合并这一步都躲不掉，所以它同时被两篇引用。

![发布侧按大 V 阈值分流：普通用户写扩散到粉丝收件箱，大 V 只写自己的发件箱](images/Feed推拉混合扇出.svg)

图怎么读：左半边是发布侧，同一条内容按作者类型走两条路——普通用户写扩散（扇出 = 粉丝数 F，写进 F 个 `inbox` 有序集合），大 V 读扩散（扇出 = 1，只写自己的 `outbox`）；右半边是读取侧，把「推来的 inbox」与「现场拉的大 V」两路按 (排序键, 内容 ID) 归并、按内容 ID 去重，取够一页即停。底部那行点出接缝所在：模式切换与重叠关注会让同一内容从两路同时冒出，所以**去重只能放在读取合并这一步**，键用内容 ID。

## 三、按什么顺序读、彼此怎么依赖？

**本节要点**：三篇零件不是并列关系，而是**有依赖的链条**。按下面的顺序读，每一篇都为下一篇提供前提。

### 3.1 阅读顺序

| 顺序 | 篇目 | 读之前需要什么 | 读完能回答什么 |
|---|---|---|---|
| 1 | [写扩散与读扩散.md](写扩散与读扩散.md) | 无（起点） | 内容"怎么到用户面前"，成本落在写侧还是读侧 |
| 2 | [时间线存储与分页.md](时间线存储与分页.md) | 已确定拉取模型 | 推来的那份/拉出的几路"存在哪、怎么翻页" |
| 3 | [排序与去重.md](排序与去重.md) | 已确定存储结构 | "按什么排、怎么去重、翻页中途插新内容怎么办" |

### 3.2 依赖关系

- **写扩散与读扩散 → 时间线存储与分页**：先决定"推的单条时间线"还是"拉的多路发件箱"，才知道要存几个结构、分页要不要做合并。**这一篇是另两篇的前提。**
- **时间线存储与分页 → 排序与去重**：分页用的游标就是排序键的取值；存储用的有序集合分数就是排序键本身。**分页方式反过来约束了排序键必须唯一且单调**（见 [排序与去重.md](排序与去重.md) 第二节）。
- **排序与去重 → 前两篇**（反向约束）：一旦要引入兴趣分，排序键就不再是纯时间戳，游标语义随之变化；这会倒逼 [时间线存储与分页.md](时间线存储与分页.md) 重新考虑"分数还得漂移吗"。

> 一句话：**1 定模型、2 定结构、3 定序**；而 3 又会回头改 1 和 2 的假设 —— 真设计时是一个来回收敛的过程，不是单向流水线。

## 四、与朋友圈设计、社交互动系统怎么划边界？

**本节要点**：仓库里已经有 [朋友圈设计.md](../社交互动系统/朋友圈设计.md)，它讲的是**朋友圈这一具体场景**的要素分析与推拉分层。本目录讲的是**通用 Feed 流**的工程实现。两者有重叠的概念（推 / 拉），但**问题域和抽象层级不同**，必须划清，避免重复造篇。

### 4.1 三个视角的分工

| 视角 | 篇目 | 讲什么 | 不讲什么 |
|---|---|---|---|
| **具体场景** | [朋友圈设计.md](../社交互动系统/朋友圈设计.md) | 朋友圈的要素分析、表设计、数据分层；"朋友圈为什么可以推" | 不展开通用分页、排序键、多路合并的工程细节 |
| **关系链** | [关注粉丝设计.md](../社交互动系统/关注粉丝设计.md) | 关注关系怎么存、怎么分片、推拉在"关注型"关系下的代价 | 不管时间线怎么存、怎么翻页 |
| **通用 Feed** | 本目录三篇 | 拉取模型、时间线存储与分页、排序与去重 —— 与具体业务场景无关 | 不重讲朋友圈的 ER 表，也不重讲关系链分片 |

### 4.2 具体怎么划

- **朋友圈那篇**回答"**某个具体场景**下有哪些要素、分几层"；本目录回答"**任意 Feed** 的时间线，工程上怎么存、怎么翻、怎么排"。前者是**场景推演**，后者是**零件实现**。
- **推 / 拉这个概念两边都出现**，但落点不同：[朋友圈设计.md](../社交互动系统/朋友圈设计.md) 用它说明"朋友圈好友数有上限，所以可以推"；本目录的 [写扩散与读扩散.md](写扩散与读扩散.md) 把它当成一个**可量化的代价结构**，给出"大 V 阈值怎么定""粉丝数变化时怎么切"这类通用判据。
- **关系链存储**在 [关注粉丝设计.md](../社交互动系统/关注粉丝设计.md)（那边讲"存两份、按两个维度分片"），**时间线扇出**在本目录 —— 前者是"边怎么存"，后者是"一条内容怎么扩散成 N 条时间线条目"。

> 引用关系上，本目录与朋友圈那篇**互引**：朋友圈篇讲"为什么朋友圈可以推"，到了需要展开通用分页与排序键时，就指向本目录。

## 五、这套系统的数据存哪？

前三节讲的是「怎么拉、怎么存、怎么排」，这一节补上**存储选型**的视角：把 Feed 里每份数据按住**角色**归位 —— 内容本体才是真相，时间线只是它的指针副本。

| 数据 | 角色 | 存储 | 理由 |
|---|---|---|---|
| 内容本体（正文、作者、标签） | 权威源 | MySQL | 唯一真相，按 ID 点查，要持久 |
| 时间线（inbox / outbox：内容 ID + 排序键） | 副本 | Redis ZSet | 只存指针；可从内容 + 关注关系重建 |
| 检索（按标签 / 关键词找内容） | 检索副本 | Elasticsearch | 从内容本体同步，供搜索用 |
| 互动计数（点赞 / 评论数） | 副本 | Redis 计数（定期落库） | 高频自增，可从互动明细重算 |
| 图片 / 视频 | 归档 / 静态资源 | 对象存储 + CDN | 体积大、走 CDN，库里只存 URL |
| 冷归档（一年以上的内容与日志） | 归档 | 对象存储 + 列存文件 | 极低频，用最便宜的介质 |

⭐ 判据：**「这份数据丢了能不能重建」** —— 内容本体不能重建，是权威源；时间线、检索、计数、归档都能从它派生，可丢。**时间线里只有指针、内容本体才是真相**，两者不该放同一种存储、也不该有同一个生命周期 —— 这一条在 [时间线存储与分页.md](时间线存储与分页.md) 的 1.4 已经展开。

完整的分工视角见 [存储选型与组合.md](../存储选型与组合.md)。

## 使用：从一次发布到一屏刷新的完整链路

把三篇零件串成一条端到端的链路，帮助定位"某一步该看哪一节"。

### 发布侧

1. **内容落库**（持久化，与其他系统一致）。
2. **按拉取模型决定扇出**：普通用户走写扩散，把内容写进每个粉丝的时间线；大 V 走读扩散，只写自己的发件箱 —— 见 [写扩散与读扩散.md](写扩散与读扩散.md) 二。
3. **为每条时间线条目算好排序键**（分数 = 时间戳或综合分），写入有序集合 —— 见 [排序与去重.md](排序与去重.md) 二。

### 读取侧

1. **取游标**：客户端带上"上一页最后一个排序键"，没有就是首页。
2. **读自己的时间线**（推来的那部分），若含大 V 则并发拉取大 V 发件箱 —— 见 [时间线存储与分页.md](时间线存储与分页.md) 一、三。
3. **多路合并 + 去重**：按排序键归并，按内容 ID 去重 —— 见 [排序与去重.md](排序与去重.md) 三。
4. **按稳定排序键截断一页**，返回并回带新的游标 —— 见 [时间线存储与分页.md](时间线存储与分页.md) 二。

```text
发布：落库 → 判推/拉 → 算排序键 → 写有序集合
读取：取游标 → 读时间线(+拉大V) → 归并去重 → 截断一页 → 回带游标
        └─ 存储与分页 ─┘   └──── 排序与去重 ────┘
```

> ⚠️ 本目录三篇均为**设计讲解与骨架**，未做新的本机实测；正文凡涉及读数的均不编造，确需数字的地方只给**判据与量级方向**。

## 延伸追问

- **通用 Feed 和朋友圈，能不能合成一篇？** → 不建议。朋友圈那篇的价值在**具体场景的要素推演**（哪些数据、怎么分层），本目录的价值在**跨场景的工程零件**（存储、分页、排序）。合成一篇会两头不讨好：讲通用零件时被场景细节打断，讲场景时又被泛化判据稀释。
- **为什么把"存储与分页"合成一篇，而不是拆成两篇？** → 因为**存储结构决定了分页方式**：有序集合能按分数游标翻页，普通列表只能按下标翻。两者是同一个决策的两面，拆开会逼着读者来回跳。
- **排序与去重为什么也放一起？** → 因为**排序键就是去重键**。多路合并时"按什么排"和"按什么判重"是同一个字段，分开写会重复描述同一个键。
- **这三篇需要依赖关系链的存储吗？** → 不需要。时间线扇出只关心"**我要写给哪些人**"，不关心"这段关系在库里怎么分片"。所以本目录可以独立于 [关注粉丝设计.md](../社交互动系统/关注粉丝设计.md) 阅读，只在"粉丝数变化时怎么切模式"处引用它。
