## 一、场景题：设计一个直播弹幕系统

**本节要点**：开放设计题。**重点不是完美方案，而是分层思路** ——
条件往往后面才补，边补边迭代即可，**这个迭代过程本身就是设计工作的常态**。

### 1.1 场景题的推进节奏

> 场景设计题的推进节奏是：**先给出大体思路 → 与需求方讨论需求和资源约束** →
> **补充关键元素或提出疑问 → 据此调整设计 → 逐步完善**。
>
> **它不是一开始就有一个一成不变的设计**。有缺陷没关系，**关键是必须要有思路能拿出来讨论**。

### 1.2 完整设计（四层）

![弹幕系统的四层架构：接入限流、双路径分流、缓存持久化、发布订阅扇出](images/弹幕四层架构.svg)

#### 第 1 层：接入限流（防刷屏）

客户端发弹幕 → 服务端**第一步先限流**：

- 限流维度：**按用户 / 设备 ID / 客户端**；
- 频率：如 10 分钟 1 条、1 分钟 1 条——**由业务需求决定**；
- 触发限流 → **直接丢弃**，不再往下走。

#### 第 2 层：双路径分流

通过限流后，弹幕数据要走**两条路**：

| 路径 | 目的 |
|---|---|
| **推送链路** | 推送到前端**实时展示** |
| **持久化链路** | 保存数据，供**直播回放**展示或**弹幕数据分析** |

#### 第 3 层：持久化 —— 为什么必须走缓存

**弹幕数据的特征**：
- 属于**娱乐性数据**，重要性低，**丢几条不影响业务**，不涉及经济损失和核心体验；
- **生产成本极低**——用户只需编辑发送，没有任何成本门槛；
- 因此**发送频率极高**（即使加了限流，量依然很大）。

**为什么不能直接写数据库**：

> 如果每发一条弹幕就写一次库，**弹幕的写入 TPS 会和数据库的查询 TPS 相当**，
> 而这类高频插入正是数据库最不擅长的。

**方案**：
1. **先写入 Redis 缓存**（读写性能远高于 MySQL 这类数据库）；
   - 代价：缓存可能因主动淘汰丢数据——但对弹幕来说，**丢了就丢了，可以接受**；
2. **通过定时任务或消息队列批量落库**；
3. 落库目标可选**关系型数据库**或 **MongoDB 这类文档型数据库**，取决于具体方案。

> **原则**：尽量避免"每条新数据都写一次库"，**尽可能改成批量操作**。

#### 第 4 层：推送链路 —— 用 Redis 发布订阅打通分布式节点

**问题**：服务端是**分布式部署**的，前面有负载均衡：
- 一个请求**具体落到哪台服务器不确定**；
- 用户的 **WebSocket 长连接建立在哪台服务器上也不确定**（可能连 1 号、2 号、3 号都能连）。

**如果只靠单机内存维护连接映射，就会出现"弹幕推给了没有这个连接的机器"**。

**解法：引入 Redis 发布订阅**

```text
所有服务器都订阅同一个主题
        ↓
收到弹幕数据的服务器 → PUBLISH 到该主题
        ↓
所有持有 WebSocket 连接的服务器都能收到通知
        ↓
各自通过 WebSocket 推送给自己的在线用户
```

![Redis 发布订阅把弹幕扇出到所有持有 WebSocket 连接的节点](images/Redis发布订阅跨节点扇出.svg)

这样，**弹幕的推送不再依赖"用户恰好连在哪台机器"**。

### 1.3 这段的设计要点

1. **先给框架**：限流 → 双路径（实时推送 + 持久化）；
2. **主动解释关键权衡**：弹幕可容忍丢失 → 所以缓存优先、批量落库；
3. **主动暴露分布式的坑**：负载均衡下连接位置不确定 → 所以需要发布订阅；
4. **保留被追问的余地**：对方会补充元素或质疑设计，据此迭代即可。

## 二、这套系统的数据存哪？

弹幕的价值低、量大、生产成本极低 —— 这三点决定了它的存储可以「缓存优先、批量落库、冷层兜底」：同一份弹幕在不同生命周期里落在不同层，绝大部分可以丢。

| 数据 | 角色 | 存储 | 理由 |
|---|---|---|---|
| 弹幕本体 | 权威源 | MySQL（量再大就转列存 / 日志） | 回放与分析的原始数据，批量落库；单条可丢但整体要留存 |
| 在途弹幕 / 房间订阅 | 缓存 | Redis（Pub/Sub） | 实时扇出的一次性推送与订阅状态，直播结束即失效，丢了无妨 |
| 热点房间缓存 | 缓存 | Redis | 读高度集中，缓存在库前挡量；可从落库弹幕重建 |
| 历史弹幕 | 归档 / 冷数据 | 对象存储 + 列存文件 | 只在回放时读，量最大，用最便宜的介质 |
| 弹幕分析 | 分析副本 | 列存 | 按房间 / 时段聚合，不拖垮在线库；从弹幕本体派生 |

⭐ 判据：问「这份数据丢了能不能重建」—— 在途弹幕、房间订阅与热点缓存都是可重建的副本，丢了最多影响一时体验；真正要留的是落库的弹幕本体，它是回放与分析不可重建的源，所以缓存优先、批量落库、冷层兜底。

完整的分工视角见 [存储选型与组合.md](../存储选型与组合.md)。

## 延伸追问

- **弹幕该推还是拉？** → 先看在线房间规模与消息量：小规模直接广播；大规模以「房间订阅 + 服务端推」为主，配合客户端批量拉取做补偿。核心是**别让每个观众都去扫全量**。
- **弹幕要不要持久化？** → 分场景，而且链路必须分开：实时弹幕可丢（走内存 Pub/Sub），历史弹幕要存（写 MQ 落库或对象存储）。混在一条链路上，存储抖动会在直播期间形成尖刺。
- **高并发写入怎么削峰？** → 先写内存队列 / MQ 缓冲，消费端按自身能力匀速落库；直播间热度差异极大，要能**按房间动态分配配额**，别让一个热门房间拖垮全局。
- **怎么防刷屏？** → 分层做：客户端节流 → 网关按用户与房间双维度限流 → 内容侧滑动窗口频控与去重。
- **一致性上能妥协吗？** → 能而且**必须**：弹幕允许短暂乱序与丢失，用最终一致换低延迟——但这个取舍要自己主动说出来，别等着被追问。
- **落地骨架里最该讲的代码点？** → 连接管理：怎么维护「房间 → 连接集合」映射、读写并发的安全边界、以及断连时的清理——这里最容易漏协程（见 [协程泄漏与死锁.md](../../../01-编程语言/go/并发编程/协程泄漏与死锁.md)）。
