# 推荐系统

> 从工程实现角度拆解推荐系统：召回 → 粗排 → 精排 → 重排的分层流水线、在线与离线两条链路、特征存储、延迟预算，以及兜底与降级。

## 一、推荐系统为什么先讲架构，而不是模型？

**本节要点**：推荐系统的工程难点不在「有一个好模型」，而在「**一次请求要在几十毫秒内，从几百万条内容里挑出用户会看的十几条**」。模型只是这条流水线里的一个算子，架构决定它有没有机会发挥作用。

### 1.1 一条推荐请求背后是四个系统

用户下拉刷新一次，工程侧实际发生的事是：**取候选 → 打分 → 选最终列表**。这三步因为量级和延迟要求差得太大，被拆成四层：召回、粗排、精排、重排。每一层只解决「上一层筛完还剩下什么」的问题。

### 1.2 模型是「精排」里的一个算子

精排才真正用模型给候选打分。召回阶段往往用不上复杂模型（要跑几百万条，跑不动），粗排用的是轻量模型或规则，重排很多时候是业务规则而不是模型。**把架构讲清楚，才知道模型被放在哪一层、被谁约束。**

### 1.3 本篇的边界

本组文档**只讲服务架构**：分层、链路、特征、延迟预算、降级。**不推导模型数学**（embedding 怎么训练、损失函数怎么写），那些属于算法侧，仓库里另有向量检索相关的机制篇可以参考。

## 二、四层流水线各自解决什么问题？

**本节要点**：四层是一条**漏斗**——候选集逐层变小、打分逐层变准、延迟逐层变紧。每一层都有明确的输入输出和「兜底不了就交给下一层」的边界。

### 2.1 召回：从全库到候选集

召回面对的是**全部内容**（百万到亿级）。它的目标不是「排得准」，而是「**别把用户可能喜欢的漏掉**」——在几毫秒内，用多路并行的手段各捞一批，拼成一个几千条的候选集。关键是**召回率**，不是精度。

### 2.2 粗排：给精排做一次「预筛」

精排模型比较重，对几千条候选逐条跑不划算。粗排用**轻量模型或规则**把候选从几千砍到几百，代价是损失一点精度。它的定位是「**省钱的那一层**」：如果精排足够快，粗排可以没有。

### 2.3 精排：对几百条候选打分

精排对每条候选算出「用户点击 / 转化」的**预估分**，把几百条排成一个有序列表。这一层用了特征最多、模型最复杂，也是最耗时的环节——延迟预算大多被它吃掉。

### 2.4 重排：打分之外还要「像人排的」

精排给出的是「单条内容各自多好」，但一个真实列表还要考虑**内容之间的关系**：别整屏都是同一类、别都是同一个作者、广告要按规则插入。重排在这一层做多样性、打散与业务规则。

## 三、为什么分层：延迟预算从宽到窄

**本节要点**：分层的根本原因是**候选数量和延迟要求反向变化**——越往后的层，候选越少、对延迟越苛刻。把所有工作塞进一层，要么跑不动，要么超时。

### 3.1 候选数量级逐层收窄

工程上常见的量级是：召回从**百万级**捞到**几千条**，粗排筛到**几百条**，精排给**几百条**打分，重排输出**几十条**给前端。注意这些是**量级参考**（每家的具体数字不同），不是实测读数；真正要记的是「**每层砍一个数量级**」这个形态。

| 层 | 输入量级 | 输出量级 | 主要目标 |
|---|---|---|---|
| 召回 | 全库（百万~亿） | 数千 | 召回率（别漏） |
| 粗排 | 数千 | 数百 | 省算力（别太贵） |
| 精排 | 数百 | 数百（有序） | 精度（排得准） |
| 重排 | 数百 | 数十 | 体验与业务规则 |

### 3.2 延迟预算逐层收紧

反过来，层越靠后，留给它的时间越少。常见的预算是「整条链路几十毫秒」，其中召回允许几毫秒、粗排几毫秒、精排十几毫秒、重排一两毫秒，再留一段给网络的余量。⚠️ 这些是**设计目标**而非实测值；真实预算必须以线上监控为准，本篇未做压测。

### 3.3 分层是为了「把可并行的放在前面」

召回的多路（热门、协同、向量……）**彼此独立、可以并行**，所以放在最前，用「取最慢的一路」当总耗时。粗排精排需要对候选逐条评估，天然是串行的、逐条累加成本，只能往后放并压缩条数。**能并行的一起跑，必须串行的尽早砍量**，这就是分层的账。

## 四、在线与离线两条链路怎么分工？

**本节要点**：推荐系统由**离线**（算得慢、数据全、产出模型与特征）和**在线**（算得快、只看当下、产出最终列表）两条链路组成。它们通过**特征存储**交接：离线把算好的东西写进去，在线在请求时读出来。

### 4.1 离线：算得慢、样本全

离线链路按天/小时跑，用全量日志训练模型、算用户画像、算物品统计（如热度、共现）。它的特点是**可以很慢，但结果要能沉淀**——沉淀成模型文件与特征。

### 4.2 在线：算得快、只看当下

在线链路在一次请求里完成召回→粗排→精排→重排。它只能读**已经算好的特征**，加一点**当下的实时信号**（这次会话刚点了什么），做的计算必须都能在毫秒级完成。

### 4.3 近线：补上「来不及离线」的那一段

有些特征变化很快（用户最近几分钟的行为、内容刚上线的初始热度），按天离线太慢、纯在线又太贵。于是加一条**近线**链路：消费实时消息流，秒级到分钟级地把中间结果写进特征存储。它是离线与在线之间的缓冲层。

## 六、这套系统的数据存哪？

推荐系统里被当成「模型输入」的东西 —— 特征与样本 —— 几乎全是派生数据：它们都能从用户行为重算，所以可丢、可重刷；真正不可重建的只有行为与互动本身。

| 数据 | 角色 | 存储 | 理由 |
|---|---|---|---|
| 用户 / 物品 / 互动 | 权威源 | MySQL | 唯一真相；特征、样本、向量全由它派生，丢了不可重建 |
| 在线特征 | 缓存 | Redis / 特征存储 | 请求时毫秒级读取；可从权威源与行为流重算 |
| 离线样本 / 特征快照 | 分析副本 | 列存 / 对象存储（Parquet） | 训练用大宽表，按天重刷；全可由行为派生 |
| 召回向量 | 检索副本 | 向量索引 / ES | 供近邻检索；模型重训即可整体重建 |
| 历史样本与行为日志 | 归档 / 冷数据 | 对象存储 + 列存文件 | 体量最大、罕见读出；是重刷样本与模型的最后退路 |

⭐ 判据：问「这份数据丢了能不能重建」—— 用户、物品、互动是权威源，丢了重建不出来；在线特征、离线样本、召回向量全是它们的派生副本，模型与样本都能重算，所以可丢、可重刷。

完整的分工视角见 [存储选型与组合.md](../存储选型与组合.md)。

## 使用：给一次推荐请求画延迟预算

> ⚠️ 下面是**方法**，不是实测数据。真实预算要靠线上监控量出来，本篇未做压测。

给一条请求画预算，就三步：

1. **定总预算**：前端能等多久（比如「首屏卡片要快，整条链路留几十毫秒」），减掉网关与网络，剩下的才是推荐服务的时间。
2. **按层切**：召回（可并行，取最慢一路）→ 粗排 → 精排 → 重排，每层给一个上限，并强约「超了就走降级」。
3. **给每层配兜底**：任意一层超时或报错，都要有「退到上一层的结果」或「退到热门」的具体动作，而不是把请求挂住。

```text
总预算 = 网关 + 召回(取最慢一路) + 粗排 + 精排 + 重排 + 序列化/网络
                            ↑ 可并行      ↑ 逐条累加，靠砍条数压时间
```

⭐ 两条纪律：**能量化的延迟都要设上限**（没有上限就一定会偷偷超）；**越靠后的层越要短**（它面对的候选最少，却最容易拖长尾巴）。

## 延伸追问

- **为什么不直接用一个大模型一次排完？** → 因为召回面对的是百万~亿级候选，模型对全集逐条跑不动；分层的意义就是**把重模型只留给已经被砍到几百条的候选**。
- **粗排能不能省掉？** → 当精排模型足够轻、几百到几千条也能在预算内跑完时可以省；省不掉的是「**必须有一层把候选砍到精排扛得住的量**」，这层叫召回或粗排都行。
- **离线与在线为什么一定要用同一套特征口径？** → 训练时用的特征和线上打分时读到的特征如果不一致，模型学到的东西就错位了，这叫**线上线下一致性**问题，展开在 [特征与冷启动.md](特征与冷启动.md)。
- **推荐服务挂了会怎样？** → 必须能退到一个**不需要模型**的结果（热门 / 编辑精选 / 兜底缓存），保证页面能出来。见 [特征与冷启动.md](特征与冷启动.md) 的兜底一节。
