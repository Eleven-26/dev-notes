## 一、场景题：设计一个秒杀系统

**本节要点**：秒杀题**不考"你能堆多少中间件"**，考的是「**每一步在挡什么**」。
下面按「先想清楚有什么 → 找出第一性问题 → 逐层加手段 → 说清代价」的顺序推，
每一步都附本机实测读数 —— 因为这道题最容易被答成一张组件清单。

**先看这张清单** —— 秒杀要解决的七个问题、各自的手段、以及落在本篇哪一节（或哪一篇子系统）：

| # | 问题 | 手段 | 落在哪 |
|---|---|---|---|
| 1 | **瞬时高并发**（峰值是均值几百倍） | 前端按钮置灰 → 接入层答题 → 网关多维度限流 | 1.6 · [限流算法.md](../../分布式/服务治理/限流算法.md) |
| 2 | **库存扣减**（共享可变量的原子性） | Redis Lua / 带条件 UPDATE / CAS | 1.3、1.5 |
| 3 | **防超卖** | 原子判定 + 唯一索引兜底 | 1.2 · [库存系统设计.md](库存系统设计.md) |
| 4 | **限流** | 按用户优先、IP 兜底（别一刀切按 IP） | 1.6 |
| 5 | **队列削峰** | 异步批量入队 + 有界消费 | 1.4 |
| 6 | **缓存**（热点商品 + 库存） | 静态化 / 预热 / 防击穿（singleflight / 逻辑过期）/ 缓存与 DB 同步 | [商品详情页设计.md](商品详情页设计.md) · [库存系统设计.md](库存系统设计.md) |
| 7 | **异步下单** | 入队 → 消费者落库 + 幂等 + 对账 | 1.4 · [订单系统设计.md](订单系统设计.md) |
| 8 | ⭐ **优惠券 / 红包发放**（**扩展**，见下方说明） | 原子判重 + 唯一索引兜底 + 异步发放 | [优惠券系统设计.md](优惠券系统设计.md) |

⚠️ **第 8 条是扩展，不属于上面这七步** —— 秒杀本身不发券，它是「同一批手段（原子判定 + 唯一索引 + 异步）
在另一种发放场景上的应用」：券稀缺的是**份数**，红包稀缺的是**金额**。
放在这里是因为两者经常被一起问（"你还能怎么用这套东西"），而不是因为它在这条链上。

⭐ 这七条不是并列的选项，而是**一条链上依次要过的关**：
流量先被限流挡掉大部分（1、4）→ 剩下的进 Redis 做原子扣减（2、3）→ 抢到的异步入队（5、7）→
落库与对账保最终一致（7）→ 而缓存（6）贯穿整条链，是"读"的那一侧。

### 1.1 第一步：要素分析（先想清楚"有什么"）

| 要素 | 秒杀场景下的特点 |
|---|---|
| **商品** | 数量少（往往 1 个 SKU）、信息读多写少 → 静态化 + CDN 就够（怎么切见 [商品详情页设计.md](商品详情页设计.md) 第六节） |
| **库存** | ⭐ **零和的稀缺资源**，是整个系统唯一必须"精确"的东西 |
| **用户** | 海量、且**大部分注定抢不到** —— 这是与其他业务最大的不同 |
| **订单** | 数量等于库存（不是等于请求数），但要**能追溯、不能丢** |
| **时间窗** | 极短（通常 1~10 秒内打完）→ 峰值是均值的几百倍 |

由此得出三个**互相冲突**的硬指标，后面每一个手段都是在它们之间做取舍：

1. **不超卖**（正确性）—— 卖出的数量必须恰好等于库存；
2. **不宕机**（可用性）—— 99% 的请求注定失败，但系统不能跟着它们一起倒；
3. **防刷 / 公平**（业务性）—— 不能让脚本把货全抢走（黄牛）。

⭐ 一句话抓住要害：**秒杀系统的本质是「用一个可控的方式，处理掉绝大多数注定失败的请求」**。

### 1.2 第二步：为什么「超卖」是这类系统的第一性问题

**本节要点**：因为它是**唯一一个"代码看起来完全正确、结果却是错的"**的问题。
库存是个**共享可变量**，而「读 → 判断 → 写」这三步在并发下**不是原子的**。

下面是四组实测的四类错误写法与正确写法对照。**统一参数**：初始库存 **1000**、
并发请求 **5000~10000**（每个请求买 1 件）。判定标准：**成功数 = 1000 且剩余 = 0 才算对**。

| 环境 | 写法 | 成功数 | 库存 | 结论 |
|---|---|---|---|---|
| **Go 内存** | 无保护「先查再减」 | 1158 / 1201 / 1266 | 0 | ❌ **超卖 158~266** |
| **Redis** | `GET` 检查 → `DECR`（两次往返） | **5000** | **-4000** | ❌ **全部成交** |
| **MySQL** | `SELECT` 后把「读到的值 - 1」写回 | **5000** | **990** | ❌ **丢失更新**（只减掉 10 次） |
| **MySQL** | `SELECT` 判断后 `SET stock = stock - 1` | 2872~2909 | **-1872~-1909** | ❌ 超卖 + 负库存 |
| Go 内存 | 互斥锁 | 1000 | 0 | ✅ 但对热点串行 |
| Go 内存 | 单 key `atomic.CompareAndSwap` | 1000 | 0 | ✅ 失败重试 237~313 次 |
| Redis | **Lua 脚本** | 1000 | 0 | ✅ 服务端一次执行 |
| MySQL | 单条 `UPDATE ... WHERE stock > 0` | 1000 | 0 | ✅ 看 `RowsAffected` |

⭐ **三个最值得记住的读数**：

1. **Redis 那行是 5000/5000** —— 不是"超卖一点点"，是**所有请求都成交了**。
   原因很朴素：5000 个请求在自己的连接上读到的库存都还是 `1000`（还没被扣），
   于是**每一个都通过了 `> 0` 的检查**，然后各自去 `DECR`。
2. **MySQL 的「丢失更新」最阴** —— 成功 **5000**、库存却有 **990**：
   1000 个并发请求里，真正减掉的只有 **10 次**。
   顾客全都收到"下单成功"，而账上是"库存还剩 990" —— **系统自己完全没察觉**。
   这类 bug 在低并发测试里永远复现不出来。
3. **正确写法只有一条思路**：把「判断 + 修改」压进**一个原子操作**里 ——
   锁（串行）、CAS（重试）、Lua（服务端串行）、带条件的 UPDATE（行锁 + 当前读）。

### 1.3 第三步：库存扣减写在哪（Redis 预扣 + 异步落库）

**本节要点**：主流形态是 **Redis 扣减（挡住流量）+ 异步落库（最终一致）**。
但"用 Redis"只解决了一半，**另一半是"别在客户端分两步"**。

Redis 侧的四个对照（同一批 5000 并发请求，Redis 7.4.11）：

```text
=== ① 客户端两步（GET 检查 → DECR）===
  第 1 轮：成功  5000  库存 -4000  超卖 +4000  耗时 720ms
  第 2 轮：成功  5000  库存 -4000  超卖 +4000  耗时 667ms
  第 3 轮：成功  5000  库存 -4000  超卖 +4000  耗时 674ms

=== ② 客户端只发 DECR，用返回值判断（<0 则视为失败）===
  第 1 轮：成功  1000  库存 -4000（负数 = 被扣穿，需回补）  耗时 315ms
  第 2 轮：成功  1000  库存 -4000（负数 = 被扣穿，需回补）  耗时 321ms
  第 3 轮：成功  1000  库存 -4000（负数 = 被扣穿，需回补）  耗时 347ms

=== ③ Lua 脚本（读-判-写在服务端一次执行）===
  第 1 轮：成功  1000  库存     0  耗时 434ms
  第 2 轮：成功  1000  库存     0  耗时 597ms
  第 3 轮：成功  1000  库存     0  耗时 642ms

=== ④ Lua 脚本（先 DECR，为负就 INCR 回补）===
  第 1 轮：成功  1000  库存     0  耗时 570ms
  第 2 轮：成功  1000  库存     0  耗时 533ms
  第 3 轮：成功  1000  库存     0  耗时 377ms
```

⭐ **② 与 ③ 的对照，是这一节最值钱的地方**：

- **②「先减再判」在客户端做**：成功数**是对的**（1000），但库存被扣成 **-4000**。
  这就是「**成功数对 ≠ 账对**」—— 你必须再写一次 `INCR` 把多扣的 4000 补回来，
  而**回补本身又是一次网络往返**（补的过程中库存是错的，其他人看到的可用量也是错的，甚至会再放大一波流量）。
- **④ 同样的「先减再判 + 回补」放进 Lua**：完全正确。
  **命令顺序一模一样，差别只在"这段逻辑跑在谁的进程里"**。

⭐ 由此得到这条判据，它比"记住用 Lua"重要得多：

> **原子性的边界在服务端。** 只要「读」和「写」之间隔着一次网络往返（或一次函数返回），
> 那个间隙就是竞态窗口 —— 无论你在客户端写得多小心。

**正确形态的骨架**（预扣阶段只做一件事：把"能不能买到"变成一次原子判定）：

```lua
-- KEYS[1] = 库存 key（如 stock:sku_1001），ARGV[1] = 本次购买数量
-- 返回：剩余库存（>=0 表示扣减成功），-1 表示 key 不存在，-2 表示库存不足
local left = redis.call('GET', KEYS[1])
if not left then return -1 end
local n = tonumber(left)
local want = tonumber(ARGV[1])
if n < want then return -2 end
return redis.call('DECRBY', KEYS[1], want)
```

调用侧只有在返回值 `>= 0` 时才认为"抢到了"，然后**立刻把订单请求丢进消息队列**，
真正的落库、扣积分、发券由消费者慢慢做（下一节就是讲"为什么要排队"）。

### 1.4 第四步：削峰 —— 拒绝还是排队？

**本节要点**：削峰**不是让系统变快**，而是把「**不可控的雪崩**」换成「**可控的等待**」。
而且 ⚠️ **「用了消息队列」≠「削峰成功」** —— 入队吞吐必须远大于下游，否则队列自己就是新瓶颈。

固定条件：下游处理能力 **并发 50、每条 20ms（≈ 2500 条/秒）**；
洪峰 **10000 个请求同时到达**（是下游能力的 **4 倍**）。用 NATS 2.10 JetStream（FileStorage）实测：

```text
下游能力：并发上限 50、每条处理 20ms（≈ 2500 条/秒）
洪峰：10000 个请求同时到达（下游能力的 4.0 倍）

=== ① 同步直连：请求直接打下游 ===
  成功    50  被拒  9950  耗时 23ms
  ⭐ 洪峰没有被消化，只是被拒绝了 —— 被拒的那部分就是真实丢掉的订单

=== ② JetStream 削峰：先入队，消费者按自己的节奏取 ===
  [同步 Publish] 入队 10000 条：耗时 15.983s（≈ 625 条/秒）
  消费完成 10000 条：成功 10000  失败 0  耗时 16.038s（≈ 623 条/秒）
  排队等待：第 1 条 7ms，最后 1 条 15.987s
  队列积压峰值 10000 条
  ⭐ 一条没丢、下游并发始终不超过 50 —— 代价是后面那部分订单要排队等待

=== ③ 同样的队列，换成异步批量入队（PublishAsync）===
  入队 10000 条（异步批量 + 等落盘）：耗时 139ms（≈ 71949 条/秒）
  队列积压峰值约 10000 条 —— 入队远快于消费，积压是必然的
  ⭐ 对比 ② ：同一个队列，**入队方式**决定了它能不能真的削峰
```

⭐ **读数说明（必读，否则会高估一个数量级）**：上面 ②③ 两段的**绝对值依赖宿主机磁盘状态** ——
本机 JetStream 用 `FileStorage`，每条消息都要 fsync，连跑四次的区间是：

| 场景 | 四次区间 | 结论（这个才是稳定的） |
|---|---|---|
| ② 同步 `Publish` 入队速率 | 225 ~ 625 条/秒 | **几百条/秒量级** |
| ③ 异步批量入队速率 | 21721 ~ 71949 条/秒 | **万条/秒量级** |

⭐ **要记住的不是 71949，而是「两者差两个数量级」** —— 这才是「入队方式决定削峰成败」的证据。
⚠️ 下面 1.8⑤ 那句「入队速率必须远大于下游（2500 条/秒）」用 `FileStorage` 衡量会显得苛刻；
换内存存储的 NATS 或换读数更小的下游，这条约束会放松，但**结论方向不变**。

⭐ **三行结论，一行比一行重要**：

1. **① 是"没有削峰"的样子**：10000 个请求在 23ms 内被拒掉 9950 个。
   系统没垮 —— 但**9950 个真实订单被丢掉了**，用户看到的是"活动太火爆，请稍后再试"。
2. **② 是"用了队列但削峰失败"的样子**：入队速率只有 **625 条/秒**，比下游（2500 条/秒）**还慢 4 倍**。
   原因不神秘：同步 `Publish` 每条消息都要**等一次落盘 ack**（一次往返 + 一次 fsync），
   10000 条串行等下来就是 16 秒 —— **队列成了新的瓶颈**，
   积压数从第一秒就是满的（10000），因为**生产比消费还慢**。
3. **③ 才是真的削峰**：`PublishAsync`（异步批量 + 一次等落盘）把入队抬到 **71949 条/秒**（快 115 倍）。
   于是洪峰被"吸"进队列只用 139ms，下游按自己的 2500 条/秒慢慢消费 —— 一条不丢。

⭐ 由此可以给"削峰"下一个不带水分的定义：

> **削峰 = 让"入队速率"远大于"下游速率"，从而把"瞬时并发压力"换成"队列长度 + 等待时间"。**
> 判据很简单：**看积压曲线** —— 真的削峰，积压应该是「**瞬间冲高、然后线性下降**」；
> 如果积压一开始就是满的、而且不降，那是**生产侧也在被下游拖住**（② 就是这种）。

**代价必须一起讲**：③ 的第 1 条只等了 7ms，最后 1 条等了 **约 16 秒**。
这 16 秒就是"削峰"的价格 —— 秒杀业务可以接受（前端显示"排队中"），
但**换到支付回调那种链路就未必**（那里的等待意味着真金白银的时间差）。

### 1.5 第五步：真正的瓶颈是「同一行」

**本节要点**：前面都在说"怎么写对"，这一节说"**为什么再怎么写也快不了**"——
因为**同一行的 UPDATE 必须串行**。

同样 5000 个并发请求、1000 库存，MySQL 8.0.46（隔离级别 `REPEATABLE-READ`）的五组对照：

```text
=== ① SELECT 判断，再把「读到的值 - 1」写回（丢失更新）===
  第 1 轮：成功  5000  剩余   990  超卖 +4000  耗时 34.618s
  第 2 轮：成功  5000  剩余   996  超卖 +4000  耗时 31.949s
  第 3 轮：成功  5000  剩余   995  超卖 +4000  耗时 1m6.39s

=== ② SELECT 判断，但写 `stock = stock - 1`（判断与写入脱节）===
  第 1 轮：成功  2872  剩余 -1872  超卖 +1872  耗时 28.056s
  第 2 轮：成功  2900  剩余 -1900  超卖 +1900  耗时 32.406s
  第 3 轮：成功  2909  剩余 -1909  超卖 +1909  耗时 21.351s

=== ③ 单条 UPDATE ... WHERE stock > 0（看 RowsAffected）===
  第 1 轮：成功  1000  剩余     0  超卖    +0  耗时 5.996s
  第 2 轮：成功  1000  剩余     0  超卖    +0  耗时 6.715s
  第 3 轮：成功  1000  剩余     0  超卖    +0  耗时 6.903s

=== ④ 乐观锁：WHERE version = ? 失败就重读重试 ===
  第 1 轮：成功   767  剩余   233  超卖  -233  重试  92132 次  耗时 1m20.821s
  第 2 轮：成功   773  剩余   227  超卖  -227  重试  92167 次  耗时 1m30.806s
  第 3 轮：成功   773  剩余   227  超卖  -227  重试  92122 次  耗时 1m43.285s

=== ⑤ 悲观锁：事务内 SELECT ... FOR UPDATE ===
  第 1 轮：成功  1000  剩余     0  超卖    +0  耗时 28.719s
  第 2 轮：成功  1000  剩余     0  超卖    +0  耗时 32.248s
  第 3 轮：成功  1000  剩余     0  超卖    +0  耗时 21.771s
```

**读数一：③ 是唯一"又快又对"的，但它也只有 833 次/秒。**
5000 次扣减花 **6 秒** —— 换算过来 **≈ 833 次/秒**。
这不是 MySQL 慢（它空跑几万 QPS），而是**同一行的行锁让它必须排队**：
每次 `UPDATE` 都要拿到那一行的排他锁，改完才能放手。
⭐ 所以秒杀的**第一性瓶颈是"行"**，不是"库"：
**一台数据库的吞吐上限，在这里等于"每秒能串行地改多少次同一行"。**

**读数二：④ 乐观锁在热点行上是负优化。**
成功只有 **767~773**（**漏卖 227~233**！），重试 **9.2 万次**，耗时 **80~103 秒**（比 ③ 慢 15 倍）。
为什么漏卖：重试上限（20 次）撞满后只能放弃 ——
⭐ **乐观锁的隐含假设是"冲突很少"，而秒杀的库存行恰好是全系统冲突最多的一行**，
假设与场景完全相反。

**读数三：⑤ 悲观锁正确但慢 4 倍。**
`SELECT ... FOR UPDATE` 把"读-判-写"锁成一个原子段，正确性没问题，
但它把并发彻底压成串行（21~32 秒，接近 ① 的开销）。
⭐ 一句话对比：**③ 让数据库自己判断（一次往返），⑤ 让你自己排队（三次往返 + 持锁）** ——
能用 ③ 就不要用 ⑤。

**那怎么办？把"一行"变成"多行"** —— 这就是**分段库存**。
Go 内存侧的实测（10000 并发请求 / 1000 库存，每种写法跑 3 轮）：

```text
=== ① 无保护（先查再减）===
  第 1 轮：成功  1158  剩余    0  超卖  +158  耗时 3.188ms
  第 2 轮：成功  1201  剩余    0  超卖  +201  耗时 3.459ms
  第 3 轮：成功  1266  剩余    0  超卖  +266  耗时 3.045ms

=== ② 互斥锁 ===
  第 1 轮：成功  1000  剩余    0  超卖    +0  耗时 3.654ms
  第 2 轮：成功  1000  剩余    0  超卖    +0  耗时 4.481ms
  第 3 轮：成功  1000  剩余    0  超卖    +0  耗时 3ms

=== ③ 单 key CAS（无锁自旋）===
  第 1 轮：成功  1000  剩余    0  CAS 失败重试     237 次  耗时 2.132ms
  第 2 轮：成功  1000  剩余    0  CAS 失败重试     308 次  耗时 2.118ms
  第 3 轮：成功  1000  剩余    0  CAS 失败重试     313 次  耗时 3.579ms

=== ④ 分段 CAS（16 段，起点按请求散列 + 轮询其他段）===
  第 1 轮：成功  1000  剩余    0  CAS 失败重试      14 次  耗时 3.518ms
  第 2 轮：成功  1000  剩余    0  CAS 失败重试      11 次  耗时 2.947ms
  第 3 轮：成功  1000  剩余    0  CAS 失败重试       9 次  耗时 2.52ms

=== ⑥ 分段数扫描（每种段数跑 5 轮，看重试次数与耗时的范围）===
  段数     1：成功  1000  剩余   0  重试    50~203   次  耗时 3.107ms~8.196ms
  段数     8：成功  1000  剩余   0  重试     6~30    次  耗时 3.533ms~7.509ms
  段数    64：成功  1000  剩余   0  重试     1~8     次  耗时 4.814ms~6.267ms
  段数   256：成功  1000  剩余   0  重试     1~5     次  耗时 10.509ms~12.737ms
  段数  1024：成功  1000  剩余   0  重试     0~5     次  耗时 37.142ms~44.728ms
```

⭐ 分段的收益是**冲突次数**（重试 200 量级 → 1~8 次，**约 20 倍**），
但代价很有意思：**段数从 256 开始耗时反而上升**（1024 段时 **37~44ms**，比 16 段慢 10 倍）。
原因是起点散列后请求要"扫段"，段越多扫的段越多 —— **分段不是越细越好**。

⚠️ **分段还有两个必须知道的坑**（都在下面实测出来了）：

**坑一：只试自己那一段时，起点分布一倾斜就漏卖。**

```text
=== ⑤ 分段 CAS：只试自己那一段时，起点分布决定成败 ===
  起点均匀 + 不轮询                   第 1 轮：成功  1000  剩余    0  漏卖    0  耗时 5.527ms
  起点均匀 + 不轮询                   第 2 轮：成功  1000  剩余    0  漏卖    0  耗时 2.002ms
  起点倾斜（都从段 0 起）+ 不轮询           第 1 轮：成功    63  剩余  937  漏卖  937  耗时 2.998ms
  起点倾斜（都从段 0 起）+ 不轮询           第 2 轮：成功    63  剩余  937  漏卖  937  耗时 2.005ms
  起点均匀 + 轮询其他段                 第 1 轮：成功  1000  剩余    0  漏卖    0  耗时 2.997ms
  起点均匀 + 轮询其他段                 第 3 轮：成功  1000  剩余    0  漏卖    0  耗时 4.002ms
```

—— 起点均匀时"只试一段"碰巧也能卖完（因为每段都有足够的请求）；
但**一旦流量倾斜**（同一批脚本、同一批网段、或者段的库存分配不均），
段 0 卖光之后剩下的请求全被拒，而其他段还有 **937** 件没卖出去。
⭐ 所以分段的正确性依赖「**起点散列均匀**」这个假设，**必须配"轮询其他段"兜底**。

**坑二：在单机 Redis 上，分段带不来任何收益，而"轮询兜底"会实打实地变慢。**

```text
=== ⑤ Lua 单 key vs 分段 key（16 段）===
  单 key（不打散）               第 1 轮：成功  1000  剩余    0  耗时 450ms
  单 key（不打散）               第 2 轮：成功  1000  剩余    0  耗时 450ms
  单 key（不打散）               第 3 轮：成功  1000  剩余    0  耗时 432ms
  16 段 + 轮询其他段             第 1 轮：成功  1000  剩余    0  耗时 6.129s
  16 段 + 轮询其他段             第 2 轮：成功  1000  剩余    0  耗时 6.806s
  16 段 + 轮询其他段             第 3 轮：成功  1000  剩余    0  耗时 7.031s
  16 段但只试自己那一段             第 1 轮：成功  1000  剩余    0  耗时 602ms
  16 段但只试自己那一段             第 2 轮：成功  1000  剩余    0  耗时 561ms
  16 段但只试自己那一段             第 3 轮：成功  1000  剩余    0  耗时 421ms
```

读这张表要连着看两行：**"只试一段"与单 key 基本持平（约 0.5s）** ——
说明分段的**收益为零**（Redis 单线程执行 Lua，本来就没有 CAS 冲突可省）；
而**"轮询其他段"慢到 6.1~7.0 秒（约 14 倍）** —— 那部分开销**全部来自扫段的额外往返**。
⭐ 所以不是"分段有害"，而是**在单机 Redis 上它既没收益、又要为兜底付出往返成本**。

⭐ 于是可以给"要不要分段"一条明确判据：

| 场景 | 分段有用吗 | 为什么 |
|---|---|---|
| **Go 内存**（多核 CAS） | ✅ 有用 | 核之间真的在抢同一个内存地址，分段能减少自旋 |
| **单机 Redis / 单机 MySQL 单行** | ❌ 反而更慢 | 服务端本来就是串行的，分段只增加往返与扫段成本 |
| **Redis Cluster / 分片 MySQL** | ✅ 有用 | 不同段的 key 落在**不同分片**上 → 行锁/单线程争用被真正分散 |

**一句话**：分段的本质是「**把争用挪到不同的物理资源上**」；
如果物理资源本来就只有一个（单机 Redis），分段只是把"排队"换成了"多跑几趟"。

### 1.6 第六步：防刷与限购

**本节要点**：前五步解决"**系统别死、账别错**"，这一步解决"**别让脚本把货抢光**"。
要按「**成本递增**」逐层加，前端能挡住的绝不留到服务端。

| 层 | 手段 | 挡什么 | 代价 |
|---|---|---|---|
| **前端** | 按钮置灰、倒计时、随机化参数名 | 手速正常的普通用户重复点 | 对脚本无效，只是减少无效流量 |
| **接入层** | 答题 / 滑块 / 验证码 | 纯脚本（无人值守） | 增加一步交互，影响体验 |
| **网关** | 按 IP / 用户 / 设备的**多维度限流** + 黑名单 | 单机高频、已知恶意特征 | 要处理 NAT（一个门店共用一个出口 IP —— 别一刀切按 IP） |
| **服务层** | **一人一单**（同用户同商品只允许一单） | 脚本换号循环抢 | 需要一次原子判定（同 1.3 的 Lua） |
| **数据层** | **唯一索引**（`uk(user_id, sku_id)`） | ⭐ **前面全被绕过时的最后一道** | 无（索引成本） |

⭐ 两个容易答错的点：

1. **限流别只按 IP**：摄影工作室、校园、企业出口往往共用一个 NAT IP，
   按 IP 限流会**误伤整栋楼**。要按「用户 ID 优先、IP 兜底」的维度组合
   （维度设计与键的选择见 [限流算法.md](../../分布式/服务治理/限流算法.md)）。
2. **"一人一单"必须落到数据库唯一索引**：服务层的判重也可能被并发穿透
   （同一个用户两个并发请求同时通过检查）——**唯一索引是唯一不会骗人的那层**
   （两道防线的实测，以及 ⚠️「给已有脏数据的表补唯一索引会直接失败」的报错原文，
   见 [优惠券系统设计.md](优惠券系统设计.md) 第二节）。

### 1.7 第七步：兜底 —— 抢到了没付款怎么办

**本节要点**：库存被"预扣"之后，用户可能**不付款**。
不回收，库存就被永久占住；回收逻辑写错，会把已付款的订单也放回去（**超卖的反向事故**）。

| 环节 | 做法 | 关键判据 |
|---|---|---|
| **超时回收** | 下单时投一条"延迟消息"（或定时扫表），到点检查状态；未支付则**归还库存** | ⭐ 归还前**必须再查一次订单状态**（可能刚好付款成功） |
| **幂等** | 每个写操作带一个去重键（订单号 / `requestId`） | 消费者重投、用户重复提交都要靠它兜住 |
| **对账** | 定时比对「Redis 剩余库存 + 已下单数」与「DB 库存 + 订单表」 | 对不上不自动改，先**告警 + 人工确认** |
| **补偿** | 对账捞出「订单已落库但 `sku_stock` 未扣」（消费端条件 `UPDATE` 影响 0 行） | ⭐ **从订单表出发**算差集（MQ 侧无线索：重投会被Ack 掉、消息不留痕）；人工确认后**补扣或撤单**，不自动改 |
| **占位卡死** | 网络类错误不释放 Redis 占位时（见「使用」第一段），该 `(sku, uid)` 会被锁到占位 TTL 到期 | 兜底二选一：**缩短占位 TTL**（如 5 分钟，代价是同一用户多台设备会各占一次）或**按 uid 补偿释放**（确认 Redis 侧无扣减后主动 `Del`）；⚠️ 释放前必须确认「脚本没执行」，否则就是超卖 |
| **限购库存** | 活动结束后把"多预留的库存"（活动期预扣、实际未支付）一次性归位 | 归位要有**幂等标记**，避免重复归还（白扣回补的幂等键见 [优惠券系统设计.md](优惠券系统设计.md) 第二段，同一类要求的两个实例） |

⭐ 一条容易忽略的：**Redis 预扣和 DB 落库之间是"最终一致"**，所以**必须能对账**。
对账的粒度不用实时，但**必须有**；没有对账的预扣方案，等于把"账"交给了运气。

### 1.8 第八步：答题结构（怎么把上面讲完）

场景题**没有标准答案**，考的是推导过程。建议照这个顺序讲（每层一句话，被追问再展开）：

```text
① 定指标：不超卖 / 不宕机 / 防刷 —— 这三个是互相冲突的，先说清取舍方向
② 定位置：库存扣减放 Redis（挡流量）+ 异步落库（保最终一致）
③ 说清"为什么不能先查再改"：读-判-写之间就是竞态窗口（可直接引用本机对照数据）
④ 过载保护：前端 + 接入层 + 网关限流，逐层削掉注定失败的请求
⑤ 削峰：入队异步，⚠️ 强调"入队速率必须远大于下游"，否则队列自己就是瓶颈
⑥ 说清瓶颈在哪：同一行的串行上限 → 分段 / 预扣是为了绕过它
⑦ 兜底：超时回收、幂等、对账 三件事
⑧ 收尾：给一个"如果并发再涨 10 倍"的演进方向
```

⚠️ 三个**常见的减分回答**：上来就列一堆中间件名字；
说"加 Redis 就不会超卖"（不提 Lua / 原子性）；
说"加消息队列就能削峰"（不看入队吞吐 —— 本机实测 ② 就是反例）。

## 使用：最小可运行骨架（Go）

**本节要点**：把前三节的核心压成三段代码 —— **Lua 预扣**（1.3）、**异步入队**（1.4 的 ③）、
**消费落库 + 幂等**（1.7）。

> ⚠️ **三段都是骨架片段**（为可读性省略了 import、类型定义与多层错误包装）。其中
> **Lua 扣减、异步入队、带条件的 `UPDATE`** 三处逻辑取自 1.3~1.5 的实测程序，读数已在本机验证；
> **`SETNX` 一人一单**与**幂等消费整段**是**按语义补全的示意代码、未单独实测** —— 已在原处标注。
> ⚠️ 唯一的例外是**条件 `UPDATE` 影响 0 行的处置**：那一处本机实测过（MySQL 8.0.46，读数见第三段下方），
> 但**修法本身只做到「不静默丢」，没做到自愈** —— 原因写在代码注释里，不要当成已解决的问题。

### 第一段：Lua 预扣（原子判定）

```go
// 返回值 >= 0 表示扣减成功（值为剩余库存）；-1 key 不存在；-2 库存不足
const luaDeduct = `
local left = redis.call('GET', KEYS[1])
if not left then return -1 end
local n, want = tonumber(left), tonumber(ARGV[1])
if n < want then return -2 end
return redis.call('DECRBY', KEYS[1], want)
`

func Seckill(ctx context.Context, rdb *redis.Client, sku string, userID int64) (int64, error) {
	key := "stock:" + sku
	hold := fmt.Sprintf("bought:%s:%d", sku, userID)
	// ⚠️ 示意（未单独实测）：用 SETNX 占位实现「一人一单」；
	//    真正的兜底仍是 DB 唯一索引 —— 见 1.6 的两层设计
	ok, err := rdb.SetNX(ctx, hold, "1", 24*time.Hour).Result()
	if err != nil {
		return 0, err
	}
	if !ok {
		return 0, ErrAlreadyBought
	}
	left, err := rdb.Eval(ctx, luaDeduct, []string{key}, 1).Int64()
	if err != nil {
		// ⚠️ 这里**故意不 Del 占位**：`err != nil` 不等于「脚本没执行」——
		//    网络超时 / 连接中断时 Lua 很可能已在服务端执行完 DECRBY，只是确认包没回来。
		//    此时释放占位 → 用户重试 → 扣第二次 → **超卖 1 件**。
		//    只有「能确定脚本没跑」的错误才释放（判据见 isScriptNotRun 的实现骨架）。
		// ⚠️ 不释放的代价不是「全局少卖」——占位是**按 uid 定向**的：
		//    这一个用户被锁死 24h（他之后每次点都是 ErrAlreadyBought），
		//    别的用户不受影响。兜底见 1.7 兜底表的「占位卡死」那一行。
		if isScriptNotRun(err) {
			_, _ = rdb.Del(ctx, hold).Result()
		}
		return 0, err
	}
	if left < 0 {
		_, _ = rdb.Del(ctx, hold).Result() // 没抢到就释放占位（这里能确定脚本跑完了）
		return 0, ErrSoldOut
	}
	return left, nil
}
```

⚠️ 注意 `left < 0` 那个 `Del`：**"没抢到"不算数，占位要还回去** ——
否则用户第一次点显示售罄、后来有库存回流也永远买不了（这就是"占位泄漏"）。

⚠️ 但**不是所有失败都能释放占位**：`err != nil` 时脚本可能已经执行完了（见上面注释）。
两类错误的处置方向相反 ——
「确定没抢到」要**释放**（少卖），「不确定有没有扣成」要**保留**（防超卖），
**判据是「能不能确定脚本没执行」**，不是「有没有报错」。

⚠️ 不释放的代价要说准：占位是**按 (sku, uid) 定向**的，所以后果**不是全局少卖**，
而是**这个用户被卡住 24h**（他之后每次点都撞 `SetNX` 失败 → `ErrAlreadyBought`），
其他用户完全不受影响。兜底手段见 1.7 兜底表最后一行。

#### `isScriptNotRun`：判据必须写成黑名单

⚠️ **这是一个决定「超卖还是少卖」的谓词，判据方向必须写死**：
写反一次、或有人加个 `default: return true`兜底，就从「少卖一件」变成「超卖一件」。

```go
// ⚠️ 示意（未单独实测）：判据形状，不是完整实现。
//    方向写死：**只有「错误可枚举、且确定与本次执行结果无关」才返回 true**。
//    任何网络类 / 超时类一律 false —— 宁可少卖，不可超卖。
func isScriptNotRun(err error) bool {
	// 判据 1：能用errors.Is 断定的**确定型**错误（穷举，不是模糊匹配）
	switch {
	case errors.Is(err, redis.ErrScriptNotExists): // 服务端没有这个脚本 → 必然没执行
		return true
	}
	// 判据 2：错误串精确匹配「启动期失败」那几类。
	//    ⚠️ 必须是**相等/前缀**匹配，不能用 strings.Contains(err.Error(), ...) ——
	//    包含匹配会把「脚本执行到一半网络断了」这类也匹配进去，方向就反了。
	switch err.Error() {
	case "ERR Error compiling script", // 编译期就失败，脚本体从未开始执行
		"ERR wrong number of arguments": // 参数个数不对，入口就拒了
		return true
	}
	// ⛔ 兜底必须 return false，**不允许 return true**。
	//    i/o timeout / connection reset by peer / context deadline exceeded /
	//    任何没列举到的错误 → 一律保留占位。
	return false
}
```

⚠️ **为什么必须是黑名单**（这是本段最关键的一句）：
白名单 + `default: return true` 的写法下，**任何没预料到的错误都会释放占位** ——
而「没预料到」恰恰是最危险的一类（未来的库版本、新的错误包装）。
黑名单 + `default: return false` 下，**漏判的代价只是少卖一件**（可对账、可补偿），
**误判的代价是超卖一件**（不可逆）。⚠️ 两种错误的代价不对称，所以默认值必须偏保守。

⚠️ **逐处标注（铁律：跑不了的要在正文里标）**：
- ⚠️ **`isScriptNotRun` 的两个判据都是未实测**：本机**没有构造过**「脚本已执行但确认包丢失」，
  也没有逐一验证过 Redis 客户端在 `NOSCRIPT` / 编译错 / 超时三种情况下返回的具体错误值。
  上面的错误串是**按文档与常见实现写的示意**，落地前必须先用真实客户端跑一遍打印 `err` 确认。
- ⚠️ **`redis.ErrScriptNotExists` 这个哨兵错误未实测**：不同客户端版本是否导出、
  是否被 `errors.Is` 识别，都要验。
- 已实测的只有「`left < 0` 那个 `Del` 的语义」——它不依赖本函数。

### 第二段：异步入队（入队必须快）

```go
// 用 JetStream 的 PublishAsync 异步入队
func Enqueue(ctx context.Context, js jetstream.JetStream, order Order) error {
	payload, _ := json.Marshal(order)
	// ⚠️ 上面那个读数是**10000 条批量入队**的（1.4 的 ③），**单条调用拿不到这个收益** ——
	//    它来自批量对 fsync 的摊薄，不是异步本身。
	//    这里用 PublishAsync 的唯一理由是**不阻塞请求方**（请求路径上不等落盘）。
	//    批量场景才用 <-js.PublishAsyncComplete() 等整批落盘（那是 ③ 的读数来源）。
	f, err := js.PublishAsync(subjectOrderCreated, payload)
	if err != nil {
		return err // 只有「入队调用本身」的失败会走这里
	}
	// ⭐ 关键：`f` 是**落盘确认的句柄**，丢掉它 = 丢消息且**无任何信号**。
	//    生产里必须二选一：
	//      ① 注册回调/挂指标（下面示范 select 的写法，骨架里为省篇幅只留形状）；
	//      ② 或干脆同步 Publish 等确认（代价：入队掉到几百条/秒，削峰失败）。
	//    ⚠️ 只 return err 的写法会让「入队成功但落盘失败」静默消失，
	//    而这一段代码整体已经在做「可能丢」的取舍 —— 丢要有信号，否则对账都无从下手。
	go func() {
		select {
		case <-f.Ok():
		case e := <-f.Err():
			log.Printf("order enqueue failed: %v", e) // 兜底：告警 + 1.7 对账捞出
		}
	}()
	return nil
}
```

⚠️ 这里的取舍要写进注释：**异步入队 = 用"可能重投 / 可能丢"换请求路径不阻塞**，
所以消费者**必须幂等**（下一段就是它）。⚠️ **单条异步入队并不提升吞吐** ——
真正的吞吐收益只在批量形态上（1.4 的 ③）；如果业务不能容忍重投或丢失，就退回同步 `Publish` 加确认 ——
但要清楚：**同步意味着入队速率掉到几百条/秒，削峰会失败**（1.4 的 ②）。

### 第三段：消费落库 + 幂等

```go
func Consume(ctx context.Context, msg jetstream.Msg, db *sql.DB) error {
	var o Order
	if err := json.Unmarshal(msg.Data(), &o); err != nil {
		// 脏消息**显式 Ack 掉**：return nil 只是不报错，JetStream 照样按
		// MaxDeliver 重投，N 次后才进 DLQ —— 那是「有限次重投」不是「丢弃」。
		// 想保留重投机会就 return err（并把 MaxDeliver 设小）；这里选直接丢弃。
		return msg.Term() // Term = 确认并停止重投，不再进 DLQ
	}
	// ⚠️ 示意（未单独实测）：幂等靠「唯一索引 + INSERT IGNORE」——
	//    重投、重复提交都靠它兜住；真正的扣减在下面那条条件 UPDATE 上
	res, err := db.ExecContext(ctx, `
		INSERT IGNORE INTO seckill_order (order_no, user_id, sku_id, status, created_at)
		VALUES (?, ?, ?, 'PENDING_PAY', NOW())`, o.OrderNo, o.UserID, o.SKU)
	if err != nil {
		return err
	}
	if n, _ := res.RowsAffected(); n == 0 {
		// 已经处理过（重复投递），确认掉即可 —— 不要重复扣任何东西
		return msg.Ack()
	}
	// 真正的扣减：让数据库自己判断库存够不够（1.5 的 ③）
	ures, err := db.ExecContext(ctx, `
		UPDATE sku_stock SET stock = stock - 1
		WHERE sku_id = ? AND stock > 0`, o.SKU)
	if err != nil {
		return err
	}
	// ⭐ 必须看 RowsAffected（本机实测，见下）：**err 为 nil 不代表扣成功**。
	//    DB 侧 stock 被另一个活动扣成 0 时，这条 UPDATE 匹配不到行、
	//    **影响 0 行但不报错** —— 只判 err 就会 Ack 掉这条消息，
	//    订单已落库、库存永远没扣，超卖一个身位。
	if n, _ := ures.RowsAffected(); n == 0 {
		// 不Ack：让这条**再被投递一次**。⚠️ 但**下一跳就会被确认掉、消息不留痕** ——
		//    重投时 `INSERT IGNORE` 必然 n==0（订单已落库）→ 命中上面那个分支
		//    直接 `return msg.Ack()`，`UPDATE` 再也不会执行。
		//    实测（见下方读数）：5 条不 Ack 的消息重投一遍 → **5 条全被 Ack、0 条补扣**。
		// ⛔ 所以**不要指望重投能自愈，也不要指望 MQ 侧留下线索**：
		//    重投不产生 DLQ 记录、消息被确认后就没了，**补偿的唯一证据只在 DB 侧**
		//    （订单在、`sku_stock` 未扣）。对账必须**从订单表出发**，
		//    拿订单与库存的差集，而不是去 MQ 那边捞消息。
		// 这段只保证「不静默丢」，真正的补偿落点是 1.7 的对账 + 告警。
		return errors.New("扣库存影响 0 行：订单已落库，等待对账补偿")
	}
	return msg.Ack()
}
```

⚠️ **这段的 `RowsAffected` 不是"保险起见"，是本机实测到的真实故障**（MySQL 8.0.46，
`stock` 被另一活动扣成 0 后，本活动消费者积压 5 条消息）：

```text
=== M3 DB 侧 stock 被另一活动扣成 0 后，本活动消费者的条件 UPDATE 影响 0 行===
  只判 err（文档原骨架）：积压 5 条 → 确认掉 5 条；订单表 5 条；stock 0→0
  ⛔ 5 条订单已落库但 stock 一条都没扣 —— 且消息被确认掉，永远不会重投（超卖一个身位）
  判 RowsAffected（修法）：积压 5 条 → 确认掉 0 条、不 Ack 5 条；订单表 5 条；stock 0→0
  把这 5 条重投一遍：确认掉 5 条（走INSERT IGNORE 的 n==0 分支直接 Ack）
  ⛔ 补扣成功的条数 = 0 —— stock 仍是 0。重投**不会自愈**，只多绕一圈后被静默 Ack
  → 补偿落点只能在 1.7 的对账：捞出「订单已落库但 sku_stock 未扣」，人工确认后补扣或撤单
```

⭐ **这组读数要同时说明两件事**，缺一件就变成另一个错误结论：
① 不判 `RowsAffected` → 消息被静默确认，**超卖一个身位**；
② 判了 `RowsAffected` 不 Ack 也**不等于修好了** —— 重投会走 `n == 0` 分支被 Ack 掉，
**补扣不会发生**、而且**消息不留痕**（不进 DLQ、MQ 侧无线索）。
真正的自愈需要订单状态机（`PENDING_PAY` → 扣成功才置 `STOCK_OK`），本骨架没做到，
所以**只能把不一致交给对账，且对账要从订单表出发**（见上面注释）。

⭐ 三段连起来的顺序就是完整链路：
**Lua 预扣（挡住 99% 的请求）→ 入队（17ms 吸走洪峰）→ 消费落库（按下游节奏慢慢做）**，
每一步都在前面那节有对应的实测数据支撑。

## 延伸追问

- **为什么不直接用数据库扛？** →
  1.5 的 ③ 给了答案：单行 `UPDATE` 的正确写法在本机只有 **833 次/秒**，
  因为同一行的行锁必须串行。数据库不是慢在"处理能力"，而是慢在"**同一行**"。
- **Redis 挂了怎么办？** →
  两条路：① 库存同步到 DB，Redis 挂了直接拒绝（**降级到底**，宁可少卖不可超卖）；
  ② 用本地方案兜底（单机令牌式预扣）。⭐ 关键是**不能在降级时放开超卖**，
  参考 [多副本共享状态.md](../../分布式/服务治理/多副本共享状态.md) 的「退回本地不等于 fail-open」。
- **怎么保证"一人一单"不被并发穿透？** →
  服务层判重会被并发穿透（两个请求同时通过检查），
  **必须落到数据库唯一索引** `uk(user_id, sku_id)` 上 —— 那是唯一不会骗人的一层。
- **Redis 预扣的库存和 DB 的库存对不上怎么办？** →
  这是**最终一致**的必然现象，所以**必须有对账**（1.7）。
  对账口径：`Redis 剩余 + 已下单未支付占用量 == DB 库存`，对不上先**告警不自动改**。
- **分段库存分多少段合适？** →
  见 1.5 的段数扫描：**16~64 段**收益已经拿满（重试降到 10 次以内），
  256 段之后耗时反而上升（1024 段 37~44ms）。分段数要跟着**分片数**走，不是越大越好。
- **消息队列选 Kafka 还是 NATS？** →
  秒杀要的是「**高吞吐入队 + 可重放 + 幂等消费**」，两者都能做；
  选型要点与对照见 [消息队列选型.md](../../../03-数据与中间件/中间件/消息队列/消息队列选型.md)，
  幂等与重投语义见 [Kafka.md](../../../03-数据与中间件/中间件/消息队列/Kafka.md)。
- **为什么本机实测的耗时看着不快？** →
  本机是 **Docker Desktop（WSL2）+ 端口映射**的单机环境，
  网络与 IO 开销比真实生产高一个量级；所以本篇的读数只用来**对比不同写法的数量级关系**，
  不作为绝对性能指标（时序类数字都给了 3 轮范围）。
