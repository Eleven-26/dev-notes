# 秒杀系统

> 本目录收**秒杀系统**这道场景题：一篇**总体设计** + 一篇可运行骨架 + 五篇子系统篇 + 一篇存储横切篇。
> 本篇是目录导读，只给「这个系统有哪几个核心问题、有哪些零件、怎么读」三件事，
> 每个问题的解法在零件篇里；本篇不重述具体方案。
>
> 内容整理自个人学习笔记，并参考《大型网站技术架构：核心原理与案例分析》（李智慧）的伸缩性与可用性章节；参考资料与原始素材见 [素材清单](../../../素材清单.md)。
> **落地实现**：各篇实验全部在本机 Docker 环境跑通（Redis 7.4.11 / MySQL 8.0.46 / NATS 2.10 JetStream），
> 代码为 Go；正文所有 `text` 块都是本机真实运行结果（实验规模见每节标注）。

## 一、这个系统有哪几个核心问题？

**本节要点**：秒杀题**不考"你能堆多少中间件"**，考的是「**每一步在挡什么**」。七个问题依次排开，就是一条链上要过的关。

| # | 问题 | 一句话 |
|---|---|---|
| ① | **瞬时高并发** | 峰值是均值的几百倍，且 99% 的请求注定失败 —— 系统不能跟着它们一起倒 |
| ② | **库存扣减** | 共享可变量的原子性：「读 → 判断 → 写」这三步在并发下**不是原子的** |
| ③ | **防超卖** | 唯一一个"**代码看起来完全正确、结果却是错的**"的问题 |
| ④ | **限流** | 按用户优先、IP 兜底 —— 别一刀切按 IP（NAT 后面是一整栋楼） |
| ⑤ | **队列削峰** | ⚠️「用了消息队列」≠「削峰成功」：入队吞吐必须远大于下游 |
| ⑥ | **缓存** | 读的那一侧：热点商品与库存的静态化 / 预热 / 防击穿 / 缓存与 DB 同步 |
| ⑦ | **异步下单与兜底** | 入队 → 消费落库 + 幂等 + 对账；抢到了没付款怎么安全回收 |

⭐ 这七条**不是并列的选项**，而是**一条链上依次要过的关**：流量先被限流挡掉大部分（①④）→ 剩下的进 Redis 做原子扣减（②③）→ 抢到的异步入队（⑤⑦）→ 落库与对账保最终一致 → 而缓存（⑥）贯穿整条链，是"读"的那一侧。

⭐ 另有一条**扩展**（优惠券 / 红包发放）不在上面这七步里 —— 它是「同一批手段（原子判定 + 唯一索引 + 异步）用在另一种发放场景上」，券稀缺的是**份数**、红包稀缺的是**金额**；为什么单列，见 [总体设计.md](总体设计.md) 第一节的说明。

![秒杀全链路：接入限流到兜底的五道关，以及每道关的本机实测读数](images/秒杀全链路七步推导.svg)

图怎么读：五道关从上到下依次排开，就是「依次削掉注定失败的请求」，每一格都写着**它在挡什么**和自己的读数（口径：1000 库存 / 5000~10000 并发，本机实测）。① 接入限流按「用户 ID 优先、IP 兜底」，别一刀切按 IP——NAT 后面是一整栋楼；② 库存扣减用 Redis Lua 把「读-判-写」压进一次服务端执行，对照读数是 Lua 成功 1000 / 库存 0，而「GET 检查 → DECR」两步法成功 5000 / 库存 -4000；③ 削峰入队改异步，同步约 625 条/秒 vs 异步 71949 条/秒；④ 消费落库靠唯一索引幂等 + 带条件 UPDATE，单行 UPDATE 上限约 833 次/秒，所以同一行必须串行；⑤ 兜底是超时回收 + 对账，从订单表出发捞差集。

```text

     ↑              ↑                  ↑                ↑
 总体设计3.3   库存系统设计.md      秒杀骨架.md      订单系统设计.md

```

```text
① 总体设计.md        ← 总体设计：整体形态 / 核心取舍 / 一次秒杀走哪几步（含四组实测对照）
```

## 延伸追问

- **为什么不直接用数据库扛？** → 见 [总体设计.md](总体设计.md) 的 2.3：单行 `UPDATE` 的正确写法在本机只有 **833 次/秒**，因为同一行的行锁必须串行 —— 数据库不是慢在"处理能力"，而是慢在"**同一行**"。
- **Redis 挂了怎么办？** → ① 库存同步到 DB，Redis 挂了直接拒绝（**降级到底**，宁可少卖不可超卖）；② 用本地方案兜底。⭐ 关键是**降级时不能放开超卖**，见 [多副本共享状态.md](../../分布式/稳定性/多副本共享状态.md) 的「退回本地不等于 fail-open」。
- **这套笔记有实测数字吗？** → 有，且都在本机 Docker 环境跑通（Redis 7.4.11 / MySQL 8.0.46 / NATS 2.10 JetStream）。⚠️ 但本机是 **Docker Desktop（WSL2）+ 端口映射**的单机环境，网络与 IO 开销比真实生产高一个量级，所以读数只用来**对比不同写法的数量级关系**，不作绝对性能指标（时序类数字都给了 3 轮范围）。
- **读完能回答的最小闭环是什么？** → "一个人点下秒杀按钮，到订单落库、库存归位、账目对上"：限流 → 原子预扣 → 异步入队 → 消费落库（幂等 + 条件 UPDATE）→ 超时回收 / 对账 —— 每一环由哪篇负责，见 [总体设计.md](总体设计.md) 的第四节。
- **为什么不把五个子系统合成一篇？** → 它们各自是独立的知识点（状态机 / 扣减一致性 / 对账 / 缓存 / 券发放），合成一篇会变成"什么都讲一点、都讲不深"；本目录只保留总体设计 + 骨架 + 存储全景三篇横切视角。
