## 一、详情页是秒杀链路的「读的另一半」

**本节要点**：前面几篇（[库存](库存系统设计.md) / [订单](订单系统设计.md) / [支付](支付系统设计.md) / [优惠券](优惠券系统设计.md)）
讲的都是**写**：扣减、落库、对账，每个字都必须精确。
详情页是**读**，而读侧有一条完全不同的判据 —— 这一节先把这条判据立起来。

### 1.1 一次秒杀，读比写多几个数量级

秒杀 1000 件商品，可能有 **100 万人**在开抢前刷详情页。于是：

| | 量级 | 特点 |
|---|---|---|
| **读**（详情页） | 百万级 QPS，持续几分钟 | 内容几乎不变、允许陈旧 |
| **写**（库存扣减） | 千级，集中在几秒内 | 必须精确、零和 |

⭐ 两者的关键差别不是「多少」，而是「**错了会怎样**」：

- 写错了（超卖）→ **资损**，事后无法挽回；
- 读错了（详情页显示 3 秒前的价格）→ **没人发现**，甚至根本不该被发现。

所以这两条链路的手段完全不同：**写侧要原子、要锁、要对账；读侧要快、要挡、要能陈旧**。
把写侧那套（加锁、强一致）搬到读侧，会做出一个又慢又贵的详情页。

### 1.2 读侧的目标函数：把请求挡在越靠前越好

一页详情页的读，成本从低到高排成一条链：

```text
浏览器缓存 / CDN  →  Nginx 静态文件  →  应用进程内（L1 本地缓存）  →  Redis（L2）  →  MySQL（L3）
       ~0                 ~50µs               ~20ns                    ~200µs           ~1ms
```

⭐ 这条链上**每往左挪一层，成本就差一个数量级**。
本篇后面测的每一组数据，本质上都是在回答同一个问题：**这一层能挡掉多少？**

### 1.3 与通用缓存篇的分工

⚠️ 缓存击穿、穿透、雪崩这些**概念**与**通用解法**在
[缓存问题与方案.md](../../../03-数据与中间件/数据存储/缓存/缓存问题与方案.md) 与
[缓存选型与容量.md](../../../03-数据与中间件/数据存储/缓存/缓存选型与容量.md) 里已经讲透了
（含多 key 打散、本地缓存 TTL、bigcache + Pub/Sub 的实现）。

本篇**不重复那些概念**，只补两件它们没有的东西：

1. **每层到底省多少**的实测读数（那两篇讲的是"怎么选"，没有对照量）；
2. **在秒杀详情页这个具体场景下**的取舍 —— 哪部分能静态化、本地缓存能容忍多久的陈旧。

## 二、多级缓存：L1 本地 / L2 Redis / L3 DB 到底差多少？

**本节要点**：多级缓存的价值从来不是"更快"这么笼统 —— 它是**减少了下游被访问的次数**。
这一节用「打 Redis 次数」和「打 DB 次数」这两个**确定量**，量出每一层挡住了什么。

### 2.1 三组对照

统一参数：**20000 次读、200 并发**，热点集中在 100 个商品上（读 1~100 号）。

```text
=== ① 多级缓存：L1 本地 / L2 Redis / L3 DB，三种层次到底差多少 ===
    口径：20000 次读、200 并发，热点集中在 100 个商品上（每次随机读 1~100）
    策略                             总耗时          本地命中         打 Redis      打 DB
    A 只用 L2（Redis）                 10.619s      0            20000        323
    B L1(本地 1s) + L2(Redis)        2.778s       19403        597          433
    C L1(3s) + L2 + singleflight   501ms        19181        101          100
```

⭐ 先看**确定量**（这三列的读数是稳定的）：

| 策略 | 打 Redis | 打 DB | 说明 |
|---|---|---|---|
| A 只用 Redis | **20000**（一次不落） | 323 | 每次读都是一次网络往返 |
| B **加 L1（TTL 1s）** | **597**（降了 33 倍） | 433 | 98% 的读被挡在进程内 |
| C **加 singleflight** | **101**（再降 6 倍） | **100** | 回源也被合并了：100 = 商品种类数 |

⚠️ **总耗时这一列不要当结论**：同一份代码在本机跑过 **2.99s / 3.43s / 10.62s** ——
因为 A 组是 200 个并发抢同一个 Redis，排队时间不稳定。
所以这一节主张的是**「打下游的次数被降下来」**，不是"快了几倍"。

### 2.2 为什么"本地缓存"是最划算的一层

B 组和 A 组的差别只有一行代码：读之前先看一眼进程内的 map。

```go
if it, ok := l1.get(id); ok {   // TTL 未到，直接返回
    return it
}
```

但这一行让 **Redis 的访问量从 20000 降到 597**。原因是读的分布：

- 详情页是典型的**长尾 + 热点** —— 100 个商品承接了全部 20000 次读；
- 一个商品在 1 秒内被读几十次，**第 2 次以后就没必要再去 Redis 问了**。

⭐ 这就是下一节（击穿）要用的同一个工具，只是用法不同：
- **平时**用它挡掉重复读（本节）；
- **热点 key 过期那一下**用它合并回源（第三节的 singleflight / 逻辑过期）。

### 2.3 代价预告：本地缓存买到的是"陈旧"

⚠️ L1 缓存在**进程内**，别的进程**删不掉它**。
所以它的 TTL 直接等于「**这个页面的数据最多能陈旧多久**」——
第五节会把这条量化（0ms / 199ms / 999ms / 3954ms）。

⭐ 一句话判据：**本地缓存只适合「允许秒级陈旧」的数据**（标题、图片、描述、参数表），
**不适合库存、价格、开抢状态**（那些必须走 Redis / DB 的实时读，或者干脆静态化里留占位符）。

## 三、缓存击穿：热点 key 过期那一瞬间怎么办？

**本节要点**：击穿的破坏力不在"每次都慢"，而在**"某一个瞬间所有请求一起去打库"**。
这一节用「打 DB 次数」量出三种解法各自的挡法，并说清**它们的前提条件**。

### 3.1 三种方案对照

构造：先让热点 key（`item:7`）**刚好失效**，然后放 **1000 个并发请求**同时读它。

```text
=== ② 缓存击穿：热点 key 过期的瞬间，1000 个请求同时到 ===
    策略                                   打 DB       总耗时          最慢一次
    A 无保护（没命中就回源）                        975        1.569s       1.557s
    B singleflight 合并同 key               1          22ms         21ms
    C 逻辑过期（key 不物理过期）                    1          563ms        557ms
```

| 方案 | 打 DB | 代价 | 适用 |
|---|---|---|---|
| **A 无保护** | **975** | 数据库在 1.5 秒内被同一个 key 打 975 次 | 只能是"没做过治理"的现状 |
| **B singleflight** | **1** | 同 key 的并发请求要**等**（最慢 21ms，但总量只要 22ms） | 大多数场景，代码改动最小 |
| **C 逻辑过期** | **1** | 读请求**从不等库**（拿旧值返回），只让一个人后台刷新 | 热点 + 能接受秒级陈旧 |

⭐ B 与 C 的差别值得说清：**B 让请求等、C 让请求不等**。

- B 组总耗时 **22ms**：1000 个请求被合并成 1 次查询后**一起拿到结果**——快，但那 1000 个请求都阻塞了一下；
- C 组总耗时 **563ms**：因为读请求拿的是**旧值**（不用等），耗时的来源是那 1000 个请求各自还去
  `GET item:7:expire` 判断了一次是否过期 —— **多一次 Redis 往返换"从不等库"**。

### 3.2 ⭐ 逻辑过期的前提：key 必须永不物理过期

这一节最初做实验时**做错了**，而犯错的方式恰好就是它的前提。

第一版的构造是：`DEL item:7` → 放 1000 并发请求，然后在读的时候判断"逻辑是否过期"。
结果是 **C 组打库 990 次** —— 和 A 组几乎一样。

原因：**`DEL` 之后 key 真的不存在了**，读请求走的是"缓存里没有 → 同步回源"这条分支，
于是 990 个请求在第一个请求把值写回 Redis 之前，全都去打了库。

⭐ 逻辑过期的正确形态是这样（本机最终实测）：

```text
预热时：SET item:7 <json>               ← 不设 TTL（永不物理过期）
        SET item:7:expire <过期时间戳>    ← 过期信息**放在值外面**
读取时：GET item:7 → 一定命中（key 永远在）
        GET item:7:expire → 发现已过期 → 只让一个人去后台刷新
        请求本身**照常拿旧值返回**，绝不等库
```

⚠️ 所以逻辑过期与"给 key 设 TTL"是**互斥的两种做法**：

| 做法 | key 会不会物理消失 | 过期后第一个请求的遭遇 |
|---|---|---|
| 设 TTL | 会（到点就没了） | 回源（若没保护 → 击穿） |
| 逻辑过期 | **不会** | 拿旧值返回，后台异步刷新 |

⭐ 一句话：**逻辑过期是用"这份数据可能永远不被再刷新"的风险，换"永不等库"**。
所以它必须配一个**兜底**（比如后台定时任务或版本号），否则一旦没人来读，这份数据就永远停在旧值上。

### 3.3 怎么选

| 判据 | 选 |
|---|---|
| 大多数业务、想让改动最小 | **singleflight**（一行包装，等价于"同 key 只查一次"） |
| 极热点、且业务能接受秒级陈旧 | **逻辑过期**（读请求完全不等库） |
| 数据绝对不能陈旧（如库存） | 两个都别用 —— **它本来就不该缓存** |

## 四、缓存穿透：不存在的商品为什么每次都打库？

**本节要点**：穿透与击穿的区别是 —— 击穿是"**有**这个数据，只是缓存没命中"；
穿透是"**根本没有**这个数据"，所以**缓存永远加载不上**。

### 4.1 三种方案对照

构造：反复查一个**数据库里也不存在**的商品（`id=999999`），共 1000 次。

```text
=== ③ 缓存穿透：反复查一个「根本不存在」的商品（id=999999），共 1000 次 ===
    策略                                       打 DB       打 Redis
    A 无保护（查不到就不缓存）                           1000       1000
    B 空值缓存（哨兵值 + 短 TTL）                      1          1000
    C 布隆过滤器前置（bitmap + 3 哈希）                 0          0
```

| 方案 | 打 DB | 打 Redis | 代价 |
|---|---|---|---|
| **A 无保护** | **1000**（每次都打） | 1000 | 缓存对不存在的 key 完全失效 |
| **B 空值缓存** | **1** | 1000 | 要占内存（哪怕值是空的）；还要设短 TTL 防堆积 |
| **C 布隆前置** | **0** | **0** | 有误判（假阳性）；需要预热与维护位图 |

⭐ C 组连 Redis 的 `GET` 都省了（打 Redis **0** 次）：布隆过滤器在**应用侧**判断，
说"一定不在"就直接返回 404，**连一次网络往返都不需要**。

### 4.2 ⚠️ 空值缓存的坑：哨兵值必须能被"读出来是空"，而不是"读不出来"

这一节的 B 组**最初也是错的**：打库 1000 次，看起来和 A 组一样。

原因藏在读取端 —— 最初的实现是：

```go
b, err := rdb.Get(ctx, key).Bytes()
if err != nil {
    return Item{}, false        // 未命中
}
var it Item
if json.Unmarshal(b, &it) != nil {
    return Item{}, false        // ⚠️ 反序列化失败 → 也当成"未命中"
}
```

写入端用了 `"NULL"` 当哨兵值 —— 它不是合法 JSON，`Unmarshal` 直接失败，
于是**明明命中了空值，却被当成未命中**，每次照样打库。

⭐ 正确的读取端必须能区分**三种状态**：

```go
type CacheResult int

const (
    Miss  CacheResult = iota // 没缓存过 → 要回源
    Null                     // 缓存过，库里确实没有 → 直接返回 404
    Hit                      // 缓存过，有数据
)

func get(id int) (Item, CacheResult) {
    b, err := rdb.Get(ctx, keyOf(id)).Bytes()
    if err != nil {
        return Item{}, Miss
    }
    if string(b) == "NULL" {        // ⭐ 先认哨兵
        return Item{}, Null
    }
    var it Item
    if json.Unmarshal(b, &it) != nil {
        return Item{}, Miss
    }
    return it, Hit
}
```

⚠️ 这个坑很隐蔽：**写入端明明缓存了，读取端却认不出来** ——
现象不是报错，而是"缓存好像没起作用"。

### 4.3 布隆的假阳性与兜底

布隆过滤器说"**可能在**"时其实可能不在（假阳性），所以：

- 「一定不在」→ 直接返回，**可信**；
- 「可能在」→ 还是要走正常读路径（查缓存 → 查库）。

⭐ 所以生产上两者**不是二选一**：

```text
布隆过滤器（挡住绝大多数不存在的 id，连 Redis 都不打）
    ↓ 说"可能在"
缓存（含空值缓存）→ 库
```

另一点：**布隆过滤器不能删元素**。商品下架后位图里那几位还是 1，
所以要么接受（多一次无效查询），要么用**可删除的变体**（计数布隆），
要么定期重建（见 [位图与布隆过滤器.md](../../../02-计算机基础/数据结构/高级数据结构/位图与布隆过滤器.md)）。

## 五、本地缓存 TTL：Redis 压力与「多久能看到新数据」怎么权衡？

**本节要点**：第二、三节都在说本地缓存好，这一节说它的**价钱** ——
本地缓存的 TTL 就是「数据最多能陈旧多久」，而这两件事是**同一个旋钮**。

### 5.1 实测：一个旋钮，两个方向

构造：固定 **1000 QPS 持续 8 秒**（贴近详情页的真实读速率），
在第 1 秒把商品 1 的价格改掉（**改 DB + 删 Redis，但动不了本地缓存**），
然后量两件事：① Redis 被访问了多少次；② 多久之后请求能读到**新价格**。

```text
=== ④ 本地缓存 TTL：Redis 压力与「改了数据多久能看到」（固定 1000 QPS × 8 秒）===
    L1 TTL         打 Redis      看到新值需等           打 DB
    无 L1           2678         5 ms             1
    200ms          39           199 ms           1
    1s             8            999 ms           1
    5s             2            3954 ms          1
```

⭐ 这张表是本篇最有用的一行数据 —— **它是同一条曲线的两个方向**：

| L1 TTL | 每秒打 Redis | 最长陈旧时间 | 适合的数据 |
|---|---|---|---|
| **无 L1** | 2678 | **5 ms** | 价格、库存、开抢状态 |
| **200ms** | 39 | 199 ms | 变化较快但能容忍 0.2s 的（销量、评价数） |
| **1s** | 8 | 999 ms | 标题、主图 URL |
| **5s** | 2 | 3954 ms | 详情描述、参数表、店铺信息 |

⚠️ 注意「看到新值需等」这一列几乎**等于 TTL**（199ms ≈ 200ms、999ms ≈ 1s、3954ms ≈ 4s）——
说明本地缓存的一致性问题**是必然而不是偶然**：只要 TTL 是 1 秒，
改完数据后的 1 秒内，读请求一定拿到旧值。这不是 bug，是**你自己选的**。

⭐ 「无 L1」那行的 5ms 说明另一件事：**删了 Redis 之后，新值几乎立刻可见** ——
所以「DB + 删缓存」这套组合本身是对的（见 [库存系统设计.md](库存系统设计.md) 第三节），
出问题的只是**进程内那一层删不掉**。

### 5.2 两种让本地缓存"能被删掉"的做法

| 做法 | 原理 | 代价 |
|---|---|---|
| **Pub/Sub 广播失效** | 一个实例改完，往频道发一条"失效 item:7"，其他实例收到就删本地 | 广播可能丢（Redis Pub/Sub 不保证送达）→ 仍有不一致窗口 |
| **版本号 / 短 TTL 兜底** | 值里带版本，读的时候比对；或干脆把 TTL 压到几百毫秒 | 要么多一次判断，要么退化成"几乎没缓存" |

⭐ 实现细节见 [缓存选型与容量.md](../../../03-数据与中间件/数据存储/缓存/缓存选型与容量.md)（bigcache + Pub/Sub 那一段），
本篇只给结论：**广播失效把不一致窗口从"TTL"压到"广播延迟"，但不能压到零**。

## 六、静态化与 CDN：详情页里哪些部分可以「变成文件」？

**本节要点**：前面五节都在优化"**怎么读得快**"。这一节问一个更彻底的问题：
**这个请求有必要到应用里来吗？**

### 6.1 静态化 vs 动态渲染

构造：同一个详情页，两种实现各跑 **3 万次请求（50 并发）**。
为了测出差别，这一组**不走网络**（消除 HTTP 往返这个共同开销），直接调渲染函数。

```text
=== ⑤ 静态化 vs 动态渲染：同一个详情页（50 并发 × 3 万次，直接调 handler）===
    口径：不走网络（消除 HTTP 往返这个共同开销），测的是**每次请求要做的渲染工作**

    动态渲染（查缓存 + 拼 HTML）           总耗时 9593922600   ns  单次 ≈ 319797   ns  打 Redis 30000（校验和 7920000）
    静态化（预生成字节直出）                 总耗时 1521700      ns  单次 ≈ 50       ns  打 Redis 0（校验和 7920000）
```

| 实现 | 单次耗时 | 打 Redis | 每次请求做的事 |
|---|---|---|---|
| **动态渲染** | **约 320µs** | 30000 | 查一次 Redis + 拼 HTML |
| **静态化** | **约 50ns** | **0** | 返回一段已有的字节 |

⚠️ **别把这个倍数读成「模板渲染慢 6400 倍」**：动态那 320µs 里，
绝大部分是**一次 Redis 往返 + 50 并发下的排队**（第三节、第四节测过：一次 Redis 往返约 200µs）。
静态化真正去掉的是**请求路径上的 I/O**，不是"渲染逻辑"。

⭐ 这也解释了静态化为什么值钱：**它把 I/O 从请求路径上整个搬走了**。
搬走之后，请求的成本从「一次网络往返」变成「一次内存拷贝」——**三个数量级的差别**。

### 6.2 判据：怎么切「静态」与「动态」

一页详情页里，哪些能静态化？判据只有一条：

> **「这次请求读到的值，下一次请求会不会不同？」** —— 不会，就静态化。

按这条切下去，详情页自然分成两块：

| 部分 | 内容 | 说明 |
|---|---|---|
| **可静态化** | 标题 / 主图 / 描述 / 参数表 / 店铺信息 | 秒杀期间**根本不变**；生成一次，推到 CDN |
| **必须动态** | 剩余库存 / 是否开抢 / 当前价格 / 用户是否能买 | 每笔都在变；且**每个用户看到的不一样** |

⭐ 关键的工程做法是 **动静分离**：

```text
静态骨架（CDN 上的一份 HTML，所有用户共用）
    + 一小段动态数据（AJAX / ESI / 边缘计算拉取）
    = 用户看到的完整详情页
```

⚠️ 不要试图把整页静态化 —— 库存数字一旦进了静态页，CDN 缓存一分钟就是**灾难**
（用户看到有货、点进去发现抢完了）。**凡是"秒杀期间会变"的字段，一律不能进静态页。**

### 6.3 CDN 在这一层做了什么

CDN 的角色可以一句话说清：**把静态化那部分的请求，从你的机房移到离用户最近的边缘节点**。

- 它解决的是**地理距离**（北京用户不必连到广州的机房）；
- 顺带解决了**回源量**（100 万次请求里，可能只有 1 次落到你的源站）。

⚠️ 三条与秒杀特别相关的注意点（本机无法实测，属部署经验）：

1. **秒杀前必须预热**：让 CDN 提前把静态页拉过去，否则开抢瞬间大量请求同时回源 ——
   CDN 只是把你的击穿问题**推迟到了回源那一刻**；
2. **刷新要快**：改了价格 / 活动信息，要让 CDN 立刻失效（各家的"刷新"接口），
   否则用户看到的是上一版页面；
3. **并发回源要收敛**：CDN 节点很多，同时回源时要在源站侧做一次合并
   （和第三节的 singleflight 是同一个思路，只是换到了 CDN 与源站之间）。

## 使用：详情页读链路的 Go 骨架

**本节要点**：把前六节压成三段骨架 —— **多级读**（二、五）、**击穿保护**（三）、
**穿透保护**（四）。三段可以独立启用，也可以叠加。

> ⚠️ 骨架片段（省略了 import、类型定义与错误包装）。
> **多级读**与**哨兵值判断**的逻辑取自本机实测程序（读数见第二、四节）；
> **singleflight + 空值缓存**的组合是按语义补全的示意（未单独实测）。

### 第一段：多级读（L1 本地 → L2 Redis → L3 DB）

```go
type DetailReader struct {
    l1  *localCache          // 进程内，TTL 按数据类型分别设置（第五节）
    rdb *redis.Client
    db  *sql.DB
    sf  singleflight.Group   // 合并同 key 的并发回源
}

func (r *DetailReader) Get(ctx context.Context, id int) (Item, error) {
    // L1：TTL 内的旧值直接用（代价是"最多陈旧 TTL"）
    if it, ok := r.l1.get(id); ok {
        return it, nil
    }
    // L2 + L3：合并同 key 的并发（第三节 B 组：1000 并发 → 打库 1 次）
    v, err, _ := r.sf.Do(fmt.Sprint(id), func() (interface{}, error) {
        it, res, err := r.fromCacheOrDB(ctx, id)
        if err != nil {
            return Item{}, err
        }
        if res == Miss {
            return Item{}, sql.ErrNoRows
        }
        return it, nil
    })
    if err != nil {
        return Item{}, err
    }
    it := v.(Item)
    r.l1.put(id, it)
    return it, nil
}
```

### 第二段：缓存读 + 哨兵值（穿透保护）

```go
func (r *DetailReader) fromCacheOrDB(ctx context.Context, id int) (Item, int, error) {
    b, err := r.rdb.Get(ctx, keyOf(id)).Bytes()
    switch {
    case err == nil && string(b) == nullSentinel:
        // ⭐ 缓存过「空」——库里确实没有，直接短路，不查库
        return Item{}, Null, nil
    case err == nil:
        var it Item
        if json.Unmarshal(b, &it) == nil {
            return it, Hit, nil
        }
    }
    // 真回源
    it, err := r.queryDB(ctx, id)
    if errors.Is(err, sql.ErrNoRows) {
        // ⭐ 不存在的 id 也缓存（短 TTL），否则每次请求都打库
        r.rdb.Set(ctx, keyOf(id), nullSentinel, 60*time.Second)
        return Item{}, Null, nil
    }
    if err != nil {
        return Item{}, Miss, err
    }
    r.rdb.Set(ctx, keyOf(id), mustJSON(it), 10*time.Minute)
    return it, Hit, nil
}
```

### 第三段：静态化 + 动静分离

```go
// 静态骨架：预生成一次，之后所有请求共用同一份字节（第六节）
//go:embed detail_shell.html
var shell []byte

func handleDetail(w http.ResponseWriter, r *http.Request) {
    w.Header().Set("Content-Type", "text/html; charset=utf-8")
    w.Header().Set("Cache-Control", "public, max-age=60") // CDN 可以缓存 60s
    _, _ = w.Write(shell)                                  // 静态部分：一次内存拷贝

    // 动态部分：单独接口拉（前端 AJAX / ESI），或者在 HTML 里留占位符
    // ⚠️ 库存、价格、开抢状态**绝不能**进上面那份 shell
}
```

## 延伸追问

- **本地缓存要不要预热？** →
  要，但**预热的对象是热点而不是全量**：全量预热既慢又占内存，
  而秒杀的热点是可预测的（运营会提前告诉你主推哪几个 SKU）。
  做法：活动前把这几件商品的详情刷进 Redis 与各实例的 L1。

- **L1 的一致性问题有没有"零代价"解法？** →
  没有。**你只能在「一致性窗口」与「下游压力」之间选一个点**（第五节那张表就是这条曲线）。
  想做"零窗口"，就只能放弃 L1（回到每次打 Redis），或者接受 Pub/Sub 广播的**概率性**失效。

- **为什么不用「缓存永不过期 + 定时全量刷新」？** →
  定时刷新会造成**流量尖峰**（所有人同时过期，即雪崩）；
  而且刷新间隔本身就是一个"陈旧窗口"，只是从"TTL"换成了"刷新周期"。
  真正要限制的是**同时回源的数量**（singleflight / 令牌），不是"有没有 TTL"。

- **热 key 除了击穿，还有什么问题？** →
  三个（详见 [缓存问题与方案.md](../../../03-数据与中间件/数据存储/缓存/缓存问题与方案.md) 第二节）：
  ① **单线程阻塞**（Redis 命令排队）；② **网络带宽过载**（大 value × 高频）；
  ③ ⭐ **集群倾斜**（同一个 key 永远落在同一个分片，集群扩容对这个 key 毫无帮助）。
  对应的手段是**多副本打散**（`hot:item:7:0..N` 随机选一个）与**大 value 拆分**。

- **静态化和"前端缓存"是一回事吗？** →
  不是一层。**静态化**是"服务端把渲染结果做成文件"（解决服务端的 CPU / I/O）；
  **前端 / CDN 缓存**是"这个文件在哪一份被复用"（解决网络与回源）。
  两者配合才有完整体验：静态化让文件可以被缓存，CDN 让缓存有意义。

- **`Cache-Control: max-age=60` 在秒杀场景下会不会出问题？** →
  会。⚠️ 60 秒的浏览器缓存意味着**用户可能看到 1 分钟前的活动状态**。
  所以：**静态资源（图片、JS）可以长缓存**，而**动态拉取的那个接口**必须用
  `no-store` 或极短的 `max-age`。别把"整页"和"数据接口"设成同一个缓存策略。
