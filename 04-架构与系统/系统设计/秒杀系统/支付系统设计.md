## 一、幂等：支付回调被重放时，判据为什么是唯一索引而不是"先查后插"？

**本节要点**：支付回调是**天然会被重放**的外部事件 —— 渠道没收到 ack 就重发、用户刷新结果页、MQ 重投。判据只有两条：**唯一索引**与**状态幂等**（带旧状态的 `UPDATE`），都不是"先查一下再决定"。

### 1.1 三类重放来源

- **渠道重试**：我方没在约定时间内回 `SUCCESS`（超时、重启、非 2xx）→ 同一条回调**内容完全相同**地重发，可能连发多次；
- **用户刷新**：结果页 F5 / 回退再进，可能绕过渠道；
- **消息重投**：回调转成 MQ 消息后消费失败重投 —— at-least-once 语义，**至少一次**。

⭐ 共同点是**重放的是"同一件事"**：幂等的目标不是"识别哪条是重放"，而是"**同一件事来多少次，副作用只发生一次**"。

### 1.2 为什么"先查后插"不是判据

"先 `SELECT` → 没有就 `INSERT`"是两次往返，中间就是竞态窗口：两个重放请求可以**都查到"没有"**再**各插一条**。这个洞在兄弟篇 [订单系统设计.md](订单系统设计.md) 2.1 节已用本机读数证明（并发重放 2000 次：先查后插落 87 条、唯一索引恰好 1 条），本篇不重复那张表。

⭐ 一句话：**"我检查过了"不是判据** —— 检查与动作之间隔着时间；判据必须是"**数据库不让我做第二次**"。

### 1.3 两种幂等：插入型与状态型

| 副作用类型 | 例子 | 幂等写法 | 判据 |
|---|---|---|---|
| **插入型** | 落支付流水 / 通知记录 | 唯一索引 + `INSERT IGNORE` | `RowsAffected`：`1` 首次、`0` 重复 |
| **状态型** | 订单 `PENDING_PAY → PAID` | 带旧状态的 `UPDATE ... WHERE status = ?` | `1` 本次生效、`0` 别人已改过 |

### 1.4 关键：状态幂等为什么优于"先查状态"

```sql
UPDATE orders SET status = 'PAID', paid_at = NOW(3)
WHERE order_no = ? AND status = 'PENDING_PAY';
```

`RowsAffected = 0` 的意思是"**这条订单已不在待支付状态**"——可能是上次回调改的（重复回调），也可能是超时关单改的（**迟到回调**）。⚠️ 两种都返回 0，但**处置完全不同**：前者直接 ack，后者要**发起退款**。所以拿到 0 之后**必须再查一次当前状态**，不能一律当"重复"。

⭐ 这与兄弟篇 [订单系统设计.md](订单系统设计.md) 1.3、5.3 节口径一致：**带条件的 UPDATE 只负责"我改到了没有"，不负责解释"为什么没改到"**。行锁与「当前读」原理见 [MVCC与锁.md](../../../03-数据与中间件/数据存储/关系型/MySQL/MVCC与锁.md)。

## 二、异步通知：支付结果靠回调回来，怎么做到不丢、不重、扛住乱序？

**本节要点**：支付结果不靠同步返回，而是渠道**异步回调**。三个硬坑：**不丢**（回调可能永远不来）、**不重**（对方也要幂等）、**乱序**（先收到成功又收到失败）。

### 2.1 为什么不能只看同步返回

| 返回 | 含义 | 能否据此改订单 |
|---|---|---|
| 同步返回 `SUCCESS` | 渠道**受理了** | ❌ 用户可能还没扣款 |
| **异步回调 `SUCCESS`** | 钱**到账** | ✅ 这才是"支付成功"的判据 |
| 主动查单 `SUCCESS` | 钱到账（补回调） | ✅ 与回调等价 |

⭐ 同步返回只用来"跳结果页 / 显示等待中"；**订单状态只由「异步回调 + 主动查单」驱动**。

### 2.2 不丢：回调可能永远不来

| 手段 | 作用 |
|---|---|
| **先落库再处理** | 先**持久化通知原文**（通知流水表）再执行业务 —— 进程崩溃后能重放 |
| **失败要能重试** | 处理失败（DB 抖动）让渠道重发（返回非 2xx）或自己重试 |
| ⭐ **主动查单兜底** | 定时扫"已发起支付、超 N 分钟无回调"的单，**主动去渠道查**补结果 |

⭐ 兜底判据：**"回调没来" ≠ "支付没成功"**，不能把"没收到回调"当成"没付款"。

### 2.3 不重：双方都要幂等

- **我方接回调**要幂等（第一节）：渠道重试时订单状态只改一次；
- **我方发通知**（发货、发券、加积分）时，**对方也要幂等**。

⭐ 做法：发出的通知**带上幂等键**（`order_no` + 事件类型），并在协议里**要求对方幂等**。这就是**最大努力通知**的边界 —— 通知方尽力重试、不保证不重，**不重由接收方兜住**，完整口径见 [分布式事务.md](../../分布式/理论/分布式事务.md)。

### 2.4 乱序：先收到成功，又收到失败

真实渠道的回调**不保证按发生顺序到达**。判据是**本地终态不可回退**，且**以渠道最终状态为准**：

| 到达顺序 | 正确处理 |
|---|---|
| 先 `SUCCESS` 后 `FAILED` | 已 `PAID` 是终态，后面的 `FAILED` 改不动（`WHERE status='PENDING_PAY'` 影响 0 行，1.4） |
| 先 `FAILED` 后 `SUCCESS` | ⚠️ 不能因"失败过"就拒绝成功 —— 以**渠道查单确认的最终结果**为准 |

⭐ **回调的到达顺序不能用来推状态顺序**；顺序依据是**渠道最终状态（查单）+ 本地终态不可回退**。重投与顺序语义见 [Kafka.md](../../../03-数据与中间件/中间件/消息队列/Kafka.md)。

### 2.5 判据

**判据**：改订单为已支付只认**异步回调 / 主动查单**；回调丢了靠**查单兜底**；重复靠第一节幂等；通知下游要**带幂等键并要求对方幂等**；乱序靠**终态不可回退 + 渠道最终状态**。

## 三、重试与退避：为什么"多试几次"反而会把下游打死？

**本节要点**：重试是有代价的 —— 下游越慢、重试越密，越打不动它。判据分两半：**该重试的要退避**，**不该重试的绝不能重试**（尤其非幂等操作）。

### 3.1 实测：固定间隔 vs 指数退避

固定条件：下游约 **500ms** 后恢复。

```text
=== ② 重试策略：下游在 500ms 后恢复，两种退避各打了多少次 ===
  固定间隔 50ms，最多重试 10 次                      请求 11 次  耗时 505ms  → 成功
  指数退避 50/100/200/400/800ms，最多 5 次         请求  5 次  耗时 752ms  → 成功
  ⭐ 两者都在 500ms 附近成功，但无效请求数差一倍以上 —— 退避是在替下游省压力
```

### 3.2 读法

- **固定间隔**：11 次请求、505ms —— 下游还没恢复的那 500ms 里把请求一次次打了出去，大部分是**无效请求**；
- **指数退避**：5 次请求、752ms —— 间隔由短拉长，正好**跨过恢复窗口**，无效请求少了一半以上。

⭐ 两者"成功耗时"接近（505ms vs 752ms），差别全在**无效请求数**：**退避不是让自己更快，是在替下游省压力**。

### 3.3 什么该重试、什么绝不能

| 情况 | 能否重试 | 为什么 |
|---|---|---|
| 连接超时 / 抖动 / 5xx | ✅ | 通常是**瞬时**故障，退避后大概率恢复 |
| 被限流（429） | ✅ **带退避** | 下游在明确说"慢点打" |
| ⭐ **非幂等操作**（没带幂等键的"发起退款"） | ❌ **绝不能盲重试** | 重试会**重复执行副作用** —— 可能退两次款 |
| 4xx 业务失败（余额不足、签名错） | ❌ | 是**逻辑错**不是**瞬时错**，重试一万次也一样 |
| 回调通知失败 | ✅ | 但靠**接收方幂等**兜重复（2.3） |

⭐ 判据记死：**"能不能重试"取决于"重复执行一次安不安全"，不取决于"失败了几次"**；要重试就先给**幂等键**，没有幂等键的只能**告警 + 人工**。

### 3.4 重试要配合熔断与限流

退避只是"把请求打得稀疏"，但下游**彻底挂了**时，再稀疏也是打在一个死物上、还**拖慢自己**（重试占线程 / 连接）。所以重试必须和 [稳定性三件套.md](../../分布式/服务治理/稳定性三件套.md) 的**熔断 / 限流 / 降级**配套：熔断打开后**直接快速失败**。

### 3.5 判据

**判据**：用退避（看**无效请求数** 11 → 5）而非固定间隔；设**上限次数 + 总超时**别无限退避；**非幂等操作绝不盲重试**；熔断打开时**不重试**。

## 四、分布式事务：支付成功之后，订单和库存怎么跟着一致？

**本节要点**：支付成功 → 改订单 → 扣库存 / 回补，跨了支付、订单、库存三个系统。判据是「**本地消息表 + 幂等消费**就够」，只有"必须预留资源"才上 TCC。

### 4.1 不一致会以哪些形态出现

| 断在哪 | 现象 | 后果 |
|---|---|---|
| 支付成功、订单没改 | 订单还挂 `PENDING_PAY` | ⚠️ 超时关单把库存放回 → **钱收了、货卖给别人** |
| 订单改了、库存没扣 | 库存留着但货已卖出 | **少卖 / 超卖**（取决于回补时机） |
| 回调重复、库存扣两次 | 一次支付扣两件库存 | **超卖** |

### 4.2 为什么"本地消息表 + 幂等消费"够用

支付链路的**天然优势**：起点是**外部回调**，本身就是"可重放的事件"。链路设计成：**幂等落支付流水（同库事务）→ 同事务写本地消息表 → 异步投递 → 下游幂等消费**。前两步在**同一个数据库事务**里（要么都成功、要么都没有），投递失败重投、消费靠幂等键去重。

⭐ 本地消息表把"跨系统一致"降级成"**同库一致 + 可靠投递 + 幂等消费**" —— 这三样都是单机能保证的。完整对照见 [分布式事务.md](../../分布式/理论/分布式事务.md)。

### 4.3 什么时候才要 TCC

TCC（Try / Confirm / Cancel）要每个参与者都实现三段，代价高，**只有"资源必须预留、补偿逻辑清晰"时才值**：

| 场景 | 要不要 TCC | 理由 |
|---|---|---|
| 支付 → 订单 → 库存（本篇） | ❌ 不要 | 本地消息表 + 幂等消费够用，链路本身可重放 |
| 跨账户转账"先冻结" | ✅ 要 | 需要预留资金资源，冲正逻辑清晰 |
| 渠道退款 | ❌ 一般不要 | ⚠️ **未实测**：主流渠道自带退款接口与补偿，通常不自建 TCC |

### 4.4 判据

**判据**：支付链路用**本地消息表 + 幂等消费**（同库一致 + 可靠投递 + 幂等消费）；只有"必须预留资源"才上 TCC，与 [订单系统设计.md](订单系统设计.md) 第 3 节口径一致。

> 本节只给边界，**细节不在本篇重复**：2PC / TCC / Saga / 本地消息表 / **最大努力通知**（对账口径也在这篇）见 [分布式事务.md](../../分布式/理论/分布式事务.md)；事务消息 / 延迟消息选型见 [消息队列选型.md](../../../03-数据与中间件/中间件/消息队列/消息队列选型.md)；幂等生产者与重投顺序见 [Kafka.md](../../../03-数据与中间件/中间件/消息队列/Kafka.md)。

## 五、对账：为什么对账不是"查总额"？

**本节要点**：对账的判据不是"总额相等"，而是**按维度分类把差异捞出来** —— 因为两类差异可以互相抵消（多记一笔 100、漏记一笔 100，总额一模一样）。

### 5.1 实测：四类差异都要能捞出来

```text
=== ① 对账：四类差异都要能捞出来 ===
  构造：订单 10 笔（每笔 100 元）
        ｜ order_no=3 平台流水缺失；order_no=99 流水多出（无对应订单）
        ｜ order_no=5 流水金额 90（少付）；order_no=7 渠道成功但平台记为失败
  对账结果：共 5 条差异
    [金额不符  ] order_no=SO-05 渠道=100 平台=90
    [状态不符  ] order_no=SO-07 渠道=SUCCESS 平台=FAILED
    [多记    ] order_no=SO-99 平台有流水但渠道对账单里没有
    [内部不一致 ] order_no=SO-03 订单=PAID 而流水=
    [内部不一致 ] order_no=SO-07 订单=PAID 而流水=FAILED
  ⭐ 对账不是『查总额』，而是按维度分类捞差异；每一类都要有对应的处置动作
```

### 5.2 读法：总额相等才是"最危险"

实测 **5 条差异**分属下列类别：

| 类别 | 含义 | 实测样本 |
|---|---|---|
| **金额不符** | 渠道与平台的**金额**不一致 | `SO-05 渠道=100 平台=90`（少付） |
| **状态不符** | 渠道与平台的**结果**不一致 | `SO-07 渠道=SUCCESS 平台=FAILED` |
| **多记** | **平台有、渠道没有**的流水 | `SO-99 平台有流水但渠道对账单里没有` |
| **漏记** | **渠道有、平台没有**的流水 | 构造里的 `order_no=3`「平台流水缺失」即此类 |
| **内部不一致** | 平台**内部**（订单表 vs 流水表）对不上 | `SO-03 订单=PAID 而流水=空`、`SO-07 订单=PAID 而流水=FAILED` |

⭐ 为什么不能"查总额"：**漏记与多记可以互相抵消** —— 渠道多一笔 100、平台多记一笔 100，两边总额完全相等，但业务上是**两件真实的事故**。总额相等只说明"两个错误恰好凑成一对"，不代表账是对的。

### 5.3 每一类差异都要有处置动作

| 差异类型 | 典型原因 | 处置动作 |
|---|---|---|
| 金额不符 | 部分支付 / 优惠没对上 / 币种 | 人工核对 + 差额定责（我方 or 渠道） |
| 状态不符 | 回调丢了 / 我方状态被改错 | ⭐ **以渠道为准**修正平台状态（修正要留痕） |
| 多记 | 我方多落了流水 / 渠道漏发对账单 | 人工确认后冲正，**不自动删** |
| 漏记 | 回调没到 / 我方落库失败 | 补录流水 + 补触发后续动作（幂等） |

⭐ 判据：**对账的输出不是"平 / 不平"，而是一张"按类分好的差异清单"，每一条都有归属和动作**。只会喊"总额对不上"的对账系统，等于没有对账。

### 5.4 内部对账：别只盯着渠道

实测里 **5 条差异有 2 条是"内部不一致"**（订单表与流水表打架）—— 这类差异**不需要渠道对账单就能发现**。所以对账至少有两层：**内部对账**（订单表 vs 流水表，平台自己的一致，准实时 / 分钟级）与**外部对账**（平台流水 vs 渠道对账单，T+1，渠道通常次日给对账单）。

### 5.5 T+1 与准实时

- **T+1 全量对账**：渠道次日给对账单逐笔比对，是**兜底**，覆盖面全但滞后；
- **准实时单边核对**：对"已发起支付、超 N 分钟无回调"的单**主动查单**（2.2 的手段在这里复用）—— ⭐ 它挡的是"**回调丢了**"这一类，能在当天把差异压小，而不是等 T+1 才发现。

### 5.6 判据

**判据**：对账算"对上"不是总额相等，而是**每类差异都能列举并归零**；对不上**告警 + 人工确认、不自动改账**；内部对账准实时、外部对账 T+1，**两者都要有**。

## 六、资金安全：为什么复式记账是底线？

**本节要点**：单边记账会"**凭空吃掉资金**"，而且**账面上看不出来**。复式记账（借贷成对）让"所有账户余额之和恒等"，是资金系统的底线；它加上对账，构成**双保险**。

### 6.1 实测：单边记账 vs 复式记账

```text
=== ③ 资金安全：单边记账 vs 复式记账（100 个账户，每人 1000 元）===
  单边记账（只改付款方）                初始总额 100000  最终总额 60800   不守恒（凭空少了 39200 元）
  复式记账（借贷成对）                 初始总额 100000  最终总额 100000   守恒 ✅
```

### 6.2 读法

| 记账方式 | 初始总额 | 最终总额 | 是否守恒 |
|---|---|---|---|
| **单边记账**（只改付款方） | 100000 | **60800** | ❌ 不守恒（凭空少了 **39200** 元） |
| **复式记账**（借贷成对） | 100000 | **100000** | ✅ 守恒 |

⭐ **差额就是"被系统吃掉的资金"** —— 它不会以"报错"的形式出现，只会表现为"账对不上、但谁也说不清在哪一步少的"。

### 6.3 为什么单边记账会吃钱

单边记账在每一笔操作里**只记一个账户的变化**（比如只扣付款方）。只要有一处逻辑漏了对应的另一边（异常、并发、重试、部分成功），这笔钱就从总额里"蒸发"了 —— 而**单边账里没有任何一行数据能证明它蒸发过**。

### 6.4 复式记账的判据

复式记账要求**每一笔资金变动都至少写成两条分录（借 / 贷）**，金额相等、方向相反。由此得到一条可自动校验的判据：

> **任意时刻，所有账户余额之和 = 初始总额**（实测：100000 → 100000）。

一旦这个和不等于初始值，就说明有**单边分录**被写进去了 —— 系统**自己就能发现**，不必等对账、更不必等人工。

### 6.5 双保险：复式 + 对账

| 机制 | 保证什么 | 挡什么 |
|---|---|---|
| **复式记账** | 平台**内部金额恒等** | 内部漏记一边 / 写错金额 |
| **对账**（第五节） | 平台与**外部渠道一致** | 回调丢失 / 渠道与平台结果不符 |

⭐ 两者缺一不可：**复式管"内部不凭空多钱少钱"，对账管"外部对得上"**。只有对账没有复式，平台内部错了却与渠道总额碰巧相等就查不出来；只有复式没有对账，内部再自洽也发现不了"渠道根本没收到这笔钱"。

### 6.6 判据

**判据**：用**复式记账**（借贷成对）—— 单边记账一定会吃钱（实测 39200）；用 **Σ 所有账户余额 = 初始总额** 自动发现单边分录；但复式**不够**，必须配**对外对账**（第五节）。⚠️ **未实测**：手续费、退款、冻结的完整分录设计依赖具体业务，本篇只给"借贷成对 + 恒等校验"这条底线。

## 使用：支付链路的 Go 骨架

**本节要点**：把前六节压成三段可读骨架 —— **回调幂等处理**（一、二）、**重试退避**（三）、**对账查询**（五）。

> ⚠️ 三段都是骨架片段（为可读性省略了 import、类型定义与多层错误包装）。其中**带旧状态的 UPDATE**、
> **指数退避**、**对账 SQL** 三处口径分别对应本机实测（读数见 1.4、3.1、5.1）；
> **渠道签名校验**与**查单兜底**是按语义补全的示意（**未实测**）。

### 第一段：回调幂等处理

```go
// HandleNotify 处理渠道异步回调：先校验签名 → 幂等落流水 → 带旧状态改订单 → 写本地消息表。
// 三段副作用各自幂等，任一段失败都能安全重放（第一节 / 第二节）。
func HandleNotify(ctx context.Context, db *sql.DB, n Notify) error {
	// ⚠️ 示意（未实测）：先验签 + 防重放（时间戳 / nonce），否则"回调"与"重放攻击"无法区分
	if !verifySign(n) {
		return ErrBadSign
	}
	tx, err := db.BeginTx(ctx, nil)
	if err != nil {
		return err
	}
	defer tx.Rollback()

	// ① 幂等落支付流水：唯一索引 uk_channel_trade_no，重复那次影响 0 行
	res, err := tx.ExecContext(ctx, `
		INSERT IGNORE INTO pay_flow (channel_trade_no, order_no, amount, status)
		VALUES (?, ?, ?, ?)`, n.TradeNo, n.OrderNo, n.Amount, n.Status)
	if err != nil {
		return err
	}
	if dup, _ := res.RowsAffected(); dup == 0 {
		return tx.Commit() // 重复回调：流水已存在，不再触发任何动作
	}

	// ② 状态幂等：旧状态写进 WHERE（1.4）—— 影响 0 行说明订单已被改过
	res, err = tx.ExecContext(ctx, `
		UPDATE orders SET status = 'PAID', paid_at = NOW(3)
		WHERE order_no = ? AND status = 'PENDING_PAY'`, n.OrderNo)
	if err != nil {
		return err
	}
	if n0, _ := res.RowsAffected(); n0 == 0 {
		return tx.Commit() // ⚠️ 必须再查一次当前状态：区分"重复回调"与"迟到回调"（1.4）
	}

	// ③ 本地消息表：与业务同库同事务，异步投递 + 下游幂等消费（第四节）
	_, err = tx.ExecContext(ctx, `
		INSERT INTO local_msg (topic, payload, status) VALUES (?, ?, 'NEW')`,
		"order.paid", n.OrderNo)
	if err != nil {
		return err
	}
	return tx.Commit()
}
```

### 第二段：重试退避

```go
// RetryWithBackoff 指数退避重试：本机实测下游 500ms 后恢复时，
// 固定间隔打出 11 次请求、退避只打出 5 次（3.1）—— 退避是在替下游省压力。
// 前提：被重试的操作必须幂等，否则会重复执行副作用（3.3）。
func RetryWithBackoff(ctx context.Context, max int, fn func() error) error {
	base, capd := 50*time.Millisecond, 2*time.Second
	var last error
	for i := 0; i < max; i++ {
		if err := fn(); err == nil {
			return nil
		} else {
			last = err
		}
		if !retryable(last) { // 4xx / 非幂等副作用 → 直接放弃（3.3）
			return last
		}
		delay := base << i
		if delay > capd {
			delay = capd
		}
		select {
		case <-ctx.Done():
			return ctx.Err()
		case <-time.After(delay):
		}
	}
	return last
}
```

### 第三段：对账查询（按维度分类捞差异）

```sql
-- 对账不是查总额，而是逐类捞差异（5.2）：渠道对账单 ch 与平台流水 pf 逐笔比对，
-- 把「漏记 / 多记 / 金额不符 / 状态不符」一次捞出，只返回差异行。
SELECT * FROM (
    SELECT ch.trade_no, ch.order_no,
           ch.amount AS channel_amount, pf.amount AS platform_amount,
           ch.status AS channel_status, pf.status AS platform_status,
           CASE
             WHEN pf.order_no IS NULL    THEN '漏记'      -- 渠道有、平台没有
             WHEN ch.amount <> pf.amount THEN '金额不符'
             WHEN ch.status <> pf.status THEN '状态不符'
             ELSE '一致'
           END AS diff_type
    FROM channel_statement ch
    LEFT JOIN pay_flow pf ON pf.channel_trade_no = ch.trade_no
    UNION ALL
    SELECT pf.channel_trade_no, pf.order_no, NULL, pf.amount, NULL, pf.status, '多记'
    FROM pay_flow pf
    LEFT JOIN channel_statement ch ON ch.trade_no = pf.channel_trade_no
    WHERE ch.trade_no IS NULL                                   -- 平台有、渠道没有
) t
WHERE t.diff_type <> '一致';
```

⭐ 这条 SQL 返回的是"**差异清单**"，不是"是否平账" —— 对齐 5.3 的判据（每条差异都要有归属与动作）。⚠️ 真实对账还要补**内部对账**（订单表 vs 流水表，5.4）与**补偿动作**（修正要留痕、不自动删，5.6）。

## 延伸追问

- **为什么支付回调的幂等不能只靠"渠道说不重发"？** → 渠道的"不重发"是**尽力**承诺（网络超时、我方没 ack 都会触发重发），落地上必须假设**至少一次**；判据仍是我方的唯一索引 / 状态幂等（第一节）。
- **同步返回能不能直接改订单？** → 不能，同步返回只代表"渠道受理"（2.1）；订单状态只由**异步回调 / 主动查单**驱动。
- **"先收到成功又收到失败"以哪个为准？** → 以**渠道的最终状态**为准（主动查单确认）+ 本地终态不可回退（2.4）；回调的到达顺序不能用来推状态顺序。
- **重试次数是不是越多越好？** → 不是。本机实测（3.1）固定间隔打出 11 次、退避只打 5 次，无效请求差一倍以上；且**非幂等操作绝不能盲重试**（3.3）。
- **对账对不上，能不能自动改？** → ⭐ **不能自动改账**（5.6，与兄弟篇口径一致）—— 自动改会把"看得见的不一致"变成"看不见的不一致"；先告警 + 人工确认。
- **有了对账还要复式记账吗？** → 要。对账管"与外部一致"、复式管"内部恒等"，是**双保险**（6.5）；两者挡的是不同的错。
- **本篇哪些是未实测的？** → 渠道的具体对接细节、签名算法选择、手续费 / 退款 / 冻结的完整分录设计，都已标注**未实测**；正文 `text` 块里的数字全部来自本机实测。
