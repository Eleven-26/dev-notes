> 场景题：秒杀链路上的库存系统 —— 扣减一致性 / 防超卖 / 缓存与 DB 同步 / 分布式锁 四个硬问题，每个都附本机实测。

## 一、库存扣在哪：Redis 预扣 + 异步落库，还是直接扣 DB？

**本节要点**：这不只是"用不用 Redis"的问题，而是两个判据 —— **能不能接受最终一致**，以及**有没有对账兜底**。缺了第二条，预扣方案就等于把账交给了运气。

### 1.1 两条路

| 方案 | 扣减落在哪 | 一致性 | 吞吐上限 |
|---|---|---|---|
| **Redis 预扣 + 异步落库** | Redis 原子判定 → MQ → DB | 最终一致 | 高（挡住瞬时峰值，落库慢慢做） |
| **直接扣 DB** | DB 行锁 + 当前读 | 强一致 | 低（同一行 `UPDATE` 本机约 **833 次/秒**，见 [README.md](README.md) 1.5） |

⭐ 两条路不是"新旧之争"，是**吞吐与一致性之间的显式取舍**：秒杀选前者，是因为它必须扛住"峰值是均值几百倍"的瞬时流量。

### 1.2 为什么"预扣"必然引入最终一致

预扣 = 先在 Redis 上把库存**占住**，真正的落库由消费者异步做。Redis 与 DB 之间没有任何单机事务能罩住，所以两者之间**必然存在一段不一致窗口**。这不是实现的疏漏，而是这套方案能换来吞吐的**前提代价** —— 先承认它，才谈得上兜住它。

### 1.3 怎么做：让预扣只做一件事

预扣阶段只回答一个问题 —— **"这个人能不能买到"**，并把它变成 Redis 上一次原子判定（判据见第二节）。扣到了就立刻把订单请求丢进消息队列，落库、扣积分、发券都交给消费者（队列怎么选、怎么削峰见 [README.md](README.md) 1.4）。完整的 Lua 骨架在 [README.md](README.md) 1.3 与下面的 `## 使用`，本节不重复。

### 1.4 判据汇总

| 问题 | 判据 |
|---|---|
| 能不能用预扣？ | 业务能否接受"秒杀成功"与"库存真正落库"之间有几秒延迟？能 → 预扣 |
| 不能接受最终一致怎么办？ | 退回直接扣 DB（`UPDATE ... WHERE stock > 0`），**用吞吐换强一致** |
| ⭐ 预扣方案的底线 | **必须能对账**：定时比对「Redis 剩余 + 已下单占用量」与「DB 库存 + 订单表」；对不上先告警、不自动改（口径见 [README.md](README.md) 1.7） |

⭐ 一句话：**"接受最终一致"是入场券，"能对账"是安全带** —— 只买票不系安全带的预扣，迟早会以"账对不上、谁也说不清"收场。

### 1.5 两个必须一起讲的副作用

预扣换来吞吐，也带来两个只有预扣才有的麻烦 —— 讲"用 Redis 预扣"时一起说清，才显得这套方案是被想清楚的：

| 副作用 | 现象 | 怎么兜 |
|---|---|---|
| **占位泄漏** | 用户抢到了（占位成功）却最终没付款，占位一直挂着 | 超时归还 + **幂等标记**，归还前再查一次状态（见 [订单系统设计.md](订单系统设计.md) 第五节） |
| **回补成本** | 判定失败时多扣掉的那部分，必须再花一次往返补回来 | 把"判"和"改"压进**一次**原子操作（第二节），从源头不产生负数 |

⭐ 这两条都不是"边缘 case"：**占位泄漏**会让库存"看起来卖完了、其实没人买"；**回补**会让别的请求在一段时间里看到**错误的可用量**（甚至再放大一波流量）。它们都是预扣方案的固有成本，不是实现的 bug。

## 二、怎么防超卖：为什么「原子判定」是唯一出路？

**本节要点**：判据只有一句话 —— **把「判断」和「执行」压进一个原子操作**。任何「先查再改」的写法都错，因为"查"和"改"之间隔着一次网络往返或一次函数返回，那个间隙就是竞态窗口。

### 2.1 超卖错在哪

库存是**共享可变量**，「读 → 判断 → 写」三步在并发下**不是原子的**。本机实测（1000 库存 / 5000 并发）里最刺眼的一行是 Redis 的两次往返写法：**成功 5000、库存 -4000** —— 不是"超卖一点点"，是**所有请求都以为还有货**。四类错误写法与正确写法的完整对照见 [README.md](README.md) 1.2，本篇不重复那张表。

### 2.2 三种原子手段

| 手段 | 原子性来自哪 | 判据 |
|---|---|---|
| **Redis Lua** | 服务端单线程把读-判-写**一次执行** | 返回值 `>= 0` 才算抢到，`-2` 表示库存不足 |
| **带条件 `UPDATE`** | 行锁 + 「当前读」 | `RowsAffected`：`1` 生效、`0` 是空操作（原理见 [MVCC与锁.md](../../../03-数据与中间件/数据存储/关系型/MySQL/MVCC与锁.md)） |
| **CAS（内存 / 乐观锁）** | 比较并交换 | 失败重试；⚠️ 在**热点行**上是负优化（实测漏卖 + 重试 9.2 万次，见 [README.md](README.md) 1.5） |

⭐ 三种手段的读数在本机都是**成功 1000 / 库存 0**，真正的差别在代价：Lua 一次往返、带条件 `UPDATE` 排队（约 833 次/秒）、CAS 自旋重试 237~313 次。

### 2.3 为什么"先查再改"必错（最值钱的一组对照）

同一段"先减再判 + 为负就回补"的逻辑，放在**客户端**与放在 **Lua 里**，命令顺序**一模一样**，结果却相反：

- 放客户端：成功数是对的（1000），但库存被扣成 **-4000**，还得再写一次 `INCR` 回补 —— 而**回补本身又是一次网络往返**，补的过程中账一直是错的；
- 放 Lua：完全正确，因为「读-判-写」在服务端**一次执行完**，中间没有间隙。

⭐ 由此得到这条比"记住用 Lua"重要得多的判据：

> **原子性的边界在服务端。** 只要「读」和「写」之间隔着一次网络往返（或一次函数返回），那个间隙就是竞态窗口 —— 无论你在客户端写得多小心。

### 2.4 判据

| 写法 | 是否安全 | 为什么 |
|---|---|---|
| 先查再改（客户端两步） | ❌ | 两次往返之间是竞态窗口 |
| 先减再判 + 客户端回补 | ❌ | 成功数对，但**账中间是错的**，且回补又要一次往返 |
| Lua 服务端读-判-写 | ✅ | 服务端一次执行，无间隙 |
| 带条件 `UPDATE` + 看 `RowsAffected` | ✅ | 行锁 + 当前读，让数据库自己判 |
| CAS 自旋 | ✅ 但看场景 | 冲突少时好；**热点行**上重试爆炸、还会漏卖 |

## 三、缓存与 DB 怎么同步：三种更新顺序哪种对？

**本节要点**：难点在"删除缓存"删不掉**已经在路上**的旧值 —— 一次「读库 → 回填」的读线程，足以让「先删缓存」和「先写库」两种顺序同时失效。判据是：**写路径先写库、再删缓存**，并看清延迟双删的适用边界。

### 3.1 三种更新顺序的实测对照

精确构造一个「读库 → 回填」交错窗口：读线程先造缓存 miss、从 DB 读到旧值、**80ms 之后才回填**；写线程在这 80ms 内收到通知并把库存 100 改成 99。

```text
=== ① 缓存与 DB 双写：三种更新顺序（精确构造「读库 → 回填」窗口）===
    构造：读线程制造缓存 miss → 从 DB 读到旧值 100 → 通知写线程 → 80ms 后回填
          写线程收到通知之后才执行更新（把库存 100 改成 99）
    判定：全部结束之后缓存值 == DB 值才算一致（缓存已空也算一致：下次读会拉到新值）
  A 先删缓存，再写库                         不一致 5/5 轮   缓存 100 / DB 99
  B 先写库，再删缓存                         不一致 5/5 轮   缓存 100 / DB 99
  C 先写库 + 删缓存 + 延迟再删一次               不一致 0/5 轮
```

### 3.2 读法：为什么 A、B 都不一致

- **A 先删缓存、再写库**：缓存被删之后、DB 还没改之前，读线程已经把**旧值 100** 读到手里；写线程随后把 DB 改成 99，读线程 80ms 后把 **100 回填**进缓存 → 缓存 100 / DB 99。
- **B 先写库、再删缓存**：写线程先把 DB 改成 99，但读线程在**写库之前**就读到了旧值 100 并已在路上；写线程删完缓存后，读线程再把 **100 回填** → 同样不一致。

⭐ 两行一模一样（缓存 100 / DB 99），但**根因相反**：A 是"删早了"、B 是"删晚了"。共同点是 —— **`DEL` 只能删掉缓存里已有的值，删不掉"已经在路上、即将被回填"的旧值**。这就是 A、B 都逃不掉的根本原因。

### 3.3 为什么 C 有效：延迟双删

C 在 B 的基础上**再延迟删一次**：先写库 → 删缓存 → 等一个"长于读线程最大回填耗时"的延迟 → **再删一次**。第二次删的时候，那趟"在路上的旧值"早已回填完毕，被一并清掉。本机 80ms 窗口下 **0/5 轮不一致**。

### 3.4 判据与适用边界

| 问题 | 判据 |
|---|---|
| 写路径怎么走？ | **先写库、再删缓存**（Cache-Aside 写侧）；❌ 不要"先删缓存再写库"（A），更不要"写库但不删缓存" |
| 要不要延迟双删？ | 只在「读多写少 + 能容忍极端情况下短暂不一致」时才需要；⭐ **延迟必须 > 一次「读库 + 回填」的最长耗时** |
| 延迟估不准怎么办？ | 别赌延迟双删 —— 退回"缓存只读、强一致判定走 DB/Redis 原子操作"，把"读缓存"和"扣减"彻底分开 |

⚠️ **适用边界三条**：

1. 延迟双删**不是强一致** —— 它只是把不一致窗口压低，不是消灭；真正的扣减判定不该依赖缓存（见 1.3）；
2. 删缓存**可能失败**，失败要**重试 / 补偿**，否则窗口被放大（删除失败的重试口径见 [缓存问题与方案.md](../../../03-数据与中间件/数据存储/缓存/缓存问题与方案.md)）；
3. ⚠️ **未实测**：Redis 主从 / Cluster 场景下"删缓存失败 + 补偿重试"的行为、以及主从复制延迟对双删窗口的影响，本机单实例环境**未覆盖**，上表结论只在单实例上成立。

### 3.5 一张表收口

| 顺序 | 那个 80ms 窗口里发生了什么 | 结果 | 结论 |
|---|---|---|---|
| A 先删缓存、再写库 | 读线程在"删缓存之后、写库之前"读到旧值 | 缓存 100 / DB 99 | ❌ 删早了 |
| B 先写库、再删缓存 | 读线程在"写库之前"就拿到旧值、随后回填 | 缓存 100 / DB 99 | ❌ 删晚了 |
| C 先写库 + 删缓存 + 延迟再删一次 | 第二次删把"在路上"的回填一并清掉 | 一致 | ✅ |

⭐ 读这张表的正确姿势：**A、B 的失败读数完全相同，但它们是两个不同的 bug** —— 只按"顺序"死记"A 错 B 对"（或反过来），都会在另一种交错下翻车。真正稳的是 C：「**先写库 → 删缓存 → 等回填窗口过去再删一次**」。

## 四、分布式锁：TTL 怎么定，锁到底保护了什么？

**本节要点**：TTL 定错会超卖，但**改成看门狗续期也救不了另一种错误** —— 本次实测暴露了真正的坑：**锁只保护临界区、不保护业务边界**。拿到锁之后，库存是否 > 0 **必须自己在锁内重新判**。

### 4.1 三种 TTL 策略的实测对照

库存 1 件、两个 worker 抢、抢不到轮询重试；业务耗时固定约 300ms。

```text
=== ② 分布式锁：TTL 与业务耗时的关系（库存 1 件，两个 worker 抢，抢不到会轮询重试）===
    判定：库存被扣成负数 = 超卖（两个 worker 都以为自己拿到了锁）
  A TTL=100ms（< 业务 300ms），不续期            第 1 轮：库存被扣到 -1
       5 轮统计：超卖 5 轮、抢锁超时放弃 0 次
  B TTL=1s（> 业务 300ms），不续期               第 1 轮：库存被扣到 0
       5 轮统计：超卖 0 轮、抢锁超时放弃 0 次
  C TTL=100ms + 后台续期（看门狗）                第 1 轮：库存被扣到 0
       5 轮统计：超卖 0 轮、抢锁超时放弃 0 次
```

### 4.2 读法

- **A（TTL 比业务短）**：锁在业务做完**之前**就过期，第二个 worker 顺利拿到同一把锁 → **两个人都进了临界区** → 超卖 **5/5 轮**，库存被扣成 **-1**；
- **B（TTL 够长）**：**0 轮**；
- **C（看门狗续期）**：**0 轮** —— 用后台续期把 TTL 变成"**业务还活着，锁就不放手**"，效果等价于 B，但不用拍脑袋估一个足够长的 TTL。

⭐ 三组"抢锁超时放弃"都是 **0 次**：说明抢不到的那个 worker 靠**轮询**最终等到了锁，而不是被硬拒 —— "放弃 0 次"是正确性的一部分（拒绝执行不等于不扣减，见 4.4）。

### 4.3 ⭐ 锁只保护临界区，不保护业务边界（本次实测暴露的坑）

这次实验**最初的版本里，A、B、C 三种模式全都超卖** —— 而且和 TTL、和续期**都无关**。根因是代码在锁内**没有重新检查库存**：

```go
// ❌ 错误版本：拿到锁就直接扣，锁内不判库存
ok := acquireLock(...)   // 锁本身没问题：同一时刻只有一个人进临界区
if ok {
    rdb.Decr(ctx, "stock:"+sku)   // 无条件扣 —— 库存 1，两个 worker 依次进来各扣 1 → -1
}
```

锁保证了"同一时刻只有一个人进临界区"，但**没有保证"进来的时候库存还剩"**：
worker1 进来扣成 0、worker2 **随后**进来又扣一次 → **-1**。
⭐ 也就是说，**"互斥"和"业务正确"是两件事**：锁解决前者，后者要靠**锁内的业务判断**（`if cur > 0`）自己完成。补上这道判断之后，A 才**只在"锁过期"这一种情况下**超卖（回到 4.1 的读数），B、C 归零。

> ⚠️ 这条坑在真实系统里同样致命：审计、扣款、发券……凡是"先拿锁、再操作共享资源"的地方，**锁只负责排队，资源够不够、状态对不对，必须自己在临界区内重新判一遍**。

### 4.4 判据

| 问题 | 判据 |
|---|---|
| TTL 怎么定？ | **TTL > 业务最长耗时**；拿不准就用看门狗续期（C），**别赌一个估计值** |
| 看门狗就够了吗？ | ⚠️ **不够** —— 它只保证"锁不被误抢"，**不保证业务正确**，见 4.3 |
| ⭐ 锁能替代库存判定吗？ | **不能**。锁保护的是「临界区互斥」，业务边界（库存是否 > 0）必须**在锁内重新判** |
| 抢不到锁怎么办？ | 轮询重试或直接拒绝；⚠️ 拒绝要保证"**什么都没做**"，绝不能"当作扣减成功"往下走 |
| 释放锁要注意什么？ | 必须**比对 token 再删**（Lua），防误删别人的锁；SETNX / 过期 / 释放与 6 个真实故障点见 [分布式锁.md](../../../03-数据与中间件/数据存储/NoSQL/Redis/分布式锁.md) |

### 4.5 释放锁的三个前提

一把"能进也能出"的锁，释放时必须同时满足三条，缺一条都会变成事故：

1. **删的是自己的锁** —— 释放前用 Lua 比对 token（`GET == ARGV[1]` 才 `DEL`），否则会把别人刚拿到的锁删掉；
2. **锁还没过期** —— 业务耗时必须短于 TTL，或由看门狗续期兜住（4.1）；
3. **业务边界判过了** —— 释放锁不等于"业务做完了"，4.3 的双重检查必须在**释放之前**完成。

⭐ 第 3 条最容易被忽略：锁的"进"与"出"看起来对称，但**业务正确性并不在锁的语义里**。SETNX / 过期 / 释放的完整实现与 6 个真实故障点见 [分布式锁.md](../../../03-数据与中间件/数据存储/NoSQL/Redis/分布式锁.md)。

## 使用：库存扣减的 Go 骨架（Lua + 锁 + 双重检查）

**本节要点**：把四个问题压成三段可读骨架 —— **Lua 原子预扣**（一、二）、**带 token 的锁与释放**（四）、**锁内双重检查**（四 4.3 的坑）。

> ⚠️ 三段都是骨架片段（为可读性省略了 import、类型定义与多层错误包装）。其中 **Lua 扣减**与
> **锁内双重检查**的逻辑取自本机实测程序（读数见第二节、4.1~4.3）；**带 token 释放**是按语义补全的示意（未单独实测）。

### 第一段：Lua 原子预扣（判断与执行压进一次服务端执行）

```lua
-- KEYS[1] = 库存 key（如 stock:sku_1001），ARGV[1] = 本次购买数量
-- 返回：剩余库存（>=0 表示扣减成功），-1 表示 key 不存在，-2 表示库存不足
local left = redis.call('GET', KEYS[1])
if not left then return -1 end
local n, want = tonumber(left), tonumber(ARGV[1])
if n < want then return -2 end
return redis.call('DECRBY', KEYS[1], want)
```

调用侧只有在返回值 `>= 0` 时才认为"抢到了"，随后立刻把订单请求丢进消息队列（一 1.3）。

### 第二段：分布式锁（SETNX + token 释放）

```go
// 释放必须"比对 token 再删"，否则会误删别人的锁（见分布式锁.md 的 6 个故障点）
var releaseLua = redis.NewScript(`
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
end
return 0`)

func acquireLock(ctx context.Context, rdb *redis.Client, key, token string, ttl time.Duration) (bool, error) {
	// SETNX + EXPIRE 一步完成；TTL 必须 > 业务最长耗时，拿不准就上后台续期（4.4）
	return rdb.SetNX(ctx, key, token, ttl).Result()
}

func releaseLock(ctx context.Context, rdb *redis.Client, key, token string) {
	_, _ = releaseLua.Run(ctx, rdb, []string{key}, token).Result()
}

// ⚠️ 示意（未单独实测）：生产里用看门狗在业务存活期间定期把 TTL 续回，避免"业务没做完锁先过期"
```

### 第三段：锁内双重检查（本次实测的坑）

```go
// LockAndDeduct：拿到锁之后必须重新检查库存 —— 锁只保证"同一时刻只有一个人进临界区"，
// 不保证"进来时库存还剩"。本次实测最初的版本漏了这一步，三种 TTL 都超卖（见 4.3）。
func LockAndDeduct(ctx context.Context, rdb *redis.Client, sku string, ttl time.Duration) (bool, error) {
	key, token := "lock:stock:"+sku, uuid.NewString()
	ok, err := acquireLock(ctx, rdb, key, token, ttl)
	if err != nil {
		return false, err
	}
	if !ok {
		return false, ErrLockBusy // 抢不到锁：轮询重试，不是超卖
	}
	defer releaseLock(ctx, rdb, key, token)

	// ⭐ 双重检查：锁内重新读一次库存，这才是"业务边界"
	cur, err := rdb.Get(ctx, "stock:"+sku).Int64()
	if err == redis.Nil {
		return false, nil
	}
	if err != nil {
		return false, err
	}
	if cur <= 0 {
		return false, ErrSoldOut // 锁内判定，杜绝"两个人都以为还有货"
	}
	_, err = rdb.Decr(ctx, "stock:"+sku).Result()
	return err == nil, err
}
```

⭐ 把三段串起来就是库存侧的最小闭环：
**Lua 预扣挡住绝大多数注定失败的请求（一、二）→ 必需串行的场景才上锁（四）→ 锁内一定要重新判库存（4.3）**，
而缓存与 DB 的同步（三）是"读"的那一侧 —— 它只负责让读变快，**不负责让账变对**。

## 延伸追问

- **为什么预扣了 Redis，还要再扣一次 DB？** → 预扣只是"挡流量 + 占位"，DB 才是"最终落账"；两者是**最终一致**，中间的落库、幂等、超时归还由订单链路负责（见 [订单系统设计.md](订单系统设计.md)）。
- **分布式锁为什么不用 Redlock？** → 单实例 / Sentinel 下 `SETNX + TTL + token 释放` 已够；⚠️ **未实测**：Redis Cluster 下的分片行为与 Redlock 的争议，本机环境**未覆盖**，细节见 [分布式锁.md](../../../03-数据与中间件/数据存储/NoSQL/Redis/分布式锁.md)。
- **对账对不上怎么办？** → **告警、不自动改**（一 1.4）；自动改账会把"看得见的不一致"变成"看不见的不一致"（口径见 [README.md](README.md) 1.7）。
- **分段库存能不能解决单 key 热点？** → 能不能要看底下的物理资源：单机 Redis 上分段无收益、轮询兜底反而变慢，读数与判据见 [README.md](README.md) 1.5，本篇不重复。
- **延迟双删的延迟到底设多久？** → **大于一次「读库 + 回填」的最长耗时**（三 3.4）；估不准就别用延迟双删，改成"缓存只读、强一致走 DB/Redis 原子操作"。
- **能不能把 DB 行锁和 Redis 锁混着用？** → 两把锁的**顺序与粒度不同**会引入死锁；要么让扣减只走一个原子点，要么把两把锁的获取顺序固定死。行锁与当前读的原理见 [MVCC与锁.md](../../../03-数据与中间件/数据存储/关系型/MySQL/MVCC与锁.md)。
