## 一、高并发领取：为什么「先查后扣」把 100 张券发成了 5000 张？

**本节要点**：「领取」这个动作在代码里是三步 —— **读库存 → 判断够不够 → 扣减**。
这三步**任何一步单独看都对**，但并发下它们不是一个整体。这一节要量出来的就是：
这个「不是整体」到底能让 100 张券发出去多少张。

### 1.1 先看结论：100 张券，发出去 5000 张

统一参数：券总量 **100**、**5000** 人并发抢（每人限领 1 张）。判定标准：**领到数 == 100 且库存 == 0**。

```text
=== ① 高并发领取：「先查后扣」vs Lua 原子（100 张券，5000 人抢）===
    写法                                           领到         Redis 剩余     DB 剩余
    A 先查后扣（GET → 判断 → DECR，不看返回值）                5000       -4900        -1538
    B Lua 原子（读-判-扣一次执行）                          100        0            0
    C MySQL 带条件 UPDATE（remain>0）                 100        —            0
```

⭐ 三个读数分别说明三件事：

| 写法 | 领到 | 说明 |
|---|---|---|
| **A 先查后扣** | **5000** | 券只有 100 张，**实际发了 5000 张**；库存键被扣成 **-4900** |
| **B Lua 原子** | 100 | 精确；库存恰好归零 |
| **C 条件 UPDATE** | 100 | 不用 Redis 也能对：把判断写进 `WHERE` |

⚠️ A 组的实现是这样的（`claimed` 只在扣减成功后加一）：

```go
v, err := rdb.Get(ctx, "coupon:stock:1").Int()
if err != nil || v <= 0 {
    return                       // 查一下：库存还够吗？
}
rdb.Decr(ctx, "coupon:stock:1")  // ⚠️ 然后才扣
claimed.Add(1)
```

看上去无懈可击。但 5000 个请求会**同时**执行到 `if v <= 0` 这一行 ——
它们读到的都是 `100`（因为还没人扣），于是**全部通过判断**，然后各自去扣。

### 1.2 连跑 5 轮：这个错误是稳定的，不是偶发

```text
    A 组连跑 5 轮：
      第 1 轮：领到  5000 张（超发  4900）  Redis 库存 -4900
      第 2 轮：领到  4971 张（超发  4871）  Redis 库存 -4871
      第 3 轮：领到  5000 张（超发  4900）  Redis 库存 -4900
      第 4 轮：领到  5000 张（超发  4900）  Redis 库存 -4900
      第 5 轮：领到  5000 张（超发  4900）  Redis 库存 -4900
    → 最坏超发 4900 张、平均 4894 张
```

⭐ 5 轮里有 4 轮是「一个不漏地全放行」。也就是说：
**这个 bug 不是"运气不好才出现"，而是"只要并发够就必然出现"**。
只有第 2 轮少放了 29 个 —— 那几个请求恰好晚了一点点，读到了已经被扣过的值。

### 1.3 ⚠️ 一个能骗过自己的写法

这里有个很值得警惕的变体。如果 A 组改成**看 `DECR` 的返回值**再计数：

```go
if rdb.Decr(ctx, "coupon:stock:1").Val() >= 0 {   // 扣完看是不是负的
    claimed.Add(1)                                 // 负了就不算成功
}
```

在**并发不够高**的时候，这个写法会输出「领到 100 张」—— 看起来完全正确。
但 Redis 里的库存**照样被扣穿**：

⭐ **判据不能只看「成功数」，要连「库存键的值」一起看**。
一个限流/发放系统对不对，看的是「共享的那个资源有没有被超额消耗」，
不是「日志里报了多少次成功」—— 后者很容易被后置校验掩盖。

### 1.4 正确的三种写法（都是同一个道理）

**① Lua 脚本：把「读、判、扣」压进一次服务端执行**

```lua
local v = redis.call('GET', KEYS[1])
if not v then return -1 end
if tonumber(v) <= 0 then return 0 end
redis.call('DECR', KEYS[1])
return 1
```

⭐ 为什么 Lua 能行：**Redis 执行 Lua 期间不会插入其他命令**，
所以「读判断写」这三次操作在服务端是**连续、不可分割**的。

**② MySQL 带条件 UPDATE：把判断写进 WHERE**

```sql
UPDATE coupon SET remain = remain - 1 WHERE id = ? AND remain > 0;
```

判断条件（`remain > 0`）和修改（`remain - 1`）在**同一条语句**里，
由数据库的行锁保证原子性。看 `RowsAffected()` 是不是 1 就知道成没成功。

**③ CAS**：比较并交换（见 [库存系统设计.md](库存系统设计.md) 与
[../../分布式/服务治理/并发限制器.md](../../分布式/服务治理/并发限制器.md)）。

⭐ 三种写法的共同点只有一句话：**判定与执行必须在同一个原子操作里**。
只要它们分属两次调用（哪怕只隔一行代码），就一定有并发窗口。

## 二、防刷：一人一单为什么要「原子判重 + 唯一索引」两道？

**本节要点**：上一节解决的是「别超发」，这一节解决「**别让同一个人领走多张**」。
两者看着像，但**判重比扣库存多一个难点：它判的是「这个用户有没有来过」，而这是一个集合操作**。

### 2.1 只扣库存不判重：一个人拿走 50 张

构造：库里有 100 张券，**同一个用户**（`uid=7`）并发发 50 个领取请求。

```text
    写法                                           该用户领到        全表记录
    A 无去重 + 无唯一索引（只扣库存）                          50           50
    B Lua 里 SADD 判重（原子）                          1            1           （其中被去重挡下 49 次）
    C MySQL 唯一索引 + INSERT IGNORE                 1            1           （其中被唯一键挡下 49 次）
```

⚠️ 注意 A 组的口径：**先要把唯一索引摘掉**。为什么？见 2.3 —— 这本身就是个知识点。

```text
    连跑 5 轮（A 组口径：无去重 + 无唯一索引）：
      第 1 轮：该用户领到 50 张
      ...
    → 同一个用户最多领到 50 张（脚本刷券就是这么来的）
```

### 2.2 两道防线，各挡一层

**第一道：原子判重（`SADD`）** —— 在 Lua 里顺手把「已领名单」也判掉：

```lua
local v = redis.call('GET', KEYS[1])
if not v or tonumber(v) <= 0 then return 0 end
local added = redis.call('SADD', KEYS[2], ARGV[1])   -- 名单里加得进去才继续
if added == 0 then return 2 end                      -- 已经领过
redis.call('DECR', KEYS[1])
return 1
```

⭐ **名单判定必须和扣减在同一个 Lua 里**。如果写成「先 `SADD` 判重、再单独发一次 `DECR`」，
中间就又有窗口了 —— 与第一节是同一个病。

**第二道：MySQL 唯一索引** —— `uk(coupon_id, uid)` + `INSERT IGNORE`。
`RowsAffected() == 0` 就说明这个用户已经领过了。

⭐ 两道都必要的理由：Redis 那道挡的是**绝大多数**（性能好、无锁）；
数据库那道挡的是**前面那道万一被绕过**（比如缓存被清、名单 key 过期、
或者代码改动引入了 bug）。README 里那句话在这条链路上同样成立：
**唯一索引是唯一不会骗人的那层**（见 [README.md](README.md) 1.6 节）。

### 2.3 ⚠️ 唯一索引要付的代价：白扣回补 + 建索引失败

**代价一：库存会被白扣。** 库里那道拦下请求时，Redis 里的库存**已经扣过了**：

```go
res, err := db.Exec("INSERT IGNORE INTO user_coupon (coupon_id,uid,created_at) VALUES (1,?,NOW(3))", uid)
if err != nil { return }
if n, _ := res.RowsAffected(); n == 0 {          // 唯一键冲突 → 已被别的请求领过
    _, _ = db.Exec("UPDATE coupon SET remain=remain+1 WHERE id=1")   // ⚠️ 必须回补
}
```

不回补的后果是**券凭空少一张**：明明只有 1 个人领到，库存却掉了 2。

**代价二：给已有脏数据的表补唯一索引会直接失败。** 这是本机实测到的报错原文：

```text
$ mysql -e "CREATE TABLE dup_demo (coupon_id INT NOT NULL, uid INT NOT NULL);
            INSERT INTO dup_demo VALUES (1,7),(1,7),(1,8);
            ALTER TABLE dup_demo ADD UNIQUE KEY uk_coupon_uid (coupon_id, uid);"
ERROR 1062 (23000) at line 1: Duplicate entry '1-7' for key 'dup_demo.uk_coupon_uid'
```

⭐ 这个报错的含义是：**表里已经存在重复行，唯一索引加不上去**。
它经常出现在两种真实场景里：① 老表补索引；② 线上已经出了重复发放的事故，
想紧急补一道防线时反而补不上（**得先清理重复行，再建索引**）。

⚠️ 所以「上唯一索引」这件事**不能作为事后补救的最后手段** ——
它必须在建表时就带上，否则出事那天你会发现它建不起来。

## 三、分布式锁：为什么「加了锁」还是会重复发放？

**本节要点**：很多人的直觉是「加锁 = 串行 = 不会重复」。这一节要推翻这个直觉 ——
**锁保证的是「同一时刻只有一个人进临界区」，它完全不管你在临界区里干了什么**。

### 3.1 三种写法对照

构造：同一个用户、2 个并发请求、无唯一索引（否则插不进去，看不出问题）。

```text
=== ③ 分布式锁：锁本身解决什么、不解决什么（同一个用户，2 个并发）===
    A 加锁但锁内不判重（无唯一索引）                              该用户领到 2 张
    B 锁 + 锁内判重（SADD）                               该用户领到 1 张
    C 不用锁，只靠 Lua 原子判重                              该用户领到 1 张
```

A 组的代码是这样的（**看着很像正经的锁用法**）：

```go
ok := rdb.SetNX(ctx, lockKey, token, 3*time.Second).Val()
if !ok {
    return                       // 抢不到锁就算了
}
defer rdb.Del(ctx, lockKey)      // 用完释放

rdb.Decr(ctx, "coupon:stock:1")  // ⚠️ 锁内只扣库存，没有判重
db.Exec("INSERT INTO user_coupon ...")
```

两个请求**依次**进了临界区（一个先拿到锁、释放，另一个再拿到），
每个都扣了库存、都插了一条记录 → **领到 2 张**。

⭐ 一句话：**锁负责「排队」，不负责「判断」**。
它把并发变成串行，但串行执行两遍「不判重的逻辑」，结果还是两遍。

### 3.2 ⚠️ 还有一个容易忽略的前提：抢不到锁的人必须「等」

这个实验的第一版里，A 组只领到 **1** 张 —— 不是因为它对了，而是因为
**抢不到锁的请求直接 `return` 了**，根本没进临界区。

真实代码几乎都会「抢不到就等一会儿再试」（否则用户只会看到失败）：

```go
for k := 0; k < 500; k++ {          // 最多等 500ms
    if rdb.SetNX(ctx, lockKey, token, 3*time.Second).Val() {
        held = true
        break
    }
    time.Sleep(time.Millisecond)
}
```

⭐ 这个细节很值得记：**"加锁版的正确性"往往取决于抢不到锁的人怎么办**。
用「直接返回」写出来的锁看起来更安全，其实是把问题推给了调用方（请求失败）。

### 3.3 什么时候根本不需要锁

C 组给出了更重要的答案：**不用锁，1 张**。

既然 `SADD` 判重 + `DECR` 扣减可以写进同一个 Lua 脚本、由 Redis 一次性执行完，
那就不需要再在外面套一把锁 —— 锁能提供的「串行」，原子脚本本身就提供了。

⭐ 选型判据：

| 情况 | 用什么 |
|---|---|
| 临界区的**全部**逻辑都能放进一次原子操作（Lua / 一条 SQL） | **不要锁** —— 原子脚本更简单、更快、更少故障点 |
| 临界区里有**跨进程 / 跨存储**的多个步骤（改库 + 发消息 + 调外部） | 要锁（或改设计，见 [../../分布式/理论/分布式事务.md](../../分布式/理论/分布式事务.md)） |

⚠️ 锁是有成本的：它引入新的失败模式（锁过期、误删别人的锁、死锁、
Redis 挂了怎么办），细节见 [分布式锁.md](../../../03-数据与中间件/数据存储/redis/分布式锁.md)。
**能不用就不用**。

## 四、异步发放：为什么领券不该同步写库？

**本节要点**：到这一步，「券该不该发」已经判定完了。
剩下的是**用户体验与系统吞吐**的问题：用户点「领取」到看到结果，中间要不要等他写完库。

### 4.1 实测：同步 1.2 秒 vs 异步 0.26 秒

构造：1000 次领取，A 组每次直接 `INSERT`，B 组只入队、由消费者攒批写。

```text
=== ④ 异步发放：领券时同步写 DB vs 攒批异步写（1000 次领取）===
    A 同步（每单一次 INSERT）                            总耗时 1.203s       平均每单 1.203ms
    B 异步（只入队，后台攒批写）                              总耗时 262ms        平均每单 262µs       （已落库 1000 条）
    → 请求侧快了约 5 倍（1.203s → 262ms），代价是「领取成功」与「券真的到账」之间有了延迟
```

⭐ 快的原因有两层：① 请求路径上只剩一次 `RPUSH`；
② 消费者**攒批写**（一条 `INSERT` 带多个 values），把 1000 次往返压成几次。

⚠️ 倍数别当成结论：每单 1.2ms 里绝大部分是**网络往返**，不是 MySQL 慢 ——
换台机器、换个网络这个倍数就会变。要主张的是「**请求路径变短了**」这个方向，不是具体几倍。

### 4.2 异步要付的三个代价

| 代价 | 具体表现 | 怎么补 |
|---|---|---|
| **中间态** | 用户点完「领取」不知道成没成 | 前端显示「发放中」，提供「我的券」列表查询 |
| **队列可靠性** | 本机用的 Redis `List`，Redis 挂了 / 消费者崩了**就丢** | 生产用 Stream（`XADD` + 消费组 + `XACK`）或 MQ（见 [消息队列选型.md](../../../03-数据与中间件/中间件/消息队列/消息队列选型.md)） |
| **幂等消费** | 队列可能重投，同一条被消费两次 → 发两张 | 唯一索引（第二节那道）+ 消费端幂等（见 [支付系统设计.md](支付系统设计.md)） |

### 4.3 什么时候必须同步

异步不是默认答案。下面这些场景**必须同步返回结果**：

- **券的数量极少、且用户会立刻用**（比如 1 元抢购，拿到券马上要下单）；
- **需要即时告知「抢到了」**（秒杀的主流程就是同步的，见 [README.md](README.md) 1.4 节）；
- **后续步骤依赖发券成功**（比如发完券立刻扣款）—— 这时异步会把复杂度推给下游。

⭐ 判据：**「用户能不能接受一件事"稍后完成"」**。
秒杀的「抢到了」不能，所以同步；而「券记到账户上」可以，所以异步。

## 五、红包：为什么它不能照抄优惠券的库存模型？

**本节要点**：红包和优惠券看着是一类东西（都是「发东西」），
但**稀缺的资源根本不是同一种** —— 这个差别决定了它们要用完全不同的模型。

### 5.1 差别的本质：稀缺的是「份数」还是「金额」

| | 优惠券 | 红包 |
|---|---|---|
| 稀缺的是什么 | **份数**（100 张，先到先得） | **金额**（100 元，人人有份） |
| 谁来消耗 | 一个人拿走**整份** | N 个人**分掉**总额 |
| 模型 | **库存模型**（`DECR` / 条件 `UPDATE`） | **拆分模型**（先拆好，各自领自己那份） |
| 失败的形态 | 超发（发多了） | 拆错了（金额对不上） |

⭐ 一句话判据：**看「一次领取消耗一个整体，还是消耗总额里的一部分」**。
前者用库存，后者用拆分。

### 5.2 二倍均值法：实测金额分布

**规则**：每次在 `[1, 2 × 剩余金额 / 剩余人数]` 之间随机取一个整数（单位：分）。
上界取「两倍均值」是为了保证**后面的人至少还能各分到 1 分**。

```text
=== ⑤ 红包金额拆分：总额 100 元、100 个红包，两种拆法 ===
    二倍均值法（每次在 [1, 2×剩余均值] 里随机）                 总额 10000 分  最小值 1  最大值 193  前 8 个: [14 181 103 129 33 17 191 72]
    固定均分（每份都是总额/份数）                            总额 10000 分  最小值 100  最大值 100  前 8 个: [100 100 100 100 100 100 100 100]
```

⭐ 两个读数的含义：

- **二倍均值**：最小 1 分、最大 193 分（平均 100 分），**参差但期望相等**，
  且**总额恒等于 10000 分**（这个"恒等"才是正确性底线）；
- **固定均分**：每份都是 100 分。看着最公平，但**先抢和后抢拿到的一样多**——
  红包"抢"的乐趣就没了。

### 5.3 拆分不用保证「原子」吗？

要，但**不是每次都拆**。正确做法是：

1. **发红包时一次性拆完**（100 个金额算好，写进一个列表 / Redis `List`）；
2. 领的时候只是 **`LPOP` 一次**（原子、O(1)），拿到的就是自己那份。

⭐ 对比一下就清楚了：

| 做法 | 并发问题 | 性能 |
|---|---|---|
| 每次领取时**现场算**金额 | ⚠️ 需要保证「剩余金额 / 剩余人数」的读改是原子的 | 要加锁或 Lua |
| **预先拆好，领取只 `LPOP`** | 无（`LPOP` 天然原子，且拿到的一定是唯一一份） | O(1) |

⭐ 与第一节的库存模型对照：**两者最终的「发放」动作都是一次原子操作**（`DECR` / `LPOP`），
差别只在**「份额怎么产生」**（库存模型是天然有的，拆分模型要先算）。

⚠️ 未实测部分：真实红包还涉及**过期退回**（没领完的钱要退回商户）、
**领取记录对账**（和资金流水对齐，见 [支付系统设计.md](支付系统设计.md)）——

## 使用：优惠券发放链路的 Go 骨架

**本节要点**：把前五节压成三段可读骨架 —— **Lua 原子判重 + 扣减**（一、二）、
**唯一索引兜底 + 白扣回补**（二）、**异步入队与幂等消费**（四）。

> ⚠️ 三段都是骨架片段（为可读性省略了 import、类型定义与错误包装）。
> 其中 **Lua 判重扣减**、**白扣回补**的逻辑取自本机实测程序（读数见第一、二、四节）；
> **Stream 消费组**是按语义补全的示意（未单独实测）。

### 第一段：一次 Lua 完成「判重 + 扣减」

```lua
-- KEYS[1] = 券库存 key（coupon:stock:{id}）
-- KEYS[2] = 已领名单 key（coupon:users:{id}）
-- ARGV[1] = 用户 ID
-- 返回：1=领取成功，0=已抢光，2=重复领取
local stock = redis.call('GET', KEYS[1])
if not stock then return 0 end
if tonumber(stock) <= 0 then return 0 end
local added = redis.call('SADD', KEYS[2], ARGV[1])
if added == 0 then return 2 end          -- 已经领过
redis.call('DECR', KEYS[1])
return 1
```

### 第二段：落库 + 唯一索引兜底 + 白扣回补

```go
func Claim(ctx context.Context, rdb *redis.Client, db *sql.DB, couponID, uid int) (string, error) {
    r, err := rdb.Eval(ctx, luaClaimOnce,
        []string{fmt.Sprintf("coupon:stock:%d", couponID),
                 fmt.Sprintf("coupon:users:%d", couponID)}, uid).Int()
    if err != nil {
        return "", err
    }
    switch r {
    case 0:
        return "sold_out", nil          // 抢光
    case 2:
        return "already_claimed", nil   // 重复领取（Redis 这道挡下的）
    }

    // ⭐ 第二道防线：唯一索引 uk(coupon_id, uid)
    res, err := db.ExecContext(ctx,
        "INSERT IGNORE INTO user_coupon (coupon_id, uid, created_at) VALUES (?, ?, NOW(3))",
        couponID, uid)
    if err != nil {
        return "", err
    }
    if n, _ := res.RowsAffected(); n == 0 {
        // 数据库说「已经领过」→ 上面那次扣减是白扣的，必须还回去
        if _, err := db.ExecContext(ctx,
            "UPDATE coupon SET remain = remain + 1 WHERE id = ? AND remain < total", couponID); err != nil {
            // ⚠️ 回补失败要告警：券会凭空少一张，靠对账兜底
            return "", err
        }
        return "already_claimed", nil
    }
    return "ok", nil
}
```

⭐ 注意 `INSERT IGNORE` 与**回补**是一对：只用前者会让券"凭空少一张"，
只回补不判重会真的多发。

### 第三段：异步入队 + 幂等消费（Stream）

```go
// 入队：请求路径上只做这一件事（比同步写库短一个数量级，见第四节）
_, err := rdb.XAdd(ctx, &redis.XAddArgs{
    Stream: "coupon:issue",
    Values: map[string]interface{}{"coupon_id": couponID, "uid": uid, "req_id": reqID},

// 消费：XREADGROUP + XACK，用消费组保证「一条只被一个消费者拿到」
//   ⚠️ 重投是正常的（消费者崩了会重投），所以消费端必须幂等 ——
//      靠 uk(coupon_id, uid) 或 req_id 唯一索引，与第二段同一道防线
```

## 延伸追问

- **为什么用 `SADD` 而不是 `SETNX` 做「已领名单」？** →
  `SET` 一个 `uid` 也行（`SETNX coupon:user:1:7 1`），但
  **一个用户可能领多张不同券、也可能需要统计"这个用户领过哪些"**；
  用 `SET`（集合）能一次存一批、还能 `SCARD` 出总数。
  单券限一张时直接用 `SETNX` 更省内存 —— 看是否需要"名单"这个形态。

- **名单 key 会越来越大怎么办？** →
  券活动结束后**主动清理**（活动通常有明确的起止时间）；
  长年累月的活动可以按「活动 ID + 日期」分 key，过期即整键删除。
  ⚠️ 别给它设 TTL 后不管 —— TTL 一到期名单就没了，去重直接失效。

- **Redis 挂了，判重和库存一起没了吗？** →
  库存会没（除非持久化 + 从库），但**唯一索引还在** ——
  这就是第二节强调「两道」的原因：数据库那道是最后一道。
  ⚠️ 更好的做法是让 Redis 只做"挡流量"，**真正的配额以 DB 为准**，
  中间用异步对账补差（见 [支付系统设计.md](支付系统设计.md) 第五节）。

- **接口被刷（同一 IP 打几十万次）会怎样？** →
  这是**限流**要解决的问题，不是发券逻辑能解决的：
  按「用户 ID 优先、IP 兜底」组合维度限流（见
  [../../分布式/服务治理/限流算法.md](../../分布式/服务治理/限流算法.md)），
  IP 不应作为唯维度（NAT 后面是一整个公司）。验证码属于接入层手段，
  成本要比"多查一次 Redis"高得多，别放在最前面（见 [README.md](README.md) 1.6 节）。

- **为什么不用「乐观锁 + 重试」发券？** →
  热点行上重试会**越试越糟**：本机另一组实测里，
  1000 并发对同一行做乐观锁出现「漏卖 233 + 重试 9.2 万次 + 慢 15 倍」
  （见 [README.md](README.md) 1.5 节）。发券是典型的热点写，用原子脚本或条件 UPDATE。

- **券的状态机要不要和订单一样？** →
  要：`未领 / 已领 / 已使用 / 已过期 / 已作废`，
  且转移要写成带条件的 `UPDATE ... WHERE status = 旧状态`
  （否则"已使用"和"已过期"两个操作会**都报告成功**，见
  [订单系统设计.md](订单系统设计.md) 第一节）。
