## 一、订单状态机：为什么合法转移要写进 UPDATE 的 WHERE 里？

**本节要点**：状态机的难点不在"列出有多少个状态"，而在**并发下两个合法转移同时到达时，只有一个能生效**。判据是「带条件的 UPDATE + `RowsAffected`」，不是「先查一下再改」。

### 1.1 有哪些状态、哪些转移是合法的

| 当前状态 | 合法转移 | 触发方 |
|---|---|---|
| 待支付 `PENDING_PAY` | → 已支付 `PAID` / → 已取消 `CANCELED` | 支付回调 / 用户取消或超时关单 |
| 已支付 `PAID` | → 已发货 `SHIPPED` / → 退款中 `REFUNDING` | 商家发货 / 用户申请退款 |
| 已发货 `SHIPPED` | → 已完成 `COMPLETED` | 确认收货 |
| 退款中 `REFUNDING` | → 已退款 `REFUNDED` | 退款回调 |
| 已取消 / 已完成 / 已退款（终态） | **不可再转** | — |

⭐ 一条铁律：**终态不可再转**。任何"把已完成改回已取消"的请求都必须被拒绝 —— 它意味着重复退款，或者重复归还库存。

### 1.2 难点：两个请求都报告成功，只有一个真的生效

支付回调和超时关单都要把订单从 `PENDING_PAY` 改走。如果写成无条件的 `UPDATE orders SET status=? WHERE id=?`，两句都会返回成功（各影响 1 行），最终状态取决于谁后写 —— 先写的那个"成功了，但被覆盖了"。

```text
=== ② 状态机：并发下的状态转移（待支付 → 已支付 / 已取消，两个请求同时到）===
  无条件 UPDATE（后写覆盖前写）                     支付/关单 都报告成功：1 / 1   最终状态 PAID
  带条件 UPDATE ... AND status=?            支付/关单 都报告成功：0 / 1   最终状态 CANCELED
```

### 1.3 怎么做：把"旧状态"写进 WHERE

```sql
UPDATE orders SET status = 'PAID'
WHERE id = ? AND status = 'PENDING_PAY';
```

判据是 `RowsAffected`：`1` 表示这次转移真的生效；`0` 表示别人已经改过，本次是**空操作**。

⭐ 关键读法：带条件后是 **支付 0 / 关单 1**。那个 `0` 就是"支付请求发现自己来晚了"的证据 —— 它没有报错，而是**如实报告"我一行都没改到"**，调用方据此决定要不要退款、要不要重试，而不是盲目当作成功。

### 1.4 判据汇总

| 写法 | 报告成功 | 是否静默覆盖 | 结论 |
|---|---|---|---|
| 无条件 `SET status=?` | 1 / 1 | ✅ 有 | ❌ 两个都"成功"，账是错的 |
| 带条件 `... AND status=?` | 0 / 1 | ❌ 无 | ✅ 只有一个真正生效 |

⭐ 这和秒杀扣库存是同一条路子：**把判断和写入压进一个原子操作**（行锁 + 当前读），原理见 [MVCC与锁.md](../../../03-数据与中间件/数据存储/关系型/MySQL/MVCC与锁.md)。把"状态判断"从 if 里竖过来切成类，是状态机的另一种实现，见 [状态模式.md](../../../05-设计模式/行为型/状态模式.md)。

## 二、幂等：为什么判据是唯一索引，而不是"先查后插"？

**本节要点**：一次提交被重放（用户连点、MQ 重投、网关重试）时必须只落一条。判据是**唯一索引**，不是应用层的"先查再插"——后者的两次往返之间就是竞态窗口。

### 2.1 "先查后插"错在哪

"先 `SELECT` 看看有没有 → 没有就 `INSERT`"是两步。两个并发请求可以在同一个间隙里**都查到"没有"**，然后**各插一条**。本机实测（同一个 `request_id` 被并发重放 2000 次）：

```text
=== ① 幂等：同一次提交（同一个 request_id）被并发重放 2000 次 ===
  A 先查后插（普通索引）：落库 87 条  ← 期望恰好 1 条
  B INSERT IGNORE（唯一索引）：落库 1 条，其中真正插进去的 1 次  ← 恰好 1 条
```

⭐ 87 条不是"概率小"，而是**真实事故**：这 87 条若各触发一次扣库存，就是超卖。它平时压不出来，只在并发放大的那几毫秒里出现。

### 2.2 怎么做：唯一索引 + 让数据库判重

```sql
CREATE TABLE seckill_order (
  id         BIGINT       PRIMARY KEY,
  order_no   VARCHAR(32)  NOT NULL,
  user_id    BIGINT       NOT NULL,
  sku_id     BIGINT       NOT NULL,
  status     VARCHAR(20)  NOT NULL,
  created_at DATETIME(3)  NOT NULL,
  UNIQUE KEY uk_order_no (order_no),
  UNIQUE KEY uk_user_sku (user_id, sku_id)
);

-- 重放时重复的那次会命中唯一索引 → 影响 0 行，而不是报错
INSERT IGNORE INTO seckill_order (order_no, user_id, sku_id, status, created_at)
VALUES (?, ?, ?, 'PENDING_PAY', NOW(3));
```

调用侧看 `RowsAffected`：`1` = 首次落库；`0` = 重复提交，直接返回已存在的订单，**不要再做任何有副作用的动作**（扣库存、发消息、发券都不行）。

### 2.3 幂等键怎么选

| 幂等键 | 保证什么 | 用在哪 |
|---|---|---|
| `order_no` | 同一次下单只落一条 | 消费落库、支付回调 |
| `request_id` | 同一个请求被重放只处理一次 | 网关 / 提交入口 |
| `(user_id, sku_id)` | 同一用户同一商品只有一单 | 秒杀"一人一单"兜底 |

⭐ 三者不是替代关系，而是**三层**：`request_id` 防"同一次请求被重放"，`order_no` 防"同一次业务被重复落库"，`(user_id, sku_id)` 防"同一个人反复抢"。订单号怎么生成（趋势递增、不暴露业务量、可分片基因）见 [分布式ID.md](../../分布式/理论/分布式ID.md)。

## 三、分布式事务：扣库存 + 建订单 + 发消息怎么保证一致？

**本节要点**：三个动作跨了 Redis、MySQL、MQ，没有单机事务能罩住。难点是**别把"最终一致"答成"强一致"**——订单链路绝大多数只要求最终一致，代价却差一个数量级。

### 3.1 不一致会以哪些形态出现

- 扣库存成功、建订单失败 → **少卖**（库存少了，货没卖出去）；
- 建订单成功、消息没发出去 → 订单"悬空"，下游永远不知道要处理；
- 都成功、但某个环节重试了 → 重复扣减（正是第 2 节幂等要补的洞）。

### 3.2 三条路的适用边界

| 方案 | 一致性 | 适用 | 代价 |
|---|---|---|---|
| 本地消息表 | 最终一致 | ⭐ **订单链路主流**：业务与消息同库同事务，再异步投递 | 一张消息表 + 投递重试 + 幂等消费 |
| 事务消息 | 最终一致 | MQ 原生支持时可省掉消息表 | 绑定具体 MQ，实现见 [RocketMQ.md](../../../03-数据与中间件/中间件/消息队列/RocketMQ.md) |
| TCC | 最终一致（业务补偿） | 需要"预留资源"的场景（如库存冻结） | 每步都要写 Try / Confirm / Cancel 三段 |
| 2PC | 强一致 | 极少用 | 阻塞、协调者单点，性能与可用性都差 |

⭐ 判据：**订单链路用"本地消息表 + 幂等消费"就够**；只有"必须预留资源、且补偿逻辑清晰"时才上 TCC。

> 本节只给边界，细节**不在本篇重复展开**：2PC / TCC / Saga / 本地消息表 / 最大努力通知的完整对照见
> [分布式事务.md](../../分布式/理论/分布式事务.md)；延迟消息与事务消息的选型见
> [消息队列选型对比.md](../../../03-数据与中间件/中间件/消息队列/消息队列选型对比.md)；RocketMQ 的实现细节见
> [RocketMQ.md](../../../03-数据与中间件/中间件/消息队列/RocketMQ.md)。

## 四、分库分表：按什么维度分、分片键怎么选？

**本节要点**：订单量来自"每次秒杀都落一批订单"，所以订单表**必须能水平切**。难点不在"分几片"，而在**分片键一选定，跨片查询的形态就写死了**。

### 4.1 按什么维度分

| 维度 | 分片键 | 好处 | 代价 |
|---|---|---|---|
| 用户 | `user_id` | ⭐ "我的订单"单分片命中，用户维度天然均衡 | "商家查订单"要跨片 |
| 商家 | `merchant_id` | 商家后台单分片命中 | "我的订单"要跨片（一个用户会买多个商家） |
| 时间 | `created_at`（按月 / 按日） | 冷热分离、归档简单 | 老数据要跨表，热点月份单表压力大 |

⭐ 订单链路的常用答案是**按 `user_id` 分**：C 端访问最密集的查询是"我的订单"，商家侧查询低频，可以走**异构索引 / 离线数仓**兜住。

### 4.2 分片键怎么选

- 要能**覆盖最常命中的查询条件**，否则每次查询都要广播到所有分片；
- 要**足够离散**（`user_id` 比 `merchant_id` 离散，避免大商家把单分片打热）；
- 要**不可变**（分片键一旦定下就不能改，改等于数据重分布）。

### 4.3 跨片查询与路由

| 查询 | 有分片键 | 路由方式 |
|---|---|---|
| 按 `user_id` 查 | ✅ | 直接 `hash(user_id) % N`，单分片命中 |
| 按 `order_no` 查 | ❌ | ⭐ 需要**基因法 / 二次索引**：把 `user_id` 的基因编进 `order_no`，从订单号反解分片 |
| 分页 / 聚合统计 | ❌ | 各分片各查一段，再**内存归并**（代价随分片数线性增长） |

⭐ 路由中间件、双写迁移、扩容重分布等落地细节见 [分表与路由.md](../../../03-数据与中间件/数据存储/关系型/MySQL/分表与路由.md)。⚠️ 本篇**未实测**任何分库分表中间件，上表的维度与判据是设计口径，不是本机读数。

## 五、超时关单：延迟消息还是定时扫表？

**本节要点**：用户抢到库存却 30 分钟不付款，必须把库存放回去。两条路——**延迟消息**（到点投一条）与**定时扫表**（周期扫过期单）。难点在扫表的成本，以及**归还库存前必须再查一次状态**。

### 5.1 两条路

| 方案 | 触发方式 | 优点 | 代价 |
|---|---|---|---|
| 延迟消息 | 下单时投一条 30 分钟延迟消息，到点检查 | ⭐ 精确、无全表扫开销 | 依赖 MQ 延迟能力；消息可能丢，**仍要扫表兜底** |
| 定时扫表 | 每 N 秒扫一次"待支付且已超时" | 实现简单、不依赖 MQ | ⭐ 成本在"多久扫一次、每次扫多少" |

### 5.2 扫表的成本：一条索引的差距

订单表 20 万行，其中 1 万行是"待支付且已超过 30 分钟"：

```text
=== ① 无索引 ===
  命中 10000 行，实际耗时 153ms
  执行计划（EXPLAIN ANALYZE）：
    -> Aggregate: count(0)  (cost=19485 rows=1) (actual time=184..184 rows=1 loops=1)
        -> Filter: ((orders_t.`status` = 'PENDING_PAY') and (orders_t.created_at < <cache>((now(3) - interval 30 minute))))  (cost=18818 rows=6672) (actual time=0.519..183 rows=10000 loops=1)
            -> Table scan on orders_t  (cost=18818 rows=200166) (actual time=0.504..117 rows=200000 loops=1)

=== ② 加联合索引 (status, created_at) ===
  命中 10000 行，实际耗时 16ms
  执行计划（EXPLAIN ANALYZE）：
        -> Filter: ((orders_t.`status` = 'PENDING_PAY') and (orders_t.created_at < <cache>((now(3) - interval 30 minute))))  (cost=3986 rows=18992) (actual time=1.39..21.9 rows=10000 loops=1)
            -> Covering index range scan on orders_t using idx_st over (status = 'PENDING_PAY' AND created_at < '2026-10-03 09:42:21.869')  (cost=3986 rows=18992) (actual time=1.37..14 rows=10000 loops=1)

=== ③ 对照：不做全表扫，而是按主键分片小批量扫（每次 1000 行）===
  分 10 批扫完，命中 9999 行，总耗时 75ms
```

⭐ 三条读法：

1. **无索引 = `Table scan` 20 万行 153ms** —— 开销随订单表线性上涨，而且每次扫都占 IO；
2. **联合索引 `(status, created_at)` = 覆盖索引 1.9 万行 16ms**（约 10 倍）—— 因为索引本身有序，`status = ? AND created_at < ?` 直接落进区间，不必回表；
3. **分片小批量（按主键每批 1000 行）75ms** —— 比全表扫快，但**比覆盖索引慢**：它是为了**避免一次锁太多行、事务太长**，用"多批"换"单批时长"。批大小与间隔，就是"多久扫一次、每次扫多少"的旋钮。

### 5.3 归还库存前必须再查一次状态

扫到的"待支付"订单，在你处理它的这一瞬间**可能刚好支付成功**。若直接归还库存，就会出现「钱收了、库存也放回去了」→ **超卖**。

```go
// 归还库存必须带条件：只有"这次确实是我把它改成已取消的"，才归还
res, err := db.ExecContext(ctx, `
    UPDATE orders SET status = 'CANCELED', canceled_at = NOW(3)
    WHERE id = ? AND status = 'PENDING_PAY'`, orderID)
if err != nil {
    return err
}
if n, _ := res.RowsAffected(); n == 0 {
    // 状态已被改过（多半是刚支付成功）→ 什么都不做
    return nil
}
// 只有上面的 UPDATE 真的改到了行，才归还库存
return restock(ctx, skuID)
```

⭐ **顺序很重要**：先带条件改状态（拿到"这次是我改的"的证据），**再**归还库存。反过来先还库存、后改状态，中间那一瞬间就是超卖窗口。

### 5.4 判据

| 问题 | 判据 |
|---|---|
| 用延迟消息还是扫表？ | 优先延迟消息；**扫表必须保留**（消息会丢），但只做兜底 |
| 每次扫多少？ | 覆盖索引 + 小批量；⚠️ 单批别太大（避免长事务与长持锁） |
| 何时归还库存？ | ⭐ 带条件 UPDATE 改状态**成功之后**才还，`RowsAffected=0` 就跳过 |

## 使用：订单链路的 Go 骨架

**本节要点**：把前面五节压成三段能读的代码 —— **状态机转移校验**、**幂等落库**、**超时关单扫描**。

> ⚠️ 三段都是骨架片段（为可读性省略了 import、类型定义与多层错误包装）。其中**带条件的 UPDATE**与
> **超时扫描的顺序**取自本机实测程序（读数见 1.2、2.1、5.2）；幂等键的选取与合法转移表是按语义补全的示意。

### 第一段：状态机转移校验

```go
// 合法转移表：只允许表里出现的 (from, to)
var allowed = map[string][]string{
	"PENDING_PAY": {"PAID", "CANCELED"},
	"PAID":        {"SHIPPED", "REFUNDING"},
	"SHIPPED":     {"COMPLETED"},
	"REFUNDING":   {"REFUNDED"},
}

func canTransfer(from, to string) bool {
	for _, s := range allowed[from] {
		if s == to {
			return true
		}
	}
	return false
}

// Transfer 用一条带条件的 UPDATE 完成转移：
// 表里判合法 + SQL 里判旧状态，二者缺一不可 ——
// 表防的是"非法转移"，WHERE 防的是"并发下被覆盖"。
func Transfer(ctx context.Context, db *sql.DB, orderID int64, from, to string) (bool, error) {
	if !canTransfer(from, to) {
		return false, ErrIllegalTransfer
	}
	res, err := db.ExecContext(ctx,
		`UPDATE orders SET status = ? WHERE id = ? AND status = ?`, to, orderID, from)
	if err != nil {
		return false, err
	}
	n, _ := res.RowsAffected()
	return n == 1, nil // false = 别人已经改过，本次是空操作
}
```

### 第二段：幂等落库（唯一索引 + INSERT IGNORE）

```go
// 幂等落库：靠唯一索引 uk_order_no，而不是"先查后插"。
// 本机实测：先查后插并发重放 2000 次落库 87 条；INSERT IGNORE 恰好 1 条。
func CreateOrderIdempotent(ctx context.Context, db *sql.DB, o Order) (bool, error) {
	res, err := db.ExecContext(ctx, `
		INSERT IGNORE INTO seckill_order
			(order_no, user_id, sku_id, status, created_at)
		VALUES (?, ?, ?, 'PENDING_PAY', NOW(3))`,
		o.OrderNo, o.UserID, o.SKU)
	if err != nil {
		return false, err
	}
	if n, _ := res.RowsAffected(); n == 0 {
		return false, nil // 重复提交：已存在，绝不能重复扣库存或发消息
	}
	return true, nil
}
```

### 第三段：超时关单扫描（带条件改状态 + 归还库存）

```go
// CloseExpiredOrders 按主键小批量扫"待支付且已超时"的订单，
// 每条都走上一条 5.3 的"先带条件改状态、成功才归还库存"。
func CloseExpiredOrders(ctx context.Context, db *sql.DB, timeout time.Duration) (int, error) {
	deadline := time.Now().Add(-timeout)
	rows, err := db.QueryContext(ctx, `
		SELECT id, sku_id FROM orders
		WHERE status = 'PENDING_PAY' AND created_at < ?
		ORDER BY id LIMIT 1000`, deadline) // 走索引 (status, created_at)；单批 1000 行
	if err != nil {
		return 0, err
	}
	type pending struct {
		id    int64
		skuID int64
	}
	var list []pending
	for rows.Next() {
		var p pending
		if err := rows.Scan(&p.id, &p.skuID); err != nil {
			rows.Close()
			return 0, err
		}
		list = append(list, p)
	}
	rows.Close()

	closed := 0
	for _, p := range list {
		res, err := db.ExecContext(ctx, `
			UPDATE orders SET status = 'CANCELED', canceled_at = NOW(3)
			WHERE id = ? AND status = 'PENDING_PAY'`, p.id)
		if err != nil {
			return closed, err
		}
		// ⭐ RowsAffected() == 0：这一瞬间订单可能刚好支付成功 → 直接跳过
		if n, _ := res.RowsAffected(); n == 0 {
			continue
		}
		if err := restock(ctx, p.skuID); err != nil {
			return closed, err
		}
		closed++
	}
	return closed, nil
}
```

⭐ 三段的顺序就是订单链路的顺序：**状态机管"能改什么"（第 1 节）→ 幂等管"只改一次"（第 2 节）→ 扫表管"没付款的收回来"（第 5 节）**，每一段都能在前面找到对应的实测读数。

## 延伸追问

- **为什么不直接在应用层判断状态？** → 应用层"先查再改"的两次往返之间就是竞态窗口（1.2 的 1/1 → 0/1 就是证据）；必须把旧状态下推进 WHERE，让数据库用行锁来判。
- **幂等键用 `request_id` 还是 `order_no`？** → 二者管的层级不同：`request_id` 管"同一次请求被重放"，`order_no` 管"同一次业务被重复落库"（2.3）；秒杀还要加 `(user_id, sku_id)` 兜"一人一单"。
- **分布式事务一定要 TCC 吗？** → 不一定。订单链路的主流是**本地消息表 + 幂等消费**（3.2）；只有"必须预留资源"才上 TCC，完整对照见 [分布式事务.md](../../分布式/理论/分布式事务.md)。
- **订单表按 `user_id` 分了，商家侧怎么查？** → 走**异构索引 / 离线数仓**（4.1），别指望在主表上同时满足"我的订单"和"商家订单"两类查询。
- **扫表为什么不用 `status` 单列索引？** → 单列索引能命中，但范围条件仍要回表；联合索引 `(status, created_at)` 让范围也一起走索引，本机 16ms vs 153ms（5.2）就是这层差别。
- **延迟消息和扫表能不能只留一个？** → 不能只留延迟消息：消息可能丢、可能积压，**扫表是必须存在的兜底**（5.4）。
